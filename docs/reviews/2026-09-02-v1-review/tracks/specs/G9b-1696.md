No experiment script under `docs/reviews/2026-09-02-v1-review/experiments/` cites #1696, so the PR body must say the probe was in-process.

**Files touched:** `src/server/mcp/tutorial-annotations.ts`, `src/server/documents/open.ts` (the call site and its comment), `tests/server/tutorial-annotations.test.ts`, `tests/server/adr-034-open-characterization.test.ts`, and the single call in `tests/server/annotation-create-lifecycle.test.ts`, which only gains the new argument.

## Problem

**Reproduced on `a6e7352f`**, in-process through the production functions (`openFromDisk`, `removeAnnotationRecord(doc, id, "browser")`, `closeStore`, `closeDocumentById`) against a temp `…/sample/welcome.md`:

1. The first open injects the four seeds.
2. Deleting `tutorial-comment-1` writes the envelope tombstone `{id: "tutorial-comment-1", rev: 2}`.
3. After a close and a reopen, `tutorial-comment-1` is back.

The cause is ordering. In `openFromDisk`, `finalizeDocOpen` → `wireAnnotationStore` → `loadAndMerge` applies the tombstone ledger first. Only then does `injectTutorialAnnotations(doc)` run, and its guard, `if (map.has(def.id)) continue`, sees an id the merge just removed.

The issue body says the re-minted copy never reaches disk. **That is false (measured).** The seed write is `withInternal` (`DURABLE_SKIP`), but `snapshot()` serializes the whole map, so the next unrelated durable write persists the re-minted seed.

## Fix

- **`src/server/mcp/tutorial-annotations.ts`:**
  - The signature becomes `injectTutorialAnnotations(doc: Y.Doc, filePath: string)`. The parameter is required, so a call site that forgets it fails to compile instead of silently re-injecting.
  - Before the loop: `const deleted = new Set(getTombstones(docHash(filePath)).map((t) => t.id))`.
  - The guard becomes `if (map.has(def.id) || deleted.has(def.id)) continue`.
  - Imports: `getTombstones` from `../annotations/sync.js` and `docHash` from `../annotations/doc-hash.js`.
  - Add one docblock sentence: the check relies on bulk clears running with the observer detached, since the observer tombstones deletes from every origin.
- **`src/server/annotations/sync.ts`, docblock only (orchestrator, after the review loop):** `getTombstones`' docblock says "Read-only accessor for tests and (future) diagnostic tools". After this fix `injectTutorialAnnotations` is a production reader, so name it there. No code in `sync.ts` changes.
- **`src/server/documents/open.ts`:**
  - The call becomes `injectTutorialAnnotations(doc, resolved)`, and it stays AFTER `finalizeDocOpen`, which is what seeds the ledger.
  - Replace the "idempotent, safe to call on session-restored docs" comment with one line naming the tombstone check.
  - `wireAnnotationStore` keys the ledger by `docHash(resolved)`, the same key.
- The seed write stays `withInternal` (Critical Rule 2).

## Not in scope

- **Tombstone compaction, filed as #2009.** `cleanupStaleTombstones` (`src/server/session/manager.ts`) drops tombstones older than `SESSION_MAX_AGE` (30 days). It runs at boot before `restoreOpenDocuments` (`src/server/index.ts`), so its open-doc guard set is empty and `welcome.md` is not protected. Losing a tombstone does no harm for a random id, because nothing re-creates that id. It does harm for the tutorial's fixed ids: the next open re-injects the seed, and the next durable write saves it again. This guard therefore does not close #1696.
- Undo-of-delete merge semantics.
- Word `import-` ids. They are content hashes (`src/server/file-io/docx-comments.ts`), so the merge's tombstone veto covers them only for the same 30 days. This is named in #2009 and not reproduced.

## bryan

- **User-visible consequence, no code change.** If a user deletes all four seeds, the welcome tutorial now holds at step 0 across reopens. `useTutorial.svelte.ts` returns early when there are no tutorial annotations. Its dismiss control is the exit.
- **PR review round 1: Settings > Replay tutorial restores the seeds.** The guard first swallowed Replay too, because Replay's only working re-seed was the ordinary reopen the guard suppresses. `force: true` on welcome.md now replays past the tombstones, in both the normal-open and force-reload branches of `openFromDisk`. The replayed seed is minted at a rev above its tombstone and stays `withInternal`, so the tombstone survives and a later ordinary reopen still honours the deletion.
