## Problem

**Reproduced on `a6e7352f`**, in-process through the production functions (`openFromDisk`, `removeAnnotationRecord(doc, id, "browser")`, `closeStore`, `closeDocumentById`) against a temp `…/sample/welcome.md`:

1. The first open injects the four seeds.
2. Deleting `tutorial-comment-1` writes the envelope tombstone `{id: "tutorial-comment-1", rev: 2}`.
3. After a close and a reopen, `tutorial-comment-1` is back.

The cause is ordering. In `openFromDisk`, `finalizeDocOpen` → `wireAnnotationStore` → `loadAndMerge` applies the tombstone ledger first. Only then does `injectTutorialAnnotations(doc)` run, and its guard, `if (map.has(def.id)) continue`, sees an id the merge just removed.

The issue body says the re-minted copy never reaches disk. **That is false (measured).** The seed write is `withInternal` (`DURABLE_SKIP`), but `snapshot()` serializes the whole map, so the next unrelated durable write persists the re-minted seed.

## Fix

- **`src/server/mcp/tutorial-annotations.ts`:**
  - The signature becomes `injectTutorialAnnotations(doc: Y.Doc, filePath: string)`. The parameter is required, so a call site that forgets it fails to compile instead of silently re-injecting.
  - Before the loop: `const deleted = new Set(getTombstones(docHash(filePath)).map((t) => t.id))`.
  - The guard becomes `if (map.has(def.id) || deleted.has(def.id)) continue`.
  - Imports: `getTombstones` from `../annotations/sync.js` and `docHash` from `../annotations/doc-hash.js`.
  - Add one docblock sentence: the check relies on bulk clears running with the observer detached, since the observer tombstones deletes from every origin.
- **`src/server/documents/open.ts`:**
  - The call becomes `injectTutorialAnnotations(doc, resolved)`, and it stays AFTER `finalizeDocOpen`, which is what seeds the ledger.
  - Replace the "idempotent, safe to call on session-restored docs" comment with one line naming the tombstone check.
  - `wireAnnotationStore` keys the ledger by `docHash(resolved)`, the same key.
- The seed write stays `withInternal` (Critical Rule 2).
