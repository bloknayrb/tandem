# E1 — #1761 No round-trip test or `store_status()` check for the desktop keychain

Branch `fix/desktop-core-1761`. Closes #1761 (its re-scoped items 1 and 2; item 3 is two smoke lines, Bryan's). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/tauri.md:15` (stale — still describes keyring 3). Probe: `cargo test -p tandem` plus `tests/client/keychain-backend.test.ts`.

## Problem

**The original diagnosis is refuted by measurement and must not be re-planned.** `src-tauri/Cargo.toml:47` reads `keyring = "4"`, resolving to 4.2.0 (`src-tauri/Cargo.lock:3275-3284`). keyring 4.2.0's `default = ["v1"]` and `v1` *is* the three platform stores; `Entry::new` runs a `LazyLock`ed `set_credential_store()` internally (`v1.rs:47-53,108-128`) and returns `Error::NoDefaultStore` on an unsupported platform. There is no mock to fall through to. So "`set_password` returns Ok and the file fallback is never written", "every `get_or_create_token()` mints a fresh token" and "root cause of #1455" are all false. This arrived via Dependabot `c991b816`. **Do not close #1455 or treat it as resolved** — it is a dated-gate item (2026-10-15) needing its own re-check.

What is genuinely open:

1. **No round-trip test anywhere.** "keyring 4 selects a real store" is established from crate source; "a secret written by one `Entry` is readable by a second" is not.
2. **`Entry::store_status()` is never called**, and `token_store.rs:74` is worse than the issue says. `let entry = Entry::new(SERVICE, ENTRY_NAME).map_err(…)?;` **propagates**, so with no store `get_or_create_token()` returns `Err` and steps 2 and 3 (read file / generate + `write_to_file`) are never reached. The desktop starts token-less (`sidecar.rs:1482-1488`) and no token file is ever written. `keychain.rs:54-62` has the same `Entry::new` shape — correct there (no fallback exists), but its message says nothing about the store.
3. **The same bump silently broke the client-side classifier.** `src/client/keychain/keychain-backend.ts:99-111` pins `KEYRING_UNAVAILABLE_MARKERS` to keyring v3.6.3's `Display` impl. keyring 4.2.0's `v1` re-exports `keyring_core::Error`, whose strings are `"Platform failure: {err}"` (`keyring-core-1.0.0/src/error.rs:81`) and `"Couldn't access platform storage: {err}"` (`:83`). `keychain.rs:60`/`:78` format those into `keychain-get:`/`keychain-set:`, so on those paths an unavailable store is now classified `error` rather than `unavailable`. `"keychain-init"` still fires, which is why nothing went red.

## Fix

- **`src-tauri/src/token_store.rs`, `get_or_create_token`**: replace the `?` with a fall-through. `let entry = Entry::new(SERVICE, ENTRY_NAME);` then:
  - `Ok(entry)` → today's three-step body unchanged.
  - `Err(e)` → `eprintln!` once naming both `e` **and** `Entry::store_status()`'s error (that is the field saying *why* the store is unavailable), then skip step 1, continue at step 2 (`read_from_file()`), and at step 3 call `write_to_file(&token)` unconditionally instead of `if entry.set_password(...).is_err()`. The keyring-absent arm must never touch `entry`; do not introduce an `Option<Entry>` the happy path unwraps. The docblock's "Priority: 1 keyring / 2 file / 3 generate" becomes true for the first time.
  - `eprintln!`, not `log::`, matching `:83`.
  - **Signature note:** `Entry::store_status()` returns `&'static Result<()>` (`keyring-4.2.0/src/v1.rs:67`), so `Err(s)` binds a `&keyring_core::Error`. `format!` takes it as-is; do not reach for `?`.
- **`src-tauri/src/keychain.rs`, `make_entry`**: keep the `keychain-init:` prefix byte-identical (the client keys on the four prefixes) and append the store reason: on `Entry::new` error, if `Entry::store_status()` is `Err(s)`, return `format!("keychain-init: credential store unavailable: {s}")`, else today's `format!("keychain-init: {e}")`. No signature or contract change.
- **`src/client/keychain/keychain-backend.ts`, `KEYRING_UNAVAILABLE_MARKERS` (`:99-111`)**: replace the two dead v3.6.3 substrings with `"Platform failure:"` and `"Couldn't access platform storage:"`, and update both pinning comments (`:100` and the duplicate at `:142`) to name **keyring-core 1.0.0 `src/error.rs:81,83`**. Keep `"keychain-init"` first. Match on the trailing colon, not the whole sentence — both variants interpolate `{err}` after it.
- **No `Cargo.toml` change.** `keyring = "4"` already pulls the platform stores by default.
- Rules that bite: no Y.Doc, Y.Map key, testid or `/api` route here, so Critical Rules 1–2 and 7–9 are inert. Export `CARGO_TARGET_DIR` for every cargo run.

## Tests

New `#[cfg(test)] mod tests` at the foot of `src-tauri/src/token_store.rs` (it has none today):

1. `keyring_round_trips_across_entry_instances` — a unique service+account (`"tandem-roundtrip-test"` + pid + nanos, so it can never collide with the real `tandem`/`auth-token` entry): `Entry::new(...).set_password(v)`, **drop that entry**, construct a *second* `Entry` with the same pair, assert `get_password() == v`, then `delete_credential()`. **What it kills:** any per-`Entry` in-memory backend — the exact failure the original #1761 described — which returns `NoEntry` on the second handle. A single-`Entry` set-then-get passes against a mock and is the wrong test.
   - **Gate, two arms.** On `windows`/`macos`: assert `Entry::store_status().is_ok()` **first**, so the two legs where the store must exist cannot silently skip (the #1529 shape) — this assertion is also the `store_status()` half of the issue's item 2. Then, if `set_password` returns an `Err` whose `Display` contains **`"Couldn't access platform storage:"` only**, `eprintln!` a named line and return: a locked or headless login keychain on `macos-latest` is a runner fact and `store_status()` cannot detect it (`v1.rs:110-124` reflects `Store::new()` only). **`PlatformFailure` must NOT be in the skip set** — `keyring-core-1.0.0/src/error.rs:27-30` documents it as a general runtime failure, the variant a genuinely broken store also takes. Any other error fails the test. On other targets: `if Entry::store_status().is_err() { return; }` — ubuntu-latest has no Secret Service; this is a capability gate, not a quarantine.
   - **Cleanup must survive a failed assertion** (scope guard, or read into a local, delete, then `assert_eq!`), so a red run leaves nothing in the operator's Credential Manager or login keychain.
2. `tests/client/keychain-backend.test.ts` — **the two existing v3.6.3 cases at `:93-117` are REWRITTEN, not added to.** They assert `"keychain-set: Platform secure storage failure: …"` and `"keychain-set: Couldn't access platform secure storage: locked"` classify as `unavailable`; those strings no longer exist, so leaving them passing lets the laziest fix (append two markers, keep the dead two) satisfy every named test. Replace their inputs and pinning comments with real keyring-4 messages: `"keychain-get: Couldn't access platform storage: the keychain is locked"` and `"keychain-set: Platform failure: dbus not reachable"`. Keep the existing `keychain-init` case and at least one `status: "error"` case, so the change does not widen into "any error is unavailable".
3. `falls_back_to_file_when_the_keyring_is_unavailable` is **deliberately not written**: `Entry::new`'s failure is a process-global `LazyLock` with no injection seam, so the only honest test would mock the crate. Say so in the PR body rather than shipping a test that asserts a mock.

## Done when

Test 1 is in `cargo test` and passes on the **windows** leg (its macOS outcome is pass-or-named-skip — record a skip in the PR body rather than removing the test or widening the gate); the client classifier tests pass with the two dead v3.6.3 strings gone from both the constant and the tests; `get_or_create_token` reaches `write_to_file` when the store is unavailable; `keychain-init` names the store reason; both pinning comments name keyring-core 1.0; the PR body states that the mock-fallthrough premise is dead and that #1455 is untouched.
