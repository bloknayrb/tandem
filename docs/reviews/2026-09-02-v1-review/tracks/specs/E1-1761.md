# E1 — #1761 No round-trip test or `store_status()` check for the desktop keychain

Branch `fix/desktop-core-1761`. Closes #1761 (its re-scoped items 1 and 2; item 3 is two smoke lines, which are Bryan's). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/tauri.md:15` (stale — it still describes keyring 3). Probe: `cargo test -p tandem` (the two new tests below) plus `tests/client/keychain-backend.test.ts`; no experiment exists for this track.

## Problem

**The original diagnosis is dead and must not be re-planned.** `src-tauri/Cargo.toml:47` reads `keyring = "4"`, resolving to 4.2.0 (`src-tauri/Cargo.lock:3275-3284`, deps `apple-native-keyring-store` / `windows-native-keyring-store` / `zbus-secret-service-keyring-store`). keyring 4.2.0's `default = ["v1"]` and `v1` *is* those three stores; `Entry::new` runs a `LazyLock`ed `set_credential_store()` internally (`v1.rs:47-53,108-128`) and returns `Error::NoDefaultStore` on an unsupported platform. There is no mock to fall through to. So "`set_password` returns Ok and the file fallback is never written", "every `get_or_create_token()` mints a fresh token" and "root cause of #1455" are all false. This arrived via Dependabot `c991b816`, not as a fix. **Do not close #1455 or treat it as resolved** — it is a dated-gate item (2026-10-15) needing its own re-check.

What is genuinely open, and one thing the issue's own comment got wrong:

1. **No round-trip test anywhere.** "keyring 4 selects a real store" is established from crate source; "a secret written by one `Entry` is readable by a second" is not.
2. **`Entry::store_status()` is never called**, and `token_store.rs:74` is worse than the issue says. It reads `let entry = Entry::new(SERVICE, ENTRY_NAME).map_err(|e| format!("keyring init: {e}"))?;` — the `?` **propagates**, so on a Linux box with no Secret Service `get_or_create_token()` returns `Err` and steps 2 and 3 (read file / generate + `write_to_file`) are **never reached**. The comment on #1761 says this "silently takes the file fallback — correct behaviour, no diagnostic". It does not. The desktop starts token-less (`sidecar.rs:1482-1488` logs and passes `None`) and no token file is ever written. `keychain.rs:54-62` (provider API keys) has the same `Entry::new` shape with no fallback at all, which there is correct — but its error message says nothing about the store.
3. **The same Dependabot bump silently broke the client-side classifier** (found in review round 1). `src/client/keychain/keychain-backend.ts:99-111` pins `KEYRING_UNAVAILABLE_MARKERS` to **keyring v3.6.3**'s `Display` impl, with two markers that no longer exist: `"Platform secure storage failure"` and `"Couldn't access platform secure storage"`. keyring 4.2.0's `v1` feature re-exports `keyring_core::Error`, whose actual strings are `"Platform failure: {err}"` (`keyring-core-1.0.0/src/error.rs:81`) and `"Couldn't access platform storage: {err}"` (`:83`). `keychain.rs:60` / `:78` format those verbatim into `keychain-get: {e}` / `keychain-set: {e}`, so on the get/set paths a genuinely unavailable store is now classified `error` instead of `unavailable`. The `"keychain-init"` marker still fires, which is why only the get/set paths are affected — and why nothing went red.

## Fix

- **`src-tauri/src/token_store.rs`, `get_or_create_token`**: replace the `?` with a fall-through. Build `let entry = Entry::new(SERVICE, ENTRY_NAME);` and match:
  - `Ok(entry)` → today's three-step body unchanged.
  - `Err(e)` → `eprintln!` once naming both `e` **and** `Entry::store_status()`'s error (that is the field that says *why* the store is unavailable rather than *that* an entry failed), then skip step 1 and continue at step 2 (`read_from_file()`), and at step 3 call `write_to_file(&token)` unconditionally instead of `if entry.set_password(...).is_err()`. Structure it so the keyring-absent arm never touches `entry`; do not introduce an `Option<Entry>` that the happy path has to unwrap. The docblock's "Priority: 1 keyring / 2 file / 3 generate" becomes true for the first time.
  - `eprintln!`, not `log::`, matching the existing line at `:83` — this module already prints to stderr and stdout is not in play in the shell.
  - **Signature note:** `Entry::store_status()` returns `&'static Result<()>` (`keyring-4.2.0/src/v1.rs:67`), so the `Err(s)` binding is a `&keyring_core::Error`. `format!` takes it as-is; do not reach for `?` or try to move out of it.
- **`src-tauri/src/keychain.rs`, `make_entry`**: keep the `keychain-init:` prefix byte-identical (the client keys on the four prefixes, see the module docblock) and append the store reason: on `Entry::new` error, if `Entry::store_status()` is `Err(s)`, return `format!("keychain-init: credential store unavailable: {s}")`, else today's `format!("keychain-init: {e}")`. No signature, no contract, no client change.
- **`src/client/keychain/keychain-backend.ts`, `KEYRING_UNAVAILABLE_MARKERS` (`:99-111`)**: replace the two dead v3.6.3 substrings with keyring-core 1.0's — `"Platform failure:"` and `"Couldn't access platform storage:"` — and update **both** pinning comments (`:100` and the duplicate at `:142`) to name **keyring-core 1.0.0 `src/error.rs:81,83`** rather than keyring v3.6.3 `error.rs:64-67`. Keep `"keychain-init"` first in the list; it is the only marker that survived the bump and it is what kept `make_entry` failures classified correctly. Match on the trailing colon, not the whole sentence: both variants interpolate `{err}` after it, so the colon is the stable boundary.
- **No `Cargo.toml` change.** `keyring = "4"` already pulls the platform stores by default; adding explicit features would be a no-op that reads as the (dead) original fix.
- Rule that bites: nothing in this issue touches a Y.Doc, a Y.Map key, a testid or an `/api` route, so Critical Rules 1–2 and 7–9 are inert here. `CARGO_TARGET_DIR` must be exported for every cargo run.

## Tests

New `#[cfg(test)] mod tests` at the foot of `src-tauri/src/token_store.rs` (the module has none today):

1. `keyring_round_trips_across_entry_instances` — a unique service+account (`"tandem-roundtrip-test"` + pid + nanos so it can never collide with the real `tandem`/`auth-token` entry), `Entry::new(...).set_password(v)`, **drop that entry**, construct a *second* `Entry` with the same pair, assert `get_password() == v`, then `delete_credential()`. **What it kills:** any per-`Entry` in-memory backend — the exact failure the original #1761 described — which returns `NoEntry` on the second handle. A single-`Entry` set-then-get would pass against a mock and is the wrong test.
   - **Gating, revised in round 1 so a locked CI keychain cannot turn a required leg red.** Two arms, not one bare early return:
     - `#[cfg(any(target_os = "windows", target_os = "macos"))]`: assert `Entry::store_status().is_ok()` **before** anything else, so the two legs where the store must exist cannot silently skip (the #1529 shape). Then, if `set_password` returns `Err` whose `Display` names an access/authorization denial — **the `NoStorageAccess` spelling only, i.e. `"Couldn't access platform storage:"`** — `eprintln!` a named line and return; a locked or headless login keychain on `macos-latest` is a *runner* fact, not a regression, and `store_status()` cannot detect it (`v1.rs:110-124`: it reflects `Store::new()` only). **`PlatformFailure` must NOT be in the skip set, and this is the narrowing round 2 asked for.** `keyring-core-1.0.0/src/error.rs:27-30` documents it as "runtime failure in the underlying platform storage system" generally — the variant a genuinely broken store also takes — while only `NoStorageAccess` (`:32-35`) means locked / access rules. Skipping on it would make the macOS arm report pass-or-skip for almost any real breakage. Any other `set_password` error, `PlatformFailure` included, fails the test.
     - `#[cfg(not(any(...)))]`: `if Entry::store_status().is_err() { return; }` — ubuntu-latest has no Secret Service and this is a capability gate, not a quarantine.
   - **Cleanup must survive a failed assertion.** Wrap the assert so `delete_credential()` runs either way (a scope guard, or capture the read into a local, delete, then `assert_eq!`). A red run must not leave an entry in the operator's Credential Manager or login keychain.
2. `credential_store_initialises_on_desktop_platforms` — `#[cfg(any(target_os = "windows", target_os = "macos"))]`, asserts `Entry::store_status().is_ok()`. **What it kills:** a future `default-features = false`, or a features edit that drops the platform store, on the two `rust-test` legs where the answer is knowable. Do **not** write it for Linux — ubuntu-latest has no Secret Service and it would be a false red.
3. `tests/client/keychain-backend.test.ts` — **the two existing v3.6.3 cases at `:93-117` are REWRITTEN, not added to.** They currently assert `"keychain-set: Platform secure storage failure: …"` and `"keychain-set: Couldn't access platform secure storage: locked"` classify as `unavailable`; those strings no longer exist, so leaving them passing is what lets the laziest fix — append the two new markers, leave the two dead ones in place — satisfy every named test. Replace their inputs (and their pinning comments) with **real keyring-4 messages**: `"keychain-get: Couldn't access platform storage: the keychain is locked"` and `"keychain-set: Platform failure: dbus not reachable"`. The existing `keychain-init` case stays. Keep at least one `status: "error"` case so the change does not widen into "any error is unavailable".
   - **Plus one structural assertion, in the same file:** `KEYRING_UNAVAILABLE_MARKERS` has **exactly three** entries and contains neither `"Platform secure storage failure"` nor `"Couldn't access platform secure storage"`. **What the pair kills:** a list that grows to five, under which the dead strings survive as permanent noise and the next reader cannot tell which crate version the classifier is actually pinned to. Export the constant if it is not already reachable from the test.
4. `falls_back_to_file_when_the_keyring_is_unavailable` is **deliberately not written**: `Entry::new`'s failure is a process-global `LazyLock` with no injection seam, so the only honest test would mock the crate. The fall-through is covered by reading the diff; say so in the PR body rather than shipping a test that asserts a mock.
