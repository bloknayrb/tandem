# E1 — #1761 No round-trip test or `store_status()` check for the desktop keychain

Branch `fix/desktop-core-1761`. Closes #1761 (its re-scoped items 1 and 2; item 3 is two smoke lines, which are Bryan's). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/tauri.md:15` (stale — it still describes keyring 3). Probe: `cargo test -p tandem` (the two new tests below); no experiment exists for this track.

## Problem

**The original diagnosis is dead and must not be re-planned.** `src-tauri/Cargo.toml:47` reads `keyring = "4"`, resolving to 4.2.0 (`src-tauri/Cargo.lock:3275-3284`, deps `apple-native-keyring-store` / `windows-native-keyring-store` / `zbus-secret-service-keyring-store`). keyring 4.2.0's `default = ["v1"]` and `v1` *is* those three stores; `Entry::new` runs a `LazyLock`ed `set_credential_store()` internally (`v1.rs:47-53,108-128`) and returns `Error::NoDefaultStore` on an unsupported platform. There is no mock to fall through to. So "`set_password` returns Ok and the file fallback is never written", "every `get_or_create_token()` mints a fresh token" and "root cause of #1455" are all false. This arrived via Dependabot `c991b816`, not as a fix. **Do not close #1455 or treat it as resolved** — it is a dated-gate item (2026-10-15) needing its own re-check.

What is genuinely open, and one thing the issue's own comment got wrong:

1. **No round-trip test anywhere.** "keyring 4 selects a real store" is established from crate source; "a secret written by one `Entry` is readable by a second" is not.
2. **`Entry::store_status()` is never called**, and `token_store.rs:74` is worse than the issue says. It reads `let entry = Entry::new(SERVICE, ENTRY_NAME).map_err(|e| format!("keyring init: {e}"))?;` — the `?` **propagates**, so on a Linux box with no Secret Service `get_or_create_token()` returns `Err` and steps 2 and 3 (read file / generate + `write_to_file`) are **never reached**. The comment on #1761 says this "silently takes the file fallback — correct behaviour, no diagnostic". It does not. The desktop starts token-less (`sidecar.rs:1482-1488` logs and passes `None`) and no token file is ever written. `keychain.rs:54-62` (provider API keys) has the same `Entry::new` shape with no fallback at all, which there is correct — but its error message says nothing about the store.

## Fix

- **`src-tauri/src/token_store.rs`, `get_or_create_token`**: replace the `?` with a fall-through. Build `let entry = Entry::new(SERVICE, ENTRY_NAME);` and match:
  - `Ok(entry)` → today's three-step body unchanged.
  - `Err(e)` → `eprintln!` once naming both `e` **and** `Entry::store_status()`'s error (that is the field that says *why* the store is unavailable rather than *that* an entry failed), then skip step 1 and continue at step 2 (`read_from_file()`), and at step 3 call `write_to_file(&token)` unconditionally instead of `if entry.set_password(...).is_err()`. Structure it so the keyring-absent arm never touches `entry`; do not introduce an `Option<Entry>` that the happy path has to unwrap. The docblock's "Priority: 1 keyring / 2 file / 3 generate" becomes true for the first time.
  - `eprintln!`, not `log::`, matching the existing line at `:83` — this module already prints to stderr and stdout is not in play in the shell.
- **`src-tauri/src/keychain.rs`, `make_entry`**: keep the `keychain-init:` prefix byte-identical (the client keys on the four prefixes, see the module docblock) and append the store reason: on `Entry::new` error, if `Entry::store_status()` is `Err(s)`, return `format!("keychain-init: credential store unavailable: {s}")`, else today's `format!("keychain-init: {e}")`. No signature, no contract, no client change.
- **No `Cargo.toml` change.** `keyring = "4"` already pulls the platform stores by default; adding explicit features would be a no-op that reads as the (dead) original fix.
- Rule that bites: nothing in this issue touches a Y.Doc, a Y.Map key, a testid or an `/api` route, so Critical Rules 1–2 and 7–9 are inert here. `CARGO_TARGET_DIR` must be exported for every cargo run.

## Tests

New `#[cfg(test)] mod tests` at the foot of `src-tauri/src/token_store.rs` (the module has none today):

1. `keyring_round_trips_across_entry_instances` — `if Entry::store_status().is_err() { return; }` (a **capability** gate, not a quarantine: it can only fire on a runner with no credential store), then a unique service+account (`"tandem-roundtrip-test"` + pid + nanos so it can never collide with the real `tandem`/`auth-token` entry), `Entry::new(...).set_password(v)`, **drop that entry**, construct a *second* `Entry` with the same pair, assert `get_password() == v`, then `delete_credential()`. **What it kills:** any per-`Entry` in-memory backend — the exact failure the original #1761 described — which returns `NoEntry` on the second handle. A single-`Entry` set-then-get would pass against a mock and is the wrong test.
2. `credential_store_initialises_on_desktop_platforms` — `#[cfg(any(target_os = "windows", target_os = "macos"))]`, asserts `Entry::store_status().is_ok()`. **What it kills:** a future `default-features = false`, or a features edit that drops the platform store, on the two `rust-test` legs where the answer is knowable. This exists specifically so test 1's early return is not the #1529 trap: the gate is *satisfied* on the windows and macos legs, and this test fails loudly if it stops being. Do **not** write it for Linux — ubuntu-latest has no Secret Service and it would be a false red.
3. `falls_back_to_file_when_the_keyring_is_unavailable` is **deliberately not written**: `Entry::new`'s failure is a process-global `LazyLock` with no injection seam, so the only honest test would mock the crate. The fall-through is covered by reading the diff; say so in the PR body rather than shipping a test that asserts a mock.

## Done when

Both tests are in `cargo test`; test 1 passes (not skips) on the windows and macos legs; `get_or_create_token` reaches `write_to_file` when the store is unavailable; `keychain-init` names the store reason; the PR body states that the mock-fallthrough premise is dead and that #1455 is untouched.
