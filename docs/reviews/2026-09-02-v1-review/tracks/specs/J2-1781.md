# J2 — #1781 Browser/npm build has no way to open a disk file for editing; the user guide's "Path input" doesn't exist

Branch `fix/product-copy-1814`. Closes #1781. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:19`. Probe: none (read-verified against source).

## Problem

`docs/user-guide.md:138` promises: *"**Path input** — Click the **+** button in the tab bar, type an absolute file path, and click **Open**."* The **+** button (`data-testid="open-file-btn"`, `DocumentTabs.svelte:1309-1320`) opens `NewTabMenu.svelte`, whose only text input is a search box (`data-testid="new-tab-search"`, `NewTabMenu.svelte:120-127`) that filters the ALREADY-recent-files list via `searchRows`/fuzzy-match (`newTabLauncher.ts`) — typing a path that isn't already a recent entry produces "No matches", and there is no Enter-to-submit or "Open" affordance that treats the typed text as a raw path. `NewTabMenu`'s only other open route is "Browse files…" (`onBrowse`, `:196-206`), which in the non-Tauri build opens `FileOpenDialog.svelte`'s hidden `<input type="file">` — an `upload://` read-only, session-only open (`uploadFile`, `:137-166`), never a real disk path. So a first-run npm/browser user genuinely cannot open an arbitrary file on disk from the UI, matching the issue's "core loop… not reachable" impact.

## Fix

**Delete the promise rather than build the input** — reversed from the original draft of this spec during round-1 review. The wave-table note's own stated default is "prefer deleting the promise unless the input is trivially small," and the input turned out not to be trivially small: making it real without recreating this exact class of dead-end bug requires a new `data-testid` (snapshot regen), a runtime gate, a failure-surfacing path that does not exist today (see the round-1 findings below), a button-label decision, and two new test files plus an E2E case — that is the shape of a small feature, not a copy fix, for a group whose wave-1 lesson is "MINIMAL copy fixes in the named files, no new frameworks." Nothing in `NewTabMenu.svelte`, `DocumentTabs.svelte`, or `docs/user-guide.md` has been touched yet in this worktree (verified — `git diff` shows no changes to any of the three), so there is no in-progress build to preserve.

`docs/user-guide.md`'s "Opening Files" section (~L134-142) lists three ways to open a file; delete the **Path input** bullet (~L138) since no such affordance exists (`NewTabMenu.svelte`'s only text input is the recents-search box, `newTabLauncher.ts`'s `searchRows`, which never treats its query as a raw path), and renumber the intro from "three ways" to "two ways." While in this paragraph, also fix the neighboring **Upload** bullet's stale claim (~L142) that clicking **+** lets you "switch to **Upload** mode" — `NewTabMenu.svelte` has no mode switch; its only browse affordance is the **"Browse files…"** button (`data-testid="new-tab-browse"`, `:200`), which in the non-Tauri build opens `FileOpenDialog.svelte`'s hidden `<input type="file">` (an `upload://`, read-only, session-only open). Reword to describe that button by its real name rather than a nonexistent mode.

New "Opening Files" section:

```
There are two ways to open a file:

**Drag-and-drop** — Drag a file from your file manager onto the editor. A dashed border appears as a drop indicator.

**Browse or upload** — Click **+** in the tab bar, then **Browse files…**. On desktop this opens a native file picker for real (write-capable) editing. In the browser build it opens an upload dialog: uploaded files get a synthetic `upload://` path and are always read-only — `Save` preserves the session (annotations) but cannot write back to disk.
```

No `/api/open` change; no client or server behavior changes at all — this is a documentation-only fix.

`docs/user-guide.md`'s "Opening Files" section names only affordances that exist, with an accurate count; `npm run check:links` clean; typecheck + `npm test` clean (no test currently pins this doc section's wording, so no suite is expected to change).

## Not in scope

Building the typed-path "Open path" affordance the original draft of this spec proposed (rejected in round-1 review — see corrections below; the underlying gap it would have closed, that a non-Tauri first-run user cannot open an arbitrary on-disk file from the UI, is real but is a feature request, not a copy fix, and is better tracked as its own issue than built inside a copy-fix wave); any change to `pickNativeFilePath`/Tauri's native browse path, `openServerPath`, or `/api/open`; `FileOpenDialog.svelte`'s existing `openByPath`/`error` handling (already correct, unchanged, and the model a future "type a path" feature should follow — it sets `error` and does not close on failure, unlike the recents-click path).

## Review corrections (round 1)

The round-1 review raised six findings against the original "build the input" plan (three blocking, three non-blocking): a missing `data-testid` snapshot regen; a new affordance whose only failure path is `console.warn` with no visible feedback — a typo on a hand-typed path being the *common* case, not the rare one, which recreates the exact "on-screen instructions → dead end" defect class this group exists to close; a button label ("Open path") that doesn't match the doc's own "click **Open**"; a stale sibling "Upload mode" claim left standing while the section was declared accurate; an E2E "kills" claim that named a mutation (trimming) the spec's own Enter handler performs, which no proposed assertion could have caught; and a now-false provenance comment on `server-paths.ts` the fix would have left behind.

**Adopted, but by changing the decision rather than patching around it**: switched from "build the input" to "delete the promise," the wave-table note's own explicit default ("prefer deleting the promise unless the input is trivially small"). Every one of the six findings evaporates under that decision — there is no new `data-testid`, no new failure path to leave unhandled, no button label to pick, no E2E case to misdescribe, and no `server-paths.ts` comment to falsify — because there is no new affordance. The one finding that survives is the neighboring stale "Upload mode" wording, which is adopted directly (folded into the same doc edit, since the paragraph was already being touched).

This is a reversal of the original spec's own choice (it had preemptively rejected deletion in its "Not in scope" section), made explicit here rather than left implicit: the "trivially small" premise the original spec leaned on does not survive contact with what round-1 review found the input actually requires.

Not adopted: none of the six findings were declined on their merits — each identified a real gap in the "build" plan. What changed is the plan itself, not a decision to leave any of the identified gaps open within it.
