# J2 — #1781 Browser/npm build has no way to open a disk file for editing; the user guide's "Path input" doesn't exist

Branch `fix/product-copy-1814`. Closes #1781. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:19`. Probe: none (read-verified against source).

## Problem

`docs/user-guide.md:138` promises: *"**Path input** — Click the **+** button in the tab bar, type an absolute file path, and click **Open**."* The **+** button (`data-testid="open-file-btn"`, `DocumentTabs.svelte:1309-1320`) opens `NewTabMenu.svelte`, whose only text input is a search box (`data-testid="new-tab-search"`, `NewTabMenu.svelte:120-127`) that filters the ALREADY-recent-files list via `searchRows`/fuzzy-match (`newTabLauncher.ts`) — typing a path that isn't already a recent entry produces "No matches", and there is no Enter-to-submit or "Open" affordance that treats the typed text as a raw path. `NewTabMenu`'s only other open route is "Browse files…" (`onBrowse`, `:196-206`), which in the non-Tauri build opens `FileOpenDialog.svelte`'s hidden `<input type="file">` — an `upload://` read-only, session-only open (`uploadFile`, `:137-166`), never a real disk path. So a first-run npm/browser user genuinely cannot open an arbitrary file on disk from the UI, matching the issue's "core loop… not reachable" impact.

## Fix

**Adding the input is trivially small** — the wiring end-to-end already exists and needs no new server surface: `NewTabMenu`'s `onOpen: (path: string) => void` prop is already called with a raw string for existing recents (`:162`, `onclick={() => onOpen(entry.row.path)}`), and its wiring at `DocumentTabs.svelte:1331-1339` already calls the real thing — `await openServerPath(filePath)` (`src/client/utils/server-paths.ts`), which POSTs to the existing, already loopback-gated `/api/open` with no path restriction beyond what the server already enforces. **No `/api/open` change; no widening of what it accepts** — the fix is UI-only: give the user a way to hand `onOpen` a path that ISN'T already in `recentFiles`.

`NewTabMenu.svelte`, gated on `!isTauriRuntime()` (import from `../cowork/cowork-helpers.js`, matching `FileOpenDialog.svelte`'s existing convention — Tauri users have native browse + drag-drop and don't need this):

- Change the search input's `onkeydown` (currently only the outer `<div>`'s `handleKeyDown` handles Escape/Arrow keys, `:66-78`; the input itself has none) to also catch `Enter`: when `!isTauriRuntime()` and `query.trim()` is non-empty, call `e.preventDefault(); onOpen(query.trim()); onClose();` — this is Enter-to-open-a-typed-path, independent of whether `filtered` has any matches (a full path a user pastes will rarely fuzzy-match an existing recent's display name, so gating on "no matches" would miss the common case).
- Change the placeholder for the non-Tauri case to make the capability discoverable: `"Search recent files, or paste a path…"` (Tauri keeps the existing `"Search recent files…"`).
- Add a small, explicit **"Open path"** button (`data-testid="new-tab-open-path"`) in the same row as the search input, visible only when `!isTauriRuntime() && hasQuery` (mirrors the existing `hasQuery`-gated clear button at `:128-134`), calling the same handler as Enter — this gives the user-guide's literal "click Open" affordance, not just a keyboard-only one, and is the small addition that makes the promised UI real rather than hidden.

`docs/user-guide.md:138`'s existing "Path input" paragraph becomes accurate as written (no doc change needed) once this lands — re-verify the exact click sequence it describes ("Click **+** … type … click **Open**") still matches the shipped button label before leaving it unchanged.

## Tests

`tests/client/new-tab-launcher.test.ts` (pure-function `newTabLauncher.ts` tests) is unaffected — no logic there changes. New coverage:

1. `tests/e2e/new-tab-launcher.spec.ts`: extend with a case — type an absolute path to a fixture file that is NOT in `recentFiles` into the search box, press Enter (or click the new "Open path" button); assert the tab bar shows the opened file's name and the launcher closes. Kills a fix that only submits on a `filtered`-match, or that fails to call `openServerPath` with the untouched raw path (e.g. one that trims/normalizes it first, breaking a path with meaningful trailing content).
2. Component-level `NewTabMenu.svelte` test (new file, or add to an existing one if `NewTabMenu`-specific tests exist — check `tests/client/` first): with `isTauriRuntime` mocked `true`, typing text and pressing Enter does NOT call `onOpen` with unmatched text (kills a fix that forgets the runtime gate and lets a Tauri user's search-box Enter misfire as an open attempt against a non-recent string); with it mocked `false`, Enter with non-empty unmatched text DOES call `onOpen(query.trim())` exactly once, and the "Open path" button appears only when `hasQuery` is true.

## Done when

A non-Tauri user can type an absolute path in the **+** menu and open it for real (write-capable) editing without it being a prior recent or an `upload://`; `/api/open` and `openServerPath` are unchanged; `docs/user-guide.md:138` reads true; typecheck + `npm test` + `npm run test:e2e` clean.

## Not in scope

Deleting the user-guide promise (rejected — the input is trivially small, per the wave-table note's own stated preference); any change to `pickNativeFilePath`/Tauri's native browse path; validating or restricting the typed path client-side beyond `.trim()` — `openServerPath`/`/api/open` already own that validation server-side, and duplicating it client-side would be exactly the kind of new mechanism the minimality rule declines; surfacing `openServerPath`'s error to the user in the `DocumentTabs.svelte:1331-1339` `onOpen` callback (it currently only `console.warn`s on failure for the recents case too — a pre-existing gap, not introduced or worsened by this fix, and not raised by #1781).
