# J2 — #1781 Browser/npm build has no way to open a disk file for editing; the user guide's "Path input" doesn't exist

Branch `fix/product-copy-1814`. Closes #1781. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:19`. Probe: none (read-verified against source).

## Problem

`docs/user-guide.md:138` promises: *"**Path input** — Click the **+** button in the tab bar, type an absolute file path, and click **Open**."* The **+** button (`data-testid="open-file-btn"`, `src/client/tabs/DocumentTabs.svelte:1309-1320`) opens `src/client/tabs/NewTabMenu.svelte`, whose only text input is a search box (`data-testid="new-tab-search"`) that filters the already-recent-files list via fuzzy match — typing a path that isn't already a recent entry produces "No matches," with no Enter-to-submit or "Open" affordance that treats the typed text as a raw path. `NewTabMenu`'s only other open route, "Browse files…", opens a native picker on desktop but a read-only, session-only `upload://` dialog in the non-Tauri build. So a first-run npm/browser user genuinely cannot open an arbitrary file on disk from the UI.

## Fix

**Delete the promise rather than build the input.** The wave-table note's own default is "prefer deleting the promise unless the input is trivially small," and the input is not trivially small: a real "type a path" affordance needs a new `data-testid` (snapshot regen), a runtime gate, a failure-surfacing path that doesn't exist today, a button-label decision, and new tests — the shape of a small feature, not a copy fix, for a wave whose lesson is "MINIMAL copy fixes… no new frameworks."

`docs/user-guide.md`'s "Opening Files" section (~L134-142): delete the **Path input** bullet. While in this paragraph, also fix the neighboring **Upload** bullet's stale claim that clicking **+** lets you "switch to Upload mode" — there is no mode switch, only a **"Browse files…"** button (`data-testid="new-tab-browse"`), which opens a native picker on desktop or an `upload://` dialog in the browser build. Reword to describe that button by its real name.

New "Opening Files" section — no numeral, since a recent-files list (reachable via the same **+** button) is a third route most users actually take and the original three-bullet list never named it:

```
You can open a file a few ways:

**Drag-and-drop** — Drag a file from your file manager onto the editor. A dashed border appears as a drop indicator.

**Recent files** — Click **+** in the tab bar to see recently opened files; type to filter, then click one to open it.

**Browse or upload** — Click **+** in the tab bar, then **Browse files…**. On desktop this opens a native file picker for real (write-capable) editing. In the browser build it opens an upload dialog: uploaded files get a synthetic `upload://` path and are always read-only — `Save` preserves the session (annotations) but cannot write back to disk.
```

No `/api/open` change; no client or server behavior changes at all — documentation-only.
