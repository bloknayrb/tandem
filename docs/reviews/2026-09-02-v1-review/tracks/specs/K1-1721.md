# K1 — #1721 `accessibility.spec.ts` asserts only axe `violations`, so contrast failures land in `incomplete` and the run stays green

Branch `fix/test-gates-1784`. **Refs #1721 only** — the issue stays open, because its options (1)
and (2) need the "why do these nodes go incomplete" answer that is still unestablished. This PR
ships option **3** (the count pin) from the issue's own list. Ledger:
`docs/plans/2026-09-06-open-issues-sweep.md:224` ("count-pin only"). Probe: the issue's own mutation
— set `--tandem-author-user-bg` to `#4a4a4a` in `index.html`, run `-g "annotation card"`, record
whether the pinned count moves.

## Problem

`tests/e2e/accessibility.spec.ts:502` ends every scan with `expect(results.violations).toEqual([])`.
axe has three buckets — `violations`, `passes`, `incomplete` — and **nothing in the suite reads
`incomplete`**. `color-contrast` is not in `disableRules` (`:93-127`), so the rule runs; this is a
bucketing gap, not a disabled rule. The assertion is shared by the loop over **16** surfaces × 3
themes (`:487-505`), so the gap is suite-wide. The issue's measurement stands: a mid-grey card
behind dark body text reported `violations: []` in all three themes. Its *mechanism* is explicitly
not established, and the file's comment at `:300-345` already says so at length.

## Fix

A per-surface ceiling on color-contrast `incomplete` nodes, and nothing else — the gate must not
depend on the undecided colour question in #1683, and a count ceiling does not.

- New pure module `tests/e2e/axe-incomplete.ts` — **not** `.test.ts`/`.spec.ts`, so Playwright's
  `testDir: "tests/e2e"` default `testMatch` does not collect it and vitest's node project
  (`include: ["tests/**/*.test.ts"]`) does not either. It is typechecked by
  `tsconfig.tests.e2e.json`'s whole-directory include, so no config edit and no orphan. It imports
  nothing (declare its own `type AxeBucketEntry = { id: string; nodes: unknown[] }`) so it can also
  resolve into the node program when the unit test imports it. **Two** functions — the round-1
  `unknownBaselineKeys` is gone; see the key-set bullet below:
  - `colorContrastNodeCount(incomplete: AxeBucketEntry[]): number` — nodes of the `color-contrast`
    entry, `0` when the rule is absent.
  - `checkIncompleteBaseline(key, observed, baseline): string | null` — `null` when
    `observed <= baseline[key]`, otherwise a message naming key, observed and baseline. **A key with
    no baseline entry returns a message, not `null`** (fail closed): a new surface added to
    `SURFACES` must be measured, not silently unmeasured, which is the exact shape of the gap this
    issue is about. It is only ever called with a `` `${theme} / ${surface.name}` `` key, so a
    `$`-prefixed entry is never looked up as a count.
- New `tests/e2e/axe-incomplete-baseline.json` — a flat `{ "<theme> / <surface.name>": <count> }`
  object plus `$comment`. **Keys beginning with `$` are metadata and are excluded from every key
  comparison** (the convention `scripts/ci/coverage-policy.json:2-24` already uses); the remaining
  key set must be **exactly** the 48 that `SURFACES` (16 surfaces, `accessibility.spec.ts:225-469`)
  × 3 themes (`:485`) produces. That comparison lives in **`accessibility.spec.ts` as its own
  `test(...)` outside the per-surface loop**, not in the vitest unit file: `SURFACES` is a bare
  module-scope `const` in a file that calls `test.describe(...)`/`test(...)` at module scope, so
  exporting it and importing it under vitest would run Playwright's registrar. **`SURFACES` stays
  unexported.** Both directions are covered — a *missing* key by `checkIncompleteBaseline`'s
  fail-closed path, a *stale* key by this comparison — so a removed surface is as loud as an added one.
  **Seeding is two-environment and CI is authoritative**, because the gate lands inside `check` —
  a required status check with `enforce_admins: true` — and CI runs its own Chromium
  (`.github/workflows/ci.yml:366` `npx playwright install --with-deps chromium`), while this
  container aliases build 1194 in place of the 1234 `@playwright/test@1.58` expects
  (`docs/plans/2026-09-06-open-issues-sweep.md:276`) and installs no `--with-deps` fonts.
  `color-contrast` `incomplete` is a per-**node** count driven by obscuring/overlap and computed
  background detection, so line wrapping and font fallback move it. Procedure:
  1. Run `npx playwright test accessibility.spec.ts` on the reserved ports **twice** (both runs
     unconditional) and commit the per-key max of the two, so the file exists and the assertion is
     never reading an absent baseline.
  2. Read the **first CI `check` E2E run**'s counts out of the job log / Playwright report and
     commit `max(local, CI)` per key, with the `$comment` naming every key where the two
     environments disagreed and by how much, and stating the 1194-vs-1234 mismatch as the reason so
     the next reader does not re-seed locally.
  Never round up, never pad "for headroom" beyond an actually-observed number: a red first CI run is
  the measurement, not something to route around. **But "never pad" is not "never touch":** the
  `$comment` also carries the sanctioned re-seed, because a per-node count in a required check
  otherwise reads as unmaintainable — *when a deliberate UI change raises a key, re-run that
  surface, commit the newly observed number with a one-line reason in `$comment`, and never lower
  another key in the same edit.* Put that sentence in the `$comment` and in the rewritten
  `accessibility.spec.ts` block.
  **A 48-key all-zero baseline is evidence the wrong bucket was wired, not a clean result** — that
  whole-file inference is sound, because a gate reading `results.violations` yields exactly 48
  zeros (`:502` already asserts `violations` is empty). It is now an **assertion**, not a review
  step: see the seeding-outcome branch in Tests below. What is *not* sound is any per-key
  expectation: the file's 25-incomplete-vs-17-passes figure (`accessibility.spec.ts:326-327`)
  belongs to the **`#4a4a4a`-mutated** run described at `:316-318`, not to the shipped colours, so
  it bounds nothing about the unmutated baseline and the round-1 "annotation-card keys must be
  non-zero" rule is **withdrawn**. It is a hypothesis to test, not a rule.
- `accessibility.spec.ts`: read the baseline once at module scope with `readFileSync` + `JSON.parse`
  (the file's existing style; no `resolveJsonModule` dependency), and inside the existing test,
  **immediately after `const results = await scan(page)` and before either assertion**, `console.log`
  the observed `` `${theme} / ${surface.name} = <count>` `` on every run — the seeding procedure
  reads these out of the first CI run, and a surface that fails `violations` must still report its
  count. Then keep `expect(results.violations).toEqual([])` and add
  `expect(checkIncompleteBaseline(\`${theme} / ${surface.name}\`, colorContrastNodeCount(results.incomplete), baseline)).toBeNull()`.
  Keep it inside the existing `try` so the `finally` still runs `surface.close?.()`.
- Rewrite the block at `:318-334`. It currently states "NOTHING in this suite reads
  `results.incomplete`, so whatever axe files there is unasserted by construction" — that sentence
  becomes false with this change and would otherwise sit there as a comment describing a gap the
  file no longer has. Say what the pin does and does not buy: it makes a **jump** loud; it does not
  say any individual incomplete node is acceptable, and it is not a contrast gate for the user tint.
  Record the `#4a4a4a` mutation probe's outcome **in this rewritten block**, not only in the PR body
  (CLAUDE.md: a criterion whose evidence is untracked fails silently). Keep the "mechanism NOT
  established" and "do not repeat the `withRules` claim" paragraphs — they are still true and still
  the trap for the next reader.

## Tests

- `tests/scripts/axe-incomplete-baseline.test.ts` (vitest node project; `tests/scripts/**` is in
  `tsconfig.tests.node.json`), importing `../e2e/axe-incomplete.js`. **Five synthetic `it`s**:
  observed **above** baseline → a message naming the key (the required one — it proves the gate goes
  red); observed **equal** → `null`; observed **below** → `null`; **missing key** → a message. The
  equal case is the discriminating twin: without it a `>=` typo passes the red case and quietly
  fails every surface. A fifth over `colorContrastNodeCount`: an `incomplete` array holding only a
  non-contrast rule counts `0`, one holding `color-contrast` with 3 nodes counts `3` — kills a
  count-of-entries implementation.
- **A sixth `it`, and it is the only wiring proof there is**: read the committed
  `tests/e2e/axe-incomplete-baseline.json` and assert at least one non-`$` value is `> 0`, with a
  comment saying it exists so a re-seed from `results.violations` reds `check` instead of reading as
  a clean result. The five synthetic ones pass identically against either bucket; this one does not.
- **Seeding-outcome branch, so the spec has an exit.** If the clean-state run seeds any non-zero
  value, write the sixth `it` and the gate ships with its proof. If it genuinely yields 48 zeros —
  and only after logging `results.incomplete` raw and verifying by eye that
  `colorContrastNodeCount` is reading it — then **do not write the sixth `it`, do not pad, and do
  not stall**: record the raw dump and the zero result as a comment on #1721, state plainly in the
  PR body and in the rewritten `accessibility.spec.ts` block that the pin ships with **no wiring
  proof**, and drop the non-zero clause from `Done when`. That is a worse outcome honestly labelled,
  which is the only acceptable one.
- The `#4a4a4a` mutation probe is the second, weaker signal: run it and record whether the
  annotation-card key exceeded its baseline. **Report that result honestly either way.** If the
  count does not move, the pin still detects a jump — which is what option 3 buys and all it claims
  — and that measurement belongs on #1721 as a comment, since it narrows what options (1) and (2)
  will have to explain.

## Done when

`axe-incomplete.ts` (two functions) + the 48-key baseline are committed, the baseline reconciled
against the first CI `check` run and — unless the all-zero branch above fired and was recorded —
carrying at least one non-zero value **asserted by the sixth `it`**, not merely read by a human; the
`$`-prefixed `$comment` is excluded from the key-set comparison, which lives in `accessibility.spec.ts`
as its own `test(...)`; the a11y loop logs each observed count before its assertions and asserts the
ceiling as well as `violations`; the unit assertions pass; the
stale "nothing reads incomplete" comment is rewritten and carries the probe outcome; a full
`accessibility.spec.ts` run is green on the reserved ports **and in CI**; `npm run typecheck:tests`
green; the probe outcome is also a comment on #1721.

## Not in scope

Options (1) and (2) from the issue (asserting `incomplete` empty, with waivers) and the

Promoting the baseline into a CI job of its own — it rides inside the existing E2E run.

## Review corrections (round 1)

**Adopted.**

- *Blocking — a locally-seeded exact ceiling enforced in the required `check` job on a different
  Chromium is a likely permanent red* (raised twice, once non-blocking). Seeding is now explicitly
  two-environment: two local runs (both unconditional) to make the file exist, then `max(local, CI)`
  from the first CI `check` E2E run, with a `$comment` recording disagreements and the
  1194-vs-1234 build mismatch as the reason. The spec adds a per-key `console.log` so CI's numbers
  are readable, and `Done when` requires a green CI run.
- *Blocking — nothing distinguished a gate reading `incomplete` from one reading `violations`.*
  An all-zero 48-key baseline is now declared evidence of the wrong bucket (against the file's own
  recorded 25-vs-17 measurement at `:327-329`), the annotation-card keys must be non-zero, and the
  Tests section says the baseline's values — not the mutation probe — are the wiring proof.
  **Partly superseded in round 2**: the whole-file all-zero rule stands and is now an assertion; the
  per-key annotation-card clause is withdrawn (that figure is from the mutated run).
- *A stale baseline key is silent when a surface is removed.* Added `unknownBaselineKeys` and a
  sixth unit assertion; the key set must be exactly the 48 from `SURFACES` × themes.
  **Superseded in round 2**: the property is kept, the third exported function is not — the key-set
  comparison is now inline in `accessibility.spec.ts`.
- *The probe outcome lived only in the PR body.* It is now written into the rewritten
  `accessibility.spec.ts:318-334` block as well.
