# W13a — #1918 `activity.isTyping` is published true for a REMOTE doc change the user did not make

Branch `fix/activity-awareness-honesty-1918`. Closes #1918. Non-review issue, no ledger row.

## Problem

`src/client/editor/extensions/awareness.ts:232`, plugin 2's `view().update(view, prevState)`, gates the activity branch on `state.doc !== prevState.doc` alone. A remote y-tiptap transaction (`tandem_edit`, initial ySync, another tab's undo) replaces `state.doc`, so the 200 ms timer writes `Y_MAP_ACTIVITY = { isTyping: true, cursor, lastEdit: Date.now() }` for an edit the user did not make. `tandem_getActivity` then reports `isTyping: true` and `active: true` because Claude edited the document.

Plugin 1 already discriminates at `:133` via `tr.getMeta(ySyncPluginKey)`. A plugin **view** has no transaction, so it reads the plugin state instead.

## Fix

One binding at the top of `update()`, in `src/client/editor/extensions/awareness.ts`:

```ts
const ySync = ySyncPluginKey.getState(state) as
  | { isChangeOrigin?: boolean; isUndoRedoOperation?: boolean }
  | undefined;
const isRemoteChange = ySync?.isChangeOrigin === true && ySync.isUndoRedoOperation !== true;
```

- `ySyncPluginKey` is already imported (`:5`). y-tiptap recomputes both flags on every transaction (`node_modules/@tiptap/y-tiptap/dist/y-tiptap.js:191-193`), so neither is sticky and no plugin state of our own is needed.
- `isUndoRedoOperation` is set only when the Y transaction origin `instanceof Y.UndoManager` (`y-tiptap.js:800`), i.e. **this** tab's undo — a user edit that must keep counting as activity. Another tab's undo arrives as an ordinary provider update and is remote.
- Wrap **the timers and `pendingActivity` only**: keep `lastCursor = { doc: state.doc, pos: state.selection.from }` on every `state.doc !== prevState.doc`, and put `pendingActivity = true` plus both timer arms behind `!isRemoteChange`. A remote edit landing inside a window the user's own keystroke armed must still refresh `lastCursor`, or the pending write publishes a flat offset computed against the pre-remote document. Refreshing a local variable is neither a write nor a timer.
- A remote change writes nothing at all — no `cursor` refresh either. Any write costs a fresh `lastEdit`, and a caret move with no edit already writes nothing today (pinned by existing test 5b), so a stale published caret is the existing contract.
- The binding is computed once; the selection arm at `:188` consumes it in #1991. Land #1918 first.

Critical Rule 1 (`Y_MAP_ACTIVITY` from `shared/constants`, unchanged) and Critical Rule 2 (writes stay inside `withBrowser`, `pmPosToFlatOffset` stays outside the transaction callback). No `$state`, no testid, no MCP tool, no `/api` route, no skill copy.

## Tests

In `tests/client/activity-cursor-flat.test.ts`, hoist the existing `remoteChange()` helper (peer `Y.Doc` → `Y.applyUpdate`, today inside `describe("Y_MAP_SELECTION lifetime (#1624)")`) to module scope, and add `describe("activity is not published for a remote change (#1918)")`:

1. **A remote insert writes no activity record.** `boundEditor(MARKDOWN)`, fake timers, remote insert into the leading paragraph, advance `TYPING_DEBOUNCE + 250` → `activity()` is `undefined`. Kills a fix that keeps the write but flips `isTyping: false` (still a fresh `lastEdit`, still `active: true`).
2. **A local keystroke still publishes.** Reuse `typeZBeforeThree()`, advance 250 → `{ isTyping: true }` and `cursor === caretFlat(editor)`.
3. **A remote change after a local edit does not extend the record.** Type locally; advance `TYPING_DEBOUNCE + 250` so **both** local writes have landed and the record is quiescent; **now** capture it; advance 5 s; deliver a remote insert; advance 250 → `expect(activity()).toStrictEqual(captured)`. Kills a guard placed inside the debounce callback rather than at the branch. Capture after the typing window closes, not at +250: `TYPING_DEBOUNCE` is 3000 ms (`src/shared/constants.ts:186`), so a +250 capture is overwritten by the typing-clear timer and reds even with a correct guard. A red there is the ordering, never the guard — do not weaken the assertion or move the guard.
4. **A local undo still counts as the user.** After a local edit and `advanceTimersByTimeAsync(TYPING_DEBOUNCE + 50)`, run `editor.commands.undo()` and advance 250 → a record with a newer `lastEdit`. This is the only row that kills the cheaper guard with no `isUndoRedoOperation` term, so it is required. `StarterKit` is configured `undoRedo: false` (`src/client/editor/editor-extensions.ts:281-282`) and `@tiptap/extension-collaboration` routes `editor.commands.undo()` through the Y `UndoManager`, so the row is writable as specified.

## Not in scope

The selection branch and its copy (#1991/#1624), the background-tab stale slice (#1997), `activity.cursor` units (#1776, shipped), the 200 ms / `TYPING_DEBOUNCE` timings, and any latching of remoteness across an `appendTransaction` batch. On that last one: because the flags are per-transaction, a remote ySync transaction followed in the same dispatch by an appended transaction leaves the final `state` reading `isChangeOrigin === false`, so the guard fails open there. That is a strict improvement on today's unconditional publish and is left alone — a latching plugin-state slice is a new mechanism this issue does not need.
