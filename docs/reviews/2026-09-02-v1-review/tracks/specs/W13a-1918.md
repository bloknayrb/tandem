# W13a — #1918 `activity.isTyping` is published true for a REMOTE doc change the user did not make

Branch `fix/activity-awareness-honesty-1918`. Closes #1918. No review ledger row — a non-review issue, filed out of #1776's spec work. Probe: `tests/client/activity-cursor-flat.test.ts` (the `boundEditor` + peer-`Y.Doc` harness that issue #1991 measured on).

## Problem

`src/client/editor/extensions/awareness.ts:232`, plugin 2's `view().update(view, prevState)`, gates the whole activity branch on `state.doc !== prevState.doc` alone. A remote y-tiptap transaction — `tandem_edit`, the initial ySync, another tab's undo — replaces `state.doc`, so the branch arms both timers and the 200 ms one writes `Y_MAP_ACTIVITY = { isTyping: true, cursor, lastEdit: Date.now() }` for an edit the user did not make. `tandem_getActivity` then reports `isTyping: true` and `active: true` (`src/server/mcp/awareness.ts:391`, the 10 s window over `lastEdit`) purely because Claude edited the document — the agent reads its own write back as the user typing.

Plugin 1 in the same file already discriminates, at `:133` (`tr.getMeta(ySyncPluginKey)`). Plugin 2 cannot copy that literally: a plugin **view** has no transaction, only `(view, prevState)`.

## Fix

One guard at the top of `update()`, in `src/client/editor/extensions/awareness.ts`:

```ts
const ySync = ySyncPluginKey.getState(state) as
  | { isChangeOrigin?: boolean; isUndoRedoOperation?: boolean }
  | undefined;
const isRemoteChange = ySync?.isChangeOrigin === true && ySync.isUndoRedoOperation !== true;
```

- `ySyncPluginKey` is already imported (`:5`). Reading the ySync plugin state is the view-side equivalent of plugin 1's meta check: `@tiptap/y-tiptap` **recomputes both flags on every transaction** (`dist/y-tiptap.js:190-193`, comment "always set isChangeOrigin. If undefined, this is not change origin"), so neither is sticky and no plugin state of our own is needed.
- The `isUndoRedoOperation` term is deliberate, not defensive: y-tiptap sets it only when the Y transaction origin `instanceof Y.UndoManager` (`:834`), i.e. **this** tab's undo, which is a user edit and must keep counting as activity. Another tab's undo arrives as an ordinary provider update and is therefore remote.
- Wrap **only** the activity branch (`:232-...`) in `if (!isRemoteChange && state.doc !== prevState.doc)`. Nothing is written and no timer is armed for a remote change; timers already armed by the user's own edits keep running and still read `view.state` at fire time (test 5a's behaviour is untouched).
- **Decision (the open one in the issue body): a remote change does not refresh `cursor` either.** The record's shape is `{ isTyping, cursor, lastEdit }` and the server's `active` is computed from `lastEdit`, so any write costs a fresh `lastEdit` — a `cursor`-only refresh would need a second field or a remembered timestamp, i.e. a mechanism, to buy a value that is already allowed to be stale: a caret move with no edit writes nothing today (pinned by test 5b), so "the caret can be older than now" is the existing contract, not a regression.
- The selection branch at `:188` is #1991's; the same `isRemoteChange` binding is what it consumes, computed once. Land #1918 first and #1991 on top.

Rules that bite here: Critical Rule 1 (`Y_MAP_ACTIVITY` comes from `shared/constants`, unchanged) and Critical Rule 2 — the writes stay inside `withBrowser(ydoc, …)` and the `pmPosToFlatOffset` walk stays outside the transaction callback. No `$state` is touched in this file, so the `createCoalescingTick` rule does not apply. No testid, no MCP tool, no `/api` route, no skill copy: `tandem_getActivity`'s description already says only a document change triggers a write, and after this fix that is true rather than aspirational.

## Tests

In `tests/client/activity-cursor-flat.test.ts`, whose `describe("Y_MAP_SELECTION lifetime (#1624)")` block already owns `remoteChange()` (peer `Y.Doc` → `Y.applyUpdate`) — hoist that helper to module scope so a new `describe("activity is not published for a remote change (#1918)")` can use it.

1. **A remote insert writes no activity record at all.** `boundEditor(MARKDOWN)`, fake timers, a remote insert into the leading paragraph, advance `TYPING_DEBOUNCE + 250` → `activity()` is `undefined`. Kills the shape that keeps the write but flips `isTyping: false`: that still publishes a fresh `lastEdit`, and `active` would still be true.
2. **A local keystroke still publishes `isTyping: true`.** Reuse `typeZBeforeThree()`, advance 250 → `{ isTyping: true }` and `cursor === caretFlat(editor)`. Kills a guard that reads the flag from stale plugin state and suppresses everything.
3. **A remote change after a local edit does not extend the record.** Type locally, advance 250, capture `lastEdit`; advance 5 s; deliver a remote insert; advance 250 → the record is `toStrictEqual` the captured one. Kills a guard placed inside the debounce callback rather than at the branch, which would let the remote transaction re-arm the write.
4. **A local undo still counts as the user.** After a local edit and `advanceTimersByTimeAsync(TYPING_DEBOUNCE + 50)`, run `editor.commands.undo()` and advance 250 → a record with a `lastEdit` newer than the previous one. This is the only test that kills the cheaper `ySync?.isChangeOrigin === true` guard with no `isUndoRedoOperation` term. If the bound editor's history plugin turns out not to route undo through the Y `UndoManager` in this harness, say so in the PR body and keep the term with the y-tiptap source citation — do not delete the term to make a test writable.
