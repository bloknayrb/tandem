# W13a — #1918 `activity.isTyping` is published true for a REMOTE doc change the user did not make

Branch `fix/activity-awareness-honesty-1918`. Closes #1918. No review ledger row — a non-review issue, filed out of #1776's spec work. Probe: `tests/client/activity-cursor-flat.test.ts` (the `boundEditor` + peer-`Y.Doc` harness that issue #1991 measured on).

## Problem

`src/client/editor/extensions/awareness.ts:232`, plugin 2's `view().update(view, prevState)`, gates the whole activity branch on `state.doc !== prevState.doc` alone. A remote y-tiptap transaction — `tandem_edit`, the initial ySync, another tab's undo — replaces `state.doc`, so the branch arms both timers and the 200 ms one writes `Y_MAP_ACTIVITY = { isTyping: true, cursor, lastEdit: Date.now() }` for an edit the user did not make. `tandem_getActivity` then reports `isTyping: true` and `active: true` (`src/server/mcp/awareness.ts:391`, the 10 s window over `lastEdit`) purely because Claude edited the document — the agent reads its own write back as the user typing.

Plugin 1 in the same file already discriminates, at `:133` (`tr.getMeta(ySyncPluginKey)`). Plugin 2 cannot copy that literally: a plugin **view** has no transaction, only `(view, prevState)`.

## Fix

One guard at the top of `update()`, in `src/client/editor/extensions/awareness.ts`:

```ts
const ySync = ySyncPluginKey.getState(state) as
  | { isChangeOrigin?: boolean; isUndoRedoOperation?: boolean }
  | undefined;
const isRemoteChange = ySync?.isChangeOrigin === true && ySync.isUndoRedoOperation !== true;
```

- `ySyncPluginKey` is already imported (`:5`). Reading the ySync plugin state is the view-side equivalent of plugin 1's meta check: `@tiptap/y-tiptap` **recomputes both flags on every transaction** (`dist/y-tiptap.js:191-193`, under the comment "always set isChangeOrigin. If undefined, this is not change origin"), so neither is sticky and no plugin state of our own is needed.
- **The bound that non-stickiness buys, stated so it is recorded rather than claimed closed:** because the flags are recomputed per transaction, a remote ySync transaction followed in the same dispatch by an `appendTransaction` (this stack has four — `clearDocument`, prosemirror-tables' `tableEditing`/`fixTables`, link autolink, core PasteRules; see `src/client/editor/extensions/authorship.ts:1369-1374`) leaves the final `state` with `isChangeOrigin === false`, so the guard **fails open** and that remote change still publishes activity. That is a strict improvement on today's unconditional publish, and it is the residue this fix does not remove. Do not latch remoteness across the appended batch here — a plugin `state: { apply }` slice ORing the meta is the shape if it is ever needed, and it is out of scope. **Say this bound in the PR body.**
- The `isUndoRedoOperation` term is deliberate, not defensive: y-tiptap sets it only when the Y transaction origin `instanceof Y.UndoManager` (`dist/y-tiptap.js:800`), i.e. **this** tab's undo, which is a user edit and must keep counting as activity. Another tab's undo arrives as an ordinary provider update and is therefore remote.
- Wrap **the timers and the `pendingActivity` flag only**, not the whole branch: keep `lastCursor = { doc: state.doc, pos: state.selection.from }` executing on every `state.doc !== prevState.doc`, and put `pendingActivity = true` plus both timer arms behind `!isRemoteChange`. Concretely the branch becomes `if (state.doc !== prevState.doc) { lastCursor = …; if (!isRemoteChange) { pendingActivity = true; …two timers… } }`. Nothing is written and no timer is armed for a remote change; timers already armed by the user's own edits keep running and still read `view.state` at fire time (test 5a's behaviour is untouched). **Refreshing `lastCursor` is load-bearing:** a remote edit landing inside the 200 ms window the user's own keystroke armed would otherwise publish `pmPosToFlatOffset` computed against the pre-remote document — a flat offset in one version of the coordinate system read by MCP clients against the current server text. Today the remote transaction self-corrects that; keeping the assignment outside the guard preserves it at zero cost, and refreshing a local variable is neither a write nor a timer.
- **Decision (the open one in the issue body): a remote change publishes no `cursor` either** — it writes nothing at all. (This is about the published record; the in-memory `lastCursor` still tracks the live document, per the bullet above.) The record's shape is `{ isTyping, cursor, lastEdit }` and the server's `active` is computed from `lastEdit`, so any write costs a fresh `lastEdit` — a `cursor`-only refresh would need a second field or a remembered timestamp, i.e. a mechanism, to buy a value that is already allowed to be stale: a caret move with no edit writes nothing today (pinned by test 5b), so "the caret can be older than now" is the existing contract, not a regression.
- The selection branch at `:188` is #1991's; the same `isRemoteChange` binding is what it consumes, computed once. Land #1918 first and #1991 on top.

Rules that bite here: Critical Rule 1 (`Y_MAP_ACTIVITY` comes from `shared/constants`, unchanged) and Critical Rule 2 — the writes stay inside `withBrowser(ydoc, …)` and the `pmPosToFlatOffset` walk stays outside the transaction callback. No `$state` is touched in this file, so the `createCoalescingTick` rule does not apply. No testid, no MCP tool, no `/api` route, no skill copy: `tandem_getActivity`'s description already says only a document change triggers a write, and after this fix that is true rather than aspirational.

## Tests

In `tests/client/activity-cursor-flat.test.ts`, whose `describe("Y_MAP_SELECTION lifetime (#1624)")` block already owns `remoteChange()` (peer `Y.Doc` → `Y.applyUpdate`) — hoist that helper to module scope so a new `describe("activity is not published for a remote change (#1918)")` can use it.

1. **A remote insert writes no activity record at all.** `boundEditor(MARKDOWN)`, fake timers, a remote insert into the leading paragraph, advance `TYPING_DEBOUNCE + 250` → `activity()` is `undefined`. Kills the shape that keeps the write but flips `isTyping: false`: that still publishes a fresh `lastEdit`, and `active` would still be true.
2. **A local keystroke still publishes `isTyping: true`.** Reuse `typeZBeforeThree()`, advance 250 → `{ isTyping: true }` and `cursor === caretFlat(editor)`. Kills a guard that reads the flag from stale plugin state and suppresses everything.
3. **A remote change after a local edit does not extend the record.** Type locally, then `await vi.advanceTimersByTimeAsync(TYPING_DEBOUNCE + 250)` so **both** local writes have landed (the 200 ms `{isTyping: true}` one and the `TYPING_DEBOUNCE` `{isTyping: false, lastEdit: <then>}` one) and the record is quiescent; **now** capture the whole record; advance 5 s; deliver a remote insert; advance 250 → `expect(activity()).toStrictEqual(captured)`. Kills a guard placed inside the debounce callback rather than at the branch, which would let the remote transaction re-arm the write. **Capture after the typing window closes, not at +250** — `TYPING_DEBOUNCE` is 3000 ms (`src/shared/constants.ts:186`), so a record captured at +250 is overwritten by the typing-clear timer at +3000 and a strict-equality comparison against it reds even with a correct guard. A red there is the test's ordering, never the guard: do not weaken the assertion or move the guard to satisfy it.
4. **A local undo still counts as the user.** After a local edit and `advanceTimersByTimeAsync(TYPING_DEBOUNCE + 50)`, run `editor.commands.undo()` and advance 250 → a record with a `lastEdit` newer than the previous one. This is the only test that kills the cheaper `ySync?.isChangeOrigin === true` guard with no `isUndoRedoOperation` term, so it is **required, not optional**. The harness does route undo through the Y `UndoManager` — verified: `src/client/editor/editor-extensions.ts:281-282` configures `StarterKit` with `undoRedo: false`, `@tiptap/extension-collaboration/dist/index.js:112-116,135` installs `yUndoPlugin` and routes `editor.commands.undo()` through `yUndoPluginKey`'s `Y.UndoManager`, and `node_modules/@tiptap/y-tiptap/dist/y-tiptap.js:800` sets `isUndoRedoOperation: transaction.origin instanceof Y.UndoManager`. Never delete the `isUndoRedoOperation` term to make a test writable.

## Review corrections (round 1)

**Adopted**

- **BLOCKING - test 3 could not pass against a correct implementation** (raised three times). `TYPING_DEBOUNCE` is 3000 ms (`src/shared/constants.ts:186`), so the prescribed "advance 5 s" fired the typing-clear timer and replaced the record captured at +250 before the remote insert was delivered; the `toStrictEqual` reddened for a reason unrelated to remoteness, inviting the implementer to weaken the assertion or move the guard. Test 3 now captures the record AFTER `TYPING_DEBOUNCE + 250`, when both local writes have landed and the record is quiescent, and says explicitly that a red there is the ordering rather than the guard.
- **NON-BLOCKING - `lastCursor` must keep refreshing on a remote change** (raised twice). Wrapping the whole branch put the `lastCursor` assignment behind the guard, so a remote edit inside the 200 ms window the user's own keystroke armed would publish a flat offset computed against the pre-remote document. The Fix now wraps only `pendingActivity` and the two timer arms, keeps `lastCursor = { doc: state.doc, pos: state.selection.from }` on every `state.doc !== prevState.doc`, and says why. Tests 1 and 3 are unaffected (a local-variable refresh is neither a write nor a timer).
- **NON-BLOCKING - the guard fails open after an `appendTransaction`** (raised twice). `isChangeOrigin` is recomputed per transaction, so an appended transaction folded in after a remote ySync transaction leaves the final `state` reading false and activity is published. Adopted as the stated-bound option: the Fix now records the residue, names the four `appendTransaction` plugins, says a latching plugin-state slice is the shape if it is ever needed, and requires the bound in the PR body. Not adopted as a code change - the tests proposed here cannot see it, and latching remoteness across a batch is a new mechanism this issue does not need.
- **NON-BLOCKING - citation corrections and the test-4 hedge** (raised three times). `dist/y-tiptap.js:190-193` -> `:191-193` for the flag recomputation, `:834` -> `:800` for `isUndoRedoOperation: transaction.origin instanceof Y.UndoManager` (both re-read in `node_modules` here). The escape hatch on test 4 is deleted: `StarterKit` is configured `undoRedo: false` (`src/client/editor/editor-extensions.ts:281-282`) and `@tiptap/extension-collaboration/dist/index.js:112-116,135` routes `editor.commands.undo()` through `yUndoPlugin`'s `Y.UndoManager`, so row 4 is required and writable as specified.
