# A-rest — #1768 no-arg `tandem_restoreBackup` on a `.docx` restores the sidecar, ignoring `readOnly` and every safety check

Branch `fix/restore-and-close-ids-1768`. Closes #1768. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-mcp.md:19`; track row `tracks/A-stop-the-bleeding.md:19`. Probe: `docs/reviews/2026-09-02-v1-review/experiments/probe-tools.mts` case **H5** (`restoreBackup({})` on a read-only `.docx` with a sidecar) — before/after in the PR body. Reviewer: `security-reviewer` (a write reachable from a tool).

## Problem

`src/server/mcp/docx-apply.ts`, `tandem_restoreBackup`: the `if (docState.format === "docx")` block owns the whole no-`backup` (list) case. When `listDocBackups` returns zero snapshots it falls through to a **second, private restore implementation** — `fs.open(sidecar, O_RDONLY|O_NOFOLLOW)` → `atomicWriteBuffer(filePath, backupBytes)` → `mcpSuccess("Restored …")`. That path never consults `docState.readOnly`, never takes the reload guard, never calls `snapshotBeforeFirstWrite`, never runs `suppressNextChange`/`recordSelfWrite`/`rearmWatch`, and never reloads the Y.Doc — so the open document keeps showing the pre-restore text while disk holds older bytes. The tool description and `docs/mcp-tools.md:842` both call the no-arg form "list". `tests/server/restore-backup.test.ts:619` ("keeps the .docx sidecar restore unchanged") pins the destructive behaviour, and H5 reproduces it on a `readOnly: true` document.

**Decision 1 (Bryan, `decisions.md:10`):** the no-arg call **lists** the sidecar as an entry and never restores; the sidecar restore path honours `readOnly`.

## Fix

Delete the private restore. The sidecar becomes an ordinary **named** backup, restored through the one guarded path, `restoreDocumentFromBackup` (`src/server/documents/reload-family.ts:220`) — which already checks `source !== "file"`, `RESTORE_FORMATS`, `readOnly`, `isReloadInProgress`, snapshots the current bytes, runs the `#1749` triple (`suppressNextChange` → `atomicWriteBuffer` → `recordSelfWrite`, `rearmWatch` in the inner `finally` — CLAUDE.md's file-watcher gotcha; **`recordSelfWrite` before `rearmWatch`**, and the existing arg-expression equality in `document-write-rearm.test.ts` must keep holding), reloads via `reloadFromDisk`, and re-baselines `Y_MAP_SAVED_AT_VERSION` under `withInternal` (Critical Rule 2 — no new Y.Doc write is added here).

1. **`src/server/file-io/doc-backup.ts`** — one new pure export, no fs:
   `export function docxSidecarBackupPath(filePath: string): string | null` → `filePath.replace(/\.docx$/i, ".backup.docx")` when the path ends `.docx` (case-insensitive), else `null`.
   - It serves the **two read/list sites only**: the list-mode append in `docx-apply.ts` (item 3) and the sidecar resolution in `reload-family.ts` (item 2). **`applyChangesCore`'s literal at `docx-apply.ts:331` is deliberately excluded** — that expression is `resolvedBackupPath ?? filePath.replace(…)` (a caller-supplied `backupPath` may override it) and it is immediately realpath-canonicalized on the parent at `:333-336`; substituting a `string | null` helper there makes `defaultBackup` nullable and drops the override branch. So there are three literals today, not two, and one of them stays.
   - Consequence worth one sentence in the PR body: the read side derives the sidecar name **without** canonicalizing the parent, so where a parent component is a symlink the write side and the read side can disagree about which file the sidecar is. Pre-existing, unchanged by this fix, and not something the `O_NOFOLLOW` leaf guard addresses.
   - Re-point the comment at `docx-apply.ts:364-367` ("`tandem_restoreBackup`'s .docx fallback derives that name and derives it only, so a uniquified sidecar is write-only") at `docxSidecarBackupPath` and the list-mode append. The invariant still holds — only the default-named sidecar is listed and restorable — but the branch it names no longer exists.
   - **The `docxSidecarBackupPath` import in `reload-family.ts` must join the existing `../file-io/doc-backup.js` import statement at `:48`.** `tests/docs/documents-boundary.test.ts:412` asserts FAN_OUT by exact equality with the row `server/documents/reload-family.ts -> server/file-io/doc-backup.ts (value) x1`, and the count is per import **statement** — a second statement makes it x2 and goes red.
2. **`reload-family.ts` `restoreDocumentFromBackup`** — resolution and read:
   - `const sidecarPath = isDocx ? docxSidecarBackupPath(existing.filePath) : null;`

Keep the Windows asymmetry note (`O_NOFOLLOW` undefined → `lstat` fallback).
     The move is not literally verbatim in two respects. **(i)** The two refusals currently `return mcpError("INVALID_PATH", …)`, and `reload-family.ts` has no `mcpError`. They become `throw Object.assign(new Error(…), { code: "BACKUP_SYMLINK" })` — **`BACKUP_SYMLINK`, not `INVALID_PATH`**, following the precedent this same file already set twelve lines away: `applyChangesCore` hit exactly this collision and `docx-apply.ts:464-473` resolves it with a distinct internal code plus a one-line map (`if (e.code === "BACKUP_SYMLINK") return mcpError("INVALID_PATH", e.message);`), with a comment saying reusing `INVALID_PATH` "would map to FORMAT_ERROR here — a symlinked destination is not a format problem." The refusal in `reload-family.ts` is a **new** throw site this spec authors, so its internal code is free, and choosing `BACKUP_SYMLINK` keeps `tandem_restoreBackup`'s existing `INVALID_PATH || UNSUPPORTED_FORMAT → FORMAT_ERROR` fold untouched and makes item 4 a pure addition with **no wire-visible behaviour change**. `src/server/mcp/routes/_shared.ts:141` already maps `BACKUP_SYMLINK` to 400, so `POST /api/backups/restore` needs no change either. **(ii)** `ENOENT` throws the existing `FILE_NOT_FOUND`.
   - **Bound the read by compressed size before allocating it.** The block ends in `backupBytes = await handle.readFile()` with no `fstat`, and the only size gate on this path (`assertDocxWithinSizeLimits`, `reload-family.ts:288`) runs *after* the read and caps **decompressed** bytes only (`docx-size-gate.ts:44`, `:59`). Today that read is reachable only through the no-arg call with zero snapshots; after this fix it is reachable by name at any snapshot count and additionally through `POST /api/backups/restore`, on a file in the user's document directory that any local process can write. So the helper does `const st = await handle.stat();` and refuses above `MAX_DOCX_TOTAL_BYTES` (`docx-size-gate.ts:59`, 64 MiB, already exported and already pinned by `tests/server/docx-size-gate.test.ts:182`) with the same `DOCX_TOO_LARGE` code `assertDocxWithinSizeLimits` throws. Reusing that constant is deliberate: no new number needs justifying, and a compressed archive above the *decompressed* total ceiling could never have passed the existing gate anyway, so this refuses strictly earlier and never rejects something that would have succeeded.
   - Extend `restoreDocumentFromBackup`'s own coded-error JSDoc at `reload-family.ts:214` with a **new** line — `BACKUP_SYMLINK — the resolved .docx sidecar is a symbolic link` — rather than a second producer on the `INVALID_PATH` line. `sendApiError` maps `BACKUP_SYMLINK` to 400 for `POST /api/backups/restore` (`src/server/mcp/routes/_shared.ts:137-148`), unchanged.
   - Everything downstream is untouched, so the sidecar restore now also gets `assertDocxWithinSizeLimits`, plus a pre-restore snapshot of the current bytes **when the once-per-run gate allows** — which in the sidecar's own scenario it usually does not. `snapshotBeforeFirstWrite` is once-per-path-per-run and `applyChangesCore` already calls it on `filePath` (`docx-apply.ts:394`) in the very run that writes the sidecar, so by the time anyone restores that sidecar the gate is consumed and the post-`applyChanges` bytes are **not** preserved. State the size gate as a gain and the snapshot with the caveat — in the PR body and in any `docs/security.md` note — matching the wording already at `docs/mcp-tools.md:870` ("when the once-per-run gate allows"). Do not assert that the sidecar restore is itself reversible.
   - **Also rewrite `restoreDocumentFromBackup`'s JSDoc summary** (`reload-family.ts:199-201`), which today reads "Restore an open text document (.md/.txt) from a pre-overwrite snapshot". The function now resolves **two** namespaces and the second is the one carrying the symlink hazard the moved `O_NOFOLLOW` block exists for: one sentence naming both — a snapshot under `{APP_DATA}/doc-backups/`, or the `.docx` `{name}.backup.docx` sidecar beside the document, selected by exact-basename match.
   - Security note for the PR body and `docs/security.md`: the sidecar becomes a **parsed-and-reloaded** input rather than a byte copy — it flows through `assertDocxWithinSizeLimits` → `reloadFromDisk`, which re-parses the archive and re-injects Word comments as `import`-authored annotations. The sidecar lives in the user's document directory, writable by any local process, unlike snapshots under appDataDir. Net risk falls (the O_NOFOLLOW leaf read is preserved, a compressed-byte ceiling and the decompressed-size gate are added, and the *automatic* no-arg restore disappears). **Scope the equivalence claim precisely — the unqualified version must not reach `docs/security.md`:** the **parse** bound is identical to opening that file directly; the **overwrite** half is not, because opening a hostile `.docx` creates a new document while restoring the sidecar replaces the user's in place, and the pre-restore snapshot is a no-op whenever `applyChangesCore` already consumed the once-per-path-per-run gate (previous bullet). So: "the parse bound is identical to opening that file directly; the overwrite half is pre-existing on this path and unchanged."
