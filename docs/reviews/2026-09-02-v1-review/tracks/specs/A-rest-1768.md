# A-rest — #1768 no-arg `tandem_restoreBackup` on a `.docx` restores the sidecar, ignoring `readOnly` and every safety check

Branch `fix/restore-and-close-ids-1768`. Closes #1768. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-mcp.md:19`; track row `tracks/A-stop-the-bleeding.md:19`. Probe: `experiments/probe-tools.mts` case **H5** (`restoreBackup({})` on a read-only `.docx` with a sidecar) — before/after in the PR body. Reviewer: `security-reviewer` (a write reachable from a tool).

## Problem

`src/server/mcp/docx-apply.ts`, `tandem_restoreBackup`: the `if (docState.format === "docx")` block owns the whole no-`backup` (list) case. When `listDocBackups` returns zero snapshots it falls through to a **second, private restore implementation** — `fs.open(sidecar, O_RDONLY|O_NOFOLLOW)` → `atomicWriteBuffer(filePath, backupBytes)` → `mcpSuccess("Restored …")`. That path never consults `docState.readOnly`, never takes the reload guard, never calls `snapshotBeforeFirstWrite`, never runs `suppressNextChange`/`recordSelfWrite`/`rearmWatch`, and never reloads the Y.Doc — so the open document keeps showing the pre-restore text while disk holds older bytes. The tool description and `docs/mcp-tools.md:842` both call the no-arg form "list". `tests/server/restore-backup.test.ts:619` ("keeps the .docx sidecar restore unchanged") pins the destructive behaviour, and H5 reproduces it on a `readOnly: true` document.

**Decision 1 (Bryan, `decisions.md:10`):** the no-arg call **lists** the sidecar as an entry and never restores; the sidecar restore path honours `readOnly`.

## Fix

Delete the private restore. The sidecar becomes an ordinary **named** backup, restored through the one guarded path, `restoreDocumentFromBackup` (`src/server/documents/reload-family.ts:220`) — which already checks `source !== "file"`, `RESTORE_FORMATS`, `readOnly`, `isReloadInProgress`, snapshots the current bytes, runs the `#1749` triple (`suppressNextChange` → `atomicWriteBuffer` → `recordSelfWrite`, `rearmWatch` in the inner `finally` — CLAUDE.md's file-watcher gotcha; **`recordSelfWrite` before `rearmWatch`**, and the existing arg-expression equality in `document-write-rearm.test.ts` must keep holding), reloads via `reloadFromDisk`, and re-baselines `Y_MAP_SAVED_AT_VERSION` under `withInternal` (Critical Rule 2 — no new Y.Doc write is added here).

1. **`src/server/file-io/doc-backup.ts`** — one new pure export, no fs:
   `export function docxSidecarBackupPath(filePath: string): string | null` → `filePath.replace(/\.docx$/i, ".backup.docx")` when the path ends `.docx` (case-insensitive), else `null`.
   - It serves the **two read/list sites only**: the list-mode append in `docx-apply.ts` (item 3) and the sidecar resolution in `reload-family.ts` (item 2). **`applyChangesCore`'s literal at `docx-apply.ts:331` is deliberately excluded** — that expression is `resolvedBackupPath ?? filePath.replace(…)` (a caller-supplied `backupPath` may override it) and it is immediately realpath-canonicalized on the parent at `:333-336`; substituting a `string | null` helper there makes `defaultBackup` nullable and drops the override branch. So there are three literals today, not two, and one of them stays.
   - Consequence worth one sentence in the PR body: the read side derives the sidecar name **without** canonicalizing the parent, so where a parent component is a symlink the write side and the read side can disagree about which file the sidecar is. Pre-existing, unchanged by this fix, and not something the `O_NOFOLLOW` leaf guard addresses.
   - Re-point the comment at `docx-apply.ts:364-367` ("`tandem_restoreBackup`'s .docx fallback derives that name and derives it only, so a uniquified sidecar is write-only") at `docxSidecarBackupPath` and the list-mode append. The invariant still holds — only the default-named sidecar is listed and restorable — but the branch it names no longer exists.
   - **The `docxSidecarBackupPath` import in `reload-family.ts` must join the existing `../file-io/doc-backup.js` import statement at `:48`.** `tests/docs/documents-boundary.test.ts:412` asserts FAN_OUT by exact equality with the row `server/documents/reload-family.ts -> server/file-io/doc-backup.ts (value) x1`, and the count is per import **statement** — a second statement makes it x2 and goes red.
2. **`reload-family.ts` `restoreDocumentFromBackup`** — resolution and read:
   - `const sidecarPath = isDocx ? docxSidecarBackupPath(existing.filePath) : null;`
     `const useSidecar = sidecarPath !== null && backupName === path.basename(sidecarPath);`
     `const snapshotPath = useSidecar ? sidecarPath : docBackupSnapshotPath(existing.filePath, appDataDir, backupName);` (unchanged `null` → `FILE_NOT_FOUND`). The two namespaces cannot collide: `SNAPSHOT_TAIL_RE` requires `-YYYYMMDD-HHMMSS-<hex8>`, which `<name>.backup.docx` never matches.
   - Reading the sidecar keeps the **O_NOFOLLOW open-then-read** currently in `docx-apply.ts`, moved into a module-local helper in `reload-family.ts` **with its comment block intact**. This is load-bearing, not cosmetic: `fs.readFile` follows symlinks, so a plain read here would re-open the vulnerability that block documents — and it would re-open it on `POST /api/backups/restore` too, which reaches `restoreDocumentFromBackup` with a caller-supplied `backup` name. Keep the Windows asymmetry note (`O_NOFOLLOW` undefined → `lstat` fallback).
     The move is not literally verbatim in one respect: the two refusals currently `return mcpError("INVALID_PATH", …)`, and `reload-family.ts` has no `mcpError`. They become `throw Object.assign(new Error(…), { code: "INVALID_PATH" })`, and the existing `finally { await handle.close(); }` still runs on the throw path. `ENOENT` throws the existing `FILE_NOT_FOUND`.
   - Extend `restoreDocumentFromBackup`'s own coded-error JSDoc at `reload-family.ts:214`: `INVALID_PATH` now has a second producer, so the line reads `INVALID_PATH — upload:// / scratchpad source, or a symlinked .docx sidecar`. `sendApiError` maps it to 400 for `POST /api/backups/restore` (`src/server/mcp/routes/_shared.ts:137-148`), which is unchanged.
   - Everything downstream is untouched, so the sidecar restore now also gets `assertDocxWithinSizeLimits` and a pre-restore snapshot of the current bytes.
   - Security note for the PR body and `docs/security.md`: the sidecar becomes a **parsed-and-reloaded** input rather than a byte copy — it flows through `assertDocxWithinSizeLimits` → `reloadFromDisk`, which re-parses the archive and re-injects Word comments as `import`-authored annotations. The sidecar lives in the user's document directory, writable by any local process, unlike snapshots under appDataDir. Net risk falls (the O_NOFOLLOW leaf read is preserved, the decompressed-size gate is added, and the *automatic* no-arg restore disappears), and the threat bound is identical to opening that file directly — but the new parse reachability is named here rather than discovered later.
3. **`docx-apply.ts` `tandem_restoreBackup`** — the whole `if (docState.format === "docx") { … }` block is deleted. In the surviving shared list branch, append the sidecar **immediately after `listDocBackups` and BEFORE the `backups.length === 0` check** (`docx-apply.ts:632-639`): appending after that guard would answer `FILE_NOT_FOUND` for exactly the case Decision 1 exists for — `.docx`, sidecar present, zero snapshots. The append is `docState.format === "docx"` → `docxSidecarBackupPath(filePath)` → `fs.lstat` → push `{ name: path.basename(sidecar), timestamp, size }` only when `st.isFile()` (a symlinked sidecar is not listed; any error is swallowed — a missing sidecar is the normal case), then re-sort newest-first by `timestamp` so the response's own "listed newest first" sentence stays true. The empty-list `FILE_NOT_FOUND` arm is reached only when snapshots **and** sidecar are both absent, and its message gains a `.docx`-only sentence naming the `{name}.backup.docx` sidecar. Non-`file` sources keep returning `FORMAT_ERROR` in list mode — in the **shared branch's wording** ("Uploaded documents and scratchpads have no on-disk **backups**."); the `.docx`-specific phrasing at `:522-526` ("no on-disk backup **file**.") is dropped with the block. No test pins either string.
4. **`docx-apply.ts` catch arm** — split the fold: `INVALID_PATH → mcpError("INVALID_PATH", e.message)`, `UNSUPPORTED_FORMAT → mcpError("FORMAT_ERROR", e.message)`. Reason: the symlink refusal now arrives as a thrown `INVALID_PATH`, and the existing security test asserts the tool answers `INVALID_PATH` — folding it to `FORMAT_ERROR` would silently weaken a pinned security assertion. Side effect, stated in the PR body, pinned by spec 6 below and narrowed in the docs: a named restore on an upload-source document answers `INVALID_PATH` instead of `FORMAT_ERROR` (list mode is unchanged).
5. **Docs** — four surfaces, all doc-review only (no test reads any of them; see "Done when"):
   - **Tool description** (`docx-apply.ts:490-499`) — drop "For .docx with no snapshots yet, falls back to the {name}.backup.docx sidecar written by tandem_applyChanges"; say the list includes it and it restores by name.
   - **`docs/mcp-tools.md:840-872`** — rewrite the `.docx` bullet at `:844` from "calling without `backup` restores the sidecar" to "the list includes the `{name}.backup.docx` sidecar written by `tandem_applyChanges`; restore it by name like any snapshot". Rewrite the `**Errors:**` line at `:867` — it currently reads "`FORMAT_ERROR` for upload-source documents or unsupported formats", which item 4 makes wrong for a named restore — to: **`FORMAT_ERROR` for upload-source documents in list mode, or unsupported formats; `INVALID_PATH` for a symlinked sidecar or an upload-source document called with `backup`.** Rewrite the `.docx` note at `:870` (it describes the deleted copy-back). `GET /api/backups` deliberately keeps listing snapshots only: the palette action restores `backups[0]`, and adding the sidecar there would change which bytes that button writes. Say so in the docs note.
   - **`docs/gotchas.md:160`** — the pre-overwrite-backups gotcha states the deleted mechanism as current fact: "The `tandem_restoreBackup` MCP tool exposes these snapshots for `.docx` too, falling back to the `{name}.backup.docx` sidecar (written by `tandem_applyChanges`) **only when no snapshot exists**." Both halves become false. Rewrite to "lists the `{name}.backup.docx` sidecar alongside the snapshots; it restores by name through `restoreDocumentFromBackup` like any snapshot". CLAUDE.md's "Files, Sessions & Lifecycle" bullet routes readers here for this subsystem, so leaving it is a live wrong instruction.
   - **`docs/security.md:189`** — the symlink-pair entry's precondition sentence "for the restore half, an empty doc-backups store for that file (a freshly started server)" no longer bounds the (still-mitigated) path, since the sidecar is restorable by name at any snapshot count. Narrow that clause and add the one-line note from item 2 (the sidecar is now a parsed-and-reloaded input, threat bound identical to opening that file directly).
   - `skills/tandem/SKILL.md:121` describes the generic list/restore shape and stays true — **no skill version bump**.

No new tool and no new `/api` route, so the license-gated set is unchanged (`tandem_restoreBackup` is already `gatedTool`); `NON_LOOPBACK_ALLOWED` untouched; no `data-testid`.

## Not in scope

**A `readPendingConflict` refusal inside `restoreDocumentFromBackup`.** The authority is `decisions.md:10`, and Decision 1 names `readOnly` only. Snapshot restores have never taken a conflict check — `restoreDocumentFromBackup` (`reload-family.ts:220-300`) has no `readPendingConflict` call, and the only two call sites of that function are `reloadDocumentFromMarkdown` (`:108`) and `resolveExternalConflict` (`:418`) — so adding one here would change `.md`/`.txt`/`.docx` restore behaviour beyond this issue, for every format at once. **Two tracked rows still assert the conflict check as part of this fix and must be edited in the same PR**, or #1768 closes with a defect its own ledger row enumerates left claimed-and-unfixed (CLAUDE.md: a criterion whose evidence lives where the judge cannot look fails silently):
