# A-rest — #1768 no-arg `tandem_restoreBackup` on a `.docx` restores the sidecar, ignoring `readOnly` and every safety check

Branch `fix/restore-and-close-ids-1768`. Closes #1768. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-mcp.md:19`; track row `tracks/A-stop-the-bleeding.md:19`. Probe: `docs/reviews/2026-09-02-v1-review/experiments/probe-tools.mts` case **H5**. Reviewer: `security-reviewer` (a write reachable from a tool).

## Problem

`src/server/mcp/docx-apply.ts`, `tandem_restoreBackup`: the `if (docState.format === "docx")` block owns the whole no-`backup` (list) case. When `listDocBackups` returns zero snapshots it falls through to a **second, private restore implementation** — `fs.open(sidecar, O_RDONLY|O_NOFOLLOW)` → `atomicWriteBuffer(filePath, backupBytes)` → `mcpSuccess("Restored …")`. That path never consults `docState.readOnly`, never takes the reload guard, never calls `snapshotBeforeFirstWrite`, never runs `suppressNextChange`/`recordSelfWrite`/`rearmWatch`, and never reloads the Y.Doc. The tool description and `docs/mcp-tools.md:844` both call the no-arg form "list". `tests/server/restore-backup.test.ts:619` pins the destructive behaviour; H5 reproduces it on a `readOnly: true` document.

**Decision 1 (Bryan, `decisions.md:10`):** the no-arg call **lists** the sidecar as an entry and never restores; the sidecar restore path honours `readOnly`.

## Fix

Delete the private restore. The sidecar becomes an ordinary **named** backup, restored through the one guarded path, `restoreDocumentFromBackup` (`src/server/documents/reload-family.ts:220`) — which already checks source/format/`readOnly`/`isReloadInProgress`, snapshots the current bytes, runs `assertDocxWithinSizeLimits`, runs the #1749 triple (`suppressNextChange` → `atomicWriteBuffer` → `recordSelfWrite`, `rearmWatch` in the inner `finally`; `recordSelfWrite` **before** `rearmWatch`), and reloads via `reloadFromDisk`. No new Y.Doc write, so no new origin tag.

1. **`src/server/file-io/doc-backup.ts`** — one new pure export, no fs:
   `export function docxSidecarBackupPath(filePath: string): string | null` → `filePath.replace(/\.docx$/i, ".backup.docx")` when the path ends `.docx` (case-insensitive), else `null`. It serves the **two read/list sites only** (items 2 and 3). `applyChangesCore`'s literal at `docx-apply.ts:331` is deliberately excluded — that expression is `resolvedBackupPath ?? filePath.replace(…)` and is realpath-canonicalized at `:333-336`; a `string | null` helper there drops the override branch.
   - **The `reload-family.ts` import must join the existing `../file-io/doc-backup.js` statement at `:48`** — `tests/docs/documents-boundary.test.ts:412` pins `reload-family.ts -> doc-backup.ts (value) x1` per import *statement*.
   - Re-point the comment at `docx-apply.ts:364-367` at `docxSidecarBackupPath` and the list-mode append; the invariant (only the default-named sidecar is listed/restorable) still holds.
2. **`reload-family.ts` `restoreDocumentFromBackup`** — resolution and read:
   - `const sidecarPath = isDocx ? docxSidecarBackupPath(existing.filePath) : null;`
     `const useSidecar = sidecarPath !== null && backupName === path.basename(sidecarPath);`

   - Reading the sidecar keeps the **O_NOFOLLOW open-then-read** currently in `docx-apply.ts:556-600`, moved into a module-local helper **with its comment block intact** (including the Windows `lstat`-fallback asymmetry). `fs.readFile` follows symlinks, so a plain read re-opens the vulnerability that block documents — on `POST /api/backups/restore` too. Two non-verbatim changes: the refusals `throw Object.assign(new Error(…), { code: "BACKUP_SYMLINK" })` instead of `return mcpError("INVALID_PATH", …)` (the precedent is `applyChangesCore`'s own collision, `docx-apply.ts:464-473`; `routes/_shared.ts:141` already maps `BACKUP_SYMLINK` to 400), and `ENOENT` throws the existing `FILE_NOT_FOUND`.
   - JSDoc: add one coded-error line `BACKUP_SYMLINK — the resolved .docx sidecar is a symbolic link`, and extend the summary at `:199-201` to name both namespaces (a snapshot under `{APP_DATA}/doc-backups/`, or the `.docx` `{name}.backup.docx` sidecar beside the document, selected by exact-basename match).
3. **`docx-apply.ts` `tandem_restoreBackup`** — delete the whole `if (docState.format === "docx") { … }` block. In the surviving shared list branch, append the sidecar **immediately after `listDocBackups` and BEFORE the `backups.length === 0` check** (`:632-639`) — appending after that guard would answer `FILE_NOT_FOUND` for exactly the case Decision 1 exists for. The append is `docState.format === "docx"` → `docxSidecarBackupPath(filePath)` → `fs.lstat` → push `{ name: path.basename(sidecar), timestamp: new Date(st.mtimeMs).toISOString(), size: st.size }` only when `st.isFile()` (a symlinked sidecar is not listed; any error is swallowed — a missing sidecar is the normal case). ISO spelling matches `doc-backup.ts:367`, so nothing compares mixed types.
   - **Append it LAST, after the mtime-sorted snapshots — do not re-sort the merged array.** The sidecar's `timestamp` is an attacker-settable mtime on a file in the user's document directory; a re-sort would let a local process take index 0 of a list the message tells an agent to trust. List-mode `message` becomes: **"Snapshots listed newest first; the `{name}.backup.docx` sidecar is listed last and is not a Tandem-managed snapshot."**
   - **Append it in the tool's own response mapping, never inside `listDocBackups` (`file-io/doc-backup.ts:355-377`)** — that function also serves `GET /api/backups`, which feeds the palette action that restores `backups[0]`. `GET /api/backups` is deliberately unchanged. Test 1's second assertion is what enforces this.
   - The empty-list `FILE_NOT_FOUND` arm is now reached only when snapshots **and** sidecar are both absent; its message gains a `.docx`-only sentence naming the `{name}.backup.docx` sidecar. Non-`file` sources keep `FORMAT_ERROR` in list mode, in the shared branch's wording ("no on-disk **backups**"); the `.docx`-specific phrasing at `:522-526` is dropped with the block. No test pins either string.
4. **`docx-apply.ts` catch arm** (`:653-663`) — one added line, no behaviour change: `if (e.code === "BACKUP_SYMLINK") return mcpError("INVALID_PATH", e.message);`, placed before the existing `INVALID_PATH || UNSUPPORTED_FORMAT → FORMAT_ERROR` fold, which is untouched.

## Tests

1. **Lists the sidecar alongside a real snapshot, and leaves the file alone.** `.docx`, `readOnly: false`, a real (non-symlink) sidecar **and one real snapshot** (`snapshotBeforeFirstWrite` + `_resetDocBackupGateForTests`, the idiom at `:718`/`:127`). **Order the fixture so the sidecar is the NEWER file**: write the sidecar *after* `snapshotBeforeFirstWrite`, then `await fs.utimes(sidecarPath, future, future)` with an mtime clearly newer than the snapshot's. `restoreTool({})` → `error: false`; `backups.map(b => b.name)` **equals** `[<snapshot name>, "report.backup.docx"]` — snapshot first, sidecar last, **even though the sidecar is newest**. That ordering is what makes the assertion discriminate item 3's fixed last position from a merge-then-re-sort (the shape `listDocBackups` itself uses, `doc-backup.ts:374`), which is the forbidden one: an attacker-settable sidecar mtime must not reach index 0 of a list the message tells an agent to trust. Without the `fs.utimes` step a re-sorting implementation passes whenever the snapshot happens to be newer — a sub-millisecond coin flip, and the likely fixture ordering. `fs.readFile(filePath)` still holds the modified bytes.

Together these kill a fix that stops restoring but forgets to list, a fix that lists and still writes, and the lazy "keep the `snapshots.length > 0` early return and append only in the zero-snapshot arm" shape.

## Review corrections (scope cut)

- **Spec 7, the static `O_NOFOLLOW` source pin** (regex or TS-AST assertions over `reload-family.ts` / `docx-apply.ts` text). It is a drift guard, not a behaviour test, and its positive half was the round-3 blocking finding — the round-2 regex `/fs\.open\((?:[^)]|\n)*O_NOFOLLOW/` cannot match the code item 2 mandates, because the flag is bound on the preceding line and `[^)]` cannot cross the argument list's `)`; the only spelling that satisfies it destroys the `noFollow` binding the Windows `lstat` fallback reads. **Deleting the pin makes that finding moot** rather than repairing it with a three-regex replacement. ## Review corrections (post-cut)

- **Spec 1's list-order assertion did not discriminate the mitigation it exists to protect.** Item 3 makes "append LAST, do not re-sort the merged array" the security control, and the scope cut deleted the `source:` marker precisely because "Item 3's fixed last position is the actual mitigation" — but spec 1 then refused to make the sidecar newer ("fixed position, not mtime-derived, so no `fs.utimes` step"). A merge-then-re-sort-by-mtime implementation (`doc-backup.ts:374`, `out.sort((a, b) => b.mtimeMs - a.mtimeMs || …)`, with `timestamp` derived from `st.mtimeMs` at `:366`) produces the same `[snapshot, sidecar]` order whenever the snapshot is the newer file, so the forbidden shape passed specs 1–5 green. Spec 1 now writes the sidecar last and bumps its mtime with `fs.utimes`; only a non-re-sorting append passes. The removed sentence is not a scope cut being reversed — no new spec, no new machinery, one fixture line.
