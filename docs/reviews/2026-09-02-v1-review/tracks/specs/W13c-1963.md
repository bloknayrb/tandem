# W13c — #1963 Active-annotation pulse class lost on decoration rebuild (Editor.svelte, #1824 item A)

Branch `fix/client-rail-pulse-outline-and-tutorial-fixes-2014`. Closes #1963 (and is one of the six carve-outs
keeping #1824 open — **no closing keyword for #1824**). Ledger:
`docs/reviews/2026-09-02-v1-review/areas/client-editor.md:26` (row citing `Editor.svelte:287-303`, item A of
#1824). Probe: the new unit spec below; the K-client group (#1966) cut this item as "needs a cross-cutting
mechanism rather than a same-file fix" and #1963 records the mechanism it wants.

## Problem

`src/client/editor/Editor.svelte:286-302` — the `$effect` that strips and re-applies
`.tandem-annotation-active` reads exactly two reactive inputs, `editor` and `activeAnnotationId`. The class is
written onto DOM nodes the **annotation decoration plugin** produced. When that plugin rebuilds its
decorations — the #1669 case, where y-prosemirror's `_typeChanged` replaces the PM doc and ProseMirror
re-renders the `[data-annotation-id]` spans — neither input changes, the effect does not re-run, and the
pulse class is silently gone from a still-active annotation. Nothing throws and nothing warns; the highlight
just stops.

## Fix

Exactly the mechanism #1963's body asks for. Two files.

**New `src/client/editor/deco-revision.ts`** — one pure, exported predicate and nothing else:

```ts
export function shouldBumpDecoRevision(tr: Transaction): boolean {
  return tr.docChanged || !!tr.getMeta(ySyncPluginKey) || !!tr.getMeta(annotationPluginKey);
}
```

`ySyncPluginKey` from `@tiptap/y-tiptap` and `annotationPluginKey` from `./extensions/annotation` — the same
two imports `extensions/annotation.ts:5,20` and `extensions/authorship.ts:6` already use, so no new dependency.
The gate exists because `transaction` fires on **every cursor move**; `docChanged` is the ordinary rebuild,
the `ySyncPluginKey` meta is the #1669 remote-sync replacement (`annotation.ts:347` keys on the same meta for
the same reason), and the `annotationPluginKey` meta is the plugin's own explicit rebuild signal. It is a
separate module purely so it is unit-testable without mounting a Tiptap editor.

**`Editor.svelte`:**

- `let decoRevision = $state(0);`
- A new `$effect` subscribing to the editor's `transaction` event, **bridged through `createCoalescingTick`**
  (`src/client/utils/coalescing-tick.ts`) — CLAUDE.md's Tiptap gotcha is load-bearing here and the reason this
  item was carved out: `transaction` is emitted synchronously from ProseMirror's `dispatch`, so a bare
  `decoRevision++` inside it throws `state_unsafe_mutation` **in production too**. The precedent is
  `FormattingToolbar.svelte:62-63` (identical shape: `transaction` → `createCoalescingTick` → tick counter).
  The filter runs **outside** the tick — `if (!shouldBumpDecoRevision(tr)) return; bump();` — so a burst of
  qualifying transactions still collapses to one write while a cursor-move burst schedules nothing at all.
  **Copy `FormattingToolbar.svelte:56-70` verbatim, including its three `isDestroyed` guards**, which the
  earlier draft dropped: capture `const ed = editor` and `if (!ed || ed.isDestroyed) return;` at effect entry
  (the reactive prop getter is null during tab switch — that file's comment says so); guard the deferred
  body, `createCoalescingTick(() => { if (!ed.isDestroyed) bump(); })`, because the tick fires in a microtask
  that can land after teardown and the pulse effect then touches `ed.view.dom`; and guard the cleanup.
  **The cleanup must be `return () => { if (!ed.isDestroyed) ed.off("transaction", handler); };`** — a bare
  `return ed.off(...)` returns the `Editor`, not a teardown function, and Svelte would call it. Use
  `editor.on/off`, matching the step-2 effect in `useTutorial.svelte.ts:135-140` and the
  `subscribeToUserName` effect at `Editor.svelte:281-285`.
- In the pulse effect at `:286`, read the counter: `void decoRevision;` on its own line with a comment naming
  why (a decoration rebuild re-creates the spans; neither `editor` nor `activeAnnotationId` moves). The
  `void x` form is the codebase's own idiom for a dependency-only read — `FormattingToolbar.svelte:130,136`.

Nothing else moves: the effect body, `CSS.escape`, the strip-then-add order and the null-id branch documented
at `:448` all stay. No `data-testid`, no Y.Doc write (so no origin helper), no colour.

## Tests

Two files: the pure-predicate unit specs, and one behavioural E2E. The E2E is **not optional** — without
it, an implementation that ships `deco-revision.ts` and wires the counter but omits the one-line
`void decoRevision;` read in the pulse effect is 5/5 green with #1963 entirely unfixed, and no test in
`tests/` renders `Editor.svelte`.

### `tests/client/deco-revision.test.ts` (new)

Plain vitest — no `@vitest-environment happy-dom` needed, nothing touches the DOM. Transactions are
hand-built plain objects (`{ docChanged, getMeta: (k) => ... }`) cast to `Transaction`, the shape
`annotation-decoration.test.ts` already uses for the same plugin.

1. `{ docChanged: true }`, no meta → `true`. Kills a predicate that only looks at meta.
2. `{ docChanged: false }` + `ySyncPluginKey` meta → `true`. Kills a `docChanged`-only gate, i.e. exactly
   the #1669 remote-sync rebuild the fix exists for.
3. `{ docChanged: false }` + `annotationPluginKey` meta → `true`. Kills dropping the plugin's own signal.
4. **`{ docChanged: false }`, `getMeta` returns `undefined` for everything → `false`.** The discriminating
   negative: without it a `return true` passes 1–3, and the cursor-move churn the gate exists to suppress
   comes back — every caret move would schedule a microtask and a DOM re-scan.
5. **A truthy non-`true` meta → `true`; a falsy non-`undefined` meta → `false`.** Two cases in one spec,
   and they must be written with those exact expectations rather than "reads consistently":
   - `getMeta(annotationPluginKey)` returns the real object shape,
     `{ type: "toggle-decorations", visible: { comment: true, highlight: false, note: true } }` → expect
     `true`. **This is the case that kills `=== true`.** The meta is typed
     `AnnotationToggleMeta | true | undefined` (`src/client/editor/extensions/annotation.ts:277`) and
     `App.svelte:1081` dispatches the object form, so a `=== true` comparison would drop every
     decoration-visibility toggle and silently reinstate the missing pulse.
   - `getMeta(annotationPluginKey)` returns `false` → expect `false`. Pins the `!!` coercion against a
     future `getMeta` returning `0`/`""`. **Round 1 called the `false` case a kill for `=== true`; it is
     not** — `!!false` and `false === true` are both `false`, so on its own it separates nothing. It is
     kept only as the falsy half of the pair.

Full re-apply behaviour is deliberately **not** unit-tested through this file (the issue says so): it needs a
real bound editor and a real y-sync replacement, and asserting a CSS class through
`decoration-survives-sync.test.ts`'s harness would be a second copy of it. The E2E below covers it instead.

### `tests/e2e/deco-pulse-survives-rebuild.spec.ts` (new), one spec

Shaped on `tests/e2e/decoration-survives-mcp-write.spec.ts`, which already drives a y-sync doc replacement
from an MCP write and asserts on `[data-annotation-id]` spans. Open a fixture with one annotation, activate
it (click its margin card / the annotation span, so `activeAnnotationId` is set) and assert
`.tandem-annotation-active` is present on the `[data-annotation-id]` spans. Then drive an `tandem_edit`
against an **unrelated paragraph** — an MCP write, so the rebuild arrives over y-sync exactly as #1669
describes — and `expect.poll` that `.tandem-annotation-active` is **still** on those spans afterwards.
**What it kills:** a wired counter with no `void decoRevision;` read in the pulse effect, which is the single
line the whole fix rests on, and which all five unit specs are blind to. It must be observed RED on stashed
master.

## Done when

`deco-revision.ts` exists with one export; `Editor.svelte` bumps through `createCoalescingTick` with the
three `isDestroyed` guards and a `() => {}` cleanup, and the pulse effect reads the counter via
`void decoRevision;`; the five unit specs pass, spec 4 goes red when the gate is replaced by `true`, and
spec 5's truthy-object case goes red when `!!` is replaced by `=== true`; the E2E spec passes on the fix and
is observed red on stashed master; `npm run typecheck` (incl. `svelte-check --fail-on-warnings`) and
`npx playwright test deco-pulse-survives-rebuild` green.

## Review corrections (round 1)

**Adopted**

- *Spec 5 is non-discriminating and its stated kill is false* (blocking, raised twice). A meta value of
  `false` answers identically under `!!` and under `=== true`. Spec 5 is rewritten as a pair: the real
  truthy `AnnotationToggleMeta` object → `true` (the case that kills `=== true`, and the one that matters,
  since `App.svelte:1081` dispatches exactly that shape) plus a falsy `false` → `false`, with both expected
  booleans stated outright so the spec cannot be written as a tautology.
- *No test covers the `void decoRevision;` read, so the fix's load-bearing line is untested* (blocking).
  Added `tests/e2e/deco-pulse-survives-rebuild.spec.ts`, modelled on
  `tests/e2e/decoration-survives-mcp-write.spec.ts`, and put it in Done when with a red-on-master
  requirement.
- *The effect drops the `isDestroyed` guards its own cited precedent carries* (non-blocking, raised twice).
  The Fix section now requires all three guards from `FormattingToolbar.svelte:56-70`, and corrects
  `return ed.off(...)` to `return () => { ... }` — the bare form returns the `Editor`, not a teardown.
