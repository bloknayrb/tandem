## Problem

**1 — push and pull disagree after a failed Accept.** `resolveAnnotation` in `src/client/panels/useAnnotationReview.svelte.ts` writes `withBrowser(y, () => map.set(id, { ...ann, status }))` FIRST, then calls `applySuggestion`, and on a `false` return writes `revertedToPending(ann)`. Both writes are `withBrowser`, so both reach the channel observer — but only the first produces an event: `src/server/events/observers/annotations.ts`'s `action === "update" && ann.author === "claude"` branch emits `annotation:accepted` for `status === "accepted"` and `annotation:dismissed` for `dismissed`, and has **no arm for a revert to `pending`**. Claude gets `annotation:accepted` on the push path and reads `pending` on every pull path. The failure is reachable through both of `applySuggestion`'s `false` returns (unresolvable range; `snapshotContradicts`, #1629), each already pinned in `tests/client/use-annotation-review.test.ts`.

**2 — `userActions` has no status gate.** In `processUnsurfacedInboxAnnotations` (`src/server/mcp/awareness.ts`), the user bucket admits `ann.author === "user" && ann.type === "comment" && isClaudeFacing(ann)` with no `status` test, while the Claude bucket next to it tests `ann.status !== "pending"`. **Reproduced** (in-memory, this branch): a `{author: "user", type: "comment", status: "dismissed", audience: "outbound"}` record lands in `userActions` with length 1. `audience: "outbound"` is not a contrivance — `sanitizeAnnotation` derives exactly that for a user comment (measured). The dedup ledger (`surfacedIds`) hides this while a server run lasts and `transitionPending` does not bump `editedAt`; it is a module-level `Map`, so **every server restart re-surfaces every resolved user comment as a fresh user action**, and a user edit of a resolved comment does the same within one run.

**2a — the gate must not create a NEW push/pull divergence (review round 1).** The observer's user-comment `update` arm (`src/server/events/observers/annotations.ts`, the `newEditedAt <= oldEditedAt` early return) emits `annotation:edited` on **any** `editedAt` advance with no status test: `narrowForChannel` requires only non-note + `audience: "outbound"`, both of which a dismissed user comment keeps. `transitionPending` explicitly leaves Dismiss "open to every non-private record, including a user's comment", and `editAnnotation` (`src/client/panels/annotation-actions.ts`) has no status gate either (`AnnotationCard.svelte` gates edit on `onEdit !== undefined`, not on `isPending`). So a bare `status === "pending"` gate would make *surface → Claude dismisses → user edits* emit `annotation:edited` on the channel while `tandem_checkInbox` returned nothing — item 1's own defect class, newly created. The fix below therefore gates on `status === "pending" || edited`, which keeps the edit visible on both surfaces and suppresses only the unedited restart re-surface. The observer is **not** changed.

**2b — REFUTED as posed.** The issue adds "`tandem_resolveAnnotation` accepts user highlights (no author guard)". #1803 closed that: `transitionPending` gates on `isWithheldFromClaude` (= `!isClaudeFacing`), and every user highlight is `audience: "private"` after sanitize's user-scoped demotion, so it answers `invalid-note`. Pinned by `tests/server/adr027-note-write-guards.test.ts` → "refuses a user's private HIGHLIGHT on resolve and remove (#1803 residual)". No change; record it in the PR body.

**3 — REFUTED as posed.** The observation (concurrent `map.set` on one key resolves by clientID, `experiments/yjs-race.ts`) is correct and is Y.Map's defined LWW semantics. The proposed remedy — "a `version` field with compare-and-set on the write helpers" — cannot hold in a CRDT: two clients both read version *N*, both write *N + 1*, and Yjs still resolves by clientID; there is no atomic read-modify-write across peers, so the field would report a false guarantee. The two named symptoms are also already bounded: browser-Accept vs Claude `editPending` is closed by `editPending`'s `status !== "pending"` refusal once the accept syncs (the residue is sync latency, which no per-key version removes), and force-reload-clear vs browser-Accept is force-open's documented destructiveness, decided in #1827 C and tracked in #1813. Fixing this properly means an authority change (server-serialized annotation writes), which is a design decision, not a Low. Listed under `bryan`; no code.

**4 — not this issue's.** `user-guide.md:296` "held back from the document" and the Solo `tandem_comment` copy are #1779's, as the issue body itself says.

## Fix

**Item 1 — `src/client/panels/useAnnotationReview.svelte.ts`, `resolveAnnotation`.** Apply first, write the status once, only on success — and keep the failure write, which is doing a second job:

```ts
if (status === "accepted" && ann.suggestedText !== undefined) {
  const editor = getEditor();
  if (editor && !applySuggestion(ann, editor, y, getFormat?.())) {
    // Normalizing write, NOT a status change: the record is still `pending`, so
    // the observer's claude-update arm has no matching case and emits nothing.
    // What it does do is strip a stale `resolvedBy` (#1770) — see below.
    withBrowser(y, () => map.set(id, revertedToPending(ann)));
    onApplyFailed?.(ann);
    return;
  }
}
withBrowser(y, () => map.set(id, { ...withoutResolver(ann), status }));
```

- **Do not replace the failure branch with a bare `return`.** `tests/client/use-annotation-review.test.ts:281` ("strips it on the apply-failure revert too, which is the other write") seeds a **pending** record already carrying `resolvedBy: "claude"`, calls `resolveAnnotation(id, "accepted")` on an unresolvable range, and asserts the stored `resolvedBy` is `undefined` — a #1770 regression pin. Writing nothing on failure turns it red, and the substantive loss is worse than the red: `revertedToPending` (`useAnnotationReview.svelte.ts:525-528`) is the only thing that strips the stamp, `src/shared/sanitize.ts:144-146` carries it through sanitize, and `src/server/mcp/awareness.ts:703` excludes `resolvedBy === "claude"` from `userResponses` — so the user's next successful accept would be reported to nobody, forever. Keeping the write costs one no-op-status transaction on a failure path and preserves the pin **unchanged**.
- **Extract `withoutResolver`, and route both writes through it.** `function withoutResolver(ann: Annotation): Omit<Annotation, "resolvedBy"> { const { resolvedBy: _stale, ...rest } = ann; return rest; }`, with `revertedToPending(ann)` becoming `{ ...withoutResolver(ann), status: "pending" }` and its #1770 docblock moved onto `withoutResolver` (both call sites now depend on it). This closes the residual half of #1770 the two revert sites never covered: the **success** write also inherits a stale stamp today (`{ ...ann, status }`), and nothing on the client ever stamps `resolvedBy: "user"` — `src/server/annotations/lifecycle.ts:963` is the only writer of the field and only ever writes `"claude"` — so an unstamped record is exactly what `userResponses` requires. `revertedToPending` stays a named function: `undoResolveAnnotation` still calls it, and after this change it is that path's only caller.
- Emitting a compensating event was the other option in the issue; it is bigger (a new wire type through `events/queue.ts`, `delivery-state.ts` and the channel schema) and still leaves a window in which push and pull disagree. Rejected; state it in the PR body.
- `applySuggestion` reads only its `ann` argument and the editor state — never the map's `status` — so the reorder is safe by construction. The "THREE SEPARATE ONE-STATEMENT TRANSACTIONS" rule is preserved: still no wrap spanning the block, so y-prosemirror's own transaction never inherits our origin and `yUndoPlugin` keeps capturing the accepted text.
- `withBrowser` stays because this is the user's action and Critical Rule 2 requires every Y.Doc write to be tagged. It is **hygiene, not what makes the write reach the channel**: client origins never cross the wire — Hocuspocus re-tags every incoming update with the `Connection`, as `src/client/panels/annotation-actions.ts:100-110` and CLAUDE.md Critical Rule 2 both state — so both client writes reach the observer regardless of the tag.
- **The reorder inverts one strand direction; record the bound.** Today a throw or a late failure inside `applySuggestion` leaves the record `accepted` with nothing applied; after the reorder it leaves the record `pending` with the text possibly already applied (`applySuggestion`'s outer `catch` converts a mid-dispatch throw into `return false`, and the editor transaction may already have landed). A second Accept would then re-apply. Bounded: `snapshotContradicts` (#1629) refuses any record carrying a `textSnapshot`, so only the snapshot-less legacy arm (the "UNVERIFIED" warn) is exposed, and to a strictly smaller window than the accepted-with-nothing-applied state it replaces.
- **THREE docblocks become false or misleading and must change in the same commit** (verify cross-references):
  1. `applySuggestion`'s guard-inside-the-`try` rationale (`useAnnotationReview.svelte.ts:335-337`): "`resolveAnnotation` has already written `status: "accepted"` and only reverts on a `false` RETURN, so a throw escaping here would strand the annotation accepted" — after the reorder nothing has been written when it runs, so a throw strands the record `pending`; say that, and say what it can strand instead (applied text under a pending record, bounded by #1629 as above).
  2. `UseAnnotationReviewOptions.onApplyFailed` (`:443`): "The annotation has already been reverted to `pending` by the time this fires" — it was never moved off `pending`; the write that precedes the call only normalizes the record (strips a stale `resolvedBy`).
  3. `resolveAnnotation`'s own idempotency comment (`:536-540`): "critically, prevents `applySuggestion` from running twice and inserting the suggested text twice." That protection was bought by the write-first order. The guard now covers a double-fire from a **later task** only — `applySuggestion` is fully synchronous and the map still reads `pending` for its whole duration, so a re-entrant call inside the apply is no longer refused by it. No such path exists today (the only bulk caller, `SidePanel.svelte`, iterates distinct ids); say so rather than deleting the comment.

**Item 2 — `src/server/mcp/awareness.ts`, `processUnsurfacedInboxAnnotations`.** Hoist the ledger read above the bucket branch and gate the user-comment arm on it:

```ts
const key = inboxLedgerKey(documentId, ann);
const lastSurfacedEditedAt = surfaced.get(key);
const edited = lastSurfacedEditedAt !== undefined && (ann.editedAt ?? 0) > lastSurfacedEditedAt;

if (
  ann.author === "user" &&
  ann.type === "comment" &&
  isClaudeFacing(ann) &&
  (ann.status === "pending" || edited)
) {
```

with the existing body reusing `key` and `edited` (the `channelKey` line and the `surfaced.set` are otherwise unchanged).

- **`|| edited` is load-bearing, not defensive** — it is what stops the gate creating the new divergence in **2a**. A user who edits a comment Claude already dismissed still surfaces, with `edited: true`, matching the `annotation:edited` the observer emits unconditionally. Only the case with no edit — the module-level ledger lost on restart — is suppressed.
- **The gate must be a term of the `if` condition, never a check inside the block**, for the same reason as the Solo hold's `continue`: a record that fails it must take no `surfaced.set`, or the ledger is poisoned and the record is permanently dedup-skipped. Its position *among* the conjuncts is immaterial — all four terms are pure predicates over `ann` — and the `else if` chain already guarantees a rejected user record reaches no other `surfaced.set`, since the second arm requires `author === "claude"`.
- Update the branch comment to name the gate, the `|| edited` rationale, and the symmetry with the Claude bucket's `status !== "pending"`. No origin helper involved — this path only reads.
- **`docs/mcp-tools.md:1101` becomes false and changes in the same commit.** It reads "`userActions`: new or edited user comments…". Amend to "new or **edited** user comments — a comment is admitted while its `status` is `pending`, or on any later edit whatever its status (the `edited` half is what keeps this bucket in step with the unconditional `annotation:edited` channel event)", and note the symmetry with `userResponses`' `status !== "pending"`. Nothing in `tests/docs/` pins this sentence, so it drifts silently if the commit forgets it.
- **`tests/server/inbox-ledger-undo.test.ts`'s file header becomes stale** and is amended in the same commit: "User comments keep the bare-id key: their bucket is `userActions`, whose whole re-surface rule is the `editedAt` comparison" — the bare-id key is still correct, but first surfacing is now also gated on `status === "pending"`. Amend the sentence; do not delete it.
