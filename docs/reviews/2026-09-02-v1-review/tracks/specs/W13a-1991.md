# W13a — #1991 `activity.selectionAt` is re-stamped when a remote edit shifts a lingering selection

Branch `fix/activity-awareness-honesty-1918`. Closes #1991, and discharges the "Remaining" half of #1624 (which stays open — see `W13a-1624.md`). No review ledger row; #1991 was filed out of the G10 group (sweep ledger `docs/plans/2026-09-06-open-issues-sweep.md:470`). Probe: the issue's own measurement, already a spec — `tests/client/activity-cursor-flat.test.ts:238`, row (c), which pins today's re-stamp and is inverted here.

## Problem

`src/client/editor/extensions/awareness.ts:188` rewrites `Y_MAP_SELECTION` whenever `!state.selection.eq(prevState.selection)`, always with `timestamp: Date.now()`. A remote Y change rebuilds the document and `restoreRelativeSelection` moves a lingering selection's absolute positions, so `eq` fails and the record is re-stamped as if the user had just selected. Measured in the issue: a 20-minute-old selection of `three` reports as milliseconds old after a remote insert above it. `activity.selectionAt` (#1624, shipped in #1996) therefore cannot be read as "when the user selected", and every surface carries a caveat saying so — including one telling Claude that *its own* `tandem_edit` re-stamps the user's selection.

## Fix

Land on top of #1918, which introduces the `isRemoteChange` binding (`ySyncPluginKey.getState(state)`, `isChangeOrigin && !isUndoRedoOperation`) at the top of `update()`; this change consumes it. In the **non-empty** selection arm only:

- Add one closure variable beside the existing timers, `let lastSelectionStamp: number | null = null`.
- Compute the stamp at `update()` time **and assign `lastSelectionStamp` there too, not in the debounce callback**. In the non-empty arm, immediately:

  ```ts
  const prev = userAwareness.get(Y_MAP_SELECTION) as { timestamp?: number } | undefined;
  const carried =
    lastSelectionStamp ?? (typeof prev?.timestamp === "number" ? prev.timestamp : Date.now());
  const stampedAt = isRemoteChange ? carried : Date.now();
  lastSelectionStamp = stampedAt;
  ```

  and capture **only** `timestamp: stampedAt` in the `setTimeout` closure. The read is a plain `Y.Map` get inside `update()`, outside any transaction, so Critical Rule 2 is untouched (the write stays in `withBrowser`). The shifted `from`/`to` and the re-read `selectedText` are still written: those positions are real and the server slices `selectedText` from them.
- **Why the assignment must not live in the callback:** the write is 150 ms debounced and a later `update()` clears the pending timer. If `lastSelectionStamp` were only set when the timer fires, a fresh local selection made at t1 but not yet written would leave it holding the *previous* selection's stamp; a remote edit arriving 50 ms later would clear that timer, re-arm with `stampedAt = lastSelectionStamp`, and publish the t1 selection carrying the old t0 — `selectionAt` reporting a 20-minute-old time for a selection made 50 ms ago, i.e. this issue's own honesty defect inverted. Assigning at `update()` time means the variable always describes the newest selection the user has made, written or not.
- **Gate on remoteness alone, not on "`selectedText` unchanged"** as the issue body sketched. `selectionAt` answers "when did the user last make this selection"; a remote edit that mutates text *inside* the selection is no more a user selection than one above it, and the text comparison would need the previous string kept in the closure for no behavioural gain. The issue's stated acceptance (a remote insert before a lingering selection shifts `from`/`to` and leaves `timestamp` unchanged) holds under either gate.
- **The fallback chain, in order:** `lastSelectionStamp`, then the `timestamp` already on the `Y_MAP_SELECTION` record, then `Date.now()`. Reading the existing record first is what keeps a reload-then-remote sequence from minting a fresh stamp for a selection the user made before the reload — that would be this issue's defect on the one path the fallback exists for. `Date.now()` remains only as the last resort so a number rather than `undefined` is written (the schema takes `number | null` and `src/server/mcp/awareness.ts:524` already nulls `selectionAt` for a record with no numeric timestamp). The precision claim to make is the accurate one: `lastSelectionStamp` is set on every `update()` that reaches the non-empty arm, so after any selection this client has *observed* it is set; the remaining fallback path is a fresh client instance (reload) seeing a remote remap first, which the record read covers.
- The **collapsed** arm is untouched. A remote collapse writes `from === to`, which makes the server report `selectedText: null` and `selectionAt: null` regardless of the timestamp, so stamping it changes nothing observable and guarding it would be a second mechanism for a value no surface reads.

Rules: Critical Rule 1 (`Y_MAP_SELECTION` from `shared/constants`), Critical Rule 2 (the write stays in `withBrowser`; `pmSelectionToFlat` runs outside it). No `$state`, so the `createCoalescingTick` rule does not apply.

## Tests

`tests/client/activity-cursor-flat.test.ts`, the `Y_MAP_SELECTION lifetime (#1624)` block:

1. **Invert row (c)** and rename it to "a remote edit that shifts a lingering selection does NOT re-stamp it (#1991)": same 20-minute advance and remote insert, then `expect(after.from).toBe(before.from + 2)` **and** `expect(after.timestamp).toBe(t0)`. Both assertions together are the discriminator: `from` kills a fix that suppresses the write entirely (the offsets would go stale and `selectedText` would be sliced wrong), `timestamp` kills today's behaviour. Delete the "when #1991 lands…" comment.
2. **A user selection still stamps now.** After the remote shift above, select a different span locally, advance 200 → `timestamp` is `Date.now()` at selection time and strictly greater than `t0`. Kills a fix that freezes the first stamp forever (e.g. writing `lastSelectionStamp` unconditionally).
3. **A remote edit BELOW the selection does not move it, so nothing is written at all.** "After" here is positional, never temporal — an insert downstream of the selection leaves `state.selection.eq(prevState.selection)` true at `src/client/editor/extensions/awareness.ts:188` and the arm never runs. Assert `toStrictEqual` the pre-existing record. Row 1 (a remote edit **above** the selection) asserts the opposite and must stay the opposite: it *does* write, with shifted offsets and a frozen timestamp. Do not read this row as "a remote edit writes nothing" — that reading would push the fix toward suppressing the write entirely, which is exactly the failure row 1 exists to catch.
4. **A fresh local selection inside the 150 ms debounce keeps its own time.** Select span A and let the write land; advance 20 minutes; select span B locally (t1) and, 50 ms later — before the debounce fires — deliver a remote insert above it; advance 300 → the published `timestamp` is t1, **not** span A's t0. This is the only row that kills assigning `lastSelectionStamp` inside the debounce callback instead of at `update()` time.
5. Rows (a), (b), (d), (e) stay green unchanged; (a) already asserts only `typeof timestamp === "number"`, so moving the stamp from write time to selection time does not touch it.

No server test changes: `tests/server/mcp-tool-integration.test.ts`'s `selectionAt` rows read a hand-written `Y_MAP_SELECTION` record and are unaffected.
