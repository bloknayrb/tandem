# W13a — #1991 `activity.selectionAt` is re-stamped when a remote edit shifts a lingering selection

Branch `fix/activity-awareness-honesty-1918`. Closes #1991, and discharges the "Remaining" half of #1624 (which stays open — see `W13a-1624.md`). Non-review issue, no ledger row. Probe: `tests/client/activity-cursor-flat.test.ts:238`, row (c), which pins today's re-stamp and is inverted here.

## Problem

`src/client/editor/extensions/awareness.ts:188` rewrites `Y_MAP_SELECTION` whenever `!state.selection.eq(prevState.selection)`, always with `timestamp: Date.now()`. A remote Y change rebuilds the document and `restoreRelativeSelection` moves a lingering selection's absolute positions, so `eq` fails and the record is re-stamped as if the user had just selected. Measured in the issue: a 20-minute-old selection reports as milliseconds old after a remote insert above it. Every surface therefore carries a caveat saying `selectionAt` cannot be trusted — including one telling Claude that its own `tandem_edit` re-stamps the user's selection.

## Fix

Lands on top of #1918, which introduces the `isRemoteChange` binding at the top of `update()`. In the **non-empty** selection arm only:

- Add one closure variable beside the existing timers: `let lastSelectionStamp: number | null = null`.
- Compute the stamp at `update()` time and assign it there — **not** in the debounce callback:

  ```ts
  const stampedAt = isRemoteChange ? (lastSelectionStamp ?? Date.now()) : Date.now();
  lastSelectionStamp = stampedAt;
  ```

  and capture **only** `timestamp: stampedAt` in the `setTimeout` closure. The shifted `from`/`to` and the re-read `selectedText` are still written: those positions are real and the server slices `selectedText` from them.
- **Why the assignment cannot live in the callback:** the write is 150 ms debounced and a later `update()` clears the pending timer. If `lastSelectionStamp` were set only when the timer fires, a fresh local selection made at t1 but not yet written would leave it holding the previous selection's stamp; a remote edit 50 ms later would clear that timer, re-arm with the old value, and publish the t1 selection carrying t0 — this issue's defect inverted. Assigning at `update()` time means the variable always describes the newest selection the user has made, written or not.
- **Gate on remoteness alone**, not on "`selectedText` unchanged" as the issue body sketched. A remote edit that mutates text *inside* the selection is no more a user selection than one above it, and the text comparison would need the previous string kept in the closure for no behavioural gain.
- `?? Date.now()` is the only fallback, and it is reachable on exactly one path: a fresh client instance (reload) whose first observed selection change is a remote remap. That mints a stamp for a selection made before the reload, which is a residue this fix does not remove — reading the previous record back off the `Y.Map` to carry it is a second mechanism the issue does not ask for.
- The **collapsed** arm is untouched. A remote collapse writes `from === to`, which makes the server report both `selectedText` and `selectionAt` as null regardless of the timestamp.

Critical Rule 1 (`Y_MAP_SELECTION` from `shared/constants`), Critical Rule 2 (the write stays in `withBrowser`; `pmSelectionToFlat` runs outside it). No `$state`.
