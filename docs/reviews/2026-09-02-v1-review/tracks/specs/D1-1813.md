# D1 — #1813 force-open and source-view commit unlink the on-disk annotation envelope

Branch `fix/markdown-fidelity-1753`. Closes #1813, implementing [decision C](../../decisions.md) (Bryan, 2026-09-06, recorded as a comment on the issue). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:26`. Probe: none exists; this spec writes one (the track file says "none; write one").

## Problem

`src/server/documents/populate.ts`, `clearAndReload` step 0:

```ts
const dropped = clearFileSyncContext(id);
if (dropped) {
  try { await dropped.store.clear(); } catch (err) { … }
}
```
`store.clear()` is `clearOne(docHash)` in `src/server/annotations/store.ts`, whose body is `await fs.unlink(filePathFor(docHash))` — the durable envelope `<annotations-dir>/<docHash>.json` is deleted from disk, taking the user's **personal notes** (ADR-027) with it. The pre-overwrite document backup covers the text, not the envelope, so there is no copy.

Two callers reach it, and neither is "the user asked to delete their notes":

- `documents/open.ts` — `tandem_open` with `force: true` ("reload from disk", used to recover from a bad state).
- `documents/reload-family.ts` `reloadDocumentFromMarkdown` — the **source-view commit** path, where the user edited the text and expects annotations that still match to survive.

Decision C takes option 2 from the issue body: clear only the in-memory map; let the next open re-anchor from `textSnapshot`.

## Fix

**1. `populate.ts`: delete the `store.clear()` call and its try/catch; keep `clearFileSyncContext(id)`.** The detach is still load-bearing for its *other* stated reason — the durable observer must not queue a write that snapshots the mid-clear Y.Maps — and dropping it would persist the empty map, which is the same data loss by another route. Rewrite the step-0 comment to say exactly that, and why the envelope now survives: the caller re-wires the store immediately afterwards (`wireAnnotationStore` → `loadAndMerge`), the repopulated Y.Doc is a new CRDT lineage so every merged `relRange` resolves to null, and `refreshRange` re-anchors from the stored flat range **only when `storedRangeStillMatches` holds** (#1764) — a record whose `textSnapshot` no longer matches answers `degraded`, writes nothing, and surfaces as `anchor: "degraded"` on `tandem_getAnnotations`. That gate is why re-merging into changed content is safe and why this fix must not add a re-anchor pass of its own.

**2. `documents/annotation-wiring.ts`:** the `allowRecovery` comment claims "Force-reload (`clearAndReload`) deliberately clears the envelope and must NOT resurrect a stale orphan." The code is unchanged (the force path still passes no `allowRecovery`, so rename-recovery still does not run there) but the stated reason is now false. Reword to the real one: recovery is a first-open-only heuristic, and a force-reload of an already-open document has its own envelope.

**3. Docs, in the same PR.** Each of these currently asserts the deleted behaviour and would otherwise become a false claim someone acts on:
- `CLAUDE.md`, Y.js/CRDT gotcha — the bullet beginning "**`tandem_open` with `force: true` clears annotations, awareness and content in one transaction — and it also DELETES the durable annotation envelope from disk**". Replace with: the clear is in-memory only; the envelope survives and re-merges on the same open, re-anchored where the snapshot still matches and `degraded` where it does not; #1813 is decided, not open. Leave the ADR-027 "bulk clears still take notes with everything else" sentence in Key Patterns — it is about the guard not applying to a bulk clear, which is still true of the in-memory clear — but append that force-open's notes come back with the envelope.
- `docs/gotchas.md:90` "Force-reload clears in-place… annotations are still lost."
- `docs/mcp-tools.md:64` — the `LICENSE_REQUIRED` row justifies gating force-open with "it runs `clearAndReload`, which wipes the durable annotation file". **The gate stays** (force-open still replaces content and clears the Y.Maps; Critical Rule 9 — do not remove a row from the gated set); only the reason changes.
- `docs/mcp-tools.md:116`, `:150`, `:1320` — "Clears annotations and session" is now wrong; annotations return re-anchored. `:1553` (the smoke line "verify content/annotations clear-and-repopulate") gets the same correction.

Rules that bite: no new Y.Doc write is introduced, so no origin-helper choice and no `audit:origins` change; no Y.Map key; no MCP tool or `/api` route added or removed, so both license-gate coverage tables stay as they are; **no error code changes**, so `docs/mcp-tools.md`'s `**Errors:**` lines need no edit (only the prose rows above).

## Tests

New `tests/server/force-open-envelope.test.ts`:

1. **The killer.** Seed a durable envelope containing a `note` and a `comment` whose `textSnapshot` still matches the file; run `clearAndReload` for that document; assert the envelope file **still exists on disk** and, after the caller's `wireAnnotationStore`, both records are back in `Y.Map('annotations')`. A fix that merely moved the `unlink` behind a flag, or that cleared the map after the merge, fails this.
2. **Notes specifically** — asserted separately from comments, because ADR-027 notes are the loss the issue is filed about and a read filter that hid them would make a comments-only assertion pass.
3. **Source-view commit** — the same assertion driven through `reloadDocumentFromMarkdown`, not through force-open. Both callers share the line being changed, but only a two-caller test proves the source-view path (the one the issue calls "safer" and the one where the user *just edited the text*) is covered.
4. **Changed content → `degraded`, not resurrection at a wrong offset.** Reload with markdown that no longer contains the annotated span; the record survives, and `refreshRange`/`tandem_getAnnotations` reports `anchor: "degraded"` with the stored flat range and `relRange` intact. This is the spec that stops a "helpful" re-anchor pass being added on top.
5. **The observer is still detached before the clear** — `clearFileSyncContext` is called and no durable write carrying the emptied map reaches the store during the reload. Kills the tempting simplification of deleting the whole `if (dropped)` block.
6. `tests/docs/` — if a claims test covers the CLAUDE.md/mcp-tools sentences being rewritten, update it; otherwise no new doc test (do not add a new drift guard).

## Done when

The envelope survives both paths; notes come back; a no-longer-matching record is `degraded` rather than mis-anchored or deleted; CLAUDE.md, `docs/gotchas.md` and the four `docs/mcp-tools.md` lines corrected in the same commit; force-open still in the license-gated set; `documents-open`, `reload-from-markdown`, `annotations/sync` and `annotations/store` suites green.

## Not in scope

`store.clear()`'s other caller, `document-service.ts`'s rename path (`createStore(oldHash).clear()` — deleting the *old hash's* envelope after a successful re-key is correct and must stay). Backup/`.annotations.bak.<ts>` snapshots (option 1 in the issue body, not the decision taken). `tandem_applyChanges` and restore, which clear annotations by a different route.
