# D1 — #1813 force-open and source-view commit unlink the on-disk annotation envelope

Branch `fix/markdown-fidelity-1753`. Closes #1813, implementing [decision C](../../decisions.md) (Bryan, 2026-09-06, recorded as a comment on the issue). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:26`. Probe: none exists; this spec writes one (the track file says "none; write one").

## Problem

`src/server/documents/populate.ts`, `clearAndReload` step 0:

```ts
const dropped = clearFileSyncContext(id);
if (dropped) {
  try { await dropped.store.clear(); } catch (err) { … }
}
```
`store.clear()` is `clearOne(docHash)` in `src/server/annotations/store.ts:638-658`. It **cancels the pending debounced write and then** `await fs.unlink(filePathFor(docHash))` — the durable envelope `<annotations-dir>/<docHash>.json` is deleted from disk, taking the user's **personal notes** (ADR-027) with it. The pre-overwrite document backup covers the text, not the envelope, so there is no copy. Only the second half is the defect; the first half is load-bearing and the fix must keep it (see §Fix item 1).

Two callers reach it, and neither is "the user asked to delete their notes":

- `documents/open.ts` — `tandem_open` with `force: true` ("reload from disk", used to recover from a bad state).
- `documents/reload-family.ts` `reloadDocumentFromMarkdown` — the **source-view commit** path, where the user edited the text and expects annotations that still match to survive.

Decision C takes option 2 from the issue body: clear only the in-memory map; let the next open re-anchor from `textSnapshot`.

## Fix

**1. `populate.ts`: flush the pending write BEFORE the observer cleanup, then clear the context.** Two changes, not one: the `clear()` → `flush()` substitution, **and an ordering inversion** that the naive substitution gets wrong.

```ts
// step 0 — flush FIRST, while the tombstone ledger is still populated
const ctx = getFileSyncContext(id);
if (ctx) {
  try { await ctx.store.flush(); } catch (err) { … }
}
clearFileSyncContext(id);
```

**Why the order is the contract.** `clearFileSyncContext` (`events/file-sync-registry.ts:84-98`) runs `safeCleanup(docName, entry.cleanup, "close", "clear")`, and the `"close"` phase (`annotations/sync.ts:303-309`) does `tombstonesByDoc.delete(docHash)`. The thunk `flush` invokes is `snapshot(ydoc, docHash, meta)` (`sync.ts:292`), whose tombstone half is `const tombstoneMap = tombstonesByDoc.get(docHash); const tombstones = tombstoneMap ? Array.from(tombstoneMap.values()) : []` (`sync.ts:209-210`). Flushing *after* the cleanup therefore writes `tombstones: []`, and `performWrite` is a **full clobber**, not a read-modify-write: `await atomicWrite(target, JSON.stringify(doc))` (`store.ts:511-514`). The ledger is re-seeded from the FILE on every `loadAndMerge` (`sync.ts:589-605`), so the envelope holds every historical tombstone for that document — all of them would be erased in one write, whenever a durable write happened to be pending. The realizable regression: a user deletes an imported Word comment (the tombstone is what suppresses re-injection on later opens); a force-open within `DEBOUNCE_MS = 100` of any annotation mutation erases it; the next open of that `.docx` re-injects the deleted comment. That is the resurrection window `loadAndMerge`'s union seed exists to close, re-opened by the fix meant to close a different hole.

Item 1 needs one new accessor: **`getFileSyncContext(docName)` in `src/server/events/file-sync-registry.ts`**, returning the same `{ store, docHash }` shape `clearFileSyncContext` already returns, without disposing anything. (The alternative — making `clearFileSyncContext` itself `await` a flush before its `safeCleanup` call — is acceptable and keeps the two-step atomic at the registry, but it turns a synchronous function `async` for all five call sites; prefer the accessor unless that turns out cleaner in the diff.) `clearFileSyncContext(id)` is still called, unconditionally, at the same point.

The `flush()`-not-`clear()` half is the other half of the fix, and it is not a deletion — `clearOne` does **two** things, and only one of them is the bug:

```ts
async function clearOne(docHash: string): Promise<void> {          // store.ts:638-658
  const entry = pending.get(docHash);
  if (entry) { clearTimeout(entry.timer); pending.delete(docHash); }  // (a) cancels the queued write
  await fs.unlink(filePathFor(docHash));                              // (b) THE BUG
}
```
`clearFileSyncContext` does not cover (a). It calls the observer cleanup (`annotations/sync.ts:302-312` — `annMap.unobserve` / `repMap.unobserve` plus `tombstonesByDoc.delete` on the `"close"` phase) and drops the registry entry (`events/file-sync-registry.ts:84-92`); it cancels no timer. The queued thunk is `store.queueWrite(() => snapshot(ydoc, docHash, meta))` (`sync.ts:292`) — it captures the **live** `ydoc` and reads it at *fire* time, `DEBOUNCE_MS = 100` (`store.ts:58`) after the last annotation mutation. So a bare deletion re-opens the same loss by a new route: a document annotated within 100 ms of the force-open has a write in flight; it fires after `clearDocMaps(doc)` (`populate.ts:311-318`, reached at `:414` behind an `await prepareContent(...)`), snapshots the **emptied** `Y.Map('annotations')`, and `performWrite` overwrites `<annotations-dir>/<docHash>.json` with zero annotations — non-deterministically, and after the fix nothing else deletes the file, so there is no "it was going to be deleted anyway" excuse.

`flush` is the shape that keeps (a) and drops (b): `flushOne` (`store.ts:562-580`) clears the timer, removes the pending entry, and invokes the thunk **while the Y.Doc still holds the pre-reload annotations and — given the ordering above — while `tombstonesByDoc` still holds the ledger** — so the envelope handed to the caller's `loadAndMerge` is the true pre-reload one rather than a stale, an emptied, or a tombstone-stripped one. `DocStore.flush` already exists (`store.ts:699`, `flush: () => flushOne(docHash)`) and `persistSnapshot` (`sync.ts:750-758`) is the existing precedent for queue-then-flush. Keep the try/catch: `flushOne` re-throws a failing thunk by design, and the existing "failures here must not abort the reload" contract still applies.

Rewrite the step-0 comment to state that shape — **flush** the pending write first, so the envelope on disk is the pre-reload set *including its tombstones*, then detach the observer, and do **not** unlink — and why the envelope now survives the reload: the caller re-wires the store immediately afterwards (`wireAnnotationStore` → `loadAndMerge`), and each merged record is re-anchored by `refreshRange`.

**What `storedRangeStillMatches` does and does not cover.** The safety argument for re-merging into *changed* content is #1764's gate: `refreshRange`'s `repaired` arm, its lazy-attach arm and its spurious-collapse arm each compare the stored flat range against the stored `textSnapshot` before writing, and a record that no longer holds its snapshot answers `degraded`, writes nothing, and surfaces as `anchor: "degraded"` on `tandem_getAnnotations`. **That gate is conditional on the record carrying a snapshot at all**: `storedRangeStillMatches` is `ann.textSnapshot === undefined || !snapshotContradicts(...)` (`positions.ts:776-781`), so a snapshot-less record always passes. Imported Word comments have no `textSnapshot` by construction — `file-io/docx-comments.ts:786-804` destructures it off the record on the drift path and the fresh-injection branch at `:819-832` builds without one — so a force-open of a `.docx` whose bytes changed can take the `repaired` arm (`positions.ts:856-863`) and mint a fresh, confident `relRange` at offsets derived from the OLD content, with nothing warning. That is a **residual, not a covered case**; test 6 pins the observed outcome and the PR body states it. Do not describe the gate as covering every record, and do not "fix" the residual here by adding a re-anchor pass — the mint arms' `undefined` carve-out is #1764's own decision.

**The ungated `updated` arm, and the pre-decided fallback.** `relRange` is persisted in the envelope (`annotations/schema.ts:110`, and `sync.ts:29` states "relRanges must persist"), so every merged record arrives carrying a RelativePosition minted against the **pre-reload** CRDT lineage. `refreshRange` gates on `storedRangeStillMatches` only on the dead-relRange arm (`positions.ts:844-869`) and the collapse arm (`:893-900`); a stale relRange that resolves to a **wrong-but-non-null** offset falls through to `:905`, `const updated = { ...ann, range: { from: newFrom, to: newTo } }; map.set(...)` — an ungated overwrite of the stored flat range. Today that path is unreachable on force-open because the envelope is unlinked; this change makes it reachable for every annotation on every force-open. Test 1 therefore asserts the recovered **span**, not membership. **If it does not hold, the fix is to strip `relRange` from every record merged on the force-reload path before `refreshRange` runs** — decided here, not at build time: the repopulated content is a new lineage by construction, and CLAUDE.md's rule is to strip a dead `relRange`, never to preserve it, precisely so the lazy re-attachment path can re-derive one from the flat range under the gate.

**2. `documents/annotation-wiring.ts`:** the `allowRecovery` comment claims "Force-reload (`clearAndReload`) deliberately clears the envelope and must NOT resurrect a stale orphan." The code is unchanged (the force path still passes no `allowRecovery`, so rename-recovery still does not run there) but the stated reason is now false. Reword to the real one: recovery is a first-open-only heuristic, and a force-reload of an already-open document has its own envelope.

## Tests

New `tests/server/force-open-envelope.test.ts`.

**Isolation is mandatory and is the first line of the file.** This spec writes real annotation envelopes and (pre-fix) unlinks them, so run it under `useTmpAnnotationsEnvWithFlag()` from `tests/helpers/annotation-store-env.ts` — a fresh tmpdir for `TANDEM_APP_DATA_DIR` per test, plus a **deleted** `TANDEM_ANNOTATION_STORE` so the store defaults on. Both halves matter: nothing in `vitest.config.ts` sets `setupFiles`, so without the tmpdir the spec reads and destroys the developer's real store (`tests/server/annotations/store.test.ts:3-6` states the per-test-tempdir rule; `useTmpAnnotationsEnv` at `annotation-store-env.ts:28-46` and the with-flag form at `:55-78` are the sanctioned shape); and without the flag reset, an inherited `TANDEM_ANNOTATION_STORE=off` makes `clearOne` early-return (`store.ts:639`) and every write inert, so specs 1-3 would pass **vacuously against the unfixed code**. Assert the store is enabled (a written-then-read envelope exists) before spec 1's envelope-exists check, so a disabled store fails the suite rather than greening it.

1. **The killer — the recovered SPAN, not membership.** Seed a durable envelope containing a `note` and a `comment` whose `textSnapshot` still matches the file; run `clearAndReload` with **unchanged** content; assert the envelope file **still exists on disk** and, after the caller's `wireAnnotationStore`, each record is back in `Y.Map('annotations')` *over the same text it annotated*: `refreshRange`/`tandem_getAnnotations` reports `anchor` anything but `failed`, and the reported `range` slices out of `extractText(doc)` to exactly the record's stored `textSnapshot`. A membership-only assertion passes even if every recovered annotation lands at a wrong offset, which is the live hazard once the ungated `updated` arm (`positions.ts:905`) becomes reachable on this path. A fix that merely moved the `unlink` behind a flag, or that cleared the map after the merge, fails this too. If the span assertion cannot be made to hold, apply the pre-decided fallback in §Fix (strip `relRange` on the force-reload merge) rather than relaxing the assertion.
2. **Notes specifically** — asserted separately from comments, because ADR-027 notes are the loss the issue is filed about and a read filter that hid them would make a comments-only assertion pass.
3. **Source-view commit** — the same assertion driven through `reloadDocumentFromMarkdown`, not through force-open. Both callers share the line being changed, but only a two-caller test proves the source-view path (the one the issue calls "safer" and the one where the user *just edited the text*) is covered.
4. **Changed content → `degraded`, not resurrection at a wrong offset.** Reload with markdown that no longer contains the annotated span; the record survives, and `refreshRange`/`tandem_getAnnotations` reports `anchor: "degraded"` with the `range` byte-identical to the stored flat range and **`relRange` ABSENT**. The strip is the contract, not a bug: with both `relPosToFlatOffset` calls returning null and `storedRangeStillMatches` false, `positions.ts:865-869` builds `const stripped = { ...ann }; delete stripped.relRange; map.set(ann.id, stripped)` — a durable strip, which is exactly CLAUDE.md's "strip dead `relRange` RelativePositions, never preserve them" (a stale one resolving to null blocks the lazy re-attachment recovery). #1764's "the flat range and the relRange both survive" is about the three **mint** arms being skipped, not about this strip. Asserting "`relRange` intact" here would either fail or drive an implementer to preserve a dead RelativePosition. This spec is what stops a "helpful" re-anchor pass being added on top.
5. **The pending debounced write is flushed, not lost, never lands empty, and does not erase the tombstone ledger.** With fake timers: seed the envelope with **a pre-existing tombstone** and an annotation, mutate an annotation so `scheduleWrite` queues a write, immediately run `clearAndReload`, advance past `DEBOUNCE_MS = 100`, and assert (a) the on-disk envelope still holds the record (not `{}`), (b) **`tombstones` in the flushed envelope still contains the seeded tombstone**, and (c) `clearFileSyncContext` was called, so the observer is detached before the repopulate. Assertion (b) is what pins the ordering rather than leaving it incidental: flushing after the `"close"`-phase cleanup writes `tombstones: []` and `performWrite` clobbers the whole file (`store.ts:511-514`), which a "holds the record, not `{}`" assertion cannot see. This is the spec for the race the fix exists to avoid; a version written as "assert no durable write carrying the emptied map reaches the store" passes while the race is live, because the losing interleaving simply does not occur in a test that never queued a write. It also kills the tempting simplification of deleting step 0's guarded store call altogether (`if (dropped)` today, `if (ctx)` after the fix), and the equally tempting one of deleting `store.clear()` without putting `flush()` in its place.
6. **The snapshot-less residual, pinned rather than claimed away.** Seed the envelope with an `author: "import"`, `type: "note"` record carrying **no** `textSnapshot`; force-open the document with **changed** content; assert the observed outcome — whether the freshly re-imported record wins the rev contest or the envelope copy is re-anchored by the `repaired` arm at offsets derived from the old content. Pin what actually happens and name it in the PR body as a residual of #1764's `undefined` carve-out. None of specs 1-5 uses a snapshot-less record, so without this the spec suite reads as though the gate covers everything.
7. `tests/docs/` — if a claims test covers the CLAUDE.md/mcp-tools sentences being rewritten, update it; otherwise no new doc test (do not add a new drift guard). Note that no `tests/docs/*claims*` test currently covers any of the six prose sites — verified 2026-09-09 — which is why §Fix quotes an anchor phrase for each instead.
