# D1 — #1813 force-open and source-view commit unlink the on-disk annotation envelope

Branch `fix/markdown-fidelity-1753`. Closes #1813, implementing [decision C](../../decisions.md) (Bryan, 2026-09-06, recorded as a comment on the issue). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:26`. Probe: none exists; this spec's tests are it.

## Problem

`src/server/documents/populate.ts`, `clearAndReload` step 0:

```ts
const dropped = clearFileSyncContext(id);
if (dropped) {
  try { await dropped.store.clear(); } catch (err) { … }
}
```
`store.clear()` is `clearOne(docHash)` (`src/server/annotations/store.ts:638-658`), which **cancels the pending debounced write and then** `await fs.unlink(filePathFor(docHash))` — the durable envelope `<annotations-dir>/<docHash>.json` is deleted, taking the user's **personal notes** (ADR-027) with it. The pre-overwrite document backup covers the text, not the envelope, so there is no copy. Only the unlink is the defect; the timer cancellation is load-bearing.

Two callers reach it, and neither is "the user asked to delete their notes":

- `documents/open.ts` — `tandem_open` with `force: true` ("reload from disk", used to recover from a bad state).
- `documents/reload-family.ts` `reloadDocumentFromMarkdown` — the **source-view commit**, where the user edited the text and expects still-matching annotations to survive.

Decision C takes option 2 from the issue body: clear only the in-memory map; let the next open re-anchor from `textSnapshot`.

## Fix

**1. `populate.ts`: flush the pending write BEFORE the observer cleanup, then clear the context.** Two changes, not one — the `clear()` → `flush()` substitution *and* an ordering inversion the naive substitution gets wrong:

```ts
// step 0 — flush FIRST, while the tombstone ledger is still populated
const ctx = getFileSyncContext(id);
if (ctx) {
  try { await ctx.store.flush(); } catch (err) { … }
}
clearFileSyncContext(id);
ctx?.store.cancelPendingWrite();   // <- the teardown's second half; see below
```

**The flush is not the whole teardown — the cancel is.** `flushOne` awaits `performWrite` → `atomicWrite`, i.e. real disk I/O, and the annotation observer is **still attached across that await** (only `clearFileSyncContext` detaches it). Any annotation mutation landing inside that window calls `store.queueWrite(...)` (`sync.ts:292`) and `scheduleWrite` (`store.ts:523-560`) arms a **fresh** 100 ms timer keyed by docHash. `clearFileSyncContext` unobserves but never touches `pending`; today the only thing that cancels that timer is `clearOne` (`store.ts:643-647`) — the very call this fix deletes. So a naive flush-then-clear re-opens the loss by a *third* route: the surviving timer fires after `clearDocMaps(doc)` (`populate.ts:414`), snapshots the emptied `Y.Map('annotations')`, and full-clobbers the envelope (`store.ts:511-514`) — and `prepareContent` (`populate.ts:404`) is async markdown/docx parsing, so >100 ms between the window and the caller's re-read is ordinary rather than exotic.

**Why `flush` and not a plain deletion.** `clearFileSyncContext` only unobserves and drops the registry entry (`events/file-sync-registry.ts:84-98` → `annotations/sync.ts:302-312`); it cancels no timer. The queued thunk is `store.queueWrite(() => snapshot(ydoc, docHash, meta))` (`sync.ts:292`), capturing the **live** ydoc and reading it at fire time, `DEBOUNCE_MS = 100` after the last mutation. So simply deleting the `clear()` call re-opens the loss by a new route: a document annotated within 100 ms of the force-open has a write in flight, it fires after `clearDocMaps(doc)` (`populate.ts:311-318`), snapshots the **emptied** `Y.Map('annotations')`, and overwrites the envelope with zero annotations. `flushOne` (`store.ts:562-580`) clears the timer, drops the pending entry and invokes the thunk while the Y.Doc still holds the pre-reload annotations. `DocStore.flush` already exists (`store.ts:699`); `persistSnapshot` (`sync.ts:750-758`) is the queue-then-flush precedent. Keep the try/catch — `flushOne` re-throws a failing thunk, and "failures here must not abort the reload" still applies.

**Why the order is the contract.** `clearFileSyncContext` runs `safeCleanup(…, "close", "clear")`, and the `"close"` phase does `tombstonesByDoc.delete(docHash)` (`sync.ts:303-309`). The flushed thunk then reads `tombstonesByDoc.get(docHash)` and writes `tombstones: []` (`sync.ts:209-210`), and `performWrite` is a **full clobber** (`atomicWrite(target, JSON.stringify(doc))`, `store.ts:511-514`) while the ledger is re-seeded from that file on every `loadAndMerge` (`sync.ts:589-605`). Flushing after the cleanup would therefore erase every historical tombstone in one write: a user deletes an imported Word comment, a force-open within `DEBOUNCE_MS` erases the tombstone that suppresses re-injection, and the next open re-injects the deleted comment — the resurrection window the union seed exists to close.

Item 1 needs two new entry points, both thin. **`getFileSyncContext(docName)` in `src/server/events/file-sync-registry.ts`**, returning the same `{ store, docHash }` shape `clearFileSyncContext` already returns, without disposing anything. And **`cancelPendingWrite()` on `DocStore` (`src/server/annotations/store.ts`)** — `clearOne`'s first half and nothing else: `const entry = pending.get(docHash); if (entry) { clearTimeout(entry.timer); pending.delete(docHash); }`, with no `fs.unlink`, inert under `isFeatureDisabled()` like every other store op. It exists because `clearOne` was the only canceller and this PR stops calling it; splitting the two halves is what keeps the teardown total while the unlink goes away. (Making `clearFileSyncContext` itself `await` a flush is acceptable but turns a synchronous function `async` for all five call sites.) `clearFileSyncContext(id)` is still called unconditionally at the same point. Rewrite the step-0 comment to that shape: flush the pending write first so the envelope on disk is the pre-reload set **including its tombstones**, then detach the observer, and do not unlink — the caller re-wires the store immediately (`wireAnnotationStore` → `loadAndMerge`) and each merged record is re-anchored by `refreshRange`.

**Two things the re-merge does and does not guarantee, both decided here.** `refreshRange` gates its three mint arms on `storedRangeStillMatches` (#1764), so a record that no longer holds its `textSnapshot` answers `degraded` and writes nothing — but that gate passes unconditionally when `textSnapshot === undefined` (`positions.ts:776-781`), and imported Word comments have none by construction (`docx-comments.ts:819-832`). That residual is #1764's own carve-out; do not fix it here. Separately, a stale `relRange` that resolves to a wrong-but-non-null offset falls through to the ungated `updated` arm (`positions.ts:905`), which this change makes reachable on force-open. Test 1 therefore asserts the recovered **span**, not membership; **if it does not hold, the fix is to strip `relRange` from every record merged on the force-reload path before `refreshRange` runs** — decided here, not at build time, and consistent with CLAUDE.md's "strip a dead `relRange`, never preserve it".

## Tests

New `tests/server/force-open-envelope.test.ts`.

**Isolation is the first line of the file.** This spec writes real annotation envelopes and (pre-fix) unlinks them: run it under `useTmpAnnotationsEnvWithFlag()` from `tests/helpers/annotation-store-env.ts:55-78` — a per-test tmpdir for `TANDEM_APP_DATA_DIR` plus a **deleted** `TANDEM_ANNOTATION_STORE` so the store defaults on. Both halves matter: `vitest.config.ts` sets no `setupFiles`, so without the tmpdir the spec destroys the developer's real store; and with an inherited `TANDEM_ANNOTATION_STORE=off` every write is inert (`store.ts:639`) and specs 1-3 pass **vacuously against the unfixed code**. Assert a written-then-read envelope exists before spec 1's check, so a disabled store fails the suite rather than greening it.

1. **The killer — the recovered SPAN, not membership.** Seed an envelope with a `note` and a `comment` whose `textSnapshot` still matches; run `clearAndReload` with **unchanged** content; assert the envelope file still exists and, after the caller's `wireAnnotationStore`, each record is back in `Y.Map('annotations')` *over the same text it annotated* — `anchor` anything but `failed`, and the reported `range` slicing out of `extractText(doc)` to exactly the stored `textSnapshot`. A membership-only assertion passes even if every record lands at a wrong offset, the live hazard once the ungated `updated` arm becomes reachable. If the span assertion cannot hold, apply §Fix's pre-decided fallback rather than relaxing it.
2. **Notes specifically**, asserted separately from comments — ADR-027 notes are the loss the issue is filed about, and a read filter hiding them would let a comments-only assertion pass.
3. **Source-view commit** — the same assertion through `reloadDocumentFromMarkdown`. Both callers share the changed line, but only a two-caller test proves the path where the user *just edited the text*.
4. **Changed content → `degraded`.** Reload with markdown that no longer contains the annotated span; the record survives, `anchor: "degraded"`, `range` byte-identical to the stored flat range, and **`relRange` ABSENT** — `positions.ts:865-869` strips it durably, which is CLAUDE.md's rule. Asserting "`relRange` intact" here would drive an implementer to preserve a dead RelativePosition.
5. **The pending write is flushed, lands non-empty, and keeps the tombstones.** With fake timers: seed the envelope with **a pre-existing tombstone** and an annotation, mutate an annotation so `scheduleWrite` queues a write, run `clearAndReload`, advance past `DEBOUNCE_MS = 100`, and assert (a) the on-disk envelope still holds the record (not `{}`), (b) **`tombstones` still contains the seeded one**, and (c) the observer was detached. (b) is what pins the ordering rather than leaving it incidental — flushing after the `"close"` cleanup writes `tombstones: []`, which (a) cannot see. It also kills deleting step 0's guarded store call altogether, and deleting `store.clear()` without putting `flush()` in its place.

   **Second case, the one the first cannot see: a write queued from INSIDE the flush's await.** The case above queues its write *before* `clearAndReload`, so `flush()` alone passes it. Spy `performWrite` (or the `fs.writeFile` under `atomicWrite`) so that, while the flush is awaiting, the spy mutates `Y.Map('annotations')` — the observer is still attached, so `scheduleWrite` arms a fresh timer — then resolve. Advance past `DEBOUNCE_MS`, and assert the on-disk envelope **still holds the record**. Without `cancelPendingWrite()` that timer fires after `clearDocMaps`, snapshots the emptied map and clobbers the envelope to zero annotations, which is exactly the loss this spec exists to prevent. This is the spec that fails against a flush-only fix.

**One existing spec is inverted by decision C and must be RESTATED, never deleted:** `tests/server/reload-from-markdown.test.ts:190`, `it("clears all annotations on reload")`, which seeds one annotation and asserts `Y_MAP_ANNOTATIONS.size === 0` after `reloadDocumentFromMarkdown` against the real store on an isolated app-data dir (`:17-27`). Since `reload-family.ts:145,152` re-wires the store right after `clearAndReload`, the surviving envelope makes that size **1**. Rewrite to the new contract — the annotation survives the source-view commit and comes back re-anchored (or `degraded` when the seeded span no longer matches) — and retitle it. Do not weaken the fix to keep it green, and do not delete it: the reload path losing annotations silently is still worth a spec, now stated the other way round.

## Done when

The envelope survives both paths; notes come back **at the right offsets** on unchanged content; a pending write is flushed rather than firing into the emptied map, **a write queued from inside the flush's await is cancelled rather than clobbering the envelope**, **and the flushed envelope still carries its tombstones**; a no-longer-matching record is `degraded` with `relRange` stripped; the comment and doc sites in §Fix item 2 are corrected in the same commit; force-open stays in the license-gated set with every row where it is; `documents-open`, `annotations/sync`, `annotations/store` and both license-gate coverage suites green — and **`reload-from-markdown` green AFTER its `clears all annotations on reload` spec is restated to decision C**, which is part of this change, not a green-chasing edit.

## Review corrections (post-cut)

**Adopted**

1. **The step-0 rewrite left a window in which the fix loses the data it exists to save.** `flush()` is not a drop-in for `clear()`: `flushOne` awaits real disk I/O and the annotation observer stays attached across that await (only `clearFileSyncContext` detaches it), so a mutation landing mid-flush calls `queueWrite` and arms a **fresh** `DEBOUNCE_MS` timer. `clearFileSyncContext` never touches `pending`; the only canceller was `clearOne` — the call this PR deletes. Test 5 gains a second case that queues its write from inside the flush's await; the original case only covers a write queued *before* `clearAndReload` and passes against a flush-only fix.
