## Problem

`registerAnnotationObserver` (`src/server/annotations/sync.ts:253-255`) returns `(phase?: ObserverCleanupPhase) => void`, and its body is `return (phase: ObserverCleanupPhase = "close") => {` (`:303`). `loadAndMerge` repeats the optional form at `:548`. `src/server/events/file-sync-registry.ts` carries it three more times: the map value type (`:21`), `safeCleanup`'s `cleanup` parameter (`:32`), and `setFileSyncContext`'s `cleanup` parameter (`:63`).

Choosing `"close"` over `"swap"` decides whether the per-doc tombstone ledger survives. The wrong one serializes `tombstones: []` from an in-flight debounced write (#333). In production the default is never read.

- **The handle is invoked in exactly one production place:** `cleanup(phase);` inside `safeCleanup`, at `file-sync-registry.ts:37`. That call is what `phase?` currently lets someone write as a bare `cleanup()` without a compile error.
- `safeCleanup`'s OWN third parameter, `phase: ObserverCleanupPhase` (`:33`), has always been required. Its four call sites are `:72` `"close"` (replace), `:106` `"close"` (clear), `:129` `"swap"` (reattach) and `:144` `"close"` (inside `resetForTesting`, **test-only**). Dropping the argument at any of them is already TS2554 on `caf54391`, so none of them can show anything about this change.

The default's only audience is a *future* caller that omits the argument, and the handle's type still permits that caller. `tests/server/annotations/sync.test.ts:1708` ("cleanup with no argument defaults to the close phase") describes what happens to such a caller. It does not refuse it.

**Measured on `caf54391`:** with the default dropped and all five `phase?` made required, `tsc -p tsconfig.server.json` stays **green** and `tsc -p tsconfig.tests.node.json` reports **55** errors:
- 52 are TS2554 in `tests/server/annotations/sync.test.ts`.
- 2 are TS2554 in `tests/server/annotations/perf.test.ts`, at `:97` and `:120`.
- 1 is TS2345 in `tests/server/remove-annotation.test.ts:38`: `observerCleanups: Array<() => void>` receives a handle.

The tests.client and tests.e2e programs were not probed, because the handle is server-only. `npm run typecheck:tests` runs all three and is the gate. The issue body also names `event-queue.test.ts`, `event-queue-observer-split.test.ts` and `rename-document.test.ts`, but **none of them errors**. Their cleanups are either passed a phase or are zero-arg lambdas, which remain assignable to a one-parameter function type.

## Fix

- `sync.ts:303`: `return (phase: ObserverCleanupPhase) => {`, with no default.
- `sync.ts:255` and `:548`: change `(phase?: ObserverCleanupPhase)` to `(phase: ObserverCleanupPhase)`. Update the doc comment at `:240-251` so it says the phase is required and why: #333, and a wrong phase is silent.
- `file-sync-registry.ts:21`, `:32` and `:63`: the same `phase?:` → `phase:` change. **`safeCleanup`'s body and its four call sites (`:72`, `:106`, `:129`, `:144`) do not change.**
- Tests: turn every bare `cleanup()` reported by the probe into `cleanup("close")`. That is exactly the behaviour the default supplied at runtime, so no spec's meaning changes. Give `remove-annotation.test.ts:38`'s array the element type `Array<(phase: ObserverCleanupPhase) => void>`, and make its drain call pass `"close"`. **Touch only the sites `tsc` reports.** There are about 185 bare `cleanup()` calls tree-wide and most belong to unrelated helpers.
- **Delete** `sync.test.ts:1708`'s spec, "cleanup with no argument defaults to the close phase". It would guard something the type system now makes unrepresentable, as the issue itself says. Keep its two explicit-phase siblings, the close-phase ledger spec just above it and the swap-phase spec.
- No `src/` behaviour changes, no Y.Doc write (so Critical Rule 2 does not apply), and no Y.Map key.

## Tests

The type system is the test. Run `npm run typecheck:tests` and `npm run typecheck`, then vitest on `tests/server/annotations/sync.test.ts`, `annotations/perf.test.ts`, `remove-annotation.test.ts`, `event-queue.test.ts` and `event-queue-observer-split.test.ts`.

**There is no runtime test for an omitted phase once the pin spec is deleted. The type is the only guard, and that is the point of #1695.**

Mutation checks. Record each in the PR body with the observed `tsc` exit and error code, and restore from a file copy, never with `git checkout`.

1. **The discriminating check, at the only production invocation.** At `file-sync-registry.ts:37`, replace `cleanup(phase);` with `cleanup(); void phase;`.
   - The `void phase;` is required. A plain `cleanup();` also fails on `caf54391`, but with TS6133 (`'phase' is declared but its value is never read`, from `noUnusedParameters`), so it would go red on master and prove nothing.
   - **Measured on `caf54391` (planning probe):** with the mutation and master's types, `tsc -p tsconfig.server.json` exits **0**. With the mutation and only `:32` made required, it exits **2** with `file-sync-registry.ts(37,5): error TS2554: Expected 1 arguments, but got 0.`
   - The build stage repeats it on the finished branch: exit 0 on master, TS2554 at `:37` on the branch. The PR body says `:37` is the only production site that invokes the handle.
   - Optional positive control, **labelled as a control and not as evidence:** dropping `"close"` from `safeCleanup(docName, entry.cleanup, "close", "clear")` at `:106` is TS2554 on master and on the branch alike.
2. **The pre-fix shape admits omission.** Put the optional form back on all six type positions (`sync.ts:255`, `:548`, the `:303` parameter as `(phase?: ObserverCleanupPhase)` with no default, and `file-sync-registry.ts:21`, `:32`, `:63`), keep check 1's mutation at `:37`, and `tsc -p tsconfig.server.json` is green. That shows required-ness is the only thing that refuses the call.
   - Do **not** restore `?` on `:255` alone. With `:303` still `(phase: ObserverCleanupPhase) =>`, `strictFunctionTypes` fails the return with TS2322 (`Type 'ObserverCleanupPhase | undefined' is not assignable to type 'ObserverCleanupPhase'`, reviewer probe under TS 5.9.3 `--strict`). The PR body must not write "stays green" for that shape.
   - The runtime consequence of the green shape, where `phase` is `undefined`, the `=== "close"` branch is skipped and the ledger survives a close, is **argued from the code, not observed by a test.** Say so.
3. Put `= "close"` back as a default while keeping the parameter required. `tsc` still refuses the mutated call at `:37` (TS2554). That proves the pin spec's subject is gone, which justifies deleting it.
