# W13g — #1911 (Refs only) per-test timeout override for two cold-cache-sensitive `tests/docs` specs

Branch `fix/docs-and-test-tooling-drift-2005`. **References #1911 only — the issue stays open.**
This PR addresses direction 1 of the issue's four listed directions and none of the other three;
directions 2-4 remain unaddressed, so closing the issue here would overclaim. No track file
(non-review issue). No MCP probe: this is a test-config timing fix.

## Problem

The issue's own measurement: on 2026-09-08, the pre-push hook's full-suite run twice refused a
clean 12-line markdown-only diff, with a shifting failure set. Two `tests/docs` specs failed the
same way, and the mechanism there is pinned by the issue's own repro:

```
tests/docs/documents-boundary.test.ts > documents/reload-family.ts exports exactly what is written down
tests/docs/registry-primitive-containment.test.ts > does not re-export the primitives from the production barrels
```

Both failed as `Error: Test timed out in 15000ms` — a timeout, not an assertion failure — and both
bodies do dynamic `await import(...)` of server modules on first touch: `reload-family.js`
(`documents-boundary.test.ts:729`, one import) and `document-service.js` / `document.js` /
`registry.js` (`registry-primitive-containment.test.ts:124-126`, three imports) — pulling in large
chunks of `src/server/` under a cold transform cache. Re-running `documents-boundary.test.ts` alone
with `--testTimeout=90000` on the same (cold) cache passed in **10.22s** wall time (`transform
5.35s, import 1.40s, tests 8.28s`) — inside the current 15s project ceiling
(`vitest.config.ts:149,183`), but with real, thin margin once the machine is also running biome
and `cargo test` concurrently under the same pre-push hook.

`vitest.config.ts`'s `node` and `client` projects already carry a 15s `testTimeout` (raised from
vitest's 5s default) for exactly this shape of problem — the `client` project's own comment
(`:137-148`) documents a ~30x spread under contention (`useTauriFileDrop`'s 18 specs run in 2.9s
alone, ~160ms each, and time out at the 5s default when the machine is loaded) and names the
asymmetry itself as the bug: "the node project was given headroom when it hit this and the client
project never was, so every developer running the suite alongside anything else lost time to a red
run that reproduced nowhere." These two `tests/docs` specs are the same class one level further:
import-heavy and cold-cache-sensitive, currently sitting at the *project's* ceiling with no
per-spec headroom of their own.

The issue lists four directions, in order of confidence, and is explicit that the fourth is **not**
a bug fix: "Consider whether the pre-push hook should run the full suite at all, given CI's `check`
is a required status check on `master` ... Item 4 is a workflow decision, not a bug fix, and should
not be folded in without a deliberate call." This spec implements **only direction 1** ("Raise
`testTimeout` for the import-heavy specs"), and as a **per-test** override — not a global raise of
`vitest.config.ts`'s `testTimeout`. The sweep doc's own instruction for this group is explicit: "a
per-file timeout override for exactly those specs, NOT a global raise" — matching the sibling G2
test-timing group's row ("Lands first; do not raise ceilings") and the general reason: raising the
project-wide ceiling widens the window for every one of the suite's ~11,400 tests, hiding a genuine
future hang behind slack meant for two specific, already-diagnosed specs.

## Fix

Add a per-test timeout to exactly the two named `it()` blocks, using vitest's object-form third
argument — already used in this repo (`tests/server/platform.test.ts:428`:
`it("returns null against a server that never responds", { timeout: 15_000 }, async () => {
...`):

- `tests/docs/documents-boundary.test.ts:728` —
  `` it("documents/reload-family.ts exports exactly what is written down", { timeout: 45_000 }, async () => { ... }) ``
- `tests/docs/registry-primitive-containment.test.ts:122` —
  `` it("does not re-export the primitives from the production barrels", { timeout: 45_000 }, async () => { ... }) ``

**45s**, chosen as headroom over the issue's own measured 10.22s cold-cache wall time for the whole
`documents-boundary.test.ts` file — `registry-primitive-containment.test.ts`'s spec does three
dynamic imports against two of the same heavy server modules plus a third, so it is given the same
ceiling rather than a smaller one on the assumption it is cheaper. The number is comfortably short
of the ceilings used elsewhere for operations that are genuinely expensive rather than merely
cold-cache-sensitive (`tests/server/docx-apply.test.ts:88`'s real-apply-path `timeoutMs(60_000,
300_000)`).

**Explicitly not `timeoutMs()`.** `tests/helpers/timing.ts`'s `timeoutMs(normal, underCoverage)`
exists for the *V8 coverage instrumentation* slowdown specifically (`TANDEM_COVERAGE=1`, set only
by `npm run test:coverage`) and its call sites are a fixed, guarded list —
`tests/scripts/coverage-manifest-wiring.test.ts` fails if that list drifts from the helper's real
callers, and `scripts/ci/coverage-manifest.mjs` publishes it. This issue's failure mode is
different: a cold transform cache under an ordinary `npm test` / pre-push run, present with or
without coverage instrumentation. Reusing `timeoutMs()` here would mean either adding these two
sites to that guarded, coverage-specific list (inaccurate — these are not coverage-suspended
bounds) or silently borrowing a helper for a condition it was not built to answer. A plain literal,
matching the style already at `platform.test.ts:428`, is the correct and smaller change.

**No change to `vitest.config.ts`.** Both projects' `testTimeout: 15_000` (`:149`, `:183`) stay
exactly as they are — the ceiling for the other ~11,400 tests in the suite is untouched.

## Tests

This is a timing-ceiling change, not new behaviour, so there is no assertion to add that proves the
fix without itself depending on machine/cache state — a deterministic "assert the cold-cache run
takes under 15s" test would be exactly the calibration mechanism the MINIMALITY RULE forbids; the
premise of the issue is that duration varies with cache and contention state, which a unit test
cannot pin without becoming flaky by the same mechanism it is testing for. The discriminating check
is the two `it()` signatures themselves:

```
grep -n 'timeout: 45_000' tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts
```

— exactly one match per file, on the named `it()`.

Manual verification (not part of this PR's automated gate, and not run in this sandbox — see `Not
in scope`): clear the vitest transform cache (e.g. `rm -rf node_modules/.vite`) and run
`npx vitest run tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts --project=node`
cold; both named specs now have 45s rather than 15s to clear transform+import cost.

## Done when

- Both named `it()` blocks carry `{ timeout: 45_000 }` as their second argument.
- No `testTimeout` value in `vitest.config.ts` changes.
- `npm run typecheck:tests` stays green (the object-form third argument to `it` is already used
  elsewhere in the repo, so no new type shape is introduced).
- `npx vitest run tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts`
  stays green.
