# W13g — #1911 (Refs only) per-test timeout override for cold-cache-sensitive `tests/docs` specs

Branch `fix/docs-and-test-tooling-drift-2005`. **References #1911 only — the issue stays open.**
This addresses direction 1 of the issue's four listed directions; directions 2-4 are untouched, so
closing the issue here would overclaim. No track file (non-review issue). No MCP probe:
test-config timing fix.

## Problem

The issue's own measurement: on 2026-09-08, the pre-push hook's full-suite run twice refused a
clean 12-line markdown-only diff. Two `tests/docs` specs failed as `Error: Test timed out in
15000ms` (a timeout, not an assertion failure), both doing dynamic `await import(...)` of large
`src/server/` modules on first touch under a cold transform cache:
`documents-boundary.test.ts:728` (imports `reload-family.js`) and
`registry-primitive-containment.test.ts:122` (imports `document-service.js`, `document.js`,
`registry.js`). Re-running `documents-boundary.test.ts` alone with `--testTimeout=90000` cold
passed in 10.22s wall time — inside the current 15s project ceiling
(`vitest.config.ts:149,183`), but with thin margin once biome and `cargo test` are also running
under the same pre-push hook.

`vitest.config.ts`'s `node`/`client` projects already carry a 15s `testTimeout` (raised from
vitest's 5s default) for exactly this shape of problem — the `client` project's comment
(`:137-148`) documents the same asymmetry: import-heavy specs timing out under contention while
fast specs don't. These two `tests/docs` specs are the same class, sitting at the project's
ceiling with no per-spec headroom.

The issue's fourth direction ("should the pre-push hook run the full suite at all, given CI's
`check` is required") is explicitly a workflow decision, not a bug fix, and is not addressed here.
This spec implements **only direction 1** ("raise `testTimeout` for the import-heavy specs"), as a
**per-test override, not a global raise** — matching the sweep doc's instruction for this group and
the sibling G2 group's rule ("do not raise ceilings").

## Fix

Add a per-test timeout to three named `it()` blocks, using vitest's options-object second argument
(matching existing repo usage, `tests/server/platform.test.ts:428`:
`it("...", { timeout: 15_000 }, async () => { ... })`), with `timeoutMs()` from
`tests/helpers/timing.ts` (imported as in `tests/server/docx-apply.test.ts:46`) rather than a bare
numeric literal:

- `tests/docs/documents-boundary.test.ts:728` — `"documents/reload-family.ts exports exactly what
  is written down"`
- `tests/docs/documents-boundary.test.ts:738` — `"documents/open.ts exports exactly what is
  written down"` (sibling — see below)
- `tests/docs/registry-primitive-containment.test.ts:122` — `"does not re-export the primitives
  from the production barrels"`

All three: `{ timeout: timeoutMs(45_000, 120_000) }`.

**Use `timeoutMs()`, not a bare literal.** `package.json:56`'s `test:coverage` script passes
`--testTimeout=120000`, but `tests/helpers/timing.ts`'s own doc comment states that flag does not
raise a timeout written as `it`'s second argument — the explicit value wins. A bare `{ timeout:
45_000 }` would therefore *replace* the coverage run's 120s ceiling with 45s for these two specs —
a regression under exactly the run (V8-instrumented, cold-transform-sensitive) where the timeout is
most likely to matter. `timeoutMs(45_000, 120_000)` keeps 45s under an ordinary run (the fix this
issue asks for) while matching the coverage run's existing 120s ceiling. `timeoutMs()`'s eight
existing call sites (e.g. `docx-apply.test.ts:88`) are plain, unguarded callers — adding three more
here is the same kind of addition, not new membership in a drift-guarded list.

**No change to `vitest.config.ts`.** Both projects' `testTimeout: 15_000` stay as they are.

**Sibling spec, `documents-boundary.test.ts:738`, is included because it does its own cold dynamic
import** (`src/server/documents/open.js`, which does not import `reload-family.js`, so the `:728`
spec's import doesn't warm it — whichever runs first pays the cold cost independently).
`registry-primitive-containment.test.ts`'s third `it()` (`"exports exactly the surface ADR-033
sanctions, and nothing else"`, at `:142` — re-verified, not `:176`) imports only
`src/server/documents/registry.js`, already imported directly by the covered `:122` spec three
lines above; Node's module cache makes that a cache hit, not a second cold import, so it's left at
the project's 15s ceiling.

## Tests

This is a timing-ceiling change, not new behaviour — a deterministic "assert the cold-cache run
takes under 15s" test would itself be flaky by the same cache/contention variance the issue
describes, which the MINIMALITY RULE forbids building a calibration mechanism for. The
discriminating check is the `it()` signatures themselves:

```
grep -n 'timeout: timeoutMs(45_000, 120_000)' tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts
```

— two matches in `documents-boundary.test.ts` (`:728`, `:738`), one in
`registry-primitive-containment.test.ts` (`:122`).

Manual verification (not run in this sandbox): clear the vitest transform cache and run
`npx vitest run tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts --project=node`
cold; the three named specs now have 45s (120s under `npm run test:coverage`) rather than 15s.

## Done when

- The three named `it()` blocks carry `{ timeout: timeoutMs(45_000, 120_000) }` as their second
  argument, callback third.
- Both files import `timeoutMs` from `tests/helpers/timing.js`.
- No `testTimeout` value in `vitest.config.ts` changes.
- `npm run typecheck:tests` stays green.
- `npx vitest run tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts`
  stays green under both `npm test` and `npm run test:coverage`.
