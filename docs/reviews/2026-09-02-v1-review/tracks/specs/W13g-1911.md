# W13g — #1911 (Refs only) per-test timeout override for cold-cache-sensitive `tests/docs` specs

Branch `fix/docs-and-test-tooling-drift-2005`. **References #1911 only — the issue stays open.**
This PR addresses direction 1 of the issue's four listed directions and none of the other three;
directions 2-4 remain unaddressed, so closing the issue here would overclaim. No track file
(non-review issue). No MCP probe: this is a test-config timing fix.

## Problem

The issue's own measurement: on 2026-09-08, the pre-push hook's full-suite run twice refused a
clean 12-line markdown-only diff, with a shifting failure set. Two `tests/docs` specs failed the
same way, and the mechanism there is pinned by the issue's own repro:

```
tests/docs/documents-boundary.test.ts > documents/reload-family.ts exports exactly what is written down
tests/docs/registry-primitive-containment.test.ts > does not re-export the primitives from the production barrels
```

Both failed as `Error: Test timed out in 15000ms` — a timeout, not an assertion failure — and both
bodies do dynamic `await import(...)` of server modules on first touch: `reload-family.js`
(`documents-boundary.test.ts:729`, one import) and `document-service.js` / `document.js` /
`registry.js` (`registry-primitive-containment.test.ts:124-126`, three imports) — pulling in large
chunks of `src/server/` under a cold transform cache. Re-running `documents-boundary.test.ts` alone
with `--testTimeout=90000` on the same (cold) cache passed in **10.22s** wall time (`transform
5.35s, import 1.40s, tests 8.28s`) — inside the current 15s project ceiling
(`vitest.config.ts:149,183`), but with real, thin margin once the machine is also running biome
and `cargo test` concurrently under the same pre-push hook.

`vitest.config.ts`'s `node` and `client` projects already carry a 15s `testTimeout` (raised from
vitest's 5s default) for exactly this shape of problem — the `client` project's own comment
(`:137-148`) documents a ~30x spread under contention (`useTauriFileDrop`'s 18 specs run in 2.9s
alone, ~160ms each, and time out at the 5s default when the machine is loaded) and names the
asymmetry itself as the bug: "the node project was given headroom when it hit this and the client
project never was, so every developer running the suite alongside anything else lost time to a red
run that reproduced nowhere." These two `tests/docs` specs are the same class one level further:
import-heavy and cold-cache-sensitive, currently sitting at the *project's* ceiling with no
per-spec headroom of their own.

The issue lists four directions, in order of confidence, and is explicit that the fourth is **not**
a bug fix: "Consider whether the pre-push hook should run the full suite at all, given CI's `check`
is a required status check on `master` ... Item 4 is a workflow decision, not a bug fix, and should
not be folded in without a deliberate call." This spec implements **only direction 1** ("Raise
`testTimeout` for the import-heavy specs"), and as a **per-test** override — not a global raise of
`vitest.config.ts`'s `testTimeout`. The sweep doc's own instruction for this group is explicit: "a
per-file timeout override for exactly those specs, NOT a global raise" — matching the sibling G2
test-timing group's row ("Lands first; do not raise ceilings") and the general reason: raising the
project-wide ceiling widens the window for every one of the suite's ~11,400 tests, hiding a genuine
future hang behind slack meant for two specific, already-diagnosed specs.

## Fix

Add a per-test timeout to exactly three named `it()` blocks (two named by the issue, plus one
sibling — see "Sibling spec" below), using vitest's options object as the **second** argument, fn
third — already used in this repo (`tests/server/platform.test.ts:428`:
`it("returns null against a server that never responds", { timeout: 15_000 }, async () => {
...`) — **not** a third-argument numeric form; the options object must sit between the name and
the callback, exactly as `platform.test.ts:428` shows.

Use `timeoutMs()` from `tests/helpers/timing.ts` (imported as `import { timeoutMs } from
"../helpers/timing.js"`, matching `tests/server/docx-apply.test.ts:46`'s import), **not** a bare
numeric literal:

- `tests/docs/documents-boundary.test.ts:728` —
  `` it("documents/reload-family.ts exports exactly what is written down", { timeout: timeoutMs(45_000, 120_000) }, async () => { ... }) ``
- `tests/docs/documents-boundary.test.ts:738` (sibling — see below) —
  `` it("documents/open.ts exports exactly what is written down", { timeout: timeoutMs(45_000, 120_000) }, async () => { ... }) ``
- `tests/docs/registry-primitive-containment.test.ts:122` —
  `` it("does not re-export the primitives from the production barrels", { timeout: timeoutMs(45_000, 120_000) }, async () => { ... }) ``

**45s under an ordinary run**, chosen as headroom over the issue's own measured 10.22s cold-cache
wall time for the whole `documents-boundary.test.ts` file — `registry-primitive-containment.test.ts`'s
spec does three dynamic imports against two of the same heavy server modules plus a third, so it is
given the same ceiling rather than a smaller one on the assumption it is cheaper. The number is
comfortably short of the ceilings used elsewhere for operations that are genuinely expensive rather
than merely cold-cache-sensitive (`tests/server/docx-apply.test.ts:88`'s real-apply-path
`timeoutMs(60_000, 300_000)`).

**120s under `npm run test:coverage`, via `timeoutMs(45_000, 120_000)` — not a bare `45_000`
literal, and this is a correction from the spec's first draft.** `npm run test:coverage` passes
`--testTimeout=120000` (`package.json:56`), but `tests/helpers/timing.ts`'s own doc comment states
the reason that flag cannot be relied on here: "Vitest's `--testTimeout` / `--hookTimeout` flags do
NOT raise a timeout written as the second argument to `it`/`beforeAll` — the explicit value wins."
A bare `{ timeout: 45_000 }` literal therefore does not inherit the coverage run's 120s ceiling —
it *replaces* it with 45s for exactly these tests, which is a **regression** under coverage (these
are, per the issue's own citation of `vitest.config.ts:137-148`'s comment, precisely the
cold-transform-sensitive shape that V8 instrumentation slows further) and is the exact failure
`timeoutMs()` exists to prevent. `timeoutMs(45_000, 120_000)` keeps the 45s ordinary-run bound
unchanged (the cold-cache fix this issue asks for) while matching, not narrowing, the coverage run's
existing 120s ceiling.

The spec's first draft rejected `timeoutMs()` on the claim that its call sites are "a fixed, guarded
list" that adding to would be "inaccurate." **That claim was checked against the wrong helper and is
wrong.** `scripts/ci/coverage-manifest.mjs`'s `SUSPENDED_TIMING_SITES` and
`tests/scripts/coverage-manifest-wiring.test.ts` are both keyed off calls to **`expectWithinMs`**
(via `git grep -l expectWithinMs -- tests/`), not `timeoutMs` — verified: `grep -rn timeoutMs
tests/scripts/ scripts/ci/` returns nothing. `timeoutMs()`'s eight existing call sites (e.g.
`tests/server/docx-apply.test.ts:88`) join no guarded list and are subject to no drift check; two
more callers here are the same, unguarded, kind of addition — not a new membership in a mechanism
that was never tracking `timeoutMs` in the first place. `timeoutMs()` is also the *conceptually*
correct helper, independent of the guard question: these two specs' dynamic imports are exactly the
shape `timeoutMs()`'s own doc comment already describes suffering under coverage instrumentation
specifically (a second, compounding cost beyond the cold-cache one this issue diagnosed).

**No change to `vitest.config.ts`.** Both projects' `testTimeout: 15_000` (`:149`, `:183`) stay
exactly as they are — the ceiling for the other ~11,400 tests in the suite is untouched.

**Sibling spec — `documents-boundary.test.ts:738` is included, `registry-primitive-containment.test.ts:176`
is not, and here is why.** Both files have a second `it()` that does its own cold dynamic import of
server modules, in the same file as the one the issue named:

- `documents-boundary.test.ts:738` (`"documents/open.ts exports exactly what is written down"`)
  imports `src/server/documents/open.js`. Re-verified: `open.ts` does **not** import
  `reload-family.js` (checked its full import list), so the `:728` spec's import does not warm this
  one's module graph — whichever spec runs first pays the cold-transform cost, and inserting a spec
  above `:728` would move that unbounded cost onto `:738`. Both specs pay independently, so both get
  the override.
- `registry-primitive-containment.test.ts:176` (`"exports exactly the surface ADR-033 sanctions"`)
  imports only `src/server/documents/registry.js` — a module the covered `:122` spec (three lines
  above, `:126`) already imports directly. Node's module cache means the second import is a cache
  hit, not a second cold transform+import, so `:176` does not need its own override; left at the
  project's 15s ceiling.

## Tests

This is a timing-ceiling change, not new behaviour, so there is no assertion to add that proves the
fix without itself depending on machine/cache state — a deterministic "assert the cold-cache run
takes under 15s" test would be exactly the calibration mechanism the MINIMALITY RULE forbids; the
premise of the issue is that duration varies with cache and contention state, which a unit test
cannot pin without becoming flaky by the same mechanism it is testing for. The discriminating check
is the three `it()` signatures themselves:

```
grep -n 'timeout: timeoutMs(45_000, 120_000)' tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts
```

— exactly two matches in `documents-boundary.test.ts` (the `:728` and `:738` specs) and exactly one
in `registry-primitive-containment.test.ts` (the `:122` spec), each on the named `it()`.

Manual verification (not part of this PR's automated gate, and not run in this sandbox — see `Not
in scope`): clear the vitest transform cache (e.g. `rm -rf node_modules/.vite`) and run
`npx vitest run tests/docs/documents-boundary.test.ts tests/docs/registry-primitive-containment.test.ts --project=node`
cold; all three named specs now have 45s rather than 15s to clear transform+import cost under an
ordinary run, and 120s under `npm run test:coverage`.

## Done when

  `registry-primitive-containment.test.ts:122`) carry `{ timeout: timeoutMs(45_000, 120_000) }` as
  their second argument, callback third — matching `platform.test.ts:428`'s existing shape, not a
  third-argument numeric form.
- Both files import `timeoutMs` from `tests/helpers/timing.js`.
- No `testTimeout` value in `vitest.config.ts` changes.
- `npm run typecheck:tests` stays green (the options-object second-argument form of `it` is already
  used elsewhere in the repo, so no new type shape is introduced).

  stays green, under both `npm test` and `npm run test:coverage`.

## Review corrections (round 1)

Adopted:

- **Switched from a bare `45_000` literal to `timeoutMs(45_000, 120_000)`.** The first draft's
  rejection of `timeoutMs()` rested on a factually wrong claim — that its call sites are "a fixed,
  guarded list" that `coverage-manifest-wiring.test.ts` protects. That test and
  `scripts/ci/coverage-manifest.mjs`'s `SUSPENDED_TIMING_SITES` are keyed off `expectWithinMs`, not
  `timeoutMs` (verified: `grep -rn timeoutMs tests/scripts/ scripts/ci/` is empty); `timeoutMs()`'s
  existing eight callers are unguarded. Worse, a bare `45_000` literal wins over
  `--testTimeout=120000` per vitest's own precedence (explicit value beats the flag — this is
  `tests/helpers/timing.ts`'s own stated reason `timeoutMs()` exists), so it would have *lowered*
  these two specs' ceiling from 120s to 45s under `npm run test:coverage` — the exact regression the
  helper is for. Fixed to `timeoutMs(45_000, 120_000)`.
- **Fixed the argument-position inconsistency.** The Fix text said "object-form third argument";
  the Done-when said "second argument." The repo's own precedent (`platform.test.ts:428`) uses the
  options object as the **second** argument, callback third — vitest's other overload,
  `it(name, fn, number)`, only accepts a bare number in third position, not an object. Both
  sections now say "second argument" consistently and cite `platform.test.ts:428`.
- **Extended the override to `documents-boundary.test.ts:738`.** That spec does its own cold
  dynamic import (`src/server/documents/open.js`), and re-verified `open.ts`'s import list does not
  include `reload-family.js`, so the covered `:728` spec's import does not warm it — the identical
  failure mode was reachable one spec later in the same file, with no note explaining the omission.
  Added, with the same `timeoutMs(45_000, 120_000)` bound.
- **Explained, rather than silently omitted, why `registry-primitive-containment.test.ts:176` is
  NOT extended**: it imports only `registry.js`, already imported by the covered `:122` spec three
  lines above — a cache hit, not a second cold import.

Not adopted:

- None. Every round-1 finding against this spec (the blocking `timeoutMs()` finding and every
  non-blocking finding about the sibling specs and argument position) pointed at the same small set
  of correctable facts and all were adopted.
