## Problem

Re-read on `caf54391`.

**Already fixed.** `watchFile` (`src/server/file-watcher.ts:363`) never throws. If `attachWatcher` throws, it logs, calls `notifyNotWatching`, and returns `false` (`:405-412`). A failed POSIX re-arm notifies too, via `notifyWatchLost`. Both are pinned by `tests/server/file-watcher.test.ts:534` ("the INITIAL arm reports its own failure").

**Gap A: the async `error` listener unwatches silently.** Measured with Node v24.2.0 on win32, in a `mktemp -d -t tandem-XXXXXX` dir:
- `fs.watch` on a missing file throws `ENOENT` synchronously, so it is already notified.
- `fs.watch` on a file whose directory is already deleted throws `ENOENT` synchronously, so it is already notified.
- Watching an existing file and then deleting its parent directory **does not throw**. The handle emits an async `error` (`EPERM`).

That `error` reaches `attachWatcher`'s listener (`file-watcher.ts:151-155`), which logs and calls `unwatchFile` but **does not notify**. The document ends up unwatched with no signal. Linux and macOS were not measured.

**Gap B: startup delivery (the owner's gap, not fixed here).** `restoreOpenDocuments` runs `openFromDisk` → `wireFileWatcher` before the HTTP server binds. `pushNotification` (`src/server/notifications.ts:18`) reaches only current subscribers, and `/api/notify-stream` (`src/server/mcp/routes/notify-stream.ts:20`) replays nothing. A boot-time watch failure therefore reaches nobody. `src/server/session/manager.ts:400-407` already records the same bound for its own boot toast.

## Fix (Gap A only)

- **`file-watcher.ts:151-155`:** after the identity check passes, call `notifyNotWatching(filePath)` before `unwatchFile(filePath)`.
  - It uses the shared `dedupKey` `watch-lost:${path}`, as `notifyWatchLost`'s docblock (`:187-203`) argues.
  - The identity check stays first, so a stale handle's error does not notify.
  - `close()` emits `close`, never `error`, so Tandem's own close and rename flows add no notify.
- Nothing else changes: no change to `recordSelfWrite`/`rearmWatch` ordering, `swapHandle` or the POSIX re-arm. `tests/server/document-write-rearm.test.ts` is untouched, and `notifications.ts` and `notify-stream.ts` are untouched.

## Bryan (Gap B: startup delivery, a policy choice, so not built here)

Concrete options for #1662, which stays open:
1. **Boot-latch held replay in `notifications.ts`.** Hold pushes made before the first subscriber ever attaches, and replay them on a microtask to each client that connects within N seconds. Cost: the window is a policy choice, a stale pre-restart tab or a Cowork LAN client also receives the replay, and it needs the notify-stream TDZ care (a synchronous drain leaks the keepalive interval).
2. **Replay recent `warning` entries from `getBuffer()` on SSE connect**, bounded by age. It is simpler, but it replays mid-session warnings to every reconnecting tab.
3. **A durable `watched: false` fact on `documentMeta`** that the tab UI renders. It survives any connection timing, but it is a new persistent UI surface.
