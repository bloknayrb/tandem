## Problem

Re-read on `caf54391`.

**Already fixed.** `watchFile` (`src/server/file-watcher.ts:363`) does not throw. When `attachWatcher` throws synchronously, it calls `console.error` and `notifyNotWatching` (`:410`) and returns `false`. A failed POSIX re-arm also notifies, via `notifyWatchLost` (`:204-208`). Pinned by `tests/server/file-watcher.test.ts:534` ("the INITIAL arm reports its own failure").

**Gap 1: startup delivery (the owner's).**
- `restoreOpenDocuments` (`src/server/index.ts:558`) and the CHANGELOG/welcome opens (`:708-735`) run `openFromDisk` → `wireFileWatcher` (`src/server/documents/open.ts:1325`) **before** `startMcpServerHttp` binds (`:738`).
- `pushNotification` (`src/server/notifications.ts:18`) dispatches only to current subscribers.
- The only subscriber is `/api/notify-stream` (`src/server/mcp/routes/notify-stream.ts:20`), which receives future pushes only.
- So a watch failure during restore reaches nobody. `src/server/session/manager.ts:400-407` records the same bound for its own boot-time toast.
- Boot-time `index.ts:439/451` pushes (store lock errors) are lost the same way.

**Gap 2: the async `error` listener unwatches silently (measured here, not in the issue).** Node v24.2.0 on win32, in a `mktemp -d -t tandem-XXXXXX` directory:
- `fs.watch` on a missing file **throws** `ENOENT` (errno -4058).
- `fs.watch` on a file in an already-deleted directory **throws** `ENOENT`.
- Watching an existing file and then deleting its **parent directory** does **not throw**: the handle emits an async `error`, `EPERM`.

That `error` reaches `attachWatcher`'s listener (`file-watcher.ts:151-155`), which logs and calls `unwatchFile` but **does not notify**. The document is unwatched, with no signal to the user. Linux/macOS behaviour for a parent-directory delete was not measured here.

## Fix

The smallest change in each of the two named seams.

1. **`file-watcher.ts:151-155`:** after the identity check passes, call `notifyNotWatching(filePath)` before `unwatchFile(filePath)`. It shares `dedupKey` `watch-lost:${path}` with the other two sites, per the reasoning in `notifyWatchLost`'s docblock (`:187-203`). The identity check stays first, so a stale handle's error does not notify: `unwatchFile` on close deletes the entry, and a later error fails the identity check. Leave `recordSelfWrite`/`rearmWatch` ordering, `swapHandle`, and the POSIX-only re-arm untouched. `tests/server/document-write-rearm.test.ts` does not change.
2. **`notifications.ts`: hold what nobody heard.** Add a module-private `undelivered: TandemNotification[]`.
   - In `pushNotification`, when `subscribers.size === 0`, append to it, capped at `NOTIFICATION_BUFFER_SIZE` with oldest evicted, the same as `buffer`.
   - In `subscribe(cb)`, add `cb`, then **swap the held list out synchronously**, so a second subscriber in the same tick receives nothing. Deliver it in a `queueMicrotask`, only if `subscribers.has(cb)` is still true, and wrap each call in the same try/catch as `pushNotification`.
   - **The microtask is load-bearing:** `notify-stream.ts:20`'s callback calls `cleanup()`, which reads `const unsubscribe` and `const keepalive`, both still in the TDZ during a synchronous call from inside `subscribe()`. A throwing backlog write would then escape the handler.
   - `resetForTesting` clears `undelivered`.
   - Update the module docblock, and **correct `session/manager.ts:400-407`**, whose claim "the SSE route has no backlog replay … the toast reaches nobody" becomes false.
   - No client change and no new route. Info notifications are still tray-only on the client.

The decision taken is to hold every notification pushed while there are no subscribers. That covers both boot and a webview reload gap. A `watched: false` document fact and a retry-once were both rejected: the first needs a new persistent UI surface, and the second is unmotivated, since the measured failures (`ENOENT`, `EPERM` on a deleted directory) would not recover on an immediate retry.
