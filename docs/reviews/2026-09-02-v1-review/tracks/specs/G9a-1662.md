# G9a — #1662 A document whose watcher fails stays unwatched for the session, silently

Branch `fix/watcher-and-reload-silence-an-unwatched-document-a-silent-declined-reload-and-a-required-cleanup-phase-1695`. Closes #1662 unless the body names remaining work; the list is derived last. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:103` (wave 9, G9a). Probe: the `fs.watch` measurement below. **The issue's premise is partly stale.** The owner's triage comment (2026-09-08, verified against `aee088f6`) says the initial-arm failure now notifies, and it keeps the issue open for one named gap: **delivery at startup**.

## Problem

Re-read on `caf54391`.

**Already fixed.** `watchFile` (`src/server/file-watcher.ts:363`) does not throw. When `attachWatcher` throws synchronously, it calls `console.error` and `notifyNotWatching` (`:410`) and returns `false`. A failed POSIX re-arm also notifies, via `notifyWatchLost` (`:204-208`). Pinned by `tests/server/file-watcher.test.ts:534` ("the INITIAL arm reports its own failure").

**Gap 1: startup delivery (the owner's).**
- `restoreOpenDocuments` (`src/server/index.ts:558`) and the CHANGELOG/welcome opens (`:708-735`) run `openFromDisk` → `wireFileWatcher` (`src/server/documents/open.ts:1325`) **before** `startMcpServerHttp` binds (`:738`).
- `pushNotification` (`src/server/notifications.ts:18`) dispatches only to current subscribers.
- The only production subscriber is `/api/notify-stream` (`src/server/mcp/routes/notify-stream.ts:20`), which receives future pushes only.
- So a watch failure during restore reaches nobody. `src/server/session/manager.ts:400-407` records the same bound for its own boot-time toast.
- Boot-time `index.ts:439/451` pushes (store lock errors) are lost the same way.

**Gap 2: the async `error` listener unwatches silently (measured here, not in the issue).** Node v24.2.0 on win32, in a `mktemp -d -t tandem-XXXXXX` directory:
- `fs.watch` on a missing file **throws** `ENOENT` (errno -4058).
- `fs.watch` on a file in an already-deleted directory **throws** `ENOENT`.
- Watching an existing file and then deleting its **parent directory** does **not throw**: the handle emits an async `error`, `EPERM`.

That `error` reaches `attachWatcher`'s listener (`file-watcher.ts:151-155`), which logs and calls `unwatchFile` but **does not notify**. The document is unwatched, with no signal to the user.

On Linux, a parent-directory delete also deletes the file's inode, so delivery reaches the non-win32 missing arm (`:314-331`), then `swapHandle`, then `notifyWatchLost`, **which already notifies**. That is pinned for a file delete by real-fs spec (4). macOS was not measured.

## Fix

The smallest change in each of the two named seams.

1. **`file-watcher.ts:151-155`:** after the identity check passes, call `notifyNotWatching(filePath)` before `unwatchFile(filePath)`.
   - It shares `dedupKey` `watch-lost:${path}` with the other two sites, per the reasoning in `notifyWatchLost`'s docblock (`:187-203`). On Linux a double report (an error plus a delivery) coalesces on the client.
   - The identity check stays first, so a stale handle's error does not notify. `unwatchFile` on close deletes the entry, so a later error fails the identity check.
   - Tandem's own rename and close flows add no spurious notify. `document-service.ts:1370` calls `unwatchFile(oldPath)` synchronously before `await fs.rename` (`:1390`), so a late `error` on the old handle fails the identity check at `:153`.
   - Leave `recordSelfWrite`/`rearmWatch` ordering, `swapHandle`, and the POSIX-only re-arm untouched. `tests/server/document-write-rearm.test.ts` does not change.
2. **`notifications.ts`: hold what nobody heard at boot, briefly, and replay it to each client that connects in that window.**
   - Add module-private state: `held: Array<{ notification: TandemNotification; heldAt: number }>`, a latch `everSubscribed = false`, and `const HELD_REPLAY_MAX_AGE_MS = 60_000`.
   - **Hold only before the first subscriber ever attaches (boot latch).** In `pushNotification`, when `subscribers.size === 0 && !everSubscribed`, append `{ notification, heldAt: Date.now() }`. Cap it at `NOTIFICATION_BUFFER_SIZE`, evicting the oldest, the same as `buffer`. After the latch closes, a zero-subscriber push is not held, exactly as today.
   - **Replay to every subscriber that connects while entries are fresh; do not consume them.** In `subscribe(cb)`: add `cb`, set `everSubscribed = true`, then `queueMicrotask` a drain. The drain first drops entries whose `heldAt` is older than `HELD_REPLAY_MAX_AGE_MS`. It then walks the survivors in order, **re-checking `subscribers.has(cb)` before EACH item**, and calls `cb` in the same try/catch as `pushNotification`.
     - Age is measured from `heldAt`, the server's hold time, not from the caller-supplied `timestamp`.
     - Because nothing is consumed, a subscriber that disconnects before its microtask loses nothing for the next one, and a pre-restart tab reconnecting first cannot take the list away from the editor the user is looking at.
     - The client coalesces the tray by `dedupKey`, and live pushes already fan out to every tab, so a second delivery is harmless.
   - **Why the drain is a microtask.** `notify-stream.ts:20`'s callback runs inside `subscribeNotifications(...)`, before `const unsubscribe` (`:20`) and `const keepalive` (`:29`) are initialized. On a failed write, the callback's `cleanup()` evaluates `clearInterval(keepalive)` in the TDZ and throws a `ReferenceError`. The drain's try/catch logs it, so nothing escapes the handler. But `unsubscribe()` never runs, and the interval created at `:29` is never cleared. **A synchronous drain leaks the keepalive interval and the subscriber on a failed write.** That is the harm, and it is what the throwing-write spec asserts.
   - `resetForTesting` clears `held` and resets `everSubscribed` to `false`.
   - **Bounds, stated in the `notifications.ts` module docblock and in the PR body:**
     - A boot notification reaches the user only if an editor connects within 60 s of the push.
     - Any client that connects in that window gets it, including a pre-restart tab whose `EventSource` auto-reconnects (`useNotifications.svelte.ts:290`), and, under a Cowork non-loopback bind, a LAN client. The route is a GET under `lanAwareApiMiddleware` (`api-routes.ts:388`, `mcp/server.ts:646-648`). No generation check is added; the content is what that client would receive live anyway.
     - A tab that reconnects within the window pops the warning again, while its tray row coalesces.
     - A notification pushed in a later zero-subscriber gap, such as a mid-session webview reload, is still lost, as today.
   - **Correct four places that state the old no-replay semantics:** `src/server/session/manager.ts:400-407`; `src/client/App.svelte:828-830` (comment only); `tests/e2e/activity-tray.spec.ts:13-15` (comment only); and `docs/mcp-tools.md`'s `### GET /api/notify-stream` section (`:1528`), which gets one line on the boot-only held replay and its 60 s bound. Rewrite each to the new bound rather than deleting it. The two E2E-hook comments must still say why `__tandemTest.pushNotification` is needed: a mid-session zero-subscriber gap is still unheld, and a real SSE connect is still a race for a test. Do not touch `docs/security.md` or `docs/troubleshooting.md` (PR #1998 owns them).
   - No new route, no `data-testid` change, and no client behaviour change. Info notifications are still tray-only on the client.

**Decisions taken, not deferred work:**
- **"Hold every zero-subscriber gap" was rejected.** It replays hours-stale warnings into the first editor after a long headless or stdio session, because warnings always pop (`useNotifications.svelte.ts:253`). And it leaks pushes from one Playwright test's teardown into the next test's fresh page. `playwright.config` uses `workers: 1` and a shared backend, and `activity-tray.spec.ts:66` asserts "No activity" right after load.
- **"First subscriber takes all" was rejected**, because of the stale-tab and LAN-client takeover above.
- **A durable `watched: false` document fact was rejected.** It needs a new persistent UI surface, and the warning, which persists in the tray, is the carrier.
- **Retry-once was rejected.** The measured failures (`ENOENT`, `EPERM` on a deleted directory) would not recover on an immediate retry.
- **The 60 s window** covers restore → bind → webview load, and it is short enough that a replayed boot warning is still about the current session.

## Tests

1. **`tests/server/notifications.test.ts`** (new cases; the existing synchronous specs are unaffected because live dispatch stays synchronous):
   - (a) Push with no subscribers, then `subscribe(h)`. `h` is not called synchronously, and after `await Promise.resolve()` it has been called once with that notification. This kills today's behaviour, where it is never called.
   - (b) After (a), `subscribe(h2)` while the held entry is still fresh: after a microtask, `h2` has been called once with it. This kills "first subscriber takes all".
   - (c) After (a), unsubscribe every subscriber, push `n2` with none attached, then `subscribe(h3)`. `h3` receives the boot entry and **not** `n2`. This kills "hold every gap".
   - (d) `subscribe(h1)` first, push while `h1` is subscribed, then `subscribe(h2)`: `h2` receives nothing. This kills "replay `getBuffer()`".
   - (e) 60 pushes with no subscribers deliver the last 50, in order.
   - (f) `subscribe(h)` then `unsubscribe` before the microtask: `h` receives nothing, and a following `subscribe(h2)` receives the held entry. This kills a consume-on-subscribe drain.
   - (g) Age, under `vi.useFakeTimers()` (vitest 4.1.11 fakes `Date` and `setInterval` but not `queueMicrotask`, per `node_modules/vitest/dist/chunks/test.DNmyFkvJ.js:3299`): push, advance `HELD_REPLAY_MAX_AGE_MS + 1`, subscribe, and after a microtask nothing is delivered. The control at `HELD_REPLAY_MAX_AGE_MS - 1` is delivered. This kills an unbounded hold.
