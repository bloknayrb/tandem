# Gc1 — #1772 An armed "Accept all / Reject all" confirm survives a document switch and fires on the other document

Branch `fix/client-state-highs-1772`. Closes #1772. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-ui.md:18`. Probe: the review's Playwright lane (`docs/reviews/2026-09-02-v1-review/raw/verify-client.txt`).

## Problem

`bulkConfirm` (`src/client/panels/SidePanel.svelte:187`, plain component-local `$state<"accept" | "dismiss" | null>`) is armed by `onRequestAccept` / `onRequestDismiss` (`:756-757`) and consumed by `handleBulk` (`:506-509`), which iterates `filteredData.reviewPending` — the *currently rendered* document's pending review targets, recomputed from the `annotations` prop.

`SidePanel` is mounted once, through `PanelSlot` with a display toggle and no `{#key documentId}` (`App.svelte:2458-2473`). The single reset effect (`:217-224`, "Reset bulk confirm when filters change") reads `filterType` / `filterAuthor` / `filterStatus` and nothing document-shaped. So arming on document A and confirming on document B accepts or rejects **B's** pending comments; the `$effect` at `:213-215` even re-focuses the Confirm button after the switch, parking the keyboard one Enter away.

`BulkActions` renders only when `pendingCount > 1` (`BulkActions.svelte:42`), which is why the bug hides in casual testing: with fewer than two pending review targets on B the bar unmounts and the armed flag is invisible.

## Fix

**One line**, in `src/client/panels/SidePanel.svelte:217-224` — add `void documentId;` to the existing reset effect's dependency reads and widen its comment to "Reset bulk confirm when the filters **or the document** change". `documentId` is already a destructured prop (`:80`), so nothing else is threaded.

- The fix is a **reset, not a remount**: `ChatPanel`/`SidePanel` are always mounted by design (CLAUDE.md, Client/UI) so local state survives panel switches; a `{#key documentId}` would drop scroll position, filters and reply drafts with it.
- **Key the reset on `documentId` only — never on `annotations` or on array identity.** `App.svelte` recomputes `visibleAnnotations` on every store change, so an annotations-keyed reset would silently cancel the user's armed confirm every time Claude posts a comment on the document they are reviewing. **This axis is pinned by the second E2E case below** (arrival of a third comment on the *same* document must leave the confirm armed), not by code review alone.
- Svelte 5: an `$effect` that reads a prop and writes `$state` is the sanctioned shape. The forbidden shape is a **synchronous `$state` write from a Tiptap `transaction`/`update` handler** — not reached here.
- **Do not add a second reset for `promoteConfirmRequested`** (`:538`), and do not extend the four-site invariant documented at `:517-537` to a fifth. Measured: the prune effect at `:541-563` reads `filteredData.pending`, so on a switch `pruned` is empty, `pruned.size !== selectedImportIds.size`, and it clears `selectedImportIds` **and** `promoteConfirmRequested` in the same `untrack` block. A switch also empties `selectedImportIds`, so `BatchPromoteBar` unmounts outright (`BatchPromoteBar.svelte:62`, `{#if selectedCount > 0}`). State this in the PR body; **do not write a test for it** — it is existing behaviour this fix does not touch, and a switch-based assertion would be satisfied by the unmount rather than by the flag.
- **No `data-testid` is added, renamed or removed by the #1772 commit**; `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is unchanged **by this commit**. #1773's commit on the same branch does add selectors and regenerate it, so a snapshot diff at PR level is expected.
- No Y.Doc write, no Y.Map key, no MCP tool, no `/api` route: Critical Rules 1, 2 and 9 are not in play.

## Tests

**Two E2E cases, in `tests/e2e/settings-and-filters.spec.ts`**, beside the two existing bulk-confirm reset tests (`:330-365`, `:367+`), which are the shape to copy. The first pins the disarm on a document switch; the second pins that the reset is keyed on `documentId` and *not* on `annotations` — the one axis the switch case cannot separate. The existing file already proves per-dep pinning is the local convention: `:367+` and the case after it each isolate a single filter dep and each carries its own anti-false-positive mount check.

### Case 1 — the disarm on a document switch

Change the file's `beforeEach` to `createFixtureDir("sample.md", "sample2.md")` (`helpers.ts:97` is variadic; precedent `annotation-lifecycle.spec.ts:41`). Seed via MCP: open `sample.md`, add two comments (`[2,6]` "Test", `[7,15]` "Document" — the offsets this file already uses); open `sample2.md`, add two on its heading text (`# Second Document` → `[2,8]` "Second", `[9,17]` "Document"; both inside heading *text*, so no heading-markup overlap). Two per document is mandatory — `pendingCount > 1` is what keeps the bar mounted on both.

Then: `page.goto("/")`, `switchToAnnotationsTab`, click sample.md's tab (`page.locator("[data-testid^='tab-'][role='tab']").filter({ hasText: "sample.md" })` — the `tab-scroll-memory.spec.ts:36` pattern), click `bulk-accept-btn`, assert `bulk-confirm-btn` visible, click sample2.md's tab, then assert **both**:

- `bulk-dismiss-btn` is visible — the bar is still mounted, so the disarm is not an unmount artifact. Without this the test passes on a bar that simply vanished. (`bulk-dismiss-btn` is the correct mount indicator here because the assertion is that the bar is in its **rest** branch; `BulkActions.svelte:73-84` renders it only there.)
- `bulk-confirm-btn` is not visible.

That pair is the whole discriminator. Then carry it through to the harm: on sample2.md click `bulk-accept-btn` again, wait for `bulk-confirm-btn`, click it, and assert via `tandem_getAnnotations` per `documentId` that **sample2.md's two are `accepted` and sample.md's two are still `pending`** — this is what makes the flow reach a real `handleBulk` rather than stopping at a visibility check.

Open the test with a comment stating two things, per the file's local convention:

1. *A tab switch moves `documentId` and the `annotations` array together, so this case cannot on its own isolate which axis the reset keys on — case 2 is what discriminates that, by moving `annotations` with `documentId` held fixed.*
2. *The `tandem_getAnnotations` values are byte-identical to the recorded broken-build output (`docs/reviews/2026-09-02-v1-review/raw/verify-client.txt:3`, "DOC A STATUSES pending,pending; DOC B STATUSES accepted,accepted"). They are there so the flow executes a real resolve, not because they distinguish a fixed build from a broken one — the disarm pair above does that.*

### Case 2 — an armed confirm survives a new annotation on the same document

Case 1 passes on an over-broad reset. A reset keyed on `annotations` (or on array identity) disarms on *every* store change and therefore also disarms on a tab switch, so it satisfies every assertion above — while silently cancelling the user's armed confirm each time Claude posts a comment on the document they are reviewing. That is the regression the Fix section's "documentId only" bullet forbids, and this case is what makes it fail.

`PanelSlot` mounts `SidePanel` once (`PanelSlot.svelte:51`, a `display: none` toggle) and `App.svelte` passes `annotations={visibleAnnotations}` and `documentId={activeTab?.id}` as **separate props** (`:2459`, `:2463`), so the two move independently inside one document — which is what makes this axis testable at all.

Single document, no tab switch. Open `sample.md` and add the same two comments (`[2,6]` "Test", `[7,15]` "Document"); `page.goto("/")`, `switchToAnnotationsTab`, click `bulk-accept-btn`, assert `bulk-confirm-btn` is visible **and that the confirm row reads "2 annotations?"** (`BulkActions.svelte:33-36` renders `` `${pendingCount} annotations?` `` whenever `pendingCount === allPendingCount`, which holds under the default all/all/all filters). Then, with the confirm still armed, `await mcp.callTool("tandem_comment", { from: 16, to: 24, text: "Third" })` on that same document — the offsets `:367+` already uses — and assert **both**:

- `bulk-confirm-btn` is **still visible**. This is the discriminating assertion: it fails on an `annotations`- or identity-keyed reset and passes on `void documentId;`.
- the confirm row now reads "3 annotations?" — proof the new annotation actually reached the panel, so a passing first assertion cannot be an artifact of the comment never arriving.

No tab switch anywhere in this case: `documentId` is constant throughout, so the only dependency that moved is `annotations`.

Reserved harness ports only — never 3478/3479, for both cases.
