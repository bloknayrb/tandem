# Gc1 — #1772 An armed "Accept all / Reject all" confirm survives a document switch and fires on the other document

Branch `fix/client-state-highs-1772`. Closes #1772. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-ui.md:18`. Probe: the review's Playwright lane (`experiments/raw/verify-client.txt`) — no happy-dom harness experiment exists for this one.

## Problem

`bulkConfirm` (`src/client/panels/SidePanel.svelte:187`, plain component-local `$state<"accept" | "dismiss" | null>`) is armed by `onRequestAccept` / `onRequestDismiss` (`:756-757`) and consumed by `handleBulk` (`:506-509`), which iterates `filteredData.reviewPending` — the *currently rendered* document's pending review targets, recomputed from the `annotations` prop at `:264-299`.

`SidePanel` is mounted once, through `PanelSlot` with a display toggle and no `{#key documentId}` (`App.svelte:2458-2473`; `documentId={activeTab?.id}` at `:2464` does change on a tab switch, and `App.svelte:2789` keys only `ExternalConflictBanner`). The single reset effect (`:217-224`, "Reset bulk confirm when filters change") reads `filterType` / `filterAuthor` / `filterStatus` and nothing document-shaped. So arming on document A and confirming on document B accepts or rejects **B's** pending comments; the `$effect` at `:213-215` even re-focuses the Confirm button after the switch, parking the keyboard one Enter away.

`BulkActions` renders only when `pendingCount > 1` (`BulkActions.svelte:42`), which is why the bug hides in casual testing: with fewer than two pending review targets on B the bar unmounts and the armed flag is invisible.

## Fix

**One line**, in `src/client/panels/SidePanel.svelte:217-224` — add `void documentId;` to the existing reset effect's dependency reads and widen its comment to "Reset bulk confirm when the filters **or the document** change". `documentId` is already a destructured prop (`:80`), so nothing else is threaded.

- The fix is a **reset, not a remount**: `ChatPanel`/`SidePanel` are always mounted by design (CLAUDE.md, Client/UI) so local state survives panel switches; a `{#key documentId}` would drop scroll position, filters and reply drafts with it.
- Svelte 5: an `$effect` that reads a prop and writes `$state` is the sanctioned shape. The forbidden shape is a **synchronous `$state` write from a Tiptap `transaction`/`update` handler** (bridge through `createCoalescingTick`) — not reached here.
- **Do not add a second reset for `promoteConfirmRequested`** (`:538`), and do not extend the four-site invariant documented at `:517-537` to a fifth. Measured: the prune effect at `:541-563` reads `filteredData.pending` (derived from the `annotations` prop, which swaps with the document), so on a switch `validIds` holds B's import-note ids, `pruned` is empty, `pruned.size !== selectedImportIds.size`, and it clears `selectedImportIds` **and** `promoteConfirmRequested` in the same `untrack` block. Annotation ids are per-record, so A's selection can never survive into B. The `promoteConfirm` derived's `size > 0` term masks the flag until then. **This measurement is pinned by component case (e) below, not merely stated in the PR body** — a PR body is not a gate, and batch promote is the one bulk action with no undo (`SidePanel.svelte:517-519`). State it in the PR body as well, so nobody re-opens it.
- **No `data-testid` is added, renamed or removed by the #1772 commit** — Critical Rule 7 is untouched and `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is **unchanged by the #1772 commit**. It is *not* unchanged on the branch: #1773's commit on this same branch adds four session-confirm selectors and does regenerate it (see `Gc1-1773.md`), so a snapshot diff at PR level is expected and correct. No `docs/design-system-impl/testid-manifest.md` edit from #1772.
- No Y.Doc write, no Y.Map key, no MCP tool, no `/api` route: Critical Rules 1, 2 and 9 are not in play.

`review` defaults to a real `useAnnotationReview({ getYdoc: () => ydoc, getEditor: () => null, getAnnotations: () => annotations, onActiveAnnotationChange: () => {}, getScrollBehavior: () => "auto" })`, but is a **prop so a test can inject a spy** — case (f) needs `resolveAnnotation` to be a `vi.fn()`.

**2. New `tests/client/bulk-confirm-document-switch.test.ts`** (`// @vitest-environment happy-dom`, `render` + `rerender` from `@testing-library/svelte`, `tick()` between steps — the shape of `store-readonly-banner.test.ts`). Annotations must satisfy `isPendingReviewTarget` (`src/shared/types.ts:290` — `status: "pending"` and `author !== "user"`), two per document, or `BulkActions` never mounts and every assertion below passes vacuously. Each case asserts the bar *is* mounted (`bulk-dismiss-btn` visible) before asserting anything about the confirm, the way `settings-and-filters.spec.ts:361-363` already insists.

- **a) The fix.** Click `bulk-accept-btn`; assert `bulk-confirm-btn` present. `rerender` with a new `documentId` **and** B's two annotations; assert `bulk-confirm-btn` is gone and `bulk-accept-btn` is back. Kills a no-op fix and a fix that only clears on unmount.
- **b) Over-broad reset, annotations axis.** Arm, then `rerender` with the **same** `documentId` and a third annotation appended. Assert the confirm **survives**. Kills a fix keyed on `annotations` — which would silently cancel the user's armed confirm every time Claude posts a comment on the document they are reviewing. *Put this in the test's comment:* the bulk confirm's sentence is `$derived` off the live `pendingCount` prop (`BulkActions.svelte:33-38`), so it re-renders rather than going stale — which is why an annotations change does **not** invalidate it, unlike `promoteConfirmRequested`, whose sentence snapshots a user-made selection and is therefore reset at all four mutation sites (`SidePanel.svelte:526-537`). And this case pins survival **only within the document-switch fix's scope**: it is not a ruling that a stale bulk count is acceptable. If the count-staleness class is fixed later for the bulk bar too, (b) and (c) are expected to change with it.
- **c) Over-broad reset, identity axis.** Arm, then `rerender` with the same `documentId` and a *new array containing the same annotations*. Assert the confirm survives. Kills a fix keyed on array identity: `App.svelte` recomputes `visibleAnnotations` on every store change, so an identity-keyed reset is (b) with no observable trigger. Same scope caveat as (b).
- **d) Unrelated-prop no-op.** Arm, then `rerender` changing a prop `SidePanel` genuinely consumes but the fix must ignore — `storeReadOnly` (`SidePanel.svelte:87`) — with `documentId` and `annotations` unchanged; assert the confirm survives. This forces a real re-render without touching the intended key. (Do **not** write this as a `rerender` with no changed dependency: Svelte 5 re-runs no `$effect` when nothing it reads changed, so such a case observes nothing, and the always-reset failure mode it would claim to kill is already killed by (a)'s first half.)
- **e) The `promoteConfirmRequested` measurement, enforced.** Seed two `{ author: "import", type: "note", status: "pending" }` annotations on A, check both import checkboxes, click Promote to arm the BatchPromoteBar confirm; then `rerender` with B's `documentId` and B's annotations and assert the promote confirm is **gone**. This is what turns the Fix section's "do not add a fifth reset site" from narration into a gate: the prune effect (`:541-563`) is the only thing clearing it across a switch, and nothing else in the suite would notice if that stopped being true.
- **f) The harm itself: `handleBulk` resolves the right document.** Render with a spy `review` whose `resolveAnnotation` is a `vi.fn()`. Arm on A, `rerender` to B's `documentId` + B's annotations, **re-arm on B** (`bulk-accept-btn` → `bulk-confirm-btn`), click Confirm, and assert `resolveAnnotation` was called exactly twice, with **B's two ids only** and never with either of A's. This is the only case that exercises `handleBulk` (`SidePanel.svelte:506-509`) at all; without it the contract at risk — the loop over `filteredData.reviewPending` as it stands at confirm time — is pinned by zero assertions.
