# G6 — #1722 (rail half) Rail toggles are silent no-ops on a read-only settings blob

Branch `fix/rail-seam-a-tab-switch-inside-a-chat-reveal-a-reveal-that-outlives-its-pin-and-rail-toggles-that-refuse-in-silence-1719`. **Refs #1722 — the issue stays open.** Ledger: none — non-review issue; sweep row wave 9 `G6 rail seam` in `docs/plans/2026-09-06-open-issues-sweep.md`, and row 8 `E2-upgrade` (#1985, MERGED) for the half that already landed. Probe: none scripted. The read-only condition is reached by seeding a settings blob whose **`schemaVersion` exceeds `CURRENT_SCHEMA_VERSION`** — `useTandemSettings.ts:906-907` is the gate (`typeof parsed.schemaVersion === "number" && parsed.schemaVersion > CURRENT_SCHEMA_VERSION`, with `CURRENT_SCHEMA_VERSION = 20` at `:535`) and `:963` is the stamp (`return { ...normalized, ...futureFields, _readOnly: true }`). An unknown *key* alone does nothing: a blob with a current or absent `schemaVersion` falls through to `return normalizeKnownFields(parsed)` at `:965`, which never sets `_readOnly`. The existing precedent is `tests/client/use-tandem-settings-migration.test.ts:153` ("v3 forward-compat: schemaVersion=99 loads as `_readOnly: true`").

**Scope is the rail half only**, per the owner's comment of 2026-09-15: the `updateSettings` boolean and the deduplicated refusal warning landed in #1985, and **#1964's radiogroup `readOnly` contract is a separate open issue** (verified OPEN, label `ui`, titled as extending #1722). It is `Refs` rather than `Closes` because #1964 extends this issue and the owner's own comment keeps the two linked — closing #1722 here would drop that linkage. Whether #1722 closes on #1964's merge is Bryan's call.

## Problem

`updateSettings` returns `boolean` since #1985 — declared at `useTandemSettings.svelte.ts:39`, implemented at `:114-130`, returning `false` on the `_readOnly` short-circuit at `:115-118`, which also fires the one registered refusal handler. That handler is registered once at `App.svelte:283-296` and pushes a warning notification with `dedupKey: "settings-readonly"` (`:294`).

**The rail half never consumes it.** `toggleLeft` (`model.svelte.ts:165-169`) and `toggleRight` (`:171-180`) both return `void`, so neither the model nor its caller can tell a refused write from an applied one. The user-visible outcome of a refused rail toggle is: the notification fires (from #1985), and **the rail does not move** — correct, but unexplained at every layer beneath that notification.

**What the issue body claims beyond that does not hold, and this spec does not inherit it.** The body and the owner's comment say focus "drops to `<body>`" via `focusToggleTarget` (`App.svelte:1183-1192`, warn at `:1190`). Read on master, that warn is unreachable for both ids it can build at `:1185`:

- `panel-edge-collapse-${side}` is the `edgeCollapse` snippet (`App.svelte:2810-2823`), rendered unconditionally inside `.rail-full` (`{@render edgeCollapse("right", toggleRightPanel)}` at `:2487`), and `.rail-shell.collapsed .rail-full { display: none }` (`:3325-3327`) **hides rather than unmounts** it.
- `peek-strip-${side}` is `PeekStrip`'s own button (`src/client/panels/PeekStrip.svelte:84-93`, testid at `:86`), mounted unconditionally at `App.svelte:2561-2567` and hidden by inline style while the rail is open (`style={collapsed ? "" : "display: none;"}`, `:91`); the comment at `:80-83` says "Always rendered (instance persists)".

So on a refusal nothing re-renders, `document.querySelector` finds the hidden element on **both** branches, `el.focus()` at `:1188` runs against a `display: none` element and is a no-op, and the `else` at `:1189-1191` never executes. Focus stays where the click put it. **That is a read of master, not a browser measurement** — Tests item 6 is the measurement step, and it decides whether any of this changes.

`tests/client/layout-model.svelte.test.ts`'s `makeSettingsState` (`:45-78`) has no `_readOnly` axis; its own comment at `:72-74` says so and names this group as the owner.

## Fix

The user-visible signal already exists (#1985). This is about making the rail path **report** the refusal at the model layer — **do not invent a second notification channel, and do not claim a focus repair.**

- `model.svelte.ts`: `toggleLeft` and `toggleRight` return `boolean` — the value `updateSettings` returned. `toggleRight` has two branches (`:172-179`); each returns its own call's result, so the hidden→show branch (which writes `rightPanelVisible` and, in solo, `soloRailHidden`) reports its single write. Update the interface docs at `:108-111`, which currently declare `void`.
- **Define what the boolean means, in those interface docs**: "the write was applied — i.e. not refused as read-only". It is **not** a persistence signal. `updateSettings` wraps `localStorage.setItem` in a try/catch that swallows the failure (`useTandemSettings.svelte.ts:121-125`, "localStorage unavailable (incognito/storage-disabled)"), then assigns `settings = next` and returns `true` at `:129`. Say so at `model.svelte.ts:108-111` so a later reader cannot take it for a durability guarantee.
- `App.svelte:1194-1219`: guard the focus call — `if (!layoutModel.toggleLeft()) return;` before `focusToggleTarget("left", nextVisible)` (`:1202`), and the same on the right before `:1218`. **This is a defensive skip of a no-op, not a focus fix.** On refusal nothing unmounts, so the unguarded call resolves a hidden element and `focus()` does nothing; the guard removes a pointless `queueMicrotask` + `querySelector`. No measured user-visible delta, and the PR body must not claim one.
- `focusToggleTarget`'s `console.warn` **stays, unchanged** — and describe it accurately: it is retained as-is, and **no reachable case for it was measured**. Do not write that it "covers a genuine unmount race"; that is an absence claim nothing here tested.
- `toggleLeftPanel` / `toggleRightPanel` keep returning `void`: their consumers are the builtin-action bag (`App.svelte:981-982`) and the markup, all discarding.
- **The float-clearing writes before the toggle are deliberately left in place.** `pinFromFloat(side)` (`:1220-1230`) and `railFloat[side] = false` have already run when a refusal arrives; dismissing a transient hover float on a click is correct regardless of whether the pin landed, and the hover lifecycle re-arms on the next `mouseenter`.
- **Known, accepted consequence on the right:** `toggleRightPanel`'s reveal teardown + `railPinSnap` block (`:1205-1213`) also runs before the toggle, so a refused pin still dismisses an open reveal. Left as-is rather than re-ordered: the comment at `:1195-1197` states the float must be cleared BEFORE the visibility commit, and re-ordering that block to chase a rare refusal risks the `.collapsed.floating` frame it exists to prevent. The refusal notification explains why the rail did not pin. Recorded as an assumption, not discovered later.

## Tests

1. **`tests/client/layout-model.svelte.test.ts` — give `makeSettingsState` the `_readOnly` axis** its `:72-74` comment defers to this group: a second argument whose read-only form applies nothing and returns `false`. This is the harness half the issue body calls "the cheap half of the fix", and it is what made all six toggle specs structurally blind.
2. **"toggleLeft reports a refused write and changes nothing"**: read-only harness, `expect(model.toggleLeft()).toBe(false)`, and assert the whole settings object is unchanged (the `:345-365` spec's whole-object comparison is the precedent — a two-key assertion passes a write that lands elsewhere).
3. **"toggleRight reports a refused write in BOTH branches"**: once from visible→hide, once from solo-hidden→show. Two cases, because a fix that returns the boolean from only the first branch passes a single-case spec while the show path — the one that writes two keys — still reports success.
4. **"toggleLeft/toggleRight report `true` when the write lands"**: the positive twin, without which a fix that returns a constant `false` passes 2 and 3.
5. The existing toggle specs (`:328-449`) keep passing unchanged, ignoring the return value — they are the regression net for the signature change.
6. **No new E2E, and here is the measurement that decides it.** Before writing the `App.svelte` guard, drive the real app once: seed `localStorage["tandem:settings"]` (`TANDEM_SETTINGS_KEY`, `src/shared/constants.ts:212`) with `{ schemaVersion: CURRENT_SCHEMA_VERSION + 1 }` (21 today) inside a `try`/`catch` (precedent: `disableHoverReveal`, `tests/e2e/chat-reveal.spec.ts:50-61`), boot, click the right rail chevron in each direction, and record `document.activeElement` and the console. **Record the result in the PR's assumptions.**
   - If it matches the Problem section (focus unchanged, no `[tandem] focusToggleTarget` warn), add no E2E: an assertion that is green on master and green after the fix pins nothing, and the substantive behaviour is fully covered by specs 1-4. Say plainly in the PR body that the `App.svelte` guard carries no test.
   - If focus **does** move to `<body>`, the static read above is wrong: update this spec first, then add the E2E with the focus assertion as its discriminator.
   The earlier draft of this item asserted the `<body>` drop and called it "red on master" without measuring either; that claim is withdrawn.
7. **Mutation-test** (memory rule): make `toggleRight` return a constant `true` and watch **spec 3** go red by name; make the harness's read-only form return `true` and watch **specs 2 and 3** go red. The old first mutant ("drop the guard and watch the E2E focus spec go red") is withdrawn with the spec it named. Restore from a file copy, never `git checkout`.
