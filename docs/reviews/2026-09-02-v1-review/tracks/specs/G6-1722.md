# G6 — #1722 (rail half) Rail toggles are silent no-ops on a read-only settings blob, and drop keyboard focus

Branch `fix/rail-seam-a-tab-switch-inside-a-chat-reveal-a-reveal-that-outlives-its-pin-and-rail-toggles-that-refuse-in-silence-1719`. **Refs #1722 — the issue stays open.** Ledger: none — non-review issue; sweep row wave 9 `G6 rail seam` in `docs/plans/2026-09-06-open-issues-sweep.md`, and row 8 `E2-upgrade` (#1985) for the half that already landed. Probe: none scripted; the condition is reachable by seeding a settings blob carrying an unknown key (`useTandemSettings.ts:959-963` stamps `_readOnly: true`).

**Scope is the rail half only**, per the owner's comment of 2026-09-15: the `updateSettings` boolean and the deduplicated refusal warning landed in #1985, and **#1964's radiogroup `readOnly` contract is a separate open issue**. It is `Refs` rather than `Closes` because #1964 extends this issue and the owner's own comment keeps the two linked — closing #1722 here would drop that linkage. Whether #1722 closes on #1964's merge is Bryan's call.

## Problem

`updateSettings` returns `boolean` since #1985 — `false` on the `_readOnly` short-circuit, which also fires the one registered refusal handler (`useTandemSettings.svelte.ts:39`, `:114-118`; the handler is registered once at `App.svelte:283-296` and pushes a `dedupKey: "settings-readonly"` warning notification).

**The rail half never consumes it.** `toggleLeft` (`model.svelte.ts:165-169`) and `toggleRight` (`:171-180`) both return `void`, so neither the model nor its caller can tell a refused write from an applied one. It compounds one level up: `toggleLeftPanel` / `toggleRightPanel` (`App.svelte:1194-1219`) compute `nextVisible` *before* the toggle and then call `focusToggleTarget(side, nextVisible)` (`:1183-1192`) unconditionally, which queues a lookup for an element that will never mount and lands on `console.warn("… not mounted; focus dropped to body")` at `:1190`. The observable outcome of the click is: nothing moves, **and keyboard focus is silently lost to `<body>`** — and the one warning that fires names a focus problem, not the cause.

`tests/client/layout-model.svelte.test.ts`'s `makeSettingsState` has no `_readOnly` axis; its own comment at `:72-74` says so and names this group as the owner.

## Fix

The user-visible signal already exists (#1985). This is about making the rail path reach it and about focus — **do not invent a second notification channel.**

- `model.svelte.ts`: `toggleLeft` and `toggleRight` return `boolean` — the value `updateSettings` returned. `toggleRight` has two branches (`:172-179`); each returns its own call's result, so the hidden→show branch (which writes `rightPanelVisible` and, in solo, `soloRailHidden`) reports its single write. Update the interface docs at `:108-111`, which currently declare `void`.
- `App.svelte:1194-1219`: guard the focus call — `if (!layoutModel.toggleLeft()) return;` before `focusToggleTarget("left", nextVisible)`, and the same on the right. On refusal the activated chevron stays mounted, so browser focus naturally stays where the user put it; skipping is the whole fix, and no fallback focus call is needed.
- `focusToggleTarget`'s `console.warn` **stays** — it still covers a genuine unmount race, which is what it was written for.
- `toggleLeftPanel` / `toggleRightPanel` keep returning `void`: their consumers are the builtin-action bag (`App.svelte:981-982`) and the markup, all discarding.
- **The float-clearing writes before the toggle are deliberately left in place.** `pinFromFloat(side)` and `railFloat[side] = false` have already run when a refusal arrives; dismissing a transient hover float on a click is correct regardless of whether the pin landed, and the hover lifecycle re-arms on the next `mouseenter`.
- **Known, accepted consequence on the right:** `toggleRightPanel`'s reveal teardown + `railPinSnap` block (`:1205-1213`) also runs before the toggle, so a refused pin still dismisses an open reveal. Left as-is rather than re-ordered: the comment at `:1195-1197` states the float must be cleared BEFORE the visibility commit, and re-ordering that block to chase a rare refusal risks the `.collapsed.floating` frame it exists to prevent. The refusal notification explains why the rail did not pin. Recorded as an assumption, not discovered later.

Rules that bite: `localStorage` seeding in the E2E goes through `try`/`catch` (precedent: `disableHoverReveal`, `tests/e2e/chat-reveal.spec.ts:50-61`); E2E runs on the reserved harness ports only; no markup change, so **no testid is added or renamed and the snapshot is untouched**.

## Tests

1. **`tests/client/layout-model.svelte.test.ts` — give `makeSettingsState` the `_readOnly` axis** its `:72-74` comment defers to this group: a second argument whose read-only form applies nothing and returns `false`. This is the harness half the issue body calls "the cheap half of the fix", and it is what made all six toggle specs structurally blind.
2. **"toggleLeft reports a refused write and changes nothing"**: read-only harness, `expect(model.toggleLeft()).toBe(false)`, and assert the whole settings object is unchanged (the `:344-365` spec's whole-object comparison is the precedent — a two-key assertion passes a write that lands elsewhere).
3. **"toggleRight reports a refused write in BOTH branches"**: once from visible→hide, once from solo-hidden→show. Two cases, because a fix that returns the boolean from only the first branch passes a single-case spec while the show path — the one that writes two keys — still reports success.
4. **"toggleLeft/toggleRight report `true` when the write lands"**: the positive twin, without which a fix that returns a constant `false` passes 2 and 3.
5. The existing six toggle specs (`:328-449`) keep passing unchanged, ignoring the return value — they are the regression net for the signature change.
6. **E2E, new `tests/e2e/rail-toggle-readonly.spec.ts`** — the focus half cannot be reached from the model specs, because `focusToggleTarget` lives in `App.svelte`. Seed a settings blob carrying an unknown future key via `addInitScript` so `loadSettings` stamps `_readOnly` (`useTandemSettings.ts:959-963`), boot, click the right rail chevron, then assert: the rail did not move (`RAIL_HANDLE_TESTID.right` count unchanged — use the helper, never a re-typed literal, per `tests/e2e/helpers.ts:383-396`) **and** `document.activeElement` is the chevron, not `<body>`. The focus assertion is the discriminator: it is red on master and stays red for any fix that only changes return types without guarding the call. Do not assert the notification's testid here — that surface is #1985's and was not re-verified for this spec.
7. **Mutation-test** (memory rule): drop the `if (!layoutModel.toggleRight()) return;` guard and watch the E2E focus spec go red; make `toggleRight` return a constant `true` and watch spec 3 go red. Restore from a file copy, never `git checkout`.
