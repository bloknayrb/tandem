## Problem

#1689 migrated the six files it named; ten more still hand-roll the same ~8 lines
(`new McpServer` → registrars → `InMemoryTransport.createLinkedPair()` → `new Client` → two
`connect`s), four of them with a duplicate `parseResult` and two more importing a second
`parseResult` from `tests/helpers/wire-code-fixtures.ts`. Nothing in the repo distinguishes a
migrated file from an unmigrated one, so the boilerplate stays the easy shape — which is what
produces the next hand-rolled-filter test (`annotation-tools.test.ts:115`, the live
counter-example named in the harness doc comment). Six of the ten never close the client at all.

## Fix

Pure test infrastructure. `tests/helpers/mcp-harness.ts` and every `src/` file are **unchanged**;
no CLAUDE.md Critical Rule is engaged (no Y.Doc write, no Y.Map key, no `data-testid`, no MCP
tool or `/api` route, so no license-gate table edit). The contract from #1689 holds: the suite
stays observationally identical — same tests, same assertions, same `expect(` / `it(` counts per
file. A migration that changes what a test asserts is a finding, not a cleanup to absorb.

Per file, replace the local setup with `const { client, close } = await setupMcpServer([...])`
over the file's existing registrar list, in its existing order, and drop the now-unused
`McpServer` / `InMemoryTransport` imports (and `Client` where nothing else names it). Three shapes:

1. **Module-level `client` + file-level `afterEach`** — `html-read-only` (`:78`, regs
   `registerDocumentTools`, `registerAnnotationTools`), `mcp-wire-codes` (`:59`, `registerDocumentTools`,
   `registerApplyTools`), `mcp-wire-codes-mocked` (`:92`, same two), `range-bounds-validation`
   (`:64`, `registerDocumentTools`, `registerAnnotationTools`, `registerNavigationTools`),
   `read-audience-filter` (`:57`, `registerAnnotationTools`, `registerAwarenessTools`),
   `save-tool-allow-image-loss` (inline in `beforeEach` `:74`, `registerDocumentTools`),
   `wake-url-surfacing` (inline in `beforeEach` `:62`, `registerDocumentTools`,
   `registerAwarenessTools`). **#2044's guarded pattern is mandatory here** and is the reason this
   group exists: declare `let close: (() => Promise<void>) | undefined;`, call `await close?.()`
   as the **first** statement of `afterEach`, then `close = undefined;`. Unguarded, a throwing
   `beforeEach` reports `close is not a function` on top of the real cause, and on every later
   test in the file the stale binding re-closes the PREVIOUS test's client. Precedent verbatim:
   `tests/server/edit-annotation.test.ts:20,36-39`. `save-tool-allow-image-loss` has **no**
   `afterEach` today and `wake-url-surfacing` / `html-read-only` / both wire files have one that
   never closes — add/extend to `await close?.(); close = undefined;` only, touching nothing else
   in the block. That close is a deliberate hygiene delta (same one #2042 took on
   `mcp-tool-integration`), not a leak fix — `InMemoryTransport` holds only a queue.
2. **Describe-scoped client** — `convert-error-mapping` (`setupClient` `:33`,
   `registerDocumentTools`): the `let client: Client` at `:48` is inside the describe, so the
   `let close` and the new `afterEach` go in the same describe, same guarded shape.
3. **Function-local, try/finally** — `awareness-tools`'s `connectInbox` (`:1145`,
   `registerAwarenessTools`) and `held-in-solo-stamp`'s inline block (`:215`,
   `registerAnnotationTools`, `registerAwarenessTools`). These are structurally assigned before
   use, so they take the plain `await close()` in the existing `finally` / at the existing
   `await mcpClient.close()` site (`awareness-tools:1188,1211,1253`; `held-in-solo-stamp:250`) —
   **no `?.`**. `export-path-canonicalization` was excluded from #2044 for exactly this reason and
   a "for uniformity" fold was refuted there; do not re-raise it. `connectInbox` returns
   `{ client, poll }` → `{ poll, close }`; it reads `result.structuredContent`, **not** a text
   envelope, so `parseResult` does not enter it.

`parseResult` (the harness export is a superset — its union's first arm is exactly
`Awaited<ReturnType<Client["callTool"]>>`):

- Delete the file-local copies in `convert-error-mapping:27`, `range-bounds-validation:76`,
  `read-audience-filter:51`, `wake-url-surfacing:51` (named `parsed`; keep the call sites' name by
  importing as `parseResult` and renaming uses, or `import { parseResult as parsed }` — either,
  but not both in one file), plus the now-orphaned `type CallToolResponse` aliases at
  `range-bounds-validation:59`, `read-audience-filter:49`, `wake-url-surfacing:49` if nothing else
  uses them. `html-read-only`'s `call()` (`:89-94`) inlines the same parse — replace its body's
  parse half with `parseResult(res)`, keeping `call` itself.
- **`tests/helpers/wire-code-fixtures.ts:13`'s second `parseResult` is deleted**, not shimmed. Its
  only two importers (`mcp-wire-codes:20`, `mcp-wire-codes-mocked:20`) are both in this migration
  and take `parseResult` from the harness while still importing `createMinimalDocx` /
  `seedAcceptedSuggestion` from the fixtures. #1689 deliberately added no re-export shim because a
  shim is what lets two copies drift back apart while looking reconciled — deleting the definition
  is the reconciliation the issue asks for. Update the fixtures' header comment, which currently
  claims it is the harness's precedent for `parseResult`.
- **`held-in-solo-stamp:231-239`'s `inboxIds` is NOT a plain parse.** Replace only the
  `JSON.parse(content.find(...))` half: `const data = parseResult(result)?.data ?? {};`. The
  `?? {}` unwrap and both `.map((a) => a.id)` calls stay verbatim — the in-file comment records
  that getting the unwrap wrong once made `expect(await inboxIds()).not.toContain("s1")` unable to
  fail, and the positive control below it is what proves the row is not vacuous.

**`tests/server/mcp-stdio-ports.test.ts` is a permanent non-migration and must not be touched.** It
links a pair but hands `serverTransport` to `startMcpServerStdio`; production code builds the
server, so there is no registrar list to pass. Say so in the PR body so a later reader does not
read the residual probe hit as a half-done migration.

Also unchanged, each for a stated reason: `restore-backup.test.ts` (links no transport; its
`ToolResult`-typed `parseResult` is a real difference, not noise — do not flatten a typed parser
into an untyped one to make the migration uniform), and the harness itself.

## Tests

**No new spec file, and this is a decision, not an omission:** a spec asserting the helper exists
or that N files import it tests the refactor rather than the code — the mistake #1689 avoided.
Evidence is mutation plus counting.

- **Mutation, one per shape** (mutate `src/`, run the named file, restore **from a file copy,
  never `git checkout`**): (a) guarded-`afterEach` shape — break a filter in
  `src/server/mcp/annotations.js`'s read path and watch named specs in `read-audience-filter` go
  red; (b) wire-codes shape — break one error code in `src/server/mcp/` and watch named specs in
  `mcp-wire-codes` go red; (c) `held-in-solo-stamp` — remove the `heldInSolo` stamp and watch the
  restart row go red. Each must fail with **named** specs, not a file-level error. Record
  before/after counts in the PR body.
- **The #2044 hazard itself**, on a scratch copy of one migrated file (not committed): make its
  `beforeEach` throw; unguarded yields an extra `close is not a function`, guarded yields zero and
  leaves the real cause unchanged. That is what proves the guard is more than cosmetic.
- **Counts:** `expect(` and `it(` per file byte-identical before/after, and full-suite file/test
  totals identical. Baseline at branch point (`expect(` / `it(`): awareness-tools 110/51,
  convert-error-mapping 9/2, held-in-solo-stamp 22/12, html-read-only 43/11, mcp-wire-codes 38/13,
  mcp-wire-codes-mocked 13/2, range-bounds-validation 95/30, read-audience-filter 22/6,
  save-tool-allow-image-loss 8/5, wake-url-surfacing 12/3. Identical suite totals alone cannot
  prove assertions survived.
- **Probe:** the corrected command returns **1** after the change (`mcp-stdio-ports.test.ts`), down
  from 11. Quote both runs in the PR body.
- `npm run typecheck && npm run typecheck:tests`, then the ten files, then the full suite via the

  load-bearing: `platform.test.ts` keys on it).
