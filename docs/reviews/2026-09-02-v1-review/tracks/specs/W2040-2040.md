## Problem

#1689 migrated the six files it named; ten more still hand-roll the same ~8 lines
(`new McpServer` → registrars → `InMemoryTransport.createLinkedPair()` → `new Client` → two
`connect`s), four of them with a duplicate `parseResult` and two more importing a second
`parseResult` from `tests/helpers/wire-code-fixtures.ts`. Nothing in the repo distinguishes a
migrated file from an unmigrated one, so the boilerplate stays the easy shape — which is what
produces the next hand-rolled-filter test (`annotation-tools.test.ts:115`, the live
counter-example named in the harness doc comment). Six of the ten never close the client at all.

## Fix

Pure test infrastructure. `tests/helpers/mcp-harness.ts` and every `src/` file are **unchanged**;
no CLAUDE.md Critical Rule is engaged (no Y.Doc write, no Y.Map key, no `data-testid`, no MCP
tool or `/api` route, so no license-gate table edit). The contract from #1689 holds: the suite
stays observationally identical — same tests, same assertions, same per-file counts. A migration
that changes what a test asserts is a finding, not a cleanup to absorb.

Per file, replace the local setup with `const { client, close } = await setupMcpServer([...])`
over the file's existing registrar list, in its existing order, and drop the now-unused
`McpServer` / `InMemoryTransport` imports. **Where `Client` survives only as a type annotation
(`let client: Client`, a `CallToolResponse` alias), convert its import to
`import type { Client } from "@modelcontextprotocol/sdk/client/index.js"`** — that is the shape
every #1689-migrated file uses (`edit-annotation.test.ts:6`, `mcp-tool-integration.test.ts:12`,
`resolve-annotation.test.ts:10`), and nothing enforces it (`biome.json` has
`"linter": { "enabled": false }`), so it has to be said. Where nothing names `Client` at all, drop
the import.

Three shapes:

1. **Module-level `client`, no close today** — `html-read-only` (`:78`, regs
   `registerDocumentTools`, `registerAnnotationTools`), `mcp-wire-codes` (`:59`,
   `registerDocumentTools`, `registerApplyTools`), `mcp-wire-codes-mocked` (`:92`, same two),
   `save-tool-allow-image-loss` (inline in `beforeEach` `:74`, `registerDocumentTools`),
   `wake-url-surfacing` (inline in `beforeEach` `:62`, `registerDocumentTools`,
   `registerAwarenessTools`). **#2044's guarded pattern is mandatory here** and is the reason this
   group exists: declare `let close: (() => Promise<void>) | undefined;`, call `await close?.()`
   as the **first** statement of the file's `afterEach`, then `close = undefined;`. Unguarded, a
   throwing `beforeEach` reports `close is not a function` on top of the real cause, and on every
   later test in the file the stale binding re-closes the PREVIOUS test's client. Precedent
   verbatim: `tests/server/edit-annotation.test.ts:20,36-39`. Mechanics: `save-tool-allow-image-loss`
   has **no** `afterEach` at all — add one, and add `afterEach` to its vitest import at `:24`
   (currently `{ beforeEach, describe, expect, it, vi }`), or it fails to compile.
   `wake-url-surfacing:71`, `html-read-only:133`, `mcp-wire-codes:101` and
   `mcp-wire-codes-mocked:116` each have an `afterEach` that never closes — prepend
   `await close?.(); close = undefined;` to it, touching nothing else in the block. That close is
   a deliberate hygiene delta (same one #2042 took on `mcp-tool-integration`), not a leak fix —
   `InMemoryTransport` holds only a queue.
   **Two files in this shape already close and are the exception to "first statement":**
   `read-audience-filter` (`:57`, `registerAnnotationTools`, `registerAwarenessTools`) has a
   file-level `afterEach` at `:141` whose first statement is already `await client.close()` at
   `:142` — **replace that call with `await close?.(); close = undefined;` in place**, leaving
   `clearOpenDocs()` / `removeDocument(DOC_ID)` / `setCtrlMode(null)` after it untouched. And
   `range-bounds-validation` is **describe-scoped, not file-level** (below).
2. **Describe-scoped client** — `convert-error-mapping` (`setupClient` `:33`,
   `registerDocumentTools`): the `let client: Client` at `:48` is inside the describe at `:47`, so
   the `let close` and the new `afterEach` go in the same describe, same guarded shape.
   `range-bounds-validation` (`setupMcpClient` `:64`, `registerDocumentTools`,
   `registerAnnotationTools`, `registerNavigationTools`) belongs here too despite its
   **module-level** `let client: Client` at `:61`: its `beforeEach`/`afterEach` sit inside the
   describe at `:91`, and the file has two further, unrelated `afterEach` blocks at `:335` and
   `:518` that must not be touched. Put `let close` beside the existing `let client` (or in the
   describe — either, but only one), and **replace the existing `await client?.close()` at `:98`
   in place** with `await close?.(); close = undefined;`. Do **not** add a file-level hook, and do
   **not** hoist the call above the `for (const id of registered.splice(0)) removeDoc(id);` at
   `:97` — both are in-memory registry operations, but reordering teardown is a behavioural delta
   this PR's "observationally identical" claim does not cover.
3. **Function-local, try/finally or a bare close** — `awareness-tools`'s `connectInbox` (`:1145`,
   `registerAwarenessTools`) and `held-in-solo-stamp`'s inline block (`:215`,
   `registerAnnotationTools`, `registerAwarenessTools`). These are structurally assigned before
   use, so they take the plain `await close()` — **no `?.`**. The two differ and the difference
   matters: `awareness-tools` already has `finally` blocks at `:1185`, `:1210`, `:1252` whose
   `await client.close()` (`:1188`, `:1211`, `:1253`) becomes `await close()` in place — the file
   has **zero** `afterEach` and must not gain one. `held-in-solo-stamp:250` is a **bare**
   `await mcpClient.close();` as the last statement of the `it` with no `try` anywhere in the
   block — it becomes `await close();` and **stays unwrapped**; adding a `try`/`finally` there is
   out of scope. `export-path-canonicalization` was excluded from #2044 for exactly this reason
   and a "for uniformity" fold was refuted there; do not re-raise it. `connectInbox` returns
   `{ client, poll }` → `{ poll, close }`; it reads `result.structuredContent`, **not** a text
   envelope, so `parseResult` does not enter it.

`parseResult` (the harness export is a superset — its union's first arm is exactly
`Awaited<ReturnType<Client["callTool"]>>`):

- **Counts.** Two halves, and the grep half alone is not enough.
  - *Assertions:* `grep -o 'expect(' <file> | wc -l` must be byte-identical before and after.
    Baseline at branch point: awareness-tools 110, convert-error-mapping 9, held-in-solo-stamp 22,

    suite totals alone cannot prove per-file assertions survived either; both halves are required.
