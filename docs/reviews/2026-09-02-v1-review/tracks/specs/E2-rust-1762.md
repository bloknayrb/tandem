# E2-rust — #1762 the Windows updater's exe-unlock wait probes a filename that never exists on an installed build

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1762 (both halves of the suggested fix: the name, and the missing-file branch). Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:16`. Probe: none automatable — the verification is the Windows `rust-test` leg plus the §1 smoke row at `docs/release-smoke-checklist.md:34`.

## Problem

`sidecar_exe_path` (`src-tauri/src/sidecar.rs:2316`) builds `format!("node-sidecar-{}.exe", env!("TARGET_TRIPLE"))` at `:2325`. tauri-build strips the `-<triple>` when it copies an `externalBin` into the bundle, and the runtime asks for the bare name at `sidecar.rs:1712` (`.sidecar("node-sidecar")`). **Measured on this machine, both halves:** the installed app dir holds `node-sidecar.exe` (`%LOCALAPPDATA%\Tandem\`, mtime 2026-07-28) and the dev target dir holds `node-sidecar.exe` — the triple-suffixed name exists nowhere outside `src-tauri/binaries/`.

**Provenance of the live reproduction, both homes verified:** the tracked one is `docs/release-smoke-checklist.md:150-160`, written by #1932 (`7ee66a5c`) out of the v0.25.0 smoke run; Bryan also posted the same log excerpt as a comment on #1762 (bloknayrb, 2026-09-10T01:29:55Z, "Reproduced on hardware"), **checked with `gh issue view 1762` rather than assumed**. The PR body cites the checklist lines and #1932 first, because those are files a reviewer can reach without the API.

```
[2026-09-10][01:22:37][app_lib][WARN] Sidecar exe not on disk at
C:\Users\blokn\AppData\Local\Tandem\node-sidecar-x86_64-pc-windows-msvc.exe
  — skipping unlock wait (packaging bug?)
```

Documents were open at the time. So `Ok(p) if p.exists()` misses, and `wait_for_sidecar_unlock` (`:2333`) `return`s `true` — **it reports "unlocked" having never found the file to check**. That value flows to `lib.rs:2909`'s `tokio::join!`, whose `if !file_ok` arm is therefore dead, so the NSIS `NSIS_HOOK_PREINSTALL` kill is the only thing standing between an update and a running `node-sidecar.exe`.

**Not deletion.** The wait is not a thing nobody needs; it is a thing nobody has ever run. With the name corrected it probes a real file that a running sidecar really holds open on Windows, and the failure it exists to prevent (NSIS overwriting a locked exe) is real. Deleting it would leave the kill hook as the only layer *by decision* rather than by accident — a strictly worse outcome than the two-line repair.

## Fix

- `sidecar.rs`: add `pub(crate) const SIDECAR_BIN_NAME: &str = "node-sidecar";` beside the other spawn constants (near `SIDECAR_BIND_HOST`, `:167`), with a docblock saying the triple is a *build-time* convention (`src-tauri/binaries/node-sidecar-<triple>[.exe]`) that tauri-build strips, so this is the only name any runtime code may use. Use it at `:1712` (`.sidecar(SIDECAR_BIN_NAME)`) and in `sidecar_exe_path`. **The const is the fix**, not a tidy-up: divergence between the spawn name and the reconstructed path is exactly what #1762 is.
- `sidecar_exe_path` (`:2317-2329`): `let name = format!("{SIDECAR_BIN_NAME}.exe");`. Drop the inner `if cfg!(target_os = "windows")` / `else` — the function already carries `#[cfg(target_os = "windows")]` (`:2315`), so the else arm is unreachable today and would silently reintroduce a second naming rule if the gate were ever widened.
- **Extract the missing/unresolvable verdict as a pure function** so the release behaviour is pinned rather than merely read:

  ```rust
  /// Should `wait_for_sidecar_unlock` report "unlocked" when it cannot find or
  /// resolve the sidecar exe? Dev has no bundled sidecar in some layouts and must
  /// proceed; a release build that cannot find it has a packaging bug and must
  /// not let that pass as unlocked.
  fn unlock_verdict_when_absent(is_debug: bool) -> bool { is_debug }
  ```

  Both arms of `wait_for_sidecar_unlock` call it: the missing-file arm (`:2336-2344`) and the `Err(e)` resolve-failure arm (`:2345-2352`) each `return unlock_verdict_when_absent(cfg!(debug_assertions));` instead of a bare `return true;`. The function is **cross-platform** (not inside the `#[cfg(target_os = "windows")]` gate) so it is reachable from the ubuntu and macOS `rust-test` legs; add `#[cfg_attr(not(target_os = "windows"), allow(dead_code))]` if the lint complains. Release log line becomes `log::warn!("Sidecar exe not on disk at {} — reporting still-locked (packaging bug)", p.display())`; the dev line keeps `log::debug!` and its "(dev mode)" wording.
- `lib.rs:2913-2919`, the `if !file_ok` message: it currently asserts a cause it no longer always knows. Reword to `format!("Sidecar exe lock not confirmed released within {SIDECAR_UNLOCK_DEADLINE_SECS}s -- installer may prompt for retry")`. Interpolate the const, per `warn_port_still_responding`'s precedent at `lib.rs:2802`. **#1808 moves this exact block down inside `perform_install`, and #1762 lands first** — so #1808's step 3 moves it *as amended here*, not as it reads on master. The two specs are cross-referenced on this point in both directions.
- Docs — **three** places state the defect as live, not the two the first draft listed, and all three carry stale inner line numbers that the same edit must correct:
  - `docs/architecture.md:855` (sidecar-spawn step 3) ends "Anything that reconstructs the path by hand has to use the stripped name — **the one place that does not is #1762, below.**" After `SIDECAR_BIN_NAME` there is no such place: rewrite the trailing clause to say the stripped name is now carried by the shared `SIDECAR_BIN_NAME` const in `sidecar.rs`, and drop the "#1762, below" pointer.
  - `docs/architecture.md:998` — "(inert on an installed build — see #1762 below)". Rewrite or drop; it is the same claim in a parenthetical.
  - `docs/architecture.md:1019` — "on an installed build it polls nothing (#1762, open)". Rewrite to say the wait probes the installed name and that a missing file now reports still-locked. **Correct the embedded citation in the same edit**: it says `sidecar_exe_path` (`sidecar.rs:2064-2077`), which is now `sidecar.rs:2316-2329`.
  - `docs/release-smoke-checklist.md:34`'s "While you are here, check #1762" paragraph — the grep target becomes `reporting still-locked (packaging bug)`, whose presence now means a packaging regression rather than a known-dead branch. **Do not edit the "What the v0.25.0 run settled" section (`:145-167`)** — it is a record of what a run observed, not a claim about current code.

**Rules that bite:** `strip_win_prefix()` is *not* wanted here — `sidecar_exe_path` builds a path for `std::fs::OpenOptions`, not for the sidecar; the `\\?\` form is fine for Win32 and the existing code correctly does not strip. Nothing in this issue touches `TAURI_HOSTNAME`, the licensing consts or any `/api` route.

## Tests

`src-tauri/src/sidecar.rs`, in the existing `#[cfg(test)] mod sidecar_env_tests` or a sibling `#[cfg(test)] mod sidecar_name_tests` — **name the module in the commit; `sidecar.rs`'s test modules are named, and `lib.rs` has no `mod tests` at all.** The Windows `rust-test` leg exists (`ci.yml:62`, `windows-latest`) and `rust-test` is a required check, so a `#[cfg(target_os = "windows")]` test here is genuinely run — unlike the #1529 vitest trap.

1. `#[cfg(target_os = "windows")] fn sidecar_exe_path_uses_the_installed_name_not_the_build_time_triple()` — `sidecar_exe_path().unwrap()`; assert `file_name() == "node-sidecar.exe"` **and** `!path.file_name().unwrap().to_string_lossy().contains(env!("TARGET_TRIPLE"))`. **Scoped to the file name, not the whole path**: `sidecar_exe_path` is `current_exe().parent().join(name)`, and a developer running `cargo test --target x86_64-pc-windows-msvc` gets `target/x86_64-pc-windows-msvc/debug/deps/…` — a whole-path scan would false-red on correct code. (CI is safe either way: the `rust-test` leg runs a bare `cargo test --manifest-path src-tauri/Cargo.toml` with no `--target`.) The second assertion is not redundant: a future `format!("{SIDECAR_BIN_NAME}-{}.exe", …)` fails it first with a message naming the cause.
2. `fn the_sidecar_binary_name_has_exactly_one_home()` — cross-platform. Assert `SIDECAR_BIN_NAME == "node-sidecar"`, and that the string literal occurs **exactly once** in `include_str!("sidecar.rs")` — at the const definition. **The previous draft's second assertion (`!SIDECAR_BIN_NAME.contains(env!("TARGET_TRIPLE"))`) is deleted: it is tautological** once the first assertion fixes the value exactly, so it was a non-discriminating assertion sitting next to a real one. The occurrence count is the thing worth pinning, because it is what stops the spawn site and the path builder diverging again — which is all #1762 ever was. **Build the needle with `concat!` per the `sidecar.rs:3105` precedent** (`const BIN: &str = concat!("node-", "sidecar");`, then `format!("\"{BIN}\"")`) so this test's own source does not inflate the count.
3. `fn a_missing_sidecar_exe_reports_still_locked_in_release()` — cross-platform, on the extracted pure function: `assert!(unlock_verdict_when_absent(true))` and `assert!(!unlock_verdict_when_absent(false))`. This is the half the first draft conceded was untestable, and Track E's own Done-when asks for exactly it (`E-desktop-lifecycle.md`: "a test that fails … on **a missing sidecar path**"). Two lines, and it converts a declared gap into a pinned one.

Do **not** add a source-scanning drift guard for the log strings — the checklist row is the tracked home and #1762 asks for a checklist line, not a new gate.

**Mutation check:** revert `:2325` to the triple form and test 1 goes red; add a second bare `"node-sidecar"` literal at the spawn site and test 2 goes red; change `unlock_verdict_when_absent` to `|_| true` and test 3 goes red. Restore from a file copy, never `git checkout`.
