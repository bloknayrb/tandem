# E2-rust — #1762 the Windows updater's exe-unlock wait probes a filename that never exists on an installed build

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1762 (both halves of the suggested fix: the name, and the missing-file branch). Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:16`. Probe: none automatable — the verification is the Windows `rust-test` leg plus the §1 smoke row at `docs/release-smoke-checklist.md:34`.

## Problem

`sidecar_exe_path` (`src-tauri/src/sidecar.rs:2317`) builds `format!("node-sidecar-{}.exe", env!("TARGET_TRIPLE"))` at `:2325`. tauri-build strips the `-<triple>` when it copies an `externalBin` into the bundle, and the runtime asks for the bare name at `sidecar.rs:1712` (`.sidecar("node-sidecar")`). **Measured on this machine, both halves:** the installed app dir holds `node-sidecar.exe` (`%LOCALAPPDATA%\Tandem\`, mtime 2026-07-28) and the dev target dir holds `node-sidecar.exe` — the triple-suffixed name exists nowhere outside `src-tauri/binaries/`. Bryan reproduced the consequence on the real v0.24.1 → v0.25.0 upgrade (issue comment, 2026-09-10): `Sidecar exe not on disk at …node-sidecar-x86_64-pc-windows-msvc.exe — skipping unlock wait (packaging bug?)`, with documents open.

So `Ok(p) if p.exists()` misses, and `wait_for_sidecar_unlock` (`:2334`) `return true` — **it reports "unlocked" having never found the file to check**. That value flows to `lib.rs:2909`'s `tokio::join!`, whose `if !file_ok` arm is therefore dead, so the NSIS `NSIS_HOOK_PREINSTALL` kill is the only thing standing between an update and a running `node-sidecar.exe`.

**Not deletion.** The wait is not a thing nobody needs; it is a thing nobody has ever run. With the name corrected it probes a real file that a running sidecar really holds open on Windows, and the failure it exists to prevent (NSIS overwriting a locked exe) is real. Deleting it would leave the kill hook as the only layer *by decision* rather than by accident — a strictly worse outcome than the two-line repair.

## Fix

- `sidecar.rs`: add `pub(crate) const SIDECAR_BIN_NAME: &str = "node-sidecar";` beside the other spawn constants (near `SIDECAR_BIND_HOST`, `:167`), with a docblock saying the triple is a *build-time* convention (`src-tauri/binaries/node-sidecar-<triple>[.exe]`) that tauri-build strips, so this is the only name any runtime code may use. Use it at `:1712` (`.sidecar(SIDECAR_BIN_NAME)`) and in `sidecar_exe_path`. **The const is the fix**, not a tidy-up: divergence between the spawn name and the reconstructed path is exactly what #1762 is.
- `sidecar_exe_path` (`:2320-2329`): `let name = format!("{SIDECAR_BIN_NAME}.exe");`. Drop the inner `if cfg!(target_os = "windows")` / `else` — the function already carries `#[cfg(target_os = "windows")]` (`:2316`), so the else arm is unreachable today and would silently reintroduce a second naming rule if the gate were ever widened.
- `wait_for_sidecar_unlock`'s missing-file arm (`:2337-2345`): **return `cfg!(debug_assertions)`, not `true`.** Dev has no bundled sidecar in some layouts and must still proceed; a release build that cannot find the file has a packaging bug and must not let it pass as unlocked. Release log line becomes `log::warn!("Sidecar exe not on disk at {} — reporting still-locked (packaging bug)", p.display())`; the dev line keeps `log::debug!` and its "(dev mode)" wording. The `Err(e)` resolve-failure arm at `:2346-2353` takes the same treatment for the same reason.
- `lib.rs:2913-2919`, the `if !file_ok` message: it currently asserts a cause it no longer always knows. Reword to `format!("Sidecar exe lock not confirmed released within {SIDECAR_UNLOCK_DEADLINE_SECS}s -- installer may prompt for retry")`. Interpolate the const, per `warn_port_still_responding`'s precedent at `lib.rs:2802`.
- Docs, both of which currently state the defect as live: `docs/architecture.md:1019` ("on an installed build it polls nothing (#1762, open)") — rewrite to say the wait probes the installed name and that a missing file now reports still-locked; and `docs/release-smoke-checklist.md:34`'s "While you are here, check #1762" paragraph — the grep target becomes `reporting still-locked (packaging bug)`, whose presence now means a packaging regression rather than a known-dead branch. **Do not edit the "What the v0.25.0 run settled" section (`:145-167`)** — it is a record of what a run observed, not a claim about current code.

**Rules that bite:** `strip_win_prefix()` is *not* wanted here — `sidecar_exe_path` builds a path for `std::fs::OpenOptions`, not for the sidecar; the `\?\` form is fine for Win32 and the existing code correctly does not strip. Nothing in this issue touches `TAURI_HOSTNAME`, the licensing consts or any `/api` route.

## Tests

`src-tauri/src/sidecar.rs` `#[cfg(test)] mod tests`. The Windows `rust-test` leg exists (`ci.yml:62`, `windows-latest`) and `rust-test` is a required check, so a `#[cfg(target_os = "windows")]` test here is genuinely run — unlike the #1529 vitest trap.

1. `#[cfg(target_os = "windows")] fn sidecar_exe_path_uses_the_installed_name_not_the_build_time_triple()` — `sidecar_exe_path().unwrap()`; assert `file_name() == "node-sidecar.exe"` **and** `!path.to_string_lossy().contains(env!("TARGET_TRIPLE"))`. Kills the current code and every variant that reintroduces the triple. The second assertion is not redundant: a future `format!("{SIDECAR_BIN_NAME}-{}.exe", …)` would fail it first with a message naming the cause.
2. `fn sidecar_bin_name_is_the_name_the_spawn_site_asks_for()` — cross-platform; asserts `SIDECAR_BIN_NAME == "node-sidecar"` and that it carries no `-` beyond the product name (`!SIDECAR_BIN_NAME.contains(env!("TARGET_TRIPLE"))`). Cheap, and it runs on the two legs the gated test skips.

**Not testable in-process and stated as such in the PR body:** the release arm of the missing-file branch. `cfg!(debug_assertions)` is true under `cargo test`, so a test of it would assert the dev value; the release behaviour is verified by reading plus the smoke row. Do **not** add a source-scanning drift guard for the log strings — the checklist row is the tracked home and #1762 asks for a checklist line, not a new gate.

**Mutation check:** revert `:2325` to the triple form and test 1 goes red; revert the `cfg!(debug_assertions)` return to `true` and nothing goes red (that is the stated gap, not an oversight). Restore from a file copy, never `git checkout`.
