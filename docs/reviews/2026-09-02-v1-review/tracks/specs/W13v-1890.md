# W13v — #1890 `tandem channel` still exits 1 when the server is down at spawn

Branch `fix/server-and-cli-small-correctness-fixes-2003`. Closes #1890. Ledger: no `areas/*.md` row — filed against the F-runtime track after #1889 shipped #1804; tracked home is the wave 13 row in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: run `runChannelCli()` against a closed port and observe the process, converted to a vitest spec below.

## Problem

#1804 (shipped in #1889) made the SSE consumer never exit and never stop retrying, because neither push-path host is respawned inside a Claude Code session. That holds for `dist/channel/index.js` — but the plugin spawns `npx -y tandem-editor@<ver> channel`, i.e. `runChannelCli()`:

```ts
export async function runChannelCli(): Promise<void> {
  await ensureTandemServer();
  await runChannel({ skipReachabilityLog: true });
}
```

`ensureTandemServer` (`src/cli/preflight.ts`) probes `/health` once and, on failure, writes two stderr lines and `process.exit(1)`. If Tandem is not up at the moment Claude Code starts the plugin's MCP servers — the desktop app still booting, the user opening Claude Code first — the host dies before `runChannel` installs the infinite consumer, and the push path is gone for the rest of that session.

**What makes the fix one line:** `runChannel` already owns a non-fatal reachability report (`src/channel/run.ts`): it logs `Cannot reach Tandem server at <url>` plus `Start it with: tandem start` to stderr and continues anyway. `runChannelCli` passes `skipReachabilityLog: true` precisely because the fatal preflight had already probed. Dropping the fatal probe and letting the non-fatal one run removes the exit and leaves a diagnostic in place — option (a) of the issue's fix shape.

**Recorded narrowing — the two probes are not equivalent.** `ensureTandemServer` → `probeTandemServer` (`src/cli/preflight.ts:33-60`) fetches `/health` and distinguishes `kind: "unhealthy"` (non-2xx) from `"unreachable"`. `runChannel`'s surviving probe, `checkServerReachable` (`src/channel/run.ts:228-254`), is a raw TCP `createConnection`: it resolves true for **anything listening**, including a wedged Tandem or an unrelated process on 3479. The deletion therefore loses the unhealthy-server verdict on this path; what survives covers the **down** case only. Accepted (the exit is the defect; #1804 owns the consumer's probe), but it must not be described as restoring the same diagnostic.

## Fix

- `src/cli/channel.ts`: `runChannelCli` becomes `await runChannel();` — no preflight call, no `skipReachabilityLog`. Update the module docstring, which currently says "Runs the unified preflight, then hands off": the replacement names #1804, says reachability is the consumer's (reported once, never fatal), and carries the narrowing above.
- `src/channel/run.ts`: one docblock line on `RunChannelOptions.skipReachabilityLog`. Its current text ("The CLI wrapper runs a strict preflight upstream…") is made false by this diff; the replacement says the option is kept for tests that do not want the probe's stderr, with no production caller since #1890. No behaviour change.
- **Assumption, recorded:** option (a) over option (b). Option (b) (a `waitForUpstream` grace window with opt-in fail-fast) would add an option nothing would pass — there is no surviving caller that wants fail-fast.
- **Critical Rule 3:** every line here is `console.error`/`process.stderr`. This is a stdio MCP host, so a `process.stdout.write` added here would corrupt the wire directly. Nothing in the diff writes to stdout.

No Y.Doc write, no Y.Map key, no MCP tool or `/api` route: Critical Rules 1, 2 and 9 are not engaged.

## Tests

**New file `tests/cli/channel-cli.test.ts` — the issue's own acceptance test.** `vi.mock("../../src/channel/run.js")` with a `runChannel` that resolves after recording its options; spy on `process.exit` with a throwing implementation (the pattern `tests/cli/preflight.test.ts` already uses); mock `fetch` to reject (`ECONNREFUSED`).

1. `runChannelCli()` **resolves**, `process.exit` was never called, and `runChannel` was called. Kills the shipped code outright.
2. `runChannel` was called **without** `skipReachabilityLog: true` — the non-fatal probe is left armed. Kills a "fix" that deletes the preflight but keeps the flag, removing the exit *and* the last **down-server** diagnostic on this path. The comment must say down-server, not "the same diagnostic" (see the narrowing).

**Known gap, recorded rather than filled:** nothing covers `runChannel`'s own "unreachable → two stderr lines → continues" branch (`grep -rn "Cannot reach Tandem\|checkServerReachable" tests/`: zero hits). Reaching it means running `runChannel` for real, which connects a `StdioServerTransport` and installs signal handlers; the branch is #1804's.
