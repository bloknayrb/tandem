Probe: `docs/reviews/2026-09-02-v1-review/experiments/exp4.ts` sections A and C — **that is the real path**; the round-1 draft wrote a bare `experiments/exp4.ts`, which resolves to nothing from the repo root.

## Problem

**Half 1 — docx.** mammoth emits a body picture as `<p><img src="data:image/png;base64,…"/></p>` (measured on `corpus.buildEmbeddedImage`: exactly one `<img>`, always inside a `<p>`). `docx-html.ts` handles `img` in `domNodeToYxml`'s block switch (`:400-421`), but the paragraph arm defers its children to `processInlineNodes` (`:573-633`), which has arms for text, `br`, `a`, mark tags and `code` and ends in "unknown inline element — recurse (best effort)". An `<img>` has no children, so an `<img>` reached through the **inline** path is **discarded**. Nothing in `scanDocxLostFeatures` mentions images, so the fidelity report is silent, and `tandem_save` then regenerates the `.docx` through `exportYDocToDocx` and overwrites the user's file without them. `tests/server/docx-roundtrip-fidelity.test.ts:250-258` already records the loss as `"breaks"`.

**Half 2 — markdown.** `mdast-ydoc.ts#imageToYxml` (`:482-493`) downgrades a `sanitizeImageSrc`-rejected URL to a paragraph carrying `node.alt || node.title || ""`. Measured now: `![Architecture diagram](file:///C:/…/diagram.png)` and `![svg](data:image/svg+xml;base64,…)` save back as the bare words `Architecture diagram` and `svg`. The URL is gone from the user's file.

## Fix

**1. Report the docx loss.** In `src/server/file-io/index.ts`'s `docxAdapter.parse`, after the `Promise.all`, count the images mammoth surfaced that the model will not hold — a new `countDroppedImages(html): number` exported from `docx-html.ts` (that module already imports `parseDocument`; walk the DOM — **not a regex**, which would count the string inside a text node).

**The count is of DROPPED images, not of all `<img>` tags, and the difference is load-bearing.** `domNodeToYxml`'s block `case "img"` (`docx-html.ts:400-421`) **does** build a real `image` `Y.XmlElement` for a `sanitizeImageSrc`-accepted src; only the inline path discards one. Today mammoth always nests `<img>` inside a `<p>`, so "every `<img>`" and "every dropped `<img>`" coincide — but that is a measurement on one fixture, not an invariant, and the failure direction is bad: an over-count refuses the save **forever**, with no override (see Not in scope), so the user's edits could never be written back.

**Normative definition — two clauses, and the round-1 "equivalently" sentence is DELETED because it was false.** An `<img>` is dropped iff either:

1. it is reached through the **inline** path — its nearest `domNodeToYxml`-handled ancestor is a block that hands its children to `processInlineNodes` (`p`, `h1`–`h6`, `li`, `td`/`th`, blockquote paragraphs), so `domNodeToYxml`'s `case "img"` never runs on it; **or**
2. it is reached through the **block** path but its `src` is rejected by `sanitizeImageSrc`, in which case that arm returns a **paragraph** carrying the alt/title, not an `image` (`docx-html.ts:410-415`).

Round 1 offered "`img` tags minus the `image` elements `htmlToYDoc` produces" as an equivalent restatement. It is not: clause 2 is counted by that formulation and not by clause 1's, and — decisively — it **cannot be computed from `html` alone**, which is the only argument this function takes. Measured: `sanitizeImageSrc("data:image/svg+xml;base64,…")` → `null` (rejected), `sanitizeImageSrc("data:image/png;base64,…")` → passes. So the implementation must call `sanitizeImageSrc` itself on the block-path images, exactly as `domNodeToYxml` does.

**The ancestor list in clause 1 is a hand-copy of another module's dispatch, and it needs a drift guard, not a promise.** It mirrors the block switch at `docx-html.ts:390-421` and the recursion at `:565-633`; a future block arm added to `domNodeToYxml` without touching `countDroppedImages` over-counts, and the failure is the permanently unsaveable file above. So: export the ancestor list from `docx-html.ts` as a single named constant (`INLINE_DEFERRING_BLOCK_TAGS`), have `countDroppedImages` read it, put a source comment on **both** sides naming the other — and add a **source-scan drift test** in the `tests/server/` `*-seam` shape (`docx-import-write-seam.test.ts` is the existing precedent for this pattern, though not the file to put it in): read `docx-html.ts` as text, extract the `case "<tag>":` labels from `domNodeToYxml`'s block switch, and assert that set is exactly the union of `INLINE_DEFERRING_BLOCK_TAGS`, `"img"`, and an explicitly-listed remainder of self-contained blocks. A new arm then fails the test rather than silently widening the count.

Push a line into `structural` reading, count-only, **never a `src` or an `alt`** (`docx-lost-features.ts`'s module header states that contract for every line in this list and it holds here too):

> `"${n} picture(s) couldn't be imported, so this file can't be saved back as .docx — ask Claude to convert it to Markdown to keep your edits"`

**The copy must describe the refusal, not a saved file.** The line the round-1 review found — "…won't be in the saved file" — described exactly the outcome item 2 exists to prevent.

**And it must name an exit the user can actually take FROM THIS DOCUMENT.** Round 1's wording, "convert to Markdown to keep your edits", read as an instruction to press a button that does not exist here: the **only** client affordance for conversion is `src/client/components/ReviewOnlyBanner.svelte:84-88` (`data-testid="convert-to-markdown-btn"`, the sole caller of `API_CONVERT` in all of `src/client/` — verified by grep), and that banner renders only on its own review-only `visible` prop. A writable on-disk `.docx` never shows it. Paired with a total, override-less save refusal (see Not in scope), the round-1 copy would have made an image-bearing `.docx` a document whose edits the user has **no route to persist** — the fidelity banner naming a control it does not have, and Claude, who does have the tool, never seeing the line at all (`importLosses` is USER-FACING ONLY by design — `src/shared/types.ts:521-536`, "no MCP tool returns these lines"). Hence "**ask Claude to convert it to Markdown**": `tandem_convertToMarkdown` is reachable for this document today, needs no new UI, and the D2-1754 skill bump carries the matching clause on `tandem_save`'s bullet so Claude offers it on receiving the refusal. **Adding a CTA to `FidelityReportBanner.svelte` was the alternative and is rejected for this PR** — it is a new `data-testid` (Critical Rule 7: manifest + a regenerated `tests/design-system-impl/__snapshots__/testid-set.snap.txt`), a conversion affordance for *writable* documents whose semantics `ReviewOnlyBanner`'s does not settle, and neither is in scope here.

**Why Save-As is genuinely out of reach — the round-1 reason was the wrong guarantor.** It cited the `format: "md" | "txt"` typing (`document-service.ts:790-793`), which is true but is not what stops this document: `saveDocumentAsToDisk` returns an error whenever `docState.source !== "upload"` (`:806-812`), because Save-As is a promotion path for ephemeral upload/scratchpad docs only. An on-disk `.docx` is `source: "file"` and is refused before the format is consulted. Cite the source gate; the typing is a second, weaker layer. (`adapter.saveBinary` is still referenced only inside `saveDocumentToDisk`.)

Classify it as `structural` because `structural` means "things that ARE gone" (`file-io/index.ts:253-257`) and the pictures genuinely are absent from the model — **not** because it "drives the overwrite warning": that warning's copy asserts the backed-up original has features this file doesn't, and after item 2 the overwrite it describes can no longer happen for this document. Say so where the line is built, so the next reader does not restore the void rationale.

Carry the count to the save path: add `droppedImages?: number` to `LoadIssue { kind: "other" }` (`src/server/file-io/types.ts:55-70`) and to `FidelityReport` (`src/shared/types.ts:519-576`), optional for forward-compat with `?? 0` at every reader, exactly as `structuralLosses` documents. **Three sites copy it, and missing any one makes the refusal dead code no test in this list would catch:**

**2. Refuse the export.** `src/server/mcp/document-service.ts`, binary branch. Refuse when `droppedImagesOf(importSnapshot) > 0` by throwing the existing `SaveVerificationError(blockReasonMessage(reason), reason)` with a new `BlockReason` member `"import-image-loss"` (`docx-verify.ts:61`, message added to `blockReasonMessage`'s switch at `:427-437`, which TypeScript keeps exhaustive). Message, content-free like its siblings: `"this file's pictures couldn't be imported, so saving would remove them" + " — your original file was left unchanged"`.

**The compile-time exhaustiveness has a RUNTIME half, and a fourth member escapes it.** `tests/server/docx-verify.test.ts:285-292` loops a hard-coded `["reimport-failed", "degenerate-model", "gross-text-loss"] as const` and asserts each message contains `"left unchanged"` and matches no Windows absolute path. The switch stays exhaustive at compile time, but that assertion silently stops covering the new member — and content-freeness is precisely the property the security lens on this PR cares about, since the message reaches Claude verbatim (`document-service.ts:676-683`). So add `"import-image-loss"` to that array **in the same commit**, and make the array itself fail closed: declare it as `const ALL_BLOCK_REASONS = { "reimport-failed": 1, "degenerate-model": 1, "gross-text-loss": 1, "import-image-loss": 1 } satisfies Record<BlockReason, 1>` and iterate its keys. A future member omitted there is then a **type error** — `tests/` is typechecked by `npm run typecheck:tests` (CLAUDE.md's Testing gotcha), so this is a real gate, not a comment. `tests/server/docx-verify.test.ts` joins Files touched.

**Placement, and it is constrained from both sides.** `importSnapshot = fidelityReportOf(doc)` sits at `:480`, inside a window whose own comment (`:455-466`) reads "this pass must stay immediately adjacent to the `saveBinary` below … **DO NOT insert an awaited call here**: a Hocuspocus update landing in the gap would make the report describe a document that was never saved." So either (a) put the refusal **above** `prepareExportComments` (`:470`), before that window opens — `fidelityReportOf(doc)` can be read there just as well — or (b) leave it between `importSnapshot = …` and `saveBinary` and make it a **synchronous `throw`** with nothing awaited. (a) is preferred; whichever is chosen, the spec's requirement is that **no `await` is introduced inside the pinned window**.

The other two ordering facts are unchanged: **before** `saveBinary` means no bytes are generated and the once-per-run pre-overwrite backup gate is not consumed; **before** `atomicWriteBuffer`/`suppressNextChange` means the file is untouched and the watcher suppressor is never armed — the same ordering `verifyDocxRoundtrips`' own block already relies on (`:500-517`).

**Scope of the refusal — `tandem_applyChanges` must NOT gain it.** The refusal belongs to `document-service.ts`'s binary save branch only. `src/server/file-io/docx-apply.ts:502-527` edits the ORIGINAL `word/document.xml` in place and re-zips, so the pictures **survive** it; the refusal exists solely because `exportYDocToDocx` (`file-io/index.ts:296-298`) regenerates from an image-less Y.Doc. Adding it "for consistency" would break the one write path that actually preserves docx images. Since D2-1754 and D2-1755 land in the same PR, this is written down rather than left to inference, and test 6 pins it.

Why this is the right seam and not a new one: `verifyDocxRoundtrips` compares the regenerated bytes against the live Y.Doc, and both sides are equally image-less, so the verifier structurally cannot see this loss — it is an *import*-side fact. Everything downstream is already built: `SaveVerificationError` is the one error whose message the save path forwards verbatim because it is content-free (`document-service.ts:676-683`), and the client renders it as `VERIFY_BLOCKED` (`activityCenter.ts:61-63`). Add a comment on the new member saying `verifyDocxRoundtrips` never produces it, so nobody hunts for a producer inside that module.

**Note the shape of the failure, because a test will get it wrong otherwise.** `saveDocumentToDisk` **catches** `SaveVerificationError` (`:665`) and **returns** `{ status: "error", reason: err.message, errorCode: "VERIFY_BLOCKED" }` (`:697-705`; `code` is the class's `readonly` field at `:242`). It does not reject. Do not "fix" a failing test by making the save path throw — `tandem_save` and `POST /api/save` both consume a `SaveResult`.

**Document the new failure for the caller — in BOTH places, because the code is wholly undocumented today.** `grep VERIFY_BLOCKED docs/mcp-tools.md` returns nothing, even though `verifyDocxRoundtrips` can already produce it.

- `docs/mcp-tools.md:434` — `tandem_save`'s `**Errors:** FILE_LOCKED (file open in another program)` is the whole list, and the skip-code table at `:417-428` is about `saved: false` *successes*, not errors. Add `VERIFY_BLOCKED`.
- **The global error-code table at `:55-76`** — every other cross-tool code has a row there (`READ_ONLY`, `EXTERNAL_CONFLICT`, `FILE_MODIFIED`, `NO_SUGGESTIONS`, `BACKUP_FAILED`, `INTERNAL_ERROR`, …) and `VERIFY_BLOCKED` has none. Add one naming **both** producers — the post-write round-trip verifier and this new import-image refusal — and stating that its message is content-free and forwarded verbatim, so a reader knows not to expect a path or a filename in it.

The message reaches Claude verbatim, so the tool's failure vocabulary must not be undocumented. Test 9 of D2-1754 asserts both locations.

**Security reviewer's lens (#1654's bound).** The refusal adds no parameter, no route and no caller-named destination: it is a `throw` on a path that previously wrote, so it strictly *reduces* the set of bytes written. `NON_LOOPBACK_ALLOWED` is untouched, no MCP tool or `/api` route is added, and the two license-gate tables need no row. The message is a fixed string — no path, no filename, no document text — which matters because `tandem_save`'s error also reaches Claude.
