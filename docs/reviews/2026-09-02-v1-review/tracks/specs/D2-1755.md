# D2 — #1755 docx body images are dropped silently and the save overwrites the file image-less; markdown `file:`/SVG image sources become alt text

Branch `fix/docx-contract-walker-mammoth-flat-text-disagreement-and-dropped-body-images-1754`. **Closes #1755** (both halves of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:22` (docx) and `:23` (markdown). Probe: `experiments/exp4.ts` sections A and C.

## Problem

**Half 1 — docx.** mammoth emits a body picture as `<p><img src="data:image/png;base64,…"/></p>` (measured on `corpus.buildEmbeddedImage`: exactly one `<img>`, always inside a `<p>`). `docx-html.ts` handles `img` in `domNodeToYxml`'s block switch (`:400-421`), but the paragraph arm defers its children to `processInlineNodes` (`:573-633`), which has arms for text, `br`, `a`, mark tags and `code` and ends in "unknown inline element — recurse (best effort)". An `<img>` has no children, so an `<img>` reached through the **inline** path is **discarded**. Nothing in `scanDocxLostFeatures` mentions images, so the fidelity report is silent, and `tandem_save` then regenerates the `.docx` through `exportYDocToDocx` and overwrites the user's file without them. `tests/server/docx-roundtrip-fidelity.test.ts:250-258` already records the loss as `"breaks"`.

**Half 2 — markdown.** `mdast-ydoc.ts#imageToYxml` (`:482-493`) downgrades a `sanitizeImageSrc`-rejected URL to a paragraph carrying `node.alt || node.title || ""`. Measured now: `![Architecture diagram](file:///C:/…/diagram.png)` and `![svg](data:image/svg+xml;base64,…)` save back as the bare words `Architecture diagram` and `svg`. The URL is gone from the user's file.

## Fix

**1. Report the docx loss.** In `src/server/file-io/index.ts`'s `docxAdapter.parse`, after the `Promise.all`, count the images mammoth surfaced that the model will not hold — a new `countDroppedImages(html): number` exported from `docx-html.ts` (that module already imports `parseDocument`; walk the DOM — **not a regex**, which would count the string inside a text node).

**The count is of DROPPED images, not of all `<img>` tags, and the difference is load-bearing.** `domNodeToYxml`'s block `case "img"` (`docx-html.ts:399-421`) **does** build a real `image` `Y.XmlElement` for a `sanitizeImageSrc`-accepted src; only the inline path discards one. Today mammoth always nests `<img>` inside a `<p>`, so "every `<img>`" and "every dropped `<img>`" coincide — but that is a measurement on one fixture, not an invariant, and the failure direction is bad: an over-count refuses the save **forever**, with no override (see Not in scope), so the user's edits could never be written back. So define the count as **`<img>` elements reached through the inline path** — i.e. those with a block ancestor whose children `htmlToYDoc` hands to `processInlineNodes` (`p`, `h1`–`h6`, `li`, `td`/`th`, blockquote paragraphs) rather than those `domNodeToYxml` handles itself. Equivalently: `img` tags minus the `image` elements `htmlToYDoc` produces. Assert both directions in test 4.

Push a line into `structural` reading, count-only, **never a `src` or an `alt`** (`docx-lost-features.ts`'s module header states that contract for every line in this list and it holds here too):

> `"${n} picture(s) couldn't be imported, so this file can't be saved back as .docx — convert to Markdown to keep your edits"`

**The copy must describe the refusal, not a saved file.** The line the round-1 review found — "…won't be in the saved file" — described exactly the outcome item 2 exists to prevent, and it also names the user's only exit (`tandem_convertToMarkdown`), which the earlier draft left unnamed even though the refusal is total (Save-As is structurally out of reach — `saveDocumentAsToDisk` is typed `format: "md" | "txt"` at `document-service.ts:790-793`, and `adapter.saveBinary` is referenced only inside `saveDocumentToDisk`).

Classify it as `structural` because `structural` means "things that ARE gone" (`file-io/index.ts:253-257`) and the pictures genuinely are absent from the model — **not** because it "drives the overwrite warning": that warning's copy asserts the backed-up original has features this file doesn't, and after item 2 the overwrite it describes can no longer happen for this document. Say so where the line is built, so the next reader does not restore the void rationale.

Carry the count to the save path: add `droppedImages?: number` to `LoadIssue { kind: "other" }` (`src/server/file-io/types.ts:55-70`) and to `FidelityReport` (`src/shared/types.ts:519-576`), optional for forward-compat with `?? 0` at every reader, exactly as `structuralLosses` documents. **Three sites copy it, and missing any one makes the refusal dead code no test in this list would catch:**

- `populate.ts#writeImportLossReport` — the **object literal** at `:100-109` (`meta.set(Y_MAP_FIDELITY_REPORT, { importLosses, structuralLosses, exportDowngrades: [], updatedAt })`). Read `droppedImages` off the same `issue.kind === "other"` loop that sets `structuralLosses`. Because the field is optional, omitting it here is **not** a type error.
- `document-service.ts:565-578` — the save-side `meta.set(Y_MAP_FIDELITY_REPORT, …)` rebuilds `FidelityReport` from an explicit field list, so it would silently erase `droppedImages`. Carry `importSnapshot?.droppedImages` through. Currently unreachable for image-bearing docs (the save refuses first), but leaving it out makes the refusal's own input self-erasing for any future path that does save.
- A `droppedImagesOf(report)` accessor mirroring `structuralLossesOf` (`document-service.ts:165-168`), with its `typeof value === "number"` guard — `Y_MAP_FIDELITY_REPORT` is a CRDT-synced value and `fidelityReportOf` (`:153-155`) is a bare `as FidelityReport` cast. Use the accessor at the refusal site, not `?? 0` on a raw cast.

The count is computed at **parse**, not at apply, because `writeImportLossReport` reads parse-time issues only.

**2. Refuse the export.** `src/server/mcp/document-service.ts`, binary branch. Refuse when `droppedImagesOf(importSnapshot) > 0` by throwing the existing `SaveVerificationError(blockReasonMessage(reason), reason)` with a new `BlockReason` member `"import-image-loss"` (`docx-verify.ts:61`, message added to `blockReasonMessage`'s switch at `:428-437`, which TypeScript keeps exhaustive). Message, content-free like its siblings: `"this file's pictures couldn't be imported, so saving would remove them" + " — your original file was left unchanged"`.

**Placement, and it is constrained from both sides.** `importSnapshot = fidelityReportOf(doc)` sits at `:480`, inside a window whose own comment (`:455-466`) reads "this pass must stay immediately adjacent to the `saveBinary` below … **DO NOT insert an awaited call here**: a Hocuspocus update landing in the gap would make the report describe a document that was never saved." So either (a) put the refusal **above** `prepareExportComments` (`:470`), before that window opens — `fidelityReportOf(doc)` can be read there just as well — or (b) leave it between `importSnapshot = …` and `saveBinary` and make it a **synchronous `throw`** with nothing awaited. (a) is preferred; whichever is chosen, the spec's requirement is that **no `await` is introduced inside the pinned window**.

The other two ordering facts are unchanged: **before** `saveBinary` means no bytes are generated and the once-per-run pre-overwrite backup gate is not consumed; **before** `atomicWriteBuffer`/`suppressNextChange` means the file is untouched and the watcher suppressor is never armed — the same ordering `verifyDocxRoundtrips`' own block already relies on (`:500-517`).

**Scope of the refusal — `tandem_applyChanges` must NOT gain it.** The refusal belongs to `document-service.ts`'s binary save branch only. `src/server/file-io/docx-apply.ts:502-527` edits the ORIGINAL `word/document.xml` in place and re-zips, so the pictures **survive** it; the refusal exists solely because `exportYDocToDocx` (`file-io/index.ts:296-298`) regenerates from an image-less Y.Doc. Adding it "for consistency" would break the one write path that actually preserves docx images. Since D2-1754 and D2-1755 land in the same PR, this is written down rather than left to inference, and test 6 pins it.

Why this is the right seam and not a new one: `verifyDocxRoundtrips` compares the regenerated bytes against the live Y.Doc, and both sides are equally image-less, so the verifier structurally cannot see this loss — it is an *import*-side fact. Everything downstream is already built: `SaveVerificationError` is the one error whose message the save path forwards verbatim because it is content-free (`document-service.ts:676-683`), and the client renders it as `VERIFY_BLOCKED` (`activityCenter.ts:61-63`). Add a comment on the new member saying `verifyDocxRoundtrips` never produces it, so nobody hunts for a producer inside that module.

**Note the shape of the failure, because a test will get it wrong otherwise.** `saveDocumentToDisk` **catches** `SaveVerificationError` (`:665`) and **returns** `{ status: "error", reason: err.message, errorCode: "VERIFY_BLOCKED" }` (`:697-705`; `code` is the class's `readonly` field at `:242`). It does not reject. Do not "fix" a failing test by making the save path throw — `tandem_save` and `POST /api/save` both consume a `SaveResult`.

**Document the new failure for the caller.** `docs/mcp-tools.md:434` — `tandem_save`'s `**Errors:** FILE_LOCKED (file open in another program)` is the whole list, and the skip-code table at `:417-428` is about `saved: false` *successes*, not errors. Add `VERIFY_BLOCKED` (the post-write verifier's existing blocks plus this new import-image refusal). The message reaches Claude verbatim, so the tool's failure vocabulary must not be undocumented.

**Security reviewer's lens (#1654's bound).** The refusal adds no parameter, no route and no caller-named destination: it is a `throw` on a path that previously wrote, so it strictly *reduces* the set of bytes written. `NON_LOOPBACK_ALLOWED` is untouched, no MCP tool or `/api` route is added, and the two license-gate tables need no row. The message is a fixed string — no path, no filename, no document text — which matters because `tandem_save`'s error also reaches Claude.

**3. Correct the export comment.** `src/server/file-io/docx-export.ts:20-22` says "Top-level `<image>` nodes ARE exported when present", which is true of markdown-origin documents and reads as a preservation promise for `.docx` round-trips. Add the measured qualifier: a `.docx` import produces no `image` node from an inline-path `<img>`, so a `.docx`→`.docx` round-trip carries no body pictures, and the save now refuses rather than writing one silently.

**4. Markdown — keep the source instead of the alt text.** In `imageToYxml`, thread the caller's `deferred: DeferredText[]` (both call sites — `blockToYxml`'s `case "image"` at `:364` and `splitParagraphImages` at `:535` — already hold one) and replace the rejected-src arm with a paragraph whose `Y.XmlText` is deferred as `{ xmlText, nodes: [node] }`. `processInline`'s own `case "image"` (`:630-637`) then stores `serializeMdastInline(node)` as a `rawMarkdown` run — the treatment #1799 already gave the *inline* case one PR ago, whose comment says in as many words that a rejected URL should become "an inert raw text run rather than a downgraded paragraph". This aligns the standalone case with it; no new mechanism, no new node type.

Two properties this inherits rather than invents: `insertRaw` uses insert-with-attributes on an **attached** `Y.XmlText`, so every character counts 1-for-1 in `getElementText()` and no annotation offset moves (#981, and CLAUDE.md's "attach before populating"); and the raw run is *text*, never an `src`, so nothing rejected by `sanitizeImageSrc` reaches a DOM sink — the #1420 guarantee is unchanged.

   **and `fs.stat` + a byte comparison showing the original file unchanged.** Phrase it as a returned value, never a rejection (see item 2 of the Fix). `VERIFY_BLOCKED` is not discriminating on its own — the byte assertion and the negative twin below are what carry the test. 4. `tests/server/docx-lost-features.test.ts` or the adapter's own suite: `droppedImages` is `1` for the image fixture and absent/0 for a headings fixture; the loss line carries no `src` substring (`expect(line).not.toContain("base64")`) — pins the count-only contract; **and the count is 0 for a synthetic top-level `<img>` with a safe `data:` src**, which `domNodeToYxml`'s block arm keeps as a real `image` node — pinning the "dropped, not merely present" definition in the direction whose failure is a permanently unsaveable file. Assert the value survives into `Y_MAP_FIDELITY_REPORT` after a real open, not only onto the `LoadIssue`.
5. Markdown, in the existing `mdast-ydoc`/`markdown` round-trip suite: `![Architecture diagram](file:///C:/x/d.png)`, `![svg](data:image/svg+xml;base64,PHN2Zz48L3N2Zz4=)` and `![a](<my image.png>)` each round-trip **byte-identically** through `loadMarkdown` → `saveMarkdown`, and the Y.Doc holds no `image` element for them. All three are **measured** on this worktree: each parses as an mdast `image` node (urls `file:///C:/x/d.png`, `data:image/svg+xml;base64,…`, `my image.png`), each is rejected by `sanitizeImageSrc` (unknown scheme; non-allowlisted `data:` subtype; `URL_HOSTILE_CHARS` space — `src/shared/image-src-safety.ts:26,92,98-110`), and `serializeMdastInline` reproduces each **byte-for-byte**. Kills both "emit the alt text" and "let the unsafe src through as an `image` node". Add the three rejected shapes to `experiments/rt.ts`'s corpus per the track's regression rule.

   The earlier draft's third fixture, a bare `![a](my image.png)`, is **deleted**: measured, CommonMark does not parse it as an image at all (a non-bracketed link destination may not contain an unescaped space), so it yields a `text` node that never reaches `imageToYxml` — non-discriminating for this change — and it does not round-trip byte-identically today either (`remark-stringify` re-emits it as `!\[a]\(my image.png)`), so the assertion was red before and after the fix. `![a](<my image.png>)` is the bracketed form that really produces a rejected `image` node.
6. `tests/server/docx-apply.test.ts` — an image-bearing `.docx` still applies tracked changes **successfully**. Pins the Fix-2 scope note: `tandem_applyChanges` rewrites the original XML in place and preserves the pictures, so it must not inherit the refusal.
7. Idempotence: a second `loadMarkdown(saveMarkdown(...))` pass is a fixed point — the raw run must not re-escape on each save.

## Done when
