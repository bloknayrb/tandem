# D2 — #1755 docx body images are dropped silently and the save overwrites the file image-less; markdown `file:`/SVG image sources become alt text

Branch `fix/docx-contract-walker-mammoth-flat-text-disagreement-and-dropped-body-images-1754`. **Closes #1755** (both halves of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:22` (docx) and `:23` (markdown). Probe: `experiments/exp4.ts` sections A and C.

## Problem

**Half 1 — docx.** mammoth emits a body picture as `<p><img src="data:image/png;base64,…"/></p>` (measured on `corpus.buildEmbeddedImage`: exactly one `<img>`, always inside a `<p>`). `docx-html.ts` handles `img` only in `domNodeToYxml`'s block switch (`:400-421`); the paragraph arm defers its children to `processInlineNodes` (`:573-633`), which has arms for text, `br`, `a`, mark tags and `code` and ends in "unknown inline element — recurse (best effort)". An `<img>` has no children, so it is **discarded**. Nothing in `scanDocxLostFeatures` mentions images, so the fidelity report is silent, and `tandem_save` then regenerates the `.docx` through `exportYDocToDocx` and overwrites the user's file without them. `tests/server/docx-roundtrip-fidelity.test.ts:250-258` already records the loss as `"breaks"`.

**Half 2 — markdown.** `mdast-ydoc.ts#imageToYxml` (`:482-493`) downgrades a `sanitizeImageSrc`-rejected URL to a paragraph carrying `node.alt || node.title || ""`. Measured now: `![Architecture diagram](file:///C:/…/diagram.png)` and `![svg](data:image/svg+xml;base64,…)` save back as the bare words `Architecture diagram` and `svg`. The URL is gone from the user's file.

## Fix

**1. Report the docx loss.** In `src/server/file-io/index.ts`'s `docxAdapter.parse`, after the `Promise.all`, count the images mammoth surfaced that the model will not hold — a new `countImportableImages(html): number` exported from `docx-html.ts` (that module already imports `parseDocument`; walk the DOM and count `img` tags — **not a regex**, which would count the string inside a text node). Push a line into `structural` (so it is a *structural* loss, which is what drives the overwrite warning — `structuralLosses`, not the ambient style tail) reading `"${n} picture(s) couldn't be imported and won't be in the saved file"`. Count-only, never a `src` or an `alt`: `docx-lost-features.ts`'s module header states that contract for every line in this list and it holds here too.

The count is exact *because* `htmlToYDoc` currently keeps no image from a `.docx` at all. That coupling is deliberate and must be commented at the count site: **whichever PR teaches `processInlineNodes` to keep inline images must delete this count in the same change**, or the refusal below outlives its cause.

Carry it to the save path: add `droppedImages?: number` to `LoadIssue { kind: "other" }` (`src/server/file-io/types.ts:55-70`) and to `FidelityReport` (`src/shared/types.ts:519-576`), optional for forward-compat with `?? 0` at every reader, exactly as `structuralLosses` documents. `populate.ts#writeImportLossReport` (`:93-110`) copies it across alongside `structuralLosses` — it reads parse-time issues only, which is why the count is computed at parse and not at apply.

**2. Refuse the export.** `src/server/mcp/document-service.ts`, binary branch: immediately after `importSnapshot = fidelityReportOf(doc)` / `unpreservedImports = …` (`:481-482`) and **before** `await adapter.saveBinary!(doc)`, refuse when `(importSnapshot?.droppedImages ?? 0) > 0` by throwing the existing `SaveVerificationError(blockReasonMessage(reason), reason)` with a new `BlockReason` member `"import-image-loss"` (`docx-verify.ts:61`, message added to `blockReasonMessage`'s switch at `:428-437`, which TypeScript keeps exhaustive). Message, content-free like its siblings: `"this file's pictures couldn't be imported, so saving would remove them" + " — your original file was left unchanged"`.

Why this is the right seam and not a new one: `verifyDocxRoundtrips` compares the regenerated bytes against the live Y.Doc, and both sides are equally image-less, so the verifier structurally cannot see this loss — it is an *import*-side fact. Everything downstream is already built: `SaveVerificationError` is the one error whose message the save path forwards verbatim because it is content-free (`document-service.ts:676-683`), and the client renders it as `VERIFY_BLOCKED` (`activityCenter.ts:61-63`). Add a comment on the new member saying `verifyDocxRoundtrips` never produces it, so nobody hunts for a producer inside that module.

Placement is load-bearing in two directions: **before** `saveBinary` means no bytes are generated and the once-per-run pre-overwrite backup gate is not consumed; **before** `atomicWriteBuffer`/`suppressNextChange` means the file is untouched and the watcher suppressor is never armed — the same ordering `verifyDocxRoundtrips`' own block already relies on (`:500-517`).

**Security reviewer's lens (#1654's bound).** The refusal adds no parameter, no route and no caller-named destination: it is a `throw` on a path that previously wrote, so it strictly *reduces* the set of bytes written. `NON_LOOPBACK_ALLOWED` is untouched, no MCP tool or `/api` route is added, and the two license-gate tables need no row. The message is a fixed string — no path, no filename, no document text — which matters because `tandem_save`'s error also reaches Claude.

**3. Correct the export comment.** `src/server/file-io/docx-export.ts:20-22` says "Top-level `<image>` nodes ARE exported when present", which is true of markdown-origin documents and reads as a preservation promise for `.docx` round-trips. Add the measured qualifier: a `.docx` import produces no `image` node at all, so a `.docx`→`.docx` round-trip carries no pictures, and the save now refuses rather than writing one silently.

**4. Markdown — keep the source instead of the alt text.** In `imageToYxml`, thread the caller's `deferred: DeferredText[]` (both call sites — `blockToYxml`'s `case "image"` at `:364` and `splitParagraphImages` at `:535` — already hold one) and replace the rejected-src arm with a paragraph whose `Y.XmlText` is deferred as `{ xmlText, nodes: [node] }`. `processInline`'s own `case "image"` (`:630-637`) then stores `serializeMdastInline(node)` as a `rawMarkdown` run — the treatment #1799 already gave the *inline* case one PR ago, whose comment says in as many words that a rejected URL should become "an inert raw text run rather than a downgraded paragraph". This aligns the standalone case with it; no new mechanism, no new node type.

Two properties this inherits rather than invents: `insertRaw` uses insert-with-attributes on an **attached** `Y.XmlText`, so every character counts 1-for-1 in `getElementText()` and no annotation offset moves (#981, and CLAUDE.md's "attach before populating"); and the raw run is *text*, never an `src`, so nothing rejected by `sanitizeImageSrc` reaches a DOM sink — the #1420 guarantee is unchanged.

## Tests

1. `tests/server/docx-roundtrip-fidelity.test.ts` "embedded image" case (`:250-258`): keep `status: "breaks"` and keep `expect(hasNode(rt.gen1, "image")).toBe(false)` — this PR makes the loss *legible*, it does not preserve images — and add `expect(rt.importWarnings.some((w) => /picture/i.test(w))).toBe(true)`. Update the `reason` string. Kills "add the banner but drop the count", and kills a future silent regression to no-banner.
2. New in `tests/server/docx-import-write-seam.test.ts` (or a sibling): open `corpus.buildEmbeddedImage()` through the real adapter, then `saveDocument` → rejects with a `VERIFY_BLOCKED` code, **and `fs.stat` shows the original bytes unchanged**. The byte assertion is the discriminating half: it kills an implementation that throws after `atomicWriteBuffer`, which would pass a code-only test while having already destroyed the file.
3. Negative twin, same file: a `.docx` with no image (`corpus.buildHeadings()`) saves normally. Kills "refuse every `.docx`", which every assertion in test 2 would otherwise also accept.
4. `tests/server/docx-lost-features.test.ts` or the adapter's own suite: `droppedImages` is `1` for the image fixture and absent/0 for a headings fixture, and the loss line carries no `src` substring (`expect(line).not.toContain("base64")`) — pins the count-only contract.
5. Markdown, in the existing `mdast-ydoc`/`markdown` round-trip suite: `![Architecture diagram](file:///C:/x/d.png)`, `![svg](data:image/svg+xml;base64,PHN2Zz48L3N2Zz4=)` and a `![a](my image.png)` (space → rejected) each round-trip **byte-identically** through `loadMarkdown` → `saveMarkdown`, and the Y.Doc holds no `image` element for them. Kills both "emit the alt text" and "let the unsafe src through as an `image` node". Add the two rejected shapes to `experiments/rt.ts`'s corpus per the track's regression rule.
6. Idempotence: a second `loadMarkdown(saveMarkdown(...))` pass is a fixed point — the raw run must not re-escape on each save.

## Done when

An image-bearing `.docx` opens with a picture line in the fidelity banner, its save is refused with the file provably untouched, an image-free `.docx` still saves; `file:` and SVG-data markdown images round-trip verbatim; `docx-export.ts:20-22` is true; `npm run typecheck` + `npm test` green.

## Not in scope

Actually importing docx body images (preserve-the-package / Tier-B, #1142); an override or "save anyway" affordance; widening `sanitizeImageSrc`'s allowlist to admit `file:` or `svg+xml`; images in headers, footers or footnotes.
