# D2 — #1755 docx body images are dropped silently and the save overwrites the file image-less; markdown `file:`/SVG image sources become alt text

Branch `fix/docx-contract-walker-mammoth-flat-text-disagreement-and-dropped-body-images-1754`. **Closes #1755** (both halves of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:22` (docx) and `:23` (markdown).

## Problem

**Half 1 — docx.** mammoth emits a body picture as `<p><img src="data:image/png;base64,…"/></p>` (measured on `corpus.buildEmbeddedImage`: exactly one `<img>`, always inside a `<p>`). `docx-html.ts` handles `img` in `domNodeToYxml`'s block switch (`:400-421`), but the paragraph arm defers its children to `processInlineNodes` (`:573-633`), which has no `img` arm and ends in "unknown inline element — recurse (best effort)". An `<img>` has no children, so an `<img>` reached through the **inline** path is discarded. Nothing in `scanDocxLostFeatures` mentions images, so the fidelity report is silent, and `tandem_save` then regenerates the `.docx` through `exportYDocToDocx` and overwrites the user's file without them. `tests/server/docx-roundtrip-fidelity.test.ts:250-258` already records the loss as `"breaks"`.

**Half 2 — markdown.** `mdast-ydoc.ts#imageToYxml` (`:482-493`) downgrades a `sanitizeImageSrc`-rejected URL to a paragraph carrying `node.alt || node.title || ""`. Measured: `![Architecture diagram](file:///C:/…/diagram.png)` and `![svg](data:image/svg+xml;base64,…)` save back as the bare words `Architecture diagram` and `svg`. The URL is gone from the user's file.

## Fix

**1. Report the docx loss.** In `src/server/file-io/index.ts`'s `docxAdapter.parse`, after the `Promise.all`, call a new `countDroppedImages(html, footnoteBodies): number` exported from `docx-html.ts`.

**The count is of DROPPED images, not of all `<img>` tags, and the difference is load-bearing.** The block `case "img"` (`:400-421`) **does** build a real `image` `Y.XmlElement` for a `sanitizeImageSrc`-accepted src, and several other paths discard one. The failure direction is asymmetric: an over-count refuses the save **forever** with no override (see Not in scope), so the user's edits could never be written back.

> `droppedImages` = (`<img>` elements in the DOM `htmlToYDoc` actually consumes) − (`image` elements it produces)

**Do not mirror the dispatch with an ancestor list — measured, no hand-written list is right.** `"img"` is itself a member of `BLOCK_TAGS` (`docx-html.ts:33-53`, line 50) and `collectBlockChildren` (`:490-497`) routes a `BLOCK_TAGS` child back through `domNodeToYxml`, so a *direct* `<img>` child of `li`/`td`/`th`/`blockquote` takes the **block** arm and is **kept**, while the same `<img>` one level down inside a `<span>` is deferred and dropped; `<p>`, `h1`–`h6` (a regex arm above the switch) and `pre` defer wholesale; the `ul`/`ol`/`table` arms ignore a stray child outright, a third drop mode. Measured on this worktree: `<p><img></p>`, `<h1><img></h1>`, `<pre><img></pre>`, `<li><span><img></span></li>`, `<ul><img></ul>` → dropped; `<li><img></li>`, `<td><img></td>`, `<blockquote><img></blockquote>`, `<div><span><img></span></div>`, a bare top-level `<img>` → kept.

**Implementation — read the real walk's own numbers.**

- Add an optional final parameter to `htmlToYDoc`, `onImgTagCount?: (n: number) => void`, fired once with a plain recursive `<img>` tag count over `parsed.children` **after** `pruneFootnoteListItems` (`:265`) — no dispatch knowledge, and **not a regex** (which would count the string inside a text node). Counting post-prune keeps a footnote-body image out of the number: those `<li>`s are removed before the walk and reconstructed through `Y_MAP_FOOTNOTE_BODIES`, so counting them would refuse the save on a document whose body pictures are all intact. Existing callers (`docxAdapter.apply`, `docx-verify.ts:329`, four test files) are unchanged by construction.
- `kept` is read off the **output**: a recursive count of `image` `Y.XmlElement`s in the produced fragment. Nothing is threaded through the walk and no arm is edited, so the two numbers cannot drift from the dispatch.
- `countDroppedImages` runs `htmlToYDoc` against a **throwaway `Y.Doc`**, wrapped in `withInternal(probe, …)` (Critical Rule 2 satisfied literally; `htmlToYDoc` needs an outer transaction anyway, as `docx-verify.ts:329` does for the same reason), then `destroy()`s it and returns `total − kept`. The probe doc is never registered with Hocuspocus, never persisted, never observed.
- **Skip the audit when `options.scanLostFeatures === false`** — the `docx-verify.ts` re-import path reads no `prepared.issues`, so this costs one extra conversion per real document open and zero per save verification.

Push a line into `structural`, count-only, **never a `src` or an `alt`** (`docx-lost-features.ts`'s module header states that contract for every line in the list):

> `"${n} picture(s) couldn't be imported, so this file can't be saved back as .docx — ask Claude to convert it to Markdown to keep your edits"`

**The copy must describe the refusal, not a saved file**, and **must name an exit the user can take FROM THIS DOCUMENT.** The only client conversion affordance is `ReviewOnlyBanner.svelte:84-88` (`data-testid="convert-to-markdown-btn"`, the sole caller of `API_CONVERT` in `src/client/`), which renders only behind that banner's review-only `visible` prop — a writable on-disk `.docx` never shows it, and Save-As refuses anything whose `docState.source !== "upload"` (`document-service.ts:806-812`) before the `format: "md" | "txt"` typing is consulted. So the exit is Claude: `tandem_convertToMarkdown` is reachable for this document today, and D2-1754's v19 skill bump carries the matching `tandem_save` clause so Claude offers it on receiving the content-free refusal (`importLosses` is user-facing only — `src/shared/types.ts:521-536`). Classify the line `structural` because `structural` means "things that ARE gone" (`file-io/index.ts:253-257`) — **not** because it "drives the overwrite warning", which after item 2 can no longer happen for this document; say so where the line is built.

Carry the count: add `droppedImages?: number` to `LoadIssue { kind: "other" }` (`file-io/types.ts:55-70`) and to `FidelityReport` (`src/shared/types.ts:519-576`), optional with `?? 0` at every reader. Two sites, and the first is easy to miss because an omitted optional field is **not** a type error: `populate.ts#writeImportLossReport`'s **object literal** at `:100-109`, read off the same `issue.kind === "other"` loop that sets `structuralLosses`; and a `droppedImagesOf(report)` accessor mirroring `structuralLossesOf` (`document-service.ts:165-168`) with its `typeof value === "number"` guard, because `fidelityReportOf` (`:153-155`) is a bare `as FidelityReport` cast on a CRDT-synced value. Use the accessor at the refusal site. The count is computed at **parse**, not at apply, because `writeImportLossReport` reads parse-time issues only.

**2. Refuse the export.** `src/server/mcp/document-service.ts`, binary branch: when `droppedImagesOf(importSnapshot) > 0`, throw the existing `SaveVerificationError(blockReasonMessage(reason), reason)` with a new `BlockReason` member `"import-image-loss"` (`docx-verify.ts:61`; message added to `blockReasonMessage`'s switch at `:427-437`, which TypeScript keeps exhaustive). Message, content-free like its siblings: `"this file's pictures couldn't be imported, so saving would remove them" + " — your original file was left unchanged"`. Add `"import-image-loss"` to the reason array in `tests/server/docx-verify.test.ts:285-292` in the same commit, so the existing content-free sweep covers it.

**Placement is constrained from both sides.** `importSnapshot = fidelityReportOf(doc)` sits at `:480` inside a window whose comment (`:455-466`) forbids inserting an awaited call before `saveBinary`. Put the refusal **above** `prepareExportComments` (`:470`), before the window opens — `fidelityReportOf(doc)` reads just as well there. The requirement is that **no `await` is introduced inside the pinned window**. Being before `saveBinary` also means no bytes are generated and the once-per-run pre-overwrite backup gate is not consumed; being before `atomicWriteBuffer`/`suppressNextChange` means the file is untouched and the watcher suppressor is never armed — the ordering `verifyDocxRoundtrips`' own block already relies on (`:500-517`).

**Note the shape of the failure, because a test will get it wrong otherwise.** `saveDocumentToDisk` **catches** `SaveVerificationError` (`:665`) and **returns** `{ status: "error", reason: err.message, errorCode: "VERIFY_BLOCKED" }` (`:697-705`). It does not reject; `tandem_save` and `POST /api/save` both consume a `SaveResult`. The throw also lands before the `withMcp` block at `:555-585` and before `saveSession`, so this call writes no session snapshot — deliberate: the repo's softer `saved: false` + skip-reason vocabulary reads as a benign no-op, and these edits genuinely cannot reach `.docx`. Annotations are unaffected either way (durable annotation store, not `saveSession`).

**Scope — `tandem_applyChanges` must NOT gain the refusal.** `file-io/docx-apply.ts:502-527` edits the ORIGINAL `word/document.xml` in place and re-zips, so the pictures **survive** it; the refusal exists only because `exportYDocToDocx` regenerates from an image-less Y.Doc. Adding it "for consistency" would break the one write path that preserves docx images. Test 6 pins it. Likewise `verifyDocxRoundtrips` structurally cannot see this loss — both sides of its comparison are equally image-less — so comment the new member as having no producer inside that module.

Document the new failure once, where the caller reads it: `docs/mcp-tools.md:434`, `tandem_save`'s `**Errors:**` line (today the single word `FILE_LOCKED`), gains `VERIFY_BLOCKED`.

**Security lens (#1654's bound).** The refusal adds no parameter, no route and no caller-named destination — it is a `throw` on a path that previously wrote, so it strictly *reduces* the bytes written. `NON_LOOPBACK_ALLOWED` untouched, no MCP tool or `/api` route added, no licence-gate row needed. The message is a fixed string with no path, filename or document text, which matters because it reaches Claude verbatim (`document-service.ts:676-683`).

**3. Markdown — keep the source instead of the alt text.** In `imageToYxml`, thread the caller's `deferred` (both call sites — `blockToYxml`'s `case "image"` at `:364` and `splitParagraphImages` at `:505` — already hold one) and replace the rejected-src arm with `rawBlockParagraph(serializeMdastInline(node), deferred)`, the carrier `footnoteDefinition`/`definition` already use (`:383`, `:452-467`): a `paragraph[markdownRaw]` whose text is deferred to pass 2 and re-emitted verbatim on save. This is the treatment #1799 gave the *inline* image case one PR ago (`:630-637`); no new mechanism and no new node type. **Rewrite `imageToYxml`'s docblock in the same edit** — `:470-481` currently argues that the rejected arm needs no `deferred` because `new Y.XmlText(text)` bakes content in at construction, which after this change sits on code contradicting it. Two properties this inherits rather than invents: the raw run's characters count 1-for-1 in `getElementText()` so no annotation offset moves (#981), and the run is *text*, never an `src`, so nothing `sanitizeImageSrc` rejected reaches a DOM sink (#1420 unchanged).

## Review corrections (scope cut)

**Removed, and why**

- **`INLINE_DEFERRING_BLOCK_TAGS` and every ancestor-list definition of the count** (already deleted in round 3, and no list returns here). Both list-shaped findings — the `li`/`td` over-count that would make an image-bearing table permanently unsaveable, and the missing `pre` under-count — are moot: nothing mirrors the dispatch.
- **The mandated source-scan drift guard** over `domNodeToYxml`'s `case` labels. Both findings proving it unsatisfiable (`h1`–`h6` are a regex arm above the switch, not case labels) are moot with the guarded constant gone; test 4's routing fixtures are behavioural and cannot go stale against a refactor of the switch. No scanner is added.
- **The per-arm `kept` counter threaded through six walk functions.** Replaced by counting `image` elements in the produced fragment, which needs no source edit inside the walk and cannot drift from it. The optional `htmlToYDoc` parameter now reports only the post-prune `<img>` tag count.
- **The `satisfies Record<BlockReason, 1>` rewrite of `tests/server/docx-verify.test.ts`'s reason array.** A frozen-list gate the issue does not ask for; the new member is added to the existing array instead.
- **The save-side `droppedImages` carry in `document-service.ts:565-578` and its pre-seeded test.** The refusal fires first for exactly the documents with a non-zero value, and 0/absent is harmless to erase — so the carry was unreachable code with an artificial test to reach it.
- **The `VERIFY_BLOCKED` row in `docs/mcp-tools.md`'s global error table, and D2-1754's test 9 assertion on both doc lines.** One Errors line on the tool that now produces it is the documentation the issue implies; a docs-claims test is a new gate.
- **The `docx-export.ts:20-22` comment correction and the `experiments/README.md` + `experiments/rt.ts` edits.** Neither file is named by the issue and nothing in the fix reads them; the probes are evidence, not gates, and test 5 is the tracked criterion.
- **The measured nine-row routing table in the Fix section and its nine test fixtures**, cut to the prose sentence that states the mechanism plus the four fixtures that discriminate a direction (dropped, kept, rejected-src, footnote).
