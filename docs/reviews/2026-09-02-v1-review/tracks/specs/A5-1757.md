## Problem

`sendTurn` (`:900-927`) writes a user turn to `spawned.stdin` with a write callback and nothing else. When the pipe's peer goes away with a write in flight, Node emits `'error'` on the stdin `Writable`. The callback DOES receive it (the `:917-924` branch re-arms `pendingWake` and drops the latch), but a `Writable` with no `'error'` listener also throws it; the `spawned.on("error")` listener at `:1088` covers spawn failures only (measured, `epipe4.mjs`); so it lands in `index.ts:154-172`'s `handleFatalError`, which is narrowed to known Hocuspocus errors and calls `process.exit(1)`. **It does flush first** — `await captureFatal(value)` at `index.ts:170`, `sentry.ts:123` — so an earlier draft of this line saying "with no flush" was false and contradicted §Done-when, which had it right. The whole server dies under open documents because the launcher tried to nudge a session that had just gone.

**What the error actually is, measured on Node 24.14.1 (round 1, `probe-a5-r1/p10-exit-race.mjs`, 12 rounds of a child exiting under an in-flight write):** on Windows the code is **`EOF`** (libuv `UV_EOF`, errno −4095, `syscall: "write"`) — 136 callback hits and 12 `'error'` events, ZERO `EPIPE`. `EPIPE` is the POSIX spelling of the same condition (`epipe2.mjs`, where the child is an MSYS `sh` that closes fd 0 at OS level). `ERR_STREAM_DESTROYED` and `ERR_STREAM_WRITE_AFTER_END` reach the write CALLBACK only, never the `'error'` event, and both are unreachable through `sendTurn` anyway because `writable` is already `false` (the `:902` guard returns). The production peer on Windows is the **reaper** (`reaper/src/windows.rs:154-166` waits on parent OR child, so it exits the moment Claude does), which is why "child mid-exit" is the shape.

Two things this issue is adjacent to and does NOT fix, stated so the PR body does not overclaim: (1) an alive child that has stopped reading (or a child killed a moment ago) accepts a small write with no error at all — the turn sits in the OS pipe buffer, `turnInFlight` latches, and only the 10-minute latch-breaker (`:908-915`, `WAKE_LATCH_MAX_MS` `:152`) recovers it; on Windows that silent loss is the MORE likely outcome than any error. (2) A write callback that runs AFTER the child's `exit` handler already ran `teardownTurnDelivery` (`:966-977`) sets `pendingWake = true` on a closure nothing will flush — the wake is stranded. Both are pre-existing; name them in the PR body as follow-ups, do not fix them here.

The write is reachable from three places, all inside `spawnOnce`'s closure: the bootstrap/owed-wake write at `:1000-1008`, `onTandemEvent` (`:940-952`), and `flushPendingWake` (`:935-938`).

## Fix

**Policy decision (supersedes the plan's "anything else keeps today's fatal path"):** every `'error'` on the child's stdin means "this child can no longer be woken", full stop. There is no stdin-write error for which keeping the child AND continuing is right, and there is no known code that indicates a Tandem bug rather than a pipe condition — so an allowlist of pipe codes is a denylist pointed the wrong way, and round 1 proved it by measuring `EOF`, which the v1 allowlist would have re-thrown into `process.exit(1)` on the one platform Bryan runs. The listener logs `err.code` verbatim (an unseen code is VISIBLE in the log, not fatal) and ends the child. Record this in the PR body as a deviation from the plan with the `EOF` measurement as the reason.

**The seam is the HANDLER, not a classifier** (round 1 B3: an exported pure `classifyStdinError` table stays green with the listener inlined and the classification dropped). Export from `supervisor.ts`:

```ts
/**
 * Attach the one listener that turns a child-stdin write failure into
 * "this child is gone" instead of an uncaughtException (#1757).
 *
 * Any 'error' on the child's stdin means the pipe peer is gone or has stopped
 * accepting writes; nothing we can do with this child recovers it, and
 * index.ts's fatal handler would otherwise exit the whole server. Codes seen:
 * EOF (Windows, libuv UV_EOF — the write raced the child's exit; measured
 * 12/12 in probe-a5-r1/p10-exit-race.mjs on Node 24.14.1), EPIPE (POSIX). The
 * code is logged verbatim so an unseen one is visible rather than fatal.
 *
 * Ordering, measured: the write CALLBACK in sendTurn fires first (one per
 * queued write), then this event once, in a later tick. Both re-arm the wake;
 * running the pair 1..N times is idempotent because `stdin.writable` is
 * already false by the first callback, so a flushPendingWake() interleaved
 * from a `result` envelope takes sendTurn's early return and leaves the flag
 * set — do not move the re-arm above clearLatch() or relax that guard.
 */
export function attachChildStreamErrorHandlers(
  child: { stdin?: NodeJS.WritableStream | null; stdout?: NodeJS.ReadableStream | null; stderr?: NodeJS.ReadableStream | null },
  onChildGone: (err: NodeJS.ErrnoException) => void,
): void {
  if (child.stdin) {
    child.stdin.on("error", (err: NodeJS.ErrnoException) => {
      console.error(`[Launcher] Claude stdin write failed (${err.code ?? err.name}) — treating the session as gone`);
      onChildGone(err);
    });
  }
  // The READ halves are log-only and deliberately NOT routed through
  // onChildGone: a read error is not evidence the child stopped accepting
  // writes, and killing on one would be new behaviour with nothing measured
  // behind it. They still need a listener — a Readable emitting 'error' with
  // zero listeners throws by EventEmitter contract, which is #1757's exact
  // mechanism and exact blast radius, one stream over.
  for (const [name, stream] of [["stdout", child.stdout], ["stderr", child.stderr]] as const) {
    stream?.on("error", (err: NodeJS.ErrnoException) => {
      console.error(`[Launcher] Claude ${name} error (${err.code ?? err.name}) — logged only; a read error is not evidence this child stopped accepting writes, so it is not killed here`);
    });
  }
}
```
