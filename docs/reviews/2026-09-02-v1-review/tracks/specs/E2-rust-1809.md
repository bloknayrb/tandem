# E2-rust — #1809 a sidecar crash after boot is never restarted; `MAX_RESTARTS` is a boot-window budget only

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1809 — **but only because this spec implements the behaviour half.** The doc half the issue names is already done (see below), so a doc-only PR would not close it. The issue's toast clause is split out to **#1959**, filed for it, so the `Closes` carries no unfiled remainder. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:19`. Probe: none automatable; the decision function is unit-tested directly.

## Problem

`start_sidecar` (`src-tauri/src/sidecar.rs:1607`) runs `for attempt in 0..=MAX_RESTARTS` (`:1686`) and `return Ok(SpawnOutcome::Started)` the moment `wait_for_health` first succeeds (`:1872`). The retry budget is therefore consumed by, and confined to, the boot window. The per-spawn drain task's `CommandEvent::Terminated` arm (`:1812-1821`) logs a warn, sets `dead_flag`, calls `on_child_terminated` to clear the pid-keyed slot, and breaks. Nothing respawns. A crash minutes or hours in (the #1757 EPIPE crash is one reachable cause) leaves the desktop app with no server, no dialog and no toast, until the user finds Settings → Network → Restart server.

**The doc half is already fixed and must not be re-claimed.** `docs/architecture.md:857` was rewritten in `b89b07f0` (#1821 group A) and now states the boot-window confinement explicitly, citing #1809. Verified against current master. So the only work left is the behaviour, and the doc line has to be rewritten *again* once the behaviour changes, because it currently documents the absence as the design.

## Fix

Restart on an unexpected steady-state exit, bounded by a breaker, reusing the existing restart machinery rather than building a second one.

**The decision is a pure function**, so it is testable without an `AppHandle`:

```rust
pub(crate) enum CrashRestartDecision { Ignore, Restart, BreakerTripped }

fn crash_restart_decision(
    was_current_child: bool,
    healthy: bool,
    spawn_allowed: bool,
    history: &mut Vec<Instant>,
    now: Instant,
) -> CrashRestartDecision
```

- **`!was_current_child` -> `Ignore`, history untouched. This guard is FIRST and it is not optional.** `Terminated` is delivered per spawn attempt over a `channel(1)` behind `child.wait()` plus a write lock, drain tasks are never cancelled, and the drain loop is a serial `while let Some(event) = rx.recv().await` that logs every stdout/stderr line before it reaches `Terminated` — so **child A's `Terminated` can land after child B is already in the slot and already healthy**. The repo says so itself, at length, in `terminated_clears_slot`'s docblock (`sidecar.rs:1041-1047`: "child A's `Terminated` can land *after* child B has been stored … #1756 reintroduced by its own fix"), and `clear_terminated_slot` (`:1077-1096`) has a live `else` arm logging "leaving it (newer child)". Concrete path: `start_sidecar`'s retry loop kills child A on a health failure (`:1868`), sleeps 1 s (`:1704`), spawns child B, and B reaches `promote_healthy_and_drain` → `SIDECAR_HEALTHY = true` (`:1872`, `lib.rs:330`) before A's backlog drains. Without this input the decision then sees `healthy = true, spawn_allowed = true` and returns `Restart` — and `restart_sidecar` would call `stop_sidecar_gracefully`, whose `owns_child` is read from the slot (`:587-591`) **still holding the live child B**, so it POSTs `/api/shutdown` at the healthy sidecar and hard-kills it. The first draft's safety argument ("with an already-cleared slot takes `owns_child = false`") assumed the clear happened, which is precisely what the pid mismatch prevents.

  **Source the input from the identity test that already runs**, rather than adding a second one: change `clear_terminated_slot` → `on_child_terminated_in` → `on_child_terminated` to each return the `terminated_clears_slot(slot_pid, pid)` verdict as a `bool`, and pass that return value at the call site. One signature change through three one-line wrappers; no new state, no new predicate to keep in sync.
- `!healthy` -> `Ignore`, history untouched. **The second load-bearing guard.** During boot the same drain task fires `Terminated` while `start_sidecar`'s own loop is still retrying; a handler that respawns there double-spawns into the slot the loop is about to fill. `SIDECAR_HEALTHY` is exactly "the boot loop has already returned `Started`", and `restart_sidecar` clears it via `clear_healthy_under_lock` *before* stopping, so a user-initiated restart also lands here as `Ignore`.
- `!spawn_allowed` -> `Ignore`, history untouched. Covers `EXITING` (quit) and `SIDECAR_SHUTTING_DOWN` — which, **after #1808 lands in this same PR, is held across the download as well as the install**. A sidecar crash during a long update download is therefore not restarted until the guard drops. That is accepted and is stated in full in `E2-rust-1808.md`'s "The residual, named rather than implied away" paragraph; the PR body states it once, from there.
- Otherwise prune `history` of entries older than `CRASH_RESTART_WINDOW`, push `now`, and return `Restart` while `history.len() <= MAX_CRASH_RESTARTS`, else `BreakerTripped`.

**Every termination is treated as a crash, deliberately.** The arm binds `CommandEvent::Terminated(status)` and the decision does not read `status.code`. A `/api/shutdown` issued by something other than this process, and a Task-Manager kill, both produce the same event with `SIDECAR_HEALTHY` still true and no flag set — so both are respawned, up to the budget. That is the intent: the desktop app owns this sidecar, and an outside party stopping it is indistinguishable from a crash *from here*, while the two deliberate stops that matter (Quit and an install) are already covered by `spawn_allowed`. Recorded so it is a decision rather than an oversight.

Constants beside `MAX_RESTARTS` (`:152`): `const MAX_CRASH_RESTARTS: usize = 3;` and `const CRASH_RESTART_WINDOW: Duration = Duration::from_secs(300);` — the issue's own suggestion (3 per 5 minutes). The docblock must say why the window matters: a lifetime counter would make a day-long session permanently unrecoverable after three unrelated crashes, which is a worse failure than the one being fixed.

**The window is never reset by a successful manual recovery, and that is the choice.** After a trip, the user's Settings → Network → Restart server can succeed and a single later crash inside the same five minutes will trip the breaker again with no restart attempted. Clearing `CRASH_RESTARTS` on a successful user-initiated spawn was considered and rejected: it puts a reset on a path that has no idea whether the underlying fault is fixed, and the window self-heals in five minutes regardless. Say it in the docblock.

**The budget is consumed before `restart_sidecar` reports anything, and that is also the choice.** `crash_restart_decision` pushes `now` and returns `Restart` before the call; `restart_sidecar` (`:312-317`) early-returns if `RestartGate::try_acquire()` fails, and its spawned task early-returns again on `!spawn_allowed()` (`:351-354`). Neither outcome is fed back, so a crash storm racing a user restart can exhaust the budget with zero respawns attempted and then emit `sidecar-restart-failed`. Accepted rather than plumbed: threading the gate verdict back means the decision function is no longer pure, and the window self-heals. Stated in the docblock and the PR body so a reviewer does not re-derive it as a bug.

State: `static CRASH_RESTARTS: Mutex<Vec<Instant>> = Mutex::new(Vec::new());` (a `std::sync::Mutex`, const-constructible since Rust 1.63).

Call site — `sidecar.rs:1812-1821`, immediately after the `on_child_terminated(...)` call, **taking that call's new return value**:

```rust
let was_current = on_child_terminated(&terminated_handle, child_pid);
// Bind and DROP the guard before the match. A `MutexGuard` created in a
// match scrutinee lives to the end of the match body, and this whole block
// sits inside a `tauri::async_runtime::spawn` future whose loop awaits
// (`rx.recv().await`) — so a scrutinee-held `!Send` guard compiles today only
// because no arm awaits, and breaks with an error naming the spawn the moment
// one does. Poisoning is recovered the way `clear_terminated_slot` does it.
let decision = {
    let mut history = CRASH_RESTARTS.lock().unwrap_or_else(|p| p.into_inner());
    crash_restart_decision(
        was_current,
        crate::sidecar_is_healthy(),
        spawn_allowed(),
        &mut history,
        Instant::now(),
    )
};
match decision {
    CrashRestartDecision::Ignore => {}
    CrashRestartDecision::Restart => {
        log::warn!("[sidecar] crashed after boot — restarting (…)");
        restart_sidecar(terminated_handle.clone());
    }
    CrashRestartDecision::BreakerTripped => {
        log::warn!("…{MAX_CRASH_RESTARTS} crash restarts in {…}s — giving up");
        let _ = terminated_handle.emit("sidecar-restart-failed", "SIDECAR_CRASH_BREAKER_TRIPPED");
    }
}
```

**Reuse `restart_sidecar` (`:312`), do not hand-roll a spawn.** It already does everything the crash path needs and nothing it does not: `RestartGate::try_acquire` (so a crash-restart and a user click cannot race), `clear_healthy_under_lock`, `clear_startup_rejection`, the `spawn_allowed()` re-check inside the spawned task, `stop_sidecar_gracefully` — which, **now that `was_current_child` guarantees the slot really was cleared for this pid**, takes `owns_child = false`, skips the POST and reaches `kill_sidecar_inner` on an empty slot — then `start_sidecar` with its full `Started`/`Declined`/`Err` arms including the existing `sidecar-restart-failed` emit and `report_pending_opens_with`. A hand-rolled respawn would have to re-derive all of it.

**`lib.rs`** gains one accessor: `pub(crate) fn sidecar_is_healthy() -> bool { SIDECAR_HEALTHY.load(Ordering::Acquire) }`, beside `await_sidecar_healthy` (`:792`). `SIDECAR_HEALTHY` is a private static (`lib.rs:192`) and stays private — an unlocked *read* is already what `await_sidecar_healthy` does at `:799`, and the doc comment at `:206` explicitly says the mutex requirement is narrowed to writes, so this accessor is not a new licence.

**The auto-launcher consequence, named.** A crash-restart goes through `start_sidecar`, which re-reads `LAUNCHER_DEFERRED` per spawn (`sidecar.rs:1756`) and sets `TANDEM_DEFER_LAUNCHER` only while it is true. `note_user_presence` consumes the latch with `swap(false)` (`lib.rs:752`) as soon as the window is shown, so in the steady state the latch is **false** and a crash-restart therefore spawns the sidecar *without* the defer flag — which is what today's Settings → Restart server already does, except that this PR makes it automatic and repeatable up to three times per five minutes. Accepted: the re-read is the required behaviour (CLAUDE.md's latch rule forbids capturing it) and the launcher's own idempotence is what governs from there; passing `TANDEM_DEFER_LAUNCHER` unconditionally on the crash path was considered and rejected because it would make an automatic recovery behave differently from the manual one the user already has. Stated in the PR body.

**No success toast in this PR, and the clause has a tracked home.** The issue asks for a visible "Server restarted after a crash" toast; that is `src/client/**`, owned by the concurrently-running K-client group. **Filed as #1959** rather than left as "K-client's territory", which assigns it to nobody — the PR body references the number. The `warn!` clears the release log floor, and the user-visible recovery is already correct (tabs go Disconnected and reconnect on their own via the Hocuspocus generation gate). The **breaker trip** does get a toast, by reusing the existing `sidecar-restart-failed` event that `App.svelte:285` already listens for (it ignores the payload and hardcodes its message), so the terminal case is not silent.

**Docs:** rewrite `docs/architecture.md:857`'s step 5 — it currently says the boot-window confinement *is* the behaviour and cites #1809 as an open defect. New text: the boot loop is unchanged, plus the steady-state breaker (3 in 5 minutes), what trips it, and that a trip surfaces the same toast as a failed manual restart. **Correct the embedded citations in the same edit**: `:857` cites `sidecar.rs:1517` for the loop and `:1707` for the early return; they are now `:1686` and `:1872`. `docs/architecture.md:1193`'s `src/sidecar.rs` file-map line should gain "the post-boot crash breaker" to its list.

**Rules that bite:** the `LAUNCHER_DEFERRED` latch is re-read on every spawn (`sidecar.rs:1756`) — a crash-restart goes through `start_sidecar` and therefore re-reads it, which is the required behaviour and must not be short-circuited (consequence stated above). No Y.Doc write, no `/api` route, no `data-testid`.

## Tests

`src-tauri/src/sidecar.rs`, in a new `#[cfg(test)] mod crash_restart_tests` — **name the module; `sidecar.rs`'s test modules are all named and `lib.rs` has no `mod tests` at all.** Six tests, each killing a specific wrong implementation.

1. `crash_restart_decision_ignores_a_terminated_event_for_a_superseded_child()` — `was_current_child = false, healthy = true, spawn_allowed = true` -> `Ignore`, and `history` **empty** afterwards. **This is the first test because it kills the worst bug**: without the guard, a stale `Terminated` from a killed retry attempt gracefully stops and respawns a live, healthy sidecar (see the Fix section's concrete path).
2. `crash_restart_decision_ignores_a_crash_before_the_first_healthy_poll()` — `was_current_child = true, healthy = false` -> `Ignore`, history **untouched** (a version that records the attempt before checking `healthy` would burn the boot retries out of the steady-state budget). Kills the double-spawn-during-boot implementation.
3. `crash_restart_decision_ignores_a_crash_while_a_spawn_is_disallowed()` — `healthy = true, spawn_allowed = false` -> `Ignore`, history untouched. Kills a version that respawns during Quit or during an update install/download.
4. `crash_restart_decision_allows_three_in_the_window_then_trips()` — four calls at `now`, `now+1s`, `now+2s`, `now+3s` -> `Restart, Restart, Restart, BreakerTripped`. Kills a breaker that never trips and an off-by-one that allows four.
5. `crash_restart_decision_forgets_crashes_older_than_the_window()` — three entries at an old instant, then one call at `old + CRASH_RESTART_WINDOW + 1s` -> `Restart`, with `history.len() == 1` afterwards. Kills a lifetime counter and a prune that never actually drops entries.

**Build every `Instant` forward, never backward.** Seed `let old = Instant::now();` push the three old entries at `old`, and pass `now = old + CRASH_RESTART_WINDOW + Duration::from_secs(1)`. **`Instant - Duration` panics** ("overflow when subtracting duration from instant") when the result precedes the monotonic origin, and on Windows `Instant` is QPC-since-boot — so the first draft's `base - CRASH_RESTART_WINDOW - 1s` would *panic* rather than fail on a runner with under ~301 s of uptime. No wall-clock time passes either way.

6. `fn the_terminated_arm_routes_through_the_crash_decision()` — `include_str!("sidecar.rs")`, slice the `CommandEvent::Terminated(status) => {` arm to its closing brace **with `char_indices()`, not a byte range** (`sidecar.rs:4119`: "this file is full of em dashes"), and assert the slice contains **all three** of:
   - `crash_restart_decision`,
   - `restart_sidecar(`,
   - the literal `"sidecar-restart-failed"`.

   One structural test, because the arm needs a live `AppHandle` — and **all three needles, because one is not discriminating**: `let _ = crash_restart_decision(...);` with no match arms satisfies a contains-check for the first needle alone, which would leave the Done-when's two behavioural promises ("a post-boot crash respawns"; "a fourth trips the breaker and emits `sidecar-restart-failed`") pinned by nothing at all.

**Mutation check:** invert the `was_current_child` guard and test 1 goes red; invert the `!healthy` guard and test 2 goes red; delete the prune and test 5 goes red; change `<=` to `<` in the budget check and test 4 goes red; delete the `restart_sidecar(` call from the `Restart` arm and test 6 goes red. Restore from a file copy, never `git checkout`.

## Done when

A post-boot crash respawns within the budget; a stale `Terminated` from a superseded child never does; a fourth crash in five minutes trips the breaker and emits `sidecar-restart-failed`; boot, Quit and update-install/download crashes all take `Ignore`; six tests pass; `architecture.md:857` describes the new behaviour with corrected line citations; `cargo test` green.
