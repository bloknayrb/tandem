# C — #1803 The four Claude-facing write guards disagree on `audience`

Branch `fix/privacy-and-authority-1769`. Closes #1803. Ledger: `areas/server-mcp.md:24`, `areas/annotations.md:22`. Probe: reproduced in the review (`[ran]`) — `replyForClaude` refuses a `{type: "comment", audience: "private"}` parent; `transitionPending`, `editPendingAnnotation` and `removeForClaude` accept the same record.

## Problem

`src/server/annotations/lifecycle.ts` holds four Claude-facing write families and one of them carries the audience half of ADR-027:

| Family | Guard today |
|---|---|
| `replyForClaude` `:1305` | `ann.type === "note" \|\| (ann.type === "comment" && ann.audience !== "outbound")` |
| `transitionPending` `:844` | `ann.type === "note"` |
| `editPendingAnnotation` `:905` | `ann.type === "note"` |
| `removeForClaude` `:1327` | `sanitizeAnnotation(raw, onLossy).type === "note"` |

A stored `{comment, audience: "private"}` record (legacy envelope or stale-tab merge; `sanitizeAnnotation` derives an audience only when none is stored, `shared/sanitize.ts:79-87`, so it does not heal one) is something Claude cannot reply to but can edit, resolve or remove. Defence in depth — no first-party writer produces the record — but the four must say one thing.

## Fix

One module-private predicate in `lifecycle.ts`, spelled exactly as the reply guard already is, used at all four sites:

```ts
/** ADR-027 write-side: a note, or a comment whose stored audience is not outbound (#1619's write twin). Highlights are NOT here — they fall to their own arm (`not-repliable`, `invalid-suggestion-target`), see the docblock at :1289-1304. */
function isPrivateForClaude(ann: Annotation): boolean {
  return ann.type === "note" || (ann.type === "comment" && ann.audience !== "outbound");
}
```

- `:844`, `:905`, `:1305`: replace the inline condition with `if (isPrivateForClaude(ann)) return { kind: "invalid-note" }`. `:1327`: `if (isPrivateForClaude(sanitizeAnnotation(raw, onLossy))) return { kind: "invalid-note" }`.
- **Always AFTER `sanitizeAnnotation`** (a stored `flag` is a note only once normalized — CLAUDE.md), and in `transitionPending`/`editPending` still BEFORE the pending check (the disclosure ordering pinned by `adr027-note-write-guards.test.ts:80`). C-1770's author guard sits AFTER this one, so a user's private comment answers `invalid-note`, never `not-owned`.
- The arm stays `invalid-note`; its docblock (`:244-250`) already defines it as "not a Claude-facing comment". The three MCP envelopes (`mcp/annotations.ts:471-477`, `:515-519`, `:562-569`) keep their codes; the resolve/edit/remove messages say "private note or private comment".
- Keep the predicate **unexported**. Nothing new is imported by any route or MCP module, so `tests/server/annotation-remove-seam.test.ts` and `annotation-reply-seam.test.ts` keep their importer sets and counts. **Do not** add the guard to `addUserReply` (`:1250`) or `removeAnnotationRecord` (`:1050`): the user replying in, or archiving, their own private thread is what #1000/#1680 permit, and both seam tests fail if those acquire it.
- CLAUDE.md's ADR-027 paragraph already states the four guard sites; add the eight words "and `{comment, audience: private}` is refused by all four (#1803)". Review-only (no claims test reads that paragraph) — on the PR checklist.
