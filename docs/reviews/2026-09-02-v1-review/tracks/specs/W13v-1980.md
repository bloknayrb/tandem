# W13v — #1980 (Refs only) parked and quarantined annotation envelopes are never read back

Branch `fix/server-and-cli-small-correctness-fixes-2003`. **References #1980; the issue stays open.** This PR ships only the doctor-remediation sliver the triage identified as unambiguous, and names what remains. Ledger: no `areas/*.md` row — filed from the E2-upgrade group's spec review as the tracked home for a deferral in `docs/reviews/2026-09-02-v1-review/tracks/specs/E2-upgrade-1791.md`; wave 13 row in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: read the two remediation strings in `src/cli/doctor.ts` against `src/server/annotations/store.ts` and `src/server/file-io/reaper.ts`.

## Problem

Three write-only archives hold the user's personal notes (ADR-027) and nothing in the product reads any of them back: `<hash>.json.future` (plus the `<hash>.json.future.<ts>-<hex>` archives #1985 added), `<hash>.json.corrupt.<ts>`, and `<hash>.json.partial.<8 hex>` (shape per Bryan's comment on the issue, which supersedes the body).

The recovery affordance itself — `tandem doctor --recover-annotations`, a Restore entry — is a product decision about surface and stays with the issue. **Two doctor remediation strings are unambiguous, though: they state things that are not true**, verified against current source.

1. `"Written by a newer Tandem. Update, and they load again; they are never deleted."` (the `parkedFuture` warn, `src/cli/doctor.ts:2928`). Bryan's comment: *"the 'Update, and they load again' remediation this issue quotes is still the wrong promise: an upgraded build reads `<hash>.json`, and nothing reads any of these files back."* The park **renamed the file away**, so an upgrade finds nothing at the active name. The second half ("never deleted") is true and stays.
2. `"Safe to delete after inspection; kept 7d by design."` (the `quarantined` warn, `:2916`). There is no 7-day mechanism and no reaper: `ATOMIC_TEMP_RE` (`src/server/file-io/reaper.ts`) is anchored to `.tandem-tmp-<ms>-<12 hex>` — its own docstring names `<hash>.json.corrupt.<ts>` among the files it can never match — and no other caller unlinks one. They are kept **forever**.

Both are the class of text a user acts on: (1) tells them to upgrade and stop worrying, (2) tells them a cleanup exists.

**Why neither string may carry a how-to.** After a park, `<hash>.json` is **not** left absent: `parseAnnotationDoc` (`src/server/annotations/store.ts:711-731`) renames the target to `.future` and returns `emptyDoc(...)`, and the durable observer then writes a fresh `<hash>.json` from that session on. By the time a user reads the remediation that file normally holds real, current annotations — including notes created since the downgrade — so a "rename it back over `<hash>.json`" instruction destroys live data, in the one string this issue exists to make honest. Any correct how-to would also have to be upgrade-conditional (an older build re-parks the restored file on the next load). That is exactly the recovery-path design the issue still owns, so these strings state the situation and point at #1980 instead of instructing.

## Fix

Text only, in `src/cli/doctor.ts` — two `r.warn` remediation strings. No new check, no new count, no new flag, no scan change.

- `parkedFuture` → name the literal file and stop: *"Written by a newer Tandem and renamed aside to `<hash>.json.future`, so this build does not load them — it reads `<hash>.json`. They are never deleted; recovering one is manual today. See #1980."*
- `quarantined` → drop the false 7-day claim: *"Kept indefinitely — nothing deletes them. Safe to delete after inspection; reading one back is manual today. See #1980."*

Rules that bite: `runDoctor`'s path reads are an accepted, bounded security finding (#1609) whose bound is the **input** — do not widen these strings into anything that reads or opens a file, and do not add a remediation that instructs doctor to act. Critical Rule 3: doctor's reporter already owns its output stream; add no new write. The `.partial` warn (#1791/#1985) is already accurate and is **not** edited. Issue-reference form, decided rather than left open: both strings end with the literal **`See #1980.`** — no URL.

## Tests

`tests/cli/doctor.test.ts` already has a spec asserting the `parkedFuture` warn is emitted (`:336-350`), keyed on `r.data.parkedFuture` rather than on the string, so it stays green by construction. Add assertions to it, and create the quarantine sibling it lacks — the file already builds a temp annotations dir, and the fixture shape is `<hash>.json.corrupt.<epoch-ms>` (`src/server/file-io/reaper.ts:34`), e.g. `abc.json.corrupt.1758300000000`. **Select the quarantined warn by the warn itself, never by a data key.** `corruptCount` is not unique — `src/cli/doctor.ts:2832` puts `corruptCount: scan.quarantined` in the always-emitted `annotation-store` summary record, so a `"corruptCount" in r.data` selector (the shape the `parkedFuture` spec uses, unique only because `parkedFuture` appears nowhere else) resolves to the summary row, where `corruptCount === 1` also holds and there is no remediation at all — and any `r.remediation ?? ""` then makes all three negative assertions pass vacuously. Use:

```ts
const warn = results.find(
  (r) =>
    r.check === "annotation-store" &&
    r.status === "warn" &&
    r.message.includes("quarantined annotation file"),
);
expect(warn?.remediation).toBeDefined();
expect(warn?.data?.corruptCount).toBe(1);
```

Those two lines are the anti-vacuity precondition and run **before** the string assertions, so a mis-shaped fixture fails loudly instead of passing against an absent warn. Assert the remediation string directly off `warn.remediation` — never through a `?? ""` fallback, which reintroduces exactly the vacuity the precondition exists to prevent.

1. The `parkedFuture` remediation does **not** contain `"load again"`, and **does** contain the literal `.json.future`. Kills a revert and kills a rewrite that stays vague about which file to look for.
2. The `parkedFuture` remediation does **not** match `/rename .* over/i`. Kills a later rewrite that adds "rename it back over `<hash>.json`", which would tell the user to overwrite live annotations.
3. The `quarantined` remediation does **not** contain `"7d"` and **does** contain `"nothing deletes"`. Kills the false-mechanism claim specifically.

Negative assertions are used deliberately: the defect is a false promise, and a positive-only assertion passes on text that still carries it.

## Done when

Both strings corrected; the three assertions green (selected off the warn, with the `remediation`/`corruptCount` precondition); `npm test` passes. The PR body states, and the issue receives a comment stating, **what remains on #1980**: the recovery affordance itself — `tandem doctor --recover-annotations`, a Restore entry, or an equivalent — for all three archive shapes, including the ordering and upgrade-conditionality any manual route would need. That is a product decision about surface and is Bryan's to make.

## Not in scope (and stays on #1980)

The recovery path in any form, including a how-to in these strings; reaping `.corrupt.<ts>` (a real 7-day GC would make the old string true but deletes the data the issue exists to preserve); any change to the park / quarantine / partial-copy mechanism (#1791, #1985 own it); `annotation-store-scan.ts`'s counts, which #1985 already made correct.
