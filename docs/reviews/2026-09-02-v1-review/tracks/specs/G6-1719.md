# G6 — #1719 Selecting Annotations from inside a chat reveal collapses the whole right rail

Branch `fix/rail-seam-a-tab-switch-inside-a-chat-reveal-a-reveal-that-outlives-its-pin-and-rail-toggles-that-refuse-in-silence-1719`. **Refs #1719 — the issue stays open** for the half named under "Remaining work". Ledger: none — non-review issue; sweep row wave 9 `G6 rail seam` in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: the characterization spec `tests/e2e/chat-reveal.spec.ts:200`, whose own comment says **delete this spec when it is fixed**.

**The issue body's line numbers are stale** — it predates ADR-035 Unit 10b/10c, and the reveal no longer lives in `App.svelte`. Every citation below was re-read on master `4da4efa0`.

## Problem

`focusChat()` (`App.svelte:897-906`) selects Chat and calls `railContent.openReveal()`, floating `.rail-full` — the tab buttons included — over a collapsed rail. The user clicks **Annotations**, which is inside that float:

1. The capture-phase `pointerdown` closer (`rail-content.svelte.ts:146-167`) early-returns for a target inside `.rail-shell-right`, so it correctly does not fire.
2. `selectRailTab` (`model.svelte.ts:204-207`) writes the tab, then calls `opts.closeTransientChat()` because the target is not Chat — wired at `App.svelte:240` to `railContent.closeReveal()`.
3. The shell is `class:collapsed={!effectiveRightVisible}` (`App.svelte:2459`) and `class:floating={railFloat.right || railContent.revealOpen}` (`:2465`). Nothing pinned the rail, so with the reveal gone the shell is collapsed and not floating.

The panel — including the buttons the user just used — vanishes, with no message.

## Fix — one deletion

**The reveal's precondition is "the rail is collapsed", not "the tab is Chat".** A tab switch made from inside it is not a reason to tear it down, so the teardown goes.

- `model.svelte.ts`: `selectRailTab` (`:204-207`) keeps `activeRailTab = tab` and **drops the `if (tab !== "chat") opts.closeTransientChat();` line**. Delete `closeTransientChat` from `LayoutModelOptions` (`:87-95`) — it has no other caller — and update the `selectRailTab` doc on `LayoutModel` (`:113`), which still says "tearing down a transient chat reveal".
- The docblock at `:182-203` documents the Unit 10c *ordering* of a call that no longer exists; delete it and leave two lines in its place saying the reveal is deliberately NOT torn down here, and that #1719 is why. Nothing is re-ordered — the statement pair becomes one statement.
- `App.svelte`: remove the `closeTransientChat: () => railContent.closeReveal(),` line from the `createLayoutModel({…})` call (`:240`). The construction-order note at `:243-253` still holds and gets simpler: the layout model no longer references `railContent` at all.
- **Nothing opens a reveal from the tab path.** The rail is already floating when the user clicks a tab inside a reveal, so there is nothing to open; a pinned rail has `revealOpen === false` (`openReveal`'s guard, `rail-content.svelte.ts:113`) and behaves exactly as today; and no hover-float state is read or written.
- The reveal stays bounded by its four existing teardowns: outside `pointerdown` + Escape (`rail-content.svelte.ts:146-167`), document switch (`:171-174`), `toggleRightPanel` (`App.svelte:1205-1213`) and `sendChatMessage` (`:1967`). #1716 in this same group adds the fifth (the rail becoming pinned).

**Explicitly not done, and why:**

- **Pinning the rail from a tab click** — that writes persisted settings the user did not ask to change, and per #1722 the write can be refused, in which case the rail collapses anyway.
- **Calling `openReveal()` from `selectRailTab`** (the earlier shape of this spec). `effectiveRightVisible` (`App.svelte:1178`) carries persisted visibility only, so such a call also succeeds inside a **hover** float — and `railHoverReveal` defaults to `true` (`useTandemSettings.ts:298`). The latched reveal then keeps `.floating` asserted through `revealOpen` (`:2465`) while `maybeHideFloat` sets `.float-closing` (`:2466`), which the lifecycle comment at `:1243-1247` calls mutually exclusive. Cut rather than guarded: this fix needs no reveal-opening at all.
- No markup change, so **no `data-testid` is added, renamed or removed**; the testid snapshot is untouched.

## Review corrections (scope cut)

**Removed**

- **The `closeTransientChat` → `ensureRailShowable` rename and its unconditional `openReveal()` call.** Four blocking findings targeted exactly that call: it latches a reveal inside a hover float, where `railHoverReveal` defaults true, producing `.floating` + `.float-closing` co-presence. The issue asks for the rail to stop collapsing, not for a new reveal-opening path. Deleting the teardown closes the headline complaint and removes the float interaction entirely, so all four findings are moot rather than guarded.
- **The `App.svelte:240` float guard** (`if (railFloat.right || railFloatClosing.right) return;`) and the E2E regression spec written for it (the one that had to boot with `railHoverReveal` at its default and `page.evaluate`-blur to be meaningful). Both existed only to contain the call above.
- **The Related-half fix and its `Closes #1719` claim.** Making an annotation click float the rail needs the cut call; the half is named as remaining work and #1719 is downgraded to `Refs`.
- **Assumptions 1–5, the `focusChat` bullet, and the `display-menu.spec.ts` / `margin-view.spec.ts` blast-radius run list** — all consequences of opening reveals from click paths. With no new reveal path, those specs are untouched by this change.

**Kept and answered directly**

- The findings' warning that `openReveal`'s guard covers pinned rails only, not floats, is now a stated reason for the shape rather than a guard: nothing here calls `openReveal`.
- The suggested alternatives — widening `openReveal`'s guard, injecting a `getRailFloating` thunk, or clearing `railFloat` when a reveal opens — are all **not adopted**: each exists to make the cut call safe, and the call is gone.
