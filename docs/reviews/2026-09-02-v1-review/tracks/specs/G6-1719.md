# G6 — #1719 Selecting Annotations from inside a chat reveal collapses the whole right rail

Branch `fix/rail-seam-a-tab-switch-inside-a-chat-reveal-a-reveal-that-outlives-its-pin-and-rail-toggles-that-refuse-in-silence-1719`. Closes #1719 (both halves of its body — the headline tab switch and the "Related, same root" annotation click; see assumption 5, which is the condition for that). Ledger: none — non-review issue; the sweep row is wave 9 `G6 rail seam` in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: the existing characterization spec `tests/e2e/chat-reveal.spec.ts:200` ("#1719: selecting Annotations from inside the reveal collapses the whole rail"), whose own comment says **delete this spec when it is fixed**.

**The issue body's line numbers are all stale** — it was written before ADR-035 Unit 10b/10c moved this code, and the reveal no longer lives in `App.svelte`. Every citation below was re-read on master `4da4efa0`, and the one round 1 caught wrong was re-read rather than carried forward.

## Problem

`focusChat()` (`App.svelte:897-908`) selects Chat and calls `railContent.openReveal()`, floating `.rail-full` — tab buttons included — over a collapsed rail. The user clicks **Annotations**, which is inside that float:

1. The capture-phase `pointerdown` closer (`rail-content.svelte.ts:146-167`) early-returns for any target inside `.rail-shell-right`, so it correctly does not fire.
2. `selectRailTab` (`model.svelte.ts:204-207`) writes the tab, then calls `opts.closeTransientChat()` because the target is not Chat — wired at `App.svelte:240` to `railContent.closeReveal()`.
3. The shell is `class:collapsed={!effectiveRightVisible}` (`App.svelte:2459`) and `class:floating={railFloat.right || railContent.revealOpen}` (`:2465`). Nothing pinned the rail, so with the reveal gone the shell is collapsed and not floating.

The panel — including the buttons the user just used — vanishes, with no message. Every step is locally correct; neither writer asks whether the rail can still show the result.

The body's **"Related, same root"** half is the same seam: the `Editor`'s `onAnnotationClick` prop (`App.svelte:2910-2913`) calls `layoutModel.selectRailTab("annotations")` then `railContent.setActiveAnnotationId(id)`. Over a collapsed rail the side panel lives inside the hidden `.rail-full` (`.rail-shell.collapsed .rail-full { display: none }`, `App.svelte:3325-3327`), so clicking a highlighted span produces **zero feedback**.

## Fix

**The reveal is rail-scoped, not chat-scoped.** Its precondition is "the rail is collapsed", not "the tab is Chat" — so a tab switch should keep the rail showable rather than tear it down. One seam, both halves.

- `model.svelte.ts`: rename the injected option `closeTransientChat` → `ensureRailShowable: () => void` (`LayoutModelOptions`, `:84-95`) and call it **unconditionally** in `selectRailTab` (`:204-207`) — the `if (tab !== "chat")` branch goes. It stays **REQUIRED**, for the reason already recorded at `:91-94`: an optional callback lets a future consumer drop the behaviour with no signal.
- **Do not re-order `selectRailTab`.** The tab write stays BEFORE the callback; the docblock at `:182-203` states exactly how bounded that Unit 10c improvement is, and CLAUDE.md names re-ordering it as a trap. Keep the docblock's bounded claim — update only the sentence that says the callback tears a reveal *down*.
- **`App.svelte:240`: wire it float-guarded, not bare.**

```ts
ensureRailShowable: () => {
  // A hover float already shows the rail; latching a reveal over one turns a
  // transient float into a sticky panel and puts `.floating` and
  // `.float-closing` on the shell together. See assumption 1.
  if (railFloat.right || railFloatClosing.right) return;
  railContent.openReveal();
},
```

  Keep it an **arrow, not a bare reference** — the comment at `:238-239` explains the TDZ hazard, and the construction-order note at `:243-253` still applies unchanged (neither factory calls the other during construction). `railFloat` / `railFloatClosing` are declared at `:1248` and `:1260`, below this in the script but read only at call time, so no TDZ or staleness question arises.
- `openReveal` (`rail-content.svelte.ts:109-116`) already **no-ops over a pinned rail** — its guard reads `opts.getEffectiveRightVisible()` (`:113`), wired at `App.svelte:256` to `effectiveRightVisible = $derived(layoutModel.rightVisible)` (`:1178`). So pinned rails keep today's behaviour exactly: the tab switches and nothing floats. **No change to that function, and no new option on `RailContentOptions`** — the next bullet is why the float term is deliberately NOT folded into that guard.
- **`focusChat`'s own `openReveal()` at `App.svelte:905` STAYS.** An earlier draft of this spec deleted it as "now duplicated by `selectRailTab('chat')`". With the float guard the two calls are no longer equivalent: `ensureRailShowable` refuses over a hover float and `focusChat` must not, because `chat-unread-peek` (`App.svelte:2568-2574`) sits *inside* `.rail-shell-right`, so a hover float is usually armed when it is clicked — a guarded call there would refuse the reveal the user just asked for. Keep `setCapturedAnchor(null)` at `:900` and the "no-op over a pinned rail" comment at `:902-904` as they are. This is also why the float term cannot live inside `openReveal`: it would apply to `focusChat` too.

**The option not taken: pinning the rail.** Writing `rightPanelVisible: true` from a tab click mutates persisted settings the user did not ask to change, and — per #1722, this group's third issue — that write can be **refused** on a read-only blob, in which case the rail collapses anyway and the fix silently does not hold. Revealing needs no persisted write and cannot be refused.

**Consequence on the Related half, and it is a deliberate behaviour change:** clicking an annotation mark over a collapsed rail now floats the Annotations panel with that card selected, instead of doing nothing visible.

Rules that bite, checked inline:

- **Svelte 5 `$state` from a Tiptap handler.** `onAnnotationClick` is a DOM click callback from the annotation plugin, **not a `transaction`/`update` subscriber**, so it is outside the `state_unsafe_mutation` class CLAUDE.md names; it already writes two `$state` cells on that path today and the fix adds a third. No `createCoalescingTick` bridge is warranted — do not add one.
- `chatRevealDocumentId` (`rail-content.svelte.ts:99`) stays a plain `let` and off the interface. `openReveal` re-seeds it; re-opening an already-open reveal on the same document is idempotent.
- No markup change, so **no `data-testid` is added, renamed or removed** — `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched (the snapshot stores the `rail-float-right` *expression* at `App.svelte:2468`; leave that line alone).

## Assumptions (stated, not discovered)

1. **A tab click inside a HOVER float must not latch a reveal.** `effectiveRightVisible` carries persisted visibility only; the float terms are separate cells, so an unguarded `openReveal` succeeds inside a hover float — and `railHoverReveal` defaults to `true` (`useTandemSettings.ts:298`), making that the ordinary way a collapsed rail is used. The tab buttons are reachable there because `.rail-shell.rail-floating-chrome .rail-full { display: flex }` (`App.svelte:3356`) beats the collapsed `display: none` (`:3325`) by source order at equal specificity — the code's own comment at `:3344-3349` says the specificity is equal. Latched, the shell would carry `.floating` (via `revealOpen`, `:2465`) and `.float-closing` (`:2466`) together once the pointer left, which the lifecycle comment at `:1243-1247` calls mutually exclusive; the two animation rules target `.rail-full-right` at equal specificity (`:3403-3406` vs `:3411-3414`) and the later `float-closing` one wins with `forwards`. Hence the guard. **Chosen deliberately over the alternative** (let it latch, and clear `railFloat`/`railFloatClosing` when a reveal opens): that is a change of chrome ownership inside the hover lifecycle, which this group lists as out of scope.
2. **Bounded cost of the guard:** while a float is retreating (`railFloatClosing.right`, up to `FLOAT_CLOSE_MS = 300ms`, `App.svelte:1272`), a tab click or an annotation click opens no reveal. The panel is on screen and sliding out during that window; the click still switches the tab and still sets the active annotation. Accepted rather than special-cased.
3. **The same co-presence remains reachable through `focusChat`, and it is pre-existing.** With `focusChat`'s call left unguarded, a reveal opened over an armed hover float still keeps `.floating` asserted through the retreat when focus leaves the shell by keyboard or `blur()` — `onRailShellFocusOut` (`App.svelte:1348-1355`) calls `maybeHideFloat` (`:1315-1334`), which sets `railFloatClosing.right` because `railVisible("right")` is still false. An outside *pointerdown* does not reach it: the reveal's capture closer runs first. **Filed as #2014**, with its evidence bound stated there — read on master, not reproduced in a browser. Not fixed here, and this PR does not widen it: the new path is guarded.
4. **Close-then-reopen on the annotation-click path is accepted.** With a reveal open, clicking an annotation mark in the editor is a pointerdown OUTSIDE `.rail-shell-right`, so the capture closer (`rail-content.svelte.ts:146-154`) closes the reveal, and the later click runs `onAnnotationClick` → `selectRailTab("annotations")` → `ensureRailShowable` → open again. `pointerdown` and `click` are separate tasks, so the shell can commit `revealOpen === false` — dropping `.floating` and the `rail-float-right` testid — between them. Accepted: the end state is correct, and the alternative (teaching the pointerdown closer about annotation marks) puts editor knowledge into the rail model. **Noted for E2E authors: `rail-float-right` can be transiently absent during an annotation click**, so assert end states with Playwright's auto-retrying matchers, never a single synchronous read.
5. **#1719's Related half is closed by making the feedback appear, not by giving `PeekStrip` an active state.** The body names a missing `activeAnnotationId` prop on `PeekStrip` as the mechanism; this fix answers the complaint ("the collapsed rail gives zero feedback") by floating the Annotations panel with the card selected, and adds no such prop (`App.svelte:2561-2567` still passes `side`, `collapsed`, `kind`, `annotations`, `onActivate`). No PeekStrip work is deferred *against #1719*: the affordance itself is #832 (verified OPEN, label `deferred`, "PeekStrip contextual content preview"), which predates this issue and owns it independently. **If the implementer is not confident that satisfies the body, downgrade #1719 to `Refs` when deriving the `## Closes` list** — that derivation happens last, per the group's rule 1.
