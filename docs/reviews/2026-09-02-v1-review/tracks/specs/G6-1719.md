# G6 — #1719 Selecting Annotations from inside a chat reveal collapses the whole right rail

Branch `fix/rail-seam-a-tab-switch-inside-a-chat-reveal-a-reveal-that-outlives-its-pin-and-rail-toggles-that-refuse-in-silence-1719`. Closes #1719 (both halves of its body — the headline tab switch and the "Related, same root" annotation click). Ledger: none — non-review issue; the sweep row is wave 9 `G6 rail seam` in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: the existing characterization spec `tests/e2e/chat-reveal.spec.ts:200` ("#1719: selecting Annotations from inside the reveal collapses the whole rail"), whose own comment says **delete this spec when it is fixed**.

**The issue body's line numbers are all stale** — it was written before ADR-035 Unit 10b/10c moved this code, and the reveal no longer lives in `App.svelte`. Every citation below was re-read on master `4da4efa0`.

## Problem

`focusChat()` (`App.svelte:897-908`) selects Chat and calls `railContent.openReveal()`, floating `.rail-full` — tab buttons included — over a collapsed rail. The user clicks **Annotations**, which is inside that float:

1. The capture-phase `pointerdown` closer (`rail-content.svelte.ts:146-167`) early-returns for any target inside `.rail-shell-right`, so it correctly does not fire.
2. `selectRailTab` (`model.svelte.ts:204-207`) writes the tab, then calls `opts.closeTransientChat()` because the target is not Chat — wired at `App.svelte:240` to `railContent.closeReveal()`.
3. The shell is `class:collapsed={!effectiveRightVisible}` and `class:floating={railFloat.right || railContent.revealOpen}` (`App.svelte:2459-2468`). Nothing pinned the rail, so with the reveal gone the shell is collapsed and not floating.

The panel — including the buttons the user just used — vanishes, with no message. Every step is locally correct; neither writer asks whether the rail can still show the result.

The body's **"Related, same root"** half is the same seam: `onAnnotationClick` (`App.svelte:2056-2059`) calls `selectRailTab("annotations")` then `setActiveAnnotationId(id)`. Over a collapsed rail the side panel lives inside the hidden `.rail-full`, so clicking a highlighted span produces **zero feedback**.

## Fix

**The reveal is rail-scoped, not chat-scoped.** Its precondition is "the rail is collapsed", not "the tab is Chat" — so a tab switch should keep the rail showable rather than tear it down. One seam, both halves.

- `model.svelte.ts`: rename the injected option `closeTransientChat` → `ensureRailShowable: () => void` (`LayoutModelOptions:87-95`) and call it **unconditionally** in `selectRailTab` — the `if (tab !== "chat")` branch goes. It stays **REQUIRED**, for the reason already recorded at `:91-94`: an optional callback lets a future consumer drop the behaviour with no signal.
- **Do not re-order `selectRailTab`.** The tab write stays BEFORE the callback; the docblock at `:182-203` states exactly how bounded that Unit 10c improvement is, and CLAUDE.md names re-ordering it as a trap. Keep the docblock's bounded claim — update only the sentence that says the callback tears a reveal *down*.
- `App.svelte:240`: wire `ensureRailShowable: () => railContent.openReveal()`. Keep it an **arrow, not a bare reference** — the comment at `:238-239` explains the TDZ hazard, and the construction-order note at `:243-253` still applies unchanged (neither factory calls the other during construction).
- `openReveal` (`rail-content.svelte.ts:109-115`) already **no-ops over a pinned rail**, so pinned rails keep today's behaviour exactly: the tab switches and nothing floats. No change to that function.
- `App.svelte:905`: drop the now-duplicate `railContent.openReveal()` from `focusChat` — `selectRailTab("chat")` performs it. Keep the `setCapturedAnchor(null)` at `:900` and fold the "no-op over a pinned rail" comment into the remaining call.

**The option not taken: pinning the rail.** Writing `rightPanelVisible: true` from a tab click mutates persisted settings the user did not ask to change, and — per #1722, this group's third issue — that write can be **refused** on a read-only blob, in which case the rail collapses anyway and the fix silently does not hold. Revealing needs no persisted write and cannot be refused.

**Consequence on the Related half, and it is a deliberate behaviour change:** clicking an annotation mark over a collapsed rail now floats the Annotations panel with that card selected, instead of doing nothing visible. That closes the body's second half without any `PeekStrip` work.

Rules that bite, checked inline:
- **Svelte 5 `$state` from a Tiptap handler.** `onAnnotationClick` is a DOM click callback from the annotation plugin, **not a `transaction`/`update` subscriber**, so it is outside the `state_unsafe_mutation` class CLAUDE.md names; it already writes two `$state` cells on that path today and the fix adds a third. No `createCoalescingTick` bridge is warranted — do not add one.
- `chatRevealDocumentId` (`rail-content.svelte.ts:99`) stays a plain `let` and off the interface. `openReveal` re-seeds it; re-opening an already-open reveal on the same document is idempotent.
- No markup change, so **no `data-testid` is added, renamed or removed** — `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched (the snapshot stores the `rail-float-right` *expression* at `App.svelte:2468`; leave that line alone).
