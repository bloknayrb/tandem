## Problem

A function that walks a structure recursively and special-cases a **key by name at every depth** is correct only while no caller-supplied data can carry that name at any depth — a fact about the world, not about the code, and therefore invisible at the call site. This is the `ky` shape the blind-spots study found undefeatable in 12 of 12 runs.

`src/server/integrations/storage.ts:410-425` `normalizeLocalhostUrls` rewrites any key named `url` at any depth (`:416`). It is called at `:143`, **before** `IntegrationsFileSchema.safeParse` at `:144`, so it runs on raw parsed JSON from disk and the closed schema is not what protects it at the moment it runs. The rewrite is semantically live, not cosmetic (`localhost` and `127.0.0.1` differ under IPv6).

**Its live population is v3 files only.** `migrateUp` runs first (`storage.ts:137`), and `migrations.ts:29` / `:51` open each step with `IntegrationsFileV1Schema.parse` / `IntegrationsFileV2Schema.parse`, whose `url` fields are `LoopbackUrl` (`schema.ts:232`, `:270`, `:293`). A v1 or v2 file carrying `http://localhost` therefore throws inside `migrateUp` before normalization is ever reached. Only a v3 file can reach the rewrite — which is why the one end-to-end spec below has to be a v3 fixture. Do not restate the call-site comment's "files written before this tightening" as covering v1/v2; it does not.

**The gap is narrower than it looks.** The file already documents the *ordering*, both at the call site (`:138-142`) and in the function's own doc comment (`:406-407`, "Operates on the raw unknown post-migration shape so it runs before Zod validation"). **This issue is not "add a comment about ordering" — that comment exists.** What is missing is the other half: why walking every depth is safe, i.e. that no caller-supplied key named `url` can reach it.

The model is `src/server/mcp/schema-dialect.ts:89-106` `stripSchemaDialect`, which carries exactly that sentence: "Nothing in a `tools/list` result is user data — it is schemas and strings — so there is no value-shaped `$schema` to preserve." No change there.

## Fix

**Scope the rewrite rather than adding the sentence.** The issue states the preference ("Scoping is closer to the ky maintainer's actual fix and does not depend on the schema staying closed"), and one asymmetry decides it: over-reaching fails **silently** (a caller's `url` value is rewritten and validation still passes), while under-reaching fails **closed** at `LoopbackUrl` (`schema.ts:68-88`, which rejects any hostname but `127.0.0.1`). Two bounds on that "closed", both of which the PR body must respect rather than overstate:

- The failure is `read()` **throwing** (`storage.ts:145-149`, a bare `Error`), so the whole config refuses to load for every consumer. It is server-log-loud, but it reaches the wizard as a generic `{"error":"INTERNAL"}` — `storage.ts:45-52` documents exactly that flattening, and only `IntegrationsFutureSchemaError` gets a 409 branch. **Do not claim a user-facing validation error naming the field.**
- The loudness holds only *while a new `url` position is typed `LoopbackUrl`*. A future position typed `z.string().url()` or a free-form optional would under-reach silently.

The conclusion survives both bounds — a config that refuses to load is categorically better than a silently corrupted loopback address — and that asymmetry is also why this fix adds **no drift guard** for new `url` positions. State the bound so a later reader does not read "the validator already is a drift guard" as unconditional.

`src/server/integrations/storage.ts`:

- Rewrite `normalizeLocalhostUrls` (`:410-425`) to touch exactly `data.integrations[i].url`, one level under the top-level `integrations` array. **Derived from the existing schema, no schema change**: `grep -n 'url' src/server/integrations/schema.ts` gives five field positions — `:121` (`ClaudeCodeIntegration`, required) and `:159` (`OtherMcpIntegration`, `LoopbackUrl.optional()`) are the only two in the v3 file schema, and both sit directly on an integration record; `:232`, `:270`, `:293` belong to `IntegrationsFileV1Schema` / `IntegrationsFileV2Schema`, whose records are also integration records, and are cited for **structural shape only** — `migrateUp` parses those files through the same `LoopbackUrl` first, so the blob reaching the rewrite is always v3-shaped. So the positions collapse to one structural position and **no list of positions is needed** — do not add one, and do not widen `IntegrationsFileSchema` (hard rule). The scoping must not key on `kind`: `other-mcp` carries an optional `url` and must still be normalized.
- Shape: return `data` unchanged unless it is a non-array object whose `integrations` is an array; otherwise spread the file, map the array, and for each entry that is a non-array object with a **string** `url`, spread the record and replace `url` with the same `/^http:\/\/localhost([:\/]|$)/` rewrite that is there today. Every other key, at every depth, is passed through untouched. Non-object / non-array input still returns unchanged.
- **The doc comment at `:404-409` holds three sentences; replace the first, keep the other two verbatim.** (1) "Replace `http://localhost` with `http://127.0.0.1` in any `url` field across all integration records." is the **scope claim** — the one scoping falsifies, and the one to replace. (2) at `:406-407` is the **single ordering sentence** ("Operates on the raw unknown post-migration shape so it runs before Zod validation…") — keep. (3) at `:408-409` is the **pass-through contract** ("Safe to call on any value — non-object / non-array inputs are returned unchanged") — keep; it stays true under scoping and spec 4 pins it. The replacement for (1), in `stripSchemaDialect`'s form: *scoped to the one `url` position the schema has rather than walked at every depth, because it runs on the raw post-disk blob before Zod and a depth-agnostic rewrite would rest on the schema staying closed — the next free-form nested field added to it would carry a caller-supplied `url` into the rewrite with nothing to fail (#1603)*.
- **Amend one clause of the call-site comment at `:138-142`**: it currently says "files written before this tightening may carry localhost URLs", which is unreachable for v1/v2 (they are rejected earlier by their own `LoopbackUrl`). Say the rewrite is reachable for **v3 files only**. This is one clause in a comment the PR already edits, so it is in scope under the repo's bundle-small-fixes rule rather than a deferral. The ordering sentences themselves are unchanged and are not the gap.
- Export `normalizeLocalhostUrls` for the unit tests below. Precedent in the same file: `readSchemaVersion` (`:392`) is exported for sibling reuse. It gains no new caller in `src/` — the one call stays at `:143`, and the migration → normalize → Zod order at `:137-144` is **not** reordered.

**One behaviour change the specs must pin: a literal `__proto__` own key.** Today the body assigns `result[key] = …` into a `{}` literal, so an own `"__proto__"` key from `JSON.parse` hits the inherited setter — the key is silently dropped from the output and the accumulator's prototype is mutated, after which `.strict()` (`schema.ts:199`) never sees it and `read()` succeeds. The scoped shape spreads instead, and spread uses CreateDataProperty, so `__proto__` survives as a genuine own key and `.strict()` rejects the file — `read()` throws. Neither shape introduces pollution of anything outside the accumulator, and the loud direction is the intended one per `schema.ts:113-116` ("rejected loudly rather than silently stripped"). The repo has already decided this question the same way at `src/server/license/verifier.ts:18-23`, which uses `Object.create(null)` for exactly this reason. Name the change in the PR body; do not let it land unstated.

**Sweep result, to be recorded in the PR body** (the issue requires each candidate be dismissed explicitly rather than skipped). Three sweeps over `src/`:

- (a) `grep -rnE '\b(key|k|name|prop|field)\s*===\s*"'` minus `\b(e|ev|event|evt)\.key\s*===`, plus the `startsWith` / `includes` / `delete obj[key]` forms. (The issue's own suggested grep finds neither true instance cleanly — it is swamped by `e.key === "Escape"` DOM handlers.)
- (b) the recursive-JSON-walker population, enumerated **brace-tolerantly**: `grep -rnE 'Array\.isArray\((data|value|input|node|obj|v|x|entry)\)' src/ --include=*.ts`, triaging the whole result set. The narrower one-line form (`… \) return`) that an earlier draft of this spec used **structurally cannot** match a walker whose array branch is `if (Array.isArray(obj)) {` on its own line, which is how it missed `canonicalObject`. The completeness claim below rests on this wider sweep plus `grep -rln 'if (Array.isArray(' src` (13 files, each read), **not** on the one-line regex.
- (c) the membership / property-access spelling of the same special case, which neither literal-shaped sweep above can see: `grep -rnE '"[a-z$_]+" in |Object\.hasOwn' src/`.

- **True instances — two, and only two:** `stripSchemaDialect` (documented, unchanged) and `normalizeLocalhostUrls` (scoped here).
- **Recursive but not name-keyed:** `backup.ts:251-259` `canonicalJson` (sorts and serializes every key identically — no special case); `routes/diagnostics.ts:72-81` `scrubDeep` (applies one transform to every string at every depth; the caller's doc comment from `:83` onward already argues *for* walking everything, since enumerating fields is what would let a new `DoctorResult` field escape redaction); and `license/verifier.ts:10-27` `canonicalObject` — recursive over genuinely caller-supplied data (a pasted license, via `normalizePastedLicense`, whose bytes are what `:122` signature-checks), but **key-blind**: it sorts and re-emits every key identically with no name special-case, and already uses an `Object.create(null)` accumulator with its own written reasoning at `:18-23`. Dismissed on exactly `canonicalJson`'s grounds; no code change. It is the nearest living relative of the class, so its absence from an earlier draft of this list was an enumeration defect, not a missed bug.
- **Name-keyed but flat, one level, not recursive:** `useTandemSettings.ts:399-411` `parseFontByExtension` (drops `__proto__`/`constructor`/`prototype` over a caller-supplied settings blob, already carries its docblock reasoning), `apply.ts:1195-1206` and `:1335-1337` (`delete` over an explicit caller-supplied key *list*), `lifecycle.ts:759-764` `stripOwnedFields` (fixed `LIFECYCLE_OWNED_FIELDS` list, already carries a measured why), `uninstall-scrub.ts:507-556` (three fixed-key deletes at known paths), `supervisor.ts:652-653` (fixed env-key lists), and — from sweep (c) — `integrations/api-routes.ts:555-573` (`"configPath" | "workingDirectory" | "nodeBinary" | "url" in entry`, a one-level `.map` over `file.integrations` on data `store.read` has **already** validated through `IntegrationsFileSchema`, and it carries its own written why at `:563-569`).
- **The docx walkers** (`docx-apply.ts`, `docx-comments.ts`, `docx-footnotes.ts`, `docx-export.ts`, `docx-walker.ts`) compare OOXML **element** names (`w:r`, `w:t`, `w:p`, `w15:commentEx`) on a parsed XML tree inside a closed vocabulary — not keys over caller-supplied JSON. Dismissed explicitly, as the issue asks. `useRadioGroup.svelte.ts:41-43` is keyboard handling and is not in the class.
- **What the sweep cannot see** (rule 6): a walk whose special-cased name is a variable or a constant rather than a string literal; recursion expressed through a library callback rather than an explicit self-call; and — the one that already bit this spec once — **any shape whose line break falls between the sweep's anchors**, e.g. an array branch written `if (Array.isArray(x)) {` with the `return` on the next line, which is why sweep (b) is now the brace-tolerant form and the file-level `grep -rln` is the backstop. Sweep (c) closes the membership/property-access blind spot but is itself literal-shaped: a direct `obj.url !== undefined` test inside a recursive walker would still be invisible to all three.

**Item 4 — `CLAUDE.md` Gotchas: yes, one line.** Measured: the class appears nowhere in `CLAUDE.md`, `docs/gotchas.md` or `docs/lessons-learned.md` today (`grep -niE 'name-keyed|why-safe|recursive.*key|every depth'` over all three returns nothing). It fails silently, which is that section's stated admission test, and the repo's own scar tissue (#1534, Critical Rule 1, the `CTRL_ROOM` reservation, the watcher's content-hash fingerprint) is largely this same collision. One rule line under **Gotchas → MCP / Server** in `CLAUDE.md` — name-by-depth needs its why-safe sentence or scoping; over-reach fails silently, under-reach fails closed at the validator; the two instances named — with the mechanism paragraph in `docs/gotchas.md` under `### MCP / Server` (line 109), where the rules-inline/detail-linked split puts it. ## Tests

All in `tests/server/integrations/storage.test.ts` (380 lines; no localhost coverage exists there today, so the first spec is new coverage of existing behaviour), in a new `describe("normalizeLocalhostUrls", …)` beside `createIntegrationsStore`.

`normalizeLocalhostUrls` is typed `(data: unknown): unknown` and keeps that signature, so a spec cannot reach into the return value's fields without a type error — and `tests/` **is** typechecked, by `typecheck:tests` only (pre-push and CI, not `npm run typecheck`). Compare **whole objects with `toEqual` against a fully-written expected literal** rather than casting: it typechecks, and it also pins that no other key was touched.

1. **`read()` still normalizes a legacy `http://localhost` url on an integration record** — place the fixture with `await fs.promises.writeFile(store.filePath, JSON.stringify(v3OnDisk), "utf8")` (the file's own idiom at `storage.test.ts:200`), **never `store.write()`**: `writeIntegrationsFile` (`storage.ts:155`) Zod-parses first and `LoopbackUrl` would reject the very value under test. Carry two records — a `claude-code` one (`url` required, `schema.ts:121`) and an `other-mcp` one (`{kind:"other-mcp", id:"o-1", transport:"http", url:"http://localhost:3479"}`, where `url` is `LoopbackUrl.optional()`, `schema.ts:159`) — and expect both at `http://127.0.0.1:3479`. The second record is what kills a scoping that guards on a `kind` whose `url` is required. This is the only spec that goes through `read()`; the rest call the function directly, because `IntegrationsFileSchema` is `.strict()` and a blob carrying the nested key under test cannot survive Zod to be observed.
2. **Leaves a nested caller-named `url` key untouched (#1603)** — the nested object must be **structurally indistinguishable from an integration record**, or the spec is passed by a fix that merely content-sniffs while still walking every depth: `normalizeLocalhostUrls({schemaVersion: 3, integrations: [{kind: "claude-code", id: "a", url: "http://localhost:3479", nested: {kind: "claude-code", id: "b", url: "http://localhost:9/x"}}]})` rewrites the record's own `url` and returns `nested.url` **byte-identical** to the input. **This is the mutation target and the one discriminating spec**: only a body that indexes `data.integrations[i].url` positionally passes it. A narrowed-predicate fix (e.g. `key === "url" && "kind" in obj`) that keeps the recursive body passes specs 1, 3 and 4 and fails only this one.
3. **Leaves a `url` key at the file root untouched** — `{schemaVersion: 3, integrations: [], url: "http://localhost:1"}` comes back with that `url` unchanged. Cheap regression coverage that the root is passed through; it is **not** load-bearing, because the prescribed shape copies a root `url` untouched by construction and every plausible implementation of it passes. Do not describe it in the PR body as killing a class of fix — spec 2 carries that weight.
4. **Pass-throughs unchanged** — `null`, a string, a number, and an object with no `integrations` array are returned unchanged; an `integrations` entry that is a string or whose `url` is a number is left alone rather than throwing. Kills a scoping that narrows the input guard too far and starts throwing on the malformed files `read()` is supposed to hand to Zod for a clean error. This is the spec that pins doc-comment sentence (3).
5. **A literal `__proto__` own key survives as an own key** — build the input via `JSON.parse('{"schemaVersion":3,"integrations":[],"__proto__":{"x":1}}')` and assert the return still carries `__proto__` as an **own** key (`Object.hasOwn`), where the pre-fix body dropped it. Pins the behaviour change named in the Fix section: such a file now fails `.strict()` loudly instead of loading with a prototype-mutated record.

Mutation protocol (rule 5): copy `storage.ts` to the scratchpad, **paste the pre-fix depth-walking body back over the scoped one** — there is no single "scoping line" to revert, since the fix replaces the whole body, and reverting any one line yields a type error or a no-op rather than the old behaviour. Confirm spec 2 goes red and record its red output **verbatim** in the PR body, then restore **from the scratchpad file copy**, never `git checkout`.
