## Problem

A function that walks a structure recursively and special-cases a **key by name at every depth** is correct only while no caller-supplied data can carry that name at any depth — a fact about the world, not about the code, and therefore invisible at the call site. This is the `ky` shape the blind-spots study found undefeatable in 12 of 12 runs.

`src/server/integrations/storage.ts:410-425` `normalizeLocalhostUrls` rewrites any key named `url` at any depth (`:416`). It is called at `:143`, **before** `IntegrationsFileSchema.safeParse` at `:144`, so it runs on raw parsed JSON from disk and the closed schema is not what protects it at the moment it runs. The rewrite is semantically live, not cosmetic (`localhost` and `127.0.0.1` differ under IPv6).

**The gap is narrower than it looks.** The file already documents the *ordering*, both at the call site (`:138-142`) and in the function's own doc comment (`:406-407`, "Operates on the raw unknown post-migration shape so it runs before Zod validation"). **This issue is not "add a comment about ordering" — that comment exists.** What is missing is the other half: why walking every depth is safe, i.e. that no caller-supplied key named `url` can reach it.

The model is `src/server/mcp/schema-dialect.ts:89-106` `stripSchemaDialect`, which carries exactly that sentence: "Nothing in a `tools/list` result is user data — it is schemas and strings — so there is no value-shaped `$schema` to preserve." No change there.

## Fix

**Scope the rewrite rather than adding the sentence.** The issue states the preference ("Scoping is closer to the ky maintainer's actual fix and does not depend on the schema staying closed"), and one asymmetry decides it: over-reaching fails **silently** (a caller's `url` value is rewritten and validation still passes), while under-reaching fails **loudly** at `LoopbackUrl` (`schema.ts:68-88`, which rejects any hostname but `127.0.0.1` with a written message). A scoped rewrite that a future schema outgrows produces a validation error naming the field; a depth-walking one that a future schema outgrows produces a corrupted value. That asymmetry is also why this fix adds **no drift guard** for new `url` positions — the validator already is one.

`src/server/integrations/storage.ts`:

- Rewrite `normalizeLocalhostUrls` (`:410-425`) to touch exactly `data.integrations[i].url`, one level under the top-level `integrations` array. **Derived from the existing schema, no schema change**: `grep -n 'url:' src/server/integrations/schema.ts` gives five positions — `:121` (`ClaudeCodeIntegration`) and `:159` (`OtherMcpIntegration`) are the only two in the v3 file schema, and both sit directly on an integration record; `:232`, `:270`, `:293` belong to `IntegrationsFileV1Schema` / `IntegrationsFileV2Schema`, whose records are also integration records. So the two positions collapse to one structural position and **no list of positions is needed** — do not add one, and do not widen `IntegrationsFileSchema` (hard rule).
- Shape: return `data` unchanged unless it is a non-array object whose `integrations` is an array; otherwise spread the file, map the array, and for each entry that is a non-array object with a **string** `url`, spread the record and replace `url` with the same `/^http:\/\/localhost([:\/]|$)/` rewrite that is there today. Every other key, at every depth, is passed through untouched. Non-object / non-array input still returns unchanged.
- Replace the doc comment's third sentence with the why-scoped one, in `stripSchemaDialect`'s form: *scoped to the one `url` position the schema has rather than walked at every depth, because it runs on the raw post-disk blob before Zod and a depth-agnostic rewrite would rest on the schema staying closed — the next free-form nested field added to it would carry a caller-supplied `url` into the rewrite with nothing to fail (#1603)*. **Keep the two existing ordering sentences** at `:406-407` and the call-site comment at `:138-142` unchanged; they are not the gap.
- Export `normalizeLocalhostUrls` for the unit test below. Precedent in the same file: `readSchemaVersion` (`:392`) is exported for sibling reuse, and `parseFontByExtension`-style "exported for unit testing" is the repo idiom. It gains no new caller in `src/` — the one call stays at `:143`, and the migration → normalize → Zod order at `:137-144` is **not** reordered.

## Tests

All in `tests/server/integrations/storage.test.ts` (380 lines; no localhost coverage exists there today, so the first spec is new coverage of existing behaviour), in a new `describe("normalizeLocalhostUrls", …)` beside `createIntegrationsStore`.

1. **`read()` still normalizes a legacy `http://localhost` url on an integration record** — write a v3 file with `url: "http://localhost:3479"` on a `claude-code` record, read, expect `http://127.0.0.1:3479`. Kills a "fix" that deletes the normalization outright (the file would otherwise fail `LoopbackUrl` and `read()` would throw). This is the only spec that goes through `read()`; the rest call the function directly, because `IntegrationsFileSchema` is `.strict()` and a blob carrying the nested key under test cannot survive Zod to be observed.
2. **Leaves a nested caller-named `url` key untouched (#1603)** — `normalizeLocalhostUrls({schemaVersion: 3, integrations: [{id: "a", url: "http://localhost:3479", nested: {url: "http://localhost:9/x"}}]})` rewrites the record's own `url` and leaves `nested.url` exactly as given. **This is the mutation target**: restoring the depth-walking body turns this spec red. Kills every fix that keeps walking every depth.
3. **Leaves a `url` key at the file root untouched** — `{schemaVersion: 3, integrations: [], url: "http://localhost:1"}` comes back with that `url` unchanged. Kills a half-scoped fix that stops recursing into records but still special-cases the root object.
4. **Pass-throughs unchanged** — `null`, a string, a number, and an object with no `integrations` array are returned unchanged; an `integrations` entry that is a string or whose `url` is a number is left alone rather than throwing. Kills a scoping that narrows the input guard too far and starts throwing on the malformed files `read()` is supposed to hand to Zod for a clean error.

Mutation protocol (rule 5): copy `storage.ts` to the scratchpad, revert the scoping line, confirm spec 2 goes red, restore **from the file copy**, never `git checkout`.
