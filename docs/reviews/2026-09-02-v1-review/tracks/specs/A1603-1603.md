# A1603 — #1603 audit every name-keyed recursive transform for collision with caller-supplied data

Branch `fix/audit-every-name-keyed-recursive-transform-for-collision-with-caller-supplied-data-1603`. Closes #1603 (all four items of its "Proposed work"). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:109` (wave 9) — a non-review issue, so there is no `areas/*.md` row. Full analysis: `docs/spikes/ai-debugging-blind-spots-audit.md` (Finding 1).

## Problem

A function that walks a structure recursively and special-cases a **key by name at every depth** is correct only while no caller-supplied data can carry that name at any depth — a fact about the world, not about the code, and therefore invisible at the call site.

`src/server/integrations/storage.ts:410-423` `normalizeLocalhostUrls` rewrites any key named `url` at any depth (`:416`). It is called at `:143`, **before** `IntegrationsFileSchema.safeParse` at `:144`, so it runs on raw parsed JSON from disk and the closed schema is not what protects it at the moment it runs. The rewrite is semantically live, not cosmetic (`localhost` and `127.0.0.1` differ under IPv6).

**Its live population is v3 files only.** `migrateUp` runs first (`storage.ts:137`) and `migrations.ts:29` / `:51` parse each step through `IntegrationsFileV1Schema` / `IntegrationsFileV2Schema`, whose `url` fields are `LoopbackUrl` (`schema.ts:232`, `:270`, `:293`) — a v1/v2 file carrying `http://localhost` throws before normalization is reached.

**The gap is narrower than it looks.** The file already documents the *ordering*, at the call site (`:138-142`) and in the doc comment (`:406-407`). **This issue is not "add a comment about ordering" — that comment exists.** What is missing is the other half: why walking every depth is safe. The model is `src/server/mcp/schema-dialect.ts:89-106` `stripSchemaDialect`, which carries exactly that sentence ("Nothing in a `tools/list` result is user data…"). No change there.

## Fix

**Scope the rewrite rather than adding the sentence**, per the issue's stated preference. Over-reaching fails **silently** (a caller's `url` is rewritten and validation still passes); under-reaching fails **closed** at `LoopbackUrl` (`schema.ts:68-88`) — `read()` throws (`storage.ts:145-149`), reaching the wizard as a generic `{"error":"INTERNAL"}` (`storage.ts:45-52`), so **do not claim a user-facing error naming the field**, and the closedness holds only while a new `url` position is typed `LoopbackUrl`.

`src/server/integrations/storage.ts`:

- Rewrite `normalizeLocalhostUrls` (`:410-423`) to touch exactly `data.integrations[i].url`. **Derived from the existing schema, no schema change**: `grep -n 'url' src/server/integrations/schema.ts` gives `:121` (`ClaudeCodeIntegration`, required) and `:159` (`OtherMcpIntegration`, `LoopbackUrl.optional()`) in the v3 schema, both directly on an integration record — one structural position, so **no list of positions is needed** and `IntegrationsFileSchema` is not widened (hard rule). The scoping must **not** key on `kind`: `other-mcp`'s optional `url` must still be normalized.
- Shape: return `data` unchanged unless it is a non-array object whose `integrations` is an array; otherwise spread the file, map the array, and for each entry that is a non-array object with a **string** `url`, spread the record and replace `url` with the same `/^http:\/\/localhost([:\/]|$)/` rewrite that is there today. Every other key, at every depth, passes through untouched.
- **The doc comment at `:404-409` holds three sentences; replace the first, keep the other two verbatim.** (1) "Replace `http://localhost` … across all integration records" is the scope claim scoping falsifies — replace it, in `stripSchemaDialect`'s form: *scoped to the one `url` position the schema has rather than walked at every depth, because it runs on the raw post-disk blob before Zod and a depth-agnostic rewrite would rest on the schema staying closed (#1603)*. (2) the ordering sentence (`:406-407`) and (3) the pass-through contract (`:408-409`) stay verbatim; spec 4 pins (3).
- **Amend one clause of the call-site comment at `:138-142`**: "files written before this tightening may carry localhost URLs" is unreachable for v1/v2; say **v3 files only**. The migration → normalize → Zod order at `:137-144` is **not** reordered.
- Export `normalizeLocalhostUrls` for the unit specs (precedent: `readSchemaVersion` at `:392`). It gains no new `src/` caller.

**One behaviour change to state in the PR body.** Today `result[key] = …` into a `{}` literal means a literal `__proto__` own key from `JSON.parse` hits the inherited setter and is silently dropped, after which `.strict()` (`schema.ts:199`) never sees it. The scoped shape spreads, and spread uses CreateDataProperty, so `__proto__` survives as an own key and `.strict()` rejects the file — `read()` throws. The loud direction is the intended one (`schema.ts:113-116`); the repo already decided it this way at `license/verifier.ts:18-23`.

**Sweep result, recorded in the PR body** (the issue requires each candidate be dismissed explicitly). Two greps over `src/`, both re-run at implementation time and named in the body:

- (a) name-keyed literals: `grep -rnE '\b(key|k|name|prop|field)\s*===\s*"' src/`, minus `\b(e|ev|event|evt)\.key\s*===`, plus the `startsWith` / `includes` / `"x" in obj` / `delete obj[key]` forms. (The issue's own suggested grep is swamped by `e.key === "Escape"` handlers.)
- (b) the recursive-walker population, **brace-tolerantly**: `grep -rnE 'Array\.isArray\((data|value|input|node|obj|v|x|entry)\)' src/ --include=*.ts`, triaging the whole result set, with `grep -rln 'if (Array.isArray(' src` (13 files, each read) as the backstop. A one-line `…\) return` regex structurally cannot match a walker whose array branch is `if (Array.isArray(obj)) {`, which is how an earlier draft missed `canonicalObject`; the completeness claim below rests on the wider form.

- **True instances — two:** `stripSchemaDialect` (documented, unchanged) and `normalizeLocalhostUrls` (scoped here).
- **Recursive but not name-keyed:** `backup.ts:251-259` `canonicalJson`; `routes/diagnostics.ts:72-81` `scrubDeep` (deliberately transforms every string, and its doc comment argues for that); `license/verifier.ts:10-27` `canonicalObject` — recursive over genuinely caller-supplied data (a pasted license, signature-checked at `:122`) but **key-blind**: it sorts and re-emits every key identically with no name special-case, and already uses an `Object.create(null)` accumulator with its reasoning at `:18-23`. All three dismissed on the same grounds; no code change.
- **Name-keyed but flat, one level:** `useTandemSettings.ts:399-411` `parseFontByExtension`, `apply.ts:1195-1206` and `:1335-1337`, `lifecycle.ts:759-764` `stripOwnedFields`, `uninstall-scrub.ts:507-556`, `supervisor.ts:652-653`, and `integrations/api-routes.ts:555-573` (a one-level `.map` over data already validated through `IntegrationsFileSchema`, carrying its own why at `:563-569`).
- **The docx walkers** (`docx-apply.ts`, `docx-comments.ts`, `docx-footnotes.ts`, `docx-export.ts`, `docx-walker.ts`) compare OOXML **element** names inside a closed vocabulary, not keys over caller-supplied JSON — dismissed explicitly, as the issue asks. `useRadioGroup.svelte.ts:41-43` is keyboard handling, not in the class.
- **What the sweep cannot see** (rule 6): a special-cased name held in a variable or constant; recursion through a library callback; a bare `obj.url !== undefined` test inside a walker; and any shape whose line break falls between a regex's anchors — which is why (b) is the brace-tolerant form.

**Item 4 — `CLAUDE.md` Gotchas: yes, one line.** Measured: `grep -niE 'name-keyed|why-safe|recursive.*key|every depth'` over `CLAUDE.md`, `docs/gotchas.md` and `docs/lessons-learned.md` returns nothing today. It fails silently, which is that section's stated admission test. One rule line under **Gotchas → MCP / Server** in `CLAUDE.md` (name-by-depth needs its why-safe sentence or scoping; over-reach fails silently, under-reach fails closed at the validator; the two instances named), with the mechanism paragraph in `docs/gotchas.md` under `### MCP / Server`. `storage.ts` is config rather than MCP code; that heading is still the closest and a new section for two entries is worse — say so in the PR body. Cite `#1603` and the two file paths; never a bare `(§N)`-shaped citation (`tests/build/invariant-citations.test.ts`). **No claims test pins it** — that pattern is for the security and loopback inventories, and adding a third is framework this issue does not ask for.

## Tests

All in `tests/server/integrations/storage.test.ts`, in a new `describe("normalizeLocalhostUrls", …)`. The function stays `(data: unknown): unknown`, and `tests/` is typechecked (by `typecheck:tests` only), so compare **whole objects with `toEqual` against a fully-written expected literal** rather than casting — it also pins that no other key was touched.

1. **`read()` still normalizes a legacy `http://localhost` url on an integration record** — write the v3 fixture with `await fs.promises.writeFile(store.filePath, …)` (the file's idiom at `storage.test.ts:200`), **never `store.write()`** (`writeIntegrationsFile`, `storage.ts:155`, Zod-parses first and `LoopbackUrl` would reject the value under test). Carry a `claude-code` record and an `other-mcp` one (`{kind:"other-mcp", id:"o-1", transport:"http", url:"http://localhost:3479"}`); expect both at `http://127.0.0.1:3479`. The second kills a scoping keyed on `kind`. The only spec that goes through `read()` — `IntegrationsFileSchema` is `.strict()`, so the nested-key blobs below cannot survive Zod to be observed.
2. **Leaves a nested caller-named `url` key untouched (#1603)** — the nested object is **structurally indistinguishable from an integration record**, or a content-sniffing fix that still walks every depth passes: `normalizeLocalhostUrls({schemaVersion: 3, integrations: [{kind: "claude-code", id: "a", url: "http://localhost:3479", nested: {kind: "claude-code", id: "b", url: "http://localhost:9/x"}}]})` rewrites the record's own `url` and returns `nested.url` **byte-identical**. **This is the mutation target and the one discriminating spec**: only a body that indexes `data.integrations[i].url` positionally passes it; a narrowed predicate such as `key === "url" && "kind" in obj` over the recursive body passes 1, 3 and 4 and fails only this.
3. **Leaves a `url` key at the file root untouched** — `{schemaVersion: 3, integrations: [], url: "http://localhost:1"}` comes back unchanged. Regression coverage only; it is **not** load-bearing (the prescribed shape passes it by construction), so do not describe it in the PR body as killing a class of fix.
4. **Pass-throughs unchanged** — `null`, a string, a number, an object with no `integrations` array; and an `integrations` entry that is a string or whose `url` is a number is left alone rather than throwing. Pins doc-comment sentence (3) and kills a scoping that narrows the input guard into throwing on malformed files `read()` must hand to Zod.
5. **A literal `__proto__` own key survives as an own key** — build via `JSON.parse('{"schemaVersion":3,"integrations":[],"__proto__":{"x":1}}')`, assert `Object.hasOwn(result, "__proto__")`. Pins the behaviour change named above.

Mutation protocol (rule 5): copy `storage.ts` to the scratchpad, **paste the pre-fix depth-walking body back** over the scoped one (there is no single line to revert), confirm spec 2 goes red, transcribe its red output **verbatim** in the PR body, then restore **from the scratchpad copy**, never `git checkout`.
