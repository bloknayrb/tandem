# G4 — #1615 `vi.mock("string")` type-checks nothing

Branch `fix/typecheck-tests-three-configs-and-a-mock-idiom-that-check-nothing-1613`. Closes #1615
**only if the whole conversion lands** — see Boundary; a partial landing makes this Refs plus a filed
remainder. Non-review issue, `docs/plans/2026-09-06-open-issues-sweep.md:110`. Probe: mechanical
conversion of every first-party site, then `npm run typecheck:tests`.

## Problem

The mechanism holds exactly as filed: with the string overload, `M` defaults to `unknown`, so the
factory is checked against `Partial<unknown>` — `{}` — and has zero correspondence to the real module.
The typed overload `vi.mock<T>(module: Promise<T>, …)` checks it against `Partial<T>`.

**Every count in the issue understates.** Re-measured on `f6559305`:

| | issue says | measured 2026-09-16 |
|---|---|---|
| `vi.mock("…")` string form | 199 | **266** |
| …against a first-party `src/` module | 158 | **215**, in **96** files |
| typed `vi.mock(import(…))` | 0 | **0** |
| `vi.mocked(…)` sites | 173 | **238** |

All 215 first-party sites carry a factory (0 bare, 0 `vi.doMock`/`vi.unmock`), so the conversion is
uniform: `vi.mock("X", ` → `vi.mock(import("X"), `.

**Runtime equivalence is proven, not assumed.** With all 215 converted,
`vitest run tests/server/annotations/store.test.ts tests/cli/run-setup-apply.test.ts
tests/client/settings-models-tab.test.ts` → **3 files, 65 tests, all passed**. Vitest hoists the typed
form and never evaluates the `import()`.

**What the conversion surfaces: 66 errors** (node 28, client 38, e2e 0), in two families.

*Family A — idiom friction, 26 sites, mechanical.* The typed overload constrains the helper as
`importOriginal<T extends typeof module>`, so a deliberately-widening generic is now illegal:
`importOriginal<Record<string, unknown>>()` (21 sites, 10 files) and `importOriginal<object>()`
(5 sites) become TS2344. Dropping the explicit generic cleared all 20 node TS2344s in a probe and
introduced 2 follow-ons in `tests/server/document-service.test.ts` (TS2698/TS18046, `actual` inferring
`unknown`) that want the `<typeof import("…")>` form instead. 108 sites already use that correct form.

*Family B — real stale doubles, ~40 sites, the point of the exercise.* Residual TS2769s whose leaf
names a genuine mismatch. Confirmed: `applyOpsForCli: vi.fn(() => ({}))` returns `{}` where production
returns `ApplyOps`; a `ModelsState` double missing 8 members; `FindReplaceState` missing `query`,
`caseSensitive`, `wholeWord`, `regexMode`, `decoSet`; `coworkToggleIntegration` returning `{ ok }`
where production returns `CoworkToggleReport`; and several whole-module factories returning `{}` while
the module exports 4–5 symbols. Same shape as the `ScrubLogger` `warnings` omission the filing unit
already fixed.

## Fix

0. **Confirm the odd specifier shapes resolve, on one site, before converting.** 26 first-party sites
   mock a bare `.svelte` specifier whose real file is `*.svelte.ts` (`useCoworkStatus.svelte` ×10 and
   five more hooks), where Svelte's ambient `declare module '*.svelte'` is a competing resolution — if
   it won, the factory would be checked against a component default and the conversion would be churn
   that *looks* like checking. 2 more are alias specifiers
   (`tests/client/titlebar-listener-leak.test.ts:8,11`). **Measured: both shapes resolve to the real
   module** — `ts.resolveModuleName` under the tests-client options lands all six hooks on
   `src/client/hooks/*.svelte.ts` and both aliases on `src/client/cowork/cowork-helpers.ts`. A true
   component specifier *is* unresolved and falls to the ambient wildcard, but no first-party `vi.mock`
   targets a component. Re-confirm on one site (that `vi.mock(import("…/useCoworkStatus.svelte"), …)`
   infers `createCoworkStatus`, not a component default); if the ambient wins after all, leave those 26
   as string mocks and say so in the PR body.
1. **Convert all 215 first-party sites** to `vi.mock(import("…"), …)`. Leave the 51 third-party string
   mocks alone (`@tauri-apps/*`, node builtins) — the typed form buys nothing where we do not own the
   module.
2. **Family A**: drop the widening generic. Prefer bare `importOriginal()`; where inference goes to
   `unknown` (the two `document-service.test.ts` sites) use `importOriginal<typeof import("…")>()`,
   matching the 108 sites that already do.
3. **Family B**: widen each double to satisfy the real export — add the omitted members, correct the
   return shapes. **Every one is a finding, not an obstacle.** If any turns out to be a *production*
   bug rather than a stale test, stop and say so loudly in the PR body rather than editing the test to
   match.
4. **Do not touch the 238 `vi.mocked(…)` sites.** The issue is explicit and right: a bare `vi.fn()`
   loses argument checking only where it is stored in an *un-annotated* bag; where the bag carries the
   production type it still checks. The fix for that half is annotating the bag, and it is not this
   issue.

Rules that bite: `vi.mock` is hoisted file-wide, so a converted factory stays in the same position;
`TANDEM_APP_DATA_DIR=$(mktemp -d -t tandem-XXXXXX)` prefixes every vitest run (the literal `tandem` is
load-bearing for `tests/server/platform.test.ts`); run with `VITEST_MAX_FORKS=2 VITEST_MAX_THREADS=2`
while a second group is active.

**File the remainder issue BEFORE writing the PR body**, put its number in the body, and move #1615
from `Closes` to `Refs` in the same edit. Because nothing in the repo distinguishes a converted site

`grep -rhoE 'vi\.mock\("(\.\./)+src/' tests --include=*.ts | wc -l`, plus the count it returned at

through the `@client/*` path alias (`tests/client/titlebar-listener-leak.test.ts:8,11`) and score as
converted no matter what form they are in; they were converted with the rest (review round 2), and any
future alias site needs `grep -rhoE 'vi\.mock\("@(client|shared|server)/' tests --include=*.ts | wc -l`
alongside. The parent's own count was 36% stale; the next reader re-measures rather than trusting a figure.

## Tests

No new spec file; `typecheck:tests` is the gate.

1. **Mutation — and it must target a NESTED member, not a module export.** The typed overload checks
   the factory against `Partial<T>`, which makes an **omitted top-level module export legal by
   design**. Deleting a whole export from a converted factory stays green and would be misread as "the
   conversion bought nothing". Delete instead a member of a *returned object* double — e.g. a field of
   the object `applyOpsForCli` returns — which is TS2739, and confirm `npm run typecheck:tests` fails
   naming that file (restore from a file copy, never `git checkout`). Before conversion the same
   deletion is silent: run it both ways and record both in the PR body. That pairing is the only thing
   proving the conversion bought checking rather than churn. **State the bound in the PR body:** it
   checks member shapes, not module completeness.
2. **Runtime.** Full `npm test` green, and specifically the 96 converted files — the conversion must be
   observationally inert at runtime.
