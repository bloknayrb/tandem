# A4 — #1756 Desktop Quit hard-kills the sidecar; up to 60 s of edits lost

Branch `fix/graceful-quit-1756`. Closes #1756. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-runtime.md`. Rust; `cargo test` must pass (pre-push runs it; `CARGO_TARGET_DIR` is shared — builder brief). Resolved versions from `Cargo.lock`: tauri **2.11.5**, tauri-runtime-wry 2.11.4, tao 0.35.2, tauri-plugin-shell 2.3.5, tauri-plugin-updater 2.10.1.

**Design changed after round 1.** Round 1 reviewed an `ExitRequested` + `prevent_exit()` deferral and found holes it cannot close: macOS ⌘Q / Dock Quit / app-menu Quit go through tao's `applicationWillTerminate:` → `LoopDestroyed` and never raise `ExitRequested` (Tandem installs no app menu, so Tauri's default `PredefinedMenuItem::quit` → `terminate:` runs); the Linux no-tray close raises `ExitRequested` twice; `prevent_exit()` is a no-op for `RESTART_EXIT_CODE`. The design below sits on `RunEvent::Exit`, which every gesture reaches. Round 2 verified the mechanism: `App::run`'s `Exit` arm calls our callback BEFORE `cleanup_before_exit` (`tauri-2.11.5/src/app.rs:1430-1436`); the async runtime is a never-dropped multi-thread tokio (`async_runtime.rs:29,222-229`); `block_on` from the main thread cannot panic or deadlock here (`main.rs` is a plain `fn main`, no `enter()` guard on the main thread); nothing in the awaited path touches the event loop (every await is tokio IO/time; no mutex guard is held across an await; `CommandChild::kill` is a direct syscall).

## Problem

Tray Quit (`src-tauri/src/lib.rs:1402-1404`) and the no-tray window close (`:1561-1578`) call `app.exit(0)`; macOS ⌘Q goes straight to loop destruction. The only exit-time hook is `RunEvent::Exit => kill_sidecar(_app)` (`:1613`), a hard kill. `stop_sidecar_gracefully` (`sidecar.rs:268-304`: POST `/api/shutdown`, `wait_for_port_release`, `kill_sidecar`) is called only by `restart_sidecar` (`:187`) and `perform_install` (`lib.rs:2362`). Quit loses up to 60 s of unsaved edits, the tab set, and leaves the store lock behind. `docs/architecture.md:843` says "Kill sidecar, then exit".

## Fix

**Graceful stop synchronously inside `RunEvent::Exit`, bounded, panic-contained, then the existing hard kill.**

1. **`lib.rs:1613`** → `RunEvent::Exit => shutdown_sidecar_on_exit(_app)`, a new fn in `sidecar.rs`:
   - Set `EXITING: AtomicBool` (one-way; nothing clears it).
   - **Hide every window first** (`for w in app.webview_windows().values() { let _ = w.hide(); }`): `cleanup_before_exit` — which hides windows on Windows — runs AFTER our callback, so without this a tray Quit leaves a live unresponsive window for the whole budget and Windows paints "Not Responding" past `HungAppTimeout`. `hide()` from the main thread is handled inline and works with the loop destroyed.
   - Wrap the body in `std::panic::catch_unwind(AssertUnwindSafe(|| …))`: on macOS this callback runs inside `applicationWillTerminate:` (`tao-0.35.2/src/platform_impl/macos/app_delegate.rs:131-134`), and an unwind across that ObjC frame is abort/UB, not "skips the kill". `stop_sidecar_gracefully` itself calls `handle.state::<SidecarState>()` (`sidecar.rs:273`), which panics if unmanaged — `try_state` on the client alone does not cover it.
   - Client: `app.try_state::<reqwest::Client>()` → clone, else `build_http_client(HTTP_CLIENT_TIMEOUT)` (`sidecar.rs:330-336`, returns `Result`) — on `Err`, log and skip straight to the kill; never `unwrap()` here.
   - `let started = Instant::now(); log::info!("Exit: stopping sidecar gracefully (budget {}s)", EXIT_GRACEFUL_BUDGET_SECS)`.
   - `let outcome = tauri::async_runtime::block_on(tokio::time::timeout(EXIT_GRACEFUL_BUDGET, stop_sidecar_gracefully(app, &client, GRACEFUL_SHUTDOWN_DEADLINE_SECS)))`.
   - **Budget arithmetic that actually holds:** `wait_for_port_release` (`sidecar.rs:605-614`) checks its deadline only at loop top, and its last `check_health` can itself block for the client's 5 s timeout; the POST before it can also take the full 5 s. So the true worst case is `GRACEFUL_SHUTDOWN_DEADLINE_SECS + 2 × HTTP_CLIENT_TIMEOUT` (≈16 s), not 11. `EXIT_GRACEFUL_BUDGET = GRACEFUL_SHUTDOWN_DEADLINE_SECS + 2 * HTTP_CLIENT_TIMEOUT + 1 s`, with a `const` assertion of exactly that sum. On timeout: `log::warn!`.
   - **Witness, in a private submodule or not at all.** After this change `lib.rs` calls `shutdown_sidecar_on_exit`, not `kill_sidecar` (the `use` at `lib.rs:141` goes away; the only `kill_sidecar` callers left are `sidecar.rs:303` and `:544` — `lib.rs:2570`, `sidecar_job.rs:6,33` are comments). A witness struct defined in `sidecar.rs` itself is constructible by `shutdown_sidecar_on_exit`'s own body, so it constrains nothing. Do it this way: `mod graceful { pub(crate) struct GracefulAttempted(()); pub(crate) fn attempt(handle, client, budget) -> (Outcome, GracefulAttempted) { … block_on(timeout(…)) … } }` — the private field makes the token unconstructible outside `graceful`, so an edit that skips `attempt` fails to compile; `kill_sidecar_on_exit(handle, _proof: GracefulAttempted)` is the only kill the exit path can call, and the two internal callers keep a private `kill_sidecar_inner`. **State the limit plainly in the Tests section:** a mutant that calls `attempt` with a zero deadline still gets a token, and nothing in `cargo test` can tell a real graceful attempt from a neutered one — the smoke line's middle grep (`Sidecar exited gracefully after /api/shutdown`, `sidecar.rs:296`) is the sole detector, and it exists only if §1 is run. `#[must_use]` is inert (the token is consumed as an argument); don't describe it as enforcement. Expect non-fatal `dead_code`/unused-import warnings; neither CI nor pre-push runs clippy and there is no `deny(warnings)`.
   - `kill_sidecar` unconditionally, outside `catch_unwind`, even if the body panicked.
   - Final line logs the result, not just "done": `log::info!("Exit: sidecar shutdown complete (elapsed {}ms, timed_out={}, owned_child={})", …)` — so "0 ms, timed_out=false, owned_child=false" is distinguishable from a real flush. A smoke that greps two static strings is defeated by any edit that keeps the strings (#1746).
2. **Respawn race, closed under the lock, not at loop top.** Three producers can spawn during the budget: `restart_sidecar` (`sidecar.rs:159-221`, from `NetworkSettings.svelte:64`), the initial `start_sidecar` retry loop (`:412-550`), the "Retry Server Start" dialog (`lib.rs:1803`). A child spawned after `kill_sidecar` is orphaned on macOS/Linux (Windows: job object at `:482-486`, assigned before the store). Guards:
   - `pub(crate) fn spawn_allowed() -> bool { !EXITING && !SIDECAR_SHUTTING_DOWN }` (two flags, see 4).
   - `restart_sidecar`: the check goes **inside the spawned future (`spawn(async move {` at `:181`), before the `stop_sidecar_gracefully` call at `:187`** — the command body returns immediately, so a check there is passed before the task runs. Log "shutting down" and return from the future.
   - `start_sidecar`: cheap early-out at loop top, AND the load-bearing check **inside the `SidecarState` lock at the store site (`:519-523`; std `Mutex`, no `await` in the block, `child` still owned so `child.kill()` compiles)**: re-read `spawn_allowed()` under the guard; if false, `child.kill()` (not `kill_sidecar`, which would re-take the lock) and leave the loop. **Do not fall through to the terminal `Err` after the loop** (`:551+`): that `Err` reaches `restart_sidecar`'s failure arm (`:190-215` — `report_pending_opens_with(…, true, …)` + `emit("sidecar-restart-failed")`) and the retry dialog at `lib.rs:1803`, i.e. a user-facing rejection while the app is quitting. Return `Ok(())` with a log line when `EXITING` is set (say so in the fn docblock). Why the lock closes the race: the `Exit` path sets `EXITING` before the kill that takes the same lock, so either the kill sees the stored child or the store sees the flag. Residual: a child between `cmd.spawn()` and the lock when the process exits — unavoidable; Windows covered by the job object; note it.
3. **`owns_child` means "we hold a handle", not "we own :3479".** Nothing clears `SidecarState` when the child dies: the drain task's `CommandEvent::Terminated` arm (`:507-511`) sets a local flag only. After a crash the slot holds a dead handle, so `stop_sidecar_gracefully` would POST the hardcoded `SHUTDOWN_URL` at whatever now listens on :3479 (a `tandem start`, a second app-data instance) and shut it down — unreachable from Quit today, reachable after this PR. Fix: **pid-keyed** clear. Capture `let child_pid = child.pid()` before spawning the drain task (`pid(&self)` on a shared ref, `process/mod.rs:84`; `child` is not moved until `:522`, so any point in 471–521 works — `:486` already does this on Windows). The drain task at `:493` is `async move` + `'static` and captures only `rx`/`dead_flag`, so it cannot hold a `State<SidecarState>`: clone the `AppHandle` into it and split the fn — `on_child_terminated_in(state: &SidecarState, pid: u32)` (unit-testable without an app) plus a thin `on_child_terminated(handle: &AppHandle, pid)` wrapper that does `handle.state::<SidecarState>()`. The inner one takes the slot only if `guard.as_ref().map(CommandChild::pid) == Some(pid)`. A bare `take()` would clear a NEWER child's handle: drain tasks are per attempt, never cancelled, and `Terminated` is delivered over a `channel(1)` behind `child.wait()` + a write lock (`tauri-plugin-shell-2.3.5/src/process/mod.rs:320,337-357`), so child A's `Terminated` can land after child B is stored — B orphaned and the next Quit skipping the flush, i.e. #1756 reintroduced. Do NOT call `kill_sidecar` from this arm (same aliasing, with a kill attached). PID reuse inside that window is a theoretical residual; note, don't engineer. `log::info!` both branches of the `owns_child` gate (`:274-278`) with the POST target. `wait_for_port_release` polls `/health` with no identity check (#1812) — out of scope, one comment. The only readers of the slot are `:274`, `:316`, `:519-523`; UI "running" state comes from `SIDECAR_HEALTHY`, so no user-visible change beyond the intended one (and `"Killing sidecar process"` no longer logs at Exit after a crash — the smoke line must tolerate that).
4. **Two flags, two lifetimes.** `SIDECAR_SHUTTING_DOWN` is the updater's: `perform_install` (`lib.rs:2350-2450`) sets it before its `stop_sidecar_gracefully` and clears it on the `Err` arm (`:2433-2448`, app keeps running) via `compare_exchange(true, false)`. `EXITING` is one-way and is what `spawn_allowed` also reads, so an install failing DURING an exit cannot re-permit spawns. On the `Ok` arm the process exits: on Windows `download_and_install` ends in `std::process::exit(0)` (`tauri-plugin-updater-2.10.1/src/updater.rs:865`, reached from `:723`; `lib.rs:2413-2415` is only a comment asserting it) — never reaches `RunEvent::Exit`, so the pre-install stop is the only flush there and stays. On non-Windows `app.restart()` (`:2431`) from an async task → `request_exit(RESTART_EXIT_CODE)` → our `Exit` handler runs with `SIDECAR_SHUTTING_DOWN` set → skip straight to the kill. Correct.
5. `SHUTDOWN_URL`/`HEALTH_URL` hardcoded :3479 (`sidecar.rs:82,76`): out of scope (#1825); one comment at the call site: with a non-default `TANDEM_MCP_PORT` the POST misses after its own 5 s client timeout, `posted == false` skips the port wait, and the kill follows — not "immediate".
6. The route accepts an absent Origin by design and the shell's reqwest call passes every gate (`authMiddleware` loopback short-circuit, `enforceLoopbackMutation`, Host literal `127.0.0.1:3479`, the handler's gates) — source-confirmed; do not turn `SHUTDOWN_URL` into `localhost`. 202 `alreadyInProgress: true` is `is_success()`; no change.
7. No-tray `CloseRequested` branch: leave as is (harmless double `ExitRequested` under this design).

**`docs/architecture.md:843`** is a two-cell row in the tray-menu table (`:838-843`), not prose: shorten the cell to `| Quit | Graceful sidecar stop, then hard kill (see Shutdown below) |` and add a `### Shutdown` subsection next to `### Auto-Updater` (`:847`): "On `RunEvent::Exit`: hide windows, graceful stop (POST /api/shutdown, port-release wait, bounded ≈17 s), then hard kill as the fallback. Covers tray Quit, macOS ⌘Q, window close without a tray." Then what it does NOT cover: macOS logout/restart (the system's own quit timeout can force-terminate first); Windows logoff/shutdown (`WM_ENDSESSION` → `loop_destroyed` inside the wndproc, so the flush is best-effort and likely truncated near `HungAppTimeout` ≈5 s); forced termination.

## Review corrections (round 4 — on the shipped PR)

Five reviewers on PR #1847 converged on findings that contradict two claims made
above; the code and the docs are now the corrected record, and this section is
the trace.

- **"An edit that skips `attempt` fails to compile" (round 3, above) is false.**
  `kill_sidecar_inner` is private to the same module and callable directly, so an
  edit that swaps the exit path onto it compiles and leaves `kill_sidecar_on_exit`
  as a `dead_code` warning. The witness constrains an author who keeps calling
  `kill_sidecar_on_exit`; that is all. See the doc comment on that function.
- **"The smoke line's middle grep is the sole detector of a neutered attempt" is
  also false, twice over.** It was never reachable: that line is a `log::info!`
  and the release log floor is `Warn`, so it does not exist in `tandem.log` on the
  build the checklist is run against. And a neutered attempt is now unit-testable
  — `graceful::attempt` is `AppHandle`-free and
  `graceful_attempt_posts_and_waits_for_the_reply` drives a real POST against a
  loopback listener. The exit path now emits ONE `warn!` verdict line, which is
  what the checklist greps.
- **`start_sidecar` must not report a decline as `Ok(())`** — `SpawnOutcome`.
  `spawn_allowed()` is false for a whole update download, so "Retry Server Start"
  logged success and ran an update check on the dialog whose job is to say the
  server did not start, and `restart_sidecar` left a dead Restart button.
- **`SIDECAR_SHUTTING_DOWN` needed unwind protection** — it spans
  `download_and_install(..).await` and was cleared only on the `Err` arm.
  `ShuttingDownGuard` (and `RestartGate`, the same hazard on the restart gate).
- **The spawn comment claiming `tauri-plugin-shell` does not inherit the parent
  env was wrong.** Verified against `tauri-plugin-shell-2.3.5/src/process/mod.rs`:
  `Command::new` (`:162-179`) never clears, `env_clear` (`:205-208`) runs only on
  request, `spawn` (`:305-320`) hands a plain `std::process::Command` to
  `SharedChild::spawn`. The port and bind-host env are now pinned at the spawn.

Round 1: `RunEvent::Exit` instead of `ExitRequested` (⌘Q, Linux no-tray); no `perform_install` preset that latches the fix off after a failed update; `try_state`; respawn guard; clear `SidecarState` on `Terminated`; two log lines.
