# G10 — #1624 `tandem_checkInbox`'s `activity` drops `selection.timestamp`, so an old selection reads as current

Branch `fix/awareness-hygiene-selection-staleness-and-one-inbox-poll-context-1702`. Closes #1624 (both proposed items: surface the timestamp; document the field on the tool description, the output schema, `docs/mcp-tools.md` and the shipped skill). The behaviour defect found while measuring the timestamp is filed as **#1991** and is not fixed here (see Not in scope). Not a v1-review ledger row — filed 2026-08-26 from the same live investigation as #1621/#1622/#1623 (`B-1622.md:3`); sweep wave 8 group G10. Probe: the issue's own payload (`cursor` ~450 chars from `selectedText`) reproduced as a vitest fixture, plus a scratch client probe (below) whose cases become test 4. Implemented after #1702.

## Problem

`tandem_checkInbox` (`src/server/mcp/awareness.ts`, handler `:416-576`) reads `store.getUserAwareness()` (`document-store.ts:370-384`), slices `selectedText` from `Y_MAP_SELECTION`'s stored flat `from`/`to` (`:511-514`), and emits `activity: { isTyping, cursor, lastEdit, selectedText }` (`:567-572`). `selection.timestamp` is typed on the record and dropped. `cursor`/`lastEdit` come from `Y_MAP_ACTIVITY`, a different record with a different write trigger, so the two halves of one object have independent ages and only one is labelled.

### The record's lifetime — measured, not repeated

Client writer: `src/client/editor/extensions/awareness.ts`, Plugin 2 `update()`, `:188-273`. Measured on this branch (2026-09-15) with a scratch vitest probe: happy-dom, fake timers, the `boundEditor` setup from `tests/client/activity-cursor-flat.test.ts`, remote changes applied with `Y.applyUpdate` from a second `Y.Doc` so they go through y-tiptap's `_typeChanged`. The probe was deleted; each row below becomes a case in test 4.

| Event | What `Y_MAP_SELECTION` does | Evidence |
|---|---|---|
| Non-empty selection | written after a **150 ms** debounce (`:217-226`), not the 1 s dwell | probe: select at t=1 000 000 → `timestamp: 1000150` |
| Selection collapses (click, arrow, typing) | `{from, to: from}` written **immediately** (`:194-205`) → `selectedText: null` | code; test 4(b) |
| **Remote edit that moves the selection** (e.g. Claude's `tandem_edit` above it) | **re-written with a fresh `Date.now()`** | probe: clock +20 min, remote insert of `XX` before it → `from` 31→33, `to` 36→38, `timestamp` 1000150→2200150 |
| Remote edit that does not move it (after the selection) | unchanged | probe: `timestamp` stayed `2200150` |
| Remote deletion spanning the selection | collapsed write, immediate → cleared | probe: `{from:29, to:29, timestamp:5800000}` |
| Editor blur (focus moves to chat) | no write | probe: `commands.blur()` left the record unchanged |
| App-made selections: clicking an annotation card (`src/client/panels/useAnnotationReview.svelte.ts:811`, `scrollToAnnotation`) or a chat anchor (`src/client/panels/ChatPanel.svelte:199`, `scrollToAnchor`) | a non-empty `setTextSelection` over that range, so the same 150 ms write | code read (same `update()` path); not probed |

Why the re-stamp happens: y-tiptap rebuilds the document on every remote Y change and calls `restoreRelativeSelection` with no focus check, then dispatches. When the restored absolute positions differ, `!state.selection.eq(prevState.selection)` is true, and Plugin 2 has no `ySyncPluginKey` filter (Plugin 1's decoration `apply` at `~:133` is the only one in the file). The same probe showed `Y_MAP_ACTIVITY` re-written as `{isTyping: true, lastEdit: 2200200}` by that remote edit, which is **#1918** (OPEN). #1918's proposed fix covers only the activity branch, so the selection branch was tracked nowhere; it is now **#1991**.

Server side, the record is cleared only by `clearDocMaps` (`documents/populate.ts:316`, from `evictPartialDocState` and `clearAndReload`) and the watcher reload (`documents/watcher.ts:166-167`).

**What is deliberately NOT claimed.** Tab switches: `src/client/App.svelte` wraps the editor in `{#key activeTab.id}` (`:2876`, `:2974`, `:3019`, `:3038`), so the editor is destroyed on leave and rebuilt on return. In the probe, a fresh editor bound to the same already-populated `Y.Doc` wrote nothing, but the real remount binds through the Hocuspocus provider's first sync, which the probe does not reproduce. Disconnect and reload are likewise unprobed. No documentation surface says anything about tab switch, reload or disconnect.

So the issue's two lifetime claims are both wrong: the field is not dwell-gated ("last dwelled selection", #1624's proposed wording, would document a gate it does not have), and it does not persist until the next selection (it clears on collapse). It is also not always a selection the user made directly, and its timestamp is not when it was made. In the issue's payload the stale half is as likely `cursor`: it is written only when the document changes (`:232-272`; `activity-cursor-flat.test.ts` (5b)).

## Fix

Server and docs only; `src/client/**` is not changed (see Not in scope).

1. `awareness.ts` handler, beside `selectedText`: `const selectionAt = hasSelection && typeof selection!.timestamp === "number" ? selection!.timestamp : null;` and `activity: { isTyping, cursor, lastEdit, selectedText, selectionAt }`. Null exactly when `selectedText` is null — a collapsed record's timestamp is a caret move, not a selection's. The `typeof` guard is because the MCP SDK validates structured output against the schema and fails the **whole** response on a mismatch (docblock on `InboxUserAction`); an `undefined` would take the inbox down, not just the field.
2. `src/server/mcp/output-schemas.ts` `checkInboxOutputShape.activity` (`selectedText` at `:308`):
   - `selectedText: z.string().nullable().describe("The most recent non-empty selection in the user's editor for this document, including one the editor makes when the user clicks an annotation card or chat anchor, sliced at poll time from its stored flat offsets (≤100 chars). Cleared when the selection collapses (a click, arrow key or typing, or a remote edit that deletes the selected text); not cleared when focus leaves the editor, so it is not necessarily what the user is looking at now.")`
   - `selectionAt: z.number().nullable().describe("Epoch ms (browser clock) when the editor last wrote that selection record; null when selectedText is null. Any document change that moves the selection re-stamps it, including your own edits (#1991), so a recent value does not prove the user just selected this text; an old value does prove it is old.")`
   No comparison with `lastEdit` is offered: the probe shows a remote edit refreshes both (#1918). Additive; no exact-shape pin on `activity` exists (`mcp-output-schemas.test.ts`, `mcp-tool-integration.test.ts`, `wake-url-surfacing.test.ts` grepped).
3. Tool descriptions:
   - `tandem_checkInbox` (`:406`) gains: "`activity.selectedText` is the most recent non-empty editor selection, not necessarily a current one. `activity.selectionAt` is when the editor last wrote it; any document change that moves the selection re-stamps it, including your own edits, so a recent value does not prove a recent selection."
   - `tandem_getActivity` (`:353-354`) "use tandem_checkInbox's `activity.selectedText` for what the user has selected" → "use tandem_checkInbox's `activity.selectedText` for the most recent selection (see `activity.selectionAt` for when it was last written)".
   No test pins either description string (grepped `tests/` on `4f112aa4`); re-grep at implement time.
4. `docs/mcp-tools.md` (`tandem_checkInbox` Returns block ~`:1101`, Notes ~`:1112`; `tandem_getActivity` Notes ~`:1071`): add `"selectionAt": null` to the Returns block. Add one Notes bullet after the `activity.cursor` bullet covering the documented rows of the lifetime table:
   - a 150 ms debounce, not the 1 s chat-attachment dwell;
   - includes annotation-card and chat-anchor clicks;
   - cleared on collapse, including a remote deletion of the selected text;
   - not cleared on blur;
   - re-stamped by any edit that moves it, including Claude's (#1991), so a recent `selectionAt` does not prove a recent selection;
   - not comparable with `lastEdit` (#1918).

   At `:1071`, change "For what the user has selected" to "For the most recent selection". `:1051` names the coordinate system only and is unchanged. Re-read the anchors at implement time; they are approximate.
5. `skills/tandem/SKILL.md:84`: "When polling via `tandem_checkInbox`, the current selection shows up under `activity.selectedText`." → "When polling via `tandem_checkInbox`, the most recent non-empty selection shows up under `activity.selectedText` — including one made by clicking an annotation card or chat anchor — and it is not cleared when focus moves to chat, so it is not proof of what the user is looking at now. `activity.selectionAt` is when the editor last wrote it: any edit that moves the selection re-stamps it, including yours, so a recent value does not prove the user just selected it; an old value does prove it is old." Bump frontmatter `version` to the next integer after `origin/master` (21 → 22 at `4f112aa4`; re-check at rebase). In `tests/skill-instruction-contract.test.ts` update both literals in the same commit: `:109` (`/^version:\s*21$/m`) and `:430` (`{ version: "21", bodyHash: "6d0e67ccac3a" }`, with the hash recomputed). Add one sentence for the 21 → 22 bump to the bump-history comment above `:109` (`~:66-108`), noting that the edit is outside the wake section.
