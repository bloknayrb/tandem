# E1 — #1763 Deferred start-at-login launcher can never be released: the Rust caller sends no Origin

Branch `fix/desktop-core-1761`. Closes #1763. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/tauri.md:17`. Probe: the route tests plus the new `reqwest`-builder test below; the end-to-end verification is a smoke line (Bryan).

## Problem

On a login launch the sidecar starts with the launcher deferred and `show_main_window` → `note_user_presence` (`src-tauri/src/lib.rs:733-767`) is the single release point. It calls `request_launcher_start` (`lib.rs:673-712`), a two-hop `reqwest` flow: `GET LAUNCHER_NONCE_URL` then `POST LAUNCHER_START_URL`, both with `Authorization` only.

**Both hops are gated, and the issue names the wrong one as the blocker.** `makeNonceHandler` (`src/server/launcher/api-routes.ts:267`) calls `assertOriginAllowlisted` *first*, so the flow 403s at the **GET**, before the POST is ever built. `assertOriginAllowlisted` (`src/server/integrations/api-routes.ts:361-371`) fails closed on a missing header: `isLocalhostOrigin(undefined)` is false. `note_user_presence` restores the `LAUNCHER_DEFERRED` latch on failure (`lib.rs:759-766`), so it retries on every later presence signal and fails identically every time — the UI shows "deferred" for the life of the session. No client caller of `API_LAUNCHER_START` exists, so nothing else releases it.

## Fix

**Send the Origin from Rust. Do not remove either gate.** The track file offers "drop `assertOriginAllowlisted` and rely on the loopback invariant plus a parsed-JSON-body proof as `rotate-token` does" as the alternative; it is the wrong half here for a reason that only shows up once you notice the nonce route is the blocker: **`GET /api/launcher/nonce` is a GET**, so `enforceLoopbackMutation` (non-GET only, CLAUDE.md Security) does not cover it, and `assertOriginAllowlisted` is its *only* origin-level control. Dropping it would hand a single-use nonce — the CSRF token that also gates `relaunch` and `start-fresh` — to any caller that can reach the port. The CLAUDE.md precedent for `open` and `rotate-token` is a rule about **not adding** the gate to routes that never had it; it is not a licence to remove one from a route that spawns processes.

- `src-tauri/src/lib.rs`: add `const LOOPBACK_ORIGIN: &str = "http://127.0.0.1:3479";` beside the existing URL constants at `:149-156`.
- **Replace the `with_auth` closure inside `request_launcher_start` (`lib.rs:677-681`) with a named module-level function**, so the header application has a name a test can call:
  `fn launcher_request(req: reqwest::RequestBuilder, auth_token: Option<&str>) -> reqwest::RequestBuilder` — applies `Origin: LOOPBACK_ORIGIN` unconditionally and `Authorization: Bearer …` when a token is present. Both hops (`client.get(LAUNCHER_NONCE_URL)` and `client.post(LAUNCHER_START_URL).json(&body)`) go through it, exactly as they go through the closure today. **The named function is load-bearing, not tidiness**: a closure inside an `async fn` has no test seam, which is why round 1 found the fix unpinned in both languages.
- **Why this value and not `tauri.localhost`:** `LOCALHOST_ORIGIN_RE` (`src/server/mcp/api-routes.ts:112-114`) accepts `^https?://(127\.0\.0\.1|tauri\.localhost)(:\d+)?$`, so both pass. `http://127.0.0.1:3479` is the *actual* origin of the URL being requested, making the header a same-origin declaration rather than a claim to be the WebView; it also keeps CLAUDE.md's "use the `TAURI_HOSTNAME` constant, never a raw `"tauri.localhost"`" rule out of play — there is no Rust-side `TAURI_HOSTNAME`, and hand-writing that literal in Rust is exactly what the rule forbids. Deriving the constant from the same `127.0.0.1:3479` the sibling URLs already hardcode also keeps it inside #1825's existing "the constants are hardcoded" debt rather than adding a new spelling.
- **`CLAUDE.md` and `tests/docs/loopback-gate-claims.test.ts` are untouched.** That test scans `src/server/mcp/api-routes.ts` only, the launcher file is a different registrar, and no gate is being added or removed anywhere — so the "no-Origin route list grows by one" line in the track file does **not** apply to this shape. Say that explicitly in the PR body; a reviewer reading the track file will expect a CLAUDE.md edit.
- Not touched: `note_user_presence`'s latch handling, the nonce protocol, `assertLoopbackForMutation` on either route.

## Tests

1. `src-tauri/src/lib.rs`, a new `#[cfg(test)]` case `sends_loopback_origin_on_both_launcher_hops` — **this is the discriminating test and the one round 1 said was missing.** `reqwest::RequestBuilder::build()` produces a `Request` with no network at all, so:
   `let c = reqwest::Client::new();` then for each of `launcher_request(c.get(LAUNCHER_NONCE_URL), Some("t"))` and `launcher_request(c.post(LAUNCHER_START_URL), Some("t"))`, `build().unwrap()` and assert `req.headers().get("origin").unwrap() == LOOPBACK_ORIGIN` **and** that `Authorization` is `Bearer t`. Add the `auth_token: None` arm asserting `Origin` is still present and `Authorization` is absent — the login-launch case where no token was minted is exactly the one that must not lose the header. **What it kills:** deleting the `.header("Origin", …)` line, which every other test in this spec survives.
2. `src-tauri/src/lib.rs`, `mod url_constants_tests` (`:2932`) — extend `supervisor_urls_use_loopback_ip_not_localhost`'s sibling set with a test asserting `LAUNCHER_NONCE_URL.starts_with(LOOPBACK_ORIGIN)` and `LAUNCHER_START_URL.starts_with(LOOPBACK_ORIGIN)`. **What it kills:** a later port change to one constant that silently turns the Origin header into a cross-origin claim the server then 403s — the current failure, re-created with no new symptom. It does **not** pin that the header is emitted; test 1 is what does that.
3. `tests/server/launcher/api-routes.test.ts` — the file already drives a real express app with an `Origin` header (`:105`, `:864-873`). Add, in the same describes: `GET /api/launcher/nonce` **and** `POST /api/launcher/start` each succeed past the origin gate with `Origin: http://127.0.0.1:3479`. **What they kill:** a fix that sends `Origin: http://localhost:3479` (bare `localhost` is rejected by `LOCALHOST_ORIGIN_RE` — the #477 PR 2 narrowing) or an origin without the port. These are server-side accept cases and pass with or without the Rust change; they are the value pin, not the fix pin.
4. Same file — add a **genuinely header-less** request case for `GET /api/launcher/nonce` (no `Origin` key at all) asserting 403. The existing case at `:204-212` is named "rejects missing Origin" but actually sends `Origin: http://attacker.example`, so it exercises the *bad-origin* branch. The Rust failure mode is `isLocalhostOrigin(undefined)`, and only the header-less case reaches it. That case plus test 3's accept case is the discriminating pair on the server side; keep the attacker-origin case too.
   - **The existing helper cannot express it, so extend the helper first.** `tests/server/launcher/api-routes.test.ts:104-107` builds `headers` as `{ Origin: \`http://${TAURI_HOSTNAME}\`, …(extraHeaders ?? {}) }` — the Origin is always injected and `extraHeaders` is `Record<string,string>`, so no value removes the key. Add an explicit `omitOrigin?: true` option to `request()` that **deletes** the key. Do not reach for the obvious workaround: `Origin: ""` still makes `typeof req.headers.origin === "string"` at `src/server/integrations/api-routes.ts:362`, i.e. it exercises `isLocalhostOrigin("")` — a different branch from the `isLocalhostOrigin(undefined)` the Rust caller actually hits, which is the whole point of the case. The test asserts the 403 **and** that the gate observed `req.headers.origin === undefined` (a spy or a probe route on the same app), so the header-less shape is pinned rather than assumed.
