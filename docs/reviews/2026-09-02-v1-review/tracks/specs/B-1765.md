# B — #1765 A cross-block `tandem_edit` deletes the tail element and every anchor in it

Branch `fix/annotation-anchors-1764`. Closes #1765. Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:20`. Probe: `experiments/e5-merge.ts`, `experiments/e5b.ts` (the annotation on the last word of P2 reads `""` or `"ilon zeta"`; the same-block and third-paragraph controls stay right).

## Problem

`tandem_edit`'s cross-element branch (`src/server/mcp/document.ts`, the `else` after the nested-block refusal) merges the tail block into the start block with `mergeInlineTail` — which **clones** the tail's `Y.XmlText` children onto the start element — and then `fragment.delete(startIndex + 1, 1)` removes the emptied original. Yjs cannot move items, so every RelativePosition anchored in that element is dead the instant the delete lands, including annotations that sit entirely **after** the edited range and were never touched by it.

The next `refreshRange` then takes the dead-relRange arm and re-anchors from the annotation's **pre-edit** flat offsets in a document whose length has changed, reports `repaired`, and nothing warns. Measured: the annotation ends up covering `""` or unrelated text, status `pending`. Same-block edits and annotations in an untouched third paragraph are fine.

#1764's fix stops that from being persisted as a confident anchor (the record goes `degraded` instead), which makes the loss legible but does not prevent it. This spec prevents it.

## Fix

The cross-block edit is a **pure flat-text replacement**: `[from, to)` becomes `newText`. For any annotation whose live range does not intersect `[from, to)`, the post-edit offsets are exact arithmetic — identity below `from`, `+ (newText.length - (to - from))` at or above `to`. Re-anchor exactly those, in the branch that breaks them.

- **`src/server/positions.ts`** — one exported pure helper, so the arithmetic is unit-testable away from Yjs:
  `export function remapRangeAcrossReplacement(range: DocumentRange, from: FlatOffset, to: FlatOffset, newLength: number): DocumentRange | null` — returns the shifted range when `range.to <= from || range.from >= to`, and **`null` when the range intersects the replacement**. Deliberately refusing the intersecting case is the point: a partially-overwritten annotation has no arithmetically correct destination, and clamping both ends to `from` would invent one.
- **`src/server/mcp/document.ts`**, cross-element branch only (the same-block and nested-refusal branches are untouched):
  - **Before** the `withMcp` edit transaction — after every rejection, so nothing runs on a doc that will not be edited — capture the live ranges: `collectAnnotations(r.doc.getMap(Y_MAP_ANNOTATIONS), docHash(r.filePath))`, and for each record `refreshRange(ann, r.doc)` **without a map** (read-only; relRange first, flat fallback, exactly what every other reader resolves) into `{id, range}`. Skip `kind === "failed"`.
  - **After** the edit transaction, in its own `withMcp` — for the same reason `stampClaudeRange` runs in a second transaction: `anchoredRange` must read post-edit state. For each captured entry whose relRange no longer resolves (`relPosToFlatOffset` returns null for either end), compute `remapRangeAcrossReplacement(range, from, to, newText.length)`; on `null`, skip. On a range, call `anchoredRange(r.doc, next.from, next.to)` with **default options** and, when `ok && fullyAnchored`, `map.set(id, {...ann, range: anchored.range, relRange: anchored.relRange})`.
  - **No `surrogates: "ignore"`.** CLAUDE.md Critical Rule 4 enumerates exactly four ignore callers (two of which share one binding); this must not become a fifth. On a rejection — reachable only when `newText` ends mid-pair and an annotation starts exactly at `to` — log through `describeRangeFailure` and leave the record alone; #1764's guard then reports it `degraded` rather than mispinned.
  - **No `allowEmpty`.** The non-intersecting subset maps a non-empty range to a non-empty range by construction.
  - **Critical Rules that bite:** Rule 1 — `Y_MAP_ANNOTATIONS` from `src/shared/constants.js` (`document.ts` already imports from that module; add the name to the existing import, never a literal `"annotations"`). Rule 2 — the write is inside `withMcp`, the same helper `refreshAllRanges` uses; `withInternal`/`withFileSync` are wrong here (both are in `DURABLE_SKIP`, so the re-anchor would never reach the JSON envelope).
  - The `mergeInlineTail` clone itself is unchanged. Moving `Y.XmlText` content is not something Yjs offers, and re-anchoring around the delete is the route the issue names.

## Tests

1. `tests/server/positions.test.ts` — `remapRangeAcrossReplacement` table: entirely before (identity); entirely after, growing and shrinking edit (`+delta`); touching at `to` exactly (shifted, not refused); touching at `from` exactly (identity); overlapping the head, the tail, and fully contained (all `null`). Kills an off-by-one on the half-open boundaries and a version that clamps instead of refusing.
2. `tests/server/document-edit.test.ts` — the `e5-merge.ts` fixture as a real spec: `"Alpha beta gamma\n\nDelta epsilon zeta\n"`, an annotation on `"zeta"`, `tandem_edit(6, 23, "XX")` across the paragraph boundary. After the edit the annotation's refreshed range must cover exactly `"zeta"` in the new flat text, and `refreshRange` must report `ok`/`updated` — **not** `repaired`, and not `""`. This is the issue's headline and the test that kills a fix which only re-anchors annotations inside the deleted element.
3. Same file — the `e5b.ts` second shape (annotation **spanning** the join, partially deleted): it is not re-anchored, and it comes back `degraded` rather than silently repaired onto surviving text. Pins that the intersecting case refuses rather than inventing a destination.
4. Same file — the two controls from the experiment stay green: a same-block `tandem_edit` and an annotation in an untouched third paragraph both still resolve to their original text. Kills a remap that runs on every branch or shifts ranges it should not.
5. Same file — a cross-block edit on a document with **zero** annotations performs no `map.set` (spy on the annotation map) and the edit response is unchanged. Kills a version that writes an empty record or costs a walk on every edit.

## Done when

`e5-merge.ts` and `e5b.ts` show the annotation intact after the edit; the four specs above pass; typecheck + suite green.

## Assumptions

- **Only the cross-element branch gets the remap.** The same-block branch does not destroy elements and its anchors already move correctly; adding the pass there would rewrite records for no reason.
- **Annotations intersecting the replaced span are not relocated.** The issue's second measured shape is one of these; leaving it `degraded` (#1764) is honest, and any placement would be a guess.
- **Fully-anchored only.** If `anchoredRange` comes back `fullyAnchored: false`, the record is left alone rather than written with a range and no relRange.

## Not in scope

`tandem_editList`'s documented "no move op" anchor loss (a different mechanism, called out in its own tool description). `mergeInlineTail`'s clone strategy in `src/server/mcp/document-model.ts`. #1632's UI gate on lost targets, which is downstream and is a DECIDE issue.
