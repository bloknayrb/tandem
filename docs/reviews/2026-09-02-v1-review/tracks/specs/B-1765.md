# B — #1765 A cross-block `tandem_edit` deletes the tail element and every anchor in it

Branch `fix/annotation-anchors-1764`. Closes #1765. Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:20`. Measurement: `experiments/e5-merge.ts`, `experiments/e5b.ts`.

## Problem

`tandem_edit`'s cross-element branch (`src/server/mcp/document.ts`, the `else` after the nested-block refusal) merges the tail block into the start block with `mergeInlineTail` — which **clones** the tail's `Y.XmlText` children onto the start element — then `fragment.delete(startIndex + 1, 1)` removes the emptied original. Yjs cannot move items, so every RelativePosition anchored in that element dies the instant the delete lands, including annotations entirely **after** the edited range.

The next `refreshRange` takes the dead-relRange arm, re-anchors from the **pre-edit** flat offsets in a document whose length changed, reports `repaired`, and nothing warns. Measured: the annotation covers `""` or unrelated text. Same-block edits and annotations in an untouched third paragraph are fine.

#1764 makes that loss legible (`degraded` instead of a confident mint); it does not prevent it. This spec prevents it.

## Fix

The cross-block edit is a flat-text replacement — `[from, to)` becomes `newText`. For an annotation whose live range does not intersect `[from, to)` the post-edit offsets are exact arithmetic: identity below `from`, `+ (newText.length - (to - from))` at or above `to`. Re-anchor exactly those, in the branch that breaks them.

**The arithmetic holds on its own, including when the edit absorbs a heading.** Every character the branch removes outside `newText` lies *inside* `[from, to)`: an absorbed heading's prefix starts at that element's `blockStart`, which is strictly greater than `from` and less than `to` (a `to` inside a prefix is already refused by the endpoint arm, `shared/positions/ydoc.ts:344-347`), and the `endIndex - startIndex` separators that disappear are exactly the ones the span crosses. Worked: `"Para one\n## Head\nTail"` (21 units), `tandem_edit(4, 13, "X")` ⇒ `"ParaXead\nTail"` (13), delta −8 = `1 - 9`.

- **`src/server/positions.ts`** — one exported pure helper, unit-testable away from Yjs:
  `export function remapRangeAcrossReplacement(range: DocumentRange, from: FlatOffset, to: FlatOffset, newLength: number): DocumentRange | null` — the shifted range when `range.to <= from || range.from >= to`, and **`null` when the range intersects the replacement**. Refusing the intersecting case is the point: a partially overwritten annotation has no correct destination, and clamping both ends to `from` would invent one.
- **`src/server/mcp/document.ts`**, cross-element branch only (same-block and nested-refusal branches untouched):
  - **Before** the `withMcp` edit transaction — after every rejection, so nothing runs on a doc that will not be edited — capture live ranges from `collectAnnotations(r.doc.getMap(Y_MAP_ANNOTATIONS), docHash(r.filePath))`. For each record resolve **both ends with `relPosToFlatOffset`** and keep `{id, ann, range: {from, to}}` only when the record has a `relRange` and both ends resolve. **No `refreshRange` call and therefore no flat-text walk in this loop** — a live relRange is the only pre-edit position this pass can trust, and a record without one is not remappable. Skip a resolved range that has **collapsed** (`from === to` while `ann.range.from !== ann.range.to`): that is #1764's spurious-collapse shape, and remapping it would re-mint the confident anchor #1764 exists to refuse.
  - **After** the edit transaction, in its own `withMcp` (as `stampClaudeRange` does — `anchoredRange` must read post-edit state): the entries whose anchor no longer resolves (`relPosToFlatOffset` now null for either end) are the population. Compute the set first and **return before any text materialisation when it is empty**; otherwise hoist `const postText = extractText(r.doc)` once above the loop (the pass writes only annotation records, so the text is identical on every iteration). For each entry, `remapRangeAcrossReplacement(range, from, to, newText.length)`; on `null`, skip. On a range:
    1. `anchoredRange(r.doc, next.from, next.to, undefined, { allowEmpty: true })`. **`rejectHeadingOverlap` is deliberately omitted** — this relocates an existing annotation rather than creating one, and refusing would delete from the record set exactly the annotations the destroyed element held; the precedent is the watcher's relocation anchor (`documents/watcher.ts:305-310`).
    2. **verify the destination before writing:** `if (snapshotContradicts(ann, postText.slice(next.from, next.to))) continue;` (`src/shared/snapshot.ts`, which handles a truncated snapshot by prefix and a snapshot-less record by returning `false`). This is the arithmetic's fail-safe: a violated assumption leaves the record for #1764 to report `degraded` rather than pinning it to a confident wrong anchor. Test 6 is its pin.
    3. only then, when `ok && fullyAnchored`, `map.set(id, {...ann, range: anchored.range, relRange: anchored.relRange})`.
  - **`allowEmpty: true`** — point annotations are a real population here (Word comment import emits them, `file-io/docx-comments.ts:606,621`), and `remapRangeAcrossReplacement` is identity-or-shift so it preserves `to - from`: a non-empty range can never come out empty and the flag widens nothing. Without it `checkAgainstText` (`positions.ts:259`) silently drops exactly the imported comments this fix exists to save.
  - **No `surrogates: "ignore"`** — Critical Rule 4 enumerates four callers and this must not be a fifth. The default `"reject"` therefore also skips records whose *stored* offsets already sit mid-pair. Neither case is a regression (today both are `repaired` onto a stale offset); log through `describeRangeFailure` and leave the record for #1764 to report.
  - **ADR-027:** anchor maintenance is not an edit, resolve, remove or reply, so none of the four write guards applies and note records are re-anchored with the rest — the precedent is stated in the same terms at `documents/annotation-wiring.ts:41-48`. `MCP_ORIGIN` is in `CHANNEL_SKIP`, so no channel event fires.
  - **Critical Rules:** Rule 1 — `Y_MAP_ANNOTATIONS` from `shared/constants.js`, never a literal. Rule 2 — the write is inside `withMcp` (`withInternal`/`withFileSync` are in `DURABLE_SKIP` and would never reach the JSON envelope). The `collectAnnotations` import makes `document.ts` ↔ `annotations.ts` circular and that is safe because it is a hoisted `export function` declaration (`annotations.ts:209`), initialised before either module body runs.
  - `mergeInlineTail`'s clone is unchanged — Yjs offers no move for `Y.XmlText`, and re-anchoring around the delete is the route the issue names.

## Tests

**Home:** every spec naming an annotation outcome is driven through the **registered** `tandem_edit` in `tests/server/mcp-tool-integration.test.ts` (`range-bounds-validation.test.ts` is the acceptable alternative). **Not `tests/server/document-edit.test.ts`** — that file is a local `applyEdit` mirror (`:20-25`) that never calls `validateRange`, `refreshRange` or `anchoredRange` and never touches `Y_MAP_ANNOTATIONS`, so a spec added there passes with none of this fix existing. A mirror-only assertion does not count.

1. `tests/server/positions.test.ts` — `remapRangeAcrossReplacement` table: entirely before (identity); entirely after, growing and shrinking (`+delta`); touching at `to` exactly (shifted); touching at `from` exactly (identity); a point range after `to` (shifted, still a point); overlapping the head, the tail, and fully contained (all `null`). Kills an off-by-one on the half-open boundaries and a version that clamps instead of refusing.
2. `tests/server/mcp-tool-integration.test.ts` — the issue's headline as the `e5-merge.ts` fixture: `"Alpha beta gamma\n\nDelta epsilon zeta\n"`, an annotation on `"zeta"`, `tandem_edit(6, 23, "XX")` across the boundary. Afterwards the annotation covers exactly `"zeta"` and `refreshRange` reports `ok`/`updated` — not `repaired`, not `""`.
3. Same file — a **point annotation** in the tail element after `to` is remapped and resolves at the right offset. Kills the missing `allowEmpty`.
4. Same file — the `e5b.ts` shape (an annotation **spanning** the join, partially deleted) is not re-anchored and comes back `degraded`. Pins that the intersecting case refuses rather than inventing a destination.
5. Same file — the pass runs only where it should: (a) a **same-block** `tandem_edit` on a document with annotations performs no `map.set` at all; (b) a cross-block edit whose annotations all lie strictly inside `[from, to)` performs none, because every one refuses. Both are observable, unlike a zero-annotation fixture. Plus the two experiment controls: a same-block edit and an annotation in an untouched third paragraph still resolve to their original text.
6. Same file — **the destination check**, which nothing else reaches (tests 2/3 have matching destinations, 4 is refused by `remapRangeAcrossReplacement`, 5 never enters the branch), so without it an implementation that omits step 2 entirely is green. An annotation captured with a live `relRange` (dead after the cross-block delete) whose stored `textSnapshot` does **not** match the text at the **remapped** destination — arrange it by giving the record a snapshot from before an earlier in-range change. Assert **no `map.set`** for that record and that a subsequent `refreshRange` reports `degraded`.

## Done when

The six specs pass, the tool-driven ones in a file that drives the registered `tandem_edit`; `npm run typecheck` + `npm run typecheck:tests` + suite green.

**`e5-merge.ts` / `e5b.ts` are deliberately not a criterion.** Both replicate the cross-element branch directly (`e5-merge.ts:12,28,46`) and never invoke the tool, so the new post-edit pass does not run in them and they will keep printing the pre-fix output. They stay as the record of the measurement that produced this issue.

## Assumptions

- **Only the cross-element branch gets the remap.** The same-block branch destroys no elements and its anchors already move correctly.
- **Annotations intersecting the replaced span are not relocated** — the issue's second measured shape; leaving it `degraded` is honest, and any placement would be a guess.
- **A collapsed capture is not a destination.** Skipping it is what stops this pass becoming a fourth site that mints a confident anchor from an untrusted range.
- **Fully-anchored only.** If `anchoredRange` returns `fullyAnchored: false`, the record is left alone rather than written with a range and no relRange.
- **The destination check is a fail-safe, not the mechanism** — with a correct remap it never fires, which is exactly why test 6 exists.

## Not in scope

`tandem_editList`'s documented "no move op" anchor loss (a different mechanism). `mergeInlineTail`'s clone strategy. #1632's UI gate on lost targets, which is a DECIDE issue. #1766's heading refusal — a separate spec on the same branch; this pass's arithmetic does not depend on it.
