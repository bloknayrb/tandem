# B — #1765 A cross-block `tandem_edit` deletes the tail element and every anchor in it

Branch `fix/annotation-anchors-1764`. Closes #1765. Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:20`. Probe: `experiments/e5-merge.ts`, `experiments/e5b.ts` (the annotation on the last word of P2 reads `""` or `"ilon zeta"`; the same-block and third-paragraph controls stay right).

## Problem

`tandem_edit`'s cross-element branch (`src/server/mcp/document.ts`, the `else` after the nested-block refusal) merges the tail block into the start block with `mergeInlineTail` — which **clones** the tail's `Y.XmlText` children onto the start element — and then `fragment.delete(startIndex + 1, 1)` removes the emptied original. Yjs cannot move items, so every RelativePosition anchored in that element is dead the instant the delete lands, including annotations that sit entirely **after** the edited range and were never touched by it.

The next `refreshRange` then takes the dead-relRange arm and re-anchors from the annotation's **pre-edit** flat offsets in a document whose length has changed, reports `repaired`, and nothing warns. Measured: the annotation ends up covering `""` or unrelated text, status `pending`. Same-block edits and annotations in an untouched third paragraph are fine.

#1764's fix stops that from being persisted as a confident anchor (the record goes `degraded` instead), which makes the loss legible but does not prevent it. This spec prevents it.

## Fix

The cross-block edit is a flat-text replacement — `[from, to)` becomes `newText` — **given #1766's interior heading check**. For any annotation whose live range does not intersect `[from, to)`, the post-edit offsets are then exact arithmetic: identity below `from`, `+ (newText.length - (to - from))` at or above `to`. Re-anchor exactly those, in the branch that breaks them.

**The arithmetic depends on #1766 and the dependency is load-bearing.** Flat text prepends a `"## "` per top-level heading (`getHeadingPrefixLength`, `src/shared/positions/ydoc.ts:168-174`), so a cross-block range that *absorbs* a heading removes prefix characters that were never inside `[from, to)`. That is #1766's own headline: `tandem_edit(4, 13, "X")` on `"Para one\n## Head\nTail"` yields `"ParaXead\nTail"`, whose true flat delta is `newText.length - (to - from) - 3`, three units off what `remapRangeAcrossReplacement` computes. Today that shape is *accepted*, because `rejectHeadingOverlap` is endpoint-only. #1766 adds the interior term at `src/server/mcp/document.ts:757` and refuses it, which is what makes the pure-replacement premise true. The two land on the same branch; the group's implementation order puts #1766 last, so **the merged state is the contract, and test 6 below pins it** — a cross-block edit absorbing a heading must be refused, so the remap provably never sees that shape.

- **`src/server/positions.ts`** — one exported pure helper, so the arithmetic is unit-testable away from Yjs:
  `export function remapRangeAcrossReplacement(range: DocumentRange, from: FlatOffset, to: FlatOffset, newLength: number): DocumentRange | null` — returns the shifted range when `range.to <= from || range.from >= to`, and **`null` when the range intersects the replacement**. Deliberately refusing the intersecting case is the point: a partially-overwritten annotation has no arithmetically correct destination, and clamping both ends to `from` would invent one.
- **`src/server/mcp/document.ts`**, cross-element branch only (the same-block and nested-refusal branches are untouched):
  - **Before** the `withMcp` edit transaction — after every rejection, so nothing runs on a doc that will not be edited — capture the live ranges: `collectAnnotations(r.doc.getMap(Y_MAP_ANNOTATIONS), docHash(r.filePath))`, and for each record `refreshRange(ann, r.doc)` **without a map** (read-only; relRange first, flat fallback, exactly what every other reader resolves) into `{id, ann, range, hadRelRange}`. **Skip `kind === "failed"` and `kind === "degraded"`.** Only `ok` / `updated` / `attached` / `repaired` are trustworthy captures — #1764 has just given `degraded` the meaning "this range is not one the server trusts", and remapping from it would re-mint the confident anchor #1764 exists to refuse, in the same branch.
  - **After** the edit transaction, in its own `withMcp` — for the same reason `stampClaudeRange` runs in a second transaction: `anchoredRange` must read post-edit state. For each captured entry whose anchor no longer resolves — **`ann.relRange` is absent, OR `relPosToFlatOffset` returns null for either end** (a record with no relRange never had a position to lose, and after #1764's strip that is precisely the population this pass exists for) — compute `remapRangeAcrossReplacement(range, from, to, newText.length)`; on `null`, skip. On a range:
    1. call `anchoredRange(r.doc, next.from, next.to, undefined, { allowEmpty: true })`;
    2. **verify the destination before writing.** `if (snapshotContradicts(ann, extractText(r.doc).slice(next.from, next.to))) continue;` — `src/shared/snapshot.ts:158-176`, which already handles a truncated snapshot by prefix and a snapshot-less record by returning `false`. This is the arithmetic's own fail-safe: if any assumption behind the remap is violated the record is left for #1764 to report `degraded` rather than pinned to a confident wrong anchor.
    3. only then, when `ok && fullyAnchored`, `map.set(id, {...ann, range: anchored.range, relRange: anchored.relRange})`.
  - **`allowEmpty: true`.** Point annotations (`from === to`) are a real population on this path — Word comment import emits them (`src/server/file-io/docx-comments.ts:606,621`), `.docx` comment export treats them as legal (`docx-comment-export.ts:380`), and the watcher's relocation anchor carries `allowEmpty` for the same reason (`documents/watcher.ts:301-309`). `remapRangeAcrossReplacement` is identity-or-shift and therefore preserves `to - from`, so a non-empty range can never come out empty and the flag cannot widen anything; without it, `checkAgainstText`'s `if (from === to && !opts?.allowEmpty) return invalid("empty", …)` (`src/server/positions.ts:259`) silently drops exactly the imported Word comments in the destroyed tail element that this fix most exists to save.
  - **No `surrogates: "ignore"`.** CLAUDE.md Critical Rule 4 enumerates exactly four ignore callers (two of which share one binding); this must not become a fifth. Be honest about what the default `"reject"` therefore skips: **not only** the seam case where `newText` ends mid-pair and an annotation starts exactly at `to`, but also any annotation whose *stored* offsets already sit mid-pair — stored offsets are not held to the pair rule (that is why `docx-capture.ts:196-203` and `docx-comments.ts:606-621` pass `"ignore"`), so such a record is refused here too. Neither is a regression (today both are `repaired` onto a stale offset); both are silent, so on a rejection log through `describeRangeFailure` and leave the record alone, and #1764's guard reports it `degraded`.
  - **ADR-027 and notes.** `collectAnnotations` does not filter notes, so this pass will `map.set` note records under `withMcp` and persist the `sanitizeAnnotation`-normalized shape. That is deliberate and has precedent stated in the same terms: `src/server/documents/annotation-wiring.ts:41-48` — anchor maintenance is not an edit, resolve, remove or reply, so none of ADR-027's four write guards (`editPending`, `transitionPending`, `AnnotationLifecycle.remove`, `AnnotationLifecycle.reply`) applies, and `MCP_ORIGIN` is in `CHANNEL_SKIP` so no channel event fires. The guard set is untouched by this spec.
  - **Critical Rules that bite:** Rule 1 — `Y_MAP_ANNOTATIONS` from `src/shared/constants.js` (`document.ts` already imports from that module; add the name to the existing import, never a literal `"annotations"`). Rule 2 — the write is inside `withMcp`, the same helper `refreshAllRanges` uses; `withInternal`/`withFileSync` are wrong here (both are in `DURABLE_SKIP`, so the re-anchor would never reach the JSON envelope).
  - The `mergeInlineTail` clone itself is unchanged. Moving `Y.XmlText` content is not something Yjs offers, and re-anchoring around the delete is the route the issue names.

## Tests

1. `tests/server/positions.test.ts` — `remapRangeAcrossReplacement` table: entirely before (identity); entirely after, growing and shrinking edit (`+delta`); touching at `to` exactly (shifted, not refused); touching at `from` exactly (identity); a **point range** (`from === to`) after `to` (shifted, still a point range); overlapping the head, the tail, and fully contained (all `null`). Kills an off-by-one on the half-open boundaries and a version that clamps instead of refusing.
2. `tests/server/document-edit.test.ts` — the `e5-merge.ts` fixture as a real spec: `"Alpha beta gamma\n\nDelta epsilon zeta\n"`, an annotation on `"zeta"`, `tandem_edit(6, 23, "XX")` across the paragraph boundary. After the edit the annotation's refreshed range must cover exactly `"zeta"` in the new flat text, and `refreshRange` must report `ok`/`updated` — **not** `repaired`, and not `""`. This is the issue's headline and the test that kills a fix which only re-anchors annotations inside the deleted element.
3. Same file — a **point annotation** in the tail element, after `to`: it is remapped and still resolves at the right offset. Kills the missing `allowEmpty`, which drops exactly the imported-Word-comment population.
4. Same file — the `e5b.ts` second shape (annotation **spanning** the join, partially deleted): it is not re-anchored, and it comes back `degraded` rather than silently repaired onto surviving text. Pins that the intersecting case refuses rather than inventing a destination.
5. Same file — a **`degraded` record is not re-anchored**: an annotation in the tail element whose `textSnapshot` no longer matches its stored offsets (so #1764's capture reports `degraded`) is left alone by the cross-block edit and still reports `degraded` afterwards. Kills a capture that skips only `failed` and re-mints the anchor #1764 just refused.
6. Same file — a cross-block `tandem_edit` whose range **absorbs a heading** (`"Para one\n## Head\nTail"`, `tandem_edit(4, 13, "X")`) is refused with `HEADING_OVERLAP` rather than reaching the remap. This is the #1766 dependency the arithmetic rests on; without it the remap shifts every annotation past `to` by three units.
7. Same file — the two controls from the experiment stay green: a same-block `tandem_edit` and an annotation in an untouched third paragraph both still resolve to their original text. Kills a remap that runs on every branch or shifts ranges it should not.
8. Same file — the pass runs **only** in the cross-element branch and only on remappable records: (a) a **same-block** `tandem_edit` on a document that has annotations performs no `map.set` at all (spy on the annotation map); (b) a cross-block edit whose annotations all lie strictly inside `[from, to)` performs no `map.set`, because every one of them refuses. Both are observable, unlike a zero-annotation fixture, which cannot distinguish "did not run" from "had nothing to write".

## Done when

`e5-merge.ts` and `e5b.ts` show the annotation intact after the edit; the eight specs above pass; `npm run typecheck` + `npm run typecheck:tests` + suite green.

## Assumptions

- **The remap's arithmetic is valid only under #1766's interior heading check.** Stated in Fix and pinned by test 6. Both land on this branch; a revert of #1766 alone would silently reintroduce a three-unit shift.
- **Only the cross-element branch gets the remap.** The same-block branch does not destroy elements and its anchors already move correctly; adding the pass there would rewrite records for no reason.
- **Annotations intersecting the replaced span are not relocated.** The issue's second measured shape is one of these; leaving it `degraded` (#1764) is honest, and any placement would be a guess.
- **A `degraded` capture is not a destination.** Skipping it is what stops this pass from becoming the fourth site that mints a confident anchor from unverified stored offsets.
- **Fully-anchored only.** If `anchoredRange` comes back `fullyAnchored: false`, the record is left alone rather than written with a range and no relRange.
- **The destination check is a fail-safe, not the mechanism.** With #1766 in place `snapshotContradicts` should never fire here; it exists so that a violated assumption refuses instead of minting.

## Not in scope

`tandem_editList`'s documented "no move op" anchor loss (a different mechanism, called out in its own tool description). `mergeInlineTail`'s clone strategy in `src/server/mcp/document-model.ts`. #1632's UI gate on lost targets, which is downstream and is a DECIDE issue.
