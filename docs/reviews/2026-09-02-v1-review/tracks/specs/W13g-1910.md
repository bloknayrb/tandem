# W13g — #1910 pin `check-token-violation.sh`'s `continueOnBlock: true` in `.claude/settings.json` with a wiring test

Branch `fix/docs-and-test-tooling-drift-2005`. Closes #1910. No track file (non-review issue). No
MCP probe: repo-tooling/CI-config fix, not an MCP surface.

## Problem

`.claude/settings.json`'s `hooks.PostToolUse` entry for `check-token-violation.sh` (around
`:104-107`) carries `"continueOnBlock": true`. This flag has been silently dropped twice by the
harness's own normalization of hook commands to the `"$CLAUDE_PROJECT_DIR/..."` path form:
`0f8f983e` added it, a later harness rewrite dropped it while normalizing paths, `2e5854e9`
restored it, and it was dropped a second time (observed 2026-09-08, left unstaged, never
committed). Both restoring commits are in history (`git log --oneline --all | grep -i
continueOnBlock`). Each drop is silent — nothing fails, no test notices; the only signal is a
stray `M .claude/settings.json` during unrelated work.

**The mechanism, stated as the script itself states it, not as the repo's blanket hook-semantics
line describes it.** `check-token-violation.sh` exits `2` on a violation (`:40`), and its own
header (`:4`) reads: "Exit 2 + continueOnBlock = Claude self-corrects the violation; exit 0 =
clean." `continueOnBlock: true` is what turns that exit-2 into an in-turn self-correction rather
than a halted turn. `CLAUDE.md` and `.claude/hooks/README.md:7` both state a blanket "`PostToolUse`
hooks exit `0` (warn only — never block)" that's true of the other eighteen scripts but not this
one — which is why a dropped flag on an already-"warn only"-documented hook reads as a no-op rather
than a behavior change. This spec pins the flag's **presence**, not a contested account of its
purpose: the repo's own two commits frame *why* it matters differently (`0f8f983e`'s title says
"promote ... to blocking"; `2e5854e9`'s message says "so the token hook stays advisory as
designed"), and nothing here adjudicates that disagreement.

**Currently, in this worktree, the flag IS present** — verified directly. Per the HARD RULES ("do
not edit `settings.json` itself unless the flag is actually missing"), this spec does not modify
`.claude/settings.json`.

## Fix

Add `tests/scripts/token-violation-hook-advisory.test.ts` (ADR-051 style — see
`tests/scripts/node-sidecar-pin-wiring.test.ts` for the shape: read a tracked file, locate the
relevant entry, assert its properties). Resolve the settings path through a single constant —
`const SETTINGS_PATH = process.env.TANDEM_SETTINGS_PATH_FOR_TEST ?? path.resolve(__dirname,
"../../.claude/settings.json")` — so a mutation-check (see Tests) can point it at a scratch copy
via the env var, with no edit to the test file.

The test:

1. Reads and `JSON.parse`s `.claude/settings.json`.
2. Walks every lifecycle key under `hooks` (not `PostToolUse` alone — an entry copied into
   `PreToolUse`, which already blocks by exit code regardless of `continueOnBlock`, would leave a
   `PostToolUse`-only count at one and pass while the hook's behavior had changed) and collects
   every hook whose `command` contains `check-token-violation.sh`.
3. Asserts the total count across all lifecycles is exactly one, that its lifecycle is
   `PostToolUse`, and that its `continueOnBlock === true`.

One bundled tangential fix: `.claude/hooks/README.md:7`'s "Hook semantics" list states the blanket
"`PostToolUse` hooks exit `0`" line that this hook doesn't follow. Add one bullet directly under it
naming the exception, citing the script's own header comment.

No change to `.claude/settings.json` or `check-token-violation.sh` — the flag is present and the
script's exit behavior is correct as written.

## Tests

The new test file is the discriminating test: it fails if `continueOnBlock` is dropped again, or
if the entry is duplicated anywhere under `hooks`, or moved to another lifecycle. It does not (and
cannot) test what `continueOnBlock` means inside the Claude Code harness itself.

Before committing, mutation-check per the user's preference: copy `.claude/settings.json` to a
scratch path outside the repo, mutate the copy (drop `continueOnBlock`, or duplicate/move the
entry), set `TANDEM_SETTINGS_PATH_FOR_TEST` to that path, run `npx vitest run
tests/scripts/token-violation-hook-advisory.test.ts`, confirm red against each mutation, unset the
env var. No edit to the real `.claude/settings.json`, no `git checkout`.
