# W13g — #1910 pin `check-token-violation.sh`'s `continueOnBlock: true` in `.claude/settings.json` with a wiring test

Branch `fix/docs-and-test-tooling-drift-2005`. Closes #1910. No track file (non-review issue). No
MCP probe: this is a repo-tooling/CI-config fix, not an MCP surface.

## Problem

`.claude/settings.json`'s `hooks.PostToolUse` entry for `check-token-violation.sh` (inside the
`Edit|Write`-matcher group, currently around line 104-107) carries `"continueOnBlock": true`.

**The mechanism, stated as the hook script itself states it, not as the repo's blanket
hook-semantics line describes it.** `check-token-violation.sh` exits `2` on a violation
(`:40` — `exit 2`), and its own header comment (`:4`) reads: "Exit 2 + continueOnBlock = Claude
self-corrects the violation; exit 0 = clean." So `continueOnBlock: true` is what turns that exit-2
into an in-turn self-correction rather than a halted turn — the flag is what lets Claude fix the
violation and keep going, not what keeps the scan "advisory." This is a **documented exception**:
`CLAUDE.md`'s Hooks section and `.claude/hooks/README.md:7` both state a blanket
"`PostToolUse` hooks exit `0` (warn only — never block)" — a true description of the other
eighteen scripts in that inventory, but not of this one. That blanket line is itself the reason a
silent drop of the flag is easy to miss: the doc a reader checks first says `PostToolUse` never
blocks, so a dropped `continueOnBlock` on a hook that already reads as "warn only" by the doc's own
claim looks like a no-op rather than a behavior change. The repo's own two commits about this flag
give opposite framings of *why* it matters — `0f8f983e`
(`fix(hooks): promote token violation hook to blocking via continueOnBlock`) and `2e5854e9`
(`chore: keep $CLAUDE_PROJECT_DIR hook paths, restore continueOnBlock`, "so the token hook stays
advisory as designed") — and this spec does not adjudicate that disagreement; it states only what
the script and `continueOnBlock` verifiably do, per the script's own header comment, and pins the
flag's presence rather than its intended meaning.

This flag has been silently dropped from `.claude/settings.json` **twice** by the harness's own
normalization of hook commands to the `"$CLAUDE_PROJECT_DIR/..."` path form:

- `0f8f983e` (`fix(hooks): promote token violation hook to blocking via continueOnBlock`) is where
  the flag came from.
- A harness rewrite later dropped it while normalizing paths.
- `2e5854e9` (`chore: keep $CLAUDE_PROJECT_DIR hook paths, restore continueOnBlock`) restored it
  and documented the mechanism in its own commit message.
- It was dropped a **second** time — observed 2026-09-08 during an unrelated docs session, left
  **unstaged** in the working tree, not committed either way.

Both commits are present in this repo's history (verified: `git log --oneline --all | grep -i
continueOnBlock` returns both). Each occurrence is silent: nothing fails, no test notices, and the
only signal is a stray `M .claude/settings.json` in `git status` during unrelated work. A third
drop, committed via a broad `git add -A`, would quietly make the token hook blocking for everyone
with no record of why.

**Currently, in this worktree, the flag IS present** — verified directly:
`.claude/settings.json`'s `check-token-violation.sh` hook entry reads `"continueOnBlock": true`.
Per the HARD RULES ("do not edit `settings.json` itself unless the flag is actually missing"),
this spec does not modify `.claude/settings.json`.

## Fix

Add `tests/scripts/token-violation-hook-advisory.test.ts`, in the ADR-051 style used throughout
`tests/scripts/` (`docs/decisions.md`'s ADR-051: "the job does the work; a wiring test inside
`check` pins the job's shape and the inputs it reads" — the "job" here is the harness's own
settings-normalization behaviour, and this test is what turns the next silent drop into a red
`check`). Model: `tests/scripts/node-sidecar-pin-wiring.test.ts`'s shape (read a tracked file,
locate the one relevant entry, assert its properties) — simpler here because the input is JSON,
not YAML/a workflow file.

The test resolves its input through a single module-level constant —
`const SETTINGS_PATH = process.env.TANDEM_SETTINGS_PATH_FOR_TEST ?? path.resolve(__dirname,
"../../.claude/settings.json")` — rather than an inline `readFileSync(".claude/settings.json")`
buried in the assertion body, so a hand mutation-check (see Tests) can point it at a scratch copy
via the env var alone, with no edit to the test file itself.

The test:

1. Reads and `JSON.parse`s `.claude/settings.json` (via `SETTINGS_PATH`) from the repo root.
2. Walks **every** lifecycle key under `hooks` (`PreToolUse`, `PostToolUse`, and any other key
   present — not `PostToolUse` alone), each an array of `{matcher?, hooks: [...]}` groups, and
   collects every hook object across every group and every lifecycle whose `command` string
   contains `check-token-violation.sh`, recording which lifecycle each match came from.
3. Asserts the **total** count of matches across all lifecycles is **exactly one**. Walking every
   lifecycle (not `PostToolUse` alone) is required for this to actually catch a duplication: an
   entry copied into `PreToolUse` (which blocks by exit code 2 regardless of `continueOnBlock` —
   CLAUDE.md's Hooks section) would leave a `PostToolUse`-only count at one and pass, while the
   hook's blocking behavior had changed.
4. Asserts that one match's lifecycle is `PostToolUse` — this is what catches the entry being
   *moved* rather than duplicated, which the total-count assertion alone would not (a move keeps
   the total at one).
5. Asserts that entry's `continueOnBlock === true`.

**One bundled tangential fix, in the same edit** (CLAUDE.md: "if you find something broken while
working, fix it rather than filing it"): `.claude/hooks/README.md:7`'s "Hook semantics" list states
a blanket "`PostToolUse` hooks exit `0` (warnings only — they emit to stderr but never block)" that
`check-token-violation.sh` does not follow — it exits `2` on a violation, per its own header at
`:4`. Add one bullet directly under that line naming the exception, citing the script's own header
comment: `check-token-violation.sh` is the one `PostToolUse` hook that exits `2` on a violation,
with `continueOnBlock: true` making that an in-turn self-correction rather than a halted turn.
`CLAUDE.md`'s own equivalent line is left as the general statement it is — correcting every
reference to it repo-wide is a larger edit than this issue asks for; `.claude/hooks/README.md` is
the one doc a reader actually opens when a specific `PostToolUse` hook's behavior is in question,
so that is where the exception is recorded.

No change to `.claude/settings.json` or `.claude/hooks/check-token-violation.sh` — the flag is
present today and the script's exit behavior is correct as written, so per the HARD RULES this PR
is test-only for the settings pin, plus the one-line `.claude/hooks/README.md` correction above.

## Tests

The new test file itself is the discriminating test:

- **Kills**: a harness rewrite (or a hand edit) that drops `continueOnBlock` from the
  `check-token-violation.sh` entry — the exact failure mode this issue is about, for the third
  time.
- **Kills**: the entry being duplicated anywhere under `hooks` (two hook objects both matching
  `check-token-violation.sh`, whether both in `PostToolUse` or split across lifecycles) or moved
  out of `PostToolUse` into `PreToolUse` — either of which would silently change the hook's
  blocking behaviour by a different mechanism than the flag.
- **Does not kill**: a change to `continueOnBlock`'s meaning inside the Claude Code harness itself
  (outside this repo's control) — stated as a limit, not something this test can reach.

Before committing, mutation-check the new test per the user's own preference (never `npm test`
against a corrupted real file — copy `.claude/settings.json` to a scratch path outside the repo,
mutate the copy — drop `continueOnBlock`, or duplicate/move the entry — set
`TANDEM_SETTINGS_PATH_FOR_TEST` to that scratch path and run the test directly with `npx vitest
run tests/scripts/token-violation-hook-advisory.test.ts`, confirm it goes red against each
mutation, then unset the env var. No edit to the test file or to the real `.claude/settings.json`
is needed for this check, and never `git checkout` the real file.

## Review corrections (round 1)

Adopted:

- **The Problem section's causal claim was backwards and is rewritten.** The original text said
  `continueOnBlock` "is what keeps the raw-hex/semantic-token scan advisory" and that dropping it
  makes the hook "more aggressive." The script's own header (`:4`) says the opposite:
  `check-token-violation.sh` already exits `2` on a violation; `continueOnBlock: true` is what lets
  Claude self-correct in-turn rather than halting, per commit `0f8f983e`'s own title ("promote
  token violation hook to blocking via continueOnBlock"). The Problem section now states the
  mechanism as the script states it, notes `CLAUDE.md` / `.claude/hooks/README.md:7`'s blanket
  "PostToolUse never blocks" line as a documented exception this hook doesn't follow (rather than
  as evidence for the flag's purpose), and does not take a position on the two commits'
  disagreement (`0f8f983e` vs. `2e5854e9`) — it pins the flag's *presence*, not a contested account
  of its meaning.
- **Bundled a one-line `.claude/hooks/README.md` correction** naming `check-token-violation.sh` as
  the exit-2 exception to the blanket PostToolUse line, citing the script's own header — the
  cheapest fix for the actual reason a silent drop goes unnoticed (the doc a reader checks first
  says this class of hook never blocks).
- **Widened the test to walk every `hooks` lifecycle, not `PostToolUse` alone**, and split the
  single "exactly one, in the right place" assertion into two: a total-count-across-lifecycles
  assertion (catches duplication anywhere) and a separate lifecycle-of-the-one-match assertion
  (catches relocation). The original design's own "kills a move to PreToolUse" claim was false as
  written — a `PostToolUse`-only walk cannot see a copy that lands in `PreToolUse`.
- **Fixed the mutation-check procedure**, which was self-defeating as originally written (it told
  the implementer to edit the very file under test, while also saying never to restore via `git
  checkout`). The test now resolves its input path through a `TANDEM_SETTINGS_PATH_FOR_TEST`
  env-var override, so mutation-checking needs no edit to the test file and no restore step at all.

Not adopted:

- None of the round-1 findings against this spec were rejected. The items above cover the blocking
  finding and every non-blocking finding raised against this spec; all were adoptable at low cost
  and none conflicted with the issue's own scope (test-only pin, no `.claude/settings.json` edit,
  no decision on whether the hook *should* be blocking).
