## Problem

`executeRun` (`src/server/local-model/collaborator.ts`) captures the Y.Doc once — `const ydoc = open.doc;` — and hands it to `deps.runTurn({ ydoc, … })` for a whole model turn. Hocuspocus replaces a room's Y.Doc in `onLoadDocument` (`src/server/yjs/provider.ts`: merge state, `existing.destroy()`, `documents.set(...)`, `lifecycle.onDocSwapped`), so a browser connecting mid-run leaves the run holding a destroyed instance. The ownership gate that should notice cannot.

**The issue's quoted code is stale — do not paste it.** Measured on `c2666ec9`, `collaborator.ts:298-303`:

```ts
const stillOwner = () =>
  current?.token === token && !abort.signal.aborted && requireDocument(req.docName) !== null;
```

Three conjuncts, not one. `current?.token === token` already defends against supersession; `!abort.signal.aborted` against cancellation. **Only the presence conjunct is wrong, and neither of the other two sees a swap** — the token is unchanged and nothing aborts. Say that in the PR body: the function had two correct guards and one insufficient one.

Two mechanism facts the fix rests on, both measured and both required in the PR body:

- `requireDocument` re-resolves through the provider map on every call (`src/server/documents/registry.ts`: `doc: getOrCreateDocument(current.docName)`), so comparing its result against the captured instance actually observes a swap. Without this the fix would be a no-op.
- `getOrCreateDocument` **creates** on a map miss (`provider.ts:52`), so the existing comment's claim that `requireDocument` "never fabricates a phantom room" is **false**. Do not carry it forward.

## Fix — one file, one predicate

`src/server/local-model/collaborator.ts` only.

1. Move the doc resolution above the predicate: `const open = requireDocument(req.docName); if (!open) return; const ydoc = open.doc;` then the `stillOwner` definition, then the existing `if (!stillOwner()) return;` and `cachedConfig` guard in their current order. **`ydoc` must be declared before the definition, not merely before the first call** — the predicate closes over it and a TDZ `ReferenceError` would fire on the top-of-run call.

2. Change the third conjunct:

```ts
const stillOwner = () =>
  current?.token === token && !abort.signal.aborted && requireDocument(req.docName)?.doc === ydoc;
```

`?.doc === ydoc` is false when `requireDocument` returns null, so **identity subsumes presence and additionally rejects a re-created instance**. That added rejection is intended; it is not "behaviour unchanged". At the top-of-run call the comparison is trivially true (same call, same instance), so that check keeps its meaning.

3. Rewrite the comment at `:298-301`: identity not presence, name #1657, delete the phantom-room sentence, and replace "Mirrors the sink's `isOwner()`" with one sentence recording that the sink deliberately **diverges** — `makeSink` writes only to `CTRL_ROOM` via `appendClaudeChatMessage` / `updateClaudeChatMessage` (`src/server/mcp/awareness.ts`), which a document-room swap never touches, so presence is the right test there. The `:244` comment ("`stillOwner()` carries the same abort clause") stays true unchanged.

**The sink's `isOwner` is NOT touched.** Beyond the divergence above, mirroring the conjunct would drop the #1292 truncation marker on the swap path — a write that lands correctly today — because the cap branch commits it through `write()`.

**Consequence to record, not to fix silently:** identity also suppresses the terminal `pushNotification` calls on a swap. Those go to the notification buffer, not the captured doc, so they stay deliverable; today presence lets them through. Decision: keep them inside the gate — a "stopped before finishing" toast for a run whose document-bound effects were all discarded is a stale message about invisible work, and splitting the gate would give `executeRun` two ownership notions. State the choice in the PR body.

Rules that bite: no Y.Doc write added (Critical Rule 2 unaffected), no Y.Map key, no `data-testid`, no MCP tool or `/api` route, no `NON_LOOPBACK_ALLOWED` change, no skill edit.
