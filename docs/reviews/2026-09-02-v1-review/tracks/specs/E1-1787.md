# E1 — #1787 Desktop sidecar and npm global share one app-data directory

Branch `fix/desktop-core-1761`. Closes #1787 (both halves: the env-var mismatch, and decision D). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/upgrade-path.md:16`; decision D at `docs/reviews/2026-09-02-v1-review/decisions.md:30`. Probe: `tests/server/app-data-owner.test.ts` (new) + one client test; the alternating-install case is a smoke line (Bryan).

## Problem

`src-tauri/src/sidecar.rs:1547` sets `TANDEM_DATA_DIR` to Tauri's `app_data_dir()`. `resolveAppDataDir()` (`src/server/platform.ts:10-14`) reads **`TANDEM_APP_DATA_DIR`**, which nobody sets, and falls back to `envPaths("tandem", {suffix:""}).data`. `TANDEM_DATA_DIR` is used for exactly two things: the `sample/welcome.md` base (`index.ts:653`) and the bundled-doc-dirs exclusion derived from it (`mcp/server.ts:153`). So the desktop sidecar and an npm-installed `tandem` share `sessions/`, `last-seen-version`, `integrations.json`, the annotation envelope dir, doc backups, and (once the gate is live) `trial.json` / `license.json` — a documented, supported both-installed state. Alternating versions re-opens CHANGELOG on every launch of both; every downgrade hazard is reachable with no downgrade; after the flip an old npm build is a one-command gate bypass over the same license files.

The desktop already *has* a private directory — `app_data_dir()` resolves under the `com.tandem.editor` identifier, not `tandem` — it simply is not handed to the resolver.

**Two consequences of separating them that round 1 established and this spec now owns.** (a) The client's install id is derived from `storagePath` (`installIdFromStoragePath`, `src/client/utils/install-id.ts:66-90`), which is `path.join(resolveAppDataDir(), "sessions")` (`platform.ts:38-41`, published at `mcp/server.ts:772`), and that id namespaces scratchpad recovery in localStorage (`tandem:scratchpad:${installId}:${uuid}`, `useScratchpadPersistence.svelte.ts:45-46`). Moving the directory moves the id, and the module's own docblock names the failure: "Two spellings of one directory MUST produce one id, or a restart would look like a different installation and silently drop recovery." Unsaved scratchpad recovery would become unreachable on the first desktop launch after this ships. That docblock also states the *current* sharing as intentional ("an npm-global install and the desktop app both resolve the default root, so they share one id"), so this is a deliberate reversal, not a bug fix, and it needs a migration of its own. (b) The annotation store lock is per-app-data-root (`annotations/store.ts:67`, `:166`), so today it is the cross-flavor mutual exclusion — after separation each flavor holds its own.

## Fix

Two changes, matching decision D's two clauses. **Directory separation is the mechanism; the stamp is the guard that makes any residual sharing loud rather than silent.** A version stamp alone cannot work, and the reason must be in the PR body: an already-released `tandem-editor` has no code to read one.

**1. Separation (the env-var half), through a named seam so the one line that carries it is pinned.** `src-tauri/src/sidecar.rs:1541-1569` builds the child's environment inline on the `cmd` builder, so `.env("TANDEM_APP_DATA_DIR", …)` would be a line no test can observe — and **omitting it does not merely leave the bug, it makes the npm `tandem` refuse to start**: `resolveAppDataDir()` (`platform.ts:10-14`) would still return the legacy `envPaths` root, the desktop would claim *that* directory with `flavor: "desktop"`, and the next npm run would hit the flavor refusal below and exit. A green suite shipping a new hard failure for npm users is exactly what round 2 flagged.

- Extract the pairs into a module-level pure function — `fn sidecar_env_pairs(app_data_dir: &str) -> Vec<(&'static str, String)>` — returning at least `TANDEM_TAURI_SIDECAR`, `TANDEM_DATA_DIR`, `TANDEM_APP_DATA_DIR`, `TANDEM_PORT`, `TANDEM_MCP_PORT`, `TANDEM_BIND_HOST`, and have `start_sidecar` fold it onto the builder. The conditional pairs (`TANDEM_AUTH_TOKEN`, `TANDEM_CHANNEL_DIST`, `TANDEM_STDIO_BRIDGE_DIST`, `:1571-1580`) stay where they are — they are `Option`-gated and not what this fix is about.
- `TANDEM_DATA_DIR` and `TANDEM_APP_DATA_DIR` take the **same** value; extend the comment to say the first names the *resource/sample* base and the second the *state* root. `strip_win_prefix` is already applied (`:1477`); keep it. No change to `resolveAppDataDir`.
- A `#[cfg(test)]` case asserts both keys are present in `sidecar_env_pairs("/tmp/x")` and hold the same value. See Done-when; without it the whole separation half is checked by nothing (every `app-data-owner.test.ts` case passes an explicit temp dir, so none can observe the env var).

**2. Ownership stamp + one-time migration.** New `src/server/app-data-owner.ts`, one exported async `claimAppDataDir(appDataDir, version, flavor)`:

- **Failure contract, and it is the first thing to get right: `claimAppDataDir` must never throw.** It is called at the top of `main()`, and `main().catch(…) => process.exit(1)` (`index.ts:784`) makes any escaping error a startup abort — for the desktop that is `wait_for_health` failing on every attempt through `MAX_RESTARTS` into the "Retry Server Start" dialog, i.e. an app that never starts, with no in-product recovery. Everything else at that altitude is deliberately best-effort and wrapped (the backup sweep at `index.ts:299-311`, the trial clock at `:315-326`); this must be too. Concretely: `fs.mkdir(appDataDir, {recursive: true})` **before any write** (the first-ever desktop launch writes `owner.json` into a directory `app_data_dir()` merely names — nothing has created it yet, and an unguarded write is ENOENT); and a total catch around the migration and around the stamp read/write, logging to stderr and returning `"claimed"` **without** writing the stamp, so the next launch retries the migration rather than recording a copy that did not happen. Two reachable throws it must absorb: `fs.cp` over a legacy tree a live npm instance is writing (EBUSY/EPERM on Windows, or ENOENT on a `.tandem-tmp-*` that vanishes mid-walk — `docs/data-locations.md:37-40` documents those temps as normally present), and any failure of the stamp I/O itself. It may return `refused`; it may not throw.
- Stamp file `<app-data>/owner.json`, `{"version": "<APP_VERSION>", "flavor": "desktop" | "npm"}`. `flavor` is `process.env.TANDEM_TAURI_SIDECAR === "1" ? "desktop" : "npm"` — that env var is already set at `sidecar.rs:1546` and needs no new writer (adding one would widen accepted finding #1599).
- **Refusal rule, and it is on `flavor`, not on version ordering:** if a stamp exists and its `flavor` differs from ours, print to stderr and refuse. **Why flavor and not "older":** an older build cannot read the stamp at all, so a version-ordered rule protects nothing that separation has not already made impossible, while a flavor rule catches exactly the mixing decision D names — and it is robust in both directions and needs no semver comparator (`version-check.ts` has none; adding one is #1792's job in wave 8). The `version` field is recorded so the message can name the owner and so #1792 has it; it is **not** itself a gate here.
  - **The message is flavor-aware.** For the npm arm: `[Tandem] This app-data directory (<dir>) belongs to the desktop install (last used by v<version>). Refusing to share it. Set TANDEM_APP_DATA_DIR to run against a different directory.` For the desktop arm the `TANDEM_APP_DATA_DIR` sentence is **omitted** — the sidecar sets that variable explicitly on the child (`sidecar.rs:1545-1568`, and an explicit `.env()` overrides the inherited value), so the suggested remedy is inert there. That arm says instead: `… Quit the npm \`tandem\` and relaunch, or remove <dir>/owner.json if you are certain no npm install uses this directory.` The desktop case is unreachable once separation lands; the message exists for the pre-migration directory.
- Same flavor, any version → overwrite the stamp and proceed. Absent → write and proceed.
- **Migration, once, copy-only, with an explicit exclusion filter.** Before writing a *first* stamp, and only when `flavor === "desktop"` and `appDataDir !== envPaths("tandem",{suffix:""}).data` and that legacy dir exists: `fs.cp(legacy, appDataDir, {recursive: true, force: false, errorOnExist: false, filter})`. The app-data root holds only Tandem's own state — user documents live wherever the user put them and are referenced by path, so nothing of the user's is moved or duplicated. The legacy directory is left **intact**. `force: false` means an existing target file wins, so a retry cannot clobber state the desktop has since written. **The `filter` refuses five things, and each one is a defect if copied:**
  1. `owner.json` — **the stamp is the only file never copied, and that is what makes it the completion record.** `fs.cp` gives no ordering guarantee over directory entries, so a legacy `owner.json` (present after the first npm run of this same release) copied into the target before an interruption would leave a foreign-flavor stamp behind and make every subsequent desktop launch refuse. The app would be permanently unstartable with no in-product recovery, and the refusal message would be pointing at an env var rather than at a file to delete. Excluding it means an interrupted copy leaves no stamp and retries next launch — the safety property this spec claims.
  2. `annotations/store.lock` — `acquireStoreLock` returns `"readonly"` while `isPidAlive(lock.pid)` (`annotations/store.ts:166-205`, `:243`), and `releaseStoreLock` (`:371`) unlinks the lock under the *releasing process's own* resolved dir, never the copy. A copied lock holding a live npm PID makes the freshly-migrated desktop directory read-only for annotations and never clears. The trigger is the exact both-installed state this issue is about.
  3. In-flight temporaries — any `*.tmp` / `*.tmp-*` basename. A partially-written atomic-write temp copied under `force: false` becomes permanent.
  4. The auth-token file (`TOKEN_FILE_NAME`) — `src/shared/auth/token-file.ts:6-8` derives its path from `envPaths("tandem",{suffix:""}).data` **directly** and ignores `TANDEM_APP_DATA_DIR`, deliberately (`install-id.ts:34-36` documents why). So a copy in the desktop directory has no reader, is never rotated by `/api/rotate-token`, and never gets `readTokenFromFile`'s 0600 repair (`token-file.ts:15-25`). A credential with no reader in the destination is only a second copy of a secret.
  5. `.broken-backups/` (`integrations/storage.ts:44`) — forensic copies of corrupted config files, created inside a directory hardened by `setRestrictiveAcl` at mkdir time (`storage.ts:291`; the file inherits the dir DACL, and `storage.ts:256-266` states that per-file ACLs are deliberately not used because the dir-level one closes a TOCTOU window). `fs.cp` is `CopyFileEx` and does not carry the source's DACL, so copies would land under the destination's inherited ACEs only. Nothing in the desktop directory reads them, so exclusion is strictly better than re-hardening.
- **One hardened tree IS copied, and must be re-hardened after the copy:** `doc-backups/` (`file-io/doc-backup.ts:123`) holds the user's pre-overwrite document backups, which the restore UI reads, so dropping it would be a real loss. Its root carries an inheritable restrictive DACL applied by the module-private `ensureBackupRootHardened` (`doc-backup.ts:182`, called at `:512`). Export that function and call it from the migration once the copy completes, when `doc-backups/` was among what was copied. Same reasoning as above: the hardening is directory-level and inheritable by design, so re-applying it to the migrated root covers every file inside it, and no per-file ACL work is needed.
- **Placement. One order, stated identically in both specs: probe (HTTP only) → claim → sweep → trial → lock.** Call `claimAppDataDir` once from `src/server/index.ts`, in **both** transport modes, after `initSidecarCrashReporting()` (`:292`) and before the backup sweep at `:299`, the trial clock at `:315` and the store lock at `:332` — all three already read `resolveAppDataDir()`, so claiming after them would sweep and stamp two different directories. In HTTP mode E1-1758's `probeTandemInstance` / `decideStartupAction` runs immediately before the claim (a refusal exits before anything is written, which is that spec's point); in stdio mode there is no probe at this altitude — E1-1758's stdio arm sits at `:767`, after all three — so the claim is simply the first thing after crash reporting. The earlier "first statement of `main()`" phrasing is withdrawn: it contradicted E1-1758's "first thing in `main()`'s HTTP path", and both cannot be first.
- **Install-id continuity (the scratchpad-recovery half).** Separation changes `storagePath`, which changes the derived install id, which orphans every existing scratchpad recovery key. Carry the legacy id across for reads:
  - `claimAppDataDir` returns the legacy **app-data root** it migrated from (or that exists but was not migrated, for the desktop flavor). **`legacyStoragePath` is `path.join(legacyAppDataDir, "sessions")` — the same producer shape as `storagePath`, and it is stated only here.** `storagePath` is `SESSION_DIR` (`platform.ts:38-41`, published at `mcp/server.ts:772`) and `installIdFromStoragePath` (`install-id.ts:89-91`) hashes whatever string it is handed, so publishing the root instead of its `sessions/` child yields a different id, the legacy key never matches, and the fallback is silently dead. Pass `legacyStoragePath` beside `storagePath` in the `/api/info` deps at `mcp/server.ts:772`, and emit it **inside the same `if (loopback)` block of the `/api/info` handler that already gates `storagePath`** (the block named in `useScratchpadPersistence.svelte.ts:387`) — it is a filesystem path, and it belongs behind exactly the gate its sibling is behind.
  - Client: in the **recovery read path only** (`useScratchpadPersistence.svelte.ts:555-563`), when no value is found under the current install id and `legacyStoragePath` is present, retry under `installIdFromStoragePath(legacyStoragePath)`. **The retry covers BOTH reads in that block, not just the first**: the direct `scratchpadStorageKey(id, sourceUuid)` *and* the `entries.size === 1` pointer chain `scratchpadLatestKey(id)` → `scratchpadStorageKey(id, latest)`. Covering only the direct key misses every recovery that goes through the latest pointer — a fresh scratchpad uuid after the move, which is precisely the case the pointer exists to serve, and the common one after a directory change. The `entries.size === 1` gate and the attach-order reasoning at `:545-553` are unchanged and apply to the legacy attempt identically. **Writes always use the current id** — this is a one-directional fallback, so the legacy namespace is read and never grown, and it lapses on its own once the user's next scratchpad is saved.
  - If the fallback is later judged not worth its weight, the alternative is to **accept** the loss — but then it is recorded in the PR body, in `docs/data-locations.md` and as a smoke line, never left silent. Round 1's finding was that tests 1–7 would not notice either way; the client test below is what makes the choice checkable.
- **Docs, and three of them are statements this change makes false rather than merely incomplete:**
  - `docs/data-locations.md` — add the desktop row (`app_data_dir()` under `com.tandem.editor`) beside the npm `env-paths` row, one line saying the two are separate and the desktop copies the npm directory once on first launch after this version, the list of what the copy excludes, and **one line naming the store-lock consequence**: the annotation-store lock is now per-flavor, so running both flavors against the same document on different ports lets each write its own durable envelope and neither sees the other's annotations (today the second instance goes `readonly` instead). Check `tests/docs/session-file-claims.test.ts` for a claim about `SESSION_DIR`'s parent before editing.
  - Same file, the "Inside it" table (`:27`): mark `auth-token` **npm-location-only**. `src/shared/auth/token-file.ts:6-8` derives it from `envPaths` regardless of `TANDEM_APP_DATA_DIR` (exclusion item 4 above), so after separation the row is false for the desktop directory.
  - Same file, manual-cleanup step 1 (`:148`, "Delete the app-data directory for your OS (table above)"): with two rows, a user following it deletes one and leaves `license.json`, annotations and doc-backups behind. Make it "both directories, if you have both installs".
  - `src/server/mcp/routes/info.ts:52` — the handler's own docblock enumerates "Sensitive fields (loopback-only): `storagePath`, `tokenRotatedAt`, `generationId`". `legacyStoragePath` joins that list in the same edit. This is the identical omission E1-1812 raised for `health.ts:37-41`; make it once, in both files.
  - `src/client/utils/install-id.ts:28-31` — its docblock currently states the now-reversed claim that an npm-global install and the desktop app "both resolve the default root, so they share one id". Correct that paragraph and name the legacy-id read fallback, since this module is where the next reader will look for it.
- **Record the substitution against decision D.** D is minuted as "refuses to share its data dir with an older server (**version stamp**)"; what ships gates on `flavor`. Amend the decision-D row in `docs/reviews/2026-09-02-v1-review/decisions.md:30` and the sweep ledger to say flavor, with the one-sentence reason (an older build has no code to read a stamp), so the record and the code agree rather than the ledger reading satisfied against a rule that was not implemented.
- **`tests/docs/config-writer-set-claims.test.ts` needs a row.** `DURABLE_WRITER_FILES` pins **every file in all of `src/`** that durably writes, and how many times (`:44-47`, map at `:230-258`) — not just the two `SCAN_ROOTS`. Writing `owner.json` is a `writeFile` the repo-wide walk sees, so `src/server/app-data-owner.ts` gets a row with its write count. It is a new durable writer outside `SCAN_ROOTS`, **not** a config writer, so `docs/security.md`'s accepted #1599 entry is unchanged. Note that `fs.cp` is not in that test's `DURABLE_WRITE` idiom list, so the migration copy is invisible to the sweep by construction — the row covers the stamp write only.

**Known residual, name it in the PR body, do not fix it here:** two independent derivations of the legacy path survive. `src-tauri/src/token_store.rs`'s `data_dir()` computes the `env-paths` location in Rust, and `src/shared/auth/token-file.ts:6-8` computes it in Node and deliberately ignores `TANDEM_APP_DATA_DIR` (`install-id.ts:34-36`). Neither is a functional break — the OS keyring is the primary store and the shell passes the token to the sidecar via `TANDEM_AUTH_TOKEN` (`sidecar.rs:1570`), which `loadOrCreateToken` prefers over any file (`src/server/auth/token-store.ts:64-69`) — but they are two more spellings of the same fact, and they are why the migration excludes the token file rather than copying it. `keychain.rs`'s `tandem-integrations` service namespace is shared with the npm CLI **deliberately** (its docblock) and is out of scope.

## Tests

New `tests/server/app-data-owner.test.ts`, all against `mkdtemp` dirs:

1. No stamp → `claimAppDataDir` writes `{version, flavor}` and resolves.
2. Stamp with the same flavor and a different version → overwritten, resolves. **Kills** a rule that refuses on any version difference, which would brick every upgrade.
3. Stamp with a different flavor → refuses. Assert the refusal, not the exit: have `claimAppDataDir` return a discriminated result (`"claimed" | {refused: {flavor, version}}`) and let `index.ts` own the `process.exit(1)`, so the decision is testable without spawning a process.
4. Corrupt / non-JSON / missing-field stamp → treated as absent (claimed, overwritten). **Kills** a throw that would make a truncated write unrecoverable.
5. Migration: legacy dir with `sessions/a.json` + `annotations/b.json`, empty target, `flavor: "desktop"` → both copied, legacy still present, stamp written. Re-running does **not** re-copy a file deleted from the target in between. **Kills** a migration keyed on anything but the stamp, and one that moves instead of copies.
6. Migration with a **legacy `owner.json` present** (a user who ran the npm build first): after migration the target's stamp reads `flavor: "desktop"`. **Kills** the ordering bug where the copied npm stamp makes the desktop refuse its own directory on the next launch.
7. `flavor: "npm"` with a legacy dir that differs → **no** copy. **Kills** a migration that fires for the npm install too.
8. **Interrupted-copy recovery.** Legacy dir holds `owner.json` (`flavor: "npm"`) plus `sessions/a.json`; run the desktop claim; assert the target's `owner.json` reads `desktop`; then **delete the target stamp** (simulating an interruption after the copy but before the stamp) and re-run — it must claim again, not refuse. **Kills** a filter that lets the legacy stamp through, which is the state that makes the app permanently unstartable.
9. **Exclusion filter, one assertion per excluded item.** Legacy dir contains `annotations/store.lock`, a `*.tmp` file, the auth-token file, and `.broken-backups/x.json`; after migration **none** of the four is present in the target, while `sessions/a.json` and `doc-backups/y.md` are. **Kills** a wholesale `fs.cp` with no filter — round 1 found two separate defects behind that one omission (a copied live lock makes the target read-only forever; a copied stamp bricks startup).
10. **`doc-backups/` re-hardening is called.** `vi.mock("…/file-io/doc-backup.js")` and assert the exported `ensureBackupRootHardened` is invoked once with the migrated `doc-backups` root when that tree was copied, and not at all when it was absent. **The mock is the mechanism, not one of two** — the "inject it as a dependency" alternative is deleted, because it needs a fourth parameter the signature fixed above (`claimAppDataDir(appDataDir, version, flavor)`) does not have and Files-touched does not add. Cross-platform — no real `icacls`, so this adds no Windows-gated spec and does not touch the `windows-acl-proof` list (#1529).
11. **Install-id continuity, client-side, and it must go through the pointer.** In `tests/client/` (beside the existing scratchpad-persistence specs): store the recovery value under `installIdFromStoragePath(legacyRoot + "/sessions")` at a uuid **different** from the tab's, and the legacy `scratchpadLatestKey` pointing at it; store **nothing** under the current id and nothing under the legacy direct key for the tab's own uuid. The recovery path must still return it. A subsequent save writes under the **current** id only. **Kills** two things at once: the silent-orphan regression, and a fallback wired to the direct read alone — which the earlier wording ("a stored recovery value under the legacy id") was satisfied by, while the realistic post-move recovery stayed broken. Keep a second, simpler case for the uuid-stable direct-key path.
12. **`claimAppDataDir` never throws.** A migration whose copy fails (make one legacy entry unreadable, or stub `fs.cp` to reject) → the call resolves `"claimed"`, writes **no** stamp, and the next call re-attempts the migration. Same for a stamp write that rejects. **Kills** the startup-abort: an escaping error reaches `main().catch(…) => process.exit(1)` (`index.ts:784`) and, for the desktop, becomes an app that never starts.
13. **The sidecar exports both env vars.** `src-tauri/src/sidecar.rs`, `#[cfg(test)]`: `sidecar_env_pairs("/tmp/x")` contains `TANDEM_DATA_DIR` and `TANDEM_APP_DATA_DIR` and their values are equal. **Kills** dropping the one line that is the entire separation half — which does not merely leave the bug, it makes the npm `tandem` refuse to start once the desktop has claimed the legacy directory.
14. **`legacyStoragePath` is the `sessions/` child, asserted server-side.** In `tests/server/app-data-owner.test.ts` (or the info-route spec, whichever holds the publisher): the value published for a known legacy root ends with the `sessions` segment. **Kills** publishing the root, which yields a different `installIdFromStoragePath` hash and a silently dead fallback that test 11 — fabricating its own inputs client-side — cannot see.

## Done when

The sidecar exports `TANDEM_APP_DATA_DIR` **and test 13 pins it**; a desktop launch resolves app-data under the Tauri identifier; the first such launch copies the legacy directory once — excluding the stamp, the store lock, temporaries, the auth token and `.broken-backups/` — re-hardens the migrated `doc-backups` root, and stamps; **`claimAppDataDir` never throws, and a failed migration leaves no stamp so the next launch retries**; an interrupted migration retries rather than refusing; a mixed-flavor directory refuses with a flavor-appropriate message; scratchpad recovery survives the move **through both the direct key and the latest pointer**, with `legacyStoragePath` published as the `sessions/` child; `docs/data-locations.md` describes both locations, the exclusions, the per-flavor store lock, the npm-only `auth-token` row and the two-directory cleanup step; `info.ts`'s loopback-only enumeration and `install-id.ts`'s shared-id paragraph are corrected; decision D's row says flavor; `app-data-owner.ts` has its `DURABLE_WRITER_FILES` row.

Downgrade UX and the CHANGELOG-on-every-launch symptom (#1792, wave 8 E2-upgrade — it inherits a directory that is no longer shared). Envelope forward-compat (#1791). The post-v1.0 policy question "do old npm versions stay installable" — Bryan's, and unaffected by this fix. `token_store.rs`'s and `token-file.ts`'s independent path derivations, and the shared `tandem-integrations` keychain namespace.
