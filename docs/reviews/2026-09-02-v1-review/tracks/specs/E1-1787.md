# E1 — #1787 Desktop sidecar and npm global share one app-data directory

Branch `fix/desktop-core-1761`. Closes #1787 (both halves: the env-var mismatch, and decision D). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/upgrade-path.md:16`; decision D at `docs/reviews/2026-09-02-v1-review/decisions.md:30`. Probe: `tests/server/app-data-owner.test.ts` (new); the alternating-install case is a smoke line (Bryan).

## Problem

`src-tauri/src/sidecar.rs:1547` sets `TANDEM_DATA_DIR` to Tauri's `app_data_dir()`. `resolveAppDataDir()` (`src/server/platform.ts:10-14`) reads **`TANDEM_APP_DATA_DIR`**, which nobody sets, and falls back to `envPaths("tandem", {suffix:""}).data`. `TANDEM_DATA_DIR` is used for exactly two things: the `sample/welcome.md` base (`index.ts:653`) and the bundled-doc-dirs exclusion derived from it (`mcp/server.ts:153`). So the desktop sidecar and an npm-installed `tandem` share `sessions/`, `last-seen-version`, `integrations.json`, the annotation envelope dir, doc backups, and (once the gate is live) `trial.json` / `license.json` — a documented, supported both-installed state. Alternating versions re-opens CHANGELOG on every launch of both; every downgrade hazard is reachable with no downgrade; after the flip an old npm build is a one-command gate bypass over the same license files.

The desktop already *has* a private directory — `app_data_dir()` resolves under the `com.tandem.editor` identifier, not `tandem` — it simply is not handed to the resolver.

## Fix

Two changes, matching decision D's two clauses. **Directory separation is the mechanism; the stamp is the guard that makes any residual sharing loud rather than silent.** A version stamp alone cannot work, and the reason must be in the PR body: an already-released `tandem-editor` has no code to read one.

**1. Separation (the env-var half).** `src-tauri/src/sidecar.rs:1547` — add `.env("TANDEM_APP_DATA_DIR", app_data_dir_str.as_str())` next to the existing `TANDEM_DATA_DIR` line, same value, and extend that line's comment to say the first names the *resource/sample* base and the second the *state* root. `strip_win_prefix` is already applied (`:1477`); keep it. No change to `resolveAppDataDir`.

**2. Ownership stamp + one-time migration.** New `src/server/app-data-owner.ts`, one exported async `claimAppDataDir(appDataDir, version, flavor)`:
- Stamp file `<app-data>/owner.json`, `{"version": "<APP_VERSION>", "flavor": "desktop" | "npm"}`. `flavor` is `process.env.TANDEM_TAURI_SIDECAR === "1" ? "desktop" : "npm"` — that env var is already set at `sidecar.rs:1546` and needs no new writer (adding one would widen accepted finding #1599; `tests/docs/config-writer-set-claims.test.ts` pins that set — this file is not a config writer and must not become one).
- **Refusal rule, and it is on `flavor`, not on version ordering:** if a stamp exists and its `flavor` differs from ours, print to stderr `[Tandem] This app-data directory (<dir>) belongs to the <flavor> install (last used by v<version>). Refusing to share it. Set TANDEM_APP_DATA_DIR to run against a different directory.` and `process.exit(1)`. **Why flavor and not "older":** an older build cannot read the stamp at all, so a version-ordered rule protects nothing that separation has not already made impossible, while a flavor rule catches exactly the mixing decision D names — and it is robust in both directions and needs no semver comparator (`version-check.ts` has none; adding one is #1792's job in wave 8). The `version` field is recorded so the message can name the owner and so #1792 has it; it is **not** itself a gate here. See `assumptions`.
- Same flavor, any version → overwrite the stamp and proceed. Absent → write and proceed.
- **Migration, once, copy-only.** Before writing a *first* stamp, and only when `flavor === "desktop"` and `appDataDir !== envPaths("tandem",{suffix:""}).data` and that legacy dir exists: `fs.cp(legacy, appDataDir, {recursive: true, force: false, errorOnExist: false})`. The app-data root holds only Tandem's own state — user documents live wherever the user put them and are referenced by path, so nothing of the user's is moved or duplicated. The legacy directory is left **intact**. The stamp is written **last**, which makes it the completion record: an interrupted copy leaves no stamp and retries next launch, and a completed one never re-imports later npm-side edits. `force: false` means an existing target file wins, so a retry cannot clobber state the desktop has since written.
- Call it once from `src/server/index.ts`, in **both** transport modes, immediately after the `probeTandemInstance` refusal from E1-1758 and **before** the backup sweep at `:299` / trial clock at `:315` / store lock at `:332` — all three already read `resolveAppDataDir()`, so claiming after them would sweep and stamp two different directories.
- **Docs:** `docs/data-locations.md` — add the desktop row (`app_data_dir()` under `com.tandem.editor`) beside the npm `env-paths` row, and one line saying the two are separate and the desktop copies the npm directory once on first launch after this version. Check `tests/docs/session-file-claims.test.ts` for a claim about `SESSION_DIR`'s parent before editing.

**Known residual, name it in the PR body, do not fix it here:** `src-tauri/src/token_store.rs`'s `data_dir()` computes the `env-paths` location independently, so the Rust-side token *file* fallback still lands in the npm directory. It is not a functional break — the OS keyring is the primary store and the shell passes the token to the sidecar via `TANDEM_AUTH_TOKEN` (`sidecar.rs:1570`), which `loadOrCreateToken` prefers over any file (`src/server/auth/token-store.ts:64-69`) — but it is a second spelling of the same fact. `keychain.rs`'s `tandem-integrations` service namespace is shared with the npm CLI **deliberately** (its docblock) and is out of scope.

## Tests

New `tests/server/app-data-owner.test.ts`, all against `mkdtemp` dirs:
1. No stamp → `claimAppDataDir` writes `{version, flavor}` and resolves.
2. Stamp with the same flavor and a different version → overwritten, resolves. **Kills** a rule that refuses on any version difference, which would brick every upgrade.
3. Stamp with a different flavor → refuses. Assert the refusal, not the exit: have `claimAppDataDir` return a discriminated result (`"claimed" | {refused: {flavor, version}}`) and let `index.ts` own the `process.exit(1)`, so the decision is testable without spawning a process.
4. Corrupt / non-JSON / missing-field stamp → treated as absent (claimed, overwritten). **Kills** a throw that would make a truncated write unrecoverable.
5. Migration: legacy dir with `sessions/a.json` + `annotations/b.json`, empty target, `flavor: "desktop"` → both copied, legacy still present, stamp written. Re-running does **not** re-copy a file deleted from the target in between. **Kills** a migration keyed on anything but the stamp, and one that moves instead of copies.
6. Migration with a **legacy `owner.json` present** (a user who ran the npm build first): after migration the target's stamp reads `flavor: "desktop"`. **Kills** the ordering bug where the copied npm stamp makes the desktop refuse its own directory on the next launch — the single most likely way to get this wrong.
7. `flavor: "npm"` with a legacy dir that differs → **no** copy. **Kills** a migration that fires for the npm install too.

## Done when

The sidecar exports `TANDEM_APP_DATA_DIR`; a desktop launch resolves app-data under the Tauri identifier; the first such launch copies the legacy directory once and stamps it; a mixed-flavor directory refuses with a named message; `docs/data-locations.md` describes both locations.

## Not in scope

Downgrade UX and the CHANGELOG-on-every-launch symptom (#1792, wave 8 E2-upgrade — it inherits a directory that is no longer shared). Envelope forward-compat (#1791). The post-v1.0 policy question "do old npm versions stay installable" — Bryan's, and unaffected by this fix. `token_store.rs`'s independent path derivation and the shared `tandem-integrations` keychain namespace. Quiescence detection for a legacy writer active during the copy: not built, and the risk is bounded by copy-only + legacy-intact.
