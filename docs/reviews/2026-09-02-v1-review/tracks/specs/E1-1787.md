# E1 — #1787 Desktop sidecar and npm global share one app-data directory

Branch `fix/desktop-core-1761`. Closes #1787 (both halves: the env-var mismatch, and decision D). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area row `docs/reviews/2026-09-02-v1-review/areas/upgrade-path.md:16`; decision D at `docs/reviews/2026-09-02-v1-review/decisions.md:30`. Probe: `tests/server/app-data-owner.test.ts` (new) + `cargo test`; the alternating-install case is a smoke line (Bryan).

## Problem

`src-tauri/src/sidecar.rs:1547` sets `TANDEM_DATA_DIR` to Tauri's `app_data_dir()`. `resolveAppDataDir()` (`src/server/platform.ts:10-14`) reads **`TANDEM_APP_DATA_DIR`**, which nobody sets, and falls back to `envPaths("tandem", {suffix:""}).data`. `TANDEM_DATA_DIR` is used for exactly two things: the `sample/welcome.md` base (`index.ts:653`) and the bundled-doc-dirs exclusion derived from it (`mcp/server.ts:153`). So the desktop sidecar and an npm-installed `tandem` share `sessions/`, `last-seen-version`, `integrations.json`, the annotation envelope dir, doc backups, and (once the gate is live) `trial.json` / `license.json` — a documented, supported both-installed state. Alternating versions re-opens CHANGELOG on every launch of both; every downgrade hazard is reachable with no downgrade; after the flip an old npm build is a one-command gate bypass over the same license files.

The desktop already *has* a private directory — `app_data_dir()` resolves under the `com.tandem.editor` identifier, not `tandem` — it simply is not handed to the resolver.

**One consequence of separating them, established in round 1 and accepted rather than mechanised here.** The annotation store lock is per-app-data-root (`annotations/store.ts:67`, `:166`), so today it is the cross-flavor mutual exclusion; after separation each flavor holds its own. That is a doc line, not code. (The install-id / scratchpad-recovery consequence is the scope cut below.)

## Fix

Two changes, matching decision D's two clauses. **Directory separation is the mechanism; the stamp is the guard that makes any residual sharing loud rather than silent.** A version stamp alone cannot work, and the reason belongs in the PR body: an already-released `tandem-editor` has no code to read one.

**1. Separation (the env-var half), through a named seam so the one line that carries it is pinned.** `src-tauri/src/sidecar.rs:1541-1569` builds the child's environment inline on the `cmd` builder, so `.env("TANDEM_APP_DATA_DIR", …)` would be a line no test can observe — and **omitting it does not merely leave the bug, it makes the npm `tandem` refuse to start**: `resolveAppDataDir()` would still return the legacy `envPaths` root, the desktop would claim *that* directory with `flavor: "desktop"`, and the next npm run would hit the flavor refusal below and exit.

- Extract the pairs into a module-level pure function — `fn sidecar_env_pairs(app_data_dir: &str) -> Vec<(&'static str, String)>` — returning at least `TANDEM_TAURI_SIDECAR`, `TANDEM_DATA_DIR`, `TANDEM_APP_DATA_DIR`, `TANDEM_PORT`, `TANDEM_MCP_PORT`, `TANDEM_BIND_HOST`; `start_sidecar` folds it onto the builder. The `Option`-gated conditional pairs (`TANDEM_AUTH_TOKEN`, `TANDEM_CHANNEL_DIST`, `TANDEM_STDIO_BRIDGE_DIST`, `:1571-1580`) stay where they are.
- `TANDEM_DATA_DIR` and `TANDEM_APP_DATA_DIR` take the **same** value; extend the comment to say the first names the *resource/sample* base and the second the *state* root. `strip_win_prefix` is already applied (`:1477`); keep it. No change to `resolveAppDataDir`.

**2. Ownership stamp + one-time migration.** New `src/server/app-data-owner.ts`, one exported async `claimAppDataDir(appDataDir, version, flavor)`:

- **Failure contract, first: `claimAppDataDir` must never throw.** It is called near the top of `main()`, and `main().catch(…) => process.exit(1)` (`index.ts:784`) makes any escaping error a startup abort — for the desktop that is `wait_for_health` failing through `MAX_RESTARTS` into the "Retry Server Start" dialog, i.e. an app that never starts with no in-product recovery. Everything else at that altitude is deliberately best-effort and wrapped (the backup sweep at `:299-311`, the trial clock at `:315-326`); this must be too. Concretely: `fs.mkdir(appDataDir, {recursive: true})` **before any write** (the first-ever desktop launch writes into a directory `app_data_dir()` merely names — an unguarded write is ENOENT); and a total catch around the migration and around the stamp read/write, logging to stderr and returning `"claimed"` **without** writing the stamp, so the next launch retries rather than recording a copy that did not happen. Two reachable throws it must absorb: `fs.cp` over a legacy tree a live npm instance is writing (EBUSY/EPERM on Windows, ENOENT on a `.tandem-tmp-*` that vanishes mid-walk — `docs/data-locations.md:37-40` documents those temps as normally present), and any failure of the stamp I/O itself. It may return `refused`; it may not throw.
- Stamp file `<app-data>/owner.json`, `{"version": "<APP_VERSION>", "flavor": "desktop" | "npm"}`. `flavor` is `process.env.TANDEM_TAURI_SIDECAR === "1" ? "desktop" : "npm"` — already set at `sidecar.rs:1546`, so no new writer (adding one would widen accepted finding #1599).
- **Refusal rule, on `flavor`, not on version ordering:** if a stamp exists and its `flavor` differs from ours, print to stderr and refuse. **Why flavor:** an older build cannot read the stamp at all, so a version-ordered rule protects nothing separation has not already made impossible, while a flavor rule catches exactly the mixing decision D names — robust in both directions, and needing no semver comparator (`version-check.ts` has none; adding one is #1792's job, wave 8). `version` is recorded so the message can name the owner; it is not itself a gate.
  - **The message is flavor-aware.** npm arm: `[Tandem] This app-data directory (<dir>) belongs to the desktop install (last used by v<version>). Refusing to share it. Set TANDEM_APP_DATA_DIR to run against a different directory.` Desktop arm **omits** that sentence — the sidecar sets the variable explicitly on the child and an explicit `.env()` overrides the inherited value, so the remedy is inert there — and says instead: `… Quit the npm \`tandem\` and relaunch, or remove <dir>/owner.json if you are certain no npm install uses this directory.`
- Same flavor, any version → overwrite the stamp and proceed. Absent → write and proceed.
- **Migration, once, copy-only, filtered.** Before writing a *first* stamp, and only when `flavor === "desktop"` and `appDataDir !== envPaths("tandem",{suffix:""}).data` and that legacy dir exists: `fs.cp(legacy, appDataDir, {recursive: true, force: false, errorOnExist: false, filter})`. The app-data root holds only Tandem's own state — user documents live wherever the user put them and are referenced by path. The legacy directory is left **intact**, and `force: false` means an existing target file wins, so a retry cannot clobber state the desktop has since written. The filter refuses four things:
  1. `owner.json` — **the stamp is the only file never copied, and that is what makes it the completion record.** `fs.cp` gives no ordering guarantee, so a legacy `owner.json` copied before an interruption would leave a foreign-flavor stamp and make every subsequent desktop launch refuse: permanently unstartable, with the refusal message pointing at an env var rather than at a file to delete. Excluding it means an interrupted copy leaves no stamp and retries next launch.
  2. `annotations/store.lock` — `acquireStoreLock` returns `"readonly"` while `isPidAlive(lock.pid)` (`annotations/store.ts:166-205`, `:243`), and `releaseStoreLock` (`:371`) unlinks under the *releasing* process's own dir, never the copy. A copied lock holding a live npm PID makes the migrated directory read-only for annotations and never clears.
  3. In-flight temporaries — any `*.tmp` / `*.tmp-*` basename. A partial atomic-write temp copied under `force: false` becomes permanent.
  4. The auth-token file (`TOKEN_FILE_NAME`) — `src/shared/auth/token-file.ts:6-8` derives its path from `envPaths("tandem",{suffix:""}).data` **directly** and ignores `TANDEM_APP_DATA_DIR`, deliberately (`install-id.ts:34-36`). A copy in the desktop directory has no reader, is never rotated by `/api/rotate-token`, and never gets `readTokenFromFile`'s 0600 repair — it is only a second copy of a secret.
- **Placement. One order, stated identically in both specs: probe (HTTP only) → claim → sweep → trial → lock.** Call `claimAppDataDir` once from `src/server/index.ts` in **both** transport modes, after `initSidecarCrashReporting()` (`:292`) and before the backup sweep (`:299`), the trial clock (`:315`) and the store lock (`:332`) — all three read `resolveAppDataDir()`, so claiming after them would sweep and stamp two different directories. In HTTP mode E1-1758's probe runs immediately before the claim (a refusal exits before anything is written); in stdio mode there is no probe at this altitude, so the claim is simply the first thing after crash reporting. `index.ts` owns the `process.exit(1)` on a `refused` result.
- **Docs:**
  - `docs/data-locations.md` — add the desktop row (`app_data_dir()` under `com.tandem.editor`) beside the npm `env-paths` row; one line that the two are separate and the desktop copies the npm directory once on first launch after this version, with what the copy excludes; one line that the annotation-store lock is now per-flavor, so running both flavors against the same document on different ports lets each write its own durable envelope and neither sees the other's; one line that scratchpad recovery drafts do not survive the move (see the scope cut). Mark the `auth-token` row (`:27` table) **npm-location-only**. Make manual-cleanup step 1 (`:148`) name **both** directories. Check `tests/docs/session-file-claims.test.ts` for a `SESSION_DIR`-parent claim before editing.
  - `src/client/utils/install-id.ts:28-31` — its docblock states the now-reversed claim that an npm-global install and the desktop app "both resolve the default root, so they share one id". Correct that paragraph; it is a false statement after this change.
  - **Record the substitution against decision D.** D is minuted as "refuses to share its data dir with an older server (**version stamp**)"; what ships gates on `flavor`. Amend the decision-D row (`docs/reviews/2026-09-02-v1-review/decisions.md:30`) and the sweep ledger to say flavor, with the one-sentence reason.
- **`tests/docs/config-writer-set-claims.test.ts` needs a row.** `DURABLE_WRITER_FILES` pins every file in all of `src/` that durably writes and how many times (`:44-47`, map at `:230-258`), so `src/server/app-data-owner.ts` gets one. It is a new durable writer outside `SCAN_ROOTS`, **not** a config writer, so `docs/security.md`'s accepted #1599 entry is unchanged. `fs.cp` is not in that test's `DURABLE_WRITE` idiom list, so the row covers the stamp write only.

**Known residuals, named in the PR body, not fixed here:** (a) two independent derivations of the legacy path survive — `src-tauri/src/token_store.rs`'s `data_dir()` in Rust and `src/shared/auth/token-file.ts:6-8` in Node, the latter deliberately ignoring `TANDEM_APP_DATA_DIR`; neither is a functional break (the OS keyring is primary and the shell passes `TANDEM_AUTH_TOKEN`, which `loadOrCreateToken` prefers, `token-store.ts:64-69`), and they are why the migration excludes the token file. (b) The migrated `doc-backups/` tree is hardened at the **next backup write**, not at copy time: `ensureBackupRootHardened` runs before anything reads or writes the tree (`file-io/doc-backup.ts:512`) and its inheritable grant explicitly repairs subdirs already on disk (`:175-181`), so no explicit re-hardening call is needed here. (c) `keychain.rs`'s `tandem-integrations` service namespace is shared with the npm CLI deliberately (its docblock) and is out of scope.

## Tests

New `tests/server/app-data-owner.test.ts`, all against `mkdtemp` dirs:

1. No stamp → writes `{version, flavor}` and resolves `"claimed"`.
2. Same flavor, different version → overwritten, claimed. **Kills** a rule that refuses on any version difference, which would brick every upgrade.
3. Different flavor → refuses. Assert the *result*, not an exit: `claimAppDataDir` returns a discriminated `"claimed" | {refused: {flavor, version}}` and `index.ts` owns the `process.exit(1)`.
4. Corrupt / non-JSON / missing-field stamp → treated as absent (claimed, overwritten). **Kills** a throw that would make a truncated write unrecoverable.
5. Migration: legacy dir with `sessions/a.json` + `annotations/b.json`, empty target, `flavor: "desktop"` → both copied, legacy still present, stamp written. Re-running does **not** re-copy a file deleted from the target in between. **Kills** a migration keyed on anything but the stamp, and one that moves instead of copies.
6. **Exclusion filter, one assertion per excluded item, plus the interrupted-copy recovery.** Legacy dir holds `owner.json` (`flavor: "npm"`), `annotations/store.lock`, a `*.tmp` file and the auth-token file, alongside `sessions/a.json` and `doc-backups/y.md`. After the desktop claim: none of the four is in the target, both of the others are, and the target's stamp reads `desktop`. Then **delete the target stamp** (an interruption after the copy, before the stamp) and re-run — it must claim again, not refuse. **Kills** a wholesale `fs.cp` with no filter, whose two worst outcomes are a copied live lock (target read-only forever) and a copied npm stamp (app permanently unstartable).
7. `flavor: "npm"` with a legacy dir that differs → **no** copy. **Kills** a migration that fires for the npm install too.
8. **`claimAppDataDir` never throws.** A migration whose copy fails (an unreadable legacy entry, or `fs.cp` stubbed to reject) → resolves `"claimed"`, writes **no** stamp, and the next call re-attempts the migration. Same for a rejecting stamp write. **Kills** the startup abort: an escaping error reaches `main().catch(…) => process.exit(1)` and, for the desktop, becomes an app that never starts.
9. **The sidecar exports both env vars.** `src-tauri/src/sidecar.rs`, `#[cfg(test)]`: `sidecar_env_pairs("/tmp/x")` contains `TANDEM_DATA_DIR` and `TANDEM_APP_DATA_DIR` with equal values. **Kills** dropping the one line that is the entire separation half — which does not merely leave the bug, it makes the npm `tandem` refuse to start once the desktop has claimed the legacy directory.

## Done when

The sidecar exports `TANDEM_APP_DATA_DIR` **and test 9 pins it**; a desktop launch resolves app-data under the Tauri identifier; the first such launch copies the legacy directory once — excluding the stamp, the store lock, temporaries and the auth token — and stamps; **`claimAppDataDir` never throws, and a failed migration leaves no stamp so the next launch retries**; an interrupted migration retries rather than refusing; a mixed-flavor directory refuses with a flavor-appropriate message and `index.ts` exits 1; `docs/data-locations.md` describes both locations, the exclusions, the per-flavor store lock, the npm-only `auth-token` row, the two-directory cleanup step and the one-time scratchpad-recovery loss; `install-id.ts`'s shared-id paragraph is corrected; decision D's row says flavor; `app-data-owner.ts` has its `DURABLE_WRITER_FILES` row.

## Review corrections (round 1 and round 2)

**Adopted (carried forward)**

- **BLOCKING — the migration needed an exclusion filter.** A copied `owner.json` bricks startup; a copied live `store.lock` makes the migrated directory read-only forever. Both are filter entries with a test each.
- **BLOCKING — `claimAppDataDir` had no failure contract.** It is called where `main().catch(…) => process.exit(1)` turns any throw into an app that never starts. It now `mkdir`s first, catches everything, and returns `"claimed"` without a stamp so the next launch retries. Test 8.
- **BLOCKING — the `.env("TANDEM_APP_DATA_DIR", …)` line was pinned by nothing, and dropping it ships a new hard failure for npm users.** The env pairs are extracted into `sidecar_env_pairs` with test 9.
- **NON-BLOCKING — refusal on flavor, not version ordering** (an older build cannot read the stamp), with the substitution recorded against decision D.
- **NON-BLOCKING — placement contradicted E1-1758.** Both specs now state one order: probe (HTTP only) → claim → sweep → trial → lock.

**Not adopted** — None.

## Review corrections (scope cut)

**Removed**

- **The entire install-id / `legacyStoragePath` continuity mechanism** — returning the legacy root from `claimAppDataDir`, publishing `legacyStoragePath` in the `/api/info` deps and handler, the `info.ts:52` docblock enumeration edit, the read-fallback in `useScratchpadPersistence.svelte.ts` across both the direct key and the `scratchpadLatestKey` pointer chain, and its two tests (old 11 and 14). This is a second feature the issue did not ask for, spanning three modules the issue does not name. **The loss it prevented is now accepted and recorded**: unsaved scratchpad drafts held in localStorage under the old install id become unreachable once, at the first desktop launch after this ships. It is bounded (unsaved scratchpads only, one time, nothing on disk is lost), and the spec's own round-1 text names acceptance as the alternative. It goes in `docs/data-locations.md`, the PR body and a smoke line. `src/client/utils/install-id.ts` keeps only its one-line docblock correction, because that paragraph states something this change makes false.
- **Exporting `ensureBackupRootHardened` and calling it from the migration, with its `vi.mock` test (old test 10).** Verified in source that it is unnecessary: `doc-backup.ts:512` calls it before anything reads or writes the tree, and `:175-181` documents the inheritable grant as *repairing* subdirs already on disk. The migrated root is therefore hardened at the next backup write with no new code; the window is recorded as residual (b).
- **The `.broken-backups/` exclusion (old filter item 5).** Forensic copies of corrupted config files that nothing in the destination reads — a hardening refinement, not a defect if copied. Dropping it removes a filter entry and the ACL reasoning attached to it; the four entries that remain each prevent a concrete, named failure.
- **Old test 6 as a separate case.** The legacy-`owner.json` assertion is one line of test 6's exclusion sweep, where the interrupted-copy re-claim already lives.
