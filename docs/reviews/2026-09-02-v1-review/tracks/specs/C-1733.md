# C — #1733 Server-side mode provenance: record which connection last wrote `mode`

Branch `fix/privacy-and-authority-1769`. Closes #1733, scoped as the sweep ledger says: the conditional release lands under C-1769; this spec is **the provenance field and nothing more**. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:80`. Probe: the v0.24.1 measurement in the issue body (`tandem_status` said `solo` for minutes while the toggle read Tandem, with no signal on either side).

## Problem

The client-side detector (`useTandemModeBroadcast.svelte.ts:235-266`) compares the room against `lastBroadcast`, so it sees only disagreements this client is party to and can never say WHO wrote the other value. The server can: every client write reaches CTRL_ROOM through Hocuspocus, which applies it with the `Connection` as the transaction origin (`node_modules/@hocuspocus/server/dist/hocuspocus-server.esm.js:1408` — `connection ?? this.defaultTransactionOrigin`; `Connection` carries `socketId`, `:1456-1470`). Server-side writes carry a helper tag string (`shared/origins.ts:33-73`), and the ctrl-session restore applies with no origin at all (`session/manager.ts:827`). Nothing records any of it, so `tandem_status` (`mcp/document.ts:1341`) and `tandem_checkInbox` (`awareness.ts:386`) report a value with no provenance.

## Fix

- **`src/server/mode.ts`** — this file is pinned as a reader by `tests/shared/mode-writer-set.test.ts` ("keeps every mention-only file free of awareness-map writes"): the addition observes and never writes. Add:
  - `export type ModeProvenance = ({ source: "client"; connection: string } | { source: "server"; origin: string } | { source: "restore" | "unknown" }) & { at: number; value: ModeState }`. `value` is `readModeState()` taken at observation time — see "what the field means" below.
  - A module-level `let lastModeWrite: ModeProvenance | null = null`, `export function readModeProvenance(): ModeProvenance | null`, and **`export function _resetModeProvenanceForTests(): void`** (the `queue.ts#resetForTesting` pattern, underscore-prefixed like `_resetClientLog`). Module state with no reset makes every "is `null`" assertion depend on suite order — and clearing it from the unobserve cleanup is the WRONG reset: `attachCtrlObservers` runs every cleanup before re-installing (`queue.ts:533-543`), so a mid-session Hocuspocus swap would relabel the live value as `restore`. `mode-writer-set`'s third describe forbids `.set(` shapes, not exports, so this is admissible.
  - `export function installModeProvenanceObserver(ctrlDoc: Y.Doc): () => void`: observes `ctrlDoc.getMap(Y_MAP_USER_AWARENESS)` (Critical Rule 1 — both keys from `shared/constants.ts`); on `event.keysChanged.has(Y_MAP_MODE)` classify `txn.origin`: an object with a string `socketId` → `client` with `connection: socketId.slice(0, 8)` (an opaque per-connection tag — `Connection.socketId` is a `uuid.v4()` (`hocuspocus-server.esm.js:2068`) that Tandem keys no auth or identity on, `grep -rn socketId src/` is empty — enough to tell two windows apart; never the socket, the request or headers); a string → `server` with `origin` = the tag (`"internal"`, `"test"`, …); anything else → `unknown`. At install time, if the key is already present AND nothing is recorded, set `{ source: "restore", at: Date.now(), value }` — `restoreCtrlSession` runs before `attachCtrlObservers` (`src/server/index.ts:488` and `:506`, re-verified this round), so the replayed write is never observed and this is the only honest label for it. The `nothing is recorded` conjunct is load-bearing: the production swap (`yjs/provider.ts:171-172`) copies the old doc's state, so the mode key IS present on the new doc when `reattachCtrlObservers` re-installs, and without the conjunct a live `client` record would be relabelled `restore` mid-session. Test 5 (c) is the row that kills dropping it. Returns the unobserve cleanup.
  - **The link to the real shape is a type-level pin, not a comment.** The `{ socketId: string }` origin the tests fabricate is tied to hocuspocus by `const _connectionShape: { socketId: string } = {} as import("@hocuspocus/server").Connection;` in the new suite — `npm run typecheck:tests` evaluates it (`tsconfig.tests.node.json`), so a rename or removal of `Connection.socketId` on upgrade reds the suite instead of leaving production recording `unknown` forever. Put the one-line comment naming it as that link beside it.
  - **What the field means, precisely:** it names the last TRANSACTION that touched the key, not necessarily the writer of the value `mode` reports. Under a lost concurrent tie (the #1621 shape) the losing write still puts `Y_MAP_MODE` in `keysChanged` (`mode-writer-set.test.ts:9-15`; Yjs computes `keysChanged` from the changed parent subs regardless of which item ends rightmost), so `modeProvenance` can say "client X" while `mode` carries another writer's value — which is the one case the field exists to diagnose. Recording `value` at observation time is what lets a later reader see the two diverge; the docblock says this in one sentence.
- **`events/queue.ts:533` `attachCtrlObservers`** — push `installModeProvenanceObserver(ctrlDoc)` into `ctrlCleanups`, so `reattachCtrlObservers` re-installs it after the Hocuspocus doc swap (CLAUDE.md, `onDocSwapped`). `queue.ts` already imports `readModeState` from `../mode.js` (`:21`). Re-install must NOT reset `lastModeWrite` (test 5).
- **Surface it, additively.** `tandem_status` read mode (`document.ts:1352-1367`) adds `modeProvenance: readModeProvenance()`; `tandem_checkInbox` (`awareness.ts`, beside `mode` in the structured result) adds the same. `output-schemas.ts`: one `modeProvenanceSchema` (`z.object({ source: z.enum([...]), at: z.number(), value: z.enum(["solo","tandem","indeterminate"]), connection: z.string().optional(), origin: z.string().optional() }).nullable()`), added as `.optional()` on `statusOutputShape` (`:141`, beside `mode`) and required-nullable on `checkInboxOutputShape` (`:243`). The MCP SDK hard-validates structured output (`awareness.ts:648-653`), so the schema must admit every shape the union produces — pin it with the round-trip test below.
- **`docs/mcp-tools.md`** `:432-446` (status return) and `:1016-1040` (checkInbox return + notes): one line each — `modeProvenance` says who last wrote the mode key (`client` + connection tag, `server` + origin, `restore`, `unknown`), when, and what the key read at that moment; `null` before any write is observed. **Say of `connection`: "an opaque per-connection tag, not a credential; never the socket, request or headers"**, so nobody widens it. The field reaches `tandem_status`/`tandem_checkInbox` only (MCP: loopback, or token-gated on LAN) — **keep `modeProvenance` off `GET /api/mode`** (`api-routes.ts:391`, LAN-readable). **Say "the last write that touched the key — under a lost concurrent tie this is not necessarily the writer of the reported `mode`; compare `value` against `mode`"**, so the line cannot be read as agreement.
- `EXPECTED_MENTIONS` in `mode-writer-set.test.ts` is **unchanged by THIS spec** — `mode.ts`, `document.ts` and the hook already mention `Y_MAP_MODE`; `awareness.ts` reads provenance through the function, not the constant. C-1769 is the one edit to that file in this PR (it drops `routes/mode-release.ts` from the mention list and moves the write count); a resumed implement stage must not revert that.

## Tests

`tests/server/mode-provenance.test.ts`, fixture from `mode-release.test.ts:42-49` (`setMode` under `withInternal`) plus the sync-first remote-write shape from `tests/client/tandem-mode-race.test.ts:88-93` (sync ctrl → scratch, write, apply the delta to ctrl) with a `{ socketId: "0123456789abcdef" }` origin. `beforeEach` calls `_resetModeProvenanceForTests()` and `resetForTesting()`; the type-level `Connection` pin sits at module scope.

1. Install on an empty ctrl doc → `readModeProvenance()` is `null` (kills a default that fabricates `restore`; meaningful only because of the reset).
2. Apply a `"solo"` write with the socket-shaped origin → `{ source: "client", connection: "01234567", at, value: "solo" }`; `at` within the test's clock bounds. A second write with a different `socketId` replaces it (kills "first writer wins").
3. `withInternal` write → `{ source: "server", origin: "internal", value }`; `Y.applyUpdate` with no origin → `unknown`.
4. Seed the key BEFORE install (the restore order) → `restore`; then a client write overrides it.
5. **Reattach, made observable.** `attachCtrlObservers` takes no doc and re-fetches CTRL_ROOM itself, so a plain `reattachCtrlObservers()` on the same doc cannot distinguish an observer that would have died — use `removeDocument(CTRL_ROOM)` (`yjs/provider.ts:64`; `annotation-promote-pull-surface.test.ts` already does this), **then, BEFORE `reattachCtrlObservers()`, apply the OLD doc's state to the new ctrl doc (`Y.applyUpdate(newCtrl, Y.encodeStateAsUpdate(oldCtrl))`, exactly as the production swap at `provider.ts:171-172` does — or seed the mode key under `withInternal`) so the key is PRESENT on the new doc at install time**; `removeDocument` alone yields a key-less doc, on which the `nothing is recorded` guard has no killing row. Then assert (a) a client write on the NEW ctrl doc is recorded, (b) the pre-swap `client` record is still there immediately after reattach with `source` unchanged (kills both a reset in the cleanup AND a relabel-as-`restore` when the key is present), and (c) `vi.spyOn(map, "observe")` / `"unobserve"` counts on the old map — the `tandem-mode-race.test.ts:399-431` pattern — show exactly one unobserve on the old doc and one observe on the new.
6. Handler round-trip in `tests/server/mcp-tool-integration.test.ts` (`setupMcpClient()`, `:54-66`): after a socket-origin write, `tandem_status` and `tandem_checkInbox` both carry `modeProvenance.source === "client"` and `modeProvenance.value`; before any write (after the reset) both carry `null` — the structured-output validation is what this pins (a schema that omits `connection` or `value` throws `InvalidParams` on the whole response).

## Done when

Six cases green; both tools carry the field; docs updated with the "last write that touched the key" wording; `mode-writer-set` green with C-1769's edit and nothing else.

## Not in scope

Acting on the provenance (adopting, warning in the UI; C-1769's follow-up issue names it as the hook for server-side aggregation); any write to the mode key; naming the connection beyond an opaque tag; the client-side detector.

## Review corrections (round 1)

Adopted:

- Module-level state with no reset (three findings): `_resetModeProvenanceForTests()` exported and called from `beforeEach`; test 5 now pins that reattach does NOT reset.
- Fabricated origin untied to hocuspocus's shape: type-level `Connection` pin in the suite.
- Reattach test cannot discriminate: test 5 rebuilt on `removeDocument(CTRL_ROOM)` plus observe/unobserve spies.
- Provenance names the last touch, not the reported value's writer: doc wording changed and `value` recorded at observation time.
- `EXPECTED_MENTIONS` "unchanged" contradicted C-1769: reworded to "unchanged by THIS spec".

Not adopted:

- **Classify `socketId: 'server'` as `server`.** The two literals at `hocuspocus-server.esm.js:2329,2345` are the `socketId` field of the hook CONTEXT objects `DirectConnection` passes to `storeDocumentHooks`, not transaction origins; `DirectConnection.transact` (`:2316`) applies with whatever `transactionOrigin` its caller passes, and `grep -rn DirectConnection src/` returns nothing — Tandem never opens one. A classification branch for an origin that cannot occur would be untestable against anything real. If a future direct connection is added, the type-level pin and test 3's `unknown` row are where it surfaces.
