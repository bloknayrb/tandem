# Gc2b — #1778 Four `aria-modal` dialogs have no Tab trap, seven radiogroups carry `tabindex="0"`, the shipped `useRadioGroup` is untested and the tested one is dead

Branch `fix/keyboard-and-a11y-1777`. **Closes #1778.** Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-ui.md:20-21`. Probe: `tests/e2e/keyboard-a11y.spec.ts` — Playwright verified that focus leaves the command palette on the second Tab (walking the titlebar, tabs and rail) and the file-open dialog on the first.

## Problem

1. **No Tab trap.** `components/CommandPalette.svelte`, `components/FileOpenDialog.svelte` and `components/ModelEditModal.svelte` declare `aria-modal="true"` with zero Tab handling; `components/FirstRunModelPickerModal.svelte` has an `onkeydown` that deliberately lets Tab through (`if (e.key !== "Tab") e.stopPropagation();`) with nothing at the other end to catch it. `aria-modal="true"` tells assistive tech everything outside is inert while real focus walks the app. `utils/focus-trap.ts` exists and is used by `SettingsModal` and `LicenseWall`.
2. **Double tab stops.** Seven of eight `role="radiogroup"` containers carry `tabindex="0"` — four in `components/AppearanceSettings.svelte` (theme, default tab, text size, density) and three in `components/EditorSettings.svelte` (measure, editor font, font-by-extension). Every one of them already gives its `role="radio"` buttons a roving `tabIndexFor(...)`, so the container is a second, redundant stop that lands on a non-interactive div. `panels/ChipGroup.svelte` uses `tabindex="-1"` and is the in-repo precedent.
3. **The tested hook is dead.** `hooks/useRadioGroup.ts` (`useRadioGroup`) has 108 lines of tests in `tests/client/useRadioGroup.test.ts` and **zero importers in `src/`**. `hooks/useRadioGroup.svelte.ts` (`createRadioGroup`) is what all three components import and has zero test references — including the `radios?.[domIdx]?.focus()` call that is the only behavioural difference between them.

## Fix

**(1) Trap.** For each of the four, the `SettingsModal` precedent — a window-level `keydown` listener in an `$effect`, not an element `onkeydown`:

```ts
$effect(() => {
  if (!open) return;                       // gate per component, see below
  const handler = (e: KeyboardEvent) => trapTab(e, dialogEl ?? null);
  window.addEventListener("keydown", handler);
  return () => window.removeEventListener("keydown", handler);
});
```

Window-level rather than on the dialog node because `trapTab`'s recover-focus branch is the half that matters here: a click on the dialog's own padding leaves `document.activeElement` on `<body>`, and an element handler never fires again once focus is outside. `FirstRunModelPickerModal` already lets Tab bubble for exactly this shape.

- `CommandPalette` — always mounted, `{#if open}` inside, so gate on `open` (matching its own `onMount` Escape listener). Container: the `.palette-modal` div (`bind:this`), which carries `role="dialog"`/`aria-modal`; its `tabindex="-1"` keeps it out of its own focusables and `trapTab` handles `active === container` on Shift+Tab.
- `FileOpenDialog` — mounted conditionally by `App.svelte`, so no gate; `$effect` mount/cleanup is the lifecycle. Container: the outer `role="dialog"` div (`bind:this`).
- `ModelEditModal` — conditionally mounted; container: the `.mem-scrim` `role="dialog"` div.
- `FirstRunModelPickerModal` — conditionally mounted; it already has `dialogEl` bound. Add the effect; leave the `if (e.key !== "Tab") e.stopPropagation()` line alone.

Both model modals ship **dark** (`BYO_MODELS_ENABLED` is a `const false`) — say so in the PR body; the change is byte-identical in shape to the two reachable ones and costs nothing at flip time.

`focus-trap.ts`'s `offsetParent !== null` filter (the `position: fixed` note in the issue) does **not** bite here: all four containers are the fixed element, and `querySelectorAll` only returns descendants, whose `offsetParent` resolves to that positioned ancestor. It would bite only on a focusable that is itself `position: fixed`, and none of the four has one. Record that in the PR body so the next reader does not re-derive it.

**(2) Radiogroups.** Change `tabindex="0"` → `tabindex="-1"` on the seven containers. No other change: the roving `tabIndexFor` on the radios is already correct and `handleKeyDown` still fires because focus is inside the container.

**(3) The dead hook.** Delete `src/client/hooks/useRadioGroup.ts` and re-point `tests/client/useRadioGroup.test.ts` at `createRadioGroup`, adapting the call (`value` → `() => value`) and adding the two cases the shipped implementation has and the dead one does not:
- `handleKeyDown` calls `.focus()` on the radio at `values.indexOf(nextValue)` inside `e.currentTarget` — construct a container with `role="radio"` buttons, dispatch ArrowRight with `currentTarget` set, assert `document.activeElement`.
- The same with a **disabled** value in the middle: `enabled` is filtered but `domIdx` indexes `values`, so this pins which of the two lists the DOM index is taken from. Whatever the current behaviour is, assert it as-is — this is a characterization test for a shipped path, not a redesign.

## Tests

- `tests/client/dialog-focus-trap.test.ts` (new, happy-dom, `@testing-library/svelte`) — per dialog: render it open, focus the last focusable inside, dispatch a `Tab` keydown on `window`, assert `e.defaultPrevented` and that `document.activeElement` is still inside the container; then Shift+Tab from the first. Plus the recovery case: `document.body.focus()`, Tab, assert focus is pulled back in. `focusablesWithin` is already proven to work in happy-dom by `tests/client/focus-trap.test.ts`. `FileOpenDialog` has a render harness in `tests/client/FileOpenDialog.test.ts` — copy its mocks. Cover `CommandPalette` and `FileOpenDialog`; add the two dark modals only if their prop shapes render without new mocks, and say in the PR body which were covered.
- `tests/e2e/keyboard-a11y.spec.ts` — the two reachable dialogs, since this is where the bug was measured: open the command palette, press Tab three times, assert `document.activeElement` is still inside `[data-testid='command-palette']`; same for `[data-testid='file-open-dialog']` on the first Tab. Three presses, not one — the palette's reported failure is on the *second*, and a single-press assertion passes today.
- Radiogroups: extend `tests/e2e/keyboard-a11y.spec.ts`'s existing "no element uses a positive tabindex" neighbourhood with a Settings case — open Settings → Appearance, Tab from the section above the Theme group, assert the next focused element is the checked `role="radio"` button and not its container. A count-of-tab-stops assertion is what kills a fix that changes only some of the seven.
- `tests/client/useRadioGroup.test.ts` — retargeted as above. Deleting the dead module makes the old import a hard failure, so there is no way to land half of this.
