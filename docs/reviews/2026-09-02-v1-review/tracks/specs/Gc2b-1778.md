## Problem

1. **No Tab trap.** `components/CommandPalette.svelte`, `components/FileOpenDialog.svelte` and `components/ModelEditModal.svelte` declare `aria-modal="true"` with zero Tab handling; `components/FirstRunModelPickerModal.svelte` has an `onkeydown` that deliberately lets Tab through (`if (e.key !== "Tab") e.stopPropagation();`) with nothing at the other end to catch it. `aria-modal="true"` tells assistive tech everything outside is inert while real focus walks the app. `utils/focus-trap.ts` exists and is used by `SettingsModal` and `LicenseWall`.
2. **Double tab stops.** Seven of eight `role="radiogroup"` containers carry `tabindex="0"` — four in `components/AppearanceSettings.svelte` (`:73,127,165,218`) and three in `components/EditorSettings.svelte` (`:153,184,231`). Every one already gives its `role="radio"` buttons a roving `tabIndexFor(...)`, so the container is a second, redundant stop on a non-interactive div. `panels/ChipGroup.svelte` (`:128`) uses `tabindex="-1"` and is the in-repo precedent.
3. **The tested hook is dead.** `hooks/useRadioGroup.ts` (`useRadioGroup`) has 108 lines of tests in `tests/client/useRadioGroup.test.ts` and **zero importers in `src/`**. `hooks/useRadioGroup.svelte.ts` (`createRadioGroup`) is what all three components import and has zero test references — including the `radios?.[domIdx]?.focus()` call that is the only behavioural difference between them.

## Fix

**(1) Trap.** For each of the four, the `SettingsModal` precedent — a window-level `keydown` listener in an `$effect`, not an element `onkeydown`:

```ts
$effect(() => {
  if (!open) return;                       // gate per component, see below
  const handler = (e: KeyboardEvent) => {
    const owner = (document.activeElement as Element | null)?.closest('[aria-modal="true"]');
    if (owner && owner !== dialogEl && !dialogEl?.contains(owner)) return; // another dialog owns focus
    trapTab(e, dialogEl ?? null);
  };
  window.addEventListener("keydown", handler);
  return () => window.removeEventListener("keydown", handler);
});
```

Window-level rather than on the dialog node because `trapTab`'s recover-focus branch is the half that matters: a click on the dialog's own padding leaves `document.activeElement` on `<body>`, and an element handler never fires again once focus is outside.

**The owner bail is required on all five listeners, including `SettingsModal`'s existing one, and that is one commit.** `trapTab`'s recover branch (`focus-trap.ts:57-62`) fires whenever focus is anywhere outside *its* container — including inside another open dialog — with no `defaultPrevented` check, so two live traps ping-pong within one keydown. Two stacks are reachable: `ModelEditModal` renders **inside** `SettingsModal`'s subtree (`settings-tabs/SettingsModelsTab.svelte:294`), and `CommandPalette` is always mounted with `App.svelte`'s `toggle-palette` dispatch carrying no `settingsModalOpen` gate, so Ctrl+Shift+P opens the palette over Settings. `SettingsModal.svelte:528-533` currently registers a bare `trapTab(e, modalEl ?? null)`; it is the **outer** dialog in both stacks and registered first, and `CommandPalette` is mounted at App level so `modalEl.contains(paletteInput)` is false — so with the bail on only the new handlers, Settings yanks focus back on every Tab while the palette dutifully defers. Give `SettingsModal` the identical three lines. `LicenseWall` does not need them: it is a full-screen gate with nothing stacked over it. Do **not** substitute a bare `if (e.defaultPrevented) return;` — `trapTab` preventDefaults only on the wrap and recover branches, so ordinary mid-dialog Tabs would still reach both handlers.

- `CommandPalette` — always mounted, `{#if open}` inside, so gate on `open` (matching its own `onMount` Escape listener). Container: the `.palette-modal` div (`bind:this`), which carries `role="dialog"`/`aria-modal`; its `tabindex="-1"` keeps it out of its own focusables and `trapTab` handles `active === container` on Shift+Tab.
- `FileOpenDialog` — mounted conditionally by `App.svelte`, so no gate; the `$effect` mount/cleanup is the lifecycle. Container: the outer `role="dialog"` div (`bind:this`).
- `ModelEditModal` — conditionally mounted; container: the `.mem-scrim` `role="dialog"` div.
- `FirstRunModelPickerModal` — conditionally mounted; `dialogEl` is already bound. Add the effect; leave the `if (e.key !== "Tab") e.stopPropagation()` line alone.

Both model modals ship **dark** (`BYO_MODELS_ENABLED` is a `const false`) — say so in the PR body; the change is byte-identical in shape to the two reachable ones and costs nothing at flip time.

`focus-trap.ts`'s `offsetParent !== null` filter (the `position: fixed` skip the issue points at) does **not** bite here, but state the reason precisely: **every focusable is a descendant of a `position: fixed` ancestor**, so its `offsetParent` is non-null. For `FileOpenDialog`, `ModelEditModal` and `FirstRunModelPickerModal` that ancestor is the trap container itself; for `CommandPalette` it is the `.palette-scrim` (`CommandPalette.svelte:376-384`) **wrapping** the container — `.palette-modal` (`:388-403`) is statically positioned, and its `transform` makes a containing block, not an `offsetParent`. The filter would bite only on a focusable that is itself `position: fixed`, and none of the four has one.

**(2) Radiogroups.** Change `tabindex="0"` → `tabindex="-1"` on the seven containers named above. No other change: the roving `tabIndexFor` on the radios is already correct and `handleKeyDown` still fires because focus is inside the container.

**(3) The dead hook.** Delete `src/client/hooks/useRadioGroup.ts` and re-point `tests/client/useRadioGroup.test.ts` at `createRadioGroup`, adapting the call (`value` → `() => value`). Add the one case the shipped implementation has and the dead one does not — the `.focus()` at `useRadioGroup.svelte.ts:48-52` — and **spell the harness out, because the obvious shortcut does not test the code**: `e.currentTarget` is `null` outside a real dispatch and the implementation's `container?.querySelectorAll(...)` / `radios?.[domIdx]?.focus()` optional chaining makes that a silent no-op, so a hand-built `{key:"ArrowRight", currentTarget: el} as any` passes even with the `.focus()` line deleted. Required shape: build a real container of `role="radio"` buttons, `container.addEventListener("keydown", handleKeyDown)`, then `radios[0].dispatchEvent(new KeyboardEvent("keydown", { key: "ArrowRight", bubbles: true }))`, and assert `document.activeElement === radios[1]`. Deleting the `.focus()` line must turn it red.
