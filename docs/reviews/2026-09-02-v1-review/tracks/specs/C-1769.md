# C — #1769 Solo privacy: the release route writes the mode unconditionally, and `heldInSolo` is stamped from the local window's mode

Branch `fix/privacy-and-authority-1769`. Closes #1769 (both holes in its body, with one named residual — see "Not in scope"). Ledger: `docs/reviews/2026-09-02-v1-review/areas/annotations.md:17-18`. Probe: none in the review — the race was source-confirmed only, so the reproduction below is written FIRST and must be red on `origin/master` before any fix lands.

## Problem

Hole 1 — `handleModeRelease` (`src/server/mcp/routes/mode-release.ts:85`) does `withModeRelease(ctrlDoc, () => awareness.set(Y_MAP_MODE, "tandem"))` with no read of the current value, then clears every `heldInSolo` marker on every open doc (`:96-102`) and wakes (`:104`). The client fires that POST from `setTandemMode` on the Solo→Tandem edge (`src/client/hooks/useTandemModeBroadcast.svelte.ts:300-302`); its own mode write goes over the CRDT socket (`:201`). Solo→Tandem→Solo inside the POST's latency leaves the room reading `"tandem"` while the toggle shows Solo — and the markers are gone, so even a restart cannot re-hold them. The hook's observer (`:235-266`) sees the disagreement and only logs (`:256-260`); the comment at `:224-229` names re-asserting Solo as "the case that actually breaks Solo's promise" and defers it.

Hole 2 — the persisted marker is stamped from the *local window's* rune: `Toolbar.svelte:807` (`heldInSoloOnCreate(type, tandemMode)`) and `panels/annotation-actions.ts:85` (promotion). Two windows with different localStorage (Tauri WebView + browser tab) disagree; a comment created from the Tandem-believing window into a Solo room is hidden live (`hideFromAI` reads the room, `mode.ts:88`) but carries no marker, so after a restart that loses the ctrl session (`readModeState() === "indeterminate"`, `mode.ts:89`) it is delivered. Replies are already stamped server-side from `readModeState()` (`lifecycle.ts:1174-1179`); annotations are not.

## Fix

Three edits plus one client ordering change, no new writer of the mode key, no new route.

1. **Conditional release** (`routes/mode-release.ts`). Delete the mode write at `:85` and the `Y_MAP_MODE` / `Y_MAP_USER_AWARENESS` / `CTRL_ROOM` imports it needed. At the top of the handler, after the two gates: `if (readModeState() !== "tandem") { res.status(409).json({ error: "MODE_NOT_TANDEM", message: "The room does not read Tandem; nothing was released.", data: { released: 0 } }); return; }` — written inline like `annotation-reply.ts:39` (`BAD_REQUEST`), not through `sendApiError`, so `_shared.ts` is untouched. `indeterminate` refuses too (fail closed, same reading as `queue.ts:168-174`). The marker sweep, the `released > 0` wake and the `withModeRelease` marker clears stay exactly as they are. **Do not add a `mode` body parameter**: a stale POST from the first toggle would carry `"tandem"` too — the room is the only witness.

   **Three docblocks describe the route as a mode WRITER and all three are rewritten**, because after this change each is a live instruction to do the thing the fix removed: (a) the route's own `:56-79` — step 1 becomes "verify the client's CRDT write has landed; answer 409 `MODE_NOT_TANDEM` otherwise", and the "verified live / almost always" paragraph (`:66-74`) is replaced by: *409 is definitive when the room reads Solo and transient when the POST outran the client's CRDT write — the client's delayed retry (item 1b) covers the second case; keep it.* (b) `events/queue.ts:176-180` (`shouldForwardExternally`): the route now *checks* that mode reads Tandem before the wake rather than writing it, which is what keeps `isUserPrivacyHeld` from dropping the wake. (c) `events/queue.ts:445-455` (`emitModeReleaseWake`): "The caller MUST have already set mode to Tandem (the release route does this first)" → "The caller MUST have VERIFIED that mode reads Tandem (the route's 409 arm is that guarantee)".

1b. **The client POST is ordered after its own CRDT write, and a 409 is retried with a delay** (`useTandemModeBroadcast.svelte.ts` `triggerSoloRelease`, `:17-44`). Review established the ordering the old docblock called "reliable" is not guaranteed: `setTandemMode` (`:296-303`) assigns the rune and calls `triggerSoloRelease()` in the same synchronous frame, so `fetch()` (`:28`) is issued before the broadcast `$effect` (`:178-206`) has even run — the effect flushes on a microtask. The two halves:
   - `await tick()` (from `svelte`) before the first `fetch`, so the broadcast effect has flushed and the WS frame carrying `"tandem"` is on the wire before the HTTP request is. This makes the retry the exception, not the mechanism.
   - Treat a 409 whose body `error` is `"MODE_NOT_TANDEM"` as "not landed yet": retry after 250 ms, at most 3 further attempts (4 POSTs total), then give up with `logClientWarning("tandem-mode", "release-refused-room-not-tandem")` — two static literals, never a `console.warn` (`tests/client/client-log-callsites.test.ts`; the observer at `:249-255` says why). A thrown fetch keeps today's single immediate retry. Any other non-ok status keeps today's behaviour. A retry that lands after a genuine Tandem→Solo flip still gets 409 — correct, the room is the witness — and a repeat POST after a successful release clears 0 and fires no second wake (existing idempotency, `mode-release.test.ts:158`).
   - Rewrite the docblock at `:17-24` ("flip mode server-side" is gone): the route *verifies* the room reads Tandem, clears the markers and wakes; the POST is still best-effort and pull is authoritative.

2. **Client re-asserts Solo, in one direction, and same-browser tabs follow the user's own toggle** (`useTandemModeBroadcast.svelte.ts`).
   - In the observer's `parsed.data === "tandem"` branch (`:258-260`), after `logClientWarning`, write `withBrowser(bootstrapYdoc, () => awareness.set(Y_MAP_MODE, "solo"))`. Only this branch re-asserts: a client holding Tandem never writes on disagreement, so there is no ping-pong — the re-assert is `transaction.local` on the way back into this observer (`:244`). `lastBroadcast` stays `"solo"`, `tandemMode` is untouched (no `$state` write inside the observer — the docblock at `:112-132` is why), and the release POST does not fire (it lives in `setTandemMode`). **What this buys is the steady state, not the race**: once the re-assert lands the room reads Solo; it does NOT make "two windows converge on Solo" a property of the release path — see the residual under "Not in scope". Critical Rule 2: `withBrowser`, as `:201` already does. This is a second `.set(Y_MAP_MODE` in the hook and the route loses its one: `tests/shared/mode-writer-set.test.ts` `EXPECTED_MODE_WRITES` becomes `[["src/client/hooks/useTandemModeBroadcast.svelte.ts", 2]]` and `EXPECTED_MENTIONS` drops `routes/mode-release.ts` (it no longer names the constant). Edit both lists on purpose and say why in their comments; this is the ONE edit to that file in this PR (C-1733 does not touch it).
   - **Same-browser tabs.** The rune is seeded from localStorage once (`:89-106`) and nothing listens for later changes (`:141-148`), so with the re-assert a background tab of the same browser that still holds `"solo"` would veto every Tandem toggle made in the foreground tab, forever, with only a `room-holds-solo-not-ours` line to show for it. Add a `window.addEventListener("storage", …)` in the hook (registered in its own `$effect` with the listener removed in the cleanup): on `event.key === TANDEM_MODE_KEY`, `TandemModeSchema.safeParse(event.newValue)` and, on success and a value different from the current rune, route it through `setTandemMode` — this is the user's OWN toggle arriving from a sibling tab, not the room taking them out of Solo, so the observer's non-adoption argument does not apply, and going through the public setter is what keeps the Solo→Tandem edge firing the release (idempotent across tabs). `storage` never fires in the writing tab and does not fire when `setItem` stores an unchanged value, so there is no loop. The svelte-migration-reviewer owns the effect shape.
   - Rewrite every passage in the hook that still calls the route a mode writer: `:17-24` (item 1b), `:169` (the "`/api/mode/release` racing a client toggle" concurrent case becomes "the release POST landing before this client's CRDT write — answered by the route's 409 and the delayed retry"), `:214-215` ("`/api/mode/release` writing "tandem" unconditionally" is gone), and the `:217-229` paragraph (the asymmetry is now implemented one way; say which direction re-asserts, why the other never writes, that same-browser tabs converge through `storage`, and that the residual race is one RTT wide). The `:289` spec's comment in `tandem-mode-race.test.ts` says the route "answers by writing tandem into the ctrl doc" — rewrite it too (Tests 3).

3. **Server-side marker stamp**, new `src/server/annotations/held-in-solo.ts` exporting `makeHeldInSoloStampObserver({ docName, doc }): () => void`. Observe `doc.getMap(Y_MAP_ANNOTATIONS)` (Critical Rule 1); bail on `shouldSkipChannel(txn.origin)` (so `withMcp` range refreshes, `withModeRelease` clears and `withInternal` seeds never trigger it — the model is `observers/factory.ts:onChange`). The body, in this order — **filter candidates → if none return → read mode once → one write**:
   - For each key whose action is `add` or `update`: `const ann = sanitizeAnnotation(raw, (e) => relaySanitizationEvent(docName, e))` (relay exactly as `observers/annotations.ts:91` does — `docName` is in the deps for that). Candidate iff `ann.author === "user" && ann.type === "comment" && raw.heldInSolo !== true`. **Sanitized type, never raw**: a stored legacy `question` is a comment only after `sanitize.ts:178-181` (an unknown type after `:213-215`), `collectAnnotations` sanitizes on every pull read so it reaches `processInboxAnnotations` as a comment, and a raw-type check would leave it unstamped and delivered after a lost-session restart — the after-sanitize rule from CLAUDE.md's ADR-027 paragraph applied to a privacy marker.
   - If there are no candidates, return **before** reading mode: `readModeState()` does a lookup-or-create on CTRL_ROOM (`lifecycle.ts:1180-1186` names this hazard for the reply stamp), so it must not run on every Claude write to every doc.
   - `if (readModeState() === "tandem") return;` — **`!== "tandem"`, matching the reply stamp** (`lifecycle.ts:1174-1179`, "completing #1213's fail-closed invariant"), which the track says annotations should mirror. A comment created while the key is absent (lost-session restart, before the client's first broadcast) IS stamped. Consequence, stated: `queue.ts:232-238`'s sentence "an unmarked comment authored during indeterminate is still surfaced on pull" is no longer true for comments created after this lands — rewrite that sentence to say the server stamp now closes it (the push gate is no longer strictly stricter than the pull gate for new records; it still is for records that predate this).
   - ONE `withBrowser(doc, () => { for (const [key, rec] of hits) map.set(key, { ...rec, heldInSolo: true, rev: nextRev(rec) }) })` after the loop (the clear at `mode-release.ts:35-52` is the model: snapshot, then write). The write spreads the RAW record — the stamp must not also perform the migration. `withBrowser` is the actor because this completes the user's own create — the ledger row says so — and the channel is safe by construction: the stamp only happens when mode is not Tandem, and `queue.ts:245` drops every `annotation:edited` in that state. `withInternal` is WRONG here (it is in `DURABLE_SKIP`, `origins.ts:100`, so the marker would never reach disk — the restart case is the whole point). No re-entry loop: the stamp is browser-origin, so the observer runs again and finds `heldInSolo === true`.
   - **Semantics widen on `update`, deliberately.** The client stamps only on create/promote (`Toolbar.svelte:807`, `annotation-actions.ts:85`); this observer also stamps a Tandem-created, already-delivered comment that the user EDITS in Solo. That is the fail-closed direction — the edit content is what would otherwise leak after a lost-session restart — and it gives the record a `Held` pill (`AnnotationCardHeader.svelte:107`) until the next release. Say so in the file's docblock.
   - **The docblock also names the LWW race**: this is a server-side whole-record replace on a record the user just created, so a user edit issued inside the create→stamp round-trip is a concurrent writer; if the stamp wins the tie the edit is reverted, if the edit wins the observer re-fires on `update` and re-stamps (self-heals). Same shape as `clearHeldMarkersForDoc`, window is milliseconds. Written down so the next reader does not widen the condition to every `update` without seeing it.
   - Attach it in `attachObservers` (`events/queue.ts:483`) for EVERY doc, uploads included — that is the function `reattachObservers` re-runs after the Hocuspocus doc swap (CLAUDE.md, `onDocSwapped`). The client stamps at `Toolbar.svelte:807` / `annotation-actions.ts:85` stay as the immediate badge; the server stamp is the authoritative completion.
   - **`output-schemas.ts` `annotationBaseShape` (`:53-95`) gains `heldInSolo: z.boolean().optional().describe("Solo-hold marker; only meaningful when mode is indeterminate")`.** `sanitize.ts:136-138` preserves the field and the client already wrote it, but with a server stamp it now reaches a Tandem-mode `tandem_getAnnotations` response routinely; `tests/server/mcp-output-schemas.test.ts:120-134` strip-parses and deep-equals, so an undeclared field reds it. C-1770 adds `resolvedBy` to the same shape in the same edit.
   - **Expected fixture fallout, not a stamp bug:** `TEST_ORIGIN` is deliberately NOT in the channel-skip set (`observers/factory.ts:61-65`), so any suite that calls `attachObservers` and seeds user comments under `transactForTest`, bare `Y.applyUpdate` or `withBrowser` while the ctrl mode key is absent will see them gain `heldInSolo: true`, a rev bump and a second durable write — `event-queue.test.ts`, `rename-document.test.ts` and `awareness-tools.test.ts` are the likely ones. A suite asserting whole-record equality, `rev` values or write counts must seed mode `"tandem"` with the `setMode` helper (`mode-release.test.ts:42-49`) or expect the marker. Do not weaken the stamp to spare them.

`store.ts` is not touched, so J2's rebase note does not apply. `npm run audit:origins` must list the new file under `withBrowser`.

## Not in scope
