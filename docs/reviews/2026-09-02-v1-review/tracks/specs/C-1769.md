# C — #1769 Solo privacy: the release route writes the mode unconditionally, and `heldInSolo` is stamped from the local window's mode

Branch `fix/privacy-and-authority-1769`. Closes #1769 (both holes in its body, with one named residual — see "Not in scope"). Ledger: `docs/reviews/2026-09-02-v1-review/areas/annotations.md:17-18`. Probe: none in the review — the race was source-confirmed only, so the reproduction below is written FIRST and must be red on `origin/master` before any fix lands.

## Problem

Hole 1 — `handleModeRelease` (`src/server/mcp/routes/mode-release.ts:85`) does `withModeRelease(ctrlDoc, () => awareness.set(Y_MAP_MODE, "tandem"))` with no read of the current value, then clears every `heldInSolo` marker on every open doc (`:96-102`) and wakes (`:104`). The client fires that POST from `setTandemMode` on the Solo→Tandem edge (`src/client/hooks/useTandemModeBroadcast.svelte.ts:300-302`); its own mode write goes over the CRDT socket (`:201`). Solo→Tandem→Solo inside the POST's latency leaves the room reading `"tandem"` while the toggle shows Solo — and the markers are gone, so even a restart cannot re-hold them. The hook's observer (`:235-266`) sees the disagreement and only logs (`:256-260`); the comment at `:224-229` names re-asserting Solo as "the case that actually breaks Solo's promise" and defers it.

Hole 2 — the persisted marker is stamped from the *local window's* rune: `src/client/editor/toolbar/Toolbar.svelte:807` (`heldInSoloOnCreate(type, tandemMode)`, inside the create block at `:795-825`) and `panels/annotation-actions.ts:85` (promotion). Two windows with different localStorage (Tauri WebView + browser tab) disagree; a comment created from the Tandem-believing window into a Solo room is hidden live (`hideFromAI` reads the room, `mode.ts:88`) but carries no marker, so after a restart that loses the ctrl session (`readModeState() === "indeterminate"`, `mode.ts:89`) it is delivered. Replies are already stamped server-side from `readModeState()` (`lifecycle.ts:1174-1179`); annotations are not.

## Fix

Three edits plus one client ordering change, no new writer of the mode key, no new route.

1. **Conditional release** (`routes/mode-release.ts`). Delete the mode write at `:85` and the `Y_MAP_MODE` / `Y_MAP_USER_AWARENESS` / `CTRL_ROOM` imports it needed. At the top of the handler, after the two gates: `if (readModeState() !== "tandem") { res.status(409).json({ error: "MODE_NOT_TANDEM", message: "The room does not read Tandem; nothing was released.", data: { released: 0 } }); return; }` — written inline like `annotation-reply.ts:39` (`BAD_REQUEST`), not through `sendApiError`, so `_shared.ts` is untouched. `indeterminate` refuses too (fail closed, same reading as `queue.ts:168-174`). The marker sweep, the `released > 0` wake and the `withModeRelease` marker clears stay exactly as they are. **Do not add a `mode` body parameter**: a stale POST from the first toggle would carry `"tandem"` too — the room is the only witness.

   **Three docblocks describe the route as a mode WRITER and all three are rewritten**, because after this change each is a live instruction to do the thing the fix removed: (a) the route's own `:56-79` — step 1 becomes "verify the client's CRDT write has landed; answer 409 `MODE_NOT_TANDEM` otherwise", and the "verified live / almost always" paragraph (`:66-74`) is replaced by: *409 is definitive when the room reads Solo and transient when the POST outran the client's CRDT write — the client's delayed retry (item 1b) covers the second case; keep it.* (b) `events/queue.ts:176-180` (`shouldForwardExternally`): the route now *checks* that mode reads Tandem before the wake rather than writing it, which is what keeps `isUserPrivacyHeld` from dropping the wake. (c) `events/queue.ts:445-455` (`emitModeReleaseWake`): "The caller MUST have already set mode to Tandem (the release route does this first)" → "The caller MUST have VERIFIED that mode reads Tandem (the route's 409 arm is that guarantee)". **Both (a) and (c) add one more sentence: the verify and the wake are ONE synchronous frame — do not put an `await` between them.** `pushEvent` drops the synthetic `annotation:created` wake whenever mode reads non-Tandem (`queue.ts:245`), and the handler has no `await` between `readModeState()` and `emitModeReleaseWake()` (`mode-release.ts:80-106`), so a WS frame carrying `"solo"` cannot land in between; an async per-doc sweep — a plausible future "improvement" — would reopen exactly the stall the 409 arm closes.

1b. **The client POST is ordered after its own CRDT write, a 409 is retried with a delay, and an exhausted retry ADOPTS SOLO** (`useTandemModeBroadcast.svelte.ts` `triggerSoloRelease`, `:26-44`). Review established the ordering the old docblock called "reliable" is not guaranteed: `setTandemMode` (`:296-303`) assigns the rune and calls `triggerSoloRelease()` in the same synchronous frame, so `fetch()` (`:28`) is issued before the broadcast `$effect` (`:178-206`) has even run — the effect flushes on a microtask. The pieces:
   - **Signature.** `export async function triggerSoloRelease(deps: { stillTandem: () => boolean; canRelease: () => boolean; adoptSolo: () => void }, attempt = 0)` — exported beside `shouldReleaseSolo` so the retry spec drives it directly (Tests 3), and parameterised because it is module-level and cannot see the rune. The hook hoists `setTandemMode` to a named local function (returned as today) and calls `triggerSoloRelease({ stillTandem: () => tandemMode === "tandem", canRelease: () => getBootstrapYdoc() !== null && getCtrlSynced(), adoptSolo: () => setTandemMode("solo") })` — `getCtrlSynced` is the hook's existing parameter (`:87`) and `getBootstrapYdoc` the existing getter, both already in scope at the call site. Reading `tandemMode` inside `stillTandem` after an `await` is an untracked read — no reaction is active — so no `$effect` coupling is introduced; the same holds for `canRelease`.
   - **`canRelease` is what keeps the give-up arm honest: a 409 is only "the room refused our release" when a release was actually asked of the room.** In the `!bootstrapYdoc || !synced` state the broadcast effect issues no `awareness.set` at all (`:195-198`) — a Tandem toggle made during cold start, a Hocuspocus doc swap or a reconnect never reaches the wire, so the POST 409s four times inside the ~750 ms budget for a reason that has nothing to do with the room's opinion, and `tick()` cannot help (it flushes the effect; it cannot make the effect write while `synced` is false, and `provider.on("synced")` is async). Without this dep the give-up arm would silently flip a legitimate Tandem toggle back to Solo. So **before each retry AND before the give-up arm: `if (!deps.canRelease()) return;` — silently, no log, no `adoptSolo`.** The toggle stays in Tandem, the markers stay held and marked, and the next successful release (the effect's `synced` transition re-broadcasts the rune — `:178-206` reads `tandemMode` — and the pull path is authoritative regardless) delivers them. Order inside the loop: `stillTandem` bail, then `canRelease` bail, then the 409 branch.
   - `await tick()` (from `svelte`) before the first `fetch`. **What that buys, stated precisely and written into the docblock in these words:** after `tick()` the broadcast effect has RUN; whether its frame reached the server is what the route's 409 verifies. It is not "the WS frame is on the wire before the HTTP request" — two reachable states break that: the effect issues no `awareness.set` at all while `!bootstrapYdoc || !synced` (`:195-198`, doc swap / reconnect), and on a plain WS disconnect `ctrlInitialSyncComplete` stays latched (`:170-172`) so the write lands in the local doc while the provider only queues the frame (`hocuspocus-provider.esm.js:1506-1514`). In both, the POST outruns a write that is not on the wire and 409s; the bounded retry below is what covers the common case, and the give-up arm is what keeps the uncommon one honest.
   - Treat a 409 whose body `error` is `"MODE_NOT_TANDEM"` as "not landed yet": retry after 250 ms, at most 3 further attempts (4 POSTs total). **Before each retry, `if (!deps.stillTandem()) return;` — silently, no log**: the user toggled back to Solo inside the retry window (Solo→Tandem→Solo within ~750 ms), the 409 is correct, and a `logClientWarning` here would land in Copy Diagnostics and the prefilled public bug report (`client-log.ts:17-21`) reading as a fault for what was a user action. A thrown fetch keeps today's single immediate retry. Any other non-ok status keeps today's behaviour. A repeat POST after a successful release clears 0 and fires no second wake (existing idempotency, `mode-release.test.ts:158`).
   - **Give-up arm: after the fourth 409 with `stillTandem()` still true AND `canRelease()` true, `logClientWarning("tandem-mode", "release-refused-room-not-tandem")` — two static literals, never a `console.warn` (`tests/client/client-log-callsites.test.ts`; the observer at `:249-255` says why) — AND `deps.adoptSolo()`.** Without this the round-1 shape left the rune, the toggle (`ModeToggle.svelte:39` `aria-pressed`) and localStorage all saying Tandem while the room read Solo, forever, with a diagnostics line as the only signal: a Solo window in a DIFFERENT browser (Tauri WebView + browser tab, separate localStorage, so the `storage` listener in Fix 2 cannot converge them) became a permanent silent veto — #1733's reported symptom institutionalised as designed behaviour. Adopting Solo is the privacy-safe direction the `:217-229` docblock permits (only adopting *Tandem* from the room is forbidden); it runs from an async continuation, outside any observer, so no `$state` write happens inside a reaction; it re-syncs localStorage and sibling tabs through the existing persist effect and the `storage` path; and `shouldReleaseSolo("tandem", "solo")` is false, so no release loop. **The property this ships: a toggle the room refuses is visibly refused — the toggle flips back to Solo within ~1 s — never silently inert.** Its cost, named in the follow-up issue (see "Not in scope"): on a plain network blip a legitimate Tandem toggle is reverted to Solo after four 409s with only the diagnostics line to explain it; the held items stay held and stay marked, and the next Solo→Tandem toggle releases them. Honest and fail-closed; a toast is out of scope here.
   - Rewrite the docblock at `:17-24` ("flip mode server-side" is gone): the route *verifies* the room reads Tandem, clears the markers and wakes; the POST is still best-effort and pull is authoritative; the give-up arm adopts Solo and why; `canRelease` bails silently because an unsynced client asked the room nothing.
