# C — #1769 Solo privacy: the release route writes the mode unconditionally, and `heldInSolo` is stamped from the local window's mode

Branch `fix/privacy-and-authority-1769`. Closes #1769 (both holes in its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/annotations.md:17-18`. Probe: none in the review — the race was source-confirmed only, so the reproduction below is written FIRST and must be red on `origin/master` before any fix lands.

## Problem

Hole 1 — `handleModeRelease` (`src/server/mcp/routes/mode-release.ts:85`) does `withModeRelease(ctrlDoc, () => awareness.set(Y_MAP_MODE, "tandem"))` with no read of the current value, then clears every `heldInSolo` marker on every open doc (`:96-102`) and wakes (`:104`). The client fires that POST from `setTandemMode` on the Solo→Tandem edge (`src/client/hooks/useTandemModeBroadcast.svelte.ts:300-302`); its own mode write goes over the CRDT socket (`:201`). Solo→Tandem→Solo inside the POST's latency leaves the room reading `"tandem"` while the toggle shows Solo — and the markers are gone, so even a restart cannot re-hold them. The hook's observer (`:235-266`) sees the disagreement and only logs (`:256-260`); the comment at `:224-229` names re-asserting Solo as "the case that actually breaks Solo's promise" and defers it.

Hole 2 — the persisted marker is stamped from the *local window's* rune: `Toolbar.svelte:807` (`heldInSoloOnCreate(type, tandemMode)`) and `panels/annotation-actions.ts:85` (promotion). Two windows with different localStorage (Tauri WebView + browser tab) disagree; a comment created from the Tandem-believing window into a Solo room is hidden live (`hideFromAI` reads the room, `mode.ts:88`) but carries no marker, so after a restart that loses the ctrl session (`readModeState() === "indeterminate"`, `mode.ts:89`) it is delivered. Replies are already stamped server-side from `readModeState()` (`lifecycle.ts:1197`); annotations are not.

## Fix

Three edits, no new writer of the mode key, no new route.

1. **Conditional release** (`routes/mode-release.ts`). Delete the mode write at `:85` and the `Y_MAP_MODE` / `Y_MAP_USER_AWARENESS` / `CTRL_ROOM` imports it needed. At the top of the handler, after the two gates: `if (readModeState() !== "tandem") { res.status(409).json({ error: "MODE_NOT_TANDEM", message: "The room does not read Tandem; nothing was released.", data: { released: 0 } }); return; }` — written inline like `annotation-reply.ts:39` (`BAD_REQUEST`), not through `sendApiError`, so `_shared.ts` is untouched. `indeterminate` refuses too (fail closed, same reading as `queue.ts:168-174`). The marker sweep, the `released > 0` wake and the `withModeRelease` marker clears stay exactly as they are. Rewrite the docblock's step 1 (`:59-62`): the route *verifies* the client's CRDT write has landed rather than performing it; and fix `events/queue.ts:176-180`, which currently says the route writes `"tandem"` before the wake — it now *checks* that, which is what keeps `isUserPrivacyHeld` from dropping the wake. **Do not add a `mode` body parameter**: a stale POST from the first toggle would carry `"tandem"` too — the room is the only witness.
2. **Client re-asserts Solo** (`useTandemModeBroadcast.svelte.ts` observer). In the `parsed.data === "tandem"` branch (`:258-260`), after `logClientWarning`, write `withBrowser(bootstrapYdoc, () => awareness.set(Y_MAP_MODE, "solo"))`. Only this branch re-asserts: a client holding Tandem never writes on disagreement, so two windows converge on Solo (privacy wins) and there is no ping-pong — the re-assert is `transaction.local` on the way back into this observer (`:244`). `lastBroadcast` stays `"solo"`, `tandemMode` is untouched (no `$state` write inside the observer — the docblock at `:112-132` is why), and the release POST does not fire (it lives in `setTandemMode`). Rewrite the paragraph at `:217-229` to say so. **Critical Rule 2:** `withBrowser`, as `:201` already does. This is a second `.set(Y_MAP_MODE` in the hook, and the route loses its one: `tests/shared/mode-writer-set.test.ts` `EXPECTED_MODE_WRITES` becomes `[["src/client/hooks/useTandemModeBroadcast.svelte.ts", 2]]` and `EXPECTED_MENTIONS` drops `routes/mode-release.ts` (it no longer names the constant). Edit both lists on purpose and say why in their comments.
3. **Server-side marker stamp**, new `src/server/annotations/held-in-solo.ts` exporting `makeHeldInSoloStampObserver({ doc }): () => void`. Observe `doc.getMap(Y_MAP_ANNOTATIONS)` (Critical Rule 1); bail on `shouldSkipChannel(txn.origin)` (so `withMcp` range refreshes, `withModeRelease` clears and `withInternal` seeds never trigger it — the model is `observers/factory.ts:onChange`); collect keys whose action is `add` or `update`, whose raw record reads `author === "user" && type === "comment" && heldInSolo !== true`, and only when `readModeState() !== "tandem"`; then ONE `withBrowser(doc, () => map.set(key, { ...rec, heldInSolo: true, rev: nextRev(rec) }))` over the collected keys, after the loop (the clear at `mode-release.ts:35-52` is the model: snapshot, then write). `withBrowser` is the actor because this completes the user's own create — the ledger row says so — and the channel is safe by construction: the stamp only happens when mode is not Tandem, and `queue.ts:245` drops every `annotation:edited` in that state. `withInternal` is WRONG here (it is in `DURABLE_SKIP`, `origins.ts:100`, so the marker would never reach disk — the restart case is the whole point). No re-entry loop: the stamp is browser-origin, so the observer runs again and finds `heldInSolo === true`. Attach it in `attachObservers` (`events/queue.ts:483`) for EVERY doc, uploads included — that is the function `reattachObservers` re-runs after the Hocuspocus doc swap (CLAUDE.md, `onDocSwapped`). The client stamps at `Toolbar.svelte:807` / `annotation-actions.ts:85` stay as the immediate badge; the server stamp is the authoritative completion.

`store.ts` is not touched, so J2's rebase note does not apply. `npm run audit:origins` must list the new file under `withBrowser`.
