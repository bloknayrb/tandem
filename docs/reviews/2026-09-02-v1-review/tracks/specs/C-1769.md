# C — #1769 Solo privacy: the release route writes the mode unconditionally, and `heldInSolo` is stamped from the local window's mode

Branch `fix/privacy-and-authority-1769`. Closes #1769 (both holes). Ledger: `areas/annotations.md:17-18`. Probe: none in the review — the race was source-confirmed only, so Test 1 is written FIRST and must be red on `origin/master`.

## Problem

Hole 1 — `handleModeRelease` (`src/server/mcp/routes/mode-release.ts:85`) writes `Y_MAP_MODE = "tandem"` with no read of the current value, then clears every `heldInSolo` marker on every open doc (`:96-102`) and wakes (`:104`). The client fires that POST from `setTandemMode` (`src/client/hooks/useTandemModeBroadcast.svelte.ts:296-303`); its own mode write goes over the CRDT socket (`:201`). Solo→Tandem→Solo inside the POST's latency leaves the room reading `"tandem"` while the toggle shows Solo, with the markers gone.

Hole 2 — the persisted marker is stamped from the *local window's* rune (`Toolbar.svelte:807`, `panels/annotation-actions.ts:85` via `heldInSoloOnCreate(type, tandemMode)`). A comment created from a window whose rune says Tandem into a Solo room is hidden live (`hideFromAI` reads the room, `mode.ts:88`) but carries no marker, so after a restart that loses the ctrl session (`indeterminate`, `mode.ts:89`) it is delivered. Replies are already stamped server-side from `readModeState()` (`lifecycle.ts:1174-1179`); annotations are not.

## Fix

Three edits. No new writer of the mode key, no new route, no client-side mode adoption or re-assertion (see "For Bryan").

1. **Conditional release** (`routes/mode-release.ts`). Delete the write at `:85` and the `Y_MAP_MODE` / `Y_MAP_USER_AWARENESS` / `CTRL_ROOM` imports it alone needed. After the two gates: `if (readModeState() !== "tandem") { res.status(409).json({ error: "MODE_NOT_TANDEM", message: "The room does not read Tandem; nothing was released.", data: { released: 0 } }); return; }` — inline like `annotation-reply.ts:39`, so `_shared.ts` is untouched. `indeterminate` refuses too (fail closed, as `queue.ts:168-174` reads it). The marker sweep, the `released > 0` wake and the `withModeRelease` clears stay as they are. No `mode` body parameter: a stale POST from the first toggle would carry `"tandem"` too — the room is the only witness. Rewrite the route docblock `:56-79` (step 1 becomes "verify the client's CRDT write has landed; 409 otherwise", and the "reliably reaches the server BEFORE this HTTP round-trip" paragraph becomes: a 409 is definitive when the room reads Solo and transient when the POST outran the client's write — the client's one delayed retry covers the second). `queue.ts:176-180` and `:445-455` say the route *checks* mode rather than writing it; both keep "verify and wake are one synchronous frame — no `await` between them" (`pushEvent` drops the wake whenever mode reads non-Tandem, `:245`). With the route no longer writing, the room always holds the user's last CRDT write — which is what "server mode never disagrees with the last user toggle" means.
   - `tests/shared/mode-writer-set.test.ts`: `EXPECTED_MODE_WRITES` loses the `routes/mode-release.ts` row (its comment described the unconditional write) and `EXPECTED_MENTIONS` drops the same file. This is the one edit to that file in this PR.
2. **Client: one delayed retry on 409** (`useTandemModeBroadcast.svelte.ts` `triggerSoloRelease`, `:26-44`). Today `fetch()` is issued in `setTandemMode`'s synchronous frame (`:296-303`) while the broadcast `$effect` that writes `Y_MAP_MODE` flushes on a microtask, so the POST can reach the server before the CRDT frame — the route docblock's "reliably reaches the server BEFORE this HTTP round-trip (verified live)" (`mode-release.ts:66-74`) describes the common ordering, not a guarantee, and once the route refuses instead of writing, that ordering is the primary flow's correctness condition. So **defer the POST until after the flush**: `setTandemMode` does `void tick().then(() => triggerSoloRelease())` (Svelte's `tick`, the hook already runs inside a component context) rather than firing in the synchronous frame, and the 409 retry below covers only the residual where the server-side apply of the CRDT frame is still in flight. On a 409 whose body `error` is `"MODE_NOT_TANDEM"`: wait 250 ms and POST once more (two POSTs total). On a second 409, `logClientWarning("tandem-mode", "release-refused-room-not-tandem")` — two static literals, never `console.warn` (`tests/client/client-log-callsites.test.ts`); the held items stay held and marked, and the next Solo→Tandem toggle releases them (pull is authoritative regardless). A thrown fetch and any other non-ok status keep today's single immediate retry. Export `triggerSoloRelease` so Test 3 drives it directly. Rewrite the three hook passages that call the route a mode writer: the docblock `:17-24`, the "`/api/mode/release` racing a client toggle" case at `:169` (now: the POST landing before this client's write, answered by 409 + retry), and `:214-215`. The observer (`:235-266`) is unchanged: warn-only, as its docblock argues.
3. **Server-side marker stamp**, new `src/server/annotations/held-in-solo.ts` exporting `makeHeldInSoloStampObserver({ docName, doc }): () => void`, attached in `attachObservers` (`events/queue.ts:483`) for every doc, so `reattachObservers` re-runs it after the Hocuspocus doc swap. Observe `doc.getMap(Y_MAP_ANNOTATIONS)`; bail on `shouldSkipChannel(txn.origin)` (the `observers/factory.ts:onChange` model — `withMcp` refreshes, `withModeRelease` clears and `withInternal` seeds never trigger it) **and on `txn.origin == null`** — a browser write reaches the server with the Hocuspocus `Connection` as origin, so null is only a restore or a swap, and skipping it is what keeps the stamp from re-marking every historical record if a restore ever ran after attach. Body: filter candidates → if none, return → read mode once → one write.
   - Candidate: key with action `add` or `update`, `sanitizeAnnotation(raw, relay)` inside a per-key `try/catch` that `continue`s and logs the error NAME only (`projection.ts:218-248` wraps the same call for the same reason — a stored `null` throws), and `ann.author === "user" && ann.type === "comment" && raw.heldInSolo !== true`. Sanitized type, never raw: a stored legacy `question` is a comment only after sanitize, and reaches `checkInbox` as one.
   - Return before `readModeState()` when there are no candidates (it does a lookup-or-create on CTRL_ROOM — `lifecycle.ts:1180-1186`). Then `if (readModeState() === "tandem") return;` — `!== "tandem"`, matching the reply stamp: a comment created while the key is absent IS stamped. Cost, in the docblock: such a comment keeps its `Held` pill and is withheld under every later `indeterminate` until a Solo→Tandem toggle clears it (only `POST /api/mode/release` clears). `queue.ts:232-238`'s "an unmarked comment authored during indeterminate is still surfaced on pull" is rewritten: the stamp now closes that for new records.
   - ONE `withModeRelease(doc, () => { for (const [key, rec] of hits) map.set(key, { ...rec, heldInSolo: true, rev: nextRev(rec) }) })` — the RAW record spread (the stamp does not perform the migration). `withModeRelease` because `MODE_RELEASE_ORIGIN` already has exactly the profile the stamp needs — in `CHANNEL_SKIP` and NOT in `DURABLE_SKIP` (`origins.ts:91-100`), so the marker reaches disk (the restart case is the point) while never becoming a channel event — and because the route's clear of the same marker already writes under it (`routes/mode-release.ts:46`). Widen its docblock in `src/shared/origins.ts:65-72` from "the release sweep" to "the `heldInSolo` marker lifecycle, stamp and clear". Not `withBrowser`: `docs/gotchas.md:39` defines it as user edits originating in the browser and `:43`/`:53` say the skip-set governs server-side writes, so a server-origin `browser` write is channel-eligible by construction — `lifecycle.ts:936-942` spells out the same trap for a sibling server-initiated annotation write. **Channel-skip by origin (`CHANNEL_SKIP`), which also makes the observer's own re-entry impossible**: `observers/factory.ts:71` returns on `shouldSkipChannel(txn.origin)`, and the stamp observer bails on the same predicate, so the nested write never fires either observer — loop-freedom rests on the origin, not on the `heldInSolo !== true` re-read (which stays, as the candidate filter). Say that in the docblock; Test 4 pins the origin. Keep the second property too — the stamp touches neither `editedAt` nor `type` (`observers/annotations.ts:146-148`, `:134`), so even an unskipped origin would derive no `annotation:edited` from it; Test 4 asserts `editedAt` unchanged as well. The `update` arm also stamps a Tandem-created comment the user edits in Solo — the fail-closed direction; one sentence in the docblock. No new origin constant, so `tests/scripts/audit-origins.test.ts`'s helper enumeration is unchanged.
   - Expected fixture fallout: `TEST_ORIGIN` is not channel-skipped (`observers/factory.ts:61-65`), so suites that call `attachObservers` and seed user comments under `transactForTest`/`withBrowser` with the mode key absent will see `heldInSolo: true` and a rev bump (a `withMcp`/`withModeRelease`/`withInternal` seed is skipped and unaffected) (`event-queue.test.ts`, `event-queue-observer-split.test.ts`, `rename-document.test.ts`, `awareness-tools.test.ts` are the likely ones). Seed `"tandem"` with `mode-release.test.ts:42-49`'s `setMode` or expect the marker; do not weaken the stamp. `event-queue.test.ts:1186-1197` and `event-queue-observer-split.test.ts:47-52` say the `getOrCreateDocument` mock is safe because only `attachCtrlObservers` calls it — after this the stamp's mode read calls it too; correct the comment, keep the mock.

`docs/mcp-tools.md:1134`: one clause on the route row — `POST /api/mode/release` answers 409 `MODE_NOT_TANDEM` when the room does not read Tandem and no longer writes the mode key. `store.ts` untouched, so J2's note does not apply.

With the route no longer writing, the room always carries the user's last CRDT write, which is the wave note's done-when verbatim; a re-assert would make a stale window override the last toggle and so violate it. The two-window policy is handed to Bryan. Round-3 finding 2 (`canRelease`) is moot.

## Review corrections (post-cut)

Adopted, and where:

- **Fix item 3's stamp writes under `withModeRelease`, not `withBrowser`.** `withBrowser` is the client's origin (`docs/gotchas.md:39`) and the skip-set governs server-side writes (`:43`, `:53`), so a server-origin `browser` write was channel-eligible by construction and relied on the incidental `editedAt`/`type` comparison for silence — the trap `lifecycle.ts:936-942` already documents at a sibling write. `MODE_RELEASE_ORIGIN` is channel-skip and durable-persist (`origins.ts:96-104`), was created for the inverse operation on the same marker (`mode-release.ts:46`), and makes the observer's own re-entry impossible by origin rather than by re-read. Its docblock widens to the marker lifecycle; Test 4's origin row asserts `MODE_RELEASE_ORIGIN`; the `editedAt`-unchanged assertion stays as a second property. No new origin constant.
- **Test 3 gains the happy-path row.** Nothing pinned that a real Solo→Tandem toggle still releases once the route is conditional, while fix item 2's own diagnosis says the POST can beat the CRDT frame; a doubly-refused release leaves markers on disk and `hideFromAI` withholds those records after every ctrl-losing restart. Fix item 2 now defers `triggerSoloRelease` past `tick()`, and the new `tandem-mode-race.test.ts` row asserts the POST is issued only after the broadcast `$effect` wrote `Y_MAP_MODE`.
