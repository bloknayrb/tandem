# E1 — #1812 Sidecar health poll accepts any HTTP 2xx, so it passes against an old process

Branch `fix/desktop-core-1761`. Closes #1812. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area rows `docs/reviews/2026-09-02-v1-review/areas/tauri.md:21` and `areas/server-runtime.md:21`. Probe: `tests/server/health-route.test.ts` + `cargo test`; the cross-process case is a smoke line (Bryan).

## Problem

`wait_for_health` (`src-tauri/src/sidecar.rs:1736-1760`) returns `Ok(())` on `resp.status().is_success()` from `HEALTH_URL`. It never compares the responder with the child it just spawned (`child.pid()` at `:1638`, stored into `SidecarState` at `:1690`). So a 2xx from a **previous** process still holding :3479 — one waiting on the annotation-store lock, one dying slowly, or one an unrelated `tandem` started — is accepted as "our sidecar is healthy": `SIDECAR_HEALTHY` is promoted, the pending-open queue is drained at a server the shell does not own, and when the old process finally exits the shell has no signal because the process it watches is a different one. The UI stays green with no backend. `sidecar.rs:1560-1566` already names this ("gives the POST no identity check (#1812) — a foreign server already on :3479 is still mistaken for ours"). This is also what makes #1758 destructive: the poll cannot tell an old holder from a new one, so nothing upstream of `freePort` has a reason to stop.

`/health` (`src/server/mcp/routes/health.ts`) publishes `status`, `version`, `transport` publicly and `hasSession` / `push` / `delivery` to loopback callers. **Nothing identifies the process.**

## Fix

Add a process identity to `/health` and make the poll require it to match the spawned child.

- `src/server/mcp/routes/health.ts`: inside the existing `isLoopback(req.socket.remoteAddress)` block, add `body.pid = process.pid`. **Loopback-only, deliberately** — the file's docblock already establishes that identity/presence signals are withheld from LAN callers, and this is one. Read `process.pid` directly; do not add a `HealthHandlerDeps` field for it (a dep would be a seam with exactly one possible value, and the factory already exists so the gate can be driven).
- **Do NOT expose `generationId`.** It is pinned as the Hocuspocus provider's auth token (CLAUDE.md, Y.js/CRDT), so publishing it on `/health` would hand a connection credential to any loopback page — and the CORS allowlist is port-wildcarded. The issue offers `generationId`/PID as alternatives; PID is the one that is safe here. Say so in the PR body so nobody "improves" it later.
- `src-tauri/src/sidecar.rs`, `wait_for_health`: take the spawned `child_pid: u32` as a parameter (one call site, `:1695`). On a 2xx, parse the JSON body and accept only when `pid == child_pid`. A mismatch or a missing/unparseable `pid` is **not** an error — record it in `last_error` and keep polling, so the existing `HEALTH_TIMEOUT` loop handles it. Log the distinct line the issue asks for, once per distinct observed pid: `"health answered by a different process (pid {observed}, expected {child_pid}) — still waiting"`. Repeating it every 250 ms poll would bury the log.
- **Leave `check_health`, `check_health_at`, `wait_for_port_release` and `wait_for_server_gone` alone.** They ask "is *anything* answering", which is the correct question for the port-release wait (any responder means the port is still held) and for the debug-only adoption fast path at `sidecar.rs:1454` (`cfg!(debug_assertions)`), which is what lets `cargo tauri dev` attach to a hand-started `dev:standalone`. Narrowing them would break both. This also bounds the change's blast radius: only the post-spawn poll gets stricter.
- Behaviour change worth naming in the PR body: in a **release** build, a foreign or pre-upgrade Tandem on :3479 now makes `wait_for_health` time out rather than falsely succeed, so the shell takes its existing `Err` arm — kill our child, back off, retry, and after `MAX_RESTARTS` the "Retry Server Start" dialog with `port_holder_for_dialog` naming the holder. That is the intended outcome (a named holder beats a green UI over nothing) and it is why #1758's refusal must land in the same PR: with both, the second instance never gets far enough to hold the port.

## Tests

1. `tests/server/health-route.test.ts` (already drives `makeHealthHandler` with a synthetic non-loopback request): assert `pid` is `process.pid` for a loopback request and **absent** for `203.0.113.5`. **What it kills:** hoisting the field out of the loopback block — the exact regression this file was written for, and the reason it tests the handler rather than the source text.
2. `src-tauri/src/sidecar.rs` — a `#[cfg(test)]` unit test over the extracted body predicate. Factor the accept decision into a pure `fn health_body_is_our_child(body: &str, child_pid: u32) -> bool` and test: matching pid → true; different pid → false; **body with no `pid` key → false**; non-JSON body → false. **What each kills:** the third case kills a `serde` default or `unwrap_or(child_pid)` that treats an unidentified responder as ours (which restores today's bug against every pre-fix server), and the fourth kills a `contains(\"pid\")` string check.
3. No test drives the real 90-second poll; the predicate plus the route test bracket it. Say so in the PR body.

## Done when

`/health` carries `pid` for loopback callers only; `wait_for_health` accepts only the child it spawned and logs a distinct mismatch line; `check_health` and the port-release waits are unchanged; the four predicate cases pass in `cargo test`.
