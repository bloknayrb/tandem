## Problem

1. **Every settings-backed control outside the modal is a silent no-op after a downgrade.** `useTandemSettings.svelte.ts:92` is `if (settings._readOnly) return;` — the #659 defence that stops a downgraded client clobbering a newer blob. It returns `void`, so none of the **eleven** `updateSettings(...)` call sites (`App.svelte:998,1016,2207,2293,2297,2314,2320,2584`; `layout/model.svelte.ts:166,173,176`) can tell refused from applied. Only `SettingsModal.svelte:814` renders `SettingsReadonlyBanner`. Extends #1722.
2. **The integrations future-schema error becomes `{"error":"INTERNAL"}`.** `integrations/storage.ts:104-106` throws a precise message; all seven `sendInternal` callers (`api-routes.ts:518,575,608,662,809,1124,1186`) flatten it to a 500 with "Internal server error". The wizard is dead with no hint, and `checkAnnotationStore` (`doctor.ts:2766`) has no `integrations.json` counterpart. **And the two client surfaces that would show a better wire response render only the status code**, so a wire-only fix changes nothing the user sees: `SettingsClaudeCodeTab.svelte:100` sets `Failed to load integrations (HTTP ${res.status}).` and returns before any `res.json()`, and `useIntegrationWizard.svelte.ts:242` sets `Could not load existing entries (HTTP ${res.status}).` with the body read only on the `ok` path.
3. **`welcome.md` is only ever copied when absent, and the annotations anchored to it are not reconciled when it changes.** `copy_sample_files` (`lib.rs:2078`) gates each file on `if !dest.exists()` (`:2120`), so a desktop upgrader keeps the release-N sample forever. `injectTutorialAnnotations` anchors by `fullText.indexOf(def.targetText)` (`tutorial-annotations.ts:63-68`) and `console.error`s the miss, so changed target strings drop the tutorial for upgraders only. **Two consequences the bytes-only reading misses**, both verified on this branch: (i) `tutorial-annotations.ts:63` is `if (map.has(def.id)) continue;` — idempotent **by id, not by target text** — and the ids are stable constants, so an upgrader who has already opened `welcome.md` keeps the OLD tutorial records no matter what the file now says; refreshing the bytes alone cannot restore the tutorial for exactly the population the issue names. (ii) The annotation envelope is keyed by `docHash(filePath)` and the sample path does not change, so `loadAndMerge` re-inserts every stored record VERBATIM against the NEW text — and `reanchorAnnotations` has only three callers (`documents/open.ts:396` force-open, `reload-family.ts:174`, `watcher.ts:203`), **none of which is the ordinary startup `openFromDisk(samplePath)` at `index.ts:719`**. So a bytes-only refresh leaves every annotation on that document — the tutorial `note` and any personal note the user added — pinned to offsets the text no longer holds, and the durable observer persists that. Strictly worse than the missing tutorial the issue reports. **The bundled half is already guarded** — `tests/server/tutorial-annotations.test.ts:81-118` pins the live `sample/welcome.md` against every target — and **npm installs are unaffected**, because `index.ts:718` reads `sample/welcome.md` from the package dir directly. Desktop-only, and invisible to CI by construction.
4. **The CHANGELOG stamp is written before the open is attempted.** `checkVersionChange` (`version-check.ts:31-34`) writes the version file *inside itself*, then `index.ts:692-697` attempts `openFromDisk(CHANGELOG.md)`. A failed open (missing bundle file) means that release's notes never open: the next start reads `current`. **The rest of item 4 is measured NOT live**: `CLAUDE.md`'s Files/Sessions gotcha already states the `if (transportMode === "http")` bound explicitly ("do not read either as unconditional"), and the "outside every launcher branch" comment the issue attributes to `apply.ts` is at `index.ts:657` and says *launcher* branch, which is true — `grep -n "launcher branch" src/server/integrations/apply.ts` returns nothing.

## Fix

**Item 1 — `src/client/hooks/useTandemSettings.svelte.ts`.** `updateSettings` returns `boolean` (`false` on the `_readOnly` short-circuit, `true` otherwise) — this is #1722's half, done once, here. Surface it **centrally, not per call site**: add a module-level `let onWriteRefused: (() => void) | null` plus `export function setSettingsWriteRefusedHandler(fn: (() => void) | null): void`, invoked from the short-circuit before returning `false`. `App.svelte` wires it once beside `const notifications = createNotifications()` (`:271`) to

```ts
notifications.push({
  id: crypto.randomUUID(),
  timestamp: Date.now(),
  type: "general-error",
  severity: "warning",
  message: "…",
  dedupKey: "settings-readonly",
});
```

— `push` takes a full `TandemNotification` (`useNotifications.svelte.ts:58`), and `id`/`timestamp` are required (`shared/types.ts:635-660`), so the four-field literal would not typecheck. One wiring line covers all eleven call sites; `useNotifications.svelte.ts`'s dedup collapses repeated clicks into a count badge instead of a toast storm. Message in **past tense** (`types.ts:646-654`) and it must name the cause: settings were written by a newer version of Tandem, so this one will not change them.

- **`_resetTandemSettingsSingletonForTests()` must also set `onWriteRefused = null`.** It resets only `_instance` today (`:120-123`), and the module's own docblock warns that surviving module-level state silently pollutes across tests. Without this, test 1's "handler does not fire" arm is decided by test ordering rather than by the code.
- **The Settings modal is the eleventh call site and it already explains the condition.** `App.svelte:2584` passes `onUpdate={settingsState.updateSettings}` into `<SettingsModal>`, which renders `<SettingsReadonlyBanner />` at `:814`. A refusal inside the modal would surface twice — the banner plus a persistent `warning` tray entry. **Decision: suppress the toast while the modal is mounted**, by having `SettingsModal` clear the handler on mount and restore it on destroy (the setter already accepts `null`). The banner is the better surface in that context, and a persistent tray entry for a condition the user is currently reading about is noise.
- **Do not** consume the boolean in `layout/model.svelte.ts` or skip `focusToggleTarget` — that is #1722's rail half and belongs to group **G6 rail seam** (wave 9, `#1719 #1716`); doing it here would collide. `createNotifications` is **not** a singleton, which is why the handler is a setter rather than an import.

**Item 2 — `src/server/integrations/storage.ts` + `integrations/api-routes.ts` + the two client surfaces + `src/cli/doctor.ts`.** Export `class IntegrationsFutureSchemaError extends Error` carrying `{ found: number; supported: number }`, thrown at `storage.ts:104`. Add the branch **inside `sendInternal` (`integrations/api-routes.ts:1199`)**, not at the seven call sites: `409` with `error: "CONFLICT"`, a stable `code`, and a message the response builds itself — `integrations.json was written by a newer Tandem (schemaVersion N; this build supports M). Update Tandem, or remove the integrations file.` **The thrown message's `${filePath}` must not reach the wire**: `GET /api/integrations/*` is LAN-reachable and CLAUDE.md's MCP/Server gotcha forbids resolved paths in those responses; the path stays in the `console.error` line `sendInternal` already writes. Model: `sendKeychainError` (`:1211`), which is the same shape one layer out.

**The client half is required, not optional** — without it the user still sees a bare status code and spec test 2 passes anyway. At `SettingsClaudeCodeTab.svelte:100` and `useIntegrationWizard.svelte.ts:242`, on `!res.ok` parse the JSON body inside a `try`/`catch`-and-ignore and render `body.message` when it is a non-empty string, falling back to the existing `(HTTP ${res.status})` string otherwise.

Then a `checkIntegrationsFile` recorder section in `doctor.ts` beside `checkAnnotationStore` (`:2766`): read `integrations.json`, and `r.warn` when its `schemaVersion` exceeds `INTEGRATIONS_SCHEMA_VERSION` (`shared/integrations/contract.ts`), mirroring the `futureActive` warn at `doctor.ts:2859-2864` in wording and remediation.

**Item 3a — `src-tauri/src/lib.rs` (the bytes).** Extract the body of `copy_sample_files` into a pure `fn sync_sample_dir(src_dir: &Path, dest_dir: &Path, version: &str) -> Result<(), String>` (the `AppHandle` wrapper keeps only the two path lookups, so the logic is unit-testable). The rule, which refreshes **once per version, never per launch**: read `dest_dir/.tandem-sample-version`; if it equals `version`, keep today's `if !dest.exists()` behaviour exactly and return. Otherwise, for each bundled file whose bytes differ from the on-disk copy, move the on-disk copy to `<file-name>.pre-<version>.bak` and write the bundled bytes; then write the marker. A user edit made *after* an upgrade survives until the next upgrade, and is preserved as a `.bak` even then. The model is `version-check.ts`'s `last-seen-version` stamp — name it in the doc comment. `.tandem-sample-version` and `*.bak` are inert to everything that reads that directory (`index.ts:718` joins one fixed name).

**Failure policy, which today's code leaves unstated:** the per-file copy propagates with `?` out of the loop and the caller only logs (`lib.rs:1295-1297`, "Sample file copy failed (non-fatal)"). **Write the marker only when every file in the pass succeeded** — otherwise a locked or unwritable file is skipped forever, because the marker would record a refresh that did not happen. A failed pass retries on the next launch.

**Item 3b — `src/server/mcp/tutorial-annotations.ts` (the annotations).** The bytes refresh alone cannot restore the tutorial for an upgrader, and leaves their stored ranges pointing at moved text. Two changes, both in the JS half:

- **Re-seed a stale tutorial record instead of skipping it.** Replace the bare `if (map.has(def.id)) continue;` with: if the id is present **and** its stored `textSnapshot` still equals `def.targetText`, skip as today; if it is present and the snapshot no longer matches, re-anchor it to the def's current `targetText` by writing the record through `withInternal` + `map.set` (Critical Rule 2; `Y_MAP_ANNOTATIONS` from `shared/constants.ts`). **Never route this through `AnnotationLifecycle.remove`** — `tutorial-note-1` is a `note` and that path is note-guarded (ADR-027), so a remove-and-reinject would either throw or, worse, be "fixed" by widening the guard. `tutorial-note-1` **is included** in the re-seed: it is a Tandem-authored tutorial artefact, not a note the user wrote, and leaving it pinned to dead offsets is the outcome this item exists to prevent. A user's OWN notes on that document are untouched by this loop — they carry no `TUTORIAL_ANNOTATION_PREFIX` id — and are covered by the re-anchor below.
- **Run `reanchorAnnotations(doc, samplePath)` after the startup open of the sample.** The ordinary `openFromDisk(samplePath)` at `index.ts:719` reaches no re-anchor pass; the force-open branch (`documents/open.ts:396`) is the only caller that does. Without it, every non-tutorial annotation on the refreshed sample stays durably pinned to text it no longer describes. With it, a moved span answers `degraded` per #1764's `storedRangeStillMatches` gate and **writes nothing**, which preserves the flat range and the relRange for relocation and undo — that is the accepted outcome, stated here and in the PR body rather than left silent: **annotations on a refreshed sample survive as `degraded`, they are not deleted**.

**Item 4 — `src/server/version-check.ts` + `index.ts`.** Split the write out: `checkVersionChange` becomes read-only and a new `stampVersion(currentVersion, versionFilePath)` performs the `mkdir` + `writeFile`. **Extract `index.ts:691-699` into an injectable unit** — `maybeOpenChangelogOnUpgrade({ check, stamp, open })` in `version-check.ts` or a sibling — because a split that makes `checkVersionChange` read-only and forgets the `stampVersion` call in `index.ts` passes every isolated spec while producing a permanent regression: every launch reports `upgraded` and re-opens `CHANGELOG.md` read-only, forever. `index.ts` then calls that one function. It stamps **after** a successful `openFromDisk`, and also on `first-install` (where no open is attempted). A repeatedly-failing open now retries each launch and logs each time, which is the intended trade. Also change the log line at `:695` from "upgraded to vX" to a version-change-neutral wording: a *downgrade* opens the running build's own `CHANGELOG.md`, which is the correct document for the version now running, so the content is right and only the word is wrong — no semver comparator. **No behaviour change to the `transportMode === "http"` bound**: making stdio refresh skills is a behaviour change no issue asks for. Refresh `CLAUDE.md`'s stale `src/server/index.ts:591` citation to `:655` in the auto-open/skill-refresh bullet — **and touch nothing else in `CLAUDE.md`**, because PR #1979 is open against its security-findings bullet.

## Tests

1. `tests/client/` (new or beside `use-tandem-settings-migration.test.ts`): with `_readOnly: true`, `updateSettings({theme:"dark"})` returns `false`, localStorage is untouched, **and** the registered refusal handler fired exactly once; with `_readOnly` absent it returns `true` and the handler does not fire. `beforeEach` calls `_resetTandemSettingsSingletonForTests()`, which now also nulls `onWriteRefused`, and the spy is registered after it. Kills a fix that returns the boolean but never surfaces it, and one that toasts on every write.
2. **The wiring, in `tests/client/settings-readonly-ui.test.ts`** — test 1 registers its OWN handler, so a fix that exports `setSettingsWriteRefusedHandler` and never calls it from `App.svelte` passes test 1 while the user still gets a silent no-op, which is the exact defect #1792 item 1 and #1722 describe. Pin it: either a mount test asserting that with `_readOnly: true` a control click produces exactly one `notifications.push` carrying `dedupKey: "settings-readonly"`, or — if mounting `App.svelte` is impractical — a source-contract test asserting `App.svelte` calls `setSettingsWriteRefusedHandler`. One of the two is required; without it item 1's Done-when has no discriminator. Add the modal case: with `SettingsModal` mounted, the same refusal produces **no** push (the banner is the surface there).
3. `tests/server/integrations/` (beside the storage suite): a `schemaVersion`-too-new file makes `store.read()` reject with `IntegrationsFutureSchemaError`; driving that error through `sendInternal` yields **409**, a body whose `message` names both numbers, and **neither the absolute file path nor its directory portion** — assert on the full path *and* on `path.dirname(filePath)` rather than "no substring of the path", which is unsatisfiable against a message that legitimately contains the string `integrations.json`. That assertion is the one that kills the naive `message: err.message` fix.
4. Client half of item 2: a mocked `!res.ok` response carrying `{ message }` renders a string containing **both schema numbers** at `SettingsClaudeCodeTab` and at `useIntegrationWizard`; a body with no `message` (or unparseable) falls back to the `(HTTP 409)` string.
5. `tests/cli/doctor.test.ts`: a future-schema `integrations.json` produces a warn row; a current one does not.
6. `src-tauri/src/lib.rs` `#[cfg(test)]` with `tempfile` (already a dev-dependency), five cases: fresh dest copies and writes the marker; **same marker version leaves a user-edited file untouched** (kills an unconditional overwrite); a bumped marker refreshes an untouched file; a bumped marker with an edited file writes `<name>.pre-<version>.bak` **and** the new bytes (kills a fix that silently discards the edit); **a failing per-file write leaves the marker unwritten** so the next launch retries.
7. `tests/server/tutorial-annotations.test.ts` — the upgrader shape, which no existing spec covers: seed the Y.Map with the tutorial records at release-N offsets and snapshots, replace the document text with release-N+1 text, run `injectTutorialAnnotations`, and assert every `TUTORIAL_ANNOTATION_PREFIX` record — `tutorial-note-1` included — resolves onto its own current `targetText` rather than a stale offset. A second case: a NON-tutorial annotation on the same document is left alone by the loop and comes back `degraded` (not deleted, not silently re-anchored) after `reanchorAnnotations`.
8. `tests/server/changelog-on-update.test.ts`: migrate the six existing specs to the read/stamp split, and add three that exercise the extracted `maybeOpenChangelogOnUpgrade` — open succeeds → stamp written; open **throws** → stamp NOT written and the next call still returns `upgraded`; `first-install` → stamp written with no open attempted. The existing file imports only `version-check.js` and calls `checkVersionChange` directly, so nothing today would catch a dropped stamp call.
9. Mutation-test each (lesson 5): revert the `stampVersion` move, the `sendInternal` branch, the client body-parse, the marker check, the `map.has` re-seed and the refusal handler in turn, and name the test that goes red for each. Restore from a file copy, never `git checkout`.
