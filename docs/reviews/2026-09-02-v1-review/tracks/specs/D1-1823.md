## Fix

**BOM only.** `src/server/file-io/line-endings.ts` already owns the "source-encoding facts that must survive a round trip" pattern, with `normalizeAndRecordLineEnding(doc, text)` / `restoreLineEndings(doc, text)` called from exactly the two places a BOM has to be handled. Add the sibling pair beside them (and widen the module header from "line endings" to name both facts):

```ts
export function stripAndRecordBom(doc: Y.Doc, text: string): string {
  const has = text.charCodeAt(0) === 0xfeff;
  doc.getMap(Y_MAP_DOCUMENT_META).set(Y_MAP_BOM, has);
  return has ? text.slice(1) : text;
}
export function restoreBom(doc: Y.Doc, text: string): string {
  return doc.getMap(Y_MAP_DOCUMENT_META).get(Y_MAP_BOM) === true ? `<U+FEFF>${text}` : text;
}
```

Call sites, mirroring the line-ending ones exactly:
- `src/server/file-io/markdown.ts`: `mdParser.parse(stripAndRecordBom(doc, normalizeAndRecordLineEnding(doc, markdown)))` on load; `restoreBom(doc, restoreLineEndings(doc, …))` on save.
- `src/server/file-io/index.ts`, `plaintextAdapter`: the same two wrappings, so `.txt`/`.html` get it too.

`Y_MAP_BOM = "bom"` joins `src/shared/constants.ts` next to `Y_MAP_LINE_ENDING`, with the same doc comment shape — a `Y_MAP_DOCUMENT_META` field, and the write is **inert for the channel and durable-sync subsystems** (no observer on per-doc `documentMeta`), which is the accurate form `populate.ts:91` already uses. Do **not** describe it as client-invisible: per-document `documentMeta` syncs to every connected browser over Hocuspocus, and the client reads the same map for `readOnly` / `fileName` / `format`. The narrower claim is the true one and is what the origin-tagging rule actually turns on.

Rules that bite, and each has already broken something in this repo: **Critical Rule 1** — the key is a `Y_MAP_*` constant, never a literal. **Critical Rule 2** — both functions write a Y.Map, so they must run *inside* the caller's already-origin-tagged transact, exactly as `normalizeAndRecordLineEnding`'s own header instructs; they add no `doc.transact` of their own (a raw one in `src/` is forbidden). **Strip before parse, restore after serialize** — a BOM left in the parsed text becomes a character in the first text node and shifts every flat offset by one, which is an annotation-coordinate bug, not a formatting one. `restoreBom` runs **after** `restoreLineEndings` so a CRLF file's BOM is not itself line-ending-rewritten.

No MCP surface, no route, no error code — `docs/mcp-tools.md` unchanged.

## Tests

`tests/server/file-io/line-endings.test.ts` (existing home for the sibling pair):

1. `"<U+FEFF># Title\n"` round-trips byte-identical through `loadMarkdown`/`saveMarkdown`. Kills the whole defect.
2. A file **without** a BOM does not gain one (`"# Title\n"` unchanged) — kills a `restoreBom` that reads a missing key as truthy.
3. `"<U+FEFF>"` + CRLF content round-trips with the BOM first **and** CRLF endings intact — the two facts survive together, which is what a `.md` file from a Windows editor actually looks like. **It does not pin the ordering of the two restores, and must not claim to**: `restoreLineEndings` only rewrites `\n` (`line-endings.ts:64-68`), and a BOM contains no `\n` or `\r`, so `restoreBom(restoreLineEndings(x))` and `restoreLineEndings(restoreBom(x))` produce identical bytes — no assertion over the composed output can discriminate them. The ordering in §Fix stays as written (it is the shape that survives a future `restoreLineEndings` that normalizes more than `\n`), but it is a convention here, not a tested invariant.
4. **Offsets:** `extractText(doc)` of a BOM'd file starts with `#`, not `<U+FEFF>`, and an `anchoredRange` over the first heading resolves to the same offsets as the BOM-less twin. This is the discriminating test — a "fix" that kept the BOM in the doc and stripped it at save time passes 1–3 and silently shifts every annotation.
5. Same four through the plaintext adapter for a `.txt`, since it is a second call-site pair and a fix applied only to `markdown.ts` passes every markdown spec.
6. **The BOM lands off-body: `Y_MAP_DOCUMENT_META` carries it and the body fragment is byte-identical to the BOM-less twin's.** Assert both halves — `doc.getMap(Y_MAP_DOCUMENT_META).get(Y_MAP_BOM) === true`, and the serialized body content (or `extractText`) equal to the twin's. **The earlier form of this spec — "loading a BOM'd file leaves `isDirty(docId)` false" — is deleted as structurally unfailable**, and so is the "a spurious dirty flag is #1852's mechanism" rationale that justified it: `isDirty` returns `false` for any docId with no registered state (`documents/dirty.ts:201-205`), which is what a bare `loadMarkdown` on a fresh Y.Doc leaves; and even with `registerDirtyObserver` attached, the observer is `doc.getXmlFragment(BODY_FRAGMENT).observeDeep(...)` (`:109-115`), with `:150-151` stating outright that an off-fragment `documentMeta` write "bumps no version". A `documentMeta` write cannot move `isDirty`, so that assertion passes under every implementation, including one that leaves the BOM in the body. The replacement above fails against exactly that implementation, which is the risk worth a spec.
7. A new corpus fixture is **not** added: `.gitattributes` normalization makes a committed BOM fixture unreliable in the same way the corpus header already documents for CRLF — synthesize the BOM in the spec.
