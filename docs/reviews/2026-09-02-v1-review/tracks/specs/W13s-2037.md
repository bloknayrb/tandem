# W13s — #2037 `tandem_applyChanges` re-reads a possibly-swapped Y.Doc after an await

Branch `fix/security-applychanges-doc-swap-and-sentry-scrubbing-2037`. Closes #2037. Ledger: none — #2037 is a non-review issue (no `areas/*.md` row, no `experiments/README.md` entry, absent from `refuted.md`); its tracked homes are the `## Open findings` register in `docs/security.md` and `CLAUDE.md`'s Security bullet. Probe: none runnable by hand — the window between the capture and the read is one `fs.stat`, so a live probe cannot be aimed. The deterministic stand-in is the microtask-boundary spec below, which lands the swap between the synchronous prologue and the first `await`.

## Problem

`applyChangesCore` (`src/server/mcp/docx-apply.ts`) captures the room's Y.Doc once — `const { doc: ydoc, filePath } = r;` at `:146`, from `requireDocument(safeDocId)` at `:143` — and then reads that same binding again at `:309`, `const ydocFlatText = extractText(ydoc)`, **after** `await fs.stat(filePath)` at `:291`. Hocuspocus replaces a room's Y.Doc in `onLoadDocument` (`src/server/yjs/provider.ts`: merge state, `destroy()` the old instance, `documents.set(...)`), so an ordinary tab open or stale-tab reconnect during that await leaves `extractText` reading a **destroyed** instance. `ydocFlatText` is the text the accepted suggestions' offsets are scored against (`applyTrackedChanges`, `:313`), so the result is stale tracked changes written into the user's `.docx` with no error.

Same class as #1657 (fixed in #2043, `src/server/local-model/collaborator.ts`), with two differences: this is a stale **read** rather than a discarded write, and this path is **live** — `tandem_applyChanges` ships, while the collaborator twin sits behind `BYO_MODELS_ENABLED`.

What the issue body got half wrong, restated so nobody re-opens it: the `YDocStore` at `:194` is used only at `:198`, before the first await, so the store's lifetime is harmless. The raw `ydoc` binding is the whole residue. The other `ydoc` reads (`:182`, `:215-216`, `:287`) are all before `:291` and need nothing.

**Where the Y.Doc actually lives, because the guard and its test both depend on it.** `requireDocument` (`src/server/documents/registry.ts:353-364`) does **not** carry a doc on the registry entry: `OpenDoc` is `{id, filePath, format, readOnly, source}` (`registry.ts:55-61`) and `requireDocument` returns `doc: getOrCreateDocument(current.docName)` — the provider's own module-level `documents` map (`src/server/yjs/provider.ts:52-59`), which is exactly the map `onLoadDocument` rewrites. The identity predicate is therefore a predicate about the provider map, and the only way to simulate a swap is to replace the entry in that map.

## Fix

One predicate, one wire code, one error arm, one `/api` status row. The model is #2043's `stillOwner` (`collaborator.ts:325-330`): `requireDocument(docName)?.doc === ydoc` — **identity, not presence**, which subsumes the null case (`?.` yields `undefined`, never `=== ydoc`) and additionally rejects a doc that was replaced rather than removed.

- **`src/shared/types.ts`, `ToolErrorCodeSchema` (`:69`):** add `"DOCUMENT_SWAPPED",` in alphabetical position, between `"DEPRECATED"` and `"EMPTY_CONVERSION"`. This is **not optional and not a follow-up**: `mcpError(code: ToolErrorCode, …)` (`src/server/mcp/response.ts:83-84`) takes the enum, so the catch arm below is a TS2345 without it, and `tests/docs/tool-error-codes-claims.test.ts` pins the schema and the `docs/mcp-tools.md` table against each other in **both** directions — a doc row naming no schema member fails just as a schema member with no row does. **Reusing an existing code is not acceptable.** `RELOAD_IN_PROGRESS` and `CONFLICT` both read plausibly and both would leave the MCP-surface spec below non-discriminating; the whole point of the issue is an outcome the caller can tell apart from every other refusal. The schema, the catch arm, the docs row and the `/api` rows land in **one commit**.
- `src/server/mcp/docx-apply.ts`, immediately **before** `:309` (after the `FILE_MODIFIED` guard, before `extractText`):
  ```ts
  if (requireDocument(safeDocId)?.doc !== ydoc) {
    throw Object.assign(
      new Error("The document was reloaded while applying changes. Try again."),
      { code: "DOCUMENT_SWAPPED" },
    );
  }
  ```
  `requireDocument` is already imported (`:34`). Placement is the contract: it must sit after the **last** await preceding the read (`fs.stat`, `:291`) and before `extractText`, so "tidying" it up beside the `:143` resolve re-introduces the bug while still reading as a check. Carry that as a comment naming `:291` as the await it guards. **Refuse, do not re-extract** — re-extracting would score suggestions whose `relRange` positions were resolved at `:215-216` against the *old* fragment (a swap destroys it), so the two halves of the mapping would come from different documents; refusing is the only option that cannot silently write a wrong file. The caller retries.

  Two things the comment must also carry, so neither is "simplified" later. First, **the check is not a pure read**: `requireDocument` → `getOrCreateDocument` *mints and installs* a fresh empty `Y.Doc` when the registry entry survives but the provider map has been emptied (`provider.ts:52-58`). That is accepted, not overlooked — the answer is still "not the doc we captured", the refusal follows immediately, and this is the same call the code already makes at `:143`. Do not swap it for `getDocument(safeDocId)`: that takes a room *name*, while `safeDocId` is `undefined` on the active-document default path, so the two are not interchangeable. Second, **the guard protects the capture→read pairing, not the whole call.** Six awaits follow the read (`fs.readFile` `:310`, `applyTrackedChanges` `:313`, `fs.realpath` `:343`, `fs.lstat`, `copyBackupExclusive`, the `Promise.all` stats, `snapshotBeforeFirstWrite`, `atomicWriteBuffer` `:428`) and are deliberately unguarded: by then the text and the bytes are both captured and mutually consistent, so a swap in those windows cannot desync them.
- Same file, the tool's catch (`:496-536`), beside the existing `EXTERNAL_CONFLICT` / `FILE_MODIFIED` arms: `if (e.code === "DOCUMENT_SWAPPED") return mcpError("DOCUMENT_SWAPPED", e.message);`. Without it the throw falls to `withErrorBoundary` → `INTERNAL_ERROR`, which is the illegible outcome the issue asks to remove.
- `docs/mcp-tools.md`: one row in the shared error-code table, after `SOURCE_MISSING` at `:62`, in that row's own shape — ``| `DOCUMENT_SWAPPED` | **`tandem_applyChanges` only.** The editor reloaded the document between the precondition checks and the text read, so the apply refused rather than score suggestions against a replaced Y.Doc. Retry. |``
- **`POST /api/apply-changes` gets two lines, not zero.** The earlier decision to leave `_shared.ts` untouched was wrong: the default arm is 500, and `sendApiError` logs `[Tandem] Unhandled API error:` with a stack at `status >= 500` (`src/server/mcp/routes/_shared.ts:311-325`), which is exactly the "reporting an expected condition as a Tandem crash in the one artefact a user would send us about it" that `_shared.ts:176` and `docx-apply.ts:276-281` both state as a rule. The browser IS reachable: a swap is caused by any *other* tab or client loading the room, not only by the caller's own connect. So in `src/server/mcp/routes/_shared.ts`, add `case "DOCUMENT_SWAPPED":` to the existing `case "RELOAD_IN_PROGRESS":` group in **`errorCodeToHttpStatus`** (409) and to the same case in **`errorCodeToLabel`** (label `RELOAD_IN_PROGRESS`). Folding onto that label rather than minting a new one is deliberate: it is the same condition in the client's terms ("a reload is in flight, retry"), its `GENERIC_ERROR_MESSAGE` entry already reads correctly for a non-loopback caller, and `path-scrub.test.ts` asserts that map exhaustively, so a novel label would need a new key for no gain. Do **not** fold onto `CONFLICT` — its generic message is "Could not find an available filename."

Rules that bite here: **no `rearmWatch` reference may enter `docx-apply.ts`** (#1749; pinned by `tests/server/document-write-rearm.test.ts`) — this change adds none. No Y.Doc write, so no origin helper is involved (Critical Rule 2); no Y.Map key literal is added (Critical Rule 1); `tandem_applyChanges` is an existing gated tool, so the license-gate tables (Critical Rule 9) are untouched. **ADR-052 replaces this whole `.docx` pipeline with SuperDoc**, so do not refactor `docx-apply.ts` beyond these insertions.

## Tests

`tests/server/docx-apply.test.ts`, one new `describe("applyChangesCore — a mid-apply doc swap", …)` beside the write-guard block at `:975`. That file already arranges real registry state through `addDoc` / `removeDoc` / `setActiveDocId` (`src/server/documents/registry-testing.js`, two-argument `addDoc(DOC_ID, {…})` — see `:940`), imports `getOrCreateDocument` from `src/server/yjs/provider.js` at `:36`, and calls the real `applyChangesCore`, so no mocking is needed. Add `removeDocument` to that existing provider import.

The whole prologue of `applyChangesCore` through `:290` is synchronous, so the swap can be landed deterministically — and it must be landed in the **provider's** map, because that is where the Y.Doc lives (see Problem). Mutating the registry entry does nothing: `OpenDoc` has no `doc` field, so `requireDocument(safeDocId)?.doc` would still be `ydoc` and the call would proceed to write the file.

```ts
const p = applyChangesCore(DOC_ID);   // runs synchronously to `await fs.stat`
removeDocument(DOC_ID);               // drop the provider's entry…
getOrCreateDocument(DOC_ID);          // …and install a DIFFERENT Y.Doc under the same room name
await expect(p).rejects.toMatchObject({ code: "DOCUMENT_SWAPPED" });
```

(`tests/server/adr-034-open-characterization.test.ts:96,114` already drives the provider map this way.)

Three specs, each killing a different wrong implementation:

1. **Swap to a different `Y.Doc` under the same id → `DOCUMENT_SWAPPED`,** using the recipe above. Kills a presence-only check (`requireDocument(safeDocId) !== null`, which is what #1657's original code did and what the issue's phrasing invites) and kills no check at all. Assert the file on disk is **byte-identical to before the call** — the refusal must happen before `fs.readFile`/`applyTrackedChanges`, not after a partial write.
2. **Document removed from the registry entirely mid-apply → `DOCUMENT_SWAPPED`.** This one uses `removeDoc(DOC_ID)` (registry-testing), which genuinely makes `requireDocument(…)` return `null`. Kills an implementation that dereferences without `?.` (which would throw a TypeError → `INTERNAL_ERROR`) and one that treats "gone" as "unchanged".
3. **No swap → still `resolves.toMatchObject({ applied: 1 })`.** The positive control; without it, a check that always throws passes specs 1–2. The existing green apply specs at `:1089`/`:1114` are the same control at file scope, but this block needs its own so a `describe`-local arrangement bug is visible.

One MCP-surface spec in **`tests/server/mcp-wire-codes.test.ts`** — the definitive host, since it drives the real registered tools and `docx-apply.test.ts` has no tool block. Same arrangement, one level up: invoke the `tandem_applyChanges` handler without awaiting, run `removeDocument(DOC_ID)` + `getOrCreateDocument(DOC_ID)` across the same microtask boundary, then assert the envelope's `code` is exactly `"DOCUMENT_SWAPPED"`, **not** `INTERNAL_ERROR`. Kills the fix that adds the predicate and forgets the catch arm, and the one that reuses an existing code.
