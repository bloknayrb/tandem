# W13s — #2037 `tandem_applyChanges` re-reads a possibly-swapped Y.Doc after an await

Branch `fix/security-applychanges-doc-swap-and-sentry-scrubbing-2037`. Closes #2037. Ledger: none — #2037 is a non-review issue; its tracked homes are the `## Open findings` register in `docs/security.md` and `CLAUDE.md`'s Security bullet. Probe: none runnable by hand — the window is one `fs.stat`. The deterministic stand-in is the microtask-boundary spec below.

## Problem

`applyChangesCore` (`src/server/mcp/docx-apply.ts`) captures the room's Y.Doc once — `const { doc: ydoc, filePath } = r;` at `:146`, from `requireDocument(safeDocId)` at `:143` — and reads that same binding again at `:309`, `const ydocFlatText = extractText(ydoc)`, **after** `await fs.stat(filePath)` at `:291`. Hocuspocus replaces a room's Y.Doc in `onLoadDocument` (`src/server/yjs/provider.ts`: merge state, `destroy()` the old instance, `documents.set(...)`), so an ordinary tab open or stale-tab reconnect during that await leaves `extractText` reading a **destroyed** instance. `ydocFlatText` is what the accepted suggestions' offsets are scored against (`applyTrackedChanges`, `:313`), so stale tracked changes go into the user's `.docx` with no error.

Same class as #1657 (fixed in #2043, `src/server/local-model/collaborator.ts`); this one is a stale **read**, and this path is **live**.

Two facts the guard and its test both rest on:

- The `YDocStore` at `:194` is used only at `:198`, before the first await — the issue's "the store is still live" framing is true but harmless. The raw `ydoc` binding is the whole residue. The other `ydoc` reads (`:182`, `:215-216`, `:287`) all precede `:291`.
- `requireDocument` (`src/server/documents/registry.ts:353-364`) does **not** carry a doc on the registry entry: `OpenDoc` is `{id, filePath, format, readOnly, source}` (`registry.ts:55-61`), and it returns `doc: getOrCreateDocument(current.docName)` — the provider's module-level `documents` map (`src/server/yjs/provider.ts:52-59`), which is the map `onLoadDocument` rewrites. So the predicate is a predicate about the provider map, and the only way to simulate a swap is to replace the entry in that map.

## Fix

One predicate in one file. The model is #2043's `stillOwner` (`collaborator.ts:325-330`): identity, not presence — `?.` yields `undefined`, which is never `=== ydoc`, so the null case is subsumed.

`src/server/mcp/docx-apply.ts`, immediately **before** `:309` (after the `FILE_MODIFIED` guard, before `extractText`):

```ts
if (requireDocument(safeDocId)?.doc !== ydoc) {
  throw Object.assign(
    new Error("The document was reloaded while applying changes. Try again."),
    { code: "RELOAD_IN_PROGRESS" },
  );
}
```

`requireDocument` is already imported (`:34`). **Reuse `RELOAD_IN_PROGRESS`; do not mint a wire code.** A Hocuspocus doc swap *is* a reload in the caller's terms; the code is already in `ToolErrorCodeSchema`, `docx-apply.ts:631` **already carries the catch arm** (`if (e.code === "RELOAD_IN_PROGRESS") return mcpError("RELOAD_IN_PROGRESS", e.message)`), and `_shared.ts` already maps it to **409** with the label `RELOAD_IN_PROGRESS` and the message "A reload is already in progress." (`:161`, `:240-241`, `:344`). So `src/shared/types.ts`, `docs/mcp-tools.md` and `routes/_shared.ts` are all untouched, and the `/api` path never reaches the 500 default arm that logs `[Tandem] Unhandled API error` into Copy Diagnostics.

Placement is the contract: the check must sit after the **last** await preceding the read (`fs.stat`, `:291`) and before `extractText`, so "tidying" it up beside the `:143` resolve re-introduces the bug while still reading as a check. Carry a comment naming `:291` as the await it guards, plus two things that must not be simplified later:

- **The check is not a pure read.** `requireDocument` → `getOrCreateDocument` mints and installs a fresh empty `Y.Doc` when the registry entry survives but the provider map was emptied. Accepted: the answer is still "not the doc we captured", the refusal follows immediately, and this is the same call `:143` already makes. Do **not** substitute `getDocument(safeDocId)` — that takes a room *name*, while `safeDocId` is `undefined` on the active-document default path.
- **The guard protects the capture→read pairing, not the whole call.** The awaits after the read (`fs.readFile`, `applyTrackedChanges`, `fs.realpath`, the backup/stat/write sequence) are deliberately unguarded: by then the text and the bytes are captured and mutually consistent, so a swap there cannot desync them.

**Refuse, do not re-extract** — re-extracting would score suggestions whose `relRange` positions were resolved at `:215-216` against the *old* fragment (a swap destroys it), so the two halves of the mapping would come from different documents. The caller retries.

Rules that bite: no `rearmWatch` reference may enter `docx-apply.ts` (#1749) — this change adds none. No Y.Doc write (Critical Rule 2), no Y.Map key literal (Rule 1), no new tool or route (Rule 9). **ADR-052 replaces this `.docx` pipeline with SuperDoc**, so do not refactor `docx-apply.ts` beyond this insertion.

Add `removeDocument` to that existing provider import.

The prologue through `:290` is synchronous, so the swap lands deterministically — and it must land in the **provider's** map, because that is where the Y.Doc lives. Mutating the registry entry does nothing (`OpenDoc` has no `doc` field).

```ts
const p = applyChangesCore(DOC_ID);   // runs synchronously to `await fs.stat`
removeDocument(DOC_ID);               // drop the provider's entry…
getOrCreateDocument(DOC_ID);          // …and install a DIFFERENT Y.Doc under the same room name
await expect(p).rejects.toMatchObject({ code: "RELOAD_IN_PROGRESS" });
```

(`tests/server/adr-034-open-characterization.test.ts:96,114` already drives the provider map this way.)

1. **Swap to a different `Y.Doc` under the same id → rejects with `RELOAD_IN_PROGRESS`** and a message matching `/reloaded while applying/`, using the recipe above. Kills a presence-only check (`requireDocument(safeDocId) !== null`) and kills no check at all. Assert the file on disk is **byte-identical to before the call** — the refusal must precede `fs.readFile`/`applyTrackedChanges`.
2. **Document removed from the registry entirely mid-apply → same rejection,** via `removeDoc(DOC_ID)` (registry-testing), which genuinely makes `requireDocument(…)` return `null`. Kills an implementation that dereferences without `?.` (TypeError → `INTERNAL_ERROR`).
3. **No swap → still `resolves.toMatchObject({ applied: 1 })`.** The positive control; without it a check that always throws passes specs 1–2.
