# W13s — #2037 `tandem_applyChanges` re-reads a possibly-swapped Y.Doc after an await

Branch `fix/security-applychanges-doc-swap-and-sentry-scrubbing-2037`. Closes #2037. Ledger: none — #2037 is a non-review issue (no `areas/*.md` row, no `experiments/README.md` entry, absent from `refuted.md`); its tracked homes are the `## Open findings` register in `docs/security.md:243` and `CLAUDE.md`'s Security bullet. Probe: none runnable by hand — the window between the capture and the read is one `fs.stat`, so a live probe cannot be aimed. The deterministic stand-in is the microtask-boundary spec below, which lands the swap between the synchronous prologue and the first `await`.

## Problem

`applyChangesCore` (`src/server/mcp/docx-apply.ts`) captures the room's Y.Doc once — `const { doc: ydoc, filePath } = r;` at `:146`, from `requireDocument(safeDocId)` at `:143` — and then reads that same binding again at `:309`, `const ydocFlatText = extractText(ydoc)`, **after** `await fs.stat(filePath)` at `:291`. Hocuspocus replaces a room's Y.Doc in `onLoadDocument` (`src/server/yjs/provider.ts`: merge state, `destroy()` the old instance, `documents.set(...)`), so an ordinary tab open or stale-tab reconnect during that await leaves `extractText` reading a **destroyed** instance. `ydocFlatText` is the text the accepted suggestions' offsets are scored against (`applyTrackedChanges`, `:313`), so the result is stale tracked changes written into the user's `.docx` with no error.

Same class as #1657 (fixed in #2043, `src/server/local-model/collaborator.ts`), with two differences: this is a stale **read** rather than a discarded write, and this path is **live** — `tandem_applyChanges` ships, while the collaborator twin sits behind `BYO_MODELS_ENABLED`.

What the issue body got half wrong, restated so nobody re-opens it: the `YDocStore` at `:194` is used only at `:198`, before the first await, so the store's lifetime is harmless. The raw `ydoc` binding is the whole residue. The other `ydoc` reads (`:182`, `:215-216`, `:287`) are all before `:291` and need nothing.

## Fix

One predicate and one error arm. The model is #2043's `stillOwner` (`collaborator.ts:325-330`): `requireDocument(docName)?.doc === ydoc` — **identity, not presence**, which subsumes the null case (`?.` yields `undefined`, never `=== ydoc`) and additionally rejects a doc that was replaced rather than removed.

- `src/server/mcp/docx-apply.ts`, immediately **before** `:309` (after the `FILE_MODIFIED` guard, before `extractText`):
  ```ts
  if (requireDocument(safeDocId)?.doc !== ydoc) {
    throw Object.assign(
      new Error("The document was reloaded while applying changes. Try again."),
      { code: "DOCUMENT_SWAPPED" },
    );
  }
  ```
  `requireDocument` is already imported (`:34`). Placement is the contract: it must sit after the **last** await preceding the read (`fs.stat`, `:291`) and before `extractText`, so "tidying" it up beside the `:143` resolve re-introduces the bug while still reading as a check. Carry that as a comment naming `:291` as the await it guards. **Refuse, do not re-extract** — re-extracting would score suggestions whose `relRange` positions were resolved at `:215-216` against the *old* fragment (a swap destroys it), so the two halves of the mapping would come from different documents; refusing is the only option that cannot silently write a wrong file. The caller retries.
- Same file, the tool's catch (`:505-534`), beside the existing `EXTERNAL_CONFLICT` / `FILE_MODIFIED` arms: `if (e.code === "DOCUMENT_SWAPPED") return mcpError("DOCUMENT_SWAPPED", e.message);`. Without it the throw falls to `withErrorBoundary` → `INTERNAL_ERROR`, which is the illegible outcome the issue asks to remove.
- `docs/mcp-tools.md`: one row in the shared error-code table (after `SOURCE_MISSING` at `:62`), in that row's own shape — ``| `DOCUMENT_SWAPPED` | **`tandem_applyChanges` only.** The editor reloaded the document between the precondition checks and the text read, so the apply refused rather than score suggestions against a replaced Y.Doc. Retry. |``
- `POST /api/apply-changes` (`src/server/mcp/routes/apply-changes.ts`) is **unchanged**: `sendApiError` → `_shared.ts`'s default arm → `INTERNAL`. Only the MCP surface can act on the retry, the browser client never sees this state (a swap in its own room means it just connected), and adding a label row is scope the issue does not ask for. State it in the PR body so it reads as decided, not missed.

Rules that bite here: **no `rearmWatch` reference may enter this file** (#1749; pinned by `tests/server/document-write-rearm.test.ts`) — this change adds none. No Y.Doc write, so no origin helper is involved (Critical Rule 2); no Y.Map key literal is added (Critical Rule 1); `tandem_applyChanges` is an existing gated tool, so the license-gate tables (Critical Rule 9) are untouched. **ADR-052 replaces this whole `.docx` pipeline with SuperDoc**, so do not refactor `docx-apply.ts` beyond these two insertions.

## Tests

`tests/server/docx-apply.test.ts`, one new `describe("applyChangesCore — a mid-apply doc swap", …)` beside the write-guard block at `:975`. That file already arranges real registry state through `addDoc` / `removeDoc` / `setActiveDocId` (`src/server/documents/registry-testing.js`) and calls the real `applyChangesCore`, so no mocking is needed.

The whole prologue of `applyChangesCore` through `:290` is synchronous, so the swap can be landed deterministically:

```ts
const p = applyChangesCore(DOC_ID);   // runs synchronously to `await fs.stat`
addDoc({ ...entry, doc: new Y.Doc() }); // replace the registry entry, same id
await expect(p).rejects.toMatchObject({ code: "DOCUMENT_SWAPPED" });
```

Three specs, each killing a different wrong implementation:

1. **Swap to a different `Y.Doc` under the same id → `DOCUMENT_SWAPPED`.** Kills a presence-only check (`requireDocument(safeDocId) !== null`, which is what #1657's original code did and what the issue's phrasing invites) and kills no check at all. Assert the file on disk is **byte-identical to before the call** — the refusal must happen before `fs.readFile`/`applyTrackedChanges`, not after a partial write.
2. **Document removed entirely mid-apply → `DOCUMENT_SWAPPED`.** Kills an implementation that dereferences without `?.` (which would throw a TypeError → `INTERNAL_ERROR`) and one that treats "gone" as "unchanged".
3. **No swap → still `resolves.toMatchObject({ applied: 1 })`.** The positive control; without it, a check that always throws passes specs 1–2. The existing green apply specs at `:1089`/`:1114` are the same control at file scope, but this block needs its own so a `describe`-local arrangement bug is visible.

One MCP-surface spec in the same file's tool block (or `tests/server/mcp-tool-integration.test.ts` if the tool is registered there): a thrown `DOCUMENT_SWAPPED` comes back as envelope code `"DOCUMENT_SWAPPED"`, **not** `INTERNAL_ERROR` — kills the fix that adds the predicate and forgets the catch arm.
