# E2-rust — #1810 `refresh_registration` runs only on autostart launches, so a moved app or a flagless registration is never repaired

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1810. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:20`. Probe: none automatable (the repair is an OS registration write); verification is `cargo test` plus a smoke line for Bryan.

## Problem

`refresh_registration` (`src-tauri/src/autostart.rs:138`) re-writes an existing login item with the current executable path and argument list. It is idempotent by construction — it only calls `manager.enable()` when `manager.is_enabled()` already returns `Ok(true)`, so it can never turn autostart on.

Its single call site (`src-tauri/src/lib.rs:1519-1532`) sits inside `if autostart_launch {` (`:1487`), the branch that runs only when the app was itself launched *by* the registration. The repair therefore requires the thing it repairs to be working:

- A user enables start-at-login, then moves or renames the app (or a macOS update changes the bundle path). The login item points at the old path, autostart never fires, and the repair path is unreachable forever.
- A registration written by a Tandem older than `--tandem-autostart` boots visible and spawns Claude — the exact behaviour the flag exists to prevent — and is only upgraded on a launch *that registration* produced.

The existing comment at `:1524-1527` states the rationale as "a user who moved the app will autostart at least once before the path matters", which is what the issue refutes: a moved app does not autostart at all.

## Fix

Hoist the spawn block out of `if autostart_launch {` so it runs on every **eligible** launch — where "eligible" is a guard the hoist makes necessary.

### The path guard, which is the other half of the fix

`manager.enable()` bakes `std::env::current_exe()` into the login item. The autostart plugin is registered **with no `cfg` gate and no dev carve-out** (`lib.rs:1098-1101`), and `src-tauri/tauri.conf.json:3` is `"productName": "Tandem"` for debug and release alike — so a debug build's `is_enabled()` reads the *installed* app's HKCU `Run\Tandem` value and `enable()` would overwrite it with `target/debug/tandem.exe`. Today that cannot happen only because the call sits inside `if autostart_launch {`, and `autostart_launch` comes from the `--tandem-autostart` argv flag (`resolve_autostart_launch`, `lib.rs:1140`) that a `cargo tauri dev` run never passes. **Hoisting removes that accidental guard.** The next `cargo clean` would then leave the user's login item pointing at a deleted path — the exact failure #1810 exists to fix, newly introduced on the maintainer's own machine, and the same shape for a portable copy, an extracted archive or a `.app` run off a mounted DMG.

So the hoisted block is gated on a **pure, testable predicate** in `autostart.rs`:

```rust
/// May we re-bake this launch's executable path into the OS login item?
///
/// `manager.enable()` writes whatever path the plugin resolves for this launch
/// (`$APPIMAGE` on Linux when set, else `current_exe()`); the caller resolves it
/// the same way and passes it in as `exe`. An autostart launch is
/// always eligible — that launch came *from* the registration, so its path is by
/// definition the registered one. Any other launch must prove it is not an
/// ephemeral copy first, or a `cargo tauri dev` run (same `productName`, same
/// HKCU key) repoints a working login item at `target/debug/`, and a `.app` run
/// off a mounted DMG repoints it at a volume that will be ejected.
pub(crate) fn autostart_refresh_allowed(
    autostart_launch: bool,
    is_debug: bool,
    exe: &std::path::Path,
    temp_dir: &std::path::Path,
) -> bool
```

Order: `autostart_launch` -> `true`; then `is_debug` -> `false`; then `exe` under `temp_dir` -> `false`; then `exe` under `/Volumes/` -> `false` (checked on every platform — a Windows path never starts with `/Volumes/`, so no `cfg` is needed and the case stays testable on the ubuntu leg); else `true`.

The call site passes `autostart_launch`, `cfg!(debug_assertions)`, **the path the plugin will actually bake** (see below) and `std::env::temp_dir()`. A path-resolution error is a skip, not a refresh. The skip logs at `info` naming which arm refused, so a developer who wonders why their dev build did not touch autostart can find out.

**The `exe` argument is the plugin's baked path, NOT bare `current_exe()`.** `tauri-plugin-autostart` 2.5.1 does not bake `current_exe()` on Linux — it prefers `$APPIMAGE`: `#[cfg(target_os = "linux")] if let Some(appimage) = app.env().appimage … { builder.set_app_path(&appimage) } else { builder.set_app_path(&current_exe…) }` (`src/lib.rs:214-223`, read in the vendored crate). AppImage is a shipped target (`tauri.conf.json:36` is `"targets": "all"`), and on an AppImage launch `current_exe()` is always `/tmp/.mount_XXXXXX/usr/bin/tandem` — so a call site passing `current_exe()` would hit the temp arm on **every** non-autostart AppImage launch and refuse forever, while the registration it is meant to repair holds a perfectly stable `.AppImage` path. That is precisely #1810's premise (a moved app never autostarts) re-introduced as a permanent silent no-op, and the skip logs at `info`, below the release `LevelFilter::Warn` floor, so nothing would surface it.

So the call site resolves the path the same way the plugin does — on Linux `app.env().appimage` first, falling back to `std::env::current_exe()`; elsewhere `current_exe()` — and hands *that* to the predicate. The predicate itself stays pure and unchanged: the resolution is the caller's job, which is what keeps the whole thing testable by value on the ubuntu leg. macOS is unaffected: under `MacosLauncher::LaunchAgent` the plugin bakes the canonicalised `current_exe()` (`lib.rs:200-212`), which is what the `/Volumes/` arm already tests.

### The hoist itself

- Move `lib.rs:1519-1532` (the `{ let refresh_handle = app.handle().clone(); tauri::async_runtime::spawn_blocking(move || { autostart::refresh_registration(&refresh_handle); }); }` block) to just **before** the `// --- Autostart visibility decision (#1236)` marker at `:1482`, still after the tray build, wrapped in the `autostart_refresh_allowed(...)` check. It reads nothing from that branch — not `tray_available`, not `hide` — so nothing else moves with it.
- Rewrite its comment. The "Scoped to autostart launches" sentence and the "will autostart at least once" claim are now wrong and are precisely what a later reader would restore the `if` from. New text: runs on every launch that passes `autostart_refresh_allowed`, because a *moved* app never autostarts, which makes an autostart-only repair unreachable for the one case it exists to fix; still only ever refreshes an existing registration (`is_enabled()` is the gate inside the function); still off the startup critical path; and the guard is there because `enable()` bakes `current_exe()`.
- `refresh_registration`'s own docblock (`autostart.rs:130-137`) gains one line: it is called on every eligible launch, and the `Ok(false)` arm is what keeps that from being an enable.

**Why this is safe on each platform, checked rather than assumed — and the check is about *which path gets written*, not only about prompts:**

- **Windows** — an HKCU `Run` value write per launch, off the critical path via `spawn_blocking`. No prompt, no elevation. The value written is `current_exe()`, which is why the debug and temp arms exist.
- **macOS** — the plugin is registered with `MacosLauncher::LaunchAgent` (`lib.rs:1098-1099`), so `enable()` writes a `LaunchAgents` plist. It does **not** take the AppleScript path that `autostart.rs`'s module docblock warns needs Automation (TCC) approval, so there is no per-launch consent prompt. The `/Volumes/` arm covers run-from-DMG. **Read, not run — there is no macOS hardware here.**
- **Linux** — a `~/.config/autostart/*.desktop` file write. Same shape as Windows, with one path twist: a real AppImage launch resolves to `$APPIMAGE` (a stable `.AppImage` on disk) and is eligible, while an *extracted* AppImage — `--appimage-extract` then `AppRun` from a scratch dir — sets no `$APPIMAGE`, falls back to `current_exe()` and is caught by the temp arm. That split is only correct because the call site resolves the path the plugin's way; passing `current_exe()` collapses both into a refusal. **Read, not run — there is no Linux hardware here.**

**Rules that bite, all three from CLAUDE.md's start-at-login rule and none of them touched:** the `LAUNCHER_DEFERRED` latch is stored once at `lib.rs:1148` and re-read per sidecar spawn at `sidecar.rs:1756` — this edit does not move, capture or re-derive it. `show_main_window` remains the single release point. **No `tandem:settings` field is added**: the registration state is deliberately read from the OS on every call (`AutostartStatus`'s docblock, `autostart.rs:35-39`) precisely because it is mutable outside Tandem, and a mirrored boolean would drift.

**#1599 / `tests/docs/config-writer-set-claims.test.ts`:** that test pins the set of *Tandem config* writers in `src/`. `refresh_registration` writes an OS login item through `tauri-plugin-autostart`, not a Tandem config file, and is Rust — outside that test's sweep, and the accepted finding's bound is not widened. State this in the PR body.

## Tests

**One test, in `autostart.rs`'s existing `mod tests` (`:154`):** `fn autostart_refresh_is_refused_for_ephemeral_binaries()` — a pure value test on `autostart_refresh_allowed`, cross-platform, no `AppHandle`.

Assert: `(true, true, <temp path>, <temp>) == true` (an autostart launch is always eligible); `(false, true, <installed path>, <temp>) == false` (debug build); `(false, false, <temp>/x/tandem, <temp>) == false`; `(false, false, "/Volumes/Tandem/Tandem.app/…", <temp>) == false`; `(false, false, <installed path>, <temp>) == true`; and — sitting deliberately **next to** the `<temp>/x/tandem` case — `(false, false, "/home/u/Apps/Tandem.AppImage", <temp>) == true`. The pair is the point: an installed AppImage must be eligible even though its `current_exe()` is under `/tmp`, so an implementation that hands the predicate `current_exe()` instead of `app.env().appimage` goes red.

This is the invariant that makes "run it on every launch" safe. The three existing `autostart.rs` tests (`error_codes_are_path_free`, `io_errors_map_to_the_io_code`, and the anyhow one) are unaffected and must stay green.

**Mutation check:** make `autostart_refresh_allowed` return `true` unconditionally and the test goes red — specifically on the debug arm, the arm that would repoint a real user's login item at `target/debug/`. Restore from a file copy, never `git checkout`.

## Done when

The refresh block sits outside `if autostart_launch` and behind `autostart_refresh_allowed`; the call site feeds the predicate the plugin's baked path (`app.env().appimage` first on Linux), not bare `current_exe()`; the predicate test passes, AppImage case included; the stale "scoped to autostart launches" comment is gone; no debug, temp-dir or `/Volumes/` launch can rewrite a login item, and an installed AppImage is not refused; `cargo test` green.

## Not in scope

The smoke verification the issue asks for — enable start-at-login, move the app, reboot, confirm it starts — is hardware and goes under `bryan`, on all three platforms. Anything about `should_start_hidden`, the Linux first-launch backstop, the tray, or `LAUNCHER_DEFERRED`'s release timing.

## PR-body caveats this issue contributes

## PR review round 1

The hoist is unchanged. `autostart_refresh_allowed` gained three refusals and lost one bypass,
all from review findings against the eligibility predicate the hoist made necessary:

- **The `autostart_launch` short-circuit is gone, and so is the parameter.** It returned `true`
  before `is_debug` was consulted, justified as "that launch came *from* the registration". The
  flag is `has_argv_flag(args, AUTOSTART_FLAG)` — pure argv — so `target/debug/tandem.exe
  --tandem-autostart`, which is how a developer exercises the hidden-start path, took the bypass
  and re-baked a real login item into a build tree. It also bought nothing: a genuine OS autostart
  of an installed binary passes every remaining arm.
- **A `target/{debug,release}` component pair is refused.** `cfg!(debug_assertions)` is about the
  profile; the hazard the docblock describes is about the path. `cargo tauri build` followed by one
  launch of `target/release/tandem.exe` to smoke a release candidate is a release-profile binary
  outside the temp dir, and the next rebuild deletes it.
- **UNC / network paths are refused.** A `\host\share\...` exe in HKCU `Run` makes Windows resolve
  and authenticate to that SMB host at every logon, forever, with no Tandem process involved and no
  UI saying so — the NTLM-disclosure class `validate_open_candidate` already refuses UNC for,
  reached through a persistence entry instead of a file read. All three spellings, including the
  `\?\UNC\` form canonicalization itself produces.
- **Both paths are canonicalized before comparison** (`canonical_for_refresh_check`), and the temp
  prefix test is case-insensitive. Uncanonicalized, the temp arm never fired on the case it was
  written for: macOS `$TMPDIR` is `/var/folders/…` while a translocated bundle's `current_exe()` is
  `/private/var/folders/…`, and `Path::starts_with` is a literal component comparison. On Windows
  `%TEMP%` can be an 8.3 short path the long-form exe path never matches.

**Not fixed, filed instead: #1967** — the Windows twin of the `/Volumes/` arm (a launch from a
removable or external drive) needs `GetDriveTypeW`, i.e. FFI or a `windows`-crate dependency,
neither of which is in `src-tauri/Cargo.toml`. Bounded: the failure is a silently dead
start-at-login, not a security issue.
