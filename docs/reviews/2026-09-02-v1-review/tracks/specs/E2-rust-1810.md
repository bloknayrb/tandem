# E2-rust — #1810 `refresh_registration` runs only on autostart launches, so a moved app or a flagless registration is never repaired

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1810. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:20`. Probe: none automatable (the repair is an OS registration write); verification is `cargo test` plus a smoke line for Bryan.

## Problem

`refresh_registration` (`src-tauri/src/autostart.rs:138`) re-writes an existing login item with the current executable path and argument list. It is idempotent by construction — it only calls `manager.enable()` when `manager.is_enabled()` already returns `Ok(true)`, so it can never turn autostart on.

Its single call site (`src-tauri/src/lib.rs:1519-1532`) sits inside `if autostart_launch {` (`:1487`), the branch that runs only when the app was itself launched *by* the registration. The repair therefore requires the thing it repairs to be working:

- A user enables start-at-login, then moves or renames the app (or a macOS update changes the bundle path). The login item points at the old path, autostart never fires, and the repair path is unreachable forever.
- A registration written by a Tandem older than `--tandem-autostart` boots visible and spawns Claude — the exact behaviour the flag exists to prevent — and is only upgraded on a launch *that registration* produced.

The existing comment at `:1524-1527` states the rationale as "a user who moved the app will autostart at least once before the path matters", which is the assumption the issue refutes: a moved app does not autostart at all.

## Fix

Hoist the spawn block out of the `if autostart_launch {` branch so it runs on **every eligible** launch — where "eligible" is a guard the hoist makes necessary, and which the first draft did not have.

### The path guard, which is the other half of the fix

`manager.enable()` bakes `std::env::current_exe()` into the login item. The autostart plugin is registered **with no `cfg` gate and no dev carve-out** (`lib.rs:1098-1101`), and `src-tauri/tauri.conf.json:3` is `"productName": "Tandem"` for debug and release alike — so a debug build's `is_enabled()` reads the *installed* app's HKCU `Run\Tandem` value and `enable()` would overwrite it with `target/debug/tandem.exe`. Today that cannot happen only because the call sits inside `if autostart_launch {`, and `autostart_launch` comes from the `--tandem-autostart` argv flag (`resolve_autostart_launch`, `lib.rs:1140`) that a `cargo tauri dev` run never passes. **Hoisting removes that accidental guard.** The next `cargo clean` or worktree removal would then leave the user's login item pointing at a deleted path — the exact failure #1810 exists to fix, newly introduced on the maintainer's own machine, and the same shape for anyone running a portable copy, an extracted archive or a `.app` off a mounted DMG.

So the hoisted block is gated on a **pure, testable predicate** in `autostart.rs`:

```rust
/// May we re-bake `current_exe()` into the OS login item on this launch?
///
/// `manager.enable()` writes whatever binary is running. An autostart launch is
/// always eligible — that launch came *from* the registration, so its path is by
/// definition the registered one. Any other launch must prove it is not an
/// ephemeral copy first, or a `cargo tauri dev` run (same `productName`, same
/// HKCU key) repoints a working login item at `target/debug/`, and a `.app` run
/// off a mounted DMG repoints it at a volume that will be ejected.
pub(crate) fn autostart_refresh_allowed(
    autostart_launch: bool,
    is_debug: bool,
    exe: &std::path::Path,
    temp_dir: &std::path::Path,
) -> bool
```

Order: `autostart_launch` -> `true`; then `is_debug` -> `false`; then `exe` under `temp_dir` -> `false`; then `exe` under `/Volumes/` -> `false` (checked on every platform — a Windows path never starts with `/Volumes/`, so no `cfg` is needed and the case stays testable on the ubuntu leg); else `true`.

- The call site passes `autostart_launch`, `cfg!(debug_assertions)`, `std::env::current_exe()` and `std::env::temp_dir()`. A `current_exe()` error is a skip (log at `info`), not a refresh.
- The skip logs at `info` naming which arm refused, so a developer who wonders why their dev build did not touch autostart can find out.

### The hoist itself

- Move `lib.rs:1519-1532` (the `{ let refresh_handle = app.handle().clone(); tauri::async_runtime::spawn_blocking(move || { autostart::refresh_registration(&refresh_handle); }); }` block) to just **before** the `// --- Autostart visibility decision (#1236)` marker at `:1482`, still after the tray build, wrapped in the `autostart_refresh_allowed(...)` check. It does not read `tray_available`, `hide`, or anything else from that branch, so nothing else moves with it.
- Rewrite its comment. The "Scoped to autostart launches" sentence and the "will autostart at least once" claim are now wrong and are precisely what a later reader would restore the `if` from. New text: runs on every launch that passes `autostart_refresh_allowed`, because a *moved* app never autostarts, which makes an autostart-only repair unreachable for the one case it exists to fix; still only ever refreshes an existing registration (`is_enabled()` is the gate inside the function); still off the startup critical path; and the guard is there because `enable()` bakes `current_exe()`.
- `refresh_registration`'s own docblock (`autostart.rs:130-137`) gains one line: it is called on every eligible launch, and the `Ok(false)` arm is what keeps that from being an enable.

**Why this is safe on each platform, checked rather than assumed — and the check is now about *which path gets written*, not only about prompts:**

- **Windows** — an HKCU `Run` value write per launch, off the critical path via `spawn_blocking`. No prompt, no elevation. The value written is `current_exe()`, which is why the debug/temp arms of the predicate exist.
- **macOS** — the plugin is registered with `MacosLauncher::LaunchAgent` (`lib.rs:1098-1099`), so `enable()` writes a `LaunchAgents` plist. It does **not** take the AppleScript path that `autostart.rs`'s module docblock warns needs Automation (TCC) approval, so there is no per-launch consent prompt. The `/Volumes/` arm covers the run-from-DMG case, which is the macOS-specific way to write an ephemeral path. **Read, not run — there is no macOS hardware here.**
- **Linux** — a `~/.config/autostart/*.desktop` file write. Same shape as Windows; the temp arm covers an extracted-AppImage run.

**Rules that bite, all three from CLAUDE.md's start-at-login rule and none of them touched by this change:** the `LAUNCHER_DEFERRED` latch is stored once at `lib.rs:1148` from `resolve_autostart_launch` and re-read per sidecar spawn at `sidecar.rs:1756` — this edit does not move, capture or re-derive it. `show_main_window` remains the single release point. **No `tandem:settings` field is added**: the registration state is deliberately read from the OS on every call (`AutostartStatus`'s docblock, `autostart.rs:35-39`) precisely because it is mutable outside Tandem, and a mirrored boolean would drift.

**#1599 / `tests/docs/config-writer-set-claims.test.ts`:** that test pins the set of *Tandem config* writers in `src/`. `refresh_registration` writes an OS login item through `tauri-plugin-autostart`, not a Tandem config file, and is Rust — it is outside that test's sweep and the accepted finding's bound is not widened. State this in the PR body rather than leaving a reviewer to re-derive it.

## Tests

`refresh_registration` needs an `AppHandle`, so two of the three tests are structural, following `sidecar.rs:4107`'s `include_str!` precedent. **Module names:** a new `#[cfg(test)] mod autostart_refresh_tests` in `lib.rs` for test 1 — **`lib.rs` has no `mod tests`**, every test module there is named — and the existing `mod tests` in `autostart.rs` (`:154`) for tests 2 and 3. All source slicing uses `char_indices()`, never a raw byte range (`sidecar.rs:4119`: "this file is full of em dashes"; `lib.rs` is the same).

1. `fn refresh_registration_runs_on_every_launch_not_only_autostart_ones()` — `include_str!("lib.rs")`. **Both anchors of the first draft were broken; both are replaced:**

   - **The count needle must be `concat!`-ed.** The first draft asserted "exactly **one** `autostart::refresh_registration(` occurrence" over a file the test itself lives in, so the test's own literal makes the count 2 and the assertion fails on a correct fix. Build it at runtime per the precedent the spec already cited but did not follow — `sidecar.rs:3105` explains the trap ("the needles are `concat!`-ed rather than written whole, so the verbatim sequence never appears in this test") and `sidecar.rs:4071` uses it (`const APP_DATA_KEY: &str = concat!("TANDEM_APP_", "DATA_DIR");`). Here: `const CALL: &str = concat!("autostart::", "refresh_registration(");` then `assert_eq!(src.matches(CALL).count(), 1, …)`.
   - **The ordering anchor must be unambiguous.** `lib.rs` contains **two** `if autostart_launch {` — `:1223` (the deferred logging block) and `:1487` (the visibility block this spec means). A naive `find()` returns 1223, so "the call's byte offset is before that `if`" is false **both today (call at `:1529`) and after the fix (call moved to ~`:1482`, still after 1223)**: the test could never go green. Anchor on the unique marker `// --- Autostart visibility decision (#1236)` (`lib.rs:1482`, verified to occur exactly once) instead, and assert the call offset is **before** it. As a second, self-documenting guard, first assert `src.matches("if autostart_launch {").count() == 2` with its own message, so a future edit that collapses or duplicates those branches fails as a structural change rather than as a mysterious ordering inversion.

   Goes red on today's code and on any re-nesting. The occurrence count is what stops a fix that *adds* a second call rather than moving the first.
2. `fn refresh_registration_enables_only_on_an_existing_registration()` — `include_str!("autostart.rs")`, slice `refresh_registration`'s body, and assert **all three**:
   - it contains `is_enabled()`;
   - `manager.enable()` occurs **exactly once** in the slice;
   - that occurrence's byte offset lies **between** the `Ok(true) => {` offset and the `Ok(false)` offset.

   **The first draft's needles (`is_enabled()` plus `Ok(false) => {}`) are defeated by the single mutation it calls the worst outcome of the change**: `Ok(false) => { let _ = manager.enable(); }` written *alongside* an untouched empty arm still contains both literals, and an unconditional enable turns start-at-login **on** for every user on their next launch. Confining the enable to the `Ok(true)` arm positionally is what actually pins it.
3. `fn autostart_refresh_is_refused_for_ephemeral_binaries()` — a pure unit test on `autostart_refresh_allowed`, cross-platform, no `AppHandle`. Assert: `(true, true, <temp path>, <temp>) == true` (an autostart launch is always eligible); `(false, true, <installed path>, <temp>) == false` (debug build); `(false, false, <temp>/x/tandem, <temp>) == false`; `(false, false, "/Volumes/Tandem/Tandem.app/…", <temp>) == false`; `(false, false, <installed path>, <temp>) == true`. This is the invariant that makes "run it on every launch" safe, and the finding that a structural "the guard exists" scan is weaker than a value test is why it is a unit test rather than a fourth `include_str!`.

The three existing `autostart.rs` tests (`error_codes_are_path_free`, `io_errors_map_to_the_io_code`, and the anyhow one) are unaffected and must stay green.

**Mutation check:** move the block back inside `if autostart_launch {` and test 1 goes red; add a second `refresh_registration(` call instead of moving the first and test 1's count assertion goes red; add `manager.enable()` to the `Ok(false)` arm and test 2 goes red; make `autostart_refresh_allowed` return `true` unconditionally and test 3 goes red. Restore from a file copy, never `git checkout`.

## Done when

The refresh block sits outside `if autostart_launch` and behind `autostart_refresh_allowed`; all three tests pass; the stale "scoped to autostart launches" comment is gone; no debug, temp-dir or `/Volumes/` launch can rewrite a login item; `cargo test` green.

## Not in scope

The smoke verification the issue asks for — enable start-at-login, move the app, reboot, confirm it starts — is hardware and goes under `bryan`, on all three platforms. Anything about `should_start_hidden`, the Linux first-launch backstop, the tray, or `LAUNCHER_DEFERRED`'s release timing.
