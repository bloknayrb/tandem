## Problem

1. **`RESEND_FROM` is presence-checked at the point of use, after everything durable.** `sendViaResend` (`infra/license-issuance-worker/src/worker.ts:748`) only tests `!env.RESEND_FROM`. The shipped `wrangler.toml:22` value is `REPLACE_WITH_VERIFIED_SENDER`, which is *present*, so `issue()` mints the license, writes `LICENSE_KV`, writes the ledger, gets a Resend 422 and returns a retryable 500 forever — Polar retries into endpoint auto-disable, the README's dominant sale-loss mode. `SUPPORT_EMAIL` gets the opposite treatment (`:989-999`, in the fetch handler *before* `handleIssuance`).
2. **`revoke()` reads the order id from `data.id`** (`:453`). **The measured consequence is narrower than the issue's.** `:453-455` refuses before the id is ever used to write, and a genuine Polar *refund object* carries no `refunded` boolean, so it exits at `:455` as `"dropped"` — alertable, nothing committed, recoverable by a manual re-send. The junk-tombstone outcome needs a payload with a refund's id layout *and* an order's `refunded: true`, a hybrid shape no observed Polar object has. So this is a **latent id assumption**, not a live silent-revocation miss; the PR body and the issue-close note must say that. The fix is still correct — the assumption is wrong for any `order_id`-bearing payload.
3. **`isAlertable` is `result === "dropped" || stage === "email"`** (`:944`), so a bad `TANDEM_PRIVATE_KEY` (`stage: "config"`) or a bad `SUPPORT_EMAIL` (`stage: "config-support-email"`) 503s every request with no alert — and a 503 is what drives Polar's auto-disable.
4. **`infra/` coverage — half the issue's claim is refuted.** biome: `npx biome check infra` → *"Checked 0 files… these paths were provided but ignored: infra"* (`biome.json:19-28` has no `infra` entry) — **confirmed**. eslint: `npx eslint infra` lints all three files and `--no-inline-config` surfaces the suppressed warnings, so *"linted by nothing"* and *"the `eslint-disable` comments are inert"* are both **refuted**. tsc: all three files are reached transitively by the two Worker test suites, so they are typechecked today — incidentally, not by configuration.
5. **`wrangler deploy` is unpinned.** No `package.json` in either worker dir; `./crypto.js` resolves to `crypto.ts` only because the bundler rewrites the extension, which is wrangler-version behaviour.
6. **Four doc-drift lines**, all re-verified: update README `:16` says the Worker "logs only `{ result, ts }`" (it logs `reason` too); update README `:26-27` attributes `TANDEM_CF_*` to "the webhook side" when `src/server/license/kv-store.ts:6-11` says those belong to the out-of-band writer; issuance README `:87-88` omits `--remote` on `wrangler kv key get`; the issuance README deploy block never mentions `SUPPORT_EMAIL`, which the Worker 503s without.

## Fix

All in `infra/license-issuance-worker/src/worker.ts` unless named otherwise. **The model for every guard is `supportEmailProblem` + its fetch-handler call site — copy its placement, not a new shape.**

- **Rename the module-private `SUPPORT_EMAIL_PLACEHOLDER` (`:710`) to `CONFIG_PLACEHOLDER`.** Its regex `/replace_with|yourdomain/i` already covers `RESEND_FROM`'s two plausible leftovers.
- **Add `export function resendFromProblem(raw)`** — `supportEmailProblem(raw)` with `"too-long"` mapped to `null`. Doc-comment the divergence: `MAX_SUPPORT_EMAIL_LEN` (`:720`) exists because `SUPPORT_EMAIL` is printed in the email body; `RESEND_FROM` is a header, and the cap would 503 a legal `Long Display Name <noreply@…>`. Do not inline a second regex.
- **Add `"config-resend-from"` to `FailStage`** (`:121-128`) and guard in the fetch handler immediately after the `SUPPORT_EMAIL` block (`:989-999`), same shape: `log({result:"error", ts, stage:"config-resend-from"}); return jsonResponse(503);`. A **separate stage**, because the stage is the only thing telling an operator which line to fix. **This also makes an *unset* `RESEND_FROM` fail before the mint — deliberate, and the half an implementer drops** (Test 2b pins it). `sendViaResend`'s own guard stays as belt-and-braces.
- **`orderIdOf(data)`** — one module-private helper, `order_id` preferred, `id` as fallback — used by both `issue()` (`:325`) and `revoke()` (`:453`). Comment it honestly: the preference is a shape guess until the `docs/licensing-operations.md` §8 sandbox fixture lands, and it is shared so the two cannot drift — they agree on the ledger key by construction, and nothing has been deployed, so no stored record can be stranded by a wrong guess.
- **`isAlertable` (`:944`) gains the three config stages, enumerated:** `dropped || "email" || "config" || "config-support-email" || "config-resend-from"`. Comment why: `startsWith("config")` silently adopts every future stage, `result === "error"` sweeps in `ledger`/`unexpected`/`blob-size` and storms. Record the bound with it — these stages are the first alertable class reachable **before** `verifyStandardWebhook` (both config guards run in `default.fetch`, the signature gate is at `:546-554`), so their volume is bounded by inbound requests against a per-isolate throttle. That is acceptable only because they fire while the Worker is already refusing every sale; do **not** move the guards behind verification, which re-opens item 1.
- **`alertBody` (`:870-885`) gains a third arm** naming `stage`: *"The Worker is refusing every webhook (misconfiguration) — no sale can complete"*. Delete the "a third arm here would be dead code" comment. **`config` is overloaded across two secrets** (`:968` bad `TANDEM_PRIVATE_KEY`, `:518` missing `POLAR_WEBHOOK_SECRET`) — say so rather than promising a one-to-one stage→line map. Measured: the tombstone write follows the *second* read, so it narrows by one KV round trip — not by the whole request as `issue()`'s does (that one spans the async Ed25519 sign). 4. **`isAlertable` truth table.** True for `{result:"dropped"}`, `stage:"email"` and each of the three config stages.    ```
   — an unknown `config-*` stage must not be adopted into alerting, which is the property the "enumerated, not prefix-matched" comment claims.
5. **A broken `RESEND_FROM` alerts via the webhook and NOT via Resend, with the webhook channel *exhausted*.** `sendOperatorAlert` returns at `:904` the moment a stub answers ok, so any Resend assertion against a healthy webhook is vacuous. **Two separate `it()` blocks** (same shared-throttle-key reason as 2/2b), both with a placeholder `RESEND_FROM`: (a) webhook stub resolves **404** → zero calls to `https://api.resend.com/emails`, one `alert-undeliverable` line, and two assertions on the captured webhook POST body — it contains `config-resend-from`, and it does **not** contain *"a paid sale may be behind it"* (the only test that reads `alertBody`); (b) no `ALERT_WEBHOOK_URL`, only `ALERT_EMAIL` → zero calls to `api.resend.com`. 6. **A payload carrying both ids resolves through `order_id`.** Issue `ord_1`, then deliver `order.refunded` with `data = {id: "ref_1", order_id: "ord_1", refunded: true}` → `order:live:ord_1` reads `refunded: true` and `order:live:ref_1` was **never written**.
