## Problem

1. **`RESEND_FROM` is presence-checked at the point of use, after everything durable.** `sendViaResend` (`infra/license-issuance-worker/src/worker.ts:748`) only tests `!env.RESEND_FROM`. The shipped `wrangler.toml:22` value is `REPLACE_WITH_VERIFIED_SENDER`, which is *present*, so `issue()` mints the license, writes `LICENSE_KV`, writes the ledger, then gets a Resend 422 and returns a retryable 500 forever — Polar retries into endpoint auto-disable, which the README names as the dominant sale-loss mode. `SUPPORT_EMAIL` already gets the opposite treatment (`:989-999`, in the fetch handler *before* `handleIssuance`), and its own comment states the reason verbatim.
2. **`revoke()` reads the order id from `data.id`** (`:453`), which is wrong for any payload carrying `order_id`. **The consequence is narrower than the issue implies, and I am stating the measured one rather than the dramatic one.** `revoke()` refuses before the id is ever used to write: `:453-455` is `const orderId = typeof data?.id === "string" ? data.id : null; if (!orderId) return "dropped"; if (data?.refunded !== true) return "dropped";`. A genuine Polar **refund object** (order id at `order_id`, `data.id` the refund's own id) carries no `refunded` boolean, so it exits at `:455` as `"dropped"` — **alertable, nothing committed, recoverable by a manual Polar re-send.** That is already the safe arm. The junk-tombstone outcome needs a payload carrying a refund's id layout *and* an order's `refunded: true` — a hybrid shape no observed Polar object has. So the defect is a **latent id assumption**, not a live silent-revocation-miss, and the PR body and issue-close note must say that. The fix is still correct: the assumption is wrong for any `order_id`-bearing payload, and the sandbox fixture that would settle the shape (§8) does not exist yet.
3. **`isAlertable` is `result === "dropped" || stage === "email"`** (`:943-945`). A bad `TANDEM_PRIVATE_KEY` (`stage: "config"`) or a bad `SUPPORT_EMAIL` (`stage: "config-support-email"`) 503s every request with no alert at all, and a 503 is exactly what drives Polar's auto-disable.
4. **`infra/` coverage — the issue's claim is half right and I measured both halves.** biome: `npx biome check infra` → *"Checked 0 files… these paths were provided but ignored: infra"* (`biome.json:19-28` has no `infra` entry) — **confirmed**. eslint: `npx eslint infra` lints all three files, and `--no-inline-config` turns up the 10 `no-explicit-any` warnings the disables are suppressing — so **"linted by nothing" and "`eslint-disable` comments there are inert" are both refuted**; `eslint.config.js` has no `files` restriction and `npm run lint` sweeps the repo. tsc: all three infra files are reached *transitively* by `tests/server/license-issuance-worker.test.ts` and `license-update-worker.test.ts`, so they are typechecked today — but incidentally, and a future infra file no test imports would be checked by nothing.
5. **`wrangler deploy` is unpinned.** No `package.json` in either worker dir; `./crypto.js` resolves to `crypto.ts` only because the bundler rewrites the extension, which is wrangler-version behaviour. Two deploys of identical source can use different wranglers.
6. **Four doc-drift lines**, all re-verified post-rebase: update README `:16` says the Worker "logs only `{ result, ts }`" (it logs `reason` too, `worker.ts:93`); update README `:26-27` attributes `TANDEM_CF_*` to "the webhook side" when `src/server/license/kv-store.ts:6-11` says those are the **out-of-band** writer's (`scripts/sign-license.ts`), not the Worker's; issuance README `:87-88` omits `--remote` on `wrangler kv key get`, which `docs/licensing-operations.md` §9 says is not optional (a local miss reads as "the refund did not revoke"); the issuance README deploy block never mentions `SUPPORT_EMAIL`, which the Worker 503s without.

## Fix

Its regex `/replace_with|yourdomain/i` already covers `RESEND_FROM`'s two plausible leftovers: the shipped `REPLACE_WITH_VERIFIED_SENDER` and the `noreply@yourdomain.com` its own comment offers as the example.
- **Add `export function resendFromProblem(raw)`**, returning `Exclude<SupportEmailProblem, "too-long"> | null`, implemented as `supportEmailProblem(raw)` with `"too-long"` mapped to `null`. Doc-comment the divergence: the 70-character cap exists because `SUPPORT_EMAIL` is *printed in the email body* next to the base64 key (`MAX_SUPPORT_EMAIL_LEN`, `:720`), and `RESEND_FROM` is a header — applying the cap would 503 a perfectly good `Long Display Name <noreply@…>` sender. - **Add `"config-resend-from"` to `FailStage`** (`:121-128`) and guard in the fetch handler, immediately after the `SUPPORT_EMAIL` block (`:989-999`), with the same shape: `log({result:"error", ts, stage:"config-resend-from"}); return jsonResponse(503);`. **A separate stage, not `config`** — the existing comment there says the stage is the only thing telling an operator which line to fix. **This also makes an *unset* `RESEND_FROM` fail before the mint instead of after it. That widening is deliberate, and it is the half an implementer will accidentally drop** — see the `:1264` test split below, which is what pins it.
  `sendViaResend`'s own `!env.RESEND_FROM` guard stays as belt-and-braces.
- **`orderIdOf(data)`** — one module-private helper, `typeof data?.order_id === "string" ? data.order_id : typeof data?.id === "string" ? data.id : null` — used by both `issue()` (`:325`) and `revoke()` (`:453`). Correct under both payload shapes: an *order* object carries no `order_id`, so the fallback is what fires today; a *refund* object carries both, and `order_id` is the only field that can mean the order. **Comment the exposure honestly**: the preference is a shape guess until the `docs/licensing-operations.md` §8 sandbox fixture lands, and it is deliberately shared with `issue()` so the two cannot drift — `issue()` and `revoke()` therefore agree on the ledger key **by construction**, so a wrong guess cannot desynchronise dedup. - **`isAlertable` (`:943-945`) gains the three config stages, enumerated, not prefix-matched.** `entry.result === "dropped" || entry.stage === "email" || entry.stage === "config" || entry.stage === "config-support-email" || entry.stage === "config-resend-from"`. A `startsWith("config")` test silently adopts every future stage; `result === "error"` would sweep in `ledger`/`unexpected`/`blob-size` and storm. State that in the comment, **and state the amplification property with it**: these three stages are the first alertable class reachable **before** `verifyStandardWebhook` (the key import and both config guards run in `default.fetch`, `:963-999`, while the signature gate is at `:546-554`), so their volume is bounded by inbound request volume rather than by Polar's ~10 retries — against a `shouldAlert` throttle that is per-isolate. 1. **`resendFromProblem` unit table.** `undefined` → `"unset"`; `"REPLACE_WITH_VERIFIED_SENDER"` → `"placeholder"`; `"Tandem <noreply@yourdomain.com>"` → `"placeholder"` (the README's own example); `"noreply"` → `"malformed"`; and the length-divergence case, **which must assert its own length and both functions** — the round-1 draft named a 38-character literal as the ">70-character" case, which returns `null` under the copy-paste mutant too:
   ```ts
   const long = `Tandem Support (include your order id) <${"a".repeat(20)}@tandem.ink>`;
   expect(long.length).toBeGreaterThan(MAX_SUPPORT_EMAIL_LEN); // 70
   expect(supportEmailProblem(long)).toBe("too-long");
   expect(resendFromProblem(long)).toBeNull();
   ```
   The paired `supportEmailProblem` assertion is what proves the two genuinely diverge, regardless of anyone's character arithmetic. (`MAX_SUPPORT_EMAIL_LEN` is module-private; either export it for the test or hardcode `70` with the constant named in a comment. This mirrors `:1250`'s existing length positive control.)
2. **Placeholder `RESEND_FROM` → 503 with nothing written.** `LEDGER_KV.map.size === 0`, `LICENSE_KV.map.size === 0`, `fetch` never called. Kills today's order: the current code mints, entitles, ledgers and *then* calls Resend.
   **2b. Unset `RESEND_FROM` → the same three assertions.** This is the case that kills the `if (env.RESEND_FROM && …)` repair described in § Fix, and it is the surviving half of the split at `:1264`.
3. **Stage distinguishability.** Three requests → logged stages exactly `["config-resend-from", "config-support-email", "config"]`. **The collector filters to `result === "error"` first**; without that filter the `alert-undeliverable` line each newly-alertable stage now emits doubles every entry.
4. **`isAlertable` truth table.** True for `{result:"dropped"}`, `stage:"email"`, and each of the three config stages. **False for `{result:"error", stage:"ledger"}`, `{result:"error", stage:"unexpected"}`, `{result:"error", stage:"blob-size"}` and `{result:"issued"}`.** The false rows are the discriminating half — they kill both `result === "error"` and `stage?.startsWith("config")`.
5. **A broken `RESEND_FROM` alerts via the webhook and NOT via Resend — with the webhook channel *exhausted*.** `sendOperatorAlert` returns at `:904` the moment a stubbed webhook answers ok, so the Resend arm is unreachable and any assertion about it is vacuous. Two cases, both with a placeholder `RESEND_FROM` and both `ALERT_WEBHOOK_URL` and `ALERT_EMAIL` set:
   - webhook stub resolves **404** (the retired-Slack case `:899-903` names) → zero calls to `https://api.resend.com/emails`, and one `alert-undeliverable` log line;

   Both must **flush the alert before asserting**: the alert is handed to `ctx.waitUntil` when `ctx` is supplied and is otherwise a floating promise under the two-arg harness, so capture the `waitUntil` argument (pass a third arg `{waitUntil: (p) => pending.push(p)}`) and `await` it. Only then does leaving `resendIsSuspect` at `stage === "email"` go red.
6. **A payload carrying both ids resolves through `order_id`.** Issue `ord_1`, then deliver `order.refunded` with `data = {id: "ref_1", order_id: "ord_1", refunded: true}`: `LICENSE_KV` no longer holds that licenseId, `order:live:ord_1` reads `refunded: true`, and **`order:live:ref_1` was never written**. Kills `data.id`-only. **Name the case for what it pins** — this fixture is a constructed hybrid, not an observed Polar object (§ Problem item 2).
   **6b. The shape that actually occurs.** `data = {id: "ref_1", order_id: "ord_1"}` with **no `refunded` field** → result `"dropped"`, `LEDGER_KV` unchanged, and the `evt:` done-marker absent. This pins the safe arm § Problem item 2 corrects to, so a future "simplification" of the `refunded !== true` gate cannot quietly turn a real refund object into a write.
7. **Order-object payload still revokes.** `data = {id: "ord_2", refunded: true}` (no `order_id`) after issuing `ord_2` → same three assertions as 6. Kills a fix that switches to `order_id` only. Cases 6 and 7 together are what pin the *preference*, not either alone.
8. **`order.paid` resolves through the same helper, and the two agree.** Two cases: `order.paid` carrying only `id` (today's behaviour, no change expected); and **`order.paid` carrying both `id: "ord_x"` and a different `order_id: "ord_y"` → the ledger key is `order:live:ord_y`, and a subsequent `order.refunded` on the same pair revokes it.** The second is what makes "deliberately shared with `issue()` so the two cannot drift" a pin rather than a comment — today's fixtures (`:148-160`) emit `data.id` only, so nothing covers it.
