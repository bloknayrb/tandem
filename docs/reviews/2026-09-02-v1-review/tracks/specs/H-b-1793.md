## Problem

1. **`RESEND_FROM` is presence-checked at the point of use, after everything durable.** `sendViaResend` (`infra/license-issuance-worker/src/worker.ts:752`) only tests `!env.RESEND_FROM`. The shipped `wrangler.toml:22` value is `REPLACE_WITH_VERIFIED_SENDER`, which is *present*, so `issue()` mints the license, writes `LICENSE_KV`, writes the ledger, then gets a Resend 422 and returns a retryable 500 forever — Polar retries into endpoint auto-disable, which the README names as the dominant sale-loss mode. `SUPPORT_EMAIL` already gets the opposite treatment (`:989-1000`, in the fetch handler *before* `handleIssuance`), and its own comment states the reason verbatim.
2. **`revoke()` reads the order id from `data.id`** (`:453`). If Polar's `order.refunded` `data` is a *refund* object (order id at `data.order_id`, `data.id` being the refund's own id), the ledger lookup misses, a tombstone is written under the refund id, `"revoked"` is returned and the event is marked done — the real entitlement survives the refund and no retry ever comes. The same function routes the `refunded`-field uncertainty to `"dropped"` (alertable, uncommitted); the id assumption gets no such treatment.
3. **`isAlertable` is `result === "dropped" || stage === "email"`** (`:944`). A bad `TANDEM_PRIVATE_KEY` (`stage: "config"`) or a bad `SUPPORT_EMAIL` (`stage: "config-support-email"`) 503s every request with no alert at all, and a 503 is exactly what drives Polar's auto-disable.
4. **`infra/` coverage — the issue's claim is half right and I measured both halves.** biome: `npx biome check infra` → *"Checked 0 files… these paths were provided but ignored: infra"* (`biome.json:19-28` has no `infra` entry) — **confirmed**. eslint: `npx eslint infra` lints all three files, and `--no-inline-config` turns up the 10 `no-explicit-any` warnings the disables are suppressing — so **"linted by nothing" and "`eslint-disable` comments there are inert" are both refuted**; `eslint.config.js` has no `files` restriction and `npm run lint` sweeps the repo. tsc: all three infra files are reached *transitively* by `tests/server/license-issuance-worker.test.ts` and `license-update-worker.test.ts`, so they are typechecked today — but incidentally, and a future infra file no test imports would be checked by nothing.
5. **`wrangler deploy` is unpinned.** No `package.json` in either worker dir; `./crypto.js` resolves to `crypto.ts` only because the bundler rewrites the extension, which is wrangler-version behaviour. Two deploys of identical source can use different wranglers.
6. **Four doc-drift lines**, all re-verified on this branch: update README `:16` says the Worker "logs only `{ result, ts }`" (it logs `reason` too, `worker.ts:93`); update README `:26-27` attributes `TANDEM_CF_*` to "the webhook side" when `src/server/license/kv-store.ts:6-11` says those are the **out-of-band** writer's (`scripts/sign-license.ts`), not the Worker's; issuance README `:87-88` omits `--remote` on `wrangler kv key get`, which `docs/licensing-operations.md:409` says is not optional (a local miss reads as "the refund did not revoke"); the issuance README deploy block never mentions `SUPPORT_EMAIL`, which the Worker 503s without.

## Fix

All in `infra/license-issuance-worker/src/worker.ts` unless named otherwise. **The model for every guard here is `supportEmailProblem` + its fetch-handler call site — copy its placement and its reasoning, not a new shape.**

- **Rename the module-private `SUPPORT_EMAIL_PLACEHOLDER` (`:710`) to `CONFIG_PLACEHOLDER`.** It is not exported, so the rename is contained. Its regex `/replace_with|yourdomain/i` already covers `RESEND_FROM`'s two plausible leftovers: the shipped `REPLACE_WITH_VERIFIED_SENDER` and the `noreply@yourdomain.com` its own comment offers as the example.
- **Add `export function resendFromProblem(raw)`**, returning `Exclude<SupportEmailProblem, "too-long"> | null`, implemented as `supportEmailProblem(raw)` with `"too-long"` mapped to `null`. Doc-comment the divergence: the 70-character cap exists because `SUPPORT_EMAIL` is *printed in the email body* next to the base64 key (`MAX_SUPPORT_EMAIL_LEN`, `:720`), and `RESEND_FROM` is a header — applying the cap would 503 a perfectly good `Long Display Name <noreply@…>` sender. Do not inline a second regex.
- **Add `"config-resend-from"` to `FailStage`** (`:121-128`) and guard in the fetch handler, immediately after the `SUPPORT_EMAIL` block (`:989-1000`), with the same shape: `log({result:"error", ts, stage:"config-resend-from"}); return jsonResponse(503);`. **A separate stage, not `config`** — the existing comment there says the stage is the only thing telling an operator which line to fix. This also makes an *unset* `RESEND_FROM` fail before the mint instead of after it; that is a deliberate widening and strictly safer (nothing durable is written, Polar's re-delivery fulfils the event once the var is fixed). `sendViaResend`'s own `!env.RESEND_FROM` guard stays as belt-and-braces.
- **`orderIdOf(data)`** — one module-private helper, `typeof data?.order_id === "string" ? data.order_id : typeof data?.id === "string" ? data.id : null` — used by both `issue()` (`:325`) and `revoke()` (`:453`). Correct under both payload shapes: an *order* object carries no `order_id`, so the fallback is what fires today; a *refund* object carries both, and `order_id` is the only field that can mean the order. Comment that the preference is a shape guess until the §8 sandbox fixture lands, and that it is deliberately shared with `issue()` so the two cannot drift.
- **`isAlertable` (`:943-945`) gains the three config stages, enumerated, not prefix-matched.** `entry.result === "dropped" || entry.stage === "email" || entry.stage === "config" || entry.stage === "config-support-email" || entry.stage === "config-resend-from"`. A `startsWith("config")` test silently adopts every future stage; `result === "error"` would sweep in `ledger`/`unexpected`/`blob-size` and storm. State that in the comment.
- **`alertBody` (`:868-885`) gains a third arm** and its "a third arm here would be dead code" comment goes: config stages get *"The Worker is refusing every webhook (misconfiguration) — no sale can complete"*, naming `stage` so the operator knows which of the three to fix.
- **`sendOperatorAlert`'s `resendIsSuspect` (`:891`) must become `entry.stage === "email" || entry.stage === "config-resend-from"`.** This is the load-bearing half: the ALERT_EMAIL fallback sends `from: env.RESEND_FROM` (`:919`), so reporting a broken `RESEND_FROM` through Resend uses the very address that is broken. `config` and `config-support-email` leave Resend usable (`SUPPORT_EMAIL` is only `reply_to`/body and the alert mail uses neither).
- **`revoke()`'s second `readOrder` (`:466-467`) — correct the comment, keep the read.** #1825 calls it "two adjacent KV reads (narrows nothing)". Measured against the code: the two reads *are* adjacent, but the tombstone write follows the second, so the exposure window is the second read's snapshot-to-write rather than the first's — it narrows by one KV round trip, not by "the whole request" as `issue()`'s does (that one spans the async Ed25519 sign). Rewrite the comment to say exactly that. Deleting the read would remove a real, small narrowing to fix a comment.
- **`biome.json`** — add `"infra/**/*.{ts,json}"` to `files.includes`. Then run `npx biome format --write infra`: measured churn is 5 lines total (update worker 3, issuance worker 2, `crypto.ts` 0). **`npx biome check .` already runs in the required `check` job** (`ci.yml:350`), so no wiring test is needed — the guarantee is inside `check` by construction.
- **`tsconfig.tests.node.json`** — add `"infra/**/*.ts"` to `include`, making the typecheck direct rather than a side effect of two test imports. It ends `/**/*.ts`, so `tests/scripts/typecheck-tests-wiring.test.ts`'s suffix-glob rule (`:331`) accepts it, and that file's orphan sweep only walks `tests/`, so nothing else moves. `npm run typecheck:tests` runs in `check` (`ci.yml:372`).
- **Pin the deploy.** Both READMEs' deploy blocks and `docs/licensing-operations.md` §3/§3.5b/§9 change `npx wrangler` → `npx wrangler@4.130.0` (measured `npm view wrangler version`, 2026-09-10), with one sentence saying why: the `./crypto.js` → `crypto.ts` resolution and the bundle shape are wrangler's, so a floating `npx wrangler` can differ between two deploys of identical source. **Do not touch `compatibility_date`** — changing it changes deployed runtime semantics, and Ed25519-on-real-Cloudflare at that date is an open §8 gate item that only Bryan can settle.
- **Doc drift, four edits:** update README `:16` → `{ result, reason, ts }`; update README `:26-27` → attribute `TANDEM_CF_ACCOUNT_ID` / `TANDEM_CF_KV_NAMESPACE_ID` / `TANDEM_CF_KV_API_TOKEN` to the out-of-band writer `scripts/sign-license.ts` (`kv-store.ts:6-11`), not to the Worker; issuance README `:87` → add `--remote`; issuance README deploy block → add `SUPPORT_EMAIL` to the `edit wrangler.toml` line. Also update `wrangler.toml:19-22`'s `RESEND_FROM` comment to mirror `SUPPORT_EMAIL`'s at `:27-30` (the Worker now 503s on unset/placeholder rather than emailing), and `docs/licensing-operations.md` §5c + §8: config-stage failures are now alertable, and `RESEND_FROM` is enforced the way `SUPPORT_EMAIL` is.

## Tests

All in `tests/server/license-issuance-worker.test.ts`, in the `default fetch wiring (env → deps)` suite beside the `SUPPORT_EMAIL` block (`:1136-1240`) whose shape they copy. That suite already resets the alert throttle in `beforeEach` — keep using it, or every "does not alert" assertion passes vacuously.

1. **`resendFromProblem` unit table.** `undefined` → `"unset"`; `"REPLACE_WITH_VERIFIED_SENDER"` → `"placeholder"`; `"Tandem <noreply@yourdomain.com>"` → `"placeholder"` (the README's own example); `"noreply"` → `"malformed"`; **a >70-character `Long Display Name <noreply@tandem.ink>` → `null`**. The last case kills a copy-paste of `supportEmailProblem` that keeps the length cap and 503s a valid sender.
2. **Placeholder `RESEND_FROM` → 503 with nothing written.** `LEDGER_KV.map.size === 0`, `LICENSE_KV.map.size === 0`, `fetch` never called. Kills today's order: the current code mints, entitles, ledgers and *then* calls Resend.
3. **Stage distinguishability.** Three requests → logged stages exactly `["config-resend-from", "config-support-email", "config"]`. Kills a fix that folds the new failure into `config`.
4. **`isAlertable` truth table.** True for `{result:"dropped"}`, `stage:"email"`, and each of the three config stages. **False for `{result:"error", stage:"ledger"}`, `{result:"error", stage:"unexpected"}`, `{result:"error", stage:"blob-size"}` and `{result:"issued"}`.** The false rows are the discriminating half — they kill both `result === "error"` and `stage?.startsWith("config")`.
5. **A broken `RESEND_FROM` alerts via the webhook and NOT via Resend.** Env with a placeholder `RESEND_FROM` plus both `ALERT_WEBHOOK_URL` and `ALERT_EMAIL`; assert exactly one `fetch` to the webhook URL and **zero** to `api.resend.com`. Kills leaving `resendIsSuspect` at `stage === "email"`, which would try to send the alert *from* the broken address.
6. **Refund-object payload revokes the real order.** Issue `ord_1`, then deliver `order.refunded` with `data = {id: "ref_1", order_id: "ord_1", refunded: true}`: `LICENSE_KV` no longer holds that licenseId, `order:live:ord_1` reads `refunded: true`, and **`order:live:ref_1` was never written**. Kills `data.id`-only — today this writes a junk tombstone and returns `"revoked"`.
7. **Order-object payload still revokes.** `data = {id: "ord_2", refunded: true}` (no `order_id`) after issuing `ord_2` → same three assertions. Kills a fix that switches to `order_id` only. Cases 6 and 7 together are what pin the *preference*, not either alone.
8. **`order.paid` is unaffected** — the existing happy-path suite (`:329`) already mints under `data.id`; assert it still resolves through `orderIdOf` by adding one case where `order.paid` carries only `id`. No behaviour change expected.
