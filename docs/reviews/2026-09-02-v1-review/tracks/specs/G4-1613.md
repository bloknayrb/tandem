# G4 — #1613 `tests/tauri-driver` has a tsconfig nothing invokes, and a real error sitting in it

Branch `fix/typecheck-tests-three-configs-and-a-mock-idiom-that-check-nothing-1613`. Closes #1613.
Non-review issue, scheduled at `docs/plans/2026-09-06-open-issues-sweep.md:110`. Probe:
`npx tsc -p tests/tauri-driver/tsconfig.json --noEmit` **from the main checkout** — a fresh
worktree has no `tests/tauri-driver/node_modules` and reports three TS2688s instead of the real
error, which is itself the issue's point.

## Problem

Every anchor re-measured true on `f6559305`. `tests/tauri-driver/package.json` has exactly one
script, `{"test": "wdio run ./wdio.conf.ts"}` — no `tsc`. No `tsc -p tests/tauri-driver` appears in
`package.json`, `.github/workflows/` or `.husky/`. `tauri-webdriver.yml` is `workflow_dispatch`
only (since #1197) and has had no successful run since 2026-08-08. So
`tests/tauri-driver/tsconfig.json` is invoked by nothing, and running it by hand reports
`wdio.conf.ts(152,3): error TS2353: ... 'host' does not exist in type 'Config'`, exit 2.

**`host` is dead config, and the answer is `hostname`.** The harness pins `webdriverio@9.28.0`;
`@wdio/types` `Connection` (`build/Options.d.ts:36`) declares `hostname?: string` and no `host` at
all — renamed in WebdriverIO v5, and the file has carried the v4 spelling since. Today the session
connects to `DEFAULT_HOSTNAME = "localhost"` rather than the `127.0.0.1` the file says, which is
why nothing has visibly broken: `tauri-driver` binds loopback.

## Fix

1. **`tests/tauri-driver/wdio.conf.ts:152`** — `host: "127.0.0.1"` → `hostname: "127.0.0.1"`.
   Keeps the file's stated intent and pins the literal loopback address rather than inheriting
   `localhost` (which can resolve to `::1` first). `port: 4444` unchanged. **This is the only
   behavioural change in the group and the PR body says so in one line:** the connect target moves
   `localhost` → `127.0.0.1`, expected inert on a loopback-bound driver; #1197's unreproduced
   `DevToolsActivePort` failure is downstream of the connect, not caused by it. Deleting the dead
   key clears the same error with a zero runtime delta but silently concedes the file's intent was
   never in force — rejected for that reason.
2. **`tests/tauri-driver/README.md:158`** — the `extract-zip` advisory's mechanism sentence says the
   harness "sets `host`/`port`". `definesRemoteDriver` (`@wdio/utils/build/index.js:324-328`) reads
   `options.hostname` — never `host` — OR `Boolean(options.port)`, so before item 1 only `port`
   carried the short-circuit. Correct the sentence to name `hostname`/`port` and say `port` alone
   carried it before. That advisory justifies a knowingly-accepted unpatched CVE, so its mechanism
   sentence has to be right; **do not weaken the acceptance itself.**
3. **`CLAUDE.md:215`**, final clause — currently "**`tests/tauri-driver/` is excluded and is
   genuinely typechecked by nothing** — its own tsconfig is never invoked and currently holds an
   unseen TS2353." The first two clauses stay true (see the choice below); the TS2353 clause
   becomes false and nothing turns red — the wiring test's `docs match the wiring` describe asserts
   only `/typecheck:tests/` and `/typecheck-tests-wiring/`, and `grep -rn "genuinely typechecked"
   tests/` returns nothing. Amend that clause only: the config is still invoked by nothing, and it
   is now green rather than holding an unseen error. `CLAUDE.md` is auto-loaded into every session,
   so a stale rule statement there is the worst residue this group can leave.

**The coverage choice, recorded here and in the PR body: deliberately unchecked, no CI wiring.**
The issue offers two defensible ends. The cheap one is taken. Reasons, measured: the workflow is
`workflow_dispatch`-only, so a typecheck step inside it fires on no PR and no push — it would be
the #1529 green-forever shape, a step whose existence a test could pin but whose execution nothing
would; and folding the config into `typecheck:tests` would add a second `npm ci` (this directory
has its own `node_modules`, unpopulated by the root install) to the *required* `check` job for a
harness that runs on manual dispatch alone. The honest state is: green baseline, checked by nothing
automatic, re-checkable by hand with the probe command at the top of this spec. Item 3 is what keeps
the tracked prose saying exactly that.

Rules that bite: do **not** add `tests/tauri-driver` to any `tsconfig.tests.*.json` `include`; the
orphan sweep's `.filter((f) => !f.startsWith("tests/tauri-driver/"))` prefix exclusion stays as is.

## Tests

**Mutation, and it is the whole test.** Copy `wdio.conf.ts` aside, restore `host:`, confirm
`npx tsc -p tests/tauri-driver/tsconfig.json --noEmit` exits 2 with TS2353 naming `host`, restore
`hostname` **from the file copy** (never `git checkout`), confirm exit 0. Record both exit codes in
the PR body. A config that compiles proves nothing on its own; the paired run is what shows the
error was real and is gone.

No new assertion file and no new CI gate. Adding one would pin the existence of a step in a
workflow nothing runs — the thing this issue is about.
