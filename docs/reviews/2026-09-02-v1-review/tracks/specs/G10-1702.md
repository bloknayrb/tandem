# G10 — #1702 the two inbox collectors share three parameters with no shared type, and it has drifted twice

Branch `fix/awareness-hygiene-selection-staleness-and-one-inbox-poll-context-1702`. Closes #1702. Sweep wave 8 group G10; not a v1-review ledger row. Lands before #1624 (same file). Anchors were re-verified against `origin/master` `c1a4df93`: nothing has touched `awareness.ts` since `4f112aa4`.

## Problem

`src/server/mcp/awareness.ts` passes the same three values from one poll, in three positional orders:

- `processInboxAnnotations(allAnnotations, fullText, surfaced, refreshAll, documentId, modeState, wasChannelEmitted)` (`:672`)
- `processUnsurfacedInboxAnnotations(unsurfaced, fullText, surfaced, modeState, wasChannelEmitted, documentId)` (`:731`, private)
- `collectInboxUserReplies(allAnnotations, fullText, loadReplies, replySurfaced, modeState, documentId, wasChannelEmitted)` (`:890`)

`documentId: string` and `modeState: ModeState` (a string union) can be swapped at a call site without a type error. Units 8j-2 and 8j-3 each silently lost one of these values, and both losses were found only by reading the code. ADR-027 and the Solo gate depend on these parameters:

- `modeState` feeds `hideFromAI`.
- `wasChannelEmitted` stamps `alreadyPushed`.
- `documentId` scopes both surfaced ledgers.

No handler-level test pins `alreadyPushed` or the Solo hold on `userReplies`. Every `alreadyPushed` pin calls the collectors directly (`awareness-tools.test.ts`).

## Fix

`src/server/mcp/awareness.ts` plus test call sites. Behaviour-identical.

1. Export, next to `InboxUserAction`:
   ```ts
   export interface InboxPollContext {
     modeState: ModeState;
     documentId: string;
     wasChannelEmitted: (payloadId: string) => boolean;
   }
   ```
   All three fields are required. An optional field would be the 8j-2 default under a new name.
2. All three functions take `ctx: InboxPollContext` as their single trailing parameter, replacing the positional trio:
   - `processInboxAnnotations(allAnnotations, fullText, surfaced, refreshAll, ctx)`
   - `processUnsurfacedInboxAnnotations(unsurfaced, fullText, surfaced, ctx)`, called with the same `ctx` object
   - `collectInboxUserReplies(allAnnotations, fullText, loadReplies, replySurfaced, ctx)`

   Bodies read `ctx.*`; no other body line changes. `surfaced`, `refreshAll` and `loadReplies` stay outside the context because each belongs to one collector, not both.
3. In the handler (`~:457-477`), build the context once and pass the same object to both collectors: `const pollCtx: InboxPollContext = { modeState, documentId: store.documentId, wasChannelEmitted: wasEmittedViaChannel };`. `modeState` stays this poll's single `readModeState()` result.
4. Move the per-parameter JSDoc onto the interface fields. In the "REQUIRED" docblock (`~:646-657`), keep the 8j-2/8j-3 history in one sentence that points at `InboxPollContext`.
5. Convert every positional call under `tests/`, passing the same values so no fixture changes. Known files: `awareness-tools`, `adr027-note-write-guards`, `awareness`, `inbox-ledger-undo`, `read-audience-filter`. A green `npm run typecheck:tests` confirms every call site was converted.

## Tests

1. **Type pin** (`tests/server/awareness-tools.test.ts`, `describe("InboxPollContext (#1702)")`): pin the full parameter tuple of both exported collectors with `expectTypeOf(fn).parameters.toEqualTypeOf<[..., InboxPollContext]>()`. Before writing the tuples, re-read the real parameter types. Comment: "Enforced by `typecheck:tests` (CI `check`). A new per-poll value goes on `InboxPollContext`, never into these tuples."

   This is how the acceptance box ("adding a fourth shared value to one collector and not the other must fail") is met:
   - A value added to the interface reaches both collectors, because the handler passes one object.
   - A positional value added to one collector changes that collector's tuple, so `typecheck:tests` goes red (mutation row 4).
   - A collector that ignores a field is not a type error. For the three existing fields, test 2 and rows 1–3 catch it.
2. **Handler level, both buckets** (same file). Build the in-memory MCP client the way `held-in-solo-stamp.test.ts` does. Each `it` uses a fresh docId, relies on the file's `beforeEach` `resetInbox()`, and includes a positive control.
   - **(a) `alreadyPushed`.** Set `setCtrlMode("tandem")` before any write. Attach an inert `"external"` subscriber, as in `awareness-tools.test.ts`, and unsubscribe it in `finally`. Write a user comment with `writeUserComment` (outbound) and a browser user reply on a comment. Poll once and assert `alreadyPushed === true` on both `userActions[0]` and `userReplies[0]`.
   - **(b) Solo hold.** Set `setCtrlMode("solo")` before any write, using the same record shapes. Poll and assert neither id is present. Then set `setCtrlMode("tandem")`, poll again, and assert both ids are present. The browser reply is not stamped `heldInSolo`, so only `modeState === "solo"` holds it.
