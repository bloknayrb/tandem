# B — #1764 A read path persists a collapsed or unverified re-anchor, and `kind` is invisible

Branch `fix/annotation-anchors-1764`. Closes #1764 (all four numbered items of its body; the client-side split mapping in its "Suggested fix" is explicitly NOT taken — see Not in scope). Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:17-19`. Probe: `experiments/crdt-verify.ts` (the `{4,4}` / `{4,5}` / `{1,1}` section) and `experiments/harness/f-undo.test.ts`, `f2-undo.test.ts`, `f3-undo.test.ts`.

## Problem

`refreshRange` (`src/server/positions.ts`) has three arms that write through the caller's `map` and one blind spot:

1. **Collapse is an `updated`.** When both RelativePositions resolve to the same offset (block split, heading toggle, block join), `newFrom === newTo`, the guard above only rejects `newFrom > newTo`, so the arm at the end returns `{kind: "updated"}` and `map.set`s `{4,4}`. The caller is `listAnnotationsRefreshed` (`src/server/mcp/document-store.ts`), a **read**. That `map.set` destroys the stored flat range — the fallback the watcher's relocation pass needs.
2. **The `repaired` arm re-anchors from the annotation's STORED flat offsets with no `textSnapshot` comparison** and persists the result. If the text moved while the relRange died, it mints a fresh, confident anchor over the wrong span. CLAUDE.md calls this difference unmeasured; the tests below measure it.
3. **The lazy-attach arm (`!ann.relRange`) is the same mint from the same unverified stored offsets.** Fixing only (2) is defeated one call later: a `degraded` result strips the relRange, and the next refresh takes the lazy path and mints the identical wrong anchor.
4. Once a collapse has been persisted, undo resolves the two zero-width anchors to opposite ends, `newFrom > newTo` fires, and the record is `failed` forever. The precondition is the persistence in (1).
5. Every MCP consumer except the `.docx` export discards `kind`, so none of the above has a visible symptom: `tandem_getAnnotations` reports a detached annotation as healthy.

**A collapse has two causes and they need opposite answers.** A block split, heading toggle or join collapses two live anchors onto one offset while the annotated text is still in the document — that is the spurious collapse this issue is about, and persisting `{n,n}` destroys the only fallback. But *deleting the annotated span* produces exactly the same shape (`fromRel` is assoc 0, `toRel` assoc -1, so both resolve to the deletion point) and there `{n,n}` is the correct answer: the text really is gone. A guard keyed on the shape alone cannot tell them apart, and refusing both leaves a deleted annotation pinned to a stale non-empty range that `docx-comment-export.ts` will later write a Word comment over. The discriminator is the stored `textSnapshot`: if the stored range still holds it, the text did not move and the collapse is spurious.

## Fix

Surface `kind` first (it is what makes the rest observable), then stop persisting the two bad outcomes. No new `RefreshResult` kind — `degraded` already means "resolution did not produce a trustworthy range", so the `.docx` export's single `kind === "failed"` guard (`src/server/file-io/docx-comment-export.ts:335` — an `if`, not a switch) is untouched. Note that `assertNeverRefreshResult` (`positions.ts:672`) has **no call site anywhere in `src/` or `tests/`**, so it is not the exhaustiveness net this relies on; the reason no kind is added is that `degraded` already carries the meaning.

- **`src/server/mcp/output-schemas.ts`** — add to `annotationWithRepliesSchema` (only; `annotationBaseShape` is shared with `checkInbox` and must not grow):
  `anchor: z.enum(["degraded", "failed"]).optional().describe(...)`.
  **The emitted set is the two degradation verdicts, not all five kinds.** `updated`, `attached` and `repaired` are ordinary healthy outcomes and are on the wire for nobody: `updated` fires on every annotation past the edit point after any `tandem_edit`, `attached` on the first refresh of any pre-relRange record, and `repaired` on every annotation of a document that just reloaded from disk (`refreshAllRanges` is the watcher's first pass, `src/server/documents/watcher.ts:219`). After this spec's fix `repaired` and `attached` additionally mean *snapshot-verified*, i.e. explicitly healthy. Emitting them would bury the one signal #1764 asks for — "a detached annotation reads as healthy" — under noise that fires on the common path. So: **`anchor` is omitted for `ok`, `updated`, `attached` and `repaired`**, and present only when the anchor is untrustworthy.
- **`src/server/mcp/document-store.ts`** — `listAnnotationsRefreshed()` returns `RefreshResult[]` (drop the trailing `.map((r) => r.annotation)`). No second method and no compat wrapper. Two `src/` call sites (`src/server/mcp/annotations.ts:411`, `:688`) **plus five test call sites that read annotation fields straight off the result and will fail `typecheck:tests`**: `tests/server/rename-document.test.ts:957`, `:959`, `:1031`, `:1034` (`.filter((a) => a.type !== "note")`, `.some((a) => a.id === "note-1")`) and `tests/server/document-store.test.ts:324` (`.find((annn) => annn.id === id)`). Each gains `.map((r) => r.annotation)` at the call site — still no compat wrapper. `tests/server/document-store-surface.test.ts:184` pins the member NAME only and is unaffected. Update the class docblock at the top of the file, the `{@link listAnnotationsRefreshed}` reference on `refreshAnnotations`, and **`exportAnnotationsMarkdown`'s docblock at `:308-313`**, whose "a caller that hands it `listAnnotationsRefreshed()` would strip notes …" sentence describes an `Annotation[]` return that no longer exists (the hazard survives one `.map` later; the sentence must say so).
- **`src/server/mcp/awareness.ts:585-591`** — one line. That docblock argues the two refresh methods are confusable *because they share a return type*; after this change they do not, so the rationale must be restated rather than left describing a shape that no longer exists.
- **`src/server/mcp/annotations.ts`** — `tandem_exportAnnotations` adds `.map((r) => r.annotation)` at its call site (no behaviour change). `tandem_getAnnotations` keeps its filter chain unchanged by building `const kindById = new Map(refreshed.map((r) => [r.annotation.id, r.kind]))` and `let results = refreshed.map((r) => r.annotation)`; the `annotationsWithReplies` assembly spreads `...(kind === "degraded" || kind === "failed" ? { anchor: kind } : {})`.
- **`src/server/positions.ts` `refreshRange`** — one module-private predicate, used at all three guard sites:
  `function storedRangeStillMatches(ann: Annotation, text: string): boolean` — `ann.textSnapshot === undefined || !snapshotContradicts(ann, text.slice(ann.range.from, ann.range.to))`.
  **`text` is a required, already-resolved flat string, not a `Y.Doc` plus an optional hoist.** The predicate must be structurally incapable of walking the document; see the hoist bullet below for why an optional-hoist signature reintroduces the exact per-annotation walk this spec forbids.
  **The only carve-out is `undefined`.** Do not also short-circuit an empty or non-string snapshot: `src/shared/snapshot.ts:158-176` documents why — a stored empty snapshot is a real claim that the range held no text, and a non-string one is evidence the record is corrupt and must fail *toward* contradiction with a warn. `snapshotContradicts` already makes all three distinctions and already handles truncated snapshots by prefix; **do not inline a second copy of that rule**, and do not key the carve-out on `snapshotSearchPrefix`, which collapses all three to `""`. An out-of-bounds stored range slices to `""` and therefore contradicts, which is the clamp #1765's body asks for — no separate length clamp.
  - **Resolve the text at most once per `refreshAllRanges` invocation — a "hoist" that goes through `resolveDocText` per annotation is still N full-document walks.** `storedRangeStillMatches` runs on the lazy-attach, dead-relRange and collapse arms — exactly the arms that fire for *every* annotation at once, on the two paths #1764 targets: a watcher reload (`refreshAllRanges` over the whole collection) and the #1800 clone restore, where `src/server/documents/annotation-wiring.ts:20-24` records that every restored annotation takes the dead-relRange branch. The trap: `resolveDocText(ydoc, provided, tag)` calls `flatDocLength(ydoc)` on **every** call when `provided` is given (`positions.ts:400-414`), and `flatDocLength` (`mcp/document-model.ts:358-370`) walks every top-level element calling `getElementTextLength` on each. `resolveDocText`'s own docblock measures the guarded call at 5.49 ms against the unguarded 5.66 ms on a 1500-block / 125 KB document and says so outright — "what the guard removes is the 125 KB allocation per iteration, **not the walk**". So threading `{text, textTag}` into the predicate per annotation costs N tree walks, and a test that spies only on `extractText` counts 1 and passes. The shape that actually meets the Done-when:
    - a module-private `refreshOne(ann, ydoc, map, getText: () => string): RefreshResult` holds today's whole body and calls `storedRangeStillMatches(ann, getText())` **only** on the three guard arms;
    - `refreshRange(ann, ydoc, map?, opts?: { text?: string; textTag?: HoistTag })` builds a memoized `getText` (`let cached: string | undefined; () => (cached ??= resolveDocText(ydoc, opts?.text, opts?.textTag))`) and calls `refreshOne` — at most one resolution per call, and none at all when no guard arm fires;
    - `refreshAllRanges(annotations, ydoc, map?, opts?)` builds **one** memoized `getText` for the whole invocation and passes it to `refreshOne` per annotation, so `resolveDocText` — and therefore both `flatDocLength` and `extractText` — runs at most **once per `refreshAllRanges` call**, never once per annotation, whatever N is;
    - add one `HoistTag` arm `"positions/refresh-range"` for the callers that hand in a hoisted string, and widen `refreshAllRanges`' options from today's `{ skipTransact?: boolean }` to `{ skipTransact?: boolean; text?: string; textTag?: HoistTag }` — **that signature change is part of this spec, not an implementation detail**.
    - Callers: `src/server/file-io/docx-comment-export.ts:327` already has `const fullText = extractText(doc)` hoisted above its per-annotation `refreshRange` loop and passes it. `src/server/documents/watcher.ts` today computes `const text = extractText(doc)` at `:224`, **after** the `refreshAllRanges(...)` call at `:219-221`; move that declaration above the call (safe — the pass writes only annotation records, so the flat text is identical on both sides) and pass `{ skipTransact: true, text, textTag: "positions/refresh-range" }`. Omitting the option keeps today's behaviour for the read-only single-annotation callers.
  - **Docblock counts that go stale with the sixth arm** — `src/server/positions.ts:122-138` ("The five call sites that hoist an `extractText` across a loop", "a claim about what these five callers write") and the comment at `tests/server/positions.test.ts:385` ("The tag must be one of the five `HoistTag` literals"). Both say **six** after this change.
  - Lazy-attach arm: when the predicate is false, return `{kind: "degraded", annotation: ann}` and **do not write**.
  - Dead-relRange arm: when the predicate is false, take the existing strip path (`delete stripped.relRange`, `map.set`, `degraded`) instead of minting. Stripping is required by the "strip dead RelativePositions, never preserve them" gotcha — it removes a field that resolves to null, it does not mint an anchor.
  - Collapse guard, immediately after the existing `newFrom > newTo` arm so the two "the CRDT no longer describes this annotation" verdicts sit together, and before the unchanged-offsets `ok` arm:
    `if (newFrom === newTo && ann.range.from !== ann.range.to && storedRangeStillMatches(ann, getText())) return {kind: "degraded", annotation: ann}` — no write, so the stored flat range and the relRange both survive for the watcher's snapshot relocation and for undo.
    **The predicate is what separates the two causes of a collapse.** A spurious collapse (split, heading toggle, join) leaves the annotated text at its stored offsets, the predicate is `true`, and the range is preserved. A genuine deletion of the annotated span makes the stored slice contradict the snapshot, the predicate is `false`, and the record falls through to today's `updated {n,n}` — which is the correct answer there and keeps `docx-comment-export.ts` from writing a Word comment over unrelated text.
  - **Critical Rule 2:** no new transaction. Every `map.set` here is already inside `refreshAllRanges`' `withMcp` (or the watcher's `withReload` via `skipTransact`); this change only removes writes.
  - **Critical Rule 4 is untouched** — `validateRange`'s check order is not on this path.
- **`src/server/documents/watcher.ts`** — comments only, three blocks whose stated premise this change falsifies:
  - `:240-248` and the `else` arm near `:320-330`, both of which justify their behaviour with "`refreshAllRanges` above has already re-anchored a fresh `relRange` from the STALE flat offsets". After this fix that mint happens only when the stored range still holds its snapshot; on a contradicting record the relRange is stripped instead. Restate both.
  - `:299-310`, whose `allowEmpty: true` rationale is "`refreshRange` may resolve a relRange to newFrom === newTo (#1764) … so it passes both guards above and arrives here collapsed". That route survives, but only for the *deletion* cause (a snapshot-contradicting stored range); the spurious-collapse cause no longer reaches here. **`allowEmpty` is still required** — the truncated branch's `Math.min(vr.resolvedFrom + span, text.length)` clamp can independently produce a zero span — so the comment must name the clamp as a surviving reason and not read as a claim that only #1764 put it there.
- **`docs/mcp-tools.md`** §`tandem_getAnnotations`: document `anchor`, naming `degraded` as "the anchor no longer describes this text; the range shown is the last one the server trusted", and stating that the field is **absent on every healthy refresh, including `updated`, `attached` and `repaired`**.
- **`docs/architecture.md`** coordinate-systems bullets near `:647-654` (there is no "start or end inside a prefix" sentence in that file to replace — the nearest text is the top-level-heading-prefix bullet at `:654`): add the paragraph-split caveat as a new bullet — a client block split collapses both RelativePositions; the server keeps the flat range and reports `degraded`.
- **`docs/decisions.md`** ADR-032: one sentence — `tandem_getAnnotations` now carries the degradation half of `kind` as `anchor`, so "MCP errors switch on kind" is no longer true of the `.docx` export alone.
- **`docs/reviews/2026-09-02-v1-review/experiments/README.md`** — the `crdt-verify.ts` row currently sets the still-broken criterion as "prints `{4,4}`, `{4,5}`, `{1,1}`". Only `{4,4}` is this issue's; amend the row so `{4,5}` (the split-inside shrink, #1774/#1776) and `{1,1}` (the zero-length range, preserved deliberately) are named as out of scope rather than left as a criterion this PR can never meet. **B-1766 amends the same row** (its `validateRange(4,9)` clause), so the two edits land in one pass over that row rather than as competing rewrites — see B-1766's change list.

## Assumptions

- **An annotation with no `textSnapshot` keeps today's unverified re-anchor on the two mint arms.** There is nothing to verify against and refusing would strand every pre-snapshot record permanently.
- **On the collapse arm the same record is preserved, not collapsed.** `storedRangeStillMatches` reads "nothing to verify" as `true`, so an unverifiable collapse is treated as spurious. That is the deliberate opposite of the mint arms and is the safer default for #1764's headline (a split must not destroy the fallback), but it has a cost: a snapshot-less annotation whose text was genuinely deleted keeps a stale non-empty range, and `docx-comment-export.ts` (which skips only `kind === "failed"`) will export a Word comment at those coordinates. Every record `captureSnapshot` has written since #1486 carries a snapshot, so this is the legacy tail, not the common case.
- **The `.docx` export's written bytes change for a collapsed annotation, by design.** Today a spurious collapse exports as a point comment at the collapsed offset; after this fix it exports at the stored span, which is where the text still is. The export source is untouched; the coordinates it writes are not.
- **A contradicting re-anchor answers `degraded`, not `failed`** (the issue and the track both float `failed`). `failed` is the `.docx` export's skip signal, so promoting a recoverable stale anchor to `failed` would drop a real comment from an export; `degraded` leaves the stored flat range usable.
- **`refreshRange` keeps its `map` parameter and `listAnnotationsRefreshed` keeps passing it.** Removing the write wholesale would stop the relRange re-attachment reaching the durable envelope; the narrow fix is to stop persisting the two untrustworthy outcomes.
- **`failed` stays non-recoverable and unwritten.** Stripping an inverted relRange would hand the record straight to the lazy-attach mint this spec is restricting.
