# W13g — #1974 perf gate: `annotation-accept` cites closed-and-refuted #1288 present-tense, and Run 3 records no click/settle split

Branch `fix/docs-and-test-tooling-drift-2005`. Closes #1974. No track file (non-review issue). No
MCP probe: this is a test-comment and docs correction with no runtime surface, mirroring PR
#1973's own #1584 fix ("a docs/test-comment fix, no `src/` behavior change").

## Problem

Two staleness issues, both surfaced while shipping PR #1973 (which implemented #1734 / #1334's
perf-gate decision) but left unfixed there and carved out into this issue:

**1. `tests/perf/performance.spec.ts:446-450` cites #1288 in the present tense.** The comment
reads "`#1288` is that wait" — naming #1288 as the live explanation for Playwright's click-stability
wait. #1288 is CLOSED (as completed), and `docs/perf-gate-results.md:215`'s own section heading
says "`#1288` does not reproduce, and its proposed mechanism is refuted": Run 1's 7851ms
click-dispatch reading was an artifact of a superseded harness (the margin pipeline never mounted,
and the app-data wipe landed under an already-restored server), not a regression that has since
been fixed. So the comment sends the next reader to a closed issue for an explanation the project
has already withdrawn.

**2. `docs/perf-gate-results.md`'s Run 3 section (`:376-410`) records only the 311ms total for
`annotation-accept`, no click/settle split.** Runs 1-2 are analysed almost entirely in terms of
that split (`:206-207`'s table; the whole "`#1288` does not reproduce" and "What the accept
measurement actually spends" sections), and the harness prints it on every run
(`performance.spec.ts:477-479`: `` `  accept breakdown: click-dispatch ${clickMs}ms, post-click
settle ${acceptMs - clickMs}ms` ``). Run 3's closing paragraph (`:405-409`) nonetheless asserts "No
residual over-budget number and no residual click-dispatch motion coupling to file a follow-up
issue for" — the second clause is not something Run 3's own table can support, because it never
recorded the split.

A real split *does* exist, just not attached to Run 3's row. PR #1973's own body (its
"Verification" block, machine-run output from the same PR that implemented #1734) records a
*different* sample: `annotation-accept: 340.0ms (threshold 500ms); breakdown "click-dispatch
335ms, post-click settle 5ms"`, and the PR body draws the conclusion itself: "335 of the 340ms is
Playwright's pre-click stability wait." That is ≈98.5% click-dispatch — corroborating the "click
half dominates" branch of the issue's own `Done when` item 3. But it is a *different* run (340ms
total) from the one Run 3's table commits (311ms total, no split recorded); splicing "335ms/5ms"
onto Run 3's 311ms row would misattribute one sample's breakdown to another's total — exactly the
invented pairing the sweep notes for this group warn against ("do NOT invent measurements").

## Fix

1. **`tests/perf/performance.spec.ts:446-450`** — rewrite the comment so `#1288` reads as a
   closed, historical citation, not a live pointer. Content requirement: name `#1288` as closed and
   refuted, cross-reference `docs/perf-gate-results.md`'s "`#1288` does not reproduce" section by
   name (matching this file's existing citation style — see the neighbouring cross-reference at
   `:454-459` to the same doc's Run 3), and keep the substantive point the comment makes:
   Playwright's click-stability wait is a real, distinct-from-accept-latency cost, which is *why*
   the split is worth isolating — that reasoning is not stale, only the tense and the destination
   of the pointer are.

2. **`docs/perf-gate-results.md`'s Run 3 closing paragraph (`:405-409`)** — narrow the claim to
   what the table actually supports. State plainly that Run 3 recorded only the total, not the
   click/settle split, so "no residual click-dispatch motion coupling" is not something this run's
   own data can assert. Cite the real split that does exist, from the *different* PR #1973 sample,
   clearly labeled as a separate run and not folded into the Run 3 table: `click-dispatch 335ms,
   post-click settle 5ms` on a 340ms total (≈98.5% click-dispatch) — noted as corroborating
   evidence that the click half likely dominates, not as Run 3's own measurement. **Do not add a
   row to Run 3's table** — that would misattribute one sample's breakdown to another sample's
   total.

3. **Leave the Run 1 / Run 2 `#1288` citations untouched** (`docs/perf-gate-results.md:76`, `:147`).
   Re-verified: both sit inside sections explicitly marked SUPERSEDED / historical, and both are
   already past-tense and scoped to what Run 1 observed at the time ("`#1288` is real, and it
   happened under conditions worth knowing" — describing Run 1's now-invalidated numbers, not
   asserting `#1288` is currently live). This fix touches only what's actually stale.

4. **Leave the successor decision undecided.** Item 3 of the issue's `Done when` — whether
   `annotation-accept` should measure from the click's completion rather than `acceptStart` — is
   explicitly a judgement call for Bryan; PR #1973's own body says so in the same words ("a
   judgement about what the 500ms budget is meant to promise, not something a measurement
   settles"). Not decided or fixed here; listed under `bryan`.

## Tests

No new automated test. This is a comment/docs correctness fix with no `src/` behaviour change. The
issue's own body explains why nothing in the suite can catch this class: `tests/build/
dangling-citations.ts` checks tracked *plan documents* for dangling references, not issue
liveness, and building an issue-liveness scanner is a new mechanism the MINIMALITY RULE forbids
absent the issue asking for one — it does not. Manual verification: `grep -n "#1288"
tests/perf/performance.spec.ts` shows the corrected, historical-tense wording; `grep -n "no
residual" docs/perf-gate-results.md` shows the narrowed Run 3 claim.
