# W13r — #1959 a successful post-boot sidecar crash-restart is silent

Branch `fix/sidecar-restart-toast-and-rust-test-harness-residue-1970`. Closes #1959 (the client half of #1809). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md`, Wave 13 (2026-09-20); non-review issue, so no `areas/*.md` row and no experiment. Probe: none available — no browser E2E can drive a Tauri event, so the probe is the vitest spec below plus Bryan's hardware smoke.

## Problem

Since #1809 a post-boot sidecar crash is respawned. The **breaker trip** surfaces (`sidecar.rs:2139` emits `sidecar-restart-failed`, `App.svelte:301` toasts it), but a **successful** crash-restart emits nothing. The user's tabs go Disconnected and silently reconnect through the Hocuspocus generation gate — correct recovery, read by a human as a glitch.

## Fix

Two halves, modelled line-for-line on the `BreakerTripped` emit (`sidecar.rs:2136-2144`) and on `utils/startup-rejection.ts` + its `App.svelte:370` call site.

**Rust — `src-tauri/src/sidecar.rs`.**

- Add `pub(crate) const EVENT_SIDECAR_RESTARTED: &str = "sidecar-restarted";` beside `RestartCause` (`:490`).
- Emit it from `restart_sidecar_for`'s success arm, `Ok(SpawnOutcome::Started) => {}` at `:568`, **gated on `cause == RestartCause::PostBootCrash`** — not from the `CrashRestartDecision::Restart` arm at `:2089` as the issue body proposes. **This is a deliberate divergence and the spec's one design call:** the `Restart` arm is a *decision*, taken before `stop_sidecar_gracefully` and `start_sidecar` have run. Emitting there makes the toast a lie whenever the restart then fails or is declined — and those two arms (`:604`, `:633`) emit `sidecar-restart-failed`, so the user would get "restarted" immediately followed by "failed to restart". `Ok(SpawnOutcome::Started)` is the only point where success is known, it is in the same file, and `RestartCause` is `Copy` so `cause` is already available inside the spawned task (it is read at `:533` before the spawn). `UserInitiated` restarts stay silent because `NetworkSettings.svelte` already gives that click its own feedback.
- Payload-free: `handle.emit(EVENT_SIDECAR_RESTARTED, ())`. The `BreakerTripped` site passes a code string only as a log-side distinction; there is nothing to distinguish here. Follow its error handling exactly — `if let Err(emit_err) = … { log::error!(…) }`, never `unwrap`.
- Do **not** add a `log::warn!` for the success case: `:2090-2093` already warns "crashed after boot — restarting" above the release `LevelFilter::Warn` floor.
- Leave the breaker-trip copy alone. The issue's third bullet asks to "consider" it; considered — "Tandem server failed to restart." is true of a tripped breaker as well as of a failed manual click, and rewording it is a second change in a file this PR is already editing for #1970.

**Client — new `src/client/utils/sidecar-restart-toast.ts` + `src/client/App.svelte`.**

- Export `SIDECAR_RESTARTED_EVENT = "sidecar-restarted"`, `SIDECAR_RESTARTED_MESSAGE = "Tandem server restarted after a crash."` and `wireSidecarRestarted(deps): () => void`, shaped like `wireStartupRejection` (`startup-rejection.ts:106`): `deps.loadEvent: () => Promise<{ listen: … }>`, `deps.push: () => void`, optional `deps.warn`; a `cancelled` latch; `unlisten` released by the returned cleanup; a `.catch` that warns rather than throws. It is deliberately simpler than `wireStartupRejection` — there is no buffer and no drain, because a crash-restart only ever happens while the WebView is alive (the boot-window retry loop is a different path), so the event *is* the carrier here and the Files-gotcha "buffer is the load-bearing half" rule does not apply. Say that in the module docblock so nobody reads it as a missed buffer.
- `App.svelte`, immediately after the existing `sidecar-restart-failed` block (`:296-324`), inside a `if (isTauriRuntime())` guard: call `wireSidecarRestarted({ loadEvent: () => import("@tauri-apps/api/event"), push: () => notifications.push({ id: "sidecar-restarted-" + Date.now(), type: "general-error", severity: "info", message: SIDECAR_RESTARTED_MESSAGE, dedupKey: "sidecar-restarted", timestamp: Date.now() }) })` and pass the returned cleanup to `onDestroy`.
  - `severity: "info"` is the call: only `info` expires (`TandemNotification` docblock, `src/shared/types.ts:701-710`), and a recovery notice that persists in the activity tray as a warning outlives what it describes. `type: "general-error"` because the union has no success member and the sibling listener already uses it; no `errorCode`, because this is not an error.
  - `dedupKey: "sidecar-restarted"` so three crashes inside the breaker budget collapse into one toast with a count, matching `tests/client/notification-dedup.test.ts`'s contract.
  - Copy is not given in the issue; see `assumptions` / `bryan`.
- Rules that bite: the `push` closure runs from a Tauri event callback, **not** from a Tiptap handler and not inside a Svelte reaction, so `createCoalescingTick` is not needed — `notifications.push` is the same call the existing listener makes. No `localStorage`. No new colour (the toast reuses existing token-driven styles). **No new `data-testid`**, so `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched. No Y.Doc write, no MCP tool, no `/api` route, so Critical Rules 1, 2 and 9 are not engaged.

## Tests

`tests/client/sidecar-restart-toast.test.ts` (new, `// @vitest-environment happy-dom`, modelled on `tests/client/startup-rejection.test.ts`), driving `wireSidecarRestarted` with a fake `listen`:

1. **A delivered event pushes exactly one notification**, with `severity: "info"`, `dedupKey: "sidecar-restarted"` and the message equal to `SIDECAR_RESTARTED_MESSAGE` (assert the push payload the App call site builds, by exercising the same object shape). Kills a wiring registered for the wrong event name, and copy that drifts from the exported constant.
2. **Two events push twice** — dedup is the toast layer's job, not this module's. Kills a "fire once then unlisten" implementation that would swallow the second crash in a breaker window.
3. **Cleanup unlistens, and an event delivered after cleanup pushes nothing.** Kills the leak the `cancelled` latch exists for, and the "listener resolved after destroy" race `wireStartupRejection` already guards.
4. **A rejecting `loadEvent` warns and does not throw** (inject `warn`). Kills an unguarded `.then` chain that would produce an unhandled rejection in browser mode.

Rust side, in `sidecar.rs`'s existing `crash_restart_tests` module (no new file): one `#[test] fn sidecar_restarted_event_name_is_stable()` asserting `assert_eq!(EVENT_SIDECAR_RESTARTED, "sidecar-restarted")`, with a comment naming `src/client/utils/sidecar-restart-toast.ts`'s `SIDECAR_RESTARTED_EVENT` as the other half. Precedent: `startup_rejection.rs:522 open_failed_code_is_stable`. This is the only affordable pin — the emit itself needs an `AppHandle` and a real spawn, which is exactly the hardware-gated half. Do **not** add a source-scanning guard for the emit; that is the framework the minimality rule forbids.

## Done when

A post-boot crash-restart that succeeds emits `sidecar-restarted`; a failed or declined one still emits only `sidecar-restart-failed`; a user-initiated restart emits neither; the four vitest specs and the name-stability test pass; `npm run typecheck` (including `svelte-check`) and `cargo test` green; `bryan` carries the hardware smoke.
