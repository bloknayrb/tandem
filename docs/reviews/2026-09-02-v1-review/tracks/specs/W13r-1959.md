# W13r — #1959 a successful post-boot sidecar crash-restart is silent

Branch `fix/sidecar-restart-toast-and-rust-test-harness-residue-1970`. Closes #1959 (the client half of #1809). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md`, Wave 13 (2026-09-20); non-review issue, so no `areas/*.md` row and no experiment. Probe: none available — no browser E2E can drive a Tauri event, so the probe is the vitest spec below plus Bryan's hardware smoke.

## Problem

Since #1809 a post-boot sidecar crash is respawned. The **breaker trip** surfaces (`sidecar.rs:2139` emits `sidecar-restart-failed`, `App.svelte:301` toasts it), but a **successful** crash-restart emits nothing. The user's tabs go Disconnected and silently reconnect through the Hocuspocus generation gate — correct recovery, read by a human as a glitch.

## Fix

Two halves, modelled on the `BreakerTripped` emit (`sidecar.rs:2136-2144`) and on `utils/startup-rejection.ts` + its `App.svelte:370` call site.

**Rust — `src-tauri/src/sidecar.rs`.**

- Add `pub(crate) const EVENT_SIDECAR_RESTARTED: &str = "sidecar-restarted";` beside `RestartCause` (`:490`), plus a pure discriminant so the gate is testable without an `AppHandle`:

  ```rust
  pub(crate) fn announces_successful_restart(cause: RestartCause) -> bool {
      matches!(cause, RestartCause::PostBootCrash)
  }
  ```

- Emit from `restart_sidecar_for`'s success arm, `Ok(SpawnOutcome::Started) => {}` at `:568`, gated on `announces_successful_restart(cause)` — **not** from the `CrashRestartDecision::Restart` arm at `:2094` as the issue body proposes. That arm is a *decision*, taken before `stop_sidecar_gracefully` and `start_sidecar` run; emitting there makes the toast a lie whenever the restart then fails or is declined, and those arms (`:604`, `:633`) emit `sidecar-restart-failed`, so the user would get "restarted" followed by "failed to restart". `RestartCause` is `Copy` and `cause` is already read at `:533`, so it is available inside the spawned task. `UserInitiated` stays silent because `NetworkSettings.svelte` already gives that click its own feedback.
- **Both `PostBootCrash` callers are in scope and the copy is true of both**: the `Restart` arm (`:2094`) and `recover_deferred_crash` (`:310`), which pays the debt latched while spawns were suppressed — a genuine post-boot crash whose restart was merely deferred. Gating additionally on `DEFERRED_CRASH` is listed under `bryan` with the copy, not decided here.
- **One accepted false positive, debug builds only**: `SpawnOutcome::Started` also covers "(debug builds only) an external `dev:standalone` server was already answering `/health`" (`:1764-1766`). Release builds always spawn, so this cannot reach a user; recorded rather than guarded.
- Payload-free: `handle.emit(EVENT_SIDECAR_RESTARTED, ())`, with the `BreakerTripped` site's error handling exactly — `if let Err(emit_err) = … { log::error!(…) }`, never `unwrap`. No new `log::warn!`: `:2090-2093` already warns above the release `LevelFilter::Warn` floor.
- Leave the breaker-trip copy alone — "Tandem server failed to restart." is true of a tripped breaker as well as a failed manual click, and rewording it is a second change in a file this PR already edits for #1970.

**Client — new `src/client/utils/sidecar-restart-toast.ts` + `src/client/App.svelte`.**

- Export `SIDECAR_RESTARTED_EVENT = "sidecar-restarted"`, `SIDECAR_RESTARTED_MESSAGE = "Tandem server restarted after a crash."`, `buildSidecarRestartedNotification(now: number): TandemNotification` and `wireSidecarRestarted(deps): () => void`.
- **The notification object is built in the module, not at the call site**, so the decisions with consequences are assertable:

  ```ts
  { id: `sidecar-restarted-${now}`, type: "general-error", severity: "info",
    message: SIDECAR_RESTARTED_MESSAGE, dedupKey: "sidecar-restarted", timestamp: now }
  ```

  `severity: "info"` is the call: only `info` expires (`src/shared/types.ts:701-710`), and a recovery notice that persists in the activity tray outlives what it describes. `type: "general-error"` because the union has no success member and the sibling listener already uses it; no `errorCode`. `dedupKey` so three crashes inside the breaker budget collapse into one toast with a count (`tests/client/notification-dedup.test.ts`'s contract). Mirrors `startup-rejection.ts:119`, where the copy likewise lives inside the module.
- `wireSidecarRestarted(deps)` is shaped like `wireStartupRejection` (`startup-rejection.ts:106`): `deps.loadEvent: () => Promise<{ listen: … }>`, `deps.push: (notification: TandemNotification) => void`, optional `deps.warn`; a `cancelled` latch; `unlisten` released by the returned cleanup; a `.catch` that warns rather than throws. On each delivered event it calls `deps.push(buildSidecarRestartedNotification(Date.now()))`. No buffer and no drain — docblock it as *"losing this notice is acceptable — it describes a recovery that has already succeeded"*, **not** as "a crash-restart only ever happens while the WebView is alive" (`recover_deferred_crash` can restart before `App.svelte` mounts).
- `App.svelte`, immediately after the existing `sidecar-restart-failed` block (`:296-324`), inside the `isTauriRuntime()` guard: call `wireSidecarRestarted({ loadEvent: () => import("@tauri-apps/api/event"), push: (n) => notifications.push(n) })` and pass the returned cleanup to `onDestroy`. A one-liner with no design decisions in it. **The call-site wiring stays unpinned** — nothing asserts the cleanup reaches `onDestroy`, same as the sibling at `:319-322`; pinning it would mean mounting `App.svelte`.
- Rules that bite: the `push` closure runs from a Tauri event callback, not a Tiptap handler and not inside a Svelte reaction, so no `createCoalescingTick`. No `localStorage`. No new colour. **No new `data-testid`**, so the testid snapshot is untouched. No Y.Doc write, no MCP tool, no `/api` route.

**Docs.** `docs/architecture.md:857` (launch-sequence item 5) names only the breaker trip as user-visible. Add one clause: a successful post-boot crash-restart now emits the payload-free `sidecar-restarted` event and toasts once. `CHANGELOG.md` is not touched.

File set: `src-tauri/src/sidecar.rs`, `src/client/utils/sidecar-restart-toast.ts` (new), `src/client/App.svelte`, `tests/client/sidecar-restart-toast.test.ts` (new), `tests/docs/startup-open-failure-wiring-claims.test.ts`, `docs/architecture.md`.

## Tests

`tests/client/sidecar-restart-toast.test.ts` (new, `// @vitest-environment happy-dom`, modelled on `tests/client/startup-rejection.test.ts`), driving `wireSidecarRestarted` with a fake `listen`:

1. **A delivered event pushes exactly one notification, and it is the module's own object.** Assert the value handed to the injected `push`: `severity === "info"`, `type === "general-error"`, `dedupKey === "sidecar-restarted"`, `message === SIDECAR_RESTARTED_MESSAGE`, `errorCode === undefined`. Because `buildSidecarRestartedNotification` produces it, this is the real payload, not a shape the test invented.
2. **Two events push twice** — dedup is the toast layer's job. Kills a "fire once then unlisten" implementation.
3. **Cleanup unlistens, and an event delivered after cleanup pushes nothing.**
4. **A rejecting `loadEvent` warns and does not throw** (inject `warn`).

**Rust**, one `#[test]` in `sidecar.rs`'s existing `crash_restart_tests` module: `only_a_crash_restart_announces_itself`, asserting `announces_successful_restart(RestartCause::PostBootCrash)` is `true` and `announces_successful_restart(RestartCause::UserInitiated)` is `false`. No `AppHandle` needed. Without it, an implementation that emits unconditionally from the success arm toasts "Tandem server restarted after a crash." when the user clicks Restart server.

**Cross-language name pin**, added to the EXISTING `tests/docs/startup-open-failure-wiring-claims.test.ts` (no new file), copying its sibling `it("agrees with the client on the nudge event's name")` (`:324-363`) verbatim in shape:

```ts
it("agrees with the client on the sidecar-restarted event's name", () => {
  const rust = rustSourceDefining(/const EVENT_SIDECAR_RESTARTED: &str/, "EVENT_SIDECAR_RESTARTED");
  const declared = rust.code.match(/const EVENT_SIDECAR_RESTARTED: &str = "([a-z-]+)";/);
  expect(declared, "the Rust event constant is not a plain string literal any more").not.toBeNull();

  const client = stripTsComments(
    readFileSync(join(REPO_ROOT, "src", "client", "utils", "sidecar-restart-toast.ts"), "utf8"),
  );
  const listened = client.match(/const SIDECAR_RESTARTED_EVENT = "([a-z-]+)";/);
  expect(listened, "the client's SIDECAR_RESTARTED_EVENT binding is not a plain literal any more").not.toBeNull();

  expect(declared?.[1], "Rust emits one event name and the client listens for another.").toBe(listened?.[1]);
  expect(rust.code, "the emit site must pass EVENT_SIDECAR_RESTARTED, not a second literal").toMatch(
    /\.emit\(EVENT_SIDECAR_RESTARTED/,
  );
});
```

Both halves are load-bearing and the sibling's own comment says why for an identical mechanism: the event is payload-free, so a one-character disagreement is indistinguishable from no restart having happened — every spec above stays green (the four vitest specs drive an injected fake `listen`; `only_a_crash_restart_announces_itself` tests a pure discriminant), the feature is dead, and the issue closes on it. The second assertion exists because pinning the two constants against each other leaves a hardcoded second literal at the emit site green; the sibling's mutant review ran exactly that. `CLIENT_MAP`'s own target, `src/client/utils/startup-rejection.ts`, is a direct sibling of the new module, and cross-language const pinning is already a Critical-Rules-level idiom here (`tests/docs/license-flip-consts.test.ts`).

## Done when
