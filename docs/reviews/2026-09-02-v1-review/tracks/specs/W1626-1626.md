# W1626 — #1626 a reply cannot carry a suggestion, so a refined proposal degrades to prose

Branch `fix/reply-surfaces-1626`. Closes #1626 (part 2; part 1's client half already shipped in #1636/#2021 — see below — and part 1's export/`.docx` half is deliberately Not in scope). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:115` and `:484`. Probe: `tests/e2e/reply-threads.spec.ts` (an MCP-authored reply, accepted from the card).

## Problem

**Part 1 is measured DONE on the surfaces this group owns.** `CommentThread.svelte:60` no longer interpolates `{reply.text}`: it renders `<AnnotationBody text={reply.text} author={reply.author} />`, and `AnnotationBody.svelte` routes Claude-authored text through `renderMarkdown` + `markdown-body.css`. `CommentCard`, `SuggestionCard`'s reason and the annotation bodies do the same. The issue body's anchors are stale. Nothing in part 1 is re-implemented here, and **no second markdown renderer is written** — `chat-markdown.ts`'s `renderMarkdown`/`assembleBlocks` is the only one, and it already carries the two G14 review fixes (CRLF blank lines, whitespace-only lines). `AnnotationCard.svelte`'s `br { display: none }` density rule stays — #1639 acceptance item 3's parenthetical was measured false.

**Part 1's rendering is gated on `author === "claude"`, and that is deliberate, not an oversight.** `AnnotationBody.svelte:46` derives `asMarkdown` from the author because `tandem_editAnnotation` has no author gate: Claude editing a user's comment leaves `author: "user"`, and the honest fix is a separate `editedBy` field rather than rewriting `author`. So a user's own annotation bodies and replies still render literally, by design. A one-line assertion pins both branches (test 9), and the PR body states the user branch is intentional so Bryan can confirm part 1 is discharged as he meant it.

**Part 2 is untouched.** `AnnotationReply` (`src/shared/types.ts:110`) has no `suggestedText`, `AnnotationReplyRecordSchemaV1` (`annotations/schema.ts:157`) has no such field, and `tandem_annotationReply` (`mcp/annotations.ts:992`) takes `{annotationId, text, documentId}`. So Claude can propose a one-click replacement when it *creates* an annotation (`tandem_comment` + `suggestedText` → `SuggestionCard`'s `diffWords` box + Accept) and cannot in the reply thread, which is exactly where a proposal is refined after the user pushes back. The counter-proposal lands as prose with no accept affordance. #1629 (the accept path's missing target verification) is CLOSED, which discharges the only stated reason part 2 was held.

## Fix

A reply's suggestion is a proposal **over the parent's range** — a reply has no range of its own and gains none.

1. **Wire + durable.** `src/shared/types.ts`: `suggestedText?: string` on `AnnotationReply`. `annotations/schema.ts`: the same field on `AnnotationReplyRecordSchemaV1`, `z.string().max(REPLY_TEXT_MAX).optional()` — `.passthrough()` would carry it regardless, and an explicit field is what makes `normalizeReply` (`sync.ts:160`) apply the cap instead of admitting an unbounded string that the *annotation* cap never sees. Test 1 pins the cap in the direction that discriminates: `.passthrough()` alone round-trips the field, so only a LOAD-time drop proves the declaration exists.

2. **Seam — threaded as a required discriminant, not as a bare optional, and not widened to the user path.**

   `AnnotationLifecycle.reply` becomes `reply(annotationId, text, suggestion, onLossy, agentIdentity?)`, where

   ```ts
   export type ReplySuggestion = { kind: "none" } | { kind: "replacement"; suggestedText: string };
   ```

   **`suggestion` is required and positioned BEFORE the optionals, for `anchorRange`'s own reason** (Critical Rule 6: "both creators take the arm as a required discriminant, so a new one cannot default into the wrong half without a compile error"). A bare optional 5th parameter would let the second producer — `local-model/tools.ts:366`'s `reply_to_annotation`, which reaches this seam through the same `AnnotationReplier` interface — acquire the field silently the day someone wires `args.suggested_text` into it. Making it required means both existing callers must be edited, which is the compile error doing its job: `local-model/tools.ts` passes `{ kind: "none" }`, and `YDocStore.addReply` forwards its own.

   `YDocStore.addReply(annotationId, text, suggestion)` is the MCP-side route to this seam and **must be named in the pass-through chain** (`src/server/mcp/annotations.ts:1034` → `document-store.ts:399`); its member name is pinned by `tests/server/document-store-surface.test.ts:170` (names only, so a new parameter is fine). Its docblock's "no `author` parameter, and its absence is the point" paragraph stays verbatim.

   `writeReply` takes the resolved `suggestedText` and spreads it into the record literal (`...(suggestedText !== undefined ? { suggestedText } : {})`, beside the existing `private` / `heldInSolo` / `agentIdentity` spreads).

   **`addUserReply` does NOT gain the parameter.** That is the #1000 asymmetry and it is deliberate — a user replying in their own note thread is what the unguarded entry exists for, and a suggestion is a Claude capability. No new producer, so `tests/server/annotation-reply-seam.test.ts`'s importer set and unguarded-producer count are unchanged; if either goes red the change grew a second writer and that is the test working.

   **The cap is per-field at `REPLY_TEXT_MAX`, matching the durable schema exactly — not a sum.** The round-1 draft summed `text.length + suggestedText.length` and justified it as avoiding "#1295 L3's exact failure". That reasoning was backwards: the durable schema caps each field independently (`schema.ts:164`, plus the new field), so a sum is *stricter* than what `normalizeReply` accepts and cannot produce an accepted-then-dropped-at-load write in either direction. What a sum would actually introduce is a legal-at-load pair (60k + 60k) refused at write, with a `too-long` message naming a 100,000 limit that neither field exceeds — a refusal the caller cannot act on. Per-field parity is what #1295 L3 argues for: the write bound and the load bound must be the same number, for each field. The existing `text` check is unchanged, so `annotation-reply-cap.test.ts`'s three existing cases stay green untouched; the new field gets its own arm:

   ```ts
   | { kind: "suggestion-too-long"; max: number }
   ```

   on `ReplyResult`, described by `describeReplyWriteRefusal` as `INVALID_ARGUMENT` with a message naming `suggestedText` specifically. No new `ReplyRefusalCode`.

3. **Range safety — the third eventual-rewrite consumer (Critical Rule 6, #1766), validated INSIDE the seam, AFTER the ADR-027 and #1770 guards.**

   The validation runs in `replyForClaude` (`lifecycle.ts:1408`), between the ownership guard and the `writeReply` call — **not in the `tandem_annotationReply` handler ahead of `store.addReply`**, which is where round 1 put it.

   **Why the order is the contract, and what putting it first actually costs.** `replyForClaude` is the only thing holding the reply family's privacy and ownership guards: `isPrivateForClaude(ann)` → `invalid-note` (`:1424`) and `ann.author !== "claude"` → `not-owned` (`:1443`), and `:1437` states the ordering rule for exactly this reason. A range check ahead of them answers from the RANGE layer on records Claude was never allowed to touch:

   - a **note** parent, a **private comment** parent, or a promoted-note / imported Word comment stored as `author: "user"` — all reachable, because Claude legitimately holds ids of user-authored comments from `tandem_checkInbox` / `tandem_getAnnotations`;
   - and the refusal is built from **that record's own range and snapshot**. `rangeFailureToError` (`mcp/annotations.ts:110-116`) returns `resolvedFrom`/`resolvedTo` on `RANGE_MOVED` — content-derived geometry of a private note, handed to Claude — and `RANGE_GONE` reports that its snapshot is gone. `notifyRangeFailure` (`:129-145`) additionally pushes a user-visible "Annotation failed" toast for a call that should have been a silent refusal.

   So a user-authored parent would answer `INVALID_RANGE` instead of `NOT_OWNED`, contradicting `docs/mcp-tools.md:801,815` and `skills/tandem/SKILL.md`; and a note parent becomes an oracle over text ADR-027 says Claude never reads. Validating inside the seam makes the leak unreachable by construction rather than by a predicate the handler re-derives — and it covers the local-model producer, which the handler never runs through.

   Concretely, in `replyForClaude`, after the `not-owned` arm and only when `suggestion.kind === "replacement"`:

   ```ts
   const result = anchoredRange(ydoc, ann.range.from, ann.range.to, undefined, {
     rejectHeadingOverlap: true,
     rejectHeadingInterior: true,
     normalizeSpaceClass: true,
   });
   if (!result.ok) return { kind: "invalid-suggestion-range", failure: result };
   ```

   `rejectHeadingInterior` is what makes this the third eventual-rewrite consumer: a stored `suggestedText` is a rewrite deferred to Accept that `snapshotContradicts` cannot object to — the snapshot was captured over that exact span and still matches — so without it a reply stepping over a `## ` prefix deletes the heading silently. `lifecycle.ts` gains a value import of `anchoredRange` from `../positions.js`; there is no cycle (`positions.ts` reaches only `shared/*` and `mcp/document-model.ts`, neither of which imports `annotations/lifecycle.ts`).

   **The fourth argument is `undefined`, deliberately — do NOT pass `parent.textSnapshot`.** The staleness gate compares by EXACT equality (`positions.ts:600-602`: `slice === opts.textSnapshot`, with `normalizeSpaceClass` length-preserving so the normalized arm fails too), while `captureSnapshot` caps a stored snapshot at `SNAPSHOT_CAP` = 200 (`shared/snapshot.ts:34`; `mcp/annotations.ts:355` stores `textSnapshotTruncated: true` alongside). A 200-character stored snapshot never equals a 900-character slice, so **every suggestion-bearing reply on a parent spanning more than 200 characters would be refused on an untouched document** — and worse, `collectOccurrences` finds the prefix at `from`, so the gate returns `RANGE_MOVED` with `resolvedTo = from + 200`, a range shrunk to the prefix that is silent corruption if Claude retries with it. `shared/snapshot.ts:173-177` names this exact 900→200 shrink and states the rule the server gate does not implement: a truncated snapshot can only ever be prefix-matched. `anchorRange`'s own docblock records that its only existing caller passes a CALLER-transcribed snapshot, never a stored one.

   Drift detection is not lost by omitting it: it is owned by `snapshotContradicts` at accept time (`shared/snapshot.ts:221-245`), which correctly prefix-matches a truncated snapshot. This call's only job is `rejectHeadingInterior`. Test 2's fourth case is what makes the suite discriminating here.

   Because no snapshot is passed, the reply path takes no position on a `degraded` parent and needs none — `refreshRange`'s verdict is irrelevant to a heading-interior question, and the round-1 draft's `listAnnotationsRefreshed()` lookup disappears entirely. `replyForClaude` already reads the raw record from the Y.Map and sanitizes it, so there is **no second lookup, and no whole-collection re-anchor pass persisting range updates over the user's private notes as a side effect of sending a reply**. A missing parent still falls through to `writeReply`'s `not-found`, which stays the single spelling of NOT_FOUND.

   **Do not add a boolean anywhere**: `anchorRange`'s `purpose` stays a required discriminant so a fourth consumer is a compile error, and `rejectHeadingOverlap` stays hardcoded. (This call reaches `anchoredRange` directly rather than through `YDocStore.anchorRange`, because `lifecycle.ts` holds a `Y.Doc`, not the store — the options it passes are `purpose: "suggestion"`'s expansion, and step 6 updates `anchorRange`'s docblock so the two stay legible as one rule.)

   **Wire shape of the new arm.** `ClaudeReplyResult` gains `{ kind: "invalid-suggestion-range"; failure: RangeValidation & { ok: false } }`. The `tandem_annotationReply` handler branches on it BEFORE `describeReplyWriteRefusal` — `notifyRangeFailure` + `rangeFailureToError`, exactly as `tandem_comment` does — and `describeReplyWriteRefusal`'s parameter type excludes it. That split is forced, not stylistic: `describeReplyWriteRefusal` returns `{code, message}`, which cannot carry the `resolvedFrom`/`resolvedTo` a `RANGE_MOVED` must put on the wire, and `ReplyRefusalCode` is a closed set with no range vocabulary in it. Its single `never` anchor still covers every remaining arm. The `/api` route is unaffected: it calls `addUserReply`, whose `ReplyResult` cannot produce the arm, so `REFUSAL_STATUS` needs no new key. Reaching `notifyRangeFailure` at all now proves the parent is a pending, Claude-facing, Claude-authored comment — the toast is about a record the user can see and act on.

4. **Client — one diff renderer, not two, and not one testid fewer.** Extract `SuggestionCard.svelte`'s diff box (the `segments`/`diffWords` block, its `null` fallback and the truncation note) into `src/client/panels/SuggestionDiff.svelte`, props `{ id, original, replacement, truncated }`; `SuggestionCard` renders it, and `CommentThread.svelte` renders it per reply carrying `suggestedText`, diffed against the **parent's** `textSnapshot`. `diffWords` returning `null` above its caps is inherited, not re-decided.

   **`SuggestionDiff.svelte` writes both existing testids as LITERAL-prefixed attributes, verbatim: `data-testid="suggestion-diff-{id}"` and `data-testid="suggestion-original-truncated-{id}"`.** No prop-built or interpolated prefix. `tests/design-system-impl/testid-coverage.test.ts` scans attribute declarations and normalises every `{expr}` to `{*}`, so a `data-testid="{prefix}-diff-{id}"` would collapse both of today's entries — `suggestion-diff-{*}` and `suggestion-original-truncated-{*}`, `__snapshots__/testid-set.snap.txt:459-460` — into a single `{*}-diff-{*}` form. That is a REMOVAL, forbidden by Critical Rule 7, and regenerating the snapshot in the same commit is precisely what would make it land green instead of loud. It would also break `tests/client/suggestion-card-diff.test.ts:59,98,126,154`, `tests/client/promoted-import-card.test.ts:98` and `tests/e2e/margin-view.spec.ts:1300`.

   Because `id` is just interpolated, the reply instance passes the **reply's** id and still normalises to the same two `{*}` entries — the component adds no snapshot lines at all. The reply-specific selectors go on elements `CommentThread` renders itself: a `data-testid="reply-suggestion-{replyId}"` wrapper and the `data-testid="accept-reply-btn-{replyId}"` button. Those two are the only additions.

   `CommentThread`'s Props go from `{ replies }` to `{ replies, annotation, isPending, canAccept, onAcceptReplySuggestion }` (`ReplyThread` already holds the annotation and can derive the rest). **Both the diff and the Accept affordance are gated on `annotation.type === "comment"` in addition to `reply.suggestedText !== undefined`** — `getVisibleReplies` (`src/client/annotations/replies.ts:22-28`) empties only highlights, so `CommentThread` is the shared renderer for NOTE threads too. No note reply can gain the field through today's guarded seam, but `AnnotationReplyRecordSchemaV1` is `.passthrough()` and records arrive over a Y.Map any connected client can write — the same reachability `shared/snapshot.ts:209-212` and CLAUDE.md's #1619 note both cite. Without the parent gate a future writer surfaces an Accept button inside a private note thread.

   **The thread disclosure defaults closed** (`ReplyThread.svelte:46`, `let open = $state(false)`; `CommentThread` is mounted only inside `{#if open}` at `:119-123`). Two consequences, both in scope: `open` seeds to `true` when any visible reply carries a `suggestedText` on a comment parent, so the one-click accept #1626 asks for is not hidden behind a discovery step; and tests 7/8 must click `reply-toggle-{id}` before asserting on `reply-suggestion-{*}` / `accept-reply-btn-{*}`, because otherwise they assert against an unmounted subtree. The seed is a mount-time initial value, not an `$effect` that reopens a thread the user closed.

5. **Accept — one ladder, shared, and a non-destructive supersede.**

   Round 1 specified `acceptReplySuggestion` as a sibling that "reuses `applySuggestion`" and wrote `map.set(id, {...parent, suggestedText: reply.suggestedText, status: "accepted"})` as a fresh literal, calling the rest "`resolveAnnotation`'s, unchanged". It cannot be: `resolveAnnotation(id, status)` reads `ann.suggestedText` off the stored record and takes no text parameter, so a sibling re-implements its whole accept ladder — and the round-1 test list named none of it, while test 7 (which calls `undoResolveAnnotation` directly) cannot detect any of it missing.

   So: extract the ladder ONCE. An internal `applyAcceptedSuggestion(id, suggestedText, patch)` in `useAnnotationReview.svelte.ts`, called by both `resolveAnnotation`'s suggestion-accept arm and `acceptReplySuggestion`, carrying every step verbatim (`:546-604`):

   - re-read `map.get(id)` **raw**, and `if (!raw || raw.status !== "pending") return;` — the idempotency gate, whose own comment states its purpose: "what it would prevent is `applySuggestion` running twice and inserting the suggested text twice". The round-1 draft's stated gate was the UI one ("offered only while the parent is `pending` and `canAccept`"), and `canAccept` (`annotation-context-menu.ts:52`) is a render-time predicate that cannot stop two clicks racing one write;
   - `sanitizeAnnotation(raw, devSanitizeWarn)`, and build the write off THAT record, not off the props-supplied annotation. The round-1 `{...parent}` also carried a stale `resolvedBy` back in, which `revertedToPending` (`:534-539`, #1770) exists to strip: leaving it makes the user's own later accept invisible to `awareness.ts`'s `userResponses` bucket;
   - apply BEFORE the status write (#1826), with the missing-editor arm intact — `if (!editor || !applySuggestion(...))` → `withBrowser(y, () => map.set(id, revertedToPending(ann)))` + `onApplyFailed?.(ann, editor ? "range" : "no-editor")` + return. A sibling that omitted this publishes `accepted` with no text inserted, which is #1826 exactly;
   - the status write as its own one-statement `withBrowser` transaction, never one wrap spanning the apply;
   - and the postamble `lastResolvedId = id; recentlyResolved = new Set(recentlyResolved).add(id);`, which is what surfaces the Undo affordance at `SidePanel.svelte:879` (`undoable={review.getRecentlyResolved().has(ann.id)}`). Omit it and Undo is never offered in the UI while test 7 stays green.

   `applySuggestion` is reused against a synthetic `{ ...ann, suggestedText }` — no second path into the document, so #1629's `snapshotContradicts` guard, `plaintextBlockPlan`, `literalRestoreContent` and the authorship stamp are all inherited rather than re-derived.

   **`acceptReplySuggestion(annotationId, replyId)`** calls it with the reply's text and

   ```ts
   patch = {
     suggestedText: reply.suggestedText,
     supersededSuggestedText: ann.suggestedText,   // omitted when the parent had none
     supersededByReplyId: replyId,
   }
   ```

   **The supersede is non-destructive, and that is a decision, not a spread.** Round 1's `{...parent, suggestedText: reply.suggestedText}` destroyed Claude's original proposal with no archive — including after the undo the spec itself relies on. `revertedToPending` only rewrites `status`, and the undo path (`:640-690`) reads `ann.suggestedText`/`ann.textSnapshot` straight off the record, so post-undo the parent sits `pending` carrying the REPLY's text as its suggestion and `SuggestionCard.svelte:25-26` renders a diff attributing the reply's proposal to the original comment — with the first proposal existing nowhere in the record set. Keeping the prior value costs two optional fields and makes the accept recoverable.

   Both fields are declared on `Annotation` (`src/shared/types.ts`) and on `AnnotationRecordSchemaV1` (`annotations/schema.ts:135`, beside `suggestedText`), **and added to `sanitizeAnnotation`'s explicit copy list** (`src/shared/sanitize.ts:217`). `.passthrough()` is not enough on its own: `sanitizeAnnotation` rebuilds the record from a whitelist and every write here routes through it, so a field it does not name is dropped on the first sanitize regardless of what the durable schema tolerates.

   Wiring: `SidePanel → AnnotationCard → ReplyThread → CommentThread` as `onAcceptReplySuggestion?: (annotationId: string, replyId: string) => void`.

6. **Docs.** `docs/mcp-tools.md` `tandem_annotationReply` gets the `suggestedText` row, the superseding-accept note, and `INVALID_RANGE`/`RANGE_MOVED`/`RANGE_GONE` on its Errors line (with NOT_OWNED and the ADR-027 refusals still ordered ahead of them, since that is now the runtime order). Two prose enumerations of the eventual-rewrite consumers go stale otherwise and are part of this step: `YDocStore.anchorRange`'s docblock (`document-store.ts:283-317`), which describes `"suggestion"` as "`tandem_comment` carrying `suggestedText`" and says "the one call site this replaces already passed `true`", gains the reply arm and a pointer to `replyForClaude`'s direct `anchoredRange` call; and **CLAUDE.md Critical Rule 6's enumeration** gains the reply arm as the fourth carrier.

Origin tagging: server writes keep `withMcp` via `writeReply`'s existing `wrap`; the client accept keeps `withBrowser`, one statement per transaction. No raw `.transact`. No new MCP tool and no new `/api` route, so **the license-gate tables are unchanged** — `tandem_annotationReply` is already `gated` (`license-gate-coverage.test.ts:63`) and gaining a parameter does not move a row. **The `/api/annotation-reply` twin deliberately gains nothing**, because it calls `addUserReply` and a suggestion is a Claude capability (#1000 asymmetry); that is stated in the PR body so Critical Rule 9's "gate each MCP//api pair together" is not read as unmet. `data-testid` **additions only** (`reply-suggestion-{*}`, `accept-reply-btn-{*}`); nothing renamed or removed; regenerate `tests/design-system-impl/__snapshots__/testid-set.snap.txt` in the same commit and **review the regeneration as additions only — `git diff` on the snap file must show no deleted lines.** No `$state` is written from a Tiptap handler — the accept runs from a click.

Test 10 pins the five-field shape so this stays a decision rather than an omission, and **the E2E case must not wait on an `annotation:reply` event** — it waits on the rendered card.

## Tests

2. **New `tests/server/reply-suggestion-heading-guard.test.ts`** — the issue's own hazard, converted. Four cases:
