# W1626 — #1626 a reply cannot carry a suggestion, so a refined proposal degrades to prose

Branch `fix/reply-surfaces-1626`. Closes #1626 (part 2; part 1's client half already shipped in #1636/#2021 — see below — and part 1's export/`.docx` half is deliberately Not in scope). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:115` and `:484`. Probe: `tests/e2e/reply-threads.spec.ts` (an MCP-authored reply, accepted from the card).

## Problem

**Part 1 is measured DONE on the surfaces this group owns.** `CommentThread.svelte:60` no longer interpolates `{reply.text}`: it renders `<AnnotationBody text={reply.text} author={reply.author} />`, and `AnnotationBody.svelte` routes Claude-authored text through `renderMarkdown` + `markdown-body.css`. `CommentCard`, `SuggestionCard`'s reason and the annotation bodies do the same. The issue body's anchors are stale. Nothing in part 1 is re-implemented here, and **no second markdown renderer is written** — `chat-markdown.ts`'s `renderMarkdown`/`assembleBlocks` is the only one, and it already carries the two G14 review fixes (CRLF blank lines, whitespace-only lines). `AnnotationCard.svelte`'s `br { display: none }` density rule stays — #1639 acceptance item 3's parenthetical was measured false.

**Part 2 is untouched.** `AnnotationReply` (`src/shared/types.ts:110`) has no `suggestedText`, `AnnotationReplyRecordSchemaV1` (`annotations/schema.ts:157`) has no such field, and `tandem_annotationReply` (`mcp/annotations.ts:992`) takes `{annotationId, text, documentId}`. So Claude can propose a one-click replacement when it *creates* an annotation (`tandem_comment` + `suggestedText` → `SuggestionCard`'s `diffWords` box + Accept) and cannot in the reply thread, which is exactly where a proposal is refined after the user pushes back. The counter-proposal lands as prose with no accept affordance. #1629 (the accept path's missing target verification) is CLOSED, which discharges the only stated reason part 2 was held.

## Fix

A reply's suggestion is a proposal **over the parent's range** — a reply has no range of its own and gains none.

1. **Wire + durable.** `src/shared/types.ts`: `suggestedText?: string` on `AnnotationReply`. `annotations/schema.ts`: the same field on `AnnotationReplyRecordSchemaV1`, `z.string().max(REPLY_TEXT_MAX).optional()` — `.passthrough()` would carry it regardless, and an explicit field is what makes `normalizeReply` (`sync.ts:160`) apply the cap instead of admitting an unbounded string that the *annotation* cap never sees.
2. **Seam — threaded, not widened.** `writeReply` (`lifecycle.ts`) takes an optional `suggestedText` and spreads it into the record literal (`...(suggestedText !== undefined ? { suggestedText } : {})`, beside the existing `private` / `heldInSolo` / `agentIdentity` spreads); `replyForClaude` and `AnnotationLifecycle.reply` pass it through; **`addUserReply` does NOT gain the parameter.** That is the #1000 asymmetry and it is deliberate — a user replying in their own note thread is what the unguarded entry exists for, and a suggestion is a Claude capability. No new producer, so `tests/server/annotation-reply-seam.test.ts`'s importer set and unguarded-producer count are unchanged; if either goes red the change grew a second writer and that is the test working. The existing `too-long` check covers the new field only if it is counted — cap `text.length + suggestedText.length` against `REPLY_TEXT_MAX`, because the durable schema caps each separately and a write accepted here and dropped at load is #1295 L3's exact failure.
3. **Range safety — the third eventual-rewrite consumer (Critical Rule 6, #1766).** In the `tandem_annotationReply` handler, *before* `store.addReply`, when `suggestedText !== undefined`: find the parent in `store.listAnnotationsRefreshed()` by id, then `store.anchorRange(range.from, range.to, "suggestion", parent.textSnapshot)`. `purpose: "suggestion"` is what carries `rejectHeadingInterior`, and a stored `suggestedText` is a rewrite deferred to Accept that `snapshotContradicts` cannot object to — the snapshot was captured over that exact span and still matches — so without this a reply stepping over a `## ` prefix deletes the heading silently. On `!result.ok`, `notifyRangeFailure` + `rangeFailureToError`, exactly as `tandem_comment` does. **Do not add a boolean anywhere**: `anchorRange`'s `purpose` stays a required discriminant so a fourth consumer is a compile error, and `rejectHeadingOverlap` stays hardcoded.
4. **Client — one diff renderer, not two.** Extract `SuggestionCard.svelte`'s diff box (the `segments`/`diffWords` block, its `null` fallback and the truncation note) into `src/client/panels/SuggestionDiff.svelte`, props `{ id, original, replacement, truncated }`; `SuggestionCard` renders it, and `CommentThread.svelte` renders it per reply carrying `suggestedText`, diffed against the **parent's** `textSnapshot`. `CommentThread` therefore gains an `annotation: Annotation` prop (`ReplyThread` already holds it). `diffWords` returning `null` above its caps is inherited, not re-decided.
5. **Accept.** New `acceptReplySuggestion(annotationId, replyId)` on `useAnnotationReview.svelte.ts`, wired SidePanel → AnnotationCard → ReplyThread → CommentThread as `onAcceptReplySuggestion?: (annotationId, replyId) => void`, offered only while the parent is `pending` and the user may accept it (`canAccept`). It **reuses `applySuggestion` against a synthetic `{ ...parent, suggestedText: reply.suggestedText }`** — no second path into the document, so #1629's `snapshotContradicts` guard, `plaintextBlockPlan`, `literalRestoreContent` and the authorship stamp are all inherited rather than re-derived. On success it writes, in the same `withBrowser(y, …)` one-statement transaction the hook already uses, `map.set(id, { ...parent, suggestedText: reply.suggestedText, status: "accepted" })` — the suggestion **supersedes** the parent's. Apply-before-status and the `revertedToPending` + `onApplyFailed` failure arm are `resolveAnnotation`'s, unchanged.
6. **Docs.** `docs/mcp-tools.md` `tandem_annotationReply` gets the `suggestedText` row, the superseding-accept note and `INVALID_RANGE`/`RANGE_MOVED`/`RANGE_GONE` on its Errors line. `skills/tandem/SKILL.md` line 67 gains one sentence (a reply may carry `suggestedText`; it proposes over the parent's range and accepting it supersedes the parent's) — **bump frontmatter `version: 24 → 25` and update BOTH literals in `tests/skill-instruction-contract.test.ts:434`, the version and the `bodyHash`, in the same commit.**

Origin tagging: server writes keep `withMcp` via `writeReply`'s existing `wrap`; the client accept keeps `withBrowser`. No raw `.transact`. No new MCP tool and no new `/api` route, so **the license-gate tables are unchanged** — `tandem_annotationReply` is already `gated` (`license-gate-coverage.test.ts:63`) and gaining a parameter does not move a row. `data-testid` additions only (`reply-suggestion-diff-{*}`, `accept-reply-btn-{*}`); nothing renamed or removed; regenerate `tests/design-system-impl/__snapshots__/testid-set.snap.txt` with `vitest -u` in the same commit. No `$state` is written from a Tiptap handler — the accept runs from a click.

## Tests

1. `tests/server/annotation-replies.test.ts` — a reply with `suggestedText` round-trips onto the Y.Map record. Kills a wire-only change that never reaches `writeReply`.
2. **New `tests/server/reply-suggestion-heading-guard.test.ts`** — the issue's own hazard, converted. A parent comment whose range spans a `## ` prefix's interior: `tandem_annotationReply` with `suggestedText` is refused `INVALID_RANGE`, while the **same call without `suggestedText` succeeds**. The negative half is what kills passing `"suggestion"` unconditionally (which would refuse ordinary multi-section replies) and the positive half kills passing `"comment"` (the silent heading deletion). A third case: a suggestion-bearing reply whose parent range does *not* touch a heading succeeds.
3. `tests/server/annotation-reply-cap.test.ts` — `text` + `suggestedText` summing past `REPLY_TEXT_MAX` is refused at write. Kills capping only `text`, which is the accepted-then-silently-dropped-at-load shape.
4. `tests/server/annotation-reply-seam.test.ts` — unchanged and must stay green. Its redness is the discriminating signal that `addUserReply` grew the parameter.
5. `tests/server/replies-privacy-readwrite.test.ts` — a note-parent reply is still refused `invalid-note` with `suggestedText` present, and a highlight parent still answers `not-repliable`, not `invalid-note`. Kills a guard widened to `type !== "comment"` while the family was being edited.
6. `tests/client/suggestion-card-diff.test.ts` — extend for `SuggestionDiff.svelte`; a reply-level diff renders against the **parent's** snapshot. Kills diffing against the reply text or against a previous reply.
7. **New `tests/client/reply-suggestion-accept.test.ts`**, modelled on `tests/client/suggestion-accept-drift-guard.test.ts` (live Tiptap, not the mocked-editor hook suite): accepting a reply suggestion writes the reply's text into the document; after a third party edits the span, the same accept is **refused and the document untouched** (the inherited `snapshotContradicts`); and after a successful accept the parent's stored `suggestedText` equals the reply's, so `undoResolveAnnotation` restores rather than declining "text changed" — the supersede write is load-bearing, and without it undo is a live-looking button that silently does nothing.
8. `tests/e2e/reply-threads.spec.ts` — one case: MCP posts a reply with `suggestedText`, the card shows the diff, Accept writes the text and resolves the parent.
