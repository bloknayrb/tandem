# W1626 — #1626 a reply cannot carry a suggestion, so a refined proposal degrades to prose

Branch `fix/reply-surfaces-1626`. Closes #1626 (part 2). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:115`, `:484`.

## Problem

**Part 1 is measured DONE on the surfaces this group owns, and nothing here re-implements it.** `CommentThread.svelte:60` renders `<AnnotationBody text={reply.text} author={reply.author} />`; `AnnotationBody` routes Claude-authored text through `chat-markdown.ts`'s `renderMarkdown` + `markdown-body.css` (G14, PR #2021). No second renderer is written. `AnnotationCard.svelte`'s `br { display: none }` stays — #1639's acceptance item 3 was measured false. The rendering is gated on `author === "claude"` by design (`AnnotationBody.svelte:46`): `tandem_editAnnotation` has no author gate, so Claude editing a user's comment leaves `author: "user"`, and the honest fix is a separate `editedBy` field. Stated in the PR body for Bryan's confirmation; no test is added for it here.

**Part 2 is untouched.** `AnnotationReply` has no `suggestedText`, `AnnotationReplyRecordSchemaV1` has no such field, and `tandem_annotationReply` takes `{annotationId, text, documentId}`. So Claude can propose a one-click replacement when it *creates* an annotation and cannot in the reply thread — exactly where a proposal is refined after the user pushes back. #1629 is CLOSED, which discharges the only stated reason part 2 was held.

## Fix

A reply's suggestion is a proposal **over the parent's range** — a reply has no range of its own and gains none.

1. **Wire + durable.** `src/shared/types.ts`: `suggestedText?: string` on `AnnotationReply`. `annotations/schema.ts`: the same field on `AnnotationReplyRecordSchemaV1` as `z.string().max(REPLY_TEXT_MAX).optional()` — `.passthrough()` would carry it regardless, and the explicit declaration is what makes `normalizeReply` (`sync.ts:160`) apply the cap instead of admitting an unbounded string.

   **The MCP READ surface is the third declaration and is not optional.** `src/server/mcp/output-schemas.ts:115-123`'s `VisibleReplySchema` gains `suggestedText: z.string().optional().describe("Replacement proposal carried by a Claude-authored reply, over the parent annotation's range")`. `tandem_getAnnotations` builds `replies: channelVisibleReplies(...)` (`annotations.ts:484-492`) out of `collectRepliesForAnnotation`, which pushes the raw Y.Map record with **every** field, and `mcpStructured` ships that object as `structuredContent`; `tests/server/mcp-output-schemas.test.ts` parses the payload in zod strip-mode and asserts deep equality with what was emitted, so **an undeclared key turns the required `check` red** and Claude cannot read back its own proposal. Privacy is unchanged: the field is Claude's own text on a Claude-authored reply, and `channelVisibleReplies`' filtering is untouched.

2. **Seam — a required discriminant, not widened to the user path.** `AnnotationLifecycle.reply(annotationId, text, suggestion, onLossy, agentIdentity?)` where

   ```ts
   export type ReplySuggestion = { kind: "none" } | { kind: "replacement"; suggestedText: string };
   ```

   **Required and positioned before the optionals** (Critical Rule 6: both existing eventual-rewrite creators take the arm as a required discriminant so a new one cannot default into the wrong half without a compile error). A bare optional would let `local-model/tools.ts:373`'s `reply_to_annotation` acquire the field silently. Both callers must be edited: `local-model/tools.ts` passes `{ kind: "none" }`, `YDocStore.addReply(annotationId, text, suggestion)` (`document-store.ts:409`) forwards its own; its docblock's "no `author` parameter" paragraph stays verbatim.

   `writeReply` caps the resolved text **per field at `REPLY_TEXT_MAX`, reusing the existing `too-long` arm** — exact parity with the durable schema, which caps each field independently, so nothing the schema accepts is refused at write. It then spreads `...(suggestedText !== undefined ? { suggestedText } : {})` into the record literal beside the existing `private` / `heldInSolo` / `agentIdentity` spreads.

   **`addUserReply` does NOT gain the parameter** — the #1000 asymmetry; a suggestion is a Claude capability. No new producer, so `tests/server/annotation-reply-seam.test.ts` is unchanged and its redness would mean the change grew a second writer.

3. **Range safety — the third eventual-rewrite consumer, validated INSIDE the seam, AFTER the guards.** In `replyForClaude` (`lifecycle.ts:1414`), after the `not-owned` arm and only when `suggestion.kind === "replacement"`:

   ```ts
   // Screen the span the Accept will actually rewrite: the CRDT-anchored one.
   const refreshed = refreshRange(ann, ydoc); // no `map` — read-only, persists nothing
   const live =
     refreshed.kind === "degraded" || refreshed.kind === "failed"
       ? ann.range // dead/unverifiable anchor: the stored range is all there is
       : refreshed.annotation.range;
   const result = anchoredRange(ydoc, live.from, live.to, undefined, {
     rejectHeadingOverlap: true,
     rejectHeadingInterior: true,
     normalizeSpaceClass: true,
   });
   if (!result.ok) return { kind: "invalid-suggestion-range" };
   ```

   **The offsets screened must be the CURRENT ones, not the stored ones.** `anchoredRange` validates exactly the offsets handed to it (`positions.ts:675-683`), and with the fourth argument `undefined` the staleness/relocation step (`positions.ts:599`) is skipped entirely — so nothing maps a stored range onto current text. That exposure is unique to this carrier: `YDocStore.anchorRange` and `tandem_edit` both validate offsets the caller just derived from the live document, whereas a reply screens a parent anchored at some earlier time. At accept time the client resolves through `annotationToPmRange` off `relRange` (`useAnnotationReview.svelte.ts:308`), so on a document edited since the parent was anchored, screening `ann.range` checks a span that is not the one rewritten — and `snapshotContradicts` still cannot object. `refreshRange` is the existing path that resolves `relRange` to current offsets; it is called WITHOUT `map` so this write path persists no re-anchor (a read path, `listAnnotationsRefreshed`, owns that), and the stored range is the fallback only when the anchor is dead, which is the same "all there is" position the client accept lands in.

   `rejectHeadingInterior` is what makes this the third consumer: a stored `suggestedText` is a rewrite deferred to Accept that `snapshotContradicts` cannot object to, so without it a reply stepping over a `## ` prefix deletes the heading silently.

   **The order is the contract.** `replyForClaude` holds the reply family's only privacy and ownership guards — `isPrivateForClaude(ann)` → `invalid-note` (`:1424`) and `ann.author !== "claude"` → `not-owned` (`:1443`), with `:1437` stating the ordering rule for exactly this reason. Validating ahead of them would answer from the range layer on records Claude was never allowed to touch: a note, a private comment, or a promoted note / imported Word comment stored as `author: "user"` — all reachable, since Claude legitimately holds ids of user-authored comments from `tandem_checkInbox`. Running it here makes that unreachable by construction, and covers the local-model producer, which never runs through the MCP handler.

   **The fourth argument is `undefined` — do NOT pass `parent.textSnapshot`.** The staleness gate compares by exact equality (`positions.ts:600-602`, with `normalizeSpaceClass` length-preserving) while `captureSnapshot` caps a stored snapshot at `SNAPSHOT_CAP` = 200 (`shared/snapshot.ts:34`). Every suggestion-bearing reply on a parent spanning more than 200 characters would be refused on an untouched document, returning `RANGE_MOVED` with `resolvedTo = from + 200` — a range shrunk to the prefix. Drift detection is owned by `snapshotContradicts` at accept time (`shared/snapshot.ts:221-245`), which prefix-matches correctly. This call's only job is `rejectHeadingInterior`.

   **The refusal carries no range payload.** `ClaudeReplyResult` gains a bare `{ kind: "invalid-suggestion-range" }`; `describeReplyWriteRefusal` gains one case returning `INVALID_ARGUMENT` with a message naming the heading, so `ReplyRefusalCode` stays closed and its single `never` anchor still covers every arm. No `notifyRangeFailure`, no `rangeFailureToError`, no `resolvedFrom`/`resolvedTo` on the wire — a reply refusal is not a range-resolution surface, and keeping it flat removes the only channel by which a refusal could ever describe a record's geometry. The `/api` route is unaffected: it calls `addUserReply`, whose `ReplyResult` cannot produce the arm.

   `lifecycle.ts` gains a value import of `anchoredRange` and `refreshRange` from `../positions.js`; no cycle (`positions.ts` reaches only `shared/*` and `mcp/document-model.ts`). `MCP handler`: `tandem_annotationReply` gains `suggestedText: z.string().optional()` and passes the discriminant through; missing parent still falls through to `writeReply`'s `not-found`.

4. **Client — the reply box, no component extraction.** `CommentThread.svelte` renders, per reply carrying `suggestedText`, a `data-testid="reply-suggestion-{reply.id}"` box holding the proposed replacement text, plus a `data-testid="accept-reply-btn-{reply.id}"` button. **No word-diff and no shared diff component**: `SuggestionCard.svelte` is not touched, so its `suggestion-diff-{*}` and `suggestion-original-truncated-{*}` snapshot entries cannot move, and the testid change is additions-only. The parent card above already shows the original span via `AnnotationSnippet`.

   Both the box and the button are gated on `annotation.type === "comment"` in addition to `reply.suggestedText !== undefined`. `getVisibleReplies` empties only highlights, so `CommentThread` is the shared renderer for NOTE threads too; no note reply can gain the field through today's guarded seam, but records arrive over a Y.Map any connected client can write, and without the gate a future writer surfaces an Accept button inside a private note thread.

   `CommentThread`'s Props go from `{ replies }` to `{ replies, annotation, isPending, canAccept, onAcceptReplySuggestion }` (`ReplyThread` already holds the annotation). The disclosure defaults closed (`ReplyThread.svelte:46`), so `open` **seeds** to `true` at mount when a visible reply on a comment parent carries a `suggestedText` — a mount-time initial value, not an `$effect` that reopens a thread the user closed. Tests 5/6 expand `reply-toggle-{id}` first.

5. **Accept — one ladder, shared.** `resolveAnnotation(id, status)` reads `ann.suggestedText` off the stored record and takes no text parameter, so a sibling would re-implement its whole ladder. Extract it ONCE: an internal `applyAcceptedSuggestion(id, suggestedText)` in `useAnnotationReview.svelte.ts` carrying `:541-604` verbatim — re-read `map.get(id)` **raw** and `if (!raw || raw.status !== "pending") return;` (the idempotency gate, whose own comment names `applySuggestion` running twice as what it prevents); `sanitizeAnnotation(raw, devSanitizeWarn)` and build the write off THAT record, not off the props-supplied annotation, so a stale `resolvedBy` cannot ride back in (#1770); apply BEFORE the status write (#1826) with the missing-editor arm intact (`!editor || !applySuggestion(...)` → `withBrowser(y, () => map.set(id, revertedToPending(ann)))` + `onApplyFailed?.(ann, editor ? "range" : "no-editor")`); the status write as its own one-statement `withBrowser`; and the `lastResolvedId` / `recentlyResolved` postamble, which is what surfaces Undo at `SidePanel.svelte:879`. `resolveAnnotation`'s accept arm and `acceptReplySuggestion(annotationId, replyId)` both route through it; `applySuggestion` runs against a synthetic `{ ...ann, suggestedText }`, so #1629's `snapshotContradicts`, `plaintextBlockPlan` and the authorship stamp are inherited.

   **Accepting a reply's suggestion overwrites the parent's own `suggestedText` — a decision, not a side effect.** `undoResolveAnnotation` (`:640-690`) compares the current span against `appliedProjection(... ann.suggestedText ...)`, so the stored field MUST be what was applied or undo declines "text changed" on every reply accept. The parent's original proposal is therefore superseded and not archived: the refined proposal replacing the first is the whole point of #1626. Listed under Bryan below so it is a recorded call.

   Wiring: `SidePanel → AnnotationCard → ReplyThread → CommentThread` as `onAcceptReplySuggestion?: (annotationId: string, replyId: string) => void`.

6. **Docs.** `docs/mcp-tools.md`: the `suggestedText` row on `tandem_annotationReply`, the superseding-accept note, and INVALID_ARGUMENT's heading case on its Errors line (NOT_OWNED and the ADR-027 refusals stay ordered ahead, which is now the runtime order). **CLAUDE.md Critical Rule 6's enumeration** gains the reply arm as the fourth carrier. `skills/tandem/SKILL.md` line 67 gains one sentence (a reply may carry `suggestedText`; it proposes over the parent's range and accepting it supersedes the parent's) — bump frontmatter `version: 24 → 25` and update both literals in `tests/skill-instruction-contract.test.ts:434` in the same commit; the `bodyHash` is computed from the post-frontmatter body at run time, so run the suite once and paste the reported value.

Origin tagging: server writes keep `withMcp` via `writeReply`'s existing `wrap`; the client accept keeps `withBrowser`, one statement per transaction. No raw `.transact`. No new MCP tool and no new `/api` route, so the license-gate tables are unchanged (`tandem_annotationReply` is already `gated`). The `/api/annotation-reply` twin deliberately gains nothing — it calls `addUserReply` — stated in the PR body so Critical Rule 9's pairing rule is not read as unmet. `data-testid` **additions only**; `git diff` on `__snapshots__/testid-set.snap.txt` must show no deleted lines. No `$state` is written from a Tiptap handler — the accept runs from a click. The channel payload is unchanged by construction: `narrowReplyForChannel` refuses `reply.author !== "user"`, so a Claude-authored reply never projects; the E2E must wait on the rendered card, never on an `annotation:reply` event.
