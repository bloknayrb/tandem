## Problem

Since #1757, `attachChildStreamErrorHandlers` → `makeStdinGoneHandler` SIGTERMs a live child whose stdin errors, and the exit handler calls `scheduleRestart()`. If every replacement has the same broken stdin, each wake kills one child. At a cadence of about one event per 30 s or slower, the rolling window never holds 11 attempts. Meanwhile `restartIndex` drops back to the 1 s rung and `status()` reports `running: true` between wakes. The loop never ends and nothing on any surface names it. Before #1757 the throw reached `captureFatal` (opt-in Sentry). After #1757 the only trace is a `console.error`. That line does reach `tandem.log`, because `src-tauri/src/sidecar.rs` logs every sidecar stderr line at `log::warn!`, which is at the release `LevelFilter::Warn` floor.

## Fix

**Counter.** In `createSupervisor`: `let deliveryKillStreak = 0;` plus a module constant `const DELIVERY_KILL_LIMIT = 3;` with a docblock. The docblock says:
- the limit is a count of consecutive kills with **no time window**, which is the point of the issue;
- 3 means "the same failure on three successive children";
- the ladder's 1 s/5 s/30 s rungs put the fastest stdin-error trip at about 36 s;
- with G1-1867, a child that never shows receipt is killed after `TURN_RECEIPT_MS`, so the slowest receipt-driven trip is about 3 × that bound plus the rungs.

**What counts: once per spawn, only for a kill we issued.** `makeStdinGoneHandler(spawned, isCurrent, onKill?)` gains an optional third parameter. It is called inside the existing guards, immediately before `spawned.kill("SIGTERM")`. In `spawnOnce`, add a per-spawn `let killedForDelivery = false;`. The bound line becomes `const onStdinGone = makeStdinGoneHandler(spawned, () => child === spawned, markDeliveryKill);`, which is 97 columns at this indent, under Biome's 100. `markDeliveryKill` is declared as `function markDeliveryKill(): void { killedForDelivery = true; }` **above** the `const`, so the two pinned lines stay adjacent. The exit handler does the counting. Real Node sets `signalCode` only at exit, so between the kill and the exit a second stream `'error'` or a receipt timeout calls `onKill` again. The boolean is what makes that one count per spawn (the no-double-count criterion).

**Trip.** In `spawned.on("exit")`, after `if (stopRequested) return;` and before `scheduleRestart()`:

```ts
if (killedForDelivery && ++deliveryKillStreak >= DELIVERY_KILL_LIMIT) {
  breakerTripped = true;
  // Same guarded, fail-open probe as scheduleRestart's trip, for the same reason:
  // a child that exits 127 (missing CLI) can still have its stdin error land
  // before Node records the exit, and that case must route to Setup, not Restart.
  let cliUsable = true;
  try {
    cliUsable = probeCliUsable();
  } catch (err) {
    console.error("[Launcher] CLI probe failed; reporting a wake-delivery failure:", err);
  }
  lastError = cliUsable ? "wake-delivery-failed" : "cli-unusable";
  console.error(cliUsable
    ? `[Launcher] Claude was ended ${deliveryKillStreak} times in a row because it stopped accepting turns — giving up. Restart Claude Code to retry.`
    : "[Launcher] Claude kept failing to accept turns and the Claude CLI is missing or cannot be started — check the integration setup.");
  if (cliUsable) reportDeliveryTrip(DELIVERY_TRIP_REPORT);
  return;
}
```

Setting `breakerTripped` reuses every existing gate: `startInternal`, `scheduleRestart`, and the client's Restart CTA via `relaunch` → `respawn`.

**Reset.** On proof of healthy delivery: `deliveryKillStreak = 0` in `handleStdoutLine`'s `parsed.type === "result"` branch, next to `clearLatch()`. It is deliberately **not** reset on any other parsed envelope. `init` proves receipt, not that a turn completed, and G1-1867's receipt clear sits in the same function, where that consolidation would be easy to make by mistake. The ordinary 30 s `restartIndex` reset is left alone and not reused. On a user action: `deliveryKillStreak = 0` in `respawn`, beside `breakerTripped = false; recentAttempts = [];`, which is the existing breaker contract.

**Contract.** `src/shared/launcher/contract.ts` `LauncherErrorCode` gains `"wake-delivery-failed"`, with one docblock sentence: the child kept refusing turns, and the remedy is a restart. `api-routes.ts` passes `raw.lastError` through verbatim (`makeStatusHandler`), so it needs no change. Client: `useAiReadiness`'s `chip` derivation maps any `lastError` other than `cli-unusable` to `restart`, which is the right remedy. There is no client change for this issue (G1-1780 adds one for `needs-login`).

**Durable telemetry, through the existing opt-in path only, and injected rather than imported.**

- `SupervisorOpts` gains `reportDeliveryTrip?: (message: string) => void`, default a no-op, with a docblock saying it is wired to opt-in crash reporting by `index.ts`. `supervisor.ts` does **not** import `sentry.ts`. `sentry.ts` statically imports `./mcp/server.js`, and routing that graph through `supervisor.ts` would make every unmocked launcher suite load the MCP server module.
- Module constant `const DELIVERY_TRIP_REPORT = "launcher: wake delivery failed on consecutive sessions";`. It is a fixed string with no path, session id, count or content.
- `src/server/sentry.ts` gains `export function captureWarning(message: string): void { if (!sentry) return; try { sentry.captureMessage(scrub(message), "warning"); } catch {} }`. There is no flush-await, because it is not on an exit path. With `TANDEM_SENTRY_DSN` unset, `sentry` is `null` and `@sentry/node` is never loaded, so nothing new leaves the machine by default. Update the header's "We only ever capture `Error`s from the fatal-error path" sentence to name this one fixed-string warning.
- `src/server/index.ts`: pass `reportDeliveryTrip: captureWarning` at the single `createSupervisor({` call. `index.ts` already imports `captureFatal` from `./sentry.js`, so the import widens by one name.
- `docs/security.md` §"Telemetry: none by default, crash reporting strictly opt-in": the opted-in list currently ends "…and Node uncaught exceptions (sidecar)". Extend that clause to "Node uncaught exceptions plus one fixed-string warning when the launcher gives up on a Claude session that stopped accepting turns (sidecar)". This is one hunk, and #1987 has merged, so there is no owner conflict. Run `tests/docs/` after the edit.

CLAUDE.md rules that bite: Critical Rule 3 (stdout is reserved), so every log is `console.error`. Rule 9 does not apply (no new route or tool). The source-order pin in `tests/server/launcher/supervisor.test.ts` ("attaches the seam in spawnOnce as two bare statements…") must have its literal updated to the three-argument line. Its adjacency and ordering assertions stay.

## Tests

In `tests/server/launcher/supervisor-turn-delivery.test.ts`, using the mocked `spawn` harness from G1-1866 exactly as specified there: `failWrite` (held callbacks, then the stream `'error'` on a later tick), a fake `kill` that defers `signalCode`/`exit` to `setImmediate`, and `exitChild`. Each test injects `reportDeliveryTrip: vi.fn()`. No `vi.mock` of `sentry.ts` is needed. A "delivery kill" below means `failWrite(child)` on a live child, which reaches `onStdinGone` → `markDeliveryKill` → `kill` → `exit(null, "SIGTERM")`. A delivery-killed spawn keeps the saved session, so its successor resumes and receives the owed `[WAKE]` (G1-1866), and that write is the next one to fail.

1. **Slow cadence trips.** `vi.useFakeTimers({ toFake: ["Date"] })`. Delivery-kill children 1, 2 and 3, with `vi.setSystemTime(Date.now() + 11 * 60_000)` between failures. Eleven minutes is above both `CIRCUIT_BREAKER_WINDOW_MS` (5 min) and `WAKE_LATCH_MAX_MS` (10 min), so a counter windowed on either cannot survive. After the third exit: `status()` is `{ running: false, lastError: "wake-delivery-failed" }`, `spawn` was called exactly 3 times, and `reportDeliveryTrip` was called once with `DELIVERY_TRIP_REPORT`.
2. **Fast cadence trips** at the same count with no clock advance.
3. **Healthy delivery resets.** Delivery-kill children 1 and 2. Child 3 receives its `[WAKE]`, pushes `init` then `result`, and then `exitChild(child3, 1)`: an ordinary crash, not a delivery kill, and resumed inside `RESUME_CONFIRM_MS`, so child 4 is fresh. Delivery-kill children 4 and 5. Assert child 6 was spawned, `status().running` is true, and there is no `lastError`. *Kills* a reset tied to spawn success or to the 30 s timer, and a missing reset.
   - **3b, receipt is not completion.** Delivery-kill children 1 and 2. Child 3 receives `[WAKE]`, pushes only `init`, and is then delivery-killed. The trip happens at child 3 (`wake-delivery-failed`). *Kills* resetting on any parsed envelope or alongside G1-1867's receipt clear.
4. **No double count within one spawn.** For children 1 and 2: `failCallbacksOnly(all held)`, set `stdin.writable = false`, then `stdin.emit("error", EPIPE)` **twice, synchronously**. Both emits land before the fake `kill`'s deferred `exit`, and `signalCode` is still `null`, so `onKill` runs twice per spawn, which real Node allows. Child 3 receives `[WAKE]` and is left alive. Assert `status().running` is true and there is no `lastError`. *Kills* incrementing per `onKill` (moving the increment into `markDeliveryKill`: 2 after child 1, 4 after child 2, tripped) and counting in the stream `'error'` listener or the write callback.
5. **Ordinary exits are distinct, and the missing-CLI race routes to Setup.**
   - 5a: three children `exitChild(child, 1)` with no stdin error → `lastError` is not `wake-delivery-failed`, and restarts continue.
   - 5b: `probeCliUsable: () => false`. For three children, in one synchronous block: `failCallbacksOnly(all held)`, set `stdin.writable = false`, `stdin.emit("error", EPIPE)` while `exitCode` is still `null` (so `onKill` fires and `kill` is called), then `exitChild(child, 127)` before the fake `kill`'s deferred signal exit. The fake `kill`'s `setImmediate` sees `exitCode` set and emits nothing more. After the third, `lastError === "cli-unusable"` and `reportDeliveryTrip` was not called. *Kills* the trip without the probe, which would route a missing CLI to Restart.
6. **User relaunch resets.** After test 2's trip, `relaunch(dir)` spawns, and one more delivery kill does not trip (`running`, a successor spawned, no `lastError`).

In `tests/server/launcher/supervisor.test.ts`, the existing `makeStdinGoneHandler` units gain cases for the new parameter: `onKill` is called for a current live child; it is NOT called for a superseded one (`isCurrent: () => false`) or for one already marked exited (`exitCode: 127`); and `onKill` runs before `kill`. The source-order pin's literal is updated.

Test 5b drives the error-before-127-exit race rather than presetting `exitCode`. - Test 1 steps the clock +11 min (above both 5-min and 10-min windows) and adds the "5-min window" mutation.
- Test 3b: a spawn that shows only `init` and is then delivery-killed still counts. The healthy spawn in test 3 ends with an ordinary `exitChild(…, 1)`.
- `captureWarning` is injected via `SupervisorOpts.reportDeliveryTrip` and wired in `index.ts`. No import of `sentry.ts` from `supervisor.ts`, and no `vi.mock` of sentry.

**Not adopted**
