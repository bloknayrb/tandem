# G1 — #1868 Consecutive stdin-error kills never trip at human cadence; no dedicated `LauncherErrorCode`

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Closes #1868. Ledger: none. This is a #1757 follow-up, tracked in the sweep's G1 row. Probe: a source reading of `scheduleRestart` (`CIRCUIT_BREAKER_MAX_ATTEMPTS = 10`, `CIRCUIT_BREAKER_WINDOW_MS = 5 min`) and of `startInternal`'s `restartIndex = 0` reset after `RESUME_CONFIRM_MS` (30 s). Both re-read on `4f112aa4`.

## Problem

Since #1757, `attachChildStreamErrorHandlers` → `makeStdinGoneHandler` SIGTERMs a live child whose stdin errors, and the exit handler calls `scheduleRestart()`. If every replacement has the same broken stdin, each wake kills one child. At a cadence of about one event per 30 s or slower, the rolling window never holds 11 attempts. Meanwhile `restartIndex` drops back to the 1 s rung and `status()` reports `running: true` between wakes. The loop never ends and nothing on any surface names it. Before #1757 the throw reached `captureFatal` (opt-in Sentry). After #1757 the only trace is a `console.error`. That line does reach `tandem.log`, because `src-tauri/src/sidecar.rs` logs every sidecar stderr line at `log::warn!`, which is at the release `LevelFilter::Warn` floor.

## Fix

**Counter.** In `createSupervisor`: `let deliveryKillStreak = 0;` plus a module constant `const DELIVERY_KILL_LIMIT = 3;` with a docblock. The docblock says the limit is a count of consecutive kills with no time window, which is the whole point; that 3 means "the same failure on three successive children"; and that the ladder's 1 s/5 s/30 s rungs put the trip at about 36 s at the fastest.

**What counts — once per spawn, only for a kill we issued.** `makeStdinGoneHandler(spawned, isCurrent, onKill?)` gains an optional third parameter. It is called inside the existing guards, immediately before `spawned.kill("SIGTERM")`. In `spawnOnce`, add a per-spawn `let killedForDelivery = false;`. The bound line becomes `const onStdinGone = makeStdinGoneHandler(spawned, () => child === spawned, markDeliveryKill);` (97 columns at this indent, under Biome's 100). `markDeliveryKill` is a `function markDeliveryKill(): void { killedForDelivery = true; }` declared **above** the `const` so the two pinned lines stay adjacent. The exit handler does the counting, so N write callbacks plus the stream `'error'` from one failed write set one boolean once, and one spawn is counted once (the no-double-count criterion).

Why "kill issued", not "a write failed": a missing CLI makes the reaper exit 127. A wake written into that dying pipe fails too. If that counted, the 127 crash loop would trip here as `wake-delivery-failed` after 3 attempts instead of reaching the ordinary breaker's `cli-unusable` probe, and the user would be sent to Restart instead of Setup. That is #1268's routing, regressed. The handler's `exitCode`/`signalCode` guard is what excludes a child that is already dead.

**Trip.** In `spawned.on("exit")`, after `if (stopRequested) return;` and before `scheduleRestart()`:

```ts
if (killedForDelivery && ++deliveryKillStreak >= DELIVERY_KILL_LIMIT) {
  lastError = "wake-delivery-failed";
  breakerTripped = true;
  console.error(`[Launcher] Claude was ended ${deliveryKillStreak} times in a row because it stopped accepting turns — giving up. Restart Claude Code to retry.`);
  captureWarning("launcher: wake delivery failed on consecutive sessions");
  return;
}
```

Setting `breakerTripped` reuses every existing gate: `startInternal`, `scheduleRestart`, and the client's Restart CTA via `relaunch` → `respawn`.

**Reset.** On proof of healthy delivery: `deliveryKillStreak = 0` in `handleStdoutLine`'s `parsed.type === "result"` branch, next to `clearLatch()`. The ordinary 30 s `restartIndex` reset is left alone and deliberately NOT reused. On a user action: `deliveryKillStreak = 0` in `respawn`, beside `breakerTripped = false; recentAttempts = [];`, which is the existing breaker contract.

**Contract.** `src/shared/launcher/contract.ts` `LauncherErrorCode` gains `"wake-delivery-failed"`, with one docblock sentence: the child kept refusing turns, and the remedy is a restart. `api-routes.ts` passes `raw.lastError` through verbatim (`makeStatusHandler`), so it needs no change. Client: `useAiReadiness`'s `chip` derivation maps any `lastError` other than `cli-unusable` to `restart`, which is the right remedy. No client change for this issue (G1-1780 adds one for `needs-login`).

**Durable telemetry, through the existing opt-in path only.** `src/server/sentry.ts` gains a sibling of `captureFatal`, `export function captureWarning(message: string): void`. It does `if (!sentry) return; try { sentry.captureMessage(scrub(message), "warning"); } catch {}`, with no flush-await because it is not on an exit path. With `TANDEM_SENTRY_DSN` unset, `sentry` is `null` and `@sentry/node` is never loaded, so nothing new leaves the machine by default. The message is a fixed string with no path, session id or content. That puts it inside `docs/security.md` §"Telemetry: none by default, crash reporting strictly opt-in", which needs no edit: it already lists what the sidecar reports only in coarse terms. See `bryan` for whether a warning-level event is wanted at all.

CLAUDE.md rules that bite: Critical Rule 3 (stdout is reserved), so every log is `console.error`. Rule 9 does not apply (no new route or tool). The source-order pin in `tests/server/launcher/supervisor.test.ts` ("attaches the seam in spawnOnce as two bare statements…") must have its literal updated to the three-argument line. Its adjacency and ordering assertions stay.

## Tests

In `tests/server/launcher/supervisor-turn-delivery.test.ts` (mocked `spawn` harness, see G1-1866), plus `vi.mock("../../../src/server/sentry.js")`:

1. **Slow cadence trips.** Use `vi.useFakeTimers({ toFake: ["Date"] })`. Three spawns in turn each get a wake whose write callback and stream `'error'` fire while the child is alive, with `vi.setSystemTime(+60 s)` between failures. After the third exit, `status()` is `{ running: false, lastError: "wake-delivery-failed" }`, `spawn` has been called exactly 3 times, and `captureWarning` has been called once. *Kills* any time-window implementation and a reuse of `recentAttempts`.
2. **Fast cadence trips** at the same count with no clock advance.
3. **Healthy delivery resets.** Fail twice, then a spawn that pushes a `result` line, then fail twice more → still running, no `lastError`. *Kills* a reset tied to spawn success or to the 30 s timer.
4. **No double count.** Two spawns each see two held write callbacks *and* one stream `'error'`, all erroring, then a third spawn exits with an ordinary `code: 1` → not tripped. *Kills* counting in the callback or the `'error'` listener.
5. **Ordinary exits are distinct.** Three children that `exit` with code 1 and no stdin error → `lastError` is not `wake-delivery-failed`, and restarts continue. A child already marked exited (`exitCode: 127`) whose stdin then errors → `onKill` is not called and nothing is counted. *Kills* the "write failed" definition. This is the #1268 routing guard.
6. **User relaunch resets.** After a trip, `relaunch(dir)` spawns and one more failure does not trip. The existing `makeStdinGoneHandler` units in `supervisor.test.ts` get one case for the new parameter: `onKill` is called for a current live child and NOT for a superseded or exited one.

Mutation plan: remove the result-branch reset → 3 red. Move the increment into `markDeliveryKill` → 4 red. Delete the `exitCode` guard's effect on `onKill` → 5 red. Delete the `captureWarning` call → 1 red.
