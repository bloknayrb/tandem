# J2 — #1816 Save/rename failure toasts leak raw errno + absolute path on loopback

Branch `fix/product-copy-1814`. Closes #1816. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:22`. Probe: none (read-verified against source).

## Problem

`src/server/mcp/document-service.ts` builds save/save-as/rename failure `reason` and pushed-notification `message` strings directly from the raw Node error (`err.message`, e.g. `"EACCES: permission denied, open '/Users/…/file.md'"`) at four sites: `saveDocumentToDisk`'s catch (~L666-679, HEAD), `saveDocumentAsToDisk`'s catch (~L1030-1043), and two catches inside `renameDocument` (~L1310, ~L1535-1548 — one wrapping validation/`assertPathSafe`, one wrapping the actual `fs.rename`). `src/client/actions/builtin.svelte.ts:425,457` renders `result.reason` verbatim in a toast. The scrub in `_shared.ts`'s `GENERIC_ERROR_MESSAGE` (`routes/save.ts:148`, `routes/rename.ts`'s `RENAME_GENERIC_MESSAGE`) applies only to **non-loopback** callers — every desktop user is loopback, so they see the errno text and the absolute path unconditionally. `errorCode` (the bare Node error code, e.g. `EACCES`) already exists on every one of these return-type interfaces (`document-service.ts:198,733,1124`) and already survives to the client (`routes/save.ts`'s `res.json({ data: result })` spreads `result` — `errorCode` is not stripped); only the free-text `reason`/`message` need scrubbing.

## Fix

At each of the four catch sites in `document-service.ts`, stop deriving `reason`/`message` from `err.message`. Keep computing `errCode` (`(err as NodeJS.ErrnoException).code ?? "UNKNOWN"`) as today — it is the one technical detail allowed to travel — and log the raw `err` to `console.error` (stderr; Critical Rule 3) so operators can still diagnose. Replace the leaking strings:

- `saveDocumentToDisk` catch: `pushNotification` message → `` `Save failed for ${path.basename(docState.filePath)}.` `` (drop the `: ${msg}` suffix — the notification still names the FILE, not its path, which is fine, it's a basename); return `reason: "The document could not be saved."`, `errorCode: errCode`.
- `saveDocumentAsToDisk` catch: same pattern, `reason: "The document could not be saved to that location."`.
- `renameDocument`'s first catch (validation/`assertPathSafe`/name-check path): `reason: "The document could not be renamed."`.
- `renameDocument`'s second catch (`fs.rename` failure): same message; `pushNotification` message drops its `: ${msg}` suffix too.

`src/client/actions/builtin.svelte.ts`'s `triggerSave` result type (~L437-448) needs `errorCode?: string;` added alongside `reason?: string;` (it is not read there today). Render the detail as a parenthetical, not folded into the headline: `` `Save failed: ${result.reason ?? "The document could not be saved."}${result.errorCode ? ` (${result.errorCode})` : ""}` ``.

**Two stale comments this fix must also correct**, both citing the exact leak this PR closes as still-live rationale:
- `routes/save.ts`'s `#1294` comment (~L143-148, above the `!isLoopbackRequest(req)` branch) says *"`reason` is the raw write error… for a document the caller identified only by documentId"* — after this fix `reason` from `saveDocumentToDisk` is never raw. Reword to state the scrub now happens at the source (`document-service.ts`) and this branch is retained as defence-in-depth for the day that changes, matching the pattern already used in `routes/rename.ts`'s own `#1294` comment.
- `routes/rename.ts`'s `#1294` comment (~L89-96) says *"two of `renameDocument`'s reasons are absolute-path-bearing"* — after this fix, neither is. Reword identically: `reason` is scrubbed at the source now; the loopback/non-loopback split here stays as defence-in-depth, not as the only layer.

**A matching implementation already sits uncommitted in this worktree** for the four catch sites and the client type, with tests (see below) — it does **not** yet correct the two stale `#1294` comments; that's the one gap between this spec and the existing draft. Verify the four catches, add the comment corrections, then commit.

The issue text cites `builtin.svelte.ts:425` as the render site; the actual leaking line (pre-fix) is `:457`, inside `triggerSave`'s `data?.status === "error"` branch — `:425` is the unrelated `!resp.ok` HTTP-error branch of the same function, whose `message` was never errno/path-bearing.
