# J2 — #1816 Save/rename failure toasts leak raw errno + absolute path on loopback

Branch `fix/product-copy-1814`. Closes #1816. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:22`. Probe: none (read-verified against source).

## Problem

`src/server/mcp/document-service.ts` builds save/save-as/rename failure `reason` and pushed-notification `message` strings directly from the raw Node error (`err.message`, e.g. `"EACCES: permission denied, open '/Users/…/file.md'"`) at **five** sites, not four — the original count missed one, and mislabeled two others (round-1 review; see corrections below):

1. `saveDocumentToDisk`'s catch (~L665-690, HEAD).
2. `saveDocumentAsToDisk`'s main catch (~L1041-1059).
3. `renameDocument`'s **`assertPathSafe` catch** (~L1201-1209, `errorCode: "PATH_REJECTED"`) — this is the actual "validation" catch; the original count skipped it entirely.
4. `renameDocument`'s **`fs.rename` catch** (~L1289-1332 — the one with the #1040 rollback logic and the `console.error("[Rename] fs.rename failed …")` log line).
5. `renameDocument`'s **outer/function-level catch** (~L1547-1573 — wraps the whole function body, including Phase-3 best-effort bookkeeping).

`src/client/actions/builtin.svelte.ts:425,457` renders `result.reason` verbatim in a toast. The scrub in `_shared.ts`'s `GENERIC_ERROR_MESSAGE` (`routes/save.ts:148`, `routes/rename.ts`'s `RENAME_GENERIC_MESSAGE`) applies only to **non-loopback** callers — every desktop user is loopback, so they see the errno text and the absolute path unconditionally. `errorCode` (the bare Node error code, e.g. `EACCES`) already exists on every one of these return-type interfaces (`document-service.ts:198,733,1124`) and already survives to the client (`routes/save.ts`'s `res.json({ data: result })` spreads `result` — `errorCode` is not stripped); only the free-text `reason`/`message` need scrubbing.

**Deliberately excluded**: `saveDocumentAsToDisk`'s own `assertPathSafe` catch (~L850-856, also `PATH_REJECTED`). `assertPathSafe` (`src/server/integrations/apply.ts:614-657`) throws one of two messages, and the "caller's own path" rationale holds fully for only one of them: the `symlink` variant's message embeds the caller-supplied `cursor` component, so it discloses nothing the caller didn't already type. The `outside-home` variant instead embeds `realpath=<resolved>` — a value `realpathSync` computed, not one the caller supplied — but the save-as call passes `allowedRoots: [path.parse(resolved).root]` (`document-service.ts:850`), i.e. the drive root, so that branch is unreachable on POSIX and reachable only on Windows via a cross-drive junctioned ancestor. It is left excluded anyway (a Windows-only-reachable realpath disclosure, not the common case) rather than folded into this pass's scope — `routes/save.ts`'s branch 3 (~L102-121) already echoes `result.reason` verbatim **unconditionally, with no loopback gate at all**, per the exemption comment at `routes/save.ts:145-147` ("Branches 2 and 3 are exempt: their paths are the caller's own `targetPath`"), and scrubbing the symlink case would hide information the caller already supplied to themselves.

## Fix

At each of the **five** catch sites in `document-service.ts` (enumerated above), stop deriving `reason`/`message` from `err.message`. Keep computing `errCode` (`(err as NodeJS.ErrnoException).code ?? "UNKNOWN"`) as today — it is the one technical detail allowed to travel — and log the raw `err` to `console.error` (stderr; Critical Rule 3) so operators can still diagnose. Replace the leaking strings:

- `saveDocumentToDisk` catch: `pushNotification` message → `` `Save failed for ${path.basename(docState.filePath)}.` `` (drop the `: ${msg}` suffix — the notification still names the FILE, not its path, which is fine, it's a basename); return `reason: "The document could not be saved."`, `errorCode: errCode`.
- `saveDocumentAsToDisk`'s main catch: same pattern, `reason: "The document could not be saved to that location."`.
- `renameDocument`'s **`assertPathSafe`/`PATH_REJECTED` catch** (~L1201-1209): `reason: "The destination path was rejected."`, `errorCode: "PATH_REJECTED"` (unchanged). Use this exact string, not a fresh generic one — `routes/rename.ts:35`'s `RENAME_GENERIC_MESSAGE.PATH_REJECTED` is already this sentence, and matching it means a loopback and a non-loopback caller now see the *same* wording for this errorCode instead of the loopback caller getting a vaguer message than the LAN one would (inverting the disclosure gradient the route was built around). This site was missed by the original count and is where `assertPathSafe`'s absolute-path-bearing messages (`"Refusing to operate on symlinked path: <abs>"`, `"Refusing path outside allowed roots: realpath=<abs>"` — `src/server/integrations/apply.ts:614-657`) actually leak; it is untouched in the current uncommitted draft.
- `renameDocument`'s `fs.rename` catch (~L1289-1332) and outer catch (~L1547-1573): same message, `errorCode: errCode`; `pushNotification` message drops its `: ${msg}` suffix too. **Already implemented correctly in the uncommitted draft** — verify against this spec rather than re-deriving.

`src/client/actions/builtin.svelte.ts`'s `triggerSave` result type (~L437-448) needs `errorCode?: string;` added alongside `reason?: string;` (it is not read there today). Render the detail as a parenthetical, not folded into the headline: `` `Save failed: ${result.reason ?? "The document could not be saved."}${result.errorCode ? ` (${result.errorCode})` : ""}` ``. **Already implemented correctly in the uncommitted draft.**

**The rename toast path needs the identical fix and is currently missing it entirely.** `src/client/hooks/yjsSync.svelte.ts`'s `!res.ok` handler (~L768-779) reads only `body.message` from `/api/rename`'s JSON response and passes it straight to `revert(message)`, which becomes the toast text — `routes/rename.ts:97-101` sends `{ error: result.errorCode ?? "INTERNAL", message: … }`, so the code is already on the wire and simply never read. Once all three `renameDocument` catches are scrubbed to generic `reason` strings above, an unread `error` field means every rename failure — `EXDEV`, `EPERM`, a rejected symlink target, `ENOENT` — collapses to one identical zero-information toast, which is strictly worse than today's leak for anyone trying to tell failures apart. Fix: change the parsed type to `{ message?: string; error?: string }` and append the code the same way `triggerSave` does: `` const detail = body.error ? ` (${body.error})` : ""; if (body?.message) message = `${body.message}${detail}`; ``.

**`tandem_save`'s MCP surface must not silently drop the errno either.** `src/server/mcp/document.ts:1270-1274` picks an mcp error kind (`FILE_LOCKED` vs `FORMAT_ERROR`) off `result.errorCode` but only forwards `result.reason` as the message — once `reason` is generic, an MCP caller (Claude) sees `"The document could not be saved."` with no code at all, which is a worse regression than the toast leak this PR fixes (Claude has no LAN-disclosure concern; dropping the code just makes it harder to react correctly, e.g. distinguish `EACCES` from `ENOSPC`). Append the code: change both call sites to `` mcpError("FORMAT_ERROR", `${result.reason ?? "Save failed"}${result.errorCode ? ` (${result.errorCode})` : ""}`) `` (and the `FILE_LOCKED` arm identically).

**Two stale comments this fix must also correct**, both citing the exact leak this PR closes as still-live rationale:
- `routes/save.ts`'s `#1294` comment (~L143-148, above the `!isLoopbackRequest(req)` branch) says *"`reason` is the raw write error… for a document the caller identified only by documentId"* — after this fix `reason` from `saveDocumentToDisk` is never raw (this branch only ever wraps `saveDocumentToDisk`, which has no `assertPathSafe` call and thus no excluded site). Reword to state the scrub now happens at the source (`document-service.ts`) and this branch is retained as defence-in-depth for the day that changes, matching the pattern already used in `routes/rename.ts`'s own `#1294` comment.
- `routes/rename.ts`'s `#1294` comment (~L89-96) says *"two of `renameDocument`'s reasons are absolute-path-bearing"*, naming `assertPathSafe`'s symlink message and a failed `fs.rename`'s dual-path message as the two producers. **With site 3 above fixed, this becomes literally true** — neither producer's message reaches the caller raw any more. Reword to: `reason` is scrubbed at the source now (`document-service.ts`, all three of `renameDocument`'s catches); the loopback/non-loopback split here stays as defence-in-depth, not as the only layer. Do not describe it as "neither is [path-bearing]" until the `PATH_REJECTED` site is actually fixed — the wording must match the code, not aspire to it.

**A matching implementation already sits uncommitted in this worktree** for `saveDocumentToDisk`'s catch, `saveDocumentAsToDisk`'s main catch, `renameDocument`'s `fs.rename` catch, `renameDocument`'s outer catch, and the client type/render — with tests (see below). It does **not** yet fix `renameDocument`'s `assertPathSafe`/`PATH_REJECTED` catch (~L1201), does **not** yet append the errno to `tandem_save`'s mcp error messages, and does **not** yet correct the two stale `#1294` comments. Verify the four already-fixed sites against this spec, add the fifth (`PATH_REJECTED`), the `document.ts` mcp-error fix, and the comment corrections, then commit.

## Tests

`tests/server/document-service.test.ts`: for `saveDocumentToDisk` and `saveDocumentAsToDisk`, mock `atomicWrite` to reject with `Object.assign(new Error("EACCES: permission denied, open '/tmp/secret-project.md'"), { code: "EACCES" })`; assert `result.reason` is the exact new generic string and `result.errorCode === "EACCES"`. **Capture the specific `pushNotification` call rather than using `toHaveBeenCalledWith`**: `toHaveBeenCalledWith` passes if *any* recorded call matches, and `saveDocumentToDisk` has a second `pushNotification` site in the same function (the `session-save-failed` path, ~L650-661) — an any-call assertion can pass on the strength of that unrelated call even if the save-error one leaks. Instead: `` const call = vi.mocked(pushNotification).mock.calls.map(c => c[0]).find(n => n.type === "save-error"); expect(call).toBeDefined(); expect(call!.message).not.toContain(target); expect(call!.message).not.toContain("EACCES"); `` (kills a fix that scrubs one of `reason`/the captured `save-error` notification's `message` but not both, or scrubs the message but leaves the path in via `docState.filePath` interpolation elsewhere).

`tests/server/rename-document.test.ts`: delete the target file out from under an open doc so `fs.rename` throws `ENOENT` carrying both paths; assert the same `reason`/`errorCode` properties on `renameDocument`'s result. **Add a fourth case in the same file, using a mock rather than a real symlink**: a real filesystem symlink is not a viable CI instrument here — `fs.symlink` on Windows needs Developer Mode or elevation, `check` is ubuntu-only while the pre-push hook runs the full suite on Windows, and `tests/server/rename-document.test.ts` currently mocks only `session/manager.js`, `file-watcher.js` and `notifications.js`, with no `apply.js` mock to extend. Add one: `let pathSafeThrows: Error | null = null;` at module scope, `vi.mock("../../src/server/integrations/apply.js", async (importOriginal) => ({ ...(await importOriginal<object>()), assertPathSafe: (...args: unknown[]) => { if (pathSafeThrows) throw pathSafeThrows; } }))`, reset `pathSafeThrows = null` in `beforeEach`. In the new case, set `pathSafeThrows = new Error("Refusing to operate on symlinked path: /abs/target.md")` before calling `renameDocument`, then assert `result.errorCode === "PATH_REJECTED"`, `result.reason === "The destination path was rejected."` exactly, and `result.reason` contains neither `"Refusing"` nor the absolute path (kills exactly the gap this round of review found — a fix that scrubs the other two `renameDocument` catches but leaves this one raw).

In `tests/server/document-tools.test.ts` (the actual home of `tandem_save`'s handler coverage — not `document.test.ts`, which does not exist in this repo), add a case asserting a save failure's mcp error message contains the `errorCode` (e.g. ends with `(EACCES)`), not just the generic sentence.

**Client-side rename toast** (new coverage for the gap found in round 2): a test exercising `yjsSync.svelte.ts`'s rename `!res.ok` handler (or the nearest existing suite that drives it) asserts that when `/api/rename` returns `{ error: "PATH_REJECTED", message: "The destination path was rejected." }`, the resulting toast/`onError` text ends with `(PATH_REJECTED)` — mirroring the `tandem_save` case above, and pinning that the code survives the client hop the same way `triggerSave`'s save-failure toast already does.

**Two existing test docblocks assert the pre-fix rationale and must be corrected alongside the source comments**, or they read as documentation of a leak this PR just closed: `tests/server/rename-route.test.ts:136-140`'s comment claims `renameDocument`'s `reason` "can carry an absolute path" — reword to say the raw reason is now injected only by the mock (`saveDocumentToDisk`/`renameDocument` are mocked in this file) and is no longer producible by the real service; the case itself (a positive control asserting a loopback caller still gets whatever `reason` the mock returns, `tests/server/rename-route.test.ts:160-171`) is a defence-in-depth pin on the route, not evidence of a real leak, and **must be kept, not deleted** — it is what keeps the non-loopback case above it (`:150-158`) discriminating; only its comment needs correcting. Likewise `tests/server/routes/response-path-scrub.test.ts:125-145`'s two "still returns/gives the raw reason to a loopback caller" cases inject `RAW` via a mocked `saveDocumentToDisk`/`renameDocument` — reword their names/comments to state they pin the route's defence-in-depth branch for the day `document-service.ts` stops guaranteeing a generic reason, not that a raw reason is reachable today.

## Not in scope

The native Save-As dialog's own error path (`builtin.svelte.ts` ~L302-330, `runNativeSaveAs`'s `!res.ok` branch) needs no client change — `routes/save.ts` branch 3 echoes `result.reason` unconditionally (generic for the main-catch case, intentionally raw for the caller-supplied-path case) as `message`, and the branch's `json?.data?.reason` read at ~L328 is dead code (that branch never reaches `res.json({ data: result })` on error); adding an `(errorCode)` detail suffix to match `triggerSave`'s new toast would be a consistency nicety, not a leak fix, and is left alone. The issue text cites `builtin.svelte.ts:425` as the render site; the actual leaking line (pre-fix) is `:457`, inside `triggerSave`'s `data?.status === "error"` branch — `:425` is the unrelated `!resp.ok` HTTP-error branch of the same function, whose `message` was never errno/path-bearing.
