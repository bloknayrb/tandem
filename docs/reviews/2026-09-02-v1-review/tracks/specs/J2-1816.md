# J2 — #1816 Save/rename failure toasts leak raw errno + absolute path on loopback

Branch `fix/product-copy-1814`. Closes #1816. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:22`. Probe: none (read-verified against source).

## Problem

`src/server/mcp/document-service.ts` builds save/save-as/rename failure `reason` and pushed-notification `message` strings directly from the raw Node error (`err.message`, e.g. `"EACCES: permission denied, open '/Users/…/file.md'"`) at **five** sites, not four — the original count missed one, and mislabeled two others (round-1 review; see corrections below):

1. `saveDocumentToDisk`'s catch (~L665-690, HEAD).
2. `saveDocumentAsToDisk`'s main catch (~L1041-1059).
3. `renameDocument`'s **`assertPathSafe` catch** (~L1201-1209, `errorCode: "PATH_REJECTED"`) — this is the actual "validation" catch; the original count skipped it entirely.
4. `renameDocument`'s **`fs.rename` catch** (~L1289-1332 — the one with the #1040 rollback logic and the `console.error("[Rename] fs.rename failed …")` log line).
5. `renameDocument`'s **outer/function-level catch** (~L1547-1573 — wraps the whole function body, including Phase-3 best-effort bookkeeping).

`src/client/actions/builtin.svelte.ts:425,457` renders `result.reason` verbatim in a toast. The scrub in `_shared.ts`'s `GENERIC_ERROR_MESSAGE` (`routes/save.ts:148`, `routes/rename.ts`'s `RENAME_GENERIC_MESSAGE`) applies only to **non-loopback** callers — every desktop user is loopback, so they see the errno text and the absolute path unconditionally. `errorCode` (the bare Node error code, e.g. `EACCES`) already exists on every one of these return-type interfaces (`document-service.ts:198,733,1124`) and already survives to the client (`routes/save.ts`'s `res.json({ data: result })` spreads `result` — `errorCode` is not stripped); only the free-text `reason`/`message` need scrubbing.

**Deliberately excluded**: `saveDocumentAsToDisk`'s own `assertPathSafe` catch (~L850-856, also `PATH_REJECTED`). Its `targetPath` is the *caller's own* path — passed from the native Save-As dialog or the browser's serialize-only fallback — and `routes/save.ts`'s branch 3 (~L102-121) already echoes `result.reason` verbatim **unconditionally, with no loopback gate at all**, per the exemption comment at `routes/save.ts:145-147` ("Branches 2 and 3 are exempt: their paths are the caller's own `targetPath`"). Scrubbing it would hide information the caller already supplied to themselves.

## Fix

At each of the **five** catch sites in `document-service.ts` (enumerated above), stop deriving `reason`/`message` from `err.message`. Keep computing `errCode` (`(err as NodeJS.ErrnoException).code ?? "UNKNOWN"`) as today — it is the one technical detail allowed to travel — and log the raw `err` to `console.error` (stderr; Critical Rule 3) so operators can still diagnose. Replace the leaking strings:

- `saveDocumentToDisk` catch: `pushNotification` message → `` `Save failed for ${path.basename(docState.filePath)}.` `` (drop the `: ${msg}` suffix — the notification still names the FILE, not its path, which is fine, it's a basename); return `reason: "The document could not be saved."`, `errorCode: errCode`.
- `saveDocumentAsToDisk`'s main catch: same pattern, `reason: "The document could not be saved to that location."`.
- `renameDocument`'s **`assertPathSafe`/`PATH_REJECTED` catch** (~L1201-1209): `reason: "The document could not be renamed."`, `errorCode: "PATH_REJECTED"` (unchanged). This site was missed by the original count and is where `assertPathSafe`'s absolute-path-bearing messages (`"Refusing to operate on symlinked path: <abs>"`, `"Refusing path outside allowed roots: realpath=<abs>"` — `src/server/integrations/apply.ts:614-657`) actually leak; it is untouched in the current uncommitted draft.
- `renameDocument`'s `fs.rename` catch (~L1289-1332) and outer catch (~L1547-1573): same message, `errorCode: errCode`; `pushNotification` message drops its `: ${msg}` suffix too. **Already implemented correctly in the uncommitted draft** — verify against this spec rather than re-deriving.

`src/client/actions/builtin.svelte.ts`'s `triggerSave` result type (~L437-448) needs `errorCode?: string;` added alongside `reason?: string;` (it is not read there today). Render the detail as a parenthetical, not folded into the headline: `` `Save failed: ${result.reason ?? "The document could not be saved."}${result.errorCode ? ` (${result.errorCode})` : ""}` ``. **Already implemented correctly in the uncommitted draft.**

**`tandem_save`'s MCP surface must not silently drop the errno either.** `src/server/mcp/document.ts:1270-1274` picks an mcp error kind (`FILE_LOCKED` vs `FORMAT_ERROR`) off `result.errorCode` but only forwards `result.reason` as the message — once `reason` is generic, an MCP caller (Claude) sees `"The document could not be saved."` with no code at all, which is a worse regression than the toast leak this PR fixes (Claude has no LAN-disclosure concern; dropping the code just makes it harder to react correctly, e.g. distinguish `EACCES` from `ENOSPC`). Append the code: change both call sites to `` mcpError("FORMAT_ERROR", `${result.reason ?? "Save failed"}${result.errorCode ? ` (${result.errorCode})` : ""}`) `` (and the `FILE_LOCKED` arm identically).

**Two stale comments this fix must also correct**, both citing the exact leak this PR closes as still-live rationale:
- `routes/save.ts`'s `#1294` comment (~L143-148, above the `!isLoopbackRequest(req)` branch) says *"`reason` is the raw write error… for a document the caller identified only by documentId"* — after this fix `reason` from `saveDocumentToDisk` is never raw (this branch only ever wraps `saveDocumentToDisk`, which has no `assertPathSafe` call and thus no excluded site). Reword to state the scrub now happens at the source (`document-service.ts`) and this branch is retained as defence-in-depth for the day that changes, matching the pattern already used in `routes/rename.ts`'s own `#1294` comment.
- `routes/rename.ts`'s `#1294` comment (~L89-96) says *"two of `renameDocument`'s reasons are absolute-path-bearing"*, naming `assertPathSafe`'s symlink message and a failed `fs.rename`'s dual-path message as the two producers. **With site 3 above fixed, this becomes literally true** — neither producer's message reaches the caller raw any more. Reword to: `reason` is scrubbed at the source now (`document-service.ts`, all three of `renameDocument`'s catches); the loopback/non-loopback split here stays as defence-in-depth, not as the only layer. Do not describe it as "neither is [path-bearing]" until the `PATH_REJECTED` site is actually fixed — the wording must match the code, not aspire to it.

**A matching implementation already sits uncommitted in this worktree** for `saveDocumentToDisk`'s catch, `saveDocumentAsToDisk`'s main catch, `renameDocument`'s `fs.rename` catch, `renameDocument`'s outer catch, and the client type/render — with tests (see below). It does **not** yet fix `renameDocument`'s `assertPathSafe`/`PATH_REJECTED` catch (~L1201), does **not** yet append the errno to `tandem_save`'s mcp error messages, and does **not** yet correct the two stale `#1294` comments. Verify the four already-fixed sites against this spec, add the fifth (`PATH_REJECTED`), the `document.ts` mcp-error fix, and the comment corrections, then commit.

## Not in scope

The non-loopback `GENERIC_ERROR_MESSAGE`/`RENAME_GENERIC_MESSAGE` maps themselves (already correct, now largely redundant with the source-level fix but harmless to keep as the second layer); `saveDocumentAsToDisk`'s **own** `assertPathSafe`/`PATH_REJECTED` catch (~L850-856) — deliberately left raw, see Problem's "Deliberately excluded"; `EBUSY`/`ENOSPC`-specific remediation copy (Save As / Retry / Show in folder) — the issue's stretch suggestion, not requested by the wave-table note, which asks only for the generic-message-on-loopback fix. The native Save-As dialog's own error path (`builtin.svelte.ts` ~L302-330, `runNativeSaveAs`'s `!res.ok` branch) needs no client change — `routes/save.ts` branch 3 echoes `result.reason` unconditionally (generic for the main-catch case, intentionally raw for the caller-supplied-path case) as `message`, and the branch's `json?.data?.reason` read at ~L328 is dead code (that branch never reaches `res.json({ data: result })` on error); adding an `(errorCode)` detail suffix to match `triggerSave`'s new toast would be a consistency nicety, not a leak fix, and is left alone. The issue text cites `builtin.svelte.ts:425` as the render site; the actual leaking line (pre-fix) is `:457`, inside `triggerSave`'s `data?.status === "error"` branch — `:425` is the unrelated `!resp.ok` HTTP-error branch of the same function, whose `message` was never errno/path-bearing.
