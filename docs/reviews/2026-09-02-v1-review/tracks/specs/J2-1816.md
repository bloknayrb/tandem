# J2 — #1816 Save/rename failure toasts leak raw errno + absolute path on loopback

Branch `fix/product-copy-1814`. Closes #1816. Ledger row: `docs/reviews/2026-09-02-v1-review/areas/product.md:22`. Probe: none (read-verified against source).

## Problem

`src/server/mcp/document-service.ts` builds save/save-as/rename failure `reason`/`message` strings directly from the raw Node error (`err.message`, e.g. `"EACCES: permission denied, open '/Users/…/file.md'"`) at five catch sites:

1. `saveDocumentToDisk`'s catch (~L665-690).
2. `saveDocumentAsToDisk`'s main catch (~L1041-1059).
3. `renameDocument`'s `assertPathSafe`/`PATH_REJECTED` catch (~L1201-1209) — this is where `assertPathSafe`'s absolute-path-bearing messages (`src/server/integrations/apply.ts:614-657`) actually leak.
4. `renameDocument`'s `fs.rename` catch (~L1289-1332, the #1040 rollback logic).
5. `renameDocument`'s outer/function-level catch (~L1547-1573).

`src/client/actions/builtin.svelte.ts` renders `result.reason` verbatim in a toast. The non-loopback scrub (`routes/save.ts`'s inline generic, `routes/rename.ts`'s `RENAME_GENERIC_MESSAGE`) applies only to non-loopback callers — every desktop user is loopback, so they see the errno text and the absolute path unconditionally. `errorCode` already exists on every one of these return types and already survives to the client; only the free-text `reason`/`message` need scrubbing.

**Deliberately excluded**: `saveDocumentAsToDisk`'s own `assertPathSafe`/`PATH_REJECTED` catch (~L850-856) — `routes/save.ts`'s branch 3 already echoes `result.reason` verbatim, unconditionally, as the caller's own `targetPath` (exemption comment at `routes/save.ts:145-147`); scrubbing it would hide information the caller already supplied to themselves.

## Fix

At each of the five catch sites, stop deriving `reason`/`message` from `err.message`. Keep computing `errCode` (`(err as NodeJS.ErrnoException).code ?? "UNKNOWN"`) and log the raw `err` to `console.error` (stderr; Critical Rule 3):

- `saveDocumentToDisk` catch: `reason: "The save failed."` (matches `routes/save.ts:149`'s existing non-loopback generic exactly); `pushNotification` message → `` `Save failed for ${path.basename(docState.filePath)}.` `` (no errno text — `errorCode: errCode` is the structured field that carries it).
- `saveDocumentAsToDisk`'s main catch: `reason: "The document could not be saved to that location."`; same `pushNotification` pattern.
- `renameDocument`'s `PATH_REJECTED` catch: `reason: "The destination path was rejected."` — matches `routes/rename.ts:35`'s `RENAME_GENERIC_MESSAGE.PATH_REJECTED` exactly, so loopback and non-loopback callers see the same wording for this code.
- `renameDocument`'s `fs.rename` catch and outer catch: same generic pattern; `pushNotification` message drops its `: ${msg}` suffix, with no errno replacement — `errorCode` alone carries it.

`src/client/actions/builtin.svelte.ts`'s `triggerSave` result type needs `errorCode?: string;` added alongside `reason?: string;`. Render as a parenthetical: `` `Save failed: ${result.reason ?? "The document could not be saved."}${result.errorCode ? ` (${result.errorCode})` : ""}` ``.

**Native Save-As dialog** (`builtin.svelte.ts`'s `runNativeSaveAs`, ~L302-330): its `!res.ok` branch reads only `body.message` today. Change the parsed type to `{ message?: string; error?: string }` and append the code the same way `triggerSave` does: `` const detail = body.error ? ` (${body.error})` : ""; notify("error", `Save As failed: ${body.message ?? res.statusText}${detail}`); ``. Without this, scrubbing `saveDocumentAsToDisk`'s catch turns this toast into a zero-information sentence — the one-line client fix is in scope for the same reason the server scrub is.

**Client-side rename toast** (`src/client/hooks/yjsSync.svelte.ts`'s `handleTabRename`, `!res.ok` branch, ~L768-779): reads only `body.message` from `/api/rename`'s JSON response today. `routes/rename.ts:97-101` already sends `{ error: result.errorCode ?? "INTERNAL", message: … }`, so the code is on the wire and simply unread. Change the callback inline (no extraction) to:

```ts
const body = (await res.json().catch(() => ({}))) as { message?: string; error?: string };
const base = body.message ? body.message : `Rename failed (${res.status}).`;
revert(body.error ? `${base} (${body.error})` : base);
```

This is a three-line inline change next to code that already does the fetch; **it is not covered by a dedicated unit test** — nothing in `tests/` calls `createYjsSync`, and `handleTabRename` short-circuits (`if (!target) return;`) without a live tab that only a Hocuspocus bootstrap populates. Verify by code inspection at review time rather than adding a new exported helper and module-extraction machinery just to make it independently testable.

**Two stale comments** cite the exact leak this PR closes as still-live rationale — reword both once the source is fixed:
- `routes/save.ts`'s `#1294` comment (~L143-148): after this fix `reason` from `saveDocumentToDisk` is never raw; reword to say the scrub now happens at the source and this branch is retained as defence-in-depth.
- `routes/rename.ts`'s `#1294` comment (~L89-96): with the `PATH_REJECTED` site fixed, neither producer's message reaches the caller raw any more; reword to say the scrub is at the source now and the loopback/non-loopback split here is defence-in-depth.

A matching implementation sits partly uncommitted in this worktree — verify each catch site's exact string, the `pushNotification` errno suffix, and the native Save-As dialog change against this spec before committing.

Two findings from a post-cut review, both adopted directly:

- **`tandem_save`'s MCP error detail restored to scope.** The prior scope cut moved appending errno to `document.ts`'s two `mcpError(...)` calls to Not-in-scope, reasoning it needed a new MCP tool-harness test. - **Fix/Tests/Done-when contradiction on the `pushNotification` message resolved.** Fix and Done-when required a `` (${errCode}) `` parenthetical on the `saveDocumentToDisk`/rename `pushNotification` messages; Tests required asserting those same messages contain neither the target path nor the errno text (e.g. `"EACCES"`) — for `errCode = "EACCES"` those two requirements are mutually exclusive. Resolved by dropping the parenthetical: `pushNotification` messages carry no errno text at all, and `errorCode` (already a separate structured field on every one of these call sites) is the sole carrier. `triggerSave`'s client-rendered `(${result.errorCode})` suffix is a distinct, correctly-specified layer and is unaffected.

Both corrections match the implementation already in the worktree — `document-service.ts`'s five catch sites and `document-service.test.ts`'s EACCES case already reflect the no-parenthetical shape; only `document.ts`'s `mcpError` calls needed a source change.
