# G1 — #1867 An alive-but-not-reading child swallows a wake with no error; recovery waits 10 minutes

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Closes #1867. Ledger: none. This is a #1757 follow-up, tracked in the sweep's G1 row. The ledger flags the choice of delivery proof as the open question, and this spec settles it by measurement. Probe: `scratchpad/probe-loggedout.cjs`, which runs the real `claude` 2.1.272 under the supervisor's exact `CLAUDE_STREAM_JSON_FLAGS` with stdin held open, plus the recorded spike `docs/spikes/channel-push-stream-json.md` (2026-08-04, Windows 11).

## Problem

`sendTurn` sets `turnInFlight = true` and arms the latch (`WAKE_LATCH_MAX_MS`, 10 min) *before* `stdin.write`. Only a `result` envelope or the latch clears it. A child that is alive but has stopped reading stdin accepts a small write into the OS pipe buffer. Neither the write callback nor the stream's `'error'` fires, so #1757's recovery never runs, and every later event coalesces behind the latch. The user's comment goes unanswered for up to 10 minutes and nothing reports why.

## What the protocol offers (measured, not assumed)

- **`system/init` is emitted per turn, as soon as the CLI has read that turn.** Spike (2026-08-04): `init` came 0.87 s after a write that had been held for 45 s, so it tracks the turn rather than startup. It was re-emitted for the second turn. Probe (2026-09-15, 2.1.272, Windows): turn 1 got `init` at +2.39 s, turn 2 got `init` at +0.03 s.
- **A child that is not reading emits nothing for that turn.** The spike found no stdout at all before a turn is received, and the supervisor's own comments already rely on that deadlock finding.
- **A thinking child has already emitted `init`.** A long turn produces `init` within seconds and then goes quiet until its assistant or `result` lines.

So "any stdout envelope since the write" separates *not reading* from *thinking*, as far as the protocol allows. It is a **receipt** signal, and deliberately not a completion timeout. `init` specifically would be the tighter match, but keying on any parsed envelope is chosen so the check **fails soft**. A future CLI that stopped re-emitting `init` would still produce other lines, and the worst case is today's 10-minute latch, not a kill loop. Unsolicited output from a child that has stopped reading would count as receipt, and that too falls back to today's behaviour.

Windows risk checked: #1869 argues from the source that the Windows reaper does not forward stdin. If so, a receipt timer would kill every Windows session. A probe (`scratchpad/probe-reaper-stdin.cjs`) against the **installed v0.25.0** `tandem-reaper.exe` and the repo's built one found that the child's fd 0 is a pipe, a written line arrives within 1 ms, and the echo comes back on stdout. The condition was a nested job, run from this session. That is not a verdict on #1869, which stays open and out of this group.

## Fix

`src/server/launcher/supervisor.ts`:

- Module constant `const TURN_RECEIPT_MS = 120_000;`. Its docblock cites the measured figures and says the bound covers the *first* turn's startup (hooks and MCP connects: 12.7 s in the spike), which is the slowest `init` observed. `SupervisorOpts` gains `turnReceiptMs?: number`, a test seam with the same justification text as `wakeLatchMs`.
- In `spawnOnce`, a per-spawn `let receiptTimer: NodeJS.Timeout | null = null;`. `clearLatch()` also clears it, so teardown and the failed-write callback cover it for free.
- `sendTurn`: after `stdin.write(...)`, arm `receiptTimer = setTimeout(onNoReceipt, turnReceiptMs)`, replacing any existing one.
- `handleStdoutLine`: immediately after a successful `JSON.parse`, `if (receiptTimer) { clearTimeout(receiptTimer); receiptTimer = null; }`. Lines that don't start with `{` and non-JSON lines don't count. A result also clears it via `clearLatch()`.
- `function onNoReceipt()`:
  - `receiptTimer = null;`
  - log `[Launcher] No turn receipt within ${turnReceiptMs}ms — Claude is alive but not reading its input; ending the session so the wake is retried`
  - `clearLatch(); pendingWake = true;`
  - `onStdinGone(RECEIPT_TIMEOUT)`.

  `RECEIPT_TIMEOUT` is a module-level `Object.assign(new Error("no turn receipt"), { code: "ETURNRECEIPT" })`. The handler ignores its argument. That reuses its identity and liveness guards, and, with G1-1868, `markDeliveryKill`, so a stalled child counts toward the `wake-delivery-failed` streak like a stdin error does. The owed wake crosses the kill via `teardownTurnDelivery`'s promotion (G1-1866), and a resumed successor gets exactly one wake.
- Coalescing is unchanged. While `turnInFlight` stays true, events only set `pendingWake`, so there is never more than one unacknowledged write per spawn. No queue exists to grow.
- The bound is **120 s, well below 10 min**. That is a policy value (see `assumptions`). A turn that emitted `init` is never ended by this timer, however long it runs. The 10-minute latch still covers a turn that was received but never returns a `result`.

CLAUDE.md rules that bite: Critical Rule 3 (logs only via `console.error`). The source-order pin on the `onStdinGone` binding (see G1-1868) must stay adjacent and above the bootstrap write, and `onNoReceipt` is declared after the binding, inside `spawnOnce`.

## Tests

`tests/server/launcher/supervisor-turn-delivery.test.ts` (mocked `spawn` harness, see G1-1866), with `turnReceiptMs: 200`:

1. **Not reading → ended promptly, one wake carried.** Child 1 gets a `result` for the bootstrap turn. Emit an event, and the write callback succeeds with no stdout. After ~200 ms the `kill` spy is called with `SIGTERM`, and the log contains `No turn receipt within`. The restart resumes as child 2, whose writes are exactly `[SUPERVISOR_WAKE_PROMPT]`. *Kills* no timer at all (the test times out well under the latch), and a timer that skips re-arming the wake (child 2 gets zero writes).
2. **Long turn not ended.** The wake is written and child 1 pushes `{"type":"system","subtype":"init"}` at +50 ms, then nothing for 1 s (5× the receipt bound, under an injected `wakeLatchMs: 5000`). `kill` is not called. *Kills* a timer that `result` clears instead of receipt, which is the "arbitrary response timeout" the issue forbids.
3. **Coalesced during the stall.** Five events inside the 200 ms window → child 1 has exactly one wake write before the kill. *Kills* a retry-per-event or queued design.
4. **Non-JSON noise is not receipt.** Child pushes `banner text\n` only → still ended. *Kills* keying on raw stdout bytes.

Mutation plan: move the receipt clear into the `result` branch → 2 red. Drop `pendingWake = true` in `onNoReceipt` → 1 red. Remove the arm in `sendTurn` → 1 red. Restore from a file copy.
