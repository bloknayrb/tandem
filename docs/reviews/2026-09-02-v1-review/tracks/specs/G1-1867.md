# G1 — #1867 An alive-but-not-reading child swallows a wake with no error

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Follow-up to #1757, tracked in the sweep's G1 row. Provisionally closes #1867; derive the `## Closes` list at the end (rule 1). Base: `origin/master` (`c1a4df93`). Anchors re-read on `c1a4df93`.

Files: `src/server/launcher/supervisor.ts` and the shared test file.

## Problem

`sendTurn` (:1055) sets `turnInFlight` and arms the 10-minute latch (`WAKE_LATCH_MAX_MS`, :152) before `stdin.write`. Only a `result` envelope or the latch clears it. A child that is alive but has stopped reading still accepts a small write into the pipe buffer. Neither the callback nor `'error'` fires, so #1757's recovery never runs. Every later event then coalesces behind the latch for up to 10 minutes.

## What the protocol offers (measured)

- **The CLI emits `system/init` once per turn, promptly after it reads a turn written to an idle session.** Spike `docs/spikes/channel-push-stream-json.md` (2026-08-04): `init` arrived 0.87 s after a write that had been held back for 45 s, and it was emitted again for turn 2. The slowest first turn measured was 12.7 s. Probe on 2026-09-15 (claude 2.1.272, Windows, isolated empty config dir): turn 2's `init` came +0.03 s after its write; a resumed session's came +0.10 s after its first write.
- **A child that has not read a turn emits nothing.** The spike saw no stdout before a turn. On 2026-09-15 a resumed session stayed silent for 10 s with stdin open and nothing written.
- **Not measured:** whether `init` is emitted for a turn written while an earlier turn is still running.

So receipt of any JSON envelope after a write to a known-idle child separates *not reading* from *thinking*, as far as the protocol allows. This is a receipt check, not a completion timeout. Any parsed envelope counts, not only `init`, so the check fails soft: a future CLI that stops re-emitting `init` falls back to today's latch rather than a kill loop.

One finding bears on #1869. Its source reading says the Windows reaper does not forward stdin. On 2026-09-15, under a nested job, the installed v0.25.0 `tandem-reaper.exe` delivered a written line to the child within 1 ms. That is one condition only. It is not a verdict on #1869, which stays open and outside this group.

## Fix (`supervisor.ts`)

- **Bound.** Add `const TURN_RECEIPT_MS = 180_000;`. Its docblock records the figures above, notes that `init` for a large resumed conversation was not measured, and marks the value as policy (see For Bryan). `SupervisorOpts` gains `turnReceiptMs?: number`, a test seam justified the same way as `wakeLatchMs`.
- **Per-spawn state.**
  - `let receiptTimer: NodeJS.Timeout | null = null;`
  - `let unresolvedTurn = false;`, which is true once a turn is written on this spawn and until a `result` arrives.
  - `clearLatch()` also clears `receiptTimer`, so teardown and the failed-write callback cover it.
- **`sendTurn`.** Before the write, `const receiptCheckable = !unresolvedTurn; unresolvedTurn = true;`. After the write, `if (receiptCheckable) receiptTimer = setTimeout(onNoReceipt, turnReceiptMs)`. Because `turnInFlight` blocks writes until a `result`, the only write that finds `unresolvedTurn` true is the latch-expiry flush (`flushPendingWake` after the latch fired with no `result`). The earlier turn may still be running a silent tool call at that point, so that write keeps today's behaviour: no receipt timer. A spawn's first write (bootstrap, owed wake, or G1-1780's login re-check) goes to an idle child and is checked.
- **`handleStdoutLine`.**
  - Right after a successful `JSON.parse`: `if (receiptTimer) { clearTimeout(receiptTimer); receiptTimer = null; }`. Non-`{` lines and `{`-prefixed non-JSON lines do not count.
  - In the `result` branch: `unresolvedTurn = false`.
- **`onNoReceipt()`.**
  - Sets `receiptTimer = null`.
  - Logs ``[Launcher] No turn receipt within ${turnReceiptMs}ms — Claude is alive but not reading its input; ending the session so the wake is retried``. This log line is the recovery reason criterion 6 asks for.
  - Runs `clearLatch(); pendingWake = true;` and then `onStdinGone(RECEIPT_TIMEOUT)`.
  - `RECEIPT_TIMEOUT` is a module-level `Object.assign(new Error("no turn receipt"), { code: "ETURNRECEIPT" })`.
  - Going through `onStdinGone` reuses the handler's identity and liveness guards and, with G1-1868, counts toward the `wake-delivery-failed` streak. A child that never reads is killed once per bound, which evades the windowed breaker, so it needs the streak.
  - The owed wake crosses the kill through teardown's promotion (G1-1866).
- **Coalescing is unchanged.** While `turnInFlight` is true, events only set `pendingWake`, so each spawn has at most one unacknowledged write and no queue.
- **macOS.** The receipt kill SIGTERMs the reaper, which can orphan Claude on macOS. That is #1994, filed in round 1 and owned by K-sec-launcher. The PR body must say this.

Critical Rule 3: `console.error` only. `onNoReceipt` is declared after the `onStdinGone` binding, which keeps G1-1868's source-order pin intact.

## Tests (shared file, G1-1866 harness, `turnReceiptMs: 200`)

1. **A child that is not reading is ended and one wake is carried.**
   - Child 1 pushes `init` + `result` for the bootstrap turn.
   - An event produces W1, whose callback succeeds (`cb()`). Child 1 then stays silent.
   - Within ~400 ms, `kill("SIGTERM")` has been called and the log contains `No turn receipt within`.
   - Child 2 resumes and its writes are exactly `[SUPERVISOR_WAKE_PROMPT]`. It pushes `init` and is not killed over the next 400 ms.

   *Kills:* having no timer at all, and a timer that does not re-arm the wake.
2. **A long turn is not ended.** Use `wakeLatchMs: 5000`. W1 is written, child 1 pushes `init` at +50 ms and then nothing for 1 s. `kill` is not called. *Kills* a timer that is cleared by `result` instead of receipt.
3. **Events are coalesced during the stall.** Five events arrive inside the 200 ms window. Child 1's writes are exactly `[B, WAKE]` before the kill.
4. **Noise is not receipt.** Child 1 pushes only `banner text\n` and `{not json\n`. It is still ended.
5. **The flush after latch expiry is not receipt-checked.** Use `wakeLatchMs: 300`.
   - Child 1 pushes `init` for the bootstrap turn and never a `result`.
   - An event arrives during that turn. At ~300 ms the latch fires and writes `WAKE`.
   - Nothing follows for 1 s. `kill` is not called, and the writes are exactly `[B, WAKE]`.

   *Kills* arming the timer on every write.

## For Bryan (policy, not blocking the merge)

`TURN_RECEIPT_MS` ships at **180 s**. The trade-off: a machine whose first-turn `init` is slower than the bound on three consecutive spawns trips `wake-delivery-failed` after about 9 min.

- **(a) 180 s** (shipped). About 14× the slowest measured first turn.
- **(b) 120 s.** Faster recovery, but a thinner margin for slow hooks, MCP connects or a large `--resume`.
- **(c) A longer bound for a spawn's first write only** (e.g. 5 min), and 120 s after that. Costs a second constant.
