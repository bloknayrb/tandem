# G1 — #1867 An alive-but-not-reading child swallows a wake with no error; recovery waits 10 minutes

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Closes #1867. Ledger: none. This is a #1757 follow-up, tracked in the sweep's G1 row. The ledger flags the choice of delivery proof as the open question. This spec settles what the protocol offers by measurement, and puts the numeric bound in front of Bryan as policy. Probes: `probe-loggedout.cjs` and, in round 1, `probe-resume-mcp.cjs` (session scratchpad, not tracked; their outputs are quoted below and in G1-1780). Both ran the real `claude` 2.1.272 under the supervisor's exact `CLAUDE_STREAM_JSON_FLAGS` with stdin held open, alongside the recorded spike `docs/spikes/channel-push-stream-json.md` (2026-08-04, Windows 11). Base: rebase onto `origin/master`.

## Problem

`sendTurn` sets `turnInFlight = true` and arms the latch (`WAKE_LATCH_MAX_MS`, 10 min) *before* `stdin.write`. Only a `result` envelope or the latch clears it. A child that is alive but has stopped reading stdin accepts a small write into the OS pipe buffer. Neither the write callback nor the stream's `'error'` fires, so #1757's recovery never runs, and every later event coalesces behind the latch. The user's comment goes unanswered for up to 10 minutes and nothing reports why.

## What the protocol offers (measured, not assumed)

- **`system/init` is emitted per turn, promptly after the CLI reads a turn written to an idle session.** Spike (2026-08-04): `init` came 0.87 s after a write that had been held for 45 s, so it tracks the turn rather than startup, and it was re-emitted for the second turn. Probe (2026-09-15, 2.1.272, Windows): turn 1 `init` at +2.39 s, turn 2 `init` +0.03 s after its write. A resumed session: `init` +0.10 s after the first write.
- **A child that is not reading emits nothing for that turn.** The spike found no stdout at all before a turn is received. Round 1 confirmed it for a resumed session: 10 s with stdin open and no write produced no stdout.
- **Not measured: whether the CLI emits `init` for a turn written while an earlier turn is still running.** Every `init` above followed a write to an idle session. This PR therefore takes no receipt verdict on such a write (see Fix).

So "any stdout envelope since a write to a known-idle child" separates *not reading* from *thinking*, as far as the protocol allows. It is a **receipt** signal, deliberately not a completion timeout. `init` specifically would be the tighter match. Keying on any parsed envelope is chosen so the check **fails soft**: a future CLI that stopped re-emitting `init` would still produce other lines, and the worst case is today's 10-minute latch rather than a kill loop.

Windows risk checked: #1869 argues from the source that the Windows reaper does not forward stdin. If so, a receipt timer would kill every Windows session. A probe (`probe-reaper-stdin.cjs`) against the **installed v0.25.0** `tandem-reaper.exe` and the repo's built one found that the child's fd 0 is a pipe, a written line arrives within 1 ms, and the echo comes back on stdout. The condition was a nested job, run from this session. That is not a verdict on #1869, which stays open and out of this group.

## Fix

`src/server/launcher/supervisor.ts`:

- **Bound.** Exported module constant `export const TURN_RECEIPT_MS = 180_000;`. Its docblock records:
  - the measured figures above, and that the slowest `init` measured is a fresh first turn's 12.7 s in the spike (hooks and MCP connects, one machine);
  - that `init` for a resumed large conversation was **not** measured;
  - that it is a policy value (see For Bryan);
  - the combined worst case with G1-1868: a machine whose first-turn `init` takes longer than the bound on three consecutive spawns is killed three times and trips `wake-delivery-failed` after about 3 × the bound plus the ladder rungs (~9 min at 180 s), on a session that would have worked, slowly.

  `SupervisorOpts` gains `turnReceiptMs?: number`, a test seam with the same justification text as `wakeLatchMs`.
- **Known-idle gate.** Per spawn: `let receiptTimer: NodeJS.Timeout | null = null;` and `let unresolvedTurn = false;`, where the latter means a turn was written on this spawn and no `result` has arrived since. `clearLatch()` also clears `receiptTimer`, so teardown and the failed-write callback cover it for free.
- `sendTurn`: before the write, `const receiptCheckable = !unresolvedTurn; unresolvedTurn = true;`. After `stdin.write(...)`, `if (receiptCheckable) receiptTimer = setTimeout(onNoReceipt, turnReceiptMs)`, replacing any existing timer. `turnInFlight` already blocks writes until a `result` arrives, so the only write that finds `unresolvedTurn === true` is the latch-expiry flush (`WAKE_LATCH_MAX_MS` fired with no `result`). The earlier turn may still be running there, and no `init` for the queued turn has been measured. That write keeps **today's behaviour**: no receipt timer, and the latch covers it. The spawn's first write (bootstrap, owed wake or login re-check) is to an idle child and is checked.
- `handleStdoutLine`: immediately after a successful `JSON.parse`, `if (receiptTimer) { clearTimeout(receiptTimer); receiptTimer = null; }`. Lines that don't start with `{` and `{`-prefixed non-JSON lines don't count. In the `result` branch, `unresolvedTurn = false` beside `clearLatch()`.
- `function onNoReceipt()`:
  - `receiptTimer = null;`
  - log `[Launcher] No turn receipt within ${turnReceiptMs}ms — Claude is alive but not reading its input; ending the session so the wake is retried`
  - `clearLatch(); pendingWake = true;`
  - `onStdinGone(RECEIPT_TIMEOUT)`.

  `RECEIPT_TIMEOUT` is a module-level `Object.assign(new Error("no turn receipt"), { code: "ETURNRECEIPT" })`. The handler ignores its argument. That reuses its identity and liveness guards and, with G1-1868, `markDeliveryKill`. So a stalled child counts toward the `wake-delivery-failed` streak like a stdin error does. That is deliberate: a child that never reads (for example a reaper that did not forward stdin) is killed once per `TURN_RECEIPT_MS`. That cadence beats both the 10-in-5-min window and the 30 s `restartIndex` reset, so without the streak it would loop forever. The owed wake crosses the kill via `teardownTurnDelivery`'s promotion (G1-1866), and a resumed successor gets exactly one wake.
- **Coalescing is unchanged.** While `turnInFlight` stays true, events only set `pendingWake`, so there is never more than one unacknowledged write per spawn. No queue exists to grow.
- **What the timer never does:** end a turn that showed receipt, however long it runs, or judge a write made while an earlier turn is unresolved. The 10-minute latch still covers a received turn that never returns a `result`.
- **macOS:** the receipt kill SIGTERMs the reaper, and on macOS that can orphan Claude and start a second one on the same session id. The existing `supervisor.ts` caveat already says so for the stdin-error kill. This PR makes the kill timer-triggered too. It is tracked in **#1994** (filed in round 1, owned by K-sec-launcher). The PR body must say this and must not describe the receipt kill as risk-free on macOS.

CLAUDE.md rules that bite: Critical Rule 3 (logs only via `console.error`). The source-order pin on the `onStdinGone` binding (see G1-1868) must stay adjacent and above the bootstrap write. `onNoReceipt` is declared after the binding, inside `spawnOnce`.

## Tests

`tests/server/launcher/supervisor-turn-delivery.test.ts` (mocked `spawn` harness, see G1-1866), with `turnReceiptMs: 200` unless stated otherwise. Every child that is meant to stay alive past 200 ms after a checkable write pushes `init` promptly, so its own receipt timer cannot cascade.

1. **Not reading → ended promptly, one wake carried.** Child 1 pushes `init` + `result` for the bootstrap turn immediately after the bootstrap write is recorded. Emit an event → W1; its callback succeeds (`cb()`), and child 1 pushes no stdout. Within ~400 ms the `kill` spy is called with `SIGTERM`, and the log contains `No turn receipt within`. The restart resumes as child 2. Assert child 2's writes are exactly `[SUPERVISOR_WAKE_PROMPT]`, then push `init` for child 2, and assert child 2 is not killed during the following 400 ms. *Kills:* no timer at all (the test times out well under the latch), and a timer that does not re-arm the wake (child 2 gets zero writes).
2. **Long turn not ended.** W1 is written; child 1 pushes `{"type":"system","subtype":"init"}` at +50 ms, then nothing for 1 s (5× the bound, under an injected `wakeLatchMs: 5000`). `kill` is not called. *Kills* a timer that `result` clears instead of receipt, which is the "arbitrary response timeout" the issue forbids.
3. **Coalesced during the stall.** Five events inside the 200 ms window → child 1's writes are exactly `[B, WAKE]` before the kill. *Kills* a retry-per-event or queued design.
4. **Non-JSON noise is not receipt.** Child 1 pushes `banner text\n` and `{not json\n` only → still ended. *Kills* keying on raw stdout bytes, and clearing on `startsWith("{")` before the parse.
5. **The latch-expiry flush is not receipt-checked.** `wakeLatchMs: 300`, `turnReceiptMs: 200`. Child 1 pushes `init` for the bootstrap turn and **no** `result`. Emit an event while that turn is in flight, so `pendingWake` is set. At ~300 ms the latch fires and writes `WAKE`. Child 1 then pushes nothing for 1 s. Assert `kill` was not called and child 1's writes are exactly `[B, WAKE]`. *Kills* arming the receipt timer on every write, which would SIGTERM a turn still running a silent tool call.
6. **The shipped bound is not a toy value.** `expect(TURN_RECEIPT_MS).toBeGreaterThanOrEqual(10 * 12_700)` (10× the slowest measured first-turn `init`), and `expect(TURN_RECEIPT_MS).toBeLessThan(10 * 60_000)` (below the latch it exists to beat). *Kills* shipping a test-sized default.

## For Bryan (policy, not blocking the merge)

`TURN_RECEIPT_MS` ships at **180 s**. Options:
- **(a) 180 s** (shipped). About 14× the one measured first-turn start, and three consecutive slow starts trip `wake-delivery-failed` after about 9 min.
- **(b) 120 s** (the earlier draft). A faster recovery for a stuck child, and a thinner margin for slow hooks/MCP connects or a large `--resume`.
- **(c) A longer bound for a spawn's first write only** (e.g. 5 min), and 120 s after that. Better margin for cold starts, at the cost of a second constant.

Test 6 pins only the floor, so any of these is a one-line change.

## Not in scope

#1869's fix or verdict. Retrying payload-bearing turns. Changing `WAKE_LATCH_MAX_MS`. Measuring `init` for a turn queued behind a running one (the gate makes the answer irrelevant to this PR). A real-pipe end-to-end test (the mocked stdin is exactly a successful write with no consumer, which is the condition under test). The macOS reaper orphan (#1994).

## Review corrections (round 1)

**Adopted**
- The receipt timer is armed only for writes to a known-idle child (`unresolvedTurn` false: the spawn's first write, or any write after a `result`). The latch-expiry flush is not receipt-checked, and test 5 pins it with its mutation. The claim "a turn that emitted init is never ended" is replaced by the narrower, true statement: writes made while an earlier turn is unresolved are not judged.
- Test 1 cascade: child 1 pushes `init` + `result` for the bootstrap before 200 ms, and child 2 pushes `init` right after its wake write.
- Test 4 adds a `{not json` line with the matching mutation.
- Bound pinned by test 6 (≥ 10 × 12.7 s, < latch). The default is raised to 180 s so it passes that floor, and the value is put in For Bryan with concrete options.
- The slow-first-turn × streak interaction is documented in the constant's docblock and in For Bryan.
- macOS orphan hazard: issue #1994 filed, referenced here, and required in the PR body.

**Not adopted**
- "Don't count a receipt kill on a spawn's first turn toward the streak": a child that never reads stdin is receipt-killed on exactly its first write every spawn. At one kill per bound it evades the ordinary breaker's window and `restartIndex` reset, so exempting first writes would reopen #1868's unbounded loop for that case. The docblock and For Bryan carry the slow-start cost instead.
- Measuring `init` for a turn queued behind a running one: it would need a signed-in session (Bryan's real credentials, excluded by this run's rules), and the known-idle gate makes the answer unnecessary for this PR.
