# E2-upgrade — #1791 a new enum value quarantines the whole annotation file, and the `.future` park deletes the only parked copy on the second cycle

Branch `fix/upgrade-and-downgrade-paths-annotation-envelope-compatibility-and-settings-that-go-silently-inert-1791`. Closes #1791 (both halves). Ledger: `docs/reviews/2026-09-02-v1-review/areas/upgrade-path.md:19` (park) and `:20` (enum quarantine). Probes: `experiments/upgrade-envelope-probe.ts` (pre-existing) and `experiments/future-park-probe.ts` (new, added by this branch).

**Both halves measured on this branch before designing.** `npx tsx docs/reviews/2026-09-02-v1-review/experiments/upgrade-envelope-probe.ts` prints `good + additive field => ok, 2 annotations kept` / `good + future type => FAIL error=corrupt` / `good + future status => FAIL error=corrupt`. `TANDEM_APP_DATA_DIR=$(mktemp -d -t tandem-XXXXXX) npx tsx …/future-park-probe.ts` drives the **real** `createStore(...).load()` through two downgrade cycles and prints `after downgrade #1: .future = USER-NOTE-FROM-CYCLE-1`, `after downgrade #2: .future = CYCLE-2`, `CYCLE-1 PARKED COPY DESTROYED`, with exactly one `.future*` file left in the directory. One cycle looks fine; two is what shows it.

## Problem

**(a) One unreadable row fails the whole envelope.** `schema.ts:4-13` promises forward compatibility via `.passthrough()`. That holds for new *fields* only. `AnnotationRecordSchemaV1` (`schema.ts:105-111`) types `type`/`status`/`author` as the closed `z.enum`s from `src/shared/types.ts:17,19,23`; one unknown value fails the row, `z.array` fails `AnnotationDocSchemaV1` (`schema.ts:215-224`), `parseAnnotationDoc` returns `corrupt`, and `loadOne` (`store.ts:620-631`) renames the file `.corrupt.<ts>` and returns an empty doc. Every annotation is gone, **including the user's personal notes** (ADR-027), not only the row the older build could not read.

**(b) The `.future` park destroys the previous park.** `loadOne` (`store.ts:635-648`) runs `fs.unlink(futurePath)` *before* `fs.rename(target, futurePath)`, and reports to stderr only where the corrupt path toasts. `.future` is the sole surviving copy of the pre-downgrade annotations — nothing ever reads it back — so the second downgrade cycle deletes it. This also falsifies `doctor.ts:2898-2900`'s "they are never deleted". Dormant until `SCHEMA_VERSION` (`schema.ts:29`) moves; `migrations/v1_to_v2.ts` and `migrateUp` are already wired at `schema.ts:350`.

## Fix

**`src/server/annotations/schema.ts` — row-level tolerance, inside `parseAnnotationDoc` only.** No schema restructuring: filter `annotations` and `replies` row-by-row with `AnnotationRecordSchemaV1` / `AnnotationReplyRecordSchemaV1`, counting drops; build the object handed onward as `{ ...candidate, annotations: kept, replies: kept }` (a spread, so `.passthrough()` keys survive) rather than mutating the caller's arrays. The precedent is `migrateToV1` (`:400-440`), which already does exactly this per-row skip-and-count with a `console.error` naming each dropped id — copy its log shape.

- **Placement: the filter runs BEFORE `migrateUp` (`:350`), not after.** This is not cosmetic. `migrations/v1_to_v2.ts:44-46` builds `FrozenV1InputSchema = AnnotationDocSchemaV1.extend({schemaVersion: z.literal(1)})` and calls a **throwing** `.parse(input)` over the whole envelope, every record included; `schema.ts:351-356` catches that throw and returns `corrupt`. A filter placed after `migrateUp` therefore evaporates the moment `SCHEMA_VERSION` moves to 2 — the exact bump this fix exists to survive — and test 4's migrated assertion would silently flip back to `corrupt` with nothing red. Filtering first means `migrateUp` only ever receives rows that already satisfy the frozen input contract. Add a comment at the filter and a second at `v1_to_v2.ts:44` saying the two are a pair.
- **The filter is gated on `Array.isArray`, and a non-array is left untouched.** `annotations: "not an array"` must fall through to `AnnotationDocSchemaV1.safeParse` and still return `corrupt`. **Never coerce a non-array `annotations`/`replies`/`tombstones` to `[]`** — that is envelope-shell corruption, and coercing it reports a successful load of zero annotations, which `loadAndMerge` (`sync.ts:568`) then reads as `fileEmpty` and clobbers the envelope to zero. The row filter applies only where `Array.isArray` holds; that split is the envelope-vs-row discriminator the tests pin.
- **`tombstones` stays a hard `z.array` — deliberate asymmetry, and it is load-bearing.** Dropping a tombstone row resurrects a deleted annotation (#700/#695, `sync.ts:263-266`). `TombstoneRecordSchemaV1` is `{id, rev, deletedAt}` with no enum, so no additive enum change can reach it; a bad tombstone row is real corruption and must still fail the envelope. Say so in a comment at the filter.
- **Replies of a dropped annotation are retained as orphans**, matching `loadAndMerge`'s existing rule ("a deleted parent annotation just orphans its replies"). The two counts are reported separately so a notice can distinguish a lost parent from a lost reply — a `private: true` reply inside a note thread (#1000/#1619) is a reply row, not an annotation row.
- The envelope shell (`schemaVersion`, `docHash`, `meta`) still failing → `corrupt`, unchanged.

**`ParseAnnotationDocResult`'s ok arm becomes `{ ok: true; doc; skipped: { annotations: number; replies: number } }` — and `skipped` is a REQUIRED consult at every call site that PERSISTS the parsed doc, not an optional read.** The five `src` call sites split two ways, and the split is by whether the site writes `parsed.doc` back, not by whether it compiles:

- **Read-only, no change needed:** `store.ts:617` (`loadOne`, handled below), `session/manager.ts:1000` (`annotationCountForPath`), `cli/annotation-store-scan.ts:311`.
- **`session/manager.ts:1161` — `cleanupStaleTombstones` — REWRITES the envelope and must bail.** Today `if (!parsed.ok) continue;` (`:1162`) is the only thing protecting a file with an unreadable row: the file is left untouched. After the fix that file parses `ok: true` with rows already dropped, `:1173` builds `const rewritten = { ...doc, docHash: fileHash, tombstones: kept }` from the partial doc, and `:1176-1177` `store.queueWrite` + `await store.flush()` clobbers `<hash>.json` with the survivors only. The preservation copy below lives in `loadOne`, which this path never enters, so there would be **no surviving copy at all** — and the open-doc guard at `:1151` means this fires on CLOSED documents, so the user is not present. Change the line to `if (!parsed.ok || parsed.skipped.annotations + parsed.skipped.replies > 0) continue;` with a comment: *a partially-tolerated envelope is not a safe base for a full-envelope clobber.*
- **`annotations/rename-recovery.ts:134` — `recoverRenamedEnvelope` — re-keys AND unlinks, and must decline candidacy.** Same shape, worse ending: `:178` pushes `parsed.doc` as a candidate, `:191` spreads it into `rekeyed`, `:204-205` flushes the partial envelope under the NEW docHash, and `:252` `fs.unlink`s the source. The dropped rows would exist in no copy anywhere. Change to `if (!parsed.ok || parsed.skipped.annotations + parsed.skipped.replies > 0) continue;`, which keeps the function's existing "skip this candidate, never fail the whole recovery" semantics and leaves the source file on disk.

**`src/server/annotations/store.ts` — surface it, and keep a copy.** In `loadOne`, on `result.ok` with `skipped.annotations + skipped.replies > 0`: `fs.copyFile(target, `${target}.corrupt.partial`)` (catch-and-log) **before** returning the partial doc, then a notice. The copy is not optional — `sync.ts`'s `snapshot()` (`:182`) rebuilds the envelope from Y.Map state, so the skipped rows are permanently gone on the next debounced write.

- **The name is deterministic, not `Date.now()`, and the copy is written only when that file does not already exist.** The partial file is never healed on every path: `loadAndMerge` re-inserts under a file-sync origin and `registerAnnotationObserver` skips the durable queue for exactly those origins (`sync.ts:284-286`), and a store in read-only mode (a second instance holding `store.lock`) makes `queueWrite` inert entirely. A timestamped copy would therefore be written once per open, forever, each one counted by `annotation-store-scan.ts:228` and warned on by `doctor.ts:2884`. One file per envelope, `EEXIST`-guarded, is the whole guard.
- Keeping the `.corrupt.` infix is deliberate: `annotation-store-scan.ts:228` already counts `.includes(".corrupt.")`, `ENVELOPE_FILENAME_RE` (`src/server/annotations/doc-hash.ts:143`) and `ATOMIC_TEMP_RE` (`src/server/file-io/reaper.ts:39`) both refuse to match it, so no sweeper contract changes. Doctor's quarantined row will now include it — which is why its remediation string is corrected below.

**`store.ts` park order.** Replace `await fs.unlink(futurePath).catch(() => {})` with an archive rename of the previous park, then rename `target` onto `.future`. The archive name must not collide: `Date.now()` is millisecond-resolution and a third park inside one millisecond would rename onto an existing archive and destroy it — the same class of loss this fix removes. Use `${futurePath}.${Date.now()}-${crypto.randomBytes(4).toString("hex")}` (the shape `atomicWrite` already uses), or retry on `EEXIST`. **Keep `.future` as the primary park name**: `store.test.ts:221` pins "parks the file at `.future` without timestamp", `cli/annotation-store-scan.ts:229` filters `endsWith(".json.future")`, and `doctor.ts:2896` reads that count. A timestamped *primary* name would silently break all three.

**Both branches get a notice.** Add `notifyLoadIssue(docHash, filePath, message, dedupKey)` beside `notifyFailure` (`store.ts:399`) — `pushNotification` with `type: "annotation-error"` (not `"save-error"`: `activityCenter.ts`'s `formatActivityMessage` folds `errorCode` into `save-error` messages only), `severity: "warning"`, **past tense** (`types.ts:646-654`: warning/error persist in the tray, which is a log). No path in the message — only `path.basename`, as `notifyFailure:412` does.

**`src/cli/annotation-store-scan.ts` + `src/cli/doctor.ts`** — widen the parked filter at `annotation-store-scan.ts:229` from `endsWith(".json.future")` to `includes(".json.future")` so the archived parks this fix now creates are visible. `doctor.ts:2899`'s "they are never deleted" becomes true with this fix — keep it. `doctor.ts:2887`'s "Safe to delete after inspection; kept 7d by design" is **already false** (nothing reaps `.corrupt.*` — `ATOMIC_TEMP_RE` is anchored to exclude it) and is materially misleading once a `.corrupt.partial` copy can be the last copy of a user's notes: split the remediation so the wording is preservation-first ("these are the only copy of rows this build could not read; inspect before deleting — nothing reaps them"). Two-person rule: fix it here rather than filing it.

**Rules that bite:** no Y.Doc writes here, so no origin helper applies; `notifyLoadIssue` must not embed an absolute path (#1816); `console.error` with a user-named basename goes in as a `%s` argument, never the format string (CodeQL `js/tainted-format-string`, `store.ts:448`).
