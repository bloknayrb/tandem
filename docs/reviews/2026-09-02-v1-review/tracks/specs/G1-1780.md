## Problem — the issue's premise is refuted, and the real failure is quieter

The review read the auth path from code and assumed an immediate exit, which would then be counted as a crash until the breaker trips. What was observed instead, with stdin held open as the supervisor holds it:

```
t+0.06 WRITE turn 1
t+2.45 {"type":"system","subtype":"init"}
t+2.54 {"type":"assistant", content:[{type:"text",text:"Not logged in · Please run /login"}]}
t+2.55 {"type":"result","subtype":"success","is_error":true,"result":"Not logged in · Please run /login","terminal_reason":"api_error","api_error_status":null}
t+7.55 WRITE turn 2 → identical init / assistant / result
t+40.06 stdin ended by the probe → EXIT code=1 signal=null
```

stderr was empty for the whole run. **The process does not exit while stdin is open.** It answers every turn with an error `result`. The exit (code 1) happens only after stdin ends.

Round 1 added (`probe-resume-mcp.cjs`, abridged):

```
FRESH  t+0.09 WRITE turn
FRESH  t+0.64 HTTP POST /mcp initialize      ← MCP connects although signed out
FRESH  t+0.65 HTTP GET /mcp                  ← standalone stream opened
FRESH  t+0.72 init  mcp=[{name:"probe",status:"connected"}]
FRESH  t+0.75 result is_error=true "Not logged in · Please run /login" terminal_reason=api_error
FRESH  t+3.76 KILL → EXIT code=null signal=SIGTERM   (no HTTP DELETE was sent)
       transcript <id>.jsonl present under CLAUDE_CONFIG_DIR/projects/
RESUME t+7.33 HTTP POST /mcp initialize; GET /mcp opened   ← before any turn
RESUME t+7.34 … t+16.80: no stdout at all, stdin open, no write
RESUME t+16.80 WRITE turn → t+16.90 init → t+16.95 identical "Not logged in" result
RESUME t+19.95 KILL → EXIT code=null signal=SIGTERM
```

Under the supervisor, then:

- the child stays alive, `status()` reports `running: true`, and the child also holds an MCP session with an open `GET /mcp` stream, so `/health` `hasSession` is true;
- `useAiReadiness` shows the AI as ready, with no chip and no CTA;
- `result` clears the latch, so every later wake gets another `Not logged in` and nothing more;
- a `--resume` of that session **loads** (the signed-out run left a transcript) and stays silent until it is sent a turn.

Nothing on any surface says "sign in". `docs/troubleshooting.md` (the "Set up Claude Code" section, the "You have never signed in" bullet) already describes this case. Its mechanism ("exits immediately… retries until the breaker trips") is wrong, and it says Tandem "cannot yet tell them apart".

## Fix

**Classify on what was observed: the `result` envelope, not stderr or the exit code.** `src/server/launcher/supervisor.ts`:

- Module constant `const NOT_SIGNED_IN_RESULT = /^Not logged in\b/;`, anchored to the measured prefix and case-sensitive. Its docblock quotes the measured envelope, the CLI version and the date. It says an expired login was **not** measured and may read differently. It also says a mismatch fails soft to today's silent behaviour rather than to a false sign-in prompt.
- Supervisor-level `let loginRecheckOwed = false;`, with a docblock: set by the `needs-login` trip; cleared only by a `result` that is not a `needs-login` result; **not** cleared by `stop()`, `stopInternal` or `respawn`. It exists because "Check again" goes through `relaunch` → `respawn`, the saved session survives the SIGTERM (`shouldClearSession` needs a non-null code), so `buildPlan` resumes, and a resumed spawn otherwise writes no turn. The CLI emits nothing until it gets one (measured above), so nothing would ever re-classify.
- `handleStdoutLine`: widen the parsed type with `result?: unknown`. In the `result` branch, after `clearLatch()` and the G1-1867/G1-1868 resets, and **before** `flushPendingWake()`:

  ```ts
  if (parsed.is_error === true && typeof parsed.result === "string" && NOT_SIGNED_IN_RESULT.test(parsed.result)) {
    // The whole classification is identity-guarded, not just the kill: a
    // superseded spawn's late result must not trip the breaker for its successor.
    if (child === spawned) {
      lastError = "needs-login";
      breakerTripped = true;
      loginRecheckOwed = true;
      console.error("[Launcher] Claude Code is not signed in — not retrying. Run `claude` in a terminal to sign in, then use Check again.");
      try { spawned.kill("SIGTERM"); } catch { /* best-effort, as stopInternal */ }
    }
    return;
  }
  if (child === spawned) loginRecheckOwed = false;
  ```

  `breakerTripped` makes the exit handler's `scheduleRestart()` a no-op, so there is no retry. Returning before `flushPendingWake` stops a second doomed wake from being written. The kill is direct and does not go through `onStdinGone`, so it never counts toward G1-1868's delivery streak.
- `spawnOnce`'s resumed branch becomes `else if (wakeOwedAcrossSpawns || loginRecheckOwed) { if (sendTurn(SUPERVISOR_WAKE_PROMPT)) wakeOwedAcrossSpawns = false; }`. Only one wake is written either way. `loginRecheckOwed` stays set until a result answers it, so a re-check child that crashes before answering re-checks again on the next resume. The fresh branch needs no change, because its bootstrap turn is itself the re-check. This write is the spawn's first, to an idle child, so G1-1867's receipt check applies to it (a resumed `init` was measured at +0.10 s).
- `src/shared/launcher/contract.ts`: `LauncherErrorCode` gains `"needs-login"`, with a docblock sentence: the CLI is installed and answers, but is not signed in, and the remedy is to sign in and then re-check.

**Why the saved session is kept rather than cleared.** Clearing it on the trip would make the re-check fresh and need no flag. But an expired login on a real conversation was not measured, and dropping a conversation is the irreversible action #1268 keeps off the default path. The flag re-checks without losing anything.

**Client. `AiChip` gains a member instead of reusing `restart`.** `src/client/hooks/useAiReadiness.svelte.ts`:

- `AiChip = "connect" | "setup" | "sign-in" | "restart" | null`, with a doc bullet for `sign-in`.
- `chip` derivation: `lastError === "needs-login" ? "sign-in"` beside the `cli-unusable` arm.
- `AI_CTA["sign-in"]` = `{ label: "Check Claude sign-in", title: "Claude Code isn't signed in. Run “claude” in a terminal and sign in, then click to check again.", ariaLabel: "Claude Code is not signed in. Check again after signing in.", action: "restart" }`. The re-check is `relaunch`: `respawn` clears the breaker, and `loginRecheckOwed` makes the resumed spawn send one turn, which a still-signed-out CLI answers with the same result (re-trip) and a signed-in one answers normally.
- **State precedence is unchanged, deliberately (read, then measured in part).** While the signed-out child is alive, its MCP stream makes `hasSession` true (measured: the `GET /mcp` stream opens at spawn, even on resume before any turn), so `state` is `ready`. After the kill, the chip appears once that stream closes: `server.ts` registers `res.once("close", () => registry.noteStreamClosed(...))` on the `GET /mcp` handler, and `getMcpSessionCount` counts only `openStreams > 0`. The killed CLI sent no DELETE (measured), so the stream close on process death is what drops `hasSession`. That close was **read, not measured end-to-end against a running Tandem**, so the smoke row below is what verifies it. At `POLL_MS = 8_000`, expect the chip within about one poll of the trip. During a re-check the resumed child's own stream opens at spawn, so the chip can clear for up to one poll before the re-trip brings it back. A second, independent Claude session holding its own stream keeps `state` ready, which is correct, because AI then works. `needs-login` is not ranked above the session promotion, because a live session is better evidence that AI works than the launcher's `lastError`.

The `Record` makes `App.svelte` (addressed-AI notice) and `StatusBar.svelte` pick it up without edits. `src/client/components/EmptyState.svelte` needs an explicit `{:else if connected && aiChip === "sign-in"}` branch, because it switches on chip literals and would otherwise fall through to the positioning copy. The branch holds the sub line "Claude Code needs to be signed in. Open a terminal, run `claude`, and finish signing in." (with `claude` in `<code>`) and one button, `data-testid="empty-state-sign-in-recheck"` `data-ai-chip="sign-in"` "Check again", calling `onRestartClaude`. **Critical Rule 7:** this adds a testid, so regenerate `tests/design-system-impl/__snapshots__/testid-set.snap.txt` in the same commit, and add `empty-state-sign-in-recheck` (`aiChip: "sign-in"`) to the State A AI-readiness bullet of `docs/design-system-impl/testid-manifest.md` in that commit too. No selector is renamed or removed.

**Docs.** In `docs/troubleshooting.md` ("Set up Claude Code"), rewrite the never-signed-in bullet in place rather than adding a second passage. The new text says Tandem now detects a never-signed-in Claude Code, which stays running and answers "Not logged in", and shows **Check again**; the steps are to run `claude`, finish the login, then click Check again. The intro sentence "Two causes … Tandem cannot yet tell them apart" becomes one about the remaining restart cause. ## Review corrections (round 1)

**Adopted**
- Check again now provably sends a turn. `loginRecheckOwed` is set by the trip, consumed only by a non-auth `result`, and makes a resumed spawn write `SUPERVISOR_WAKE_PROMPT`. The "re-trips within about 3 s" claim is withdrawn. Test 3 is rewritten: a resumed child that pushes nothing unprompted must receive exactly one write, and a still-signed-out answer re-trips. 3b and 3c pin the clear and stop semantics. Measured in round 1: `--resume` of a signed-out session loads and stays silent until a turn is written, then answers "Not logged in" (+0.15 s).
- The two specs no longer contradict each other. G1-1866 now keeps an owed wake across `respawn` (its clear moved to the public `stop()`), and the login re-check has its own flag that `stop()` does not touch.
- The saved session is kept, not cleared (irreversible, and an expired login on a real conversation was not measured).
- Test 1 emits a wake-worthy event during the bootstrap turn and asserts child 1's writes are exactly `[bootstrap]`, so the delete-`return` and after-flush mutants go red.
- The pattern is anchored to the measured prefix. 2b is the mid-string negative.
- The whole classification (assignments, log, kill) is inside `child === spawned`. 2c is the superseded-spawn case.
- Test 2 reuses the verbatim envelope with only `result` replaced.
- MCP-session masking measured: a signed-out CLI connects MCP and opens a `GET /mcp` stream at spawn and on resume, and sent no DELETE when killed. The chip's appearance after the kill rests on the stream close (read at `server.ts`'s `res.once("close")` / `openStreams > 0`, not measured end-to-end). The spec says so, and the smoke row's timing is changed from "within seconds" to "within about 10 s", with a still-signed-out Check-again step.
- `empty-state-sign-in-recheck` is added to `testid-manifest.md` alongside the snapshot.
- Carrying a pending comment through Check again: covered by test 3. The successor's single wake turn makes Claude call `tandem_checkInbox`, which surfaces the comment.

**Not adopted**
- Requiring `terminal_reason === "api_error"` in the classifier: the anchored, measured prefix plus `is_error` already excludes mid-string mentions (2b). A second unversioned field would silently disable the classifier if the CLI renamed or dropped it. Test 2 keeps that field in the counter-fixture, so a `terminal_reason`-only key still goes red.
- Ranking `needs-login` above the MCP session promotion: the stream close that drops `hasSession` on process death is in the server source, and a genuinely live second session means AI works. The residual unmeasured step is named and left to the smoke row rather than masked by a precedence change.
