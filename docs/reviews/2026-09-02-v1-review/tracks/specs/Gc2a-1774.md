# Gc2a — #1774 find/replace is off by one per hard break

Branch `fix/position-mapping-1776`. Closes #1774. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:19`. Probe: harness `docs/reviews/2026-09-02-v1-review/experiments/harness/a-bugs.test.ts` describe B (tracked, but run by nothing — it carries its own `vitest.config.ts` and `vitest.config.ts:68` includes only `tests/**/*.test.ts`), re-measured on this branch 2026-09-08 with a two-break fixture (below). **Reproduce the numbers in the PR body rather than citing the harness path** — it is evidence a reviewer has to run by hand.

## Problem

`walkMatches` (`src/client/editor/extensions/find-replace.ts:74-86`) searches `node.textContent` (`:81`) and maps every match with `pos + 1 + idx` (`:84`). The two coordinate counts disagree at exactly one node type. Measured on this branch, on `<p>alpha<br>beta gamma<br>delta gamma</p><p>plain gamma</p>`:

| | contribution to `node.textContent` | contribution to PM positions |
|---|---|---|
| text node | `text.length` | `text.length` |
| `hardBreak` | **0** (`textContent` is `textBetween(0, size, "")`) | **1** (`nodeSize` of a non-text leaf) |

So the index-into-text and the PM offset drift by one per *preceding* break inside the block. Measured matches for `gamma`: `[11,16] [22,27] [37,42]`, covering `" gamm"`, `"a gam"`, `"gamma"` — drift 1, 2, 0. `replaceAll` with `DELTA` produced `"alpha\nbetaDELTAa\ndeltDELTAma\nplain DELTA"`: the replacement ate the space, left a stray `a`, and the count and highlight both looked right because the decoration is drawn at the same wrong offset. **The drift compounds per break, so a one-break fixture with a single match cannot tell a real fix from a constant `-1`** — hence two breaks and three matches below.

`hardBreak` is the schema's only inline non-text node (measured: `image` and `horizontalRule` are block leaves, and `walkMatches` visits only `isTextblock` nodes), so it is the whole of the bug today.

## Fix

One line, `find-replace.ts:81`:

```ts
const text = node.textBetween(0, node.content.size, undefined, "\n");
```

Every inline **leaf** then contributes exactly one character, and a non-text leaf's `nodeSize` is 1, so char index equals PM offset within the textblock **by construction** rather than by counting breaks — which is why this is preferred over subtracting a per-break correction. **That argument covers inline LEAVES only.** An inline *non-leaf* would break it silently: `Fragment.textBetween` gives a non-leaf node `nodeText = ""` and recurses into its children, while its `nodeSize` is `2 + content.size` — a 2-per-node drift no `leafText` argument can reach. Measured, the schema is safe today: no `inline: true`, `group: "inline"` or `atom: true` anywhere in `src/client/`, and `src/client/editor/editor-extensions.ts:405` configures `Image` as the block-level node its own comment names. So this is a future hazard, not a present one — which is why it belongs in the comment rather than in the arithmetic. Pass the `leafText` argument explicitly rather than relying on a node's `spec.leafText`: the passed value wins, so a future inline leaf that declares a multi-character `leafText` cannot silently re-break the alignment.

Add a comment naming the 0-vs-1 asymmetry so the next reader does not "tidy" it back to `textContent`, **and naming the deliberate twin**: `src/client/positions.ts#textblockFlatText` walks the same shape and gives every non-`hardBreak` inline leaf **zero** characters, on purpose — that walk aligns to the server's flat text, this one aligns to PM positions. Both are correct today only because `hardBreak` is the schema's sole inline node, so **any future inline node — leaf or not — has to be considered in both walks; a non-leaf inline node contributes `2 + content.size` to PM offsets and nothing of its own to the text, which breaks this identity.**

Consequences to state in the PR body:

- A query can no longer match **across** a break — `"alphabeta"` previously matched and produced a range spanning the break. `"\n"` is the separator `doc.textBetween(…, "\n", "\n")` already uses everywhere else in this codebase, and it reads as a line break to `\b` and `\s`; regex `.` does not cross it.
- **`wholeWord` gets wider, not just narrower.** `buildRegex` (`:66`) wraps in `\b…\b`, and `textContent` glued the segments either side of a break into one word: on the fixture above, `\bgamma\b` finds **2** matches today and **3** after the fix, and `\balpha\b` finds **0** today and **1** after. Match counts shown to the user change on any whole-word search over a document containing a hard break. This is the fix, not a side effect — but it is user-visible and belongs in the PR body.
- **A break becomes matchable.** In `regexMode`, a query of `\n` or `\s` can now produce a `MatchRange` covering the break itself, which `replaceActive` / `replaceAll` will `tr.insertText` over (`:266`, `:292`) — i.e. replacing a line break with text. That is the correct consequence of the break occupying one position, and it is what the old arithmetic hid.
- `replaceActive`, `replaceAll` and `buildDecoSet` are unchanged: they consume `MatchRange` and were always correct given correct input.
- **These are PM positions, not flat offsets.** `walkMatches` deliberately stays in the ProseMirror system because its consumers are `Decoration.inline` and `tr.insertText`; do not route it through `src/client/positions.ts`. (CLAUDE.md, three coordinate systems.)
- No `$state` write is added — this is plugin state, not a Svelte handler, so the `createCoalescingTick` rule is not engaged. No `data-testid` is added or renamed, so `__snapshots__/testid-set.snap.txt` is not regenerated.
- Cost is unchanged in order: `textBetween` walks the same block `textContent` already walked, on the same `docChanged` path.

## Tests

New `tests/client/find-replace-hard-break.test.ts` (harness B converted and extended to two breaks). Not added to `tests/client/live-regions-find-replace.test.ts`, which `vi.mock`s the whole `find-replace` module and so pins nothing about matching. Fixture: `<p>alpha<br>beta gamma<br>delta gamma</p><p>plain gamma</p>`, query `gamma` unless stated otherwise.

**How the tests reach `walkMatches`.** It is module-private (`find-replace.ts:74`; the file exports only `findReplaceKey`, the three interfaces, `FindReplaceExtension`, `getFindState`, `replaceActive` and `replaceAll`), so every assertion goes through the plugin: seed with `editor.commands.find({ query, caseSensitive: false, wholeWord: false, regexMode: false })` — varying the flags per test — then read `getFindState(editor.state)!.matches`. Every match count and range below is that array. `replaceActive` and `replaceAll` take a `{ state, dispatch }` view, which `editor.view` satisfies.

1. **Every match covers exactly the query.** For each match, `doc.textBetween(from, to, "\n", "\n") === "gamma"`. Fails on master at drift 1 *and* 2, so it also kills a constant `-1` correction that fixes only the first break — the reason the fixture has two.
2. **Replace-all writes the right text.** `await replaceAll(view, "DELTA")` — it is an `export async function` (`:272`), so await it; **but not for the reason an earlier draft gave.** With 3 matches and `CHUNK = 100`, `view.dispatch(tr)` runs in the first pass and `if (chunk.length < CHUNK) break` (`:303`) executes *before* the loop's only `await new Promise(resolve => setTimeout(resolve, 0))`, so the whole body is synchronous to the `return` and an un-awaited call would still observe the replaced document. Await it because the >`CHUNK` path genuinely yields and an unhandled rejection is otherwise invisible — do not claim the await is what makes this assertion sound. Then `editor.state.doc.textBetween(0, editor.state.doc.content.size, "\n", "\n")` is exactly `"alpha\nbeta DELTA\ndelta DELTA\nplain DELTA"`. Name that reader explicitly: `editor.getText()` defaults to a `"\n\n"` block separator and `textBetween` with no `leafText` renders hardBreaks as nothing, so either would make the expected string wrong. Kills a fix that corrects only the decoration; reproduces and then forbids the character-eating corruption in the issue body.
3. **`replaceActive`** on the match after one break (`" gamma"` in `beta gamma`) replaces exactly that match and leaves its neighbours intact. **State the precondition rather than relying on it.** `replaceActive` acts on `state.matches[state.activeIndex]` (`:262-263`), and `activeIndex` comes from `findActiveIndex(matches, newState.selection.from)` (`:136`, `:180`, definition at `:112-121`) — it is `0` on this fixture only because a fresh `new Editor({ content })` puts the caret at pos 1, before every match, and a `findNext()` first would target a different one. Assert `expect(getFindState(editor.state)!.activeIndex).toBe(0)` before the call, so a schema or selection-default change surfaces as a failed precondition instead of the test silently exercising a different match.
4. **Control, no hard break — must stay green under BOTH arithmetics.** Fixture `<p>alpha beta gamma</p><p>plain gamma</p>`, query `gamma`: exactly **2** matches, each satisfying (1)'s `textBetween(from, to, "\n", "\n") === "gamma"` check. A break-free textblock has zero drift (`node.textContent` and `textBetween(…, "\n")` are identical when the block holds no leaf), so this passes identically before and after. That is the point: it is the guard against an over-correction that adds an offset unconditionally.
5. **No match spans a break.** Query `"alphabeta"` returns 0 matches. Pins the `"\n"` semantics and kills a "fix" that keeps a zero-width leaf placeholder and merely subtracts.
6. **Whole-word widening, forward.** On the two-break fixture with `wholeWord: true`, query `gamma` returns **3** matches (2 on master).
7. **Whole-word widening, at the first break.** Same fixture, `wholeWord: true`, query `alpha` returns **1** match (0 on master). Free discrimination, and it pins the `"\n"` semantics from the opposite direction to (5).
8. **A break is matchable, and replacing one writes text over it.** This is the pin for the user-visible consequence stated above; without it, a later "tidy" that suppresses the break from the match text (a zero-width placeholder, say) passes every other assertion here. Two-break fixture, `regexMode: true`, query `\n`: `getFindState(editor.state)!.matches` has **2** entries, each of length 1 (`to - from === 1`) — **0 on master**, since `textContent` contains no `\n`, so it discriminates as well as pins. Then `expect(getFindState(editor.state)!.activeIndex).toBe(0)`, `replaceActive(editor.view, "X")`, and `editor.state.doc.textBetween(0, editor.state.doc.content.size, "\n", "\n")` is exactly `"alphaXbeta gamma\ndelta gamma\nplain gamma"` — the first break gone, replaced by `X`, and the second untouched.
