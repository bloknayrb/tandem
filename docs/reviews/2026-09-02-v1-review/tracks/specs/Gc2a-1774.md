# Gc2a — #1774 find/replace is off by one per hard break

Branch `fix/position-mapping-1776`. Closes #1774. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:19`.

## Problem

`walkMatches` (`src/client/editor/extensions/find-replace.ts`) searches `node.textContent` and maps every match with `pos + 1 + idx`. The two counts disagree at exactly one node type:

| | contribution to `node.textContent` | contribution to PM positions |
|---|---|---|
| text node | `text.length` | `text.length` |
| `hardBreak` | **0** (`textContent` is `textBetween(0, size, "")`) | **1** (`nodeSize` of a non-text leaf) |

So the index-into-text and the PM offset drift by one per *preceding* break inside the block. Measured on this branch on `<p>alpha<br>beta gamma<br>delta gamma</p><p>plain gamma</p>`, matches for `gamma` are `[11,16] [22,27] [37,42]` — covering `" gamm"`, `"a gam"`, `"gamma"`, drift 1, 2, 0. `replaceAll` with `DELTA` produced `"alpha\nbetaDELTAa\ndeltDELTAma\nplain DELTA"`: the replacement ate the space and left a stray `a`, and the count and highlight both looked right because the decoration is drawn at the same wrong offset. **Reproduce these numbers in the PR body.**

**The drift compounds per break**, so a one-break fixture with a single match cannot tell a real fix from a constant `-1` — hence two breaks below.

`hardBreak` is the schema's only inline non-text node (measured: `image` and `horizontalRule` are block leaves, and `walkMatches` visits only `isTextblock` nodes), so it is the whole of the bug today.

## Fix

One line:

```ts
const text = node.textBetween(0, node.content.size, undefined, "\n");
```

Every inline **leaf** then contributes exactly one character, and a non-text leaf's `nodeSize` is 1, so char index equals PM offset within the textblock **by construction** rather than by counting breaks — which is why this is preferred over subtracting a per-break correction. **That argument covers inline LEAVES only.** An inline *non-leaf* would break it silently: `Fragment.textBetween` gives a non-leaf node `nodeText = ""` and recurses into its children while its `nodeSize` is `2 + content.size` — a 2-per-node drift no `leafText` argument can reach. Measured, the schema is safe today: no `inline: true`, `group: "inline"` or `atom: true` anywhere in `src/client/`, and `editor-extensions.ts` configures `Image` as the block-level node its own comment names. Pass `leafText` explicitly rather than relying on a node's `spec.leafText` — the passed value wins, so a future inline leaf declaring a multi-character `leafText` cannot silently re-break the alignment.

Add a comment naming the 0-vs-1 asymmetry so the next reader does not tidy it back to `textContent`, **and naming the deliberate twin**: `src/client/positions.ts#textblockFlatText` walks the same shape and gives every non-`hardBreak` inline leaf **zero** characters, on purpose — that walk aligns to the server's flat text, this one to PM positions. Both are correct today only because `hardBreak` is the schema's sole inline node, so **any future inline node — leaf or not — has to be considered in both walks.**

Consequences to state in the PR body:

- A query can no longer match **across** a break. `"\n"` is the separator `doc.textBetween(…, "\n", "\n")` already uses everywhere else here; it reads as a line break to `\b` and `\s`, and regex `.` does not cross it.
- **`wholeWord` gets wider, not just narrower.** `buildRegex` wraps in `\b…\b`, and `textContent` glued the segments either side of a break into one word: on the fixture above, `\bgamma\b` finds **2** matches today and **3** after, and `\balpha\b` finds **0** today and **1** after. Match counts shown to the user change on any whole-word search over a document containing a hard break. This is the fix, not a side effect, but it is user-visible.
- **A break becomes matchable.** In `regexMode`, a `\n` or `\s` query can now produce a `MatchRange` covering the break, which `replaceActive` / `replaceAll` will `tr.insertText` over — i.e. replacing a line break with text. That is the correct consequence of the break occupying one position, and it is what the old arithmetic hid.
- `replaceActive`, `replaceAll` and `buildDecoSet` are unchanged: they consume `MatchRange` and were always correct given correct input.
- **These are PM positions, not flat offsets.** `walkMatches` deliberately stays in the ProseMirror system because its consumers are `Decoration.inline` and `tr.insertText`; do not route it through `src/client/positions.ts`.
- No `$state` write is added (plugin state, not a Svelte handler), and no `data-testid` changes, so the testid snapshot is not regenerated.

## Tests

One new file, `tests/client/find-replace-hard-break.test.ts`. Not added to `tests/client/live-regions-find-replace.test.ts`, which `vi.mock`s the whole `find-replace` module and so pins nothing about matching.

Fixture `<p>alpha<br>beta gamma<br>delta gamma</p><p>plain gamma</p>`, query `gamma` unless stated.

**How the tests reach `walkMatches`.** It is module-private (the file exports only `findReplaceKey`, the three interfaces, `FindReplaceExtension`, `getFindState`, `replaceActive` and `replaceAll`), so every assertion goes through the plugin: seed with `editor.commands.find({ query, caseSensitive: false, wholeWord: false, regexMode: false })`, varying the flags per test, then read `getFindState(editor.state)!.matches`.

1. **Every match covers exactly the query.** For each match, `doc.textBetween(from, to, "\n", "\n") === "gamma"`. Fails on master at drift 1 *and* 2, so it also kills a constant `-1` correction that fixes only the first break — the reason the fixture has two breaks.
2. **Replace-all writes the right text.** `await replaceAll(editor.view, "DELTA")`, then `editor.state.doc.textBetween(0, editor.state.doc.content.size, "\n", "\n")` is exactly `"alpha\nbeta DELTA\ndelta DELTA\nplain DELTA"`. Name that reader explicitly: `editor.getText()` defaults to a `"\n\n"` block separator and a no-`leafText` `textBetween` renders hardBreaks as nothing, so either would make the expected string wrong. (`replaceAll` is `async`; with 3 matches and `CHUNK = 100` its body is synchronous to the `return`, so the `await` is for the >`CHUNK` path and unhandled rejections — do not claim it is what makes this assertion sound.) Reproduces and then forbids the character-eating corruption in the issue body; kills a fix that corrects only the decoration.
3. **Control, no hard break — must stay green under BOTH arithmetics.** Fixture `<p>alpha beta gamma</p><p>plain gamma</p>`, query `gamma`: exactly **2** matches, each satisfying (1)'s check. A break-free textblock has zero drift, so this passes identically before and after — it is the guard against an over-correction that adds an offset unconditionally. A red (3) under the old arithmetic means the control was mis-written, not that the mutation check found something.
4. **No match spans a break.** Query `"alphabeta"` returns 0 matches. Pins the `"\n"` semantics and kills a "fix" that keeps a zero-width leaf placeholder and merely subtracts.
5. **Whole-word widening.** Same two-break fixture, `wholeWord: true`, query `alpha` returns **1** match (0 on master). Pins the `"\n"` semantics from the opposite direction to (4) and covers the user-visible count change.

**Mutation-check.** Restore `textContent` from a file copy (never `git checkout`) and re-run: (1), (2), (4) and (5) must each go **red**; (3) must stay **green**.

## Review corrections (scope cut)

The fix was always one line; the spec around it had grown. Removed, not repaired:

- **Three of the eight assertions — the `replaceActive` single-match test, the `wholeWord: true` `gamma` 2→3 count, and the `regexMode` `\n` break-replacement test.** Each was added to pin a *consequence* of the chosen implementation rather than the off-by-one the issue reports, and each carried its own preconditions to state (`activeIndex` derivation, `findActiveIndex`, the caret default of a fresh editor). The surviving five — exact cover on two breaks, the replace-all text, the break-free control, no-match-across-a-break, and one whole-word widening case — discriminate the old arithmetic, the constant `-1` near-miss and the zero-width-placeholder near-miss, which is the full set of ways this fix can be got wrong. The dropped consequences stay in the PR body as user-visible behaviour changes.
- **The dated retirement note on harness describe B — removed.** The harness is run by no config (`vitest.config.ts` includes only `tests/**/*.test.ts`), so its pre-fix assertion cannot fail anything; the derivation goes in the PR body, where a reviewer will look.
- **The round-1 / round-2 correction logs and the per-line source citations — removed.** Line numbers in this file were already drifting; the spec now names symbols and files, which is what survives a rebase.

Nothing was cut that a finding depended on: the two round-2 corrections that changed the *work* — scoping the "by construction" argument to inline leaves, and stating how the tests reach a module-private `walkMatches` — are folded into the Fix and Tests sections above as plain prose.
