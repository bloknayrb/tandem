# G9a — #1663 A user-pressed "Reload from file" that loses the reload guard returns silently

Branch `fix/watcher-and-reload-silence-an-unwatched-document-a-silent-declined-reload-and-a-required-cleanup-phase-1695`. Closes #1663 unless the body names remaining work; the list is derived last. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:103` (wave 9, G9a). Probe: none named. The issue cites `src/server/mcp/file-opener.ts`, which no longer exists (ADR-034 Unit 7c). The function is now `src/server/documents/reload-family.ts:523`.

## Problem

Traced end to end on `caf54391`:
1. **Button.** `ExternalConflictBanner.svelte` has `data-testid="external-conflict-reload-btn"`, which calls `resolve("reload")`. That `POST`s `{documentId, choice, detectedAt}` to `API_EXTERNAL_CONFLICT_RESOLVE` (`:142`). The banner shows `error` only when `!res.ok`. On success it relies on the server clearing `Y_MAP_EXTERNAL_CONFLICT` to hide itself.
2. **Route.** `src/server/mcp/routes/external-conflict.ts:73` awaits `resolveExternalConflict(docId, choice, detectedAt)` and then always answers `{ success: true }`.
3. **Function.** `reload-family.ts:599` runs `const reloaded = await reloadFromDisk(...)`, and `if (reloaded)` pushes the `file-reloaded` toast. When `reloaded` is false nothing happens.
4. **Guard.** `reloadFromDisk` (`src/server/documents/watcher.ts:121`) returns `false` when `acquireReloadGuard(id)` (`:92`) fails. It logs to stderr only and leaves the conflict flag untouched.

The result is HTTP 200 with no toast. The banner re-enables its buttons and keeps showing, or disappears later when the holder's own reload clears the flag. Either way the click reads as "nothing happened". There are four guard holders (per `watcher.ts:500-512`): a watcher pass, `resolveExternalConflict` from another tab, `restoreDocumentFromBackup`, and `reloadDocumentFromMarkdown`. The last one pushes no reload toast at all. Keeping the watcher path silent is correct and stays so (`watcher.ts:513`), because that path was never asked to act.

## Fix

Server-only, in one function, and reusing the existing notification path. There is no client change and no new UI surface.

- `reload-family.ts:599-610`: add an `else` arm that pushes one notification through `pushNotification`, which is already imported there:
  - `type: "external-conflict"` (the family's own type, as at `documents/conflict.ts:60`) and `severity: "warning"`. SSE `info` goes to the tray only (`useNotifications.svelte.ts:113`) and would stay as invisible as today; `warning` always pops.
  - `documentId: safeId` and `dedupKey: \`reload-skipped:${safeId}\``. The key is **distinct** from `reload:${safeId}`, so the holder's later success toast does not coalesce over the warning or get replaced by it.
  - Message, past tense because a warning persists in the tray (`types.ts:646-655`): `` `Reload from file did not run for ${path.basename(existing.filePath)}: another reload of it was already in progress. If the conflict banner is still showing, choose again.` `` No backticks, because the toast renders the text verbatim.
- Update the comment at `:596-598` to say that a skip is now reported, and why the watcher caller differs: it is not user-initiated, and its holder pushes its own toast.
- Leave the route's response unchanged (`{success:true}`). The two silent no-ops earlier in the function, no conflict pending (`:544`) and an episode mismatch (`:551`), also stay silent. Those are the double-click and stale-banner races, and in the mismatch case the banner re-renders for the new episode.
- `tests/server/open-result-consumption.test.ts:110`: that value is a human-readable description the spec does not assert; only the keys are asserted. Change it to `"throws RELOAD_IN_PROGRESS / reports a skipped user reload (#1663)"` so it does not describe the old behaviour.
- The only `src/` edit is in a function that already imports the notification service. `tests/server/documents-open.test.ts:153` and `tests/docs/documents-boundary.test.ts` pin importers and symbols, and neither changes. No new route or MCP tool, so Critical Rule 9 does not apply. No `data-testid` changes.

## Tests

Put these in `tests/server/external-conflict.test.ts`, in the `describe("resolveExternalConflict")` block (`:273`), using its `flaggedSetup()` helper. Import `acquireReloadGuard` / `releaseReloadGuard` from `documents/watcher.js` and `getBuffer` / `resetForTesting` from `notifications.js`, and reset the notifications in `beforeEach` if the file does not already.

1. **Guard held.** Call `acquireReloadGuard(id)`, then `await resolveExternalConflict(id, "reload")`, then release the guard in a `finally`. Assert exactly one buffered notification with `dedupKey === \`reload-skipped:${id}\`` and `severity === "warning"`, and **zero** with `type === "file-reloaded"`. The conflict flag must still be present and the text must still hold the local edit. This kills today's silent skip, and also an implementation that toasts "reloaded" on a skip.
2. **Paired direction, no guard.** The same setup without the guard gives one `file-reloaded` notification and **zero** `reload-skipped:` notifications. This kills a warning placed outside the `else`.
3. **`"keep"` with the guard held** pushes no `reload-skipped:` notification. This kills a warning raised before the `choice` branch.
4. **The watcher stays silent.** The existing #1641 spec at `tests/server/adr-034-open-characterization.test.ts:658` ("one reload per reload") must stay green unchanged. Add no new watcher assertion; this change does not touch the watcher.

Mutation check: delete the new `else` arm, restoring from a file copy, and watch case 1 go red.

**No E2E run:** no client file changes. The banner's existing Playwright coverage is unaffected by construction, and the PR body says so.
