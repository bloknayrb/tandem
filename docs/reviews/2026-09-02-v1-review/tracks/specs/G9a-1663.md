# G9a — #1663 A user-pressed "Reload from file" that loses the reload guard returns silently

Branch `fix/watcher-and-reload-silence-an-unwatched-document-a-silent-declined-reload-and-a-required-cleanup-phase-1695`. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:103`. The issue cites `src/server/mcp/file-opener.ts`, which is gone (ADR-034 Unit 7c). The function now lives at `src/server/documents/reload-family.ts:523`.

## Problem

Traced on `caf54391`:
1. **Client.** `ExternalConflictBanner.svelte`'s `external-conflict-reload-btn` POSTs to `API_EXTERNAL_CONFLICT_RESOLVE`. The banner shows an error only on `!res.ok`. A same-tab double-click never reaches the server, because of `if (pending) return` and `disabled={pending !== null}`.
2. **Route.** `src/server/mcp/routes/external-conflict.ts:73` awaits `resolveExternalConflict` and always answers `{ success: true }`. A thrown error goes to `sendApiError`.
3. **Function.** `reload-family.ts:599` runs `const reloaded = await reloadFromDisk(...)`. It pushes the `file-reloaded` toast only when `reloaded` is true, and does nothing when it is false.
4. **Guard.** `reloadFromDisk` (`src/server/documents/watcher.ts:121`) returns `false` only when `acquireReloadGuard` fails (`:125-128`), and read or populate errors throw. So a `false` can only mean "another reload was in progress", for example from another tab, a restore or a source-view commit.

The user gets HTTP 200 and no toast: the click reads as "nothing happened". The watcher path's silence on the same `false` is correct, because the in-flight holder reports its own reload.

## Fix

This is a server-only change in one function, using the existing notification path. There is no client change, no route change and no new UI surface.

- `reload-family.ts:599-610`: add an `else` arm with one `pushNotification` (already imported there):
  - `type: "external-conflict"`, `severity: "warning"` (SSE `info` goes to the tray only; `warning` pops) and `documentId: safeId`.
  - `dedupKey` is `` `reload-skipped:${safeId}` ``. It must differ from `reload:${safeId}` and from `external-conflict:${id}`, or the notifications coalesce.
  - Message: `` `Reload from file did not run for ${path.basename(existing.filePath)}: another reload of it was already in progress. If the conflict banner is still showing, choose again.` `` `pushNotification` broadcasts to every tab, so the wording has to read correctly in the tab whose reload won as well.
- **The push goes in this `else` arm, not in `reloadFromDisk`'s guard-fail branch.** Putting it there would make the watcher noisy and would double-report `restoreDocumentFromBackup`, which already throws `RELOAD_IN_PROGRESS`.
- Update the comment at `:596-598` to say a skip is now reported.
- `tests/server/open-result-consumption.test.ts:110`: the description string `"throws RELOAD_IN_PROGRESS / withholds its own toast"` becomes false. Reword it to `"throws RELOAD_IN_PROGRESS / reports a skipped user reload (#1663)"`. Only the keys are asserted.
- Critical Rules 2 and 9 do not apply (no Y.Doc write, no new route or tool), and no `data-testid` changes.
