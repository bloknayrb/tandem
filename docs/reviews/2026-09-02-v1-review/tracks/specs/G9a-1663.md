# G9a — #1663 A user-pressed "Reload from file" that loses the reload guard returns silently

Branch `fix/watcher-and-reload-silence-an-unwatched-document-a-silent-declined-reload-and-a-required-cleanup-phase-1695`. Closes #1663 unless the body names remaining work; the list is derived last. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:103` (wave 9, G9a). Probe: none named. The issue cites `src/server/mcp/file-opener.ts`, which no longer exists (ADR-034 Unit 7c). The function is now `src/server/documents/reload-family.ts:523`.

## Problem

Traced end to end on `caf54391`:
1. **Button.** `ExternalConflictBanner.svelte` has `data-testid="external-conflict-reload-btn"`, which calls `resolve("reload")`. That `POST`s `{documentId, choice, detectedAt}` to `API_EXTERNAL_CONFLICT_RESOLVE` (`:142`). The banner shows `error` only when `!res.ok`. On success it relies on the server clearing `Y_MAP_EXTERNAL_CONFLICT` to hide itself.
2. **Route.** `src/server/mcp/routes/external-conflict.ts:73` awaits `resolveExternalConflict(docId, choice, detectedAt)` and then always answers `{ success: true }`. A throw goes to `sendApiError` (`:75-77`).
3. **Function.** `reload-family.ts:599` runs `const reloaded = await reloadFromDisk(...)`, and `if (reloaded)` pushes the `file-reloaded` toast. When `reloaded` is false nothing happens.
4. **Guard.** `reloadFromDisk` (`src/server/documents/watcher.ts:121`) returns `false` only when `acquireReloadGuard(id)` (`:92`) fails (`:125-128`). It logs to stderr and leaves the conflict flag untouched. Read and populate failures throw instead, and the route maps those to an HTTP error. So "another reload was already in progress" is the only thing a `false` can mean.

The result is HTTP 200 with no toast. The banner re-enables its buttons and keeps showing, or disappears later when the holder's own reload clears the flag. Either way the click reads as "nothing happened".

There are four guard holders (per the `wireFileWatcher` comment at `watcher.ts:500-514`): a watcher pass, `resolveExternalConflict` from another tab, `restoreDocumentFromBackup`, and `reloadDocumentFromMarkdown`. The last one pushes no reload toast at all.

A same-tab double-click is **not** a source. The banner's `if (pending) return` (`ExternalConflictBanner.svelte:126`) and `disabled={pending !== null}` (`:201`, `:210`) stop it before it reaches `acquireReloadGuard`, so the build stage adds no client-side busy guard. The realistic holder while a conflict is pending is a genuinely concurrent one: another tab, a restore, or a source-view commit. While a conflict is flagged, the watcher flags rather than reloads (`alreadyConflicted`, `watcher.ts:478-490`).

Keeping the watcher path silent is correct and stays so, because that path was never asked to act.

**Delivery is a broadcast, not per-requester.** `pushNotification` reaches every connected subscriber (`src/server/notifications.ts:26-32`). In the two-tab race, the tab whose reload succeeded also receives the other tab's warning. The message's "If the conflict banner is still showing, choose again" is written to read correctly in both tabs.

## Fix

Server-only, in one function, and reusing the existing notification path. There is no client change and no new UI surface.

- `reload-family.ts:599-610`: add an `else` arm that pushes one notification through `pushNotification`, which is already imported there:
  - `type: "external-conflict"` (the family's own type, as at `documents/conflict.ts:60`) and `severity: "warning"`. SSE `info` goes to the tray only (`useNotifications.svelte.ts:113`) and would stay as invisible as today; `warning` always pops (`:253`).
  - `documentId: safeId` and `dedupKey` `` `reload-skipped:${safeId}` ``. The key is **distinct** from `` `reload:${safeId}` ``, so the holder's later success toast does not coalesce over the warning or get replaced by it. It is also distinct from `flagExternalConflict`'s `` `external-conflict:${id}` ``. The type is shared, so **new and future specs select by `dedupKey`, never by `type === "external-conflict"`.** The two existing specs that find the flag's notification by type (`tests/server/external-conflict.test.ts:214` and `:806`, `getBuffer().find((n) => n.type === "external-conflict")`) stay correct only because neither holds the reload guard. They are left unchanged, and the build stage confirms they stay green.
  - Message, past tense because a warning persists in the tray (`src/shared/types.ts:646-655`): `` `Reload from file did not run for ${path.basename(existing.filePath)}: another reload of it was already in progress. If the conflict banner is still showing, choose again.` `` No backticks inside the message, because the toast renders the text verbatim.
- **The push lives in `resolveExternalConflict`'s `else` arm, NOT in `reloadFromDisk`'s guard-fail branch.** Two reasons:
  - A push there would make the file-watcher caller noisy.
  - It would double-report `restoreDocumentFromBackup`, which already turns a skip into `RELOAD_IN_PROGRESS`.
- Update the comment at `:596-598` to say that a skip is now reported, and why the watcher caller differs: it is not user-initiated, and its holder pushes its own toast.
- Leave the route's response unchanged (`{success:true}`). The two silent no-ops earlier in the function, no conflict pending (`:544`) and an episode mismatch (`:551`), also stay silent. Those are the double-click and stale-banner races, and in the mismatch case the banner re-renders for the new episode.
- `tests/server/open-result-consumption.test.ts:110`: that value is a human-readable description the spec does not assert; only the keys are asserted. Change it to `"throws RELOAD_IN_PROGRESS / reports a skipped user reload (#1663)"` so it does not describe the old behaviour.
- The only `src/` edit is in a function that already imports the notification service, and it adds no Y.Doc write (so no origin-helper question). The message carries only `path.basename`. `tests/server/documents-open.test.ts:153` and `tests/docs/documents-boundary.test.ts` pin importers and symbols, and neither changes. No new route or MCP tool, so Critical Rule 9 does not apply. No `data-testid` changes.

## Not in scope (design decisions, not deferred work)

- **The route does not return a distinguishable body.** The banner has no consumer for one, and the warning is the carrier.
- **No automatic retry once the holder releases.** The holder's own reload clears the flag, or the banner stays and the message tells the user to choose again.
