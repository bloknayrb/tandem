## Problem

Seven paths refuse to save / close / toggle and tell the user nothing.

1. `useDocumentWorkspace.svelte.ts:509` awaits `saveExactTarget` and drops its boolean. `tabs/target-save.ts` returns a bare `false` at **four** sites — `:25` (id no longer resolves), `:31` (closed OR ydoc changed across `await deps.afterActivate()`), `:33` (source view with no registered commands), `:38` (the formatted-branch re-resolve). `:38` is **defensive, not a live silent failure**: the formatted branch awaits nothing between the two resolves, so `current` is necessarily `before`. It is handled for symmetry; the PR body must say so rather than counting it as a fourth user-visible bug.
2. `saveDocumentTargetAfterSourceCommit:478` — `if (!tab || (expectedYdoc && tab.ydoc !== expectedYdoc)) return false;` — is the one refusal that does not notify (`:483`, `:497` and the delegated arms do). `SourceView.saveWithIntent` sets `errorMessage` only when `onSave` **throws**, so a returned `false` renders nothing.
3. `triggerSave` (`builtin.svelte.ts:431`) is silent on re-entry unless `announceBusy` is passed; the workspace injects it as `(documentId) => Promise<boolean>` (`:107`) and never passes it. `triggerSaveAs:268` returns `false` at `:269` with **no announce option at all**.
4. `requestToggleSourceView:293` and `requestToggleSourceViewTarget:279` optional-chain `sourceViewCommands.get(id)?.exit()`; an unregistered id resolves normally and the user stays in source view. The target arm awaits `tick()` first (`:289`); the active arm does not, and `App.svelte:2980` keys `SourceView` on `{#key activeTab.id}`, so the remount gap is a real window.
5. `enterSourceView:256` returns silently for a non-`.md` or read-only document. Every *visible* affordance is gated, but the **Ctrl+Shift+E** shortcut (`actions/keybindings.ts:102`) is not.
6. `reopenClosedTab:411` treats `{ok:true}` as "a tab arrived". It means HTTP 2xx; the tab materialises later over Yjs. The record is popped at `:412` and restored only inside `handleFailure:431`.
7. `closeTabAndRecord:331` tolerates an unresolvable id: it skips the guards and the stack push but still runs `clearSourceDraft`, `onTabClosed` and `closeTab`. No guard, no log.

## Fix

Model: `handleFailure:431` — name the thing, carry the reason, carry a `dedupKey` so a held key cannot spam toasts. No new markup and no new `data-testid`, so no snapshot regeneration; no raw colors; `$state` is written only from plain async functions.

- **`tabs/target-save.ts`** — `TargetSaveDeps` gains **optional** `onRefused?: (reason: "no-such-tab" | "tab-changed" | "no-source-commands") => void`, called at the four bare-`false` sites. **The return type stays `Promise<boolean>`.** Each of `:31` and `:38` is **two** conditions and must be split: `!after` / `!current` → `no-such-tab`; the `isSameTarget` mismatch → `tab-changed`. `:25` → `no-such-tab`; `:33` → `no-source-commands`. A `false` bubbling out of `commands.save()` or `saveCommitted()` calls **nothing** — both already notify downstream (`saveCommitted` is item 2's function; `commands.save` is `SourceView`, whose refusals are concurrent with a visible save or an on-screen error strip), so a toast there would double-report.
- **`useDocumentWorkspace.svelte.ts`**
  - `pushSaveNotification:462` gains an optional third `dedupKey` param, used by the **new** call sites only. The three existing messages (`:483`, `:497`, `:514`) are untouched — they already notify and are not among the seven items.
  - `saveDocumentTarget:509` passes `onRefused` and pushes one `warning` per reason, `dedupKey: "save-target:<reason>:<tabId>"`: `no-such-tab` → "Not saved — that document is no longer open."; `tab-changed` → "Not saved — the document reloaded while saving."; `no-source-commands` → "Not saved — the Markdown source editor wasn't ready yet." Its `Promise<void>` return and the interface at `:183` are unchanged, so no caller moves.
  - `saveDocumentTargetAfterSourceCommit:478`: split the guard — `!tab` → the `no-such-tab` copy and key; ydoc mismatch → "Not saved — the document reloaded while saving; your last edit was not written to the file.", key `save-commit:ydoc-swapped:<tabId>` — **its own key, never item 1's `save-target:tab-changed:<tabId>`**: `coalesceActivity` and `pushTransient` both spread the NEWER notification over the matched row (`{ ...notification, id: existing.id, count: existing.count + 1 }`), so two different messages on one key collapse to a single tray row carrying whichever arrived last, and the "your last edit was not written to the file" half — the only one reporting lost work — would be overwritten by item 1's milder copy. Both `warning`. The copy states a consequence, not an instruction: a `warning` persists in the tray, which is a log. **No reassurance about surviving edits** — `commit()` clears the draft before `onSave`, and the `{#key}` remount drops it.
  - Injected `triggerSave` type `:107` widens to `(documentId: string, opts?: { announceBusy?: boolean }) => Promise<boolean>`; `:501` passes `{ announceBusy: true }`. **No `App.svelte` edit** — `:1890` passes the real `triggerSave` by reference and it already has that signature.
  - `requestToggleSourceView:293`: `await tick()` before the lookup (mirroring `:289`), then an explicit `const commands = …get(id) ?? null` — absent → `warning`, "Couldn't leave source view — the Markdown source editor was still loading.", key `source-view-exit:<id>`. Same at `:290`.
  - Same function, the ENTER arm (item 5): read-only → `info` "Source view isn't available — this document is read-only.", key `source-view-unavailable:read-only:<tabId>`; non-`.md` → `info` "Source view is only available for Markdown documents.", key `source-view-unavailable:not-markdown:<tabId>`. Both keyed because Ctrl+Shift+E is held-repeatable. **Format is checked first** — it is the durable rule: a read-only `.md` does not match the format arm and falls through to the read-only arm, which is the right message, while a read-only non-`.md` tab (an uploaded `.docx`; `App.svelte:1862` derives `isReadOnly` from the active tab's own `readOnly`, so that state is reachable) must be told the rule it can never satisfy. Read-only-first is the order that misreports: it answers "this document is read-only" to a read-only `.docx`, implying that promoting it to a writable file would enable source view, which `canSourceView`'s format gate (`:207-209`, `format === "md"` first) never will. Both branches read `opts.getActiveTab()` / `opts.getIsReadOnly()`, not the `canSourceView` boolean, which cannot say which half failed. An active id that resolves to no tab returns **silently** (a transient between tab swaps, with no format to name).
  - `reopenClosedTab`: after `result.ok`, poll `opts.getTabs()` for `rec.filePath` **inside the `try`** so `inflightReopens` holds across the wait; the first check runs before any wait. Interval/ceiling are **injectable** — `CreateDocumentWorkspaceOpts` gains optional `reopenPollMs` / `reopenTimeoutMs` defaulting to `250` / `8000`; `App.svelte` passes neither. On timeout: `closedTabStack.push(rec)` plus a notification with `handleFailure`'s `type: "general-error"` but deliberately **one severity lower — `warning`, not `error`** (the server accepted the open and the tab may yet land): "Couldn't reopen `<basename>`: the server accepted it but no tab appeared.", key `reopen-no-tab:<path>`. Restoring is safe if the tab lands late — the `existing` check at `:417` turns the next Ctrl+Alt+T into an activate.
  - `closeTabAndRecord:331`: if the id does not resolve, `console.warn` and return **before any side effect** — and return **`true`**, not `false`. `false` is reserved for "the user stopped the batch here" (#1824 item H, docblock `:327-330`) and `closeEachUntilCancelled:393` `break`s on it, so `false` for a ghost id would silently truncate a bulk close. Update that docblock. What makes a ghost id unreachable today is that `closeOtherTabs:400` sources ids from `getOrderedTabs()` while this resolves against `getTabs()`, and production's `orderedTabs` is `$derived` over `getTabs()` with `.filter(Boolean)`; the harness lets those diverge, which is what makes the guard testable.
- **`actions/builtin.svelte.ts:269`** — announce on the `saveAsInflight` early return with `notifyUser("info", "A Save As is already in progress…", { dedupKey: "save-as-inflight", id: "save-as-inflight" })`, byte-for-byte the shape `triggerSave:437` uses. Unconditional, no `announceBusy` flag: `triggerSaveAs` has one caller (`:486`) and it is always a user gesture.

## Assumptions (product decisions — all recorded for Bryan)

- Severity split: a refusal that loses a save is `warning` (persists in the tray as a log, past tense, no trailing "Try again."); a rule explanation is `info` (expires, may instruct).
- Item 1 reports through an injected `onRefused` callback rather than a returned reason union: identical user-visible messages, and nothing outside `target-save.ts` + the workspace sees a changed type.
- Only the new notifications carry `dedupKey`s. The three pre-existing `pushSaveNotification` messages are left byte-identical — they already notify and are not among the seven items.
- **Two different messages never share one `dedupKey`.** The tray coalesces on the key and keeps the newer message, so a shared key silently replaces one report with the other — which is the information loss this issue exists to fix. Two sites emitting the *same* message may share a key (item 2's `!tab` arm deliberately reuses item 1's `no-such-tab` copy and key); item 2's ydoc-mismatch arm, whose copy differs, gets its own.
- Item 5 notifies only from `requestToggleSourceView` (the ungated shortcut path). `enterSourceView`, `enterSourceViewTarget` and `requestToggleSourceViewTarget` stay silent, as the issue directs for the gated twins.
- Item 7 logs and does not notify: a ghost tab id is unreachable from the UI today, so a toast would name a state the user cannot cause.

## Review corrections (post-cut)

Two findings on the cut plan, both adopted as given. Neither adds machinery: one reverses a guard order and one splits a key.

- **Item 5's guard order was backwards, and its justification was false.** The Fix bullet said read-only must be checked first because "a format-first implementation answers 'only available for Markdown documents' for a read-only Markdown file". It does not: under format-first a read-only `.md` fails the format test, falls through, and reaches the read-only arm. Read-only-first is the order that misreports, and it does so in a reachable state — a read-only non-`.md` tab (an uploaded `.docx`; `App.svelte:1862` derives `isReadOnly` from the active tab's own `readOnly`) is told it is read-only, implying that making it writable would enable source view, which `canSourceView` (`useDocumentWorkspace.svelte.ts:207-209`, `format === "md"` first) never will. Fixed: format is checked first, with the real reason written out. Tests §5(c) gained a **third** case, `harness({ readOnly: true, tabs: [tab({ id: "a", format: "docx" })] })` — the two cases the cut plan specified each make exactly one condition true, so both orderings pass them and neither could have caught this.
- **Two different messages shared one `dedupKey`.** Item 1's `tab-changed` refusal ("Not saved — the document reloaded while saving.") and item 2's ydoc-mismatch refusal ("…your last edit was not written to the file.") were both keyed `save-target:tab-changed:<tabId>`. `useNotifications` coalesces on the key and spreads the newer notification over the matched row (`coalesceActivity`: `{ ...notification, id: existing.id, count: existing.count + 1 }`; `pushTransient` likewise), so in a session where both fire for one tab the tray — a log at `warning` — shows one row carrying whichever came last, and the only message that reports lost work can be overwritten by the milder one. Fixed: item 2's arm takes `save-commit:ydoc-swapped:<tabId>`, Tests §3 pins that key by exact string on the `:991` spec, and the Assumptions now state the rule (two different messages never share a key; two sites emitting the same message may).
