# C — #1779 Solo copy promises "won't see your comments or edits"; only the user's annotations are held

Branch `fix/privacy-and-authority-1769`. Closes #1779 (the copy; the optional `selectedText` gating in its body is declined below, and the decline is recorded on the issue). Ledger: `docs/reviews/2026-09-02-v1-review/areas/product.md:17`, `areas/annotations.md:43`. Probe: `src/server/events/queue.ts:182-187` and `:205-215` (what Solo holds), `awareness.ts:357-391` (what it does not).

## Problem

Three user-facing sentences describe Solo as hiding the user's work from the AI:

- `src/client/editor/toolbar/ModeToggle.svelte:30` — "your AI pauses and won't see your comments or edits until you switch back to Tandem".
- `sample/welcome.md:28` (mirrored byte-for-byte in `tests/fixtures/welcome-snapshot.md:28`, which `tests/server/tutorial-annotations.test.ts:97-101` compares against the live file's flat text).
- `docs/user-guide.md:296` — "the AI's pending annotations are held back from the document" (an opacity fade plus rail hide, `index.html`; `tandem_comment` in Solo still creates, decorates and toasts).

What Solo actually holds, from the code: the user's own `annotation:created` / `annotation:edited` / user `annotation:reply` events are dropped before buffering (`queue.ts:245`) and every other non-chat event is withheld from external consumers (`:186`); the pull surfaces hide the user's annotations and replies (`mode.ts:84-91`). **Chat is delivered in both directions regardless of mode** (`queue.ts:185` "the always-delivered channel"; the `chatMessages` bucket in `awareness.ts:362-376` has no mode gate; the shipped skill `:74` tells Claude to answer chat in Solo). `tandem_getTextContent`, `tandem_getContext`, `tandem_search` and `activity.selectedText` (`awareness.ts:389-391`) are ungated. **The wave-table note's phrase "what is actually held (annotations and chat)" is wrong on chat — the copy must not say chat is held, and the build must not "correct" this spec back to the note.** The PR body records this correction against the wave table so the reviewer does not reopen it.

Two more copies of the retired wording exist as code comments, not user-facing: `src/client/hooks/useAiReadiness.svelte.ts:273` and `:740` ("the AI won't see the user's edits/comments"), and `tests/client/status-ai-view.test.ts:143-144` ("Solo already says the AI won't see edits"). Tidied while in the files so the next grep for "won't see" does not find the promise restated as fact.

## Fix

Copy only; no behaviour change. **One sentence, reused from the surface that already got it right**: `src/client/status/status-ai-view.ts:109` (`SOLO_PAUSED.title`, #1287) reads "your comments and replies aren't sent to the AI until you switch to Tandem (chat and document edits still work)". The two Solo surfaces must not drift, so the toggle takes that wording:

- `ModeToggle.svelte:30` `title`: "Write undisturbed — your comments and replies aren't sent to your AI until you switch to Tandem (chat and document edits still work)." — **no "back", and WITH the trailing period**, so that after the prefix and the one `your AI`/`the AI` substitution the tail is byte-identical to `SOLO_PAUSED.title` (`status-ai-view.ts:108-109`: "Solo mode — your comments and replies aren't sent to the AI until you switch to Tandem (chat and document edits still work)."). Round 1 prescribed "switch back to Tandem" with no period, which differed from the status-bar sentence in four places while the test claimed two. The Tandem button's title (`:38`) is accurate; leave it. No `data-testid` changes (Critical Rule 7).
- `sample/welcome.md:28`: "**Solo mode** — write undisturbed. The comments and replies you write are held from your AI until you switch back to Tandem; it can still read the document and answer chat." Apply the identical edit to `tests/fixtures/welcome-snapshot.md:28`. Line 28 is not a tutorial anchor — `TUTORIAL_ANNOTATIONS` `targetText`s are "highlight text and your AI sees it" (`:3`), "edit this document at the same time" (`:9`), "accept or dismiss" (`:32`) and "simplify onboarding" (`:50`) — and the new sentence must not contain any of those substrings (`indexOf` would drift). Do not touch any other line.
- `docs/user-guide.md:296`: "**Solo** — the AI's pending annotations are faded and the annotation rail is hidden so you can write without reacting to them; the AI can still read the document and add annotations. Resolved annotations (accepted/dismissed) are always visible regardless of mode." **And `:293`'s first clause**, which otherwise contradicts the bullet two lines below it ("It holds work back in *both* directions — the AI's annotations are held from you, and your own comments are held from the AI"): rewrite to "It works in *both* directions — the AI's pending annotations are faded and its rail hidden for you, and your own comments and replies are held from the AI." `:298` already describes the held direction correctly; `:302-312` (the hold table) is accurate and stays. **J2 note, mirroring C-1769's for `store.ts`**: J2 (`fix/product-copy-1814`, unmerged) touches "docs" without naming which; before the implement stage, check J2's file set for `docs/user-guide.md` and rebase before shipping. If J2 owns that file, cut the `:293`/`:296` edit to a follow-up rather than resolving a copy conflict in this PR — the toggle, the welcome file and the status bar are the load-bearing surfaces; the user guide is the one no test reads.
- `status-ai-view.ts:104-109` already reads "Solo · comments held" with the sentence above — no edit.
- `useAiReadiness.svelte.ts:273` and `:740`: rephrase to "the user's comments and replies are withheld from the AI" (comments only; no behaviour). `tests/client/status-ai-view.test.ts:143-144`: the comment becomes "Solo already says comments and replies are withheld, which is stronger and more relevant than 'nothing is delivering them'".

`selectedText` gating (the issue's optional half): **declined, and the decline covers the whole `activity` bucket, not `selectedText` alone.** `awareness.ts:381` destructures `{ selection, activity }` from `store.getUserAwareness()` and `:388-391` delivers `activity` on the pull path with no mode gate — `output-schemas.ts:253-258` declares it as `{ isTyping, cursor, lastEdit, selectedText }` — so in Solo `tandem_checkInbox` carries the timing signals (`isTyping`, `cursor`, `lastEdit`) that the push side explicitly withholds (`queue.ts:140-148`: events "carry TIMING — they tell an idle session 'the user is doing things right now, go look', which is precisely what Solo promises not to do"). A decline recorded against `selectedText` only would be narrower than what ships. The rationale is the same for all four fields: `awareness.ts:389` feeds the skill's selection-context rule (`SKILL.md:78`, "In Solo mode, hold reactions until the user sends a chat message"), chat itself is delivered in Solo and needs the context, and document text is ungated anyway. The copy above says chat and document edits still work, which covers the selection; it makes no claim about activity, so it is honest by omission. **The decline is written into #1779's closing comment, quoting this paragraph and naming the `activity` object with its four fields**, so it is answerable from a tracked surface after the issue closes — the workflow's `bryan[]` array is a per-run return value, not a tracked file. If Bryan wants any of it held, it is a queue/awareness gate with its own spec.
