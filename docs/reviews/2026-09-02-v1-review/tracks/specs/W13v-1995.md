# W13v — #1995 a superseded spawn's late exit acts on its successor; `startInternal` ignores a breaker tripped during its await

Branch `fix/server-and-cli-small-correctness-fixes-2003`. Closes #1995. Ledger: no `areas/*.md` row — filed from G1 (#1866 #1868 #1867 #1780) implementation, which fixed the third symptom of the same root; tracked home is the wave 13 row in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: read from source, not reproduced — the issue says so.

## Problem

Both items share one root, already documented in `spawnOnce`'s exit handler: `stopInternal` does not wait for a handle that is already `killed` (the stdin-gone #1757, receipt #1867 and sign-in #1780 kills all leave one), and `respawn` then lowers `stopRequested` and `breakerTripped`. So a user relaunch can start a new spawn before the old one's `exit` — or its `error` — lands.

**1. A superseded spawn's late event acts on the successor, in three places.** `confirmTimer` is supervisor-scoped (`supervisor.ts:1199`), while `resumeConfirmed` is per-spawn (`:1217`). G1 added `const wasCurrent = child === spawned` and guards the *restart* on it; three statements above that guard are not identity-guarded:

```ts
// spawned.on("exit"), :1641
const wasCurrent = child === spawned;
if (wasCurrent) child = null;
if (confirmTimer) { clearTimeout(confirmTimer); confirmTimer = null; }   // (a)
...
if (shouldClearSession({ resuming: plan.resuming, code, resumeConfirmed })) {
  clearSavedSession();                                                   // (b)
}
...
if (stopRequested || !wasCurrent) return;                                // guard is HERE

// spawned.on("error"), :1601 — the SAME unguarded clear, ABOVE its own
// identity guard at :1617
if (confirmTimer) { clearTimeout(confirmTimer); confirmTimer = null; }   // (c)
```

(a) and (c) are one defect in two handlers: when the spawn firing the event has been superseded, `confirmTimer` holds the **successor's** handle. Clearing it leaves the successor's `resumeConfirmed` false for its whole life, so `shouldClearSession` (`:377`) is satisfied by any later non-zero exit and `clearSavedSession()` deletes `launcher-session.json` — the #1169/#1268 class.

(b) is the same class one step earlier: `shouldClearSession` runs on the *exiting* spawn's `plan.resuming`/`resumeConfirmed`, but the unlink hits the single shared session file the successor is now running on. A superseded resuming spawn exiting **non-zero** (on Windows `kill("SIGTERM")` surfaces as a non-null code) deletes it directly, no timer involved.

The error handler's comment at `:1603-1606` justifies (c) by the leaked-timer risk — "the 30s timer from a failed resuming spawn would fire later and null out confirmTimer for a subsequent spawn". The callback change below removes that risk, after which (c) is purely harmful.

**2. `startInternal` re-checks `stopRequested` after `await buildPlan()` but not `breakerTripped`.** It opens with `if (child) return; if (breakerTripped) return;` (`:1821-1822`), awaits `buildPlan()` (`:1825`), then re-checks only `stopRequested`. A trip landing inside that await still spawns.

## Fix

All in `src/server/launcher/supervisor.ts`. No new runtime state, no new runtime timer.

- **`spawned.on("exit")`:** move **both** (a) and the `shouldClearSession`/`clearSavedSession` block (b) inside `if (wasCurrent)`, beside `child = null`. Comment: a superseded spawn's verdict must not act on state the successor now owns — the timer slot it no longer holds, and the one `launcher-session.json` the successor is running on.
- **`spawned.on("error")`:** move (c) into the existing `if (child === spawned)` block at `:1617` and rewrite the stale `:1603-1606` comment. **Both long-lived handlers clear the shared slot and both must be identity-guarded**; `stopInternal` (`:1907`) is the only clear correct unguarded, because it runs against the current child by construction. **No test:** Node emits `'error'` on a child only for spawn/kill/send failure, so a superseded-then-error sequence is not constructible without a `spawn` seam this file does not have; put that rationale in the source comment beside the guard (see Tests).
- **`spawnOnce`'s confirmation timer:** hold the handle locally and let the callback null the shared slot only if it still owns it —
  ```ts
  const timer = setTimeout(() => {
    resumeConfirmed = true;
    if (confirmTimer === timer) confirmTimer = null;
  }, resumeConfirmMs);
  confirmTimer = timer;
  ```
  This is what makes the two handler guards complete: a superseded spawn's own leaked timer would otherwise null the successor's handle out of the slot, leaving `stopInternal` nothing to cancel. **Recorded consequence:** a superseded spawn's timer is then cancelled by nothing and stays pending until it fires (at most `RESUME_CONFIRM_MS`). Deliberate and harmless — the callback sets only its own dead spawn's `resumeConfirmed` and cannot touch the slot — and the callback comment must say so.
- **`startInternal`, after `await buildPlan()`:** `if (breakerTripped) return;` beside the existing post-await `stopRequested` check, same `console.error` shape. The pre-await check stays: this is a re-check of a flag that moves during the await, exactly like `stopRequested`. **No test:** every trip site (`:1537` sign-in, `:1625` ENOENT, `:1771` `scheduleRestart`) fires from a live child's handlers, and `startInternal` has already returned at `:1821` if `child` is set; the real window is `scheduleRestart` calling `startInternal` without the op lock, which the harness cannot reach without a test-only setter. Put that rationale in the source comment.
- **Test seam: `resumeConfirmMs?: number` on `SupervisorOpts`**, defaulted to `RESUME_CONFIRM_MS`, read once into a `const` beside `wakeLatchMs` (`:698`) and used **only** at the confirmation timer (`:1220`) — a 30-second safeguard no test can otherwise reach, the same justification `wakeLatchMs` / `turnReceiptMs` / `restartBackoffsMs` carry. Its docblock must say it is **not** wired to `RESUME_CONFIRM_MS`'s second use at `:1847` (the `restartIndex` backoff reset), a different timer sharing the constant.

Critical Rule 3 holds by construction: the supervisor logs through `console.error` and the new line must too — the stdin channel to the child must not gain a writer. No Y.Doc, Y.Map key, MCP tool or `/api` route: Rules 1, 2 and 9 are not engaged.

## Tests

**Home: `tests/server/launcher/stream-json-protocol.test.ts`,** in a new describe. That is where the spawn harness lives — `stub-claude-cli.cjs`, the `TANDEM_CLAUDE_CMD` sentinel, `TANDEM_REAPER_PATH`, the record dir (`:30-90`). `tests/server/launcher/supervisor.test.ts` cannot host these: it never spawns a child and says so at `:95`.

**Timers real, not faked** — these drive a real child over a real pipe, so `vi.useFakeTimers()` would stall `stopInternal`'s escalation ladder. Pass `resumeConfirmMs` in the low hundreds of milliseconds and wait on real events. To make a *late* exit reproducible rather than racy, add `TANDEM_STUB_CLAUDE_EXIT_DELAY_MS` beside the existing `TANDEM_STUB_CLAUDE_TURN_DELAY_MS` in the stub, so spawn A's exit can be held until `respawn()` has made B current. The supersede itself is the existing `TANDEM_STUB_CLAUDE_CLOSE_STDIN_AFTER_FIRST_TURN` path.

1. **A superseded spawn's late EXIT does not act on its successor.** Resuming spawn A; stdin-gone kill leaves a `killed` handle; `respawn()` makes resuming spawn B current; *then* A's exit lands with a **non-zero code** — the discriminating case, since a zero/null code passes with the hole intact. Assert `launcher-session.json` still exists immediately (kills unguarded (b)), and still exists after `resumeConfirmMs` elapses and B exits non-zero (kills unguarded (a)).
2. **The current spawn's own exit still cancels its timer and still clears its session.** A single resuming spawn exits non-zero before `resumeConfirmMs`; assert the session **is** cleared and that waiting past `resumeConfirmMs` afterwards throws nothing. Kills an over-fix that drops either clear, or that gates `shouldClearSession` on something that never holds.

**No test for guard (c), the error-handler clear.** It ships on the argument in the Fix section — the same treatment the `breakerTripped` re-check gets — and that rationale must be written into the source comment beside the guard. The handler is attached to a real `ChildProcess` (`spawned.on("error", ...)`, `:1601`) and Node emits `'error'` on a child only for spawn failure, kill failure or send failure; a spawn that started, accepted a turn and was then superseded cannot produce one. The sequence the killing spec would need — A running, stdin-gone kill, `respawn()` makes B current, *then* A's `error` lands — is therefore not constructible in this harness: `stream-json-protocol.test.ts` has no `spawn` mocking by design (`:11-13`) and `SupervisorOpts` (`:56-116`) exposes no `spawn` seam. Adding one is a larger change than this group's tier; if the guard must be tested, the seam has to be specified first.

## Done when

Specs 1–2 are green; the breaker re-check's and guard (c)'s rationales are in the source comments; the existing supervisor, stream-json and turn-delivery suites are unchanged and green; `npm run typecheck`, `npm run typecheck:tests` and `npm test` pass.

## Not in scope

Making `stopInternal` await an already-`killed` handle — that is the root, it changes stop latency for every caller, and the issue proposes the guards instead; #1822 items 4–6 and #1994; any change to `shouldClearSession`'s predicate or to `RESUME_CONFIRM_MS`'s value.

## Review corrections (scope cut)

**Removed**

- *Old test 4*, the "stale callback does not steal the successor's handle" spec. The spec itself recorded that the callback guard has **no public observable** (`stop()` sends SIGTERM, so `code === null` and `shouldClearSession` cannot fire) and that the test was a liveness pin, not a killing one. A spec that cannot fail on the defect it names is noise; the callback guard ships on the argument in the Fix section, where that argument already lived.
- *Old test 5*, which existed only to say that the breaker re-check has no reachable test. Compressed into the Fix bullet that owns the change, so the rationale sits next to the line it justifies instead of masquerading as a test.
- *The round-1 corrections log* and the duplicated restatements of the (a)/(c) equivalence across Problem and Fix.

**Kept, deliberately**

- All three guards, the callback identity fix and the breaker re-check — each is one of the two items #1995 names, and the error-handler guard (c) is the blocking finding's own demanded change.
- The two test seams (`resumeConfirmMs` on `SupervisorOpts`, `TANDEM_STUB_CLAUDE_EXIT_DELAY_MS` on the stub). Neither is new product mechanism: the opts sibling is the file's established pattern for safeguards measured in tens of seconds, and without them specs 1–3 cannot run at all — #1995's only evidence of correctness is those specs.
