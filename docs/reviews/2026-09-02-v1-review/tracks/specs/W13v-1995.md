# W13v — #1995 a superseded spawn's late exit clears the successor's `confirmTimer`; `startInternal` ignores a breaker tripped during its await

Branch `fix/server-and-cli-small-correctness-fixes-2003`. Closes #1995. Ledger: no `areas/*.md` row — filed from G1 (#1866 #1868 #1867 #1780) implementation, which fixed the third symptom of the same root and left these two; tracked home is the wave 13 row in `docs/plans/2026-09-06-open-issues-sweep.md`. Probe: read from source, not reproduced — the issue says so, and item 2 was observed once in `tests/server/launcher/supervisor-turn-delivery.test.ts` before G1's exit-handler guard closed the window that exposed it.

## Problem

Both items share one root, already documented in `spawnOnce`'s exit handler: `stopInternal` does not wait for a handle that is already `killed` (the stdin-gone #1757, receipt #1867 and sign-in #1780 kills all leave one), and `respawn` then lowers `stopRequested` and `breakerTripped`. So a user relaunch can start a new spawn before the old one's `exit` — or its `error` — lands.

**1. A superseded spawn's late event acts on the successor, in three places.** `confirmTimer` is supervisor-scoped (declared beside `child`, `supervisor.ts:1199`), while `resumeConfirmed` is per-spawn (a `let` inside `spawnOnce`, `:1217`). G1 added `const wasCurrent = child === spawned` and guards the *restart* on it — but three statements above that guard are not identity-guarded:

```ts
// spawned.on("exit"), :1641
const wasCurrent = child === spawned;
if (wasCurrent) child = null;

// Cancel the confirmation timer — the process has already exited.
if (confirmTimer) { clearTimeout(confirmTimer); confirmTimer = null; }   // (a)
...
if (shouldClearSession({ resuming: plan.resuming, code, resumeConfirmed })) {
  clearSavedSession();                                                   // (b)
}
...
if (stopRequested || !wasCurrent) return;
```

```ts
// spawned.on("error"), :1601 — the SAME unguarded clear, ABOVE its own
// identity guard at :1617
if (confirmTimer) { clearTimeout(confirmTimer); confirmTimer = null; }   // (c)
...
if (child === spawned) { child = null; ... }
```

(a) and (c) are one defect in two handlers: when the spawn firing the event has been superseded, `confirmTimer` no longer holds that spawn's handle — `spawnOnce` overwrote it with the successor's. Clearing it leaves the successor's `resumeConfirmed` false for its whole life, so `shouldClearSession({resuming, code, resumeConfirmed})` (`:377`) is satisfied by **any** later non-zero exit and `clearSavedSession()` deletes `launcher-session.json`. The conversation pointer is lost — the #1169 / #1268 class.

(b) is the same class reached one step earlier: `shouldClearSession` runs on the *exiting* spawn's `plan.resuming` / `resumeConfirmed` but its effect — the unlink — is on the single shared session file the successor is now running on. A superseded resuming spawn that exits with a **non-zero code** (on Windows `kill("SIGTERM")` surfaces as a non-null code; the stdin-gone / receipt / sign-in kills are exactly this scenario) deletes the successor's session pointer directly, with no timer involved.

The error handler's existing comment at `:1603-1606` justifies (c) by the leaked-timer risk — "the 30s timer from a failed resuming spawn would fire later and null out confirmTimer for a subsequent spawn". That risk is what the confirmation-timer change below removes, so after this fix (c) is purely harmful.

**2. `startInternal` re-checks `stopRequested` after `await buildPlan()` but not `breakerTripped`.** The function opens with `if (child) return; if (breakerTripped) return;` (`:1821-1822`), then awaits `buildPlan()` (`:1825`), then re-checks only `stopRequested`. A trip landing inside that await — a superseded spawn's late `error` with `code: "ENOENT"` (`:1625`), or `scheduleRestart`'s own windowed trip (`:1771`) — still spawns.

## Fix

Three guards plus one test seam in `src/server/launcher/supervisor.ts`. No new runtime state, no new runtime timer.

- **`spawned.on("exit")`:** move **both** the `confirmTimer` clear (a) and the `shouldClearSession`/`clearSavedSession` block (b) inside `if (wasCurrent)`, beside `child = null`. Comment: a superseded spawn's verdict must not act on state the successor now owns — the timer slot it no longer holds, and the single `launcher-session.json` the successor is running on.
- **`spawned.on("error")`:** move the `confirmTimer` clear (c) into the existing `if (child === spawned)` block at `:1617`, the same identity discipline, and rewrite the stale comment at `:1603-1606` — it credits this clear with preventing a leaked timer from nulling a subsequent spawn's slot, which the callback guard below now handles. **Both long-lived handlers clear the shared slot and both must be identity-guarded.** `stopInternal` (`:1907`) is the only clear that is correct unguarded, because it runs against the current child by construction.
- **`spawnOnce`'s confirmation timer:** hold the handle in a local and have the callback null the shared slot only if it still owns it —
  ```ts
  const timer = setTimeout(() => {
    resumeConfirmed = true;
    if (confirmTimer === timer) confirmTimer = null;
  }, resumeConfirmMs);
  confirmTimer = timer;
  ```
  Same identity discipline, and it is what makes the two handler guards complete: a superseded spawn's own leaked timer would otherwise fire later and null the successor's handle out of the shared slot, leaving `stopInternal` with nothing to cancel. **Recorded consequence:** once the handler clears are identity-guarded, a superseded spawn's own timer is cancelled by nothing and stays pending until it fires (≤ `RESUME_CONFIRM_MS`). That is deliberate and harmless — the callback sets only its own spawn's dead `resumeConfirmed` and cannot touch the shared slot — and the comment on the callback must say so, so a later reader does not "fix" it back.
- **`startInternal`, after `await buildPlan()`:** `if (breakerTripped) return;` beside the existing post-await `stopRequested` check, sharing its `console.error` shape ("Breaker tripped while building the spawn plan — not spawning"). The pre-await `if (breakerTripped) return;` stays: this is a re-check of a flag that can move during the await, exactly like `stopRequested`.
- **Test seam: `resumeConfirmMs?: number` on `SupervisorOpts`**, defaulted to `RESUME_CONFIRM_MS`, read once into a `const` beside `wakeLatchMs` (`:698`) and used **only** at the confirmation timer (`:1220`). Its docblock takes the same justification as `wakeLatchMs` / `turnReceiptMs` / `restartBackoffsMs`: a safeguard no test can reach in under 30 s is an unverified safeguard. **It must not be wired to `RESUME_CONFIRM_MS`'s second use at `:1847`** (the `restartIndex` backoff reset), which is a different timer that merely shares the constant — say so in the docblock.

Rules that bite: nothing here touches a Y.Doc, a Y.Map key, an MCP tool or an `/api` route — Critical Rules 1, 2 and 9 are not engaged. Critical Rule 3 holds by construction: the supervisor already logs through `console.error`, and the new line must too — a `console.log` here would still be redirected in `index.ts`, but the file's convention is `console.error` and the stdin channel to the child must not gain a writer.

## Tests

**Home: `tests/server/launcher/stream-json-protocol.test.ts`,** in a new describe. That is where the spawn harness actually lives — `stub-claude-cli.cjs`, the `TANDEM_CLAUDE_CMD` sentinel, `TANDEM_REAPER_PATH`, the record dir and the per-pid turn records are all set up there (`:30-90`). `tests/server/launcher/supervisor.test.ts` **cannot** host these: it never spawns a child, references no stub, and says so at `:95` ("We can't fully exercise spawn without a real binary"). Reusing the existing harness in place beats duplicating it into a new file; the file header gains one clause naming the confirmation-timer lifecycle as its second subject.

**Timers: real, not faked.** These specs drive a real child over a real pipe, so `vi.useFakeTimers()` would stall `stopInternal`'s escalation ladder and the harness's own waits. The seam replaces it: pass `resumeConfirmMs` in the low hundreds of milliseconds and wait on real events. A stub knob is needed to make a *late* exit reproducible rather than racy — add `TANDEM_STUB_CLAUDE_EXIT_DELAY_MS` beside the existing `TANDEM_STUB_CLAUDE_TURN_DELAY_MS`, so spawn A's exit can be held until after `respawn()` has made B current. The supersede itself is the existing `TANDEM_STUB_CLAUDE_CLOSE_STDIN_AFTER_FIRST_TURN` path: the stdin-gone kill (#1757) leaves a `killed` handle, `stopInternal` early-returns without awaiting it, and `respawn()` spawns B.

1. **A superseded spawn's late EXIT does not act on its successor.** Drive: resuming spawn A; stdin-gone kill leaves a `killed` handle; `respawn()` so resuming spawn B is current; *then* A's exit lands, with a **non-zero code** — the discriminating case. Assert `launcher-session.json` **still exists** immediately (kills unguarded (b)), and that after `resumeConfirmMs` elapses and B exits non-zero the file **still exists** (kills unguarded (a)). A zero/null stale exit code passes with the hole intact, so the non-zero code is load-bearing and the spec must say so.
2. **A superseded spawn's late ERROR does not act on its successor.** Same setup as (1), but deliver A's `error` (a non-ENOENT spawn error, so the breaker is not involved) instead of its exit; advance past `resumeConfirmMs`; exit B non-zero; assert `launcher-session.json` still exists. **This is the spec that kills an exit-handler-only fix** — (1) alone stays green while (c) remains unguarded.
3. **The current spawn's own exit still cancels its timer and still clears its session.** A single resuming spawn exits non-zero before `resumeConfirmMs`; assert the session **is** cleared, and that waiting past `resumeConfirmMs` afterwards throws nothing. Kills an over-fix that drops either clear outright, or that gates `shouldClearSession` on something that never holds.
4. **The stale callback does not steal the successor's handle.** After (1)'s setup, let A's own confirmation deadline elapse while B is current, then `stop()` and `relaunch()`; assert both resolve and the supervisor comes back `running`. **Recorded bound:** the callback guard's direct effect — the shared slot not being nulled — has **no public observable**; `stop()`'s own kill is a SIGTERM (`:1924`), so `code === null` and `shouldClearSession` can never fire from it. This spec is therefore a liveness pin, not a killing test, and the one-line guard ships on the argument in the Fix section rather than on an assertion. Stating that is the point: an assertion dressed up as discriminating here would pass either way.
5. **`startInternal`'s post-await breaker re-check ships with a recorded no-test rationale.** No public path trips the breaker while `startInternal` awaits `buildPlan()`: all three trip sites (`:1537` sign-in, `:1625` ENOENT, `:1771` `scheduleRestart`'s window) fire from a live child's handlers, and `startInternal` has already returned at `:1821` if `child` is set. The production window is real — `scheduleRestart` calls `startInternal` **without the op lock** after `child` is nulled, while a superseded spawn's `error` can still land — but it is not reachable from the harness without a test-only setter, which is not worth minting for a one-line symmetry with the `stopRequested` re-check directly above it. Write the rationale into the code comment, not only here.

## Done when

Specs 1–4 are green; spec 5's rationale is in the source comment; the existing supervisor, stream-json and turn-delivery suites are unchanged and green; `npm run typecheck`, `npm run typecheck:tests` and `npm test` pass.

## Not in scope

Making `stopInternal` await an already-`killed` handle — that is the root, it changes stop latency for every caller, and the issue proposes the guards instead; #1822 items 4–6 (cwd/env confinement) and #1994 (macOS reaper orphan), which the issue states do not overlap; any change to `shouldClearSession`'s predicate or to the value of `RESUME_CONFIRM_MS`.
