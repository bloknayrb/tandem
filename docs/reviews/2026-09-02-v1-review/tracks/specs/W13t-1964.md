# W13t — #1964 Settings radiogroups ignore the read-only contract

Branch `fix/settings-read-only-radiogroup-and-desktop-token-panel-1964`. Closes #1964. Ledger:
`docs/plans/2026-09-06-open-issues-sweep.md:464` (the K-client row, one of #1824's six carve-outs).

## Problem

`src/client/components/AppearanceSettings.svelte` and `src/client/components/EditorSettings.svelte`
hold **seven** `createRadioGroup(...)` call sites — `themeRg` (`:48`), `primaryTabRg` (`:53`),
`textSizeRg` (`:58`), `densityRg` (`:63`) in Appearance; `editorFontRg` (`:71`), the
`fontByExtensionRgs[row.format]` factory (`:82`) and `measureRg` (`:141`) in Editor. Every one
omits the hook's 4th argument, `isDisabled?: (v: T) => boolean`
(`src/client/hooks/useRadioGroup.svelte.ts:22`). The hook owns arrow-key navigation and the roving
tabindex, so under `readOnly` the keyboard path still calls `setValue` → `onUpdate` →
`updateSettings`, a write refused at `useTandemSettings.svelte.ts:114-117`.

All **eight** `role="radio"` markup sites — `AppearanceSettings.svelte:83, 136, 148, 175, 228`
and `EditorSettings.svelte:167, 197, 244` (three inside `{#each}` loops, so the rendered instance
count is higher) — carry native `disabled={readOnly}`, which drops focus to the nearest focusable
ancestor on click.

**Probe (what is reachable today):** mount `AppearanceSettings` with `readOnly: true` and click a
theme card. The native `disabled` swallows the click and focus lands on the `role="radiogroup"`
container, which carries a static `tabindex="-1"` (`:74-77`). ArrowRight from there **does** reach
`themeRg.handleKeyDown` and **does** fire the refused write. Nothing visible changes — every
affordance derives from `settings` (`aria-checked={settings.theme === t}`, `tabIndexFor`'s
`getValue` is `() => settings.theme`, `cardStyle(settings.theme === t, readOnly)`) and a refused
write never mutates `settings`. The live defect is a *silent refused write on a keyboard path the
hook was given `isDisabled` to close*, not a moving selection.

**Scope note.** `readOnly` cannot flip mid-session: `createTandemSettings` is a singleton
(`useTandemSettings.svelte.ts:104-107`), `_readOnly` is fixed at construction, `updateSettings`
never writes it, and there is no `storage` listener — so `SettingsModal.svelte:424`'s
`$derived(settings._readOnly === true)` is constant for the life of the page. The flip spec below
is a **mechanism pin** discriminating a live getter from an init-time ternary, not a user
scenario, and the PR body must say so. The `isDisabled` argument becomes fully load-bearing
*because* the `aria-disabled` migration restores focusability to the radios.

## Fix

The in-repo precedent for `aria-disabled` over native `disabled` is
`src/client/components/FileOpenDialog.svelte:55-62` (#1773) — its rationale comment ("disabling
the focused node blurs it") and its shape at `:459-463` (`aria-disabled={actionInFlight}` plus
`onclick={() => { if (actionInFlight) return; … }}`). This is the **first settings-side
instance**; #1722's two merged halves are the `updateSettings` boolean (#1985) and the rail
toggles returning it (#2016) — there is no `aria-disabled` half of #1722, and no such claim may
appear in the PR body.

- **All seven `createRadioGroup` call sites:** pass `() => readOnly` as the 4th argument.
  `readOnly` is a required `boolean` on `SettingsTabContext` (`SettingsModal.svelte:34`) and both
  files destructure it off `$props()`, which the compiler rewrites to a getter, so the arrow
  re-reads it per call. **Not** `readOnly ? () => true : undefined` — that ternary is evaluated
  once at init and is the specific wrong implementation the flip spec kills.
- **All eight `role="radio"` markup sites:** `disabled={readOnly}` → `aria-disabled={readOnly}`,
  and guard the handler by hand — `onclick={() => { if (readOnly) return; onUpdate({ … }); }}` —
  because `aria-disabled` does not block clicks. Scope is the `role="radio"` buttons **only**:
  every other `disabled={readOnly}` in these two files (checkboxes, hue slider,
  `font-by-extension-reset`, save-folder input/pick/reset) keeps its native `disabled`.
- **The refusal stays silent, deliberately.** #1722's rail toggles route refusals through `notify`
  because the title bar has no standing indicator; `settings-readonly-banner` is rendered
  modal-wide (`SettingsModal.svelte:811`) the whole time these controls are visible.
- `disabledControlStyle(readOnly)` / `cardStyle(selected, readOnly)` unchanged — already
  token-driven.
- No `data-testid` added, renamed or removed, so
  `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched.
  `tests/e2e/display-menu.spec.ts:226` asserts `aria-checked` on `editor-measure-wide`, not
  `disabled`, so it is unaffected.

## Tests

All in `tests/client/settings-readonly-ui.test.ts`.

1. **Same-commit `CASES` migration, polarity kept.** The three `role="radio"` entries —
   `theme-dark-btn`, `density-compact-btn`, `editor-measure-wide` — currently assert
   `control.disabled === true/false`. Give `ControlCase` an `ariaDisabled?: true` flag, set it on
   those three, and for them assert: read-only arm `getAttribute("aria-disabled") === "true"`
   **and** `hasAttribute("disabled") === false` (the second half is load-bearing — without it an
   implementation that adds `aria-disabled` while keeping `disabled={readOnly}` passes everything
   and leaves the focus half unfixed); enabled arm
   `expect(control.getAttribute("aria-disabled")).not.toBe("true")`, phrased negatively so it does
   not depend on Svelte stringifying `false`. Carry a comment saying the native-`disabled`
   contract is relaxed for `role="radio"` only and why. **Every other CASE keeps asserting
   `.disabled`.** The existing `control.click(); expect(onUpdate).not.toHaveBeenCalled()` stays for
   all cases and is what kills an `aria-disabled` swap with no `onclick` guard.
2. **Flip spec (new `describe`), one per file — structural, not named.** `render` with
   `readOnly: false`, `await rerender({ ...ctx, readOnly: true })` on the live instance (`rerender`
   is async — `tests/client/DisplayMenu.svelte.test.ts:48, :108`), `await tick()`, then iterate
   `container.querySelectorAll('[role="radiogroup"]')` and assert for **every** group that (a)
   every `[role="radio"]` descendant reports `tabindex="-1"` and `aria-disabled="true"`, and (b)
   `new KeyboardEvent("keydown", { key: "ArrowRight", bubbles: true })` on the group container
   leaves `onUpdate` uncalled. Iterating rather than naming covers `primaryTabRg`, `textSizeRg`,
   `editorFontRg` and the `fontByExtensionRgs` factory — a named spec leaves four groups shippable
   with the defect and every test green — and it fails closed when a group is added. Mounting
   already-read-only cannot distinguish the getter from the ternary; only the flip does.
3. Same `describe`, enabled twin: with `readOnly: false` the same per-group ArrowRight **does**
   call `onUpdate` — without it a fix hard-coding `() => true` passes spec 2.
