# W13t — #1964 Settings radiogroups ignore the read-only contract: no `isDisabled`, and a native `disabled` that blurs mid-interaction

Branch `fix/settings-read-only-radiogroup-and-desktop-token-panel-1964`. Closes #1964. Ledger:
`docs/plans/2026-09-06-open-issues-sweep.md:464` (the K-client row, which records #1964 as one of
#1824's six carve-outs).

**Probe (what is actually reachable today):** mount `AppearanceSettings` with `readOnly: true`
and click a theme card. The button is natively `disabled`, so the click fires no handler and
focus lands on the nearest focusable ancestor — the `role="radiogroup"` container, which carries
a static `tabindex="-1"` (`AppearanceSettings.svelte:76`). From there ArrowRight **does** reach
`themeRg.handleKeyDown`, which calls `setValue` → `onUpdate` → `updateSettings`, a write refused
at `useTandemSettings.svelte.ts:114-117`. Nothing visible changes — every affordance in these
groups is derived from `settings` (`aria-checked={settings.theme === t}`, `tabIndexFor`'s
`getValue` is `() => settings.theme`, `cardStyle(settings.theme === t, readOnly)`), and a refused
write never mutates `settings`. So the live defect is a *silent refused write on a keyboard path
the hook was given an `isDisabled` argument to close*, not a moving selection.

## Problem

`src/client/components/AppearanceSettings.svelte` and `src/client/components/EditorSettings.svelte`
hold **seven** `createRadioGroup(...)` call sites between them — `themeRg` (`:48`), `primaryTabRg`
(`:53`), `textSizeRg` (`:58`), `densityRg` (`:63`) in Appearance; `editorFontRg` (`:71`), the
`fontByExtensionRgs[row.format]` factory in the `FONT_FORMAT_ROWS` loop (`:82`) and `measureRg`
(`:141`) in Editor. Every one omits the hook's 4th argument, `isDisabled?: (v: T) => boolean`
(`src/client/hooks/useRadioGroup.svelte.ts:22`). The hook owns arrow-key navigation and the
roving tabindex, so under `readOnly` the keyboard path still calls `setValue` and the roving
tabindex still nominates a tab stop on a group that refuses every write.

Separately, all **eight** `role="radio"` markup sites across the two files —
`AppearanceSettings.svelte:83, 136, 148, 175, 228` and `EditorSettings.svelte:167, 197, 244`
(three of them inside `{#each}` loops, so the rendered instance count is higher and varies with
`TEXT_SIZES` / `FONT_OPTIONS` / `FONT_FORMAT_ROWS`) — carry native `disabled={readOnly}`. A
native `disabled` on a focusable control is what drops focus to the nearest focusable ancestor on
click, and would blur the focused node outright if the flag could flip mid-interaction.

**Two scope notes that keep this honest.** (a) `readOnly` cannot flip mid-session in the shipped
app: `createTandemSettings` is a singleton (`useTandemSettings.svelte.ts:104-107`), `_readOnly` is
fixed at construction from `loadSettings()`, `updateSettings` never writes it, and there is no
`storage` listener — so `SettingsModal.svelte:424`'s `$derived(settings._readOnly === true)` is
constant for the life of the page. The flip spec below is therefore a **mechanism pin** that
discriminates a live getter from an init-time ternary, not a reproduction of a user scenario, and
the PR body must describe it that way. (b) The `isDisabled` 4th argument becomes fully
load-bearing *because* the `aria-disabled` migration restores focusability to the radios: once a
read-only radio can hold focus, ArrowRight from the radio itself reaches `handleKeyDown` too.

## Fix

The in-repo precedent for choosing `aria-disabled` over native `disabled` is
`src/client/components/FileOpenDialog.svelte:55-62` (#1773) — its rationale comment ("the confirm
buttons carry `aria-disabled` rather than `disabled` — disabling the focused node blurs it") and
its shape at `:459-463` (`aria-disabled={actionInFlight}` plus
`onclick={() => { if (actionInFlight) return; … }}`) are what this change adopts. This is the
**first settings-side instance**; #1722's two merged halves are the `updateSettings` boolean
(#1985) and the rail toggles returning it (#2016) — there is no `aria-disabled` half of #1722, and
no such claim may appear in the PR body.

- **Both files, all seven call sites:** pass `() => readOnly` as the 4th argument. `readOnly`
  is a required `boolean` on `SettingsTabContext` (`SettingsModal.svelte:34`) and both files
  destructure it straight off `$props()`, which the compiler rewrites to a getter — so the
  arrow function re-reads it on every call. **Not** `readOnly ? () => true : undefined`: that
  ternary is evaluated once at component init and never sees a later flip, and it is the
  specific wrong implementation the flip spec below kills.
- **Both files, every `role="radio"` markup site (all eight, enumerated above):**
  `disabled={readOnly}` → `aria-disabled={readOnly}`, and guard the handler by hand —
  `onclick={() => { if (readOnly) return; onUpdate({ … }); }}` — because `aria-disabled` does not
  block clicks. Scope is the `role="radio"` buttons **only**: every other `disabled={readOnly}`
  in these two files (checkboxes, the hue slider, the `font-by-extension-reset` button, the
  save-folder input/pick/reset) keeps its native `disabled`, and the reset button's
  `disabled={readOnly || !hasFontOverrides}` is untouched.
- **Add `aria-disabled={readOnly}` to each `role="radiogroup"` container** as well. With
  `isDisabled` live, `tabIndexFor` returns `-1` for every value (`useRadioGroup.svelte.ts:56-62`)
  and the containers already carry a static `tabindex="-1"`, so nothing in the group is a tab
  stop — without a group-level attribute the state would be unannounced to assistive tech. One
  line per container; no testid impact.
- **The refusal stays silent on this surface, deliberately.** #1722's rail toggles route a
  refusal through `notify` because the title bar has no standing indicator; the Settings modal
  renders `settings-readonly-banner` modal-wide (`SettingsModal.svelte:811`) for the whole time
  these controls are visible, so a per-click toast would be redundant. Recording the reason is
  required; changing to `notify` is not.
- `disabledControlStyle(readOnly)` / `cardStyle(selected, readOnly)` stay as they are — the
  muted look is already token-driven (`var(--tandem-*)`, Critical Rule: no raw hex here).
- **`SettingsModal.svelte:26-34`**, the `readOnly` doc comment, currently states the contract as
  "tabs must `disabled` every control that writes settings". Amend it to record the
  `role="radio"` carve-out, why (a native `disabled` on a focusable control loses focus; cf.
  `FileOpenDialog.svelte:55-62`), and the clause that the carve-out buys focus **retention**, not
  keyboard **reachability** — a read-only group has no tab stop either way, exactly as today.
- No `data-testid` is added, renamed or removed, so
  `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched.
  `tests/e2e/display-menu.spec.ts:226` asserts `aria-checked` on `editor-measure-wide`, not
  `disabled`, so it is unaffected.

## Tests

All in `tests/client/settings-readonly-ui.test.ts`.

1. **Required same-commit migration, with the polarity kept.** The `CASES` array's three
   `role="radio"` entries — `theme-dark-btn`, `density-compact-btn`, `editor-measure-wide` —
   assert `control.disabled === true/false` through the generated pair. Give `ControlCase` an
   `ariaDisabled?: true` flag, set it on those three, and for them assert:
   - read-only arm: `control.getAttribute("aria-disabled") === "true"` **and**
     `control.hasAttribute("disabled") === false`. The second half is load-bearing — without it
     an implementation that adds `aria-disabled` while keeping `disabled={readOnly}` passes every
     assertion in this spec and leaves the focus half of #1964 unfixed.
   - enabled arm: `expect(control.getAttribute("aria-disabled")).not.toBe("true")`. Phrased as a
     negative so it does not depend on Svelte stringifying `false` as the literal `"false"`.

   Carry a comment saying the native-`disabled` contract is relaxed for `role="radio"` only and
   why. **Every other CASE keeps asserting `.disabled` unchanged** — that is what stops the
   migration widening into a blanket relaxation. The existing
   `control.click(); expect(onUpdate).not.toHaveBeenCalled()` assertion stays for all cases and
   is what kills an `aria-disabled` swap with no `onclick` guard.
2. **The discriminating spec (new `describe`), one per file — structural, not named.** `render`
   with `readOnly: false`, then `await rerender({ ...ctx, readOnly: true })` on the live instance
   (`rerender` is async — see `tests/client/DisplayMenu.svelte.test.ts:48, :108`), then
   `await tick()` before reading attributes. Then iterate **every** group:
   `for (const group of container.querySelectorAll('[role="radiogroup"]'))` assert
   (a) every `[role="radio"]` descendant reports `tabindex="-1"` and
   `getAttribute("aria-disabled") === "true"`, and (b) dispatching
   `new KeyboardEvent("keydown", { key: "ArrowRight", bubbles: true })` on the group container
   leaves `onUpdate` uncalled. Iterating rather than naming `theme-*` / `editor-measure-*` is
   what covers `primaryTabRg`, `textSizeRg`, `editorFontRg` and the `fontByExtensionRgs` factory
   — a named spec leaves four groups shippable with the original defect and every test green —
   and it fails closed when a new radiogroup is added. **Mounting already-read-only cannot
   distinguish the getter from the broken ternary** — only the flip does, which is why this spec
   exists rather than another `CASES` row.
3. Same `describe`, the enabled twin: with `readOnly: false`, the same per-group ArrowRight
   **does** call `onUpdate` — without it, a fix that hard-codes `() => true` passes case 2.

## Review corrections (round 1)

**Adopted**

- *Problem/Probe described an unreachable symptom.* Rewrote both: nothing moves (every affordance
  derives from `settings`, refused writes never mutate it) and `_readOnly` cannot flip
  (`useTandemSettings.svelte.ts:104-117`, no `storage` listener). The reachable path — native
  `disabled` click → focus to the `tabindex="-1"` container → ArrowRight → refused write — is now
  what the Probe states, and the flip spec is labelled a mechanism pin.
- *#1722 has no `aria-disabled` half.* Struck the attribution. The cited precedent is now
  `FileOpenDialog.svelte:55-62, 459-463` (#1773), confirmed by
  `grep -rn aria-disabled src/client --include=*.svelte` returning only that file, and the spec
  states this is the first settings-side instance.
- *Tests cover 3 of 8 markup sites / 2 of 7 hook sites.* Tests 2 and 3 are now structural: iterate
  `[role="radiogroup"]` and assert over every `[role="radio"]` descendant, so all eight sites and
  all seven groups are covered without naming any, and a new group is covered automatically.
- *The `CASES` migration removes the only proof that native `disabled` is gone.* The read-only arm
  now asserts `hasAttribute("disabled") === false` alongside `aria-disabled === "true"`.
- *Site counts wrong ("seven"/"eleven").* Replaced with the enumerated markup sites (eight) and
  the enumerated `createRadioGroup` lines (seven); the loop multiplication is called out so the
  rendered-instance count is not read as a checklist.
- *`rerender` not awaited.* Spec now says `await rerender(...)` plus `await tick()`, citing
  `DisplayMenu.svelte.test.ts:48, :108`.
- *Enabled-arm assertion depended on `"false"` stringification.* Changed to `.not.toBe("true")`.
- *Read-only group has no tab stop and no group-level state.* Added `aria-disabled={readOnly}` on
  each `role="radiogroup"` container, and the amended `SettingsModal` comment now says the
  carve-out buys focus retention, not reachability.
- *Silent no-op diverges from #1722's refusal contract without saying why.* Added the sentence:
  `settings-readonly-banner` is visible modal-wide (`SettingsModal.svelte:811`), unlike the title
  bar, so silence is deliberate.
- *Doc-only Done-when items can be skipped silently.* The `SettingsModal.svelte` comment moved to
  an explicit "Also do (not verified by any listed test)" section.

**Not adopted**

- Keeping native `disabled` and changing only the 4th hook argument (offered as option (b) under
  the #1722 finding): rejected on the merits — it leaves the focus-loss half of #1964, which the
  issue names, unfixed, and `FileOpenDialog.svelte:61` is an in-repo precedent for the opposite
  choice.
- Routing the click guard through `notify`: offered as an either/or by the same finding; the
  alternative (state why silence is right) is adopted instead, for the banner reason above.
