# W13t — #1964 Settings radiogroups ignore the read-only contract: no `isDisabled`, and a native `disabled` that blurs mid-interaction

Branch `fix/settings-read-only-radiogroup-and-desktop-token-panel-1964`. Closes #1964. Ledger:
`docs/plans/2026-09-06-open-issues-sweep.md:464` (the K-client row, which records #1964 as one of
#1824's six carve-outs). Probe: mount `AppearanceSettings` with `readOnly: false`, flip the prop
to `true`, press ArrowRight on the theme radiogroup — the selection still moves today.

## Problem

`src/client/components/AppearanceSettings.svelte` and `src/client/components/EditorSettings.svelte`
hold **seven** `createRadioGroup(...)` call sites between them — `themeRg`, `primaryTabRg`,
`textSizeRg`, `densityRg` (Appearance) and `editorFontRg`, the `fontByExtensionRgs[row.format]`
factory in the `FONT_FORMAT_ROWS` loop, `measureRg` (Editor). Every one omits the hook's 4th
argument, `isDisabled?: (v: T) => boolean` (`src/client/hooks/useRadioGroup.svelte.ts:22`). The
hook is where arrow-key navigation and the roving tabindex live, so under `readOnly` the
keyboard path still calls `setValue` — `onUpdate` no-ops silently, and the user watches a
selection that never persisted move under the arrow keys. That is the #1722 failure exactly,
one surface over.

Separately, all eleven `role="radio"` buttons across the two files carry native
`disabled={readOnly}`. A native `disabled` applied to the element that currently has focus
blurs it to `<body>` the instant the flag flips, which is what the `aria-disabled` half of
#1722's merged work exists to avoid.

## Fix

Mirror #1722's merged halves; do not invent a second pattern.

- **Both files, all seven call sites:** pass `() => readOnly` as the 4th argument. `readOnly`
  is a required `boolean` on `SettingsTabContext` (`SettingsModal.svelte:34`) and both files
  destructure it straight off `$props()`, which the compiler rewrites to a getter — so the
  arrow function re-reads it on every call. **Not** `readOnly ? () => true : undefined`: that
  ternary is evaluated once at component init and never sees a later flip, and it is the
  specific wrong implementation the test below kills.
- **Both files, every `role="radio"` button:** `disabled={readOnly}` → `aria-disabled={readOnly}`,
  and guard the handler by hand — `onclick={() => { if (readOnly) return; onUpdate({ … }); }}` —
  because `aria-disabled` does not block clicks. Scope is the `role="radio"` buttons **only**:
  every other `disabled={readOnly}` in these two files (checkboxes, the hue slider, the
  `font-by-extension-reset` button, the save-folder input/pick/reset) keeps its native
  `disabled`, and the reset button's `disabled={readOnly || !hasFontOverrides}` is untouched.
- `disabledControlStyle(readOnly)` / `cardStyle(selected, readOnly)` stay as they are — the
  muted look is already token-driven (`var(--tandem-*)`, Critical Rule: no raw hex here).
- **`SettingsModal.svelte:26-34`**, the `readOnly` doc comment, currently states the contract as
  "tabs must `disabled` every control that writes settings". Amend it to record the
  `role="radio"` carve-out and why (focus loss), or the next reader restores the native
  attribute as a consistency fix.
- No `data-testid` is added, renamed or removed, so
  `tests/design-system-impl/__snapshots__/testid-set.snap.txt` is untouched.
  `tests/e2e/display-menu.spec.ts:226` asserts `aria-checked` on `editor-measure-wide`, not
  `disabled`, so it is unaffected.

## Tests

All in `tests/client/settings-readonly-ui.test.ts`.

1. **Required same-commit migration.** The `CASES` array's three `role="radio"` entries —
   `theme-dark-btn`, `density-compact-btn`, `editor-measure-wide` — assert
   `control.disabled === true/false` through the generated pair. Give `ControlCase` an
   `ariaDisabled?: true` flag, set it on those three, and branch the two assertions onto
   `getAttribute("aria-disabled")` (`"true"` / `"false"`) for them. Carry a comment saying the
   native-`disabled` contract is relaxed for `role="radio"` only and why. **Every other CASE
   keeps asserting `.disabled` unchanged** — that is what stops the migration widening into a
   blanket relaxation. The existing `control.click(); expect(onUpdate).not.toHaveBeenCalled()`
   assertion stays for all cases and is what kills an `aria-disabled` swap with no `onclick`
   guard.
2. **The discriminating spec (new `describe`), one per file.** `render` with `readOnly: false`,
   then `rerender({ ...ctx, readOnly: true })` on the live instance. Assert (a) every
   `[role="radio"]` inside the theme (resp. measure) radiogroup now reports `tabindex="-1"` —
   `tabIndexFor` returns `-1` for all values only when `isDisabled` is live; and (b) dispatching
   `new KeyboardEvent("keydown", { key: "ArrowRight", bubbles: true })` on the
   `[role="radiogroup"]` container leaves `onUpdate` uncalled. **Mounting already-read-only
   cannot distinguish the getter from the broken ternary** — only the flip does, which is why
   this spec exists rather than another `CASES` row.
3. Same `describe`, the enabled twin: with `readOnly: false`, the same ArrowRight **does** call
   `onUpdate` — without it, a fix that hard-codes `() => true` passes case 2.

## Done when

Seven call sites carry `() => readOnly`; every `role="radio"` button carries `aria-disabled` plus
a guarded `onclick` and no other control changed; the three `CASES` rows migrated with the
comment; the flip spec present for both files; `SettingsModal.svelte`'s contract comment amended;
`npm run typecheck` (incl. `svelte-check`) and the vitest client suite green; the testid snapshot
unchanged by construction.
