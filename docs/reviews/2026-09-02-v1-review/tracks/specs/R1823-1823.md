## Problem

Measured, not quoted: **52** single-line placeholder sites in `src/server/` (`grep -rnE 'console\.(log|warn|info|error)\([^)]*%[sdifjoOc]' src/server/ --include=*.ts | wc -l`), not the issue's 48, and that regex cannot see calls wrapped across lines. No count is claimed for multi-arg sites.
2. **Sentry ships the hostname and absolute frame paths** (`sentry.ts:94` `sendDefaultPii: false`, `:99` `beforeSend`). The hook rewrites `event.message` and each `exception.values[].value` and nothing else. Measured with a real captured event under our exact options: `server_name` is the machine hostname and frames carry an absolute `filename` with `in_app: true`. **Both `filename` and `abs_path` are declared on the SDK's `StackFrame`** (`node_modules/@sentry/core/build/types/types/stackframe.d.ts:3` and `:9`, 10.73) — an earlier draft of this spec asserted `abs_path` did not exist and that scrubbing it was a no-op; that was measured wrong and corrected in review round 1, because acting on it would delete a live redaction.
3. **stdio never exits on stdin EOF** (`index.ts:188-192`, not `:735-752`). The handler's whole body is a `console.error`. `StdioServerTransport` registers only `data`/`error` on stdin, never `end`, so the server outlives its client forever. **The handler is armed at module scope while `restoreOpenDocuments()` is awaited inside `main()` (`:553-560`)** — which is what makes the naive fix unsafe (Fix 3).
4. **REFUTED as written.** There is no comment at `index.ts:229-233`; the constant is `SIGTERM_GRACE_MS = 6_000` at `supervisor.ts:1935` and it is **not dead code** — on Windows `kill("SIGTERM")` is `TerminateProcess`, the reaper dies at once and the race resolves immediately; only the SIGKILL escalation is unreachable there. ## For Bryan

Two items are decisions, not fixes. Each is measured; neither blocks the other nine.

- **Item 8 — may a startup reclaim a lock whose PID is alive?** `startedAtMs` is written, parsed and never compared, so a reused PID after a reboot forces `"readonly"` until the user finds `POST /api/store/reclaim-lock`. The repo already owns the answer for the *user-initiated* path — `doReclaim` (`store.ts:286-360`) probes process identity and refuses on indeterminate, with `process-identity.ts:10-13` stating "a wrong answer here can at worst REFUSE a reclaim — never grant one." Wiring that into `acquireStoreLock` means a new injectable probe seam plus a boot-instant estimate (`Date.now() - os.uptime()*1000`, and `os.uptime()` has **zero** hits in `src/` today), and a wrong *grant* means two writers both flushing the annotation envelope — a full clobber that takes the ADR-027 personal notes and the tombstone ledger. The issue itself calls the trigger rare. Decide whether the rare read-only is worth that, or whether it belongs with #1077's v2-lock work.
- **Item 12 — what should the launcher report during the HTTP boot window, and how should the UI render it?** `resolveInitialLauncherReason` (`initial-reason.ts:37`) returns `"stdio-mode"` as the fallback for every non-kill-switch case, so an HTTP start holds it until `startLauncherSupervisor()` runs — after the server is listening — and `GET /api/launcher/status` answers `{available:false, reason:"stdio-mode"}`, which resolves readiness to `unconfigured` and shows a fully-configured user the setup CTA. Fixing it needs a **new member on `LauncherUnavailableReason`** (`src/shared/launcher/contract.ts:63` — measured: the enum holds exactly `stdio-mode`, `disabled-by-env`, `spawn-failed`, `deferred-autostart`) plus a decision the neighbouring predicate makes load-bearing: `isTransientlyUnavailable` (`:85`) is **not** a rendering seam — it is the authorization gate on `POST /api/launcher/start` (`api-routes.ts:544`), the only route that can create a supervisor from null, whose docblock calls that check what stops the route being "an HTTP bypass of `TANDEM_DISABLE_LAUNCHER=1`". So the choice is between widening a security gate and adding a second UI-only predicate with its own client consumers. That is a contract change, not a label fix.
- **Item 4's behaviour half** — whether Windows should get a graceful reaper stop instead of `TerminateProcess`. Same family as the OPEN #1994 (macOS). Comments are corrected by this PR; the behaviour is untouched.
