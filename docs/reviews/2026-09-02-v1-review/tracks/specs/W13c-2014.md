# W13c — #2014 Chat reveal over a hover-floating rail leaves `.floating` and `.float-closing` co-present

Branch `fix/client-rail-pulse-outline-and-tutorial-fixes-2014`. Closes #2014. Ledger: none — #2014 is a
post-review observation filed against master `4da4efa0`, not a v1-review area row; the sweep row is wave 13,
group W13c. Probe: `tests/e2e/rail-float-reveal.spec.ts` (new), driving the issue body's own reachable path.

## Problem

`src/client/App.svelte:1245-1249` states the hover-float lifecycle is `idle → floating (railFloat) → closing
(railFloatClosing) → idle`, "the two phases mutually exclusive". The shell's class bindings break that,
because the chat reveal is OR-ed into one phase and not the other:

- `class:floating={railFloat.right || railContent.revealOpen}` (`:2477`)
- `class:float-closing={railFloatClosing.right}` (`:2478`)

`maybeHideFloat` (`:1317-1336`) has two early-out arms that mean "there is nothing to retreat" — the rail is
pinned (`railVisible(side)`) or motion is off — and otherwise hands off to the closing phase. **An open
reveal is a third such condition and is not listed**: the reveal keeps the panel painted over the editor on
its own, so a retreat slide has nothing to retreat from. With the reveal open, `railFloat.right = false`
still sets `railFloatClosing.right = true`, and both classes land at once. The later `float-closing` rule
(`:3423-3424`) wins at equal specificity and carries `forwards`, so the panel is held off-screen for
`FLOAT_CLOSE_MS` while `.rail-shell.rail-floating-chrome .rail-full` (`:3368`) keeps it `display: flex` —
i.e. the reveal the user asked for is invisible until the timer drops the flag.

The reachable path is the issue body's: collapsed right rail, `railHoverReveal` default `true`
(`useTandemSettings.ts:298`), `focusChat` (`App.svelte:888-900`) opens the reveal, hover arms
`railFloat.right` (`onRailShellEnter`, `:1299`), then a **keyboard or programmatic** focus exit reaches
`onRailShellFocusOut` (`:1351`) → `maybeHideFloat`. An outside *pointerdown* cannot be used: `rail-content
.svelte.ts:146-154`'s capture-phase closer tears the reveal down first.

## Fix

One arm, in `src/client/App.svelte`'s `maybeHideFloat`. **The model is the `railVisible(side)` arm two lines
below it** — same meaning ("the panel is on screen for another reason; drop straight to idle"), same body:

```ts
// A reveal owns the float chrome while it is open: the panel is already
// painted over the editor, so there is nothing to slide back into the edge.
// Same meaning as the `railVisible` arm below. Without this, `.floating`
// (via `revealOpen`, :2477) and `.float-closing` (:2478) are co-present and
// the closing keyframe's `forwards` fill holds the revealed panel off-screen
// for FLOAT_CLOSE_MS.
if (railVisible(side) || (side === "right" && railContent.revealOpen) || motionOff(...)) {
  railFloatClosing[side] = false;
  return;
}
```

**`side === "right"` is required, not defensive.** `railContent.revealOpen` is a single app-global chat
reveal that only ever renders in the right shell (`:2474-2480`; the left shell at `:2412-2416` never reads
it), so an unguarded term would make a left-rail retreat silently stop animating whenever chat is revealed
on the right.

Rules that bite here: the write is to a `$state` object from a DOM event handler that is **not** a Tiptap
event handler, so `createCoalescingTick` does not apply (`maybeHideFloat` already writes `railFloat[side]`
synchronously today and is reached from `focusout`/`setTimeout`, never from a ProseMirror dispatch). No
`data-testid` is added, renamed or removed — `rail-float-right` (`:2480`) keeps its exact current
expression, which is `data-testid={railFloat.right || railContent.revealOpen ? "rail-float-right" :
undefined}` (**note the `|| railContent.revealOpen`: the testid is present from the reveal ALONE, so it is
not evidence that the hover float armed — see the Tests section**) — so
`__snapshots__/testid-set.snap.txt` is untouched, and **no new `data-testid` may be added.** No colours, no CSS change at all: the two
keyframe rules stay as they are, because the defect is which flags are set, not what they animate.

**Deliberately not done:** the issue's first option (have `openReveal` clear `railFloat`/`railFloatClosing`).
It puts hover-lifecycle writes inside `rail-content.svelte.ts`, which owns no `railFloat` state and would
need two more injected thunks — a mechanism where an arm will do. Recorded as `assumptions`.

## Tests

`tests/e2e/rail-float-reveal.spec.ts` (new), two specs. Vitest cannot reach this: the lifecycle lives in
`App.svelte` script scope with no exported seam, and extracting one would be the mechanism the minimality
rule forbids.

**File preamble, shared by both specs.**

- `test.use({ contextOptions: { reducedMotion: "no-preference" } })` at the top, routed through
  `contextOptions` (it is a `BrowserContextOption`, not a `PlaywrightTestOption`; the bare form is silently
  discarded). Precedent and the full note: `tests/e2e/annotation-ping.spec.ts:22-31`. **Belt-and-braces, not
  a bug fix:** the round-1 finding said Playwright defaults `reducedMotion` to `"reduce"`; that is wrong, the
  default is `no-preference`, and `annotation-ping.spec.ts:28-31` records that correction in-repo. The option
  is written anyway because `motionOff` (`src/client/panels/cardMotion.ts:103-110`) ORs the OS query into the
  retreat gate at `App.svelte:1325-1328`, so a runner or CI image that ever flips the default would make both
  specs vacuous with no failure.
- The float timings are **duplicated literals, not imports**: `HOVER_ENTER_MS = 120`, `HOVER_LEAVE_MS = 180`,
  `FLOAT_CLOSE_MS = 300` are module-scope consts in `src/client/App.svelte:1268-1274` and are not exported.
  Declare them at the top of the spec with a one-line comment naming that file:line so a retune is findable.
- Rail collapse uses `setRailVisible(page, "right", false)` from `tests/e2e/helpers.ts:414`. **There is no
  `right-panel-toggle` testid** — an earlier draft named one that exists nowhere in `src/client/` or in
  `__snapshots__/testid-set.snap.txt`; the real controls are `panel-edge-collapse-right` and
  `peek-strip-right`, and the helper drives the keyboard toggle instead.
- The reveal is opened by dispatching the `tandem:focus-chat` window event, the pattern
  `tests/e2e/chat-reveal.spec.ts:67-75` documents (the Ctrl+Shift+J chord is also Chrome's DevTools
  shortcut). **Unlike `chat-reveal.spec.ts`, this file must NOT seed `railHoverReveal: false`** — the
  hover float is the thing under test.

1. **The discriminating spec — reveal open.** `tandem_open` a fixture, `page.goto("/")`,
   `setRailVisible(page, "right", false)`, dispatch `tandem:focus-chat`, assert `.rail-shell-right` has
   `floating`. Then `hover()` `.rail-shell-right` and **hold the pointer inside for `HOVER_ENTER_MS + 150` ms
   with `page.waitForTimeout`** before moving it away. **The wait is deterministic on purpose: do NOT poll
   for `[data-testid="rail-float-right"]`.** That testid is already present from `revealOpen` alone
   (`App.svelte:2480`), so the poll resolves immediately, the pointer can leave inside the 120 ms enter
   delay, `onRailShellLeave` (`:1337-1341`) `clearTimeout`s the pending enter timer, `railFloat.right` is
   never set, and `maybeHideFloat`'s `if (!railFloat[side]) return;` (`:1319`) fires first —
   `float-closing` is never set and the assertion passes on unfixed master. Nothing else in the DOM
   distinguishes the two states: `class:floating` (`:2477`), `class:rail-floating-chrome` (`:2474-2476`) and
   the `rail-float-shadow` block (`:2482`) are all OR-ed with `revealOpen` too, which is why
   `tests/e2e/chat-reveal.spec.ts:22-38` says outright there is no DOM signal separating them.
   Then move the pointer to the editor's left edge and
   `page.evaluate(() => (document.activeElement as HTMLElement)?.blur())` — the keyboard/programmatic
   exit the issue identifies, chosen because an outside click closes the reveal first. Then `expect.poll`
   over `el.classList.contains("float-closing")` for `HOVER_LEAVE_MS + FLOAT_CLOSE_MS + 200` ms: it must
   never be true while `floating` is. Tail assertion in the same spec:
   `[data-testid="chat-composer-input"]` is visible at the end. **What it kills:** today's code; any fix that
   only reorders the two `class:` bindings (both flags would still be set); and a fix that closes the reveal
   on focus-out, which the tail assertion catches.
2. **The positive control — no reveal.** Same setup minus the `tandem:focus-chat` dispatch: collapsed
   right rail, hover `.rail-shell-right`, hold `HOVER_ENTER_MS + 150`, move the pointer to the editor.
   Assert `float-closing` **does** appear within `HOVER_LEAVE_MS + 150` ms. **Why it is load-bearing:** it is
   the only thing proving the hover arms at all under this file's timing. Without it, a run in which the
   float never armed satisfies spec 1 vacuously and reports green on unfixed code. It must be green on master
   and on the fix alike — the new arm is gated on `side === "right" && railContent.revealOpen`, so it
   does not touch this path.

No unit test is added; say so in the PR body rather than adding a seam to enable one.
