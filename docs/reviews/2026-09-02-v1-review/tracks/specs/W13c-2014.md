# W13c — #2014 Chat reveal over a hover-floating rail leaves `.floating` and `.float-closing` co-present

Branch `fix/client-rail-pulse-outline-and-tutorial-fixes-2014`. Closes #2014. Ledger: none — #2014 is a
post-review observation; sweep row wave 13, group W13c.

## Problem

`src/client/App.svelte:1245-1249` states the hover-float lifecycle is `idle → floating (railFloat) → closing
(railFloatClosing) → idle`, "the two phases mutually exclusive". The class bindings break that, because the
chat reveal is OR-ed into one phase and not the other:

- `class:floating={railFloat.right || railContent.revealOpen}` (`:2477`)
- `class:float-closing={railFloatClosing.right}` (`:2478`)

`maybeHideFloat` (`:1317-1336`) has two early-out arms meaning "there is nothing to retreat" — the rail is
pinned (`railVisible(side)`), or motion is off. **An open reveal is a third such condition and is not
listed**: the reveal keeps the panel painted over the editor on its own. With the reveal open,
`railFloat.right = false` still sets `railFloatClosing.right = true`, both classes land at once, the later
`float-closing` rule (`:3423-3424`) wins at equal specificity and carries `forwards`, and
`.rail-shell.rail-floating-chrome .rail-full` (`:3368`) keeps the panel `display: flex` — so the reveal the
user asked for is held off-screen for `FLOAT_CLOSE_MS`.

Reachable path (the issue body's): collapsed right rail, `railHoverReveal` default `true`
(`useTandemSettings.ts:298`), `focusChat` (`:888-900`) opens the reveal, hover arms `railFloat.right`
(`onRailShellEnter`, `:1299`), then a **keyboard or programmatic** focus exit reaches `onRailShellFocusOut`
(`:1351`) → `maybeHideFloat`. An outside *pointerdown* cannot be used: `rail-content.svelte.ts:146-154`'s
capture-phase closer tears the reveal down first.

## Fix

One arm, in `src/client/App.svelte`'s `maybeHideFloat`, modelled on the `railVisible(side)` arm it joins:

```ts
// A reveal owns the float chrome while it is open: the panel is already painted
// over the editor, so there is nothing to slide back into the edge. Same meaning
// as the railVisible arm. Without this, `.floating` (via revealOpen, :2477) and
// `.float-closing` (:2478) are co-present and the closing keyframe's `forwards`
// fill holds the revealed panel off-screen for FLOAT_CLOSE_MS.
if (railVisible(side) || (side === "right" && railContent.revealOpen) || motionOff(...)) {
  railFloatClosing[side] = false;
  return;
}
```

**`side === "right"` is required, not defensive.** `railContent.revealOpen` is a single app-global chat
reveal rendered only in the right shell (`:2474-2480`; the left shell at `:2412-2416` never reads it), so an
unguarded term would stop a left-rail retreat from animating whenever chat is revealed on the right.

No Tiptap handler is involved (`maybeHideFloat` runs from `focusout`/`setTimeout`, never a ProseMirror
dispatch), so `createCoalescingTick` does not apply. No CSS change — the defect is which flags are set, not
what they animate. **No `data-testid` is added, renamed or removed**; `rail-float-right` (`:2480`) keeps its
current expression, `data-testid={railFloat.right || railContent.revealOpen ? "rail-float-right" :
undefined}` — note the `|| railContent.revealOpen`: **the testid is present from the reveal alone, so it is
not evidence that the hover float armed.** `__snapshots__/testid-set.snap.txt` is untouched.

**Deliberately not done:** the issue's first option (have `openReveal` clear `railFloat`/`railFloatClosing`)
— it puts hover-lifecycle writes in `rail-content.svelte.ts`, which owns no `railFloat` state.

## Tests

`tests/e2e/rail-float-reveal.spec.ts` (new), **one spec**. Vitest cannot reach this: the lifecycle lives in
`App.svelte` script scope with no exported seam, and extracting one would be a new mechanism.

Preamble: `test.use({ contextOptions: { reducedMotion: "no-preference" } })` — routed through
`contextOptions` because it is a `BrowserContextOption` (precedent:
`tests/e2e/annotation-ping.spec.ts:22-31`). It is a cheap guard on `motionOff`
(`src/client/panels/cardMotion.ts:103-110`, read at `App.svelte:1325-1328`), **not** a fix for a Playwright
default: the default is already `no-preference`, as `annotation-ping.spec.ts:28-31` records in-repo. Float
timings are duplicated literals with a pointer comment, not imports — `HOVER_ENTER_MS = 120`,
`HOVER_LEAVE_MS = 180`, `FLOAT_CLOSE_MS = 300` are unexported module consts at `App.svelte:1268-1274`.
Collapse the rail with `setRailVisible(page, "right", false)` (`tests/e2e/helpers.ts:414`); there is no
`right-panel-toggle` testid. Open the reveal by dispatching the `tandem:focus-chat` window event
(`tests/e2e/chat-reveal.spec.ts:67-75`), and **do not seed `railHoverReveal: false`** — the hover float is
under test.

**The spec.** `tandem_open` a fixture, `page.goto("/")`, `setRailVisible(page, "right", false)`, dispatch
`tandem:focus-chat`, assert `.rail-shell-right` has `floating`. `hover()` `.rail-shell-right` and **hold the
pointer inside for `HOVER_ENTER_MS + 150` ms with `page.waitForTimeout`** before moving it away. **The wait
is deterministic on purpose: do NOT poll for `[data-testid="rail-float-right"]`** — that testid is present
from `revealOpen` alone (`:2480`), so the poll resolves immediately, the pointer can leave inside the 120 ms
enter delay, `onRailShellLeave` (`:1337-1341`) `clearTimeout`s the pending enter timer, `railFloat.right` is
never set, and `maybeHideFloat`'s `if (!railFloat[side]) return;` (`:1319`) fires first, so `float-closing`
is never set and the spec passes on unfixed master. Nothing in the DOM distinguishes the two states
(`class:floating` `:2477`, `class:rail-floating-chrome` `:2474-2476` and the `rail-float-shadow` block
`:2482` are all OR-ed with `revealOpen`; `tests/e2e/chat-reveal.spec.ts:22-38` says so outright), which is
why the hold, not a selector, is the arming proof. Then move the pointer to the editor's left edge and
`page.evaluate(() => (document.activeElement as HTMLElement)?.blur())` — the keyboard/programmatic exit the
issue identifies. Then assert the negative over the closing window with a plain sampling loop, **not
`expect.poll`** — `expect.poll` retries until the assertion PASSES, so polling for
`float-closing === false` over a window longer than `FLOAT_CLOSE_MS` succeeds the moment the class clears
and is green on unfixed master. `focusout` runs `maybeHideFloat` synchronously (`:1351`), so read
`el.classList` **immediately** after the `page.evaluate(blur)` with no wait and
`expect(contains("float-closing")).toBe(false)`, then repeat that read every ~50 ms for `FLOAT_CLOSE_MS` ms,
asserting `false` on every sample and asserting `floating` is still present on the same sample — the loop
fails on the first true rather than waiting one out. Tail assertion:
`[data-testid="chat-composer-input"]` is visible at the end.

**What it kills:** today's code; a fix that only reorders the two `class:` bindings (both flags still set);
a fix that closes the reveal on focus-out (the tail assertion).
