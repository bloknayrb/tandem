## Problem

`renderMarkdown` (`src/client/panels/chat-markdown.ts:46`) builds block structure by string
substitution. Three passes at the end of the chain emit markup that is never opened, never closed,
or never wrapped:

- `:128` `.replace(/^[*-] (.+)$/gm, "<li>$1</li>")` — an `<li>` with no `<ul>` ancestor.
- `:130` `.replace(/\n\n/g, "</p><p>")` — no opening tag at the start, no closing tag at the end.
- `:132` `.replace(/\n/g, "<br>")` — runs *after* the list pass, so every `<li>` is preceded by a `<br>`.

So `a\n\nb` is the **text node** `a` followed by `<p>b</p>`: paragraph one is not an element, and
`> :first-child` selects paragraph *two*. `intro\n\n` + a fenced block leaves a stray empty `<p>`,
because the `</p><p>` pair straddles the `\x00BLOCK<n>\x00` placeholder.

Two rules in `src/client/panels/markdown-body.css` exist only for this and both name #1639 as their
owner: the deliberately **absent** `> :first-child { margin-top: 0 }` (explanatory comment at
**`:29-46`**, sitting above the `> :last-child` rule at `:47`) and the load-bearing
`p:empty { display: none }` (comment + rule at **`:157-165`**, selector at `:163`).

Two `{@html}` sinks consume it: **`ChatPanel.svelte:372`** (Claude messages) and
`AnnotationBody.svelte:73` (annotation + reply bodies, three cards). Presentation only — no
coordinate-system, annotation-model or wire impact.

## Fix

**`src/client/panels/chat-markdown.ts`.** Keep `:128`'s per-line `<li>` pass. Delete the `:130`
paragraph pass and the `:132` line-break pass. Add a module-private `assembleBlocks(input: string)`
called **after** the inline chain and **before** the block-restore
`return result.replace(/\x00BLOCK(\d+)\x00/g, …)` at **`:164-167`** — the restore must stay last so
placeholders are still detectable as placeholders.

**Classification is per LINE, and a line is never split.** (Round-0 split each chunk on the
placeholder and classified the *fragments*; that is the defect review round 1 killed — see
"Review corrections" below.)

```
for each chunk of input.split(/\n{2,}/)           // blank line = block break
  para: string[] = []   items: string[] = []
  flushPara = () => if (para.length) out.push(`<p>${para.join("<br>")}</p>`), para = []
  flushList = () => if (items.length) out.push(`<ul>${items.join("")}</ul>`), items = []
  for each line of chunk.split("\n")
    if line.trim() === ""            -> continue                         // arm 0
    if line.startsWith("<li>")       -> flushPara(); items.push(line)    // arm 1
    if /^<h[123]>/.test(line)        -> flushPara(); flushList(); out.push(line)   // arm 2
    if /\x00BLOCK\d+\x00/.test(line) -> flushPara(); flushList(); out.push(line)   // arm 3
    otherwise                        -> flushList(); para.push(line)     // arm 4
  flushList(); flushPara()
```

Four properties to state in the docblock, because each is load-bearing and invisible:

1. **No line is ever split — that is what keeps a block out of the wrapping `<p>`.** Arm 3 tests
   whether a line *contains* a placeholder and emits the **whole line** bare. A piece-level split on
   the placeholder would instead cut an element that an earlier inline pass opened: measured against
   the real renderer, `**a ```x``` b**` reaches assembly as the single line
   `<strong>a \x00BLOCK0\x00 b</strong>`, and splitting it yields
   `<p><strong>a </p><pre>…</pre><p> b</strong></p>` — an element opened in one `<p>` and closed in
   another. The same holds for `[label](url)` (the link guard at `:120` rejects a placeholder only in
   the **URL**, never in the label) and for `# heading`.
2. **Arm order is the contract: `<li>` is tested BEFORE the placeholder.** `<li>` legally accepts
   flow content, so a fence inside a bullet stays inside its item —
   `- see ```x``` here` → `<ul><li>see <pre>…</pre> here</li></ul>` (measured) — rather than being
   hoisted out of the list by arm 3.
3. **Both the tag-prefix dispatch and the placeholder test are sound only because of
   escape-first / strip-first.** Every `<` and every `\x00` in the intermediate string was emitted by
   this function: a user typing `<li>` is already `&lt;li&gt;` and a forged `\x00BLOCK0\x00` is
   already plain `BLOCK0`, both by `:64`. A change that moves escaping or the NUL strip later breaks
   this dispatch as well as the XSS property. **Test case 9 pins it**; round 0 stated it and pinned
   nothing.
4. **An empty run is never flushed (the `if (run.length)` guards) and a whitespace-only line is
   never a paragraph line (`line.trim() !== ""`, arm 0).** Those two together remove the stray empty
   `<p>` (acceptance item 4) and are what let `p:empty` be deleted. They are separate decisions with
   separate failure modes and are mutation-tested separately below.

**A recorded bound of the subset, not a defect introduced here.** A mid-line fence on a *plain prose*
line (`see ```x``` here`, matching no earlier arm) is emitted bare by arm 3, so the prose around it
stays a top-level text node rather than becoming a `<p>`. That is **exactly what ships today**
(measured: today's output is `see <pre>…</pre> here`); this change neither fixes nor regresses it,
and closing it would mean deciding what a mid-line fence *means*, which is a subset question the
issue does not ask. State it in the docblock beside the ordered/nested-list exclusions.

The escaping invariant is untouched: `escapeHtml` at `:64` still runs over the whole input before any
tag exists, and `assembleBlocks` neither decodes nor emits a `"`.

property alone, no hand-written prefixes):

- Delete the **`:29-46`** comment block; add `.tandem-markdown > :first-child { margin-top: 0 }`
  beside the existing `> :last-child` rule at `:47`. **The placement is free, not an invariant:**
  `.tandem-markdown > :first-child` is specificity (0,2,0) and beats `.tandem-markdown p` (`:75`),
  `.tandem-markdown h1|h2|h3` (`:51-53`) and the new `ul` rule, each (0,1,1), regardless of source
  order. Say so, so a later reorder is not read as load-bearing.
- Delete the **`:157-165`** comment + `p:empty { display: none }` rule.
- **Add a `ul` rule, and move the indent onto it.** **Corrected rationale (round 0 asserted an
  absence it had not measured):** `index.html:44` carries
  `* { margin: 0; padding: 0; box-sizing: border-box; }`, inside the inline `<style>` that is emitted
  verbatim (`tests/design-system-impl/css-pipeline-contract.test.ts`). A round-0 grep scoped to

  the `margin-left: 1.25em` declaration at `:88` from the `.tandem-markdown li` rule whose selector
  is `:87`**, keeping `list-style: disc`. Leaving both doubles the indent.

and `<ul>` is a new block child its `*` already covers); update its comment at `:511-517` to name

## Tests

All structural assertions go through the **parsed DOM** using the `parse()` helper already at
`tests/client/chat-markdown.test.ts:16-20` (`host.innerHTML`, happy-dom) — the defect is invisible to
string inspection because the parser rescues it.

**The discriminator is `childNodes.length === children.length`, not `closest("p")`.** Round 0 named
`pre.closest("p") === null` as what kills the weaker fix; measured in the worktree's own happy-dom, it
is **true for every implementation**, because the parser always reparents a `<pre>` out of a `<p>` —
which is the issue's own premise. `<p>intro<pre><code>x</code></pre>outro</p>` parses to children
`P,PRE` with **3 childNodes** (a bare `outro` text node); the correct output parses to `P,PRE,P` with
3 childNodes and 3 children. The bare-text-node count is what has no parser escape hatch. Keep
`closest("p")` only as a redundant companion and say in the test comment that it is not the
discriminating assertion.

New describe in `tests/client/chat-markdown.test.ts`, each case named with the implementation it
kills (every expected value below was produced by running a prototype of the algorithm above, not by
reading it):
