## Problem

`renderMarkdown` (`src/client/panels/chat-markdown.ts:46`) builds block structure by string
substitution. Three passes at the end of the chain emit markup that is never opened, never closed,
or never wrapped (line numbers verified on `33a99d00`):

- `:128` `.replace(/^[*-] (.+)$/gm, "<li>$1</li>")` — an `<li>` with no `<ul>` ancestor.
- `:130` `.replace(/\n\n/g, "</p><p>")` — no opening tag at the start, no closing tag at the end.
- `:132` `.replace(/\n/g, "<br>")` — runs *after* the list pass, so every `<li>` is preceded by a `<br>`.

So `a\n\nb` is the **text node** `a` followed by `<p>b</p>`: paragraph one is not an element, and
`> :first-child` selects paragraph *two*. `intro\n\n` + a fenced block leaves a stray empty `<p>`,
because the `</p><p>` pair straddles the `\x00BLOCK<n>\x00` placeholder.

Two rules in `src/client/panels/markdown-body.css` exist only for this and both name #1639 as their
owner: the deliberately **absent** `> :first-child { margin-top: 0 }` (the explanatory comment at
`:28-45`, sitting above the `> :last-child` rule at `:47`) and the load-bearing `p:empty
{ display: none }` at `:163`.

Two `{@html}` sinks consume it: `ChatPanel.svelte:371` (Claude messages) and
`AnnotationBody.svelte` (annotation + reply bodies, three cards). Presentation only — no
coordinate-system, annotation-model or wire impact.

## Fix

**Decision, recorded per the issue's closing section: hand-balance, do NOT migrate to `marked` +
`DOMPurify`.** The issue says a fix needing a real block-level parse is the signal to migrate. This
one does not: the pass is a line grouping over text that is *already escaped and already
tokenised*, and it adds no new parsing of user syntax. Migration would add two runtime dependencies
to a `{@html}` sink, which is Bryan's call and not this group's — not taken, so nothing goes to him
on that axis.

**`src/client/panels/chat-markdown.ts`.** Keep `:128`'s per-line `<li>` pass. Delete the `:130`
paragraph pass and the `:132` line-break pass. Add a module-private `assembleBlocks(input: string)`
called **after** the inline chain and **before** the block-restore `replace` at `:154-157` — the
restore must stay last so placeholders are still detectable as placeholders.

```
for each chunk of input.split(/\n{2,}/)          // blank line = block break
  for each piece of chunk.split(/(\x00BLOCK\d+\x00)/)   // capture group keeps the delimiters
    if piece is exactly /^\x00BLOCK\d+\x00$/  -> emit bare        // the #1636 trap, closed
    else for each non-empty line of piece.split("\n"):
      /^<li>/   -> flush paragraph; push to list run
      /^<h[123]>/ -> flush paragraph; flush list; emit bare
      otherwise -> flush list; append to paragraph run
    flush list; flush paragraph      // at most one run is ever non-empty (each arm flushes the other)
paragraph run -> `<p>${lines.join("<br>")}</p>`      list run -> `<ul>${items.join("")}</ul>`
```

Three properties to state in the docblock, because each is load-bearing and invisible:

1. **Splitting on the placeholder is what keeps a block out of the wrapping `<p>`** — not
   special-casing a chunk that *is* a placeholder. An inline fence (`` see ```x``` here ``) puts a
   placeholder mid-line, and a chunk-level test would wrap it. This is the #1636 trap; the test
   below is the one that kills the weaker form.
2. **Dispatching on `<li>` / `<h1>` string prefixes is sound only because of escape-first.** Every
   `<` in the intermediate string was emitted by this function; a user typing `<li>` is already
   `&lt;li&gt;` by `:64`. A change that moves escaping later breaks this dispatch as well as the
   XSS property.
3. **Dropping empty lines is what removes the stray empty `<p>`** (acceptance item 4), so it is a
   decision, not tidiness.

The escaping invariant is untouched: `escapeHtml` at `:64` still runs over the whole input before
any tag exists, and `assembleBlocks` neither decodes nor emits a `"`.

**`src/client/panels/markdown-body.css`** (bundled side of the two-pipeline rule — write the
standard property alone, no hand-written prefixes):

- Delete the `:28-45` comment block; add `.tandem-markdown > :first-child { margin-top: 0 }` beside
  the existing `> :last-child` rule at `:47`.
- Delete the `:156-165` comment + `p:empty { display: none }` rule.
- **Add a `ul` rule, and move the indent onto it.** Measured: there is no global `ul` reset —
  `index.html` has no `ul`/`list-style` rule at all, and the only `ul` rules under `src/client` are
  `editor.css:78-79` (`.tandem-editor`-scoped), `FidelityReportBanner`, `CollapsibleSection`,
  `CommandPalette` and `OutlinePanel`, none of which can reach `.tandem-markdown`. So a new `<ul>`
  takes the UA default (`margin-block: 1em`, `padding-inline-start: 40px`). Add
  `.tandem-markdown ul { margin: 0.25em 0; padding-inline-start: 1.25em }` — the margin matching
  `.tandem-markdown p` at `:75` so a list and a paragraph space alike — and **remove
  `margin-left: 1.25em` from `.tandem-markdown li` at `:87`**, keeping `list-style: disc`. Leaving
  both doubles the indent.

**`src/client/panels/AnnotationCard.svelte` — both density rules stay; only their comments change.**
Measured, and this contradicts the parenthetical in acceptance item 3: the fix removes the `<br>`
*between list items*, but `\n` → `<br>` inside a paragraph survives by design, so a two-line Claude
comment still emits one. `br { display: none }` at `:535-538` is therefore still reachable and still
load-bearing for the one-line teaser — rewrite its comment at `:530-534`, which currently justifies
itself entirely by the list case. The `*` flatten rule at `:518-523` becomes *more* load-bearing,
not less (every paragraph is now a real `<p>`, and `<ul>` is a new block child its `*` already
covers); update its comment at `:511-517` to name `<ul>`.

Rules that bite and are satisfied by construction, stated so nobody "fixes" them: **no `data-testid`
is added, renamed or removed**, so `tests/design-system-impl/__snapshots__/testid-set.snap.txt` and
`docs/design-system-impl/testid-manifest.md` are untouched (Critical Rule 7); no colour value is
added, so `npm run check:tokens` is unaffected; no editor code is touched, so the Tiptap
`$state` rule does not arise; E2E runs on the reserved harness ports only.

## Tests

All structural assertions go through the **parsed DOM** using the `parse()` helper already at
`tests/client/chat-markdown.test.ts:16-20` (`host.innerHTML`, happy-dom) — the defect is invisible
to string inspection because the parser rescues it.

New describe in `tests/client/chat-markdown.test.ts`, each case named with the implementation it kills:

1. `a\n\nb` → `host.children.length === 2`, both `P`, **and `host.childNodes.length === 2`**. The
   childNodes half is what kills a fix that emits two `<p>` plus a stray text node.
2. Fenced block never inside a `<p>`, over two interleavings: `intro\n\n<fence>\n\noutro` (chunk
   position) **and an inline fence mid-line** (`` see ```x``` here ``). Assert `pre.closest("p") === null`
   and that the surrounding words are inside `<p>`s. **The inline case is the one that kills a fix
   which only special-cases a chunk equal to a placeholder** — the #1636 trap reintroduced.
3. `intro\n\n` + fence → every `<p>` has non-empty `textContent`. Kills the need for `p:empty`.
4. `Findings:\n- alpha\n- beta` → exactly one `<ul>`, its element children exactly two `<li>`,
   `ul.querySelectorAll("br").length === 0`, and `Findings:` in a `<p>` that precedes the `<ul>`.
   Kills: unwrapped `<li>`; `<br>` left between items; the list swallowed into the paragraph.
5. Two lists separated by a paragraph → **two** `<ul>` elements. Kills a fix that opens one `<ul>`
   around the whole body.
6. `# H\n\npara` → `h1.closest("p") === null`. Kills a fix that wraps every line.
7. `a\nb` → one `<p>` containing exactly one `<br>`. This is the survivor case: it kills a fix that
   drops `<br>` wholesale, and it is what keeps `AnnotationCard.svelte:535` honest.
