# C — #1619 Audience gate closed on push only: the MCP reads still carry `{comment, audience: private}`

Branch `fix/privacy-and-authority-1769`. Closes #1619, folded into the same PR as #1803 (its write-side twin) per `areas/annotations.md:31-32`. Ledger: that row; the ADR-035 Unit 8a note in `src/server/annotations/projection.ts:21-27`. Probe: source-confirmed — the four reads gate on `type` only.

## Problem

`narrowForChannel` (`projection.ts:187-268`) requires `audience === "outbound" && type !== "note"` before anything reaches the channel. The pull surfaces — which CLAUDE.md makes authoritative over every push path — still test type alone:

- `mcp/annotations.ts:64` `channelVisibleReplies`: `annotation.type !== "comment"`.
- `:409-410` `tandem_getAnnotations`: `a.type !== "note"`.
- `:633` `tandem_exportAnnotations`: `a.type !== "note"`.
- `mcp/awareness.ts:614` `userActions`: `ann.author === "user" && ann.type === "comment"`; `:636` `userResponses`: `ann.author === "claude" && ann.type !== "note" && ann.status !== "pending"`.

So a stored `{comment, audience: "private"}` record is withheld from the channel and delivered on the next poll, and the channel reads as if the property holds. Same reachability as #1803: legacy envelope or stale-tab merge, not a first-party writer — except the import asymmetry the issue names (an untriaged import's reply is withheld by Unit 8a while the parent could still surface).

## Fix

One exported read-side predicate, next to the push-side one so the two cannot drift by inspection:

- **`projection.ts`**: `export function isClaudeFacing(ann: Pick<Annotation, "type" | "audience">): boolean { return ann.type !== "note" && ann.audience === "outbound"; }` — the conjunction `narrowForChannel` re-asserts at `:255-265`. Leave those two reason-carrying `if`s in place (they feed `onRefused`) and add one sentence above them: the predicate and this pair must agree, and test 5 below is what enforces it. Rewrite the header paragraph `:21-27` ("This closes the push half only… Tracked in #1619") to say the pull half now uses `isClaudeFacing`. It is NOT the same predicate as C-1803's `isPrivateForClaude`: a private *highlight* is unreadable here but is refused by its own arm on the write side; the two names carry that difference.
- **`annotations.ts:64`**: `if (annotation.type !== "comment" || !isClaudeFacing(annotation)) return [];`. This is the single reply gate every Claude egress routes through (`:56-58`), so `collectInboxUserReplies` (`awareness.ts:706`) and both reads inherit it.
- **`:409-410`**: keep `notesExcluded` as it is; add `const privateExcluded = results.filter((a) => !isClaudeFacing(a)).length; results = results.filter(isClaudeFacing);` after the note filter, and return `...(privateExcluded > 0 ? { privateExcluded } : {})` beside `notesExcluded`. `output-schemas.ts:174-181` `getAnnotationsOutputShape` gains `privateExcluded: z.number().optional()` with the same "omitted when zero" phrasing (the SDK hard-validates structured output, `awareness.ts:648-653`). Silent filtering here would be the honesty bug the export path already refused (`:645-646`).
- **`:633` — the export, disclosed the same way, because it is the one call site whose inline comment forbids silent filtering.** Replace `:644-647` with three steps over DISJOINT operands, so every record lands in exactly one of `notesExcluded` / `privateExcluded` / `heldFromExport` / `exportable`:

  ```ts
  const claudeFacing = notesFiltered.filter(isClaudeFacing);
  const privateExcluded = notesFiltered.length - claudeFacing.length;
  const exportable = claudeFacing.filter((a) => !hideFromAI(a, modeState));
  const heldFromExport = claudeFacing.length - exportable.length;
  ```

  `heldFromExport` is measured against the Claude-facing base, never `notesFiltered`: keeping `notesFiltered.length - exportable.length` while narrowing `exportable` folds every audience exclusion into the Solo count, and the sidecar the user hands to colleagues then over-reports the hold (the round-1 text prescribed exactly that and its own Test 2 could not pass against it). Folding is safe precisely because `privateExcluded` is ALSO emitted — the invariant is `notesFiltered.length === privateExcluded + heldFromExport + exportable.length`, and Test 2 asserts it. Emit `...(privateExcluded > 0 ? { privateExcluded } : {})` beside `heldFromExport` at the THREE existing payload sites — `:826` (sidecar JSON), `:851` (JSON response) and `:859` (the markdown arm's response object). **There is no markdown footer line and none is added**: `heldFromExport` never appears in the markdown text (`store.exportAnnotationsMarkdown(exportable)` at `:677` builds it and knows nothing of either count), and adding one would change `exportAnnotationsMarkdown`'s output for every caller — new scope. `tandem_exportAnnotations` has no entry in `output-schemas.ts`, so this costs no schema edit. Rewrite the `:643-647` comment to name both counts and the disjointness invariant.
- **`awareness.ts:614`**: `&& isClaudeFacing(ann)`; `:636`: `ann.author === "claude" && isClaudeFacing(ann) && ann.status !== "pending"` (C-1770 adds `&& ann.resolvedBy !== "claude"` to the same line). `processInboxAnnotations` receives `store.listAnnotations()`, which sanitizes (`document-store.ts:220`), so production records always carry `audience`. **Fixture sweep — a starting point, not a closed list:** `makeAnnotation` (`tests/helpers/ydoc-factory.ts:41-58`) has no `audience` default, so any fixture that reaches a Claude-facing read WITHOUT passing through sanitize must now pass `audience: "outbound"`. `tests/server/awareness.test.ts` (0 mentions today) and `awareness-tools.test.ts` (1) are the two known ones; sweep every suite whose assertions read a user highlight or a legacy comment back through a Claude-facing tool (`annotations.test.ts`, `edit-annotation.test.ts`, `document-store.test.ts`, `annotation-text-snapshot.test.ts`, `multi-document.test.ts` are the candidates). Records seeded raw and read back through `store.listAnnotations()` are sanitized and mostly survive; any assertion that a USER highlight is returned will not, and that is the fix working. **Do not** loosen the predicate to `audience !== "private"` to spare the fixtures: that reads an absent field as consent, which is the fail-open the channel brand tests reject (`tests/server/events/channel-eligible-brand.test.ts:227-236`).
- **`docs/security.md:400-403`** — the `### Closed: #1680` narrative says "#1619 itself — the read half, on `tandem_checkInbox` and three sibling reads — remains open, which means the two halves now disagree in the other direction: a record Claude can still SEE is one it can no longer reply to." That becomes false with this PR and no claims test reads it (`tests/docs/security-findings-claims.test.ts` parses only the `## Open findings` top-level bullets and CLAUDE.md's count bullet). Rewrite to one sentence: the read half closed with #1619/#1710 via `isClaudeFacing` in `projection.ts`, so the two halves now agree — a record Claude cannot reply to is one it cannot see. And `:162` ("What the AI sees: … annotations you create") becomes "comments you create (highlights and notes are private)" once user highlights are excluded on every read (C-1710). Both are review-only; the PR checklist carries them beside the CLAUDE.md sentence C-1803 already lists.
- `docs/mcp-tools.md:634` (getAnnotations) and `:1036-1037` (checkInbox notes): one sentence each — records whose stored `audience` is not `outbound` are excluded on every Claude-facing read, matching the channel; `privateExcluded` reports the count. The export section (`:781`) adds: the sidecar and response carry `heldFromExport` (Solo holds) and `privateExcluded` (audience exclusions) as two separate floors, both absent when zero — **and both are written into the sidecar file the user may hand to colleagues**, so a shared review summary now states how many private annotations exist (cardinality only, the same class of disclosure `heldFromExport` already makes; the skill at `SKILL.md:120` calls the export "a review summary the user can share").
- **`skills/tandem/SKILL.md:116` rides C-1770's version-16 edit** (one bump, one `bodyHash` recompute in `tests/skill-instruction-contract.test.ts:333`). Its import recipe says "If anything does appear there [`author: "import"`], it is a real imported comment — act on it." After `isClaudeFacing`, an import-authored record surfaces only with a STORED `audience: "outbound"` — `sanitize.ts:79-87` derives `private` for any import lacking one — so the positive branch becomes a legacy-envelope corner rather than a normal state. Reword to: "A record can appear there only if it was stored outbound (a legacy envelope); treat it as a real imported comment." The sentence is not deleted: it is still true, and it is what stops Claude reading an unexpected hit as noise.

Critical Rule 1: no Y.Map keys change. No new tool, route, or gate.

## Tests

The author is load-bearing: `sanitize.ts:154-162` demotes a USER-authored outbound note/highlight/flag to `private`, and `narrowForChannel` re-runs sanitize internally (`projection.ts:187-268`) while `isClaudeFacing` reads whatever object it is handed — so with user fixtures the `{highlight, outbound}` and `{note, outbound}` cells either collapse into their private twins (four distinct states, the note/highlight arms never reached with `audience === "outbound"`) or red on correct code (an unsanitized user literal gives `isClaudeFacing → true`, `narrowForChannel → null`).
