# Gc2b — #1777 Ctrl+Enter double-fires, AltGr layouts trigger chords, six Enter handlers ignore IME composition, `capturedRange` is not mapped through remote edits

Branch `fix/keyboard-and-a11y-1777`. **Closes #1777** (all four numbered items of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:21-24` (four rows, all #1777). Probe: `experiments/harness/e-keys.test.ts` — `E2` (AltGr, synthetic) and `E3` (Ctrl+Enter inserts a `<br>`), both `[ran] Reproduced`.

## Problem

1. **Ctrl+Enter does two things.** `App.svelte`'s window `keydown` handler (the `$effect` holding `function handler(e)` that calls `matchShortcut`) never reads `e.defaultPrevented`. Tiptap's `HardBreak`/`PlaintextBreaksExtension` claims `Mod-Enter` on the `.ProseMirror` node — a bubble listener that runs *before* the window one and calls `preventDefault()` — so with the caret in the editor a single Ctrl+Enter inserts a hard break **and** accepts (or, with Shift, dismisses) the first pending annotation. `shouldIgnoreShortcut` does not save it: that predicate only suppresses `INPUT`/`TEXTAREA` and `isComposing`, never `contenteditable`.
2. **AltGr chords fire app shortcuts.** `matchShortcut` (`src/client/hooks/useAppShortcuts.ts`) computes `mod = e.ctrlKey || e.metaKey` and most `e.code` branches carry no `altKey` gate. Windows/Linux deliver AltGr as `ctrlKey && altKey`, so on pl/ro/cs/de layouts `ś ń ó ț € {` … match `save` / `new-scratchpad` / `open-file` / `pick-tab` and are swallowed by the handler's `preventDefault()`. The file header's "Layout-independence guarantees" is exactly what this contradicts. **The current test file pins the bug**: `tests/client/useAppShortcuts.test.ts` has a `describe("matchShortcut — legacy no-modifier-gate preservation")` whose cases assert Ctrl+Alt+S → `save` and friends.
3. **Six Enter handlers ignore `isComposing`.** `panels/ChatPanel.svelte#handleKeyDown` (`e.key === "Enter" && !e.shiftKey`), `editor/toolbar/LinkEditor.svelte#handleKeyDown`, `editor/find-replace/FindReplaceBar.svelte#handleKeydown`, `tabs/TabRenameInput.svelte#onKeydown`, `components/CommandPalette.svelte#handleKeydown`, `components/OutlinePanel.svelte#handleSearchKeydown`. Zero `isComposing` references in all six. A CJK candidate-confirm Enter sends a half-converted chat message, commits a half-converted link, or renames a tab mid-conversion.
4. **`capturedRange` is a frozen PM range.** `editor/toolbar/Toolbar.svelte:128` declares it, `captureSelectionRange()` writes raw `{from,to}` PM positions, re-capture is suppressed while `popupHasFocus()`, and `createAnnotation` / `handleHighlight` / `handleClearHighlight` read `capturedRange ?? editor.state.selection`. A remote (y-sync/MCP) insertion above the span while the user types the comment is never mapped in, so the annotation lands on shifted text.

## Fix

**(1) `defaultPrevented`.** First statement inside `App.svelte`'s window `handler(e)` — above the F2 branch — `if (e.defaultPrevented) return;`, with a comment naming Tiptap's `Mod-Enter` binding as the case. Blanket, not per-handler, and safe by audit: the only other editor keymap that both `preventDefault`s and collides with an app chord is ProseMirror's base `Mod-a`, and `dispatch["select-all"]` already returns early when `document.activeElement.closest(".ProseMirror")`. `find-replace.ts` and `list-item-checkbox.ts` bind only `Escape`/`Enter` (no modifier), which `matchShortcut` does not match. This is the same guard `App.svelte`'s Escape-to-deselect comment already documents for the slash menu — one mechanism, now applied to the shortcut path too.

**(2) AltGr.** Add `!e.altKey` to the `mod`-block branches that have no alt gate today: `settings` (Comma), `toggle-help` (`e.key === "/"`), `save` (KeyS), `toggle-palette` (Shift+KeyP), `new-scratchpad` (KeyN), `close-tab` (KeyW), `open-file` (KeyO), `pick-tab` (`Digit[1-9]`), `find` (KeyF), `find-nav` (KeyG), `annotation-accept-or-dismiss` (`e.key === "Enter"`). **Do not touch the three deliberate Ctrl+Alt chords** — `reopen-closed-tab` (Alt+KeyT), `comment-on-selection` (Alt+KeyM), `toggle-authorship` (Alt+KeyA) — nor the branches that already gate alt (`select-all`, `save-as`, `focus-chat`, `toggle-source-view`, `toggle-mode`, `new-tab-menu`). The alt-only block below is already immune (`!e.ctrlKey && !e.metaKey`), and the override layer's `chordMatches` compares `chord.alt === e.altKey` exactly, so no change there. Extend the header's "Layout-independence guarantees" list with the AltGr line and rewrite the "legacy no-modifier-gate preservation" comment block inside the `mod` branch — it currently instructs the next reader to preserve the bug.

**(3) IME.** One shared predicate rather than six copies of the same two-term test. Add to `src/client/hooks/useTabKeyboardShortcuts.ts` (which already owns this file's two IME-aware predicates):

```ts
export function isImeComposing(e: Pick<KeyboardEvent, "isComposing" | "keyCode">): boolean {
  return e.isComposing || e.keyCode === 229;
}
```

`keyCode === 229` is the second term because Safari and some IMEs deliver the confirm keydown with `isComposing` already false but `keyCode` still 229. Have `shouldIgnoreShortcut` and `shouldIgnoreSaveAsShortcut` delegate their first line to it (they only check `isComposing` today — a strict widening, and `matchShortcut`'s own `if (e.isComposing) return null` gains the same term). Then, as the **first** statement of each of the six handlers, `if (isImeComposing(e)) return;` — before `TabRenameInput`'s `e.stopPropagation()` is fine (it must still stop), so there it goes immediately after that line. Nothing here writes `$state` from a Tiptap callback, so `createCoalescingTick` is not involved.

**(4) `capturedRange`.** Demote `Toolbar.svelte:128` from `$state<{from,to}|null>(null)` to a plain `let capturedRange: { from: number; to: number } | null = null;`, and map it in the `$effect` that already attaches `selectionUpdate` (the one gated on `showPopup`, using the captured-`ed` pattern):

```ts
const onTx = ({ transaction }: { transaction: Transaction }) => {
  if (!capturedRange || !transaction.docChanged) return;
  const from = transaction.mapping.map(capturedRange.from, 1);
  const to = transaction.mapping.map(capturedRange.to, -1);
  capturedRange = { from, to: Math.max(from, to) };
};
ed.on("transaction", onTx);   // detach in the same cleanup as onSelChange
```

Assoc `1`/`-1` keeps an insertion exactly at either edge **outside** the annotation; a remote insert above shifts both, which is the issue's case. If the span is deleted the two cross and clamp to a point, and all three readers already `return` on `from === to` — the annotation is refused rather than written onto the wrong text.

Why demote instead of bridging through `createCoalescingTick`, given the CLAUDE.md rule: the rule exists because the write targets `$state`, and **nothing reactive reads this cell** — no `$derived`, no template expression; the only reads are the three action handlers and the `!capturedRange` guard inside the `$effect` that also writes it. Removing `$state` retires the `state_unsafe_mutation` hazard for the new `transaction` subscriber *and* for the existing `selectionUpdate` one, which writes `$state` synchronously from a Tiptap callback today. A coalesced tick would also lose intermediate mappings unless a plain mirror were added anyway — two sources of truth for the same range. **State the one behavioural delta in the PR body:** that `$effect` loses `capturedRange` as a dependency, so it no longer re-runs on the `capturedRange = null` inside `handleHighlight`/`handleClearHighlight`; the outcome is unchanged because both readers refuse a collapsed range and `?? editor.state.selection` is that same collapsed selection (the swatch handlers call `setTextSelection(to)` immediately after).
