# Gc2b — #1777 Ctrl+Enter double-fires, AltGr layouts trigger chords, six Enter handlers ignore IME composition, `capturedRange` is not mapped through remote edits

Branch `fix/keyboard-and-a11y-1777`. **Closes #1777** (all four numbered items of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:21-24`. Probe: `docs/reviews/2026-09-02-v1-review/experiments/harness/e-keys.test.ts` — `E2` (AltGr) and `E3` (Ctrl+Enter inserts a `<br>`), both `[ran] Reproduced` (repo-relative; there is no `experiments/` at the repo root).

## Problem

1. **Ctrl+Enter does two things.** `App.svelte`'s `"annotation-accept-or-dismiss"` dispatch entry (`App.svelte:1563`) checks `shouldIgnoreShortcut(e)` — which covers only `INPUT`/`TEXTAREA`/`isComposing`, never `contenteditable` — and never `e.defaultPrevented`. Tiptap's HardBreak claims `Mod-Enter` on the `.ProseMirror` node and `preventDefault()`s before the window listener runs, so with the caret in the editor one Ctrl+Enter inserts a hard break **and** accepts the first pending annotation.
2. **AltGr chords fire app shortcuts.** `matchShortcut` (`src/client/hooks/useAppShortcuts.ts`) computes `mod = e.ctrlKey || e.metaKey` and most branches carry no `altKey` gate. Windows/Linux deliver AltGr as `ctrlKey && altKey`, so on pl/ro/cs/de layouts `ś ń ó {` … match `save` / `new-scratchpad` / `open-file` / `pick-tab` and are swallowed. The file header's "Layout-independence guarantees" is what this contradicts, and `describe("matchShortcut — legacy no-modifier-gate preservation")` in `tests/client/useAppShortcuts.test.ts` currently pins the bug.
3. **Six Enter handlers ignore `isComposing`.** `panels/ChatPanel.svelte#handleKeyDown`, `editor/toolbar/LinkEditor.svelte#handleKeyDown`, `editor/find-replace/FindReplaceBar.svelte#handleKeydown`, `tabs/TabRenameInput.svelte#onKeydown`, `components/CommandPalette.svelte#handleKeydown`, `components/OutlinePanel.svelte#handleSearchKeydown` — zero `isComposing` references in all six. A CJK candidate-confirm Enter sends a half-converted message.
4. **`capturedRange` is a frozen PM range.** `editor/toolbar/Toolbar.svelte:128` holds raw `{from,to}` PM positions; re-capture is suppressed while `popupHasFocus()`; `createAnnotation` / `handleHighlight` / `handleClearHighlight` read `capturedRange ?? editor.state.selection`. A remote (y-sync/MCP) insert above the span while the user types is never mapped in, so the annotation lands on shifted text.

## Fix

**(1) `defaultPrevented`, on the one branch that needs it.** In `App.svelte`'s `"annotation-accept-or-dismiss"` dispatch entry, as the first statement beside the existing `shouldIgnoreShortcut` line:

```ts
// The editor claims Mod-Enter (HardBreak; exitCode in a code block; the .txt
// split in PlaintextBreaks) and preventDefault()s it. Without this, one
// keystroke inserts a break AND accepts the annotation (#1777 item 1).
if (e.defaultPrevented) return;
```

**Per-branch, not blanket, and that is the whole of the fix.** A blanket `if (e.defaultPrevented) return;` at the top of the window handler reaches every branch and silently kills `Ctrl+,` (Settings, `Mod-,` is bound by Subscript) and `Ctrl+Shift+S` (Save As, `Mod-Shift-s` is bound by Strike) whenever the caret is in the editor — the exact defect this issue reports, reproduced twice. Scoping the guard to the branch the issue names leaves every other chord exactly as it is today.

**Consequence, and it must be stated in the PR body:** with the caret in the editor, Ctrl+Enter now does one thing — a hard break (or `exitCode` in a code block, or the `.txt` split) — and no longer accepts. Ctrl+Shift+Enter is claimed by nothing (prosemirror-keymap normalizes it to `"Shift-Ctrl-Enter"`), so dismiss still works there. Accept keeps working everywhere the caret is not inside ProseMirror, which is the annotation rail — where the affordance is actually used. `docs/user-guide.md:277,399`, `docs/workflows.md:271,347`, `OnboardingTutorial.svelte:32` and `builtin.svelte.ts:1285` do not scope the chord to the editor, so no copy is wrong; they are less complete than before.

**(3) IME.** As the **first** statement of each of the six handlers, the issue's own line — inline, six copies, no shared module:

```ts
if (e.isComposing || e.keyCode === 229) return;
```

`keyCode === 229` is the second term because Safari and some IMEs deliver the confirm keydown with `isComposing` already false. In `TabRenameInput` it goes immediately after the existing `e.stopPropagation()`, which must still run. Nothing here writes `$state` from a Tiptap callback, so `createCoalescingTick` is not involved.

**(4) `capturedRange`.** Demote `Toolbar.svelte:128` from `$state<…>(null)` to a plain `let capturedRange: { from: number; to: number } | null = null;`, and map it in the existing `$effect` that attaches `selectionUpdate` (`Toolbar.svelte:744-755`, the captured-`ed` pattern):

```ts
const onTx = ({ transaction }: { transaction: Transaction }) => {
  if (!capturedRange || !transaction.docChanged) return;
  const from = transaction.mapping.map(capturedRange.from, 1);
  const to = transaction.mapping.map(capturedRange.to, -1);
  capturedRange = { from, to: Math.max(from, to) };
};
ed.on("transaction", onTx);   // detach in the same cleanup as onSelChange
```

Assoc `1`/`-1` keeps an insertion at either edge outside the annotation; a remote insert above shifts both, which is the issue's case.

Demote rather than bridge through `createCoalescingTick`: the CLAUDE.md rule exists because the write targets `$state`, and nothing reactive reads this cell — no `$derived`, no template expression, only the three action handlers and the `!capturedRange` guard. Removing `$state` retires `state_unsafe_mutation` for the new `transaction` subscriber *and* for the existing `selectionUpdate` one. State the one delta in the PR body: that `$effect` no longer re-runs on `capturedRange = null` in `handleHighlight`/`handleClearHighlight`; the outcome is unchanged because both readers refuse a collapsed range and `?? editor.state.selection` is that same collapsed selection.

**(4a) The delete polarity, because this fix is what makes it reachable.** If the span is deleted the mapped positions collapse and `createAnnotation` returns `undefined` — the third of the three returns `Toolbar.svelte:935-942` calls unreachable. Today `submitAsComment`/`submitAsNote` call `dismissPopup()` unconditionally and it clears `annotationText`, so the typed draft would vanish silently. In both functions move `dismissPopup()` inside the `if (id)` arm; on the `undefined` arm set `capturedRange = null` **first** (otherwise the next submit retries the same dead range forever — the re-capture path only fires when `capturedRange` is null and `selectionUpdate` bails while `popupHasFocus()`), then `onNotify?.(…)` with copy saying both that the draft is kept and that the passage must be re-selected. Leave the `tandem:addressed-ai` dispatch inside `if (id)`. Rewrite the `:935-942` invariant comment to record that the third return is now reachable.
