# Gc2b — #1777 Ctrl+Enter double-fires, AltGr layouts trigger chords, six Enter handlers ignore IME composition, `capturedRange` is not mapped through remote edits

Branch `fix/keyboard-and-a11y-1777`. **Closes #1777** (all four numbered items of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:21-24` (four rows, all #1777). Probe: `docs/reviews/2026-09-02-v1-review/experiments/harness/e-keys.test.ts` — `E2` (AltGr, synthetic) and `E3` (Ctrl+Enter inserts a `<br>`), both `[ran] Reproduced`. (Repo-relative — there is no `experiments/` at the repo root.)

## Problem

1. **Ctrl+Enter does two things.** `App.svelte`'s window `keydown` handler (the `$effect` holding `function handler(e)` that calls `matchShortcut`) never reads `e.defaultPrevented`. Tiptap's `HardBreak` claims `Mod-Enter` on the `.ProseMirror` node — a bubble listener that runs *before* the window one and calls `preventDefault()` — so with the caret in the editor a single Ctrl+Enter inserts a hard break **and** accepts the first pending annotation. `shouldIgnoreShortcut` does not save it: that predicate only suppresses `INPUT`/`TEXTAREA` and `isComposing`, never `contenteditable`.

   **The collision is asymmetric, and that constrains the fix.** `PlaintextBreaksExtension#splitInsteadOfBreak` (`src/client/editor/extensions/plaintext-breaks.ts`) returns `false` on a non-plaintext format, so on a `.md` document `Mod-Enter` falls through to HardBreak's binding, which returns true and makes prosemirror-view `preventDefault()`. Ctrl+**Shift**+Enter is not claimed by anything: prosemirror-keymap normalizes it to `"Shift-Ctrl-Enter"`, `Enter` is not a single-character key name so none of the noShift / base-keycode fallbacks apply, and neither `"Mod-Enter"` nor `"Shift-Enter"` matches. So a blanket `if (e.defaultPrevented) return;` alone would silently kill **accept**-in-editor while leaving **dismiss**-in-editor working — an undocumented asymmetry against four user-facing surfaces that promise `Ctrl+Enter` accepts (`docs/user-guide.md:277`, `:399`; `docs/workflows.md:271`, `:347`; `src/client/components/OnboardingTutorial.svelte:32`; the command-palette row at `src/client/actions/builtin.svelte.ts:1285`).

2. **AltGr chords fire app shortcuts.** `matchShortcut` (`src/client/hooks/useAppShortcuts.ts`) computes `mod = e.ctrlKey || e.metaKey` and most `e.code` branches carry no `altKey` gate. Windows/Linux deliver AltGr as `ctrlKey && altKey`, so on pl/ro/cs/de layouts `ś ń ó {` … match `save` / `new-scratchpad` / `open-file` / `pick-tab` and are swallowed by the handler's `preventDefault()`. The file header's "Layout-independence guarantees" is exactly what this contradicts. **The current test file pins the bug**: `tests/client/useAppShortcuts.test.ts` has a `describe("matchShortcut — legacy no-modifier-gate preservation")` whose cases assert Ctrl+Alt+S → `save` and friends.

3. **Six Enter handlers ignore `isComposing`.** `panels/ChatPanel.svelte#handleKeyDown` (`e.key === "Enter" && !e.shiftKey`), `editor/toolbar/LinkEditor.svelte#handleKeyDown`, `editor/find-replace/FindReplaceBar.svelte#handleKeydown`, `tabs/TabRenameInput.svelte#onKeydown`, `components/CommandPalette.svelte#handleKeydown`, `components/OutlinePanel.svelte#handleSearchKeydown`. Zero `isComposing` references in all six. A CJK candidate-confirm Enter sends a half-converted chat message, commits a half-converted link, or renames a tab mid-conversion.

4. **`capturedRange` is a frozen PM range.** `editor/toolbar/Toolbar.svelte:128` declares it, `captureSelectionRange()` writes raw `{from,to}` PM positions, re-capture is suppressed while `popupHasFocus()`, and `createAnnotation` / `handleHighlight` / `handleClearHighlight` read `capturedRange ?? editor.state.selection`. A remote (y-sync/MCP) insertion above the span while the user types the comment is never mapped in, so the annotation lands on shifted text.

## Fix

**(1a) Stop HardBreak claiming `Mod-Enter`, so Ctrl+Enter reaches the window handler at all.** In `src/client/editor/editor-extensions.ts#buildSchemaExtensions`, add `hardBreak: false` to the `StarterKit.configure({…})` call and register the node explicitly instead:

```ts
import HardBreak from "@tiptap/extension-hard-break"; // already installed

// hardBreak:false above, then:
// Mod-Enter is deliberately NOT rebound. HardBreak's stock keymap claims it,
// which makes prosemirror-view preventDefault() and silently swallows the
// app-level Ctrl+Enter "accept annotation" chord whenever the caret is in the
// editor (#1777 item 1). Shift+Enter runs the identical command — including
// setHardBreak's exitCode() arm — so nothing is lost: the affordance keeps its
// other binding and Ctrl+Enter stops meaning two things at once.
HardBreak.extend({
  addKeyboardShortcuts() {
    return { "Shift-Enter": () => this.editor.commands.setHardBreak() };
  },
}),
```

This resolves the collision at its source rather than by dropping a documented shortcut, so **no user-facing copy changes**: `docs/user-guide.md:277,399`, `docs/workflows.md:271,347`, `OnboardingTutorial.svelte:32` and `builtin.svelte.ts:1285` all stay true, and accept/dismiss stay symmetric in the editor.

The one place they are *both* still suppressed is a plaintext (`.txt`) document, where `splitInsteadOfBreak` claims `Mod-Enter` **and** `Shift-Enter` and genuinely edits the document — symmetric, deliberate, and worth one line in the PR body.

**(1b) `defaultPrevented`, for the remaining collisions.** First statement inside `App.svelte`'s window `handler(e)` — above the F2 branch — `if (e.defaultPrevented) return;`, with a comment naming the mechanism. Blanket, not per-handler. The audit of what it now changes, corrected from round 1:

- ProseMirror's base `Mod-a` — already handled: `dispatch["select-all"]` returns early when `document.activeElement.closest(".ProseMirror")`. No behavioural delta.
- **`Mod-Shift-7` / `Mod-Shift-8` vs `pick-tab`** — a real collision the first draft missed. `useAppShortcuts.ts`'s `pick-tab` branch matches `/^Digit[1-9]$/` with no shift gate, while Tiptap's OrderedList/BulletList bind `Mod-Shift-7`/`Mod-Shift-8` and prosemirror-keymap's base-keycode fallback resolves Ctrl+Shift+7 to `"Shift-Ctrl-7"`. Today Ctrl+Shift+7 in the editor toggles an ordered list *and* switches to tab 7. The guard fixes that; record it as an intended behavioural change, not a side effect.
- `find-replace.ts` and `list-item-checkbox.ts` bind only `Escape`/`Enter` (no modifier), which `matchShortcut` does not match.

This is the same guard `App.svelte`'s Escape-to-deselect comment already documents for the slash menu — one mechanism, now applied to the shortcut path too.

**(2) AltGr.** Add `!e.altKey` to the `mod`-block branches that have no alt gate today: `settings` (Comma), `toggle-help` (`e.key === "/"`), `save` (KeyS), `toggle-palette` (Shift+KeyP), `new-scratchpad` (KeyN), `close-tab` (KeyW), `open-file` (KeyO), `pick-tab` (`Digit[1-9]`), `find` (KeyF), `find-nav` (KeyG), `annotation-accept-or-dismiss` (`e.key === "Enter"`). **Do not touch the three deliberate Ctrl+Alt chords** — `reopen-closed-tab` (Alt+KeyT), `comment-on-selection` (Alt+KeyM), `toggle-authorship` (Alt+KeyA) — nor the branches that already gate alt (`select-all`, `save-as`, `focus-chat`, `toggle-source-view`, `toggle-mode`, `new-tab-menu`). The alt-only block below is already immune (`!e.ctrlKey && !e.metaKey`), and the override layer's `chordMatches` compares `chord.alt === e.altKey` exactly, so no change there.

Rewrite **two** comment blocks that this invalidates, not one:

- the "legacy no-modifier-gate preservation" block inside the `mod` branch — it currently instructs the next reader to preserve the bug;
- the `save-as` branch comment, which reads "`!altKey` so Ctrl+Shift+Alt+S falls through to the ungated save branch (legacy behavior)". After the `save` branch gains `!e.altKey`, Ctrl+Shift+Alt+S matches nothing and that sentence is false.

Extend the header's "Layout-independence guarantees" list with the AltGr line.

**(3) IME.** One shared predicate rather than six copies of the same two-term test. Add to `src/client/hooks/useTabKeyboardShortcuts.ts` (which already owns this file's two IME-aware predicates), declared **structurally with both properties optional** so it accepts every existing narrowed parameter shape and every synthetic test literal unchanged:

```ts
export function isImeComposing(e: { isComposing?: boolean; keyCode?: number }): boolean {
  return e.isComposing === true || e.keyCode === 229;
}
```

A `Pick<KeyboardEvent, "isComposing" | "keyCode">` signature does **not** typecheck at the three delegation sites: `shouldIgnoreShortcut` / `shouldIgnoreSaveAsShortcut` take `Pick<KeyboardEvent, "target" | "isComposing">` (no `keyCode`), and `matchShortcut` takes `KeyboardEventLike`, whose `isComposing?: boolean` is optional and which has no `keyCode` — as do the literals in `tests/client/useAppShortcuts.test.ts`, `src/client/actions/shortcut-conflicts.ts` and `tests/client/keybindings.test.ts`. Add `keyCode?: number` to `KeyboardEventLike` so a real `KeyboardEvent` still assigns and the second term is reachable from `matchShortcut`.

`keyCode === 229` is the second term because Safari and some IMEs deliver the confirm keydown with `isComposing` already false but `keyCode` still 229. Have `shouldIgnoreShortcut` and `shouldIgnoreSaveAsShortcut` delegate their first line to it (they only check `isComposing` today — a strict widening, and `matchShortcut`'s own `if (e.isComposing) return null` gains the same term). Then, as the **first** statement of each of the six handlers, `if (isImeComposing(e)) return;` — before `TabRenameInput`'s `e.stopPropagation()` is fine (it must still stop), so there it goes immediately after that line. Nothing here writes `$state` from a Tiptap callback, so `createCoalescingTick` is not involved.

**(4) `capturedRange`.** Demote `Toolbar.svelte:128` from `$state<{from,to}|null>(null)` to a plain `let capturedRange: { from: number; to: number } | null = null;`, and map it in the `$effect` that already attaches `selectionUpdate` (the one gated on `showPopup`, using the captured-`ed` pattern):

```ts
const onTx = ({ transaction }: { transaction: Transaction }) => {
  if (!capturedRange || !transaction.docChanged) return;
  const from = transaction.mapping.map(capturedRange.from, 1);
  const to = transaction.mapping.map(capturedRange.to, -1);
  capturedRange = { from, to: Math.max(from, to) };
};
ed.on("transaction", onTx);   // detach in the same cleanup as onSelChange
```

Assoc `1`/`-1` keeps an insertion exactly at either edge **outside** the annotation; a remote insert above shifts both, which is the issue's case.

**The delete polarity needs three more changes, because this fix is what makes it reachable.** If the span is deleted the two positions cross and clamp to a point, and all three readers `return` on `from === to`. `Toolbar.svelte:935-939` currently carries an explicit invariant comment — "All three of `createAnnotation`'s undefined returns are unreachable from here today … The third is the one that stops being true once anything can collapse mid-compose" — and the `onTx` mapping is precisely that thing. As shipped today, `submitAsComment` / `submitAsNote` call `dismissPopup()` unconditionally on the `undefined` arm, and `dismissPopup()` sets `annotationText = ""`: the user's typed comment would vanish with no annotation and no notice. So:

- (4a) In both `submitAsComment` and `submitAsNote`, move `dismissPopup()` inside the `if (id)` arm. On the `undefined` arm keep the composer mounted with `annotationText` intact.
- (4b) On that arm call the existing `onNotify` prop (`Toolbar.svelte:93`) with a warning — the annotated text was changed or removed, so the note/comment was not saved. Do **not** dispatch `tandem:addressed-ai` (unchanged: it is already inside `if (id)`).
- (4c) Rewrite the `:935-939` comment block in the same commit to record that a remote delete can now collapse `capturedRange` mid-compose, that the third return is therefore reachable, and that the composer is deliberately kept open on it.

Why demote instead of bridging through `createCoalescingTick`, given the CLAUDE.md rule: the rule exists because the write targets `$state`, and **nothing reactive reads this cell** — no `$derived`, no template expression; the only reads are the three action handlers and the `!capturedRange` guard inside the `$effect` that also writes it. Removing `$state` retires the `state_unsafe_mutation` hazard for the new `transaction` subscriber *and* for the existing `selectionUpdate` one, which writes `$state` synchronously from a Tiptap callback today. A coalesced tick would also lose intermediate mappings unless a plain mirror were added anyway — two sources of truth for the same range. **State the one behavioural delta in the PR body:** that `$effect` loses `capturedRange` as a dependency, so it no longer re-runs on the `capturedRange = null` inside `handleHighlight`/`handleClearHighlight`; the outcome is unchanged because both readers refuse a collapsed range and `?? editor.state.selection` is that same collapsed selection (the swatch handlers call `setTextSelection(to)` immediately after).
