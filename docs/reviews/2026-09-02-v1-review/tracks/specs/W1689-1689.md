It stays exactly as it is; its typed parser is a real difference, not noise, and is **not** flattened into an untyped one to make the migration uniform.

## Fix

New `tests/helpers/mcp-harness.ts`, exporting:

```ts
export async function setupMcpServer(
  registrars: Array<(server: McpServer) => void>,
): Promise<{ client: Client; close: () => Promise<void> }>;
export function parseResult(result: Awaited<ReturnType<Client["callTool"]>>): any;
```

- **It imports no `src/` module** — only `Client`, `InMemoryTransport` and `McpServer` from `@modelcontextprotocol/sdk`. This is load-bearing, not tidiness: seven of the sixteen (`convert-error-mapping`, `html-read-only`, `mcp-wire-codes`, `mcp-wire-codes-mocked`, `range-bounds-validation`, `save-tool-allow-image-loss`, `wake-url-surfacing`) decide their module graph with hoisted `vi.mock` factories and `await import`, and a helper that pulled in a `src/server` module would resolve it ahead of their mocks. `tests/helpers/wire-code-fixtures.ts:5-6` already states and relies on the same constraint; the new file carries the sentence too.
- Registrars are passed as closures, so arity-2 registrars fit unchanged: `mcp-output-schemas.test.ts:95` and `:203` become `(s) => registerDiagnosticsTools(s, opts)`. No `server` handle is returned — nothing measured needs one, and returning it invites a caller to register after connect.
- **`parseResult` moves here and `wire-code-fixtures.ts:13` loses it**, its two consumers (`mcp-wire-codes`, `mcp-wire-codes-mocked`) importing it from `mcp-harness.js` instead. No re-export shim: a compatibility re-export is the thing that lets the two drift back apart. `wire-code-fixtures.ts` keeps `createMinimalDocx` and `seedAcceptedSuggestion`.
- Migrate all **16**, each keeping its own registrar list as its own argument, and each deleting its local `setupMcpClient`/`setupClient`/`mcpClient`/`connectInbox` body and its local parser. The four differently-named parsers keep their names as thin wrappers where a call site reads better that way (`html-read-only`'s `call()` stays, its body becoming `parseResult(await client.callTool(...))`).
- **`close` is called by every migrated file**, in `afterEach`. Eight files close today (`annotation-promote-pull-surface:156`, `awareness-tools:1188/1211/1253`, `held-in-solo-stamp:250`, `mcp-stdio-ports:39`, `range-bounds-validation:98`, `read-audience-filter:142`); eight do not, and a leaked transport surfaces much later as an unrelated timeout, never as a failure in the file that leaked it.
- Rules that bite: `tests/helpers/**/*.ts` is already inside `tsconfig.tests.node.json`'s include (whole directory, not a suffix glob), so the new file is typechecked by `typecheck:tests` and the orphan sweep in `tests/scripts/typecheck-tests-wiring.test.ts` stays green — verify, do not assume. No `src/` change, so no Y.Map key, origin-tag, `data-testid`, license-gate or `NON_LOOPBACK_ALLOWED` surface is touched; say that explicitly in the PR body so no reviewer goes looking. `npx biome format --write` over every changed file before each commit.

**Observational identity is the contract.** Same tests, same assertions, same counts. If a migration would change what a test asserts, that is a finding to report in the PR body, not a cleanup to absorb. The one deliberate behavioural delta is the eight new `close()` calls; if adding one turns a file red, that is a finding too.

## Tests

No new spec asserts that the helper exists — that would be a test of the refactor rather than of the code, and a guard/drift sweep is out of scope (the issue asks for none).

The discriminating evidence is **mutation, run by hand and recorded in the PR body with before/after output**. For a pure refactor the question is not "does the harness work" but "do the migrated files still fail when the behaviour under test breaks". Three mutations, one per migration shape, each restored from a file copy — never `git checkout`:
