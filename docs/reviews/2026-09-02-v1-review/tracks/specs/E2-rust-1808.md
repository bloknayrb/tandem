# E2-rust — #1808 `perform_install` stops the sidecar before the download, so a failed download leaves no backend while the UI says "running"

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1808. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:18`. Probe: none automatable (needs a desktop build with a reachable updater); verification is `cargo test` plus a Windows smoke line.

## Problem

`perform_install` (`src-tauri/src/lib.rs:2817`) runs, in order: acquire `SidecarShuttingDownGuard`, `stop_sidecar_gracefully`, the port/exe-lock waits, then `update.download_and_install(...)` (`:2927`). The download is the long, failure-prone step — offline, proxy, a 403, a signature mismatch — and it happens with the sidecar already dead. On failure the `Err` arm clears the pending-update marker and shows a native dialog, and the function returns; **nothing respawns the sidecar.** The app keeps running with no backend, every tab "Disconnected". The code's own comment at `:2941-2943` names the consequence.

Read against current master, not the issue's line numbers: `lib.rs` moved under #1940/#1944/#1945, which added `UpdateRoute`, `WithheldReason`, `window_ended_copy` and `show_update_window_ended_dialog` around `check_for_update`. None of those touch the ordering above.

## Fix

Split the plugin call, which is what the issue asks for and what the plugin already supports. `tauri-plugin-updater 2.11.0` exposes `Update::download(on_chunk, on_download_finish) -> Result<Vec<u8>>` and `Update::install(bytes)` separately; `download_and_install` is literally `self.download(..).await?` then `self.install(bytes)` (`updater.rs:761-765`), and **`verify_signature` runs at the end of `download`** (`:739`). So the split is behaviour-identical except for *when the sidecar is down*.

New order in `perform_install`:

1. `SidecarShuttingDownGuard::try_acquire()` stays exactly where it is (`:2849`). It is the re-entrancy gate for two clicks on "Restart to install" as well as the spawn interlock; moving it later would let two futures both download. Holding it across the download makes Settings → Restart server a no-op for the download's duration — correct, not a regression: a restart racing an imminent install is what the latch exists to refuse.
2. `let bytes = match update.download(on_chunk, on_download_finish).await { ... }`. The two closures move, subject to the comment edits below. On `Err`: `log::error!`, `pending_update::clear_pending_update(app)`, `show_update_error_dialog(...)`, `return`. **Both failure arms must clear the marker** — the finish closure fires before `verify_signature`, so a signature failure still writes one.
3. Only then: `let mut pre_install_warnings`, the `stop_sidecar_gracefully` block (`:2879-2903`) and the `#[cfg(target_os = "windows")]` / `#[cfg(not(...))]` wait blocks (`:2905-2925`), **moved down as amended by #1762** — which lands first in this PR and rewords the `if !file_ok` literal to `Sidecar exe lock not confirmed released within {SIDECAR_UNLOCK_DEADLINE_SECS}s -- installer may prompt for retry`. Move the amended text. `pre_install_warnings` is declared with them, not before the download — it sits at `:2865` today only because the stop's verdict is the first thing that can fill it.
4. `match update.install(bytes)` with the existing `Ok(())` arm (`app.restart()`) and the existing `Err` arm, `pre_install_warnings` threading included.

### Two comments the reorder falsifies — rewritten, not moved verbatim

Moving them unchanged would ship a false rationale *in the same commit that cites it as the evidence for the change*, and the natural repair for a later reader is to restore the old order.

- **`lib.rs:2941-2943`**, inside the #1118 marker-placement block: "the sidecar is already dead by this point, so the WebView sits in 'Server unavailable' for the entire download". **After the reorder the sidecar is alive for the whole download, so this is false.** Rewrite to keep the load-bearing half and drop the dead-sidecar clause: the marker still must not be written before the download, because `build_updater` sets no timeout and any process death during a long download — tray Quit, the Linux-without-tray window close, a crash, a sleep-kill — strands a marker with no `Err` arm to clean it up, and each becomes a false "your update may not have completed" on the next boot. The **"NOT on the `Ok` arm below"** half stays verbatim.
- **The `perform_install` docblock, `lib.rs:2814-2816`**: "kill sidecar, await port + file-lock release, then download+install" is the old order. Rewrite to the new one, with the reason in one clause: a download failure must never be the thing that leaves the app with no backend.

Every other `download_and_install` mention in the moved comments (`:2823`, `:2835`, `:2840`, `:2862`, `:2867`) is prose about the plugin and stays; where it names the combined call as the thing the guard spans, edit it to name `download()` and `install()` so the RAII rationale still reads true.

### The architecture doc's install flow, which the reorder also falsifies

`docs/architecture.md:981-1005` is the `Install flow:` code block, and **every arrow in it states the order this fix inverts**: `ShuttingDownGuard::try_acquire()` → `stop_sidecar_gracefully()` (`:988-995`) → `Poll /health … + on Windows … exe unlocks` (`:996-998`) → `download_and_install()` (`:999`) → `on download finish: write update-pending.json` (`:1000`) → `on install error: clear the marker` (`:1004`). This group owns that section, and #1762's spec already edits `architecture.md:998` — line 21 *of this same block* — so leaving the ordering alone ships a diagram contradicted by the code in its own commit. The spec's own standard for the two `lib.rs` comments applies verbatim: moving or keeping a false rationale in the commit that cites it as evidence is what a later reader restores the old order from.

So rewrite `docs/architecture.md:988-1004` to the new order: `try_acquire()` → `update.download()` **with the sidecar still up** → on download finish, write `update-pending.json` → `stop_sidecar_gracefully()` → poll `/health` + the Windows exe-unlock wait → `update.install(bytes)`. Add the arm the block has never carried: **`on download error: clear the marker, show the dialog, and the sidecar keeps running (#1808)`** — that arm *is* the fix, so its absence from the flow would be the same omission in doc form. The prose under the block already says "The sidecar kill before install is required to prevent a port conflict"; that stays true and needs no edit — the kill is still before `install()`, just no longer before the download.

**`docs/decisions.md:1480` (ADR-043's Context) and `:1490(a)` describe the old order too and are deliberately NOT edited** — an ADR is the record of what was decided then, not a mirror of current code. State that choice in the PR body so it reads as a decision rather than a missed file.

**One bundled copy fix.** `show_update_error_dialog` (`:2282`) opens with "Could not check for updates.", which is already the wrong sentence on the install path and would be wrong on the *download* path too. Give it a `lead: &str` first-message parameter and pass the right sentence at each of its three call sites (the two check sites keep "Could not check for updates."; the download and install arms say "Could not install the update."). Four lines inside a function this PR's callers already move — bundled per CLAUDE.md's scope rule rather than left as an unfiled observation.

**What this makes impossible:** every error that can occur while the sidecar is *deliberately* down is now an *install* error, and no path deliberately stops the sidecar and then returns without installing. The issue's second clause ("on any error before install respawn the sidecar") is satisfied by there being no such error.

**The residual, named rather than implied away.** *Deliberately* is load-bearing. The guard is held across the whole function and `spawn_allowed()` is `!EXITING && !SIDECAR_SHUTTING_DOWN` (`sidecar.rs:255`), so for the download's duration every spawn producer declines — Settings → Restart server, `start_sidecar`'s retry loop, the Retry Server Start dialog, and (new in this PR, #1809) the crash handler. If the sidecar *crashes* during the now-longer download, nothing respawns it until the guard drops. Accepted: the latch stays whole-function because the alternative is a fresh child landing in the slot the installer is about to overwrite on disk. **#1809's `!spawn_allowed -> Ignore` bullet cross-references this paragraph**, so the PR body states the interaction once.

**What moves and must not be dropped:** the `#[must_use] StopReport` handling and its two `log::warn!` arms at `:2890-2903`. The success string `Pre-install: graceful sidecar shutdown complete — unsaved edits were flushed before the update` is pinned by `respawn_guard_lines_are_warns_and_match_the_smoke_checklist` in `sidecar.rs`, which requires it **exactly once** in `lib.rs` as the first argument of an uncommented `log::warn!`. Moving keeps that true; rewording does not.

**Marker window, stated rather than changed:** `record_pending_update` still fires at download-finish, so a stop-and-wait (up to 15 s) now sits between the marker write and `install()`. A process death there strands a marker exactly as a death during `install()` does today. Narrowing the marker to just before `install(bytes)` is deliberately not done — it would change #1118's semantics inside a PR about ordering.

**Rules that bite:** no `/api` route, MCP tool, Y.Doc write, `data-testid` or licensing const is touched. `perform_install` is downstream of `build_updater`'s route choice and reads neither const.

## Tests

`perform_install` takes an `AppHandle` and a real `tauri_plugin_updater::Update`, neither constructible in a unit test, so the one discriminating test is structural, following `sidecar.rs:4107`'s `include_str!` precedent. **One test, not three** — the ordering *is* the fix.

`fn perform_install_downloads_before_it_stops_the_sidecar()`, in a new named `#[cfg(test)] mod install_order_tests` in `lib.rs` (**there is no `mod tests` in `lib.rs`** — every test module there is named). `include_str!("lib.rs")`, slice `perform_install`'s body from `async fn perform_install(` to the next `\n}\n` at column 0, **with `char_indices()`/`get()`, never a raw byte range** — `lib.rs` is full of em dashes and a byte slice landing mid-`—` panics (`sidecar.rs:4119` documents exactly this). The end boundary `.expect("perform_install body must be delimited")`, so a renamed function fails as a rename.

```rust
let dl = body.find("update.download(").expect("perform_install must call update.download(");
let stop = body.find("stop_sidecar_gracefully(").expect("perform_install must still stop the sidecar");
assert!(dl < stop, "the download must complete before the sidecar is stopped (#1808)");
```

**Bind both offsets with `.expect()` before comparing.** A bare `Option` comparison is vacuously true on today's code: there is no `update.download(` in `lib.rs` yet, so the left side is `None`, and `None < Some(_)` is `true` — the test would pass unfixed. The `.expect()`s are what make it discriminating.

**Mutation check:** swap the two blocks back and the test goes red. Restore from a file copy, never `git checkout`.

## Done when

The sidecar is alive for the whole download; the ordering test passes; the two falsified comments are rewritten; `docs/architecture.md`'s install-flow block states the new order and carries the download-error arm; the `StopReport` warn pair and its pinned string survive the move; `show_update_error_dialog` leads with the right sentence at each call site; `cargo test` green.

## Not in scope

**A respawn on the `install()` failure arm.** That path still ends with the sidecar stopped, deliberately: on Windows `install_inner` ends in `std::process::exit(0)` on success, so a failure there means the installer could not even be launched — a terminal state whose recovery is the failure dialog plus Settings → Network → Restart server. Spawning a child while an installer may be mid-write over the binary is what `SIDECAR_SHUTTING_DOWN` exists to prevent. Named in the PR body as a decision, not a gap.

**"Surface the updater error in the Settings → Updates copy"** (the issue's third clause). One reason: the error *is* surfaced — natively, with the error string verbatim and the pre-install warnings appended, on both failure arms — and this PR makes that surface accurate by fixing its lead sentence. Settings → Updates is one possible surface, not the required one.

## PR review round 1

**The residual paragraph above was wrong, and is superseded.** It says a sidecar crash during the
download "is not restarted until the guard drops". Nothing restarts it after the guard drops
either — see `E2-rust-1809.md`'s round-1 section for the mechanism (one-shot `Terminated`, no
health watchdog, two `restart_sidecar` call sites). So the comment on this PR's own failure arm,
"the sidecar was never stopped, so the app keeps its backend", was false in exactly the case the
issue is about.

The ordering fix stands unchanged. What was added: the failure arm now drops the
`SidecarShuttingDownGuard` and calls `sidecar::recover_deferred_crash(app)` **before** the error
dialog — in that order, because `restart_sidecar` re-checks `spawn_allowed()` and a recovery made
while still latched is a silent no-op. `the_download_failure_arm_releases_the_latch_then_recovers_a_deferred_crash`
pins it.
