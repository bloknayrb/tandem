# E2-rust — #1808 `perform_install` stops the sidecar before the download, so a failed download leaves no backend while the UI says "running"

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1808. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:18`. Probe: none automatable (needs a desktop build with a reachable updater); verification is `cargo test` plus a Windows smoke line.

## Problem

`perform_install` (`src-tauri/src/lib.rs:2817`) runs, in order: acquire `SidecarShuttingDownGuard`, `stop_sidecar_gracefully` (`:2891`), the port/exe-lock waits (`:2905-2925`), then `update.download_and_install(...)` (`:2927`). The download is the long, failure-prone step — offline, proxy, a 403 from the endpoint, a signature mismatch — and it happens with the sidecar already dead. On failure the `Err` arm (`:2965`) clears the pending-update marker and shows a native dialog, and the function returns; **nothing respawns the sidecar.** The app keeps running with no backend, every tab "Disconnected". The code's own comment at `:2941-2943` already names the consequence ("the sidecar is already dead by this point, so the WebView sits in 'Server unavailable' for the entire download, actively inviting a quit").

Read against current master, not the issue's line numbers: `lib.rs` moved under #1940/#1944/#1945, which added `UpdateRoute`, `WithheldReason`, `window_ended_copy` and `show_update_window_ended_dialog` around `check_for_update`. None of those touch the ordering above.

## Fix

Split the plugin call, which is what the issue asks for and what the plugin already supports. `tauri-plugin-updater 2.11.0` exposes `Update::download(on_chunk, on_download_finish) -> Result<Vec<u8>>` and `Update::install(bytes)` separately; `download_and_install` is literally `self.download(..).await?` then `self.install(bytes)` (`updater.rs:761-765`), and **`verify_signature` runs at the end of `download`** (`:739`). So the split is behaviour-identical except for *when the sidecar is down*.

New order in `perform_install`:

1. `SidecarShuttingDownGuard::try_acquire()` stays exactly where it is (`:2849`). It is the re-entrancy gate for two clicks on "Restart to install" as well as the spawn interlock; moving it later would let two futures both download. Holding it across the download makes Settings → Restart server a no-op for the download's duration — that is correct, not a regression: a restart racing an imminent install is the thing the latch exists to refuse.
2. `let bytes = match update.download(on_chunk, on_download_finish).await { ... }`. The two closures move, subject to the **comment edits enumerated below** — they are not verbatim, because the reorder falsifies one of them. On `Err`: `log::error!`, `pending_update::clear_pending_update(app)`, `show_update_error_dialog(app, "Could not install the update.", &e.to_string())`, `return`. **Both failure arms must clear the marker** — the closure fires before `verify_signature`, so a signature failure still writes one, which is exactly the case the existing comment at `:2946-2948` covers.
3. Only then: `let mut pre_install_warnings`, the `stop_sidecar_gracefully` block (`:2879-2903`) and the `#[cfg(target_os = "windows")]` / `#[cfg(not(...))]` wait blocks (`:2905-2925`), **moved down as amended by #1762** — which lands first in this PR and rewords the `if !file_ok` literal to `Sidecar exe lock not confirmed released within {SIDECAR_UNLOCK_DEADLINE_SECS}s -- installer may prompt for retry`. Move the amended text; a later reader diffing the block must not restore the pre-#1762 message. `pre_install_warnings` must be declared with them, not before the download — it currently sits at `:2865` only because the stop's verdict is the first thing that can fill it.
4. `match update.install(bytes)` with the existing `Ok(())` arm (`app.restart()`) and the existing `Err` arm, `pre_install_warnings` threading included.

### Comment edits — the "verbatim" instruction was wrong and is replaced

Two comment blocks state facts the reorder inverts. Moving them unchanged would ship a false rationale *in the same commit that cites it as the evidence for the change*, and the natural repair for a later reader is to restore the old order. Both are rewritten, explicitly:

- **`lib.rs:2941-2943`**, inside the `#1118` marker-placement block: "Not hypothetical: the sidecar is already dead by this point, so the WebView sits in 'Server unavailable' for the entire download, actively inviting a quit." **After the reorder the sidecar is alive for the whole download, so this sentence is false.** Rewrite the paragraph to keep the load-bearing half and drop the dead-sidecar clause: the marker still must not be written before the download, because `build_updater` sets no timeout and any process death during a long download — tray Quit, the Linux-without-tray window close, a crash, a sleep-kill — would strand a marker with no `Err` arm to clean it up, and every one of those becomes a false "your update may not have completed" on the next boot. The **"NOT on the `Ok` arm below"** half is unchanged and stays verbatim.
- **The `perform_install` docblock, `lib.rs:2814-2816`**: "Shared install flow: kill sidecar, await port + file-lock release, then download+install via the Tauri updater plugin." That is the old order. Rewrite to the new one: download (and verify) first, then stop the sidecar, await port + file-lock release, then install — and say why, in one clause: a download failure must never be the thing that leaves the app with no backend.

Every other `download_and_install` mention in the moved comments (`:2823`, `:2835`, `:2840`, `:2862`, `:2867`) is prose about the plugin's behaviour and stays; where it names the combined call as the thing the guard spans, prefer editing it to name `download()` and `install()` so the RAII rationale still reads true.

**Native dialog copy, corrected here rather than deferred.** `show_update_error_dialog` (`:2282`) opens with "Could not check for updates.", which is the wrong sentence on the install path and would now be the wrong sentence on the *download* path too. Give it a `lead: &str` first message parameter and pass the right sentence at each of its three call sites (`:2689` and `:2717` keep "Could not check for updates."; the download and install arms say "Could not install the update."). Four lines, inside a function this PR's callers already move — the kind of small tangential fix CLAUDE.md's scope rule says to bundle rather than file.

**What this makes impossible:** every error that can occur while the sidecar is *deliberately* down is now an *install* error, and there is no longer any path that deliberately stops the sidecar and then returns without installing. The issue's second clause ("on any error before install respawn the sidecar") is satisfied by there being no such error, which is strictly better than a respawn.

**The residual, named rather than implied away.** The word *deliberately* is load-bearing. `SidecarShuttingDownGuard` is acquired at `:2849` and held across the whole function, and `spawn_allowed()` is `!EXITING && !SIDECAR_SHUTTING_DOWN` (`sidecar.rs:255`), so for the duration of the download **every** spawn producer declines — Settings → Restart server, `start_sidecar`'s retry loop, the Retry Server Start dialog, and (new in this PR, see #1809) the crash handler. If the sidecar *crashes* during the now-lengthened download, nothing respawns it until the download finishes and the guard drops. That is the original #1808 symptom in a narrower window, and it is accepted: the latch stays whole-function because the alternative is letting a fresh child land in the slot the installer is about to overwrite on disk, which is exactly what `SIDECAR_SHUTTING_DOWN` exists to prevent. **#1809's `!spawn_allowed -> Ignore` bullet cross-references this paragraph**, so the combined PR body states the interaction rather than leaving a reviewer to re-derive it from two specs.

**What moves and must not be dropped:** the `#[must_use] StopReport` handling and its two `log::warn!` arms at `:2890-2903`. The success string `Pre-install: graceful sidecar shutdown complete — unsaved edits were flushed before the update` is pinned by `respawn_guard_lines_are_warns_and_match_the_smoke_checklist` in `sidecar.rs`, which requires it **exactly once** in `lib.rs` as the first argument of an uncommented `log::warn!`. Moving the block keeps that true; rewording it does not.

**Marker window, stated rather than changed:** `record_pending_update` still fires at download-finish, so there is now a stop-and-wait (up to 15 s) between the marker write and `install()`. A process death in that window strands a marker exactly as a death during `install()` does today. Narrowing the marker to just before `install(bytes)` is **deliberately not done** — it would change #1118's semantics (the signature-failure case currently writes and clears one) inside a PR about ordering.

**Rules that bite:** no `/api` route, MCP tool, Y.Doc write, `data-testid` or licensing const is touched. `LICENSE_GATE_ENABLED` and `LICENSE_UPDATE_ENDPOINT` stay as they are — `perform_install` is downstream of `build_updater`'s route choice and this change reads neither.

## Tests

`perform_install` takes an `AppHandle` and a real `tauri_plugin_updater::Update`, neither constructible in a unit test, so the discriminating test is structural and follows the existing source-reading precedent in `src-tauri/src/sidecar.rs` (`start_sidecar_folds_the_env_pairs_onto_the_command`, `:4107`, which reads its own file via `include_str!`).

**Module:** a new `#[cfg(test)] mod install_order_tests` in `lib.rs`. **There is no `mod tests` in `lib.rs`** — every test module there is named (`pending_opens_tests` at `:2988`, `url_constants_tests` at `:3313`, and four more), so "lib.rs's test module" names nothing.

**Slicing rule for all three tests:** take the body with `char_indices()`/`get()`, never a raw byte range. `lib.rs` is full of em dashes and a byte slice landing mid-`—` panics; `sidecar.rs:4119` documents exactly this ("Char-indexed, not byte-sliced: this file is full of em dashes"). The end boundary must `.expect("perform_install body must be delimited")` rather than falling back to the file end, so a renamed function fails as a rename.

1. `fn perform_install_downloads_before_it_stops_the_sidecar()` — `include_str!("lib.rs")`, slice `perform_install`'s body from `async fn perform_install(` to the next `\n}\n` at column 0. **Bind both offsets with `.expect()` first, then compare:**

   ```rust
   let dl = body.find("update.download(").expect("perform_install must call update.download(");
   let stop = body.find("stop_sidecar_gracefully(").expect("perform_install must still stop the sidecar");
   assert!(dl < stop, "the download must complete before the sidecar is stopped (#1808)");
   ```

   **A bare `Option` comparison is vacuously true on today's code**: there is no `update.download(` in `lib.rs` yet, so the left side is `None`, and `None < Some(_)` is `true` in Rust — the test would pass on the unfixed code. The `.expect()`s are what make it discriminating, not decoration.
2. `fn perform_install_clears_the_pending_marker_on_both_failure_arms()` — same slice; assert `pending_update::clear_pending_update(` occurs **twice**, counting only lines whose first non-whitespace is not `//`. **The comment filter is required**, not hygiene: the existing `Err` arm already carries a comment about the clear (`:2969-2973`), and the new download-failure arm plausibly will too, so a raw count is inflatable by prose. This follows `respawn_guard_lines_are_warns_and_match_the_smoke_checklist` (`sidecar.rs:3115-3205`), which checks "not commented out" for exactly this reason — a comment satisfying the check was the measured defeat of its predecessor. Kills the most likely implementation slip: splitting the call and clearing the marker only on the install arm, which would leave a stranded marker nagging "your update may not have completed" on the next boot after every failed download.
3. `fn perform_install_no_longer_calls_download_and_install()` — assert the slice does not contain **`update.download_and_install(`**, the call form. **Not the bare symbol:** `download_and_install` appears seven times in `perform_install` and six are comments (`lib.rs:2823`, `:2835`, `:2840`, `:2862`, `:2867`, `:2936`) that the fix keeps, including the #1756 RAII-guard rationale and the #1118 marker-placement block — so a bare-symbol scan goes red on a correct implementation and the natural repair is to delete load-bearing rationale to satisfy a string search. `update.download_and_install(` occurs exactly once in the whole file (verified), and no comment uses the `update.` receiver (the nearest, `:2835`, reads `download_and_install(..).await`). Kills a partial edit that adds a `download()` call while leaving the combined one.

**Mutation check:** swap the two blocks back and test 1 goes red; delete one `clear_pending_update` and test 2 goes red; restore `update.download_and_install(` and test 3 goes red. Restore from a file copy, never `git checkout`.

## Done when

## Not in scope

**A respawn on the `install()` failure arm.** That path still ends with the sidecar stopped, and it is deliberately left as it is: on Windows `install_inner` ends in `std::process::exit(0)` on success, so a failure there means the installer could not even be launched — a terminal state whose recovery is the existing failure dialog plus Settings → Network → Restart server. Spawning a child while an installer may be mid-write over the binary is the condition `SIDECAR_SHUTTING_DOWN` exists to prevent. Named in the PR body so it reads as a decision, not a gap.

**"Surface the updater error in the Settings → Updates copy"** (the issue's third clause). **One reason, not two:** the error *is* surfaced — natively, with the error string verbatim and the pre-install warnings appended, on both the download and install failure arms — and this PR makes that surface accurate by fixing its lead sentence (it said "Could not check for updates." after an install failure). Settings → Updates is one possible surface, not the required one. The PR body quotes the new copy and says so on the issue; it does **not** also plead scope, because pleading two reasons for one decline is how a clause ends up belonging to nobody.
