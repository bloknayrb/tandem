# E2-rust — #1808 `perform_install` stops the sidecar before the download, so a failed download leaves no backend while the UI says "running"

Branch `fix/desktop-sidecar-lifecycle-and-start-at-login-repair-1762`. Closes #1808. Ledger: `docs/reviews/2026-09-02-v1-review/areas/tauri.md:18`. Probe: none automatable (needs a desktop build with a reachable updater); verification is `cargo test` plus a Windows smoke line.

## Problem

`perform_install` (`src-tauri/src/lib.rs:2817`) runs, in order: acquire `SidecarShuttingDownGuard`, `stop_sidecar_gracefully` (`:2891`), the port/exe-lock waits (`:2905-2925`), then `update.download_and_install(...)` (`:2927`). The download is the long, failure-prone step — offline, proxy, a 403 from the endpoint, a signature mismatch — and it happens with the sidecar already dead. On failure the `Err` arm (`:2965`) clears the pending-update marker and shows a native dialog, and the function returns; **nothing respawns the sidecar.** The app keeps running with no backend, every tab "Disconnected". The code's own comment at `:2942-2947` already names the consequence ("the WebView sits in 'Server unavailable' for the entire download, actively inviting a quit").

Read against current master, not the issue's line numbers: `lib.rs` moved under #1940/#1944/#1945, which added `UpdateRoute`, `WithheldReason`, `window_ended_copy` and `show_update_window_ended_dialog` around `check_for_update`. None of those touch the ordering above.

## Fix

Split the plugin call, which is what the issue asks for and what the plugin already supports. `tauri-plugin-updater 2.11.0` exposes `Update::download(on_chunk, on_download_finish) -> Result<Vec<u8>>` and `Update::install(bytes)` separately; `download_and_install` is literally `self.download(..).await?` then `self.install(bytes)` (`updater.rs:761-765`), and **`verify_signature` runs at the end of `download`** (`:739`). So the split is behaviour-identical except for *when the sidecar is down*.

New order in `perform_install`:

1. `SidecarShuttingDownGuard::try_acquire()` stays exactly where it is (`:2849`). It is the re-entrancy gate for two clicks on "Restart to install" as well as the spawn interlock; moving it later would let two futures both download. Holding it across the download makes Settings → Restart server a no-op for the download's duration — that is correct, not a regression: a restart racing an imminent install is the thing the latch exists to refuse.
2. `let bytes = match update.download(on_chunk, on_download_finish).await { ... }`. The two closures move verbatim, including the `record_pending_update` closure and its `:2934-2960` comment block. On `Err`: `log::error!`, `pending_update::clear_pending_update(app)`, `show_update_error_dialog(app, &e.to_string())`, `return`. **Both failure arms must clear the marker** — the closure fires before `verify_signature`, so a signature failure still writes one, which is exactly the case the existing comment at `:2957-2959` covers.
3. Only then: `let mut pre_install_warnings`, the `stop_sidecar_gracefully` block (`:2879-2903`) and the `#[cfg(target_os = "windows")]` / `#[cfg(not(...))]` wait blocks (`:2905-2925`), moved down unchanged. `pre_install_warnings` must be declared with them, not before the download — it currently sits at `:2874` only because the stop's verdict is the first thing that can fill it.
4. `match update.install(bytes)` with the existing `Ok(())` arm (`app.restart()`) and the existing `Err` arm verbatim, `pre_install_warnings` threading included.

**What this makes impossible:** every error that can occur while the sidecar is down is now an *install* error, and there is no longer any path that stops the sidecar and then returns without installing. The issue's second clause ("on any error before install respawn the sidecar") is satisfied by there being no such error, which is strictly better than a respawn.

**What moves and must not be dropped:** the `#[must_use] StopReport` handling and its two `log::warn!` arms at `:2890-2903`. The success string `Pre-install: graceful sidecar shutdown complete — unsaved edits were flushed before the update` is pinned by `respawn_guard_lines_are_warns_and_match_the_smoke_checklist` in `sidecar.rs`, which requires it **exactly once** in `lib.rs` as the first argument of an uncommented `log::warn!`. Moving the block keeps that true; rewording it does not.

**Marker window, stated rather than changed:** `record_pending_update` still fires at download-finish, so there is now a stop-and-wait (up to 15 s) between the marker write and `install()`. A process death in that window strands a marker exactly as a death during `install()` does today. Narrowing the marker to just before `install(bytes)` is **deliberately not done** — it would change #1118's semantics (the signature-failure case currently writes and clears one) inside a PR about ordering.

**Rules that bite:** no `/api` route, MCP tool, Y.Doc write, `data-testid` or licensing const is touched. `LICENSE_GATE_ENABLED` and `LICENSE_UPDATE_ENDPOINT` stay as they are — `perform_install` is downstream of `build_updater`'s route choice and this change reads neither.

## Tests

`perform_install` takes an `AppHandle` and a real `tauri_plugin_updater::Update`, neither constructible in a unit test, so the discriminating test is structural and follows the existing source-reading precedent in `src-tauri/src/sidecar.rs` (`start_sidecar_folds_the_env_pairs_onto_the_command`, `:4107`, which reads its own file via `include_str!`). Put these in `lib.rs`'s test module.

1. `fn perform_install_downloads_before_it_stops_the_sidecar()` — `include_str!("lib.rs")`, slice `perform_install`'s body from `async fn perform_install(` to the next `\n}\n` at column 0, and assert `body.find("update.download(") < body.find("stop_sidecar_gracefully(")`. This is the whole issue in one assertion: it goes red on today's code and on any re-ordering that puts the stop back first. Assert both `find`s are `Some` with messages naming which symbol moved, so a rename fails as a rename rather than as an inverted comparison.
2. `fn perform_install_clears_the_pending_marker_on_both_failure_arms()` — same slice; assert `clear_pending_update` occurs **twice**. Kills the most likely implementation slip: splitting the call and clearing the marker only on the install arm, which would leave a stranded marker nagging "your update may not have completed" on the next boot after every failed download.
3. `fn perform_install_no_longer_calls_download_and_install()` — assert the slice does not contain `download_and_install`. Kills a partial edit that adds a `download()` call while leaving the combined one.

**Mutation check:** swap the two blocks back and test 1 goes red; delete one `clear_pending_update` and test 2 goes red. Restore from a file copy, never `git checkout`.

## Done when

The sidecar is alive for the whole download; three structural tests pass; the `StopReport` warn pair and its pinned string survive the move; `cargo test` green.

## Not in scope

**A respawn on the `install()` failure arm.** That path still ends with the sidecar stopped, and it is deliberately left as it is: on Windows `install_inner` ends in `std::process::exit(0)` on success, so a failure there means the installer could not even be launched — a terminal state whose recovery is the existing failure dialog plus Settings → Network → Restart server. Spawning a child while an installer may be mid-write over the binary is the condition `SIDECAR_SHUTTING_DOWN` exists to prevent. Named in the PR body so it reads as a decision, not a gap.

**"Surface the updater error in the Settings → Updates copy"** (the issue's third clause): `show_update_error_dialog` already surfaces it natively on both arms, and Settings copy lives in `src/client/**`, which the concurrently-running K-client group owns. The native dialog is the surface; no client change.
