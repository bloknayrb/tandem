# A8 — #1796 `tandem_convertToMarkdown` maps every `FILE_NOT_FOUND` to "No document is open"; three other codes flatten to `FORMAT_ERROR`

Branch `fix/convert-error-mapping-1796`. Closes #1796 (both halves of its body). Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-mcp.md:21`. Probe: `probe-tools.mts` (convert with a missing `outputPath`).

## Problem

`convertToMarkdown` (`src/server/mcp/convert.ts`) throws `code: "FILE_NOT_FOUND"` for two unrelated conditions: no document (`:64-66`, "Document not found.") and a missing output directory (`:151-153`, "Output directory does not exist: <resolved>"; the comment at `:148-150` says the code was chosen so an AI caller creates the directory). The MCP handler (`src/server/mcp/document.ts:1341`) maps the *code*, not the condition, to `noDocumentError()` ("No document is open. Call tandem_open first."), which also **discards the thrown message** (`response.ts:95-97`). So a caller with an open `.docx` and a typo in `outputPath` is told to open a document; and a caller naming a closed `documentId` is told nothing is open while other documents are. Second half (issue body, "Related"): `document.ts:1342-1349` flattens `INVALID_PATH`, `EMPTY_CONVERSION` and `OPEN_FAILED` to `FORMAT_ERROR`, so the per-tool error line at `docs/mcp-tools.md:529` is wrong in both directions. That flattening is NOT in #1823's list, so deferring it would drop it from every tracked home.

## Fix

Distinguish conditions at the throw site; map codes 1:1 in the handler. The model is `docx-apply.ts:651-652` (`tandem_restoreBackup`): `NO_DOCUMENT → noDocumentError()`, `FILE_NOT_FOUND → mcpError("FILE_NOT_FOUND", e.message)` — **with one deliberate divergence**: `docx-apply.ts:653-655` folds `INVALID_PATH` into `FORMAT_ERROR`, this handler does not (convert's three `INVALID_PATH` throws are path problems, and `_shared.ts:181` already understands the code). `document.ts:429-433` is a same-file sibling already doing `mcpError("FILE_NOT_FOUND", e.message)`.

- `convert.ts:64-66`: `code: "NO_DOCUMENT"`, message **"No document is open, or documentId names a document that is not open."** — no backticks: `ReviewOnlyBanner.svelte:33-41` renders `/api/convert`'s loopback `message` verbatim to a human. **Only this throw.** `UNSUPPORTED_FORMAT` (`:67-71`) and `INVALID_PATH` for uploads (`:74-81`) stay as they are — folding them onto `NO_DOCUMENT` is the over-fold the tests below exist to catch.
- `convert.ts:151-153`: unchanged (`FILE_NOT_FOUND`, message names the directory).
- `document.ts:1341-1349` catch, code-keyed, no message inspection:
  - `NO_DOCUMENT` → `safeDocId !== undefined ? mcpError("NO_DOCUMENT", e.message) : noDocumentError()` (a named-but-closed id gets the message that says so; the no-arg case keeps the shared text). Branch on `safeDocId` (computed before the `try` at `:1329`, and it is what `convertToMarkdown` receives), and add a comment: `getCurrentDoc` (`registry.ts:345-351`) uses `documentId ?? activeDocId` — `??`, not `||` — so a defined-but-empty `""` does NOT fall back to the active document and correctly reaches this branch; a "simplification" to `||` inverts that silently.
  - `FILE_NOT_FOUND` → `mcpError("FILE_NOT_FOUND", e.message)`.
  - `INVALID_PATH` → `mcpError("INVALID_PATH", e.message)`; `EMPTY_CONVERSION` → `mcpError("EMPTY_CONVERSION", e.message)`; `OPEN_FAILED` → `mcpError("OPEN_FAILED", e.message)`; `UNSUPPORTED_FORMAT` → `mcpError("FORMAT_ERROR", e.message)` (the one that IS a format error). All five codes already exist as strings (`mcpError` takes `string`, `response.ts:77`; `ToolErrorCodeSchema` in `src/shared/types.ts:58-70` is a client-side decoration that already omits several live codes — no type change).
  - Everything else rethrows (`throw err`, the default arm stays a rethrow) to `withErrorBoundary` → `INTERNAL_ERROR` as today: `CONFLICT` after 1000 attempts, and every non-`ENOENT` `realpath` failure at `convert.ts:147` (`ENOTDIR` for an ancestor that is a file, `EACCES`) plus `stat`/`atomicWrite` `EACCES`/`EPERM`/`ENOSPC`. Named in the PR body. Platform note for the docs: POSIX `realpath` on `…/file.docx/out` yields `ENOTDIR` (→ `INTERNAL_ERROR`) while Windows maps it to `ENOENT` (→ `FILE_NOT_FOUND`), so the docs sentence is "failures the resolver does not classify → `INTERNAL_ERROR`", not "any other filesystem failure".
- `docs/mcp-tools.md:529`: rewrite the `**Errors:**` line to the real set: `NO_DOCUMENT`, `FILE_NOT_FOUND` (the `outputPath` directory does not exist; message names the resolved directory), `INVALID_PATH` (relative/UNC/upload/existing file), `FORMAT_ERROR` (not a `.docx`), `EMPTY_CONVERSION`, `OPEN_FAILED`, `INTERNAL_ERROR` (failures the resolver does not classify). The global table at `:43-44` already has `NO_DOCUMENT` ("or specified `documentId` not found" — already describes the new use) and `FILE_NOT_FOUND`; `EMPTY_CONVERSION`/`OPEN_FAILED` are absent — add rows. **Do not add remediation prose ("create the directory")** to mcp-tools.md or the shipped skill: `convert.ts:138-140` says the directory must exist, and #1654's acceptance leans on that property — guidance to `mkdir` and retry would widen an accepted finding by a docs edit.
- `POST /api/convert`: **no code change.** `src/server/mcp/routes/convert.ts:51` delegates to `sendApiError`; `_shared.ts:128-136` maps both `NO_DOCUMENT` and `FILE_NOT_FOUND` to 404 and `:180-186` folds both to label `NOT_FOUND`. **Precisely what is unchanged:** HTTP status, the `error` label, and the non-loopback (LAN) body (`GENERIC_ERROR_MESSAGE.NOT_FOUND`). **What changes:** `sendApiError` (`_shared.ts:250-262`) sends `e.message` to a loopback caller, so the browser/Tauri body's `message` moves from "Document not found." to the new prose — intended. State it that way in the PR body; do not add a route test (`tests/server/routes/response-path-scrub.test.ts:32-33` mocks `convertToMarkdown`, so a route test there would assert the mock).
- Audit outcome (pre-computed, record it in the PR body): **22** `noDocumentError()` call sites in `src/server/mcp/` (`annotations.ts` ×7, `awareness.ts` ×2, `document.ts` ×7, `docx-apply.ts` ×3, `navigation.ts` ×3); 19 are condition-keyed (`if (!store)` ×12, `if (!r)` ×6, `if (!docState)` ×1); the three code-keyed ones are `document.ts:1341` (this fix), `docx-apply.ts:461` and `docx-apply.ts:651` (both key on `NO_DOCUMENT` — fine). `document.ts:1341` is the only site in the repo mapping a thrown `FILE_NOT_FOUND` onto `noDocumentError()`. `tandem_rename` uses `mcpError("NO_DOCUMENT", …)` directly at `document.ts:1249`. `annotations.ts:726-729`'s "matching `convert.ts` for the identical condition" refers to `convert.ts:151`, unchanged — one PR-body line so nobody re-opens it. No client, skill or UI code keys on the old message or on `FORMAT_ERROR`-from-convert (`ToolErrorCodeSchema`'s `ToolError`/`ToolResponse` have zero referents); no skill version bump.
