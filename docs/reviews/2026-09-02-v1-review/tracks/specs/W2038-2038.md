# W2038 — #2038 Store lock: a reused PID after reboot leaves the annotation store read-only with no in-app recovery

Branch `fix/store-lock-recovery-2038`. Closes #2038. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:116,485` (decision 7 — "refuse over grant"; Bryan: "We don't ever want to lose the user's hard work, full stop."). Probe: none — server-internal startup path, unit + wiring tests only.

## Problem

`tryReclaimStaleLock` (`src/server/annotations/store.ts:233-264`) treats any live PID at `lock.pid` as an unconditional refusal (`if (isPidAlive(lock.pid)) return false;`). `isPidAlive` only answers "is *some* process running at this PID" — not "is it the process that wrote this lock." A dead PID already self-heals (case 1, untouched). A **reused PID after a reboot** (case 2) does not: `isPidAlive` reports the unrelated new process as alive, the store stays `"readonly"` forever, and every future restart repeats the identical wrong check.

`lockfilePayload()` (`lockfile.ts:24-26`) already writes `startedAtMs: Date.now()`; nothing in `src/` compares it against the current boot (`grep -rn startedAtMs src/` finds only the write, the type and the read). A `startedAtMs` older than the current boot is evidence the PID was reused — but `Date.now()` (wall clock) and `os.uptime()` (monotonic) are two different clock bases: a forward system-clock step between the lock being written and the check running (NTP correcting a drifted RTC, a VM resume, dual-boot RTC skew) can make that comparison alone misread a **live, current-boot** lock as prior-boot. Decision 7 forbids that wrong-grant outcome, so the boot comparison is evidence requiring corroboration, not a verdict by itself — `store.ts` already imports the corroborating signal (`probeProcessIdentity`/`isTandemLikeProcessName` from `process-identity.ts`, used by `doReclaim`'s own button-driven reclaim), so no new machinery is needed.

## Fix

**`src/server/annotations/lockfile.ts`** — add the pure predicate next to the format it reads:

```ts
import os from "node:os";

/** Absorbs os.uptime()'s whole-second truncation + read jitter only — NOT a
 * defense against a system-clock step; see isLockFromPriorBoot. */
const BOOT_TIME_SAFETY_MARGIN_MS = 5_000;

export function systemBootMs(): number {
  return Date.now() - os.uptime() * 1000;
}

/**
 * True when a lock's startedAtMs predates the estimated current boot by more
 * than the margin. EVIDENCE, not a verdict: startedAtMs and nowBootMs are
 * both wall-clock-derived, taken at different instants, so a forward
 * system-clock step after the lock was written can make a LIVE, same-boot
 * lock read as "prior boot." Callers with a live PID MUST corroborate a
 * `true` result with an independent signal (the process-identity probe)
 * before treating the lock as stale. Missing/non-numeric startedAtMs
 * answers `false` (no evidence, no reclaim).
 */
export function isLockFromPriorBoot(
  lock: LockfileContents,
  nowBootMs: number = systemBootMs(),
): boolean {
  return (
    typeof lock.startedAtMs === "number" &&
    lock.startedAtMs < nowBootMs - BOOT_TIME_SAFETY_MARGIN_MS
  );
}
```

**`src/server/annotations/store.ts`** — thread an injectable `probe` through `acquireStoreLock`/`tryReclaimStaleLock` (same pattern `reclaimStoreLock` already uses at `:301`), and require it to corroborate `isLockFromPriorBoot` before a live-PID lock is ever unlinked. Import `isLockFromPriorBoot` alongside the existing `LockfileContents`/`parseLockfile` import; `probeProcessIdentity`/`isTandemLikeProcessName`/`ProcessIdentity` are already imported (`:29-33`) for `doReclaim`.

```ts
export async function acquireStoreLock(
  probe: (pid: number) => Promise<ProcessIdentity> = probeProcessIdentity,
): Promise<"locked" | "readonly"> {
  // ...
  const staleReclaimed = await tryReclaimStaleLock(lockPath, probe);
  // ...
}

async function tryReclaimStaleLock(
  lockPath: string,
  probe: (pid: number) => Promise<ProcessIdentity>,
): Promise<boolean> {
  // ...
  if (isPidAlive(lock.pid)) {
    // Reclaim only when BOTH signals agree: the boot-time estimate says the
    // lock predates this boot, AND the process at this PID no longer looks
    // like Tandem. Neither alone is proof (#2038).
    if (!isLockFromPriorBoot(lock)) return false;
    const identity = await probe(lock.pid);
    if (identity.kind !== "name" || isTandemLikeProcessName(identity.name)) return false;
  }

  await fs.unlink(lockPath).catch(() => {});
  return true;
}
```

Real callers (`index.ts`, `doReclaim`'s own internal call) get the default `probeProcessIdentity` and are unaffected; tests inject a fake so the corroborated-reclaim path is deterministic instead of depending on what the OS reports for the test runner's own PID. `doReclaim` itself is untouched — it already probes every live PID regardless of boot time via its own decision matrix.

**`src/cli/doctor.ts`** — the issue names a second liveness site (`isPidLive`, `:2731-2738`, feeding `checkAnnotationStore`'s lock-status block at `:2949-2962`) that must stay consistent with the recovery fix above. `isPidLive` itself is unchanged (doctor is read-only diagnostics — no probe call belongs there; the boot comparison alone is the right amount for a message). What changes is the live-PID arm at `:2950-2955`: after this fix a live PID whose lock predates this boot is reclaimable on the *next* server start, so the existing unconditional `r.pass("Annotation store lock held by live PID …")` is actively wrong for that case. Import `isLockFromPriorBoot` from `lockfile.ts` and branch:

```ts
if (isPidLive(pid)) {
  if (isLockFromPriorBoot(lock)) {

      `Annotation store lock at ${lockPath} is held by PID ${pid}, but its startedAtMs predates this boot`,

      { lockHeld: true, pid, pidLive: true, priorBoot: true },

    r.pass(`Annotation store lock held by live PID ${pid}`, undefined, {

} else {
  // ...unchanged dead-PID arm
}
```

## Tests

1. **New `tests/server/annotations/lockfile.test.ts`** (pure, no filesystem). Seed `const boot = Date.now() - 86_400_000` (not derived at call time, so a predicate ignoring `nowBootMs` — e.g. `startedAtMs < Date.now() - MARGIN` — is caught, not coincidentally passed):
   - `startedAtMs: boot - 10_000` → `true`; `boot`, `boot + 10_000`, `boot - 1_000` → `false` (margin direction is toward refuse); missing `startedAtMs` → `false`.
   - `startedAtMs: Date.now() - 60_000` against the 24h-old `boot` → `false` — the case a `nowBootMs`-ignoring shape gets wrong (it would say `true`).
   - `systemBootMs()` actually uses `os.uptime()`, not a stub: `expect(Math.abs(systemBootMs() - (Date.now() - os.uptime() * 1000))).toBeLessThan(2_000)` and `expect(Date.now() - systemBootMs()).toBeGreaterThan(1_000)`.

2. **`tests/server/annotations/store.test.ts`**: bump the existing `"reclaims a live-PID v2 lockfile when identity is non-Tandem"` fixture's `startedAtMs: 1` → `startedAtMs: Date.now()` (`:448`) — its setup helper `enterReadOnly` calls the un-injected `acquireStoreLock()`, and under this fix `startedAtMs: 1` would make that internal call invoke the *real* `probeProcessIdentity` against the test runner's own PID, which isn't what that test is about. New describe block:

```ts
describe("acquireStoreLock — reused PID after reboot (#2038)", () => {
  // writeLock(startedAtMs) writes { pid: process.pid, startedAtMs, app: "tandem" } to store.lock

  it("reclaims a live-PID lock that predates this boot AND probes as non-Tandem", async () => {
    await writeLock(1); // startedAtMs: 1 predates any real boot
    const probe = vi.fn().mockResolvedValue({ kind: "name", name: "explorer.exe" });
    expect(await acquireStoreLock(probe)).toBe("locked");
    expect(probe).toHaveBeenCalledWith(process.pid);
    await releaseStoreLock();
  });

  it("refuses when the probe reports a Tandem-like identity", async () => {
    await writeLock(1);
    expect(await acquireStoreLock(vi.fn().mockResolvedValue({ kind: "name", name: "node" }))).toBe("readonly");
    await releaseStoreLock();
  });

  it("refuses when the probe is indeterminate", async () => {
    await writeLock(1);
    expect(await acquireStoreLock(vi.fn().mockResolvedValue({ kind: "indeterminate" }))).toBe("readonly");
    await releaseStoreLock();
  });

  it("refuses a live, current-boot lock without ever calling the probe", async () => {
    await writeLock(Date.now() - 60_000);
    const probe = vi.fn().mockResolvedValue({ kind: "name", name: "explorer.exe" });
    expect(await acquireStoreLock(probe)).toBe("readonly");
    expect(probe).not.toHaveBeenCalled();
    await releaseStoreLock();
  });

```

3. **`tests/cli/doctor.test.ts`**: bump the existing `:370` JSON-object-format fixture's `startedAtMs: 123` → `Date.now()` — that fixture exists to assert the live-PID `pass` arm, and under this fix `startedAtMs: 123` would (correctly, but not what that test is about) route into the new prior-boot `warn` arm instead. ## Review corrections (scope cut)

All 5 blocking findings from the prior review argue one defect: a bare `startedAtMs`-vs-boot-estimate comparison is a wrong-*grant* hazard under a system-clock step, so a live PID must never be reclaimed on that comparison alone. The fix above already requires the existing process-identity probe (the one `doReclaim` already uses) to corroborate before any live-PID lock is unlinked, and the test suite above pins both the corroboration (4 store cases) and the predicate's actual dependence on `os.uptime()` (the 24h-`boot` fixture + the real `systemBootMs()` assertion) — so no version of the bare comparison ships or is left passable by the tests. Cut from the previous draft, none of it required to close #2038 or to satisfy the findings:

- **Per-symbol docblock rewrites** on `acquireStoreLock`'s return type, the module header, and an unrelated existing comment sentence. Replaced by the one safety-property docblock on `isLockFromPriorBoot` itself.
- **An "Assumptions" section** (margin-value rationale, `os.uptime()` cross-platform-suspend disclaimer, why `doReclaim`/UI stay untouched). Moot or one sentence: the probe corroboration means a wrong boot estimate can at most trigger or skip an unnecessary probe call, never grant a reclaim by itself.
- **A line-by-line "Review corrections (round 1)" log** of a prior pass (5 blocking + 12 non-blocking findings). Superseded by this section; the fix it described is unchanged.
