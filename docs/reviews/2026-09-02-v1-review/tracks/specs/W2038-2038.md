## Problem

`tryReclaimStaleLock` (`src/server/annotations/store.ts:233-264`), called from `acquireStoreLock` on every process start when `store.lock` already exists, treats a live PID as an unconditional refusal:

```ts
// :260
if (isPidAlive(lock.pid)) return false;
```

`isPidAlive` (`:156-163`) is `process.kill(pid, 0)` — it answers "is *some* process running at this PID number", not "is it the process that wrote this lock". Two situations produce a live-PID lock at startup, and only one of them is the true holder:

1. **Stale lock, dead PID.** `isPidAlive` returns `false`, the existing code unlinks and reclaims. Already self-heals — this item does not touch it.
2. **Reused PID after a reboot.** The OS assigns the lock's PID number to an unrelated process across a reboot (Windows recycles PIDs aggressively; it happens on other OSes too). `isPidAlive` returns `true` for that unrelated process, so `acquireStoreLock` degrades to `"readonly"` and stays there — every future restart re-runs the identical check against the identical still-alive, still-wrong PID and gets the identical wrong answer. This does **not** self-heal, unlike case 1: the module docblock (`:10-14`) already advertises the `POST /api/store/reclaim-lock` banner button as the recovery path (`docReclaim`, `:299-368`), but that path requires the user to notice the read-only banner and click it, and its own recovery mechanism (process-identity name probing, `process-identity.ts`) is deliberately broad — `isTandemLikeProcessName` matches `/node|tandem/i` "by design", so most recycled-PID processes in practice still refuse. Restarting Tandem itself — the case-1 self-heal path — does nothing for case 2.

The data needed to tell the two cases apart is already on disk and already parsed: `lockfilePayload()` (`lockfile.ts:24-26`) writes `startedAtMs: Date.now()` into every v2 lock; `parseLockfile` (`lockfile.ts:35-56`) reads it back into `LockfileContents.startedAtMs`. Nothing in `src/` compares it against anything (confirmed: `grep -rn startedAtMs src/` returns only the write, the type, the read, and doc comments). A lock's `startedAtMs` that predates the current boot is conclusive: no process survives a reboot, so whatever is alive at `lock.pid` right now cannot be the process that wrote it, regardless of what `isPidAlive` reports.

A second liveness site, `isPidLive` in `src/cli/doctor.ts:2731-2738`, duplicates `isPidAlive` for the read-only `doctor` diagnostic (`checkAnnotationStore`, `:2790-2966`) and has the same blind spot: it reports "held by live PID N" with no way to say that N is recycled and the next restart will already fix it.

## Fix

Two files get the comparison; a third (`store.ts`) gets the one call site wired in. No new lock machinery, no new probe, no new route, no new UI — the fix makes case 2 self-heal on the next start exactly the way case 1 already does, so there is nothing for a user to click.

**`src/server/annotations/lockfile.ts`** — add the pure predicate next to the format it reads, so `doctor.ts` (which imports only `parseLockfile` from here specifically to avoid `store.ts`'s file-io/notifications/platform deps, per this file's own docblock) can use it too:

```ts
import os from "node:os";

/**
 * Safety margin subtracted from the boot estimate before comparing. Absorbs
 * `Date.now()`/`os.uptime()` read jitter between the two calls — nothing
 * more. A genuine reboot moves `startedAtMs` by minutes at least (POST +
 * OS boot), so this does not need to be, and must not be, large enough to
 * paper over a real "is this still the same boot" question.
 */
const BOOT_TIME_SAFETY_MARGIN_MS = 5_000;

/**
 * Epoch ms of the current boot. `os.uptime()` is seconds-since-boot,
 * re-read on every call (no memoization needed or wanted — it must reflect
 * "now", every time it's asked).
 */
export function systemBootMs(): number {
  return Date.now() - os.uptime() * 1000;
}

/**
 * True when a lockfile's `startedAtMs` (#1077) predates the current boot —
 * the PID it names cannot be the process that wrote it, because no process
 * survives a reboot (#2038: this is exactly how "PID reused after reboot"
 * happens). The margin only ever pushes the verdict toward `false`
 * (refuse-over-grant, see `annotations/store.ts`'s lock docblock): jitter
 * can make a genuinely-prior-boot lock read as "not sure", never the
 * reverse. Missing `startedAtMs` (a legacy raw-PID lockfile, or a v2 lock
 * whose field didn't parse as a number) answers `false` for the same
 * reason — no evidence, no reclaim.
 */
export function isLockFromPriorBoot(
  lock: LockfileContents,
  nowBootMs: number = systemBootMs(),
): boolean {
  return (
    typeof lock.startedAtMs === "number" && lock.startedAtMs < nowBootMs - BOOT_TIME_SAFETY_MARGIN_MS
  );
}
```

**`src/server/annotations/store.ts`** — wire it into the one call site that currently self-heals only case 1. Import `isLockFromPriorBoot` alongside the existing `LockfileContents`/`parseLockfile` import (`:28`). Replace the unconditional refusal at `:260`:

```ts
// was:
if (isPidAlive(lock.pid)) return false;

// becomes:
if (isPidAlive(lock.pid) && !isLockFromPriorBoot(lock)) return false;
```

The surrounding comment block (`:253-259`, "Intentionally no `pid === process.pid` shortcut...") is unchanged — it explains a different thing (why there's no self-PID fast path) and stays true. Add one sentence above the new condition naming #2038 and pointing at the docblock rationale above, so the "refuse over grant" framing isn't re-litigated at the call site. Everything below (unlink + `return true`) is unchanged and now correctly covers both "dead PID" and "live PID from a prior boot".

`doReclaim` (`:314-368`, the user-initiated `POST /api/store/reclaim-lock` path) is **not touched**. It already has its own (weaker but independent) recycled-PID handling via process-identity probing, and #2038's ask — "self-heals the way case 1 already does" — is specifically about the startup path having no self-heal at all, not about improving the button. Leaving it alone also avoids a real test conflict: `doReclaim`'s own tests construct a live-PID-but-clearly-recycled scenario and expect the *identity probe* to be what settles it (see Tests, below).

**`src/cli/doctor.ts`** — the issue explicitly asks to keep this second liveness site consistent. Add `isLockFromPriorBoot` to the existing `parseLockfile` import (`:32`). In `checkAnnotationStore`'s lock section (`:2949-2962`), branch the live-PID case on it:

```ts
const { pid } = lock;
if (isPidLive(pid)) {
  if (isLockFromPriorBoot(lock)) {
    r.warn(
      `Annotation store lock at ${lockPath} names live PID ${pid}, but its startedAtMs predates this boot`,
      "The PID was recycled after a reboot; the next server start will reclaim the lock automatically.",
      { lockHeld: true, pid, pidLive: true, priorBoot: true },
    );
  } else {
    r.pass(`Annotation store lock held by live PID ${pid}`, undefined, {
      lockHeld: true,
      pid,
      pidLive: true,
    });
  }
} else {
  // unchanged dead-PID warn branch
}
```

`isPidLive` itself is **not** touched or unified with `isPidAlive` — it's a read-only diagnostic duplicate by design (R1823's own "Not in scope" already said this site "reports, it does not gate"), and unifying the two functions is exactly the kind of extra mechanism minimality rules out here.

Nothing here touches a Y.Map key, a Y.Doc write, a `data-testid`, an MCP tool, or an `/api` route — Critical Rules 1, 2, 7 and 9 are not in play.

## Tests

Each test names the mutation it kills.

1. **New file `tests/server/annotations/lockfile.test.ts`** — pure predicate, no filesystem, deterministic via the injected `nowBootMs` parameter:
   - `isLockFromPriorBoot({ pid: 1, startedAtMs: boot - 10_000 }, boot)` → `true`. Kills an inverted comparison.
   - `isLockFromPriorBoot({ pid: 1, startedAtMs: boot + 10_000 }, boot)` → `false`.
   - `isLockFromPriorBoot({ pid: 1, startedAtMs: boot }, boot)` → `false`, and `isLockFromPriorBoot({ pid: 1, startedAtMs: boot - 1_000 }, boot)` → `false`. Both sit inside the margin — kills a margin of `0` (an off-by-jitter false positive) and confirms the safety direction is "toward refuse".
   - `isLockFromPriorBoot({ pid: 1 }, boot)` → `false`. Kills dropping the `typeof … === "number"` guard (a legacy lockfile with no `startedAtMs` must never be treated as evidence).
   - `systemBootMs()` returns a number less than `Date.now()` and greater than `0` — the only sanity check the real (non-injected) path needs; the predicate itself is exercised entirely through the injected parameter above.

2. **`tests/server/annotations/store.test.ts`** — new describe after "lockfile v2 format" (`:356`), proving the wiring through the real public entry point (`acquireStoreLock`), the same style as the existing `#8` dead-PID case:

   ```ts
   describe("acquireStoreLock — reused PID after reboot (#2038)", () => {
     it("reclaims a live-PID lock whose startedAtMs predates this boot", async () => {
       const annotationsDir = getAnnotationsDir();
       await fs.mkdir(annotationsDir, { recursive: true });
       // Our own PID is certainly alive, but startedAtMs=1 cannot be this
       // boot — no real system has been up since 1970. isPidAlive alone
       // would refuse this; the boot-time comparison is what must reclaim it.
       await fs.writeFile(
         path.join(annotationsDir, "store.lock"),
         JSON.stringify({ pid: process.pid, startedAtMs: 1, app: "tandem" }),
       );

       expect(await acquireStoreLock()).toBe("locked");
       const lockContents = await fs.readFile(path.join(annotationsDir, "store.lock"), "utf-8");
       expect(JSON.parse(lockContents)).toMatchObject({ pid: process.pid, app: "tandem" });

       await releaseStoreLock();
     });
   });
   ```

   Kills reverting the `store.ts` change back to the bare `if (isPidAlive(lock.pid)) return false;`. The two negatives are **already** pinned and must stay green unmodified: "acquire treats a live-PID legacy lockfile as held" (`:336-343`, no `startedAtMs` at all) and "acquire treats a live-PID v2 lockfile as held" (`:345-355`, `startedAtMs: Date.now()`) — both prove the fix does not turn a genuinely-current lock read-write.

   **One existing fixture must change**, or it breaks against the new code for an unrelated reason: `"reclaims a live-PID v2 lockfile when identity is non-Tandem"` (`:447-455`) calls `enterReadOnly(JSON.stringify({ pid: process.pid, startedAtMs: 1, app: "tandem" }))`, and `enterReadOnly` itself calls `acquireStoreLock()` to get into the read-only state it's setting up. With this fix, `startedAtMs: 1` is exactly the "prior boot" fixture from the new test above, so `enterReadOnly`'s own `acquireStoreLock()` would reclaim immediately and its `expect(await acquireStoreLock()).toBe("readonly")` assertion would fail *before* the test reaches the thing it's actually testing (the identity-probe branch of `doReclaim`). Change `startedAtMs: 1` → `startedAtMs: Date.now()` at `:448` — the test's subject is identity probing, not boot time, and a current timestamp keeps it exercising that path unchanged (probe still called, still asserted, still reclaims — just via the identity route, not the boot-time route).

## Assumptions

- **Margin value (5 s).** Not specified by the issue. Chosen to comfortably absorb `Date.now()`/`os.uptime()` read jitter between two back-to-back calls while staying far smaller than any real reboot gap (POST + OS boot is realistically tens of seconds at the very least). Trivially tunable as one constant if it ever needs to change.
- **`doReclaim` stays untouched.** The issue's own framing ("self-heals the way case 1 already does") is specifically about the startup path; the button already has an independent, if weaker, mechanism for the same class of problem, and touching it would mean rewriting its existing, deliberately-designed test matrix (the `startedAtMs: 1` fixture at `store.test.ts:448` — bumped here only because it collides with the *startup* path via `enterReadOnly`, not because `doReclaim` itself changes).
- **No new UI/UX.** The issue's own scope line calls for "whatever the least amount of recovery UX the issue actually requires" — since case 1 requires zero UX (transparent self-heal on restart), and #2038 asks for case 2 to behave the same way, the answer is zero new UX here too.
