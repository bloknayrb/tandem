That spec named **both** halves of the mechanism: the boot-instant estimate (`Date.now() - os.uptime()*1000`) **and** an injectable probe seam on `acquireStoreLock` (`:58`, `:72`: "the injectable `probe` parameter ... AND the `os.uptime()` boot-instant margin"). Decision 7 answers the "is a wrong grant worth it" question in the refuse-over-grant direction. **Round 1 of this spec's own review found that the first draft here had silently dropped the probe half** — wiring the bare `startedAtMs`-vs-boot comparison in alone is a wrong-grant hazard, not a refusal-only one: `startedAtMs` and the boot estimate are read at different wall-clock instants, so a forward system-clock step (NTP correcting a drifted/dead-battery RTC, a VM resumed from a snapshot, dual-boot RTC-localtime disagreement) after the true holder started can make a LIVE, current-boot lock read as "prior boot," and the original fix would then unlink it — two writers on the annotation store, exactly the outcome decision 7 forbids. #2038's actual scope, corrected: wire the boot-time comparison in **as a trigger**, but require it to be corroborated by the same process-identity probe `doReclaim` already uses before the startup path unlinks anything.

## Problem

`tryReclaimStaleLock` (`src/server/annotations/store.ts:233-264`), called from `acquireStoreLock` on every process start when `store.lock` already exists, treats a live PID as an unconditional refusal:

```ts
// :260
if (isPidAlive(lock.pid)) return false;
```

`isPidAlive` (`:156-163`) is `process.kill(pid, 0)` — it answers "is *some* process running at this PID number", not "is it the process that wrote this lock". Two situations produce a live-PID lock at startup, and only one of them is the true holder:

1. **Stale lock, dead PID.** `isPidAlive` returns `false`, the existing code unlinks and reclaims. Already self-heals — this item does not touch it.
2. **Reused PID after a reboot.** The OS assigns the lock's PID number to an unrelated process across a reboot (Windows recycles PIDs aggressively; it happens on other OSes too). `isPidAlive` returns `true` for that unrelated process, so `acquireStoreLock` degrades to `"readonly"` and stays there — every future restart re-runs the identical check against the identical still-alive, still-wrong PID and gets the identical wrong answer. This does **not** self-heal, unlike case 1: the module docblock (`:10-14`) already advertises the `POST /api/store/reclaim-lock` banner button as the recovery path (`docReclaim`, `:299-368`), but that path requires the user to notice the read-only banner and click it, and its own recovery mechanism (process-identity name probing, `process-identity.ts`) is deliberately broad — `isTandemLikeProcessName` matches `/node|tandem/i` "by design", so most recycled-PID processes in practice still refuse. Restarting Tandem itself — the case-1 self-heal path — does nothing for case 2.

The data needed to tell the two cases apart is already on disk and already parsed: `lockfilePayload()` (`lockfile.ts:24-26`) writes `startedAtMs: Date.now()` into every v2 lock; `parseLockfile` (`lockfile.ts:35-56`) reads it back into `LockfileContents.startedAtMs`. Nothing in `src/` compares it against anything (confirmed: `grep -rn startedAtMs src/` returns only the write, the type, the read, and doc comments). A lock's `startedAtMs` that predates the current boot is **evidence** that no process survives a reboot, so whatever is alive at `lock.pid` right now might not be the process that wrote it — but that estimate is itself wall-clock-derived (see Fix), so it is not, by itself, conclusive; a system-clock adjustment can produce the same reading for a genuinely live, same-boot holder.

A second liveness site, `isPidLive` in `src/cli/doctor.ts:2731-2738`, duplicates `isPidAlive` for the read-only `doctor` diagnostic (`checkAnnotationStore`, `:2790-2966`) and has the same blind spot: it reports "held by live PID N" with no way to say that N is recycled and the next restart will already try to fix it.

## Fix

Two files get the comparison; a third (`store.ts`) gets the one call site wired in, now including a corroborating probe call in the rare branch where a live PID's lock predates this boot. No new lock machinery, no new route, no new UI, and **no new probe module** — `store.ts` already imports `probeProcessIdentity`/`isTandemLikeProcessName` from `process-identity.ts` for `doReclaim`'s decision matrix, and this reuses exactly that (this is what R1823:58/:72 scoped, and what round 1 of this spec's review restored after the first draft dropped it). The fix still makes case 2 self-heal on the next start the way case 1 already does whenever the probe can corroborate the boot-time evidence; when it cannot (indeterminate, or a genuinely live Tandem-like process), the store stays read-only and the existing `POST /api/store/reclaim-lock` button remains the recovery path — the same place every other "live PID, ambiguous" case lands today. There is still nothing new for a user to click in the case this issue is actually about.

**`src/server/annotations/lockfile.ts`** — add the pure predicate next to the format it reads, so `doctor.ts` (which imports only `parseLockfile` from here specifically to avoid `store.ts`'s file-io/notifications/platform deps, per this file's own docblock) can use it too:

```ts
import os from "node:os";

/**
 * Safety margin subtracted from the boot estimate before comparing.
 * `os.uptime()` truncates to whole seconds, so this absorbs about a second
 * of read jitter between the two `Date.now()`/`os.uptime()` calls, plus a
 * small arbitrary pad — nothing more. It is NOT a defense against a system
 * clock adjustment: see `isLockFromPriorBoot`'s docblock. Enlarging this
 * constant does not make the predicate safer against that hazard, because
 * the hazard's size is the size of the clock step, not of read jitter — no
 * margin value bounds it. That hazard is why the predicate below is
 * treated as evidence requiring corroboration, not a verdict (see
 * `store.ts`'s `tryReclaimStaleLock`).
 */
const BOOT_TIME_SAFETY_MARGIN_MS = 5_000;

/**
 * Epoch ms of the current boot. `os.uptime()` is seconds-since-boot,
 * re-read on every call (no memoization needed or wanted — it must reflect
 * "now", every time it's asked).
 */
export function systemBootMs(): number {
  return Date.now() - os.uptime() * 1000;
}

/**
 * True when a lockfile's `startedAtMs` (#1077) predates the estimated
 * current boot by more than the margin — i.e. this looks like a lock
 * written before the machine last rebooted, which (if true) means the PID
 * it names cannot be the process that wrote it, because no process
 * survives a reboot (#2038: this is exactly how "PID reused after reboot"
 * happens).
 *
 * This is EVIDENCE, not a verdict, and no caller may grant a reclaim on it
 * alone (#2038 review round 1 — the first draft of this function's
 * docblock claimed the margin "only ever pushes the verdict toward
 * `false`... never the reverse", which is false in the dangerous
 * direction). Both `lock.startedAtMs` and `nowBootMs` mix a wall-clock
 * reading (`Date.now()`) with a monotonic one (`os.uptime()`), taken at
 * two different times. A forward step of the *system* clock after the lock
 * was written — an NTP correction on a drifted/dead-battery RTC, a VM
 * resumed from a snapshot, a dual-boot Windows/Linux RTC-localtime
 * disagreement — moves `nowBootMs` forward while the lock's `startedAtMs`
 * stays fixed, so a LIVE, same-boot holder can read as "prior boot" once
 * the step exceeds the holder's own age. The margin cannot bound this: the
 * error is the size of the clock step, not of read jitter. Callers with a
 * live PID MUST corroborate a `true` result here with an independent
 * signal (the process-identity probe in `process-identity.ts`) before
 * treating the lock as stale — see `store.ts`'s `tryReclaimStaleLock`.
 *
 * Missing `startedAtMs` (a legacy raw-PID lockfile, or a v2 lock whose
 * field didn't parse as a number) answers `false` for the same
 * refuse-over-grant reason — no evidence, no reclaim.
 */
export function isLockFromPriorBoot(
  lock: LockfileContents,
  nowBootMs: number = systemBootMs(),
): boolean {
  return (
    typeof lock.startedAtMs === "number" && lock.startedAtMs < nowBootMs - BOOT_TIME_SAFETY_MARGIN_MS
  );
}
```

// becomes:
async function tryReclaimStaleLock(
  lockPath: string,
  probe: (pid: number) => Promise<ProcessIdentity>,
): Promise<boolean> {
  ...
  if (isPidAlive(lock.pid)) {
    // #2038 (review round 1): a live PID is not, alone, proof of a live
    // holder — but `isLockFromPriorBoot` alone is not proof of a dead one
    // either (see its docblock: a system-clock step can make it agree on a
    // genuinely live lock). Reclaim only when BOTH signals agree, the same
    // refuse-over-grant matrix `doReclaim` already uses for the
    // user-initiated button below.

  await fs.unlink(lockPath).catch(() => {});

## Assumptions

- **Margin value (5 s).** Not specified by the issue. Its only job, after round 1, is absorbing `Date.now()`/`os.uptime()` read jitter (`os.uptime()`'s whole-second truncation plus a small arbitrary pad) between two back-to-back calls — it is **not**, and cannot be sized to be, a defense against a system-clock adjustment; that hazard is instead bounded by requiring the process-identity probe to also agree before a reclaim is granted. Trivially tunable as one constant if the jitter tolerance ever needs to change.
- **`os.uptime()`'s cross-platform semantics (suspend/hibernate behaviour) are unmeasured in this repo** — `grep -rni "os.uptime" src/` returns zero hits before this change, and the three platforms' underlying counters (Windows `GetTickCount64`, Linux `/proc/uptime`/`CLOCK_BOOTTIME`, macOS `kern.boottime`) are known to differ on whether a long sleep advances them. This is now non-load-bearing for correctness: because a live-PID reclaim also requires the process-identity probe to independently agree, a wrong boot estimate (in either direction) at worst triggers an unnecessary probe call or skips a legitimate one — it cannot, by itself, grant a reclaim against a genuinely live holder. Measuring the real platform behaviour remains useful future work but is not a precondition for this fix's safety.
- **`doReclaim` stays untouched.** The issue's own framing ("self-heals the way case 1 already does") is specifically about the startup path; the button already has an independent, boot-time-agnostic mechanism for the same class of problem, and touching it would mean rewriting its existing, deliberately-designed test matrix (the `startedAtMs: 1` fixture at `store.test.ts:448` — bumped here only because it collides with the *startup* path via `enterReadOnly`, not because `doReclaim` itself changes).
- **No new UI/UX.** The issue's own scope line calls for "whatever the least amount of recovery UX the issue actually requires" — since case 1 requires zero UX (transparent self-heal on restart), and #2038 asks for case 2 to behave the same way whenever it safely can, the answer is zero new UX here too; the pre-existing banner/button remains the fallback for the cases the probe cannot corroborate.
