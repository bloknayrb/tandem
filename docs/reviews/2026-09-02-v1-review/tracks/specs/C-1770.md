# C — #1770 Annotation authority: author-scope edit and reply, never accept your own, keep Claude's resolves out of `userResponses` and `applyChanges`, and surface a decision made after Undo

Branch `fix/privacy-and-authority-1769`. Closes #1770 (all three items; decisions 3 and 4 are taken — `docs/reviews/2026-09-02-v1-review/decisions.md:12-13`). Ledger: `areas/annotations.md:19-21`, `areas/skill-plugin.md:20`. Probe: `experiments/harness/g-inbox-ledger.test.ts` (item 3, reproduced).

## Problem

1. `editPendingAnnotation` (`src/server/annotations/lifecycle.ts:891-953`) and `replyForClaude` (`:1279-1313`) have no author guard; the comment at `:939-945` admits Claude edits a USER-authored pending comment under the user's byline. The client predicate `annotation-context-menu.ts:69` states the opposite rule.
2. `transitionPending` (`:807-859`) lets Claude accept its own annotation, and records it indistinguishably from the user: `awareness.ts:636` puts every `author: claude` non-pending record into `userResponses`; `output-schemas.ts:246-248` documents that bucket as user decisions; `docx-apply.ts:204` writes every `accepted` suggestion into the Word file. And an MCP accept never applies `suggestedText` — `applySuggestion` is client-only (`useAnnotationReview.svelte.ts:299`) — so it flips status without editing.
3. The inbox ledger keys on `editedAt` alone (`awareness.ts:566-569`, `:635`, `:638`); the client's Undo writes `status: "pending"` without touching it (`useAnnotationReview.svelte.ts:732`), so accept → poll → undo → dismiss → poll returns `userResponses: []`.

## Fix

**Item 1 — author guard, `lifecycle.ts`.** In `editPendingAnnotation` after the ADR-027 guard (`:905`, C-1803's `isPrivateForClaude`) and before the pending check: `if (ann.author !== "claude") return { kind: "not-owned", author: ann.author };` `EditResult` (`:378-384`) gains `| { kind: "not-owned"; author: Annotation["author"] }`. Same line in `replyForClaude` after `:1305-1307`; `ClaudeReplyResult` (`:251`) gains the arm, `ReplyRefusalCode` (`:254`) gains `"NOT_OWNED"`, `describeReplyWriteRefusal` (`:283`) gains the case (message: "Claude can only reply on annotations it authored; answer a user's comment with tandem_reply"), and `routes/annotation-reply.ts:29-33` `REFUSAL_STATUS` gains `NOT_OWNED: 403` — the `Record` is exhaustive and will not compile without it, which is the point of that record; the browser route never produces the code (it calls `addUserReply`). MCP: `annotations.ts:559` edit switch gains `case "not-owned": return mcpError("NOT_OWNED", …)`; the reply handler (`:906`) needs no change. Order is the contract: not-found → sanitize → private → **not-owned** → pending. A user's note answers `invalid-note`, unchanged (track "done when"). Guards go on `editPending`/`reply` only — never on `addUserReply` or `removeAnnotationRecord` (seam tests). The local-model loop (`local-model/tools.ts:294`, dark) inherits the reply guard; note it in the PR body.

**Item 2 — never accept your own; stamp who resolved.** `transitionPending`, after the pending check (`:846-848`, so `not-pending` keeps precedence and `annotation-lifecycle.test.ts:102-119` stay meaningful): `if (nextStatus === "accepted") { if (ann.author === "claude") return { kind: "accept-refused", reason: "own-annotation" }; if (ann.suggestedText !== undefined) return { kind: "accept-refused", reason: "unapplied-suggestion" }; }`. `LifecycleResult` (`:152-156`) gains `| { kind: "accept-refused"; reason: "own-annotation" | "unapplied-suggestion" }`. The decision allowed "apply `suggestedText` or refuse"; **refuse** — applying would make the tool write document content, falsifying `license-gate-coverage.test.ts:69` and pre-empting decision F (track H). The `updated` literal (`:850-854`) adds `resolvedBy: "claude"`. Dismiss stays open to every non-private record (Claude answering a user's comment then dismissing it is the existing flow). `mcp/annotations.ts:466-483`: add `case "accept-refused"` → `mcpError("INVALID_ARGUMENT", …)` naming the reason, and a `default: { const unhandled: never = result; … }` in the shape of `:520-528`; rewrite the tool description (`:443-447`) — "Claude may dismiss (withdraw) its own annotations; accept is the user's decision. Accepting a user-authored comment never applies text."

- `src/shared/types.ts:233` area: `resolvedBy?: "user" | "claude"` on `AnnotationBase` (docblock: absent means the user, the legacy reading). **`shared/sanitize.ts:130-146` is a strict allowlist** — add `...(ann.resolvedBy === "user" || ann.resolvedBy === "claude" ? { resolvedBy: ann.resolvedBy } : {})` or every Claude-facing read strips it silently (the `heldInSolo` lesson at `:132-138`). Durable schema is `.passthrough()` (`annotations/schema.ts:6`); no change.
- `awareness.ts:636`: `&& ann.resolvedBy !== "claude"`. `output-schemas.ts:248` describe: "The USER's accept/dismiss decisions; Claude's own resolves never appear."
- `docx-apply.ts:204`: `if (ann.status !== "accepted" || ann.resolvedBy === "claude") continue;` — legacy belt for records resolved before this landed.

**Item 3 — ledger keyed on status for Claude's records, `awareness.ts`.** Add `function inboxLedgerKey(documentId: string, ann: Annotation): string { const base = ledgerKey(documentId, ann.id); return ann.author === "claude" ? `${base}#${ann.status}` : base; }` and use it at `:567`, `:615`, `:635`, `:638`. Undo then makes the dismissed record a fresh key. Not `rev`: the client's resolve and undo writes (`useAnnotationReview.svelte.ts:528`, `:732`) do not bump it. User comments keep the id key, so Claude dismissing a user comment does not re-surface it as a `userAction`. **Known limit, state it in the PR body:** accept → undo → accept is not re-reported (same key, same `editedAt`); Claude's last report equals the final state, so nothing is misread.
