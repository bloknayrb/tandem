## Problem

1. `editPendingAnnotation` (`src/server/annotations/lifecycle.ts:891-953`) and `replyForClaude` (`:1279-1313`) have no author guard; the comment at `:939-945` admits Claude edits a USER-authored pending comment under the user's byline. The client predicate `annotation-context-menu.ts:69` states the opposite rule.
2. `transitionPending` (`:807-859`) lets Claude accept its own annotation, and records it indistinguishably from the user: `awareness.ts:636` puts every `author: claude` non-pending record into `userResponses`; `output-schemas.ts:246-248` documents that bucket as user decisions; `docx-apply.ts:204` writes every `accepted` suggestion into the Word file. And an MCP accept never applies `suggestedText` — `applySuggestion` is client-only (`src/client/panels/useAnnotationReview.svelte.ts:299`) — so it flips status without editing.
3. The inbox ledger keys on `editedAt` alone (`awareness.ts:566-569`, `:635`, `:638`); the client's Undo writes `status: "pending"` without touching it (`useAnnotationReview.svelte.ts:732`), so accept → poll → undo → dismiss → poll returns `userResponses: []`.

## Fix

**Item 1 — author guard, `lifecycle.ts`.** In `editPendingAnnotation` after the ADR-027 guard (`:905`, C-1803's `isPrivateForClaude`) and before the pending check: `if (ann.author !== "claude") return { kind: "not-owned", author: ann.author };` `EditResult` (`:378-384`) gains `| { kind: "not-owned"; author: Annotation["author"] }`. Same line in `replyForClaude` after `:1305-1307`; `ClaudeReplyResult` (`:251`) gains the arm, `ReplyRefusalCode` (`:254`) gains `"NOT_OWNED"`, `describeReplyWriteRefusal` (`:283`) gains the case (message: "Claude can only reply on annotations it authored; answer a user's comment with tandem_reply or a fresh tandem_comment"), and `routes/annotation-reply.ts:29-33` `REFUSAL_STATUS` gains `NOT_OWNED: 403` — the `Record` is exhaustive and will not compile without it, which is the point of that record; the browser route never produces the code (it calls `addUserReply`). MCP: `annotations.ts:559` edit switch gains `case "not-owned": return mcpError("NOT_OWNED", …)`; the reply handler (`:906`) needs no change. **Order is the contract: not-found → sanitize → private → not-owned → pending.** Consequences that follow from the order and are stated so nobody "fixes" them: a user's note answers `invalid-note`, unchanged (track "done when"); a user's private comment answers `invalid-note`, never `not-owned`; **a USER highlight answers `not-owned` on both edit and reply** (the guard sits before `invalid-suggestion-target` at `:913-915` and before `writeReply`'s highlight arm at `:1163`), while a CLAUDE highlight still answers `invalid-suggestion-target` / `not-repliable` — `replies-privacy-readwrite.test.ts:166` (b6) and C-1803's test 3 stay green because their fixtures are Claude-authored (`ydoc-factory.ts:50`, `lifecycle.ts:748`). Guards go on `editPending`/`reply` only — never on `addUserReply` or `removeAnnotationRecord` (seam tests). The local-model loop (`local-model/tools.ts:294`, dark) inherits the reply guard; note it in the PR body.

- **Promotion no longer enables a Claude in-thread reply, and that is a decision to state, not a side effect to discover.** `promoteNotesToComments` writes `author: "user"` (`src/client/panels/annotation-actions.ts:57,78`), so a promoted Word comment or promoted note is user-authored and `tandem_annotationReply` on it answers `NOT_OWNED`. The replacement path is `tandem_reply` (chat, quoting the comment) or a fresh `tandem_comment` on the same text. Decision 4 is what forces this; the PR body says so in those words, and the three surfaces that described the old flow change together: `tests/server/annotation-promote-pull-surface.test.ts:286-318` (Tests 1), `skills/tandem/SKILL.md:115-118` and `docs/mcp-tools.md`'s reply section (below).
- **`userReplies` items are NOT all on Claude's own annotations.** `collectInboxUserReplies` iterates every comment parent regardless of author (`awareness.ts:705-706`), so a user's reply on the user's OWN comment is a `userReplies` item Claude can no longer answer in-thread. Make the rule mechanical: `inboxUserReplySchema` (`output-schemas.ts:251`) gains `parentAuthor: AuthorSchema.describe("Author of the parent annotation; reply in-thread only when it is \"claude\"")`, populated from `ann.author` in `collectInboxUserReplies` (one field on the pushed object). The skill and docs word the rule on that field.

**Item 2 — never accept your own; stamp who resolved.** `transitionPending`, after the pending check (`:846-848`, so `not-pending` keeps precedence and `annotation-lifecycle.test.ts:102-119` stay meaningful): `if (nextStatus === "accepted") { if (ann.author === "claude") return { kind: "accept-refused", reason: "own-annotation" }; if (ann.suggestedText !== undefined) return { kind: "accept-refused", reason: "unapplied-suggestion" }; }`. `LifecycleResult` (`:152-156`) gains `| { kind: "accept-refused"; reason: "own-annotation" | "unapplied-suggestion" }`. The decision allowed "apply `suggestedText` or refuse"; **refuse** — applying would make the tool write document content, falsifying `license-gate-coverage.test.ts:69` and pre-empting decision F (track H). The `updated` literal (`:850-854`) adds `resolvedBy: "claude"`. Dismiss stays open to every non-private record (Claude answering a user's comment then dismissing it is the existing flow). `mcp/annotations.ts:466-483`: add `case "accept-refused"` → `mcpError("INVALID_ARGUMENT", …)` naming the reason, and a `default: { const unhandled: never = result; … }` in the shape of `:520-528`; rewrite the tool description (`:443-447`) — "Claude may dismiss (withdraw) its own annotations; accept is the user's decision. Accepting a user-authored comment never applies text."

- `src/shared/types.ts:233` area: `resolvedBy?: "user" | "claude"` on `AnnotationBase` (docblock: absent means the user, the legacy reading; **it means who performed the CURRENT resolution, not who ever touched the record** — see the client strip below). **`shared/sanitize.ts:130-146` is a strict allowlist** — add `...(ann.resolvedBy === "user" || ann.resolvedBy === "claude" ? { resolvedBy: ann.resolvedBy } : {})` or every Claude-facing read strips it silently (the `heldInSolo` lesson at `:132-138`). Durable schema is `.passthrough()` (`annotations/schema.ts:6`); no change.
- **`output-schemas.ts` `annotationBaseShape` (`:53-95`) gains `resolvedBy: z.enum(["user", "claude"]).optional().describe("Who resolved this record; absent means the user")`** — declared, not tolerated (`:68-79` states the rule for exactly this case). It is spread into `annotationWithRepliesSchema` (`:169`), `userActionSchema` (`:199`) and `userResponseSchema` (`:208`); `tandem_getAnnotations` returns dismissed records by default (`annotations.ts:400-410`), so the field is present on every record Claude dismisses and `mcp-output-schemas.test.ts:120-134`'s strip-parse deep-equal would red without the declaration. C-1769 adds `heldInSolo` to the same shape in the same edit.
- **The client strips it on the way back to pending, so "absent = user" stays true by construction.** With the allowlist line, the client's three status writes in `src/client/panels/useAnnotationReview.svelte.ts` spread the SANITIZED record and would carry a stale `resolvedBy: "claude"` forward: `:528` (`{ ...ann, status }`), `:536` (apply-failed revert to pending) and `:732` (Undo to pending). Today the path is latent — the pending gate at `:519` (`if (raw.status !== "pending") return;`) means the client never touches a Claude-resolved record, and Undo is offered only for the client's own resolves (`SidePanel.svelte:823`, `undoable={review.getRecentlyResolved().has(ann.id)}`) — but `undoResolveAnnotation` (`:572-577`) has no ownership gate and the harness calls it directly, and a future reopen path would inherit the stamp and have the user's own later accept dropped by both consumers below. So at `:536` and `:732`: `const { resolvedBy: _dropped, ...rest } = ann; map.set(id, { ...rest, status: "pending" })` — the `clearHeldMarkersForDoc` pattern (`mode-release.ts:48`). `:528` is left alone: with both paths back to pending stripping, a pending record never carries the field, so the resolve write cannot forward one. This pulls `useAnnotationReview.svelte.ts` into the svelte-migration-reviewer's scope.
- `awareness.ts:636`: `&& ann.resolvedBy !== "claude"`. `output-schemas.ts:248` describe: "The USER's accept/dismiss decisions; Claude's own resolves never appear."
- `docx-apply.ts:204`: `if (ann.status !== "accepted" || ann.resolvedBy === "claude") continue;` — comment: **Claude cannot accept (`transitionPending` refuses), so this matches only a record whose stamp survived a status write that did not strip it; it is the belt for the client strip above, not a legacy guard** — no pre-existing record carries the field.

**Item 3 — ledger keyed on status for Claude's records, `awareness.ts`.** Add `function inboxLedgerKey(documentId: string, ann: Annotation): string { const base = ledgerKey(documentId, ann.id); return ann.author === "claude" ? `${base}#${ann.status}` : base; }` and use it at `:567`, `:615`, `:635`, `:638`.
