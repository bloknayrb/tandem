# D3 — #1941 the image-loss save refusal has no override: a browser user with no Claude attached has no exit

Branch `fix/docx-image-loss-save-the-explicit-override-both-surfaces-1941`. **Closes #1941** (both
surfaces of its body — the flag AND the UI affordance; the flag alone does not close it, by the
issue's own closing condition). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md`, wave 10 row
`D3 docx save override`. #1941 is not a v1-review finding and has no `areas/*.md` row of its own;
its ancestor is `areas/server-data.md:22` (#1755), whose spec is `D2-1755.md`. Probe: the e2e spec
in Tests 6 plus the screenshots, since no `probe-tools.mts` case covers a refused save.

**The shape is already decided and is not re-opened here.** Bryan, 2026-09-10, in the issue body:
refuse by default, add an explicit override. #1939 (`1aca8bc1`) shipped the refusal; this is the
escape hatch, split out so the safety half was not held up by it.

## Problem

`document-service.ts:496` refuses the binary save whenever the persisted fidelity report carries
`droppedImages > 0`, throwing `SaveVerificationError(blockReasonMessage("import-image-loss"))`.
Correct as a default, and the file is provably untouched. But the refusal is **total**: there is
no parameter, no body field and no control anywhere that lets a user who knows the picture is a
decorative header get their text edit onto disk. The only exit is `tandem_convertToMarkdown`,
which needs a Claude attached — so a browser user with none is at a dead end, and `saveAnyway`
appears nowhere in `src/`.

The refusal is also **over-countable by construction**, which is what makes the override
load-bearing rather than a convenience. `countDroppedImages` is `total − kept` read off the real
walk (D2-1755.md:15, :117); an over-count refuses that document's save *forever*, and today
nothing bounds that failure.

Two consequences of the old behaviour must not be overstated in the PR body:
`snapshotBeforeFirstWrite` (`file-io/doc-backup.ts`) **does** cover the `.docx` binary branch, so
pre-#1939 the images were recoverable-but-undiscoverable, not silently destroyed. That is what
makes this a real trade-off rather than an obvious one.

## Fix

**1. The flag.** `saveDocumentToDisk(docId, source, opts?: { allowImageLoss?: boolean })` —
a third optional parameter, so `reload-family.ts:188,191`, `autoSaveAllToDisk` and
`document-service.ts:1206` are unchanged by construction. The gate at `:496` becomes
`if (!opts?.allowImageLoss && reportCount(fidelityReportOf(doc), "droppedImages") > 0)`.

**Scope it to `import-image-loss` only.** The second throw (`:547`, `verdict.kind === "blocked"`)
stays untouched: those three reasons are post-write verification saying *the regenerated file is
broken*, which is a different claim from *the import never held the pictures*. A flag spanning
both would let a user force a `degenerate-model` write.

- `tandem_save` (`document.ts:1319-1323`): add `allowImageLoss: z.boolean().optional()` to the
  inputSchema, destructure it in the handler at `:1324`, pass it at `:1380`. Describe it as
  destructive in the `.describe()` — it is the one parameter of this tool that loses data.
- `POST /api/save` (`routes/save.ts`, branch 1 at `:130`): read
  `const allowImageLoss = body.allowImageLoss === true`. **Strict `=== true`, not truthiness and
  not a default** — `express.json()` is mounted with no `type` option, so a `text/plain` POST
  leaves `req.body` undefined and `body` falls back to `{}`; every parse failure must therefore
  land on `false`. Do not touch `assertOriginAllowlisted` at `:51`: it is the control that closed
  the simple-request CSRF, and a new optional field must not re-create a tolerated-missing-body
  path into a destructive default. Branches 2 and 3 (serialize, save-as) do not take the field.

**Critical Rule 9 — verified, no new row.** Both coverage tables key on the *surface*:
`license-gate-coverage.test.ts:72` (`tandem_save`, ungated) and
`license-gate-api-coverage.test.ts:87` (`API_SAVE`, ungated). A parameter is not a surface, so
neither table nor `docs/licensing-explained.md` gains a row. No route or tool is added;
`NON_LOOPBACK_ALLOWED` is untouched. **#1654's bound holds**: the flag changes *whether* a save
proceeds, never *where* it lands — no caller-named destination is introduced.

**2. The copy, in two places, and `blockReasonMessage` stays content-free.**

- `docx-verify.ts:448`, the `import-image-loss` arm, must **name the override** so the exit is
  discoverable from the refusal rather than from docs — and it must be **surface-neutral**. The same
  string reaches both readers: `document-service.ts:735-760` surfaces `SaveVerificationError.message`
  verbatim as the pushed notification *and* as the returned `reason`, which `tandem_save`
  (`document.ts:1383`) hands to Claude. Copy naming only "the document notice" points an agent at a
  UI it cannot see, and copy naming only the parameter is useless to a human. Still no path, no
  filename, no count — three files assert that property (`builtin.svelte.ts:55`,
  `activityCenter.ts:63`, `document-service.ts:749`) and a fourth sweeps it
  (`docx-verify.test.ts:291`). Breaking it is a privacy regression, not a copy change;
  `allowImageLoss` is a scalar parameter name rather than content, so naming it is not a breach.
  Proposed: `` `this file's pictures couldn't be imported, so saving would remove them — save anyway if you accept that (allowImageLoss), or convert it to Markdown instead${tail}` ``.
  **Pin it.** "Names the override" is a Done-when line that today's sweep
  (`docx-verify.test.ts:285-296`, which only checks `toContain("left unchanged")` and
  `not.toMatch(/[A-Z]:\\/)`) would pass on *any* wording, including one naming no exit at all. Add
  `expect(blockReasonMessage("import-image-loss")).toMatch(/save anyway/i)` to that block, and use
  the same phrase as the button label in §3 so the refusal cannot tell the user to click something
  that does not exist by that name.
- `file-io/index.ts:291-292` currently reads "so this file **can't be saved** back as .docx — ask
  Claude to convert it to Markdown to keep your edits". **This PR falsifies that sentence** and it
  is the line the banner renders, so it must change to describe a refusal-with-an-exit. It has
  **three** downstream assertions, not two — `docx-roundtrip-fidelity.test.ts:263`
  (`toContain("can't be saved")`), `:264` (`not.toMatch(/won'?t be in the saved file/i)`) and `:266`
  (`toMatch(/ask claude to convert it to markdown/i)`). `:263` and `:266` change with the copy;
  **`:264` is a wording constraint on the replacement, not incidental** — a new line phrased
  "…won't be in the saved file unless you choose Save anyway" turns it red. Keep it: the line must
  not read as though a lossy save is what happens by default. A grep for `can't be saved` /
  `ask claude to convert` across `src/`, `tests/`, `skills/`, `docs/` returns only those assertion
  sites plus the two source lines and the D2 spec's own quotations.

**3. The affordance — the half that matters.** `FidelityReportBanner.svelte`.

- The banner's normalize-on-read (`:44-53`) builds a **four-field object literal** and would
  silently discard `droppedImages`. Add it (`typeof raw.droppedImages === "number" ? … : 0`).
  This is the easy-to-miss half: `FidelityReport.droppedImages` is declared `droppedImages?: number`
  (`src/shared/types.ts:591`), so omitting it from the literal is not a type error.
- **The CTA is NOT nested in the `fidelity-report-import-losses` section, and `droppedImages` joins
  the banner's render gate.** Round 1 caught this: `hasLosses` (`:76-79`) reads only
  `importLosses.length > 0 || exportDowngrades.length > 0 || hasIntegrity`, the whole banner sits
  behind `{#if hasLosses && report}` (`:120`), and the import-losses section behind
  `{#if report.importLosses.length > 0}` (`:156`). A report carrying `droppedImages > 0` with an
  **empty** `importLosses` is reachable and already pinned by a test: `document-service.ts:633`
  takes `importLosses` from the PINNED `importSnapshot` while `:646` deliberately RE-READS
  `droppedImages` off the live doc (its own comment describes a file-watcher reload landing in the
  five-await window), and `tests/server/docx-fidelity-report.test.ts`'s "carries droppedImages set
  MID-SAVE — the refusal is not erased" is exactly that scenario for a file that was image-free
  before the reload. The refusal at `document-service.ts:496` reads that same re-read value, so
  nesting the CTA inside the import-losses `{#if}` puts the exit **precisely where it is absent for
  a document whose save is refused** — the dead end #1941 exists to remove. So: add
  `(report?.droppedImages ?? 0) > 0` as a **fourth term of `hasLosses`**, and render the CTA as its
  own block inside `fidelity-report-details` keyed on `droppedImages > 0` alone.
- Gate the CTA on `droppedImages > 0`, **not** on a failed save: the report is already
  server-authoritative and already rendered here, whereas keying off a save result would require
  the user to fail a save first and would need new client state.
- The CTA calls `triggerSave(documentId, { allowImageLoss: true, announceBusy: true })`.
  `triggerSave` (`builtin.svelte.ts:441`) gains the `allowImageLoss` option and puts it in the
  `/api/save` body. **`announceBusy: true` is required, not decoration** — the default is `false`
  and a re-entrant save then returns `false` silently, which the function's own docblock
  (`:434-440`) says "reads as a broken button for a human one"; the activity-tray Retry opts in for
  the same reason (`App.svelte:2701`). **Import `triggerSave` directly**, as `App.svelte:19` does.
  There is a **second declaration** of its options bag — `useDocumentWorkspace.svelte.ts:129`
  declares `opts?: { announceBusy?: boolean }` — and a wider real signature stays assignable to that
  narrower one, so leaving it alone type-checks; the banner deliberately does not route through the
  injected dep, and that bag type stays narrow.
- **`documentId` is already declared in `Props` but is deliberately NOT destructured** — `:30` reads
  `const { ydoc, fileName }: Props = $props();`, with the comment at `:28-29` calling it "part of
  the mount contract". Add it to the destructure and delete that comment; skipping it is a
  `documentId is not defined` at the call site rather than anything subtle.
- **Mirror `ExternalConflictBanner`'s `forDoc` pin AND its teardown reset — the pin alone is a
  bug.** That banner holds its own `pending`/`error` state and pins the document across the await
  (`:162`: `if (forDoc === documentId && …) pending = null`), but it is safe only because its
  `$effect` teardown (`:94-99`) **also** resets `pending` and `error`. This component is mounted in
  a plain `{#if activeTab && activeTab.format === "docx"}` with **no `{#key}`**
  (`App.svelte:2906-2911`) and its own comment (`:64-66`) states the instance is reused across
  docx→docx tab swaps, while its teardown (`:61-67`) resets only `report` and `expanded`. With the
  pin but no reset, a save started on doc A that settles after a swap leaves `pending` non-null
  forever and the new document's `disabled={pending !== null}` button is stuck for the session. So:
  reset the new `pending`/`error` in the **existing** teardown alongside `report`/`expanded`.
- **The loss is stated before the click**, per the issue's closing condition. The CTA lives inside
  the details panel, which starts collapsed (`expanded = false`, `:33`), so the intended chain is
  **refusal → Details → hint → CTA** and the e2e in Tests 6 must walk it. The section header already
  reads "Not imported — lost if you save over the original" and the import-loss line names the
  count, so the button label states the consequence rather than repeating it: **"Save anyway without
  pictures"** — it must contain the same "save anyway" phrase the refusal message names (§2), which
  is what the new `blockReasonMessage` assertion pins. Above it, a one-line hint saying the pictures
  will not be in the saved file and that **your original is backed up and can be restored** (the
  wording the integrity copy already uses at `:86`). Do **not** promise a guaranteed restorable
  backup: `snapshotBeforeFirstWrite` is best-effort by contract — "a snapshot failure must not block
  the save" (`document-service.ts:~530`).
- **This banner's docblock currently claims an invariant this PR falsifies.** `:17-19` reads
  "Read-only over Y.js — no CTA mutates server state". Rewrite that sentence in the same commit to
  carve out the save-anyway CTA: it mutates the **file**, not the Y.Doc, and the banner is still not
  dismissible.
- **New `data-testid="fidelity-report-save-anyway"`** (kebab-case). Critical Rule 7: regenerate
  `tests/design-system-impl/__snapshots__/testid-set.snap.txt` (`vitest -u`) **in the same
  commit** — it currently tracks 494 testids, 8 of them `fidelity-report-*`. The manifest at
  `docs/design-system-impl/testid-manifest.md:180-182` is **already stale** (it lists 5 of the 8,
  missing `fidelity-report-live-polite`, `-live-assertive` and `-integrity-warnings`), so updating
  it is best-effort convenience only — trust the snapshot, per Critical Rule 7.
- **This is what engages Critical Rule 7 for this banner.** `D2-1755.md:66` records the snapshot and
  manifest as "deliberately not touched … Critical Rule 7 is not engaged" — true of #1939, and
  superseded here. Say so in the PR body so the two specs do not read as contradicting each other.
- **No Convert CTA.** D2-1755.md:70 flags that one carries conversion semantics for writable
  documents which `ReviewOnlyBanner`'s does not settle. Out of scope; the ask is "Save anyway".
- **The report stays armed after an honoured override — decided, not incidental.** `:646` re-reads
  and re-persists `droppedImages` on every successful binary save, and `:633` carries the
  `importSnapshot`'s `importLosses` verbatim, so after an overridden save the notice and the refusal
  both return even though the pictures are now gone from disk. That is the intended behaviour —
  **one click, one save** — and the copy is knowingly stale for that second pass. Pinned by a named
  test (Tests 2b) rather than left as an unexamined side effect.

**4. Docs and skill.** `docs/mcp-tools.md`'s **`### tandem_save`** parameter table gains the

## Done when

An image-bearing `.docx` is still refused by default on both surfaces; a user can save it from the
browser UI alone, with the loss stated before the click; the CTA renders for a report carrying
`droppedImages > 0` **even with an empty `importLosses`**, and is enabled again after a tab swap;
`tandem_save` and `POST /api/save` both accept the flag and both default to refusing on any parse
failure, pinned at the route by an argument assertion plus one positive end-to-end case;
`blockReasonMessage` names the override, stays content-free, and is **pinned by a `/save anyway/i`
assertion** whose phrase the button label shares; the `file-io/index.ts` line no longer claims the
file can't be saved and still does not read as a lossy-save-by-default; a second plain save after an
honoured override is still refused; the new testid is in the regenerated snapshot;
`docs/mcp-tools.md` and `SKILL.md` (v23 → v24, both literals in
`tests/skill-instruction-contract.test.ts` — the regex at `:113` and the
`{ version: "23", bodyHash: "ca9991f2313c" }` pair at `:434`) carry the second exit; typecheck +
suite + `npm run test:e2e` green, with screenshots of the banner collapsed and expanded.

## Not in scope

Actually importing `.docx` body images (Tier-B preserve-the-package, #1142) — the thing that makes
both the refusal and this override moot. A Convert CTA on the banner (D2-1755.md:70). Extending the
override to `tandem_applyChanges` (pictures survive it) or to the three post-write-verification
block reasons. Persisting the choice across saves or documents — one click, one save; **decided and
pinned in §3 + Tests 2b**, not merely deferred. Any change to `NON_LOOPBACK_ALLOWED`, to the
`/api/save` gates, or to where a save lands.
