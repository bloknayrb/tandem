# D3 — #1941 the image-loss save refusal has no override: a browser user with no Claude attached has no exit

Branch `fix/docx-image-loss-save-the-explicit-override-both-surfaces-1941`. **Closes #1941** (both
surfaces of its body — the flag AND the UI affordance; the flag alone does not close it, by the
issue's own closing condition). Ledger: `docs/plans/2026-09-06-open-issues-sweep.md`, wave 10 row
`D3 docx save override`. #1941 is not a v1-review finding and has no `areas/*.md` row of its own;
its ancestor is `areas/server-data.md:22` (#1755), whose spec is `D2-1755.md`. Probe: the e2e spec
in Tests 6 plus the screenshots, since no `probe-tools.mts` case covers a refused save.

**The shape is already decided and is not re-opened here.** Bryan, 2026-09-10, in the issue body:
refuse by default, add an explicit override. #1939 (`1aca8bc1`) shipped the refusal; this is the
escape hatch, split out so the safety half was not held up by it.

## Problem

`document-service.ts:496` refuses the binary save whenever the persisted fidelity report carries
`droppedImages > 0`, throwing `SaveVerificationError(blockReasonMessage("import-image-loss"))`.
Correct as a default, and the file is provably untouched. But the refusal is **total**: there is
no parameter, no body field and no control anywhere that lets a user who knows the picture is a
decorative header get their text edit onto disk. The only exit is `tandem_convertToMarkdown`,
which needs a Claude attached — so a browser user with none is at a dead end, and `saveAnyway`
appears nowhere in `src/`.

The refusal is also **over-countable by construction**, which is what makes the override
load-bearing rather than a convenience. `countDroppedImages` is `total − kept` read off the real
walk (D2-1755.md:15, :117); an over-count refuses that document's save *forever*, and today
nothing bounds that failure.

Two consequences of the old behaviour must not be overstated in the PR body:
`snapshotBeforeFirstWrite` (`file-io/doc-backup.ts`) **does** cover the `.docx` binary branch, so
pre-#1939 the images were recoverable-but-undiscoverable, not silently destroyed. That is what
makes this a real trade-off rather than an obvious one.

## Fix

**1. The flag.** `saveDocumentToDisk(docId, source, opts?: { allowImageLoss?: boolean })` —
a third optional parameter, so `reload-family.ts:188,191`, `autoSaveAllToDisk` and
`document-service.ts:1206` are unchanged by construction. The gate at `:496` becomes
`if (!opts?.allowImageLoss && reportCount(fidelityReportOf(doc), "droppedImages") > 0)`.

**Scope it to `import-image-loss` only.** The second throw (`:547`, `verdict.kind === "blocked"`)
stays untouched: those three reasons are post-write verification saying *the regenerated file is
broken*, which is a different claim from *the import never held the pictures*. A flag spanning
both would let a user force a `degenerate-model` write.

- `tandem_save` (`document.ts:1319-1323`): add `allowImageLoss: z.boolean().optional()` to the
  inputSchema, destructure it in the handler at `:1324`, pass it at `:1380`. Describe it as
  destructive in the `.describe()` — it is the one parameter of this tool that loses data.
- `POST /api/save` (`routes/save.ts`, branch 1 at `:130`): read
  `const allowImageLoss = body.allowImageLoss === true`. **Strict `=== true`, not truthiness and
  not a default** — `express.json()` is mounted with no `type` option, so a `text/plain` POST
  leaves `req.body` undefined and `body` falls back to `{}`; every parse failure must therefore
  land on `false`. Do not touch `assertOriginAllowlisted` at `:51`: it is the control that closed
  the simple-request CSRF, and a new optional field must not re-create a tolerated-missing-body
  path into a destructive default. Branches 2 and 3 (serialize, save-as) do not take the field.

**Critical Rule 9 — verified, no new row.** Both coverage tables key on the *surface*:
`license-gate-coverage.test.ts:72` (`tandem_save`, ungated) and
`license-gate-api-coverage.test.ts:87` (`API_SAVE`, ungated). A parameter is not a surface, so
neither table nor `docs/licensing-explained.md` gains a row. No route or tool is added;
`NON_LOOPBACK_ALLOWED` is untouched. **#1654's bound holds**: the flag changes *whether* a save
proceeds, never *where* it lands — no caller-named destination is introduced.

**2. The copy, in two places, and `blockReasonMessage` stays content-free.**

- `docx-verify.ts:448`, the `import-image-loss` arm, must **name the override** so the exit is
  discoverable from the refusal rather than from docs. Still no path, no filename, no count —
  three files assert that property (`builtin.svelte.ts:55`, `activityCenter.ts:63`,
  `document-service.ts:749`) and a fourth sweeps it (`docx-verify.test.ts:291`). Breaking it is a
  privacy regression, not a copy change. Proposed: `` `this file's pictures couldn't be imported, so saving would remove them — save anyway from the document notice, or ask Claude to convert it to Markdown${tail}` ``.
- `file-io/index.ts:291-292` currently reads "so this file **can't be saved** back as .docx — ask
  Claude to convert it to Markdown to keep your edits". **This PR falsifies that sentence** and it
  is the line the banner renders, so it must change to describe a refusal-with-an-exit. Its two
  assertions at `docx-roundtrip-fidelity.test.ts:263,266` change with it; a grep for
  `can't be saved` / `ask claude to convert` across `src/`, `tests/`, `skills/`, `docs/` returns
  only those two assertion sites plus the two source lines and the D2 spec's own quotations.

**3. The affordance — the half that matters.** `FidelityReportBanner.svelte`, inside the existing
`fidelity-report-import-losses` section (`:156`), which already tells the user about the dropped
pictures in exactly the place the button belongs.

- The banner's normalize-on-read (`:44-53`) builds a **four-field object literal** and would
  silently discard `droppedImages`. Add it (`typeof raw.droppedImages === "number" ? … : 0`).
  This is the easy-to-miss half: the field is optional, so omitting it is not a type error.
- Gate the CTA on `droppedImages > 0`, **not** on a failed save: the report is already
  server-authoritative and already rendered here, whereas keying off a save result would require
  the user to fail a save first and would need new client state.
- The CTA calls `triggerSave(documentId, { allowImageLoss: true })` — `triggerSave`
  (`builtin.svelte.ts:441`) gains that option and puts it in the `/api/save` body. **`documentId`
  is already declared in `Props` but is deliberately NOT destructured** — `:30` reads
  `const { ydoc, fileName }: Props = $props();`, with the comment at `:28-29` calling it "part of
  the mount contract". Add it to the destructure and delete that comment; this is the edit that
  makes the prop real, and skipping it is a `documentId is not defined` at the call site rather
  than anything subtle. `ExternalConflictBanner` is the precedent for a banner CTA that
  mutates — it holds its own `pending`/`error` state and pins the document across the await; mirror
  that shape, including the `forDoc` pin, since this component also accepts a swappable `ydoc`.
- **The loss is stated before the click**, per the issue's closing condition: the section header
  already reads "Not imported — lost if you save over the original", and the import-loss line
  names the count. The button is the confirmation, so its label states the consequence rather than
  repeating the count: **"Save without pictures"**, with a one-line hint above it saying the
  pictures will not be in the saved file and the backup is still restorable.
- **New `data-testid="fidelity-report-save-anyway"`** (kebab-case). Critical Rule 7: regenerate
  `tests/design-system-impl/__snapshots__/testid-set.snap.txt` (`vitest -u`) **in the same
  commit** — it currently tracks 494 testids, 8 of them `fidelity-report-*`. Also add it to
  `docs/design-system-impl/testid-manifest.md:180-182` (a convenience copy no test reads, so it
  drifts silently — trust the snapshot).
- **No Convert CTA.** D2-1755.md:70 flags that one carries conversion semantics for writable
  documents which `ReviewOnlyBanner`'s does not settle. Out of scope; the ask is "Save anyway".

**4. Docs and skill.** `docs/mcp-tools.md:404-412` gains the `allowImageLoss` parameter row and a
sentence on the Errors line (`:440`) that `VERIFY_BLOCKED` for dropped pictures is now overridable.
`skills/tandem/SKILL.md:135` currently tells Claude to offer `tandem_convertToMarkdown` as the
**only** way out; that instruction is now incomplete — add the override as the second exit, framed
as "ask the user first" since it destroys the pictures. Bump frontmatter `version: 23` → `24` and
update **both** literals in `tests/skill-instruction-contract.test.ts` in the same commit: the
regex at `:113` and the `{ version: "23", bodyHash: "ca9991f2313c" }` pair at `:434`. Recompute the
hash **once, after the body edit has landed** (sha256 of everything after the closing `---`, CRLF
normalised, first 12 hex chars). A content edit without the bump reaches **nobody**:
`refreshExistingSkillIfStale` bails at `>=`.

**Not extended to `tandem_applyChanges`.** `file-io/docx-apply.ts` edits the original
`word/document.xml` in place and re-zips, so pictures **survive** it — it is the one write path
that preserves them, and #1939's gate deliberately skips it. An override there is meaningless at
best. `docx-apply.ts` must also still contain no reference to `rearmWatch`.

## Tests

Each says what wrong implementation it kills.

1. `tests/server/docx-fidelity-report.test.ts`, beside the refusal spec at `:452`: an
   image-bearing `.docx` with `allowImageLoss: true` returns `status: "saved"`, and the file on
   disk **changed** (byte comparison against the original, the mirror of the existing spec's
   untouched-bytes assertion). **Mutation target (rule 5, first half):** revert the `!opts?.allowImageLoss`
   term and this goes red.
2. Same file: the default is unchanged — the existing
   "refuses the save of an image-bearing .docx and leaves the file untouched" spec stays green
   verbatim, and a new twin passes `{ allowImageLoss: false }` explicitly. **Mutation target
   (rule 5, second half):** flip the default to `true` and spec 2 goes red while spec 1 stays
   green, which is the asymmetry that proves the default still refuses.
3. Same file: `allowImageLoss: true` does **not** override a `verdict.kind === "blocked"` verdict —
   reuse `document-service.test.ts:800`'s garbage-bytes `saveBinary` spy, assert still
   `VERIFY_BLOCKED`. Kills a flag wired at `:547` or around both throws.
4. `tests/server/routes/` (or the save-route suite): `POST /api/save` with **no body at all**, and
   with `{ allowImageLoss: "true" }` (a string), both refuse. Kills truthiness parsing and the
   tolerated-missing-body path the `assertOriginAllowlisted` comment exists to prevent.
5. `tests/client/fidelity-report-banner.test.ts`: the CTA is **absent** when `droppedImages` is 0
   or missing (kills "always show it"), **present** when it is > 0, and clicking it calls the
   save with `allowImageLoss: true` (stub `fetch`, assert the parsed body). A fourth case sets a
   report with `droppedImages` present and asserts the normalizer kept it — kills the silent
   four-field-literal drop, which no type error catches.
6. `tests/e2e/docx-save-anyway.spec.ts` (new): open a committed image-bearing fixture, expand
   Details, assert the loss text is visible **before** the click, click
   `fidelity-report-save-anyway`, assert the save succeeds. Needs a new deterministic fixture
   `tests/e2e/fixtures/body-image.docx` + `scripts/fixtures/make-image-docx.mjs`, following
   `make-reviewer-docx.mjs` exactly (fixed zip mtime, committed binary); the content mirrors
   `tests/helpers/docx-corpus.ts#buildEmbeddedImageWithText`, which pairs the picture with a text
   paragraph so there is something to save.
7. `tests/client/actions/save-outcome.test.ts`: `triggerSave` omits `allowImageLoss` from the body
   when not asked. Kills a client that always sends it.

## Done when

An image-bearing `.docx` is still refused by default on both surfaces; a user can save it from the
browser UI alone, with the loss stated before the click; `tandem_save` and `POST /api/save` both
accept the flag and both default to refusing on any parse failure; `blockReasonMessage` names the
override and stays content-free; the `file-io/index.ts` line no longer claims the file can't be
saved; the new testid is in the regenerated snapshot; `docs/mcp-tools.md` and `SKILL.md` (v24,
both literals) carry the second exit; typecheck + suite + `npm run test:e2e` green, with
screenshots of the banner collapsed and expanded.

## Not in scope

Actually importing `.docx` body images (Tier-B preserve-the-package, #1142) — the thing that makes

block reasons. Persisting the choice across saves or documents — one click, one save. Any change to
`NON_LOOPBACK_ALLOWED`, to the `/api/save` gates, or to where a save lands.
