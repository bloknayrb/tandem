# E1 — #1758 `tandem` from npm kills the desktop's server: the store-lock retry runs before `freePort`

Branch `fix/desktop-core-1761`. Closes #1758. Ledger: `docs/plans/2026-09-06-open-issues-sweep.md:413`; area rows `docs/reviews/2026-09-02-v1-review/areas/server-runtime.md:18` and `areas/product.md:16`. Probe: `tests/server/platform.test.ts`; the two-instance race is a smoke line (Bryan).

## Problem

In `src/server/index.ts` a second instance on the default ports (a) waits up to 30 s for the annotation-store lock and commits to `readonly` (`:335-360`), then (b) reaches `freePort(wsPort); freePort(mcpPort)` (`:609-610`) and **SIGKILLs / `taskkill /F`s** whatever holds them (`src/server/platform.ts:51-61`, `:178-249`). `freePort` looks up a listening PID and kills it; it has no way to ask whether that PID is a healthy Tandem serving a human. So `tandem` from a terminal — which `doctor` and several docs suggest running — kills the desktop app's sidecar under the user's open documents, and the survivor is the read-only instance that cannot save annotations. The stdio branch has the same shape at `:767` (`freePort(wsPort)` with no probe).

**The npm flavor is the bug; the desktop's own child is not.** The Tauri shell delegates port reclamation *to* the sidecar it spawns — `src-tauri/src/sidecar.rs:1450-1453`: "a stale `tsx watch` dev session, an older release process, or any other listener on the MCP/WS ports can answer /health but be incompatible with this app's auth token / session state … The sidecar's own `freePort()` step on start handles port conflicts cleanly." The sidecar *is* `src/server/index.ts` in HTTP mode, so a refusal placed there without a carve-out fires inside the desktop's child too, and removes the app's only self-heal. That is the shape round 1 rejected; see Fix.

**Doc state, re-derived.** `docs/release-smoke-checklist.md:217-220` certifies the opposite of the code ("the npm server retries for 30s and gives up rather than displacing the app. Correct behaviour") and must be rewritten. `docs/troubleshooting.md`'s "Port already in use" section (starting `:147`) already describes the current behaviour **accurately** — it says Tandem kills "whatever" is listening, names the desktop-app consequence and cites #1758 — so it needs updating for the new refusal, not correcting for a false claim. Note that `tests/scripts/e2e-guard-wiring.test.ts:185-196` forbids any harness port literal in that file, so the rewritten paragraph must keep the existing `4478`/`4479` example unchanged.

## Fix

Probe before the lock; refuse rather than displace — **in the npm flavor only**; reserve `freePort` for listeners that fail the probe.

- **New `probeTandemInstance(mcpPort, schedule?): Promise<{ pid: number; version: string } | null>` in `src/server/platform.ts`**, beside `freePort` / `waitForPort` — that is where port lifecycle already lives and the pairing ("`freePort` is for listeners that fail this probe") should be readable in one file. `fetch("http://127.0.0.1:<mcpPort>/health")` with an `AbortSignal.timeout(timeoutMs)`; return `null` on any throw, non-2xx, non-JSON, or a body without `status === "ok"` **and** a numeric `pid` **and** a string `version`.
  - **Retry before concluding absence: three attempts, 1 s timeout each, ~250 ms apart.** A single 1 s window is not enough evidence to authorise a SIGKILL: a healthy Tandem whose event loop is briefly blocked (a `.docx` convert, a large `extractText`, a big annotation-envelope parse) answers slowly, probes as `null`, and is then killed by `freePort` — the exact outcome this spec exists to prevent, reached through the fix. A positive result on any attempt short-circuits.
  - **The schedule is an optional parameter — `{attempts = 3, timeoutMs = 1000, delayMs = 250}` — defaulting to exactly those values, and no production call site passes one.** It exists so the absence test can run in ~150 ms instead of ~3.5 s: the specified baseline is `3×1000 + 2×250 = 3500 ms` against vitest's 5000 ms default per-test timeout, which is ~1.5 s of headroom on a `check` runner that also runs the acceptance harness — a flake waiting to happen, and one that reads as a real failure.
  - Always `127.0.0.1`, never the bind host — this asks "is something already on the loopback port I am about to take".
- **`pid` is what #1812 adds to `/health`.** A pre-fix Tandem therefore probes as `null` and is still `freePort`ed, which is today's behaviour and is the right call for an upgrade replacing its own predecessor. State that limit in the PR body; it is the reason the two issues ship together.
- **Keep the whole decision — including the second probe — in one pure function.** `decideStartupAction({ probe, defaultProbe, mode, isSidecar, wsPort, mcpPort }): { action: "refuse" | "proceed"; freeWsPort: boolean }` in the same module. `freeWsPort` replaces the old `"skip-freeport"` action: the two things a caller needs to know are "may I start at all" and "may I kill whatever holds the WS port", and folding the second probe into the same return is what stops it from being a fourth, untabled branch written inline at the call site.
  - `isSidecar` (i.e. `process.env.TANDEM_TAURI_SIDECAR === "1"`, the same discriminant E1-1787 uses for `flavor`) → `{action: "proceed", freeWsPort: true}`, whatever either probe says. **The desktop keeps today's `freePort` recovery because the shell owns the port lifecycle and has no other one.** Log the probe result; do not act on it.
  - `probe !== null && mode === "http"` → `{action: "refuse", freeWsPort: false}`. The issue's case.
  - `probe !== null && mode === "stdio"` → `{action: "proceed", freeWsPort: false}`. Do not exit (see the stdio bullet below); skip the kill.
  - `probe === null` → `{action: "proceed", freeWsPort: !defaultPortHolds}`, where `defaultPortHolds` is `defaultProbe !== null` **only when `wsPort === DEFAULT_WS_PORT && mcpPort !== DEFAULT_MCP_PORT`** and `false` otherwise. Otherwise today's behaviour: `freePort` still runs.
  - **That port gate is the whole guard and it must live inside the pure function.** `DEFAULT_WS_PORT` / `DEFAULT_MCP_PORT` come from `src/shared/constants.ts` (`:1-2`). An ungated default-port probe is not a smaller bug than the one this spec fixes: **the E2E and perf harnesses' backend *is* `src/server/index.ts`** (`playwright.config.ts:91-93` runs it through `scripts/e2e-server.mjs` with `TANDEM_PORT`/`TANDEM_MCP_PORT` set to the reserved pair at `:120-121`; `tests/perf/playwright.config.ts:188-191` does the same), and `scripts/test-ports.ts:9-12` names that boot's own `freePort()` as the mechanism that reclaims a squatted reserved port. With a desktop Tandem up on :3479 — the state CLAUDE.md's Testing & E2E gotcha says the harness is designed to coexist with — an ungated probe returns non-null and suppresses `freePort(4728)` / `freePort(PERF_WS_PORT)`, so a stale holder of the reserved ws port is never cleared, intermittently and only when the app happens to be running.
- **`src/server/index.ts`, HTTP mode:** run the probe as the **first** thing in `main()`'s HTTP path — before `claimAppDataDir` (E1-1787), the backup sweep at `:299`, the trial clock at `:315` and the store-lock block at `:332`, all of which already touch app-data. The agreed order across both specs is **probe (HTTP only) → claim → sweep → trial → lock**. On `"refuse"`, print to stderr and `process.exit(1)`:
  `[Tandem] Tandem is already running at http://127.0.0.1:<mcpPort> (v<version>, pid <pid>). Not starting a second instance — quit the running one first, or run on different ports: see "Port already in use" in docs/troubleshooting.md (TANDEM_PORT, TANDEM_MCP_PORT and TANDEM_URL all have to match).`
  Exit **1**, not 0: this is a refusal to start, and a 0 would read as success to a wrapper script. Nothing has been mutated at this point — no lock taken, no port killed — which is the whole point of probing first.
  - **The message must not name a partial recipe.** An either/or "`TANDEM_PORT` / `TANDEM_MCP_PORT`" invites the user to set only the MCP port; the probe then finds that port free, returns `null`, startup proceeds, and `freePort(wsPort)` SIGKILLs the desktop's Hocuspocus on :3478 under the user's open documents — `freePort` keys on the port, not the bind address (`platform.ts:179-210`, `:212-249`). Naming all three, and pointing at the doc section that already says "All three need to match", is what keeps the remedy from re-creating the bug.
- **Second probe before `freePort(wsPort)` (HTTP mode), and it fires for exactly one configuration.** The refusal covers the *configured* `mcpPort` only, so the case it exists for is "the user moved only `TANDEM_MCP_PORT`": `wsPort === DEFAULT_WS_PORT && mcpPort !== DEFAULT_MCP_PORT`. Under that condition, and only under it, probe the **default** MCP port (`DEFAULT_MCP_PORT`) as well and pass the result to `decideStartupAction` as `defaultProbe`; on `freeWsPort: false`, skip `freePort(wsPort)` and log `[Tandem] Another Tandem is serving :3479 — leaving :<wsPort> alone`. The call site performs the extra probe only when the gate holds (no needless request), and the pure function re-checks the same gate, so a call site that probes unconditionally still cannot change the verdict. Both halves matter: without the gate the harness loses its own port reclamation whenever a desktop Tandem is up (previous bullet), and a user with `TANDEM_PORT=5001 TANDEM_MCP_PORT=5000` would have a genuinely stale holder of :5001 left in place by an unrelated Tandem on :3479, falling through to `waitForPort`'s "proceeding anyway" (`src/server/index.ts:612-615`).
- **`src/server/index.ts`, stdio mode (`:767`):** same probe, `freeWsPort: false` — skip `freePort(wsPort)` and log `[Tandem] Another Tandem is serving :<mcpPort> — leaving :<wsPort> alone`. Do not exit: an MCP client's init would fail, and the branch already tolerates a Hocuspocus bind failure (`:775-777` catches and logs). Skipping the kill converts "silently killed the desktop" into "MCP works, Hocuspocus did not bind", which is the honest outcome. No default-port probe in stdio mode — the gate above is HTTP-only.
- **`freePort` itself is unchanged.** It stays the tool for a listener that answers nothing — a wedged process, a crashed sidecar, an unrelated program. Do not add the probe inside it: three of its callers (the E2E harness's own boot, `scripts/`, the stdio path) have different needs, and a probe hidden inside a kill primitive is the kind of implicit control the reviewers should reject.
- **Docs, in the same PR:** rewrite `docs/release-smoke-checklist.md:217-220` — §4 now refuses with a named message instead of contending, and the "gives up rather than displacing" certification is withdrawn as never having matched the code. Update the "Port already in use" section of `docs/troubleshooting.md` (from `:147`) to describe the new behaviour: an npm `tandem` now identifies the holder first and refuses rather than killing a live Tandem, `freePort` still frees a listener that does not answer `/health` as a Tandem, and the desktop app is deliberately exempt because its shell relies on `freePort` to reclaim its own port. Keep the `4478`/`4479` example bytes intact (`e2e-guard-wiring.test.ts:185-196`).
- Rules that bite: none of this writes to a Y.Doc, so Critical Rules 1–2 are inert; no new `/api` route or MCP tool, so Rule 9 and `NON_LOOPBACK_ALLOWED` are untouched; `/health` is not a mutating route.

## Tests

1. `tests/server/platform.test.ts` — `probeTandemInstance` against a real `http.createServer` on an ephemeral port: (a) a Tandem-shaped body → returns `{pid, version}`; (b) `{status:"ok", version:"x"}` with **no** `pid` → `null`; (c) a 200 of `"hello"` → `null`; (d) 404 → `null`; (e) nothing listening → `null`. **What (b) kills:** accepting any JSON `status: "ok"` as Tandem, which would let an unrelated health endpoint block startup forever — a refusal that cannot be recovered from is worse than the bug. **What (c)/(d) kill:** a `res.ok`-only check.
2. Same file: a server that never responds → the probe resolves `null`. Drive it with an explicit short schedule (`{attempts: 3, timeoutMs: 50, delayMs: 10}`) and give the case an explicit `{ timeout: 15_000 }`, so it neither sits on vitest's default nor depends on runner load. **What it kills:** a missing timeout, which would hang every startup behind a black-holed port. Add one assertion that the *default* schedule is `{attempts: 3, timeoutMs: 1000, delayMs: 250}` (read it off the exported default object) so shortening the test cannot silently shorten production.
3. Same file: a server that answers a Tandem-shaped body only on its **third** request → the probe returns `{pid, version}`, again on a short schedule. **What it kills:** the single-shot probe, under which a momentarily-blocked healthy Tandem is classified absent and then SIGKILLed.
4. Same file — `decideStartupAction`, one row per outcome, and each names what it kills. Every row supplies `wsPort`/`mcpPort`; unless stated they are `DEFAULT_WS_PORT`/`DEFAULT_MCP_PORT` and `defaultProbe: null`:
   - `{probe: null, mode: "http", isSidecar: false}` → `{action: "proceed", freeWsPort: true}`. Kills a refusal that fires with no evidence, **and** is the "probe says no → kill still happens" half — nothing else asserts that `freePort` is still reached.
   - `{probe: {…}, mode: "http", isSidecar: false}` → `{action: "refuse", freeWsPort: false}`. The issue's case.
   - `{probe: {…}, mode: "http", isSidecar: true}` → `{action: "proceed", freeWsPort: true}`. **Kills a refusal that strands the desktop app behind its own orphaned sidecar** — on macOS/Linux there is no job object (`sidecar.rs:1620-1629` is Windows-only), so a force-quit shell leaves a live sidecar; with an unconditional refusal the fresh child exits 1, `wait_for_health` bails, and `start_sidecar` burns all `MAX_RESTARTS` into the "Retry Server Start" dialog with nothing left to clear the orphan.
   - `{probe: {…}, mode: "stdio", isSidecar: false}` → `{action: "proceed", freeWsPort: false}`. Kills the stdio branch inheriting the exit, which would break every MCP client that spawns it.
   - **Moved MCP port only:** `{probe: null, defaultProbe: {…}, mode: "http", isSidecar: false, wsPort: DEFAULT_WS_PORT, mcpPort: 5000}` → `freeWsPort: false`. Kills dropping the second probe, which is the Done-when clause "a user who has moved only the MCP port does not lose :3478".
   - **Both ports moved:** `{probe: null, defaultProbe: {…}, mode: "http", isSidecar: false, wsPort: 5001, mcpPort: 5000}` → `freeWsPort: true`. Kills an ungated default-port probe that leaves a genuinely stale holder of the user's own custom WS port in place.
   - **Harness shape:** `{probe: null, defaultProbe: {…}, mode: "http", isSidecar: false, wsPort: E2E_WS_PORT, mcpPort: E2E_MCP_PORT}` → `freeWsPort: true`, imported from `scripts/test-ports.ts` so a renumbering travels. **Kills the regression this round found**: an ungated default-port probe disables the E2E/perf harness's own reserved-port reclamation whenever a desktop Tandem is running.
5. `tests/server/platform.test.ts` — assert `freePort` is still exported and unchanged in signature (it has existing specs; do not weaken them).
6. **New `tests/server/startup-probe-wiring.test.ts` — a source-shape test, because the fix is entirely call-site ordering and no test can drive `main()` (the module binds ports on import).** Follow the repo's existing pattern for exactly this problem (`tests/docs/loopback-gate-claims.test.ts`, `tests/server/document-write-rearm.test.ts`): read `src/server/index.ts` as text and assert, by index within the file, that the `decideStartupAction(` call appears **before** `acquireStoreLock`/the store-lock block, before **both** `freePort(` occurrences, and before the backup-sweep and trial-clock imports; that the `"refuse"` arm's body contains `process.exit(1)`; that both `freePort(wsPort)` sites are guarded by the `freeWsPort` result rather than called unconditionally; and that `probeTandemInstance(` appears at least twice (the configured-port probe and the gated default-port probe). **What it kills:** the laziest passing implementation — landing `probeTandemInstance` and `decideStartupAction` fully tested and never calling them, or calling them *after* `freePort`. Under that implementation every other test here is green and all four behavioural clauses of Done-when are unchecked. This test is in Done-when so it cannot be dropped as tidiness.
7. The two-instance cross-process run stays a smoke line (Bryan); say in the PR body that tests 4 and 6 together are what stand in for it.

## Done when

Starting `tandem` from npm while a current-version Tandem holds :3479 exits 1 with the named message and kills nothing; the **desktop sidecar** still runs `freePort` and self-heals against a stale holder; a wedged non-Tandem listener is still freed; a slow-but-answering server is not classified absent; stdio mode leaves the port alone and logs; a user who has moved only the MCP port does not lose :3478; **the E2E and perf harnesses still reclaim their reserved ws port while a desktop Tandem is running** (test 4's harness row); **`tests/server/startup-probe-wiring.test.ts` pins that the decision is consulted before the lock and before both `freePort` calls, and that the refusal exits 1**; the smoke-checklist certification is withdrawn and the troubleshooting section describes the new behaviour.

## Files touched

`src/server/platform.ts`, `src/server/index.ts`, `tests/server/platform.test.ts`, `tests/server/startup-probe-wiring.test.ts` (new), `docs/release-smoke-checklist.md`, `docs/troubleshooting.md`.

## Not in scope

Attaching as a client to the running instance (the issue's second option — a feature, not a fix). Multi-instance support on non-default ports. `freePort`'s SIGKILL semantics, and its port-keyed (not bind-address-keyed) lookup: a Tandem bound to a LAN interface via `TANDEM_BIND_HOST` is invisible to the 127.0.0.1 probe and would still be killed — name that in the PR body beside the pre-#1812 limit. #1812's health-poll identity check, which is its own spec in this PR. Whether `doctor` should suggest a different command when an instance is already running (#1790, wave 3).
