# D1 — #1850 `atomicWrite` leaves an orphaned `.tandem-tmp-*` file when the temp-file write fails

Branch `fix/markdown-fidelity-1753`. Closes #1850. No area-ledger row of its own — found during review of PR #1849 (#1796); the same condition is the first `#1823` **server-data** bullet, so this PR also `Refs #1823` (see `D1-1823.md`). Probe: none needed; the defect is a missing `catch`, read directly off the source.

## Problem

`src/server/file-io/index.ts:361-365`:

```ts
export async function atomicWrite(filePath: string, content: string): Promise<void> {
  const tempPath = tempSiblingPath(filePath);
  await fs.writeFile(tempPath, content, "utf-8");     // <- no cleanup on failure
  await renameWithRetry(tempPath, filePath);
}
```
`atomicWriteBuffer` (`:372-376`) is byte-for-byte the same shape. If `fs.writeFile` fails partway — ENOSPC, EDQUOT, EIO — a partial `.tandem-tmp-<ms>-<12 hex>` file is left **in the user's document directory**, next to their real file, and the error propagates with the sibling still on disk.

Nothing cleans it up. The second half of `atomicWrite` already does this correctly: `renameWithRetry`'s failure arm is `await fs.unlink(tempPath).catch(() => {}); throw err;`. The boot-time reaper deliberately never sweeps user document directories — `reapOrphanedTemps` covers the annotations + sessions dirs only, and CLAUDE.md states that as an invariant, so widening the reaper is not the fix. Every writer that goes through these two functions is affected: save, save-as, restore, convert, export, docx-apply, backups, the annotation store.

## Fix

Give the first half the same cleanup the second half already has, in both functions:

```ts
export async function atomicWrite(filePath: string, content: string): Promise<void> {
  const tempPath = tempSiblingPath(filePath);
  try {
    await fs.writeFile(tempPath, content, "utf-8");
  } catch (err) {
    // Mirror renameWithRetry's failure arm: a partial temp sibling in the
    // USER's document directory is never reaped (the boot reaper sweeps the
    // annotations + sessions dirs only). Swallow the unlink — the write error
    // is the one the caller must see (#1850).
    await fs.unlink(tempPath).catch(() => {});
    throw err;
  }
  await renameWithRetry(tempPath, filePath);
}
```
and the identical change in `atomicWriteBuffer`.

Four properties a rewrite must keep: the **original** error is rethrown (an unlink failure must not mask ENOSPC); the unlink is `.catch(() => {})` because the temp file may legitimately not exist (an ENOSPC that failed before `open`); the `try` wraps **only** `writeFile`, so a `renameWithRetry` failure keeps taking its own existing path rather than being unlinked twice; and no retry or fallback is added — the caller's error contract is unchanged.

**`reaper.ts:45-49`'s comment becomes true with this PR, so amend it here.** It currently reads "The error path unlinks the temp on terminal rename failure, so failed writes never orphan" — false today for exactly the reason #1850 is filed, and true once both halves clean up. Amend it to name both failure paths and cite #1850, so the reaper's stated safety boundary is dated to the change that established it.

Rules that bite: no Y.Doc write, no Y.Map key, no MCP tool or `/api` route added, so neither license-gate half nor `NON_LOOPBACK_ALLOWED` is touched. No error code changes — the same rejection with the same `code` reaches `sendApiError`/`withErrorBoundary` — so `docs/mcp-tools.md`'s Errors lines are unchanged; say so in the PR body, because a reviewer will check. **The file-watcher triple is untouched**: `recordSelfWrite` / `rearmWatch` are the callers' responsibility and sit after the `await atomicWrite`, so none of them run on a throwing write and the site table pinned by `tests/server/document-write-rearm.test.ts` is unaffected.

## Tests

New `tests/server/file-io/atomic-write-cleanup.test.ts` (no existing suite owns `atomicWrite` directly; the ~10 files that mention it all mock it). Use a real temp directory plus a spy on the module the code under test uses: `src/server/file-io/index.ts:2` is `import fs from "fs/promises"`, so the spec does `import fs from "node:fs/promises"` and `vi.spyOn(fs, "writeFile")` — the default-import form `tests/server/annotations/store.test.ts:10,123` already uses against the same target. Reject with `Object.assign(new Error("no space"), { code: "ENOSPC" })`.

1. **`atomicWrite`, partial write then failure.** The spy writes some bytes to `tempPath` and *then* rejects, so the cleanup has a real file to remove rather than passing vacuously. `atomicWrite` rejects with the original `ENOSPC` error, and `readdir` of the directory contains **no** entry matching the reaper's own regex — `import { ATOMIC_TEMP_RE } from "../../../src/server/file-io/reaper.js"` (already exported, `reaper.ts:39`) rather than re-typing it; a looser `startsWith(".tandem-tmp-")` check would still pass against a differently-named leak.
2. **Same for `atomicWriteBuffer`.** The discriminating one: a fix applied to `atomicWrite` alone leaves the binary path leaking `.docx` temps, the largest files Tandem writes.
3. **Unlink failure does not mask the write error:** spy `writeFile` → ENOSPC and `unlink` → EPERM; the rejection is still ENOSPC. Kills a `catch { await fs.unlink(tempPath); throw err; }` written without the `.catch`.
4. **Happy path unchanged:** a normal `atomicWrite` still lands the content and leaves no temp sibling. Kills a cleanup accidentally moved outside the catch.

## Done when

Both functions clean up their own temp sibling on a `writeFile` failure; the original errno propagates; the four specs green; `npm run typecheck` and the touched suites green.

## Review corrections (scope cut)

**Removed**

1. **The separate no-partial-write spec.** Merged into spec 1: writing bytes before rejecting is strictly stronger than a `writeFile` that created nothing, so two specs measured one thing.
2. **The rename-failure spec** (spy `rename` → non-EPERM, assert the existing unlink-and-rethrow still runs exactly once). It pins pre-existing behaviour this diff does not change; the "`try` wraps only `writeFile`" property is stated in §Fix and is visible in the four-line diff.

**Kept**

- Spec 2 (`atomicWriteBuffer`) — the half a partial fix silently leaves leaking `.docx` temps.
- `ATOMIC_TEMP_RE` imported rather than re-typed, and the `reaper.ts` comment amendment — the comment is a claim the same diff makes true, and leaving it false is what let #1850 sit unnoticed.
