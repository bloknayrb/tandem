# D1 — #1850 `atomicWrite` leaves an orphaned `.tandem-tmp-*` file when the temp-file write fails

Branch `fix/markdown-fidelity-1753`. Closes #1850. No area-ledger row of its own — found during review of PR #1849 (#1796); the same condition is the first `#1823` **server-data** bullet ("`atomicWrite` (`index.ts:349-364`) leaks the temp file on `writeFile` failure"), so this PR also `Refs #1823` (see `D1-1823.md`). Probe: none needed; the defect is a missing `catch` and is read directly off the source.

## Problem

`src/server/file-io/index.ts`:

```ts
export async function atomicWrite(filePath: string, content: string): Promise<void> {
  const tempPath = tempSiblingPath(filePath);
  await fs.writeFile(tempPath, content, "utf-8");     // <- no cleanup on failure
  await renameWithRetry(tempPath, filePath);
}
```
`atomicWriteBuffer` is byte-for-byte the same shape. If `fs.writeFile` fails partway — ENOSPC, EDQUOT, EIO — a partial `.tandem-tmp-<ms>-<12 hex>` file is left **in the user's document directory**, next to their real file, and the error propagates with the sibling still on disk.

Nothing cleans it up. The second half of `atomicWrite` already does this correctly: `renameWithRetry`'s failure arm is `await fs.unlink(tempPath).catch(() => {}); throw err;`. And the boot-time reaper deliberately never sweeps user document directories — `reapOrphanedTemps` covers the annotations + sessions dirs only, and CLAUDE.md's "Files, Sessions & Lifecycle" section states that as an invariant, so widening the reaper is not the fix. Every writer that goes through these two functions is affected: save, save-as, restore, convert, export, docx-apply, backups, the annotation store.

## Fix

Give the first half the same cleanup the second half already has, in both functions:

```ts
export async function atomicWrite(filePath: string, content: string): Promise<void> {
  const tempPath = tempSiblingPath(filePath);
  try {
    await fs.writeFile(tempPath, content, "utf-8");
  } catch (err) {
    // Mirror renameWithRetry's failure arm: a partial temp sibling in the
    // USER's document directory is never reaped (the boot reaper sweeps the
    // annotations + sessions dirs only). Swallow the unlink — the write error
    // is the one the caller must see (#1850).
    await fs.unlink(tempPath).catch(() => {});
    throw err;
  }
  await renameWithRetry(tempPath, filePath);
}
```
and the identical change in `atomicWriteBuffer`.

Four properties this shape has and a rewrite must keep: the **original** error is rethrown (an unlink failure must not mask ENOSPC); the unlink is `.catch(() => {})` because the temp file may legitimately not exist (an ENOSPC that failed before `open`); the `try` wraps **only** `writeFile`, so a `renameWithRetry` failure keeps taking its own existing path rather than being unlinked twice; and no retry or fallback is added — the caller's error contract is unchanged.

Rules that bite: no Y.Doc write, no Y.Map key, no MCP tool or `/api` route added, so neither license-gate half nor `NON_LOOPBACK_ALLOWED` is touched. No error code changes — the same rejection with the same `code` reaches `sendApiError`/`withErrorBoundary` — so `docs/mcp-tools.md`'s Errors lines are unchanged, and that claim is worth stating in the PR body because a reviewer will check it. **The file-watcher triple is untouched**: `recordSelfWrite` / `rearmWatch` are the callers' responsibility and none of them run on a throwing write today (they sit after the `await atomicWrite`), so this does not touch the site table pinned by `tests/server/document-write-rearm.test.ts`.

## Tests

New `tests/server/file-io/atomic-write-cleanup.test.ts` (no existing suite owns `atomicWrite` directly; the ~10 files that mention it all mock it). Use a real temp directory plus a `vi.spyOn(fs.promises, "writeFile")` that rejects with `Object.assign(new Error("no space"), { code: "ENOSPC" })` on the **first** call:

1. `atomicWrite` rejects with the original `ENOSPC` error (not the unlink's), and `readdir` of the directory contains **no** entry matching the reaper's own regex `^\.tandem-tmp-(\d+)-([0-9a-f]{12})$`. Reusing that exact regex is what makes the assertion honest — a test matching a looser `startsWith(".tandem-tmp-")` would still pass against a differently-named leak.
2. Same for `atomicWriteBuffer`. This is the discriminating one: a fix applied to `atomicWrite` alone leaves the binary path leaking `.docx` temps, which are the largest files Tandem writes.
3. **Partial-write case:** make the spy write some bytes to `tempPath` and *then* reject, so the cleanup has a real file to remove rather than passing vacuously against a `writeFile` that never created anything.
4. **Unlink failure does not mask the write error:** spy `writeFile` → ENOSPC and `unlink` → EPERM; the rejection is still ENOSPC. Kills a `try { … } catch { await fs.unlink(tempPath); throw err; }` written without the `.catch`.
5. **Happy path unchanged:** a normal `atomicWrite` still lands the content and leaves no temp sibling (kills a cleanup accidentally moved outside the catch).
6. **Rename-failure path unchanged:** spy `rename` to reject with a non-EPERM code; the existing unlink-and-rethrow still runs exactly once and no temp remains — this pins that the new `try` did not swallow or double-handle the second half.

## Done when

Both functions clean up their own temp sibling on a `writeFile` failure; the original errno propagates; the six specs green; `npm run typecheck` and the touched suites green.

## Not in scope

The boot reaper's directory set (deliberately narrow; see CLAUDE.md). Any change to `renameWithRetry`'s retry policy.
