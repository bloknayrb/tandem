## Problem

1. **Channel-error log injection (`src/server/mcp/channel-routes.ts:101-117`).** `message` is interpolated raw into `console.error` on both arms (`:108`, `:114`), and `String(error)` is too on the `UNKNOWN_CODE` arm — which logs the rejected value *before* the 400, directly contradicting the comment two lines above it ("Validate the code so a future caller can't smuggle a free-form string through unfiltered logs"). ESC/BEL/CR/LF and a full OSC-0 title sequence reach the operator's terminal verbatim, with no length bound. `POST /api/channel-error` is in `NON_LOOPBACK_ALLOWED` (`api-routes.ts:214-225`), so under a LAN bind any **bearer-authenticated** peer reaches it. The same shape sits at `:160` (`toolName`, `requestId`) and `:182` (`requestId`) on two more carved-out routes — but those two fields are `typeof … !== "string"`-guarded at `:147` and `:174`, so on those routes the hazard is control characters and length only. **`message` and `error` on `/api/channel-error` are unvalidated**, which is a second bug on top of the injection: `String(value)` **throws** for a JSON-craftable object. Measured in review round 1 — `node -e 'String(JSON.parse("{\"toString\":1,\"valueOf\":2}"))'` → `TypeError: Cannot convert object to primitive value`. A throw inside an `/api` handler registered on the **outer** app is not caught by any error handler this branch adds (see item 3), so it lands on Express's default HTML error page with absolute `node_modules` frames — the same disclosure item 3 closes, on a route item 3's handler structurally cannot reach.
2. **No `maxPayload` on Hocuspocus (`src/server/yjs/provider.ts:101-212`).** `startHocuspocus` calls `hocuspocusInstance.listen()` with no websocket options, so `Server`'s `new WebSocketServer({ noServer: true, ...websocketOptions })` takes ws's 100 MiB default. Measured in the issue: an *unauthenticated* peer's 90 MiB frame moved RSS 179→331 MB; 120 MiB closed 1009. Hocuspocus always binds `127.0.0.1` (`provider.ts:106`), so this is loopback-only. `events/wake-socket.ts:172` already caps its own socket at 1024 with a comment describing exactly this hazard — the in-repo precedent.
3. **413 ships an HTML stack trace with the install path (`src/server/mcp/server.ts:560`, `:761`), and it is NOT loopback-only.** Re-measured on `8924d54f` with a real server: a 200 kB `application/json` body to `POST /mcp` returns `413 text/html; charset=utf-8` whose `<pre>` is `PayloadTooLargeError: request entity too large` followed by absolute `C:\Users\…\node_modules\raw-body\index.js:163` frames. **Reach, corrected in review round 1:** `createMcpExpressApp` installs a bare `express.json()` at the sub-app root, and `app.use(mcpApp)` (`:761`) mounts that sub-app at the ROOT with no path prefix — above `registerApiRoutes` (`:764`) — so **every** `/api` body passes through the 100 kB parser too, not just `/mcp`. Verified with a standalone Express reproduction in this worktree: an over-limit `application/json` POST to a route registered on the *outer* app returns the same 413 that the sub-app's parser raised. Six `/api` routes are carved out of `enforceLoopbackMutation` in `NON_LOOPBACK_ALLOWED` (`api-routes.ts:214-225`), so under a Cowork LAN bind a **bearer-authenticated** LAN peer gets the operator's username and install path from the HTML page. That makes this a LAN information disclosure on those six, not a cosmetic loopback leak. (`app.use("/api", authMiddleware)` at `:707` runs before the mount, so a token is required; `finalhandler` emits `err.stack` whenever `NODE_ENV !== "production"`, which #1822 item 6 — K-sec-launcher's, unstarted — reports is the shipped sidecar's state.) **`docs/security.md:166` needs two edits, not one**: its citation `src/server/mcp/server.ts:517-547` now misses `largeBody` (`:549`) and `createMcpExpressApp` (`:560`); and its clause "`/api` file-open and upload get their own `express.json({ limit: \"70mb\" })` … So the effective ceiling on a given request is whichever parser it hit" is **false in effect** — the root-mounted 100 kB parser runs first and `express.json` no-ops once `req._body` is set, so the 70 MB parser never sets a ceiling (measured during planning: `POST /api/upload` at 50 kB → 200, at 300 kB → 413; filed as **#1981**, verified OPEN). The 50 MB sentence on that line is about `MAX_FILE_SIZE` and is correct.
4. **Item 7 — phantom 200s (`server.ts:851-857`).** The SPA fallback answers any unmatched path with `index.html`, byte-identical, so `/.git/HEAD` returns 200 without a file ever being read. `refuted.md:13` records the traversal claim itself as refuted. Bryan: *"returning index.html at a dotfile-shaped URL is not evidence that the requested file was read. No scanner-appeasement change is planned on that basis."*
5. **Item 8 — the dark license wire (`src/server/mcp/routes/license.ts:38-51`, `:88-97`).** While the gate is dark both wires emit `status: "licensed"` next to `gateActive: false`, and the LAN-scrubbed wire additionally carries `licenseInstalled` (`:95`).

## Fix

**Item 1 — `channel-routes.ts`.** Add one module-private helper plus an exported clamp constant, and use the helper at all five interpolation sites:

```ts
export const LOG_FIELD_MAX = 200;
function sanitizeForLog(value: unknown): string
```

The helper must be **total before it strips**, because two of its inputs are unvalidated request-body fields and `String(value)` throws on a JSON-craftable object (measured above):

```ts
let s: string;
try {
  s = typeof value === "string" ? value : String(value);
} catch {
  s = "[unstringifiable]";
}
```

Then strip **C0 including `\n`/`\r`/`\t`, C1 (`\x80-\x9f`), DEL, and the Trojan-Source bidi set** (`\u200e\u200f\u202a-\u202e\u2066-\u2069\u061c`), then clamp to `LOG_FIELD_MAX` characters with a `…` marker. Model: `stripControlChars` (`src/client/utils/diagnostics.ts:73`) and the clamp reasoning in `cli/doctor.ts:1150-1170`. **Three deliberate divergences to write into the comment:** it is *not imported* from `diagnostics.ts` because `src/server` imports nothing from `src/client` today (verified: zero such imports; the five greps that match are prose in comments); it strips `\x0a`, which `stripControlChars` deliberately preserves (`client-log.ts:138`) — a bare LF forges a second log line, which is the whole point here; and it is total, which `stripControlChars` (typed `(s: string)`) does not need to be. **Add a one-line back-reference comment above `stripControlChars` (`diagnostics.ts:73`) naming this server twin**, so a future change to the bidi set has a pointer to the other copy — the two sets will otherwise drift silently. Sites: `:108` (both `error` and `message`), `:114` (`message`), `:160` (`toolName`, `requestId`), `:182` (`requestId`). Keep the `UNKNOWN_CODE` log where it is — the diagnostic trail is the comment's stated intent; sanitizing is what makes the comment true. Rewrite that comment so it describes the sanitize-and-clamp rather than claiming the schema check alone prevents smuggling. **`NON_LOOPBACK_ALLOWED` does not change**; the carve-out is this finding's premise.

**Left with reason, and it must be said in the PR body:** `src/server/yjs/provider.ts:92` (`"…unparseable origin: %s", origin`) and `:96` (`` `…Rejected connection from origin: ${origin}` ``) interpolate an attacker-supplied `Origin` header into `console.error` with no strip and no clamp — the same class. Hocuspocus binds `127.0.0.1` unconditionally (`:106`), so they are loopback-only and strictly lower severity than item 1; item 2 already opens that file, so the decision to leave them is deliberate rather than unnoticed. Do not leave it unaddressed **and** unmentioned.

**Item 2 — `provider.ts`.** Add a module constant and pass it as `listen`'s **third positional argument**:

```ts
export const MAX_SYNC_PAYLOAD_BYTES = MAX_FILE_SIZE + 16 * 1024 * 1024; // 66 MiB
…
await hocuspocusInstance.listen(null, null, { maxPayload: MAX_SYNC_PAYLOAD_BYTES });
```

`MAX_FILE_SIZE` comes from `src/shared/constants.ts:155` (50 MB) — **do not add a new constant to `shared/constants.ts`**; import the existing one. The ceiling is derived, not round, because a cap below a real document's sync is a data-loss bug strictly worse than the DoS it prevents. **The safety argument has two parts, and review round 1 replaced the load-bearing one**, because the first is headroom evidence rather than a proof of the maximum:

- **Structural (this is the one that holds).** `maxPayload` bounds **inbound** frames only — `WebSocketServer` passes `this.options.maxPayload` to the receiver it builds for each socket; server→client messages are unbounded. On the inbound leg the repo has **no client-side Yjs persistence** (`grep -rn "IndexeddbPersistence\|y-indexeddb" src/ package.json` returns nothing), so a browser's `syncStep2` on first connect is empty and everything after it is an incremental update carrying only what that client typed or pasted. No legitimate inbound frame is sized by the document, only by the edit.
- **Headroom (evidence, not a bound).** Measured during planning with `yjs` in this worktree, and to be recorded in the PR body as a sizing table: Yjs encodes a fresh document at **1.08×** its **extracted text length** (100 kB → 107,923 B; 10 MB → 10,842,841 B), a char-by-char-typed document at **1.00×**, and 500 annotation records carrying a 200-char body, a 200-char `textSnapshot` and a 120-char `relRange` at **299,712 B**. **State the basis as extracted text length, never as file size** — the two are not the same number, see the residual.

**Residual, and it must be measured rather than asserted absent.** `MAX_FILE_SIZE` gates **bytes on disk** (`documents/open.ts:718`, `stat.size > MAX_FILE_SIZE`) or **uploaded bytes** (`:568`, `Buffer.byteLength`). `.docx` is a ZIP, so a 50 MB `.docx` can carry far more than 50 MB of extracted text, and `MAX_FILE_SIZE × 1.08` is not its worst case. The reachable failure is one client-origin transaction that inserts more than the cap's worth of text in a single frame (a bulk paste or source-view commit on such a room); ws answers 1009 at the frame header and the hocuspocus provider reconnects and re-sends, so the symptom is a wedged sync loop on a document that opened fine, not a dropped message. **Measure it:** synthesize a `document.xml` of N MB of representative prose, deflate it into a `.docx` container, and record `extracted text bytes ÷ zip bytes`. If `ratio × MAX_FILE_SIZE > MAX_SYNC_PAYLOAD_BYTES`, **file one issue** for it (title naming extracted-text expansion versus `MAX_FILE_SIZE`) and state the number in the PR body; if it does not, state the measured ratio in the PR body and nothing more. Either way the PR body says which, because the spec's own standard is that a cap below a real document's sync is worse than the DoS.

ws enforces the cap at the **frame header** — `node_modules/ws/lib/receiver.js:437-450` (`haveLength`) rejects on the declared `_payloadLength` before any payload is accumulated — so the rejection is structurally before Hocuspocus's `onAuthenticate`, which is what the issue asks for. `listen`'s signature is `(portOrCallback = null, callback = null, websocketOptions = {})` and `typeof null !== "number"`, so the port already set in the constructor config survives; the options reach `new Server(this, websocketOptions)` → `new WebSocketServer({ noServer: true, ...websocketOptions })`. **Per Bryan: no connection-count ceiling** — so the PR body must also say that this closes the per-frame bound only: N concurrent connections at just under the cap each remain unbounded, by decision, and #1822 item 2 is therefore not fully mitigated.

**Item 3 — `server.ts`.** Register a four-argument JSON error handler on **`mcpApp`**, immediately after the three `mcpApp.*("/mcp", …)` route definitions (the last ends at `:667`; register before the `app.use(mcpApp)` mount at `:761`). Verified by a standalone Express reproduction in review round 1 that this placement (a) converts the over-limit 413 to JSON with no stack, (b) leaves normal `/mcp` routing at 200, (c) leaves the outer app's SPA fallthrough intact, and (d) **also answers body-parse errors for `/api` routes**, because the parser that raises them is the sub-app's — an error thrown inside a mounted sub-app is offered to that sub-app's own error handlers before the parent's `finalhandler`. Reproduction output, to paste into the PR body:

```
/mcp        413 application/json  {"handled":"sub","code":"entity.too.large"}
/api/x      413 application/json  {"handled":"sub","code":"entity.too.large"}
/api/throws 500 text/html         <!DOCTYPE html>…<pre>Error: boom-in-outer-handler
```

The third line is the bound: a throw inside an `/api` **route handler** on the outer app is past the sub-app's stack and still reaches `finalhandler`, which is why item 1's helper has to be total rather than relying on this handler.

Shape: bail to `next(err)` when `res.headersSent`; use `err.status` when it is a number, else 500. **Branch the body on `err.type`, and on the path**, because one envelope for three cases is wrong in two of them:

- `req.path === "/mcp"` → a JSON-RPC envelope, which is the shape every other `/mcp` error on this server already uses (`sendJsonRpcError`, `server.ts:301`, called at `:592` and `:620`) and what `src/cli/mcp-stdio.ts` parses: `{"jsonrpc":"2.0","error":{"code":-32600,"message":"Request body exceeds this endpoint's size limit."},"id":null}`.
- otherwise `err.type === "entity.too.large"` → `{ error: "PAYLOAD_TOO_LARGE", message: "Request body exceeds this endpoint's size limit." }`.
- otherwise `err.type === "entity.parse.failed"` → `{ error: "BAD_REQUEST", message: "Request body is not valid JSON." }` — a malformed body is the caller's input, not an internal error, and this handler now sees `/api` parse failures too.
- otherwise → `{ error: "INTERNAL_ERROR", message: "Request could not be processed." }`.

**No `err.message` and no `err.stack` on the wire**, in any branch. The static copy deliberately names the *limit* rather than saying nothing, so the live #1981 bug stays diagnosable from the wire after the HTML page (which at least said `PayloadTooLargeError`) is gone; none of these strings contains a path. **The blast radius is `/api` as well as `/mcp`, and that must be stated in the PR body** so E2-upgrade — which owns `api-routes.ts` and is running concurrently — is not surprised by `/api` body-parse errors changing shape without its file being edited.

Also edit `docs/security.md:166`: update the citation from `src/server/mcp/server.ts:517-547` to the range that actually holds both parsers; add one clause saying an over-limit body is answered with a JSON 413 carrying no stack; and **add one clause recording that the 70 MB parser is shadowed** — the SDK sub-app's `express.json()` is mounted at the root above `registerApiRoutes`, so the measured effective ceiling on every `/api` body today is 100 kB (#1981). **Do not "fix" the 50 MB sentence — it is about `MAX_FILE_SIZE` and is already correct.** The 70 MB clause is the one this group has itself disproved, and leaving it unqualified on a line this PR edits is the stale-register drift class the sweep exists to close.

**Item 4 (issue item 7) — no code change.** The analysis and the reason are the deliverable. A 404 rule narrow enough to be safe cannot be written from the shape of the path: the SPA fallback is what serves every client route, and any route containing a dot — which is every deep link to a document whose id or name carries one — is indistinguishable from `/.git/HEAD` by pattern alone. Nothing is disclosed either way (`refuted.md:13`). Bryan's triage already records the disposition; this spec records the mechanism so the next reviewer does not re-derive it. **Post it as a comment on #1822 at ship time AND put the same reasoning verbatim in the PR body** — the comment step is manual and nothing enforces it, so the PR body is the copy that cannot be skipped.

**Item 5 (issue item 8) — no code change; both halves are recommendations to Bryan.** The sweep's own rule is that security-policy items always go to him (`docs/plans/2026-09-06-open-issues-sweep.md:30`), and both halves are behaviour changes inside a system that ships dark.

So the issue's premise — "any consumer that forgets `gateActive`" — describes zero consumers today. Against that, three costs: the sentinel is documented at `routes/license.ts:22-28` as existing so an **older** client or Tauri shell talking to a newer sidecar stays byte-identical; `CLAUDE.md` requires the gate to stay byte-identical while dark; and `"inactive"` is not in `LicenseStatus` (`license/license-types.ts:31`) or in `LicenseStatusResponse["status"]` (`client/utils/license-ui.ts:15`), so it is a type change in two languages plus Rust's `Option<String>`. **Effect at the flip, which is the fact that settles it:** the sentinel lives only on the `!state.gateActive` arm, and that arm is unreachable once `LICENSE_GATE_ENABLED` flips — so changing it buys nothing after the flip and risks the dark window before it. Recommend to Bryan rather than change; listed under `bryan`.
- **`licenseInstalled` on the LAN-scrubbed wire: recommend removal, do not remove it here.** Round 1 found the planned rationale to be a non-sequitur and the change to contradict a sibling spec, so it is routed to Bryan with both facts rather than shipped as code. The honest statement of the exposure: the field reports **the host's** purchase state, and `app.use("/api", authMiddleware)` (`server.ts:707`) means the only caller who can read it already holds a token the operator issued — so it is one bit to an authenticated peer, not an open leak. The cost of removing it is named in the code itself (`routes/license.ts:42-47`): without it "a dark build has no way to tell a user their activation worked… the hint keeps saying 'activate it now' whether or not they just did. The README sends every beta user down exactly that path" — and `license.ts:115` explicitly names the LAN caller as supported, so a Cowork user reading Settings from a LAN browser is exactly who loses the confirmation. **`H-c-1789.md:168` in this same review already recorded `licenseInstalled` as "documented deliberate"**, so removing it here would have put two specs in the same review in contradiction. Both facts and that cross-reference go in the PR body under `bryan`, alongside the `status` recommendation. **If Bryan approves the removal**, it is two lines — delete `licenseInstalled: darkInstallInfo().installed` from `scrubForNonLoopback`'s dark arm (`routes/license.ts:95`) and the field from that function's return type (`:86`), leaving `toLicenseStatusWire` (`:48`) untouched because `handleGetLicenseStatus` branches on `isLoopback(req.socket.remoteAddress)` (`:143`) and that is the arm the desktop shell and a same-machine browser get — plus amending `tests/server/license-status-route.test.ts:263` and updating the `:42-47` comment to say the confirmation is loopback-only. **Critical Rule 9 does not bite either way** — this route reads, mutates nothing, and its row in `tests/server/license-gate-api-coverage.test.ts` is unchanged.
