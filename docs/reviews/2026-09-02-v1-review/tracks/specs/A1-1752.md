# A1 — #1752 `validateRange` accepts out-of-bounds, mid-surrogate, zero-length and fractional offsets

Branch `fix/validate-range-bounds-1752`. Closes #1752; post a verdict on #1823 for its `tandem_getContext` item (fixed here). Ledger: `docs/reviews/2026-09-02-v1-review/areas/{server-mcp,crdt}.md`.
Probes: `docs/reviews/2026-09-02-v1-review/experiments/exp2.ts` (surrogate), `probe-tools.mts:67` (edit(6, 99999), negative from, fractional). `exp8.ts` is #1751, not this.

## Problem

`validateRange` (`src/server/positions.ts:110-172`) checks only `from > to`, snapshot staleness, and optional heading overlap. Out-of-bounds offsets are not rejected: `resolveToElement` (`src/shared/positions/ydoc.ts:364-373`) clamps any offset past the end to the last element's end and returns non-null, and a negative `from` clamps `textOffset` to 0 (`:348-351`). So `tandem_edit(6, 99999)` deletes to end of document and reports `edited: true`; a negative `from` edits from 0. Non-integers pass through (`String.slice` truncates). `from === to` passes. An offset between the halves of a surrogate pair passes, and the edit writes U+FFFD on both sides.

## Fix — input validation at the boundary, not a coordinate-system change

The clamp in `resolveToElement` stays: `refreshRange` sits on it with stored offsets (`positions.ts:243-244,263-264`) and changing it is track B (#1764/#1767). Do not change `ydoc.ts` behaviour.

**The bound is the length of the one string the checks slice — never a second walk.** A fragment walk modelled on `resolveToElement` (separator on child index) disagrees with `extractText` (separator on an `emitted` element counter, `document-model.ts:296-305`) whenever a non-element top-level child exists; `flatDocLength` (`document-model.ts:358-370`, already the bounds primitive for `tandem_editList` at `document.ts:836`) is the existing Y.Doc-only length. No new length helper.

1. **Pure function** in `src/server/positions.ts`: `validateFlatRange(text: string, from: number, to: number, opts?: { allowEmpty?: boolean }): RangeValidation`. Order: integer (`Number.isInteger` both; rejects NaN/Infinity/fractions) → ordering `from > to` → lower bound `from < 0` → upper bound `to > text.length` (`to === text.length` valid) → empty `from === to` unless `allowEmpty` → surrogate. **The surrogate predicate is the PAIRED form only:** reject at `i` iff `charCodeAt(i-1)` ∈ D800–DBFF AND `charCodeAt(i)` ∈ DC00–DFFF, for `i = from` (when `from > 0`) and `i = to`. A one-sided "unit at `i` is any surrogate" check passes every `"a😀b"` case and then rejects the legal boundary between two adjacent astral characters, which has no alternative offset; the `"😀😀"` control below kills it. At `to === text.length`, `charCodeAt` is NaN — accepted; pin it.
2. **`validateRange(ydoc, from, to, opts)` order:** integer → ordering → `from < 0` → staleness (`textSnapshot`; may return `RANGE_MOVED`/`RANGE_GONE`, unchanged) → upper bound, empty, surrogate on the caller's coordinates → heading overlap (unchanged).
   - Lower bound BEFORE staleness: `String.prototype.slice` wraps a negative start (`"hello world".slice(-3, 11) === "rld"`), so a negative `from` with a coincidentally matching snapshot would pass staleness, and a non-matching one would be answered with a relocation instead of `out-of-bounds`. Neither the watcher nor `tandem_edit` produces a negative or fractional `from`, so steps 1–3 cannot mask a relocation.
   - Upper bound AFTER staleness: after an external edit shortens the file, the watcher's relocation probe (`documents/watcher.ts:245-256`) passes stale offsets past the new end with a snapshot and relies on `RANGE_MOVED`; bounds-first would return `INVALID_RANGE` and pin the annotation to dead offsets — silent annotation loss. Same for `tandem_edit` with a correct `textSnapshot` (`docs/mcp-tools.md:266` documents the retry path).
   - The surrogate check applies only to the range about to be returned `ok`; relocated coordinates are re-checked on the caller's retry.
   - Two accidents to pin, not redesign: the staleness gate is truthiness-checked (`if (opts?.textSnapshot)`), so `""` skips it — do not change to `!== undefined`; and with a snapshot `from === to` never reaches `"empty"` (the slice is `""`, staleness fires first) — build the `"empty"` case WITHOUT a snapshot.
3. **One materialization.** `validateRange` computes `extractText(ydoc)` once and uses it for staleness, bounds and surrogate. Today it materializes only when a snapshot is given (`:130-131`); making it unconditional adds a full-document walk to `stampClaudeRange` (`document.ts:368`), `local-model/tools.ts:204`, `document-store.anchorRange`, `tutorial-annotations.ts:70` and `ctrl-chat.ts:40` — ~3.5 ms at 460 KB per `flatDocLength`'s own docstring. Accepted; say so in the PR body. Opts gain `allowEmpty?: boolean`, `text?: string` ("must equal `extractText(ydoc)` at this call; lets a loop hoist one extraction") and `surrogates?: "reject" | "ignore"` (default `"reject"`; see the export/capture callers). **Two guards on `text`, one of them in production:** (a) always, `opts.text.length !== flatDocLength(ydoc)` → `console.error` + recompute — `flatDocLength` (`document-model.ts:358-370`) builds no string (a tree walk reading `child.length`), so this costs no materialization, though it is still a walk per call and the hoist buys one string build per loop, not one walk. **It is a smoke alarm, not a contract**: it catches only a length-CHANGING mutation; a same-length string (a same-length edit, or a sibling document of equal length) passes it and silently changes the staleness and surrogate verdicts in production. That is why the hoisted-`text` list below is restricted to genuine loops over an unchanging document, and why (b) exists: under `process.env.VITEST === "true"` — NOT `NODE_ENV` (precedent `src/server/integrations/api-routes.ts:193-200`; `launcher/supervisor.ts:745-749` uses `NODE_ENV` with a second belt-and-braces condition for the same reason: a tsup-built server started without `NODE_ENV` evaluates `!== "production"` as true) — additionally assert `text === extractText(ydoc)`. ## Review corrections (rounds 1–4)

**Implementation round 2 (supersedes §3's `text` guard).** §3 above still specifies the two-guard shape — an always-on `text.length !== flatDocLength(ydoc)` plus a `process.env.VITEST === "true"` string equality — and argues it from "`flatDocLength` builds no string". That shape shipped and was replaced twice; read this line, not §3, for what is in the tree.

The VITEST half was removed because a guard that runs only under tests is a test that self-heals: production compared lengths alone, so no spec could ever be red for the production behaviour. Its first replacement was an UNCONDITIONAL `extractText` content compare, which was correct and inverted the option's purpose — a caller passing `text` then cost more than one omitting it, rebuilding the whole projection per loop iteration. What is in the tree now is the length walk alone, unconditional and not test-gated, with the sufficiency argument stated as a SCOPED claim: the five hoist callers write only `Y_MAP_AUTHORSHIP` / `Y_MAP_ANNOTATIONS` between hoist and use, never the `default` fragment, so the only staleness the guard can meet is structural and a structural change moves the length. A same-length in-place text edit mid-loop would slip past; no hoist caller produces one, and `resolveDocText` says so rather than claiming completeness.

Two corrections to §3's own reasoning, measured rather than argued. `flatDocLength` does build no string, but it is only ~13% cheaper per call than `extractText` (5.49 ms vs 5.66 ms on a 1500-block / 125 KB document): both are dominated by the Y.js tree traversal, not the concatenation, so what the guard actually removes is the per-iteration allocation. And the hoist loops were never linear — `resolveToElement` and `flatOffsetToRelPos` each walk the fragment per call, so `stampClaudeAuthorshipWholeDoc` is O(blocks²) in tree walks and always was (17.0 s → 14.7 s across this change, median of 5, on a noisy box). The hoist is worth having; it is not what makes that loop expensive.
