# W13g — #2005 `docs/security.md`'s #1654 bound still says `docx-apply.ts` folds `INVALID_PATH` onto `FORMAT_ERROR`

Branch `fix/docs-and-test-tooling-drift-2005`. Closes #2005. No track file (non-review issue — not
part of the v1-review 84-issue set, so no ledger row and no per-area experiment). No MCP probe:

## Problem

`docs/security.md:474`, inside the `#1654` ("Accepted (bounded)") entry's "What an MCP caller
sees" paragraph, currently reads (in part):

> `docx-apply.ts` still folds `INVALID_PATH` onto `FORMAT_ERROR` and remains the live instance of
> this trap.

That was true when written. It no longer is: the K-server MCP-surface PR removed the fold.
`tandem_applyChanges`'s handler (`src/server/mcp/docx-apply.ts:508`) now maps a core
`INVALID_PATH` throw 1:1 — `if (e.code === "INVALID_PATH") return mcpError("INVALID_PATH",
e.message);` — and the code's own comment at `:505-507` records why ("It was FORMAT_ERROR, which
is not what either condition is."). `tandem_restoreBackup`'s handler (`:625-627`) does the same
for `BACKUP_SYMLINK` / `BACKUP_NOT_A_FILE` / `INVALID_PATH`. Verified directly against
`src/server/mcp/docx-apply.ts` in this worktree — both arms are present on current `master`.

So the sentence describes a trap the code no longer has. Per the issue body, `docs/security.md`
belongs to a different concurrently-running group (K-sec-launcher), so the PR that fixed the code
did not edit the doc, and no test pins the sentence — a `tests/` grep for it finds nothing, so
nothing catches the drift on its own. `tests/docs/security-findings-claims.test.ts` only pins the
`#1654` entry's *opening* clause (the first 240 characters of its top-level bullet, per its own
`entryOpenings()` helper) against `CLAUDE.md`'s count/enumeration; it never reads this deep
paragraph, so correcting the paragraph cannot break that test.

## Fix

Rewrite the second half of `docs/security.md:474`'s "What an MCP caller sees" paragraph. The
model is the paragraph's own first sentence, which already states the identical fact correctly for
`tandem_exportAnnotations` and `tandem_convertToMarkdown`. Replace:

> `docx-apply.ts` still folds `INVALID_PATH` onto `FORMAT_ERROR` and remains the live instance of
> this trap.

with a sentence naming `tandem_applyChanges` alongside the two the first sentence already covers,
per the issue's own instruction ("rewrite the sentence so all three MCP handlers —
`tandem_exportAnnotations`, `tandem_convertToMarkdown`, `tandem_applyChanges` — are listed as
surfacing `INVALID_PATH` intact"), e.g.:

> `tandem_applyChanges` (`docx-apply.ts:508`, #1823) now does the same: its `INVALID_PATH` throws
> map 1:1 to `mcpError("INVALID_PATH", ...)` rather than folding onto `FORMAT_ERROR`.
> `tandem_exportAnnotations`, `tandem_convertToMarkdown` and `tandem_applyChanges` all now surface
> `INVALID_PATH` intact.

(Exact prose is the implementer's call; the content requirement is: no live "folds `INVALID_PATH`
onto `FORMAT_ERROR`" claim survives, and the three named tools are listed as surfacing
`INVALID_PATH` intact. **Do not write "all three MCP handlers that take a caller-supplied path"**
— `tandem_restoreBackup` (`docx-apply.ts:619-627`) also takes a caller-supplied `backupPath` and
also maps `INVALID_PATH` 1:1, so that universal quantifier is false the moment it's written in a
register whose whole value is that its claims are checkable; enumerate the three by name without
quantifying. Separately, this sentence sits ~19 lines above the entry's own "Four sites take a
caller-supplied write path" bullet — the three named here are the MCP-reachable subset of those
four, since Save-As (the fourth) has no MCP verb; the existing entry already explains that, so no
new sentence is needed, just avoid a phrasing that reads as contradicting it.)

Leave the following sentence — "`PathRejectedError` (`apply.ts:284-293`) carries no `.code`, so a
naive catch chain lets it escape as a 500." — as-is in *substance*, per the issue's own
instruction ("re-verify it on its own. This issue makes no claim about it"): re-verified against
`src/server/integrations/apply.ts` in this worktree — `PathRejectedError` still has no `.code`
field, only `.path` and `.reason`, so the claim holds.

**Two bundled tangential fixes, in the same edit** (CLAUDE.md: "if you find something broken while
working, fix it rather than filing it" — this project is two people, scope gates are minimal):

   Correct that one citation too, to `apply.ts:327-336`, leaving the rest of that dated historical

Do not touch the `#1654` entry's opening bullet line (the `- **[#1654]...**` line, ~115 characters,
