# Gc2b — #1775 The slash-command menu opens inside code blocks; Enter then converts the block or deletes text

Branch `fix/keyboard-and-a11y-1777`. **Closes #1775.** Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:20` (High, `[ran] Reproduced`). Probe: `docs/reviews/2026-09-02-v1-review/experiments/harness/a-bugs.test.ts` and the same directory's `e-keys.test.ts` case `E1` (repo-relative — there is no `experiments/` at the repo root) — `/e` + Enter inside a code block converts it to a paragraph, `cd /t` + Enter deletes text. Also verified in a real browser (`docs/reviews/2026-09-02-v1-review/raw/verify-client.txt`).

## Problem

`resolveActiveSlashCommand` (`src/client/editor/slash-menu/extension.ts`) gates on `isSlashMenuSuppressed()` and `selection.empty`, then reads `$from.parent.textBetween(0, $from.parentOffset, …)` and matches. It never asks what kind of block the caret is in. `suppression.ts` is DOM-presence probes only (find bar focused, command palette mounted, selection-popup testids present) — it cannot see document structure, so it is the wrong layer for this.

Consequence: any `/` inside a code block — a path, a regex, a URL, a comment — opens the `Slash commands` listbox offering Paragraph, Heading 1, …, Horizontal rule. The plugin's `handleKeyDown` then claims Enter (`event.preventDefault(); return executeSlashCommand(editor, active)`), so the keystroke the user meant as a newline runs a block conversion instead, deleting the matched `/query` text on the way.

## Fix

One guard, in `resolveActiveSlashCommand`, immediately after `const $from = selection.$from;` and before the `textBetween` read:

```ts
// A "/" inside a code block is literal text (a path, a regex, a URL) and Enter
// there means a newline, not a block conversion. Same exemption
// `PlaintextBreaksExtension#splitInsteadOfBreak` uses, for the same reason.
if ($from.parent.type.spec.code) return null;
```

The precedent is `src/client/editor/extensions/plaintext-breaks.ts`, which already declines on `this.editor.state.selection.$from.parent.type.spec.code` and whose comment states the rule ("a newline typed inside one is genuinely a newline and the node stores it literally"). `spec.code` rather than a `type.name === "codeBlock"` comparison, so any future code-ish node inherits it.

Placing the guard in the **resolver** rather than in `handleKeyDown` is what makes the Enter half impossible: the resolver is the single entry point for both initial activation and every subsequent keystroke (its own comment says so), so `active` is never non-null inside a code block and the plugin's `Enter` / `ArrowUp` / `ArrowDown` / `Escape` branches are unreachable there. A guard at the Enter branch alone would still flash the menu open.

Nothing here touches `$state`, Y.Doc writes, `data-testid` selectors or the suppression list.

**One user-facing sentence goes stale and is fixed in the same commit.** `docs/user-guide.md:76` reads "…it stays out of the way while the find bar, command palette, or an annotation popup is open." Append `, or when the caret is inside a code block` before the closing period. Nothing reads that line — `tests/docs/slash-menu-guide-claims.test.ts` parses only the command/alias enumeration in the paragraph above — so it would otherwise drift unread.

## Tests

`tests/client/slash-menu-code-block.test.ts` (new, `@vitest-environment happy-dom`) — the harness `E1` cases with the assertions **inverted**, using a real Tiptap `Editor` built from `buildSchemaExtensions()` + `SlashCommandExtension` exactly as `experiments/harness/e-keys.test.ts` does:

1. `content: "<pre><code>echo hi\n</code></pre>"`, caret at the end, `insertContent("/")` then `"e"` → `slashCommandPluginKey.getState(editor.state)?.active` is `null`. Kills the fix-at-the-Enter-branch variant, which leaves `active` set.
2. Same setup, then dispatch a `keydown` `{key:"Enter"}` on `editor.view.dom` → `editor.getHTML()` still contains `<pre>` and the code block's text still **contains** `echo hi`. **Do not assert strict equality with the pre-Enter text**: with the slash plugin declining, ProseMirror's base `Enter` chain reaches `newlineInCode` and appends a literal newline — which is the correct post-fix behaviour and what the user asked for.
3. `content: "<pre><code>cd </code></pre>"`, type `/t`, Enter → the code block's text still **contains** `cd /t` (again, a trailing newline is expected, not a failure). The space-then-slash shape is a distinct `findSlashCommandMatch` path from case 1.
4. **Discriminating positive:** the same `/e` typed in a plain paragraph still activates (`active` non-null with `query === "e"`). Without it, `return null` at the top of the resolver passes every negative case and disables the feature entirely.

## Not in scope

Inline `code` **marks**: `spec.code` is a node-spec property, so the guard is deliberately blind to them — inside an inline `code` run the caret is still in a paragraph, Enter there is a genuine block-level Enter and `newlineInCode` would not fire, so the menu keeps working. Widening to `$from.marks()` is a separate product call. Also out: `suppression.ts`'s DOM-probe design and its `POPUP_TESTIDS` list; the `isTypedInsertionAtCaret` open-gating logic (#998); the slash menu's ARIA/listbox shape; anything in `commands.ts`.
