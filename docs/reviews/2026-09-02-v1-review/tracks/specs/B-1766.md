# B — #1766 Critical Rule 6 is endpoint-only: a range spanning a heading prefix passes and can delete the heading

Branch `fix/annotation-anchors-1764`. Closes #1766 (both halves: the spanning range, and documenting the exclusive-end asymmetry). Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:21`. Probe: `experiments/crdt-verify.ts`, the `validateRange(4, 9)` section.

## Problem

`validateRange`'s heading gate (`src/server/positions.ts:493-502`) resolves **only the two endpoints** and rejects when either lands inside a heading prefix:

```
if (startPos.clampedFromPrefix || endPos.clampedFromPrefix) return { ok: false, code: "HEADING_OVERLAP" };
```

On `"para\n## Head\nnext"` both `validateRange(4, 9)` and `(0, 9)` pass with `rejectHeadingOverlap: true`, because neither endpoint sits inside `"## "` even though the interior contains all of it. `tandem_edit(4, 13, "X")` on `"Para one\n## Head\nTail"` produces `"ParaXead\nTail"` — the heading is gone. That is exactly what Critical Rule 6 exists to prevent.

The related asymmetry is real and is not a bug: `to` equal to the *first* character of a heading prefix is rejected, even though the end is exclusive, because `resolveToElement(to)` lands at offset 0 of the heading and reports `clampedFromPrefix`. It is simply undocumented.

**`rejectHeadingOverlap` is not `tandem_edit`-only, and that governs the whole shape of this fix.** There are three callers, measured:

| Caller | Site | What it does with a range |
|---|---|---|
| `tandem_edit` | `src/server/mcp/document.ts:755-758` (`validateRange`) | **Rewrites document text** |
| `tandem_comment` / `tandem_suggest` | `src/server/mcp/annotations.ts:311` → `YDocStore.anchorRange` (`src/server/mcp/document-store.ts:283-289`, whose docblock says "**`rejectHeadingOverlap` is unconditional and is NOT a parameter**") | Creates an annotation; writes no text |
| local-model anchor resolution | `src/server/local-model/tools.ts:204` (`anchoredRange`) | Creates an annotation; writes no text |

`src/server/annotations/lifecycle.ts:407-409` states the same inventory, and `tests/server/mcp-tool-integration.test.ts:431` pins that `tandem_comment` enforces the endpoint rule today.

So ORing an interior scan into the shared `rejectHeadingOverlap` term would **newly refuse annotation creation across a heading**: on `"Intro para\n## Section\nBody text"`, `tandem_comment` over `[0, 25]` — a comment about a whole section — succeeds today and would answer `INVALID_RANGE` with the message "Target the text content only", advice a multi-section comment cannot follow. Critical Rule 6 is about *editing* heading markup; annotating across a heading is legal and stays legal.

## Fix

Add an interior scan behind its **own** option, passed only by `tandem_edit`; keep the endpoint check exactly as it is, so the exclusive-end behaviour does not change and annotation creation is untouched.

- **`src/shared/positions/ydoc.ts`** — next to `resolveToElement`, which owns this walk today:
  `export function rangeOverlapsHeadingPrefix(fragment: Y.XmlFragment, from: FlatOffset, to: FlatOffset): boolean`. Walk the fragment's direct children accumulating flat offsets with **the same arithmetic `resolveToElement` uses**. Two details of that arithmetic are load-bearing and a re-implementation drifts on the second one:
  - each element contributes `prefixLen + textLen` (`getHeadingPrefixLength` + `getElementTextLength`);
  - **a non-`Y.XmlElement` child must consume no separator.** In `resolveToElement` (`ydoc.ts:340-362`) the `\n` is added per child INDEX under `i < fragment.length - 1`, but a non-element child hits `continue` **before** that line — the same rule `extractTextWithBreaks` states as "one separator between *emitted* elements" (`mcp/document-model.ts:298-300`). A walker that drops the `continue` and lets a stray text node earn a separator shifts every later element's `blockStart` by one and puts the predicate's heading window one unit off. Mirror the loop shape, `continue` included, rather than re-deriving it.
  - **Do not chase the `[el, el, text]` accumulator difference — it cannot reach this predicate.** `resolveToElement` adds a separator after the element at index `fragment.length - 2` even when the last child is not an element, where an elements-only walker adds none; but that difference lives in the accumulator **past the last element**, and `rangeOverlapsHeadingPrefix` only ever reads element `blockStart`s. Worked through: on `[el, el, text]` the second element's `blockStart` is `len0 + 1` under both walkers and under `extractText`. The hazard is the `continue`, above; this is not a second one.

  For each element with `getHeadingPrefixLength(node) > 0`, its prefix occupies `[blockStart, blockStart + prefixLen)`; return `true` on the standard half-open overlap `blockStart < to && blockStart + prefixLen > from`. Same file as the resolver on purpose: a fifth independent walker over the separator contract is how the existing four would drift, and CLAUDE.md records that heading prefixes are **top-level only**, so a top-level walk is complete.
- **`src/server/positions.ts`** — a **new, separate** option on `RangeValidationOpts`:
  `rejectHeadingInterior?: boolean`. Inside the existing `if (rejectHeadingOverlap)` block, after the `startPos`/`endPos` resolution and the `unresolvable` arm, keep `startPos.clampedFromPrefix || endPos.clampedFromPrefix` exactly as it is and OR in `(opts?.rejectHeadingInterior === true && rangeOverlapsHeadingPrefix(fragment, from, to))`. Two reasons for the union rather than a replacement: the overlap predicate alone would newly *accept* `to === blockStart`, silently relaxing behaviour `tandem_edit` callers and `tests/server/local-model/tools.test.ts` depend on; and the endpoint rule must stay the rule for the two annotation-creation callers.
- **`src/server/mcp/document.ts:755-758`** — the one call site that gains `rejectHeadingInterior: true`. `YDocStore.anchorRange` and `local-model/tools.ts:204` are **not** changed and keep the endpoint-only rule.
- **Nothing about the check order moves.** CLAUDE.md Critical Rule 4 puts heading overlap last, after emptiness — so an empty range inside a prefix still answers `empty` without `allowEmpty` and `HEADING_OVERLAP` with it. This spec adds a term to the last check, not a new position in the sequence.
- **`skills/tandem/SKILL.md`** — line 182 currently reads "With **no** `reason` the cause is heading markup (e.g. `## `) or a pattern that was not found — target text content only, not the heading prefix." After this change a `tandem_edit` whose *interior* spans a heading also answers `HEADING_OVERLAP` with no `reason`, and the caller has already targeted text content only — the same "advice no tool could follow" failure `src/server/mcp/document.ts:806-830` calls out for the nested-block case. Amend the line to say that for `tandem_edit` a range whose start, end **or interior** overlaps a heading prefix is refused, and the remedy is to split the edit at the heading — and that annotation tools refuse only the endpoints, so a comment may still span one. **Bump the frontmatter `version` to the next integer above `origin/master` (currently 17 ⇒ 18) and update BOTH pinned literals in `tests/skill-instruction-contract.test.ts` in the same commit** (CLAUDE.md: a stale rule in the shipped skill is a product bug). There are two, and naming only the first turns `check` — a required status check with `enforce_admins: true` — red, so the PR cannot merge:
  1. `:83` — `expect(skill).toMatch(/^version:\s*17$/m)`, the version regex;
  2. `:335` — `.toEqual({ version: "17", bodyHash: "4e3cdecc0e7a" })` in the `#1790` "reds on a body-only skill edit" spec, whose own failure message says to "update BOTH literals here in the same commit". `bodyHash` is the first 12 hex of the sha256 of everything **after** the frontmatter's closing `---`, with CRLF normalised to LF first; recompute it from the edited file, do not hand-edit it.

## Assumptions

- **The interior rule is `tandem_edit`'s, not `validateRange`'s.** Measured from the three-caller table above. Widening the shared flag would refuse a comment spanning a section, which is legal today and has no alternative phrasing the caller could follow.
- **The exclusive-end asymmetry is documented, not removed.** The issue calls it "undocumented", not wrong, and relaxing it would let `tandem_edit` delete the newline separating a paragraph from the heading below it.
- **Top-level scan only.** A nested heading contributes no prefix (`resolveToTextblock`'s documented contract), so descending would find nothing and would need a fifth copy of the separator arithmetic.
- **The predicate is a boolean, not a position.** No caller needs to know *which* heading; returning one would invite a message that names it and a second consumer.

## Not in scope

`YDocStore.anchorRange` and `local-model/tools.ts:204` gaining the interior term — see the caller table; they create annotations and write no text. The `HEADING_OVERLAP` wire code itself (its `tandem_edit` message text is in scope; the code is not). Heading prefixes inside list items or table cells, which do not exist in this model.
