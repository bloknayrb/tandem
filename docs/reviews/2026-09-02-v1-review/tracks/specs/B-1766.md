# B — #1766 Critical Rule 6 is endpoint-only: a range spanning a heading prefix passes and can delete the heading

Branch `fix/annotation-anchors-1764`. Closes #1766 (both halves: the spanning range, and documenting the exclusive-end asymmetry). Ledger: `docs/reviews/2026-09-02-v1-review/areas/crdt.md:21`. Probe: `experiments/crdt-verify.ts`, the `validateRange(4, 9)` section.

## Problem

`validateRange`'s heading gate (`src/server/positions.ts`) resolves **only the two endpoints** and rejects when either lands inside a heading prefix:

```
if (startPos.clampedFromPrefix || endPos.clampedFromPrefix) return { ok: false, code: "HEADING_OVERLAP" };
```

On `"para\n## Head\nnext"` both `validateRange(4, 9)` and `(0, 9)` pass with `rejectHeadingOverlap: true`, because neither endpoint sits inside `"## "` even though the interior contains all of it. `tandem_edit(4, 13, "X")` on `"Para one\n## Head\nTail"` produces `"ParaXead\nTail"` — the heading is gone. That is exactly what Critical Rule 6 exists to prevent.

The related asymmetry is real and is not a bug: `to` equal to the *first* character of a heading prefix is rejected, even though the end is exclusive, because `resolveToElement(to)` lands at offset 0 of the heading and reports `clampedFromPrefix`. It is simply undocumented.

## Fix

Add an interior scan; keep the endpoint check exactly as it is, so the exclusive-end behaviour does not change.

- **`src/shared/positions/ydoc.ts`** — next to `resolveToElement`, which owns this walk today:
  `export function rangeOverlapsHeadingPrefix(fragment: Y.XmlFragment, from: FlatOffset, to: FlatOffset): boolean`. Walk the fragment's direct children accumulating flat offsets with **the same arithmetic `resolveToElement` uses** (`prefixLen + textLen`, plus one `\n` separator between siblings — mirroring `collectElementFlat`'s separator contract). For each element with `getHeadingPrefixLength(node) > 0`, its prefix occupies `[blockStart, blockStart + prefixLen)`; return `true` on the standard half-open overlap `blockStart < to && blockStart + prefixLen > from`. Same file as the resolver on purpose: a fifth independent walker over the separator contract is how the existing four would drift, and CLAUDE.md records that heading prefixes are **top-level only**, so a top-level walk is complete.
- **`src/server/positions.ts`** — inside the existing `if (rejectHeadingOverlap)` block, after the `startPos`/`endPos` resolution and the `unresolvable` arm, keep `startPos.clampedFromPrefix || endPos.clampedFromPrefix` and OR in `rangeOverlapsHeadingPrefix(fragment, from, to)`. The union is deliberate: the overlap predicate alone would newly *accept* `to === blockStart`, silently relaxing behaviour that `tandem_edit` callers and `tests/server/local-model/tools.test.ts` depend on.
- **Nothing about the check order moves.** CLAUDE.md Critical Rule 4 puts heading overlap last, after emptiness — so an empty range inside a prefix still answers `empty` without `allowEmpty` and `HEADING_OVERLAP` with it. This spec adds a term to the last check, not a new position in the sequence.
- **`CLAUDE.md` Critical Rule 6** — "A range whose **start, end or interior** overlaps a heading prefix (e.g. `## `) returns INVALID_RANGE."
- **`docs/architecture.md`** coordinate-systems section (currently "start or end inside a prefix") — same widening, plus one sentence on the exclusive end: a `to` equal to the first character of a heading prefix is rejected, because the exclusive end still resolves into the heading block.
- **`docs/mcp-tools.md`** — the `tandem_edit` heading line gains the same two facts.

## Tests

1. `tests/server/positions.test.ts` — on `"para\n## Head\nnext"`, `validateRange(off(4), off(9), { rejectHeadingOverlap: true })` and `(off(0), off(9), …)` both return `HEADING_OVERLAP`. The issue's two measured cases; kills the endpoint-only check.
2. Same file — the **deletion** the issue read but did not run: on `"Para one\n## Head\nTail"`, `tandem_edit(4, 13, "X")` is refused rather than producing `"ParaXead\nTail"`. Drive it through the tool (`tests/server/document-edit.test.ts` if the harness there is cheaper) so the test covers the wiring, not just the predicate — `tandem_edit` is the only caller that matters.
3. Same file — **negatives that must stay green**: a range entirely inside one heading's *text* (after the prefix) is accepted; a range spanning two ordinary paragraphs with no heading between them is accepted; a range ending exactly at the last character before a heading's prefix (`to === blockStart`) is still **rejected**, pinning the documented asymmetry rather than relaxing it. Without the third, an implementation that replaces the endpoint check with the overlap predicate passes everything else and silently changes behaviour.
4. Same file — a range starting inside a heading's prefix and ending inside the same heading's text is still `HEADING_OVERLAP` (the endpoint arm alone already did this; pins that the OR did not reorder anything).
5. Same file — the existing `rejectHeadingOverlap: false` spec still accepts a prefix range, and the existing `"unresolvable"` spec still reports `unresolvable` rather than the new overlap verdict. The scan must not run ahead of the resolver's `null` arm.
6. `tests/docs/` — no new pin. Critical Rule 6 has no source-pinned test today and adding one is the kind of drift guard this sweep is not building.

## Done when

`crdt-verify.ts`'s `validateRange(4, 9)` section reports `HEADING_OVERLAP`; the specs above pass; Critical Rule 6, `docs/architecture.md` and `docs/mcp-tools.md` all say "start, end or interior" and document the exclusive end; typecheck + suite green.

## Assumptions

- **The exclusive-end asymmetry is documented, not removed.** The issue calls it "undocumented", not wrong, and relaxing it would let `tandem_edit` delete the newline separating a paragraph from the heading below it.
- **Top-level scan only.** A nested heading contributes no prefix (`resolveToTextblock`'s documented contract), so descending would find nothing and would need a fifth copy of the separator arithmetic.
- **The predicate is a boolean, not a position.** No caller needs to know *which* heading; returning one would invite a message that names it and a second consumer.

## Not in scope

`tandem_comment` / `tandem_suggest` gaining `rejectHeadingOverlap` (they deliberately do not pass it — annotating a heading is legal). The `HEADING_OVERLAP` wire code and its message. Heading prefixes inside list items or table cells, which do not exist in this model.
