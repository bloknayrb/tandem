## Problem

The mechanism is established and is not re-derived here: `build_updater`'s `.endpoints()` **replaces** the manifest list rather than falling back, so a licensed install whose `LICENSE_KV` entry is gone gets a 204, `tauri-plugin-updater` early-returns `Ok(None)`, and the app says "You're up to date" forever while starved. `docs/licensing-operations.md:250-252` lists five ways in: a failed KV write, a refund (`applyRefund` deletes the entitlement while the blob still verifies forever), the §7 revocation procedure, KV eviction, and a namespace-id mismatch between the two `wrangler.toml` files.

`CLAUDE.md:244`, `docs/licensing-explained.md:514`, `docs/licensing-operations.md:252-253` and `docs/security.md:181` **all four** call the Worker's `reason` enum the only detector. It is not a detector:

- **Nothing retains it.** `infra/license-update-worker/src/worker.ts:147` is a bare `console.log`; neither `wrangler.toml` has an `[observability]` block, so the lines are kept nowhere. The only reader is `wrangler tail`, which the runbook itself (§5c) calls "a debugging tool, not an alert: no history, no thresholds, no notification, and it dies with the terminal session."
- **Nothing notifies.** The update Worker has no `ALERT_*` wiring at all. The issuance Worker has the whole plumbing (`isAlertable` / `shouldAlert` / `alertBody` / `sendOperatorAlert`, `worker.ts:845-945`); the update Worker got none of it.

**A detector is something that reaches a human without a user reporting it.** Retention alone is not one either — it makes the evidence readable after someone already suspects. Both halves are needed.

**Two things the round-1 draft got wrong, both measured, both changing the design.**

1. **`unknown-id` is NOT "structurally zero in health".** Two of the five named causes are *intended operations* that produce it forever. `applyRefund` (`infra/license-issuance-worker/src/worker.ts:434`) does `entitlementKv.delete(rec.licenseId)` while the offline blob still verifies, and §7's revocation procedure deletes the same key by hand. After H-a, `update_route` step 4 (`src-tauri/src/lib.rs:2455-2459`, comment: *"Regardless of `update_window_current`"*) returns `Licensed(id)` whenever `probe.license_id` is present, so a refunded or revoked install keeps sending `X-Tandem-License-Id` on **every** update check for the life of the blob, in every new isolate, indefinitely. A channel that pages on every refund gets muted, and a muted detector detects nothing — the issue's own thesis. The draft excluded `expired` for exactly this reason ("would otherwise be paged for on every out-of-window customer, forever") and then failed to notice that refund and revocation are the same shape.
2. **`unknown-id` is reachable by any unauthenticated caller.** `infra/license-update-worker/src/worker.ts:97-101` reads the header and does one KV `get` — no signature, no secret, no allowlist, no shape check — and `wrangler.toml:16-18` leaves `[[routes]]` commented out, so the Worker is served on a public `*.workers.dev` host. Contrast the issuance Worker, whose only alertable `dropped` result sits behind `verifyStandardWebhook`. Scanner traffic would page the operator on a healthy system, and a low-rate flood holds the 5-minute per-isolate throttle slot and **suppresses the genuine event** — defeating the detector this issue exists to build.

**What H-a already did, and must not be rebuilt.** H-a (#1785) added `UpdateRoute::NoUpdates(WithheldReason)` and `show_update_withheld_dialog`, covering the cases the *device itself* can see: restricted, and an unreachable loopback probe. Its own spec hands over the residue explicitly: *"a `Licensed` device whose Worker-side entitlement has lapsed receives a 204 from the Worker and is still told 'up to date'. The client genuinely cannot distinguish that."* That is this issue's case, and it is the Worker's to detect.

**The issue's client-side suggestion is not implementable as written, and I am saying so rather than half-building it.** It asks the licensed app to "record the last successful licensed check and warn after N days without one". There is no such observable: `updater.check()` collapses a 204 (no entitlement) and a 200 whose manifest is not newer (perfect health, no release this week) into the same `Ok(None)` — the plugin exposes neither status nor headers. Distinguishing them needs the app to issue its own parallel request to the endpoint, i.e. a second updater. The remaining client surface named in the issue — the Settings warning keyed on local `updateWindowCurrent` (`SettingsLicenseTab.svelte`) — is license UX copy and belongs to **H-c (#1789 #1819)**, which runs concurrently and owns those components. So this group fixes the Worker halves and records both boundaries.

## Fix

### Make deliberate removal distinguishable from loss

This is the change that makes the detector a detector rather than a pager. **A refund and a revocation are the operator's own action; an entitlement that vanished is not.** Today both look identical from the update Worker, because both are an absent key.

- **`infra/license-issuance-worker/src/worker.ts` `applyRefund` (`:433-438`) writes a tombstone instead of deleting.** Replace `await deps.entitlementKv.delete(rec.licenseId)` with a `put` of `{"updateWindowEnd": null, "status": "revoked"}` (`KvNamespace` at `:86` already has both methods; the mint path at `:391` uses `put`). The offline run-license is unaffected — it was always perpetual by design, and the update entitlement is still gone.
- **`infra/license-update-worker/src/worker.ts` gains a `"revoked"` member of `NoUpdateReason`** and returns it when `entry.status === "revoked"`. **Placement is load-bearing: the check goes immediately after the JSON parse and BEFORE the `updateWindowEnd` comparison.** The `Entitlement` interface (`:72-76`) already carries an optional `status`, and `null updateWindowEnd` currently means *never expires (grandfathered)* — so a tombstone read by the window branch would **serve the manifest to a refunded customer.** Say that in the comment; it is the one way this change can go wrong.
- **`"revoked"` is deliberately NOT alertable.** It is the operator's own action, recorded and readable, and paging on it is what mutes the channel.
- **`docs/licensing-operations.md` §7** — the revocation procedure changes from `wrangler kv key delete` to a `wrangler kv key put` of the same tombstone, with one sentence saying why: a deleted key is indistinguishable from a lost one and fires the §3c alert on every subsequent check by that install, forever.

### The retention half

- **`infra/license-update-worker/wrangler.toml`** — add `[observability]` / `enabled = true`, and a commented `# ALERT_WEBHOOK_URL = "REPLACE_WITH_INCOMING_WEBHOOK_URL"` under `[vars]` with the same wording as the issuance toml's `:32-40` block, plus the sentence that this Worker's alert is the *only* automatic detector of a licence issued without an entitlement. **Add a comment on the var in both tomls** that an incoming-webhook URL is a bearer credential and `wrangler secret put ALERT_WEBHOOK_URL` is the safer form; `[vars]` is kept only to match the issuance precedent, and the choice is now written down rather than inherited.
- **`infra/license-issuance-worker/wrangler.toml`** — add the same `[observability]` block. One line; the issue asks for both files.
- **Say what retention costs.** The update Worker's header (`:11-16`) records a deliberate invariant: the log line carries no license id, because per-customer update-check logs would be telemetry. Workers Logs retains an **invocation record** alongside each line — URL, method, colo, outcome — not request headers, so the id still never lands. Put that sentence in the §3c and §5c doc edits, not only in a code comment: `docs/security.md`'s "no telemetry" claim is a statement about what Tandem records, and this change moves that line.

### The notification half

- **`infra/license-update-worker/src/worker.ts`** — mirror the issuance Worker's alert plumbing rather than inventing a shape. The two Workers are separate Cloudflare builds with no shared module (the issuance one imports only `./crypto.js`), so this is a **deliberate duplication, not an oversight** — say so in a comment where the copy starts.
  - Add the local `ExecutionContext` interface (copy the issuance file's convention) and widen `export default { fetch }` to `(request, env, ctx?)`. `ctx` optional, so the two-arg test harness still calls it.
  - `WorkerEnv` gains `ALERT_WEBHOOK_URL?: string`. **No `ALERT_EMAIL` here** — this Worker has no Resend binding, and adding one would give the update endpoint a reason to hold a mail secret it otherwise never needs.
  - `export function isAlertable(entry: LogEntry): boolean` → `entry.reason === "unknown-id" || entry.reason === "unparseable"`. **Enumerated, and the other four are the discriminating half:** `no-header` is an ordinary unlicensed client; `expired` is expected and benign (the Worker is working correctly); `revoked` is the operator's own action; `upstream` is a GitHub-side blip that would alert-storm. `unparseable` joins `unknown-id` because it is the same family — an entry we wrote that we can no longer read — and is likewise impossible in a healthy system.
  - **Alertability has a second precondition, outside `isAlertable`: the id must be one this system could have minted.** Ids come from `globalThis.crypto.randomUUID()` (issuance `worker.ts:1006`), so the `fetch` wiring alerts only when the received header matches `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`. `isAlertable` stays reason-only (it is the exported, unit-testable predicate); the shape gate lives at the call site, where the raw header is in scope. **The id itself never enters the alert body**, so the privacy pin is unaffected. Anything non-UUID still logs `unknown-id` — the noise is retained, it just never pages.
  - **Record the residual explicitly**, in that comment and in §5c: a UUID-shaped flood still reaches the channel and still consumes the throttle slot. The endpoint is unauthenticated by design (it must answer any updater), so this is a bound, not a hole — but it is the one an operator needs to know when a genuine `unknown-id` fails to arrive. Do not add a KV counter for it; that is new stateful mechanism on a stateless Worker for less detection, not more.
  - `alertBody(entry)` carries `reason` and a pointer to the repair (`re-PUT the entitlement from the ledger`, `docs/licensing-operations.md §3`) and **nothing else**. Spell the citation in full — `tests/build/invariant-citations.test.ts:47` scans `infra`, and a bare or parenthesised `§3` is flagged as dangling.
  - `shouldAlert(key, nowMs)` + `ALERT_THROTTLE_MS = 5 * 60 * 1000` + `_resetAlertThrottleForTests()`, copied verbatim from the issuance file's `:845-866` including its comment about isolates being short-lived.
  - `sendOperatorAlert(env, entry)` posts `{text: body}` to `ALERT_WEBHOOK_URL`; a non-ok response counts as a failure (a retired Slack webhook 404s rather than throwing); when the channel is absent or exhausted, log `{result: "alert-undeliverable", ts, reason}` so the consumed throttle slot leaves a trace.
  - Wire it in the `fetch` `log` callback — **not inside `handleUpdateRequest`**, which stays pure and I/O-injected — and hand the promise to `ctx.waitUntil` with `.catch(() => {})`. **An alert must never delay or fail the request it reports on, and must never change the response bytes**: the no-existence-oracle invariant in this file's header is the reason the 204 is byte-identical across all reasons, and `revoked` joins them unchanged.
- **Alert on occurrence, throttled — not on a rate.** The issue says "keyed on `unknown-id` rate". With the tombstone above, `unknown-id` means *an entitlement we did not remove is gone* — genuinely abnormal — while an unlicensed client lands on `no-header` and, after H-a, a restricted device issues no request at all. A rate threshold could only add a way to miss the first one, and rate state on a stateless Worker means a KV counter. Recorded as an assumption, together with the flood residual above.

## Tests

All in `tests/server/license-update-worker.test.ts`, extending the existing `no-update reasons (the silent-failure detector)` suite (`:189`). `beforeEach(_resetAlertThrottleForTests)` — the issuance suite's own comment records that without it the second test to provoke a given key is silently suppressed and every "does not alert" assertion passes vacuously. **Every test that asserts on `console.log` or on `fetch` captures `ctx.waitUntil`'s argument and `await`s it first**, except item 7's no-channel case, which is the one that happens to be synchronous (no `await` is reached before the `alert-undeliverable` line).

1. **`isAlertable` truth table.** True for `unknown-id` and `unparseable`; **false for `no-header`, `expired`, `revoked`, `upstream` and `{result:"served"}`**. The false rows kill both an alert-on-every-no-update (which would fire on every unlicensed client) and an alert-on-nothing.
2. **Wiring, through `default.fetch`.** A request with an unknown **UUID-shaped** id, env carrying `ALERT_WEBHOOK_URL`, a stubbed global `fetch`: exactly one POST to the webhook URL; body contains `unknown-id`; **body does NOT contain the license id that was sent**. The negative is the privacy pin — it kills an alert body that echoes the header.
3. **A non-UUID id logs but does not page.** `X-Tandem-License-Id: not-a-uuid` → status 204, the log line still reads `unknown-id`, and **zero webhook POSTs**. This is the anti-flood pin; without it, alerting is wired to input any internet caller controls.
4. **The response is unchanged by alerting.** Status 204, `await res.text()` empty, and byte-identical to the same request with no `ALERT_WEBHOOK_URL`.
5. **The alert is off the response path, provably.** `ctx.waitUntil` called exactly once with a promise — **and** a webhook stub that never settles must still let `default.fetch` resolve with 204 while `fetchMock` holds one pending call. The `waitUntil`-count assertion alone is satisfied by an implementation that sends inline and hands over an already-settled promise; the pending-stub half is what kills an `await`ed alert.
6. **A failing alert channel cannot fail the request.** Webhook `fetch` rejects, then a variant where it resolves 404: both still return 204.
7. **Throttle.** Two unknown-id requests in one isolate → one webhook POST. Then `_resetAlertThrottleForTests()` and a third → two.
8. **No channel configured → no alert fetch, and an `alert-undeliverable` log line.** Kills silently burning the throttle slot with no trace.
9. **`expired` does not alert** even though it is a no-update — the case an operator would otherwise be paged for on every out-of-window customer, forever.
10. **The tombstone, both halves.** In `tests/server/license-issuance-worker.test.ts`: a refund leaves `LICENSE_KV` holding `{updateWindowEnd: null, status: "revoked"}` for that licenseId rather than an absent key. In `license-update-worker.test.ts`: that exact value → **204 with reason `revoked` and no alert**, and — the discriminating assertion — **not** a served manifest. A `revoked` check placed after the window comparison serves `null updateWindowEnd` as grandfathered, so this row is what pins the ordering.
