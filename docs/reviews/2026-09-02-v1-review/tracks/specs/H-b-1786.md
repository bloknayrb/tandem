## Problem

The mechanism is established and is not re-derived here: `build_updater`'s `.endpoints()` **replaces** the manifest list rather than falling back, so a licensed install whose `LICENSE_KV` entry is gone gets a 204, `tauri-plugin-updater` early-returns `Ok(None)`, and the app says "You're up to date" forever while starved. `docs/licensing-operations.md:250-252` lists five ways in: a failed KV write, a refund (`applyRefund` deletes the entitlement while the blob still verifies forever), the §7 revocation procedure, KV eviction, and a namespace-id mismatch between the two `wrangler.toml` files.

`CLAUDE.md:244`, `docs/licensing-explained.md:514-515`, `docs/licensing-operations.md:252-253`, `docs/security.md:181` **and — the fifth, found in round 2 — `infra/license-update-worker/src/worker.ts:23-30`, the docblock of the very type being changed** all call the Worker's `reason` enum the only detector. It is not a detector:

- **Nothing retains it.** `infra/license-update-worker/src/worker.ts:147` is a bare `console.log`; neither `wrangler.toml` has an `[observability]` block, so the lines are kept nowhere. The only reader is `wrangler tail`, which the runbook itself (§5c) calls "a debugging tool, not an alert: no history, no thresholds, no notification, and it dies with the terminal session."
- **Nothing notifies.** The update Worker has no `ALERT_*` wiring at all. The issuance Worker has the whole plumbing (`isAlertable` / `shouldAlert` / `alertBody` / `sendOperatorAlert`, `worker.ts:845-945`); the update Worker got none of it.

**A detector is something that reaches a human without a user reporting it.** Retention alone is not one either — it makes the evidence readable after someone already suspects. Both halves are needed.

**Two things the round-1 draft got wrong, both measured, both changing the design.**

1. **`unknown-id` is NOT "structurally zero in health".** Two of the five named causes are *intended operations* that produce it forever. `applyRefund` (`infra/license-issuance-worker/src/worker.ts:434`) does `entitlementKv.delete(rec.licenseId)` while the offline blob still verifies, and §7's revocation procedure deletes the same key by hand. After H-a, `update_route` step 4 (`src-tauri/src/lib.rs:2455-2459`, comment: *"Regardless of `update_window_current`"*) returns `Licensed(id)` whenever `probe.license_id` is present, so a refunded or revoked install keeps sending `X-Tandem-License-Id` on **every** update check for the life of the blob, in every new isolate, indefinitely. A channel that pages on every refund gets muted, and a muted detector detects nothing — the issue's own thesis. The draft excluded `expired` for exactly this reason ("would otherwise be paged for on every out-of-window customer, forever") and then failed to notice that refund and revocation are the same shape.
2. **`unknown-id` is reachable by any unauthenticated caller.** `infra/license-update-worker/src/worker.ts:97-101` reads the header and does one KV `get` — no signature, no secret, no allowlist, no shape check — and `wrangler.toml:16-18` leaves `[[routes]]` commented out, so the Worker is served on a public `*.workers.dev` host. Contrast the issuance Worker, whose only alertable `dropped` result sits behind `verifyStandardWebhook`. Scanner traffic would page the operator on a healthy system, and a low-rate flood holds the 5-minute per-isolate throttle slot and **suppresses the genuine event** — defeating the detector this issue exists to build.

**What H-a already did, and must not be rebuilt.** H-a (#1785) added `UpdateRoute::NoUpdates(WithheldReason)` and `show_update_withheld_dialog`, covering the cases the *device itself* can see: restricted, and an unreachable loopback probe. Its own spec hands over the residue explicitly: *"a `Licensed` device whose Worker-side entitlement has lapsed receives a 204 from the Worker and is still told 'up to date'. The client genuinely cannot distinguish that."* That is this issue's case, and it is the Worker's to detect.

**The issue's client-side suggestion is not implementable as written, and I am saying so rather than half-building it.** It asks the licensed app to "record the last successful licensed check and warn after N days without one". There is no such observable: `updater.check()` collapses a 204 (no entitlement) and a 200 whose manifest is not newer (perfect health, no release this week) into the same `Ok(None)` — the plugin exposes neither status nor headers. Distinguishing them needs the app to issue its own parallel request to the endpoint, i.e. a second updater. The remaining client surface named in the issue — the Settings warning keyed on local `updateWindowCurrent` (`SettingsLicenseTab.svelte`) — is license UX copy and belongs to **H-c (#1789 #1819)**, which runs concurrently and owns those components. So this group fixes the Worker halves and records both boundaries.

## Fix

### Make deliberate removal distinguishable from loss

This is the change that makes the detector a detector rather than a pager. **A refund and a revocation are the operator's own action; an entitlement that vanished is not.** Today both look identical from the update Worker, because both are an absent key.

- **`infra/license-issuance-worker/src/worker.ts` `applyRefund` (`:433-438`) writes a tombstone instead of deleting.** Replace `await deps.entitlementKv.delete(rec.licenseId)` with a `put` of `{"updateWindowEnd": null, "status": "revoked"}` (`KvNamespace` at `:86` already has both methods; the mint path at `:391` uses `put`). The offline run-license is unaffected — it was always perpetual by design, and the update entitlement is still gone. **`applyRefund`'s own docblock (`:429-432`) says "delete its entitlement"** and goes stale with the code — rewrite it in the same edit.
  **The guard is unchanged and the `put` sits INSIDE it.** The line is `if (!deps.isTest && rec.licenseId) await deps.entitlementKv.delete(rec.licenseId);` — describing this as a bare `delete`→`put` swap invites a literal reading that lifts the write out. `rec.licenseId` is `""` on the refund-before-paid tombstone path (`worker.ts:477-481`), which is exactly what that half of the guard skips, and `!deps.isTest` is what keeps a sandbox run out of the real namespace. **Add the matching assertion to the *refund that outraces the paid event* case (`tests/server/license-issuance-worker.test.ts:686`)**, whose `expect(entitlementKv.map.size).toBe(0)` is the only thing that would catch a tombstone written under an empty key.
  **Commit placement, decided in round 3: this bullet ships in the #1793 commit, not this one.** `H-b-1793.md` § Tests items 6/6b/7 assert the tombstone's *value*, and implementation order is #1793 → #1786, so leaving the `put` here makes that commit knowingly red against its own suite — misleading a per-commit review or a `git bisect`. So the `delete`→`put`, its docblock, the shared `REVOKED_ENTITLEMENT` literal and the **seven** issuance-suite assertion rewrites enumerated below travel with #1793; **this** commit carries the update Worker, the docs, the `wrangler.toml` blocks and the update-worker tests. `H-b-1793.md` records the reciprocal. No commit in the branch is red against its own tests.
- **Seven existing assertions in `tests/server/license-issuance-worker.test.ts` change with it, and they are named here rather than discovered by CI** — the same standard `H-b-1793.md` applies to `:1173`/`:1264`. `baseDeps` sets `isTest: false` (`:137`), so the write really happens under test and every one of these reads the post-refund key:
  - **Five read it as ABSENT and must become the tombstone's exact parsed VALUE** — `expect(JSON.parse(deps.entitlementKv.map.get(licenseId) as string)).toEqual({updateWindowEnd: null, status: "revoked"})` — at `:617` (*"revoked"*), `:652` (the confirmed-refund arm of the ambiguous test), `:664` and `:669` (*"NOT resurrected"*, the H2 pin) and `:780` (*"revoked, not orphaned"*, the concurrent-mint race). **Never `toBeDefined()`.** `:669` and `:780` are semantic pins whose obvious repair — swapping `toBeUndefined()` for `toBeDefined()` — passes equally for a resurrected **live** entitlement, which deletes the thing each exists to catch.
  - **Two already read it as PRESENT and stop discriminating** — `:626` (*"NOT revoked"*, the explicit `refunded:false` H1 case) and `:640` (*"NOT revoked on a guess"*, the ambiguous-field case). After the tombstone a revoked entitlement is *also* `toBeDefined()`, so both must be strengthened to assert the **live** value (`status: "personal"`, a non-null `updateWindowEnd`). That is precisely the ambiguous-`refunded` safety property `H-b-1793.md` § Problem item 2 is about, and it is the half a `toBeDefined()` sweep would silently hollow out.
  - **`H-b-1793.md` § Tests items 6 and 7 are written against this same value, not against absence** — implementation order is #1793 → #1786 inside one branch, so an absence assertion there is green when written and red when this lands. That cross-reference is recorded in both specs.
- **`infra/license-update-worker/src/worker.ts` gains a `"revoked"` member of `NoUpdateReason`** — which makes **four in-file comments wrong in the same file, and one of them is a FIFTH copy of the "only detector" claim the § Problem section says there are four of.** All four change in this edit: `:20-21` (*"All **five** reasons return identical bytes"* → six), `:23-30` (*"It is the single detector for the worst failure mode… A rising `unknown-id` count is the only evidence…"* — the in-code copy, which needs the same alert-and-precondition rewrite as the four docs), `:35` (*"THE alert-worthy one"* on `unknown-id`, now that `unparseable` is alertable too), and `:90-91` (*"byte-identical across all five branches"*). It returns `revoked` when `entry.status === "revoked"`. **Placement is load-bearing: the check goes immediately after the JSON parse and BEFORE the `updateWindowEnd` comparison.** The `Entitlement` interface (`:72-76`) already carries an optional `status`, and `null updateWindowEnd` currently means *never expires (grandfathered)* — so a tombstone read by the window branch would **serve the manifest to a refunded customer.** Say that in the comment; it is the one way this change can go wrong.
- **`"revoked"` is deliberately NOT alertable.** It is the operator's own action, recorded and readable, and paging on it is what mutes the channel.
- **The tombstone is NOT a `LicenseEntitlement`, and that must be written down where the lockstep claim lives — otherwise the drift is silent.** `src/server/license/license-types.ts:107-111` types `status` as `LicenseMetadata["type"]` (`"personal" | "commercial" | "grandfathered"`) and requires `version: string`; its docblock at `:100-106` calls it the *"Canonical shape shared by the REST writer"* with a *"structurally-identical local copy kept in lockstep by a parity test"*, and `infra/license-update-worker/src/worker.ts:66-76` repeats the claim from the reader side. `{updateWindowEnd: null, status: "revoked"}` is a value neither the canonical type nor `writeLicenseEntitlement` can produce, and the parity test (`tests/server/license-update-worker.test.ts:162-179`) types its fixture as `LicenseEntitlement`, so a tombstone typed the same way would not compile. Nothing goes red today — the Worker's local `status?: string` tolerates it — which is exactly why this is a spec bullet rather than something CI will catch. **Do it as documentation plus one shared literal, not by widening the canonical type:** amend both docblocks to say the namespace now holds **entitlements AND revocation tombstones**, that the tombstone is deliberately not a `LicenseEntitlement` (the writer never mints one; only `applyRefund` and the §7/§9 hand-run `kv key put` do), and name it `RevokedEntitlement` in the prose so the two shapes have distinct names. Then make the three copies one value — **and note that round 2's "the same **string** in three places" is not implementable as written**: `applyRefund` writes a TS object through `JSON.stringify`, the Worker's `revoked` fixture is a TS literal, and `docs/licensing-operations.md:602` will hold a shell-quoted `'{"updateWindowEnd":null,"status":"revoked"}'`. A literal string equality across those three forms is either impossible or degrades into a brittle source-text substring match. **Instead: export one constant `REVOKED_ENTITLEMENT` from `infra/license-issuance-worker/src/worker.ts`**, have `applyRefund` and the update-worker test fixture both use it, and assert `JSON.parse(<the JSON literal extracted from the §9 runbook line>)` `toEqual(REVOKED_ENTITLEMENT)`. **Compare parsed values, never strings** — key order and whitespace differ between a hand-written runbook line and `JSON.stringify` output, so a string comparison fails on formatting while missing a genuine key change.
  Widening `LicenseEntitlement["status"]` to `| "revoked"` was considered and rejected: it would make a tombstone assignable everywhere a live entitlement is expected, including `writeLicenseEntitlement`'s parameter, which is the one place it must never be constructible.
- **Every `wrangler` invocation this spec adds is spelled `wrangler@4.130.0`.** `H-b-1793.md`'s new zero-match assertion sweeps five files — both READMEs, the runbook **and both `wrangler.toml` comment blocks** — for `/\bwrangler(?!@4\.130\.0\b)(@\S+)?\s+(deploy|secret|kv|tail|dev|versions|types|login|whoami)\b/`. Both change.

### The notification half

- **`infra/license-update-worker/src/worker.ts`** — mirror the issuance Worker's alert plumbing rather than inventing a shape. The two Workers are separate Cloudflare builds with no shared module (the issuance one imports only `./crypto.js`), so this is a **deliberate duplication, not an oversight** — say so in a comment where the copy starts.
  - Add the local `ExecutionContext` interface (copy the issuance file's convention) and widen `export default { fetch }` to `(request, env, ctx?)`. `ctx` optional, so the two-arg test harness still calls it.
  - `WorkerEnv` gains `ALERT_WEBHOOK_URL?: string`. **No `ALERT_EMAIL` here** — this Worker has no Resend binding, and adding one would give the update endpoint a reason to hold a mail secret it otherwise never needs.
  - `export function isAlertable(entry: LogEntry): boolean` → `entry.reason === "unknown-id" || entry.reason === "unparseable"`. **Enumerated, and the other four are the discriminating half:** `no-header` is an ordinary unlicensed client; `expired` is expected and benign (the Worker is working correctly); `revoked` is the operator's own action; `upstream` is a GitHub-side blip that would alert-storm. `unparseable` joins `unknown-id` because it is the same family — an entry we wrote that we can no longer read — and is likewise impossible in a healthy system.
  - **Alertability has a second precondition, outside `isAlertable`: the id must be one this system could have minted.** **There are two mint sites and the shape gate must cite both**, or a future non-UUID id from the second silently drops its whole cohort out of alerting: the issuance Worker's `globalThis.crypto.randomUUID()` (**`worker.ts:1012`** — round 2 cited `:1006`, which is `entitlementKv: env.LICENSE_KV,`; re-resolved) and the out-of-band writer `scripts/sign-license.ts:142` (`crypto.randomUUID()`). Both are UUIDs today, so the gate is correct. **The round-2 justification for naming the second was wrong and is corrected here:** it called that the *"most failure-prone"* entitlement write, citing `docs/licensing-operations.md:84-90` as saying `writeLicenseEntitlement` *"never throws"*. Measured, that passage says the opposite — *"Without them the script prints the key and then **exits non-zero** — deliberately… Do not deliver a key the script refused to entitle"* — a loud refusal, and the phrase "never throws" appears nowhere in the runbook or in `src/server/license/`. The real property, and the one to write in the comment: the script fails **loudly** on missing KV credentials, and `--skip-entitlement` is the one documented way a key ships un-entitled. The design is unaffected either way — the shape gate covers both mint sites regardless — but the justification would have read as settled once it was in a code comment. So the comment names both sites (with the corrected line number and the corrected property) and adds one sentence: any future id generator must stay UUID-shaped or the alert stops covering it. The `fetch` wiring alerts only when the received header matches `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`. `isAlertable` stays reason-only (it is the exported, unit-testable predicate); the shape gate lives at the call site, where the raw header is in scope. **The id itself never enters the alert body**, so the privacy pin is unaffected. Anything non-UUID still logs `unknown-id` — the noise is retained, it just never pages.
  - **Record the residual explicitly**, in that comment and in §5c: a UUID-shaped flood still reaches the channel and still consumes the throttle slot. The endpoint is unauthenticated by design (it must answer any updater), so this is a bound, not a hole — but it is the one an operator needs to know when a genuine `unknown-id` fails to arrive. Do not add a KV counter for it; that is new stateful mechanism on a stateless Worker for less detection, not more.
  - `alertBody(entry)` carries `reason` and a pointer to the repair (`re-PUT the entitlement from the ledger`, `docs/licensing-operations.md §3`) and **nothing else**. Spell the citation in full — `tests/build/invariant-citations.test.ts:47` scans `infra`, and a bare or parenthesised `§3` is flagged as dangling.
  - `shouldAlert(key, nowMs)` + `ALERT_THROTTLE_MS = 5 * 60 * 1000` + `_resetAlertThrottleForTests()`, copied verbatim from the issuance file's `:845-866` including its comment about isolates being short-lived. **"Verbatim" carries no key — the key is built at the CALL site, and this Worker's is different.** The issuance call site (`worker.ts:958`) keys on `` `${entry.result}:${entry.stage ?? "-"}` ``; this Worker has no `stage`, so **the key is `` `${entry.result}:${entry.reason ?? "-"}` ``**, stated here because a literal copy keying on `result` alone collapses `unknown-id` and `unparseable` into one 5-minute slot — and then an `unparseable` storm silently suppresses the genuine `unknown-id` this detector exists to deliver. Test 7 discriminates it.
  - `sendOperatorAlert(env, entry)` posts `{text: body}` to `ALERT_WEBHOOK_URL`; a non-ok response counts as a failure (a retired Slack webhook 404s rather than throwing); when the channel is absent or exhausted, log `{result: "alert-undeliverable", ts, reason}` so the consumed throttle slot leaves a trace.
  - Wire it in the `fetch` `log` callback — **not inside `handleUpdateRequest`**, which stays pure and I/O-injected — and hand the promise to `ctx.waitUntil` with `.catch(() => {})`. **An alert must never delay or fail the request it reports on, and must never change the response bytes**: the no-existence-oracle invariant in this file's header is the reason the 204 is byte-identical across all reasons, and `revoked` joins them unchanged.
- **Alert on occurrence, throttled — not on a rate.** The issue says "keyed on `unknown-id` rate". With the tombstone above, `unknown-id` means *an entitlement we did not remove is gone* — genuinely abnormal — while an unlicensed client lands on `no-header` and, after H-a, a restricted device issues no request at all. A rate threshold could only add a way to miss the first one, and rate state on a stateless Worker means a KV counter. Recorded as an assumption, together with the flood residual above.

## Tests

All in `tests/server/license-update-worker.test.ts`, extending the existing `no-update reasons (the silent-failure detector)` suite (`:189`). `beforeEach(_resetAlertThrottleForTests)` — the issuance suite's own comment records that without it the second test to provoke a given key is silently suppressed and every "does not alert" assertion passes vacuously. **Every test that asserts on `console.log` or on `fetch` captures `ctx.waitUntil`'s argument and `await`s it first**, except item 7's no-channel case, which is the one that happens to be synchronous (no `await` is reached before the `alert-undeliverable` line).

**Two structural rules, both new in round 3, and each is the difference between a pin and a green-forever assertion. Neither is visible to CI.**

- **Which entry point a test drives decides whether it can see an alert at all.** The suite's only existing helper is `reasonFor` (`:190-204`), which calls **`handleUpdateRequest`** directly with an injected `log`. This spec requires the alert to be wired **in the `fetch` `log` callback, not inside `handleUpdateRequest`** (§ Fix), so `handleUpdateRequest` has **no alert plumbing by construction** and every "does not alert" assertion written against `reasonFor` is structurally vacuous — green whatever the implementation does. **Items 2, 3, 5, 6, 7, 8, 9 and the no-alert half of 10 MUST drive `default.fetch(request, env, ctx)`** with `ALERT_WEBHOOK_URL` set and a stubbed global `fetch`. `reasonFor` may be used only for `reason` / status / body / manifest assertions — items 1 (a pure unit table on the exported predicate), 4's no-webhook comparison arm, 10's `revoked`-reason-and-not-served half, and 11. Round 2 named `default.fetch` only in item 2, which left items 9 and 10's negatives asserting the absence of a mechanism that was never in the code path under test.
- **Every pair of cases sharing a throttle key sits in its own `it()`** (or calls `_resetAlertThrottleForTests()` between them). `H-b-1793.md` § Tests carries this rule for the issuance suite and it transfers verbatim: `shouldAlert` (`infra/license-issuance-worker/src/worker.ts:854-859`, the shape copied here) returns false for 5 minutes on a repeated key, and the reset is a `beforeEach` (`:864-866` is the exported resetter) firing **per `it()`, not per case**. A second case in the same `it()` runs with the slot already consumed — no alert is attempted, the webhook stub is never called, and *"still returns 204"* and *"zero webhook POSTs"* are both satisfied **trivially**, so an implementation whose failure path throws would still pass. Items 6 and 5 are named below as the two that violate it.

1. **`isAlertable` truth table.** True for `unknown-id` and `unparseable`; **false for `no-header`, `expired`, `revoked`, `upstream` and `{result:"served"}`**. The false rows kill both an alert-on-every-no-update (which would fire on every unlicensed client) and an alert-on-nothing.
2. **Wiring, through `default.fetch`.** A request with an unknown **UUID-shaped** id, env carrying `ALERT_WEBHOOK_URL`, a stubbed global `fetch`: exactly one POST to the webhook URL; body contains `unknown-id`; **body does NOT contain the license id that was sent**. The negative is the privacy pin — it kills an alert body that echoes the header.
3. **A non-UUID id logs but does not page.** `X-Tandem-License-Id: not-a-uuid` → status 204, the log line still reads `unknown-id`, and **zero webhook POSTs**. This is the anti-flood pin; without it, alerting is wired to input any internet caller controls.
4. **The response is unchanged by alerting.** Status 204, `await res.text()` empty, and byte-identical to the same request with no `ALERT_WEBHOOK_URL`.
5. **The alert is off the response path, provably. TWO SEPARATE `it()` BLOCKS**, for the same reason as item 6 — both halves provoke `unknown-id` and share the key `no-update:unknown-id`. (a) `ctx.waitUntil` called exactly once with a promise. (b) a webhook stub that never settles must still let `default.fetch` resolve with 204 while `fetchMock` holds one **pending** call. (b) happens to survive being second — a suppressed alert leaves `fetchMock` with **zero** pending calls, so the assertion is not vacuous — but it survives by luck, and the rule is cheaper than the reasoning. The `waitUntil`-count assertion alone is satisfied by an implementation that sends inline and hands over an already-settled promise.
   **Be precise about what the never-settling half pins, because round 1 oversold it.** It does *not* kill an `await`ed alert as written: `reject` (`infra/license-update-worker/src/worker.ts:92-95`) calls `log?.({...})` and returns immediately, discarding the return value, so an `await sendOperatorAlert(...)` placed inside the `fetch` `log` callback cannot delay the 204 either way. Keep the case — it is a real guard against a later change that makes `reject` (or the `log` callback) await its logger — but describe it as that, so a future reader does not treat it as a discriminator it is not.
6. **A failing alert channel cannot fail the request. TWO SEPARATE `it()` BLOCKS.** Both drive `default.fetch`; both provoke `unknown-id`, i.e. the single throttle key `no-update:unknown-id`. (a) webhook `fetch` **rejects** → still 204. (b) webhook `fetch` resolves **404** → still 204. **Written as one `it()` the second half is throttle-suppressed**: no alert is attempted, the stub is never called, and *"still returns 204"* holds for free — an implementation whose 404 path throws and fails the request would pass. Name them separately, or call `_resetAlertThrottleForTests()` between them.
7. **Throttle — and the throttle KEY.** Two unknown-id requests in one isolate → one webhook POST. Then `_resetAlertThrottleForTests()` and a third → two. **Third case, and it is the discriminating one:** one `unknown-id` then one `unparseable` **in the same isolate, with no reset between** → **two** webhook POSTs. Without it, an implementation that copies `shouldAlert` but keys on `entry.result` alone (the same string, `"no-update"`, for every reason) passes items 1–7 while collapsing the two alertable reasons into one 5-minute slot — so an `unparseable` storm suppresses the genuine `unknown-id`.
8. **No channel configured → no alert fetch, and an `alert-undeliverable` log line.** Kills silently burning the throttle slot with no trace.
9. **`expired` does not alert** even though it is a no-update — the case an operator would otherwise be paged for on every out-of-window customer, forever. **Through `default.fetch`, with `ALERT_WEBHOOK_URL` set and global `fetch` stubbed**: zero webhook POSTs. Written against `reasonFor` this assertion is vacuous — `handleUpdateRequest` has no alert plumbing, so "does not alert" is true of every implementation.
10. **The tombstone, both halves.** In `tests/server/license-issuance-worker.test.ts`: a refund leaves `LICENSE_KV` holding `{updateWindowEnd: null, status: "revoked"}` for that licenseId rather than an absent key — **plus the seven existing assertions enumerated in § Fix (`:617, :652, :664, :669, :780` rewritten to the tombstone value; `:626`, `:640` strengthened from `toBeDefined()` to the live value), which are part of this commit, not a follow-up.** In `license-update-worker.test.ts`: **two cases, because the halves need different entry points.** (a) through `reasonFor`: that exact value → **204, reason `revoked`**, and — the discriminating assertion — **not** a served manifest. A `revoked` check placed after the window comparison serves `null updateWindowEnd` as grandfathered, so this row is what pins the ordering. (b) through **`default.fetch`** with `ALERT_WEBHOOK_URL` set and global `fetch` stubbed: **zero webhook POSTs.** The no-alert half cannot ride on (a) — `reasonFor` drives `handleUpdateRequest`, which by design holds no alert plumbing, so "no alert" there is true of every implementation including one that pages on `revoked`.
11. **The no-existence-oracle test learns the sixth reason.** `tests/server/license-update-worker.test.ts:245-265` hand-enumerates five results, asserts `new Set(...).size === 5` and one indistinguishable `${status}:${body}`. Add a sixth row (the tombstone → `revoked`) and bump the size to **6**.
