## Problem

`chatReveal` (`rail-content.svelte.ts:88`) is torn down from exactly four places, all of which route through `closeReveal` (`:103-107`): the capture-phase `pointerdown` + Escape effect (`:146-167`), the document-switch effect (`:171-174`), `App.svelte`'s `toggleRightPanel` (`:1204-1219`, the close at `:1210`) and `sendChatMessage` (`:1962-1969`, the close at `:1967`).

**Nothing observes effective visibility.** The rail can become visible without the user pinning it, and the reveal survives: in Solo with `soloRailHidden` set, `layoutModel.rightVisible` is false (`model.svelte.ts:120-123`); the user opens the reveal; the server flips the session to Tandem — mode lives in `CTRL_ROOM` and broadcasts, so this is not a local action — and `rightVisible` becomes true with `chatReveal` still true. Same shape via `settings.rightPanelVisible` flipping from the Settings modal.

A **pinned** rail then renders as a float: `class:rail-floating-chrome` and `class:floating` (`App.svelte:2462-2465`), the `rail-float-shadow` block (`:2476-2482`), and `data-testid="rail-float-right"` (`:2468`). The testid is the part with teeth: it is how E2E identifies a floating rail (`tests/e2e/chat-reveal.spec.ts:63`), so a spec arriving in this state gets a wrong answer with nothing failing.

## Fix

**One derived rule, not a fifth manual clear site** — the reveal exists only to show content over a *collapsed* rail, so its precondition failing should end it.

- `rail-content.svelte.ts`: add a fourth `$effect`, beside the document-switch effect at `:171-174` and in the same shape — **both reads unconditional**:

```ts
$effect(() => {
  const visible = opts.getEffectiveRightVisible();
  if (chatReveal && visible) closeReveal();
});
```

  Written this way on purpose. The short-circuited form (`if (chatReveal && opts.getEffectiveRightVisible())`) never calls the thunk while `chatReveal` is false, so `effectiveRightVisible` drops out of the effect's dependency set between reveals and is re-acquired on the next open. That converges — `chatReveal` is always tracked — but it is not the shape of the sibling effect this bullet cites, which reads `opts.getActiveTabId()` unconditionally on `:172` before testing `chatReveal` on `:173`. Matching it keeps the dependency set stable and the "same shape" claim true.
  `getEffectiveRightVisible` is already an injected thunk (`:52`), wired at `App.svelte:256` to `effectiveRightVisible` (`:1178`), a `$derived` over `layoutModel.rightVisible` — settings and mode — so the dependency is live. This is the **general** form of what `toggleRightPanel` does for one specific path.
- **It writes one of its own dependencies, and that is fine here** — the document-switch effect already does exactly that (`chatReveal`, read unconditionally) and converges; the comment at `:89-101` records that measurement. `closeReveal` is guarded (`:104`, `if (!chatReveal) return`), so the second pass is a no-op.
- **Keep `toggleRightPanel`'s explicit `closeReveal()`** (`App.svelte:1204-1219`) rather than deleting it as now-redundant. It is the **synchronous** half: it lands the close in the same commit as `railPinSnap.right = true` (`:1206`), whose whole job is one frame (`:1249-1253`). The effect flushes afterwards, so removing the direct call would let the pin-snap frame paint a still-floating shell — the exact flash `railPinSnap` exists to prevent. Its `railContent.revealOpen` read at `:1205` also still decides whether the pin-snap runs at all.
- **The adjacent note in the body:** `ChatState.acknowledgeVisible` is declared at `useChatState.svelte.ts:31` and implemented at `:232-236` with **zero callers** — measured by `grep -rn acknowledgeVisible src/ tests/` on master, which returns only the declaration, the implementation, the differently-named `acknowledgeVisibleMessages`, and a prose mention in `model.svelte.ts:153`. Drop the interface member and its implementation. `acknowledgeVisibleMessages` (`:113`) stays — it is called from the effect at `:164`, which is the live path; update the prose reference in `model.svelte.ts:153` only if the deletion makes it wrong (it describes the effect, not the dropped member — re-read before editing).

Rules that bite: the new effect **registers no listener**, so the capture-phase teardown-identity rule (the third argument is part of the listener identity) is untouched; `chatRevealDocumentId` stays a plain `let` off the interface (`:99`), cleared by `closeReveal` as today; no markup change, so **no testid snapshot regeneration**.

## Tests

All in `tests/client/rail-content.svelte.test.ts`, whose harness already exposes `setRightVisible` and is `$state`-backed per its rule 1 (`:16-31`, `:40-86`). `mount` (`:88-97`) builds the model inside a real `$effect.root`, which is what makes the new effect run at all.

1. **"a reveal closes when the rail becomes pinned"**: open a reveal over a collapsed rail, `setRightVisible(true)`, assert `revealOpen` is false. Kills today's code and any fix that only clears inside `toggleRightPanel` — the whole point is the path where the user took no local action. **It does not kill an inverted or dropped condition** (see spec 3), and the ordering here must not be read as implying it does.
2. **"the reveal is not resurrected when the rail unpins again"**: continue spec 1 with `setRightVisible(false)` and assert `revealOpen` stays false. Kills an implementation written as a `$derived` mirror of visibility rather than a one-way teardown.
3. **Negative twin, and the inversion killer — "a collapsed rail leaves the reveal alone"**: with `rightVisible` false throughout, `openReveal()`, flush, and assert `revealOpen` is **still true**. That surviving-open assertion after the first effect flush is the whole instrument: an inverted condition (`chatReveal && !visible`) or a dropped one (`if (chatReveal)`) closes the reveal at open time, which spec 1 cannot see — spec 1 asserts `false` at the end, and an early close still reads `false`. **Do not attribute the kill to mutating an unrelated stub**: `setAnnotations` / `setFindBarOpen` (`:69-80`) feed `getVisibleAnnotations` / `getFindBarOpen`, which this effect never reads, so they re-run nothing. Keep one such call only if the spec labels it a no-op control, or leave it out.
4. The existing `:100` spec ("opens over a collapsed rail and no-ops over a pinned one") is the twin that must stay green — it pins `openReveal`'s guard, which the new effect complements rather than replaces.
5. **`acknowledgeVisible` removal** is pinned by `npm run typecheck` and `npm run typecheck:tests` (the tests tree is typechecked only by the latter — CLAUDE.md). The grep above found no spec asserting the member, so no suite changes; do not add a test for a deleted member.
6. **Mutation-test** (memory rule): delete the new effect's body and watch **spec 1** go red by name; invert its condition and watch **spec 3** go red by name — spec 3 is the only one that fails that mutant, so a reviewer trimming "redundant" specs must not remove it. Restore from a file copy, never `git checkout`.
