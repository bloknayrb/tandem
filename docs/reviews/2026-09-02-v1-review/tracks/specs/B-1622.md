# B — #1622 A U+00A0 in the document makes `textSnapshot` unwinnable: `RANGE_GONE` for text that is present

Branch `fix/annotation-anchors-1764`. Closes #1622. Ledger: not a v1-review row — filed 2026-08-26 from the live investigation alongside #1621/#1623/#1624, folded into track B because it is the fifth `textSnapshot` defect. Probe: the issue's own `tandem_resolveRange` table against a document containing NBSP; reproducible offline from the fixture in the tests below.

## Problem

`validateRange`'s staleness gate (`src/server/positions.ts:465-489`) compares `fullText.slice(from, to) !== opts.textSnapshot` and, on a mismatch, searches with `indexOf`. Both are exact. `tandem_getTextContent` returns a U+00A0 faithfully, but it is indistinguishable from U+0020 to a model reading the output, so the caller sends back a snapshot with a regular space: the comparison correctly fails, `indexOf` finds nothing, and the tool answers `RANGE_GONE` — "Target text no longer exists in the document" — for text that is right there. The same call with `textSnapshot` omitted succeeds and then **stores** the NBSP-bearing string as the annotation's snapshot, so the stored value differs from the rejected one by one invisible codepoint. The issue rules out both plausible alternative causes (divergent extractors, a live-editing race).

The same transcription problem defeats the issue's own diagnostic. `tandem_resolveRange` does not call `validateRange` at all: `src/server/mcp/navigation.ts:242-250` calls `findOccurrence(fullText, pattern, occurrence)`, and `findOccurrence` (`navigation.ts:100-129`) is a `new RegExp(escapeRegex(pattern), "g")` sweep over the flat text. A phrase transcribed with U+0020 over an NBSP-bearing span answers `INVALID_RANGE: Text "…" not found`, and the tool the skill recommends as the way to get "offsets that are correct by construction" is the one that cannot find the text.

The issue's own proposed fix — relocate to `RANGE_MOVED` with a `whitespaceMismatch` flag — is insufficient, and this is the design call this spec takes. At the *correct* offsets the exact slice still differs, so the retry the caller is told to make comes back `RANGE_MOVED` pointing at the offsets it just passed, forever. A relocation cannot answer a mismatch that is not a relocation.

## Fix

A whitespace-class difference is a **transcription** difference, not evidence the document changed underneath — which is the only thing `textSnapshot` exists to detect. So treat a normalized-equal slice as a match, reserve relocation for text that actually moved, and give the occurrence search the same fallback so the diagnostic works too.

- **`src/server/positions.ts`** — one exported, **length-preserving** normalizer (exported rather than module-private because `navigation.ts` needs the same set; a second copy is how the two would drift):
  `export function normalizeSpaceClass(s: string): string` — `s.replace(/[\u00A0\u1680\u2000-\u200A\u202F\u205F\u3000]/g, " ")`. That set is exactly Unicode `Zs` minus U+0020. **Length-preserving is the invariant**: one code unit in, one out, so every offset computed against the normalized copy is valid against the original — the same constraint `flattenHeadingText` documents. Do not add `\t`, `\r` or `\n` (a newline is a block separator in this coordinate system, and collapsing it would let a range cross a boundary), and do not add zero-width characters (U+200B, U+FEFF) — they are not spaces and normalizing them would be a silent content claim.
- **The normalization is opt-in, and only the caller-supplied-snapshot sites opt in.** Add `normalizeSpaceClass?: boolean` to `RangeValidationOpts`, defaulting to **off**, and pass `normalizeSpaceClass: true` at exactly two sites: `src/server/mcp/document.ts:756` (`tandem_edit`) and `src/server/mcp/document-store.ts:288` (`YDocStore.anchorRange`, whose only caller is `annotations.ts:311` — `tandem_comment` / `tandem_suggest`). Those are the complete set of `validateRange`/`anchoredRange` calls in `src/` whose `textSnapshot` came from the **caller**; the deprecated `tandem_highlight` / `tandem_suggest` / `tandem_flag` stubs accept a `textSnapshot` param but never validate a range, and `docx-apply.ts:251` / `tutorial-annotations.ts:121` carry a snapshot into a record rather than into `validateRange`. **The default is off because that direction fails safely**: a forgotten opt-in reproduces today's visible `RANGE_GONE`, whereas a forgotten opt-out would silently accept a stale range. See the Assumptions bullet on the watcher for why the two stored-snapshot callers must stay exact — this option is what keeps them exact.
- Inside the existing `if (opts?.textSnapshot)` block — steps 2 and 4 **only when `opts.normalizeSpaceClass === true`**; steps 1, 3 and 5 are unconditional and unchanged — in this order:
  1. exact slice comparison — unchanged, and it is still the fast path;
  2. **new:** `normalizeSpaceClass(slice) === normalizeSpaceClass(opts.textSnapshot)` ⇒ fall through as a match (no relocation, no error). This is the issue's headline case.
  3. exact `indexOf` sweep — unchanged, still preferred, so a document with both an exact and a normalized-only occurrence relocates to the exact one;
  4. **new:** when the exact sweep finds nothing, repeat it against `normalizeSpaceClass(fullText)` with the normalized snapshot, and build the same `RANGE_MOVED` from those offsets. Offsets are valid on the original text because the normalization is 1:1.
  5. `RANGE_GONE` only when the normalized sweep is empty too — so the error now means what it says.
- **Cost: the normalized full text is computed at most once per call and only on the miss path.** Step 4 is a full-document regex replace, and `validateRange` runs once per annotation inside the watcher's relocation loop (`src/server/documents/watcher.ts:277-283`), which already hoists `const text = extractText(doc)` across the loop precisely so a per-annotation full-document cost does not return (#1752). So: compute the normalized copy lazily inside `validateRange` (a `let normalizedFull: string | undefined` filled on first use), never at the top of the function, and never for a call that passes no `textSnapshot` or whose exact comparison succeeds. Do **not** add a normalized twin to `RangeValidationOpts.text` — the hoist's guard is a flat-length comparison against the live document, and a second cached string would need its own guard. The cost is bounded to the sweep-miss path, which is the path that was about to answer `RANGE_GONE`.
- **`src/server/mcp/navigation.ts` `findOccurrence`** — the same fallback, so `tandem_resolveRange` (and the local-model `resolveAnchor` that shares it) can find NBSP-bearing text from a transcribed pattern. **Its trigger is `count === 0`, not `count < occurrence`** — the exact sweep must find **zero** matches before the normalized sweep runs; then re-sweep `normalizeSpaceClass(fullText)` with `normalizeSpaceClass(pattern)` and index into **that** sweep for the nth occurrence. On a hit, return `from`/`to` from the normalized match (valid on the original because the normalizer is 1:1) and **`text` sliced from the ORIGINAL `fullText`**, so the caller sees the document's real bytes. The empty-pattern guard, `escapeRegex`, and `totalCount` on a genuine miss are unchanged.
  **The zero trigger is what keeps the two halves in step, and `count < occurrence` would not.** `countOccurrences` (below) falls back only when the exact count is zero, so with a `< occurrence` trigger on this side a document holding **one** exact match queried at `occurrence: 2` would have `countOccurrences` return 1 (exact, no fallback) while `findOccurrence` dropped into the normalized sweep and could return a hit — precisely the disagreement `navigation.ts:132-137` says cannot happen ("the SAME literal (regex-escaped) matching as `findOccurrence` so the count and a subsequent resolve can never disagree"), on the path `local-model/tools.ts:190-194` depends on. One trigger, both halves. Test 8 carries the row.
- **`src/server/mcp/navigation.ts` `countOccurrences` takes the same fallback**, because its docblock (`navigation.ts:132-137`) claims a shared invariant this fix would otherwise silently break: "using the SAME literal (regex-escaped) matching as `findOccurrence` so the count and a subsequent resolve can never disagree." `src/server/local-model/tools.ts:191-194` is the caller that depends on it — `countOccurrences` → clamp `occ` to 1 iff `count === 1` → `findOccurrence`. With the fallback on only one half, an NBSP-bearing span queried with U+0020 counts **0** (so the clamp never fires) while `findOccurrence` now hits, which is exactly the disagreement the docblock says cannot happen. Give it the same shape — exact sweep first; if it finds **zero**, re-count over the normalized text with the normalized pattern — **the identical trigger `findOccurrence` uses**, which is the whole point: one condition, evaluated the same way in both functions, is what makes the docblock's invariant true rather than nearly true. Amend the docblock to say the pairing now covers the normalized fallback too, and that **both** halves fall back only on an exact count of zero, so the clamp counts normalized matches exactly when the exact count is zero.
- **`tandem_search` is deliberately OUT.** It stays an exact literal/regex search (`navigation.ts:163+`): it is a user-facing find, its `regex: true` mode makes a silent normalization actively wrong, and it feeds no range resolution — so an exact-only search cannot produce the create/resolve contradiction #1622 is about. State that in `docs/mcp-tools.md` alongside the `tandem_resolveRange` line, so the asymmetry reads as a decision rather than an omission.
- **The order contract is untouched.** CLAUDE.md Critical Rule 4 fixes the sequence integer → ordering → lower bound → **staleness** → upper bound → empty → surrogate → heading. This changes only the comparison *inside* the staleness step; nothing moves across it, and the two pinned accidents (an empty `textSnapshot` skips the gate by truthiness; `from === to` with a snapshot never reaches `"empty"`) are unaffected.
- **No new wire field.** The issue asks for a `whitespaceMismatch` flag so the caller can retry with exact bytes; with (2) there is no longer anything to retry — the call succeeds. Adding a flag to `RANGE_MOVED` would grow the MCP error surface for a case the caller can no longer hit.
- **`docs/mcp-tools.md`** — one line under the range errors: for the tools that take a caller-supplied `textSnapshot` (`tandem_edit`, `tandem_comment` / `tandem_suggest`), snapshot matching ignores the difference between U+0020 and the other Unicode space separators, so a snapshot transcribed with ordinary spaces still matches, and `RANGE_GONE` means the text is absent under that normalization too. Say that the server's own internal re-anchoring stays byte-exact, so this is a transcription allowance for callers, not a change to what counts as a document edit. Plus one line on `tandem_resolveRange`: its search prefers an exact match and falls back to the same normalization, so a pattern typed with ordinary spaces finds an NBSP-bearing span.

## Tests

**Every `validateRange` spec below passes `normalizeSpaceClass: true`** — the option is off by default, so a spec that omits it is asserting the unchanged exact behaviour. Test 10 is the one that deliberately omits it.

1. `tests/server/positions.test.ts` — fixture containing `"…emails, Teams chats…"`. `validateRange(doc, from, to, { textSnapshot: <same text with U+0020> })` returns `ok` with the range unchanged. The issue's headline; kills the current exact comparison and kills a `RANGE_MOVED`-with-a-flag fix, which would not return `ok`.
2. Same file — **the loop guard**: feed the result of a `RANGE_MOVED` retry back in. A snapshot that is normalized-equal at its own offsets must never answer `RANGE_MOVED` pointing at those same offsets. This is the test that says why the issue's proposal was not taken.
3. Same file — **moved and normalized**: the NBSP-bearing text relocated elsewhere in the document, queried at its old offsets with a U+0020 snapshot ⇒ `RANGE_MOVED` with the true offsets, and `fullText.slice(resolvedFrom, resolvedTo)` is the NBSP-bearing text. Pins that the normalized sweep's offsets are valid on the original string, i.e. that the normalizer is length-preserving.
4. Same file — **`RANGE_GONE` is still reachable**: genuinely deleted text with an ordinary-space snapshot returns `RANGE_GONE`. The issue names this explicitly: without it the fix could turn `RANGE_GONE` into dead code and nothing would notice.
5. Same file — **exact wins over normalized**, with the fixture stated precisely, because the loose wording ("a document holding both … relocates to the exact occurrence") fails under this spec's own step order whenever the queried range happens to be the NBSP variant, and the obvious repair — moving step 2 after step 3 — breaks the headline. The queried `[from, to)` must be **stale**: it matches the snapshot neither exactly nor under normalization. The document holds an exact occurrence and an NBSP variant elsewhere; the result is `RANGE_MOVED` at the **exact** one. Kills a fix that normalizes both strings up front and drops the exact sweep.
   One sentence for the reader who reaches for the reorder anyway: when the queried range **is** the NBSP variant, the correct answer is `ok` (step 2), not a relocation to the exact occurrence — that is the headline behaviour tests 1 and 2 pin, and it is why step 2 must stay ahead of step 3.
6. Same file — **newlines are not normalized**: a snapshot with a space where the document has a block separator (`\n`) still fails. Kills a `\s`-class regex.
7. Same file — **the normalized copy is built only on the miss path**, and the mechanism matters: **do not "spy on the normalizer".** `normalizeSpaceClass` is exported from `src/server/positions.ts` and called from `validateRange` **in the same module**, and an ESM intra-module call binds the local declaration, not the namespace object — a `vi.spyOn` on the module export never intercepts it and the spec passes green in every world. Use a **module-private counter with a test-only reader**, following the existing precedent at `src/server/positions.ts:319-324` (`__testResetHoistMismatchCounts`): a `__testNormalizedFullBuilds()` reader plus a reset, incremented where `normalizedFull` is filled. **Assert four enumerated rows, because the headline case builds zero and a spec that says otherwise gets "fixed" into the regression it exists to prevent** — step 2 normalizes a **slice** (`normalizeSpaceClass(slice) === normalizeSpaceClass(opts.textSnapshot)`), not the full text, so `normalizedFull` is filled only by step 4:
   - exact match at the queried offsets ⇒ **0**;
   - no `textSnapshot` ⇒ **0**;
   - **normalized-equal at the queried offsets (step 2 — the issue's headline) ⇒ 0**;
   - a stale range that relocates only via the normalized sweep (step 4) ⇒ exactly **1**, not one per comparison.
   A non-zero count on the third row means the build was hoisted out of the miss path — which puts a full-document regex replace on the **success** path of `validateRange`, called once per annotation by the watcher's relocation loop (`src/server/documents/watcher.ts:277-283`), the exact #1752 cost the Fix bullet forbids. (`vi.spyOn(String.prototype, "replace")` is the fallback only if paired with an explicit statement that `validateRange` performs no other `replace` on the path — it counts every unrelated one.) Pins the lazy placement against the #1752 hoist's rationale.
8. `tests/server/navigation-tools.test.ts` — `findOccurrence` / `tandem_resolveRange`: an ordinary-space pattern finds the NBSP-bearing span, returns offsets that slice to the document's real bytes on the original text, and the returned `text` carries the NBSP. Plus the negatives: an exact match still wins and `totalCount` is unchanged on a genuine miss; the empty-pattern guard still fires.
   **And the shared-invariant rows, both of them** — one per trigger side, because a single row on the exact-count-zero path leaves the mismatched-trigger bug green:
   - *exact count zero*: an NBSP-bearing span queried with U+0020 — `countOccurrences` returns 1 and `findOccurrence` resolves it, so `local-model/tools.ts`'s `count === 1` occurrence clamp fires exactly as it does for an exactly-matching pattern.
   - *exact count non-zero, `occurrence: 2`*: a document holding **one exact** occurrence of the pattern **and** one NBSP variant elsewhere, queried at `occurrence: 2`. `countOccurrences` returns **1** (exact sweep found one; no fallback) and `findOccurrence` must **also** not fall back — it returns the not-found error with `totalCount: 1`. This is the row that kills a `count < occurrence` trigger on `findOccurrence`, which would drop into the normalized sweep and return a hit the count says does not exist.
   Without both, the docblock's "can never disagree" is false with the suite green, and the clamp silently misbehaves for this population.
9. `tests/server/mcp-tool-integration.test.ts` — `tandem_comment` with an ordinary-space snapshot over an NBSP span succeeds and stores the document's real bytes as `textSnapshot`, ending the self-contradiction the issue describes (the identical call without a snapshot already succeeded).
10. `tests/server/positions.test.ts` — **the gate, in both directions, on a document whose annotated span had its NBSP replaced by U+0020.** Take a record whose stored `textSnapshot` carries the NBSP, edit the document so that span now holds a U+0020 instead, and assert:
    - `validateRange(doc, from, to, { textSnapshot: <the stored NBSP snapshot> })` — **no `normalizeSpaceClass`**, the watcher's shape — does **not** return `ok`; it relocates or answers `RANGE_GONE` exactly as today, and `snapshotContradicts(ann, <the U+0020 slice>)` is `true`, i.e. the two comparators still agree;
    - the same call **with** `normalizeSpaceClass: true` returns `ok`, which is the caller-supplied behaviour tests 1–3 rely on.
    This is the spec that keeps the watcher's stored-snapshot probe from silently diverging from `snapshotContradicts` and from #1764's `storedRangeStillMatches` — the #1631 shape named in Assumptions. A fix that normalizes unconditionally passes tests 1–9 and fails only this one.

## Assumptions

- **Whitespace-class equality is accepted as a match, not reported as a relocation.** Stated in Fix; the cost is that a real edit which only swapped U+00A0 for U+0020 across the same span no longer reads as stale. That edit is invisible to the caller by construction, which is the whole issue.
- **`snapshotContradicts` stays exact, and the `normalizeSpaceClass` opt is what keeps `validateRange` from diverging from it.** The earlier version of this bullet claimed the normalizer was confined to comparisons of a **caller-supplied** string. That is false as a property of `validateRange`: **two `src/` sites pass a STORED snapshot into it.** `src/server/documents/watcher.ts:278` calls `validateRange(doc, ann.range.from, probeTo, { textSnapshot: probe, … })` where `probe = snapshotSearchPrefix(ann)` (`:250`) is the annotation's own stored snapshot, and `:315-317` calls `anchoredRange(doc, vr.resolvedFrom, resolvedTo, ann.textSnapshot, relocOpts)` with the stored snapshot on the non-truncated branch. Left unguarded, the normalization would reach both, and on a single watcher reload after an external edit that swapped U+00A0 for U+0020 inside an annotated span the probe would answer `ok` and `continue` silently (today it answers `RANGE_GONE` / `RANGE_MOVED` and logs), while `snapshotContradicts` — still exact (`src/shared/snapshot.ts:176`) — refuses the editor accept and the `.docx` apply, and #1764's `storedRangeStillMatches` reported the same record `degraded` one pass earlier. That is the #1631 divergence shape.
  **Decision taken: gate the normalization, leave the stored-snapshot comparators exact.** `normalizeSpaceClass: true` is passed only by the two caller-supplied sites (`document.ts:756`, `document-store.ts:288`); the watcher's probe and relocation anchor pass nothing and keep today's exact comparison, so they stay in step with `snapshotContradicts`. `findOccurrence` / `countOccurrences` need no flag — their pattern is caller-supplied by construction (`tandem_resolveRange`, local-model `resolveAnchor`). Extending the normalizer to `snapshotContradicts` instead was rejected: it gates the `.docx` apply and the editor accept, which write bytes, and it is a **stored**-vs-document comparison where a whitespace change genuinely is a document change. What survives from the old bullet is narrower and still true: every stored snapshot comes from `captureSnapshot`'s own slice (`annotations.ts:316`), never from the caller's `textSnapshot`, so a normalized-accepted create still stores the document's real bytes and cannot mint a record `snapshotContradicts` refuses forever.
- **No log line on a normalized-only match.** `validateRange` runs once per annotation in the watcher's reload loop, so a warn there is a per-reload multiplier for no reader.
- **`Zs` minus U+0020 is the set.** Tab is not a space separator in Unicode and does not occur in this coordinate system's flat text as a substitute for one.
