# B — #1622 A U+00A0 in the document makes `textSnapshot` unwinnable: `RANGE_GONE` for text that is present

Branch `fix/annotation-anchors-1764`. Closes #1622. Not a v1-review ledger row — filed 2026-08-26 from the live investigation alongside #1621/#1623/#1624, folded into track B as the fifth `textSnapshot` defect. Repro: the issue's own `tandem_resolveRange` table against a document containing NBSP.

## Problem

`validateRange`'s staleness gate (`src/server/positions.ts`) compares `fullText.slice(from, to) !== opts.textSnapshot` and, on a mismatch, searches with `indexOf`. Both are exact. `tandem_getTextContent` returns a U+00A0 faithfully, but it is indistinguishable from U+0020 to a model reading the output, so the caller sends back a snapshot with a regular space: the comparison correctly fails, `indexOf` finds nothing, and the tool answers `RANGE_GONE` — "Target text no longer exists in the document" — for text that is right there. The same call with `textSnapshot` omitted succeeds and then **stores** the NBSP-bearing string as the annotation's snapshot, so the stored value differs from the rejected one by one invisible codepoint. The issue rules out both plausible alternative causes.

The same transcription problem defeats the issue's own diagnostic, which is what its whole reproduction table is made of: `tandem_resolveRange` never calls `validateRange` — `src/server/mcp/navigation.ts:242-250` calls `findOccurrence`, an exact `new RegExp(escapeRegex(pattern), "g")` sweep — so the tool the skill recommends for "offsets correct by construction" is the one that cannot find the text.

**The issue's own proposed fix is insufficient**, and this is the design call the spec takes. Relocating to `RANGE_MOVED` with a `whitespaceMismatch` flag leaves the exact slice still different at the *correct* offsets, so the retry the caller is told to make comes back `RANGE_MOVED` pointing at the offsets it just passed, forever. A relocation cannot answer a mismatch that is not a relocation.

## Fix

A whitespace-class difference is a **transcription** difference, not evidence the document changed underneath — the only thing `textSnapshot` exists to detect.

- **`src/server/positions.ts`** — one exported, **length-preserving** normalizer (exported because `navigation.ts` needs the same set; a second copy is how the two drift):
  `export function normalizeSpaceClass(s: string): string` — one `String.prototype.replace` of a character class with `" "`. The class is U+00A0, U+1680, U+2000–U+200A, U+202F, U+205F, U+3000, written as `\uXXXX` escapes in the source: exactly Unicode `Zs` minus U+0020. **Length-preserving is the invariant**: one code unit in, one out, so every offset computed against the normalized copy is valid against the original — the constraint `flattenHeadingText` already documents. Do not add `\t`, `\r` or `\n` (a newline is a block separator here, and collapsing it would let a range cross a boundary) and do not add zero-width characters, which are not spaces.
- **The normalization is opt-in, and only the caller-supplied-snapshot sites opt in.** Add `normalizeSpaceClass?: boolean` to `RangeValidationOpts`, default **off**, passed at exactly two sites: `src/server/mcp/document.ts` (`tandem_edit`'s `validateRange`) and `src/server/mcp/document-store.ts` (`YDocStore.anchorRange`, whose only caller is `annotations.ts:311` — `tandem_comment` / `tandem_suggest`). Those are the complete set of `validateRange`/`anchoredRange` calls in `src/` whose `textSnapshot` came from the **caller**. **Two sites pass a STORED snapshot and must stay exact**: `documents/watcher.ts:278` (`textSnapshot: probe`, where `probe = snapshotSearchPrefix(ann)`) and `:315-317` (`anchoredRange(..., ann.textSnapshot, ...)`). Normalizing there would make the watcher's probe answer `ok` on an external NBSP→U+0020 edit while `snapshotContradicts` — still exact — refuses the editor accept and the `.docx` apply: the #1631 divergence shape. **Default off because that direction fails safely**: a forgotten opt-in reproduces today's visible `RANGE_GONE`, a forgotten opt-out would silently accept a stale range. Test 9 pins both directions.
- Inside the existing `if (opts?.textSnapshot)` block — steps 2 and 4 **only when `opts.normalizeSpaceClass === true`**, steps 1, 3 and 5 unconditional and unchanged — in this order:
  1. exact slice comparison — unchanged, still the fast path;
  2. **new:** `normalizeSpaceClass(slice) === normalizeSpaceClass(opts.textSnapshot)` ⇒ fall through as a match (no relocation, no error). The issue's headline case;
  3. exact `indexOf` sweep — unchanged, still preferred, so a document with both an exact and a normalized-only occurrence relocates to the exact one;
  4. **new:** when the exact sweep finds nothing, repeat it against `normalizeSpaceClass(fullText)` with the normalized snapshot and build the same `RANGE_MOVED` from those offsets, valid on the original because the normalization is 1:1;
  5. `RANGE_GONE` only when the normalized sweep is empty too — so the error means what it says.
  **Build the normalized full text lazily** (a `let normalizedFull: string | undefined` filled on first use in step 4), never at the top of the function: step 2 normalizes a slice, not the document, and `validateRange` runs once per annotation inside the watcher's relocation loop, which hoists its `extractText` precisely so a per-annotation full-document cost does not return (#1752). Do not add a normalized twin to `RangeValidationOpts.text` — the hoist's guard is a flat-length comparison and a second cached string would need its own.
- **`src/server/mcp/navigation.ts`** — the same fallback on `findOccurrence`, so the issue's own reproduction resolves: when the exact sweep finds **zero** matches, re-sweep `normalizeSpaceClass(fullText)` with `normalizeSpaceClass(pattern)` and index into that sweep for the nth occurrence; return `from`/`to` from the normalized match and **`text` sliced from the ORIGINAL `fullText`**, so the caller sees the document's real bytes. The empty-pattern guard, `escapeRegex` and `totalCount` on a genuine miss are unchanged. **`countOccurrences` takes the identical trigger** — exact sweep first, normalized re-count only when the exact count is zero — because its docblock (`navigation.ts:132-137`) claims "the SAME literal (regex-escaped) matching as `findOccurrence` so the count and a subsequent resolve can never disagree", and `local-model/tools.ts:190-194` clamps on `count === 1` before calling `findOccurrence`. One trigger, evaluated the same way in both halves, is what keeps that true: a `count < occurrence` trigger on either side lets one exact match queried at `occurrence: 2` disagree. Amend the docblock to say the pairing covers the fallback and that both halves fall back only on an exact count of zero.
- **The order contract is untouched.** Critical Rule 4 fixes integer → ordering → lower bound → **staleness** → upper bound → empty → surrogate → heading. This changes only the comparison *inside* the staleness step.
- **No new wire field.** The issue asks for a `whitespaceMismatch` flag so the caller can retry with exact bytes; with step 2 there is nothing to retry — the call succeeds.
- **`docs/mcp-tools.md`** — one line under the range errors: for the tools taking a caller-supplied `textSnapshot` (`tandem_edit`, `tandem_comment`/`tandem_suggest`), snapshot matching ignores the difference between U+0020 and the other Unicode space separators, and `RANGE_GONE` now means the text is absent under that normalization too; the server's own internal re-anchoring stays byte-exact. Plus one line on `tandem_resolveRange`: its search prefers an exact match and falls back to the same normalization.

## Tests

**Every `validateRange` spec below passes `normalizeSpaceClass: true`** — the option is off by default, so a spec that omits it asserts the unchanged exact behaviour. Test 9 deliberately omits it.

1. `tests/server/positions.test.ts` — fixture containing `"…emails, Teams chats…"`. `validateRange(doc, from, to, { textSnapshot: <same text with U+0020>, normalizeSpaceClass: true })` returns `ok`, range unchanged. The headline; kills both the exact comparison and a `RANGE_MOVED`-with-a-flag fix, which would not return `ok`.
2. Same file — **the loop guard**: a snapshot that is normalized-equal at its own offsets must never answer `RANGE_MOVED` pointing at those same offsets. This is why the issue's proposal was not taken.
3. Same file — **moved and normalized**: the NBSP-bearing text relocated elsewhere, queried at its old offsets with a U+0020 snapshot ⇒ `RANGE_MOVED` with the true offsets, and `fullText.slice(resolvedFrom, resolvedTo)` is the NBSP-bearing text. Pins that the normalizer is length-preserving.
4. Same file — **`RANGE_GONE` is still reachable**: genuinely deleted text with an ordinary-space snapshot ⇒ `RANGE_GONE`. Without it the fix could turn it into dead code.
5. Same file — **exact wins over normalized**, with the queried `[from, to)` **stale** (matching the snapshot neither exactly nor under normalization) and the document holding an exact occurrence plus an NBSP variant elsewhere ⇒ `RANGE_MOVED` at the **exact** one. Kills a fix that normalizes both strings up front and drops the exact sweep. Note for the reader who reaches for a reorder: when the queried range **is** the NBSP variant the correct answer is `ok` (step 2), which is why step 2 stays ahead of step 3.
6. Same file — **newlines are not normalized**: a snapshot with a space where the document has a block separator still fails. Kills a `\s`-class regex.
7. `tests/server/navigation-tools.test.ts` — `findOccurrence` / `tandem_resolveRange`: an ordinary-space pattern finds the NBSP-bearing span, the offsets slice to the document's real bytes on the original text, and the returned `text` carries the NBSP. Negatives: an exact match still wins, `totalCount` is unchanged on a genuine miss, the empty-pattern guard still fires. **Both trigger sides of the shared invariant**, because one row leaves a mismatched trigger green: *(a) exact count zero* — an NBSP span queried with U+0020: `countOccurrences` returns 1 and `findOccurrence` resolves it, so the `count === 1` clamp fires as it does for an exact pattern; *(b) exact count non-zero, `occurrence: 2`* — one exact occurrence plus one NBSP variant elsewhere: `countOccurrences` returns **1** and `findOccurrence` must **also** not fall back, returning not-found with `totalCount: 1`.
8. `tests/server/mcp-tool-integration.test.ts` — `tandem_comment` with an ordinary-space snapshot over an NBSP span succeeds and stores the document's real bytes as `textSnapshot`, ending the self-contradiction the issue describes.
9. `tests/server/positions.test.ts` — **the gate, both directions**, on a document whose annotated span had its NBSP replaced by U+0020: the watcher's shape (`textSnapshot` = the stored NBSP snapshot, **no** `normalizeSpaceClass`) does **not** return `ok` — it relocates or answers `RANGE_GONE` exactly as today — and `snapshotContradicts(ann, <the U+0020 slice>)` is `true`, i.e. the two comparators still agree; the same call **with** `normalizeSpaceClass: true` returns `ok`. A fix that normalizes unconditionally passes tests 1–8 and fails only this one.

## Done when

The nine specs pass; the issue's live table resolves end to end — `tandem_resolveRange` on the full phrase returns the span, and `tandem_comment` with the transcribed snapshot succeeds; both `docs/mcp-tools.md` lines land; `npm run typecheck` + `npm run typecheck:tests` + suite green.

## Assumptions

- **Whitespace-class equality is accepted as a match, not reported as a relocation.** The cost is that a real edit which only swapped U+00A0 for U+0020 across the same span no longer reads as stale to a caller-supplied snapshot. That edit is invisible to the caller by construction, which is the whole issue.
- **`snapshotContradicts` stays exact, and the opt is what keeps `validateRange` from diverging from it.** Extending the normalizer to `snapshotContradicts` was rejected: it gates the `.docx` apply and the editor accept, which write bytes, and it is a **stored**-vs-document comparison where a whitespace change genuinely is a document change. Every stored snapshot comes from `captureSnapshot`'s own slice (`annotations.ts:316`), never from the caller's string, so a normalized-accepted create still stores the document's real bytes.
- **`findOccurrence` / `countOccurrences` need no flag** — their pattern is caller-supplied by construction (`tandem_resolveRange`, local-model `resolveAnchor`).
- **No log line on a normalized-only match** — `validateRange` runs once per annotation in the watcher's reload loop, so a warn there is a per-reload multiplier for no reader.
- **`Zs` minus U+0020 is the set.** Tab is not a space separator in Unicode and does not occur in this coordinate system as a substitute for one.

## Not in scope

The issue's item 3 — `tandem_getTextContent` reporting the offsets of the non-ASCII whitespace it returned. That is a new inspection surface, and once the match succeeds there is nothing to inspect. `tandem_search` stays an exact literal/regex find: its `regex: true` mode makes a silent normalization actively wrong and it feeds no range resolution, so it cannot produce the create/resolve contradiction this issue is about. #1621/#1623/#1624 from the same investigation.
