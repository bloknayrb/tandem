# B — #1622 A U+00A0 in the document makes `textSnapshot` unwinnable: `RANGE_GONE` for text that is present

Branch `fix/annotation-anchors-1764`. Closes #1622. Ledger: not a v1-review row — filed 2026-08-26 from the live investigation alongside #1621/#1623/#1624, folded into track B because it is the fifth `textSnapshot` defect. Probe: the issue's own `tandem_resolveRange` table against a document containing NBSP; reproducible offline from the fixture in the tests below.

## Problem

`validateRange`'s staleness gate (`src/server/positions.ts`) compares `fullText.slice(from, to) !== opts.textSnapshot` and, on a mismatch, searches with `indexOf`. Both are exact. `tandem_getTextContent` returns a U+00A0 faithfully, but it is indistinguishable from U+0020 to a model reading the output, so the caller sends back a snapshot with a regular space: the comparison correctly fails, `indexOf` finds nothing, and the tool answers `RANGE_GONE` — "Target text no longer exists in the document" — for text that is right there. The same call with `textSnapshot` omitted succeeds and then **stores** the NBSP-bearing string as the annotation's snapshot, so the stored value differs from the rejected one by one invisible codepoint. The issue rules out both plausible alternative causes (divergent extractors, a live-editing race).

The issue's own proposed fix — relocate to `RANGE_MOVED` with a `whitespaceMismatch` flag — is insufficient, and this is the design call this spec takes. At the *correct* offsets the exact slice still differs, so the retry the caller is told to make comes back `RANGE_MOVED` pointing at the offsets it just passed, forever. A relocation cannot answer a mismatch that is not a relocation.

## Fix

A whitespace-class difference is a **transcription** difference, not evidence the document changed underneath — which is the only thing `textSnapshot` exists to detect. So treat a normalized-equal slice as a match, and reserve relocation for text that actually moved.

- **`src/server/positions.ts`** — one module-private, **length-preserving** normalizer:
  `function normalizeSpaceClass(s: string): string` — `s.replace(/[\u00A0\u1680\u2000-\u200A\u202F\u205F\u3000]/g, " ")`. That set is exactly Unicode `Zs` minus U+0020. **Length-preserving is the invariant**: one code unit in, one out, so every offset computed against the normalized copy is valid against the original — the same constraint `flattenHeadingText` documents. Do not add `\t`, `\r` or `\n` (a newline is a block separator in this coordinate system, and collapsing it would let a range cross a boundary), and do not add zero-width characters (U+200B, U+FEFF) — they are not spaces and normalizing them would be a silent content claim.
- Inside the existing `if (opts?.textSnapshot)` block, in this order:
  1. exact slice comparison — unchanged, and it is still the fast path;
  2. **new:** `normalizeSpaceClass(slice) === normalizeSpaceClass(opts.textSnapshot)` ⇒ fall through as a match (no relocation, no error). This is the issue's headline case.
  3. exact `indexOf` sweep — unchanged, still preferred, so a document with both an exact and a normalized-only occurrence relocates to the exact one;
  4. **new:** when the exact sweep finds nothing, repeat it against `normalizeSpaceClass(fullText)` with the normalized snapshot, and build the same `RANGE_MOVED` from those offsets. Offsets are valid on the original text because the normalization is 1:1.
  5. `RANGE_GONE` only when the normalized sweep is empty too — so the error now means what it says.
- **The order contract is untouched.** CLAUDE.md Critical Rule 4 fixes the sequence integer → ordering → lower bound → **staleness** → upper bound → empty → surrogate → heading. This changes only the comparison *inside* the staleness step; nothing moves across it, and the two pinned accidents (an empty `textSnapshot` skips the gate by truthiness; `from === to` with a snapshot never reaches `"empty"`) are unaffected.
- **No new wire field.** The issue asks for a `whitespaceMismatch` flag so the caller can retry with exact bytes; with (2) there is no longer anything to retry — the call succeeds. Adding a flag to `RANGE_MOVED` would grow the MCP error surface for a case the caller can no longer hit.
- **`docs/mcp-tools.md`** — one line under the range errors: `textSnapshot` matching ignores the difference between U+0020 and the other Unicode space separators, so a snapshot transcribed with ordinary spaces still matches; `RANGE_GONE` means the text is absent under that normalization too.

## Tests

1. `tests/server/positions.test.ts` — fixture containing `"…emails, Teams chats…"`. `validateRange(doc, from, to, { textSnapshot: <same text with U+0020> })` returns `ok` with the range unchanged. The issue's headline; kills the current exact comparison and kills a `RANGE_MOVED`-with-a-flag fix, which would not return `ok`.
2. Same file — **the loop guard**: feed the result of a `RANGE_MOVED` retry back in. A snapshot that is normalized-equal at its own offsets must never answer `RANGE_MOVED` pointing at those same offsets. This is the test that says why the issue's proposal was not taken.
3. Same file — **moved and normalized**: the NBSP-bearing text relocated elsewhere in the document, queried at its old offsets with a U+0020 snapshot ⇒ `RANGE_MOVED` with the true offsets, and `fullText.slice(resolvedFrom, resolvedTo)` is the NBSP-bearing text. Pins that the normalized sweep's offsets are valid on the original string, i.e. that the normalizer is length-preserving.
4. Same file — **`RANGE_GONE` is still reachable**: genuinely deleted text with an ordinary-space snapshot returns `RANGE_GONE`. The issue names this explicitly: without it the fix could turn `RANGE_GONE` into dead code and nothing would notice.
5. Same file — **exact wins over normalized**: a document holding both the exact snapshot and an NBSP variant relocates to the exact occurrence. Kills a fix that normalizes both strings up front and drops the exact sweep.
6. Same file — **newlines are not normalized**: a snapshot with a space where the document has a block separator (`\n`) still fails. Kills a `\s`-class regex.
7. `tests/server/mcp-tool-integration.test.ts` — `tandem_comment` with an ordinary-space snapshot over an NBSP span succeeds and stores the document's real bytes as `textSnapshot`, ending the self-contradiction the issue describes (the identical call without a snapshot already succeeded).

## Done when

The seven specs pass; the issue's live table resolves (`tandem_resolveRange` on the full phrase, `tandem_comment` with the transcribed snapshot); `docs/mcp-tools.md` line lands; typecheck + suite green.

## Assumptions

- **Whitespace-class equality is accepted as a match, not reported as a relocation.** Stated in Fix; the cost is that a real edit which only swapped U+00A0 for U+0020 across the same span no longer reads as stale. That edit is invisible to the caller by construction, which is the whole issue.
- **No log line on a normalized-only match.** `validateRange` runs once per annotation in the watcher's reload loop, so a warn there is a per-reload multiplier for no reader.
- **`Zs` minus U+0020 is the set.** Tab is not a space separator in Unicode and does not occur in this coordinate system's flat text as a substitute for one.

## Not in scope

The issue's item 3 — `tandem_getTextContent` reporting the offsets of the non-ASCII whitespace it returned. That is a new inspection surface, and once the match succeeds there is nothing for the caller to inspect. `tandem_resolveRange`'s own occurrence search (it is exact by design and the issue's table uses it only as a diagnostic). #1621/#1623/#1624 from the same investigation.
