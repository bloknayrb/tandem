# J1 — #1737 tandem skill: tell Claude not to insert line breaks mid-paragraph

## Problem

Tandem's editor soft-wraps prose to the pane width, so there is nothing to gain by hard-wrapping generated text at a fixed column — but nothing in `skills/tandem/SKILL.md` says so, and LLMs default to hard-wrapping. A hard-wrapped mid-paragraph newline reaching `tandem_edit`'s `newText` isn't cosmetic: existing Hard Rule 4 already establishes that `tandem_edit` newlines become literal characters rather than paragraph breaks (rewritten by `J1-1820.md` in this same PR to state the format-conditional version: a soft-wrapped literal line break in Markdown, a real run-level break in `.docx`, refused outright in a plaintext-adapted document — see that spec). A manual mid-paragraph `\n` is exactly the case Rule 4 warns about: a literal break sitting inside what should be one flowing paragraph. It reads wrong in the editor (each "line" renders as its own visual break inside the paragraph) and, in a plaintext-adapted document, is the literal shape Rule 4's `INVALID_ARGUMENT` refusal exists to prevent — and even in Markdown, where it's merely tolerated as literal text, round-tripping through save can turn one logical paragraph into a ragged multi-line block rather than the single line most markdown tooling expects.

## Fix

Add one new Hard Rule to `skills/tandem/SKILL.md`'s Hard Rules section (`:18-27`), placed immediately after the rewritten Rule 4 (see `J1-1820.md` — the two land in the same commit range since both touch this block and #1820 item 1 already establishes the newline-handling context this rule extends): when writing or editing prose destined for Tandem, write each paragraph as one continuous line and let the editor's own soft-wrap handle display — don't insert a **mid-paragraph** line break. Cross-reference Rule 4 rather than re-explaining the `tandem_edit` mechanics.

No source or tool-schema change — this is Claude-facing instruction only.

This kills a fix that adds a generic "write clean prose" rule with no discriminating instruction about *where* a break is and isn't acceptable — the issue is specifically about mid-paragraph breaks, not paragraph boundaries, which remain real newlines.
