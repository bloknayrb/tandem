# Gc2a — #1776 `activity.cursor` is written as a ProseMirror position and published where flat offsets are expected

Branch `fix/position-mapping-1776`. Closes #1776. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:18`. Probe: harness `docs/reviews/2026-09-02-v1-review/experiments/harness/a-bugs.test.ts` describe A (tracked, but run by nothing — it carries its own `vitest.config.ts` and `vitest.config.ts:68` includes only `tests/**/*.test.ts`), re-measured on this branch 2026-09-08 — on `# Title\n\nSome text here\n\n- one\n- two three`, with one `Z` inserted at the flat offset where `three` begins, the plugin publishes `activity.cursor: 38` (a PM position) while `Y_MAP_SELECTION.from` from the same plugin, same transaction, is `32` (the flat offset of `three`). **Reproduce the derivation in the PR body rather than citing the harness path** — the harness is evidence a reviewer has to run by hand.

## Problem

`src/client/editor/extensions/awareness.ts` plugin 2 writes `state.selection.from` — a ProseMirror position — into `Y.Map('userAwareness')` under `Y_MAP_ACTIVITY` at three sites (`:226` capture, `:237` the debounced typing write, `:252` the typing-clear write), while `Y_MAP_SELECTION`, written 40 lines earlier in the same `update()`, goes through `pmSelectionToFlat` (`:182`). The server publishes the value unchanged in `tandem_getActivity` and `tandem_checkInbox`. Two numbers in one payload, in two coordinate systems, neither labelled on the wire.

Five surfaces now disagree in different directions, which is why the current state has to be established before editing any of them:

| Surface | Says today | After this fix |
|---|---|---|
| the wire (`awareness.ts:226,237,252`) | PM position | flat offset |
| tool description (`src/server/mcp/awareness.ts:283`, rewritten by #1907) | "a ProseMirror position, not a flat offset (#1776)" | flat, UTF-16 code units; still a proximity hint |
| `docs/mcp-tools.md:91` (coordinate-systems preamble) | "MCP tools handle the conversion, **with one documented exception** noted under `tandem_getActivity`" | no exception — the clause goes |
| `docs/mcp-tools.md:1044`, `:1063`, `:1105` (corrected by wave 3 group B, #1903) | PM position; "**Do not feed `cursor` to `tandem_edit`…**" | flat, UTF-16; **still a proximity hint, not an edit anchor** |
| `skills/tandem/SKILL.md:86` | says nothing about units | names the coordinate system **and keeps the proximity-hint restriction** |

`refuted.md:43` downgrades the issue's own "documented as flat" premise — no doc *stated* a system when the issue was filed, so this is a naming trap plus a doc omission. The bug itself (a structural position published where every other offset on this wire is flat) stands and is what the fix removes.

**The fix changes the UNITS, not the freshness.** `Y_MAP_ACTIVITY` is written only when the document changes (`awareness.ts:225`, `state.doc !== prevState.doc`): the `isTyping: true` write is 200 ms debounced and the `isTyping: false` write lands `TYPING_DEBOUNCE` = 3000 ms later, and moving the caret without editing never refreshes either. The value carries no `textSnapshot` sibling (`output-schemas.ts:304-309`), so Critical Rule 4's staleness check has nothing to catch a caret that moved, and `tandem_getActivity` keeps returning the last-written `cursor` after `active` has flipped false — the 10 s window gates `active`, not `cursor`. So the "do not use it as a range endpoint" half of the current warning is a **staleness** claim, not a units claim, and it survives this fix unchanged. Every surface below keeps it.

## Fix

**Convert the value; keep the field name.** The alternative — renaming to a PM-labelled field — is rejected: no MCP client holds a ProseMirror document, so a structural position is uninterpretable off-client, and the two docs that name it PM did so as a bug notice, not as a contract. Recorded as an assumption.

- `src/client/editor/extensions/awareness.ts`, plugin 2 `update()` — three sites, model is the `pmSelectionToFlat` call at `:182` in the same function:
  - `:226` `lastCursor = state.selection.from` → `lastCursor = pmPosToFlatOffset(state.doc, toPmPos(state.selection.from))`. Convert at capture time, against the doc the position came from. (This is a **style preference, not a pinned invariant**: `lastCursor` is re-captured on every doc-changing transaction, so a conversion deferred into the 200 ms timer would read the same doc, and none of the tests below can discriminate the two shapes. Prefer capture-time because it keeps the position and the doc it indexes in one expression.)
  - `:237` keeps `cursor: lastCursor`, now flat. No other change.
  - `:252` `cursor: view.state.selection.from` → compute `const cursor = pmPosToFlatOffset(view.state.doc, toPmPos(view.state.selection.from))` **before** the `withBrowser(...)` call and pass it in. Both halves then read one `view.state`.
  - Imports: add `pmPosToFlatOffset` to the existing `../../positions` import at `:18`; `toPmPos` is already imported at `:16`.
  - **Critical Rule 2 holds unchanged**: all three writes stay inside their existing `withBrowser(...)` wrappers, and `withBrowser` stays the helper — these are browser-origin writes and only `browser` generates channel events. Do not put the doc walk inside the transaction callback.
  - Cost, stated per path because the two branches are gated independently (`:181` on selection change, `:225` on doc change): on a **local keystroke** the selection branch already runs two `pmPosToFlatOffset` walks, so this is a third of the same order. On a **remote doc change that does not move the local caret** (Claude editing after the cursor, initial ySync, an undo) the selection branch is skipped entirely, so this goes 0 → 1 walk per synced transaction. Both are O(doc) and acceptable; do not optimise the local path here. If the remote-path walk ever matters, the equivalent-semantics cheaper shape is to capture `lastCursorPm` + `lastCursorDoc` at `:226` and convert inside the timer (PM nodes are immutable, so it converts against exactly the doc the position came from) — one walk per publish rather than per transaction. Out of scope for this fix.

## Tests

**Fixture construction (load-bearing).** Build the Y.Doc with `loadMarkdown` on `# Title\n\nSome text here\n\n- one\n- two three\n` **first**, then bind a `Collaboration` editor with `AwarenessExtension` to it (the pattern in `tests/client/authorship-anchor.test.ts:14`) — not `new Editor({ content })` into an empty doc. Test (3) compares the client's `pmPosToFlatOffset` against the server's `extractText`, and that is only sound if the heading `level` reaches the Y.XmlElement as a JS **number**: `isHeadingLevel` (`src/shared/offsets.ts:46-48`) requires `typeof level === "number"`, and a non-numeric attribute makes `extractText` charge 0 for the `# ` prefix while the client charges 2. **A two-character mismatch on (3) means the heading attribute, not the conversion — do not "fix" the conversion to close it.** The fixture must carry a heading and a list: in a single-paragraph document PM and flat coincide and every assertion below passes with the bug in place.

**Caret placement (load-bearing).** `const flat = extractText(ydoc); const target = toFlatOffset(flat.indexOf("three")); editor.commands.setTextSelection(flatOffsetToPmPos(editor.state.doc, target)); editor.commands.insertContent("Z");` — one character inserted immediately before `three`, so the caret lands at the start of `three` afterwards. That placement is what reproduces the probe's PM 38 / flat 32; typed anywhere else, (1) and (3) are unsatisfiable and the natural retune (an empty slice) is vacuous in every coordinate system.

Write `editor.state.selection.from` and `Y_MAP_SELECTION.from` in full throughout — this spec's whole subject is two identically-named fields in two coordinate systems.

1. **Discriminating-fixture guard.** `editor.state.selection.from` (38, a PM position) ≠ `pmPosToFlatOffset(editor.state.doc, toPmPos(editor.state.selection.from))` (32, flat), and the published `activity.cursor` equals the second, not the first. Kills a fixture that silently stops discriminating if the schema or `extractText` changes.
2. **Typing write is flat, derived independently.** After the keystroke and 250 ms, the primary assertion is `expect(activity.cursor).toBe(pmPosToFlatOffset(editor.state.doc, toPmPos(editor.state.selection.from)))`. `expect(activity.cursor).toBe((userAwareness.get(Y_MAP_SELECTION) as { from: number }).from)` is a **secondary** assertion only. Deriving the expectation from the sibling Y.Map key alone is passed by `cursor: userAwareness.get(Y_MAP_SELECTION).from` — a copy that ships a real bug (the selection branch is gated on `!state.selection.eq(prevState.selection)`, so a remote `tandem_edit` leaves `Y_MAP_SELECTION` stale, and a non-collapsed selection writes the debounced selection **start**, not the caret).
3. **Flat means flat, not merely self-consistent.** `extractText(ydoc).slice(cursor, cursor + 5) === "three"`, asserted together with the slice being non-empty. Kills a conversion that is internally consistent but in the wrong system (both sides converted with the same wrong function).
4. **The typing-clear site too.** After `TYPING_DEBOUNCE`, the `isTyping: false` write's `cursor` satisfies (2)'s independent derivation and (3). Kills fixing only the two burst sites and leaving `:252`.
5. Drive the timers with `vi.useFakeTimers()` + `await vi.advanceTimersByTimeAsync(...)` — probed working against a Collaboration-bound editor on this branch; the plugin's three timers are plain `setTimeout`. Restore real timers in `afterEach` and `editor.destroy()`.
