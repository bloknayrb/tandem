# Gc2a — #1776 `activity.cursor` is written as a ProseMirror position and published where flat offsets are expected

Branch `fix/position-mapping-1776`. Closes #1776. Ledger: `docs/reviews/2026-09-02-v1-review/areas/client-editor.md:18`. Probe: harness `experiments/harness/a-bugs.test.ts` describe A, re-measured on this branch 2026-09-08 — on `# Title\n\nSome text here\n\n- one\n- two three`, one keystroke publishes `activity.cursor: 38` (a PM position) while `Y_MAP_SELECTION.from` from the same plugin, same transaction, is `32` (the flat offset of `three`).

## Problem

`src/client/editor/extensions/awareness.ts` plugin 2 writes `state.selection.from` — a ProseMirror position — into `Y.Map('userAwareness')` under `Y_MAP_ACTIVITY` at three sites (`:226` capture, `:237` the debounced typing write, `:252` the typing-clear write), while `Y_MAP_SELECTION`, written 40 lines earlier in the same `update()`, goes through `pmSelectionToFlat` (`:182`). The server publishes the value unchanged in `tandem_getActivity` (`src/server/mcp/awareness.ts:320`) and `tandem_checkInbox` (`:493`). Two numbers in one payload, in two coordinate systems, neither labelled on the wire.

Three surfaces now disagree in different directions, which is why the current state has to be established before editing any of them:

| Surface | Says today | After this fix |
|---|---|---|
| the wire (`awareness.ts:226,237,252`) | PM position | flat offset |
| tool description (`src/server/mcp/awareness.ts:283`, rewritten by #1907) | "a ProseMirror position, not a flat offset (#1776)" | flat, UTF-16 code units |
| `docs/mcp-tools.md:1044`, `:1063`, `:1105` (corrected by wave 3 group B, #1903) | PM position; "**Do not feed `cursor` to `tandem_edit`…**" | flat, usable |
| `skills/tandem/SKILL.md:86` | says nothing about units | names the coordinate system |

`refuted.md:43` downgrades the issue's own "documented as flat" premise — no doc *stated* a system when the issue was filed, so this is a naming trap plus a doc omission. The bug itself (a structural position published where every other offset on this wire is flat) stands and is what the fix removes.

## Fix

**Convert the value; keep the field name.** The alternative — renaming to a PM-labelled field — is rejected: no MCP client holds a ProseMirror document, so a structural position is uninterpretable off-client, and the two docs that name it PM did so as a bug notice, not as a contract. Recorded as an assumption.

- `src/client/editor/extensions/awareness.ts`, plugin 2 `update()` — three sites, model is the `pmSelectionToFlat` call at `:182` in the same function:
  - `:226` `lastCursor = state.selection.from` → `lastCursor = pmPosToFlatOffset(state.doc, toPmPos(state.selection.from))`. **Convert at capture time, against the doc the position came from.** Deferring the conversion into the 200 ms timer would map a stale PM position through a newer doc — the exact drift this issue is about.
  - `:237` keeps `cursor: lastCursor`, now flat. No other change.
  - `:252` `cursor: view.state.selection.from` → compute `const cursor = pmPosToFlatOffset(view.state.doc, toPmPos(view.state.selection.from))` **before** the `withBrowser(...)` call and pass it in. Both halves then read one `view.state`.
  - Imports: add `pmPosToFlatOffset` to the existing `../../positions` import at `:18`; `toPmPos` is already imported at `:16`.
  - **Critical Rule 2 holds unchanged**: all three writes stay inside their existing `withBrowser(...)` wrappers, and `withBrowser` stays the helper — these are browser-origin writes and only `browser` generates channel events. Do not put the doc walk inside the transaction callback.
  - Cost: one extra `pmPosToFlatOffset` document walk per doc-changing transaction. The selection branch above already runs two of them per keystroke, so this is a third walk of the same order, not a new class of cost. Do not optimise it here.
- `src/server/mcp/awareness.ts`: **no value change** — both publish sites pass through and stay pass-through. Rewrite the description clause at `:283` to "`cursor` is a flat text offset in UTF-16 code units — the same coordinate system as annotation ranges and `tandem_checkInbox`'s `selectedText`."
- `src/server/mcp/document-store.ts:372,380`: `cursor: number` → `cursor: FlatOffset` in `getUserAwareness`'s return type and its Y.Map cast, matching the `selection` sibling on `:371`/`:377`. `FlatOffset` is already imported (`:79`). Type-level label only; it is an assertion over a Y.Map read exactly as `selection`'s is.
- `src/server/mcp/output-schemas.ts:306`: `cursor: z.number().nullable().describe("Flat text offset (UTF-16 code units) of the user's caret — same coordinate system as annotation ranges")`. `.describe()` is the established idiom in this file and `tests/server/mcp-output-schemas.test.ts` validates shape, not descriptions.
- `docs/mcp-tools.md`: replace the bold warning paragraph at `:1044` with one sentence naming the flat system and this fix; `:1063` and `:1105` likewise. Delete "It is the one place in this document where an offset is not in the flat coordinate system" and the "Do not feed `cursor` to…" sentence — both become false the moment this lands.
- `skills/tandem/SKILL.md:86`: append to the existing `tandem_getActivity` bullet — "`cursor` is a flat text offset (UTF-16 code units), the same system as annotation ranges." **Bump `version: 17` → `18`** and move both literals in `tests/skill-instruction-contract.test.ts` in the same commit: the `/^version:\s*17$/m` assertion at `:83` and the `toEqual({ version: "17", bodyHash: "4e3cdecc0e7a" })` at `:335` (bodyHash = first 12 hex of sha256 over the body after the frontmatter block, CRLF-normalised — take it from the failing assertion's own diff). Add a line to the comment block above `:83` saying who moved it and why. **Re-check the number against `origin/master` at rebase time**; the ledger says nothing else in wave 4 touches the skill.

## Tests

2. **Typing write is flat.** After one keystroke and 250 ms, `activity.cursor === selection.from` — the flat twin the same plugin wrote in the same transaction. Kills leaving `:226`/`:237` unconverted.

4. **The typing-clear site too.** After `TYPING_DEBOUNCE`, the `isTyping: false` write's `cursor` is still flat and still satisfies (3). Kills fixing only the two burst sites and leaving `:252`.
5. Drive the timers with `vi.useFakeTimers()` + `await vi.advanceTimersByTimeAsync(...)` — probed working against a Collaboration-bound editor on this branch; the plugin's three timers are plain `setTimeout`. Restore real timers in `afterEach` and `editor.destroy()`.
