## Problem

**1 — the ghost.** `injectCommentsAsAnnotations` (`src/server/file-io/docx-comments.ts`) protects an already-promoted Word comment from re-injection two ways, and both are gated on the same predicate, so they fail together: the index build `if (!isCanonicalWordId(cid)) continue;` (`:555`) and the lookup `const drift = isCanonicalWordId(comment.commentId) ? byCommentId.get(...) : undefined;` (`:756`). For a `w:id` that predicate rejects (`/^\d{1,9}$/` + canonical form), a drifted comment misses `map.has(offsetId)`, gets `drift === undefined`, and the `else` at `:817` injects a fresh note beside the promotion. `docx-comment-export.ts`'s `isImportRoundtrip` bypasses the type/audience gates for import records, so the next save writes **two Word comments for one original** — a change to the user's file (#1448). Verified on this tree: all four ids reach the `else`; `7` does not.

**1a — D2 made the drift path newly reachable, so this is a live window rather than a latent one.** D2 merged as `1aca8bc1` (`fix(docx): walker flat text; refuse image-losing save (#1754 #1755) (#1939)`) and changed `docx-walker.ts`'s `SINGLE_CHAR_ELEMENT` mapping so each single-character element emits mammoth's own character rather than a literal space — three of the eight change *length*. `calculateCommentRanges` (`docx-comments.ts:440-459`) derives every imported comment's flat offsets from that same walk, and `importAnnotationId` mixes those offsets into `offsetId`. So **any previously imported `.docx` containing a tab, line break, hyphen or `w:sym` now produces a different `offsetId` on its next open**: `map.has(offsetId)` misses and the drift path is taken. This sentence belongs in the PR body.

**1b — the same ghost through export.** `reusableCommentId` (`docx-comment-export.ts:189`) reuses the original `w:id` only when `isCanonicalWordId` passes, so a promoted `1000000000` / `-1` / `0123` is written back under a **fresh** id; the next open presents an id the drift index has never seen, and the ghost lands from the opposite end. Fixing only the import half moves the ghost rather than closing it.

**1c — the `nc:` population** #1692 created (a `w:id` beginning `nc:` takes the fallback pre-image, so its `offsetId` moved versus master). Not a defect and the tag clause is not removable; it is closed *incidentally* by the fix below (`nc:x` is short and non-numeric, so it indexes and looks up under its own literal raw id) — assert that rather than restating it as a residual.

**2 — the write-seam census is defeatable.** `tests/server/docx-import-write-seam.test.ts` direction 1 counts `/\b(?:map|repliesMap)\.set\(/` in one file; direction 3's stamp regex matches a signature type annotation or a stamp-then-overwrite spread.

**3 — unbounded ids in stderr.** Eleven `console.error` sites in `docx-comments.ts` interpolate `w:id` / `paraId` / reply-id text (`:281, :292, :300, :331, :453, :563, :567, :601, :627, :749, :857`) — the issue says "seven"; the tree has eleven, counted here rather than carried forward. **They split into two classes and the split is load-bearing for the mutation battery:**

- **Length-unbounded (eight): `:281, :292, :300, :331, :453, :601, :627, :857`.** These read `comment.commentId`, the raw `w:id`, or `paraId` attribute text straight off the parse, so a crafted `.docx` writes arbitrary volume. `:453` joins **every** unclosed id into one line.
- **Already capped at 32 (three): `:563`, `:567`, `:749`.** `:563`/`:567` interpolate `cid`, read from `val?.importSource?.commentId`, which was written sliced at `:652`; `:749` slices both sides explicitly. `logId` still applies here, for the **control-character half only** — the 32-char slice does not exclude a newline or U+0000, so line forging is live at all eleven.

**4 — a stored reply's `annotationId` is never repaired.** In the reply dedup at `:846-861`, when a reply already exists but its stored `annotationId` names a different root than this run's `effectiveKey`, the `continue` fires before anything rebuilds it. `exportableReplies` filters strictly on `reply.annotationId !== annotationId`, so the reply is silently absent from the re-saved `.docx` — the loss class #1691 closed, from a different direction.

## Fix

**The contract, stated once because both consumers must agree on it:** the drift index is sound only when the key it stores equals the key the *next* import will present. Two things decide that key — the stored id survives the `IMPORT_COMMENT_ID_MAX` slice verbatim, and (when Tandem saved in between) export wrote the id back unchanged or under the one rewrite export is allowed to perform. So the two consumers get **different** predicates keyed on their own property, not one widened predicate. This departs from the issue's "give the drift index its own predicate keyed on *survives the slice un-truncated*" only on the export half: "survives the slice" is not expressible on export, whose `w:id` must be a number.

**And the index key is RAW-FIRST, not normalized.** Review round 1 established that a single normalized key (`String(reusableWordId(raw))`) is **non-injective** — `"0123"`, `"123"` and `"-0"`/`"0"` collapse together — and that neither ordering of a bucket-consuming `delete` closes it, because the hazard is reachable with **one** stored record and **two** incoming comments, and because the `if (map.has(offsetId))` arm at `:662` never consults the index at all. A normalized-only key would produce three distinct failures that do not exist on master: a cross-comment content swap (the exact thing `docx-comment-id.ts`'s module doc says the narrow gate exists to prevent), a silently vanished Word comment, and a reply threaded onto the wrong root. The design below fails toward the **accepted duplicate-on-drift** behaviour instead, which is what the module doc already commits to.

### `src/server/file-io/docx-comment-id.ts`

Leaf module, no project imports — keep it that way. Move `IMPORT_COMMENT_ID_MAX` here from `docx-comments.ts:223` (sole `src` consumer, no test importer; drop the `export` there and import it — **no compat re-export**), delete `isCanonicalWordId` (it ends with zero consumers; a rename-and-keep is the overloaded-compat shape this repo refuses), and **rewrite the twenty-line module doc**, which is written entirely about `isCanonicalWordId` and its "two consumers". The new doc must state the two-predicate contract and say plainly *why the export half cannot express "survives the slice"* (its output is an XML attribute that must parse as a number, so length-survival is not a condition it can test).

Two new exports:

- **`reusableWordId(raw: string | undefined): number | null`** — export's predicate. `/^-?\d+$/.test(raw) && String(Number(raw)) === raw` is **not** the condition; the condition is `/^-?\d+$/`, `Number.isSafeInteger(n)` and `-2147483648 <= n <= 2147483647`. Leading zeros therefore reuse `Number("0123") === 123`. The int32 bound is deliberate: `ST_DecimalNumber` is `xsd:integer`, but Word writes int32, and a 16-digit `w:id` in the file we generate risks Word refusing the document — which would be a worse outcome than the ghost. **Negative ids are reused, as an accepted and explicitly unverified change to bytes in the user's file:** `-1` reaching us means it was already in the user's document, but nothing in this tree establishes that Word itself *emits* or *reopens* a negative `w:comment/@w:id` — the only `-1` in evidence is the filer's hand-assembled fixture. Accepted because the alternative reopens 1b for every negative id, and the value written is the value read. Say it in this shape in the module doc: an accepted bound, not a fact.
- **`driftIndexKeys(raw: string | undefined): { raw: string; normalized: string | null } | null`** — the index's predicate. `null` when `!raw || raw.length >= IMPORT_COMMENT_ID_MAX`. Otherwise `raw` verbatim, plus `normalized` = `String(reusableWordId(raw))` **when that is non-null AND differs from `raw`**, else `null`. The length gate (`>=`, not `>`) is what makes the raw key injective: a stored value shorter than the cap cannot be a truncation of anything, so stored === original raw. A stored value of *exactly* the cap is ambiguous (32-char raw, or a truncation of a longer one) and is excluded from both sides together. The `normalized` field exists for exactly one reason and the doc must say so: **it is the id export would have written back for this stored raw**, so it is the only rewrite the next import can legitimately present.

### `docx-comments.ts` — the two-map index

Replace the single `byCommentId` map with two, built in one pass over `map`:

- `byRawId: Map<string, { key, ann }>` — keyed on `driftIndexKeys(cid).raw`.
- `byNormalizedId: Map<string, { key, ann }>` — keyed on `driftIndexKeys(cid).normalized`, only for records where it is non-null.

The existing author/promoted filter (`val.author !== "import" && !isPromoted` → `continue`) and the existing deterministic promoted-preference on a duplicate raw `commentId` both stay exactly as they are, on the **raw** map. That preference is correct where two records genuinely share one raw id.

**Poisoning — a `Set<string>` of normalized keys that lookup must refuse.** Build it in the same pass plus one pre-scan of the incoming `comments` array (`const incomingRaws = new Set(comments.map((c) => c.commentId))`). A normalized key `N`, contributed by a stored record whose raw is `R`, is poisoned when any of:

1. **`incomingRaws.has(R)`** — `R` itself is present in this file un-rewritten, so this run's stored record is claimed by its own raw id and anything presenting as `N` is a *different* comment. This is the one-stored-record / two-incoming case that no `delete` ordering can reach.
2. **another stored record produces `N`** as its own raw or normalized key, with a differing raw — the two-stored-record case, which the promoted-preference at `:559-566` would otherwise resolve *before* any delete could run.
3. `N` is contributed by two or more distinct stored raws (a special case of 2, stated separately because it is what a reader will look for).

Collect the stored raws for clause 2 from **every** record carrying an eligible `importSource.commentId`, not only the ones that pass the author/promoted filter — a record outside the filter still owns its literal id.

A poisoned key degrades to the pre-fix duplicate-on-drift outcome. That is the accepted behaviour, and the poison set must carry a comment saying so.

### `docx-comments.ts` — the lookup and the consuming branches

- `:756` becomes: compute `const k = driftIndexKeys(comment.commentId)` **hoisted above `if (map.has(offsetId))`** at `:662`, then inside the `else`:
  `const drift = k === null ? undefined : (byRawId.get(k.raw) ?? (poisoned.has(k.raw) ? undefined : byNormalizedId.get(k.raw)));`
  Note the normalized lookup uses the **incoming raw** (`k.raw`), not the incoming's own normalized form: `byNormalizedId` is keyed on what export wrote, and export wrote exactly that string. Raw-first is what makes poisoning safe — poisoning can never break a raw match.
- **Consume the bucket** — `byRawId.delete(k.raw)` and `byNormalizedId.delete(k.raw)` — in the drift-update branch (`:761-806`), the promoted-skip branch (`:816`), **and on the `map.has(offsetId)` hit path** (`:662`), which is why the key is hoisted. With raw-first + poisoning the delete is not load-bearing for soundness (two incoming comments can no longer reach one stored record); it is kept as defence-in-depth so the invariant "each stored record is consumed at most once per run" holds literally, and the hit-path delete is what makes that true.
- Update the rationale paragraphs at `:546-554`, `importAnnotationId`'s docblock at `:131-137`, and the `isCanonicalWordId` sentence at `:42` to the two-predicate contract. **Do not touch `annotationPreImage`/`replyPreImage`** — their gate is the delimiter/tag, not this predicate, and every pinned digest in `docx-comments.test.ts:1240-1270` must stay byte-identical.

## The residual, stated as the general condition

The residual class is **every id `reusableWordId` rejects**, not "non-numeric ids". By its own definition that is three populations:

1. **Non-numeric** — `c-9182`. Cannot be written into a `w:id` at all.
2. **Numeric but outside int32** — `3000000000`. `driftIndexKeys` indexes it happily (so the no-save drift path works), but export refuses it, mints a fresh id, and the next open reproduces finding 1b exactly as `c-9182` does.
3. **Raw ids at or past `IMPORT_COMMENT_ID_MAX`** — `driftIndexKeys` returns `null` on both sides, so neither path applies.

Two further residuals, both accepted and both stated in the PR body rather than implied:

- **Pre-existing ghosts are not healed.** A user who promoted a `w:id="1000000000"` comment and saved under current master already has a document whose promoted record keys on `"1000000000"` while the file presents the small id `allocate()` minted. Post-fix the two still never meet: the ghost persists and still double-writes. Healing is a separate mechanism (it would have to write to the annotation store from the save path, which this PR excludes).
- **A promoted import's exported `w:id` may change value once**, on the first save after this PR, as export stops minting a fresh id and starts reusing the original. `commentKey` (`src/server/file-io/docx-verify.ts:157`) reads only author + body, so the save verifier will not notice. It must be stable thereafter — test 2's stability row asserts that.

Populations 1–3 and the healing gap go into **one filed follow-up issue with a number**, referenced from the residual test's comment and from the PR body, before `## Closes #1693` is written. `Closes #1693` still stands: the issue's §1b names `1000000000`, `-1` and `0123` as the reproducing class and all three are closed; the follow-up covers the ids §1b does not name and the healing question it does not ask.
