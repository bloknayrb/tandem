## Problem

**1 — the ghost.** `injectCommentsAsAnnotations` (`src/server/file-io/docx-comments.ts`) protects an already-promoted Word comment from re-injection two ways, and both are gated on the same predicate, so they fail together: the index build `if (!isCanonicalWordId(cid)) continue;` (`:555`) and the lookup `isCanonicalWordId(comment.commentId) ? byCommentId.get(...) : undefined` (`:756`). For a `w:id` that predicate rejects (`/^\d{1,9}$/` + canonical form), a drifted comment misses `map.has(offsetId)`, gets `drift === undefined`, and the `else` at `:817` injects a fresh note beside the promotion. `docx-comment-export.ts`'s `isImportRoundtrip` bypasses the type/audience gates for import records, so the next save writes **two Word comments for one original** (#1448). Verified on this tree: `1000000000`, `-1`, `0123`, `c-9182` all reach the `else`; `7` does not.

**1a — D2 made the drift path newly reachable, so this is a live window rather than a latent one.** D2 (`1aca8bc1`) changed `docx-walker.ts`'s `SINGLE_CHAR_ELEMENT` mapping so each single-character element emits mammoth's own character; three of the eight change *length*. `calculateCommentRanges` derives every imported comment's flat offsets from that same walk and `importAnnotationId` mixes them into `offsetId`, so **any previously imported `.docx` containing a tab, line break, hyphen or `w:sym` now produces a different `offsetId` on its next open** and takes the drift path. Belongs in the PR body.

**1b — the same ghost through export.** `reusableCommentId` (`docx-comment-export.ts:189`) reuses the original `w:id` only when `isCanonicalWordId` passes, so a promoted `1000000000` / `-1` is written back under a **fresh** id and the next open presents an id the drift index has never seen. Fixing only the import half moves the ghost rather than closing it.

**3 — unbounded ids in stderr.** Eleven `console.error` sites in `docx-comments.ts` interpolate `w:id` / `paraId` / reply-id text (`:281, :292, :300, :331, :453, :563, :567, :601, :627, :749, :857`) — the issue says seven; the tree has eleven, counted here rather than carried forward. Eight are length-unbounded (`:281, :292, :300, :331, :453, :601, :627, :857`); three (`:563, :567, :749`) are already sliced at 32 but still admit newlines and NUL, so line forging is live at all eleven. `:453` joins **every** unclosed id into one line.

**4 — a stored reply's `annotationId` is never repaired.** In the reply dedup at `:845-862`, when a reply already exists but its stored `annotationId` names a different root than this run's `effectiveKey`, the `continue` fires before anything rebuilds it. `exportableReplies` filters strictly on `reply.annotationId`, so the reply is silently absent from the re-saved `.docx` — the loss class #1691 closed, from another direction.

## Fix

The issue's own recommendation is adopted: **the two consumers get separate predicates keyed on their own property.** The drift index needs "this stored id survives the slice un-truncated, so it equals the id the next import will present". Export needs "this id can be written into a `w:id` and read back as the same string". Neither is the other, and neither is a widened `isCanonicalWordId`.

### `src/server/file-io/docx-comment-id.ts`

Delete `isCanonicalWordId` (it ends with zero consumers; a rename-and-keep is the overloaded-compat shape this repo refuses) and export **`reusableWordId(raw: string | undefined): number | null`** — `/^-?\d+$/`, `Number.isSafeInteger(n)`, `-2147483648 <= n <= 2147483647`, **and `String(n) === raw`**.

- The round-trip term is what keeps this predicate honest, and it is why `"0123"` is **not** reused. `ExportComment.id` is a `number` (`docx-comment-export.ts:93`), so a stored `"0123"` could only be written back as `123`, and the next import would present an id the stored record does not carry — 1b moved rather than closed. Reusing it verbatim means changing that field to a string and reworking `usedIds`/`allocate` for one hostile form; that is not this fix. `"0123"`'s **no-save** half closes here (test 1); its save-mediated half is a residual, follow-up (b).
- Widening to int32 and to negatives is what closes `1000000000` and `-1` on both halves. **Negative reuse is an accepted and explicitly unverified change to bytes in the user's file:** a `-1` reaching us was already in their document, but nothing in this tree establishes that Word emits or reopens a negative `w:comment/@w:id`. Accepted because the alternative reopens 1b for every negative id and the value written is the value read. Say it in the module doc in that shape — an accepted bound, not a fact.
- **The int32 top edge interacts with `docx-apply.ts` and is recorded, not fixed.** `docx-apply.ts:857` scans `document.xml` for `w:id` numerically and `:869-871` does `maxId += 2` per suggestion, so a reused id within `2 × suggestions` of the ceiling emits a revision id past int32. Clamping would couple a leaf module to that allocator. Follow-up (b). `docx-apply.ts:926` reads `w:id` as a **string** map key, so the wider reuse only makes its `commentLastParaIds` lookup start hitting; `docx-footnotes.ts:120` and `docx-walker.ts:328,338` are other id spaces.
- Rewrite the twenty-line module doc, which is written entirely about `isCanonicalWordId` and its "two consumers".

### `docx-comments.ts` — the index

The drift index keeps its single `byCommentId` map, its existing author/promoted filter and its deterministic promoted-preference. **Only the gate changes**, in both places, to the length condition and nothing else:

- build (`:555`): `if (!cid || cid.length >= IMPORT_COMMENT_ID_MAX) continue;`
- lookup (`:756`): the same test on `comment.commentId`, then `byCommentId.get(comment.commentId)`.

`>=`, not `>`, is what makes the key injective: a stored value shorter than the cap cannot be a truncation of anything, so stored === original raw. A value of exactly the cap is ambiguous (a 32-char raw, or a truncation of a longer one) and is excluded. `IMPORT_COMMENT_ID_MAX` stays where it is (`:223`) — no module move, no new import.

Update the rationale comment at `:546-554`, `importAnnotationId`'s docblock (`:131-137`) and the `isCanonicalWordId` sentence at `:42` to the two-predicate contract. **Do not touch `annotationPreImage` / `replyPreImage`** — their gate is the delimiter, and every pinned digest in `docx-comments.test.ts:1240-1270` must stay byte-identical.

Applied at **all eleven** sites — length at the eight, control characters at all eleven. `:453` additionally caps its join to the first 10 keys plus `(+N more)`. It is a log helper, not a validator: nothing downstream reads these strings. Spell control characters as escapes, never literals — `tests/scripts/src-control-characters.test.ts` scopes `tests/` too.
- **Finding 4:** inside `if (clash)` (`:845`), after the body-differs collision log, add
  `else if (clash.author === "import" && clash.annotationId !== effectiveKey && !map.has(clash.annotationId))` → rewrite through
  `writeImportReply(repliesMap, replyId, { ...clash, annotationId: effectiveKey, private: true, rev: nextRev() })`,
  count into `repairedReplies`, append `(repaired N reply parents)` to the summary at `:880`.
  - **The `!map.has(clash.annotationId)` term is load-bearing.** Without it the repair fires in the residual population (`c-9182`, `nc:x`, `3000000000`), where the drift lookup misses, `:817` injects a ghost and `effectiveKey` becomes the **ghost's** key — while the promotion is still exported (`promotedAnnotation` leaves it `type: "comment"` / `audience: "outbound"` / `status: "pending"`, so all three gates at `docx-comment-export.ts:315-317` pass). `exportableReplies` (`:235-254`) and `collectRepliesForAnnotation` (`src/server/mcp/annotations.ts:81-91`) both key strictly on `annotationId`, so an unconditional reparent moves the reply's text into the ghost's duplicate Word comment and empties the user's promoted thread — a regression master does not have (master `continue`s and leaves the reply on the promotion). ## Residual

Every id `reusableWordId` rejects: **non-numeric** (`c-9182`, and `nc:x` — the population #1692 created; `ST_DecimalNumber` has no representation for it, so this is a permanent property of the format, recorded in the module doc and **deliberately not filed**); **outside int32** (`3000000000` — indexed fine, so the no-save half works, but export mints a fresh id); **non-canonical form** (`0123`, same shape); **raws at or past the cap**.
