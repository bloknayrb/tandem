## Problem

**1 — the ghost.** `injectCommentsAsAnnotations` (`src/server/file-io/docx-comments.ts`) protects an already-promoted Word comment from re-injection two ways, and both are gated on the same predicate, so they fail together: the index build `if (!isCanonicalWordId(cid)) continue;` (`:555`) and the lookup `const drift = isCanonicalWordId(comment.commentId) ? byCommentId.get(...) : undefined;` (`:756`). For a `w:id` that predicate rejects (`/^\d{1,9}$/` + canonical form), a drifted comment misses `map.has(offsetId)`, gets `drift === undefined`, and the `else` at `:817` injects a fresh note beside the promotion. `docx-comment-export.ts`'s `isImportRoundtrip` bypasses the type/audience gates for import records, so the next save writes **two Word comments for one original** — a change to the user's file (#1448). Verified on this tree: all four ids reach the `else`; `7` does not.

**1b — the same ghost through export.** `reusableCommentId` (`docx-comment-export.ts:189`) reuses the original `w:id` only when `isCanonicalWordId` passes, so a promoted `1000000000` / `-1` / `0123` is written back under a **fresh** id; the next open presents an id the drift index has never seen, and the ghost lands from the opposite end. Fixing only the import half moves the ghost rather than closing it.

**1c — the `nc:` population** #1692 created (a `w:id` beginning `nc:` takes the fallback pre-image, so its `offsetId` moved versus master). Not a defect and the tag clause is not removable; it is closed *incidentally* by the fix below (`nc:x` is short and non-numeric, so it indexes and looks up under its own literal id) — assert that rather than restating it as a residual.

**2 — the write-seam census is defeatable.** `tests/server/docx-import-write-seam.test.ts` direction 1 counts `/\b(?:map|repliesMap)\.set\(/` in one file; direction 3's stamp regex matches a signature type annotation or a stamp-then-overwrite spread.

**3 — unbounded ids in stderr.** Eleven `console.error` sites in `docx-comments.ts` interpolate raw `w:id` / `paraId` attribute text (`:281, :292, :300, :331, :453, :563, :567, :601, :627, :749, :857`) — the issue says "seven"; the tree has eleven, counted here rather than carried forward. `:453` joins **every** unclosed id into one line. `w:id` is capped only where it is *stored*, so a crafted `.docx` writes arbitrary volume, and a `w:id` containing `\n` forges log lines.

**4 — a stored reply's `annotationId` is never repaired.** In the reply dedup at `:846-861`, when a reply already exists but its stored `annotationId` names a different root than this run's `effectiveKey`, the `continue` fires before anything rebuilds it. `exportableReplies` filters strictly on `reply.annotationId !== annotationId`, so the reply is silently absent from the re-saved `.docx` — the loss class #1691 closed, from a different direction.

## Fix

**The contract, stated once because both consumers must agree on it:** the drift index is sound only when the key it stores equals the key the *next* import will present. Two things decide that key — the stored id survives the `IMPORT_COMMENT_ID_MAX` slice verbatim, and (when Tandem saved in between) export wrote the id back unchanged. So the two consumers get **different** predicates keyed on their own property, not one widened predicate. This departs from the issue's "give the drift index its own predicate keyed on *survives the slice un-truncated*" only on the export half: "survives the slice" is not expressible on export, whose `w:id` must be a number.

`src/server/file-io/docx-comment-id.ts` (leaf module, no project imports — keep it that way): move `IMPORT_COMMENT_ID_MAX` here from `docx-comments.ts:223` (sole `src` consumer, no test importer; drop the `export` there and import it — **no compat re-export**), delete `isCanonicalWordId` (it ends with zero consumers; a rename-and-keep is the overloaded-compat shape this repo refuses), and add two:

- `reusableWordId(raw: string | undefined): number | null` — export's predicate. `/^-?\d+$/.test(raw) && String(Number(raw)) === raw` is **not** the condition; the condition is `/^-?\d+$/`, `Number.isSafeInteger(n)` and `-2147483648 <= n <= 2147483647`. Leading zeros therefore reuse `Number("0123") === 123`. The int32 bound is deliberate: `ST_DecimalNumber` is `xsd:integer`, but Word writes int32, and a 16-digit `w:id` in the file we generate risks Word refusing the document — which would be a worse outcome than the ghost. Negative ids **are** reused: `-1` was already in the user's file and Word opened it, so writing it back is fidelity, not a new value.
- `driftIdentityKey(raw: string | undefined): string | null` — the index's predicate. `null` when `!raw || raw.length >= IMPORT_COMMENT_ID_MAX`; otherwise `String(reusableWordId(raw))` when that is non-null, else `raw` verbatim. The length gate (`>=`, not `>`) is what makes it injective: a stored value shorter than the cap cannot be a truncation of anything, so stored === original raw. A stored value of *exactly* the cap is ambiguous (32-char raw, or a truncation of a longer one) and is excluded from both sides together.

`docx-comments.ts`:
- `:555` → `const key = driftIdentityKey(cid); if (key === null) continue;` and bucket under `key`. `:756` → `const driftKey = driftIdentityKey(comment.commentId); const drift = driftKey === null ? undefined : byCommentId.get(driftKey);`.
- **Consume the bucket**: `byCommentId.delete(driftKey)` in both the drift-update branch (`:761-806`) and the promoted-skip branch (`:816`). Today two incoming comments never share a key (`commentMap` is keyed by `w:id`, so a repeated id collapses at parse); normalization makes `"0123"` and `"123"` share one, and without the delete the second would drift-update the first's record — the cross-comment content swap the module doc exists to prevent. One line, no new mechanism.
- Update the `isCanonicalWordId` rationale paragraphs at `:546-554` and `importAnnotationId`'s docblock `:131-137` to the two-predicate contract. **Do not touch `annotationPreImage`/`replyPreImage`** — their gate is the delimiter/tag, not this predicate, and every pinned digest in `docx-comments.test.ts:1240-1270` must stay byte-identical.
- Finding 3: a module-private `logId(raw: string): string` — it replaces every C0 control character (U+0000 to U+001F), U+007F and the C1 range (U+0080 to U+009F) with U+FFFD, then truncates to 64 units with a trailing ellipsis — applied at all eleven sites. `:453` additionally caps the join to the first 10 keys plus `(+N more)`. It is a log helper, not a validator: nothing downstream reads these strings.
- Finding 4: inside `if (clash)` (`:846`), after the body-differs collision log, add `else if (clash.author === "import" && clash.annotationId !== effectiveKey)` → rewrite through `writeImportReply(repliesMap, replyId, { ...clash, annotationId: effectiveKey, rev: nextRev(clash) })`, count into a new `repairedReplies` and append `(repaired N reply parents)` to the summary at `:880`. **The repair is the arm, not the log**, because the issue's own loss is that export drops the reply: a log leaves the `.docx` wrong. Guarded on `author === "import"` and on the bodies matching (the differing-body case is the genuine id collision and keeps its existing log — reparenting there would move a *different* reply). It must go through `writeImportReply`, not `repliesMap.set`, or the census in finding 2 reds.

`docx-comment-export.ts`: `reusableCommentId` (`:189`) becomes a call to `reusableWordId`; delete the local wrapper and its now-wrong docblock sentence about the shared canonical gate. No other change — `usedIds`/`allocate` (`:410-423`) already dedupe, and a reserved negative id cannot collide with `nextId`, which starts at 1.

Rules that bite: nothing here writes a Y.Doc outside the existing `withInternal` transact (Critical Rule 2 — the writes stay inside `injectCommentsAsAnnotations`'s single `withInternal`, and `writeImportReply` is the funnel). Y.Map keys stay `Y_MAP_ANNOTATIONS` / `Y_MAP_ANNOTATION_REPLIES` (Rule 1). No range logic moves: `anchoredRange(..., { surrogates: "ignore" })` at `:620` stays exactly as it is — comment IMPORT is one of Critical Rule 4's four `"ignore"` callers, and export's outward SNAP is a distinct strategy that this PR does not touch. Imported comments carry no `textSnapshot` (#1764's carve-out), which is why the drift branch strips one rather than trusting it. No MCP tool, no `/api` route, no `data-testid`, no skill change.
