## Problem

**1 — the ghost.** `injectCommentsAsAnnotations` (`src/server/file-io/docx-comments.ts`) protects an already-promoted Word comment from re-injection two ways, and both are gated on the same predicate, so they fail together: the index build `if (!isCanonicalWordId(cid)) continue;` (`:555`) and the lookup `const drift = isCanonicalWordId(comment.commentId) ? byCommentId.get(...) : undefined;` (`:756`). For a `w:id` that predicate rejects (`/^\d{1,9}$/` + canonical form), a drifted comment misses `map.has(offsetId)`, gets `drift === undefined`, and the `else` at `:817` injects a fresh note beside the promotion. `docx-comment-export.ts`'s `isImportRoundtrip` bypasses the type/audience gates for import records, so the next save writes **two Word comments for one original** — a change to the user's file (#1448). Verified on this tree: all four ids reach the `else`; `7` does not.

**1a — D2 made the drift path newly reachable, so this is a live window rather than a latent one.** D2 merged as `1aca8bc1` (`fix(docx): walker flat text; refuse image-losing save (#1754 #1755) (#1939)`) and changed `docx-walker.ts`'s `SINGLE_CHAR_ELEMENT` mapping so each single-character element emits mammoth's own character rather than a literal space — three of the eight change *length*. `calculateCommentRanges` (`docx-comments.ts:440-459`) derives every imported comment's flat offsets from that same walk, and `importAnnotationId` mixes those offsets into `offsetId`. So **any previously imported `.docx` containing a tab, line break, hyphen or `w:sym` now produces a different `offsetId` on its next open**: `map.has(offsetId)` misses and the drift path is taken. This sentence belongs in the PR body.

**1b — the same ghost through export.** `reusableCommentId` (`docx-comment-export.ts:189`) reuses the original `w:id` only when `isCanonicalWordId` passes, so a promoted `1000000000` / `-1` / `0123` is written back under a **fresh** id; the next open presents an id the drift index has never seen, and the ghost lands from the opposite end. Fixing only the import half moves the ghost rather than closing it.

**1c — the `nc:` population** #1692 created (a `w:id` beginning `nc:` takes the fallback pre-image, so its `offsetId` moved versus master). Not a defect and the tag clause is not removable. **Its no-save half is closed incidentally** by the fix below — `nc:x` is short and non-numeric, so it indexes and looks up under its own literal raw id, and test 1 asserts that. **Its save-mediated half is not, and the PR body must not say otherwise:** `nc:x` is non-numeric, so `reusableWordId` refuses it, export mints a fresh id, and the next open behaves exactly like `c-9182` — population 1 of the residual. `nc:x` therefore appears in **both** test 1 (closed) and test 3 (residual), with a comment on each saying which half it is.

**2 — the write-seam census is defeatable.** `tests/server/docx-import-write-seam.test.ts` direction 1 counts `/\b(?:map|repliesMap)\.set\(/` in one file; direction 3's stamp regex matches a signature type annotation or a stamp-then-overwrite spread.

**3 — unbounded ids in stderr.** Eleven `console.error` sites in `docx-comments.ts` interpolate `w:id` / `paraId` / reply-id text (`:281, :292, :300, :331, :453, :563, :567, :601, :627, :749, :857`) — the issue says "seven"; the tree has eleven, counted here rather than carried forward. **They split into two classes and the split is load-bearing for the mutation battery:**

- **Length-unbounded (eight): `:281, :292, :300, :331, :453, :601, :627, :857`.** These read `comment.commentId`, the raw `w:id`, or `paraId` attribute text straight off the parse, so a crafted `.docx` writes arbitrary volume. `:453` joins **every** unclosed id into one line.

## Fix

**The contract, stated once because both consumers must agree on it:** the drift index is sound only when the key it stores equals the key the *next* import will present. Two things decide that key — the stored id survives the `IMPORT_COMMENT_ID_MAX` slice verbatim, and (when Tandem saved in between) export wrote the id back unchanged or under the one rewrite export is allowed to perform. So the two consumers get **different** predicates keyed on their own property, not one widened predicate. This departs from the issue's "give the drift index its own predicate keyed on *survives the slice un-truncated*" only on the export half: "survives the slice" is not expressible on export, whose `w:id` must be a number.

**And the index key is RAW-FIRST, not normalized.** Review round 1 established that a single normalized key (`String(reusableWordId(raw))`) is **non-injective** — `"0123"`, `"123"` and `"-0"`/`"0"` collapse together — and that neither ordering of a bucket-consuming `delete` closes it, because the hazard is reachable with **one** stored record and **two** incoming comments, and because the `if (map.has(offsetId))` arm at `:662` never consults the index at all. A normalized-only key would produce three distinct failures that do not exist on master: a cross-comment content swap (the exact thing `docx-comment-id.ts`'s module doc says the narrow gate exists to prevent), a silently vanished Word comment, and a reply threaded onto the wrong root. The design below fails toward the **accepted duplicate-on-drift** behaviour instead, which is what the module doc already commits to.

### `src/server/file-io/docx-comment-id.ts`

Leaf module, no project imports — keep it that way. Move `IMPORT_COMMENT_ID_MAX` here from `docx-comments.ts:223` (sole `src` consumer, no test importer; drop the `export` there and import it — **no compat re-export**), delete `isCanonicalWordId` (it ends with zero consumers; a rename-and-keep is the overloaded-compat shape this repo refuses), and **rewrite the twenty-line module doc**, which is written entirely about `isCanonicalWordId` and its "two consumers". The new doc must state the two-predicate contract and say plainly *why the export half cannot express "survives the slice"* (its output is an XML attribute that must parse as a number, so length-survival is not a condition it can test).

Two new exports:

- **`reusableWordId(raw: string | undefined): number | null`** — export's predicate. `/^-?\d+$/.test(raw) && String(Number(raw)) === raw` is **not** the condition; the condition is `/^-?\d+$/`, `Number.isSafeInteger(n)` and `-2147483648 <= n <= 2147483647`. Leading zeros therefore reuse `Number("0123") === 123`. The int32 bound is deliberate: `ST_DecimalNumber` is `xsd:integer`, but Word writes int32, and a 16-digit `w:id` in the file we generate risks Word refusing the document — which would be a worse outcome than the ghost. **Negative ids are reused, as an accepted and explicitly unverified change to bytes in the user's file:** `-1` reaching us means it was already in the user's document, but nothing in this tree establishes that Word itself *emits* or *reopens* a negative `w:comment/@w:id` — the only `-1` in evidence is the filer's hand-assembled fixture. Accepted because the alternative reopens 1b for every negative id, and the value written is the value read. Say it in this shape in the module doc: an accepted bound, not a fact. **The one other `src` reader of a `w:id` was checked and is unaffected:** `docx-apply.ts:857` scans `/w:id="(\d+)"/g` to compute a `maxId` for allocating `w:ins`/`w:del` revision ids — an exported `w:id="-1"` simply does not match, and it does not need to, because comment ids and revision ids are separate OOXML id spaces and `maxId` only ever grows from positives. Record that sentence in the module doc so the negatives decision carries its own cross-reference.
- **`driftIndexKeys(raw: string | undefined): { raw: string; normalized: string | null } | null`** — the index's predicate. `null` when `!raw || raw.length >= IMPORT_COMMENT_ID_MAX`. Otherwise `raw` verbatim, plus `normalized` = `String(reusableWordId(raw))` **when that is non-null AND differs from `raw`**, else `null`. The length gate (`>=`, not `>`) is what makes the raw key injective: a stored value shorter than the cap cannot be a truncation of anything, so stored === original raw. A stored value of *exactly* the cap is ambiguous (32-char raw, or a truncation of a longer one) and is excluded from both sides together. The `normalized` field exists for exactly one reason and the doc must say so: **it is the id export would have written back for this stored raw**, so it is the only rewrite the next import can legitimately present. **It is also UNVERIFIABLE, and the doc must say that too** — see the fourth residual below: a normalized hit cannot distinguish "export rewrote this stored id" from "a different comment now carries the normalized id", and its narrowness is the whole of its safety. `normalized` is non-null **only** when `String(reusableWordId(raw)) !== raw`, i.e. only for a leading-zero or `-0` stored raw; `-1`, `1000000000` and `3000000000` all yield `normalized === null` and can never take the fallback.

### `docx-comments.ts` — the two-map index

Replace the single `byCommentId` map with two, built in one pass over `map`:

- `byRawId: Map<string, { key, ann }>` — keyed on `driftIndexKeys(cid).raw`.
- `byNormalizedId: Map<string, { key, ann }>` — keyed on `driftIndexKeys(cid).normalized`, only for records where it is non-null.

The existing author/promoted filter (`val.author !== "import" && !isPromoted` → `continue`) and the existing deterministic promoted-preference on a duplicate raw `commentId` both stay exactly as they are, on the **raw** map. That preference is correct where two records genuinely share one raw id.

**Poisoning — a `Set<string>` of normalized keys that lookup must refuse.** Build it in the same pass plus one pre-scan of the incoming `comments` array (`const incomingRaws = new Set(comments.map((c) => c.commentId))`). A normalized key `N`, contributed by a stored record whose raw is `R`, is poisoned when either of:

1. **`incomingRaws.has(R)`** — `R` itself is present in this file un-rewritten, so this run's stored record is claimed by its own raw id and anything presenting as `N` is a *different* comment. This is the one-stored-record / two-incoming case that no `delete` ordering can reach, **and it is also what protects the `map.has(offsetId)` hit path**: a comment taking that path presents its own raw id, which is by construction in `incomingRaws`, so its stored record's normalized key is poisoned for every other incoming comment in the same run.
2. **Two or more distinct stored raws contribute `N`** — e.g. `"0123"` and `"00123"`. The bucket is ambiguous, so neither record may be reached through it.

Round 1's third clause ("another stored record produces `N` **as its own raw**") is **deliberately dropped, and the reason belongs in the code comment**: the lookup is raw-first, so whenever a stored record's raw equals `N`, `byRawId.get(N)` short-circuits before `poisoned` is ever read. The clause was unreachable in every ordering, and a clause no input can exercise cannot be mutation-tested — it would have shipped as unpinned code with a battery row claiming a kill that cannot happen.

Collect the stored raws for clause 2 from **every** record carrying an eligible `importSource.commentId`, not only the ones that pass the author/promoted filter — a record outside the filter still owns its literal id.

A poisoned key degrades to the pre-fix duplicate-on-drift outcome. That is the accepted behaviour, and the poison set must carry a comment saying so.

### `docx-comments.ts` — the lookup and the consuming branches

- `:756` becomes, **inside the `else`** (no hoist — see below): `const k = driftIndexKeys(comment.commentId)`, then
  `const drift = k === null ? undefined : (byRawId.get(k.raw) ?? (poisoned.has(k.raw) ? undefined : byNormalizedId.get(k.raw)));`
  Note the normalized lookup uses the **incoming raw** (`k.raw`), not the incoming's own normalized form: `byNormalizedId` is keyed on what export wrote, and export wrote exactly that string. Raw-first is what makes poisoning safe — poisoning can never break a raw match.
- **No key is computed on the `map.has(offsetId)` hit path, and nothing is deleted there.** Round 1 required a hoist + a hit-path delete to stop a second incoming comment reaching the hit comment's stored record through the normalized fallback. Poison clause 1 already refuses exactly that, on a strictly wider condition: the hit comment's own raw is in `incomingRaws` by construction, so its normalized key is poisoned for the whole run. The hoist would therefore be dead code whose battery row (round 1's "hit-path key hoist + delete → 5b") names a kill no mutation can produce — and it drags in a nullability trap, because `driftIndexKeys` returns `null` for the ≥32-char ids the existing `docx-comments.test.ts` `"9".repeat(64)` spec already drives down that path. Test 5b stays exactly as specified; it now reds on **clause 1**, which is what actually holds it.
- **Consume the bucket** in the drift-update branch (`:761-806`) and the promoted-skip branch (`:816`), **keyed on the CONSUMED RECORD's own keys, not on `k.raw`.** Round 1 specified `byNormalizedId.delete(k.raw)`, which is wrong whenever the record was reached by raw: a record with raw `"0123"` sits in `byNormalizedId` under `"123"`, so `delete("0123")` misses it and the stated invariant does not hold. Carry the keys in the index value — `{ key, ann, rawKey, normKey }` — and delete `byRawId.delete(hit.rawKey)` plus `if (hit.normKey) byNormalizedId.delete(hit.normKey)`. With raw-first + poisoning this is **not** load-bearing for the well-formed case (two incoming comments with distinct raws can no longer reach one stored record; the proof is one line — the only non-raw route is the normalized fallback, and two distinct incoming raws cannot both equal one `normalized`). It is load-bearing for a **malformed file carrying the same `w:id` twice**, which is the one input that can present one raw twice, and test 5e pins it there rather than leaving it as unpinned defence-in-depth.
- Update the rationale paragraphs at `:546-554`, `importAnnotationId`'s docblock at `:131-137`, and the `isCanonicalWordId` sentence at `:42` to the two-predicate contract. **Do not touch `annotationPreImage`/`replyPreImage`** — their gate is the delimiter/tag, not this predicate, and every pinned digest in `docx-comments.test.ts:1240-1270` must stay byte-identical.

### `docx-comments.ts` — findings 3 and 4

## The residual, stated as the general condition

The residual class is **every id `reusableWordId` rejects**, not "non-numeric ids". By its own definition that is three populations:

1. **Non-numeric** — `c-9182`. Cannot be written into a `w:id` at all.
2. **Numeric but outside int32** — `3000000000`. `driftIndexKeys` indexes it happily (so the no-save drift path works), but export refuses it, mints a fresh id, and the next open reproduces finding 1b exactly as `c-9182` does.
3. **Raw ids at or past `IMPORT_COMMENT_ID_MAX`** — `driftIndexKeys` returns `null` on both sides, so neither path applies.

Three further residuals, all accepted and all stated in the PR body rather than implied:

- **A normalized match is UNVERIFIABLE, and on the promoted-skip arm it can silently swallow a genuine Word comment.** This is a NEW path master does not have, it is the same #1448 class as the bug being fixed, and it is stated here because the three-clause poison set does **not** cover it. The poison clauses fire on `incomingRaws.has(R)` or on two stored raws sharing `N`; neither fires when the stored raw `R` is absent from the file and no second stored record exists — which is exactly the state after a Tandem save (export rewrote `0123` → `123`, so `"0123"` is gone from the file). If the file's `123` is then a **different** comment — Word renumbers `comments.xml` on its own saves — `byNormalizedId.get("123")` hits the promoted record and the promoted-skip branch (`docx-comments.ts:806-816`) sets `effectiveKey` and **injects nothing**: the genuine comment never enters the map, is not exported on the next save, and the #1448 scoreboard cannot score it, because a comment never injected is ABSENT rather than negative. The un-promoted twin is the `drift.ann.author === "import"` arm (`:759-805`), which **overwrites** the stored note's content with the other comment's body — the cross-comment content swap `docx-comment-id.ts`'s module doc says the narrow gate exists to prevent. On master the promoted record is not in the index at all (`:555`), so the incoming comment injects normally.

  **What makes it acceptable is the bound, and the bound must be quoted next to the `normalized` field in `driftIndexKeys`'s doc:** `normalized` is non-null **only** when `String(reusableWordId(raw)) !== raw`, i.e. only for a **leading-zero or `-0`** stored raw. `-1`, `1000000000` and `3000000000` all yield `normalized === null`, so the entire matrix except `0123` is structurally outside this path. The trade is a *possible* swallow for a leading-zero id whose original is gone from the file, against a *certain* duplicate-on-drift for every leading-zero id after every save — and duplicate-on-drift is the very #1448 change to the user's file this PR exists to stop.

  **The clean fix is excluded by scope, and the exclusion is named:** distinguishing the two cases requires stamping the id export actually wrote back onto the stored record, which "Any write to the annotation store from the export/save path" rules out in "Not in scope". It therefore folds into follow-up issue (b) as a line item alongside populations 2–3 and the unhealed ghosts. Test 5 carries a dedicated row (5f) asserting the currently-specified outcome, so the trade is **pinned rather than discovered**.

- **Pre-existing ghosts are not healed.** A user who promoted a `w:id="1000000000"` comment and saved under current master already has a document whose promoted record keys on `"1000000000"` while the file presents the small id `allocate()` minted. Post-fix the two still never meet: the ghost persists and still double-writes. Healing is a separate mechanism (it would have to write to the annotation store from the save path, which this PR excludes).
- **A promoted import's exported `w:id` may change value once**, on the first save after this PR, as export stops minting a fresh id and starts reusing the original. `commentKey` (`src/server/file-io/docx-verify.ts:157`) reads only author + body, so the save verifier will not notice. It must be stable thereafter — test 2's stability row asserts that.

**Follow-up issue (b) is scoped to the CLOSABLE half**: population 2 (numeric but outside int32), population 3 (raw ids at or past the cap), the unhealed pre-existing ghosts, and the unverifiable-normalized-match trade above — each of which has a mechanism that could land. **Population 1 is not in it.** A non-numeric `w:id` has no representation to be written back under (`ST_DecimalNumber`), so it is a permanent property of the format, not a defect, and an issue containing it could never be closed — the untracked-deferral failure in the other direction. It is recorded instead in `docx-comment-id.ts`'s rewritten module doc and in test 3's comment, as a property with a reason. `Closes #1693` still stands: the issue's §1b names `1000000000`, `-1` and `0123` as the reproducing class and all three are closed; the follow-up covers the ids §1b does not name and the healing question it does not ask.
