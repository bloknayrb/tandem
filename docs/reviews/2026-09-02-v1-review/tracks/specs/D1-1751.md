# D1 — #1751 marks inside raw-carrier blocks serialize as literal XML tags on save

Branch `fix/markdown-fidelity-1753`. Closes #1751. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:18`.

**Reproducing the measurements.** `npx tsx docs/reviews/2026-09-02-v1-review/experiments/exp2.ts` (mark leak) and `.../exp8.ts` (`tandem_edit` mark inheritance) are tracked and runnable. For the figures below, a scratch `npx tsx` script that `loadMarkdown`s the fixture, applies a `bold` format to a Y.XmlText range through the doc, and prints `saveMarkdown`. Re-run 2026-09-09.

## Problem

Reproduced verbatim. Loading a document with frontmatter, a footnote definition, a fenced code block and a raw HTML block, applying a `bold` format to the first three characters of each and saving writes:

```
<bold>---</bold>
title: X
---

<bold>[^1</bold>]: A footnote def.

```js
<bold>let</bold> x = 1;
```

<bold><di</bold>v>
raw html
</div>
```

`Y.XmlText.toString()` renders every formatting attribute as an XML element, and **three production readers that write bytes into the user's file use it** (`grep -n 'instanceof Y.XmlText' src/server/file-io/`):

- `mdast-ydoc.ts:886-894`, `getElementPlainText()` — feeds the `case "paragraph"` arm that emits `{ type: "html", value: … }` for any element carrying `MARKDOWN_RAW_ATTR` / `MARKDOWN_HTML_ATTR` (frontmatter, footnote and reference definitions, raw HTML blocks).
- `mdast-ydoc.ts:714-723`, `case "codeBlock"` — its own loop.
- `docx-export.ts:699-705`, `readXmlTextChild()`, whose single caller is `case "codeBlock"` at `:562`. A bold mark inside a fence exports the literal `<bold>let</bold>` into `word/document.xml`. It also **shifts the Word-comment anchor cursor**: `:563-570` feeds that string to `emitTextSegments`, which advances `emit.pos` over the string's own length (`:297`), so every comment anchored after the block lands at a wrong offset.

`html` node values are written **verbatim** by `remark-stringify`, so the tags land unescaped and unwarned. Frontmatter corruption breaks any static-site tool that parses it; a mark in a fence silently changes the code. Reachable client-side by applying a mark across such a block, and server-side by a cross-block `tandem_edit` whose insertion inherits marks from the preceding inline run.

## Fix

One **exported** helper in `mdast-ydoc.ts`, used at all three sites — the model is `getElementText()` in `src/server/mcp/document-model.ts`, which CLAUDE.md's Y.js gotcha already names as the mark-stripping reader ("uses `toDelta()`, not `toString()`"):

```ts
/** Text of a Y.XmlText with every mark stripped. `toString()` renders marks as
 *  XML elements, which raw-carrier blocks write verbatim to the user's file (#1751). */
export function xmlTextPlain(t: Y.XmlText): string {
  let out = "";
  for (const op of t.toDelta()) if (typeof op.insert === "string") out += op.insert;
  return out;
}
```

- `getElementPlainText()` (`mdast-ydoc.ts:886-894`): `child.toString()` → `xmlTextPlain(child)`. Its `hardBreak` sibling branch is untouched — that branch is load-bearing (the function's header explains why both hardBreak forms stay reachable after #1448's `whitespace: "pre"` fix) and an embed carries no `insert: string`, so the sibling walk must remain.
- `case "codeBlock"` (`mdast-ydoc.ts:714-723`): same substitution inside its existing loop.
- `docx-export.ts`'s `readXmlTextChild()` (`:699-705`): same substitution, importing `xmlTextPlain` from `./mdast-ydoc.js`. The import direction has precedent (`plaintext-flatten.ts:3` imports three attrs from the same module), so this adds no new coupling shape. Exported rather than duplicated so a fourth reader cannot be written against `toString()` without the helper sitting beside it.

Deliberately **not** also refusing marks at insertion time (the issue's alternative). The serializer fix closes the failure on disk for all three readers at once — client format, `tandem_edit` inheritance, a future producer — while an edit-time refusal has to enumerate producers and still leaves already-marked in-memory documents writing tags. The mark stays in the Y.Doc (a client showing a raw block bolded keeps showing it bolded until reload); only the bytes on disk are clean. State that in the PR body: a serialization guarantee, not a schema guarantee. State the docx anchor consequence too — the fix restores the anchor offsets by restoring the string length, and no separate change is needed.

Rules that bite: no Y.Doc write is added, so no origin helper and no `audit:origins` surface; no Y.Map key; `toDelta()` on an attached `Y.XmlText` is safe here — every caller is inside `yDocToMdast`, walking a fragment already attached to the doc (the "attach before populating" gotcha is about the build side).

## Tests

`tests/server/markdown-raw-constructs.test.ts` (existing home for #981 raw carriers), each spec **formatting through the Y.Doc and asserting the saved bytes** — a text-only round-trip is green today:

1. Frontmatter — bold the first 5 chars; saved output contains `title: X` and **no** `<bold`. Kills a fix applied only to `codeBlock`.
2. Footnote definition — italic inside `[^1]: …`; saved output equals the input.
3. Raw HTML block — bold across `<div>`; saved output equals the input. Kills a fix applied to the `codeBlock` arm but not to `getElementPlainText`.
4. Code block — bold `let`; saved fence body is exactly `let x = 1;`.
5. **The user's own literal `<bold>` tags survive — the one spec a post-hoc scrub cannot pass.** Specs 1-4 are all satisfied by `saveMarkdown(...).replace(/<\/?bold>/g, "")`. So use a document whose raw HTML block source is literally `<bold>\nliteral\n</bold>` **and** whose fence body is literally `<bold>x</bold>`, apply a mark to a *different* block, and assert the save is byte-identical to the input. Both shapes are measured reachable: the bare `<bold>…</bold>` block parses to one mdast `html` node re-emitted via `getElementPlainText` (`mdast-ydoc.ts:651-652`), and the fenced form feeds the `codeBlock` reader (`:714-722`). Only the `toDelta()` helper passes it.
6. A negative: a bold run in an ordinary paragraph still serializes as `**bold**` (kills a helper accidentally routed into `deltaToPhrasingContent`).
7. **The `.docx` writer**, in the existing docx-export suite under `tests/server/file-io/` (do not start a new suite if one already drives `exportDocx`): a document whose fenced code block carries a bold mark on `let` exports `word/document.xml` containing **no** `<bold`.

`tests/fixtures/roundtrip/raw-blocks.md` is already registered clean in `roundtrip-corpus.test.ts` and must stay clean.

## Done when

All four block types survive a mark + save byte-identical; a document carrying literal `<bold>` tags in a raw block and a fence is byte-identical too; the `.docx` export of a marked fence contains no `<bold`; `markdown-fidelity`, `markdown-raw-constructs`, `roundtrip-corpus` and the docx-export suite green.
