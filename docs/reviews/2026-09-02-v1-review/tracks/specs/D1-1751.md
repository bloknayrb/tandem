## Problem

Reproduced verbatim. Loading `---\ntitle: X\n---\n\n[^1]: A footnote def.\n\n```js\nlet x = 1;\n```\n\n<div>\nraw html\n</div>\n`, applying a `bold` format to the first three characters of each block and saving writes:

```
<bold>---</bold>
title: X
---

<bold>[^1</bold>]: A footnote def.

```js
<bold>let</bold> x = 1;
```

<bold><di</bold>v>
raw html
</div>
```

All four block types leak, and the cause is one line each. `Y.XmlText.toString()` renders every formatting attribute as an XML element; **three production readers that write bytes into the user's file use it** (`grep -n 'instanceof Y.XmlText' src/server/file-io/`):

- `src/server/file-io/mdast-ydoc.ts:886-894`, `getElementPlainText()` — `if (child instanceof Y.XmlText) value += child.toString();`. Feeds the `case "paragraph"` arm that emits `{ type: "html", value: getElementPlainText(el) }` for any element carrying `MARKDOWN_RAW_ATTR` or `MARKDOWN_HTML_ATTR` (frontmatter, footnote/reference definitions, raw HTML blocks).
- Same file, `case "codeBlock"` (`:714-723`) — `value += child.toString();` in its own loop.
- **`src/server/file-io/docx-export.ts:699-705`, `readXmlTextChild()`** — `if (c instanceof Y.XmlText) out += c.toString();`, whose single caller is `case "codeBlock"` at `:562` (`const inner = readXmlTextChild(el);`). This is the `.docx` writer, so a bold mark inside a fence exports the literal `<bold>let</bold>` into `word/document.xml`. **And it desyncs the Word-comment anchor cursor**: `:563-570` splits `inner` into lines and runs `emitTextSegments(line, codeMarks, emit, children)`, which advances `emit.pos += take` over the string's own length (`:297`). An inflated string therefore moves `emit.pos` past every later flat offset, so every Word comment anchored after that code block lands in the wrong place. (`spike-docx-export.ts:340` is the same shape but is a spike, not a production writer, and is out of scope.)

For the markdown writer, `html` node values are written **verbatim** by `remark-stringify`, so the tags land in the file with no escaping and no warning. Frontmatter corruption breaks any static-site tool that parses it; a mark in a code block silently changes the code. For the `.docx` writer the tags land as literal run text and the comment anchors shift.

Reachable two ways: client-side by applying a mark across such a block, and server-side by a cross-block `tandem_edit` whose insertion inherits marks from the preceding inline run (`src/server/mcp/document-model.ts` `mergeInlineTail` / the measured link-inheritance case).

## Fix

One **exported** helper in `mdast-ydoc.ts`, used at all three sites — the model is `getElementText()` in `src/server/mcp/document-model.ts`, which the CLAUDE.md Y.js gotcha already names as the mark-stripping reader ("uses `toDelta()`, not `toString()`"):

```ts
/** Text of a Y.XmlText with every mark stripped. `toString()` renders marks as
 *  XML elements, which raw-carrier blocks write verbatim to the user's file (#1751). */
export function xmlTextPlain(t: Y.XmlText): string {
  let out = "";
  for (const op of t.toDelta()) if (typeof op.insert === "string") out += op.insert;
  return out;
}
```

- `getElementPlainText()` (`mdast-ydoc.ts:886-894`): `child.toString()` → `xmlTextPlain(child)`. Its `hardBreak` sibling branch is untouched — that branch is load-bearing (the function's own header explains why both hardBreak forms stay reachable after #1448's `whitespace: "pre"` fix), and an embed carries no `insert: string` so `toDelta()` skips it, which is why the sibling walk must remain.
- `case "codeBlock"` (`mdast-ydoc.ts:714-723`): same substitution inside its existing loop.
- **`docx-export.ts`'s `readXmlTextChild()` (`:699-705`): same substitution**, importing `xmlTextPlain` from `./mdast-ydoc.js`. The import direction already has precedent — `plaintext-flatten.ts:3` imports `FRONTMATTER_ATTR` / `MARKDOWN_HTML_ATTR` / `MARKDOWN_RAW_ATTR` from the same module — so this adds no new coupling shape. It is `export`ed rather than duplicated precisely so a fourth reader cannot be added against `toString()` without the exported helper sitting next to it in the same file.

Deliberately **not** also refusing marks at insertion time, which the issue offers as an alternative. The serializer fix makes the failure impossible on disk for every producer at once — client format, `tandem_edit` inheritance, a future one — while an edit-time refusal is a second mechanism that has to enumerate producers and would still leave already-marked in-memory documents writing tags. **"Every producer" is a claim about the three readers enumerated in §Problem, and it is only true because the `.docx` writer is fixed here too**; leaving `docx-export.ts` out would have left the same class open on the one path that also shifts comment anchors. The mark stays in the Y.Doc (so a client that shows a raw block bolded keeps showing it bolded until reload); only the bytes on disk are clean. State that in the PR body: this is a serialization guarantee, not a schema guarantee.

Rules that bite: no Y.Doc write is added, so no origin helper and no `audit:origins` surface; no Y.Map key; `toDelta()` on an attached `Y.XmlText` is safe here — every caller is inside `yDocToMdast`, walking a fragment already attached to the doc (the "attach before populating" gotcha is about the build side).

## Tests

`tests/server/markdown-raw-constructs.test.ts` (the existing home for #981 raw carriers), one spec per block type, each **formatting through the Y.Doc and asserting the saved bytes**, because a test that only round-trips text is green today:

1. Frontmatter — bold the first 5 chars of the frontmatter block; saved output contains `title: X` and **no** `<bold`. Kills a fix applied only to `codeBlock`.
2. Footnote definition — italic inside `[^1]: …`; saved output equals the input.
3. Raw HTML block — bold across `<div>`; saved output equals the input. Kills a fix applied only to the `codeBlock` arm and not to `getElementPlainText`, since HTML blocks and footnote defs share that reader with frontmatter but arrive through different attributes.
4. Code block — bold `let`; saved fence body is exactly `let x = 1;`.
5. **Cross-block `tandem_edit` reachability** (the measurement described at the top of this spec, landed as a spec): run the five-step edit from inside a code block into a bold paragraph (`replaceFlatRangeInElement` ×3 + `mergeInlineTail` + `frag.delete`) and assert the save has no `<bold>`. This is the one that fails if someone later "fixes" this at the client instead.
6. A negative: a bold run in an ordinary paragraph still serializes as `**bold**` (kills a helper accidentally routed into `deltaToPhrasingContent`).
7. **The user's own literal `<bold>` tags survive — the one spec a post-hoc scrub cannot pass.** Specs 1-6 are all satisfied by a lazy `saveMarkdown(...).replace(/<\/?bold>/g, "")`: 1 asserts "no `<bold`", 2-4 assert equality on inputs that contain no literal tag, 5 asserts "no `<bold>`", and 6's negative is `**bold**` in an ordinary paragraph. So add a document whose raw HTML block source is literally `<bold>\nliteral\n</bold>` **and** whose fence body is literally `<bold>x</bold>`, with a mark applied to a *different* block, and assert the save is **byte-identical to the input**. Both shapes are measured as reachable: `"<bold>\nliteral\n</bold>\n"` parses to a single mdast `html` block, which `case "paragraph"` re-emits verbatim through `getElementPlainText` (`mdast-ydoc.ts:651-652`), and ` ```html\n<bold>x</bold>\n``` ` parses to a `code` node feeding the `case "codeBlock"` reader (`mdast-ydoc.ts:714-722`). Only the `toDelta()` helper passes it; a scrub deletes the user's own tags. Without this spec the suite does not discriminate the real fix from the corrupting one.

8. **The `.docx` writer, in the existing docx-export suite** (`tests/server/file-io/` — whichever spec file already drives `exportDocx`; do not start a new suite if one owns that entry point). Two assertions on one document whose fenced code block carries a bold mark on `let`:
   - the exported `word/document.xml` contains **no** `<bold` — the third reader is fixed;
   - a Word comment anchored **after** that code block resolves to the **same** flat offsets as the identical document with no mark applied. This is the discriminating half: a fix that scrubbed the tag out of the emitted run text would pass the first assertion and still leave `emit.pos` advanced over the inflated string (`docx-export.ts:297`), silently moving every later comment anchor.

`tests/fixtures/roundtrip/raw-blocks.md` is already registered clean in `roundtrip-corpus.test.ts` and must stay clean.
