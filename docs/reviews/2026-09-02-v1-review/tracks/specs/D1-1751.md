# D1 — #1751 marks inside raw-carrier blocks serialize as literal XML tags on save

Branch `fix/markdown-fidelity-1753`. Closes #1751. Ledger: `docs/reviews/2026-09-02-v1-review/areas/server-data.md:18`.

**Reproducing the measurements** (no probe file is tracked — `experiments/` is not in the worktree, so cite commands, not scripts): case 1 is a scratch `npx tsx` script that `loadMarkdown`s the fixture below, applies a `bold` format to a Y.XmlText range through the doc, and prints `saveMarkdown`. The cross-block `tandem_edit` reachability is the five-step sequence in test 5, driven against `src/server/mcp/document-model.ts`'s `replaceFlatRangeInElement` / `mergeInlineTail`. Both re-run 2026-09-09.

## Problem

Reproduced verbatim. Loading `---\ntitle: X\n---\n\n[^1]: A footnote def.\n\n```js\nlet x = 1;\n```\n\n<div>\nraw html\n</div>\n`, applying a `bold` format to the first three characters of each block and saving writes:

```
<bold>---</bold>
title: X
---

<bold>[^1</bold>]: A footnote def.

```js
<bold>let</bold> x = 1;
```

<bold><di</bold>v>
raw html
</div>
```

All four block types leak, and the cause is one line each. `Y.XmlText.toString()` renders every formatting attribute as an XML element; the raw-carrier read paths use it:

- `src/server/file-io/mdast-ydoc.ts`, `getElementPlainText()` — `if (child instanceof Y.XmlText) value += child.toString();`. Feeds the `case "paragraph"` arm that emits `{ type: "html", value: getElementPlainText(el) }` for any element carrying `MARKDOWN_RAW_ATTR` or `MARKDOWN_HTML_ATTR` (frontmatter, footnote/reference definitions, raw HTML blocks).
- Same file, `case "codeBlock"` — `value += child.toString();` in its own loop.

`html` node values are written **verbatim** by `remark-stringify`, so the tags land in the file with no escaping and no warning. Frontmatter corruption breaks any static-site tool that parses it; a mark in a code block silently changes the code.

Reachable two ways: client-side by applying a mark across such a block, and server-side by a cross-block `tandem_edit` whose insertion inherits marks from the preceding inline run (`src/server/mcp/document-model.ts` `mergeInlineTail` / the measured link-inheritance case).

## Fix

One private helper in `mdast-ydoc.ts`, used at both sites — the model is `getElementText()` in `src/server/mcp/document-model.ts`, which the CLAUDE.md Y.js gotcha already names as the mark-stripping reader ("uses `toDelta()`, not `toString()`"):

```ts
/** Text of a Y.XmlText with every mark stripped. `toString()` renders marks as
 *  XML elements, which raw-carrier blocks write verbatim to the user's file (#1751). */
function xmlTextPlain(t: Y.XmlText): string {
  let out = "";
  for (const op of t.toDelta()) if (typeof op.insert === "string") out += op.insert;
  return out;
}
```

- `getElementPlainText()`: `child.toString()` → `xmlTextPlain(child)`. Its `hardBreak` sibling branch is untouched — that branch is load-bearing (the function's own header explains why both hardBreak forms stay reachable after #1448's `whitespace: "pre"` fix), and an embed carries no `insert: string` so `toDelta()` skips it, which is why the sibling walk must remain.
- `case "codeBlock"`: same substitution inside its existing loop.

Deliberately **not** also refusing marks at insertion time, which the issue offers as an alternative. The serializer fix makes the failure impossible on disk for every producer at once — client format, `tandem_edit` inheritance, a future one — while an edit-time refusal is a second mechanism that has to enumerate producers and would still leave already-marked in-memory documents writing tags. The mark stays in the Y.Doc (so a client that shows a raw block bolded keeps showing it bolded until reload); only the bytes on disk are clean. State that in the PR body: this is a serialization guarantee, not a schema guarantee.

Rules that bite: no Y.Doc write is added, so no origin helper and no `audit:origins` surface; no Y.Map key; `toDelta()` on an attached `Y.XmlText` is safe here — every caller is inside `yDocToMdast`, walking a fragment already attached to the doc (the "attach before populating" gotcha is about the build side).

## Tests

`tests/server/markdown-raw-constructs.test.ts` (the existing home for #981 raw carriers), one spec per block type, each **formatting through the Y.Doc and asserting the saved bytes**, because a test that only round-trips text is green today:

1. Frontmatter — bold the first 5 chars of the frontmatter block; saved output contains `title: X` and **no** `<bold`. Kills a fix applied only to `codeBlock`.
2. Footnote definition — italic inside `[^1]: …`; saved output equals the input.
3. Raw HTML block — bold across `<div>`; saved output equals the input. Kills a fix applied only to the `codeBlock` arm and not to `getElementPlainText`, since HTML blocks and footnote defs share that reader with frontmatter but arrive through different attributes.
4. Code block — bold `let`; saved fence body is exactly `let x = 1;`.
5. **Cross-block `tandem_edit` reachability** (the measurement described at the top of this spec, landed as a spec): run the five-step edit from inside a code block into a bold paragraph (`replaceFlatRangeInElement` ×3 + `mergeInlineTail` + `frag.delete`) and assert the save has no `<bold>`. This is the one that fails if someone later "fixes" this at the client instead.
6. A negative: a bold run in an ordinary paragraph still serializes as `**bold**` (kills a helper accidentally routed into `deltaToPhrasingContent`).
7. **The user's own literal `<bold>` tags survive — the one spec a post-hoc scrub cannot pass.** Specs 1-6 are all satisfied by a lazy `saveMarkdown(...).replace(/<\/?bold>/g, "")`: 1 asserts "no `<bold`", 2-4 assert equality on inputs that contain no literal tag, 5 asserts "no `<bold>`", and 6's negative is `**bold**` in an ordinary paragraph. So add a document whose raw HTML block source is literally `<bold>\nliteral\n</bold>` **and** whose fence body is literally `<bold>x</bold>`, with a mark applied to a *different* block, and assert the save is **byte-identical to the input**. Both shapes are measured as reachable: `"<bold>\nliteral\n</bold>\n"` parses to a single mdast `html` block, which `case "paragraph"` re-emits verbatim through `getElementPlainText` (`mdast-ydoc.ts:651-652`), and ` ```html\n<bold>x</bold>\n``` ` parses to a `code` node feeding the `case "codeBlock"` reader (`mdast-ydoc.ts:714-722`). Only the `toDelta()` helper passes it; a scrub deletes the user's own tags. Without this spec the suite does not discriminate the real fix from the corrupting one.

`tests/fixtures/roundtrip/raw-blocks.md` is already registered clean in `roundtrip-corpus.test.ts` and must stay clean.

## Done when

All four block types survive a mark + save byte-identical; a document carrying literal `<bold>` tags in a raw block and a fence is byte-identical too; the cross-block edit spec is green; `markdown-fidelity`, `markdown-raw-constructs`, `roundtrip-corpus` and `roundtrip-repo-metric` green — **and on the repo-metric, "do not widen `KNOWN_KINDS`" is the whole rule.** Its assertion is `expect(renderDifferent.filter((f) => !KNOWN_KINDS.has(f.kind))).toEqual([])` (`roundtrip-repo-metric.test.ts:244`): set membership one way only, so a kind that *disappears* is invisible to it. Do not treat a green run as evidence about removals.
