# W13c — #1965 Tutorial step 2 has no chat-only advance branch (#1824 item M)

Branch `fix/client-rail-pulse-outline-and-tutorial-fixes-2014`. Closes #1965 (one of the six carve-outs
keeping #1824 open — **no closing keyword for #1824**). Ledger:
`docs/reviews/2026-09-02-v1-review/areas/product.md:26` (the L row ending "tutorial step 2 has no AI-absent
branch"). Probe: the new hook spec below, which is the issue's own stated test.

## Problem

`src/client/hooks/useTutorial.svelte.ts:113-121` — the step-1 effect (the "Ask a question" step,
`OnboardingTutorial.svelte`'s `BASE_STEPS[1]`, displayed as step 2) advances on one condition only:

```ts
if (annotations.some(isNonTutorialUserAnnotation)) { … currentStep = 2; }
```

The step's own copy and `docs/user-guide.md`’s quick-tour item 2 ("Or type in the Chat panel.") both say sending a chat message also completes it. A user
who only uses Chat during that step is stuck: nothing advances, and nothing explains why.

## Fix

The issue's own shape — a fourth getter, matching the three already there. Three files.

**`src/client/hooks/useTutorial.svelte.ts`:**
- `createTutorial(getAnnotations, getEditor, getActiveTabFileName, getChatMessages)` — a fourth parameter
  `getChatMessages: () => ChatMessage[]`, typed from `../../shared/types` (the same module `Annotation`
  comes from in this file). **A getter, not a value**, for the reason `rail-content.svelte.ts:39-46`
  spells out at length: a by-value capture freezes at mount, and `chatState.messages` is `[]` then, so a
  frozen read would make this branch permanently dead — a fix that compiles, ships, and does nothing.
- Extend the step-1 effect's condition, **time-scoped against `stepAdvancedAt`**:

  ```ts
  if (
    annotations.some(isNonTutorialUserAnnotation) ||
    getChatMessages().some((m) => m.author === "user" && m.timestamp > stepAdvancedAt)
  )
  ```

  **The `m.timestamp > stepAdvancedAt` term is required, not a refinement.** Chat is durable and
  app-global: `src/server/session/manager.ts:713-827` snapshots and restores `Y_MAP_CHAT`, and
  `useChatState.svelte.ts:41` repopulates `messages` from the ctrl Y.Doc on connect, while
  `ChatMessage.documentId` is optional (`src/shared/types.ts:676`) so the array is not scoped to the active
  document either. `restartTutorial` (`useTutorial.svelte.ts:167-172`) resets only
  `currentStep`/`stepAdvancedAt`/`completed` — it cannot clear chat history. Without the timestamp term,
  every tutorial replay, and any first run against a server with prior chat, would see the step-0 effect
  advance to 1 and the chat term already true, advancing to 2 in the same flush: the "Ask a question" step
  silently auto-skips, which is the exact failure #1965 exists to fix, inverted. `stepAdvancedAt` is stamped
  on entry to step 1 at `:107-108` (and reset to `0` by `restartTutorial`), and `ChatMessage.timestamp` is a
  required `number` (`src/shared/types.ts:675`). It is a plain `let`, not `$state`, so reading it here adds
  no dependency — the effect still re-runs off `getChatMessages()`/`getAnnotations()`, which is what it
  needs.

  The `stepAdvancedAt = Date.now()` / `currentStep = 2` body is unchanged — the step-2 editor handler's
  2-second guard (`:131`) already depends on that stamp being refreshed on every advance, by either route.
  On tracking: `||` short-circuits, so the chat getter is only evaluated when the annotation term is false,
  which is the only case in which it can decide anything; the effect self-disqualifies on
  `currentStep !== 1` after either advance. (An earlier draft said "both terms are read inside the effect so
  both are tracked" — that sentence was wrong and is deliberately removed, because the same reasoning
  applied elsewhere would be a real bug.)
- **Required, not optional:** a call site that forgets the argument must be a compile error, not a silent
  regression to today's behaviour. `tests/scripts/typecheck-tests-wiring.test.ts` keeps `tests/` typechecked,
  so the one test caller below is caught by `npm run typecheck:tests`.

**`src/client/App.svelte:2186-2190`:** pass `() => chatState.messages` as the fourth argument.
`chatState` is created at `:1966` and exposes `messages` as a getter over `$state`
(`useChatState.svelte.ts:41,196-198`), so the thunk reads live state. It is declared above the
`createTutorial` call, so no reordering is needed.

**`tests/client/use-tutorial-restart.svelte.test.ts:39-43`:** add `() => []` as the fourth argument. That
test never reaches step 1 (it asserts `tutorialActive` and `currentStep === 0` around `restartTutorial`), so
an empty-array stub is sufficient — the issue says so and the source confirms it.

Rules that bite: **no Tiptap event handler is involved** — this reads `$state` inside an existing `$effect`,
not from a ProseMirror dispatch, so `createCoalescingTick` does not apply and adding it would defer the
advance for no reason. ChatPanel stays always mounted (unchanged — nothing here touches mounting). No
`data-testid`, no Y.Doc write, no colour, no skill edit.

## Tests

`tests/client/use-tutorial-chat-advance.svelte.test.ts` (new `.svelte.test.ts` — the runes need the Svelte
compiler; `use-tutorial-restart.svelte.test.ts:22-27` is the harness precedent: `$effect.root` + `flushSync`
+ `happy-dom` for `localStorage`, and `localStorage.clear()` in `afterEach`).

Drive to step 1 the way the hook itself does: `getActiveTabFileName` returns `"welcome.md"`, and the
annotation stub first returns one **resolved** tutorial seed (id prefixed with `TUTORIAL_ANNOTATION_PREFIX`
from `src/shared/constants`, `status !== "pending"`) so the step-0 effect advances to 1. Then swap the stubs
and `flushSync()`. Every chat message stub carries a `timestamp`; the advancing ones must be stamped
**after** the step-0 advance (e.g. `Date.now() + 1000`, or captured from a `vi.setSystemTime` clock), since
the fix compares against `stepAdvancedAt`.

1. **The discriminating spec.** At step 1, `getChatMessages` returns one `{ author: "user", timestamp: <after
   the advance> }` message and `getAnnotations` returns **only the resolved seed** (no user annotation) →
   `currentStep` becomes 2. Kills today's code, and kills any fix that ORs the chat term into the wrong
   step's effect.
2. **Claude-authored messages do not advance.** One `{ author: "claude" }` message, no user annotation →
   still step 1. Kills `chatMessages.length > 0`, which would advance the instant the seeded welcome/Claude
   traffic arrives and make the step un-completable-by-doing.
3. **The annotation route still works.** No chat messages, one non-tutorial user annotation → step 2.
   Kills a fix that replaces the annotation term instead of adding to it.
4. **Empty chat, empty annotations → holds at step 1.** The negative that stops `return true`-shaped
   regressions and pins that the step does not auto-skip.
5. **The getter is live, not frozen — and the liveness is a REASSIGNMENT, not a push.** Inside the
   `$effect.root`, hold the messages in a `$state` variable: `let messages = $state<ChatMessage[]>([])`,
   construct with the thunk `() => messages`, then advance by **reassigning**
   `messages = [...messages, { author: "user", timestamp: <after the advance>, … }]` and `flushSync()` →
   advances. **Both halves are mandatory and an implementer must not write the push version.** A `push` onto
   a plain non-`$state` array changes no tracked dependency, so `flushSync()` re-runs nothing and the spec
   fails for the wrong reason; and even if it did re-run, `createTutorial(…, chatState.messages)` — the
   by-value mutant this spec exists to kill — holds the *same* array object and sees an in-place push
   identically. Reassignment is what a captured value misses and what the effect tracks.
6. **A pre-existing chat message does not advance the step.** At step 1, `getChatMessages` returns one
   `{ author: "user", timestamp: <before the step-1 stamp> }` message and no user annotation → still step
   1. Pins the timestamp term: without it this is the replay case that silently skips "Ask a question" for
   every user with any chat history. The cleanest construction is `vi.useFakeTimers()` with a stub message
   stamped at a time before the step-0 advance.

## Done when

`createTutorial` takes four required getters; the chat term is `m.author === "user" && m.timestamp >
stepAdvancedAt`; `App.svelte` and the one existing test caller pass the fourth argument; the six specs pass,
spec 5 goes red when the getter is replaced by a captured value, and spec 6 goes red when the timestamp
comparison is dropped; `npm run typecheck` and `npm run typecheck:tests` green.

## Review corrections (round 1)

**Adopted**

- *The chat term advances off ANY historical user chat message, so every replay auto-skips step 1*
  (blocking; also raised non-blocking). The Fix section now specifies
  `m.author === "user" && m.timestamp > stepAdvancedAt`, with the durability evidence
  (`session/manager.ts:713-827`, `useChatState.svelte.ts:41`, `restartTutorial` resetting only three cells)
  and the note that `stepAdvancedAt` is a plain `let`, so the read adds no dependency. Spec 6 is new and
  pins it. **This is a code decision, not a product one, so #1965 stays a closer rather than dropping to
  Refs**: the intended behaviour is stated by the step's own copy ("Ask a question" — an action taken
  during the step), the annotation term is already effectively time-scoped because a *new* user annotation
  is what satisfies it, and nothing here needs Bryan.
- *Spec 5 neither runs nor discriminates — an in-place push is invisible to Svelte and is seen identically
  by a by-value capture* (blocking). Spec 5 is rewritten to hold the messages in a `$state` variable and to
  advance by reassignment, with both requirements stated explicitly so the inert version cannot be written.
- *The "both terms are tracked" rationale is wrong — `||` short-circuits* (non-blocking). The sentence is
  removed and replaced with the accurate one, plus a note saying why the old wording was worth deleting even
  though it was harmless here.

**Not adopted**

- *"Drop #1965 to Refs per the group's product-decision rule."* Not adopted: the finding's own preferred
  remedy (compare against `stepAdvancedAt`) is available and is what the spec now does, so no product
  decision is outstanding. The alternative it offered — "state that this matches the annotation term's
  behaviour and is accepted" — is rejected on the merits, since the replay auto-skip is a real regression
  path, not a parity argument.
