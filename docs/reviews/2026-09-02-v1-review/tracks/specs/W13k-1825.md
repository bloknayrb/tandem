## Fix

No source or test change. Each item below is re-verified with file:line evidence and the commit
that landed it; nothing further is needed to close the residue this group was asked to check.

**1. lint-staged JSON key matches nothing.** At the commit the issue's triage sampled
(`aee088f`), the key was the literal string `"**/*.json !package-lock.json"` — lint-staged keys
are single micromatch patterns, so a space-separated negation is not one and the key never
matched any staged file; the command silently ran on zero files. Current `package.json:96-98`
reads `"**/*.json": [...]` with no embedded negation — landed in `018a434a` (#1955, Wave 7
I-release). The exclusion moved to where glob negation actually works: `biome.json:34` carries
`"!package-lock.json"` in `files.includes`, confirmed present in the current tree. **Fixed —
`018a434a`.**

**2. Zero-assertion "does not throw" specs.** The issue named
`awareness.test.ts:130`, `changelog-path.test.ts:32`, `file-watcher.test.ts:178`,
`integrations/apply.test.ts:335`. All four files were rewritten with real assertions in #1783
(Wave 1 K1 test gates, before this issue was even filed against them) — confirmed by reading each
file at and around the cited lines: `tests/server/awareness.test.ts` (real `expect` calls
throughout), `tests/server/changelog-path.test.ts:16-49` (every case asserts a return value or
`existsSync`), `tests/server/file-watcher.test.ts` and `tests/server/integrations/apply.test.ts`
(no "does not throw" title remains — see the swept-repo evidence below). A repo-wide scan for
every `it("...does not throw...")` / `it("...never throws...")` / `it("...no throw...")` title in
`tests/**/*.ts`, with each body's brace-matched (accounting for the one title that embeds a
literal `{0,0}`, which a naive scan misreads as a brace) and checked for `expect(`/`assert(`/
`.rejects`/`.resolves`, found **zero** zero-assertion specs — 30 such titles, all real. **Fixed —
#1783 (Wave 1).**

**3. `cwd-preview.test.ts` silently green on symlink-creation failure.**
`tests/server/launcher/cwd-preview.test.ts:246-261` (`"normalizes Claude's side too, so a
symlinked home is not a permanent nudge"`) wraps `fs.symlinkSync` in try/catch and, on failure
(unprivileged Windows without Developer Mode), calls `ctx.skip()` with the comment `// unprivileged
Windows without Developer Mode: report SKIPPED, not passed (#1825)` — landed in #1973 (`3ab75719`,
Wave 7 K-tests). This machine (Windows 11, this session) does not have symlink privilege
confirmed either way, so the exact branch wasn't re-exercised here, but the code path is present
and unambiguous: a bare `return` inside `it()` (the old shape) reports PASSED in every reporter;
`ctx.skip()` reports SKIPPED. **Fixed — `3ab75719`.**

**4. `annotation-remove-seam.test.ts` / `annotation-reply-seam.test.ts` guard asymmetry.**
`tests/server/annotation-remove-seam.test.ts:376-455` ("who may reach the unguarded mechanism")
now carries the same alias/re-export regex guards `annotation-reply-seam.test.ts:114-119` has —
`not.toMatch(/export\s+(?:const|let|var|function)\s+\w+\s*=?\s*removeAnnotationRecord\b/)` and the
aliased-re-export twin, at `annotation-remove-seam.test.ts:440-445` — plus an occurrence-count pin
on the mechanism itself (`removeAnnotationRecord` == 2: declaration + `removeForClaude`'s call,
`:450-453`), landed in #1973 (`3ab75719`). CLAUDE.md's own Key Patterns bullet documents what each
file pins today and they are **not** identical, by design: `annotation-reply-seam.test.ts` pins an
*additional* occurrence count on `writeReply` (`:92-95`, ==3) because `addUserReply` and the
guarded `replyForClaude` both delegate to a shared **private** mechanism one layer down —
`removeAnnotationRecord` has no such layer (`removeForClaude` calls it directly, `:1679` in
`lifecycle.ts`), so there is nothing analogous to pin. The prior session that landed #1973 recorded
this explicitly in its own PR: "analysis suggests \[the alias/re-export guards\] are likely
*redundant* with the existing occurrence-count check for this single-layer, non-wrapped symbol.
Added anyway, per the issue's explicit ask and for a clearer failure message." That reasoning
still holds against the current tree — the importer-set equality check (`filesMentioning`,
`:397-417` vs. reply's `:35-49`) and the occurrence-count check are present on both files today;
the one thing reply pins and remove does not (the `writeReply` count) has no removal-side referent
to pin. **Fixed — `3ab75719`; the surviving difference is structural, not a gap.**
