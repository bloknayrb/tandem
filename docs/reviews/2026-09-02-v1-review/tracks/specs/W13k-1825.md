**3. `cwd-preview.test.ts` silently green on symlink-creation failure.**
`tests/server/launcher/cwd-preview.test.ts:246-261` (`"normalizes Claude's side too, so a
symlinked home is not a permanent nudge"`) wraps `fs.symlinkSync` in try/catch and, on failure
(unprivileged Windows without Developer Mode), calls `ctx.skip()` at `:255` with the comment
`// unprivileged Windows without Developer Mode: report SKIPPED, not passed (#1825)` — landed in
#1973 (`3ab75719`, Wave 7 K-tests). This machine's symlink privilege wasn't re-exercised in this
session, but #1825's own landing comment (bloknayrb, on `3ab75719`) already ran the inverted
mutation this brief asks for: "Inverted mutation, forcing `symlinkSync` to throw: pre-fix **32
passed**, post-fix **31 passed | 1 skipped**." That is a run, not a read — the bare `return` (old
shape) reported PASSED in every reporter; `ctx.skip()` reports SKIPPED, and the mutation proves the
branch is reachable and that the reporter status actually changes.

One caveat the brief's "report a skip reason" wording raises: `ctx.skip()` is called with no
argument. `vitest@^4.1.0`'s `TestContext.skip(note?)` accepts an optional message that reporters
surface; here the reason lives only in the adjacent source comment, which no reporter prints. A
run that hits this branch shows a bare `SKIPPED` with no inline explanation — the brief's ask is
satisfied by the *mechanism* (skip vs. pass) but not by a reporter-visible *reason*. Judged
sufficient for this pass since the mechanism is what #1529 is about (a skip reads as a skip, not a
pass); a one-line follow-up (`ctx.skip("symlink/junction creation unavailable — unprivileged
Windows without Developer Mode (#1825)")`) would close the gap if a future pass wants it. **Fixed —
`3ab75719`**, with the reporter-visible-reason nuance above and a further open question — see
`bryan`.

**4. `annotation-remove-seam.test.ts` / `annotation-reply-seam.test.ts` guard asymmetry.**
`tests/server/annotation-remove-seam.test.ts:376-455` ("who may reach the unguarded mechanism")
now carries the same alias/re-export regex guards `annotation-reply-seam.test.ts:114-119` has —
`not.toMatch(/export\s+(?:const|let|var|function)\s+\w+\s*=?\s*removeAnnotationRecord\b/)` and the
aliased-re-export twin, at `annotation-remove-seam.test.ts:440-445` — plus an occurrence-count pin
on the mechanism itself (`removeAnnotationRecord` == 2: declaration + `removeForClaude`'s call,
`:451`), landed in #1973 (`3ab75719`). CLAUDE.md's own Key Patterns bullet documents what each
file pins today and they are **not** identical, by design — and round 1 found the prior spec's
account of *why* was narrower than the facts on two points, both now corrected:

  a. **The "one surviving difference" claim was incomplete.** It named only the `writeReply`
     occurrence count. There is a second, orthogonal difference: **who pins "the browser's route
     must not acquire Claude's guard", and how.**
     | | reply | remove |
     |---|---|---|
     | route-must-not-acquire-the-guard | static regex, `annotation-reply-seam.test.ts:68-73` (`not.toMatch(/\bcreateAnnotationLifecycle\b/)` and `not.toMatch(/\.reply\s*\(/)` over `stripComments(...routes/annotation-reply.ts)`) | behavioural: `annotation-remove-seam.test.ts:62-80` drives the real `handleRemoveAnnotation` on a user's own note and asserts `200` + `map.has(id) === false` + the reply thread cleared — which fails exactly the same way a static regex would if the route were rewired onto `lifecycle.remove` |
     | private-mechanism occurrence count | `writeReply` == 3, `:93` (declaration + `addUserReply` + `replyForClaude`) | no referent — `removeForClaude` calls `removeAnnotationRecord` directly, `lifecycle.ts:1679`, with no private layer underneath to count |
     Coverage is equivalent on the first row (the remove seam's behavioural pin is, if anything,
     stronger than a static one — it fails on a *rewire*, which a regex checking for one named
     symbol could miss if the route called a differently-named guarded wrapper), and there is
     genuinely nothing analogous to pin on the second row. But "the one thing reply pins and
     remove does not is the `writeReply` count" understated the first row's existence — it isn't
     absent, it's pinned a different way.
  b. **The occurrence-count regexes are asymmetric in a way this file didn't flag.** Remove's is
     `lifecycle.match(/removeAnnotationRecord/g)` (`:451`, no boundary); reply's equivalent is
     `lifecycle.match(/\baddUserReply\b/g)` (`:127`, `\b`-bounded) and
     `filesMentioning("writeReply")`/`("addUserReply")` are also boundary-matched internally. Per
     CLAUDE.md's "symbol regex needs a trailing boundary" lesson, an unbounded regex over a
     symbol name that is a substring of nothing else in this codebase is not a live hole today
     (`removeAnnotationRecord` has no reachable false-positive superstring in `lifecycle.ts`), but
     it is a one-character divergence in what the two tests pin that the prior spec's "not
     identical, by design" language did not name. Left as-is rather than edited — this pass is
     re-verification, not a code change, and the divergence does not change the conclusion (both
     files' occurrence-count checks are mutation-verified to fire on a wrapper). A follow-up
     tightening `:451` to `/\bremoveAnnotationRecord\b/g` would be a one-line, test-only change if
     a later pass wants full textual symmetry.
  The prior session that landed #1973 recorded this explicitly in its own PR: "analysis suggests
  \[the alias/re-export guards\] are likely *redundant* with the existing occurrence-count check
  for this single-layer, non-wrapped symbol. Added anyway, per the issue's explicit ask and for a
  clearer failure message." That reasoning still holds against the current tree. **Fixed —
  `3ab75719`; the surviving differences are structural (a) and cosmetic (b), neither a gap.**

## bryan

- **Item 3's `catch` arm may be unreachable, which would weaken its own justification.** The
  branch is written for "unprivileged Windows without Developer Mode", but the call it guards is
  `fs.symlinkSync(projA, link, "junction")` — an NTFS *directory junction*, not a true symlink.
  Junctions don't require `SeCreateSymbolicLinkPrivilege` or Developer Mode on Windows; true
  symlinks do. If the `catch` has genuinely never fired on real Windows, it's dead code dressed as
  a fix rather than one, and the #1973 comment's "31 passed | 1 skipped" mutation run *forced*
  `symlinkSync` to throw rather than observing a natural failure, so it doesn't settle whether the
  natural failure mode this comment describes is real. A one-line run on an unprivileged Windows
  box (no elevation, Developer Mode off) settles it either way. Not something to guess at from
  this session — leaving the arm in place either way, since removing it on a hunch is worse than
  leaving an unreachable safety net.
- **Item 4b's regex-boundary divergence** (`removeAnnotationRecord` unbounded vs. `\baddUserReply\b`
  bounded) is judged benign and left unedited in this pass — see item 4's paragraph (b). If a
  later pass wants the two seam files textually symmetric rather than just equivalently safe, that
  one-line tightening is there whenever it's wanted; not urgent enough to bundle into a
  re-verification-only spec.
