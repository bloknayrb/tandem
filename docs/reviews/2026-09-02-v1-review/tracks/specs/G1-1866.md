# G1 — #1866 A failed-write callback that lands after teardown strands the owed wake in a dead closure

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Closes #1866. Ledger: none. #1866 is a follow-up to #1757 (CLOSED), not a `v1-review` row; the sweep ledger row for group G1 is its tracked home. Probe: none needed. The ordering is pinned below by a deterministic test with a mocked `spawn`, not by a timing experiment. #1869 is related, but it is **not** in this group and this PR does not close it.

## Problem

In `createSupervisor` → `spawnOnce` (`src/server/launcher/supervisor.ts`):

- `sendTurn` → `stdin.write(..., cb)`: a failed write runs `clearLatch(); pendingWake = true;`. `pendingWake` is a `let` inside the per-spawn closure.
- `teardownTurnDelivery` (called first thing by `spawned.on("exit")` and `spawned.on("error")`) promotes the owed wake with `if (pendingWake) wakeOwedAcrossSpawns = true; pendingWake = false;`.

When the callback runs after teardown, it sets `pendingWake = true` in a closure whose subscription has already been removed (`unsubscribeFromEvents()`) and whose child is gone. Nothing reads that flag again, and the next spawn checks only `wakeOwedAcrossSpawns`. The wake is lost until some unrelated event arrives. The docblock on `sendTurn` already records this ("strands it (pre-existing, #1866 follow-up)").

A second gap sits beside it, in the same promotion: `teardownTurnDelivery` promotes even when the teardown was caused by an explicit user `stop()`, `relaunch()` or `startFresh()`. `stopInternal` sets `stopRequested = true` and the child's `exit` handler then runs teardown. So a resumed relaunch carries a wake the user never asked for, which #1866's last acceptance criterion rules out.

## Fix

All in `spawnOnce`, `src/server/launcher/supervisor.ts`. Two per-spawn `let`s beside `pendingWake`:

- `let tornDown = false;`
- `let carryOwedWake = false;` — latched at teardown time, so a late callback uses the stop-state as it was *for this spawn*. `respawn` lowers `stopRequested` before the successor spawns, so reading the live value from a late callback would be wrong.

`teardownTurnDelivery`: set `tornDown = true; carryOwedWake = !stopRequested;` first, then change the promotion to `if (pendingWake && carryOwedWake) wakeOwedAcrossSpawns = true;`. Everything else in it stays as it is.

`sendTurn`'s write callback becomes:

```ts
clearLatch();
if (tornDown) {
  if (carryOwedWake) wakeOwedAcrossSpawns = true;
} else {
  pendingWake = true;
}
```

A stale callback therefore touches only its own closure (`clearLatch`, whose timers are per-spawn) and a supervisor-level boolean. It never writes to `child` or to a successor's stdin (acceptance criterion 3). `wakeOwedAcrossSpawns` is a boolean, so N late callbacks from one failed write, or the callback plus the stream `'error'`, still mean one wake, never a duplicate. Coalescing (`onTandemEvent` / `flushPendingWake`) is untouched.

`stopInternal`: also clear `wakeOwedAcrossSpawns = false` next to the `releaseTurnDelivery()` calls. Without that, a wake owed by an earlier crash that no spawn has discharged yet would survive a user stop. This keeps the reset in the same place as the breaker's own user-action reset (`respawn` clears `breakerTripped` / `recentAttempts`).

Update the `sendTurn` docblock: remove the "strands it (pre-existing, #1866 follow-up)" clause and describe the latch.

**Ordering assumption, stated because no test can pin it:** the successor spawn is created by `scheduleRestart` behind a `setTimeout` of `restartBackoffs[0]` (1 s in production), or by a user action that sets `stopRequested`. A callback for a write that failed on the dead pipe settles within a few event-loop ticks of that pipe's `'error'`. So in production the late promotion lands before the successor reads `wakeOwedAcrossSpawns`. With `restartBackoffsMs: [0]` a test could in principle schedule the successor first, which is why the test below drives the callback explicitly *before* the successor spawns.

CLAUDE.md rules that bite: none of Critical Rules 1–9 touch this file (no Y.Doc writes, no ranges, no routes). Do not break the `child === spawned` identity-guard convention. The new flags are closure-local for the same reason.

## Tests

New file `tests/server/launcher/supervisor-turn-delivery.test.ts`. It has to be new because it `vi.mock`s `node:child_process`, which is file-wide and hoisted. G1-1867, G1-1868 and G1-1780 share it. The harness:

- `spawn` returns a fake `ChildProcess`: an `EventEmitter` with `pid`, `exitCode`/`signalCode` (`null`), and a `kill` spy that sets `signalCode` and emits `exit`.
- `stdin` is `{ writable: true, write(data, cb) { writes.push({ data, cb }) }, on() {} }`, so the test holds every write callback and decides when it runs.
- `stdout` and `stderr` are `PassThrough` streams.
- It emits `spawn` on the next tick. `TANDEM_REAPER_PATH = process.execPath` (so `reaperPath()`'s `existsSync` passes), a real integrations file in a `tandem-`-prefixed temp dir, `subscribeToEvents` injected, and `restartBackoffsMs: [0]`.

1. **Teardown before callback carries exactly one wake.** `startFresh(dir)` gives child 1 with a pending bootstrap write. Push a `result` line on stdout, emit an annotation event (write W1, callback held), then emit child 1 `exit` (code 1). Run W1's callback with an `EPIPE` error, and only then let the restart spawn child 2, which resumes. Assert child 2's writes are exactly `[SUPERVISOR_WAKE_PROMPT]`. *Kills* the unfixed callback (zero writes), and any queue in place of the boolean (two writes).
2. **Callback before teardown is unchanged.** Same flow, but the callback runs before `exit`. Child 2 again gets exactly one wake. *Kills* a fix that moves the promotion to the callback only.
3. **A stale callback cannot reach the successor.** After test 1's successor is up, run a *second* held callback from child 1 with an error. Child 2's write count and `kill` spy are unchanged. *Kills* a callback that calls `sendTurn`/`flushPendingWake` via `child`.
4. **User stop carries no wake.** With a pending wake in flight, `await sup.stop()`, run the held callback with an error, then `relaunch(dir)` (resumed). Child 2 gets zero writes. *Kills* promotion that reads live `stopRequested` or skips the latch. Mutation-check `carryOwedWake` in both places.
5. Existing `stream-json-protocol.test.ts` cases "coalesces a burst arriving mid-turn into exactly one wake", "carries an undelivered wake across a crash restart" and "a failed wake write ends the child…" stay green unchanged. They are the coalescing and crash-carry controls.

Mutation plan: revert the `if (tornDown)` branch → test 1 red. Drop `carryOwedWake` from teardown → test 4 red. Drop the `stopInternal` clear → a variant of test 4 red, where the wake is owed from a crash before the stop. Restore from a file copy.
