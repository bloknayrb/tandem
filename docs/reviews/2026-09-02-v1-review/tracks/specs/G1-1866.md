# G1 — #1866 A failed-write callback that lands after teardown strands the owed wake in a dead closure

Branch `fix/launcher-stdin-wake-delivery-and-the-logged-out-claude-code-dead-end-1866`. Closes #1866. Ledger: none. #1866 is a follow-up to #1757 (CLOSED), not a `v1-review` row; the sweep ledger row for group G1 is its tracked home. Probe: none needed. The ordering is pinned below by deterministic tests with a mocked `spawn`, not by a timing experiment. #1869 is related, but it is **not** in this group and this PR does not close it.

**Base.** Rebase onto `origin/master` before implementing. At round 1 (2026-09-15) that is `c1a4df93`: #1987 has merged, so its files are free. #1989 is still open and still owns `docs/release-smoke-checklist.md`.

## Problem

In `createSupervisor` → `spawnOnce` (`src/server/launcher/supervisor.ts`):

- `sendTurn` → `stdin.write(..., cb)`: a failed write runs `clearLatch(); pendingWake = true;`. `pendingWake` is a `let` inside the per-spawn closure.
- `teardownTurnDelivery` (called first thing by `spawned.on("exit")` and `spawned.on("error")`, and by `stopInternal` via `releaseTurnDelivery`) promotes the owed wake with `if (pendingWake) wakeOwedAcrossSpawns = true; pendingWake = false;`.

When the callback runs after teardown, it sets `pendingWake = true` in a closure whose subscription has already been removed (`unsubscribeFromEvents()`) and whose child is gone. Nothing reads that flag again, and the next spawn checks only `wakeOwedAcrossSpawns`. The wake is lost until some unrelated event arrives. The docblock on `sendTurn` already records this ("strands it (pre-existing, #1866 follow-up)").

A second gap, which #1866's last acceptance criterion names: nothing distinguishes an explicit user `stop()` from a crash. `stop()` tears the child down through the same promotion, and a wake that a crash owed before the stop also survives it. A later `start()` then resumes and delivers a wake the user stopped Claude to avoid.

## Semantics decided here

- **Explicit `stop()`** carries no wake to a later spawn. That covers a wake in flight on the stopped child, a late callback from it, and a wake owed by an earlier crash.
- **`relaunch()` / `startFresh()`** are recovery, not a stop. They carry an owed wake, both one owed by an earlier crash (the "Restart Claude Code" CTA after a breaker trip) and one pending on the live child they replace. Dropping it there is #1866's own symptom. `startFresh` sends the bootstrap turn anyway, which discharges it.
- A late callback uses the stop-state **latched at this spawn's first teardown**, never the live value. Both `startInternal` and `respawn` lower the flags before the successor reads `wakeOwedAcrossSpawns`.

## Fix

All in `src/server/launcher/supervisor.ts`.

**Supervisor-level.** Add `let userStopped = false;` beside `stopRequested`, with a docblock: raised only by the public `stop()`, never by `stopInternal`, so `respawn` does not look like a stop. The public `stop()` becomes:

```ts
async function stop(): Promise<void> {
  return withLock(async () => {
    userStopped = true;
    // Before stopInternal, not after, so this spawn's teardown latch is what
    // decides (and is what the tests can see).
    wakeOwedAcrossSpawns = false;
    await stopInternal();
  });
}
```

`startInternal` and `respawn` set `userStopped = false` next to their existing `stopRequested = false`. `stopInternal` gets **no** new clear. `respawn` calls `stopInternal` first, so a clear there would drop a crash-owed wake on every Restart.

**Per spawn, beside `pendingWake`:**

- `let tornDown = false;`
- `let carryOwedWake = true;`

`teardownTurnDelivery` begins with a first-run-only latch, because it is documented as idempotent and can run twice. On the abandoned-handle path, `stopInternal`'s `releaseTurnDelivery` runs it during a stop, and the process's `exit` may run it again after `start()` lowered the flag:

```ts
if (!tornDown) {
  tornDown = true;
  carryOwedWake = !userStopped;
}
```

The promotion then becomes `if (pendingWake && carryOwedWake) wakeOwedAcrossSpawns = true;`. Everything else in teardown stays as it is.

`sendTurn`'s write callback becomes:

```ts
clearLatch();
if (tornDown) {
  if (carryOwedWake) wakeOwedAcrossSpawns = true;
} else {
  pendingWake = true;
}
```

A stale callback therefore touches only its own closure (`clearLatch`, whose timers are per-spawn) and one supervisor-level boolean. It never writes to `child`, to its own dead stdin, or to a successor's stdin (acceptance criterion 3). `wakeOwedAcrossSpawns` is a boolean, so N late callbacks from one failed write, or the callback plus the stream `'error'`, still mean one wake, never a duplicate. Coalescing (`onTandemEvent` / `flushPendingWake`) is untouched.

**`sendTurn` docblock.** Remove the "strands it (pre-existing, #1866 follow-up)" clause, describe the latch, and state the bounded cost. A late callback that lands after a successor already consumed `wakeOwedAcrossSpawns` sets it again, so that successor's own resumed successor gets one extra payload-free wake. Its worst case is one extra nudge, never a lost one.

**Ordering, stated because production timing is not what the tests pin:** `scheduleRestart` creates the successor behind `setTimeout(restartBackoffs[...])` (1 s at the shortest production rung, or 1 s again once `restartIndex` resets after 30 s alive). A callback for a write that failed on the dead pipe settles within a few event-loop ticks of that pipe's `'error'`. So in production the late promotion normally lands before the successor reads the flag. If it lands after, the cost is the bounded extra wake above. The tests drive both orderings explicitly rather than relying on this.

CLAUDE.md rules that bite: none of Critical Rules 1–9 touch this file (no Y.Doc writes, no ranges, no routes). Critical Rule 3: every log goes through `console.error`. Do not break the `child === spawned` identity-guard convention. The new per-spawn flags are closure-local for the same reason.

## Tests

New file `tests/server/launcher/supervisor-turn-delivery.test.ts`. It has to be new because it `vi.mock`s `node:child_process`, which is file-wide and hoisted. G1-1867, G1-1868 and G1-1780 share it. **The harness is load-bearing for every spec in this group, so its behaviour is specified exactly:**

- `vi.mock("node:child_process", async (importOriginal) => ({ ...(await importOriginal()), spawn: vi.fn() }))`. Spread the original: `integrations/storage.ts` → `acl-win.ts` imports `execFile`, and on win32 a factory returning only `spawn` throws "No execFile export defined on the mock" on Bryan's local run while ubuntu CI stays green.
- `spawn` returns a fake child: an `EventEmitter` with `pid`, `exitCode = null`, `signalCode = null` and `killed = false`. Its `kill` spy mirrors real Node ordering: it sets `killed = true` synchronously and returns `true`, then on `setImmediate`, unless `exitCode`/`signalCode` is already set, sets `signalCode = sig` and emits `exit(null, sig)`. It must **not** set `signalCode` synchronously. Real Node sets it only at exit, and a synchronous set would make `makeStdinGoneHandler`'s liveness guard hide a second `onKill` (G1-1868 test 4). It must **not** emit `exit` synchronously either: `stopInternal` calls `c.kill` before `c.once("exit")`, so a synchronous emit is missed and every `stop()` waits `SIGTERM_GRACE_MS` 6 s plus 4 s against the 15 s `testTimeout`.
- A helper `exitChild(child, code, signal = null)` sets `exitCode`/`signalCode` and then emits `exit`. It is used for crashes the supervisor did not cause.
- `stdin` is an `EventEmitter` that **keeps its listeners** (so `attachChildStreamErrorHandlers`'s `'error'` listener is real), with a mutable `writable = true` and `write(data, cb) { writes.push({ data, cb }); return true; }`. The test holds every callback and decides when, and how, it runs.
- A helper `failWrite(child, entries = all held)` reproduces the measured order recorded at `supervisor.ts` in the `attachChildStreamErrorHandlers` docblock: set `stdin.writable = false`, run each held `cb(EPIPE)`, then `setImmediate(() => stdin.emit("error", EPIPE))`. A second helper, `failCallbacksOnly(entries)`, runs the callbacks with no stream `'error'`, for the orderings below that need the callback without a kill.
- `stdout` and `stderr` are `PassThrough` streams. `spawn` is emitted on `setImmediate`.
- `TANDEM_REAPER_PATH = process.execPath` (so `reaperPath()`'s `existsSync` passes), a real integrations file in `fs.mkdtempSync(path.join(os.tmpdir(), "tandem-"))`, `subscribeToEvents` injected, `probeCliUsable` injected (default `() => true`), and `restartBackoffsMs: [0]` unless a test says otherwise. `afterEach` awaits `sup.stop()` and removes the temp dir.
- Fresh versus resumed follows the real session file. A fresh spawn persists its id. A delivery kill (`exit(null, "SIGTERM")`) never clears it. An `exitChild(resumed, 1)` inside `RESUME_CONFIRM_MS` clears it, so the next spawn is fresh. Each test states which spawn it expects.

1. **Teardown before callback carries exactly one wake.** `startFresh(dir)` → child 1 with bootstrap write B, whose callback is held. Push a `result` line, then emit an annotation event → write W1 (callback held). In one synchronous block: `exitChild(child1, 1)`, then `failCallbacksOnly([B, W1])`. Await child 2 (resumed). Assert child 2's writes are exactly `[SUPERVISOR_WAKE_PROMPT]`. *Kills:* the unfixed callback (zero writes), and a queue in place of the boolean (two failed callbacks → two writes).
2. **Callback before teardown is unchanged.** Same flow, but `failCallbacksOnly([W1])` runs before `exitChild`. Child 2 again gets exactly one wake. *Kills* a fix that deletes the teardown promotion and relies on the callback alone.
3. **A stale callback cannot reach the successor (regression control plus bounded-cost pin).** Test 1's flow, but B's callback is held back. After child 2 is up and its `[WAKE]` recorded, run `failCallbacksOnly([B])`. Assert child 1's writes are still exactly `[B, W1]`, child 2's writes are still `[WAKE]`, and child 2's `kill` was not called. Then push `init` + `result` into child 2 and `exitChild(child2, null, "SIGTERM")` (a signal exit keeps the session, so child 3 resumes). Assert child 3's writes are exactly `[WAKE]`: the one extra nudge the `sendTurn` docblock documents. This case passes on the unfixed code for its first half, which is why it is labelled a control. *Kills:* a callback that calls `sendTurn`/`flushPendingWake` on its own spawn (child 1's writes grow). The child-3 assertion pins the documented cost, so a later change to it is deliberate rather than silent.
4. **User stop: a late callback carries nothing, even one landing after `start()` lowered the flags.** Child 1 via `startFresh`, a `result`, then an event → W1 (held). `await sup.stop()`. Then call `sup.start()`, and in the **`spawn` mock implementation for child 2** (which runs at the top of `spawnOnce`, before the resumed branch reads `wakeOwedAcrossSpawns`) run `failCallbacksOnly([W1])` before returning the fake child. Assert child 2's writes are `[]`. *Kills:* a callback that ignores `carryOwedWake` (always promotes), and one that reads live `userStopped`/`stopRequested` (both already lowered by `startInternal` at that moment). Uses `start()`, not `relaunch()`.
5. **User stop: a wake pending at teardown is not promoted.** Child 1, a `result`, an event → W1, then `failCallbacksOnly([W1])` while child 1 is alive (so `pendingWake = true`). `await sup.stop()`, then `await sup.start()`. Child 2's writes are `[]`. *Kills* a teardown promotion that ignores the latch. That mutant is visible only because `stop()` clears the flag **before** `stopInternal`.
6. **User stop drops a wake a crash owed earlier.** `restartBackoffsMs: [5_000]`. Child 2's writes are `[]`. *Kills* removing the clear in `stop()`.
7. **Relaunch keeps a wake a crash owed.** Test 6's crash, then `await sup.relaunch(dir)` instead of stop/start. Child 2 (resumed) gets exactly `[WAKE]`. *Kills* moving the clear into `stopInternal`, which `respawn` calls first.

## Review corrections (round 1)

**Adopted**
- The `stopInternal` clear is removed. It stranded a crash-owed wake on every Restart/Relaunch because `respawn` calls `stopInternal` first. The clear now lives in the public `stop()` only, placed before `stopInternal`. Tests 6 and 7 pin both sides.
- Test 4 no longer ends in `relaunch()`, whose `stopInternal` masked the callback mutants. It uses `start()`, and the late callback runs inside the child-2 `spawn` mock, after `startInternal` lowered the flags. That is what makes the live-read mutant go red. Separate cases cover the `stop()` clear (6), the teardown promotion (5) and relaunch carry (7, 8), each with its own mutation row. The earlier "drop `carryOwedWake` from teardown → test 4 red" claim is withdrawn.
- The latch keys on a new `userStopped` (raised only by `stop()`) instead of `stopRequested`. That makes relaunch/startFresh carry a wake pending on the live child rather than dropping it, since #1866's goal is to not lose that wake.
- First-teardown-only latch (`if (!tornDown)`), so the abandoned-handle path cannot flip it back after `respawn`/`start` lowers the flags. Test 9 drives the abandon branch under fake `setTimeout`.
- Harness: stdin is a listener-keeping `EventEmitter` with mutable `writable`, plus a `failWrite` helper in the measured callback-then-error order and a `failCallbacksOnly` helper.
- Harness: fake `kill` sets `killed` synchronously and sets `signalCode` and emits `exit` on `setImmediate`, matching real Node and avoiding the missed-`exit` 10 s wait in `stopInternal`.
- `vi.mock` spreads `importOriginal()`, so the Windows ACL path keeps `execFile`.
- Test 1 fails both held callbacks, so a queue would write twice.
- Test 3 asserts child 1's writes are unchanged, is labelled a regression control, and pins the bounded extra wake on child 3. The `sendTurn` docblock states that worst case.

**Not adopted**
- "Latch `carryOwedWake = !stopRequested`" as written: replaced by `userStopped`, because `stopRequested` is also raised by `respawn`, and latching on it drops a live child's pending wake at Relaunch, which is #1866's symptom. The explicit-stop criterion is still met (tests 4–6).
