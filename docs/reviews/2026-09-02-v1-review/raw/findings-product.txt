## Findings — high confidence (additional)

M-19. HIGH — npm `tandem` started while the desktop app is running waits 30 s, goes read-only, then SIGKILLs the desktop app's server
  src/server/index.ts:300-370 (store-lock retry → lock stays "readonly", no exit) → :580-581 (`freePort(wsPort); freePort(mcpPort)` unconditionally) ; src/server/platform.ts:214-244 (freePortUnix: `lsof -ti TCP:<port> -sTCP:LISTEN` → `process.kill(pid, "SIGKILL")`) and :179-212 (freePortWindows: `taskkill /F` on every netstat holder)
  [read: src/server/index.ts:300-370,578-586 + src/server/platform.ts:179-244]
  Nothing between the read-only lock outcome and freePort() checks whether the port holder is another Tandem, so a customer who installed both the desktop app and the npm package (README offers both) and types `tandem` in a terminal kills the desktop app's sidecar under their open documents; the desktop then auto-restarts the sidecar up to MAX_RESTARTS=3 (sidecar.rs:136) and the two fight over the ports until the Server Error dialog appears. The Windows smoke run (docs/release-smoke-checklist.md:209-214) recorded the CLI as "gives up rather than displacing the app" — that reading is consistent with the desktop sidecar winning the restart race, not with the CLI refraining, and the same doc's next sentence ("will then take the ports the moment the app releases them") is the kill path being observed. Confidence: high on the code path (both platforms kill unconditionally); medium on which process wins on Windows. Not run this session.

  src/client/components/NetworkSettings.svelte:212 ; src/cli/index.ts:180-181 (`start` takes no options) ; src/cli/start.ts:11-45 (reads only TANDEM_MCP_PORT / TANDEM_URL env)
