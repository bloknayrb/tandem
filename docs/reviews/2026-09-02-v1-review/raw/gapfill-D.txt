=== 2. Tauri bundler (2.x): prerelease semver in NSIS vs MSI/WiX ===

ANSWER:
- MSI/WiX: Since tauri-bundler 1.2.0, the bundler supports a prerelease identifier and a build-metadata number for the .msi target, but requires each to be numeric-only (this constraint originates from the Windows Installer ProductVersion/UpgradeCode versioning model, which WiX maps onto). A non-numeric prerelease or build string (e.g. "rc.1", or build metadata with hex like "+1a2b3c4d") is REJECTED for MSI/WiX with a build error to the effect of "optional build metadata in app version must be numeric-only." The overall `version` field must still be semver-compliant.
- NSIS: Originally shared the same numeric-only restriction (a bug — GitHub issue #8038, "NSIS bundler: semver version metadata is required to be numeric-only," argued this restriction should only ever have applied to WiX, since Windows' VIProductVersion/ProductVersion display string can accept arbitrary text for NSIS installers). This was fixed by PR #12136 ("fix(windows): removed NSIS semver build version numeric-only ... "), which changes NSIS to WARN rather than hard-fail on non-numeric build metadata: non-numeric build/prerelease components are replaced with ".0" when constructing the strictly-numeric `VIProductVersion`/`VIFileVersion` fields (which Windows requires in X.X.X.X numeric form), while the original full version string (e.g. "1.0.0-rc.1") is preserved elsewhere (e.g. the installer's displayed ProductVersion / DisplayVersion).
- Net effect for `1.0.0-rc.1` specifically: NSIS accepts it (mapped to a numeric-only VIProductVersion like 1.0.0.0 for the Windows resource fields, with the real string kept for display); MSI/WiX rejects a literal "-rc.1" prerelease unless it is numeric-only (WiX would need something like a numeric prerelease convention, or the tag stripped/converted, otherwise the build fails).

SOURCES:
- https://github.com/tauri-apps/tauri/issues/8038 ("NSIS bundler: semver version metadata is required to be numeric-only")
- https://github.com/tauri-apps/tauri/pull/12136 ("fix(windows): removed NSIS semver build version numeric-only...")
- https://v2.tauri.app/release/tauri-bundler/v1.2.0/ (changelog entry: ".msi bundle target" prerelease/build-number numeric-only support added)
DATE: issue/PR content as currently on GitHub (fetched 2026-09-02); tauri-bundler 1.2.0 changelog is historical (v1.x line, mechanism carried into 2.x bundler per issue discussion referencing current NSIS/WiX bundlers).

=== 3 & 4. tauri-plugin-updater 2.x version comparison and URL template expansion ===

ANSWER (3):
Default comparison in `Updater::check()` (plugins-workspace, `plugins/updater/src/updater.rs`) is:
```rust
let should_update = match self.version_comparator.as_ref() {
    Some(comparator) => comparator(self.current_version.clone(), release.clone()),
    None => release.version > self.current_version,
};
```
- This is strict semver greater-than (`>`) via the `semver` crate's `Version` ordering when no custom `version_comparator` is supplied via the builder.
- Semver ordering rules apply, which means a PRERELEASE manifest version is treated as OLDER than the corresponding stable version (semver spec: `1.0.0-rc.1 < 1.0.0`), i.e. the plugin does NOT treat a prerelease as newer than a stable release by default — it follows standard semver precedence, which ranks any prerelease below its associated normal version.
- No downgrade path exists in the default comparator: `release.version > self.current_version` is false whenever the manifest is older or equal, so `should_update` is false and no downgrade is offered. A downgrade is only possible if the app supplies a custom `version_comparator` via the builder that returns `true` for an older manifest version — the plugin supports this via `.version_comparator()`/`.updater_builder()` as an explicit escape hatch, but it's opt-in application code, not default behavior.

ANSWER (4):

Substitution happens in the same code path regardless of source, so custom endpoints passed via `updater_builder().endpoints(...)` DO get `{{target}}`/`{{arch}}`/`{{current_version}}` expanded at runtime, identically to config-file endpoints.

=== 5. GitHub CodeQL default setup vs advanced setup + codeql-config.yml ===

=== 6. Cloudflare Workers: KV namespace id cross-check across workers ===

ANSWER: CONFIRMED — no cross-check exists.
- `wrangler.toml`'s `kv_namespaces` entries are just `{ binding, id }` pairs; `id` must be a real KV namespace id in the account (Wrangler/the Cloudflare API validates that the id EXISTS in the account at deploy time — deploying with a nonexistent id fails, e.g. reports like "a namespace ... already exists [code: 10014]" or 404-style "namespace not found" errors when the id is wrong/missing), but this is existence-validation only.
- There is no mechanism, in Wrangler or the Cloudflare API, that checks whether two different Workers' `kv_namespaces` entries that happen to share the same `binding` name ("MY_KV") point at the same or a "compatible" underlying namespace id. Each Worker script independently declares whichever `id` it wants for a given binding name; Cloudflare's platform has no concept of a binding name being a cross-worker identity — the binding name is purely local to how the one Worker's code refers to that namespace. Two workers can use the same binding name "MY_KV" bound to entirely different namespace ids, or different binding names bound to the same namespace id, with zero validation or warning either way.

=== 10. tauri-plugin-updater 2.x: does UpdaterBuilder::endpoints() reject non-https URLs? ===

ANSWER:
It rejects non-https endpoints by default in release builds, but the enforcement is gated by a `dangerous_insecure_transport_protocol` config flag and appears to differ between debug and release builds. `UpdaterBuilder::endpoints()` calls into `crate::config::validate_endpoints(&endpoints, self.context.config.dangerous_insecure_transport_protocol)`:

```rust
pub fn endpoints(mut self, endpoints: Vec<Url>) -> Result<Self> {
    crate::config::validate_endpoints(
        &endpoints,
        self.context.config.dangerous_insecure_transport_protocol,
    )?;
    self.endpoints.replace(endpoints);
    Ok(self)
}
```

Inside `validate_endpoints` (`plugins/updater/src/config.rs`), the scheme check is:

```rust
if url.scheme() != "https" {
```

Behavior as summarized from the fetch:
- `dangerous_insecure_transport_protocol == false` (the default): a non-`https` endpoint URL causes the validator to return `Err(crate::Error::InsecureTransportProtocol)` in RELEASE builds (hard rejection, propagated as an `Err` out of `.endpoints()`); in DEBUG builds the same condition instead only logs/emits a warning and does NOT error, i.e. `http://` is accepted with a warning during development.
- `dangerous_insecure_transport_protocol == true`: the scheme check is bypassed entirely — `http://` (or any non-https scheme) is accepted silently, no warning, no error. This flag is the documented escape hatch (it's also a `tauri.conf.json` updater-plugin setting, not just a builder-time toggle) for intentionally using an insecure transport.

So: NOT "accept silently" by default, and NOT "only warn" in release — it's a hard `Err` rejection in release, softened to a warn-only in debug builds, and fully bypassed when the app opts into `dangerous_insecure_transport_protocol = true`.

SOURCE: https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/src/config.rs (fetched via WebFetch, v2 branch tip, 2026-09-02)
CONFIDENCE: Medium-high on the overall shape (hard error by default, flag-gated bypass) — consistent with the `InsecureTransportProtocol` error variant name and the flag's own name (`dangerous_...`) implying it's an explicit, named opt-out rather than a silent default. Medium on the specific debug-vs-release split (warn-only in debug, error in release): this detail came from the WebFetch summarization rather than a literal grep of a `#[cfg(debug_assertions)]` gate, so it should be verified with a raw source read (e.g. `git show` on a pinned tag) before being stated as fact in a security-relevant document — the debug/release split is plausible but is the least-certain part of this answer.
