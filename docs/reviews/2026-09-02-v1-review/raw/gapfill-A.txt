7. Q: what makes the annotations store.lock "alive", and is there a boot-id/timestamp check against PID reuse after reboot?
ANSWER: Liveness = `process.kill(pid, 0)` succeeding; NO boot-id/timestamp check defeats PID reuse on the automatic startup path.
FILES: src/server/annotations/store.ts:139-146 (isPidAlive), 216-247 (tryReclaimStaleLock), 297-343 (doReclaim); src/server/annotations/lockfile.ts:18,25,44.
JUSTIFICATION: `function isPidAlive(pid) { try { process.kill(pid, 0); return true; } catch ... }` (store.ts:139-143) is the sole liveness test used by the automatic startup path `tryReclaimStaleLock`: "if (isPidAlive(lock.pid)) return false;" (line 243) — no comparison against the lockfile's own `startedAtMs` field. The lockfile format does carry `startedAtMs` (`lockfilePayload()` in lockfile.ts:25: `JSON.stringify({ pid: process.pid, startedAtMs: Date.now(), app: LOCK_APP_ID })`), but grepping the annotations dir shows `startedAtMs` is only ever written, never read/compared anywhere — so nothing catches PID reuse after a reboot on the startup path (a reused PID reads as "alive" and the store falls into read-only mode). The user-initiated `doReclaim`/`reclaimStoreLock` path adds a *name*-based identity probe (`probeProcessIdentity`) to catch a Tandem-crash-then-PID-recycled-by-an-unrelated-process case (store.ts:265-341), but that is a process-name heuristic, not a boot-id or timestamp check, and does not apply to the automatic startup path at all.

10. Q: does each reconnect retry send a fresh initialize (new server session), and does backoff cap at 30s with unlimited retries?
ANSWER: YES to both.
FILE: src/cli/mcp-stdio.ts:923-940 (armReconnectRetry), 1002-1082 (runReconnect), 108-110 & 289-297 (nextBackoffMs/BACKOFF_MAX_MS).
JUSTIFICATION: `const BACKOFF_MAX_MS = 30_000;` (line 110) and `nextBackoffMs` doubles and clamps: "return { delayMs: current, nextMs: Math.min(current * 2, BACKOFF_MAX_MS) };" (line 296), with an explicit comment "This is a backoff, not a budget: it never *refuses* a reconnect... however many restarts it took" (284-286) — i.e. unlimited retries. Each fire of `armReconnectRetry`'s timer calls `runReconnect(reason)` (937), which replays the originally captured client handshake against a brand-new upstream transport: "const fresh = createUpstream(); ... http = fresh; await fresh.start(); const pendingResponse = awaitReplayResponse(replayId); const sent = fresh.send({ ...(init as object), id: replayId } as JSONRPCMessage);" (1046-1062) — a fresh `initialize` request is sent to the server each retry, which the server treats as a brand-new session because it's a new HTTP transport/session negotiation.

13. Q: when the source file is deleted while open, what is the user-visible sequence (toast/banner vs. only console.warn)?
ANSWER: There IS a user-visible toast, not just a console log.
FILES: src/server/mcp/document-service.ts:390-398 (SOURCE_MISSING skip); src/client/actions/builtin.svelte.ts:445-453 (result handling), 536-537 (message text).
JUSTIFICATION: On save, if `fs.stat(docState.filePath)` throws `ENOENT`, the server returns `{ status: "skipped", reason: "Source file no longer exists", skipCode: "SOURCE_MISSING" }` (document-service.ts:392-397) over HTTP 200 (not just a console log — the ENOENT branch does not log at all; only the *unexpected*-error branch does `console.error("[AutoSave] Unexpected stat error for %s:", ...)` at line 399, which SOURCE_MISSING skips past). On the client, `performSave`'s success-path handler checks `if (result?.status === "skipped") { notifyUser("warning", saveSkippedMessage(result.skipCode, result.reason)); return false; }` (builtin.svelte.ts:451-454), and `saveSkippedMessage` maps `"SOURCE_MISSING"` to the user-visible string `"Not saved — the original file no longer exists. Reopen it or use Save As."` (line 536-537) — delivered via `notifyUser("warning", ...)`, i.e., a toast, not merely a console message.
