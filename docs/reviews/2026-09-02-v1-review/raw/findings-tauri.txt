## Findings — high confidence

### H1. (High) `keyring` has no platform backend enabled, so every desktop "keychain" write goes to an in-memory mock
- src-tauri/Cargo.toml:~30 (`keyring = "3"`, no `features`); src-tauri/src/token_store.rs:72-101; src-tauri/src/keychain.rs:154-193
- [read: ~/.cargo/registry/.../keyring-3.6.3/src/lib.rs:269-297 + Cargo.toml [features]; src-tauri/Cargo.lock keyring deps = log, zeroize only]
- keyring 3.x ships with NO default features; the Windows/macOS/Secret Service backends are opt-in features (`windows-native`, `apple-native`, `sync-secret-service` etc.) and `Cargo.toml` enables none, so `keyring::default` resolves to `keyring::mock` on every target (confirmed: Cargo.lock shows keyring pulling in only `log` and `zeroize` — none of `windows-sys`/`security-framework`/`secret-service`). Mock `Entry::new` builds a fresh `MockCredential` per Entry with `CredentialPersistence::EntryOnly`, so `set_password` "succeeds" and is gone as soon as the `Entry` drops.
- Concrete consequence A (auth token split-brain): `token_store::get_or_create_token()` calls `entry.get_password()` → Err(NoEntry) → mints a new random token → `entry.set_password()` Ok → returns it WITHOUT ever taking the `write_to_file` fallback (that branch only runs on keyring Err). The sidecar spawn (sidecar.rs:~377) therefore gets a fresh `TANDEM_AUTH_TOKEN` on every spawn, and Node's `loadOrCreateToken` (src/server/auth/token-store.ts:63-70) returns an env-supplied token without persisting it. Meanwhile `cowork_apply_token` / `cowork_install_into_workspace` (cowork_commands.rs:~470 → cowork_installer.rs:~704) call `get_or_create_token()` again and get a DIFFERENT token, which is what gets written into the Cowork workspace config as `TANDEM_AUTH_TOKEN`. The Cowork VM is non-loopback and the server requires Bearer on non-loopback, so a Cowork-provisioned workspace 401s against the running desktop server by construction — every time, not intermittently.
- Concrete consequence B: `keychain_set` / `keychain_get` / `keychain_delete` commands are a write-only sink in the desktop build — the client stores a Sentry/BYO-model secret, it is "saved", and the next `keychain_get` (new `Entry`) returns NoEntry. docs/data-locations.md:54-55 claims Credential Manager / Keychain / Secret Service storage. `tests/client/keychain/keychain-backend.test.ts` expects keyring platform error strings the mock never produces. roadmap.md:~621 notes a real-keychain round-trip has never been run, and #1455 is open on that round-trip — this finding extends #1455 with the root cause: it cannot pass until a backend feature is turned on, and consequence A makes it a Cowork functional bug not just a persistence one.
- Confidence: high (source-level; mechanical). Not hardware-verifiable-only, but a desktop smoke step is listed below.

### H2. (High) `sidecar_exe_path()` computes a filename that tauri-build never produces, so the Windows updater's exe-unlock wait is dead code
- src-tauri/src/sidecar.rs:877-890 (`sidecar_exe_path`), :894-924 (`wait_for_sidecar_unlock`)
- [read: ~/.cargo/registry/.../tauri-build-2.6.3/src/lib.rs:56-81 `copy_binaries` does `.replace(&format!("-{target_triple}"), "")`; tauri-plugin-shell-2.3.5/src/process/mod.rs:120-132 `relative_command_path`]
- `sidecar_exe_path` builds `node-sidecar-<TARGET_TRIPLE>.exe` next to the app exe, but tauri-build strips the `-<triple>` suffix when copying `externalBin`, and the runtime spawns via `.sidecar("node-sidecar")` — the bundled file is `node-sidecar.exe`. `wait_for_sidecar_unlock` therefore hits `!path.exists()` and returns `true` immediately with a warn ("packaging bug?"), so `perform_install` proceeds to NSIS while `node-sidecar.exe` may still be open.
- docs/architecture.md:~860 documents this wait as the mechanism that prevents the "file in use" NSIS failure during in-app update; on a real machine it never waits. The NSIS `PREINSTALL` hook's `KillProcessCurrentUser node-sidecar.exe` (windows/installer-hook.nsi:27-31) is the only thing actually protecting the update, and that hook is gated on `$UpdateMode`. Plausibly related to the beta v0.21.1→v0.22.0 update failure report, but that link is [inferred].
- Confidence: high on the dead-code claim; medium on user-visible impact (the NSIS kill likely masks it most of the time).

### H3. (High) Deferred autostart launcher can never be released: `request_launcher_start` is rejected by the origin gate and nothing else ever calls the start route
- src-tauri/src/lib.rs:673-712 (`request_launcher_start`), :734-764 (`note_user_presence`); src/server/launcher/api-routes.ts:530-567 (`makeStartHandler`); src/server/mcp/api-routes.ts:110-121 (`isLocalhostOrigin`)
- [read: src/server/launcher/api-routes.ts:530-536 + src/server/integrations/api-routes.ts:340-357 `assertOriginAllowlisted` + src/client grep for API_LAUNCHER_START = no callers]
- When the app is launched at login (`--tandem-autostart`), the sidecar is spawned with `TANDEM_DEFER_LAUNCHER=1` and `show_main_window` later POSTs `/api/launcher/start` from Rust via reqwest with no `Origin` header. `makeStartHandler` calls `assertOriginAllowlisted` first, which calls `isLocalhostOrigin(undefined)` → false → 403, so the release never lands; the Rust side logs and moves on, `note_user_presence` re-arms `LAUNCHER_DEFERRED`, and every subsequent sidecar respawn in that process sends `TANDEM_DEFER_LAUNCHER=1` again. The server comment at api-routes.ts:536 says "client fires this on every visibility change", but the client only calls `API_LAUNCHER_NONCE` (builtin.svelte.ts:~584) and `API_LAUNCHER_START_FRESH` (:~923) — there is no `/api/launcher/start` caller anywhere in src/client. `tests/server/launcher/api-routes.test.ts` covers start-fresh only.
- Net effect: on any login-launched desktop session the auto-launcher never starts for the life of that process; `isTransientlyUnavailable` only recognises `"deferred-autostart"` so the UI shows the "deferred" state indefinitely. CLAUDE.md's "`show_main_window` is the single release point" is true of the Rust side but the release point is dead. The same class as the `open`/`rotate-token` note in CLAUDE.md Security (reqwest sends no Origin) — this is a third such route that WAS given the gate.
- Confidence: high on the 403 (code path fully traced); the only unverified link is whether `TANDEM_DEFER_LAUNCHER` is honoured when the `--tandem-autostart` flag is absent (it is not sent then, so non-autostart launches are unaffected).

### H4. (Medium) `perform_install` stops the sidecar before download and never restarts it on a failed download/install
- src-tauri/src/lib.rs:~2350-2450
- [read: src-tauri/src/lib.rs:2350-2450; tauri-plugin-updater-2.10.1/src/updater.rs:652 `download`, :718 `install`, :723 `download_and_install`, :787-865 Windows `install_inner` → `std::process::exit(0)`]
- The install flow calls `stop_sidecar_gracefully` (POST /api/shutdown, then kill) and `wait_for_sidecar_unlock` BEFORE `update.download_and_install(...)`. If the download fails (offline, GitHub 5xx, signature mismatch, partial transfer) the `Err` branch reports to the WebView but does not respawn the sidecar; `SIDECAR_HEALTHY` is left true and `RESTART_IN_PROGRESS` was never taken, so the banner shows "server running" while every MCP/WS call fails until the user finds Settings → Network → Restart. The plugin exposes `download()` and `install()` separately, so the stop could be moved between them.
- Confidence: high on the code path; medium on frequency (needs a failing download mid-update).

### H5. (Medium) A post-boot sidecar crash is never restarted; MAX_RESTARTS applies to the boot window only
- src-tauri/src/sidecar.rs:493-549 (`CommandEvent::Terminated` handler sets `dead_flag`), :~300-420 (`start_sidecar` restart loop bounded by `wait_for_health`)
- [read: src-tauri/src/sidecar.rs:300-560]
- `MAX_RESTARTS=3` is consumed inside `start_sidecar`'s health-wait loop; once `promote_healthy_and_drain` has run, the `Terminated` event only flips `dead_flag`, which nothing reads after health. Node's narrowed exception handler calls `process.exit(1)` on unknown errors (CLAUDE.md Gotchas), so any such error hours into a session leaves the desktop app serverless with a stale "Connected" until the user restarts from Settings. docs/architecture.md:~819 says "On crash, retries up to MAX_RESTARTS", which reads as steady-state supervision.
- Confidence: high on mechanism (traced); no runtime reproduction (cargo not buildable here).

## Findings — remaining

### R1. (Medium) `refresh_registration` only runs on autostart launches, so its two stated purposes are unreachable
- src-tauri/src/autostart.rs:138-151; src-tauri/src/lib.rs:~1444, :1483-1488
- [read: src-tauri/src/lib.rs:1440-1490]
- The comment says the refresh exists (a) to re-point the LaunchAgent/registry entry after the app is moved and (b) to upgrade a pre-flag registration to `--tandem-autostart`. It is called only inside `if autostart_launch {…}`, i.e. only when the existing registration already worked and already carried the flag. A user who enabled start-at-login, then moved Tandem.app or upgraded from a flagless build, is never refreshed: the app either never autostarts again or autostarts without the flag (so the launcher is not deferred and `LAUNCHER_DEFERRED` semantics silently differ).
- Confidence: high on reachability; impact medium-low.
