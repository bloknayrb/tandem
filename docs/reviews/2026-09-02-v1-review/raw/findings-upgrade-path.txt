F4. [Medium] Annotation-envelope forward-compat is all-or-nothing at the ARRAY
    level: one record with a new enum value quarantines the WHOLE file
    src/server/annotations/schema.ts:215-224 (`annotations: z.array(...)`),
    src/shared/types.ts:17,19 (closed enums), quarantine at
    src/server/annotations/store.ts:592-603
    [ran: npx tsx probe.ts in scratchpad/exp-upgrade — results:
     baseline => ok, 1 kept; good + additive field => ok, 2 kept;
     good + future `type: "suggestion"` => FAIL error=corrupt;
     good + future `status: "superseded"` => FAIL error=corrupt]
    The module header (schema.ts:4-13) promises forward-compat via
    `.passthrough()` — "Strict rejection would turn a harmless additive change
    into a 'corrupt' error" — and that holds for new FIELDS, but a new value in
    `AnnotationTypeSchema`/`AnnotationStatusSchema`/`AuthorSchema` is rejected

F5. [Medium] The `.future` downgrade-park path is silent, and a SECOND
    downgrade cycle deletes the parked copy
    src/server/annotations/store.ts:605-622
    [read: src/server/annotations/store.ts:592-622]
    The `corrupt` branch calls `notifyFailure(...)` so the user gets a toast;
    the `future` branch (a newer schemaVersion, i.e. exactly the
    downgrade-after-a-bad-update case) parks the file as `<hash>.json.future`
    and returns an empty doc with only a `console.error` — in the desktop app
    that goes to a log file the user never sees, so every annotation on every
    document simply vanishes with no explanation. Worse, the park does
    `await fs.unlink(futurePath).catch(() => {})` before the rename "so we
    always keep the most recent copy": upgrade → downgrade (real annotations
    parked to `.future`, empty v_next file written on the next save) →
    re-upgrade → downgrade again deletes the `.future` that held the only copy
    of the user's annotations and replaces it with the empty one.
    Confidence: High (code), Med (reachability — needs SCHEMA_VERSION > 1,
    which is dormant-but-wired today: src/server/annotations/migrations/v1_to_v2.ts exists)

## Unchecked leads
- **Does the Tauri updater's silent Windows install reach `PageLeaveReinstall`,
  and therefore append `/UPDATE` to the old uninstaller's command line?**
  `src-tauri/windows/installer-hook.nsi` NSIS_HOOK_PREUNINSTALL skips the
  uninstall scrub only when `$UpdateMode <> 1` is false, and `$UpdateMode` is
  set by `un.onInit` parsing `/UPDATE`, which the comment says is appended by
  the installer's `PageLeaveReinstall`. NSIS silent installs (`/S`, which is
  what tauri-plugin-updater runs) skip page callbacks. If `/UPDATE` is not
  appended on the auto-update path, EVERY Windows auto-update runs the full
  scrub — wiping start-at-login, Cowork registrations and firewall rules —
  which would be High and directly contradicts docs/data-locations.md:89-93
  ("It is skipped during an *upgrade* … so your settings survive updates").
  NEXT CHECK: read `tauri-plugin-updater`'s `install_inner` NSIS branch (the
  `installer_args` it passes) and Tauri's bundled `installer.nsi`
  `Section Install` silent branch; neither is vendored in this checkout, so
  `cargo vendor` / crates.io source is needed. A cheap partial: run a Windows
  auto-update and check whether `HKCU\...\Run\Tandem` survives.
- Whether `stop_sidecar_gracefully`'s `POST /api/shutdown` reliably flushes
  before the NSIS installer replaces `node-sidecar.exe`; the code tolerates
  both "still locked" and "still responding" and proceeds anyway
  (lib.rs:2372-2392). NEXT CHECK: instrument the two warning strings during a
  real Windows update smoke run.
- Whether a session file written by a build with a NEWER

- Post-v1.0 gate bypass: `ensureTrialStarted`/`resolveLicenseState` are

## Doc drift
- src/server/annotations/schema.ts:4-13 (module header) claims:
  "All object schemas use `.passthrough()` … Strict rejection would turn a
  harmless additive change into a 'corrupt' error and trip the `.json.future`
  fallback path unnecessarily."
  The code contradicts the scope of that promise: `annotations: z.array(
  AnnotationRecordSchemaV1)` (schema.ts:221) plus the closed enums at
  src/shared/types.ts:17,19,23 means a new *enum value* — the most likely
  additive change to an annotation model — is rejected AND fails the whole
  envelope, not the row. Measured, not argued: [ran: npx tsx probe.ts] a single
  `type: "suggestion"` record turns a 2-annotation envelope into
  `error: "corrupt"`. The header should either say "additive FIELDS only" or
  the array should be per-row tolerant.

- docs/data-locations.md:89-93: "the uninstaller runs the scrub automatically
  — nothing to do. It is skipped during an *upgrade* … so your settings survive
  updates."
  This is verified for the *interactive installer-over-install* path (the
  `$UpdateMode <> 1` guard in src-tauri/windows/installer-hook.nsi), but the
  doc's flat "updates" also covers the Tauri auto-updater's silent NSIS run,
  which is unverified here (see Unchecked leads). The sentence is broader than
  what the code demonstrably guarantees.

- CLAUDE.md:199: "Auto-open `sample/welcome.md` on first run; on upgrade
  `CHANGELOG.md` opens instead, read-only … Both open **before**
  Hocuspocus/MCP start."
  Accurate for HTTP mode (src/server/index.ts:592-640), but both sit inside
  `if (transportMode === "http")` at index.ts:562 and neither happens in stdio
  mode — the rule reads as unconditional. (See F10.)

- src-tauri/src/lib.rs:1942 doc comment: "Copies each file only if the
  destination doesn't already exist (first-run)." Accurate, but nothing in
  CLAUDE.md or the docs says the consequence: the tutorial document is never
  refreshed by an upgrade, so tutorial-annotation target strings and the
  shipped welcome.md can silently diverge (F9).

## Verified fine
- `IntegrationsFile` has a real versioned migration chain (v1→v2→v3) with Zod
  validation of the v_n input, migrate-on-read, and an explicit refusal (rather
  than silent coercion) for a future version. [read: src/server/integrations/migrations.ts]
- Client settings carry a 20-step forward migration chain, a REMOVED_FIELDS
  resurrection block, and a forward-compat `_readOnly` mode that stops a
  downgraded client clobbering a newer client's Models registry.
  [read: src/client/hooks/useTandemSettings.ts:400-520, :875-939]
- The #1118 pending-update marker is careful: version-free stable reason code,
  read-side plausibility guard, unconditional one-shot clear, and
  `verdict_after_clear` deliberately SUPPRESSES the hint when the clear failed
  so it can never become an un-dismissable every-boot nag. It cannot fire on a
  fresh install (no marker ⇒ NoMarker) and the marker is written at
  download-finish rather than before the download, so a quit during the
  download does not produce a false positive.
  [read: src-tauri/src/pending_update.rs:95-113, :300-345, lib.rs:2395-2440]
- `record_pending_update`, `clear_pending_update` and
  `evaluate_pending_update_marker` all resolve the same
  `app.path().app_data_dir()`, so write and read cannot diverge.
- The client's hint drain is take-once and chains the boot drain onto the
  listener's resolution, so a hint landing between the two is not lost.
  [read: src/client/utils/pending-update-hint.ts:88-130]
- No `version_comparator` is set on the updater builder
  (src-tauri/src/lib.rs:2233-2248), so tauri-plugin-updater's default
  strictly-greater semver comparison applies — a `latest.json` naming an older
  version cannot drive a downgrade.
- `.github/workflows/tauri-release.yml:69-77` refuses to publish when the tag
  and `tauri.conf.json` version disagree, and `verify-release-manifest`
  (:755-843) asserts all 11 platform keys are present, every URL resolves to an

  "one platform is told it's up to date forever" failure mode is gated.
- `tests/plugin/plugin-version-pin.test.ts` pins plugin.json's top-level
  version, both npx pins, both monitor command pins and Cargo.toml to

- `perform_install` gracefully shuts the sidecar down first
  (POST /api/shutdown flushes dirty docs and saves the session) and waits for
