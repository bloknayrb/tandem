# Review F — src/shared, src/cli, src/channel, src/monitor, src/stdio-bridge (+ docs/cli.md, docs/configuration.md)
Repo: master 3fb6408, v0.24.1. Read-only review; nothing in the repository was changed. All `[ran:]` experiments used a scratch HOME under the scratchpad (fakehome, fakehome2/3/4) and never touched the real HOME or ports 3478/3479.

## Findings — high confidence

### F1. High — stdio bridge's fail-closed identity check refuses every Tandem version upgrade, leaving Claude Desktop's tools dead until Claude Desktop restarts
- Where: src/cli/mcp-stdio.ts:269 (`describeServerInfo` renders `${name}@${version}`), :1095-1109 (throws `upstream identity changed across re-initialize (was …, now …)`), src/server/mcp/server.ts:242-245 (`new McpServer({ name: "tandem", version: APP_VERSION })`).
- Evidence: [read: src/cli/mcp-stdio.ts:215-280, 741-760, 1085-1130; src/server/mcp/server.ts:242-245; src-tauri/src/lib.rs:2431]
- Failure: The Tauri updater relaunches the sidecar (`app.restart()` at lib.rs:2431) with a new `APP_VERSION`, so the long-lived Claude Desktop bridge sees its next tool call answered with 404 `-32001`, reconnects, replays the captured `initialize` under a private id, and compares `tandem@0.24.1` against `tandem@0.25.0` — a mismatch that the code treats as a foreign upstream. The catch path clears the reconnect queue, escalates backoff and synthesizes `-32000 "Tandem HTTP upstream session lost"` for every subsequent request, forever, because the bridge never exits (by design, #1588) and the identity baseline is never refreshed; the user gets the exact "dead for the rest of the day" outage #1588 (CHANGELOG.md:84) claims to have fixed, now triggered by every release rather than by the idle reaper.
- Why the test suite does not catch it: tests/cli/mcp-stdio.test.ts:1947 exercises `setServerInfo({ name: "not-tandem", version: "9.9.9" })` — name and version change together; a version-only change is never pinned. Compare `name` (and optionally `protocolVersion`) only, or re-capture the baseline when `name` matches.
- Confidence: high.

### F2. High — three docs instruct a channel-shim removal command that does not remove anything
- Where: README.md:230, CHANGELOG.md:328, docs/architecture.md:577 (all: re-run `tandem setup --apply` without `--with-channel-shim` to remove the shim) vs src/cli/setup.ts:193-202 + src/server/integrations/apply.ts `resolveChannelShimIntent` (absent flag → preserve existing registration) + src/cli/index.ts:144 (`withChannelShim: args.includes("--with-channel-shim") || undefined`).
- Evidence: [ran: HOME=<scratch>/fakehome TANDEM_APP_DATA_DIR=<scratch>/fakehome/data npx tsx src/cli/index.ts setup --apply --target=claude-code --with-channel-shim, then the same without the flag; ~/.claude.json still contains `mcpServers["tandem-channel"]`, rewritten with the current dist path, and the CLI prints "Registered for: Claude Code" with no mention of the shim]
- Failure: A user following any of the three documents runs the no-flag command expecting the shim to go away; the shim entry is preserved and refreshed, so Claude Code keeps launching `dist/channel/index.js` on every session, and nothing in the output says the removal was skipped. The comment at setup.ts:~196 says there is "deliberately no `--no-channel-shim`", so there is no CLI path at all that removes the shim short of hand-editing `~/.claude.json` or `tandem uninstall`.
- Confidence: high.

### F3. Medium — monitor and channel shim give up after ~30 s of server downtime, and the monitor's printed remedy cannot work
- Where: src/shared/sse-consumer.ts:167-223 (`CHANNEL_MAX_RETRIES=5`, delays 2/4/8/16/30 s → ~60 s worst case but only 5 attempts; `process.exit(1)` at :206/:223), src/monitor/run.ts:174-177 (`"Tandem monitor disconnected — restart Tandem to restore real-time events"`), :257-270 (comment: a monitor that exits is never respawned — spike F9), docs/architecture.md:530-534.
- Evidence: [read: src/shared/sse-consumer.ts:160-230, 264-278; src/monitor/run.ts:130-185, 250-285; docs/spikes/plugin-monitor-tty-activation.md F9]
- Failure: A Tauri auto-update, a `tandem start` restart, or a laptop sleep longer than the retry window exhausts the five retries; the monitor POSTs `/api/channel-error` and exits 1, and per the repo's own measurement Claude Code never respawns it. The wake line tells the user to "restart Tandem", but restarting Tandem does not bring the monitor back — only a new Claude Code session does — so the user follows the instruction, sees no wakes, and concludes push is broken; the channel shim has the same exit path with no user-visible remedy at all.
- Confidence: high (code), medium that Claude Code never respawns (repo's own spike, not re-measured here).

### F4. Medium — stdio bridge exits on startup preflight failure although nothing respawns a Claude Desktop child
- Where: src/cli/mcp-stdio.ts:725 (`deferredShutdown`, PREFLIGHT_GRACE_MS 1500 → `shutdown(1, synth)`), :1233-1247 (preflight `/health` failure path), :1245 (synth message `"Tandem server not running. Start the Tauri app or run \`tandem start\`."`); own docblock :24-45, :999, :1199 state a Desktop child is never respawned; docs/troubleshooting.md:94.
- Evidence: [read: src/cli/mcp-stdio.ts:20-50, 720-760, 990-1010, 1195-1260]
- Failure: Claude Desktop launched before the Tauri app (the common cold-boot order, and exactly the case the message describes) gets one synthesized error and then a dead transport; when the user starts Tandem as instructed, the tools stay dead because the bridge process is gone and Claude Desktop will not relaunch it until the app is restarted. The message names the first step and not the second, and troubleshooting.md:94 ("pre-flights the server and returns a real error, so Claude can relay it") reads as if relaying were enough; the 404-reconnect path (never exit) is the right model for the preflight path too.
- Confidence: high for the code; medium for Desktop's respawn behaviour (repo's own claim at :24-45).

### F5. Medium — `tandem doctor` ignores TANDEM_PORT / TANDEM_MCP_PORT and reports a false "server not running"
- Where: src/cli/doctor.ts:2948 (`report = await runDoctor();` — no port opts) vs :2819 `runDoctor(opts)` which accepts ports; docs/troubleshooting.md:145 tells users to `export TANDEM_MCP_PORT=4479`; tests/cli/doctor.test.ts:379-385 only ever call `runDoctor` with explicit ports.
- Evidence: [ran: TANDEM_MCP_PORT=4479 TANDEM_PORT=4478 HOME=<scratch>/fakehome npx tsx src/cli/index.ts doctor → "Ports 3478 + 3479 not listening" / health / sse checks fail against 3479, with the remedy "run `tandem start`"]
- Failure: A user who moved Tandem off the default ports per troubleshooting.md runs `doctor` and is told the server is down, with a remedy that would start a second instance on the wrong ports. The pure function honours the env; only the CLI wrapper drops it, so the unit tests pass.
- Confidence: high.

### F6. Medium — `tandem doctor` passes a user-level `~/.claude.json` entry it never validates (false green on wrong port/path)
- Where: src/cli/doctor.ts:1167 (`r.pass("tandem registered in ~/.claude.json")` after only checking the key exists) vs :1017 (the project `.mcp.json` checker validates `type === "http"` and `url.includes("/mcp")`).
- Evidence: [ran: HOME=<scratch>/fakehome4 with `mcpServers.tandem = {type:"http", url:"http://127.0.0.1:9999/nope"}` → doctor prints a green "tandem registered in ~/.claude.json"]
- Failure: After a port change or a hand edit, `doctor` tells the user the registration is fine while Claude Code's `/mcp` fails to connect; the very check that exists for the project file is missing for the user file, so the two checkers disagree on what "registered" means. (Bare `localhost` in the URL is accepted by the SDK's `localhostHostValidation` on `/mcp` — server/express.js:36-38 — so the false green is about port/path, not host.)
- Confidence: high.
