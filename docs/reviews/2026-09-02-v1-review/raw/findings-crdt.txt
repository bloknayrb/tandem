## Findings — high confidence

### E. High — Pressing Enter anywhere before an annotation in the same paragraph collapses the annotation to zero length and the server records the collapse as "updated"
- Location: src/server/positions.ts:276-289 (refreshRange resolves relRange, from===to is not treated as failure, stored range overwritten as kind "updated"); node_modules/y-prosemirror/src/plugins/sync-plugin.js:~1145-1300 (updateYFragment implements a split as delete-tail-from-left-XmlText + insert new element)
- Evidence: [ran: cd scratchpad/exp && npx tsx crdt-verify.ts — section E, live Tiptap Editor + Collaboration, editor.commands.splitBlock()]
- Failure: Document "aaa bbb ccc", Claude comment on "bbb" (flat 4-7, relRange anchored). The user puts the caret after "aaa " and presses Enter: y-prosemirror deletes "bbb ccc" from the first XmlText and inserts a fresh paragraph, so both RelativePositions collapse to the deletion point; the next tandem_getAnnotations/refreshRange returns kind=updated range={4,4} and WRITES that to the Y.Map — the flat fallback is destroyed too, the client skips the decoration (from>=to), and the comment is orphaned with no console.warn/error anywhere. Same result when Enter is pressed after "a" (annotation entirely inside the moved tail: range={1,1}) and partial loss when Enter lands inside the annotation (range={4,5}, covers "b" only). Only Enter *after* the annotation is safe (kind=ok).
- Why it matters: splitting a long paragraph is the most ordinary edit a reviewer makes; every Claude comment in the tail of that paragraph is silently lost, and because the "updated" arm persists the collapsed range there is no recovery — textSnapshot relocation runs only on the watcher reload path, never on the MCP read path or the client.
- Possibly adjacent to open #1737 ("tell Claude not to insert line breaks mid-paragraph") — issue body not read; if that issue is about this mechanism the delta is that it is the *user's* Enter through y-prosemirror, not a Claude-inserted break, and that the server-side "updated" arm makes it irreversible.
- Recommendation: in refreshRange treat a resolved from===to on a previously non-empty range as `failed`/`degraded` (do not persist), and run the textSnapshot relocation (already implemented in watcher.ts) on that arm; longer term, anchor `to` with a relative position in the element that *received* the tail (y-prosemirror move semantics cannot be recovered post hoc, so relocation by snapshot is the practical fix).
- Confidence: high (reproduced live).
