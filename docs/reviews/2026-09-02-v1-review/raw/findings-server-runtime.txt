# Server-runtime review (C) — src/server/{index,bind-check,auth,events,launcher,integrations,license,local-model,models}, Tauri sidecar lifecycle
Base: master 3fb6408 (v0.24.1). Read-only. Repo untouched. No server started; ports 3478/3479 never touched.

## Findings — high confidence

### H1. Desktop Quit hard-kills the sidecar; the graceful /api/shutdown flush only runs on restart/update
- Severity: High
- Where: src-tauri/src/lib.rs:1404 (tray MENU_QUIT -> app.exit(0)), src-tauri/src/lib.rs:1574 (Linux no-tray CloseRequested -> exit(0)), src-tauri/src/lib.rs:1613 (RunEvent::Exit => kill_sidecar), src-tauri/src/sidecar.rs:~182 and src-tauri/src/lib.rs:~2362 (the only two callers of stop_sidecar_gracefully)
- Evidence: [read: src-tauri/src/lib.rs:1395-1412,1549-1592,1600-1640,2340-2420; src-tauri/src/sidecar.rs:170-330]
- Failure: Every desktop Quit path ends in RunEvent::Exit -> kill_sidecar (a bare child.kill()), and there is no ExitRequested / prevent_exit handler anywhere in src-tauri, so the server's shutdown() sequence (autoSaveAllToDisk + saveCurrentSession + closeMcpSession + supervisor.stop + releaseStoreLock) never runs on Quit. With autosave and session persistence both on a 60 s cadence (src/server/session/manager.ts:25, documents/autosave.ts) and no client beforeunload save, up to 60 s of edits plus the open-tab set are silently lost on every Quit; the launched Claude Code child is left to the reaper's SIGKILL with no flush, and the store lock file is left behind for the next boot's PID-liveness check. #1088 (CHANGELOG) fixed exactly this for restart_sidecar and perform_install by adding stop_sidecar_gracefully, but Quit was not given the same treatment.
- Confidence: high (the absence of any ExitRequested handler and the single kill_sidecar arm at RunEvent::Exit were confirmed by grep across src-tauri/src).

### H2. Supervisor stdin write to a dead/closing child raises an unhandled stream 'error' -> uncaughtException -> process.exit(1) with no flush
- Severity: High
- Where: src/server/launcher/supervisor.ts:~900-927 (sendTurn: spawned.stdin.write(serializeUserTurn(text), cb)), supervisor.ts:1088 (only spawned.on("error")), supervisor.ts:1123 (spawned.on("exit")), src/server/index.ts:154-178 (handleFatalError)
- Evidence: [ran: node scratchpad/epipe2.mjs, epipe3.mjs, epipe4.mjs (Node v22.22.2)]
- Failure: In Node 22 a write to a child's stdin whose read end is closed (child closed fd 0 / is mid-exit) invokes the write callback with EPIPE AND emits 'error' on the child.stdin Writable; a ChildProcess-level 'error' listener does NOT catch it, so with no stdin.on("error") the error becomes uncaughtException. handleFatalError only swallows known Hocuspocus messages, so the whole Tandem server exits 1 — skipping autoSaveAllToDisk/saveCurrentSession/releaseStoreLock — because the launched Claude Code child happened to be exiting while a wake turn was written (the wake-on-annotation path and the bootstrap-turn-on-spawn path both race the child's lifetime). The safe case (child already reaped by Node -> stdin destroyed -> ERR_STREAM_DESTROYED via callback only) is the one the code's callback handling covers; the mid-exit window is the one it does not. No supervisor test covers a stdin error (grep of tests/server for EPIPE/stdin.*error: none).
- Confidence: high for the mechanism (reproduced three ways); medium that the window is hit in practice — it needs a wake write during the child's exit, which the circuit-breaker/relaunch loop makes likelier, not rarer.

### H3. Store-lock retry runs BEFORE freePort: a second instance stalls 30 s, then SIGKILLs the live holder and runs read-only for the whole session
- Severity: Medium
- Where: src/server/index.ts:302-372 (store lock acquire with 30 s retry in HTTP mode), src/server/index.ts:580-581 (freePort), src/server/annotations/store.ts:125-260 (PID-only isPidAlive liveness), src-tauri/src/sidecar.rs:95-140 (HEALTH_TIMEOUT 30 s, comment admitting the lock retry is unsized)
- Evidence: [read: src/server/index.ts:302-372,580-635; src/server/annotations/store.ts:125-260; src-tauri/src/sidecar.rs:95-140]
- Failure: When a healthy Tandem already holds the lock and 3478/3479 (the documented "npm global + desktop" or double-launch case), the newcomer spins on the lock for 30 s (the holder is alive, so PID liveness never releases it), gives up into read-only annotations mode, and only then reaches freePort, which SIGKILLs the healthy holder to take its ports — so the user's original instance dies without flush (see H1 consequences) and the survivor is the one that already decided it is read-only for the rest of its life. During those 30 s the Tauri health poll (HEALTH_TIMEOUT 30 s) is answering against the OLD process's /health, so the desktop can report "healthy" against a sidecar that is about to be killed. The ordering (lock -> freePort) is the inverse of what would make the lock a guard.
- Confidence: high on ordering and on the SIGKILL-the-holder outcome (freePort's kill semantics are pinned by the E2E gotcha in CLAUDE.md); medium on the "desktop reports healthy against the old process" tail, which is inferred from HEALTH_TIMEOUT overlap rather than run.

### H4. MAX_CONFIG_BYTES (5 MiB) contradicts apply.ts's own "routinely multi-megabyte" note; an oversize ~/.claude.json makes the wizard fail generically and the boot sweep silently skip
- Severity: Medium
- Where: src/server/integrations/apply.ts:217-223 (MAX_CONFIG_BYTES = 5 MiB, applied in readConfigForMutation/applyConfig), apply.ts:1735 (comment: .claude.json is "routinely multi-megabyte"), apply.ts:1856-1971 (refreshAllMcpEntryBinaries: "untouched (oversize)" stderr only)
- Evidence: [read: src/server/integrations/apply.ts:217-223,1007-1194,1243-1278,1735,1856-1971]
- Failure: Claude Code's ~/.claude.json grows with project history/caches and the file itself says it is routinely multi-megabyte, so a 5 MiB cap is not a corruption tripwire but a ceiling real users will cross. Past it the setup wizard returns WRITE_FAILED with no size hint (the size error is mapped to the generic code), and the boot-time binary-path refresh silently leaves the stale node path in place — after an update the Claude Code MCP entry then points at a binary that no longer exists and the user sees "Tandem MCP failed to connect" with nothing in doctor pointing at size (doctor has no MAX_CONFIG_BYTES handling; grep confirmed).
- Confidence: high that the cap and the comment conflict and that the failure surfaces are generic; medium on how many real configs exceed 5 MiB.

### H5. applyConfig replaces a malformed ~/.claude.json with a fresh one, while readConfigForMutation refuses to — the wizard path is the destructive one and reports success
- Severity: Medium
- Where: src/server/integrations/apply.ts:1056-1147 (malformed JSON -> backup to .broken-backups -> "replacing with fresh config" at 1133-1135), apply.ts:1243-1278 (readConfigForMutation: never creates, never replaces malformed)
- Evidence: [read: src/server/integrations/apply.ts:1007-1194,1243-1278]
- Failure: If the wizard's read races Claude Code's own rewrite of ~/.claude.json (or hits any transient truncation), applyConfig treats the parse failure as "broken config", moves the user's whole file — every project entry, OAuth/account block, MCP servers — into .broken-backups and writes a fresh config containing only Tandem, logging to stderr only while the wizard UI reports "applied". The sibling reader in the same module already encodes the safer policy (refuse and leave the file alone), so the two writers disagree on whether a parse failure is authority to replace. Whether Claude Code writes ~/.claude.json atomically (which would make the torn-read trigger impossible) is NOT verified — see Unchecked leads.
- Confidence: high on the code path and the reporting asymmetry; medium on the real-world trigger frequency.

### R2. Sentry events carry hostname (server_name) and absolute local file paths in stack frames despite sendDefaultPii:false
- Severity: Low (privacy, opt-in telemetry only)
- Where: src/server/sentry.ts (init: defaultIntegrations:false, sendDefaultPii:false, beforeSend scrubs only message/exception values), node_modules/@sentry/node-core/build/cjs/sdk/client.js:14 (server_name defaults to os.hostname() unless includeServerName===false)
- Evidence: [ran: node --experimental-strip-types scratchpad/sentry-probe.mjs with Tandem's exact init options]
- Failure: The emitted event contains server_name=<machine hostname>, contexts.runtime, and frames with absolute filename paths (which embed the user's home directory / username on all three OSes). docs/security.md's privacy section describes Sentry as scrubbed; the scrubber never sees these fields. Fix is includeServerName:false plus a frame-path rewriter (or the RewriteFrames integration, which defaultIntegrations:false removed).
- Confidence: high.
