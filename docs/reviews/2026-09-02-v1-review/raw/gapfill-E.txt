Key output:

      snapshot tail : "xxxxx\ud83d"  lastCharCode d83d  loneSurrogate: true
      wellFormed    : false

      relocate(after round-trip): {"action":"NOT FOUND (RANGE_GONE)"}      <- BUG
  (b) hard break at the cap boundary
      snapshot tail "yyyyy\n"; relocate before and after round-trip: "valid (no move)"

  e6b.ts (the accept guard, src/shared/snapshot.ts snapshotContradicts):
      pre-roundtrip  contradicts: false
      post-roundtrip contradicts: true   | snapshot changed: true
      post-JSON      contradicts: false  | snapshot changed: false
Explanation:
  src/server/mcp/annotations.ts:186-187 — `text.slice(0, SNAPSHOT_CAP)` is a UTF-16
  code-unit slice with no surrogate-boundary guard, so a capped snapshot can end on a
  lone high surrogate (`SNAPSHOT_CAP = 200`, src/shared/snapshot.ts:34).
  The record is then stored in Y.Map(annotations); Yjs serialises strings as UTF-8
  (Y.encodeStateAsUpdate — used for session persistence at src/server/session/manager.ts:81
  and :358, for the doc swap at src/server/yjs/provider.ts:171, and for every client sync),
  and a lone surrogate is not encodable, so it comes back as U+FFFD. The JSON disk path is
  lossless (\udXXX escape), so only the CRDT path corrupts it — which is the path the
  server's own restore uses.
  After that the snapshot is no longer a substring of its own document:
  validateRange(..., {textSnapshot: probe}) returns RANGE_GONE, and the watcher's
  relocation pass treats RANGE_GONE as "leave as-is" (watcher.ts:261 comment), so the
  annotation is permanently un-relocatable; snapshotContradicts now returns true, so the
  accept paths that gate on it refuse the suggestion.
User impact: an annotation whose text is longer than 200 characters and happens to have an
emoji or other astral character exactly at the 200-char boundary silently becomes
un-relocatable after a server restart or client sync, and its suggestion can no longer be
accepted — with no error surfaced anywhere.
