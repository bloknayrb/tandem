--- F1 [High] A pending "Accept All / Reject All" confirmation survives a document
    switch and silently retargets the new document
file: src/client/panels/SidePanel.svelte:186, 216-223, 501-503, 737-747
evidence: [read: src/client/panels/SidePanel.svelte:180-230, 495-520, 735-750]
A user clicks "Accept All (N)" in the annotations rail on document A; the row swaps to
"Accept N annotations?" with a Confirm button. Before confirming they switch tabs —
SidePanel is always mounted (PanelSlot display-toggle) and App.svelte does NOT wrap it in
`{#key documentId}`, and the only reset for `bulkConfirm` is an $effect keyed on the three
FILTER values, so the confirmation stays armed and `handleBulk` iterates
`filteredData.reviewPending`, which is now document B's list. If B has >1 pending
annotation the row is still on screen (BulkActions renders on `pendingCount > 1`) reading
B's count, and the `$effect(() => { if (bulkConfirm) confirmBtnEl?.focus() })` re-focuses
Confirm the moment the bar re-mounts — one Enter resolves every pending annotation in a
document the user never asked about, with no undo.
This is the identical hazard the batch-promote code documents having already been bitten by
and fixed (SidePanel.svelte:505-518: "Relying on it alone was a bug — Clear left the flag
set, and re-checking a single import re-mounted the bar straight into the confirm branch,
warning text and stolen focus included, with nothing requested"). `promoteConfirmRequested`
got four reset sites; `bulkConfirm` got one. Existing coverage is filter-only
(tests/e2e/settings-and-filters.spec.ts:283, 330, 367) — no document-change case exists.
confidence: high

--- F2 [High] "Clear all" and the per-row "×" in the Open dialog destroy saved annotation
    sessions with one unguarded click
file: src/client/components/FileOpenDialog.svelte:64-82, 326-335, 369-376
evidence: [read: src/client/components/FileOpenDialog.svelte:60-85, 320-380;
           src/client/utils/sessions.ts:56-67]
Each recent-session row renders "<relative time> · N annotations" and a "×" button one
element to its right; `onclick={() => deleteSession(session.filePath)}` POSTs
/api/sessions/delete immediately. Above the list a small underlined "Clear all" link calls
`clearAllSessions()` for every document ever opened. Neither has a confirmation step, an
undo, or a toast; the only feedback is the row vanishing. In a dialog whose primary action
is a click on the adjacent row, a mis-click permanently discards the persisted annotation
state for that document (or, one row higher, for all of them).
confidence: high that both are unconfirmed and irreversible from the UI; medium on the exact
blast radius (whether the deleted session file is the only home of those annotations).

--- F4 [Medium] 7 of 8 role="radiogroup" containers are themselves tab stops, doubling every
    tab stop in Settings
file: src/client/components/AppearanceSettings.svelte:74-78, 124-128, 162-166, ~215;
      src/client/components/EditorSettings.svelte (3 groups)
evidence: [read: src/client/components/AppearanceSettings.svelte:40-230;
           src/client/panels/ChipGroup.svelte:126-131;
           ran: grep -A2 'role="radiogroup"' → 7 of 8 carry tabindex="0"]
Each Settings radiogroup is `<div role="radiogroup" tabindex="0" onkeydown=...>` whose
children use the roving tabindex from `tabIndexFor` (0 on the checked radio). Tab therefore
stops on the group container and then again on the checked radio — two stops per group, four
groups in Appearance plus three in Editor. ChipGroup, the eighth radiogroup in the app, uses
`tabindex="-1"` on the container, which is the WAI-ARIA APG-correct value, so the two
patterns disagree inside one product. A screen-reader user tabbing through Appearance hears
"Theme, radio group" with nothing selected, then Tab again to hear the selected radio.
confidence: high

--- F7 [Low] Enter or click on a shortcut row in the command palette does nothing AND
    discards the focus-restore target
file: src/client/components/CommandPalette.svelte:300-330, 473-478
evidence: [read: src/client/components/CommandPalette.svelte:290-345, 470-480]
`runResult()` sets `opener = null` on its first line, then branches on `kind`; there is no
`shortcut` branch ("shortcut items: display-only, no action on Enter"). A user in `?` mode
who presses Enter on a highlighted row gets no feedback and the palette stays open, and the
subsequent Escape can no longer restore focus to wherever they opened the palette from — the
exact regression the `opener` mechanism was added to fix. The rows are `role="option"` with
`aria-selected` and a pointer-driven `onmouseenter` selection, so nothing signals they are
inert.

--- R3 [Low] Three independent Escape owners at window/document level; stopPropagation does
    not stop same-target listeners
file: src/client/components/CommandPalette.svelte:252-263;
      src/client/editor/toolbar/Toolbar.svelte:~755-765;
      src/client/components/SettingsModal.svelte:491-510
evidence: [read: those regions + src/client/utils/escape-owner.ts:1-48]
CommandPalette and Toolbar both register capture-phase keydown listeners on `window`.
`stopPropagation()` does not suppress other listeners on the SAME target, so an Escape that
dismisses the palette also runs Toolbar's handler in the same phase and can close the
selection popup underneath it. `escape-owner.ts`'s subtree-claim mechanism only covers
popovers nested inside the editor, not sibling window-level owners.
confidence: medium

--- R4 [Low] Chat read state is shared, not per-viewer
file: src/client/hooks/useChatState.svelte.ts:45-49, 65-71
evidence: [read: src/client/hooks/useChatState.svelte.ts:35-80]
`seenIds` comes from `Y_MAP_CHAT_SEEN` in the ctrl room, so with two windows/tabs open on the
same server, reading a Claude message in one clears the unread badge in the other. Likely
intended for a single-user product but it is not stated anywhere near the derivation.
confidence: high

--- R5 [Low] focus-trap skips position:fixed descendants
file: src/client/utils/focus-trap.ts:27-33
evidence: [read: src/client/utils/focus-trap.ts:19-45]
`el.offsetParent !== null` is documented as catching `display:none` and detached subtrees; it
is also false for any `position: fixed` element, so a fixed-position control inside a trapped
dialog would be silently excluded from Tab wrapping. No current instance found in
SettingsModal/LicenseWall/HelpModal/IntegrationWizardModal — this is a latent trap for the
next dialog that uses one.
confidence: medium
