### High — Typing-activity `cursor` is a ProseMirror position, but the server publishes it as a flat offset
src/client/editor/extensions/awareness.ts:225-256 ; src/server/mcp/awareness.ts:269, :438 ; src/server/document-store.ts:336
[ran: vitest run --config ./vitest.config.ts a-bugs.test.ts]
Plugin 2 of the awareness extension writes `Y_MAP_ACTIVITY.cursor = state.selection.from` (a PM position, which counts node boundaries) while the sibling `Y_MAP_SELECTION` write goes through `pmSelectionToFlat` correctly; `tandem_getActivity` / `tandem_checkInbox` pass `activity.cursor` through untouched into the same field family the docs show as a flat offset (docs/mcp-tools.md:907-925 "cursor": 142, no caveat) and skills/tandem/SKILL.md:79 tells Claude to check it before annotating near the cursor. In the harness doc `"# Title\nSome text here\none\ntwo Zthree"`, `activity.cursor` read 38 while the same caret's flat `selection.from` was 32, so a Claude that honours the skill avoids the wrong region (here "hree" instead of the true caret) and the drift grows with every block boundary above the caret.
Confidence: high (reproduced end-to-end, both writers and both readers read).

### High — Find/Replace positions are off by one per preceding hard break; replace corrupts text
src/client/editor/extensions/find-replace.ts:74-88 (walkMatches), :258-270 (replaceActive), :272-309 (replaceAll)
[ran: vitest run --config ./vitest.config.ts a-bugs.test.ts]
`walkMatches` searches `node.textContent` (in which a hardBreak contributes zero characters) but converts match indices with `pos + 1 + idx` (in which a hardBreak occupies one position), so every match after a `<br>` in the same textblock is shifted one position left per break, and the shifted range is what `replaceActive`/`replaceAll` hand to `insertText`. Reproduced: `<p>alpha<br>bravo charlie</p>` find "bravo" → match {6,11} = `<br>brav`; replaceActive("XXXXX") → `<p>alphaXXXXXo charlie</p>` (break deleted, wrong letters replaced); `replaceAll` cat→dog on `<p>one<br>two<br>cat sat</p>` → `<p>one<br>twdogat sat</p>`. Highlights show the same shift, so the user sees the wrong text selected before pressing Replace.
Confidence: high. Fix shape: walk `node.forEach` text children (or `textBetween(pos+1, pos+node.nodeSize-1, "￼")`) so hardBreak is one char in both coordinate systems.

### High — Slash menu opens inside code blocks and rewrites code on Enter
src/client/editor/slash-menu/extension.ts:80-108 (resolveActiveSlashCommand), :342-345 (Enter) ; slash-menu/commands.ts:104-110, :260-267
[ran: vitest run --config ./vitest.config.ts e-keys.test.ts]
`resolveActiveSlashCommand` gates on `isSlashMenuSuppressed()`, an empty selection and the `/(?:^|\s)\/([A-Za-z0-9 -]*)$/` regex on `$from.parent.textBetween`, but never on `$from.parent.type.spec.code`, so typing a path like `cd /t` (or any `/word` at a line start) inside a fenced code block opens the menu; Enter — the key that inserts a newline in code — is captured, `executeSlashCommand` deletes the "/t" and runs the first match. Reproduced: `<pre><code>echo hi\n</code></pre>` + "/e" + Enter became `<p>echo hi\n</p>`; `cd /t` + Enter became `<p>cd </p>` (text deleted, code block converted to a paragraph). Tiptap's own suggestion utility has an explicit `allowedPrefixes`/`allow` hook for exactly this; Tandem's custom matcher lacks the equivalent.
Confidence: high.

### Medium — Ctrl+Enter both inserts a hard break AND accepts the pending annotation
src/client/hooks/useAppShortcuts.ts:266 ; src/client/App.svelte:1563-1571 ; node_modules/@tiptap/extension-hard-break/dist/index.js:62-63 ; src/client/editor/extensions/plaintext-breaks.ts:86-89
[ran: vitest run --config ./vitest.config.ts e-keys.test.ts]
Tiptap's HardBreak (and Tandem's PlaintextBreaks for .txt) bind `Mod-Enter` and handle it inside ProseMirror (`defaultPrevented: true`), but the window keydown listener in `useAppShortcuts` still matches `Enter` with `ctrlKey` as `annotation-accept-or-dismiss`, and the App.svelte dispatcher checks `shouldIgnoreShortcut` (INPUT/TEXTAREA/isComposing only — contenteditable is not covered) but never `e.defaultPrevented`. With the caret in the editor and a pending Claude comment, Ctrl+Enter inserts `<br>` at the caret and accepts the annotation in the same keystroke; Ctrl+Shift+Enter inserts `<br>` and dismisses it. Reproduced in harness (HardBreak run gave `<br>` + defaultPrevented; `matchShortcut` on the identical event returned `annotation-accept-or-dismiss`).
Confidence: high that both fire; Medium severity because it needs a pending annotation and the caret in the document (the documented "accept from anywhere" affordance is what makes it reachable).

### Medium — AltGr (Windows/Linux Ctrl+Alt) characters are swallowed by Ctrl shortcuts on non-US layouts
src/client/hooks/useAppShortcuts.ts:126-312 (matchShortcut: `const mod = e.ctrlKey || e.metaKey`, no `altKey` gate on KeyS/KeyN/KeyW/KeyO/KeyF/KeyG/Digit1-9/Enter; `altKey && KeyT/KeyA/KeyM` branches)
[ran: vitest run --config ./vitest.config.ts e-keys.test.ts]
On Windows, AltGr is delivered as `ctrlKey && altKey`, and because matching is by `e.code` (documented as the layout-independence choice) the branch cannot see that the produced character is a letter: Polish `ś` (AltGr+S) → `save`, `ń` → `new-scratchpad`, `ó` → `open-file`, `ą` → `toggle-authorship`, Romanian `ț` (AltGr+T) → `reopen-closed-tab`, Czech/German `{`/`[` on Digit7/Digit8 → `pick-tab`; each handler calls `preventDefault()`, so the character never reaches the document. Users on pl/ro/cs/de/hu layouts lose ordinary letters and brackets while typing prose. Fix: return null when `e.ctrlKey && e.altKey && !e.metaKey` for the non-Alt branches (Chrome's own convention), or gate on `e.key.length === 1 && !/^[a-z0-9]$/i.test(e.key)`.
Confidence: high on the code path (harness), medium that real Chromium/WebView2 delivers the exact flags (well-documented, not run here).

### Medium — Heading toggle on an annotated paragraph shifts the annotation and the server stamps it `repaired` from stale offsets (extends the already-reported repaired-arm finding)
src/client/positions.ts (relRangeToPmPositions null path) ; src/server/positions.ts refreshRange
[ran: vitest run --config ./vitest.config.ts a-bugs.test.ts]
Delta only: toggling a paragraph to a heading via y-prosemirror rebuilds the Y.XmlElement, so both RelativePositions die; the client falls back to the stale flat range, which now points three characters early once the `## ` prefix is counted ("charlie" → "vo char"), and the server's `refreshRange` re-anchors from the same stale flats and thereafter reports `ok` forever. Same root cause as the reported repaired-arm bug; this is a third door (heading toggle) alongside join and the reported cases, and it is the one a user hits from the toolbar with no text editing at all. List wrap and Enter-at-start were fine.
Confidence: high.

### Medium — Enter handlers in five inputs ignore `isComposing` (IME users submit/commit on the composition Enter)
src/client/panels/ChatPanel.svelte:184 ; src/client/editor/toolbar/LinkEditor.svelte:42 ; src/client/editor/find-replace/FindReplaceBar.svelte:256 ; src/client/tabs/TabRenameInput.svelte:55 ; src/client/components/CommandPalette.svelte:344 ; src/client/components/OutlinePanel.svelte:116
[read: src/client/panels/ChatPanel.svelte:180-190]
Only `matchShortcut` and `shouldIgnoreShortcut` check `e.isComposing`; each of these listens for `key === "Enter"` and acts (send chat message, apply link, jump to next match, commit rename, run palette command) with `preventDefault()`. For Japanese/Chinese/Korean input the Enter that confirms the candidate is delivered as a keydown with `isComposing: true` (and, in Safari, a trailing keydown with keyCode 229), so a chat message is sent with the half-converted text and the link editor commits a partial URL. Chat is the worst: the message goes to Claude and cannot be recalled.
Confidence: medium (code read; behaviour is the standard IME contract, not run in a browser).

### Medium — Toolbar `capturedRange` is a PM range frozen while the comment composer has focus; remote edits above it are not mapped
src/client/editor/toolbar/Toolbar.svelte:738-749, :788-793, :821-825
[read: src/client/editor/toolbar/Toolbar.svelte:730-830]
`captureSelectionRange` stores raw `{from,to}` PM positions when the composer opens and re-capture is suppressed while `popupHasFocus()`; `createAnnotation` uses `capturedRange ?? editor.state.selection` and sends it via `pmToFlat` at submit time. If Claude (y-sync) inserts or deletes text above the captured span while the user is typing the comment, the stored positions are not mapped through the remote transaction, so the annotation lands on shifted text. A `Mapping`/`tr.mapping.map` in the `transaction` handler (or storing a `TextSelection` bookmark) fixes it.
Confidence: medium (read; the y-sync rebuild path is exactly the #1669 class, not executed here).

### Low — Ctrl+N / Ctrl+W / Ctrl+T are documented unconditionally, but the browser build cannot claim them
docs/user-guide.md:406-409 ; README.md:104 ; src/client/components/OnboardingTutorial.svelte:42 ; src/client/hooks/useAppShortcuts.ts (no tauri/isDesktop gate on KeyN/KeyW/KeyT)
[read: docs/user-guide.md:400-412]
Chromium and Firefox treat Ctrl+N (new window), Ctrl+W (close tab) and Ctrl+T (new tab) as browser-reserved — the page's `preventDefault()` is ignored — yet the shortcut table, the README and the first-run tutorial ("Open a tab or scratchpad with Ctrl+N") present them with no desktop-only caveat, and no doc or help surface mentions the browser limitation (grep for "reserved"/"intercept" across user-guide, troubleshooting, HelpModal, OnboardingTutorial returned nothing). In the npm-global browser install, Ctrl+W closes the Tandem tab itself (losing an unsaved scratchpad) and Ctrl+N opens a blank browser window instead of a scratchpad; the tutorial then tells a brand-new user to press the one key that does the wrong thing. Mitigation exists (ShortcutEditorList lets users remap) but nothing points them at it.
Confidence: high on the doc/code state; the browser behaviour is the platform contract, not run here. Promotes the "Unchecked lead" above; keep the lead entry as resolved.
