### Desktop / Tauri

`cargo tauri dev` / `cargo tauri build`. Layout, sidecar lifecycle, origin handling and the
logging/DevTools split are in [architecture.md](architecture.md). These bite silently:

- **`single-instance` must be the FIRST plugin registered** in `lib.rs` — later registration breaks instance detection with no error.
- **Redact a captured child-process stream BEFORE truncating it, never after** (#1372). `redact_home` matches the home directory as a plain substring, so cutting the string first can slice through that prefix; `contains(home)` is then false, the redaction silently no-ops, and the surviving fragment still spells the username. The redaction ends up active only in the cases where truncation was *not* — i.e. never in the long outputs that most need it. `firewall.rs`'s `redact_and_truncate` is the one place the ordering lives; the excerpt it returns is what goes on the wire **and** into the log line, because logging the raw one makes the durable copy the unredacted copy (`TargetKind::LogDir` keeps 25 MB that users attach to bug reports, and release builds log at `Warn`).
- **`#[serde(rename_all = "camelCase")]` on an enum renames the VARIANTS only, not struct-variant fields.** `rename_all_fields = "camelCase"` (serde ≥ 1.0.184) is the one that renames fields. `FirewallError::NetshFailure` went out as `exit_code`/`stderr_tail` while `src/client/types.ts` read `exitCode`/`stderrTail`, so `truncateStderr(undefined)` threw and the UI fell back to raw JSON — for months, with no type error on either side. Any tagged enum crossing the Tauri boundary needs both attributes.
- **Two `externalBin`s: `node-sidecar` AND `tandem-reaper`.** Both must exist or `cargo tauri dev/build` fails its existence check. The reaper shipped missing in every desktop build before #1268 — "Relaunch Claude" could not spawn.
- **`create_overlay_titlebar()` must be called post-page-load**, from the component's `onMount` — the hit-test JS `tauri-plugin-decorum` injects is cleared on WebView navigation. No error; the titlebar just stops hit-testing.
- **The `devtools` feature is mutually exclusive with `tauri-plugin-log`** — both install a global `tracing` subscriber, so the log plugin is `#[cfg(not(feature = "devtools"))]`-gated.
- **A sync `#[tauri::command]` runs on the main thread, and `#[tauri::command(async)]` on a sync fn does NOT fix it (#1371).** Tauri picks the execution context from *syntax*: a plain `fn` is `ExecutionContext::Blocking` and is dispatched inline on the UI thread, so any `Command::output()` inside it freezes the window. `(async)` on a sync fn looks like the cure — `tauri-macros` even labels that shape `"sync_threadpool"` (`command/wrapper.rs:264`) — but that string is only a `tracing` span field. `body_async` calls the sync fn *inside* the future (`wrapper.rs:389`) and `respond_async_serialized_inner` hands it to `async_runtime::spawn` (`tauri/src/ipc/mod.rs:385`), i.e. tokio's **worker** pool, so one blocking wait also delays every other `respond_async` command and each repeat click adds another. Use `async fn` + `tauri::async_runtime::spawn_blocking`, and **bound the external process with a deadline** — `tokio::time::timeout` around `spawn_blocking` abandons the wait but does not cancel the work, so the deadline has to live where a `kill()` is possible (`src-tauri/src/bounded_command.rs`). Two further traps once you move off the main thread: the main thread WAS the serialization, so a user-repeatable command needs an explicit in-flight guard (`src-tauri/src/single_flight.rs`); and a bare `try_wait` poll loop with no concurrent reader deadlocks as soon as the child fills the pipe buffer. Worked examples: `port_holder_for_dialog` and `cowork_detect_vethernet_subnet`.
- **Cowork detection scans TWO roots** (ADR-044) and candidate dirs must be UUID-shaped or carry a `cowork_plugins\` marker — **never write plugin-registry files into other siblings**. All four write entry points re-run `revalidate_resolved_path` at write time (#433 TOCTOU); `check_acl` fails closed.

### Origin tagging — which helper to use (Critical Rule 2)

Raw `doc.transact(...)` is forbidden anywhere in `src/`. Pick one of the six helpers from
`src/shared/origins.ts`. **Picking the wrong one is a silent bug — the helper choice is the
contract, not a label.** See ADR-031.

| Helper | Use for |
|---|---|
| `withMcp` | Claude-initiated writes from MCP tools |
| `withFileSync` | Echoes from the durable-annotation file-writer / the file-watcher reload path's JSON→Y.Map merge |
| `withInternal` | Server-internal setup writes: session restore, mdast/docx population, tutorial seeding, scratchpad seeding, force-reload, server metadata broadcasts |
| `withReload` | The `reloadFromDisk` file-watcher flow, including the post-reload `refreshAllRanges` continuation |
| `withModeRelease` | The server-owned Solo→Tandem release sweep. Behaviourally mirrors `mcp` today, but a server-owned sweep is not a Claude-initiated write and carries its own semantic identity |
| `withBrowser` | User edits originating in the browser |

Who skips what: the durable-annotation sync observer skips `file-sync` and `internal`. The
channel event queue skips `mcp`, `file-sync`, `internal`, `reload` and `mode-release` — so
**only `browser` writes generate channel events.**

**Client origins never cross the wire, and two shipped comments got this wrong (#1482).** Two
independent reasons, either alone sufficient. Yjs never serializes the origin: `yjs.cjs:3389` emits
`transaction.origin` as a local JS event argument *beside* the encoded update, so it is not in the
bytes. And Hocuspocus re-tags every incoming client update with the `Connection` anyway —
`readSyncStep2(..., connection ?? this.defaultTransactionOrigin)` at
`hocuspocus-server.esm.js:1408`, reaching `Y.applyUpdate(doc, ..., transactionOrigin)` at `:1151`.
Since `shouldSkipChannel` compares against string constants, a `Connection` instance never matches
and browser traffic is never skipped — which is what actually makes a user edit channel-eligible.
So a server observer **cannot** distinguish a `withBrowser` write from an untagged one, and no
client-side consumer filters on origin either (Tiptap's Collaboration tracks only
`ySyncPluginKey`). Client-side tagging is hygiene, auditability and one mental model — **it is not
a privacy or channel-filtering control**, and a PR describing it as closing a leak is wrong. The
skip-set table above governs writes made *on the server*.

**Never call an editor command inside a `with*` callback.** ProseMirror commands dispatch through
y-prosemirror's own `doc.transact(..., ySyncPluginKey)`, and a transact opened while an outer one
is live **inherits the outer origin**. Since `yUndoPlugin` captures only `ySyncPluginKey`
transactions, wrapping a command in `withBrowser` makes the resulting text **un-undoable** —
and y-prosemirror's `mux` self-echo guard releases before the deferred observers run, so the
editor also takes a full-document `replace`. Split such code into separate one-statement
transactions around the command, never one wrap spanning it. `useAnnotationReview`'s accept path
is the worked example: three transactions, because `applySuggestion` sits between them.

Enforcement is warn-only: the `check-raw-transact.sh` PostToolUse hook plus the
`npm run audit:origins` static walk. There is no blocking pre-commit hook and no Biome rule.
**The hook is PostToolUse-only** — it only ever sees files an agent just edited, which is how
three raw `.transact(` calls sat in `src/client/hooks/useChatState.svelte.ts` unnoticed: nothing
swept code nobody happened to touch. Since #1482 the audit walks all of `src` (not just
`src/server`), covers `.svelte`, and reports a **census of correctly tagged sites** rather than a
bare `clean`, because post-fix the count of bad things in `src/client` is zero — and so is the
count an audit that stopped scanning reports. The script still exits 0; the gate is
`tests/scripts/audit-origins.test.ts`, which fails if the walk is re-narrowed.

**A bare `map.set(...)` is invisible to all of the above**, since there is no `.transact(` to
match and static detection is not achievable at usable precision (`.set(` collides with native
`Map`/`Set`, ProseMirror and `$state`; and `withBrowser(doc, () => helper())` is correct code no
intra-procedural rule can bless). The complement is a DEV-only runtime check —
`installUntaggedWriteWarning` in `src/client/utils/`, armed on both `new Y.Doc()` sites in
`yjsSync.svelte.ts` — which warns on any mutating transaction with a null origin. One known benign
source: `y-prosemirror.cjs:834` merges adjacent Y.Text nodes in an untagged transact of its own.

### Y.js / CRDT
- **Y.XmlText must be attached before populating.** Inserting formatted text into a detached Y.XmlText reverses segment order. Always attach to Y.Doc first, then insert (two-pass pattern in `mdast-ydoc.ts`).
- **Y.XmlElement.setAttribute needs `as any` for numbers.** TypeScript types say string-only but Tiptap stores numeric heading levels.
- **Stale browser tabs are auth-rejected after a server restart (generation gate).** Historically a tab surviving a restart would CRDT-merge its old Y.Doc state back on reconnect, duplicating/reverting content whenever the server loaded fresh from disk (disjoint histories). Now every `HocuspocusProvider` pins the server run's `generationId` (from `GET /api/info`, loopback-only field) as its auth token at construction; the server's `onAuthenticate` hook (`yjs/provider.ts`) rejects mismatches for **every** room including `CTRL_ROOM` — sync messages queue until auth passes, so a rejected stale doc never merges. On `authenticationFailed` the client re-fetches the generation and rebuilds ctrl + all tabs with fresh Y.Docs (`scheduleRebuild` in `yjsSync.svelte.ts`). The generation id lives in module state (`getGenerationId()`) and travels over HTTP only — deliberately never broadcast via the ctrl Y.Map, where a stale merge could clobber it (concurrent YMap set → clientID coin flip). Unsaved browser edits from before the restart are dropped by design (the shutdown disk flush + session save make graceful restarts lossless for synced edits). Tokens are pinned strings, not closures: a provider whose ydoc predates the restart must never re-authenticate. In stdio mode no HTTP route serves the generation, so browser clients are fully locked out — they were already non-functional there (the editor needs the :3479 API).
- **Force-reload clears in-place.** `tandem_open` with `force: true` clears annotations, awareness, and content in a single transaction. Don't use mid-review -- annotations are still lost. See observer ownership table in [architecture.md](architecture.md#ymap-observer-ownership).
- **CRDT fallback logging.** `buildDecorations()` emits `console.warn` when an annotation falls back to flat offsets. Check the browser console -- these indicate CRDT degradation.
- **Dead CRDT RelativePositions must be stripped, not preserved.** After `reloadFromDisk` replaces Y.Doc content, old `relRange` RelativePositions reference deleted items. `refreshRange` strips dead `relRange` and re-anchors from flat offsets. A stale `relRange` that resolves to null blocks the lazy re-attachment recovery path -- deletion is better than preservation.
- **A CRDT-anchored range self-heals under DELETION but not under insertion — the asymmetry is easy to over-generalise (#1471 gap 3).** Because the two endpoints are independent anchors, clipping either side of a range makes it resolve to exactly the sub-span it still owns, with no arithmetic: prefix, suffix, boundary and whole-range deletions all come out right for free. An insertion *between* the endpoints touches neither of them, so the range silently widens to cover text it does not own. For authorship that means one entry stretching across another author's words while that author's own entry sits on the same characters — two inline decorations with conflicting `data-tandem-author`, and a gutter counting those characters for both authors. `splitCoveringEntries` in `authorship.ts` handles it by cutting the covering entry into the pieces it still owns, all in one pass over the transaction's whole insertion set (a per-insertion pass has to skip entries it already cut, which re-creates the bug on find-replace-all). Note the reverse of the usual intuition: **anchoring makes this case worse before better** — with frozen offsets the widening was unreliable and half-healed into a different wrong, while anchored it is stable, reproducible and permanent. Three things about that fix bite silently if changed: it splits **only when the authors differ**, because testing containment against every entry costs two document walks each on the keystroke path (measured 42–51× slower at 1,500 entries, *including* where nothing splits); that skip is only safe because **the gutter resolves an author per character** rather than summing per-entry overlaps, so a same-author entry left stretched cannot inflate `dominant`; and piece ids are **derived from the original** (`{id}#1`), because `stampClaudeAuthorshipWholeDoc` re-`set`s `claude-block-{i}` on every re-open and would otherwise restore the whole-block range on top of orphans it cannot see. **A block-structure change is a different mechanism entirely, and `splitCoveringEntries` deliberately does not cover it** — see the next bullet (#1512).
- **A structural step destroys an anchor outright, and the loss is SILENT (#1512).** y-prosemirror implements a block-structure change by deleting the affected text out of its `Y.XmlText` and re-inserting it, or rebuilding the `Y.XmlElement` outright — no CRDT relationship survives, so a covering entry's anchor cannot follow. Nothing warns, because `resolveAuthorshipRange` deliberately does not fall back to the flat range for an anchored entry (#1471 §1.5): the entry stays in the map painting nothing at all. **Five doors reach it, and Enter — the one originally filed — is the mildest.** A backspace-join, a heading toggle and a list or blockquote wrap each lose the WHOLE entry; a multi-block paste is worse still, stretching the covering entry over the pasted text so content from elsewhere paints as the user's own work. The repair (`capturePositions` + `reanchorCaptured` in `authorship.ts`) snapshots each entry's position during `EditorState.apply`, while the pre-change Y.Doc is still readable, then re-anchors from the ProseMirror mapping — the only witness to where the text went. Three things bite if changed: the gate must **not** be keyed on `step.structure` alone, because paste's step carries `structure: false` and is the door that mis-attributes rather than merely losing; the capture must be **invalidated by an appended transaction**, whose steps are invisible to the root transaction's mapping; **coalescing must be refused outright on a structural transaction** — a split destroys the candidate entry's `toRel`, Yjs resolves the destroyed anchor to the LEFT EDGE of the deletion, and for a mid-run split that is exactly where the new text was typed, so the adjacency test passes on a coincidence, merges into the dead entry and rewrites its `toRel` to the split boundary, losing everything past it forever (the merge also keeps the candidate's id, which made the repair skip the very entry it exists to rebuild — measured identical on master, so it is a gap the repair closes rather than one it introduced); and a repaired entry routinely **spans a block boundary**, which is why the gutter must count content positions only (#1519) — a cross-block entry otherwise marks each adjacent block's open and close token as an authored character.
- **A remote sync REPLACES the doc, so every inline decoration maps to nothing (#1669).** y-prosemirror's `_typeChanged` does not patch the ProseMirror doc, it rebuilds it: one `ReplaceStep` spanning the whole document, tagged with `ySyncPluginKey` meta. `InlineType.map` maps `from` with assoc `+1` and `to` with assoc `-1`, so every inline decoration collapses to `from >= to` and is dropped — highlights, comment underlines, suggestion squiggles and the authorship overlay all vanish on any MCP write or remote keystroke. **A plugin that only `.map()`s its `DecorationSet` on `docChanged` therefore loses its decorations, and an identity-keyed recovery gate cannot catch it**: `mapChildren` always returns a fresh `DecorationSet` once there are children, so the first mapped result is never the `DecorationSet.empty` singleton — sync N wipes, N+1 still fails the gate, and only N+2 can fire. The fix is to REBUILD on the tagged transaction rather than map: `_typeChanged` runs during Yjs transaction cleanup, so the Y.Doc is already updated and the CRDT anchors resolve to the right text, which mapping cannot do. `annotation.ts`, `authorship.ts` and `awareness.ts` each carry that branch; a **new** decoration plugin needs its own, because nothing structural forces one. Two existing plugins deliberately do NOT: `find-replace.ts` re-runs `walkMatches` on every `docChanged`, so it is immune by construction, and `annotationPing.ts` is map-only and therefore still loses its ping to a concurrent write — accepted, because a ping is a sub-second flourish and its absence is indistinguishable from it having finished. Three facts worth not re-deriving, all checked against the pinned y-prosemirror 1.3.7: local PM->Y edits carry no ySync meta (its own `mux` mutex suppresses the re-entrant fire), no awareness- or cursor-only transaction is tagged, and the UndoManager replay IS tagged (`isUndoRedoOperation`). So the branch fires on every remote character, every MCP write, every watcher reload and every undo replay — affordable only because `_typeChanged` is already re-serializing the whole fragment on the same transaction, which is why nothing expensive (a settings load, an I/O read) belongs inside it. **Two more tagged shapes the list above deliberately omits, because they behave differently:** `_forceRerender` (fired on view init) is Y-derived and wants the rebuild like the rest; `renderSnapshot`/`unrenderSnapshot` are NOT — they dispatch a doc built from a historical `Y.typeListToArraySnapshot`, so a rebuild resolving anchors against the LIVE Y.Doc would paint onto a historical projection and the index-parallel Y/PM walk would misalign. Nothing in `src/` sets snapshot meta today, so the branches are unguarded on purpose — but **a View-History feature cannot be built on top of them as they stand.** And the affordability of the rebuild is a measured fact, not a deduction: on a 200-paragraph document, ms per remote transaction, `.map()` versus rebuild, 0 annotations 0.75 -> 0.82, 50 annotations 1.03 -> 1.20, 150 annotations 1.85 -> 4.55. It does NOT hide behind `_typeChanged`'s own cost — `createNodeIfNotExists` returns the cached PM node for every unchanged top-level child, so that baseline is the changed subtree, not the whole document. `tests/client/decoration-rebuild-cost.bench.test.ts` re-derives the table.
- **Authorship stamps COALESCE, so one entry is a run of typing rather than one keystroke — and three of its conditions fail silently if changed.** The map gained an entry per doc-changing transaction and was never compacted; anchored entries are never reaped (#1480), so nothing removed them. Measured: 500 distinct keys encode to 136,290 bytes of session file, 500 re-sets of one key to 310 — but **that 440x is a property of `doc.gc`**, and setting `gc: false` anywhere to preserve history would take it away with no other signal. `coalesceIntoPrevious` extends the previous entry when the author matches and the new text is adjacent, assembling the merged anchor from the two endpoint anchors that **already exist** rather than re-minting (re-deriving a known-good anchor crosses the PM-Y seam of #1450/#1459, and `flatOffsetToRelPos`'s assoc-directed retry returns a *wrong* anchor rather than none). Adjacency is compared in **PM positions**; the candidate is found by one id in extension storage, never a map scan, since an O(entries) fix would defeat its own purpose. The three silent ones: `lastStampId` is **left alone by a transaction that stamps nothing**, because backspace is exactly that and backspace-then-retype is the commonest editing rhythm there is — clearing it there guts the saving; it is **cleared before the y-sync early return**, or a remote/MCP/force-reload change leaves a candidate the next keystroke extends; and there is deliberately **no collapsed-candidate guard**, because measuring showed its only effect is to strand the collapsed entry forever, which is the accumulation being fixed.
- **An annotation's `textSnapshot` may be a PREFIX, not the whole range — ask `isSnapshotTruncated()` before doing anything with it (#1486).** `captureSnapshot` caps it at 200 characters to bound record size against pathological ranges (#1000 review R2), and since #1486 reports the cut as `textSnapshotTruncated` rather than marking it in the text. **A prefix locates the range's START and says nothing about its END**, and that asymmetry decides what each consumer may do — the predicate and `snapshotSearchPrefix()` live in `src/shared/snapshot.ts` precisely so the four of them cannot drift apart:
  - **Undo** (`useAnnotationReview.svelte.ts`) needs the whole text and must **decline** — restoring a prefix deletes everything past the cap. The decline is permanent, so it reports via `onUndoFailed`, not just a console warning.
  - **The reload relocation pass** (`documents/watcher.ts`) may **relocate on the prefix and carry the original span across**. Both simpler options are wrong: re-anchoring to `match + snapshot.length` shrinks a long annotation to 200 chars on every reload (after which accept replaces the wrong span), and *skipping* is no better, because `refreshAllRanges` has already minted a fresh `relRange` from the stale offsets — so the record ends up durably pinned to the wrong text and never revisited.
  - **The `.docx` apply guard** (`file-io/docx-apply.ts`) must compare with `startsWith`, not `===`. Exact comparison rejects every suggestion over a 200-char range and reports it as "the text changed" when nothing had.
  - **The chat anchor** (`App.svelte`) is deliberately outside all of this and keeps its in-band ellipsis — not because it stays local (it reaches the AI through `tandem_checkInbox`) but because nothing writes it back into the document. `SnapshotBearing` requires an `id` so it cannot be passed to these functions by mistake.

  Two more things worth knowing. The reload hazard was **dormant by accident** before #1486 — the old `"..."` occurs nowhere in a document, so `indexOf` missed and the range fell to a harmless RANGE_GONE; removing the marker to fix undo is what armed it. And `isSnapshotTruncated` detects pre-#1486 records (no flag, exactly 200 chars, trailing `"..."`), because those are what is on users' disks; `snapshotSearchPrefix` trims those three characters so legacy records relocate rather than stranding.
- **Hocuspocus replaces Y.Doc in `onLoadDocument`.** The `onDocSwapped` callback in `provider.ts` reattaches server event queue observers to the new instance. A runtime warning fires if the callback is missing. See #178 audit.
- **Annotation-sync cleanups distinguish swap vs close.** `registerAnnotationObserver` returns `(phase?: "swap" | "close") => void`. A Y.Doc swap keeps the per-doc tombstone ledger alive so in-flight debounced writes still serialize tombstones; only `"close"` drops the ledger. `reattachObservers` passes `"swap"`; `clearFileSyncContext` / `setFileSyncContext`'s replace path pass `"close"`. See #333.
- **Y.js "Invalid access" warnings** during session restore are harmless stderr noise.
- **`getElementText()` strips inline marks and separates nested blocks.** The function uses `toDelta()` (not `toString()`) for XmlText content, emitting `\n` for embedded elements (hardBreaks) **to preserve XmlText index alignment**. Child XmlElements (listItem, paragraph, blockquote) are separated by `\n`. This matches ProseMirror's block structure for correct flat-offset alignment.

### MCP / Server
- **Channel shim uses low-level `Server`, not `McpServer`.** The Channels spec requires `import { Server } from '@modelcontextprotocol/sdk/server/index.js'` with explicit `setRequestHandler()` calls. The HTTP MCP server uses the high-level `McpServer` wrapper.
- **The boot sweep rewrites the user's MCP config, and every guard on it fails silently.** `repairEntryInPlace` repairs stale absolute paths in `tandem`/`tandem-channel`, and since the npx-convergence rule it also replaces a bare-`npx` `tandem` entry's `args` wholesale. A wrong match here edits `~/.claude.json` or the Claude Desktop config -- files holding other vendors' entries and bearer tokens -- with no type error and no failing test. Three rules: ownership is decided ONLY by `REFRESHABLE[key].classify` (a required three-arm discriminant, never a branch above the gate); the convergence arm must EARLY-RETURN, because falling through re-classifies the entry as already-repaired and exits `{changed: false}`, discarding the mutation silently; and convergence is scoped to `targetKind === "claude-desktop"`, the only target Tandem writes a stdio entry to. Gates refuse rather than sanitize, and the durability gate fails CLOSED.
- **Channel meta keys use underscores only.** The Channels API silently drops meta keys containing hyphens. Use `document_id`, `annotation_id`, `event_type` -- not `document-id`.
- **`APP_VERSION` is baked at build time** via the `__APP_VERSION__` tsup define in `src/server/mcp/server.ts`. Falls back to `createRequire("../../package.json")` in tsx dev and vitest. `__MCP_SDK_VERSION__` follows the same pattern. `findChangelogPath()` in the same file walks up from `__dirname` to find `CHANGELOG.md` (handles both `src/server/mcp/` in dev and `dist/server/` in production).
- **MCP must start before Hocuspocus** in stdio mode -- init timeout fires if order is reversed.
- **HTTP MCP is multi-session: one `McpServer` per transport, keyed by `Mcp-Session-Id`** (`mcp/transport-registry.ts`, ADR-045). **This is the *legacy* branch as of MCP `2026-07-28`, which removed protocol-level sessions, the `Mcp-Session-Id` header and the `initialize` handshake** — accurate today (no SDK implements the new revision yet) and required for as long as un-upgraded clients exist, but do not key new per-client state on it. See ADR-045's 2026-07-30 amendment and #1249. `initialize` never evicts another session. Two SDK facts are load-bearing: `Protocol.connect()` throws if a server already has a transport (so servers can *not* be shared), and `transport.sessionId` is minted while *handling* the initialize request, so entries can only be registered from the `onsessioninitialized` callback -- not after `connect()`. Unknown session id → 404 `-32001`, never 503. `X-Claude-Session-Id` (the *Claude Code* session, distinct from the MCP session) is **optional**: only the stdio-bridge config path carries it; the direct-HTTP entry `buildMcpEntries` writes for Claude Code CLI has no subprocess and sends nothing. Never assume it is present. Read it inside a tool handler via `getCurrentSessionId()` (`sessions/context.ts`); the `AsyncLocalStorage.run()` must wrap the **entire awaited** `handleRequest`.
- **An open `GET /mcp` stream pins its session against the idle reaper (#1588).** `reapIdle()` filters on `lastSeenAt < cutoff && openStreams === 0`, and the second clause is the load-bearing one: `lastSeenAt` advances *only* in `dispatchToSession`, so a client holding a live SSE stream and simply making no tool calls looked exactly like one that had been SIGKILLed and got closed after 30 minutes. That is what broke Claude Desktop's bridge for the rest of the day. Three details bite. **`openStreams` is a counter, not a boolean** — a client reconnecting its stream can have the new open observed before the old close, and an unbalanced boolean wedges either at false (reaping a live client) or true (leaking the session). **The increment and its `res.on("close")` decrement must be adjacent and synchronous** in the GET route, because anything that throws between them pins the session permanently, recoverable only by LRU. And **`onEntry` fires before the awaited `handleRequest`, deliberately** — for a GET, `handleRequest` does not resolve until the stream closes, so "simplify this to after the dispatch" would silently never mark a stream open. **LRU eviction is deliberately NOT pin-aware**: `lastSeenAt` is evidence of use, `openStreams` only of attachment, and keeping LRU pin-blind is what stops the pin locking a legitimate client out — the cap-exceeding `initialize` still evicts, and the bridge's reconnect makes that recoverable. Pinned by a test.
- **The stdio bridge re-initializes on a `404 -32001` rather than being respawned (#1588).** `src/cli/mcp-stdio.ts` used to carry an explicit "no reconnection logic" comment resting on the plugin loader respawning it — true for Claude Code, false for Claude Desktop, which keeps the child alive all day. Recovery replays a handshake the bridge never owned: the client's `initialize` and `notifications/initialized` are captured in flight and replayed on a **new** transport (the SDK's is single-use — `close()` aborts the abort controller without clearing it, so `start()` throws on a reused instance) under a private `__tandem_reinit_<uuid>` id whose response is swallowed. Four things are easy to get wrong. The SDK's **`close()` fires `onclose` unconditionally**, so the old transport's handlers must be unwired and the generation bumped before closing it, or the first reconnect calls `shutdown(1)`. **`http = fresh` is assigned before the handshake**, so a failure leaves a live session-less transport that 404s and re-triggers, rather than a closed one whose every `send()` rejects with an AbortError carrying no `.code`. **The replay deadline must bound the POST, not just the wait for its answer** — a server that accepts and never responds leaves `send` pending forever and latches the reconnect. And **the replay must include `initialized`** (synthesized if the client never sent one), because the SDK opens the standalone GET stream only from that notification's 202 branch. Failure is soft — `-32000` for what is pending, one capped-exponential retry, never an exit. One more that only shows up after a give-up: **the replay id is swallowed by prefix, not by id-equality against the awaited one.** A failed reconnect deliberately leaves its transport installed, so a merely-wedged server can answer that POST seconds after the deadline nulled `pendingReplayId` — an equality check forwards that answer to stdout, where the host reports `Received a response for an unknown message ID`.
- **Advertised tool schemas must declare no JSON Schema dialect (#1564).** The SDK stamps `"$schema": "http://json-schema.org/draft-07/schema#"` on every `inputSchema` and `outputSchema` it converts, and Claude Code's client validates output schemas as **2020-12 only** — it rejects the tool *client-side*, before any call reaches the server, so the seven `outputSchema` tools (the whole poll surface, `tandem_checkInbox` and `tandem_status` included) disappeared from live sessions while `curl` against `/mcp` kept working. `installSchemaDialectStrip` in `src/server/mcp/schema-dialect.ts` wraps the SDK's `tools/list` handler inside `createMcpServer`, so a new tool inherits the fix; a hand-rolled `Server` (the channel shim) does not, and writes its schema literally instead. Two things that look wrong and are deliberate: **input schemas are stripped too** even though only output schemas are rejected today — they carry the identical declaration and pass only because the client doesn't run them through that validator — and the installer **logs rather than throws** if the SDK's handler map moves, matching `snapshotToolCount` eight lines away in `server.ts`: throwing propagates to `process.exit(1)` and takes out the editor, Hocuspocus and all document access, to avoid a degradation in which everything but seven tools kept working. The gate that actually catches that drift is `tests/server/mcp-schema-dialect.test.ts`, which drives a real `tools/list` over HTTP.
- **Mutating integration routes (`POST /api/integrations`, `POST /api/integrations/apply`, `POST/DELETE /api/integrations/secrets/:ref`, `POST /api/integrations/install-claude-code`) require both `assertOriginAllowlisted` AND `assertLoopbackForMutation` at handler top, BEFORE any state mutation.** The apply route additionally gates on a constant-time nonce compare + in-process mutex + `IntegrationsFileSchema.safeParse` defense-in-depth. The install-claude-code route gates on origin + loopback + a dedicated in-process mutex (`getInstallGate()`/`_resetInstallGateForTests()`, mutex set inside the `try`) but **deliberately carries NO nonce** (S3: no persisted intent to bind, host-pinned + idempotent install). Read-only `GET` routes are intentionally exempt from the loopback gate; `GET /api/integrations/existing` scrubs `env`/`headers` so the bearer token in `~/.claude.json` never reaches the wire (`extractEntry` in `src/server/integrations/existing-config.ts`). `GET /api/integrations/claude-cli-status` is also ungated and LAN-reachable, so its response is **enum-only** (`{ presence }`) — never the resolved `~/.local/bin` path (F6). The installer itself (`install-claude-cli.ts`) fetches the pinned `https://claude.ai/install.{sh,ps1}` script and `execFile`s the interpreter on a locked-down temp file — never `| bash`/`| iex`; minimal allowlisted env so the wire-fetched script never sees the auth token (F1).
- **`tandem_convertToMarkdown` reports a malformed Windows `outputPath` as `FILE_NOT_FOUND`, and the advice that code carries is wrong there — known gap, not a bug to re-file (#1796).** `convert.ts` classifies `fs.realpath`'s errno, and on Windows `realpath` answers plain **ENOENT** for every shape POSIX distinguishes: a component that is not a directory (`C:\a\file.txt\sub`), an over-long component, and a genuinely missing directory all look identical (measured, Windows 11 26200). So the ENOTDIR/ELOOP/ENAMETOOLONG → `INVALID_PATH` arm is unreachable there and those cases land on `FILE_NOT_FOUND` — "Output directory does not exist" — a code chosen *specifically* to steer an AI caller into creating the directory, which then fails with its own ENOTDIR. The `it.runIf(POSIX)` gate on those specs in `tests/server/export-path-canonicalization.test.ts` is therefore correct rather than lazy: the conditions are unconstructible on Windows, not merely unrun (#1529). Distinguishing them would need a `stat`-the-nearest-existing-ancestor walk, which is more machinery than the gap warrants — this note is the closure. **Permission failures are NOT part of this gap**: they are classified across all three syscalls that can trip them and are pinned on Windows by `tests/server/convert-output-acl-win.test.ts` in the `windows-acl-proof` job.

### Files, Sessions & Lifecycle
- **A plaintext document cannot hold a break inside a block, so every producer of one is guarded — do not add a seventh (#1460).** `populateYDoc` makes one paragraph per line; `extractText` joins blocks with `"\n"` *and* renders a `hardBreak` as `"\n"`. The bytes are therefore always right and always ambiguous, and the reopen resolves the ambiguity as separate paragraphs — so a document that held a break silently comes back a different shape. The fix is six local guards keyed on `isPlaintextFormat` (`src/shared/plaintext-format.ts`), **not** a save-time normalizer: `plaintextAdapter.save` is also reached from `serializeDocument`, which backs the browser download preview and must not restructure a live document.
  - The six: `PlaintextBreaksExtension` (Shift+Enter / Mod+Enter → `splitBlock`), `splitPastedHardBreaks` (rich paste carrying `<br>`), **`splitSliceHardBreaks` (a `text/plain`-only paste)**, `tandem_edit` (refuses a newline — it is shaped as a single-paragraph replacement and `RANGE_MOVED`'s retry contract assumes that), `flattenPlaintextBreaks` at Save-As promotion, and `applySuggestion`'s block path.
  - **The sixth was missed on the first pass, and the reason generalizes: `transformPastedHTML` never runs for a clipboard with no `text/html` flavour.** That is an ordinary Ctrl+V out of a terminal, a code editor, `less` or an OS text field, where `clipboardTextParser` hands the text to `markdownToSlice` — whose token spec maps markdown break syntax straight onto a `hardBreak`. Ctrl+Shift+V was always safe and plain Ctrl+V was not, which is the opposite of the intuition. **Auditing the HTML paste path is not auditing "paste".**
  - **Each surface must carry the `codeBlock` exemption, and the Shift+Enter one shows why it is not merely redundant.** `splitBlock` has no `code` guard, so without the check it SUCCEEDED, cut the code block in two, and swallowed `Mod-Enter`'s exit-the-block affordance.
  - **A heading COLLAPSES to spaces; a table cell too; `<pre>` takes a literal newline.** Splitting a heading invents a `#` line the file will not contain, and `container.after()` on a `<td>` inserts a cell into the ROW — the row gains a column and ProseMirror pads every other row to match. All three were split by the first cut of the paste path, which disagreed with the Save-As path about identical content.
  - **A `codeBlock` at the top level IS flattened**, against the intuition that a newline there is genuinely a newline: `collectElementFlat` emits a code block with **no fences**, so in a plaintext file its bytes are already N lines and the reopen already yields N paragraphs. Excluding it left the divergence for the content most likely to be multi-line. Nested containers (list, table, blockquote) are *not* flattened and cannot be — `populateYDoc` rebuilds none of them from flat text — so `flattenPlaintextBreaks` **warns** rather than returning a bare `true` that reads as "the invariant now holds".
  - **`applySuggestion` declines to split anywhere but the top level**, matching undo's `canRestoreBlockBoundary`, and falls back to a hard break there. And **undo compares against what accept ACTUALLY WROTE** (`appliedProjection`), not against `suggestedText` — the heading collapse and any CRLF suggestion both make those differ, and comparing the raw suggestion made those accepts permanently un-undoable behind a live-looking Undo button.
  - **The Save-As flatten runs AFTER the write succeeds.** A Y.js transaction does not roll back, so flattening first meant a failed `atomicWrite` returned an error having already split the user's scratchpad. Byte-neutrality is what makes the position free — `output` is identical either way.
  - **`isPlaintextFormat` is a DENYLIST of `md`/`docx`, deliberately.** The plaintext set is `getAdapter`'s `??` fallback, so `.html`, `.log`, `.csv` and every unknown extension route through the same loader; an allowlist would leave them exposed. `undefined` reads as not-plaintext, so each guard fails OPEN rather than restructuring on a guess.
  - **`flattenPlaintextBreaks` is the only one that touches existing content, and it is safe because it is BYTE-NEUTRAL** — a hard break and a block boundary render identically, so when the split kills a `relRange` anchor `refreshRange` re-anchors from stored flat offsets and those still point at the same characters (measured for both split strategies). Two traps its own byte assertions caught: a **heading collapses to spaces rather than splitting** (`flattenHeadingText` already maps its newlines to spaces, so splitting would invent a heading and a line that were never in the file), and a `Y.XmlText` must be **attached before it is populated** or successive inserts reverse.
  - **Paste composition order is load-bearing:** split, *then* `normalizePastedHtmlWhitespace`. Collapsing first leaves the newline after the `<br>` interior to the paragraph, and the second half arrives with a leading space.
  - Byte round-tripping is pinned separately by `tests/server/txt-byte-fidelity.test.ts` (six whitespace shapes × five cycles, plus the divergence case as its control) — the bytes were never the defect, which is why no assertion about characters ever caught this.
  - **Historical correction, because it was wrong twice in the tracker:** #1460's disposition was once "invisible tier, document don't fix", on the grounds that both paste doorways were shut (`buildPlainTextSlice` splits on newline runs; `normalizePastedHtmlWhitespace` collapses a newline in a `<p>` to a space). Both facts are still true and both are about *literal newlines only*. **Shift+Enter is a one-keystroke doorway and a `<br>` in a rich paste is a second**, and neither normalizer sees either, because both produce a `hardBreak` node rather than a newline character. `tests/client/txt-intra-paragraph-newline.test.ts` pins the two normalizers; it never covered the break-node route.

- **OS file-association cold start.** When the Tauri desktop app is launched via the OS file-association handler (e.g. double-clicking a `.md` from Finder / Explorer), `src-tauri/src/lib.rs` reads `std::env::args()` via `extract_file_arg` (which, with the rest of the open-candidate cluster, lives in `src-tauri/src/open_candidate.rs` since #1415), validates extension + path, and exports it as `TANDEM_OPEN_FILE` before spawning the sidecar. `src/server/startup-file.ts#maybeOpenStartupFile` consumes the env var and calls `openFromDisk` (`src/server/documents/open.ts`, since ADR-034 Unit 7a) *before* HTTP bind, naturally preempting the `welcome.md` fallback. Warm-start (second instance) uses the `tauri-plugin-single-instance` callback to POST `/api/open` against the running sidecar. macOS file-association launches deliver paths via `RunEvent::Opened` (Apple Event `kAEOpenDocuments`) — not argv — and are queued in `PendingOpens` until `wait_for_health()` returns, then drained before the `SIDECAR_HEALTHY` flag flips. macOS cold-start can briefly show `welcome.md` before switching to the requested file (known limitation). **Since #1344 both entry points share one validator, `validate_open_candidate`** — argv reaches it via `extract_file_arg`, the macOS Apple Event via the `RunEvent::Opened` handler — so an invariant added to it covers both. Since #1415 it returns a `ScreenedOpenPath` rather than a bare `PathBuf`, and that type's constructor is private to `open_candidate.rs`: a future producer that skips the screener stops compiling instead of stopping being noticed. `tests/build/screened-open-path.test.ts` pins the arrangement (private field; exactly one `ScreenedOpenPath(...)` construction in that file and it inside the screener, so a `#[cfg(any(test, …))] mod fixtures` fabricator cannot slip past a `#[cfg(test)]`-shaped grep; check order). It refuses UNC (`\\` / `//`) **before** any filesystem call, because `is_file()` on a network path performs the SMB handshake the check exists to prevent, and it scans the *resolved absolute* path for a stray colon (NTFS alternate data streams); scanning the un-joined candidate let a relative `f:ADS.md` through. **Rejection delivery is two-surfaced and the buffer is the load-bearing half**: a cold-start rejection is classified in `setup()`, before `App.svelte` exists, so an event alone drops silently on exactly the failure it reports. The reason code is buffered unconditionally and drained by the take-once `get_startup_rejection()`; the `startup-file-rejected` event is a **payload-free nudge** to call that drain, never the carrier. That is why Rust never needs to know whether the listener is wired — which it cannot know. **Since #1416 the same buffer also carries post-validation failures** (`open-failed`): a non-2xx from `/api/open` — the server enforces a 50 MB cap and the `.docx` parse, neither of which the Rust validator performs (and UNC via a *symlinked target*, which it deliberately does not resolve; the validator's own pre-syscall UNC refusal above is not redundant with this and must not be removed on the strength of it — see #1417) — a transport failure, or an open that arrived after the app stopped trying to start the server. Three rules there, each of which failed silently before: (1) **the pending-open queue is never destroyed** — `promote_healthy_and_drain` is the only take, because "Retry Server Start" deliberately re-runs `start_sidecar` with the queue intact and taking it on failure means a recovery action that appears to succeed and still loses the file; (2) **giving up is a latch, not a deletion** — `SIDECAR_GAVE_UP`, set under the `PendingOpens` mutex exactly like `SIDECAR_HEALTHY`, cleared by any new start attempt, and read by `try_queue_or_post` so a *later* open fails fast with a toast instead of joining a queue with no consumer (without it, file 1 gets a dialog and files 2..N are silent at `info`, below the release log floor); and (3) **one OS batch produces exactly one surface call for everything it resolves SYNCHRONOUSLY** — validation refusals, gave-up routes and POST failures share one `RejectionBatch` resolved inside a single spawned task, because two writes to the one-slot buffer show the user a count badge whose value depends on where the client's async drain landed. The claim stops there on purpose: a path that comes back `Queued` has no verdict yet and may not have one for minutes (it arrives when the user answers the server-failure dialog), so the client keys its toast dedup on the code — `startup-file-rejected:${code}` — rather than the batch carrying an accumulator across a user-timescale wait. On the **cold-start** path terminality is decided by which dialog button the user presses, so the latch is set on the **Close** branch rather than at `setup()`'s `start_sidecar` call site (which still offers Retry); the restart-failure and retry-failure arms latch directly, the latter right at its own `start_sidecar` call site. Three latch sites, one of them a button.
- **File watcher self-write filtering is two-layer (arrival counter + delivery fingerprint).** Layer 1: `suppressNextChange()` is consumed in the `fs.watch` callback (arrival), not inside the debounce timer callback (delivery) — checking at delivery time would let an external edit arriving within the debounce window get suppressed instead of the self-write. But the arrival counter is armed *once* per write while an atomic rename fires two or three events, so one leaks past it. **Correcting a claim this line carried for a year (#1749): those are `rename` events, not `change` ones.** Measured on Node 24/win32 — a self-write via `fs.promises` delivers `rename, rename, change`, one via a synchronous temp write `rename, rename`, an external tmp+rename `rename, rename` with no `change` at all, an in-place write `change, change`, a delete a lone `rename`, and a recreate `rename, change`. Layer 2: pair `recordSelfWrite(filePath, content)` *after* every `atomicWrite`/`atomicWriteBuffer` self-write (save, save-as in `document-service.ts`; restore in `documents/reload-family.ts`), and then `rearmWatch(filePath)` in an inner `finally` wrapping exactly that suppress/write/record triple — **`recordSelfWrite` MUST precede `rearmWatch`**, because the re-arm clears the arrival counter (see the `rename` bullet below) and the fingerprint is then the only layer left — it stores a content fingerprint (size + SHA-256 of the exact bytes, hashed in-memory so it's synchronous and race-free), and `isSelfWriteEcho` in the debounce timer skips the reload only when the on-disk bytes match it exactly. Must be a **content hash, not size+mtime** (mtime is unreliable on FAT/exFAT/SMB and for mtime-preserving writers; a false match would silently drop a real external edit). The fingerprint is TTL-bounded (`SUPPRESS_TTL_MS`) so it's an echo detector, not a long-lived content oracle. `tandem_applyChanges`'s write is intentionally *not* fingerprinted — its reload re-imports tracked-changes markup (semantic), not an identical-bytes echo. It also takes **no `rearmWatch`**, and `docx-apply.ts` must contain no reference to that symbol at all (pinned at whole-file scope by `tests/server/document-write-rearm.test.ts`): on Linux the write's `rename` is queued against the OLD inotify watch and the `await` continuation runs before libuv dispatches it, so re-arming there `close()`s the handle with the event still pending, `uv_fs_event_stop` discards it, and the reload never lands. On Windows `rearmWatch` is a no-op, so that mistake passes locally and fails only in ubuntu `check`.
- **`rename` is a real event and the re-arm is POSIX-only (#1749).** The watcher used to drop every `eventType !== "change"`, which made an external atomic save — vim, VS Code, `sed -i`, git, anything tmp+rename — invisible on every platform, and on POSIX also left the handle on an unlinked inode forever. Now: **arrival** records `sawRename`, consumes the counter and schedules the debounce, taking no verdict on existence (the first `rename` of a delete-then-write can resolve ENOENT 33–190 ms before the recreate lands); **delivery** `stat`s the path with `fs.promises.stat` (async, explicitly — a synchronous call cannot be parked, and three ordering guarantees depend on that) and only then decides. Both re-arm sites use one shape: attach the new handle inside its own **total** catch (every errno — `fs.watch` on POSIX throws EMFILE and ENOSPC as well as ENOENT, and a rethrow on the delivery path is an `unhandledRejection` → `process.exit(1)`), **store** it, then a **guarded** `close()` of the old — attach-before-close cannot lose an event, and store-before-close keeps the new handle reachable by `unwatchFile` and makes `attachWatcher`'s identity check discard a `close()`-adjacent error on the old one. **Windows needs none of it**: `fs.watch` on a file is `ReadDirectoryChangesW` on the parent directory filtered by name, so the handle survives delete+recreate; `rearmWatch` is a no-op there and a missing file is not a lost watch. **macOS is given the Linux treatment unverified** — FSEvents is path-keyed and probably survives an atomic replace, but the kqueue fallback build would need the re-arm.
- **Word comment offsets need re-anchoring.** `.docx` comment ranges reference HTML-converted content. `docx-comments.ts` re-resolves via `anchoredRange()` after Y.Doc population.
- **Exception handler is narrowed, not blanket.** `uncaughtException`/`unhandledRejection` only swallow known Hocuspocus/ws errors (via `isKnownHocuspocusError`). Unknown errors call `process.exit(1)`.
- **Boot-time orphaned-temp reaper.** `reapOrphanedTemps` (`src/server/file-io/reaper.ts`) sweeps `.tandem-tmp-*` atomic-write siblings older than 1 hour from the annotations + sessions dirs **only** (never user document dirs). These orphan when the process is SIGKILLed between `writeFile` and `rename` (dev restarts, force-quits). Fire-and-forget at boot (un-awaited, with `.catch()`), skipped when the store is read-only. The 1-hour age gate — not the store lock — is what makes it safe against a concurrently-starting instance, since session-dir writes aren't lock-gated. The match regex (`^\.tandem-tmp-(\d+)-([0-9a-f]{12})$`) is the safety boundary: `store.lock`, `<hash>.json`, `.corrupt.*`, `.future`, and session files can never match.
- **Pre-overwrite document backups are path-keyed and once-per-run.** `snapshotBeforeFirstWrite` (`src/server/file-io/doc-backup.ts`) copies a `.md`/`.txt`/`.docx` file's on-disk bytes verbatim to `{APP_DATA}/doc-backups/<path-hash>/` before Tandem's FIRST write to that path per server run — the text branch (`atomicWrite`) AND the binary branch (`.docx` via `atomicWriteBuffer`); also called from Save-As when the target exists, and from `restoreDocumentFromBackup` (so a restore is itself reversible). The module is format-agnostic (raw `Buffer` copy), so `.docx` snapshots restore byte-identical; `restoreDocumentFromBackup` reads/writes them as a `Buffer` and routes through `reloadFromDisk` (re-parses + re-injects Word comments). The `tandem_restoreBackup` MCP tool exposes these snapshots for `.docx` too, falling back to the `{name}.backup.docx` sidecar (written by `tandem_applyChanges`) only when no snapshot exists. Keyed by `docHash(filePath)` not docId (docId survives rename; the snapshot question is per-path). Failure contract is the OPPOSITE of `integrations/backup.ts`: a failed snapshot warns and lets the save proceed (gate stays unset → retried next save). Deliberate skips (no source file / byte-identical / 500 MB cap) DO set the gate. **A directory the sweep cannot read for permission reasons is repairable, not terminal (#1433):** `sweepDocBackups` re-applies the root's inheritable Windows grant (once per run, memoised as a promise that resolves to whether the grant succeeded and **never rejects** — a memo that rejects would surface in `snapshotBeforeFirstWrite`'s outer catch, returning `failed` and toasting the user for what is meant to be invisible hygiene, with the gate left unset so every 60s autosave retries) and retries the read once, on both the root and the per-path branches. Correcting v0.21.0's #1299 changelog entry, which said a poisoned install "repairs itself the next time it runs": as shipped the repair hung off `snapshotBeforeFirstWrite` alone, so it ran on the next document **save**, not the next run — and an upgrade auto-opens `CHANGELOG.md` **read-only**, so precisely the boots most likely to hit this never saved anything and never repaired. Note the repair only helps if `setRestrictiveAcl` itself succeeds; when icacls is what is failing, `ensureBackupRootAcl` swallows it (by design) and the folder stays broken. Shutdown now flushes dirty docs (`autoSaveAllToDisk`, 5s-bounded) before `saveCurrentSession`; the order is `unwatchAll` → `stopAutoSave` → `autoSaveAllToDisk` → `saveCurrentSession`.

- **The sidecar download's existence check is version-aware now, and was not for fourteen months (#1747).** `scripts/download-node-sidecar.mjs` used to `process.exit(0)` as soon as it found a binary at the output path clearing a 20 MB size floor — the version was never consulted, so bumping the pin was a **silent no-op in any tree that already had a sidecar**, and the stale binary got bundled while every constant in the repo said otherwise. It survived because CI cannot see it: runners check out fresh, and `rust-cache` scopes to `./src-tauri -> target` rather than `binaries/`, so only local `cargo tauri build` was affected. A sibling `<sidecar>.version` marker now gates the skip, and a **missing** marker counts as stale — that is the state every pre-#1747 checkout is in, and reading absence as "fine" would have left the bug everywhere it already lived. The version and the expected archive SHA-256s live in `scripts/node-sidecar-version.mjs`, deliberately apart from the downloader, which does its work at the top level (importing it spawns `rustc -vV` and reaches a top-level `await download(...)`).

### Testing & E2E
- **E2E and perf run on reserved port pairs from `scripts/test-ports.ts`, never the product's 3478/3479** (#1492, retiring #1483's residual gaps). The backend entries are `reuseExistingServer: false`, so a stale server can no longer be adopted past `scripts/e2e-server.mjs`'s per-run wipe, and the desktop sidecar is simply not on the harness ports. What remains, stated honestly: **the reserved pair is reserved, not guarded.** Playwright's "already used" refusal fires only for something answering 200–403 on the MCP port; a wedged holder, a non-HTTP process, or anything on the ws port (which no Playwright check ever probes) is SIGKILLed by the harness server's own boot `freePort()` -- desirable self-healing for stale E2E servers, and the reason harness ports must never collide with ports any doc tells users to occupy (`tests/scripts/e2e-guard-wiring.test.ts` pins `docs/troubleshooting.md` against every constant, and pins product-port literals out of `tests/e2e/` entirely). The load-bearing run-time check is now the *served-client* half of `scripts/e2e-guard.ts` (`globalSetup`): it fetches the dev-served `backend-ports.ts` module and fails closed unless the Vite actually serving the suite carries the harness `VITE_TANDEM_*` env -- a served client still baked to :3479 would drive the destructive suite into the user's real backend through the UI, with the backend isolation working perfectly (the loopback origin gate admits any 127.0.0.1 port by design). The perf harness's equivalent is an in-page `window.__TANDEM_PORTS__` assertion before any seeding, because `vite preview` serves a static build with no dev server to interrogate; its client builds to `dist/perf-client`, never `dist/client`, so `npm run perf:gate` cannot leave a port-baked client where `node dist/server/index.js` would serve it -- and package.json's `files` carries an explicit `"!dist/perf-client"`, because `files: ["dist/"]` publishes the whole directory and `prepublishOnly`'s `npm run build` does not clean it.
- **The release client build strips `VITE_TANDEM_*`, and that is why `npm run build` shells out to `scripts/build-client.mjs` instead of running `vite build`** (#1492). `src/client/utils/backend-ports.ts` reads those vars through `import.meta.env`, which Vite substitutes **from the ambient environment at build time** -- so `export VITE_TANDEM_MCP_PORT=4729` (a plausible shell state: `.claude/skills/e2e-debug/SKILL.md` walks you into running Vite standalone against a relocated backend) followed by `npm run build`, `npm publish` or `cargo tauri build` would bake `http://127.0.0.1:4729` into the shipped client. The app is then permanently "Disconnected" and nothing at runtime reveals which port was compiled in. Second line of defence: `scripts/ci/verify-harness-stripped.mjs` greps the emitted bundle for the harness ports as **bare digits** -- the URL never survives minification as one literal (`MCP_BASE_URL` stays the template `http://127.0.0.1:${port}` with the port as a variable), so `127.0.0.1:4729` would find nothing; the inlined env value is the only form actually present. Both halves are pinned by `tests/scripts/e2e-guard-wiring.test.ts`.
- **An element screenshot of anything inside the settings modal clips to the visible scroll area, and reads as an overflow bug.** The modal is fixed at 900x680 with a scrolling body *regardless of viewport*, so `locator.screenshot()` on a section below the fold returns it cut mid-glyph -- which looks exactly like content overflowing its container. Observed while closing #1432's visual gate: the first capture appeared to show a clipped section, and scrolling the body to the bottom showed it terminating cleanly. Scroll the modal body before capturing, or capture the page and crop; do not widen the viewport expecting the modal to grow, because it will not.
- **Uploaded files (`upload://` paths) are read-only.** `tandem_save` returns a session-only save.
- **`cargo test` requires sidecar stubs + GTK libs — and the pre-push hook runs it**, so a fresh clone cannot push until both are in place. `tauri_build::build()` checks all declared `resources` (`dist/client`, `dist/server`, `dist/channel`, `dist/stdio-bridge`) and both `externalBin`s. **`dist/monitor` is NOT a declared resource** — it was listed here for months and is not in `tauri.conf.json`, so `mkdir`ing it is harmless but proves nothing; `.github/workflows/ci.yml` omits it and passes. Keep this list synced with `bundle.resources`, not with `dist/`:
  ```sh
  TRIPLE=$(rustc -vV | sed -n 's/host: //p')
  mkdir -p src-tauri/binaries dist/{channel,server,client,stdio-bridge}
  touch src-tauri/binaries/{node-sidecar,tandem-reaper}-$TRIPLE{,.exe}
  apt-get install -y libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf libxdo-dev
  ```
  **`libxdo-dev` is required to link and is easy to miss** — it is pulled in by a Cargo feature, so the failure is a bare `rust-lld: error: unable to find library -lxdo` thousands of lines into linker output, long after the GTK packages everyone remembers are installed. Same dependency as the #1227 runtime bug.

### Windows / Cross-platform
- **Never spawn a Windows system binary by bare name — anchor it.** `Command::new("netsh")` does not hand a bare name to `CreateProcess`; Rust resolves it first (`std::sys::process::windows::search_paths`), and that search reaches **the application directory before System32**. Tandem installs per-user into `%LOCALAPPDATA%\Tandem` with `RequestExecutionLevel user`, so that directory is writable by the unelevated user. The cwd is *not* in the order, so `NoDefaultCurrentDirectoryInExePath` is a red herring. Rust: `src-tauri/src/system_paths.rs` (`system32_exe`, `windows_exe`, `windows_powershell_exe`). Node: `systemBin` in `src/server/platform.ts` — route *through* it rather than hand-rolling the same join, which `install-claude-cli.ts` did and which is how one copy of a rule drifts from the other. **Anchor via `GetSystemDirectoryW`, never by concatenating `%SystemRoot%`** — the environment block belongs to whoever launched the process, so an env-derived anchor is attacker-controlled input and needs no filesystem write at all to poison. Resolution failure **fails closed**; a bare-name fallback would perform exactly the search being avoided. Three sub-traps: `powershell.exe` is *not* in System32 (it is under `WindowsPowerShell\v1.0\`), so a bare name misses every system directory and falls through to the inherited `PATH`; `explorer.exe` is in `%SystemRoot%`, i.e. step 4, so it is outranked by the application directory *and* System32 and needs `windows_exe`, not `system32_exe`; and `pwsh.exe` legitimately has no fixed path, so PATH is its real discovery mechanism and it stays unanchored on purpose. **Counting the sites is not a grep**: `uninstall_scrub.rs` contains no `netsh` and spawns one anyway, via `firewall::remove_cowork_rules()`.
- **`core.autocrlf=true` + late `.gitattributes eol=lf` leaves the working tree CRLF-stale.** The `eol` attribute only affects future checkouts — when `biome check .` fails locally on Windows with only CRLF format errors while CI passes, check `git ls-files --eol | grep "w/crlf"` before blaming the change under review; the fix is `git add --renormalize .` committed as its own dedicated PR, never `core.autocrlf=false`.
- **`.husky/pre-commit` needs its `#!/usr/bin/env sh` shebang.** Without it, git-bash on Windows fails the commit with "cannot spawn: Exec format error" — restore the shebang rather than reaching for `--no-verify` (which `block-no-verify.sh` blocks anyway).
- **`path.basename` on Linux doesn't split Windows backslash paths** (`path.basename('C:\\x\\f.md')` returns the whole string in Ubuntu CI). Normalize first — `filePath.replace(/\\/g, "/")` — before any separator-aware `path.*` call (`basename`/`dirname`/`extname`); pattern lives in `docIdFromPath` in `src/server/mcp/document-model.ts`.
