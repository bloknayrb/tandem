## 0. What changed from v3

**v4.1 (2026-09-17) — Bryan's decisions, and session rename.** Every §5 decision is made; the recommended option was taken in all twelve. Three replace an earlier choice of his: §5.1 defers the per-directory headless session to Phase 4, §5.2 refuses a non-owner edit rather than downgrading it to a suggestion, and §5.7 keeps `cwd` a record property rather than deriving it from the first-opened document. §5.12 gains **session rename**: a record carries an optional `nickname`, set by Bryan from the badge popover or by a session for itself with `tandem_status({nickname})`; the badge and the Assign list show it, with the label always beside it, and the label stays the address every control uses (§3.11). This is what removes the §5.12-C case — telling two terminals in different repos apart — without publishing a project directory.

- **Resurfacing is keyed on a per-item delivered-to ledger, not on `timestamp ≥ since`** (§3.5, OWN-INB-08). Every delivery writes `deliveredTo[item] = {ownerId, at, documentId | null}` in memory; release and reassignment resurface exactly the entries delivered to the outgoing owner and not handled. The first batch of every tenure — the one that triggered the claim — is included by construction. The protection against dragging back a message answered in an earlier server run is kept, also by construction: the ledger is empty at boot. The same ledger makes doc-less and closed-document chat resurface on record death (OWN-CHAT-08), and states the restart residual plainly (OWN-INB-10).
- **Chat on a document that is not open is never stranded** (§3.5 "detached chat", §3.6, OWN-CHAT-07). A message whose `documentId` is closed, a closed scratchpad or a doc that failed to restore is in every pass like doc-less chat — first poller, claims nothing — and a `replyTo` answer to it is a reply with no ownership check, because there is no document to own.
- **The wake socket is keyed by an unguessable per-record watch id, not by the public label** (§3.10, OWN-SEC-05, OWN-WAKE-09). `wakeUrl` is `…/api/wake?watch=<id>`; the label stays published for the badge and the Assign list and appears in no URL. The id is derived per server run from the owner id, so a record re-created for the same identity keeps its watch; `bindHandle` re-points the presenting transport's watch to the handle's record; and a live socket **pins its transport against the idle reaper** the way an open `GET /mcp` stream does (§5.11, decided 2026-09-17). The one residual — an LRU-evicted direct-HTTP transport — is a known limitation with the pull path as its backstop. The transcript exposure of the id is argued against the threat model in §6.
- **Every refusal class is placed relative to the queue** (§3.4a, OWN-Q-08): a refusal decided by static document properties or argument shape (`READ_ONLY`, format-by-extension, `NO_DOCUMENT`, `DOCUMENT_REQUIRED`, license, handle errors) runs before the queue and never claims; a refusal decided by live content, the disk or the lock set at write time (`INVALID_RANGE`, `RANGE_MOVED`, `SAVE_IN_PROGRESS`, `EXTERNAL_CONFLICT`, serializer `FORMAT_ERROR`, I/O) runs inside and keeps the claim. A refused edit on `CHANGELOG.md` claims nothing.
- **The launcher child binds on its first call, whatever it is, and a fresh pre-bind record is absorbed rather than refused** (§3.8, §3.2, OWN-LCH-09). The bootstrap and wake prompts name the handle up front and say "pass it on your first Tandem call"; SKILL v25 Workflow step 1 says the same. A never-bound, single-transport `mcp:` record that already claimed documents is absorbed into the handle's record on bind — its docs move, its delivered entries are re-keyed, nothing resurfaces — so child exit releases them. This narrows one Codex-7 rule ("no merging") and is §5.10, decided 2026-09-17.
- **`tandem_switchDocument` is owner-only and never claims** (§3.3, OWN-OPEN-10). It runs outside the queue; on an unowned document it answers `NOT_OWNER {ownerLabel: null}`. The D1 row no longer lists it among the queued tools.
- **Stdio transport mode has an identity** (§3.2, OWN-DEF-07): one process-wide `stdio` record, attached for the process's life. §2's "every client has a transport" is corrected.
- **Handles are issued only on request, with a stated lifetime** (§3.2, OWN-GRP-05): `tandem_status({issueHandle: true})` mints one (idempotent per record); a plain status never carries one. A handle is live while its record exists — attached or inside the detach grace — and dies when the record is dropped or, for the launcher, on teardown. Presenting it inside the grace re-attaches; after the drop it is `INVALID_OWNER_HANDLE`.
- **Labels are human-readable in the popover** (§3.11, OWN-CTL-06): each record carries a descriptor — kind (`terminal`, `bridge`, `auto-launched`, `stdio`) and the client's `initialize` `clientInfo.name` — published beside the label on doc entries; the Assign list comes from a loopback-only `GET /api/ownership/owners`; `tandem_status` returns the caller's own label, nickname and kind. Since v4.1 a record also carries an optional **nickname** shown in place of the label (§3.11). Argued against security F6 in §6; `cwd` is never published (§5.12).
- **`#1952` is closed per request, not per bind** (§4, §6, OWN-SEC-07): the MCP request context gains `peerIsLoopback` from `req.socket.remoteAddress`, and `wakeUrlField()` suppresses only for a non-loopback peer. A local hand-started session under a Cowork bind keeps its `wakeUrl`. The register sentence "per-request loopback detection is not available inside a tool handler" becomes false when this lands and is on the sequenced-edit list.
- **The remaining story gaps are closed in place**: user tab close releases and notifies the owner (§3.4); `tandem_scratchpad` claims and activates, a re-open of one's own document neither claims nor activates (§3.4); Release/Assign no-ops are defined (§3.4); unlabeled sockets keep Phase 1 semantics for ownership frames (§3.4b); `tandem_restoreBackup` list mode and `tandem_exportAnnotations` are reads (§3.7); the handle-scrub tool set is enumerated (§6); the Phase 2 chat label is a `ChatMessage.ownerLabel` field stamped in Phase 1 (§3.6, §7); the optional `cwd` argument is a Phase 4 schema change (§3.1 D6, §7); remote and worktree-isolated subagents are covered with a stated assumption and fallback (§3.2); the bootstrap prompt tells a child how to find the document (§3.8); `channel-reply` marks handled via `replyTo` only (§3.6).

## 1. Summary

- A document open in Tandem is **owned** by at most one owner record, and only the owner responds to it (D1). Ownership is **server-enforced in the MCP tool layer** (D4): a write from a non-owner is refused; `/api` is the user's own surface and is not gated (§6).
- An owner record is **attached to the caller's transport**, so a model never carries or recovers a credential. Loss of transport releases the docs after a short grace; the launcher child's record is pinned by the supervisor to the child process, per spawn; stdio mode has one record for the process. "Owner connected" means exactly that a transport is attached, and the release bounds are ≈32 minutes in the crash case (§3.2).
- A record's live owned set is its **group** (D2, D6). Groups are in-memory and die with the server run.
- The process-global `activeDocId` **is no longer an MCP default**. A tool without `documentId` targets the caller's single owned doc, else the single open doc, else `DOCUMENT_REQUIRED`. Reads stay open to everyone; reads never claim.
- **All ownership changes and all MCP mutations for a document go through one per-document operation queue.** Static refusals run before the queue and never claim; live-state refusals run inside and keep the claim (§3.4a).
- `tandem_checkInbox` covers the caller's owned docs plus every unowned doc plus doc-less and closed-document chat. **A poll that returns actionable work on an unowned doc claims it, before any ledger write.** Every delivery is recorded per item with the owner it went to; **"handled" means answered**, and on release, reassignment or record death the unhandled items delivered to that owner resurface.
- **Assigning a document wakes its new owner** with a payload-free notice; pull remains authoritative and ownership changes are always in the inbox.
- Chat send is disabled on an empty tab with a visible reason (D5); scratchpads stay open in §5.3.
- **One watch per session (D3):** `wakeUrl` carries a private per-record watch id; the server resolves scope per event from the live map. A live socket pins its transport against the idle reaper (§5.11).
- The user's **Release / Assign** controls ship in Phase 1 with enforcement, with a popover that names each session by nickname, kind and client, and lets Bryan rename a session.

## 2. Terminology

| Term | Meaning |
|---|---|
| **Owner record** | Server-side record `{ownerId, kind, label, watchId, descriptor, nickname?, cwd?, transports, handle?, since, boundFromHandle}`. `kind` ∈ `claude-session` \| `bridge` \| `mcp-session` \| `handle` \| `stdio`. In memory only. |
| **Owner** | The owner record `ownerByDoc` maps a document to, with the time it was claimed (`since` — display only since v4; resurfacing no longer reads it). |
| **Transport** | A registered `Mcp-Session-Id` entry (`transport-registry.ts:52-76`) in HTTP mode. **In stdio mode there is no registry and no session id** (`server.ts:522-533` connects one `StdioServerTransport`; `index.ts:111`, `:920`); the process-wide `stdio` record stands in for the transport (§3.2). No stateless (`2026-07-28`) branch exists (`context.ts:50-58` describes a future era). |
| **Attached / connected** | A record is *attached* (response field `ownerConnected`) while ≥1 of its transports is registered, or while the supervisor pins it, or — stdio — while the process runs. Detached records release their docs after `DETACH_GRACE_MS`. Connected is a statement about a transport, not about responsiveness. |
| **Owner handle** | Opaque server-minted string (`th_` + 32 base64url chars) presented on an entry tool to bind the presenting transport to an existing record. Issued only on request (§3.2). A hand-off, not an identity. Low-grade capability (§6). |
| **Watch id** | Opaque per-record id (22 base64url chars) carried only in `wakeUrl` as `?watch=`; the socket resolves it to a record at dispatch. Not the label, never published on doc entries. Low-grade capability of the same class as the handle (§6). |
| **Owner label** | Non-secret, non-ordinal per-run id (`owner-k7qx`) published to clients on doc entries. Never derived from a handle, a watch id or a session id. Appears in no URL. |
| **Descriptor** | `{kind, client?}` on a record: the display kind and the sanitized `clientInfo.name` the client sent at `initialize`. Published beside the label; `cwd` is not part of it (§5.12). |
| **Nickname** | `{text, setBy: "user" \| "session"}` on a record, optional (v4.1). A display name for the badge and the Assign popover, never an address: assignment, refusals and frames use the label. In memory with the record, so it is lost on restart and on record death. A name Bryan set cannot be overwritten by the session (§3.11). |
| **Owned set / group** | Docs mapped to one record. Group is D2's word for the same set. |
| **Unowned doc** | Open, no owner: restored after restart, user-opened with no responder yet, or released. |
| **Doc op queue** | The per-document serial queue every MCP mutation and every ownership change runs through (§3.4a). |
| **Implicit claim** | An op on an unowned doc records the caller as owner at the op's turn in the queue, or a poll that returns actionable work on it (§3.5). Reads, `tandem_switchDocument`, list-mode `tandem_restoreBackup` and `tandem_exportAnnotations` never claim. |
| **Delivered** | An item returned by a poll and recorded in the **delivered-to ledger** `deliveredTo[itemKey] = {ownerId, at, documentId \| null}`: chat additionally gets `read: true` (`types.ts:663`); the annotation and reply ledgers (`awareness.ts:57`, `:71`) become this map. |
| **Handled** | An item answered: for chat on an open doc, a Claude reply linked by `replyTo` or any reply on that doc by the owner it was delivered to; for doc-less or detached chat, a `replyTo` reply only; for a user comment or reply, a later Claude reply on the thread or the annotation leaving `pending`; for an accept/dismiss, delivery itself (§3.5). |
| **Detached chat** | A user message whose `documentId` names a document that is not open (closed, a closed scratchpad, failed restore). Treated like doc-less chat for scope, claim and reply (§3.5, §3.6). |

## 3. Decided design

### 3.1 D1–D7 made concrete

| Decision | Concrete rule |
|---|---|
| D1 | Every mutating tool and `tandem_reply` with a resolved **open** document run inside the doc op queue and check `ownerByDoc.get(doc)?.ownerId === caller.ownerId` there, before any record lookup. A non-owner of a **live**-owned doc gets `NOT_OWNER`. An unowned doc is claimed by the op. No non-owner write of any kind is allowed (§3.7). `tandem_switchDocument` is owner-only, checked at handler entry, outside the queue, and **never claims** (§3.3). |
| D2 | A record's owned set is its group. User-initiated opens (`POST /api/open`, Tauri file association) are unowned until a session responds or a poll delivers their work. **Bryan believed "a headless session in the file's directory" is current behaviour; it is not** — the supervisor holds one child (`supervisor.ts:705 let child`) in one cwd (`:1049 resolveCwd`). Interim (Phases 1–3): unowned docs go to whoever is delivered their work first. Directory routing is Phase 4 (§5.1). |
| D3 | **One watch per session (Bryan, 2026-09-16).** One socket per owner record, `?watch=<watchId>`; the server resolves each event's scope from the live map. §3.10. |
| D4 | Enforcement lives in the MCP tool handlers, is server-side, and is not delegated to `SKILL.md`. `/api` routes are the browser user's surface and are deliberately not ownership-gated. Ownership is coordination between Claude sessions, not a security boundary (§6). |
| D5 | `chat-send-btn` (`testid-set.snap.txt:48`; `ChatPanel.svelte:447-453`) is disabled when `yjsSync.activeTabId` is null (`App.svelte:1975` passes it as the message's `documentId`), with a visible reason. `chatState.send` (`useChatState.svelte.ts:30`) already carries `documentId`. A scratchpad tab has a `documentId`, so send is enabled there; who owns a *user-created* scratchpad is §5.3. |
| D6 | **Decided by Bryan, 2026-09-17:** `cwd` is a property of the owner record — set by the supervisor for the launcher child (`plan.cwd`, Phase 1, internal), optionally passed on `tandem_status`/`tandem_open` by a hand-started session (**Phase 4 schema change** — the argument has no consumer before directory routing, OWN-GRP-04), otherwise unknown. Not derived from the first-opened doc. Never published (§5.12). §5.7. |
| D7 | **Decided by Bryan, 2026-09-17:** a non-owner write is refused with the owner's label, not downgraded to a suggestion — the downgrade cannot be built as v1 described (§3.7 evidence). §5.2. |

### 3.2 Identity: the transport-attached owner record

Module: `src/server/sessions/ownership.ts`. Stores `records: Map<ownerId, OwnerRecord>`, `ownerByDoc: Map<docId, {ownerId, since}>`, the per-doc op queues (§3.4a), `inFlightByTransport: Map<mcpSessionId, number>`, the delivered-to ledger (§3.5), `ownerIdByWatch` and `watchAlias` (§3.10).

**Binding at `initialize`** (`server.ts:712-719`, where `readClaudeSessionHeader` (`:296`) already runs). The registry entry gains `ownerId`, derived once:

1. `X-Claude-Session-Id` present → `claude:<id>`. Sent by the stdio bridge when Claude Code spawned it (`mcp-stdio.ts:377-379`; `cli-runtime.ts:93` names the header, `:159-160` forwards it — on `--resume` too). Stable across a bridge respawn, a 404 re-initialize and `claude --resume` next morning.
2. Else `X-Tandem-Client-Id` present → `bridge:<id>`. **New header**, minted once per bridge process (`randomUUID()` beside `upstreamHeaders` at `mcp-stdio.ts:377`) and reused by every reconnect (`createUpstream`, `:393-398`). Covers Claude Desktop and Cowork. The `_meta` echo proposed by model-ux 3 is not used: the SDK's `_oninitialize` returns only `protocolVersion`, `capabilities`, `serverInfo`, `instructions` (`node_modules/@modelcontextprotocol/sdk/dist/esm/server/index.js:259-268`).
3. Else → `mcp:<Mcp-Session-Id>`. The **direct-HTTP Claude Code** case — the default `tandem setup --apply` entry (`src/server/integrations/apply.ts:512`). Identity lives exactly as long as the transport, **except that a live wake socket pins the transport against the idle reaper** (§3.10, §5.11).
4. **Stdio mode (OWN-DEF-07).** `startMcpServerStdio` (`server.ts:522-533`) connects one `McpServer` to one `StdioServerTransport`; nothing runs `runWithMcpContext`, so `getMcpContext()` is undefined for every handler. The ownership module registers one record `stdio:<pid>` (`kind: "stdio"`, descriptor `{kind: "stdio", client}` from `clientInfo`) at start, attached until the process exits — stdin EOF already shuts the process down (`index.ts:212-221`). `getCurrentOwner()` returns it whenever `transportMode === "stdio"` and the context is undefined; in HTTP mode an undefined context means server-internal work, which never reaches an ownership check. No handle is ever issued to it (there is no second transport to hand anything to), `wakeUrl` is already absent there (`wake-url.ts:55-58`; `wake-socket.ts:85-86`), and the singleton fallback (§3.3) makes the single stdio client's id-less calls work as today.

**Descriptor.** At `onsessioninitialized` (`server.ts:439`) the record stores `descriptor.kind` from the rule that matched (`claude-session` → shown as **terminal**, `bridge` → **bridge**, `mcp-session` → **terminal**, `handle` → **auto-launched**, `stdio` → **stdio**) and `descriptor.client` = `server.server.getClientVersion()?.name` (the SDK stores `clientInfo` at `initialize`, `server/index.js:262`, and exposes it at `:280-281`; nothing in `server.ts` reads it today), sanitized to `^[A-Za-z0-9 ._-]{1,32}$` or dropped. A launcher-minted `handle` record's `client` is filled in by the first transport that binds to it. §3.11 shows it; §6 argues it.

`McpRequestContext` (`context.ts:37-59`) gains `ownerId` and **`peerIsLoopback: boolean`** (`isLoopback(req.socket.remoteAddress)`, the same predicate `auth/middleware.ts:164-165` uses), both populated in `dispatchToSession` (`server.ts:700-703`) and on the initialize path (`:717-718`). Handlers call `getCurrentOwner()`; nothing is threaded through tool args. `peerIsLoopback` is what `wakeUrlField()` reads (§3.10, `#1952`).

**Handles: issuance and lifetime (OWN-GRP-05).** A handle is minted **only on request**: `tandem_status({issueHandle: true})` returns `ownerHandle` for the caller's record, idempotently — one handle per record for the record's life; a plain `tandem_status` never carries one, so the transcript surface F2 names is opened only by a session that is about to hand a document off. The supervisor mints the launcher child's handle itself (§3.8). **A handle is live exactly while its record exists**: attached, or detached inside the grace. It dies when the record is dropped at grace expiry, or — for a launcher record — in `teardownTurnDelivery`. Presenting a handle whose record is detached-inside-grace is the "otherwise" row below: the presenting transport attaches, the docs are intact, and while that transport stays attached the record does not detach. Presenting one after the drop is `INVALID_OWNER_HANDLE`; nothing revives a dropped record. When a launcher record is torn down while a helper transport is bound to it, the helper's transport is re-homed to a fresh `mcp:` record owning nothing (its next call works; the child's docs were released with the child).

**Hand-off and rebinding (Codex 7, narrowed by §5.10).** `ownerHandle` is an optional argument on four entry tools only — `tandem_status`, `tandem_open`, `tandem_scratchpad`, `tandem_checkInbox`. Presenting a handle runs `bindHandle(transport, handle)` **first in the handler, before the tool's body**, with these outcomes and no others:

| Condition | Outcome |
|---|---|
| Handle unknown, expired (record dropped or child run over), or malformed | `INVALID_OWNER_HANDLE` — recoverable. **No side effects:** the transport is not rebound, nothing is claimed, the body does not run. "This handle is not live. Use the handle from your most recent Tandem turn, or call without one." |
| Transport already bound to that record | Success, idempotent; the body runs. |
| `inFlightByTransport[transport] > 0` | `OWNER_HANDLE_CONFLICT` — no side effects. An in-flight op is never re-attributed mid-run; the caller retries after it settles. |
| Transport's current record owns ≥1 doc **and** (has ≥2 transports, or is not of kind `mcp-session`, or was itself bound from a handle) | `OWNER_HANDLE_CONFLICT` — no side effects, **no merging of groups**. The message says only "this connection already owns documents under another identity". |
| Transport's current record owns ≥1 doc and is a **never-bound, single-transport `mcp-session` record** (the launcher child that opened or wrote before its first bind — OWN-LCH-09) | **Absorbed (§5.10, decided 2026-09-17):** for each owned doc, `setDocOwner(D, R, "bind")` at D's queue turn — no resurfacing, the delivered-to entries are re-keyed from the old record to R, no `ownership:released` frame (the old record ceases to exist), the badge updates via `broadcastOpenDocs`. The transport then moves to R and the body runs under R. The docs now release on child exit, which is the point. |
| Otherwise (transport's record owns nothing) | The transport moves to the handle's record; its previous record is dropped if no other transport is on it, and its watch id becomes an alias of R's (§3.10). The body runs under the new record. |

The bind is synchronous — no `await` between the check and the mutation — so concurrent requests on the same transport are ordered by arrival, and a request still in flight (counted in `inFlightByTransport`, incremented when a doc op is enqueued and decremented when it settles) makes the bind refuse rather than race it. The absorb row's `setDocOwner` calls are enqueued synchronously and the transport switch is applied when the last settles; a request arriving in between sees the old record and is refused by the in-flight rule, so the absorb cannot interleave with a claim under the old identity.

**Subagents.** In-process subagents (Claude Code's `Agent` tool, `fork`) run inside the orchestrator's process and call tools over its MCP client, so they present the orchestrator's transport and inherit its record; `docs/workflows.md:247` already has them calling `tandem_comment` directly. Hard Rule 7 (`SKILL.md:28`, sub-agents never poll) stays, for the ledger reason it already gives. **Remote and worktree-isolated subagents (OWN-GRP-06).** *Assumption:* an agent dispatched with `isolation: "remote"`, or any separately spawned `claude` process, has its own MCP transport and therefore its own record; it would get `NOT_OWNER` against its orchestrator. SKILL v25's "Document ownership" section therefore says: *before dispatching an agent that may run in its own process, call `tandem_status({issueHandle: true})` and pass the handle in the agent's prompt; the agent presents it on its first Tandem call.* *Fallback if the assumption is false* (the agent shares the orchestrator's client): the handle is presented on a transport already bound to that record, which is the idempotent-success row — the guidance is harmless in both worlds. Whether worktree-isolated agents share the MCP client is `needs-human-evidence`.

**Liveness, presence and release — with the bounds stated (Codex 5).**

- A record is *attached* while any of its transports is in the registry. `onEvicted` (`transport-registry.ts:92`, fired from `closeEntry :153-167` on `lru | idle | explicit`) and `DELETE /mcp` both notify ownership.
- When the last transport goes, the record is *detached* and `DETACH_GRACE_MS` (2 min, §5.8) starts. A new transport binding to the same `ownerId` inside the grace re-attaches with its docs intact — the bridge's 404 reconnect ladder (`mcp-stdio.ts:113-115`, 1 s → 30 s) and a Claude Code bridge respawn. On expiry the record's docs are released through `setDocOwner` (§3.4), **its delivered-to entries — including doc-less and detached chat — are swept** (§3.5), and the record is dropped (its handle dies).
- **`handle` records minted by the supervisor are pinned** to one child run (`spawned`, `supervisor.ts:1157-1165`) and released in `teardownTurnDelivery` (`:1410-1429`), which runs on `exit` and `error`, on `stop()` and on relaunch. A child whose direct-HTTP transport is idle-reaped keeps its docs.
- **The response field is `ownerConnected`, never "responsive".** It is exactly "attached". No `lastSeenAt` is exposed.

> **Bounds, prominently.** Ownership release follows *transport* death, and transport death is detected late:
> - Clean client shutdown (`DELETE /mcp`) → detached at once → released after the 2-minute grace.
> - **A crashed client with no open `GET /mcp` stream is noticed only by the idle reaper — 30 minutes (`transport-registry.ts:138`) — so its documents stay owned for up to ≈32 minutes.** A client that held a stream is no better: the stream's close only starts the same TTL (`:231-265`). A client that held a **wake socket** is no better either: the socket closes with the process and the same TTL follows — the pin (§5.11) extends nothing for a dead peer.
> - The launcher child is the exception: the supervisor's exit handler releases its record immediately.
> - **An idle *live* client with no `GET /mcp` stream, no wake socket and no call for 30 minutes is reaped (`:261`) and loses ownership while alive.** Its next call re-initializes under a new id owning nothing; the singleton fallback and implicit claim return the docs nobody else has taken, and the badge shows what happened. From Phase 3, a session that armed its watch is not in this case: its live socket pins the transport (§3.10). Whether current Claude Code holds a GET stream is a world fact; `Reaping idle MCP session` in Bryan's `tandem.log` answers it.
>
> During any of these windows the user's **Release / Assign** control (Phase 1, §3.4, §3.11) is the remedy, and it is why the control ships with enforcement rather than after it.

**Stateless clients.** A `2026-07-28` client has no transport to bind. Tandem does not serve that era (ADR-045 amendment, `decisions.md:1611-1631`), so there is no such caller today. When dual-era lands, the fallback is the per-call `ownerHandle` on every mutating tool — recorded here so it is a known future row.

### 3.3 Default `documentId`

Replaces `getCurrentDoc(documentId)`'s `activeDocId` fallback (`registry.ts:345-346`) and the three direct `?? getActiveDocId()` sites (`document.ts:1585`, `:1613`; `awareness.ts:604-605`) for every MCP tool:

1. `documentId` given → any open doc for a read; for a write, §3.4's ownership rule at the op's turn.
2. `documentId` omitted → the caller's owned set if it has exactly one doc; else the single open document if exactly one is open (**the cold-start and hand-started single-doc path**); else `DOCUMENT_REQUIRED` carrying `ownedDocumentIds` and `openDocumentIds`. **Reads never claim** — the SKILL v25 sentence is "reading does not reserve".
3. `tandem_status`, `tandem_listDocuments`, `tandem_diagnostics`, `tandem_checkInbox` stay global in scope (checkInbox's scope is §3.5). `tandem_listDocuments` entries gain `ownerLabel | null`, `ownerNickname | null`, `ownerConnected`, `ownerKind`, `ownerClient`, `ownedByYou`. **`tandem_status` returns the caller's own `ownerLabel`, `ownerNickname`, `ownerKind` and `ownedDocumentIds`** (so a session can tell Bryan "I am owner-k7xq, the terminal one"), and `ownerHandle` only with `issueHandle: true` (§3.2). An optional `nickname` argument sets the caller's own nickname, subject to §3.11's rules.
4. `activeDocId` survives as client UI state (which tab is shown). `tandem_switchDocument` (`document.ts:1665-1681`, body calls `activateDocument`) is **kept**, re-described as "bring this document's tab to the front in the user's editor; it no longer changes what tools default to". **Owner-only, checked at handler entry, outside the queue, never an implicit claim** (OWN-OPEN-10): on a doc owned by another live record → `NOT_OWNER {ownerLabel, ownerConnected}`; on an unowned doc → `NOT_OWNER {ownerLabel: null}` with "this document has no owner — open or write it first". A tab flip is a response in the user's eyes, so the owner does it; a UI nudge must not commit a session to a document. A race with a reassignment costs at worst one tab flip, which is why it needs no queue. Tool count, `DEPRECATED_STUBS` (`tool-count-drift.test.ts:39`), the license row (`license-gate-coverage.test.ts:84`, "tab management") and `document-tools.test.ts:283` are untouched.

In order it: updates `ownerByDoc` (stamping `since`); **resurfaces unhandled work** delivered to the previous owner on this doc (§3.5; skipped for `reason: "bind"`, where the entries are re-keyed instead, and for `"closed"`, where they become detached); records a pull-visible `ownership` entry for both records; publishes via `broadcastOpenDocs` (`registry.ts:159-190`, `withInternal`) — never an ad-hoc broadcast; and last **wakes** (§3.4b). **Record death** (grace expiry, launcher teardown) runs `setDocOwner(D, null, reason)` for each owned doc and then a record-level sweep for the doc-less and detached entries (§3.5).

#### 3.4a Serialized ownership: the per-document operation queue (Codex 2)

`runDocOp(docId, caller, fn)` appends `fn` to the document's serial promise chain and returns its result. **Every MCP mutation and every ownership change runs through it; ownership is checked inside `fn`, at its turn, not at handler entry.** The shape of a mutating handler becomes:

```
gatedTool("tandem_edit", async (args) => {           // 1. license gate — existing wrapper (license-gate.ts:65-74), before anything
  const target = resolveTarget(args.documentId);      // 2. §3.3 — registry lookup only: DOCUMENT_REQUIRED / NO_DOCUMENT here
  const parsed = validateArgs(args);                  // 3. argument shape (integers, non-empty, path shape …)
  refuseOnStaticState(target);                        // 4. READ_ONLY, format-by-extension — properties fixed since open
  return runDocOp(target.id, caller, async () => {    // 5. the doc's turn
    assertOwnerOrClaim(target.id, caller);            //    NOT_OWNER, or the implicit claim — the op's first effect
    /* existing body: range validation against the live text, the write, the file I/O */
  });
});
```

**Placement of every refusal class (OWN-Q-08).** The rule: *a refusal decided by facts fixed since the document was opened, or by the arguments alone, runs before the queue and never claims; a refusal decided by the live Y.Doc, the disk or the lock set at write time runs inside and keeps the claim.*

| Before the queue — never claims | Inside the op — keeps the claim |
|---|---|
| `LICENSE_REQUIRED` (`gatedTool`; the in-handler force gate, `document.ts:528-530`) | `INVALID_RANGE` (every `reason`, incl. `surrogate` and heading overlap), `RANGE_MOVED`, `RANGE_GONE` — read from the live text |
| `NO_DOCUMENT`, `DOCUMENT_REQUIRED` (§3.3) | `SAVE_IN_PROGRESS`, `RENAME_IN_PROGRESS` — the `savingDocs` set at that instant (`document-service.ts:385-393`, `:1358-1373`) |
| `INVALID_ARGUMENT`, `INVALID_PATH` — argument shape (schema, the newline rule, absolute paths) | `EXTERNAL_CONFLICT` — the pending-conflict flag is read at save time (`document-service.ts:421-427`); the session that tried to save is the one that will resolve it |
| `READ_ONLY` — `docState.readOnly` is fixed at open (`document.ts:727`, `:1127`, `:1266`; `tandem_save`'s read-only branch `:1375` is not a refusal, see below) | `FORMAT_ERROR` raised **by the serializer** mid-write (`document.ts:1174`, `:1462-1466`) — content-dependent |
| `FORMAT_ERROR` decided **by `docState.format`/the extension** (`document.ts:1131`, `:1273`; open-time `:565`, `:579`) | Disk I/O errors, backup failures |
| `INVALID_OWNER_HANDLE`, `OWNER_HANDLE_CONFLICT` (`bindHandle` runs before the body) | — |

So a `tandem_edit` on the read-only `CHANGELOG.md` or an `upload://` answers `READ_ONLY` and claims nothing (OWN-OPEN-07); a `tandem_comment` on the same document claims it, because annotations are its editing surface. `tandem_save` on a read-only or uploaded document is a *success* (`saved: false`, session-only, `document.ts:1354-1385`) and runs inside the op, so it claims — saving is engaging the document, and it is what a session does routinely on the doc it works on. A restricted-license session can still own a document through the ungated tools (`tandem_save`, plain `tandem_open`, `tandem_reply`, `tandem_checkInbox`, `tandem_close`, `tandem_rename`, `tandem_convertToMarkdown`) — consistent with the gate covering content writes, not coordination (OWN-LIC-02).

- **A failing request never claims.** Steps 1–4 run before the queue and touch no ownership state.
- **A failure inside the op keeps the claim.** Once `assertOwnerOrClaim` has run, the caller has engaged the document and is the session that will retry — rolling the claim back would let a second session race the retry, which is the coordination D1 exists to prevent. The response carries `claimed: true` either way. `NOT_OWNER` is not a failure of this kind: it means the claim never happened.
- **Reassignment waits for the running op and pre-empts the queued ones.** `POST /api/ownership` (or a detach-expiry release) enqueues `setDocOwner`. The op in flight finishes; `setDocOwner` runs; every op queued behind it by the old owner reaches its turn, finds `ownerByDoc` changed, and fails `NOT_OWNER` — including the old owner's own `tandem_save`. A `tandem_close` that was queued before the change and reaches its turn after it is refused the same way; the tab stays open.
- **A long-running op holds the queue for its duration, bounded by `OWNERSHIP_WAIT_MS`.** `tandem_applyChanges` (`docx-apply.ts:496-536`) and a `.docx` `tandem_save` are seconds. If the user clicks Release inside that window the route waits up to 10 s, then answers `409 busy` and the badge says "an operation is in progress — try again"; nothing is queued behind the user's back. `applyChanges`'s reload is not part of the op: it lands later through the file watcher (`docx-apply.ts:410-428`), as server-internal work outside the queue, exactly as today.
- **Hocuspocus browser edits are NOT in the queue and must not be.** They arrive as Y.Doc updates over `:3478` and interleave with an in-flight MCP op at Y transaction granularity, as today. Ownership never gates Surface A (`connection-gate.ts:12-33` gates on license only).

**Composition with the locks that exist, and why there is no deadlock:**

| Existing mechanism | Where | How it composes |
|---|---|---|
| Per-doc save lock `savingDocs` | `document-service.ts:128`; taken non-blockingly at `:385-393` (save), `:986-989` (save-as), `:1358-1373` (rename); cleared on close `:1797` | A `Set` check that answers `SAVE_IN_PROGRESS` / `RENAME_IN_PROGRESS` instead of waiting. Neither side blocks on the other, so no cycle. Autosave (`:1217`) stays outside the queue and is serialized against an MCP save by this set, as today. |
| Store lock `store.lock` | `annotations/store.ts:78`, `acquireStoreLock :175` | Process-level, acquired at boot. Orthogonal. |
| Integrations apply mutex + nonce, install mutex | `integrations/api-routes.ts:185-198`, `:223-243` | Guard config writes; touch no document. Orthogonal. **There is no `tandem_applyChanges` mutex** — its serialization is the queue's. |
| File-watcher write triple | `file-watcher.ts:370`, `:465`, `:485`, `:516` | Runs inside the save op, unchanged (`document-write-rearm.test.ts` pins the site table). |
| Reload family (watcher reload, external conflict) | `documents/reload-family.ts` | Server-internal, outside the queue; `tandem_restoreBackup` in restore mode is an MCP op and is inside it; its list mode is a read (§3.7). |
| Close path | `document-service.ts:1711-1823` | Runs outside the queue as today; the ownership hook is a synchronous map mutation plus a queue drain. |
| Supervisor lock | `supervisor.ts:1975 withLock` | Guards spawn/stop; the supervisor's ownership calls (mint, release) are synchronous map mutations that never await the doc queue. |

Every queue entry awaits only its own op's promise; no op awaits another document's queue or the supervisor lock, so the wait graph has no cycle.

#### 3.4b Waking the recipient (Codex 3, push H3)

After `setDocOwner` has made pending work available (resurfacing, §3.5) it notifies, **payload-free and never through the event queue**:

| Change | Who is woken | How |
|---|---|---|
| Assign to record R | R | A socket-local frame `{id, type: "ownership:assigned", timestamp}` on R's newest live socket (§3.10). If R is the launcher child's pinned record, additionally `supervisor.requestWake()` — a new method on the `Supervisor` interface (`supervisor.ts:308-336`) that writes `supervisorWakePrompt(handle)` through the same `sendTurn` / `turnInFlight` / `pendingWake` coalescing as `onTandemEvent`. |
| Release (to unowned) with unhandled work resurfaced | Every other attached record, and the child if it is not the loser | `ownership:available` frame on each record's newest socket; the doc is now eligible-unowned for all of them. |
| Any change away from record L (assign, release, user close) | L | `ownership:released` frame on L's socket, with the reason in the inbox entry (not in the frame). |

**Sockets that carry no `?watch=` (OWN-WAKE-08):** in Phase 1 no socket does, and every frame above goes to every attached socket — today's everyone-wakes, payload-free. **Phase 3 keeps exactly that for an unlabeled socket**: it receives every wake-worthy `TandemEvent` (as today) *and* every ownership frame, broadcast. A v25 session that armed before Phase 3 therefore still gets its Assign nudge; only a session that read a `?watch=` URL is scoped. One rule, one table, no third mode.

These three literals widen `WakeFrame.type` (`wake-scope.ts:44-48`) beyond `TandemEvent["type"]`. They never enter `pushEvent` (`queue.ts:227`), so `isWakeWorthy` (`wake-scope.ts:39-41`), the supervisor's event subscription, the SSE `?filter=wake` stream and the shim/monitor parsers (`shared/events/types.ts:117-132`, which return `null` on a type outside `VALID_EVENT_TYPES :101-111`) never see them. Pull is the backstop: the same change is in the next `tandem_checkInbox` as an `ownership` entry, so a lost wake costs latency, not correctness.

**Solo: the assignment wake is not held.** `isUserPrivacyHeld` (`queue.ts:207-217`) exists to keep the *content* of the user's own annotations from reaching a model before the user flips to Tandem. An ownership frame carries no content, is triggered by the user's own click or by a transport death, and the poll it provokes still withholds every held record (`hideFromAI`, `awareness.ts:752`, `:938`). §5.9 records this as decided on 2026-09-17.

### 3.5 Inbox: scope, delivery, claim-on-delivery, handled (Codex 1)

`tandem_checkInbox` (`awareness.ts:402-588`) today stamps the poll (`recordInboxPoll :423`), resolves the global delivery round (`:431`), drains every unread chat message and marks it `read: true` in the pass (`:485-499`, a `withMcp` write on `Y_MAP_CHAT`, `constants.ts:260`), and keys annotation surfacing on the process-global `surfacedIds` / `replySurfacedIds` (`:57`, `:71`).

**Three words, kept apart.** *Surfaced / read* means a poll returned the item (delivery). *Handled* means it was answered. The pass writes the first; the second is derived from state the answer itself leaves behind:

| Item kind | Delivered when | Handled when |
|---|---|---|
| Chat message M on an open doc D (`types.ts:655-671`) | `M.read = true` **and** `deliveredTo[M.id] = {ownerId, at, documentId: D}` | A Claude-authored message R with `R.replyTo === M.id` exists in `Y_MAP_CHAT` (persisted with the CTRL_ROOM session, `session/manager.ts:614`, `:736`) — **or** the owner M was delivered to sent any reply on D after delivery (`handledChat`, in-memory, §3.6). |
| Doc-less chat (no `documentId`; D5 makes new ones impossible) and **detached chat** (`documentId` not open — OWN-CHAT-07) | `M.read = true` and `deliveredTo[M.id] = {ownerId, at, documentId: null \| D}` | A `replyTo` reply only — there is no owned document for the same-doc rule to key on. |
| User comment / edited comment (`userActions`) | `deliveredTo["a:" + D + ":" + id + ":" + editedAt]` (this map **is** the former `surfacedIds`, plus the owner) | A Claude reply on the thread with `timestamp ≥` the surfaced `editedAt`, or the annotation is no longer `pending`. |
| User reply on a thread (`userReplies`) | `deliveredTo["r:" + D + ":" + replyId]` (the former `replySurfacedIds`) | A later Claude reply on the same thread. |
| Accept / dismiss (`userResponses`) | ledger entry as above | On delivery — there is nothing to answer. |

**The pass, in order.** The whole pass from scope resolution to the writes is synchronous — `refreshAnnotations` and `listReplies` are Y transactions, and no `await` sits between steps 2 and 6 — and the design states that as a requirement:

1. `recordInboxPoll()` — unchanged, before everything.
2. **Scope.** `documentId` given: it must be open and owned by the caller **or unowned**, else `NOT_OWNER` returned here, before any write. Omitted: the caller's owned set ∪ every unowned doc, **plus doc-less chat and detached chat in every pass** — the residual ADR-049 first-poller arbitration, now with three members. A caller owning nothing is therefore never `DOCUMENT_REQUIRED` here.
3. **Collect without writing.** For each open doc in scope: annotations through `processInboxAnnotations` in a dry mode (Solo-held records filtered by `hideFromAI :752` first — a held record is never "actionable" and never claims; neither is a note, ADR-027), replies through `collectInboxUserReplies` (`:938`), and user chat with `!read` whose `documentId` is in scope. Then every `!read` user message that is doc-less or detached.
4. **Claim on delivery.** For each *unowned* open doc D in scope with ≥1 collected item, `tryClaimNow(D, caller)`: succeeds iff D is still unowned and D's op queue is idle. If it fails — a write from another session is mid-flight and will claim at its turn — D's items are dropped from this pass unmarked. A doc with nothing collected is not claimed. Doc-less and detached items claim nothing (there is nothing to claim). An empty poll claims nothing.
5. **Write.** Ledger entries and `read: true` — only for docs the caller owns after step 4, and for doc-less and detached items; every entry records `ownerId` and `at`.
6. `resolveDeliveryRound(docsCovered)` for the docs in scope (below).
7. Return.

**Resurfacing (OWN-INB-08, OWN-CHAT-08).** Two sweeps over the delivered-to ledger, both `withInternal` for the chat flip (server bookkeeping mirrored to clients; the ctrl-chat observer skips non-browser origins, so no `chat:message` event fires and §3.4b's frame is the only notice; the client never reads the flag — `useChatState.svelte.ts:219` only writes `read: false` on send — so nothing changes visually):

- **Per document**, inside `setDocOwner(D, …)` away from record X (assign, release, detach expiry): every entry with `ownerId === X && documentId === D` whose item is not handled — chat set back to `read: false`; annotation and reply entries deleted so the next owner's dry collection returns them. Handled entries stay, so the next owner is not shown a question already answered. This includes the item that triggered X's claim, because it was delivered under X.
- **Per record**, on record death (grace expiry, launcher teardown): the per-document sweep for each owned doc, then every remaining entry with `ownerId === X` — the doc-less and detached chat X drained — set back to `read: false`. Doc-less chat drained by a session that dies now reaches the next poller.
- **Not on user close** and **not on absorb**: close leaves the entries under X as detached (X is alive and can answer); absorb re-keys them to the handle's record.
- **Why the earlier-run protection still holds:** the ledger is in memory and empty at boot, so a `read: true` message from an earlier server run has no entry and is never dragged back — the property v3 obtained from `timestamp ≥ since`, without the off-by-one-batch. **Restart residual (OWN-INB-10, known limitation):** an item delivered but unanswered when the server restarts is lost to resurfacing — `read: true` is persisted, the ledger is not, and re-flipping every `read: true` message with no `replyTo` at boot would re-deliver every message ever answered without one. The user re-asks, as today.

**Delivery rounds** (`delivery-state.ts:86 pendingSince`, `:164-179 resolveDeliveryRound`, `:189-200 recordWakeForward`): `pendingSince` becomes a map keyed by `documentId` (doc-less and detached events use a `"*"` key). `recordWakeForward(now, docId)`; `resolveDeliveryRound(now, docsCovered)` closes only the rounds the pass covered. `/health` reports the oldest open round. Phase 1, because the filtered inbox alone makes the global round false.

**Solo.** `hideFromAI` drops held records before collection, so a held annotation never claims; chat is not held and does. On the Solo→Tandem flip `emitModeReleaseWake` (`queue.ts:484-496`) wakes everyone, the held records become collectable, and the first poll that returns them claims — the same rule, no special case.

**Output shape.** `userActions` / `userResponses` / `userReplies` / `chatMessages` items carry `documentId` (absent for doc-less; present-but-closed for detached, with `documentOpen: false`); a new `ownership: {released: [{documentId, reason}], assigned: [...], claimed: [...]}` field lists changes affecting the caller since its last poll, including the docs this poll just claimed. `checkInboxOutputShape` and `mcp-output-schemas.test.ts:403,451,482` change.

### 3.6 Chat send and reply routing (Codex 6)

- **Send: D5.** `ChatMessage.documentId` stays optional in the type for legacy records. The disabled button carries `title`/`aria-label` "Open a document to chat — messages go to the session working on that document".
- **Reply — `tandem_reply({text, replyTo?, documentId?})` (`awareness.ts:589-610`), resolved deterministically:**
  1. `replyTo` given → look up the message in `Y_MAP_CHAT`; unknown id → `INVALID_ARGUMENT`. If the message carries `documentId` D **and D is open**: an explicit `documentId ≠ D` → `INVALID_ARGUMENT` ("replyTo belongs to another document"); the target is D, the reply is a responding write on D (queue, claim if unowned, `NOT_OWNER` if foreign-owned), and on success M is handled. **If the message is detached (D not open — OWN-CHAT-07)** or doc-less: the reply is stamped with M's own `documentId` (or none), runs no queue and no ownership check — there is no document to own — and on success M is handled. An explicit `documentId` on a doc-less message targets that doc with the ownership rule, as v3.
  2. No `replyTo` → explicit `documentId` if given (must be open, else `NO_DOCUMENT`; ownership rule); else the §3.3 fallback (single owned doc, else single open doc); else `DOCUMENT_REQUIRED`. **A failed resolution is an error, never a silent global send.**
  3. Any successful reply on an open doc D by owner X marks every chat message on D delivered to X before now as handled (`handledChat`), so a model that answers three questions with one message and no `replyTo` leaves nothing to resurface.
  4. The reply is stamped with the resolved `documentId` **and with the sender's `ownerLabel`** — a new optional `ChatMessage.ownerLabel` field (`types.ts:655-671`), written by `appendClaudeChatMessage` (`awareness.ts:194-218`, `withMcp`, `Y_MAP_CHAT` from constants) in **Phase 1** and rendered in Phase 2 (OWN-UPG-06). A label is a public per-run id, not token-derived, so §3.7's "no token-derived data reaches a Y.Map" holds; the field persists with the CTRL_ROOM session like every other chat field. ### 3.8 Restart and the launcher (Codex 7, OWN-LCH-09, OWN-LCH-06)

- Restart drops every record; restored docs are unowned and badged.
- **The launcher child is identified by a supervisor-minted handle, one per child run, named on every turn.** There is no resume turn (`supervisor.ts:1452-1463`: `SUPERVISOR_INITIAL_PROMPT` only when `!plan.resuming`), and the child's MCP entry is direct-HTTP (`apply.ts:512`), so neither a header nor an env var reaches the server from it. What *does* reach the child on every turn it ever runs is the supervisor's stdin prompt (`:1433-1439`). So: `spawnOnce` mints `handle` beside `spawned` (`:1157-1165`), registers a pinned `handle` record with `cwd = plan.cwd`, and the prompts become builders — `supervisorInitialPrompt(handle)` and `supervisorWakePrompt(handle)` in `contract.ts` (replacing the constants at `:322-325` and `:338`; the no-arm clause `:310-312` is unchanged).
- **The handle rides the first call, whatever it is.** Both builders open with the handle, not close with it: *"Your Tandem owner handle for this run is `th_…`. Pass it as `ownerHandle` on your **first** Tandem call this turn, whichever tool that is — `tandem_status`, `tandem_open`, `tandem_scratchpad` and `tandem_checkInbox` all accept it — then call `tandem_checkInbox({ownerHandle})` to see what needs attention."* SKILL v25 Workflow step 1 (`SKILL.md:35`) gains: *"If the turn that started you named an `ownerHandle`, pass it here — and on whichever Tandem call you make first."* A child that follows SKILL step 1 and calls `tandem_status({ownerHandle})` binds there; one that opens first binds there. **A child that binds late** — one that opened or wrote before presenting the handle — is the absorb row of §3.2: its fresh `mcp:` record's docs move to the handle's record, and they release on exit like everything else it owns. Only a child that never binds at all leaves docs on an unpinned record (below).
- **The bootstrap turn names the document (OWN-LCH-06).** `supervisorInitialPrompt` replaces `:323-324`'s "A document has been opened in Tandem for review" with: *"Tandem has documents open for review. `tandem_listDocuments` lists them; `isActive` marks the one in front of the user. Pass `documentId` explicitly whenever more than one is open."* — because the active-doc default is gone and a bare `tandem_getOutline()` on a multi-doc restore answers `DOCUMENT_REQUIRED`.
- **Invalidated on exit.** `teardownTurnDelivery` (`:1410-1429`) releases the record — its docs become unowned, its delivered entries are swept (§3.5) — on `exit`, `error`, `stop()` and relaunch. A same-run crash-resume gets a **new** handle with the next spawn; it re-claims by being delivered the work (the owed wake crosses spawns via `wakeOwedAcrossSpawns`, `:1422`, `:1464-1468`) — no ghost owner and no inherited group.
- **It cannot loop, verified against the supervisor.** Every turn the child runs is started by one of four supervisor writes, all carrying the live handle: the bootstrap turn (`:1456`), the owed wake on a resumed spawn (`:1468`), the event wake (`:1395`) and the deferred wake (`:1381`); `sendTurn` (`:1323-1371`) is the only writer. A stale handle errors once with no side effects; the next call with the handle from the most recent turn succeeds.
- **Known limitation, unchanged.** A child that responds to the error by calling with *no* handle, and never binds, runs as an ordinary `mcp:` record and may claim unowned docs under it; those release on transport death, not child exit. The error text tells it not to; the server cannot tell a launcher child from any other direct-HTTP client.
- **Phase 1 does not pre-claim.** The child owns what it is delivered or responds to.
- `launcher-session.json` is unchanged; the handle is never written there. Tests pinning the prompt constants (`tests/server/launcher/{supervisor,stream-json-protocol,supervisor-turn-delivery}.test.ts`) change from constants to builders.

### 3.10 Push paths (D3 — one watch per session; OWN-SEC-05, OWN-WAKE-09)

| Path | Design |
|---|---|
| **Self-armed `ws` wake** | Every `wakeUrl` producer (`WAKE_URL_PRODUCERS`, `wake-url.ts:44`) returns `ws://127.0.0.1:<port>/api/wake?watch=<watchId>` — the caller's record's **watch id**, never its label. **`watchId = base64url(HMAC-SHA256(runSecret, ownerId))[0..22)`**, `runSecret` random per server run: derivable by the server from any record without storage, unguessable to anyone without the secret, and the **same for a record re-created for the same `ownerId`** — a `claude:` or `bridge:` record that came back after the grace keeps the socket it armed. `ownerIdByWatch` is populated at record creation; `watchAlias` (below) overrides it. **One socket per session.** For every event the server resolves the socket's record **at dispatch** — `resolve(watch) = records.get(watchAlias.get(watch) ?? ownerIdByWatch.get(watch))` — and applies: no `documentId` → deliver; doc unowned → deliver; doc owned by this record → deliver; doc owned by another record → drop. A socket with no `?watch=` receives everything (Phase 1 semantics, §3.4b). **A document newly assigned to a session is covered with no re-arm.** **Bound per watch id:** at most `MAX_SOCKETS_PER_WATCH = 2`; a third arm closes the oldest (close code 4000, reason `replaced`). **Each event is delivered to the newest live socket of a watch id only**, so one session gets one wake per event whatever its reconnect overlap; the older socket exists to survive a Monitor reconnect and is reaped by the heartbeat (`wake-socket.ts:265-278`) or the next arm. **Because the id is unguessable, newest-wins is no longer a hijack primitive** (OWN-SEC-05): a local caller that reads a label from `tandem_listDocuments` or `Y_MAP_OPEN_DOCUMENTS` (`constants.ts:300`) cannot derive the watch id; it can only arm an unknown id, which owns nothing. The global cap stays `MAX_WAKE_CONSUMERS = 16` (`:75`), unraised. **The `SKILL.md:116` stand-down heuristic keeps its meaning:** a doubled wake again means a *second consumer*. Frames stay `{id, type, timestamp}` (`wake-scope.ts:78-80`); **`documentId` is in neither the frame nor the URL** (ADR-049 D2). Hygiene (security F5, now for `?watch=`): validated against `^[A-Za-z0-9_-]{1,64}$`; an unknown id is accepted silently and treated as owning nothing (no oracle); never logged (`:209` and `:257` stay URL-free; `log-sanitize.ts` redacts the pattern if anything else ever logs a URL) nor shown in diagnostics beyond counts; three pinned tests. |
| **Label stability and socket follow-through (OWN-WAKE-09)** | Three paths re-created or switched a caller's record in v3 and left its socket blind. The socket is evidence of attachment (it dies with the process — TCP close, or the heartbeat), not of use, which is the same distinction #1588 drew. **LRU eviction stays pin-blind, on purpose** (CLAUDE.md), so the residual is: a direct-HTTP session evicted by the 16-session cap re-initializes under a new `ownerId`, and its once-armed socket still receives unowned-doc and doc-less events but is dropped for the docs it re-claims. **Known limitation**, bounded by `DEFAULT_MAX_SESSIONS` (`:137`) and by the pull path the skill already mandates every 2–3 calls; SKILL's "arm at most once per session" (`:99`) is not touched for it. A record's sockets are **not** closed on detach expiry: a Monitor can outlive its MCP transport, and a socket resolving to no record still receives unowned-doc and doc-less events, which is how that session re-claims by polling. The three ownership frames (§3.4b) are emitted socket-locally from `wake-socket.ts`, never through the queue. |
| **`#1952`, per request (OWN-SEC-07)** | `wakeUrlField()` (`wake-url.ts:55-58`) returns nothing when `getMcpContext()?.peerIsLoopback === false` (§3.2) — the calling peer, not the bind. - **B:** hold it like a user annotation, delivered on the next routine poll.
- **Decided (2026-09-17):** A, as recommended (§3.4b). B leaves the user's own Assign inert until the recipient happens to poll.

### 5.10 Absorb a pre-bind record on handle bind, or refuse it (new — narrows Codex 7)

- **A (this design):** when a transport presenting a handle sits on a **never-bound, single-transport `mcp:` record** that already owns documents, the bind succeeds and those documents move to the handle's record (§3.2). This is the launcher child that opened or wrote before its first `checkInbox`; absorbing is what makes child exit release them.
- **B (Codex 7 as written):** `OWNER_HANDLE_CONFLICT`; the child must `tandem_close` its own claims (releasing them to the first poller — itself, usually — under a record that never releases on exit) or keep two identities.
- **Evidence:** the SKILL v25 ordering fix (§3.8) makes this rare, not impossible — a child that skips its prompt and follows an older habit still lands here. The narrowing is bounded: a record with two transports, one bound from a handle, or of any other kind still conflicts, so no *second session's* group is ever merged — only the presenting transport's own fresh claims. A document Bryan **assigned** to the pre-bind label moves with the rest and its badge changes label; that is the same process under its correct name.
- **Decided (2026-09-17):** A, as recommended.

### 5.11 A live wake socket pins its transport against the idle reaper (new — touches #1588)

- **A (this design):** in Phase 3, a wake socket whose `?watch=` resolves to a record pins that record's transports against `reapIdle` exactly as an open `GET /mcp` stream does; LRU eviction stays pin-blind.
- **B:** no pin; an armed direct-HTTP session idle for 30 minutes is reaped, re-initializes under a new identity, and its socket goes blind for the docs it re-claims (OWN-WAKE-09 path 3 becomes a permanent known limitation instead of a bounded one).
- **Evidence:** the reaper's own rationale (`transport-registry.ts:233-239`) is that idleness cannot tell "vanished" from "attached but quiet"; a socket that dies with the process is the same evidence a stream is. Cost: the "sessions accumulate" failure mode the pin already has, still bounded by `maxSessions`; the pinned-skip log line (`:251-259`) covers it. Whether a Monitor socket reliably closes when Claude Code exits on each OS is `needs-human-evidence`; the heartbeat (`wake-socket.ts:265-278`) bounds a stale pin to one keepalive interval past a dead peer.
- **Decided (2026-09-17):** A, as recommended.

### 5.12 What the Assign list shows, and renaming sessions (bounds security F6)

- **A + rename (Bryan's decision, 2026-09-17):** nickname else label · kind · client name (`clientInfo.name`) on every doc entry and in the loopback-only owners list, with the label always beside a nickname in the popover; Bryan renames a session from the popover and a session may name itself with `tandem_status({nickname})`; `cwd` never published (§3.11).
- **A without rename (v4's recommendation):** the same, minus nicknames — two terminals in different repos then read identically.
- **B:** label only (v3), with the user told to ask each session for its label.
- **C:** A plus the cwd basename, so two terminals in different repos are distinguishable.
- **Evidence:** kind and client name are static per record and carry no timing — the presence bit stays `ownerConnected` alone (§6). The cwd basename is a project name, which under a non-loopback bind would reach a remote bearer holder on every doc entry; two terminals in different repos are the D2 headless-per-directory case, which is Phase 4's problem and where C would come back with the cwd already on the record.
- **Decided (2026-09-17):** A plus session rename. Rename answers what C was for — telling two terminals apart — without publishing a project name on every doc entry, which under a non-loopback bind reaches a remote bearer holder. A nickname is still a published string with the same exposure as the client name; the difference is that Bryan (or the session) chooses its contents, and `SKILL.md` tells a session to name the task rather than the directory (§6).

## 6. Security posture

- **Ownership is a low-grade coordination capability, not an auth boundary.** `auth/middleware.ts:164-165` bypasses bearer auth for loopback callers, so locally there is no auth at all; every local process already holds every write. A leaked owner handle lets a local caller act as that session — silent writes, an inbox drain — which any local caller could do by binding its own record and claiming. Mitigations that are cheap and taken: handles are minted only on request (`issueHandle: true`) and per launcher child run; they die with their record; they are redacted by `log-sanitize.ts`; an invalid handle has **no side effects** and a conflicting one never merges another session's group (the §5.10 absorb moves only the presenting transport's own claims). **Handle-scrub tool set (OWN-SEC-06):** any argument that is persisted or synced is refused with `INVALID_ARGUMENT` when it contains a live handle or a live watch id — `tandem_reply.text`; `tandem_comment.text` and `.suggestedText`; `tandem_editAnnotation`; `tandem_annotationReply`; `tandem_edit.newText`; `tandem_appendContent`; `tandem_editList`; `tandem_scratchpad.content`; `tandem_rename.newName`; `tandem_status.text` and `.nickname`. The check compares against the live set, never the pattern, so an expired handle-shaped string is not refused (no oracle). `CTRL_ROOM` chat is persisted (`session/manager.ts:614`) and synced to every client, which is why chat is on the list.
- **The watch id is a second capability of the same class (OWN-SEC-05).** It gates *which wakes a socket receives*, nothing else; a holder can absorb a session's wakes (silent DoS, the `#1952` class) but cannot read, write or drain anything the pull path would not show it — and pull is authoritative. **Where it is exposed:** in the `wakeUrl` of the session's own tool responses, hence in that session's transcript, and in the `Monitor` tool's arguments — the same places the unlabeled `wakeUrl` appears today. A process that can read Bryan's transcript files is a local process, and a local process already holds every write (`middleware.ts:164-165`); a page on an allowlisted `127.0.0.1:<port>` origin can open a wake socket but cannot read a transcript, so it can arm only an unknown id, which owns nothing. It is never logged server-side (`wake-socket.ts:209`, `:257`); `log-sanitize.ts` redacts the pattern. The residual — a transcript-reading local process silencing one session's wakes — is recorded here as accepted-by-design, not fixed: closing it would need a credential the Monitor ws source cannot send (no headers) or a nonce per connection, and the earlier reviews already rejected a credential in a logged URL for exactly this exposure. The id is strictly better than the public label v3 used.
- **Bypasses, stated plainly:** a session refused `NOT_OWNER` and holding Bash can `curl` `POST /api/save`, `/api/apply-changes`, `/api/close`, `/api/remove-annotation`, `/api/annotation-reply`; `POST /api/channel-reply` (`channel-routes.ts:130-143`) takes a caller-chosen `documentId` and is a `NON_LOOPBACK_ALLOWED` carve-out. None of these is ownership-gated, by design. `SKILL.md`'s refusal guidance names the tab's owner badge and Assign, and never `/api`.
- **Takeover and lockout:** removed. A hostile local MCP client can claim only unowned docs; it cannot displace a live owner; the user's Release/Assign is authoritative, ships in Phase 1, and is not reachable over MCP. **Release alone re-opens the first-poller race** (OWN-SEC-02) — a rogue client that grabs on delivery can grab again — so the badge copy and the refusal text steer to Assign when a specific session should have the document. The ownership frames never enter the queue, so they cannot wake anything through `isWakeWorthy`.
- **Presence and the descriptor (F6, OWN-CTL-06):** `ownerConnected` boolean only; labels are random, not ordinal; `ownerKind` and `ownerClient` are static per record and add no timing information — they say what kind of client owns a document, not when it was last active; `cwd` is never published (§5.12). The **enumeration** of attached sessions lives only behind `GET /api/ownership/owners`, which checks `req.socket.remoteAddress` in-handler and never crosses the LAN. The record map is never returned by `tandem_status` (own record only) or `tandem_diagnostics` (counts only). Under Cowork a remote bearer holder learns, per open document, that it is owned, whether that owner is attached, and that the owner is e.g. a `terminal` running `claude-code` — one static word beyond what `/health`'s `hasSession` already gives. The ≈32-minute bound (§3.2) is a liveness fact, not a leak. **Nicknames (v4.1)** are published the same way: a session may put a project or file name in its own nickname, so under Cowork that string reaches a remote bearer holder — `SKILL.md` tells a session to name the task, and a name Bryan sets is his own. A nickname changes only when someone renames the session, so it adds no timing; it cannot be mistaken for a label, because the label pattern is refused and the popover prints the label beside it.
- **Loopback rules:** unchanged. `/api/wake` keeps `verifyWakeUpgrade`'s `remoteAddress` check (`wake-socket.ts:118-140`, fed at `:181`). No new `NON_LOOPBACK_ALLOWED` entry. `/api/ownership` (POST) is non-GET, so loopback-only by the path-wide invariant, and carries `assertOriginAllowlisted`; the GET checks loopback itself.
- **Cowork and `#1952`:** addressed in Phase 1, **per request** (§3.10): only a non-loopback peer loses `wakeUrl`; a local session under a Cowork bind keeps it (OWN-SEC-07). **Unwoken remote owner, documented:** a remote session cannot arm the wake socket (`:133`) but can own docs; the local launcher child will not respond to them (D1), so the user's items wait for the remote session's own poll. The tab badge shows the remote label and the user can Release or Assign. Bound: non-loopback binds only.
- **`?watch=`:** hygiene in §3.10; three pinned tests (no log, charset/length, no oracle). `?owner=` and `?doc=` no longer exist.
- Register entries: none new. Once Phase 1 ships, `#1952` moves from *open* to the register's *fixed* column, and its "per-request loopback detection is not available inside a tool handler" sentence is corrected, in the same sequencing as the other `docs/security.md` edits (§8) — the register's own label for an implemented change, not a status this document claims.
